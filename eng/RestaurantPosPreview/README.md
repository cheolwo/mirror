# 음식점 PC POS 합성 화면 검토

`RestaurantDeskApp`의 실제 주문 목록·상세 Razor, 상세 처리 코드, POS 표시 정책, MainLayout·탐색 및 CSS를 source-link한다. 이 호스트가 소유하는 것은 합성 검토 푯말·시험 제어와 메모리 fake ports뿐이다. 운영 인증·서버·DB·실배차·결제·알림음·물리 인쇄는 사용하지 않는다. MAUI 운영체제 생명주기와 Windows 실제 실행은 별도다.

PowerShell에서 `$env:ASPNETCORE_ENVIRONMENT = 'Development'`를 지정하고 저장소에서 `dotnet run --project eng/RestaurantPosPreview`로 실행한 뒤 `http://127.0.0.1:5371/orders`를 연다. Development와 loopback 접근만 허용한다. 각 브라우저 circuit의 자료는 독립이며 새로고침·재시작 후 초기 자료로 돌아간다.

상단 `검증 제어`에서 시험 주문을 선택한다. 화면의 `주문 수락` → 검증 제어의 `기사 배정` → 화면의 `조리 시작` → `픽업 준비 완료` → 검증 제어의 `기사 픽업 확인` 순서로 본다. 기사 배정과 픽업은 음식점 권한 버튼이 아니라 합성 외부 신호다. 픽업 확인을 배송 완료로 바꾸지 않는다.

`신규 주문 추가`는 선택과 입력 보존을, `조회 실패/조회 복구`는 마지막 표시와 작업 잠금·명시적 복구를, `인쇄 요청 실패`는 수락 성공과 출력 실패의 분리를 확인한다. 조리 버튼은 합성 상태에 맞는 `AvailableActions`로만 제공하며 서버 정책 자체를 시험하는 호스트는 아니다.

실제 개인정보·사진 속 주문·점포·주소는 seed에 포함하지 않았다. 각 상품 단가×수량과 주문 합계는 일치한다. 상세 취소 합의·설정 등 이번 범위 밖의 목적지나 API는 실제 연결하지 않았다.

`/viewport/390`, `/viewport/320`은 동일 호스트의 주문 화면을 지정 폭·높이840px iframe으로 보여준다. 두 폭만 허용하며 임의 URL·폭은 받지 않는다. IAB 창 안의 실제 좁은 CSS viewport 검토이며 APK·기기 검증은 아니다.
