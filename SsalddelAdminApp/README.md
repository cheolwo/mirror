# 관리자 모바일 음식 운영

## 로그인·갱신·다시 조회의 수명 (2026-11-05)

관리자 로그인과 토큰 갱신 뒤 원래 업무를 다시 조회한다. 새 로그인·로그아웃 이후 도착한 이전 인증 응답과 업무 응답은 현재 계정에 적용하지 않는다. 같은 계정의 새 로그인도 구분하며, 정상 갱신은 진행 중인 최신 로그인 의도를 취소하지 않는다. 로그인 시작만으로 기존 인증을 지우지 않는다.

앱을 처음 열어 저장된 인증을 읽거나 갱신을 기다리는 중에도 같은 기준을 적용한다. 대기 중 로그아웃·계정 변경이 있으면 이전 요청을 중단하고 현재 계정으로 다시 조회하도록 안내한다.

현재 USB 목록에 기기가 없다(r52). 등록 휴대폰 연결과 디버깅 승인이 확인되면 설치판을 대조하고 같은 합성 주문의 요약·이력 펼침·목록 복귀를 이어간다. 재개 근거는 `artifacts/local/app-resume-r52/f000a6bae3034c4f921faa4f6dfbd310/run-status.json`다.

등록 기기의 일반 잠금을 해제했다(r50). 배민커넥트 인증 안내가 없는 상태에서 현재 검토 APK를 대조하고 같은 주문의 요약·이력 펼침·목록 복귀를 확인한다. 재개 근거는 `artifacts/local/app-resume-r50/2362674f119a476f8157abba0c3b6ae1/run-status.json`다.

재부팅 뒤 검증 환경을 재개했다(r49). 기존 볼륨과 격리 DB에서 환경 읽기 8개와 같은 합성 주문·실행 원장 조회 2개를 확인했다. 당시 휴대폰은 잠금 화면에서 대기했다. 기기 사용 조건과 현재 검토 APK를 대조한 뒤 같은 주문의 요약·이력 펼침·목록 복귀를 확인한다. 재개 근거는 `artifacts/local/app-resume-r49/eed14ec6d3dd440a8311d18a68363f8f/run-status.json`다.

이전 재개 확인(r48)에서도 등록 기기·기존 관리자 설치 바이트는 일치했지만 전면 배민의 인증 입력 화면을 보존했다. 기기 입력·전환·설치·새 APK/제품 시험은 없다. 같은 소유 Simulation·격리 DB의 ready/참여 요약/run·DB와 SQL4·Mongo ping은 독립 읽기1회/8확인 정상이며 실제 서버 풀과 과거503 원인을 해결한 것은 아니다. 현재 재개 근거는 `artifacts/local/app-resume-r48/bd0a150bfddd45d7b650edce5c8af8bd/run-status.json`이며 이전 r29/r33/r36/r40와 r43 읽기 점검 기록도 보존한다. 관리자 현재 화면·인증·목록 복귀는 계속 대기한다.

Session은 기존 일곱 장치 저장 키로 상태·저장·복원을 직렬화하고, 인증 Service는 해당 문맥의 로그인/refresh만 반영한다. API Client는 원 계정과 고정 요청 토큰을 유지하며 정상401의 동일 요청 한 번 재전송을 보존한다. 연결 오류나 결과가 불명확한 명령은 자동 재송신하지 않는다.

[인증 연속성 보완·실행 근거와 기기 미확인 범위](../docs/Changes/2026-11-05-admin-authentication-continuity-r26.md)를 따른다. 자동시험의 메모리 장치 저장소와 실제 휴대폰 SecureStorage는 별개이며, r25의 준비138은 이후 인증 변경을 포함하지 않는다.

## 주문 상세의 요약·이력 읽기 (2026-11-05)

한 음식 주문의 현재 상태·다음 담당·확인 시각과 필수 경고를 먼저 읽는다. 기사 정산의 수령액/미확정·배달료 확인 필요·공제 미확정·지급 재원/실제·테스트 구분·보류 이유도 기본으로 표시한다. 확정된 금액 구성은 ‘정산 세부 내역’에서 확인한다.

현재 진행 단계는 서버가 정확히 ‘완료’로 표시하지 않은 항목이다. 진행/대기·주의/복구 필요·종료/해당 없음·미지원 상태는 그대로 기본에 남기고, 완료 단계만 이력에서 펼친다. 각 그룹의 원래 순서와 기존 원장 동기화 제외는 유지한다. 같은 주문/계정의 펼침과 재조회, 다른 주문/계정의 표시 초기화를 구분하며 펼침으로 업무 명령을 실행하지 않는다. 로그인·중단 검토·목록 복귀는 기존 경로를 따른다.

[변경·현재 검증과 실제 기기 확인의 경계](../docs/Changes/2026-11-05-admin-order-summary-r1.md)를 따른다. 기존 시안·과거 캡처는 새 관리자 앱 실행 근거가 아니다.

이 앱의 음식 운영 보완은 운영자가 한 음식 주문의 진행과 중단 검토 결과를 확인하는 책임을 맡는다. [페이지 단일 책임](../docs/Architecture/WholeRoadmapPagePrinciple.md)과 [역할 앱 시각 기준](../docs/Architecture/RoleAppVisualDesignStandard.md)을 따른다.

음식 목록은 고객 주소·연락처·원시 payload 없이 주문번호·음식점·진행 상태·시각만 반환한다. 목록 GET, 기존 operations-trace와 interruption-review는 서버관리자 권한과 FoodDeliveryWorkflow를 따른다. APK의 기본 홈은 업무 진입 허브이며 다른 도메인의 API를 미리 호출하지 않는다. 화물 OFF가 음식 목록/상세를 차단하지 않고 음식 OFF도 화물 진입 자체를 차단하지 않는다.

적용된 검색과 입력이 같고 조회가 성공해 검색 결과가 0건일 때 **검색 지우고 전체 보기**를 표시한다. 누르면 기존 관리자 목록 조회의 검색어 없는 첫 페이지를 연다. 미제출 입력, 조회 실패, 로그인 필요와 검색어 없는 빈 목록은 각자의 기존 안내를 따른다.

상태·가능 행동의 정본은 서버다. 조회가 성공한 같은 주문/계정에서만 검토한다. 상태를 조회했다고 조리·배차·검토·지급을 자동 실행하지 않는다. 정산은 실제/모의/미확정을 서버 값대로 구별하고 이 화면에는 지급 실행 기능을 섞지 않는다.

업무 조회의 오류는 정형 응답의 `detail`·`message`·`title` 순서로 표시한다. 그런 안내가 없는 HTML·일반 문자열·불완전한 JSON은 원문 대신 “관리자 요청을 처리하지 못했습니다.”로 안내하며 HTTP 상태와 업무 오류 코드는 보존한다. 실패를 정상 빈목록으로 바꾸거나 자동 재전송하지 않는다. 인증 만료와 기능 미활성 안내는 기존 구분을 유지한다. 관련 경계는 `Services/AdminAuthenticatedApiClient.cs`, 음식 목록의 명시적 재조회는 `Services/AdminFoodOperationsService.cs`에서 확인한다.

페이지 → AdminFoodOperationsService → 음식주문운영추적Controller → 음식주문운영추적UseCase/음식배달중단검토UseCase → 음식주문/배차/배달시도/기사정산 원장으로 연결한다. 검토 상태는 공용 FoodDeliveryInterruptionReviewState를 웹·모바일이 같은 의미로 소비한다. 계정이 바뀌면 표시와 진행 중 요청을 폐기하고 로그인 복귀 후 정본을 조회한다.

검증은 코드/관련 시험, 격리 API·DB, 실제 Android APK, 공개 HTTPS·개인 휴대폰을 분리한다. 이번 보완의 원본/지문과 실행 근거는 Git 제외 artifacts/local/azure-mobile-hardening-r1/admin/에 보관하며 통합 검증은 총괄 작업에서 수행한다.
