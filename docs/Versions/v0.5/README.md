# 문화교통 0.5

## 목표

문화교통 `0.5`는 **개별주문과 개별 원장** 단계입니다. 사용자가 `0.0`의 공개 음식·재료 근거에서 상품을 고른 뒤, 본인의 상품·수량·수령 조건과 철회 가능한 주문 의향을 다른 사람의 주문과 섞지 않고 관리합니다.

## 핵심 흐름

```text
0.0 공개 음식·재료 근거
  → 상품과 수량 선택
  → 수령 권역·시간·보관 조건 확인
  → 철회 가능한 개별주문 의향 저장
  → 본인 소유 개별 원장 재조회
  → 수정·철회 또는 단독 유지
  → 같이 주문 참여에 동의한 경우에만 1.0 같이 주문 후보로 인계
```

## 원칙

- 개별주문은 한 사람의 원장이며 같이 주문 참여와 분리합니다.
- 저장 성공 뒤 같은 stable ID의 원장을 다시 조회합니다.
- 수정과 철회 이력을 남기고 철회한 원장은 1.0 집계에서 제외합니다.
- 같이 주문 참여 동의는 별도 상태이며 기본값은 미동의입니다.
- 개인의 상세 주소·연락처·결제 정보는 공개 원장이나 공동 집계에 포함하지 않습니다.
- 개별 원장은 결제, 매매 계약, 재고 예약, 배송 확정 또는 수입 신고가 아닙니다.
- `0.0`의 원자료 출처, 기준 시각, 단위와 한계를 주문 문맥에서도 보존합니다.

## 1.0 인계

`1.0`은 개별주문 원본을 복제하지 않습니다. 같이 주문 참여에 동의했고 철회되지 않은 stable 개별 원장 ID와 집계에 필요한 최소 조건만 참조해 같이 주문 후보를 만듭니다. 한 개별 원장은 같은 같이 주문 원장에 중복 포함될 수 없습니다.

## 실행 경계

현재 저장소의 일부 개별 원함 API는 기존 `GroupPurchaseDemandWorkflow` 안에서 1.0 집단화와 함께 동작합니다. 0.5의 독립 활성화 전에는 [0.5 checklist](checklist.md)에 따라 개별 원장 저장·수정·철회와 1.0 집단화 Command 경계를 분리해야 합니다.

## App 역할

- `SsalddelApp`은 `/community`에서 시작해 0.0 정보 탐색과 0.5 개별주문 진입·간단 조회·철회를 담당합니다.
- `OrdererApp`은 같은 본인 원장에서 수량 수정, 상세 조건, 같이 주문 후보 진행을 업무 관점으로 관리합니다.
- 두 App은 원장을 복제하거나 화면 간 임의 값을 전달하지 않고 같은 API·contract·ViewModel 경계를 사용합니다.
- 현재 호환 workflow에서는 같이 주문 후보 미리보기 뒤 별도 참여 동의를 해야 저장할 수 있습니다. 개별 원장만 먼저 저장하는 완전한 독립 상태 전이는 release gate로 남아 있습니다.
