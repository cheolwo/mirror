# 문화교통 1.5

## 목표

문화교통 `1.5`는 **공급·가격·무역 준비** 단계입니다. `1.0`에서 확인된 수요와 개별 주문에 국내외 공급자·구매자 근거, 견적, 원가, HS·HTS 후보와 수입·수출 준비 체크포인트를 연결해 문화와 재료가 실제 이동하기 전에 사람이 확인할 질문을 닫습니다.

## 핵심 결과

- 출처와 확인 시각이 있는 공급자·기업 후보
- 통화, 단위, 최소수량, 유효기간이 명시된 견적
- 상품 원가, 예상 관세·세금·국제 운송비와 국내 이행비를 분리한 예상 총원가
- 재료·상품과 연결된 HS·HTS 후보 및 검토 근거
- 판매자, 수입자·수출자, 관세사·무역 검토자, 운송 수행자와 플랫폼의 책임 초안
- 실제 계약·신고 전 준비 완료 여부와 미확인 항목

`1.5`의 자료는 의사결정 지원 정보입니다. 전문 품목분류, 수입 적격성, 수출 요건·전략물자 판정, 식품 규제, 신고 대행과 계약 판단을 자동 확정하지 않습니다.

수입 준비는 하나 이상의 `group-purchase` 수요 집단을 기존 정식 `group-import` 원장에 연결하고 공급·가격·무역 준비와 포워더 인계·회신을 그 원장의 블록으로 저장합니다.

수출 준비의 권장 여정은 `수출 교류장 → 당사자의 별도 주문 동의 → order → individual-export`입니다. 수출 교류장은 기존 커뮤니티 게시글·비구속 관심·가원장을 조립하고 마음이나 관심을 점수화하지 않습니다. 이미 당사자가 직접 합의한 주문은 교류장 없이 시작할 수 있으며, 교류가 있더라도 주문 원본을 복제하거나 대신하지 않습니다. 여러 수출 건을 같은 집하·합포장·포워더 인계 단위로 조율할 때에는 `group-export → individual-export[]` 관계를 사용하며, 수출자별 신고·서류·적재 실적을 공동 원장으로 합쳐 덮어쓰지 않습니다. 세부 모델은 [개별수출·공동수출 원장](../../Architecture/ExportLedgerModel.md)을 따릅니다.

## 구현 흐름

```text
하나 이상의 1.0 승인후속대기 수요 집단·재료
  → 공급자·기업 원출처 근거
  → 견적·MOQ·납기·포장·Incoterms 후보
  → 상품·국제운송보험·관세·세금·국내이행 예상비
  → 한국 HSK 또는 미국 HTSUS 후보
  → 국가별 규제 검토와 책임 초안
  → 최소 정보 포워더 인계
  → 포워더 LCL/FCL·견적·일정 회신
  → 자격 있는 전문 검토자 인계 가능 상태

수출 교류장(선택)
  → 문화·사용 경험, 서로의 원함, 상호 이익·기여와 비용·노동·위험
  → 비구속 관심
  → 연락처 공개와 분리된 주문 제안·조건 동의
개별주문
  → 개별수출 확장
  → 수출자·해외 구매자·B2B/B2C 문맥
  → HS·원산지·Incoterms·전략물자/목적국 요건 근거
  → 신고 방식·수리·적재기한
  → 사람의 포워더 인계와 선적 실적 기록
  → 필요 시 여러 개별수출을 공동수출 원장에 물류 집계
  → 완료 뒤 별도 동의가 있을 때만 비식별 경험·편익을 교류장에 환류
```

## 1.5 OS

`GroupPurchaseImportOS`는 같이 수입 원장을 직접 확정하는 엔진이 아니라, 기존 원장의 1.5 준비 블록과 규칙을 읽어 다음 작업을 조율하는 독립 OS입니다.

- 상태: `자료 수집 중 → 근거 재확인 → 사람의 포워더 인계 대기 → 포워더 회신 진행 → 전문 검토 인계 후보`
- 내부 작업: 다중 재료 수요 묶음, 공급자 근거 최신성, 견적·예상 총원가 유효성, HSK·HTSUS·국가별 규제 검토, 책임 초안과 사람 handoff 점검
- 공유 입력: 기존 1.0 OS에 등록된 KAMIS 일·월 가격, USDA NASS 월 가격, 공식 기업 근거와 커뮤니티 가격 브리프 Quartz 작업
- 운영 방식: 정기 worker 점검과 관리자 수동 점검·재시도, 멱등 키, 기대 `Revision`, 작업별 시도 횟수와 마지막 실행 시각
- 사람 경계: 관리자가 실제 포워더·물류대행업체와 전문 검토 수신자·범위·메모를 기록하되, 인계 기록을 전문 판단 완료나 실행 승인으로 해석하지 않음
- 정보 경계: 기본값은 집계 수요만 전달하고, 사용자 단위 정보는 명시적 동의와 동의 근거가 있을 때만 최소 범위로 구성

공유 공공데이터 점검은 등록 상태를 읽을 뿐 외부 API를 즉시 호출하지 않습니다. 외부 수집·게시 작업은 기존 Quartz 스케줄과 자격 증명 설정을 그대로 사용합니다.

수출 교류장·개별수출·공동수출은 현재 `CommunityTrust` OS가 `교류 → 별도 주문 동의 → 개별수출 → 선택적 환류`와 원장 handoff 순서를 조율하고 `수출 통관·규제 검토 엔진`을 후보·누락 판단에만 사용합니다. 실제 신고 제출, 전략물자 판정·허가, 포워더 자동 선정·외부 전송과 선적 지시는 `1.5`에서 실행하지 않습니다.

- 독립 빌드 단위: `Ssalddel.v1.5.slnx`
- 관리자 작업대: `SsalddelAdmin`과 `SsalddelAdminApp`의 `/trade-readiness`
- 관리자 API: `GET|PUT api/v1/admin/orderer/group-purchase-demand-os/groups/{autoGroupId}/trade-readiness`
- OS API: `GET .../trade-readiness/os`, `POST .../os/workloads/run`, `POST .../os/qualified-review-handoff`
- 저장 선행 조건: `1.0` 인계 상태 `승인후속대기`, 승인자·승인 시각·인계 ID 존재
- 저장 안전장치: `Idempotency-Key`, 기대 `Revision`, 관리자 정책, `CustomsAndTradeDataWorkflow`
- 추적성: 기존 또는 새로 연결된 정식 `group-import` 원장 ID를 원천 1.0 OS의 `대상원장Id`에 멱등 연결
- 실행 경계: 포워더 자동 선정·외부 자동 전송, 계약 서명, 결제, 신고, 공급자 자동 선정, 운송 지시와 창고 변경은 항상 `false`

## 주문자 앱 연결

주문자는 `/group-purchase/wishes/new`에서 여러 재료와 수량을 한 번에 선택할 수 있습니다. 한 번의 입력에서 B2B/B2C·가격 기준은 공유하지만 재료별 개별 원함 원장은 따로 저장합니다. 이 단계는 비구속 원함이며 결제·계약·주문·수입·운송을 확정하지 않고 LCL/FCL도 미리 고정하지 않습니다.

`/group-purchase/wishes`와 그 상세·수정 화면은 로그인한 주문자 본인의 개별 원함을 먼저 보여 줍니다. 활성 원함은 희망 수량만 변경하거나 철회할 수 있습니다. 철회는 비구속 원함을 닫는 동작이며 이미 별도로 만들어진 주문이나 계약을 취소하지 않습니다.

`/group-purchase/groups`와 `/group-purchase/groups/{AutoGroupId}`는 전체 집단을 먼저 노출하지 않고 본인 원함이 실제 포함된 공동 집계만 보여 줍니다. 다른 참여자의 식별정보는 표시하지 않습니다. 공동 진행에 정식 같이 수입 원장이 연결된 경우에만 해당 원장의 1.5 읽기 화면으로 이어집니다.

기존 `/group-purchase/import-review/{ProductId}`는 한 재료의 공식 기업·HSK·HTSUS 후보와 Simulation 예상 원가를 읽기 전용으로 보여 줍니다. 정식 같이 수입 원장에 연결된 준비 자료는 다음 원장별 읽기 화면으로 분리합니다.

- `/group-purchase/imports/{GroupImportLedgerId}`: 여러 재료, 준비도와 미확인 항목
- `.../suppliers`: 공급자 후보와 원출처
- `.../costs`: 견적 조건과 예상 도착 비용
- `.../classification`: HSK·HTS 후보와 국가별 규제 검토 항목
- `.../handoff`: 사람이 포워더에게 전달한 범위와 기록된 LCL/FCL·견적·일정 회신
- `.../consent`: 저장된 정보 제공 범위와 별도 동의 근거 확인 상태

각 원장별 화면은 `autoGroupId`로 로그인 사용자가 원천 자동집단에 참여했는지 확인한 뒤 조회합니다. 모두 읽기 전용이며 계약·결제·신고·운송 지시, 포워더 자동 선정이나 외부 자동 전송을 실행하지 않습니다. 특히 `.../consent`는 사용자의 동의를 새로 받거나 변경하는 화면이 아니라 기존 동의 근거의 확인 상태를 보여 주는 화면입니다. 같이 수입 원장의 1.5 준비 블록 저장은 관리자 API에서만 수행합니다.

`/orders`와 `/orders/{OrderLedgerId}`는 로그인한 주문자에게 자신의 개별주문 원장 목록·상세와 연결 이행 원장을 보여 줍니다. 기존 음식 주문 이력은 `/orders/food`로 분리되어 유지됩니다.

현재 배포 준비도와 남은 운영 게이트는 [2026-07-23 평가서](../deployment-readiness-assessment-2026-07-23.md)를 기준으로 합니다.
