> **2026-10-25 현재 기준:** 통합 제품 목표는 [1.0](unified-1.0/README.md) 하나입니다. 아래 버전별 표는 이전 업무 분류별 완료 조건으로 재사용하며 여덟 개의 독립 제품 출시를 요구하지 않습니다. 공통 검증·실제 운영 요건은 계속 적용합니다.

# 릴리즈 게이트

릴리즈 게이트는 구현된 capability를 사용자에게 어느 수준까지 안전하게 열 수 있는지 판단하는 기준입니다. 통합 1.0 전체 업무 범위의 구현을 진행하면서 각 기능의 준비를 확인합니다. 독립 조회·설명의 공개와 실제 외부 운영 공개를 구분하며, 후자는 [전체 역할 통합 공개 r105](../AI/Planning/공통/PLAN-OPERATIONS-NEIGHBORHOOD-MICRO-HUB/integrated-public-release.r105.md)의 필수 항목을 같은 현재 후보에 결속한 뒤 함께 공개하는 조건을 유지합니다.

현재 기본 노출의 호환 분류는 `0.0`이고 전체 제품 목표는 통합 `1.0`입니다. 아래 옛 `0.5` 이후 업무 분류별 게이트는 구현된 기능을 `내부 검증 → Simulation → 제한 공개 → 운영 공개 → 기본 공개`로 판정할 때 재사용합니다. 독립적인 조회·설명 capability는 자신의 선행조건을 충족한 범위에서 열 수 있습니다. 앱의 공통 제작·검증 순서는 [공통 절차](../AI/Planning/시스템/PLAN-SYSTEM-PLANNING-IMPLEMENTATION-CHECKLIST/app-production-input-guide.md)를 따르며 제작 입력 확인을 공개 승인으로 사용하지 않습니다.

## 공개 단계

| 단계 | 의미 |
| --- | --- |
| 내부 검증 | 코드와 원장을 구현하고 개발·테스트 환경에서만 확인합니다. |
| Simulation | 샘플·FakePG·모의 흐름으로 사용자 여정을 검증하며 실제 외부 효과는 실행하지 않습니다. |
| 제한 공개 | 사용자·역할·지역·기능을 제한해 조회 또는 베타 흐름을 엽니다. |
| 운영 공개 | 허가·제휴·약관·개인정보·복구 조건을 충족한 외부 효과만 명시적으로 엽니다. |
| 기본 공개 | 모니터링·중단·복구 절차까지 검증된 capability를 기본 사용자 흐름에 포함합니다. |

## 공통 게이트

| 구분 | 조건 |
| --- | --- |
| 빌드·테스트 | 영향 프로젝트 빌드와 핵심 회귀 테스트가 통과합니다. |
| 데이터 | 마이그레이션, 롤백·복구와 데이터 소유 범위가 기록됩니다. |
| 기능 플래그 | 범위 밖 워크플로우는 기본 비활성이고 서버에서도 차단됩니다. |
| 실행 경계 | `Simulation`과 `Operational`이 분리되고 외부 효과는 명시적으로 승인됩니다. |
| 개인정보 | 주소, 연락처, 계좌와 거래 자료는 최소 수집·최소 노출·철회 원칙을 따릅니다. |
| 공정성 | 국적·언어 등 보호되거나 비관련 속성을 집단화·순위·가격 차별 기준으로 사용하지 않습니다. |
| 책임 표시 | 판매자, 수입자, 운송사, 창고, 관세사와 플랫폼의 책임이 화면·계약·원장에 구분됩니다. |
| 문서 | 해당 버전의 `README.md`, `scope.md`, `checklist.md`, `migration-notes.md`가 코드와 일치합니다. |

## 버전별 게이트

| 버전 | 공개 방향 | 릴리즈 가능 조건 |
| --- | --- | --- |
| `0.0` | **현재 기본 공개 기준** | 음식·재료 데이터의 출처와 기준 시각을 표시하고, 게시글·댓글·참여 동의·공동 원장·신고가 후속 실행 모듈 없이 동작합니다. |
| `0.5` | 준비된 capability부터 순차 공개 | 사용자가 본인 소유 개별주문을 멱등하게 등록·변경·철회하고 같은 stable ID로 재조회하며, 같이 주문 참여 동의를 별도 상태로 관리합니다. 결제·계약·재고 예약·배송은 실행하지 않습니다. |
| `1.0` | 준비된 capability부터 순차 공개 | 같이 주문 참여에 동의한 0.5 개별주문만 품목·지역·수령 조건별로 멱등 집단화하고 모집 원장·참여 수·목표 수량을 개인정보 없이 보여 줍니다. 결제·계약·신고·배차는 실행하지 않습니다. |
| `1.5` | 정보·준비 capability부터 순차 공개 | 공급자·관련 기업 근거, 견적, 통화·단위·유효시각, 예상 원가, HS·HTS 후보와 수입 준비 체크포인트를 원장에 연결합니다. 전문 판단과 확정 코드는 자격 있는 검토자에게 인계됩니다. |
| `2.0` | 운영 요건을 갖춘 capability부터 공개 | 확인된 구매·출고 원장에서 운송 의뢰가 만들어지고, 허가·보험·약관이 확인된 수행자에게 인계되며 상차·하차·인수 증빙과 정산 후보가 남습니다. 준비 전에는 실제 유상 주선과 자동 배차를 거부합니다. |
| `2.5` | 운영 요건을 갖춘 capability부터 공개 | 입고, 검수, 적재, 재고, 피킹, 포장, 출고, 판매채널과 주문자 배분이 stable ID와 권한 범위로 연결되고 각 상태 전이가 멱등합니다. |
| `3.0` | 음식점·배달 capability별 순차 공개 | 음식점 주문이 접수, 조리, 픽업과 고객 배송으로 이어지며 마트 재고 흐름과 분리됩니다. |
| `3.5` | 옛 전체 업무 분류의 마트·도심 물류 | 마트 주문이 재고, 피킹, 포장과 도심 배송으로 이어지고 공동구매·음식점 주문 정책과 섞이지 않습니다. 통합 제품 목표는 1.0입니다. |

## 단계 의존성

| 버전 | 입력으로 사용할 수 있는 결과 | 강한 의존을 피할 대상 |
| --- | --- | --- |
| `0.0` | 없음 | 모든 후속 실행 모듈 |
| `0.5` | `0.0`의 공개 데이터, 사용자 동의와 원장 기반 | 같이 주문 자동 가입·결제·배송 확정 |
| `1.0` | `0.5`의 동의되고 철회되지 않은 개별주문 원장 | 통관·운송·창고 필수화 |
| `1.5` | `1.0`의 검증된 수요 집단 | 특정 운송사·창고 자동 선정 |
| `2.0` | `1.0` 수요와 `1.5` 준비 원장 | 창고·판매채널 필수화 |
| `2.5` | `1.0` 주문자 집단과 `2.0` 운송 인계 | 음식 배달·마트 정책 흡수 |
| `3.0` | `0.0` 참여 기반과 `2.0` 운송 원칙 | 공동구매·마트 주문 혼합 |
| `3.5` | `2.5` 창고 이행과 `3.0` 배달 원칙 | 공동구매·음식점 정책 혼합 |

국내 공동구매는 `1.5`의 통관 단계를 건너뛸 수 있습니다. 반대로 같이 수입은 `1.5`의 준비 게이트를 통과하기 전 `2.0` 운송 실행으로 넘어가지 않습니다.

## 판정 절차

1. `scope.md`에서 포함·보류 범위를 확인합니다.
2. 버전별 체크리스트와 공통 게이트를 검토합니다.
3. 마이그레이션과 설정 변경을 기록합니다.
4. 기능 플래그와 `SsalddelExecution:Mode`를 확인합니다.
5. 사용자 여정을 수요 등록부터 해당 단계의 종료 결과까지 검증합니다.
6. 법률·계약·허가가 필요한 외부 효과는 별도 책임자의 서면 결정 뒤에만 운영 전환합니다.
