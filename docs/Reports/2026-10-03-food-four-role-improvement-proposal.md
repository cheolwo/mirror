# 음식 배달 네 역할 운영 보완 제안서

음식 배달의 다음 우선순위는 주문자·음식점·기사·운영자가 같은 주문의 현재 상태를 보고, 문제가 생겼을 때 자기 역할의 다음 행동을 수행하도록 연결을 마무리하는 것이다. 기존 화면과 서버 기능을 재사용하고 상태 갱신·취소·현장 중단·알림·정산의 빈틈부터 보완할 것을 제안한다.

2026-10-03 `dev/mirror-integration` 작업 사본의 기획서·앱 소비 코드·서버 계약·시험 소스·기존 실행 기록을 대조했다. 기획 방향, 코드 연결 결손, 아직 실행하지 않은 조건을 구별했다. 아래 재정렬 r2는 상태 갱신·주문 작성 복귀와 로그인 분리 완료 뒤의 읽기 감사다. 이번 재정렬에서는 제품 코드·DB·실제 앱을 변경하거나 실행하지 않았다.

## 현행 우선순위 재정렬 r2

사용자 후속 선택으로 이 r2의1·2번을 [음식 배달 예외 명령·신규 수신 분리 r1](../Changes/2026-10-03-food-exception-intent-r1.md)에 구현했다. [책임 카드·코드/API·DB](../ProjectOverview/page-docs/food-exception-intent-r1.md)를 현재 구현 근거로 사용한다. 아래 표의 결손과 바로 다음 작업 설명은 구현 전 제안 snapshot이며 현재 결손으로 재사용하지 않는다. 다음 묶음은3번 앱 밖 알림·전표 복구이며, 배차 재탐색/만료의 음식·화물 활성화 결속은 별도 재현 후보로 유지한다. 이번 구현은 해당 Job·운영 모드·요금/지급 정책을 변경하지 않는다.

이전1순위의 상태 갱신·작성 복귀는 [구현과 실제 화면](../Changes/2026-10-03-food-state-refresh-r1.md)까지 완료했다. 이후 지적한 로그인/업무 겹침도 [책임 분리 r1](../ProjectOverview/page-docs/auth-workspace-separation-r1.md)과 [변경·실제 화면](../Changes/2026-10-03-auth-workspace-separation-r1.md)에 반영했다. 확인한 화면·상태의 완료이며, 모든 역할의 새 APK/모든 페이지를 실제로 확인했다는 뜻은 아니다. 현재 디자인 기준과 페이지 단일 책임 기준은 유지한다.

새 화면 수보다 기존 API를 역할 앱에서 실행하고 같은 주문을 다시 확인할 수 있는지가 검토 당시 남은 핵심이었다. 아래 번호는 r2 검토 당시의 순위이며1·2번 후속 구현은 위 변경 기록을 따른다.

| 새 순위 | 다음 보완 | 지금 부족한 부분 | 작게 끝내는 기준 |
| --- | --- | --- | --- |

실제 화면 검증은5순위까지 미루지 않는다. 각1~4 작업의 완료 조건에 해당 역할 앱과 다른 역할의 같은 주문 재조회를 포함한다. 기존7실패는 음식 배달의 새 오류7개가 아니며 좁은 마감 작업으로 병행한다. 실결제·은행 지급은 재원·마감·지급 수단이 정해진 뒤 별도로 진행한다.

### r2 검토 당시 첫 작업: 주문자 취소1건

[주문자 취소 API](../../Ssalddel/Controllers/Food/음식주문Controller.cs)는 기존 `POST {orderNo}/cancellation`과 서버 허용 행동을 제공한다. [주문자 Client](../../Ssalddel.Ui.Common/Areas/App/Services/음식주문Client.cs)의 등록/조회/수령 확인에는 취소가 없다. [현재 상세](../../Ssalddel.Ui.Common/Areas/App/Components/Food/OrdererFoodOrderDetailPanel.razor)에 보조 행동으로 취소 검토·사유·명시 확인을 연결하는 것이 가장 작은 다음 구현이다.

서버가 제공한 `FoodOrder.Cancel`, 현재 Revision, 같은 시도의 요청 ID를 사용한다. 성공·409 충돌·응답 유실 뒤 같은 주문을 재조회하고 음식점 확인과 취소의 경합, 다른 사용자·중복 실행·401 복귀를 검증한다. 조리 이후 직접 취소나 환불 규칙을 화면에서 새로 정하지 않는다. 음식점 변경 확인과 운영자 조회는 기존 화면을 재사용한다.

주문 내역 Workspace 자체는 인증/업무 배타 분기가 있지만 [소비 페이지](../../OrdererApp/Components/Pages/FoodOrderHistory.razor)는 업무 제목/주문하기 버튼을 인증 상태와 무관하게 조립하고 현재 셸 인증 표시 문맥도 소비하지 않는다. 취소를 연결할 때 이 소비 화면에도 기존 인증 표시 계약을 적용할 작은 후속이 남아 있다. 이번 읽기 감사에서는 실제 익명 화면을 다시 실행하지 않았으므로 런타임 재현 결과와 구별한다.

[기사 업무 API](../../Ssalddel/Controllers/Driver/Food/음식배달기사업무Controller.cs)의 가게 도착/중단은 [FDriver Client](../../FDriverApp/Services/FoodDeliveryDriverApiService.cs)에 없다. 기사 현장 작업은 시도 ID·판본·도착/준비/지연 시각을 화면 모델에 보존하고 서버 허용 행동으로 도착부터 연결한다. 이후 보호 중단1사례→음식점 변경→[운영자 검토 API](../../Ssalddel/Controllers/Admin/Food/음식주문운영추적Controller.cs)를 닫는다. 조회·모의 지급과 독립된 검토 결과는 별도 컴포넌트/진입점으로 소유하고 기존 추적 페이지에 여러 업무 폼을 모두 펼치지 않는다.

### 병행 확인: 미배차 재탐색·추천 만료

후보 없음 재탐색과 추천 만료 정리는 코드가 있다. [큐 스캔 Job](../../Ssalddel/Infrastructure/BackgroundJobs/DispatchQueue/배차큐스캔Job.cs)의74~93행은 음식 후보 없음의 재시도를 처리하고 [만료 Job](../../Ssalddel/Infrastructure/BackgroundJobs/DispatchQueue/추천만료정리Job.cs)은 만료된 추천을 다시 처리한다. 따라서 자동 복구 자체가 미구현이라고 제안하지 않는다.

다만 두 Job의 실행 전 점검은 [공통 활성화 정책](../../Ssalddel/Infrastructure/BackgroundJobs/SsalddelBackgroundJobActivationPolicy.cs)의 `DomesticTransportDispatch`→`DomesticTransportWorkflow`에 연결되어 있다. [기능 판정](../../Ssalddel/Services/Versioning/VersionFeatureFlagService.cs)의79~81행과109~110행은 음식/화물을 독립 판정하므로, 음식 ON·화물 OFF에서 음식 재탐색/만료까지 차단되는 소스 결속이 확인된다. 실제 해당 운영 프로필의 주문 실패를 재현한 결과는 아니며 배포 조합과 실행 전제를 격리 시험에서 확인할 후보다. 현재 운영 장애를 확정하거나 운영 전체 활성화로 우회하지 않는다.

[Job 등록](../../Ssalddel/Extensions/ServiceCollectionExtensions.BackgroundJobs.cs)은 Operational 조건이고 기존 검증 호스트는 Simulation이다. [관찰 호스트](../../Ssalddel/Services/Development/FoodObserver/음식배달관찰검증Hosting.cs)는 Quartz를 제외하고 [전용 배차 작업자](../../Ssalddel/Services/Development/FoodObserver/음식배달관찰배차작업자.cs)는 추천대기만 처리한다. 기존 호스트의 미재탐색 관찰만으로 제품의 복구 실패를 판정하지 않는다. 격리 시험에서 음식 ON/화물 OFF·반대·둘 다 OFF의 실행 경계와 같은 주문의 후보 없음→기사 가능→재추천, 만료→다음 추천을 먼저 확인하고 결손이 재현되면 별도 수정한다. 음식 복구 때문에 OFF인 화물 큐·외부 알림·지급까지 실행하면 안 된다. 이를 위해 현재 서버를 Operational로 바꾸거나 전체 기능을 활성화하지 않는다.

### 금액/정산에서 먼저 지킬 정확성

[정산 Recorder](../../Ssalddel/Application/Food/음식주문기사정산Recorder.cs)는 수락 때 동결 대금과 계산 근거를 이미 저장한다. [정산 DTO](../../Ssalddel.Contracts/Food/FoodDeliveryOrderSettlementDtos.cs)에는 그 요금 구성 근거의 완료 내역 전달이 빠져 있고 [기사 업무 조회](../../Ssalddel/Application/Driver/Food/FoodDeliveryDriverWorkspaceUseCase.cs)의102~108행은 완료 정산을 최근40건으로 제한한다. 총액·공제 미확정·모의 지급을 없다고 평가하거나 이 제한 목록을 당일 전체로 합산하지 않는다.

[당일 정산 방향 r63](../AI/Planning/시스템/PLAN-SYSTEM-FRANCHISE-OPERATIONS/free-platform-daily-settlement.direction.r63.md)은 유지한다. 실제 지급은 재원·마감·지급 수단 미정이며 현재 [지급 UseCase](../../Ssalddel/Application/Admin/Food/음식주문기사정산UseCase.cs)는 Simulation 모의 지급이다. 금액을 설명하는 작업과 실제 송금 연결을 구별한다.

### r2 검토 근거와 경계

현재 소스·기획·시험 소스·최근 완료 기록을 읽기 대조했다. 취소/도착/중단/검토의 앱 명령 결손, 기사 수신/운행 상태 결속, 정산 근거 전달/최근40건 경계는 소스 근거다. 다른 역할의 실제 UI·Job 실행·Android 백그라운드·물리 인쇄·실지급은 이번 검토에서 실행하지 않았다. 기존 완료 기록의 시험/설치본 결과를 새 실행 결과로 보고하지 않는다. r2 출처 지문·전후 문서·링크/문서 검증은 Git 제외 `artifacts/local/food-four-role-audit-r2/`에 보관한다.

## 이전 상태 갱신 1순위 적용 현황

사용자 요청으로 음식점 상세 자동 갱신과 주문 작성 인증/수명 복귀를 구현했다. [페이지·코드·DB](../ProjectOverview/page-docs/food-state-refresh-r1.md)와 [변경·시험·실제 화면](../Changes/2026-10-03-food-state-refresh-r1.md)에 최종 결과를 연결했다.

관련118/118·전체 build가 통과했다. 전체시험6,032/6,039의 실패7개는 기존 기준선과 동일하며 새 실패는0개다. 최종 두 Debug APK 설치 지문과 에뮬레이터 합성 주문의 최종401→재로그인·작성 유지→UI등록, 음식점 확인→기사HTTP수락→상세 자동 배정 표시, 별도 표본의503 잠금/자동복구를 확인했다. 취소·재배정·화면 이탈·계정 경계는 시험 근거와 실제 실행을 구별한다. 실제 영업·네 역할 전체UI·물리 단말·인쇄·은행 지급의 완료를 뜻하지 않는다.

아래 빈틈 설명의1순위 부분은 이전 구현 전 검토 사본이다. 상태 갱신 근거는 위 두 문서를 우선한다. 당시 다음 개발 대상으로 제안한 기존 취소·현장 중단·운영자 검토는 이 문서 상단의 후속 구현 기록을 따른다.

## 현재 갖춰진 기반

[최근 앱 실행 기록](../ProjectOverview/page-docs/app-flow-stability-r1.md)에는 같은 합성 주문을 음식점 확인 → 기사 수락 → 조리·준비 → 픽업·전달 → 주문자 수령 확인까지 실제 Android 설치본으로 수행하고 운영자 웹에서 조회한 근거가 있다. 등록과 합성 위치 준비는 Client·HTTP였으므로 메뉴 선택부터 주문 제출까지의 전체 앱 입력 증거와 구별한다.

기사 배정 뒤 조리 시작과 음식점 준비 뒤 픽업이라는 서버 조건도 이미 있다. 로그인 복귀·503 재조회·기사 배달/정산/내 정보 분리·대표 화면의 시각 정리도 앞선 완료 범위다. 이 부분을 새 기능처럼 다시 만들 필요는 없다.

| 역할 | 가장 먼저 답해야 하는 사용자 질문 | 기본 화면의 책임 |
| --- | --- | --- |
| 주문자 | 내 주문이 어디까지 왔고 지금 무엇을 할 수 있나 | 주문 진행·준비시간 변경·허용된 취소·수령 확인 |
| 음식점 | 지금 조리해도 되며 어느 주문을 먼저 준비해야 하나 | 기사 배정 확인·조리시간·준비 완료·최근 변경 사유 |
| 기사 | 지금 수행할 배달과 다음 행동은 무엇이며 얼마를 받나 | 현재 수행·수락 시 동결 금액·도착/픽업/전달·문제 알림 |
| 운영자 | 어느 주문이 막혔고 누가 어떤 조치를 해야 하나 | 지연·중단 원인·허용된 검토·역할 인계·정산 근거 |

## 권장 개발 순서

아래 표는 최초 검토 r1의 순서를 보존한 기록이다. 완료 항목을 제외한 현행 순서는 위 재정렬 r2를 우선한다.

| 순위 | 보완 묶음 | 먼저 하는 이유 | 완료 기준 |
| --- | --- | --- | --- |
| 1 | 같은 주문의 화면 갱신과 주문 작성 복귀 | 오래된 배정 표시, 만료된 로그인으로 반복 제출, 화면 이탈 뒤 늦은 응답의 이동을 줄인다. | 상세에 머문 동안 배정·취소·재배정이 반영되고, 주문 등록의 401 오류 뒤 복귀하며 이탈한 화면의 늦은 결과를 적용하지 않는다. |
| 2 | 네 역할의 취소·도착·중단·검토 연결 | 정상 흐름 밖에서 사용자가 기존 서버 기능을 실행할 수 없는 공백을 닫는다. | 주문자 취소, 기사 가게 도착/중단, 운영자 검토를 각 앱으로 제출하고 다른 역할의 같은 주문을 재조회한다. |
| 3 | 새 배차 수신 의사와 현재 배달 수행 분리 | 새 일을 받지 않으려는 의사가 현재 수행·위치 갱신의 종료로 이어지지 않게 한다. | 새 제안 OFF 상태에서도 수락한 배달과 필요한 위치 갱신을 유지하고, 실제 운행 종료는 별도 조건으로 처리한다. |
| 4 | 화면 밖 알림과 음식점 전표 복구 | 다른 화면·앱 전환·인쇄 실패가 주문 누락으로 이어지는 경계를 보완한다. | 실제 Android 새 주문/제안 알림, 알림 후 정확한 주문 재조회, 같은 전표의 재출력과 재시작 복구를 확인한다. |
| 5 | 주문별 대금 설명과 당일 지급 준비 | 이미 있는 동결 대금·모의 정산을 사용자가 이해할 수 있게 연결한다. | 기사 지급 구성, 공제 미확정, 지급 예정/보류를 구별하고 당일 집계·지급 가능액·후속 조정의 조건을 문서와 원장에 결속한다. |
| 6 | 네 역할 전체 입력 검증과 릴리즈 마감 | 코드가 있는 것과 실제 앱에서 이용 가능한 것을 같은 기준으로 마무리한다. | 메뉴 선택부터 주문 제출·수령·운영자 조회까지 동일 주문으로 수행하고 재시작·중복 클릭·지연·권한을 검증한다. 기존 전체 시험의 실패 7건도 해결한다. |

각 순위는 작은 변경으로 나눠 진행한다. 1순위는 음식점 상세 갱신과 주문 작성 인증/수명 복귀로 나눠 적용했다. 이후도 각 변경부터 관련 시험과 실제 앱 확인을 붙이며6순위까지 실행 검증을 미루지 않는다.

## 기획과 코드 사이에서 확인한 빈틈

이 절은 최초 검토 r1의 구현 전 소스 위치와 제안 기록이다. 상태 갱신·작성 복귀는 이미 적용됐으므로 현행 결손으로 읽지 않으며, 현재 판단은 위 완료 링크와 재정렬 r2를 우선한다.

### 음식점 상세의 최신 상태 전달

현재 [주문 상세](../../RestaurantDeskApp/Components/Pages/OrderDetail.razor)의 168행·289행은 최초/수동 조회를 소비한다. [수신함](../../RestaurantDeskApp/Components/Pages/OrderInbox.razor)의 실시간 구독은 수신함을 나갈 때 381행부터 해제된다. 상세에 머문 상태에서 기사 배정·취소·재배정이 변경돼도 수동 새로고침까지 이전 표시가 남을 수 있는 연결 결손이다. 서버 판본과 허용 행동 검사는 있으므로 잘못된 조리가 확정된다고 단정하지 않는다.

상세 화면의 주문번호에 한정해 상태 변경과 재연결 뒤 정본 재조회를 연결한다. 다른 주문을 선택하거나 화면을 떠난 뒤의 늦은 응답은 기존 차단을 유지한다. 음식점이 보고 있던 조리시간 입력을 불필요하게 초기화하지 않도록 조회 정보와 작성 중 입력을 구별한다. 최근 취소·지연 사유도 재조회 가능한 서버 이력으로 설명한다.

### 주문자의 직접 취소와 주문 작성 복귀

[음식주문Controller](../../Ssalddel/Controllers/Food/음식주문Controller.cs) 86행에는 주문자 취소 API가 있고 서버는 `FoodOrder.Cancel` 허용 행동을 제공한다. 현재 주문자 공용 Client·화면에는 취소 명령 연결이 없다. 서버가 허용한 상태에서만 확인 후 실행하고, 성공·실패 뒤 같은 주문을 재조회하도록 기존 주문 내역에 연결한다. 조리 이후 취소·환불 조건을 화면에서 새로 만들어내지 않는다.

주문 내역의 401 오류 복귀는 완료됐지만 [음식점 주문 작성 Workspace](../../Ssalddel.Ui.Common/Areas/App/Components/Food/OrdererRestaurantWorkspace.razor.cs) 106행의 제출 경로는 작성 실패에서 반환하며 인증 복구를 호출하지 않는다. 주문 작성 중 최종 401 오류를 실제로 재현해 로그인 입력과 안전한 작성 복귀를 연결해야 한다. 제출 결과가 불명확한 요청은 같은 요청 식별자로 조회·재시도하여 중복 주문을 방지하는 조건도 함께 확인한다.

같은 경로의 108~116행은 수명 토큰 없이 등록 응답을 기다리고 화면 이탈을 확인하지 않은 채 성공 콜백으로 이동한다. 늦은 응답이 떠난 화면의 이동을 유발할 수 있는 소스 경계이며 실제 장치 재현은 별도다. 기존 동일 내용 재시도용 요청 ID는 있으므로 멱등 기능 전체가 없다고 평가하지 않는다. 화면 요청 취소와 서버 주문 취소를 구별하고, 서버 저장 여부가 불명확하면 같은 요청을 재조회한다.

### 기사 현장 문제와 운영자 처리

[음식 기사 서버 API](../../Ssalddel/Controllers/Driver/Food/음식배달기사업무Controller.cs) 170행·182행은 가게 도착과 배달 중단을 제공한다. 조리 지연·재조리·재배차 처리도 서버에 있다. 그러나 [FDriver Client](../../FDriverApp/Services/FoodDeliveryDriverApiService.cs)의 기존 업무 인터페이스에는 이 두 명령이 없고 앱이 관련 시도 식별자·판본·지연 기준을 충분히 전달하지 않는다. 현장에서 지연이나 사고를 알릴 수 있도록 기존 서버 조건과 최소 입력을 연결할 필요가 있다.

[운영자 중단 검토 API](../../Ssalddel/Controllers/Admin/Food/음식주문운영추적Controller.cs) 56행 이후와 검토 UseCase는 있지만 [운영 추적 Client](../../SsalddelAdmin/Services/FoodOrderOperationsTraceAdminService.cs)·[화면](../../SsalddelAdmin/Components/Pages/FoodOrderOperationsTrace.razor)은 조회·모의 지급만 연결한다. 운영자에게 근거·현재 판본·검토 사유를 확인하는 진입점을 붙인다. 검토만으로 자동 재배차나 실지급까지 완료됐다고 표시하지 않는다. 사고·질병·차량 고장 등 보호 대상 중단을 기사 귀책으로 자동 판정하지 않는 기존 서버 경계를 유지한다.

현재 추적은 주문번호를 알고 조회하는 방식이다. 기존 관리자 배차 목록과 연결을 먼저 대조하고, 아직 없다면 장기 미배차·중단·준비 지연처럼 확인이 필요한 주문만 보여주는 최소 목록을 후속 후보로 둔다. 새 통계 대시보드보다 문제 주문에서 담당자의 다음 행동까지 연결되는 것이 우선이다.

### 기사 수신 의사와 운행 상태

[지도 첫 화면 기획](../AI/Planning/공통/PLAN-OPERATIONS-FOOD-DRIVER-MAP-HOME/README.md) 53~59행은 신규 배차 받기와 운행 세션을 분리한다. 현재 [MainPageModel](../../FDriverApp/PageModels/MainPageModel.cs) 386행의 ToggleWork는 운행 종료와 새 제안 수신 중지를 하나로 처리하고, 1008행의 위치 갱신은 운행 상태에 묶여 있다. 현재 수행 목록은 유지되므로 사라지는 버그로 단정하지 않는다. 다만 새 제안만 잠시 중지하면서 현재 배달과 위치 갱신을 이어가는 기획을 표현할 수 없는 구현 결손이다.

이 분리는 화면 토글만 추가해서 끝내지 않는다. 서버의 수신 의사·실제 후보 가능 여부·운행 세션·수락된 수행을 구별하고, 연결 오류를 사용자의 거절이나 OFF 의사로 바꾸지 않도록 한다.

### 알림과 전표 복구

[음식점 알림음](../../RestaurantDeskApp/Services/주문알림Service.cs) 50~75행은 Windows 조건부 구현이다. 주문 알림 소비도 수신함에 있으며 Android 상세/다른 화면/백그라운드의 신규 주문 수신 연결은 부족하다. FDriver 역시 화면 모니터와 위치 갱신에 의존하고 화면 이탈 때 모니터를 취소한다. 백그라운드에서 계속 추천을 받고 위치가 유지되는지에 대한 실제 기기 증거도 없다. 활성 업무에 필요한 범위의 알림과 위치 수명을 패키지·권한별로 확인해야 한다.

알림은 같은 주문의 중복 재생을 억제하고, 누르면 서버의 정확한 주문을 다시 읽는다. 알림 자체가 수락·조리·픽업을 실행하는 권위가 되지 않는다. 화면 복귀 시 놓친 상태를 서버 조회로 보충한다.

[음식점 상세](../../RestaurantDeskApp/Components/Pages/OrderDetail.razor) 340~370행은 주문 확인과 전표 생성/출력을 연결한다. 출력 실패 안내는 있지만 이미 확인한 주문을 재출력하는 별도 경로가 없고 출력 시각은 메모리에 남는다. [문서 생명주기 제안](../Versions/document-lifecycle-app-placement-proposal.md) 197~203행·354~356행의 같은 문서 ID·출력 횟수·출력 실패/재출력 분리는 아직 연결할 부분이다. 주문 확인을 반복하지 않고 전표만 복구하도록 분리하며 Android와 Windows 실제 인쇄 확인도 별도로 남긴다.

### 대금 설명과 당일 지급 방향

[기사 지급 상세 기획](../AI/Planning/공통/PLAN-OPERATIONS-FOOD-DRIVER-PAYOUT-DETAIL/README.md)은 기본·거리·기상·수요·조정 항목과 공제·수령액을 나눈다. 현재 [주문별 정산 Recorder](../../Ssalddel/Application/Food/음식주문기사정산Recorder.cs)는 수락 시 동결 대금과 계산 근거를 저장하지만 기사 화면은 총액·공제·수령액 요약 중심이다. 기존 동결 근거를 읽는 상세부터 연결하고 과거 배달을 현재 요율로 재계산하지 않는다.

[초기 무료 이용과 당일 정산 방향](../AI/Planning/시스템/PLAN-SYSTEM-FRANCHISE-OPERATIONS/free-platform-daily-settlement.direction.r63.md)은 확정된 목표이며 지급 재원·마감 시각·지급 수단·역할별 무료 범위는 미정이다. 현재 [기사 정산 UseCase](../../Ssalddel/Application/Admin/Food/음식주문기사정산UseCase.cs) 31행 이후는 Simulation 모의 지급이다. 기존 주문별 정산이 전혀 없다고 평가하거나 모의 성공을 실입금으로 평가하지 않는다.

다음 정산 보완은 주문 한 건의 동결 대금 → 한국 시각의 일별 대상 → 공제 근거/미확정 → 지급 가능액/보류 → 후속 조정의 연결이다. 이후 선택된 지급 수단으로 실제 지급을 별도 검증한다. 플랫폼 무료 이용·음식 주문대금·기사 노동 대가·결제/송금 비용을 각각 설명한다. 과거 요금 메모와 개발 기본값을 실제 운영 요금으로 확정하지 않는다.

## 사용자 배려와 화면 기준

현재 [페이지 책임 원칙](../Architecture/WholeRoadmapPagePrinciple.md)과 [시각 디자인 기준](../Architecture/RoleAppVisualDesignStandard.md)을 유지한다. 다음 보완은 현재 단계·지금 할 행동·막힌 이유를 먼저 읽을 수 있게 만드는 데 집중한다.

- 주문자는 준비시간 변경과 취소 가능 여부를 알 수 있어야 한다. 실패 후 입력을 어디서 이어갈지도 설명한다.
- 음식점은 조리 시작 가능 여부와 다음 준비 주문을 먼저 본다. 서버 식별자·상세 원장·인쇄 이력은 필요한 곳에서 펼친다.
- 기사는 수행 중 필요한 행동과 약속된 총액을 먼저 본다. 사고·중단은 선택적 문제 처리 진입점으로 두고 운전 중 반복 입력을 요구하지 않는다.
- 운영자는 문제 주문의 담당 역할·최근 변경·허용된 조치부터 본다. 지원에 필요한 개인정보는 권한과 목적에 맞춰 공개한다.
- 대기·성공·실패·오래된 조회는 문구로 구별한다. 보조기기도 상태 변경을 읽도록 확인하고, 중요한 금액·취소 처리는 실행 전 검토/확인과 중복 실행 방지를 함께 검증한다. 이는 [W3C 상태 메시지 기준](https://www.w3.org/WAI/WCAG22/Understanding/status-messages.html)과 [실수 방지 기준](https://www.w3.org/WAI/WCAG22/Understanding/error-prevention-legal-financial-data.html)을 적용할 제안이며 현재 앱의 접근성 준수 판정은 아니다.

## 실제 앱 검증에서 마무리할 조건

동일 주문번호로 네 역할의 서버 상태와 화면을 대조한다. 기본 사례는 주문자 메뉴/수령 정보 입력·제출 → 음식점 인지 → 기사 수락 → 음식점 조리/준비 → 기사 픽업/전달 → 주문자 수령 → 운영자 추적/정산이다.

예외는 한 번에 하나씩 실행한다. 주문 작성401, 주문대기 취소, 상세 체류 중 배정/재배정, 현장 중단과 운영자 검토, 조리시간 변경, 알림 뒤 복귀, 앱 재시작, 출력 실패/재출력, 중복 클릭·응답 유실을 순차적으로 확인한다. 마지막 판본의 APK와 기록을 결속한다. 실제 지도·도로 경로·물리 단말·실지급은 준비된 조건에서 별도 검증하고 합성 자료와 혼합하지 않는다.

기획서의 `Deferred` 등 상태 문구만으로 전체 미구현을 판정하지 않는다. 이후 변경 기록에서 부분 구현된 범위를 확인해 기획 → 소비 화면 → 서버/API → 원장 → 시험 → 실제 실행의 연결을 갱신한다. 기존 전체 시험의 실패 7건은 가장 최근 화물 작업에서도 유지된 기준선이며 음식 배달의 새 결손으로 계산하지 않는다.
