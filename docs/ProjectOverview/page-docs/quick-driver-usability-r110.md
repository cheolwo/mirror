# 퀵 기사 업무 시작과 픽업·전달 안내 r110

2026-10-18. 사용자는 r109 사용성 점검 후 퀵 배송을 우선해 구현하도록 요청했다. 이번 개발 순서는 **운행·신규 수신 시작 → 추천 수락 → 픽업·전달 준비 → 완료 확인·다음 업무**다. 기존 통합앱의 `cargo-driver`와 화물 운송 API를 사용하며 퀵 전용 원장이나 새 배차 엔진을 만들지 않는다.

## 기기별 마감 범위 r111 — 2026-10-18 사용자 확정

사용자는 기사 업무는 모바일에 집중하고, 화주는 모바일과 데스크톱을 모두 사용하되 데스크톱의 주요 이용자로 보도록 요청했다. 아래 표는 개발·검증의 우선순위다. 기존 기사 route나 공통 컴포넌트 삭제, 데스크톱 접근 차단 또는 공개 운영 전환을 지시한 것은 아니다.

| 사용자·기기 | 주 업무 | 마감 시 확인할 것 |
| --- | --- | --- |
| 퀵 기사 · 모바일 | 운행·신규 수신, 추천 알림/수락, 픽업·전달, 사진 증빙, 완료 내역 | 휴대폰의 터치·알림·위치·카메라와 상태별 현재 업무/다음 행동. 통신 중단·권한 거절·응답 유실·중복 처리 보호 |
| 화주 · 데스크톱 | 단건·다건 의뢰 작성/검토, 운임·결제 조건 확인, 의뢰 목록·검색·진행, 증빙·정산 조회 | 키보드 입력·넓은 목록·필터·파일 입력, 행별 성공/실패·미확정 결과, 접수 후 다음 행동. 실제 서버 등록과 단순 미리보기를 구별 |
| 화주 · 모바일 | 현장 단건 접수, 진행 확인, 변경·문제 접수, 완료·증빙 확인 | 간편 입력·세로 화면·터치, PC와 같은 의뢰의 최신 상태와 권한, 재접속/작성 복귀 |
| 퀵 기사 · 데스크톱 | 이번 마감의 신규 제품 화면·별도 최적화 대상에서 제외 | PC 브라우저의 공통 UI 검토는 개발 확인 수단이다. 그것으로 기사 휴대폰 사용성·권한·알림·GPS·카메라를 통과 처리하지 않음 |

화주 모바일도 독립적으로 단건 접수를 완료할 수 있게 유지한다. 모바일에 데스크톱의 대량 입력 표를 그대로 축소해 넣거나, 기사에게 화주의 관리 화면을 요구하지 않는다. 양쪽 화주 화면은 같은 서버 의뢰·상태·권한을 사용하며 별도 원장을 만들지 않는다.

### PC 호스트 재확인 r112 — 2026-10-18

r111에서 데스크톱 기능 비교에 웹 경로를 사용했으나, 사용자 확인 요청 후 현재 소스의 `UseMaui=true`와 Windows target을 재검사했다. **PC 화주는 기존 `SsalddelApp` Windows MAUI를 우선 활용**하고 별도 `Ssalddel.Web.ShipperApp`은 브라우저 선택지로 유지한다. MAUI의 단건·일괄등록과 웹의 단건·CSV 미리보기를 구분한다. Windows 네이티브 지도는 현재 Android 전용 구현을 사용할 수 없으므로 기존 목록 대체를 유지한다. 현재 소스 빌드, 공통 UI 브라우저 렌더, Windows 앱 실제 창 조작은 각각 다른 검증이다. [조사·보완 결과 r112](../../Changes/2026-10-18-shipper-pc-closeout-r112.md)가 이번 작업 범위를 소유한다.

### 현재 확인한 차이

- 별도 웹 [단건 최종 확인](../../../Ssalddel.WebApp/Pages/ShipperRequestReviewPage.razor)은 작성 VM의 서버 등록을 소비한다. 신규 초안 편집이 기존 접수 의뢰 수정까지 구현됐다는 뜻은 아니다.
- 별도 웹 [CSV 화면](../../../Ssalddel.WebApp/Pages/ShipperBulkImportPage.razor)은 형식 미리보기다. MAUI PC·모바일 [일괄등록 화면](../../../SsalddelApp/Components/Pages/ShipperBulkImportPanel.razor)의 서버 미리보기·선택 행 등록과 같은 완료 상태로 표시하지 않는다. 양쪽의 같은 URL만으로 기능 동일성을 판단하지 않는다.
- 화주 모바일·웹의 결제/후불 승인 공백은 아래 접수 원천·정산 경계를 따른다. 담당 권한·준비 상태·결과 조회를 확인한 뒤 기존 서버 기능에 연결해야 한다.

### 다음 집중 순서

1. **화주 데스크톱 단건 접수 마감:** 입력·견적/조건 확인·접수·결과 재조회·현재 의뢰와 다음 행동까지 연결한다. 접수와 결제/승인·실배차는 각각 구분한다.
2. **퀵 기사 모바일 수행 마감:** 준비된 한 건의 추천→수락→픽업→전달→내역을 실제 모바일 진입으로 확인한다. r110 로컬 검사와 USB 단말 결과를 합치지 않는다.
3. **화주 모바일 왕복 확인:** PC에서 접수한 의뢰를 모바일에서 확인하고, 모바일 접수도 PC 목록에서 같은 ID·상태로 확인한다. 새 요청 중복 생성·권한 확대 없이 처리한다.
4. **화주 데스크톱 일괄 접수 마감:** 기존 서버 미리보기·등록 계약의 재사용을 검토하고, 등록 전 행별 오류·선택과 등록 후 부분 성공·미확정 결과의 복구를 분리한다. 이미 등록된 행을 자동 재전송하지 않는다.

이번 r111은 기기별 책임과 순서를 정한 문서 변경이다. 새 제품 코드·화면 구현·실행 시험·APK 제작/설치·commit/push는 수행하지 않았다. 영상 채널 성장과 앱 완성도 개선은 병행하되, 화면의 준비 상태를 실제 운영 중으로 광고하지 않는다.

## 접수 원천과 정산 경계

- 일반인의 생활 간편접수 `/community/exchange/deliveries/new`는 `NeighborhoodDeliveryUseCase`의 직접 현장지급 조건을 사용한다. 후불승인과 같은 흐름으로 표시하지 않는다.
- 화주 4단계 `/shipper/request/...`는 일반 운송 의뢰를 만든다. 현재 `ServerBackedShipperOperationsService`의 선결제·플랫폼 수납 변환과 승인 가능한 실제 조건을 별도로 확인해야 한다.
- 기존 후불승인 서버 API는 있지만, 현재 앱 응답에는 해당 사용자 권한·모의 처리 제외·승인 준비를 모두 판독하는 가능 행동 계약이 없다. 이번 화면에 임의의 승인 가능 버튼을 추가하지 않는다. 후속은 서버가 확인한 권한·준비 상태를 화면에 제공하고 해당 원천의 결제/승인 화면을 연결하는 작업이다.
- 통합 기사 화면은 준비된 추천과 운송을 소비한다. 이번 기사 UI 보완을 접수·결제·추천의 실제 서버 전체 완주, 실수납·정산·송금으로 표현하지 않는다.

## 검증 상태

구현과 검증 결과는 [r110 기록](../../Changes/2026-10-18-quick-driver-usability-r110.md)에 기록한다. 기본 OFF인 기능·worker·실운영 경계를 유지하고 USB·APK 설치·외부 서버·실제 금융은 이번에 수행하지 않는다. 실제 처음 사용하는 사람의 설명 없는 완주 판정도 별도다.
