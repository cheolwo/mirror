# 주문자 비구속 수요 등록

[페이지 원칙](../../../../Architecture/WholeRoadmapPagePrinciple.md) · [후속 구조 정리 r2](../../../../AI/Planning/공통/PLAN-OPERATIONS-REFACTOR-SRP/implementation.r2.md)

## 페이지 책임

| 항목 | 기록 |
| --- | --- |
| 주 사용자·페이지/소스 | 주문자. 기존 `/group-purchase/demands/new/{ProductId}`와 GroupPurchaseDemandCreate/GroupPurchaseDemandPanel을 유지한다. PageKey·route를 신설/변경하지 않는다. |
| 대상·진입 문맥 | 목록에서 선택한 상품과 현재 희망 수량·단가, 작성 중 배송 범위. |
| 한 문장 목적 | 주문자가 선택 상품의 비구속 수요와 모집권을 확인하여 명시적으로 등록하거나 기존 수요를 철회한다. |
| 완료 결과·상태별 주 행동 | 모집권 확인 → 비구속 동의 → 등록. 등록된 수요는 기존 정본/철회 행동으로 확인한다. 인증 완료가 등록을 자동 실행하지 않는다. |
| 기본 정보 | 상품·HS 확인·희망 수량/단가·공개 배송 범위·현재 등록 결과와 다음 행동. |
| 보조 정보 | 같은 수요의 모집 상태·근거와 기존 안내. 현재 정보 배치와 문구를 유지한다. |
| 독립 업무·제외 정보 | 실제 결제·집단 확정·운송 실행은 이 등록의 결과로 간주하지 않는다. 기존 별도 흐름으로 인계한다. |
| 진입·실패·복귀 | 등록과 후속 조회의 결과를 구분한다. 등록 후 조회 예외와 철회 후 조회 예외의 현행 처리 차이를 보존한다. 상품 변경/로그아웃 때 지우는 상태와 유지하는 출처키·초안도 현재 동작을 따른다. |
| 코드·API·DB | 기존 Panel → 내부 DemandSession → 기존 GroupPurchaseShipmentTrackingService → 서버 공동구매 수요/집단 원장. 명령 DTO·SHA 기반 출처키·권한과 영속 상태는 기존 서버가 소유한다. |
| 책임 판정·검증 | 같은 목적의 구성. r2는 화면·행동·route를 유지하고 내부 선택/요청 수명만 분리한다. 코드·가짜 service 회귀와 실제 화면/휴대폰/운영 검증은 구분한다. 실행 결과는 r2 구현 문서가 소유한다. |

## 변경 전후 정보 배치

모든 입력·인증 표시·상태 메시지·등록/철회 버튼은 기존 위치에 둔다. Razor는 표시와 사용자 입력을 조립하고 Session은 모집권 선택·등록/철회 뒤 정본 조회 상태를 소유한다. 새로운 페이지·메뉴·결제 기능을 추가하지 않는다.
