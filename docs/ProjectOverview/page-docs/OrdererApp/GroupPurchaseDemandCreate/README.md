# 주문자 비구속 수요 등록

## 페이지 책임

| 항목 | 기록 |
| --- | --- |
| 주 사용자·페이지/소스 | 주문자. 기존 `/group-purchase/demands/new/{ProductId}`와 GroupPurchaseDemandCreate/GroupPurchaseDemandPanel을 유지한다. PageKey·route를 신설/변경하지 않는다. |
| 대상·진입 문맥 | 목록에서 선택한 상품과 현재 희망 수량·단가, 작성 중 배송 범위. |
| 한 문장 목적 | 주문자가 선택 상품의 비구속 수요와 모집권을 확인하여 명시적으로 등록하거나 기존 수요를 철회한다. |
| 완료 결과·상태별 주 행동 | 모집권 확인 → 비구속 동의 → 등록. 등록된 수요는 기존 정본/철회 행동으로 확인한다. 인증 완료가 등록을 자동 실행하지 않는다. |
| 기본 정보 | 상품·HS 확인·희망 수량/단가·공개 배송 범위·현재 등록 결과와 다음 행동. |
| 보조 정보 | 같은 수요의 모집 상태·근거와 기존 안내. 현재 정보 배치와 문구를 유지한다. |
| 독립 업무·제외 정보 | 실제 결제·집단 확정·운송 실행은 이 등록의 결과로 간주하지 않는다. 기존 별도 흐름으로 인계한다. |
| 진입·실패·복귀 | 명령 성공과 후속 원장 조회 성공을 구분한다. 처리 중 상품·모집권을 바꿔도 제출한 대상은 바꾸지 않으며, 이전 결과·안내는 새 선택에 덮어쓰지 않는다. 확인된 수요 출처키와 원래 대상은 화면 결과와 별도로 보존한다. 등록 후 조회 예외와 철회 후 조회 예외의 기존 안내 차이는 유지한다. |
| 코드·API·DB | [Panel](../../../../../OrdererApp/Components/GroupPurchase/GroupPurchaseDemandPanel.razor)은 입력·인증·명시 제출, [DemandSession](../../../../../OrdererApp/Components/GroupPurchase/GroupPurchaseDemandSession.cs)은 선택과 명령 대상·결과 반영, [GroupPurchaseShipmentTrackingService](../../../../../OrdererApp/Services/GroupPurchaseShipmentTrackingService.cs)는 HTTP 요청을 맡는다. 명령 DTO·SHA 기반 출처키·권한과 영속 상태는 기존 서버가 소유한다. |
| 책임 판정·검증 | 같은 목적의 구성. 기존 r2의 화면·행동·route와 책임 분리를 유지하면서 처리 중 선택 변경의 대상 결속을 보완한다. 아래 회귀 시험과 실제 화면·휴대폰·운영 검증을 구분한다. r2 당시 결과는 기존 구현 문서에 보존한다. |

## 변경 전후 정보 배치

모든 입력·인증 표시·상태 메시지·등록/철회 버튼은 기존 위치에 둔다. Razor는 표시와 사용자 입력을 조립하고 Session은 모집권 선택·등록/철회 뒤 정본 조회 상태를 소유한다. 새로운 페이지·메뉴·결제 기능을 추가하지 않는다.

## 화면 흐름을 따라 읽기

1. **상품 확인:** 선택 상품과 희망 수량·단가를 확인한다.
2. **모집권 선택:** 주소로 후보를 찾고 사용할 모집권을 선택·동의한다. 추천 후보만으로 등록하지 않는다.
3. **명시 등록:** 로그인과 비구속 신청 조건을 확인한 뒤 등록한다. 서버 등록 응답을 받은 뒤, 제출했던 같은 상품·모집권의 원장을 조회한다.
4. **결과 확인·철회:** 조회한 원장으로 모집 현황을 표시한다. 철회는 성공이 확인된 출처키의 원래 수요를 대상으로 하며, 철회 응답 뒤 그 상품·모집권을 다시 조회한다.

## 처리 중 선택 변경과 실패

- 화면에서 보고 있는 선택과 이미 서버에 보낸 명령의 대상은 구분한다. 선택을 바꿨다고 처리 중 명령을 취소하거나 다른 대상으로 재전송하지 않는다.
- 명령 대기 중에는 등록·철회를 겹쳐 보내지 않는다. 처리 중 상품·모집권을 바꾸거나 결과를 지운 뒤에는 이전 응답·안내를 현재 선택의 결과로 표시하지 않는다.
- 등록 성공 후 조회가 실패해도 확인된 출처키와 대상은 보존한다. 다음 철회가 다른 상품·모집권의 조회로 바뀌지 않게 하기 위해서다. 철회 성공 후 조회 실패 역시 철회 실패와 구분한다.
- 로그아웃 시 결과 지우기와 출처키 보존의 기존 의미를 유지한다. 이 내부 상태 보완을 계정 전환·실서버 권한 검증 완료로 해석하지 않는다.
