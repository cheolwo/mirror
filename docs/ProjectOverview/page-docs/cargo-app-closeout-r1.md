# 화물 앱 마무리 · 인수증과 예외 복구

2026-10-24. 기존 화주·기사·운영자의 업무 경계와 전문 앱을 유지한다. 이번 범위는 Web 인수증 등록의 누락 배선, 공통 상하차의 명확한 미적용 거절 복구, 전문 기사 신고의 화면 수명 보호다.

## 화주 증빙 화면 책임

| 항목 | 기준 |
| --- | --- |
| 사용자·대상 | 해당 의뢰의 조회·인수확인 권한을 서버에서 검사받는 화주 |
| 한 문장 목적 | 선택 의뢰의 운송 완료와 정산 조건을 확인하고 실제 수령·검수한 인수증 번호를 명시 등록한다. |
| 기본 정보·주 행동 | 현재 운송·증빙 상태, 등록 번호·시각, 수령·검수 확인 뒤 인수증 등록 |
| 보조 정보 | 검수 메모와 기존 증빙. 연락처·계좌를 새 입력으로 요구하지 않는다. |
| 실패·미확정 | 원 요청 보호 기록을 유지하고 동일 의뢰 GET으로 확인한다. POST를 자동 반복하지 않는다. |
| 재진입 | 등록된 인수증을 보여주되 원 번호와 비교할 근거가 없으면 이전 요청 성공으로 단정하지 않는다. |
| 복귀 | 기존 ReturnPath와 의뢰 상세의 조회 흐름을 유지한다. |
| 제외 | 운송 완료·정산·입금을 인수증 등록과 합치지 않는다. 새 금융·권한·사진 정책을 만들지 않는다. |

실제 경로는 `/shipper/request/{RequestId}/proofs`다. 기존 공통 `ShipperReceiptRegistrationPanel`과 서버 인수증 등록 handler를 사용한다. 일반 상세·이력·결제 조회를 증빙 등록의 쓰기 능력으로 확대하지 않는다.

## 기사 상하차와 신고 책임

- 공통 상하차는 서버가 해당 단계에 대해 명확히 `NotApplied`를 반환하고 같은 운송·기사·도착 단계를 재조회한 경우에만 해당 미확정 보호 기록을 해제한다. 사진은 유지하며 운송 보류·가능 행동 제한은 유지한다.
- timeout·연결 단절·5xx·다른 운송·판단 근거가 없는 재실행은 미적용으로 추측하지 않는다. 과거 신고 존재만으로 이번 신고를 성공 처리하지 않는다.
- 전문 기사 신고는 운송·인증 문맥 변경과 화면 종료 때 이전 작업을 취소하고 늦은 응답을 버린다. 처리 중 또는 결과 미확정이면 같은 화면의 중복 신고를 막는다.
- 전문 기사 앱에는 동일 요청 영수증에 결속된 신고 결과 조회가 아직 없다. 결과가 미확정이면 운영자 확인을 안내한다. 현재 화면의 중복 방지는 앱 재실행 뒤의 영속 보호가 아니다.

## 검증·잔여 범위

현재 판본의 시험·빌드·실제 브라우저 화면은 [변경 기록](../../Changes/2026-10-24-cargo-app-closeout-r1.md)을 따른다. 로컬 화면 예시는 실제 제품 HTTP·단말·사진·운영 결과와 구분한다. 기존 운영 비활성, 실제 PG·송금·FCM·배포 경계는 유지한다.
