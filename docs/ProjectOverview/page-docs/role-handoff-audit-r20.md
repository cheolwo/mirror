# 여덟 역할의 업무 인계·상태 조화 조사 r20

2026-10-06. 사용자가 선택한 검토 초점은 업무 인계다. [r19 첫 진입 검토](role-entry-review-r19.md) 다음으로, 한 역할의 처리가 서버 저장과 상대방 재조회·다음 행동으로 이어지는지 대조했다. 이번 결과는 **기존 연결의 조사와 보완 명세**이며 제품 코드·API·DB·권한·요금·정산을 변경하지 않았다.

## 판정과 결론

정상 인계의 기반은 연결돼 있고 관련 자동시험이 통과했다. 음식과 화물을 하나의 상태 머신으로 통합할 필요는 없다. 반면 통합 운영자에서 화물 예외를 처리하는 화면 연결, 의뢰자의 기본 보류 안내, 통합 기사 화면의 완료 내역 접근에는 부족한 부분이 있다. 모든 역할의 실제 제품 화면이 같은 운영 건으로 함께 완주했다고 판정하지 않는다.

- **연결 확인:** 현재 소스의 저장·조회·행동 관계와 이번 자동시험이 뒷받침하는 범위. 별도 표기가 없으면 로컬 시험 수준이다.
- **불일치:** 같은 서버 사실이 표시 단계에서 서로 다른 안내로 보이는 확인된 차이.
- **연결 부족:** 기능·API가 있어도 해당 역할의 실제 진입/다음 업무 동선이 연결되지 않은 범위.
- **실행 미검증:** 실제 HTTP/DB·여러 계정의 제품 화면·단말 실행까지 확인하지 않은 범위. 앞의 판정과 함께 붙일 수 있다.

시험 실패는 없었으며 확인된 부족을 서버 원장의 손실이나 모든 앱의 고장으로 확대하지 않는다. 홈의 여덟 선택지는 현재 활동 선택이며 역할 선택만으로 권한을 만들지 않는다. 생활은 제품의 별도 동네 지도, 다른 일곱 역할은 공통 업무 화면을 사용한다. [역할 목록](../../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Core/RoleWorkspaceCatalog.cs), [Web 진입](../../../Ssalddel.WebApp/Pages/RoleWorkspacePage.razor), [통합 앱 진입](../../../SsalddelApp/Components/Pages/RoleWorkspacePage.razor), [등록](../../../eng/role-workspace/RoleWorkspaceRegistration.cs)을 확인했다.

## 확인된 부족과 보완 명세

### H01 · 우선 1 · 운영자의 화물 예외 처리 화면 연결 부족

- **근거:** [공통 운영자 adapter](../../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Food/OperatorRoleWorkspaceAdapter.cs)는 음식 목록·추적·배차 검토와 음식 중단 입력만 제공한다. [화물 관리 Controller](../../../Ssalddel/Controllers/Admin/03_진행/운송진행관리Controller.cs)에 사건 목록 `GET api/v1/admin/transports/incidents`와 결정 `PUT api/v1/admin/transports/incidents/{incidentStableId}/decision`이 존재한다. 이번 클라이언트 소스 검색에서는 이 사건 API/검토 DTO를 쓰는 UI가 발견되지 않았다. API 부재가 아니라 통합 운영 흐름의 연결 부족이다.
- **재현:** 기사가 화물 수량 불일치 등을 신고해 운영 검토 대기 사건을 만든 뒤 `/workspace/operator`에 진입한다. 음식 원장을 조회하므로 해당 사건 목록과 검토 입력으로 이동할 수 없다. 이번에는 저장·검토를 자동시험으로 확인했고 실제 제품 HTTP/UI에서 이 전체 순서를 실행하지 않았다.
- **수정 책임:** 공통 운영 UI와 Web/통합 앱의 운영자 업무 연결. 음식·화물 목록은 별도 업무로 유지하며 사건 목록과 독립 검토 입력을 제공한다. 같은 `operator` 인증을 사용하고 서버 관리자·제품 기능 관문을 유지한다.
- **최소 구현 명세:** 기존 GET/PUT와 [검토 계약](../../../Ssalddel.Contracts/Admin/Progress/비정상운송사건운영Dtos.cs)을 재사용한다. 사건·운송·의뢰 ID를 결속하고 현재 상태·영향 수량·보류 범위를 보여준다. 결정·검토 사유·필요 수량은 독립 입력, `클라이언트요청Id`와 `예상Revision`을 유지한다. 저장 성공 후 사건을 재조회하고 운영 목록으로 복귀한다. 계약·DB·새 역할·자동 판정은 추가하지 않는다.
- **수정 후 확인:** 일반 계정 403, 기능 비활성, 빈 목록, 다른 사건 응답 차단, revision 충돌·응답 유실 재시도, 정상분 인수/영향분 보류와 전체 운송 보류의 구별, 당사자 재조회가 같은 결과를 보여야 한다.

### H02 · 우선 2 · 의뢰자 기본 보류 안내의 표시 불일치

- **근거/재현:** [화주 카드](../../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Cargo/CargoWorkspaceAdapters.cs)는 `비정상운송검토보류중=true`일 때 `확인 필요`를 상세에 추가하지만 기본 요약과 `운송중` 상태는 그대로다. [공통 표시](../../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Core/RoleMapWorkspace.razor)는 기본에 요약만, 상세를 펼친 뒤에 섹션을 표시한다. 같은 진행중·배정 기사 의뢰에 보류 flag만 바꿔 실제 매핑 코드를 실행한 결과 `summaryUnchanged=true`와 상세 안내 추가를 확인했다. 원시 재현은 Git 제외 `shipper-hold-probe.json`이다. 브라우저 캡처나 실제 운송 사건 실행 결과가 아니다.
- **생활 쪽 대조:** [생활 배송 상세](../../../Ssalddel.Ui.Common/Areas/App/Components/Community/Exchange/NeighborhoodDeliveryDetail.razor)는 동일 의뢰 응답의 보류/사건 필드를 별도 안내로 소비하지 않고 배차·운송 진행·지급을 표시한다. 단순히 화주 화면만 수정하면 생활 의뢰자는 같은 사실을 놓칠 수 있다. 이 부분은 소스에서 확인했으며 제품 렌더 재현은 미실시다.
- **수정 책임/명세:** 화주 adapter와 생활 배송 표시. 기본 화면에 `운영 검토 중 · 운송 내역 확인`을 우선 안내하고 정산 보류·영향 수량 보류·전체 운송 중단을 섞지 않는다. 운송 상태 문자열 자체를 임의 변경하거나 기사를 배차 전으로 되돌리지 않는다. 사건 DTO의 확인된 상태만 사용하고 담당이 없으면 담당 미확인으로 표시한다. 사유·증빙·개인정보는 상세 권한 범위를 유지한다.
- **수정 후 확인:** 일반 진행은 기존 표시 유지, 보류와 재개는 첫 카드에서 구분, 영향 수량만 보류한 사건은 전체 중단으로 표시하지 않음, 생활 본인 조회와 화주 조회의 같은 사건 안내 일치, 지급 완료를 자동 생성하지 않음.

### H03 · 우선 3 · 통합 기사 화면의 완료 내역 진입 연결 부족

- **근거:** [음식 기사 adapter](../../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Food/FoodDriverRoleWorkspaceAdapter.cs)의 주 목록은 활성 배달과 추천이며 운행/수신/위치 제어를 제공한다. [화물 기사 adapter](../../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Cargo/CargoWorkspaceAdapters.cs)는 지정한 완료 건을 유지할 수 있지만 공통 화면의 내역 진입은 없다. 전용 음식 앱에는 [완료 배달 내역](../../../FDriverApp/Pages/MainPage.xaml)과 [정산 조회](../../../FDriverApp/PageModels/MainPageModel.cs), Web에는 [화물 운송 내역](../../../Ssalddel.WebApp/Pages/DriverTransportHistoryPage.razor)이 이미 있다.
- **재현:** 공통 기사 화면에서 업무를 끝내고 홈을 거쳐 다시 진입한다. 다음 현재 업무에 집중하는 것은 맞지만 완료된 건을 찾아 인계·증빙·지급 상태를 확인하는 명시적 동선이 없다. 전용 앱의 기능 부재나 완료 데이터 삭제로 해석하지 않는다.
- **수정 책임/명세:** 공통 기사 화면의 보조 navigation과 기존 완료 내역 소비. 현재 배달 카드에 다른 배달 목록을 넣지 않고 별도 내역→상세로 이동한다. 음식·화물 내역과 각각의 인증·지급 기준은 분리한다. 완료 당시 운임과 실지급을 구별하며 주소/연락처의 제공 기한과 권한을 유지하고 기존 역할/선택으로 복귀한다.
- **수정 후 확인:** 현재 수행/없음 두 상태에서 내역 접근, 다른 계정 기록 차단, 완료·취소·중단 분류, 정보 기한 만료 뒤 금액/증빙 요약과 고객 상세 보호, 상세에서 현재 업무 복귀.

### H04 · 후속 실행 관문 · 같은 한 건의 실제 다중 역할 완주 미검증

자동시험·표시 매핑·예시 화면과 실제 역할 앱/HTTP/운영 DB/입금을 구별한다. 이번 261개 시험은 SQLite/EF InMemory·fake API·알림/외부 adapter 대역을 포함하며 실제 후보 선정·push 도착·휴대폰 네트워크를 보장하지 않는다. 오래된 [음식 역할 흐름 그림](../../Changes/2026-07-26-food-order-cross-app-state.md)의 수락 직후 조리중 설명은 과거 snapshot이다. 현재 코드의 주문확인→기사배정→조리 시작과 혼용하지 않는다.

후속 검증은 분리된 개발 환경에서 음식 정상 1건·재배차 1건, 창고 연계 화물 정상 1건·예외 1건, 생활 배송 1건의 식별 관계를 고정하고 당사자별 별도 인증/조회로 이어 간다. 모든 단계에서 저장→새 조회→표시→다음 행동을 확인하고 실제 인계 전 상차, 준비 전 픽업, 동의 없는 주소 제공, 완료만으로 지급 완료 처리를 실패 조건으로 둔다. 기존 [화물 검증 도구](../../../eng/verification/cargo-journey.ps1)는 후보지만 이번에 Prepare/Up/Load/Serve를 실행하거나 공유 환경의 데이터를 바꾸지 않았다. 휴대폰/Azure·외부 운영은 추가 증거가 필요하다.
