# OS 생명주기와 역할별 상태 카드 조사

현재 카드가 업무 상태에 맞는지 판단하려면 OS의 큰 단계, 실제 원장 상태, 역할의 다음 행동, 화면의 통신 상태를 구별해야 한다. 음식 기사와 화물 기사의 정상 수행은 단계별 목적지와 행동을 나누는 기반이 있다. 다만 음식의 일부 안내가 실제 단계보다 앞서고, 창고 검수와 화물 예외의 조회 연결에는 결손이 있다. 카드의 최종 구성은 사용자 검토 대상으로 남긴다.

2026년 10월 5일 현재 작업본의 소스 조사다. [기존 카드 검토표](role-state-card-review-r16.md)를 OS·원장·서버 정책과 추가 대조했다. 일곱 업무 역할의 공통 지도 카드와 연결된 대표 전문 화면을 중심으로 확인했으며, 모든 OS의 모든 페이지·복합 상태를 실제 앱에서 실행한 결과는 아니다. 제품 코드는 변경하지 않았다.

## 상태를 읽는 기준

| 구분 | 의미 | 카드 판단에 사용하는 방식 |
| --- | --- | --- |
| OS 생명주기 단계 | 주문, 배차, 픽업, 전달, 검수 등 업무 책임의 큰 구간 | 해당 카드가 어떤 업무에 속하는지 찾는다. 단계의 정렬 번호를 실제 상태 전이로 간주하지 않는다. |
| 저장된 업무 상태 | 주문 상태, 배차 상태, 현재 조리 회차·준비 완료, 기사 수행, 인수·정산·예외 상태 | 현재 누구에게 무엇이 필요한지 결정한다. 한 상태 문자열만으로 다른 원장 상태를 대신하지 않는다. |
| 서버가 허용한 행동 | 권한·현재 상태·준비 조건을 확인한 실행 가능 여부 | 버튼과 다음 안내를 함께 맞춘다. 화면에서 누를 수 있다고 업무 권한을 생성하지 않는다. |
| 화면 상태 | 불러오는 중, 오류, 재조회, 인증 만료, 위치 지연, 숨김·복귀 | 업무 상태 위에 별도로 표시한다. 조회 실패를 업무 없음이나 완료로 바꾸지 않는다. |

[페이지 단일 책임 기준](../../Architecture/WholeRoadmapPagePrinciple.md)에 따라 한 화면은 **한 역할이 선택한 업무의 현재 상태를 이해하고 다음 행동을 판단하는 질문**을 소유한다. 같은 판단에 필요한 장소·요청 사항·주문 정보는 여러 카드나 섹션으로 함께 구성할 수 있다. 카드 하나 또는 상태값 하나마다 새 페이지가 필요한 것은 아니다. 증빙 입력·정산 실행·정책 변경처럼 따로 완료·취소·재시도하는 일은 기존 독립 화면으로 인계한다.

공통 화면은 [표시 계약](../../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/RoleWorkspaceContracts.cs)의 기본 요약·상세 섹션·주 행동을 [현재 업무 카드](../../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Core/RoleMapWorkspace.razor)에 조립한다. 역할별 업무 판단은 각 adapter가 맡는다. 이 계약 자체는 OS 단계별 카드 대응표나 전이 정책을 정의하지 않는다. 최종 서버 상태와 카드 표시가 일치하는지는 별도 대조가 필요하다.

## OS와 역할 화면의 조사 범위

[OS 식별 대장](../../../Ssalddel.Contracts/Common/Versioning/OperatingSystemIdentityCatalog.cs)에는 10개 OS가 있다. 이 중 5개에 공통 생명주기 41단계가 정의돼 있다. 나머지 5개의 공통 단계는 [상호작용 대장](../../../Ssalddel.Contracts/Common/Versioning/OperatingSystemInteractionCatalog.cs)에서 `LifecyclePending`이다. 이는 업무 코드가 없다는 뜻이 아니다. 공동구매·생활 협업·교육에는 각각 별도 계약과 실제 상태 전이가 있다.

| OS | 공통 단계 수 | 역할·화면 연결과 이번 조사 깊이 |
| --- | ---: | --- |
| 화주 운송 관리 | 8 | 화주 공통 카드, 운송·결제·정산의 대표 상세와 서버 정책 대조 |
| 국내 화물 운송 | 8 | 화물 기사 공통 카드, 실제 운송 상태·다음 행동·예외 조회 대조 |
| 창고·커머스 이행 | 9 | 창고 공통 카드 5종, 입고·검수·적재·피킹·포장·인계의 운영 코드 대조 |
| 공동구매 수요 | 대기 | 모집·승인·후속 원장 인계 상태와 주문자 대표 화면 대조 |
| 공동구매 수입 준비 | 대기 | 준비 상태·근거 점검·전문 검토 인계와 대표 화면 확인. 모든 공급·선적 화면을 전수 조사하지 않음 |
| 음식 배달 | 8 | 주문자·음식점·음식 기사·운영자 공통 카드, 현재 조리·배차·가능 행동과 대표 전문 상세 대조 |
| 살뜰마트 도심물류 | 8 | 주문자 비구속 주문요청·창고 마트 허브 확인. 확정 주문부터 모든 배송 자식의 실행 연결은 미검증 |
| 지역 교류·신뢰 | 대기 | 생활 지도·협업·보관·본인 배송 카드와 상태·허용 행동 대조. 댓글·친구·투표 등 전체 세부 흐름은 미검토 |
| 플랫폼 운영 | 대기 | 공통 운영자 adapter는 음식 업무 범위. 플랫폼 전체 관리자 업무와 같지 않으며 나머지 관리자 상태 전수 조사는 미실시 |
| 교육·현장 체험 | 대기 | 실제 원장·계획·보호자 확인·학교 심사 계약과 UseCase 존재 확인. 전체 교육 UI는 깊게 조사하지 않음 |

[역할 대장](../../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Core/RoleWorkspaceCatalog.cs)은 8개 선택지를 제공한다. [공통 adapter 등록](../../../eng/role-workspace/RoleWorkspaceRegistration.cs)은 음식 4개·화물/창고 3개이며, [생활 역할](../../../SsalddelApp/Components/Pages/RoleWorkspacePage.razor)은 기존 동네 지도로 별도 연결된다. OS 10종, 역할 8개, adapter 7개를 같은 수로 맞추거나 하나의 상태 머신으로 합칠 이유는 없다.

[API의 OS 설명 대장](../../../Ssalddel/ApiMetadata/SsalddelApiVersionAttribute.cs)은 9종을 설명하고 교육 항목은 빠져 있다. 교육의 실제 업무는 [상태 계약](../../../Ssalddel.Contracts/Common/Education/현장체험활동Dtos.cs)과 [UseCase](../../../Ssalddel/Services/Education/현장체험활동UseCase.cs)에 존재한다. 대장 누락과 기능 누락을 따로 분류한다.

## 음식 배달의 역할별 상태 대조

일반 조리 대상의 정상 운영은 음식점의 주문 인지·수락 뒤 유효한 기사 배차를 확정하고 조리를 시작한다. 수락 시 즉시 픽업 가능한 음식은 별도 준비 기록을 가진다. OS 설명 대장의 조리 30·배차 40은 정렬 번호이며 강제 전이 순서가 아니다. [조리 시작 정책](../../../Ssalddel/Services/Food/음식점주문진행Policy.cs) 43~55행은 기사 배정을 선행 조건으로 확인한다. 현재 조리 회차·준비 시각, 기사 시도와 가게 도착, 주문자 수령, 정산은 서로 다른 상태 축이다.

| 역할과 실제 상태 | 현재 카드와 주 행동 | 판정과 보완 후보 |
| --- | --- | --- |
| 음식점 주문대기 | 메뉴 요약, 조리 단계·준비 시각, 주문 수락. 조리시간·거절은 독립 입력 | 수락과 조리 시작의 분리는 맞다. 전문 화면에 있는 원문 요청사항이 공통 기본·상세에는 모두 빠졌다. |
| 음식점 주문확인·기사 미확보 | 조리 시작을 열지 않고 기사 배정·가능 여부 확인 안내 | 정상 대기의 기반은 맞다. 배차불가·조리 시작 후 기사 재배정 대기를 기본 안내가 구별하지 못하는 조합이 있다. |
| 음식점 기사배정·현재 음식 미시작 | 서버 허용과 `조리시작가능`을 확인한 조리 시작 | 현재 책임과 행동이 맞다. 계획 조리분을 실제 준비 완료 시각으로 취급하지 않는다. |
| 음식점 조리중·준비 미완료 | 메뉴, 준비 예정, 픽업 준비 완료 | 정상 조리의 주 행동은 맞다. 현재 준비 회차와 요청사항을 함께 볼 정보 배분은 검토가 필요하다. |
| 음식점 준비완료·미픽업 | 준비 완료, 기사에게 인계 안내 | 유효한 기사·현재 음식이 준비된 경우에 맞는다. 배차불가·재배정 대기에서는 인계 안내가 먼저 나오지 않도록 대조가 필요하다. |
| 음식점 픽업완료·전달 중 | 상태는 픽업완료지만 준비완료 시각이 있으면 계속 인계 안내 | **상태와 안내 불일치.** 픽업 이후 단계가 준비 시각보다 우선해야 한다. 재조리 이력도 현재 인계 대기로 남지 않아야 한다. |
| 음식점 전달완료·수령확인·취소·거절 | 처리된 주문 내역 확인 | 종료 안내는 존재한다. 전달 완료와 주문자 수령 확인을 전문 화면처럼 구별하는 배치는 후보로 남긴다. |
| 음식 기사 현재 수행 없음 / 제안 | 현재 수행 없이 운행·배차 설정, 제안은 픽업지·배달료·제안 거리·수락 | 기존 권한·운행·제안을 구분한다. 제안 가격·거리와 수락 후 현재 업무의 정보는 같은 값이 있다고 가정하지 않는다. |
| 음식 기사 음식점 이동 | 픽업 주소·배달료·준비 예정, 음식점 도착 | 단계에 맞는 주소와 주 행동이다. 고객 전달 요청·긴 주문·연락처는 기본에서 제외된다. |
| 음식 기사 가게 도착·현재 음식 미준비 | 픽업 주소·준비 예정, 픽업 확인 비활성 | 버튼 관문은 맞다. 재조리인 경우 기본 안내가 준비 완료 전에도 픽업을 지시하는 결손이 있다. |
| 음식 기사 현재 음식 준비완료·미픽업 | 픽업 확인은 서버 가능 행동이 있을 때 활성 | 현재 차수·준비 완료·허용 행동의 결속은 유지한다. 준비 시각만으로 행동을 활성화하지 않는다. |
| 음식 기사 픽업완료·전달 중 | 전달 주소·전달 요청·배달료, 고객 전달 완료 | 현재 목적에 맞다. 수령인·마스킹 연락처·긴 주문·메뉴 요약은 상세로 분리된다. 전체 메뉴 DTO를 받는다는 뜻은 아니다. |
| 음식 기사 수행 완료 / 다음 업무 | 활성 수행에서 제거하고 다음 현재 업무를 선택 | 현재 업무 집중은 유지한다. 공통 역할 화면에서 완료 이력·정산으로 가는 명시적 진입은 빠져 있다. 전문 앱에는 이미 별도 내역이 있다. |
| 주문자 주문대기 / 기사 확보 대기 | 주문 진행·조리 예정·최근 변경·위치 시각·다음 확인, 허용된 취소는 상세 | `주문확인`과 `기사배정`을 같은 조리·픽업 준비로 표현한다. 실제 조리 전 기사 확보 대기의 설명을 별도로 검토할 필요가 있다. |
| 주문자 조리중 / 픽업대기 / 전달 중 | 주문 상태별 진행, 최근 위치와 만료 처리 | 정상 진행·위치 관문은 있다. 배차불가·추천 만료·수락 취소 등의 회복 안내가 전문 상세보다 부족하다. |
| 주문자 전달완료·수령 미확인 | 수령 확인 대기, 수령 조건과 서버 허용을 만족한 음식 수령 확인 | 기사 전달과 본인 수령을 구별한다. 위치 추적 종료도 맞다. |
| 주문자 수령확인·취소·거절 | 종료 상태와 처리 내역 | 종료 상태에도 동일한 조리·위치 시각 지표가 남는 표시량은 조정 후보다. 본인 수령 정보·요청·진행 이력은 전문 상세에 있고 공통 상세에서는 빠져 있다. |
| 운영자 정상 인계 | 현재 단계·담당·최근 변경·확인 사항, 상세의 경고·복구 | 현재 책임을 표시하는 기반이 있다. 경고의 원인을 기본에서 얼마나 보여 줄지는 미확정이다. |
| 운영자 현재 정상 수행과 과거 중단 시도 공존 | 모든 중단 시도에 같은 검토 버튼을 만들고 첫 버튼을 주 행동으로 선택 | 현재 수행과 과거 검토의 책임을 구분해야 한다. 시도별 문맥을 붙이고 현재 담당의 안내를 보존하는 배치가 필요하다. |
| 수령 완료 뒤 정산 보류·지급 미요청 | 공통 운영자와 음식 기사 수행 카드에 정산 상태·명시 진입 없음 | 배달 완료가 정산·입금 완료는 아니다. 수행과 별도 정산 화면을 연결하는 후보다. 지급 입력을 수행 카드에 합치지 않는다. |

## 화물 운송과 화주 카드

화물의 [실제 전이 정책](../../../Ssalddel/Application/Driver/Transport/Services/기사운송상태전이Service.cs)은 의뢰·기사 소유권을 검증하는 [명령 실행기](../../../Ssalddel/Application/Driver/Transport/Services/기사운송상태변경CommandExecutor.cs)와 함께 판단해야 한다. 지도 카드의 목적지 분기, 서버의 다음 행동, 실제 허용 전이가 일부 상태에서 같은 표를 사용하지 않는다.

| 역할과 실제 상태 | 현재 카드·행동 | 판정과 보완 후보 |
| --- | --- | --- |
| 화물 기사 추천 | 상차·하차지, 거리·거리 기준, 운임 미확정, 추천 조건 확인 | 수락 전 조건은 별도 입력 책임이다. 추천 DTO에 없는 운임을 만들지 않은 것은 맞다. |
| 화물 기사 `배차확정`·`확정`·`매칭중`·`이동중` | 상차지·운임·거리, 상차지 도착 | 다음 목적지는 맞다. DTO가 제공하는 상차 시간창·필수 증빙은 공통 기본·상세에서 빠져 있다. |
| 화물 기사 `배차대기` | 하차 단계로 분류되고 도착 주 행동 없음 | 서버는 상차지 도착을 허용하므로 대응이 어긋난다. 조회 코드상 들어올 수 있으나 실제 배정 원장의 발생 사례는 실행하지 않았다. |
| 화물 기사 `상차지도착` | 상차 정보, 상차 확인 → 독립 증빙 입력 | 독립 입력 분리는 맞다. 사진·인수증·서명 등 필수 조건을 기본 안내에서도 짧게 확인할 수 있어야 한다. |
| 화물 기사 `상차완료`·`운송중` | 하차지·전달 요청, 하차지 도착 | 현재 업무에 맞다. 하차 시간창은 DTO에 있으나 공통 adapter가 표시하지 않는다. |
| 화물 기사 `하차지도착` | 하차 정보, 하차 확인 → 독립 완료 입력 | 완료 증빙 조건을 사전에 안내하는 후보다. 사진·서명·문제 수량 입력을 지도 요약에 합치지 않는다. |
| 화물 기사 인수 완료·종료 | 수행 행동·활성 핀 제거 | 운송 종료는 맞다. 증빙·정산 상태와 별도 내역으로 가는 완료 후 동선은 부족하다. |
| 화물 기사 현장 예외 | DTO 예외 flags가 있으면 확인 안내·주 행동 비활성 | 신고 직후 응답과 재조회 응답이 같은 예외를 투영하지 않는다. 아래의 읽기 결손을 먼저 보완해야 한다. |
| 화물 기사 정보 제공 보류 | 주소·금액·핀·실행 행동을 제외하고 접근 안내 | 현행 보호 범위 유지. 카드 보완을 이유로 비공개 정보를 복원하지 않는다. |
| 화주 미배차·배차 진행 | 상차지·물품·운임·기사 위치 미확인, 운송 내역 | 위치 미확인은 배차 대기의 설명을 대신하지 못한다. 현재 담당·배차 대기·다음 확인을 기본 안내의 후보로 둔다. |
| 화주 배차 확정·상차 | 상차지, 고정 운송 내역 행동 | 담당 기사·시간창·현재 단계 안내 후보. 연락처와 계약 전체는 상세 책임을 유지한다. |
| 화주 운송 중·하차 | 하차지로 변경, 고정 운송 내역 행동 | 목적지 변경은 맞다. 결제 확보 여부와 수행 상태는 별도로 표시해야 한다. |
| 화주 인수 완료 | 하차지, 운송 종료 후 위치 비공개 | 종료 뒤에는 위치보다 인수·증빙·정산 상태가 중요하다. 운임을 실제 지급 완료액으로 표현하지 않는다. |
| 화주 비정상 운송 검토 보류 | 예외는 상세에 있고 기본 요청칸은 기사 위치 안내 | 보류 이유와 현재 검토 담당·확인 경로를 기본에 올리는 후보다. 모든 상태의 고정 내역 링크 자체를 실행 오류라고 단정하지 않는다. |

### 예외 신고 뒤 재조회 결손

[신고 명령](../../../Ssalddel/Application/Driver/Transport/Handlers/운송문제신고CommandHandler.cs)은 예외 메모·첨부·해당 사건을 저장하고 즉시 응답에 확인 필요 flags를 넣는다. 반면 [운송 상세 조회](../../../Ssalddel/Application/Driver/Transport/Handlers/운송상세조회QueryHandler.cs)와 [목록 조회](../../../Ssalddel/Application/Driver/Transport/Handlers/운송목록조회QueryHandler.cs)는 원시 첨부 등을 반환하지만 현재 사건을 이 flags·안내로 복원하지 않는다. 카드가 이 flags에 의존하므로 새로 조회하면 예외 안내·버튼 차단이 사라질 수 있다. 원장이 비어 있는 문제와 다르다.

[비정상 운송 사건](../../../Ssalddel/Services/Operations/비정상운송사건Service.cs)은 유형별 운영 검토·업무 통제 범위를 보존하고 관련 화주 정산을 보류한다. [입금 요청](../../../Ssalddel/Application/Driver/Transport/Services/운송완료입금요청Service.cs)은 열린 사건을 확인해 실제 요청을 보류한다. 조사한 운송 전이 정책·실행기는 사건을 직접 조회하지 않는다. **정산 보류가 모든 운송 행동 중단과 같다는 결론은 내리지 않는다.** 서버가 현재 사건·통제 범위·역할별 허용 행동을 함께 반환하고, 카드의 안내와 버튼을 그 근거에 맞추는 것이 우선이다.

## 창고 카드의 단계 연결

창고 공통 화면은 [adapter](../../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Cargo/WarehouseWorkspaceAdapter.cs) 30~46행의 입고·적재·피킹·포장·인계 준비 5종만 조회한다. OS의 9단계마다 반드시 카드가 하나씩 필요한 것은 아니지만, 실제 다음 업무가 존재하는 검수와 출고예정 검토·실제 인계로 이어지는 연결은 필요하다.

| OS 단계와 실제 상태 | 현재 카드·행동 | 판정과 보완 후보 |
| --- | --- | --- |
| 입고 예정·운송중 | 예정 수량·보관 위치·외부 창고 주소, 입고 확인 → 수령 입력 | 서버는 두 상태에서 수령 완료를 허용한다. 같은 입력 진입을 오류로 단정하지 않되 예정 수량과 실제 수령 수량은 구별한다. |
| 수령 완료 `입고완료` | 활성 입고 목록에서 제거 | 입고요청과 새 입고상품은 다른 ID다. 생성된 재고의 검수로 인계하는 공통 동선이 빠져 있다. |
| 검수 대상: 재고 `보관중` | 검수 업무 조회·카드·진입 없음 | **확정된 연결 결손.** 검수 대상·수량·필요 조건은 요약하고 정상/불량 수량 입력은 기존 독립 검수 화면으로 보낸다. |
| 적재 대상 `검수완료`·`검수완료-불량포함` | 가용수량·보관 위치, 적재 확인 | 검수 후 적재 관문은 맞다. 상세 DTO의 받은·불량·예약 수량, 검수 근거·보관 조건이 공통 표시에서 빠진다. |
| 출고 할당 | 공통 업무 종류·진입 없음 | 출고예정·재고 예약·운송의뢰 상품 할당의 전문 업무는 있다. 할당 미완료·의뢰 미연결의 다음 업무를 알려주는 연결이 필요하다. |
| 피킹 `대기`·`진행중` | 수량·보관 위치, 모두 피킹 확인 | 입력 화면과 서버는 시작·완료를 구별한다. 기본 행동명도 현재 단계에 맞추는 후보다. |
| 포장 `적재완료` → `포장완료-{유형}` | 가용수량·위치, 포장 확인 | 전체 수량·표찰 조건은 입력과 서버가 확인한다. 필요한 포장·보관 조건과 불량·예약 수량의 요약이 빠져 있다. |
| 출고 인계 준비 | 출고 인계 확인, 준비 완료 뒤 활성 목록에서 제거 | 실제 효과는 `출고준비중` 출고예정 생성이다. 운송의뢰·재고 예약을 만들거나 기사에게 인계를 완료하는 행동이 아니다. 명칭과 다음 검토 경로를 구별해야 한다. |
| 실제 출고·운송 인계 `출고완료` | 공통 업무 종류 없음, 기존 전문 화면 있음 | 같은 의뢰의 실제 기사 수락·상차 전 상태·상품 할당·예약 수량을 확인한다. 준비 버튼을 단순히 완료 버튼으로 바꿀 수 없다. |
| 수량 이상 보류·재검수 회복 | 공통 예외 종류 없음 | 생명주기와 개발 검증 시나리오에는 있다. 조사한 운영 Service/UseCase에서는 별도 보류→재검수 경계를 확인하지 못했으므로 실행 범위를 먼저 확인해야 한다. 전체 프로젝트 미구현으로 단정하지 않는다. |

[입고·검수 서비스](../../../Ssalddel/Services/LogisticsProcessing/Warehouse/WarehouseOperationService.cs) 603~645·883~891·967~985행에서 수령 완료는 재고 `보관중`과 초기 가용수량(입고수량−불량수량)을 만든다. 따라서 검수 전 가용수량이 없다고 설명하지 않는다. 검수 후 적재는 [적재 UseCase](../../../Ssalddel/Application/Warehouse/적재작업UseCase.cs), 피킹은 [피킹 UseCase](../../../Ssalddel/Application/Warehouse/피킹작업UseCase.cs), 포장은 [포장 UseCase](../../../Ssalddel/Application/Warehouse/포장작업UseCase.cs)의 허용 조건을 따른다.

[인계 준비](../../../Ssalddel/Application/Warehouse/출고인계준비UseCase.cs)와 [실제 인계 완료](../../../Ssalddel/Application/Warehouse/출고운송인계완료UseCase.cs)는 다른 업무다. 이후 [출고예정 검토](../../../Ssalddel/Application/Warehouse/출고예정검토UseCase.cs)와 [창고→화물 책임 인계](../../../Ssalddel/Services/Operations/출고화물운송운영체제인계Service.cs)도 원천 원장·기존 의뢰를 결속하며 새 의뢰나 배차를 자동 생성하지 않는다.

[기존 검수 화면](../../../WarehouseManagerApp/Components/Pages/InboundInspectionRecord.razor)과 [공통 검수 입력](../../../Ssalddel.Ui.Common/Areas/App/Components/WarehouseOperations/InboundInspectionRecordScreen.razor)은 이미 있다. [일반 운송 인계](../../../WarehouseManagerApp/Components/Pages/GeneralTransportHandoff.razor)·[출고예정 검토 화면](../../../WarehouseManagerApp/Components/Pages/OutboundPlanReview.razor)을 재사용하는 방향이 적합하다. 지도 아래 새 거대 폼을 만들 필요는 없다.

창고의 실내 업무에서는 외부 주소·지도 핀보다 상품·수량·적재대·표찰·보관 조건이 현재 판단에 중요하다. 지도는 창고 선택과 외부 운송 인계에 유지하고, 카드 내부의 우선 정보만 작업에 맞게 조정하는 후보다. 실제 실내 이동 경로 데이터가 있다고 가정하지 않는다.

## 생활·다른 OS의 상태 연결

생활 역할은 공통 7개 adapter와 별도로 기존 동네 지도·선택 상세를 재사용한다. 공개 지도는 동네 대표점 집계이며 본인 권한이 있는 배송만 사적 픽업·전달·최근 위치를 다룬다. 상태 조사와 카드 정리를 이유로 공개 지도에 실제 인계 주소를 올리지 않는다.

| 업무 | 이미 있는 상태·카드 | 보완 후보와 조사 한계 |
| --- | --- | --- |
| 생활 협업 | 요청→합의→진행→완료 제안→상대 확인·완료, 취소·거절·만료. 현재 조건·내 역할·허용 행동·응답 미확정 복구와 배송·보관 인계 링크 | 내 행동 필요와 상대 확인 대기를 먼저 구별하는 요약 후보. 기존 조건·이력·공개 기록 동의를 복제하지 않는다. |
| 생활 보관 | 공간 공개 상태와 예약·보관중·반환 상태가 별도. 양쪽 입고·반환 확인과 현재 허용 행동 카드 있음 | 제공 관리와 실제 물품 보관·반환의 책임을 분리한다. 상대 확인 대기·미확정 요청의 회복 안내는 기존 흐름에 맞춘다. |
| 공동구매 수요 | 모집·확인 검토·모집 종료·인계 준비 큐, 승인 대기·승인됨/후속 연결 대기. 대상 원장 ID가 있을 때만 후속 카드 | 인계 승인과 다음 OS 원장 생성은 다른 사건이다. 승인됐다고 후속 업무 완료나 운송 진행으로 표시하지 않는다. |
| 수입 준비 | 자료수집·근거재확인·전문 검토 인계 준비·검토중·다음 단계 후보, 근거 신선도·차단 사유 | 준비 후보가 계약·결제·신고·운송 실행은 아니다. 근거 검토는 독립 화면, 실제 위치·원장 연결이 있는 인계만 지도 요약 후보로 둔다. |
| 마트 | 주문요청 `Submitted`·`Withdrawn`은 비구속 의향. 별도 창고 입고·재고·피킹·포장 허브 존재 | 요청→확정 주문→피킹·포장→음식 배달 자식의 연결 상태를 확인해야 한다. 창고 허브의 기사 인계 버튼은 준비중 비활성이라 서버 서비스 존재만으로 UI 연결 완료라고 할 수 없다. |
| 교육 | 계획·활동·보호자 확인·제출·학교 심사·인정/미인정 상태와 실제 UseCase | API OS 설명 대장 누락은 정리 후보. 전체 교육 UI 상태별 카드 판정은 미검토다. |
| 플랫폼 운영 | 공통 승인·정책·정산·예외의 설명 대장 있음 | 음식 운영자 카드를 플랫폼 전체 완료 근거로 사용하지 않는다. 다른 관리자 업무는 별도 조사 필요다. |

생활의 근거는 [협업 상태](../../../Ssalddel.Contracts/Common/Community/생활협업Dtos.cs), [협업 UseCase](../../../Ssalddel/Services/Community/생활협업UseCase.cs), [보관 상태](../../../Ssalddel.Contracts/Common/Community/생활보관공간Dtos.cs), [보관 서비스](../../../Ssalddel/Services/Community/생활보관공간Service.cs)다. 실제 [지도 선택 패널](../../../Ssalddel.Ui.Common/Areas/App/Components/Community/Exchange/NeighborhoodMapWorkspacePanel.razor)은 기존 [협업 상세](../../../Ssalddel.Ui.Common/Areas/App/Components/Community/Exchange/NeighborhoodCollaborationDetail.razor)와 [보관 상세](../../../Ssalddel.Ui.Common/Areas/App/Components/Community/Exchange/NeighborhoodStorageDetail.razor)를 재사용한다. 30초 갱신은 배송 중심이며 모든 생활 상세의 상대 변경이 같은 주기로 자동 갱신된다고 확대하지 않는다.

공동구매의 [모집 상태](../../../Ssalddel.Contracts/Common/Orderer/공동구매수요모집OsDtos.cs)와 [수입 준비 상태](../../../Ssalddel.Contracts/Common/Orderer/같이수입준비OsDtos.cs)는 별도 계약이다. [주문자 집단 상세](../../../OrdererApp/Components/GroupPurchase/GroupPurchaseGroupDetailScreen.razor)는 대상 원장 ID에 따라 인계 카드와 미연결 안내를 구별한다.

마트의 [주문요청 계약](../../../Ssalddel.Contracts/Mart/마트주문요청Dtos.cs)과 [주문요청 상세](../../../Ssalddel.Ui.Common/Areas/App/Components/Mart/OrdererMartOrderRequestDetailPanel.razor)는 의향과 실제 실행을 분리한다. [창고 마트 허브](../../../Ssalddel.Ui.Common/Areas/App/Components/WarehouseOperations/SsalddelMartWarehouseWorkflowHub.razor)의 기사 인계 준비 상태도 별도로 확인했다. 프랜차이즈 확인 경로의 [Simulation controller](../../../Ssalddel.Simulation.Hosting/Controllers/프랜차이즈공급망SimulationController.cs)는 세션 표현 경계다. 이를 운영 공급 계약·발주·배송의 실제 권위나 새 OS의 완성으로 승격하지 않는다. 이번에 프랜차이즈 전체 운영 코드를 전수 조사하지 않았다.

## 확인한 재현

현재 제품의 음식점·음식 기사 표시 adapter를 읽기 전용 예시 DTO로 실행했다. 다음 결과는 브라우저나 휴대폰 업무 완주가 아니라 실제 표시 코드의 반환값을 확인한 것이다. 서버 저장 요청은 실행하지 않았다.

| 입력 상태 | 현재 기본 안내 | 판정 |
| --- | --- | --- |
| 음식점 픽업 대기, 준비 완료 시각 있음 | 기사에게 현재 준비된 음식을 인계해 주세요 | 준비된 미픽업 예시의 안내다. 실제 유효 배차를 결속한 서버 응답 사례는 아니므로 그 조건은 별도 대조한다. |
| 음식점 픽업 완료, 준비 완료 시각 있음 | 기사에게 현재 준비된 음식을 인계해 주세요 | 이미 인계한 단계에서 인계를 다시 안내한다. 상태 분기 보완이 필요하다. |
| 음식점 전달 완료 | 처리된 주문 내역을 확인해 주세요 | 앞선 인계 안내는 없어지지만 전달 완료·주문자 수령 확인의 구분은 전문 화면보다 약하다. |
| 음식 기사 재조리 2회차, 가게 도착, 준비 미완료 | 재조리 음식을 픽업해 주세요 | 픽업 버튼은 비활성이다. 기본 안내는 준비 완료를 기다리는 상태와 맞지 않는다. |
| 음식 기사 재조리 2회차, 가게 도착, 준비 완료·픽업 허용 | 재조리 음식을 픽업해 주세요 | 입력 DTO의 허용 행동과 일치한다. 실제 서버의 DTO 생성까지 확인한 사례는 아니다. |

근거: [음식점 기본 안내](../../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Food/RestaurantRoleWorkspaceAdapter.cs) 77~99행, [음식 기사 기본 안내](../../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Food/FoodDriverRoleWorkspaceAdapter.cs) 223~272행. 재현 원문과 판정은 Git 제외 `artifacts/local/os-state-card-audit-r17/adapter-probe.log`, `probe-verification.json`에 보관한다.

## 보완 우선순위

| 순서 | 최소 보완 범위 | 완료를 판단할 기준 |
| --- | --- | --- |
| 1 | 화물 예외의 재조회 투영과 현재 허용 행동 결속 | 신고→재조회·앱 복귀 뒤에도 사건·담당·통제 범위가 유지된다. 정산 보류와 운송 중단을 구별하고 안내·버튼이 서버 조건과 맞는다. |
| 2 | 창고 수령→검수, 인계 준비→출고예정 검토→실제 인계의 원장 연결 | 새 재고·기존 의뢰 ID로 해당 전문 업무에 진입한다. 준비 완료를 실물 인계 완료로 보이지 않는다. |
| 3 | 음식의 현재 조리 회차·기사 수행·배차 예외에 따른 안내 | 픽업 후 인계 지시가 없고, 재조리 미준비에는 기다리는 이유가 나온다. 서버 가능 행동과 안내가 일치한다. |
| 4 | 현재 작업에 필요한 기존 정보와 완료 후 동선 | 화물 시간창·증빙 조건, 창고 수량·보관 조건, 음식점 요청사항을 필요한 단계에 배치한다. 정산·이력은 독립 화면으로 연결한다. |
| 5 | OS–원장 상태–역할–기존 페이지–허용 행동의 공통 대조표 유지 | 실제 상태 코드·소유 서비스·갱신 시각·실패 복구 경로를 결속한다. 생활·공동구매·마트의 인계는 원천 ID가 있는 경우만 다음 단계로 연결한다. |

1~3은 상태·안내의 정합성과 끊긴 업무를 먼저 다루는 순서다. 4의 카드 수·순서·강조는 사용자가 결정할 부분이다. 5는 새 역할 화면을 늘리는 일이 아니라 현재 있는 흐름의 대응 근거를 유지하는 작업이다.

## 검증 범위

이번에 실행한 제품 동작은 읽기 전용 표시 adapter 두 개의 다섯 사례뿐이다. 나머지 판정은 현재 코드·계약·대표 전문 화면의 소스 대조다. 기존 시험 파일이나 r16 캡처·통과 기록은 참고 근거이며 이번 상태 전수 실행의 증거가 아니다.

모든 상태의 실제 UI, 서버/DB 업무 완주, 휴대폰 설치·위치·지도 SDK, Azure 통신, 실제 정산·입금은 이번 조사에서 검증하지 않았다. 상태별 후속 구현 시에는 정상 전이와 보류·재조회·복귀·완료 직후를 별도로 확인해야 한다. 문서 검증 결과와 작업 범위 보존 기록은 Git 제외 `artifacts/local/os-state-card-audit-r17/` 및 `artifacts/local/validation/`에 남긴다.

## 후속 카드 결정 방법

역할·상태마다 아래 항목을 결정하면 카드 배치를 한 목적에 맞출 수 있다. 기존 [r16 검토표](role-state-card-review-r16.md)의 기본·상세·주 행동을 이 조사에서 확인한 서버 상태와 함께 검토한다.

| 항목 | 결정할 내용 |
| --- | --- |
| 사용자의 질문 | 지금 어디로 가거나 무엇을 확인·처리해야 하는가 |
| 기본 카드 | 현재 대상·장소·단계, 행동에 필요한 수량·금액·시간·요청 사항 |
| 상세 정보 | 같은 업무의 긴 기록·메뉴 전체·연락처·비용 내역 중 필요한 것 |
| 주 행동 | 서버가 현재 허용한 다음 행동 하나 또는 기다리는 이유 |
| 예외 카드 | 정상 진행을 막는 조건, 현재 담당자, 다음 확인·회복 행동 |
| 다른 화면으로 인계 | 독립된 입력·증빙·검수·정산·정책 업무와 돌아오는 경로 |
| 확인할 전이 | 앞 단계 완료 직후, 미준비·보류, 오류 후 재조회, 완료 후 다음 업무 |

카드 수·문구·강조 순서는 이번 조사에서 최종 승인하지 않는다. 단계 판단의 오류를 바로잡는 것과 사용자가 원하는 정보 배치를 결정하는 것을 구별한다.
