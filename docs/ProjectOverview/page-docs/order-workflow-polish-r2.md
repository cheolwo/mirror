## 페이지 → 코드/API → DB

- 주문 작성은 기존 `OrdererRestaurantWorkspace`·`OrdererFoodOrderComposer`와 `음식주문작성ViewModel`을 소비한다. 기존 공개 메뉴 GET과 `POST api/v1/food-orders`를 사용하며 입력 오류·가격 변경 응답을 구별한다.
- 서버 메뉴 검증은 최신 메뉴를 금액의 권위로 유지한다. 변경 금액 확인 여부는 요청의 추가 선택 필드로 구분하고 기존 소비자의 호환을 유지한다. 본인 요청 ID로 접수된 주문은 최신 메뉴 재검증보다 기존 결과 조회를 먼저 한다.
- 음식점은 기존 `OrderDetail`과 `음식점주문DeskService`·주문 진행 변경 API를 사용한다. 미확정 요청 전체를 보존하고 서버가 반환한 주문을 안내에 적용한다.
- 기존 음식 주문·상품·진행 이력·운영 활동 원장을 재사용하며 DB 스키마와 요금·정산 정책을 변경하지 않는다.

## 구현된 복구 흐름

- 주문 작성은 `메뉴가격확인필요=true`로 보낸다. `FOOD_MENU_PRICE_CHANGED`·`FOOD_MENU_UNAVAILABLE`의 확정400은 미확정 저장 요청을 해제하고 기존 수량·수령 입력을 보존한다. 최신 메뉴 확인은 GET만 실행하고 이전/현재 단가를 보여 준다. 새 가격을 확인하는 명시 버튼에서만 새 요청 ID를 만들어 POST한다.
- 삭제·품절 메뉴를 선택에서 제외하면 메뉴명을 안내한다. 음식점이 더 이상 공개되지 않으면 다른 음식점으로 돌아가는 버튼을 제공한다. 연결 실패에는 초안을 보존한다. 접수 미확정 후 동일 요청 재제출에서 나온 메뉴 오류도 같은 확인 흐름에 연결한다.
- 이미 접수된 주문자+요청 ID는 최신 메뉴 검사보다 먼저 기존 주문을 반환한다. 기존 클라이언트의 선택 필드 기본값은false이며 기존 가격 정본화 동작을 유지한다. 저장 후 일반 예외를 입력 거절400으로 바꾸지 않는다.
- 음식점 조리시간 변경은 원래 작업·요청 ID·분·사유·revision을 현재 프로세스 메모리에 함께 보존한다. 재시도는 GET 정본부터 확인하고 이미 처리된 요청이면 POST하지 않는다. 미접수면 원래 입력을 다시 제출한다. 충돌409 뒤 정본 조회가 성공하면 다음 명시 변경에 새 ID를 사용한다.
- 성공 안내와 입력 시간은 서버가 반환한 적용값이다. 같은 계정의 인증 만료에는 미확정 요청을 보존하고 다른 계정·명시 로그아웃에는 폐기한다. 음식점 앱 프로세스 종료 후의 영속 복구는 이번 범위가 아니다.
- 음식점의 기존 통신 재시도 실행기는 전송 실패에 같은 요청 객체를 한 번 자동 재시도한다. 이번 보완은 그 ID와 전체 입력을 유지한다. 두 시도가 모두 미확정이면 다음 사용자 시도에서 정본 GET을 먼저 수행하며 다른 입력으로 자동 POST하지 않는다.
