# 판매자의 주문자 수요 허브

[페이지 원칙](../../../../Architecture/WholeRoadmapPagePrinciple.md) · [후속 구조 정리 r2](../../../../AI/Planning/공통/PLAN-OPERATIONS-REFACTOR-SRP/implementation.r2.md)

## 페이지 책임

| 항목 | 기록 |
| --- | --- |
| 주 사용자·페이지/소스 | 판매자. 기존 `/seller/orderer-demand`, SellerApp/Components/Pages/OrdererDemand.razor. PageKey·route를 신설/변경하지 않는다. |
| 대상·진입 문맥 | 판매자에게 허용된 개별 주문·공동 주문·집단 수요·수출 원장과 현재 검색. |
| 한 문장 목적 | 판매자가 현재 주문자 수요를 구분해 보고 대응할 기존 업무 흐름을 선택한다. |
| 완료 결과·상태별 주 행동 | 허용된 수요 목록/진행을 확인하고 해당 전문 업무로 진입한다. 이 허브에서 계약·결제·출고를 완료한 것으로 취급하지 않는다. |
| 기본 정보 | 수요 유형·상품/진행 요약·검색 결과·기능 미활성/조회 오류·기존 대응 진입. |
| 보조 정보 | 같은 수요의 진행률·상태와 다음 대응 문구. 기존 네 유형의 배치·조건·문구를 유지한다. |
| 독립 업무·제외 정보 | 개별 주문 처리·공동 원장 실행·수출 검토는 각각의 기존 페이지와 권한을 따른다. 참여자 이름·상세 주소·개별 주문량을 새로 노출하지 않는다. |
| 진입·실패·복귀 | 현재 조회 순서와 부분 반영을 유지한다. 집단수요/수출의 403·404만 기존 미활성 안내로 표시하며 일반 실패를 빈 목록 성공으로 바꾸지 않는다. timer 폐기는 진행 중 API를 새로 취소하지 않는다. |
| 코드·API·DB | Razor → 내부 ReadSession/집단수요 Projection → 기존 네 service/client → 각 전문 원장 조회. 표시 계층은 DB를 직접 조회하거나 원장 상태를 확정하지 않는다. |
| 책임 판정·검증 | 같은 목적의 진입 허브. 내부 조회/polling과 순수 표시 계산을 분리하되 독립 업무를 이 화면에 추가하지 않는다. fake service 회귀와 실제 UI/모바일/운영 증거를 구분한다. 실행 결과는 r2 구현 문서가 소유한다. |

## 변경 전후 정보 배치

기존 네 수요 분류·검색·요약·진입은 같은 위치에 둔다. Session은 응답·오류·조회 순서와 timer를, Projection은 검색/정렬·진행률·라벨을 소유한다. 새로운 화면이나 조회/실패 정책을 도입하지 않는다.
