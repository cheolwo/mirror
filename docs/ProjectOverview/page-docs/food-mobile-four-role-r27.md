# 음식 배달 4역할 모바일 시험 마감 r27

2026-10-07. 사용자가 승인한 보완 순서는 시험 서버 자동 제안·직접 수락 → 상태별 필요한 정보와 주 행동 → 주문 작성 화면부터 네 역할 완주 → APK와 휴대폰 시험이다. 최신 답변 `지금은 로컬 검증까지만`에 따라 애저 조회·배포는 제외하고 로컬 서버·공통 화면·USB 시험 APK를 준비한다. 기본은 본인용 Simulation 시험이며 기존 [페이지 단일 책임](../../Architecture/WholeRoadmapPagePrinciple.md)과 [역할 앱 시각 기준](../../Architecture/RoleAppVisualDesignStandard.md)을 따른다.

## 구현 전 페이지 책임 카드

| 화면 | 사용자 질문·결과 | 기본 정보·주 행동 | 보조 정보·복귀 |
| --- | --- | --- | --- |
| 주문자 음식 주문 상세 | 지금 무엇을 기다리거나 확인해야 하는가? | 현재 주문 상태와 통신 상태. 수령 대기에는 기존 수령 확인 행동을 상품 상세 앞에 한 번 표시 | 상품·수령 정보·진행 이력·기존 수행 조건/지원 기능은 보존. 목록·지도 복귀 유지 |
| 운영자 음식 주문 추적 | 현재 어느 담당이 무엇을 처리해야 하는가? | 현재 단계·다음 담당·허용 행동. 재조회 실패 뒤 남은 내용은 이전 확인 정보임을 표시 | 금액·상세 이력은 기존 구성 유지. 실패 시 새로고침·목록 복귀. 최신 조회 전 행동 차단 보존 |
| 음식점 현재 주문 | 지금 인지·조리·준비 중 무엇을 해야 하는가? | 메뉴·수량·요청과 서버가 허용한 현재 행동. 기사 선행 배정 조건 유지 | 기존 수신함·상세·뒤로가기 사용. 별도 신규 페이지 없음 |
| 음식 기사 현재 업무 | 지금 어느 장소에서 무엇을 처리해야 하는가? | 픽업 전 음식점/픽업 정보, 픽업 후 전달지→고객 요청→주문. 현재 목적지·주 버튼 | 기존 지도 중심·접기/펼치기·완료 목록/상세·지원 화면 유지. 완료 후 다음 업무 갱신 검증 |

화면 상태·허용 행동·금액은 서버 응답이 권위다. 조회 실패를 최신 성공처럼 표시하거나 UI가 다음 업무 상태를 임의로 확정하지 않는다. 기사 전달 완료와 주문자 수령 확인, 사건 종결과 실제 지급을 분리한다. r24/r25의 기존 기능·작업은 보존한다.

실제 작성 화면 연결에서 모의 서버의 주문 허용과 화면의 판매자 인증 요구가 불일치함을 확인했다. 기존 안내 응답에 `ExecutionModeCode`를 가산하고 서버가 `Simulation`을 명시한 최신 안내에서만 판매자 판본 없는 안내 확인을 허용한다. 구형 응답·운영 모드·조회 실패는 이 예외를 허용하지 않는다. 판매자는 미확인 상태로 표시하며 실제 신원 확인 결과나 운영 거래 자격으로 승격하지 않는다. 동의는 사용자의 체크로 받고 기존 운영 서버 검증은 보존한다.

## 시험 환경과 완료 경계

- Staging+Simulation의 전용 시험 DB·허용된 시험 주문/주소/기사에만 음식 자동 제안·만료·재추천을 연결한다. 운영 정책과 실제 경로 검사에는 예외를 추가하지 않는다.
- 시험용 거리·주소는 명시적 시험 출처를 보존하고 실제 지도 요청/운행 결과로 표현하지 않는다. 기사 수락·조리·픽업·전달·수령 확인은 사용자가 실제 화면에서 수행한다.
- 주문 작성 화면부터 같은 주문·배차 ID를 화면/client/HTTP/DB에 결속한다. 서버 준비 상태, 모바일 폭, 오류/재진입/중복 방지, 고객 상세 3일 제한을 검증한다.
- 구현/시험/브라우저 화면/APK 생성/에뮬레이터/애저 HTTPS/실제 휴대폰은 각각 별도 근거로 보고한다. 실제 애저 대상·로그인·기기 연결이 없으면 완료를 대신 인증하지 않는다.
