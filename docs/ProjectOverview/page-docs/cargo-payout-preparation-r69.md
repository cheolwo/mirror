# 화물 기사 운송대금 조회 r69

2026-10-14. [페이지 단일 책임 기준](../../Architecture/WholeRoadmapPagePrinciple.md)과 [역할 앱 시각 기준](../../Architecture/RoleAppVisualDesignStandard.md)을 적용한다. 기존 월 정산의 플랫폼 이용료 의미는 유지하며 운송대금 조회를 독립 업무로 연결한다.

## 페이지 책임

| 항목 | 기록 |
| --- | --- |
| 주 사용자·페이지/소스 | 화물 기사, DriverApp의 `/driver/payouts` 목록과 `/driver/payouts/{TransportId}` 상세 |
| 대상·진입 문맥 | 사용자 메뉴 → 기존 배달 내역 → 운송대금 목록. 상세는 현재 조회 연·월과 운송 ID를 보존한다. |
| 한 문장 목적 | 기사가 완료한 운송의 약정 지급 예정 운임과 현재 지급 준비·보류 이유를 확인한다. |
| 완료 결과·상태별 주 행동 | 조회 성공이면 상세 확인, 오류이면 같은 월 재조회, 인증 필요이면 기존 독립 로그인 후 원래 경로 복귀. 지급 실행은 제공하지 않는다. |
| 기본 정보 | 완료일, 운송 식별자, 지급 예정 운임/미확정, 지급 준비 상태와 서버가 알려준 보류 이유. 미확정을 0원으로 채우지 않는다. |
| 보조 정보 | 상세에 원천 의뢰, 화주 수납·운임 정산 상태와 현장수금 여부. 주소·연락처·사진 원문은 이 조회 DTO에 없으며 추가 조회하지 않는다. |
| 독립 업무·제외 정보 | 월 플랫폼 이용료, 계좌 관리와 운송 수행은 기존 독립 화면으로 남긴다. 승인·송금·운영 활성화·다른 기사 조회는 제외한다. |
| 진입·실패·복귀 | 초기 로딩/정상 빈 목록/연결·기능·권한 오류/로그인/상세 미발견을 구분한다. 기간·선택·계정 변경과 이탈 후 늦은 응답은 폐기한다. 상세 복귀는 같은 월 목록이다. |
| 코드·API·DB | Razor → `기사운송대금PageViewModel` → `DriverPayoutPreparationApiService` → 기존 `GET api/v1/driver/payout-preparations?year=&month=` → `기사지급준비UseCase` → 완료 운송·화주 의뢰·운임 구성·정산계좌·비정상 사건. 읽기만 한다. |
| 책임 판정·검증 | 목록/선택 상세는 같은 조회 목적의 독립 경로다. 구현 전 책임 검토 완료. 코드·시험 결과, 실제 렌더·APK·단말·입금 증거는 통합 검증에서 별도로 보고한다. |

## 변경 전후 정보 배치

| 정보 또는 행동 | 사용자에게 필요한 이유 | 변경 후 위치 | 근거 |
| --- | --- | --- | --- |
| 원장 운임 | 기존 운송 이력 확인 | 기존 배달 내역 유지 | 원장 운임과 기사 지급 예정 운임은 다르다. |
| 운송별 지급 예정 운임 | 이번 운송에서 받을 금액의 확인 | 독립 운송대금 목록·상세 | 기존 지급 준비 API의 nullable 금액을 그대로 표시한다. |
| 지급 준비/보류 | 아직 지급 준비가 안 된 이유 확인 | 목록 상태·상세 이유 | 서버 `ReadinessCode`·`ReadinessMessage`를 사용한다. |
| 실제 지급 여부 | 준비·수금·입금을 혼동하지 않음 | 목록 안내와 상세 | 현재 API는 지급 준비 조회이며 송금 완료를 증명하지 않는다. |
| 월 이용료 | 플랫폼 이용료 확인 | 기존 월 정산 유지 | 기존 이용료 원장/계산을 바꾸지 않는다. |

목록의 연·월은 기존 서버의 UTC 월별 조회 계약이며 완료 시각은 기존 한국시간 표시기를 사용한다. 월 경계를 임의로 다시 계산하거나 과거 금액을 변경하지 않는다. 같은 월에 없는 운송 상세는 미발견으로 표시하고 다른 월이나 다른 운송으로 대체하지 않는다. 조회 실패를 정상 0건으로 숨기지 않는다.
