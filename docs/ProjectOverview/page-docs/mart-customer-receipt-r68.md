# 마트 주문자 수령과 문제 보류 r68

## 사용자의 질문과 책임

‘내가 주문한 물품을 전부 받았는가, 일부가 없거나 파손됐는가’를 실제 주문자 본인이 확인하는 서버 책임이다. 기사 전달 기록과 다른 사실이며 작업자 보수·지급 신고·은행 이체를 자동으로 완료하지 않는다. 현재는 화면을 추가하지 않고 API와 전문 근거를 준비한다.

## 상태와 다음 행동

기사 전달 전에는 수령 확인을 열지 않는다. 정확한 주문·배송시도·사용한 전표·전량 출고 이력이 갖춰지면 실제 주문자가 전량 수령 또는 문제 신고를 선택한다. 수령 확인은 본인의 진술을 검증된 전달 원천에 연결하는 것이며 운영자·기사·판매자가 대신할 수 없다.

수령 확인 뒤에도 부분/누락/파손 신고는 별도의 보류로 기록한다. 기존 수령 근거와 발생 보수·지급 신고를 지우지 않고 새 양수 지급을 보류한다. 보류 해제·분쟁 종결·환불 확정은 이 API에 없다. 근거가 없거나 현재 출고·판본·당사자가 다르면 안전하게 확정하지 않고 최신 정본 확인이 필요하다는 이유를 반환한다.

응답 유실은 같은 주문의 요청 결과를 먼저 확인한다. 같은 요청 ID의 다른 입력은 충돌이며 같은 의미는 재사용한다. 요청 결과 404를 확정 거절로 표시해 새 요청을 유도하지 않는다.

`ReceiptRecorded`·`HoldRecorded`는 저장된 본인 요청의 존재이고 `ReceiptConfirmed`·`PaymentReleaseReady`는 현재 전문 원본까지 검증한 결과다. 이후 취소·출고 변경으로 현재 검증에 실패해도 원요청의 접수 사실은 조회할 수 있다. 손상된 근거는 409로 보류하고 검증되지 않은 보류 상세는 표시하지 않는다.

## 정산과 확인 한계

수령량은 상품별 출고 수량을 한 번 합산한다. 피킹과 포장 작업량의 합은 고객 수령량이 아니다. 고객 수령 근거는 성과금용 `RewardOutcome`이나 매출 근거와 구분한다. 수령·보류가 사전 합의 판본·단가를 바꾸지 않으며 기존 양측 확인된 보수의 명시적 지급 신고만 관문을 통과할 수 있다.

수령 API의 `PaymentReleaseReady`는 수령 측 요건을 뜻한다. 실제 보수 지급 신고는 정산 API가 작업 근거·금액·양측 확인·부담자·잔액 등 전체 조건을 다시 검사한다. 이 값만으로 지급 버튼이나 실제 이체 완료를 표시하지 않는다.

운영 기본 OFF·Simulation을 유지한다. 현재 검증 상태는 [수용 설계](../../AI/Planning/공통/PLAN-OPERATIONS-NEIGHBORHOOD-MICRO-HUB/mart-customer-receipt.implementation.r68.md)와 [변경 기록](../../Changes/2026-10-13-mart-customer-receipt-r68.md)을 따른다. 실제 앱 화면·HTTP/단말·공유 DB·계약·은행 입금은 별도다.
