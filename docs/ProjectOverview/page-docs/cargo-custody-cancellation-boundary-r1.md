# 퀵·화물 수락 취소와 물품 보유 보호

2026-10-16. 기존 `POST api/v1/driver/dispatch-actions/{requestId}/cancel-acceptance`의 서버 책임을 보완한다. 새 취소·환불·반송 요금이나 관리자 승인 권한을 만들지 않는다.

| 항목 | 책임 |
| --- | --- |
| 사용자·질문 | 인증된 담당 기사가 아직 물품을 받기 전의 수락을 취소할 수 있는가? |
| 정상 결과 | 상차 전 현재 담당자에게만 수락 취소를 허용하고 같은 의뢰를 재추천/공개 콜 대기로 전환한다. 수납·기존 보수·정산 기록은 유지한다. |
| 물품 보유 이후 | 상차 완료·운송 중·하차지 도착·인수 완료 또는 픽업/도착 시각이 있으면 일반 수락 취소를 차단한다. 원장·담당 기사·물품 보유·사진 기록을 지우지 않고 현재 운송의 문제 신고에서 반납·재전달 등 다음 처리를 확인하도록 안내한다. |
| 현재 담당자 | 확정 기사와 이전 추천 대상이 다르면 확정 기사가 우선한다. 다른 수행자에게 연결된 운송이나 일반 회원 전용 배송을 이 API에서 취소하지 않는다. |
| 업무 상태 | 확정·배차 확정·픽업지 이동·상차지 도착처럼 확인된 상차 전 단계만 허용한다. 큐의 확정 표식만으로 종료·취소·미확인 상태를 허용하지 않는다. |
| 동시변경 | Command의 사전 검사는 최종 허가가 아니다. 실제 전환 서비스가 최신 원장과 원의뢰를 재조회하고 Serializable 트랜잭션 및 기존 RowVersion을 사용한다. 기존 미저장 변경을 덮어쓰지 않고, 동시 변경 충돌은 재확인으로 남긴다. |
| 공식 문제·보류 | 비정상 운송 사건의 검토 대기·업무 일부/전체 보류·정산 보류가 남으면 취소로 해제하지 않는다. 기존 사건의 검토 담당·권한과 별도 정산 재검사를 유지한다. |
| 실패·복귀 | HTTP 409의 `FreightCustodyRecoveryRequired` 또는 `FreightCancellationStateChanged`를 반환한다. 수락 취소 저장과 후속 추천은 별도 결과이며 추천 실패가 이미 저장된 취소를 허위 실패로 바꾸지 않는다. |
| 다른 업무 | 일반 수락 취소는 반납 수령·재전달·사건 종결·고객 환불·기사 지급이 아니다. 기존 분산 배송 반납은 공간 담당자의 바코드·수량·사진 관문을 계속 사용한다. 일반 퀵의 별도 반송지/추가 보수 합의 정책은 자동 확정하지 않는다. |

## 연결

- `배차응답가능정책.수락취소가능`은 최신 운송의 상태·담당자·실물 인수 사실을 읽는 순수 정책이다.
- `배차수락취소CommandHandler`는 기존 참여자 실행 권한을 검사하며, 실제 전환 서비스의 거절 사유·409를 보존한다.
- `배차대기원장전환Service.AcceptanceCancellation.cs`는 직접 호출과 사후 이벤트 호출 모두 같은 보호 경로를 사용한다. 일반 초기화 정책은 음식 중단의 소비 경계를 위해 바꾸지 않는다.
- 상차 완료는 기존 `기사운송상태전이Service`가 `출발_픽업`을 기록하며, 사진 업로드·소유 검사는 기존 상차/하차 Handler가 맡는다.
- 비정상 운송 사건 결정·정산 보류 해제는 기존 관리자 Controller/UseCase, 지급 재원·실지급은 기존 정산 원장/전문 기능이 소유한다.

## 검증 경계

`CargoAcceptanceCancellationCustodyTests`는 상차 전/후·모순된 시각·다른 기사·원의뢰 진행·전용 배송·사건 보류·미저장 변경·추적 사본·사전검사 후 픽업이 먼저 저장되는 순서, 실제 SQLite의 상차 전 취소를 대조한다. 코드·시험과 실제 서버 HTTP·MySQL 동시 실행·APK·기기·실물 반납/재전달·운영 금융은 각각 별도 증거다. 화면 구조를 바꾸거나 운영 기능을 활성화하는 작업이 아니다.
