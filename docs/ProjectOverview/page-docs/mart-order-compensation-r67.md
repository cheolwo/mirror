# 주문별 원가·보수 조회와 마트 작업 정산 r67

## 책임과 현재 범위

사용자의 질문은 ‘이 주문을 위해 내가 어떤 작업을 했고, 어떤 비용이나 보수가 연결되어 있는가’다. 이번에는 앱 화면을 추가하지 않고 기존 원장·정산 아래 서버 조회와 작업 완료 근거 연결을 보완한다. 현재 구현과 검증 상태는 [r67 수용 범위](../../AI/Planning/공통/PLAN-OPERATIONS-NEIGHBORHOOD-MICRO-HUB/mart-order-compensation.implementation.r67.md)를 따른다.

원주문은 Mongo의 포함 참조가 원본이다. 하위 상태·금액은 SQL의 전문 업무 및 정산에서 읽고 원주문에 복제하지 않는다. 기존 정산 설정의 기본 OFF와 Simulation 전용 경계를 유지한다. 이 조회를 호출하는 것만으로 약정·채무·지급·입금·외부 효과를 만들지 않는다.

## 금액을 해석하는 방법

- 상품 대금은 상품 대금이며 플랫폼 수입 전체가 아니다. 주문 접수는 확정 매출이나 수금이 아니다.
- 작업자 보수는 실제 확인 처리량과 사전 합의 단가에 연결한다. 단가 미정은 null/합의 대기이며 무료 약정의 0원과 구분한다.
- 입고·보관 원가 귀속은 원천 비용을 주문별 사용 수량에 나눈 회계 기록이다. 원천 작업자에게 다시 지급할 채무가 아니다.
- 발생액·확정액·지급 신고·수령 진술은 각각의 정산 사실이다. 은행 입금을 확인했다는 뜻이 아니다.
- 확인된 부분 금액을 전체 손익으로 표시하지 않는다. 플랫폼 수익·비용 근거가 충분하지 않으면 손익은 미확인으로 둔다.

## 작업 근거와 보류

배정자와 실제 완료자를 구분하고 신규 완료 근거를 동결한다. 포장에 실제 시작 명령이 없는 현재 구조에서는 같은 상품의 선행 피킹 시작을 보수적인 **사전 합의 기한**으로 사용한다. 이것을 실제 포장 시작시각이라고 표시하지 않는다. 근거 없는 과거 완료·불명확한 주문 연결·작업 뒤 체결한 단가 판본은 자동 보수 인증에 사용하지 않는다.

기존 포장 작업의 표시·재처리 계약에 쓰이던 시작시각 기본값은 보존한다. 이 값이 완료시각으로 채워져도 새 완료 근거의 실제 포장 시작시각은 null이며, 사전 합의 기한과도 구분한다.

완료 재요청과 이후 투영은 이미 기록한 완료 근거를 바꾸거나 같은 작업을 다른 약정에서 다시 청구할 수 없도록 검사한다. 고객 인계·배송 실패는 과거 작업 근거와 이미 발생한 보수를 지우지 않는다. 이 상태의 지급 가능 여부는 기존 정산 관문이 별도로 판단한다.

마트 고객 수령의 전문 근거를 이번에 추가하지 않으므로 마트 보수의 지급 해제는 후속이다. 이번 완료 범위는 작업 완료→보수 발생 근거→본인 조회다. 실제 완료자와 배정자가 다른 경우에는 배정자에게 잘못 청구하지 않도록 보류한다.

## 권한과 확인 한계

원주문을 볼 수 있어도 타인의 정산이나 전체 Lot 비용을 받지 않는다. 정확히 연결된 본인 작업자에게는 본인 보수 확인에 필요한 최소 정보만 제공한다. 입고 원가 귀속은 그 주문의 실제 비용 부담자 범위로 제한한다. 다른 주문의 작업·주소·가격을 조회에 섞지 않는다.

로컬 시험과 실제 운영은 구분한다. 실제 단말·은행 입금·공유 DB·Azure·GCS·Unity·배포·커밋·푸시는 이번 구현의 완료 근거가 아니다.
