# 생활·음식 배달 자동 수행과 조건 확인 r25

2026-10-07. [승인 범위](../../AI/Planning/공통/PLAN-OPERATIONS-NEIGHBORHOOD-MICRO-HUB/fulfillment-routing.implementation.r25.md)는 기존 생활 배송 및 음식 주문의 작성·상세와 음식점의 배달비 지원 설정을 보완한다. 첫 연결은 Simulation이며 실제 청구·입금·업체 접수의 증거와 구별한다.

| 페이지/역할 | 한 가지 업무 질문·결과 | 기본 정보·주 행동 | 보조 정보·실패·복귀 |
| --- | --- | --- | --- |
| 생활 배송 작성/이용자 | 내 비용·시간 조건 안에서 배송을 접수할 수 있는가 | 본인 비용 상한·희망 완료 시각·허용 수행처/정보 제공 범위·자동 접수 동의 → 접수 | 기존 인계 입력·거래보호 안내를 보존. 조건 미충족/조회 실패는 초안과 멱등 ID를 유지하고 재조회 |
| 음식 주문 작성/주문자 | 메뉴와 내 배달비 부담 조건으로 주문할 수 있는가 | 서버 메뉴 합계·음식점 정액 지원·본인 잔여 부담 상한·자동 접수 동의 → 주문 | 메뉴 가격 재확인·판매자/거래보호는 별도 동의. 기능 미지원·지원 설정 판본 변경은 재확인하고 자동 전송하지 않음 |
| 생활/음식 상세/주문자 | 선정된 수행은 어디까지 진행됐고 내가 무엇을 해야 하는가 | 선정 처리처·이유·모의 구분·분담 금액·현재 단계·최신 확인 → 해당 상태의 서버 허용 행동 | 긴 이력은 펼침. 결과 불명확/취소 중에는 같은 시도 재확인, 중복 접수 금지. 기존 목록·지도에서 같은 상세로 복귀 |
| 음식점 주문 상세/음식점 | 유효한 기사 확보를 확인하고 조리를 시작할 수 있는가 | 주문 확인 → 배정 확인 → 명시적 조리 시작·준비 완료 | 공급자 접수와 기사 배정을 구분. 해제/오래된 배정은 조리 행동을 열지 않음. 조리·재조리 이력 보존 |
| 음식점 지원 설정/음식점 | 이후 주문에 얼마의 배달비를 지원할 것인가 | 인증된 내 매장·정액 지원액·현재 판본·명시적 설정 동의 → 저장 | 주문 조리 명령과 독립된 설정 진입/복귀. 저장 오류는 원 입력 유지. 이미 접수된 주문의 동결 지원액은 변경하지 않음 |
| 자체 기사 업무/기사 | 내 제안을 수락하고 배달을 수행할 수 있는가 | 기존 제안 금액·경로·현재 상태·수락/픽업/전달 | 공급자 후보 선정과 기사 개인의 수락은 별개. 모의 외부 배달을 기사 제안·지급 완료로 보여주지 않음 |

공통 UI는 실제 source API의 성공/재조회 뒤 같은 주문을 표시한다. 음식점 지원은 실제 출금·입금이 아니며 고객 배달비와 내부 기사 지급액을 합치지 않는다. 공개 지도와 예시 캡처에는 정확한 고객 주소·연락처·업체 토큰을 추가하지 않는다. 외부 기사 위치가 없으면 없는 상태를 표시하고 내부 위치로 대체하지 않는다.

기존 공통 컴포넌트와 역할 앱 경로를 재사용하고 별도의 플랫폼 홈을 만들지 않는다. 소비 클라이언트 컴파일, synthetic 공유 Razor 렌더, HTTP/DB 상태 전이, 단말·운영 실행은 각각의 검증 결과로 보고한다. 320/390px의 조건 입력·분담 금액·진행·오류·복귀를 검증한다. 실제 결과는 [변경 기록](../../Changes/2026-10-07-fulfillment-routing-r25.md)에 결속한다.

로컬 검증은 실제 공유 Razor/VM의 13상태×2폭, 26장면 통과다. 원 요청 복구는 기존 견적이 남아 있거나 낡아도 표시하고 원 요청의 상한·멱등 ID를 보존한다. 기능 OFF의 자동 요청은 조회 전용, 비용·본인 상한은 확인 필요로 표시한다. 자동 오류는 실제 오류 값만 표시하며 원시 속성명을 노출하지 않는다. 화면 검토는 합성 응답과 설치된 Chrome을 사용했고 운영 HTTP/DB·휴대폰·실제 접수는 실행하지 않았다.
