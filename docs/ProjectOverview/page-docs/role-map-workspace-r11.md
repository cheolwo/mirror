# 역할 선택 홈·역할별 지도 책임 카드 r11

## 필수 절차와 선택 도구 r22 — 구현 전 책임 카드

2026-10-06 사용자 승인. 역할 화면의 질문은 “현재 업무를 진행하려면 무엇을 해야 하며, 필요할 때 어떤 도구를 이용할 수 있는가”다. 현재 대상·상태·필수 정보·다음 행동은 기본 카드에 둔다. 운송내역·증빙 조회·정산내역 등 독립 업무는 기존 페이지로 이동하는 접힌 `업무 도구` 메뉴에 모으고 선택 대상과 복귀 경로를 유지한다. 생활 지도는 기존 전용 지도 호스트와 등록·내 활동 도구를 사용한다.

표시 분류는 필수 절차·조건부 필수·선택 도구·미분류로 구별한다. `IsPrimary`는 강조 표현일 뿐 필수 여부가 아니다. 미분류 행동은 기존 위치에 남긴다. 취소·거절·문제 신고·재시도·로그인은 메뉴에만 숨기지 않는다. 현재 업무가 없으면 기존 시작 진입을 바로 제공한다. 메뉴 열기와 도구 조회는 업무 명령이나 동의·결제·상태 변경을 실행하지 않는다.

조건부 증빙·서명·창고 인계·재조리, 위치 수신 조건과 기능/권한/서버 가능 행동은 기존 정책이 소유한다. 증빙 조회와 제출, 지도 표시와 GPS 전송, 결제 화면 링크와 결제 필요 조건을 합치지 않는다. 개인별 도구 표시 설정은 추가하지 않는다. API·JSON·DB·역할 권한·업무 전이는 변경하지 않는다.

Web과 MAUI가 같은 공통 UI를 소비한다. 좁은 화면에서 메뉴 기본 접힘, 필수/복구 행동의 가시성, 빈 상태의 시작 진입, 기존 독립 페이지 진입/복귀, 비활성 상태, 조회 실패와 개인정보 보호를 시험한다. 실제 공유 컴포넌트 렌더·소비 앱 빌드·물리 단말·Azure·Figma 증거는 따로 기록한다.

2026-10-05. 사용자 승인: 8역할을 메인 홈에서 선택하고 같은 통합 앱 안의 역할별 지도·하단 카드로 이동한다. 구현 전 책임 기준이며 검증 결과는 별도로 기록한다.

홈의 질문은 “오늘 어떤 역할로 활동할 것인가”다. 생활 이용자·주문자·음식점·음식 기사·화주·화물 기사·창고·운영자의 이름과 짧은 목적, 진입만 제공한다. 역할 선택은 권한·계정·업무 상태를 바꾸지 않는다.

역할 화면의 질문은 “내 현재 업무 대상이 어디에 있고 다음에 무엇을 처리해야 하는가”다. 지도에는 기존 API가 해당 역할에 허용한 좌표와 출처 있는 경로만 표시한다. 하단 카드의 기본 정보는 대상·상태·핵심 정보·다음 행동이고 상세는 같은 대상의 정보 섹션으로 펼친다. 입력·로그인·설정·정산 이력은 독립 화면으로 이동하며 복귀 문맥을 유지한다.

화면/선택/접기 상태는 공통 조립 ViewModel, 업무 조회·명령은 역할별 adapter와 기존 API, 위치·지도·보안 저장은 host adapter가 소유한다. 네이티브 음식 기사 수행 로직은 공용 표현에 연결하며 기존 전용 앱을 삭제하지 않는다. 음식·화물 수행과 관리자 권한을 합치지 않는다.

역할/계정 변경·중단·이탈은 이전 비공개 DTO·핀·경로·조회/알림을 정리한다. 늦은 응답과 완료 콜백은 role/session generation에 결속한다. 서버 원장 재조회 뒤에만 업무 결과를 반영한다. 좌표 null과 지도 실패는 목록·안내로 표시하며 성공·0·가짜 핀으로 대신하지 않는다.

검증: 8역할 진입, 현재 상태별 행동, 인증 성공/취소/만료, 전환 중 늦은 응답, 지도 실패/좌표 없음, 카드/지도/입력 복귀, 모바일 실제 렌더와 APK. 실제 휴대폰·Azure·Android 타일·Figma는 별도 증거다. [페이지 원칙](../../Architecture/WholeRoadmapPagePrinciple.md)과 [시각 기준](../../Architecture/RoleAppVisualDesignStandard.md)을 소비한다.

## 완료 확인·기사 기본 정보 r12

2026-10-05 사용자 승인: 보완 제안 1번과 2번. 음식 행동 입력 화면의 질문은 “보낸 요청이 해당 업무에 실제로 반영되었는가”다. 서버가 요청에 응답한 단계와 후속 원장 상태를 확인한 단계를 구분한다. 해당 주문·배달 시도·판정과 행동별 기대 상태/값을 대조한 뒤에만 완료로 표시한다. 응답이 확인된 명령 뒤 조회 실패·이전 상태는 확인 대기로 남기고 조회만 다시 실행한다. 명령 응답 미확인은 기존 불변 본문·동일 요청 ID 재시도를 보존한다. 계정/대상 변경에는 비공개 입력·보류 상태·늦은 응답을 제거한다.

기사 기본 카드의 질문은 “이 제안을 수락할 조건 또는 지금 갈 곳과 필수 요청은 무엇인가”다. 수락 전에는 배달료·앱 제안 거리·픽업 장소를, 수락 후 픽업 단계에는 픽업 주소와 준비 안내를, 전달 단계에는 전달 주소와 필수 전달 요청을 기본으로 표시한다. 현재 API가 제공하는 정보만 사용하며 수행 중 거리값은 DTO에 없으면 생성하지 않는다. 긴 메뉴·주문 요약·수령인·마스킹 연락처는 기존 상세에 유지한다. 기존 접기, 상태별 가능 행동, 지도와 인증/업무 분리는 유지한다.

이 판본은 완료 후 다음 업무 선택, 타 역할 변경 자동 갱신, 목록 페이지 확장, 지도 SDK/휴대폰/Azure 연결을 포함하지 않는다. 소스·행동별 회귀시험·실제 공유 컴포넌트 렌더·내장 APK의 증거는 [r12 변경 기록](../../Changes/2026-10-05-role-workspace-completion-card-r12.md)에 연결한다.

## 상태별 업무 연결과 예외 복원 r18

2026-10-05 사용자 승인: [OS 상태 카드 조사 r17](os-state-card-audit-r17.md)의 우선순위에 따라 화물 예외 복원 → 창고 수령·검수/출고 연결 → 음식 복합 상태 안내 → 현재 단계의 필수 정보와 독립 업무 연결을 보완한다.

| 화면의 질문 | 상태·정보·행동 책임 |
| --- | --- |
| 화물 기사: 지금 운송을 계속할 수 있는가 | 원장의 최근 신고와 관련 사건 전체를 서버에서 투영한다. 운영 확인 요청·정산 보류·전체 운송 보류를 구별한다. 가능한 행동은 기존 전이 정책과 현재 보류에 결속하며 지도 카드·독립 입력·POST에 같은 전체 보류 판정을 적용한다. 이미 저장한 완료 뒤 새 보류는 이전 완료를 실패로 바꾸지 않는다. |
| 창고: 지금 어떤 재고/출고를 처리하는가 | 수령 요청 ID와 새 재고 ID, 인계 준비 재고 ID와 출고예정 ID의 관계를 확인한다. 수령 후 검수는 기존 검수 폼, 출고 검토·운송 의뢰·실제 기사 인계는 기존 전문 화면으로 이동한다. 준비 완료를 실제 인계나 새 운송 의뢰 생성으로 간주하지 않는다. |
| 음식점·음식 기사·주문자: 현재 음식과 배달은 어느 단계인가 | 현재 조리 회차·준비 완료·배차·허용 행동을 함께 해석한다. 음식점은 픽업 후 재인계를 지시하지 않고, 기사는 재조리 준비 전 대기한다. 주문자는 기사 배정 대기/배정됨을 조리 중과 구별한다. |
| 기본 카드와 독립 입력 | 현재 갈 곳·시간창·필수 증빙·준비/검토 안내는 기본 정보, 같은 대상의 사건/조리회차/요청은 상세 섹션이다. 검수·운송 의뢰·현장 증빙처럼 다른 입력 책임은 별도 페이지이며 같은 역할 세션·선택 업무·복귀 경로를 유지한다. |

계정 변경·권한 거절·느린 응답은 기존 수명 정책으로 보호한다. 새 예외 필드도 생활 배송의 정보 제공 동의에 따라 가린다. DTO 추가는 기존 필드를 유지하며 화물의 `가능한행동=null`은 구판 응답, 빈 목록은 명시적 수행 금지다. OS 설명 단계·공통 생명주기 Sequence를 실제 전이 권한으로 사용하지 않는다.

[r18 변경 기록](../../Changes/2026-10-05-state-card-polish-r18.md)은 실제 실행·렌더·Android 빌드와 미확인 단말/Azure 경계를 별도로 기록한다. 모든 역할/상태의 최종 카드 디자인 승인이나 실제 운영 업무 완료를 주장하지 않는다.

## 처음 이용하는 사람의 역할 선택 r19

2026-10-05 사용자 방향: 중개 수수료 수익보다 사람들이 기능을 이용해 서로 협업하고 생활을 개선하는 장을 우선하며, 여덟 입장의 사용성을 계속 보완한다. 상세 역할 검토는 [여덟 진입점 검토](role-entry-review-r19.md)에 연결한다.

홈의 질문과 결과는 기존처럼 “지금 어떤 활동 화면으로 들어갈까”다. 이번에는 각 역할의 설명을 현재 구현으로 할 수 있는 행동으로 바꾸고, 홈의 표시명을 현행 Mirror(거울)로 맞춘다. 특히 주문자는 현재 음식 주문 흐름이며 모든 종류의 상품 구매를 제공한다고 표현하지 않는다. 역할 키·이름·순서·route·선택 표시·로그인과 권한은 유지한다. 홈은 배차·가입·거래·대금 확인을 실행하지 않는다.

후원·광고는 선택적인 운영비 조달 후보이며 방식은 미정이다. 이번 홈에 결제·광고·후원 UI를 추가하거나 기존 배달료·정산·수수료 정책을 해제하지 않는다. 수수료를 받지 않는 방향과 운송 수행자의 대가·당사자 부담 조건은 별도다. 사용자 선택과 비용·노동 부담을 검토하는 공통 방향은 [현재 결정](../../AI/DECISIONS.md#2026-10-05-수수료-중개보다-참여자의-교류와-생활-개선을-우선)이 소유한다.

## 역할 간 인계 보완 r21 · 구현 전 페이지 책임

2026-10-06 사용자 승인: [r20 조사](role-handoff-audit-r20.md)의 H01~H03을 보완한다. 음식·화물의 원장, 기존 인증·기능 관문·공제·지급 기준은 유지한다.

| 책임 카드 항목 | 운영자 화물 사건 목록 / 검토 | 기사 완료 내역 목록 / 상세 | 화주·생활의 기본 보류 안내 |
| --- | --- | --- | --- |
| 주 사용자·진입 | 기존 `operator` 계정, 운영 화면에서 화물 사건으로 이동 | 기존 `food-driver` / `cargo-driver` 계정, 현재 업무에서 내역으로 이동 | 본인 운송 의뢰 조회 |
| 한 문장 목적 | 목록에서 검토할 사건을 찾고, 독립 검토 화면에서 해당 사건의 조치를 기록한다 | 목록에서 완료한 업무를 찾고, 별도 상세에서 금액·진행·허용된 정보를 확인한다 | 지금 의뢰가 보류됐는지와 그 범위를 알아낸다 |
| 완료 결과·주 행동 | 결정 응답 뒤 같은 사건·운송·의뢰와 revision을 재조회해 결과 확인 | 읽기 전용 목록→상세→현재 업무 복귀, 지급 실행 없음 | 같은 DTO에서 보류·재개 안내, 운송 상태는 별도 유지 |
| 기본 정보 | 사건 유형·상태·담당·영향 범위, 검토에서는 수량·결정·사유 | 날짜/종료 상태·업무 번호·금액, 상세는 저장 당시 요금 근거·확인 상태 | 전체 운송 / 영향 수량 / 정산 보류를 구별한 짧은 안내 |
| 보조 정보 | 원장 식별 관계·증빙 등록 여부·검토 시각 | 서버가 허용한 주문/고객 상세와 증빙 등록 여부, 원본 증빙은 기존 전문 업무 | 동일 사건의 상세는 기존 운송 내역 |
| 독립 업무·제외 | 음식 중단 검토와 분리; 자동 판정·신규 사건 접수·원본 증빙 공개 제외 | 현재 수행 카드에 다른 업무 목록을 넣지 않음; 음식/화물 API 분리; 플랫폼 결제·실입금 생성 제외 | 상세 입력/판정을 기본 카드로 옮기지 않음 |
| 실패·복귀·수명 | loading/empty/error/권한/기능 비활성·동일 요청 재시도·revision 충돌 재조회; 계정 변경 시 초안 제거 | loading/empty/error/retry·계정 변경/늦은 응답 차단; 목록의 날짜·역할 선택 복귀 | 미확인을 정상 진행으로 표시하지 않으며 재조회 결과로만 안내 갱신 |
| 코드→API→DB | 공통 VM/컴포넌트→기존 관리자 사건 GET/PUT→사건·의뢰·운송 원장 | 공통 VM/컴포넌트→기존 음식 일별 정산/기한 있는 상세 또는 기사 화물 목록/상세→각 원장 | 공통 표시 helper→기존 의뢰 응답의 사건·보류 필드 |
| 책임 판정·검증 | 목록과 결정 입력은 다른 결과이므로 별도 route; 시험/실제 렌더/단말을 구별 | 목록과 상세는 명시적 route, 현재 업무와 분리; 음식 내역은 전달 완료 정산 기록 범위 | 현재 판단에 필요한 정보이므로 기본 표시; 수량 일부 보류를 전체 중단으로 표현하지 않음 |

새 화면은 Web와 통합 앱이 같은 공통 컴포넌트를 소비한다. 공개 API/JSON·DB·운영 설정은 변경하지 않는다. 실제 여러 계정의 제품 업무 완주·휴대폰·Azure·입금은 별도 증거로 남긴다.

구현·시험·실제 공통 렌더와 Figma/단말 미확인 범위는 [r21 변경 기록](../../Changes/2026-10-06-role-handoff-fixes-r21.md)에 결속한다. `/workspace/operator/cargo-incidents`와 `…/{IncidentId}/review`가 목록·검토를, `/workspace/{RoleKey}/history`와 `…/{RecordId}`가 목록·상세를 분리한다. 생활 배송의 Figma 대응은 기존 `01 Community` 배송 진행 카드지만 이번 세션에 node 확인/갱신 도구가 없어 그 부분을 완료로 보고하지 않는다.
