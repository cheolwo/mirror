# 본인 APK 업무 검증

사용자가 승인한 마감 계획에 따라 기존 음식 배달 화면과 실제 서버의 연결을 보완하고, 통합 앱과 음식 기사 앱의 설치용 판본을 검증한다. 첫 시험은 격리된 Simulation 서버와 시험 자료를 사용한다. 운영 거래 준비 관문을 우회하지 않으며 공개 운영·Azure·실제 휴대폰 결과는 각각 구분한다.

## 검증 대상

동일 음식 주문의 주문자·음식점·기사·운영자 진행, 실제 UI/client와 HTTP/DB 연결, 로그인 복귀·중복 요청·통신 실패와 권한 경계를 확인한다. 최신 두 APK는 소스·서버 주소·서명·SHA-256에 결속하고 에뮬레이터 설치·실행을 확인한다. 휴대폰 없이 가능한 범위를 먼저 마치며 지도 미설정 상태에서는 기존 목록 대체 화면을 사용한다.

구현 결과·실제 서버/화면·설치 인계의 증거와 한계는 [r26 변경 기록](../../Changes/2026-10-06-apk-workflow-completion-r26.md)에 연결한다. 실제 입금·신원기관·Azure 연결은 이 시험의 성공으로 판정하지 않는다.

## 기존 계약의 호환 보완

현재 수행 조회 `FoodDeliveryDriverActiveDeliveryDto`에 기본값이 빈 문자열인 `OrderNo`를 추가한다. 서버의 현재 배달 시도 또는 기존 운송 원장의 원본 주문 키에서 투영하며 제목·상호·OfferId로 추론하지 않는다. 이전 서버가 이 필드를 주지 않으면 해당 수행 화면의 거래 문제 접수 진입을 제공하지 않는다. 기존 지원 명령은 `PrivateEvidence`·`ExpectedRevision`·`ClientRequestId`를 그대로 사용한다.
