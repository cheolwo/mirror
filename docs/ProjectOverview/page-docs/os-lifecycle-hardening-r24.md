# OS 생명주기 보완과 APK 검증 준비 r24

[승인 범위](os-lifecycle-hardening-r24-plan.md)에 따라 [r23 조사](os-lifecycle-static-audit-r23.md)의 확인된 결함을 보완했다. r23 JSON은 당시 소스의 조사 기록으로 보존한다. 현재 코드와 바뀐 파일 해시만 결속해 r23 전체 조사를 새로 완료했다고 처리하지 않는다.

## 보완한 처리 경계

| r23 항목 | 현재 처리 |
| --- | --- |
| FOOD-R23-001 | 배차 Outbox는 현재 주문과 이미 결속된 큐를 재조회한다. 같은 큐 재시도는 진행/완료 상태와 최초 시각을 보존하며 다른 큐 덮어쓰기는 거절한다. |
| FOOD-R23-006 | 미지원 원시 주문 상태는 초기 주문으로 해석해 변경하지 않는다. 기존 주문접수 별칭은 유지한다. |
| OTHER-TRUST-001/002 | 공개 동의는 인증된 수신자와 결속한다. 응답·동의·알림 Outbox를 한 transaction/SaveChanges로 저장한다. |
| LOG-WH-01 | 기존 put-away/pack와 새 UseCase가 같은 상태·전체 가용 수량 관문을 사용한다. 같은 완료 요청의 재전송은 이력·Event를 중복 생성하지 않는다. |
| LOG-SHIP-01 | 승인·결제·배차·기사 배정 이후 비가격 핵심 조건 변경도 409로 거절한다. 연락처 변경·동일 조건 재전송·확정 전 초안 수정은 보존한다. 새 합의 workflow를 구현했다고 주장하지 않는다. |
| OTHER-EDU-001 | 전송 worker는 제출대기 상태만 학교심사중으로 바꾸며 이미 내려진 인정/미인정 결정을 보존한다. |
| OTHER-EDU-002 | 읽은 Revision으로 원장을 저장한다. 경쟁 수정은 덮어쓰지 않고 409와 재조회 안내를 반환한다. |
| OTHER-EDU-003 | 원장에 남은 제출 의도로 누락 큐를 같은 ID로 복구한다. 전송 완료 영수증과 원장 반영 완료를 분리해 반영 실패를 외부 재전송 없이 재시도한다. |
| OTHER-IMPORT-001 | 과거 이벤트는 이력에 남기며 현재 상태·위치·시각을 되돌리지 않는다. Upsert도 이력을 병합하고 경쟁 쓰기를 검사한다. 예외 뒤에는 마지막 정상 단계를 보존한다. |
| META-R23-001/002 | 참여자 대장 3쌍과 다섯 OS의 책임 단계 21개를 추가했다. 기존 41개 단계 ID/선언을 보존하여 총 10개 OS·62개 책임 단계가 됐다. 런타임 권한은 추가하지 않는다. |
| LOG-MART-01 | 마트/음식/창고 기능과 실제 마트 주문·출고 소유자 결속을 검사한다. 마트 원천을 수행할 기사 consumer 연결이 없는 현재 상태에서는 큐·인계·Outbox를 만들지 않고 보류한다. 창고 포장 결과는 유지한다. |

독립 코드 검토에서 찾은 추가 반례도 보완했다. 교육 제출은 내용 digest가 같은 요청만 재사용하며 새 활동 기록 후 재제출은 새 ID로 연결한다. 선적의 `DomesticCarrierPickup → Exception → DocumentRegistered`는 과거 단계로 회귀하지 않는다. 미분류 이벤트는 이력에 보존하며 알려진 정상 상태를 대체하지 않는다.

교육 큐의 신규 `원장반영완료` 필드가 없는 기존 문서도 반영 복구 대상으로 읽는다. 성공 전송과 영수증 저장 사이에 프로세스가 중단되면 외부 중복 전송 가능성은 남는다. API는 같은 제출 ID의 Idempotency-Key를 사용하며 SMTP 헤더만으로 수신기관의 중복 제거를 보장하지 않는다. 원장 조회/재요청 시 예약 누락을 복구하며, 사용자가 다시 조회하지 않은 모든 원장을 주기적으로 검색하는 서비스는 추가하지 않았다.

실제 DB 실행에서도 추가 경계를 보완했다. Mongo의 기본 `_id`에는 사용자 지정 unique 인덱스를 다시 만들지 않는다. MySQL의 자동 재시도 전략 안에서 배차 결속의 transaction·재조회·저장·commit 전체를 실행하며, 실패가 남긴 Modified 사본은 정본으로 다시 읽고 호출자가 이미 가진 transaction은 commit하지 않는다. 이 경계를 검사하는 SQLite 회귀시험은 전용 공유 EF provider를 사용해 전체 시험의 provider cache와 분리한다. 전역 경고를 억제하지 않았다.

격리 음식 서버의 가상 기사도 운행 시작과 배달 요청 수신 의사를 별도로 처리한다. 관찰 Runner는 정상 기사 API로 수신 의사를 On으로 바꾸고 변경 시각을 재조회한다. 배차 정책이나 실효 적격성 정본을 직접 쓰는 방식으로 시험을 통과시키지 않는다. 실행 실패와 보완 후 정상 흐름 결과는 변경 기록에 따로 결속한다.

## 설치용 앱과 휴대폰 검증

대표 앱은 여덟 역할로 들어갈 수 있는 `SsalddelApp`이고, 별도 음식 기사 앱은 `FDriverApp`이다. APK는 자체 관리 어셈블리가 포함된 Debug 판본 `0.1.24 (24)`, Android API 24 이상, arm64-v8a/x86_64용으로 준비한다. Google 지도 키가 없는 상태와 서버에 접속하지 못하는 상태를 실제 업무 완료로 취급하지 않는다.

초기 APK의 실제 Android 화면에서 익명 로그인 버튼이 지도 아래 화면 밖에 놓이는 문제를 확인했다. 공통 `RoleMapWorkspace`는 로그인 복원 중 로딩, 익명/401 로그인 안내, 403 권한 안내와 인증된 업무 화면을 구분한다. 인증 안내 중 native 지도를 숨기고 로그인 복원 뒤 다시 그리며 기존 경로·ReturnUrl·권한을 유지한다. 수정 APK는 Android API 36/x86_64 에뮬레이터에 설치하고 서명된 최종 파일과 설치된 base APK의 SHA-256을 대조했다. 두 앱의 로그인·업무 조회와 통합 앱의 지도 연결 안내→목록 전환을 확인했다. 초기 실행의 splash 화면과 UI 입력 자동화 실패도 이전 증거로 보존한다. Debug 최초 실행 시간은 휴대폰 성능 측정으로 사용하지 않는다.

서버 주소는 `http://127.0.0.1:5361/`이다. 휴대폰에서는 휴대폰 자신의 주소이므로 PC에 연결해 USB reverse를 설정해야 한다. 휴대폰 단독 Azure 접속용으로는 확인된 공개 HTTPS 주소를 넣어 별도로 패키징해야 한다. 확인되지 않은 Azure 주소나 지도 키를 넣지 않았다.

최종 APK·SHA-256·서명/정렬/패키지 검사와 설치 안내는 Git 제외 `artifacts/local/os-lifecycle-hardening-r24/apk/`에 보관한다. 에뮬레이터의 설치·시작·역할 이동은 실제 휴대폰/GPS/다중 사용자 서버 업무 검증과 구별한다.

완료 상세의 미확정 공제·수령액은 항목 이름을 한 번만 표시하도록 정리했다. APK 화면 확인은 격리 서버에서 자동 역할들이 수행한 정상 배달과 별개이며, 주문·고객 정보의 3일 열람 기한과 실제 입금 미확정 상태를 유지한다.

## 검증 기록

최종 실행 결과와 문제별 상태는 [변경 기록](../../Changes/2026-10-06-os-lifecycle-hardening-r24.md)을 따른다. 실제 Mongo 회귀 검증은 [전용 probe](../../../eng/Ssalddel.LifecycleProbe/README.md)를 사용하며 본인 GUID DB만 생성·삭제한다. 외부 교육기관으로 전송하지 않는다. 실패·재시도 시험과 API/공통 UI 시험, Android 패키징을 별개로 기록한다.

## 남은 운영 연결

- 마트의 `SsalddelMartPackedOrder`를 음식 기사 consumer가 수용하는 adapter 및 완료 증거 반환은 별도 연결이 필요하다. 기존 준비중 UI를 유지하며 지원되지 않은 작업을 기사 큐에 넣지 않는 관문을 추가한다. 포장 완료를 고객 전달 완료라고 표시하지 않는다.
- 창고 수량 불일치의 재검수/재계수 재진입은 실제 명령 연결 확인과 보완이 남는다. 이번 정상 검수/적재/전체 수량 포장 관문 통일로 이 예외 workflow를 구현했다고 처리하지 않는다.
- 음식 주문 완료, 기사 정산 후보, 지급 상태는 서로 다른 상태축이다. 결제/환불/음식점 보상 연결을 플랫폼 결제나 중개 수수료의 새 필수 기능으로 만들지 않았다.
- 교육의 공통 책임 단계는 채웠으나 기존 API CommunityTrust 표시와 enum은 호환성을 위해 유지했다. 별도 API 분류 확장은 후속이다.
- 기존 음식 검증 서버는 food4 계정·기능 중심이다. 화주·화물·창고·운영자까지 사용할 때는 해당 기능 설정과 권한·자료를 갖춘 서버가 필요하다. 전역 운영 기본 설정을 시험 편의를 위해 활성화하지 않는다.

이번 변경은 모든 역할의 모든 업무가 운영 환경에서 완성됐다는 판정이 아니다. 실제 휴대폰 설치, 서버 로그인·여러 역할 간 업무 완주, 지도/GPS, Azure 및 실제 입금은 각 실행 증거로 확인한다.
