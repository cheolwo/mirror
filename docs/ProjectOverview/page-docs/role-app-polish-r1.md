# 화물·음식점·주문자 앱 마감 r1

사용자는 네이버 지도를 제외하고 기존 페이지의 보완 7개를 모두 진행하도록 승인했다. 기존 업무와 역할별 원장을 유지하며 주문·운임·조리·배차 정책을 새로 만들지 않는다. 기준은 [페이지 단일 책임](../../Architecture/WholeRoadmapPagePrinciple.md)과 [역할 앱 시각 기준](../../Architecture/RoleAppVisualDesignStandard.md)이다.

## 책임과 완료 조건

| 항목 | 업무 질문과 결과 | 기본 정보·주 행동 | 실패·복귀와 검증 |
| --- | --- | --- | --- |
| 1 화주 의뢰 수정 | 같은 의뢰의 연락처/종류만 수정하고 원값을 유지하는가 | 기존 수정 초안과 저장 | 변경하지 않은 수량·파손주의·운임을 같은 의뢰로 재조회 |
| 2 음식점 메뉴 저장 | 인증 만료 후 같은 메뉴 제출 결과를 확인하는가 | 메뉴 초안, 로그인 또는 같은 요청 재확인 | 인증 화면은 업무와 분리, 같은 owner만 복귀, 명시 로그아웃·다른 계정 폐기 |
| 3 기사 완료 사진 | 같은 완료 재시도가 원장 첨부를 늘리지 않는가 | 기존 상하차 완료 | 같은 단계/ObjectName은 하나, 다른 사진·단계는 별도 기록 |
| 4 주문자 현재 주문 | 갱신 중에도 현재 주문을 읽고 최신 상태로 행동하는가 | 마지막 성공 상세와 작은 갱신 안내 | 실패 시 내용 유지·행동 잠금, 계정/주문 변경은 즉시 제거, 앱 복귀 정본 조회 |
| 5 음식점 주문 확인 | 조리 전 기존 요청과 배차 대기 이유를 읽는가 | 주문 메뉴와 원문 전달 요청, 예외 상태 안내 | 원문을 조리 요구로 임의 해석하지 않고 없는 정보는 추가하지 않음 |
| 6 화물 운송 내역 | 현재 기사 본인 이력을 국내 시각으로 읽는가 | 기존 내역 목록 | 이탈·계정 변경·겹친 조회의 늦은 결과 폐기, 한국시간 날짜 경계 |
| 7 주문자 접수 복구 | 종료 전 제출한 주문이 접수됐는지 먼저 확인하는가 | 접수 확인 상태, 결과 확인 또는 주문 상세 보기 | 미접수 확인 뒤 명시적 동일 요청 재제출, 인증/조회 실패는 새 주문으로 넘기지 않음 |

## 항목 7 페이지 → 코드/API → DB

기존 음식점 탐색 route의 별도 접수 확인 표시 모드가 결과를 소유한다. 자격 입력은 기존 인증 모드에만 있고, 미확정 요청이 있으면 새 작성 영역을 동시에 노출하지 않는다. 앱 재시작이나 재로그인은 조회만 수행하며 자동 POST하지 않는다.

- `OrdererRestaurantWorkspace` → 페이지별 `FoodOrderSubmissionRecoveryViewModel`과 같은 인스턴스를 사용하는 작성 VM. 초기 HTTP 조회가 첫 렌더 이후 끝나는 경우에도 DOM 준비 뒤 접수 복구를 시작한다. 계정/페이지 수명과 늦은 응답을 구별한다.
- 제출 전 `IFoodOrderPendingSubmissionStore`에 owner·동일 요청 ID·원 제출 payload를 보관한다. OrdererApp은 MAUI SecureStorage, 웹 기본 adapter는 현재 탭의 sessionStorage이며 웹 브라우저 재시작 전체 복구까지 주장하지 않는다. 자격 정보/토큰은 이 저장물에 포함하지 않는다. 저장 실패 시 POST하지 않는다.
- `GET api/v1/food-orders/client-requests/{requestId:guid}` → 기존 주문자 조회 UseCase → 로그인 owner와 동일 요청 ID의 EF 음식주문 조회 → 주문번호만 응답. 원장 쓰기·배차/조리 재실행은 없다. 다른 owner·미접수는404, 익명은401이다.
- GET404만으로 자동 재주문하지 않는다. 명시적인 `같은 주문 다시 제출`은 보관된 payload와 ID를 기존 멱등 POST로 보내므로 최초 요청이 뒤늦게 접수돼도 같은 주문을 돌려받는다. 401/5xx/응답 유실은 저장물과 잠금을 유지한다. 서버의 명시적인400/403/404/422 거절은 작성 수정으로 복귀한다.
- 성공 또는 기존 주문 확인 뒤 저장 요청을 ID 조건으로 제거한다. 다른 계정은 이전 저장물을 폐기하며 명시 로그아웃은 모바일·웹 탭의 저장물도 제거한다. 인증 만료는 재로그인 복귀를 위해 저장물을 유지한다. 저장물 손상/접근 실패는 빈 성공으로 숨기지 않으며 초기 확인과 새 제출을 잠근다. 저장소 정리 실패에도 개인 화면의 로그인 표시를 즉시 해제하고 정리 오류를 남긴다.
