운임구성의 추가 열은 `expected_distance_km`, `per_km_rate`, `minimum_fare`, `distance_basis`, `rate_source` 다섯 개이며 모두 nullable이다. 기존 행에 거리나 단가를 0으로 채우지 않는다. 기존 기본운임·거리운임·대기료·수작업비·할증·최종운임 열과 의뢰/구성 ID를 유지한다. migration `20261003190000_AddCargoFareQuoteEvidence`와 모델 snapshot이 같은 열을 정의한다.

## 변경 가능 시점과 실패

견적은 생성됨·결제대기·미시작이며 승인 전 정산 상태인 의뢰에서 변경한다. 확정 기사·진행/종결 상태에서는 `409 FreightPricingLocked`로 차단한다. 비정상 운송 사건의 보류와 구성 연결 불일치도 저장하지 않는다. 동일 가격의 재전송은 가격 변경으로 판정하지 않아 승인 후 연락처 같은 일반 수정이 가능하다.

화주 앱 조회·수정 초안은 최상위 `최종운임`의 null을 그대로 보존한다. 요금옵션에 별도 견적 금액이 있어도 확정 원값 대신 보내지 않는다. 예상거리·기사 지급 예정 운임·확인된0은 각각 원값을 유지한다.

주소를 변경하면 이전 좌표를 제거한다. 새 입력 거리 또는 변경한 주소의 좌표 쌍이 필요하며 기존 주소의 거리를 재사용하지 않는다. 음수 입력과 서버 견적보다 낮은 결제예정액을 조용히 보정하지 않는다. client가 보낸 최종운임·거리계산방식·단가출처는 서버 견적 근거로 사용하지 않는다. 신규 의뢰도 견적을 계산하지 못한 금액 입력에 임의 근거를 붙이지 않는다.

RDB 저장 뒤 Mongo 발행 실패는 저장됨과 동기화 미확인을 나눠 반환한다. 열린 caller RDB 트랜잭션의 persisted snapshot은 commit 뒤 발행해야 한다. 이번 CAS·투영 보호는 내구성 있는 재발행 outbox 또는 외부 후속 처리의 정확히 한 번 전달 구현이 아니다.

## 거리와 단가의 의미

이번 실제 API 표본은 합성 `입력거리` 3.5km와 기존 `v1.0 기본단가`를 사용해 35,000 + 3.5 × 1,300 = 39,550원을 계산했다. 실제 도로 주행·현재 시장 운임·법정 요율이 아니다. 기존 Service의 경로 제공자 선택은 유지하지만 이 작업에서 외부 경로 API를 호출하거나 창고 주소의 자동 좌표/경로 조회를 검증하지 않았다. 해당 자료가 없으면 미확인 상태를 보존한다.

기존 화주 앱의 화물 수정 DTO는 모델에 없는 수량/파손주의 원값을 보존하지 못하는 경계가 남아 있다. 이번에는 그 수정 기능을 제거하지 않고 앞선 동작을 유지했다. 이를 정산 원값 보존 시험의 완료 범위로 확대하지 않는다.
