# 생활 공간의 분산 입고·기사 피킹·다거점 배송 r36

기준은 [승인 구현 r30](../../AI/Planning/공통/PLAN-OPERATIONS-NEIGHBORHOOD-MICRO-HUB/distributed-warehouse.implementation.r30.md)다. 모바일 앱과 서버에 구현했고 로컬 검증과 네 역할 APK 준비를 완료했다. Unity는 제외하며 휴대폰·Azure·실운영 확인은 별도다. 기존 역할 선택·지도 작업공간에서 업무 화면에 진입하고 같은 맥락으로 돌아간다. 공간 등록과 상품 재고, 주문 예약, 배송 완료와 수령 확인은 서로 다른 상태다.

## 화면과 책임

### 재고 정리와 공간 종료 책임 · 2026-10-17

공간 제공자·물품 소유자는 기존 잔여 재고 정리 화면에서 정상 반출과 불량 폐기·실사 소실 정정을 구분해 합의한다. 처리 종류·수량·담당자·조건에 양측이 동의한 뒤 지정 담당자가 바코드·사진·처리 근거를 제출해야 해당 가용/불량 재고만 감소한다. 예약·기사 보관·미수령 입고 보호와 입고 누계·기수행 보수는 유지한다. 수량 정정은 재입고나 물품 반환의 증거가 아니며 손실 배상·금전 지급도 자동 확정하지 않는다. 연결된 재고 근거가 없는 물품은 임의로 0으로 만들지 않고 별도 확인 대상으로 남긴다.

주 행동은 현재 정리 합의의 동의 또는 현장 처리 완료다. 새 정리 조건 제안과 공간 사용 종료는 같은 대상의 별도 단계로 표시한다. 원문 합의·실수량·사진·RequestId·revision은 기존 공간 메타데이터와 재고이력·명령 영수증에 보존한다. 기본 OFF·Simulation 제한을 유지하며 실제 운영 전환·폐기 실행·공용 DB 변경을 뜻하지 않는다.

2026-10-10 예외 지속 보완의 책임: 같은 역할/업무의 미확정 요청은 화면 복귀 후 영수증 확인부터 이어간다. 사진 업무는 원본을 저장하지 않고 업로드 번호와 증빙 참조를 복원·재조회한다. 원본 부재와 업로드 미확인은 재촬영 필요로 구분하며 새 완료로 간주하지 않는다. [승인 범위](../../AI/Planning/공통/PLAN-OPERATIONS-EXCEPTION-CONTINUITY/exception-continuity.implementation.r1.md).

공통 경로는 `/workspace/{role}/distributed/{section}`이며 선택 대상은 `selected`로 유지한다. `warehouse`, `shipper`, `cargo-driver`, `orderer`, `operator`의 역할 선택은 로그인·서버 권한 부여와 다르다. 서버 조회 역할은 창고·화주·기사·주문자로 제한하며 운영자의 출고 묶음은 창고 운영 범위로 조회한다.

| 섹션 | 담당자 | 표시와 현재 행동 | 서버·원장 |
| --- | --- | --- | --- |
| `sites` 공간 | 소유자·관리담당자 | 기존 본인 창고 선택 또는 첫 생활 공간 등록, 층·구역·출입 확인, 당사자별 동의·철회, 위치 바코드 등록 | `sites`, `consents`, `locations` → 기존 `창고` + `distributed_sites`, `distributed_locations` |
| `inventory` 재고 | 공간 관리자·판매자 | 상품 소유자와 판매자, SKU·lot·위치, 실수령·가용·예약 수량, 검토한 기존 재고 연결 | `lots`, `workspace` → 기존 `입고상품` + `distributed_lots` |
| `inbound` 입고 | 판매자·공간 관리자 | 기존 원천 선택 또는 본인 상품의 첫 입고 예정 선언, 거점별 분할, 위치·SKU 대조 후 부분 수령 | `inbound-plans`, `receipts` → 기존 `입고요청`·`입고상품`·`재고이력` + `distributed_inbound_plans` |
| `orders` 주문 | 판매자·주문자 | 기존 화물 의뢰와 물품 연결·수량 예약, 내 주문 취소, 전달 후 본인 수령 확인 | `waves/{id}/orders`, `cancel`, `acknowledgements` → `distributed_orders`, `distributed_reservations` + 기존 `출고예정` |
| `waves` 출고 묶음 | 공간 운영자 | 주문 마감·픽업·전달 시간창, 기사 후보, 경로 근거와 미완료 사유, 마감·계획 | `waves`, `close`, `plan` → `distributed_waves` + 기존 화물 의뢰·운송 원장 |
| `round` 현재 순회 | 배정 기사 | 총 제안 배달료, 현재 정차의 피킹 위치/물품 또는 전달, 스캔·부분 피킹·전달 | `accept`, `picks`, `deliveries` → 기존 배차 수락·기사 운송 상태 + 수량별 영수증 |

입력·검토를 한 페이지에 섞지 않는다. 기존 등록 후보는 서버가 인증 계정에 제공한 목록에서 선택한다. 기존 창고가 없는 이용자는 본인이 확인한 이름·도로명주소·픽업 좌표와 확인 항목으로 첫 공간을 등록한다. 관리자는 인증 본인으로 연결하며 소유자·관리자 동의는 각각 별도로 처리한다. 기존 직원 권한을 자동 추가하지 않는다. 내부 ID를 직접 입력하거나 공공 주소 후보를 공간 사용 허가로 취급하지 않는다. 정확한 출입 정보와 바코드는 공간 관리 또는 현재 유효한 기사 업무 권한으로만 조회한다.

첫 상품 등록은 상품명·SKU·예정 수량·본인 소유 및 판매 확인 근거를 받고 적재 위치별 예정 수량으로 나눈다. 기존 원천 선택과 새 원천 선언을 섞지 않는다. 이 단계의 실재고는 0이며 관리자가 수량·위치·SKU를 대조해 수령한 만큼만 가용 재고가 생긴다.

## 상태와 복구

### 원주문 선택 책임 r41

판매자는 선택한 기존 화물 의뢰의 물품을 예약할 때 같은 판매자·고객의 열린 원주문에 연결할지 판단한다. 기존 `orders` 작성 양식에 선택 항목을 조립하며 새 독립 주문·결제·정산을 만들지 않는다. 기본은 연결하지 않음이다. 연결을 선택하면 서버가 현재 계정과 해당 화물에 허용한 원주문 표시명·상태 중에서 고르고, 판본과 내부 ID는 전송 검증에만 사용한다.

주 행동은 기존 물품 확인 후 주문 추가다. 목록 로딩·조회 실패/재조회·빈 후보·변경된 선택을 현재 항목 옆에 표시하며 실패를 빈 성공 목록으로 바꾸지 않는다. 계정·출고 묶음·화물 변경은 후보와 선택을 무효화한다. 원주문 조회 실패는 작성 물품을 지우지 않으며 연결 상태에서는 같은 대상의 성공 재조회와 선택 전까지 제출을 막는다. 서버는 저장 직전 당사자·권한·상태·판본을 다시 검사한다. 기존 미연결 주문 작성과 응답 불명확 시 원 요청 확인·복구를 유지한다.

화면 → 기존 공유 ViewModel/Client → 보호된 분산 후보 API/UseCase → 원주문 접근 조회와 기존 연결 Adapter를 사용한다. 업무 실행 결과와 원주문 연결 상태, 기사 전달·고객 수령·정산은 각각 별개다. [승인 범위 r35](../../AI/Planning/공통/PLAN-OPERATIONS-NEIGHBORHOOD-MICRO-HUB/root-order-selection-concurrency.implementation.r35.md)를 따른다. 선택·조회 실패/재시도·빈 후보·권한 철회와 선택 판본 전송의 로컬 결과는 [r41 변경 기록](../../Changes/2026-10-08-root-order-selection-concurrency-r41.md)에 남긴다. 실제 단말·운영 API를 검증한 결과와 구별한다.

### 원주문 연결 확인 r40

배송 상태·고객 수령 확인과 원주문 연결 확인은 별개다. 서버가 현재 당사자에게 반환한 `Connected`만 원주문 상세로 연결하고, `Pending`은 배송 저장 사실을 유지하며 현재 원주문 판본과 허용 행동이 있을 때 연결 재확인을 제공한다. `Blocked`는 권한·조건 확인 안내이며 원주문 ID·판본·재시도 행동을 제공하지 않는다. 연결 재확인은 물품을 다시 예약하거나 배송 완료·수령·정산을 확정하지 않는다. r40 당시에는 기존 보호된 연결 API를 준비했고 신규 선택 양식은 후속이었다. 위 r41에서 해당 선택 양식을 추가했다.

이번 책임은 주문 진행에서 전문 배송 상세로 이동하고 같은 주문 맥락으로 복귀하는 것이다. 내부 원장 ID를 직접 입력하도록 요구하지 않고 현재 상태의 재조회·실패 복구만 담당한다. 서버 저장 연결과 로컬 렌더·실기기 확인 범위는 [r40 변경 기록](../../Changes/2026-10-08-order-ledger-role-refactor-r40.md)에서 구별한다.

서버가 반환한 `AllowedActions`와 현재 정차를 기준으로 버튼을 제공한다. 명령은 `RequestId`와 기대 revision을 보내고, 응답 뒤 동일 원장을 다시 조회한다. 응답이 불명확하면 원 요청·입력을 보존하고 본인의 명령 영수증부터 확인한다. 다른 내용으로 같은 요청 ID를 재사용하거나 늦은 응답을 새 계정·선택 화면에 덮어쓰지 않는다.

예약은 실재고의 가용 수량을 조건부로 줄인다. 주문 화면에서는 새 예약과 이미 예약된 본인 출고 물품을 구분해 선택하며 기존 예약은 다시 차감하지 않는다. 피킹은 위치 바코드·소유자·SKU·남은 수량·현재 정차·배차·시간창을 모두 대조한다. 일부만 인수한 상태는 완료가 아니며, 한 고객의 모든 물품을 인수해야 전달할 수 있다. 기사의 전달과 고객의 수령 확인은 별개다.

취소는 서버가 허용한 주문자·판매자·운영 담당자에게만 제공하고 선택한 주문·사유·확인을 결속한다. 아직 인수하지 않은 물품은 예약 해제하고, 이미 인수한 물품은 반납 확인을 기다린다. 접수 중 일부 주문만 취소하면 남은 묶음의 접수 상태와 마감 시각을 보존한다. 동의 철회는 신규 입고·예약·피킹을 막지만 인수한 물품의 책임을 지우지 않는다. 재계획은 완료 이력과 현재 적재량을 보존하며 남은 화물에 기존 확정 기사가 있으면 명시적 배정 해제 없이 다른 기사로 바꾸지 않는다. 순회 완료·배정 해제·시간 만료 후 기사에게 상세 주소·바코드를 계속 제공하지 않는다.

기존 화물 수락의 주의사항은 실제 오류·경고 코드와 설명을 보존한다. 기사가 확인한 서버 경고만 다음 수락에 전달하며 확인 없이 자동 승인하지 않는다. 활성 수행에서는 현재 피킹·전달 카드를 먼저 표시하고 순회 선택·전체 방문 조건은 접을 수 있는 보조 정보로 둔다. 내부 revision은 전송·재조회 검증에 사용하고 정상 카드에서는 기술 문구를 반복하지 않는다.

주의사항 확인은 화물별로 나눈다. 한 화물에서 확인한 코드가 같아도 다음 화물의 설명을 읽고 확인하기 전에는 자동 수락하지 않는다. 일반 화물 진행 화면에서 분산 물품의 피킹·전달 기록을 건너뛰지 못하도록, 기존 출고 예정과 `DLOC-` 적재 위치로 연결된 화물은 출고 완료 뒤에도 순회 화면으로 안내한다. 이 검사에는 새 분산 테이블을 조회하지 않으며 일반 화물의 기존 상태 전이는 유지한다.

체크 항목을 포함한 주요 조작 영역은 최소 48px 높이로 제공한다. 접수 화면의 사용자 표시에서 기술적인 판본 번호는 제거하고 명령의 내부 revision 검증은 유지한다.

## 활성화와 확인 한계

`DistributedFulfillment:Enabled=true`, 정확 profile `distributed-fulfillment-r36`, 기존 실행 모드 `Simulation`이 모두 필요하다. 기본은 비활성이다. 실제 경로 제공자는 별도 명시 설정이며 근거가 없으면 계획을 보류한다. 기존 경로·화물 요금·원장·배차 수락을 재사용하고 새 결제·지급을 만들지 않는다.

검증 결과와 실행 환경은 [변경 기록](../../Changes/2026-10-08-distributed-fulfillment-r36.md)에 별도로 연결한다. 로컬 시험·공통 화면 렌더·APK 빌드가 실제 단말·Azure·실입고·실운행 증거는 아니다.
