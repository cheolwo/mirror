# 음식 주문의 합의 취소와 지급 준비 책임 r1

## 승인 구현 범위

음식점이 수락했으나 조리를 시작하지 않았고 유효한 기사 수행이 없는 주문에서, 주문자와 해당 음식점 운영자가 비용 조건을 제안·동의한 뒤 명시적으로 취소를 실행한다. 수락 전 직접 취소와 별개이며 지원 사건의 결과 통지를 당사자 동의로 바꾸지 않는다.

| 단계 | 전문 원장의 근거와 결과 |
| --- | --- |
| 조건 제안 | 현재 주문 판본·상태와 주문자/음식점 부담액·비용 근거를 동결한다. 0원도 명시적으로 입력하며 미확정 비용을 0원으로 채우지 않는다. 제안은 동의나 주문 취소가 아니다. |
| 당사자 동의 | 본인 주문자 또는 현재 음식점 역할·범위의 운영자만 같은 조건 판본에 동의/철회를 기록한다. 제안자에게도 자동 동의를 부여하지 않는다. |
| 실행 | 양측 동의·합의 판본·원주문 판본·조리 전/기사 미확정·내부 수행을 재검증하고 주문 취소·배차 종료·합의 실행 영수증을 같은 SQL transaction으로 저장한다. |
| 비용·금융 | 동결된 부담액과 비용 근거는 취소 합의 원장에 보존한다. 실제 수납·환불·기사 보상·은행 지급은 별도이며 이 실행이 만들지 않는다. |
| 예외·재조회 | 주문·조리·기사 배정 상태가 달라지면 이전 합의로 실행하지 않는다. 조리 후/기사 수행/픽업 후와 모의 외부 수행은 기존 지원 검토로 인계한다. 불명확한 POST는 같은 합의/요청 번호를 GET으로 확인하고 자동 재송신하지 않는다. |

API 응답은 주문번호·조건·동의 상태·본인 요청 영수증만 제공한다. 고객 주소·연락처·수령인명·다른 당사자의 사용자 ID나 비공개 지원 증거를 반환하지 않는다. 주문 원장은 이유와 전문 원장 참조를 소비하며 새로운 상위 원장을 만들지 않는다.

## 기존 상세 화면의 책임 카드

주문자 음식 주문 상세와 음식점 주문 상세는 같은 주문의 상태를 판단하는 목적 안에서 `조리 전 취소 조건 협의`를 보조 펼침으로 제공한다. 조리/수행 이후의 기존 지원 링크는 유지한다. 펼침 안에는 최근 조건 확인·명시 부담액/근거 제안·본인 동의/철회·양측 동의 후 별도 실행만 두며 저장/협의/취소 결과를 혼동하지 않는다. 오류와 미확정 요청 결과 확인은 펼침 밖에 남겨 숨기지 않는다. 현재 상세 판본과 합의 판본이 다르면 동의/실행하지 않고 같은 주문 정본을 다시 조회한다. 새 route나 로그인/개인정보 입력은 이 패널에 넣지 않는다.

POST 중 응답이 유실되면 같은 합의 ID·요청 ID로 GET만 수행한다. 서버의 본인 영수증이 확인돼야 완료로 표시한다. 작성 수명은 현재 상세 컴포넌트이며 앱 재실행까지의 영속 초안/요청 보관을 구현했다고 표시하지 않는다. 화면 재진입은 정본을 새로 읽으며 POST를 자동 실행하지 않는다.

## 지급 준비의 한계

음식 기사 정산의 전달 완료·주문자 수령 확인·공제·모의 지급은 기존 상태로 유지한다. 현재 음식 결제의 과거 승인/현장결제 메모만으로 사용 가능한 지급 재원을 인증할 수 없으므로 운영 지급 준비 상태에 `FundingEvidenceMissing`을 명시한다. 전달 증빙이나 고객 무응답만으로 실제 지급을 열거나 수령 확인을 생성하지 않는다. 고객 신고의 보류와 실금융 연결은 별도 권위 검증을 유지한다.

## 검증 구분

계약·권한·영속 동의/취소·동일 요청 재조회·판본/상태 경합·고객 정보 비노출을 격리 DB 시험으로 확인한다. 운영 호출·실금융·공유 DB migration·APK/단말·외부 공개는 별도이며 구현/로컬 시험을 운영 완료로 표시하지 않는다.

## 늦은 수락 이벤트와 취소 경합

과거 음식점 수락 배차 Outbox는 현재 원주문이 취소/거절이면 큐를 만들거나 배차 시작 알림을 보내지 않고 소비를 끝낸다. 주소 좌표 조회는 transaction 밖에서 수행하고, 그 뒤 정본을 다시 읽어 SQL 큐 생성과 원주문 결속을 같은 Serializable transaction으로 처리한다. 결속 실패 시 SQL 큐도 롤백하며 재시도에는 실패한 추적 사본을 재사용하지 않는다. 이미 처리된 수락 이벤트와 별개로 취소 동기화 Outbox가 최신 취소 원장을 투영한다.

이 SQL 경계가 배달권 실행공간·Mongo 투영·알림까지 하나의 transaction으로 묶는 것은 아니다. 알림 직전에도 현재 취소 상태를 다시 확인하되, 외부 발송과 동시 취소의 완전한 원자성이나 실제 MySQL 병렬 경합은 별도 검증 대상이다. 격리 HTML 렌더 시험은 명시적 확인·버튼 활성 조건·접힘 밖 오류 배치를 검증하며 휴대폰 화면·시각 검수와 구분한다.

## 합의 취소의 운송·음식 투영 재개

합의 취소 실행은 주문번호·합의 ID·현재 SQL 큐 ID만 가진 `agreedCancellation` 의도를 기존 음식 동기화 Outbox 한 행에 함께 기록한다. 고객 정보나 과거 큐 상태·금액 사본을 담지 않는다. 기존 소비자는 실행된 합의·현재 취소 원주문·결속된 취소/종료 음식 큐의 출처를 재검증한 뒤 기존 운송 Mongo 동기화(CAS)로 배송 하위원장을 닫고, 음식 원장의 취소 상태와 포함 관계를 갱신한다. 일반 음식 원장 이벤트와 구분한 명시적 취소 후속이며 새로운 worker나 권한을 만들지 않는다.

배송 투영 성공 후 음식 투영이 실패한 경우에도 같은 Outbox가 Pending/Failed 정책으로 남는다. 재개는 SQL 정본과 현재 Mongo 판본을 다시 읽으며 합의 취소·비용·기사 정산을 재실행하지 않는다. 격리 회귀시험은 실제 두 투영 Service와 메모리 CAS 저장소를 이용해 배송/음식 단계별 실패와 새 Context 재개를 검사한다. 실제 Mongo 연결·운영 송금의 완료 증거는 아니다.
