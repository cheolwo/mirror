# 운송 주간 명세 자동 준비·재검증 검토 r1

2026-10-17. 기존에 승인된 운송별 지급 채무를 한국 시간 수요일 경계의 주간 명세로 준비하는 서버 작업을 검토하고 두 공백을 보완했다. 이 문서의 소스와 집중 시험은 준비된 상태다. 최종 빌드·시험·DB 적용·운영 실행·실제 입금은 통합 검증 기록에서 별도로 확인한다.

## 역할과 금융 경계

```text
운송 완료와 기존 지급 채무 승인
└─ 한국 시간 수요일 기준 완료 주가 닫힘
   ├─ 이미 편입된 자동 명세: 현재 조건 재검증
   │  ├─ 신고·환불·계좌·금액·원천 연결 변경 → 해당 행 보류
   │  └─ 보류 원인 해소 → 같은 승인 채무와 현재 근거를 다시 검사
   └─ 아직 편입되지 않은 승인 채무: 상한 안에서 조회
      ├─ 무효 금액·기사·완료 시점 → 비금융 검토 기록, 다음 정상 채무 계속 진행
      └─ 동일 기사·완료 주별 기존 준비 명령 → 한 채무 한 명세 행
         └─ 명세 준비·보류 조회
            └─ 실제 지급 승인·송금·입금 확인은 기존 별도 업무
```

명세는 승인되지 않은 채무를 새로 만들거나 승인하지 않는다. 지급 Outbox, 제공자 호출, 기사 계좌 이체도 만들지 않는다. 늦게 승인된 건은 승인일이 아니라 원래 운송 완료 주의 별도 명세에 추가된다. 같은 지급 요청을 건별·주간 명세에 중복 편입할 수 없는 기존 고유 제약과 멱등 키를 유지한다.

관리자 HTTP의 준비·재검증은 기존 관리자 권한·ExpectedRevision 검사를 유지한다. 자동 작업은 별도의 내부 인터페이스만 사용하며 새 public HTTP 경로를 열지 않는다. 작업 활성화에는 기존 Operational·DomesticTransportWorkflow 관문과 `DriverPayoutBatch.Enabled`, `AutomaticPreparationEnabled`가 모두 필요하다. 두 옵션의 기본값은 OFF다. 수요일·목요일 예정 시각은 명세의 일정이며 은행 입금 완료가 아니다.

## 발견한 공백과 보완

| 공백 | 보완 | 보존한 근거 |
| --- | --- | --- |
| 새 후보만 조회해 이미 준비된 명세의 새 신고·환불·계좌 변경이나 보류 해소가 반영되지 않음 | 자동 생성된 닫힌 주간 명세를 오래된 검증부터 순환 조회해 기존 재검증 Core를 재사용. Prepared·Held 모두 검사 | 원천 채무·동결 금액·관리자 HTTP 권한·revision |
| 상한 앞의 무효 승인 채무가 매 회차 다시 선택돼 뒤의 정상 채무가 진행하지 못함 | 기존 지급 요청에 nullable 검토 시각·표준 코드만 기록하고 미검토 건을 먼저 조회. 재시작 이후에도 진행을 보존 | 승인 상태·채무 금액·Provider 결과는 변경하지 않음 |

재검증과 새 후보 조회에 각각 설정 상한을 적용하며 새 대형 원장을 만들지 않는다. 같은 시각의 반복 작업에서도 revision을 함께 정렬해 기존 명세가 순환한다. DB 경합이나 다른 실행의 선행 편입은 다음 회차의 정본 조회로 이어지며 자동 승인·중복 송금으로 우회하지 않는다. 무효 채무는 정상 정산으로 숨기지 않고 `ReviewRequiredLines`와 표준 원인 코드로 검토 대상임을 남긴다.

## 남은 확인

SQLite 집중 시험 준비와 실제 MySQL 다중 서버·Quartz 실행은 별개다. 공용 DB migration 적용, 실제 운영 설정 활성화, 큰 원장 규모의 조회 비용, 검토 코드가 운영자 알림으로 전달되는 실제 경로, 실제 지급 제공자·입금은 이 변경의 완료 주장이 아니다. 기존 음식·피킹·포장 보수를 운송 채무로 자동 합치지 않으며 각각의 전문 정산 경계를 유지한다.
