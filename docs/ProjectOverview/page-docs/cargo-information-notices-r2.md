# 화물 정보 공고 — 페이지 책임

## 페이지 책임

| 항목 | 기록 |
| --- | --- |
| 주 사용자·페이지/소스 | 비로그인 포함 이용자의 `/community/cargo-notices`, 로그인 작성자의 `/shipper/cargo-notices`. 공통 CargoNotice Screen과 통합 MAUI·Web의 얇은 진입 페이지 |
| 대상·진입 문맥 | 공개 공고의 넓은 지역·희망 조건을 조회하거나 본인의 서버 저장 공고를 선택한다. 운송 의뢰·배차와 별도 대상이다 |
| 한 문장 목적 | 공개 목록은 게시된 화물 정보를 비교하고, 내 공고는 초안 저장→공개 내용 확인·동의→게시 또는 철회를 완료한다 |
| 완료 결과·상태별 주 행동 | 초안: 저장·공개 미리보기, 게시: 수정 또는 철회, 수정 후: 다시 동의해 게시, 만료·철회: 내용 확인 후 재게시. 서버가 반환한 최신 상태만 완료 판단에 사용한다 |
| 기본 정보 | 제목·화물명·수량·선택 중량/차량 분류·출발/도착의 공개 지역·희망 시간. 상세주소·연락처 입력은 받지 않는다 |
| 보조 정보 | 선택 공고의 희망 시간·만료·게시 상태. 공개 미리보기에는 작성자 식별자나 운송 내부 정보가 없다 |
| 독립 업무·제외 정보 | 운송 의뢰·기사 추천·배차·계약·수금은 이 화면에서 생성하지 않는다. 개정 번호·요청 식별자는 제품 화면에 표시하지 않는다 |
| 진입·실패·복귀 | loading/empty/error/retry/feature disabled, 로그인 복귀 exact allowlist. 계정·서버별 미확정 요청은 기존 WorkflowRecoveryStore에 원 요청을 보존하고 결과 GET으로 먼저 확인한다. 자동 재전송하지 않는다. 계정/세션 변경의 늦은 응답은 무시한다 |
| 코드·API·DB | CargoNotice Client → `api/v1/community/cargo-notices` → 독립 Mongo 공고. 소유권·동의·만료·중복 요청·개정 충돌은 서버 권위. 원 요청 결과는 과거 사본이므로 최신 내 공고를 별도 재조회한다 |
| 책임 판정·검증 | 목록과 관리 두 목적을 분리하고 공통 DTO/요약을 재사용한다. 구현/집중 시험/실제 390·1280 렌더/운영 활성화는 별개다. Figma 대응 Pending. 실제 실행 결과는 상위 변경 기록에서 마감한다 |

## 미확정 요청의 현재 상한

서버는 성공 원 요청만 보관하며 미적용 확정 영수증은 제공하지 않는다. 따라서 입력 오류 응답 이후에도 결과 GET의 404만으로 보호 기록을 해제하거나 새 요청으로 바꾸지 않는다. 대표 개인정보 형식·길이·수량·지역·시간을 전송 전에 검사하고, 미확정 상태에서는 결과 조회와 동일 원 요청의 명시적 재전송만 제공한다. 계속 확인되지 않는 입력 오류의 새 입력 재개는 이번 범위에서 지원하지 않는다. 보호 저장소의 payload 보관 기간이 끝난 경우 결과 조회만 가능하다.
