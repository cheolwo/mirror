# 쌀떨 Simulation 규칙 자료집

공간기획자를 위한 현재 규칙·권위·상태 전이 정리
작성 기준: 2026-08-17

> 핵심 문장: AreaSet이 어떤 지역 세계를 만들지 선언하고, 공공데이터가 현실 근거를 제공하며, Simulation 서버가 시간·결정·작업·효과를 확정하고, Unity와 Synty는 그 결과를 표현한다.

## 1. 문서의 목적과 읽는 법

이 문서는 현재 저장소에 만들어져 있는 Simulation 규칙을 공간기획자가 한 번에 파악하도록 정리한 참고서다. API 이름만 나열하지 않고, 각 규칙이 공간에 무엇을 요구하고 어떤 상태를 만들며 Unity에서 무엇으로 보일 수 있는지 연결해 설명한다.

이 자료집에서 완료를 말할 때는 다음 증거를 구분한다.

| 구분 | 의미 |
| --- | --- |
| 확정 결정 | `docs/AI/DECISIONS.md`에 수용된 장기 원칙 |
| 코드 구현 | 계약·도메인·응용 서비스·저장소·API 코드가 존재 |
| 자동 시험 | 관련 단위·통합 시험이 저장소에 존재하고 최근 작업 기록에 통과 사실이 남음 |
| 실행 확인 | 실제 DB, HTTP, Unity Play Mode 또는 Game View에서 확인 |
| 설계 보완안 | 대화·기획에서 합의했지만 아직 확정 결정·코드 계약으로 닫히지 않은 내용 |

이 자료집의 최초 작성은 문서 정리만 수행했지만, 2026-08-17에 감자 300kg 수확부터 Farm→Hub 운송·입고 검수·창고 적재까지를 공간 능력·예약과 연결한 첫 E3 공급선을 추가했다. 최신 구현·시험 범위와 미검증 관문은 [세계 상호작용 단위 중심 공간–Simulation 통합](../Architecture/세계상호작용단위중심공간Simulation통합.md), 전체 행위 목록은 [세계 상호작용 단위 대장](../AI/generated/world-interaction-catalog.md)을 함께 따른다.

## 2. 전체 구조 한눈에 보기

```text
AreaSet 지역 세계 의도
├─ 여러 경관 그래프
├─ 공간·시설 역할
└─ 필요한 현실 근거
        ↓
공공데이터·공간 파생
├─ 지형·토지피복·건물·도로
├─ 출처·기준일·좌표계·해시
└─ 높이·토지피복·배치 마스크
        ↓
Simulation Session
├─ 세계 시간과 개정
├─ 결정 → 작업 → 효과
├─ 재정·노동·창고·재고
├─ 주문·물류·수출
├─ 농장 생활·생존·전투
└─ 팀·NPC·카드·사건
        ↓
관점별 조회 결과·렌더링 의도
        ↓
Unity + Synty 표현
```

권위의 방향은 위에서 아래로 흐른다. Unity의 배치 객체, 애니메이션, 차량 위치, 상자 수, 파티클과 화면 버튼은 서버 상태를 보여줄 수 있지만 업무 완료·승패·재고·시간을 확정하지 않는다.

## 3. 모든 규칙에 공통으로 적용되는 불변 원칙

### 3.1 서버가 최종 상태를 확정한다

- 클라이언트는 안정적인 고유 식별자, 명령 식별자와 예상 개정만 보낸다.
- 비용·기간·성공 확률·피해·보상·수량 보정은 서버가 규칙 개정과 시나리오 seed로 계산한다.
- Unity가 계산한 운임, 무게 보정, 전투 피해, 작업 완료 시각은 권위 입력이 아니다.
- 오래된 예상 개정은 충돌로 거부하며 클라이언트가 임의로 개정을 올려 재전송하지 않는다. 최신 상태를 다시 조회한다.

### 3.2 미리보기와 확정과 완료를 나눈다

```text
현재 상태 조회
→ 미리보기: 후보 계산, 상태 불변
→ 명시적 확정: 결정 기록, 자원 예약, 작업 생성
→ 세계 진행: 작업 진행·완료
→ 효과 적용: 재정·재고·시설 상태 변경
→ 최신 상태 재조회
```

- 미리보기는 `WorldTick`, 개정, 재고를 바꾸지 않는다.
- 확정은 보통 비용·노동·용량·원천 수량을 예약하고 작업을 만든다.
- 실제 수량 변화와 완료 상태는 예정된 세계 진행 시점에만 적용한다.
- 같은 명령 식별자의 동일 요청은 멱등 재사용하고, 다른 내용으로 재사용하면 거부한다.

### 3.3 Simulation과 운영을 분리한다

- 모든 게임 규칙은 기본적으로 `SimulationOnly=true`, `IsOperationalState=false`다.
- 실제 주문·결제·계약·기사 배차·GPS·통관·정산·개인 알림을 만들지 않는다.
- 운영에서 수집한 공공데이터는 읽기 전용 근거로 사용할 수 있지만 Simulation 결과를 운영 원장으로 자동 승격하지 않는다.
- 공유 공공데이터 DB, 공간 파생 DB, Session 저장 DB의 책임과 권한을 분리한다.

### 3.4 표현은 권위가 아니다

- 차량이 목적지에 도착해 보여도 물류 상태가 완료되는 것은 아니다.
- NPC 애니메이션이 끝나도 업무 완료가 아니다.
- 카메라 전환·선택·관전은 `WorldTick`이나 개정을 바꾸지 않는다.
- Synty 원본 Prefab 이름·경로·GUID는 업무·공간 고유 식별자가 아니다.

## 4. 시간·세션·개정 규칙

### 4.1 세계 시간

기본 달력 규칙은 `1 Tick = 1 Game Day`다. 세계 상태에는 Session 고유 식별자, 시나리오 seed, 자료 개정, 규칙 개정, `WorldTick`, `WorldRevision`, 게임 날짜가 함께 보존된다.

경영 중의 조회·미리보기·카메라 이동·공간 이동만으로 날짜가 자동 진행되지 않는다. 턴 마감 미리보기와 명시적 확정 또는 규칙에 정의된 세계 진행 명령에서만 다음 Tick으로 넘어간다.

### 4.2 세계 시간과 전투 시간

병렬 전투는 세계 시간과 별도의 `BattleTick`, `BattleRevision`을 가진다.

| 시간축 | 소유 상태 | 다른 시간축과의 관계 |
| --- | --- | --- |
| 세계 Tick | 경영·노동·재고·물류·농장·정착지 | 전투 명령만으로 증가하지 않음 |
| 전투 Tick | 배치·전투 명령·자동 판정 | 세계 경영 진행만으로 증가하지 않음 |

전투가 끝나도 결과가 즉시 세계 상태를 덮어쓰지 않는다. 완료 결과는 대기 상태로 남았다가 다음 안전한 세계 Tick에 합류한다.

### 4.3 개정과 동시성

- 상태 변경 명령은 예상 개정을 검사한다.
- 미리보기 응답은 어떤 상태를 기준으로 계산했는지 개정을 포함한다.
- Unity는 서버 상태 사본보다 낮은 개정을 적용하지 않는다.
- 같은 고유 식별자와 같은 상태는 유지하고, 높은 개정만 갱신한다.
- 중복 고유 식별자나 낮은 개정이 섞인 상태 사본은 부분 적용하지 않고 전체를 거부한다.

## 5. 결정–작업–효과 공통 원장

Simulation의 대부분의 업무는 다음 세 층으로 기록된다.

| 층 | 질문 | 대표 상태 |
| --- | --- | --- |
| 결정 | 무엇을 하기로 했는가? | 미리보기 후보, 확정 결정 |
| 작업 | 언제 무엇이 진행되는가? | 예정, 진행 중, 완료, 차단 |
| 효과 | 무엇이 실제로 달라졌는가? | 대기, 적용 완료, 취소 |

확정된 결정에는 작업과 효과의 인과가 연결된다. 화면은 효과가 적용된 최신 상태를 다시 조회해야 하며, 버튼 클릭 성공이나 애니메이션 완료만으로 적용 완료를 가정하지 않는다.

자원은 확정 시 예약하고 작업 완료 시 실제 반영한다. 예약된 재정·노동·창고 용량·수확물·NPC·보급품을 다른 활성 작업이나 전투가 중복 사용할 수 없다.

## 6. 정착지 경제와 수확 판로

### 6.1 정착지 상태

시나리오가 제공한 경우에만 다음 게임 상태를 가진다.

- 재정: 전체, 예약, 사용 가능
- 공동 노동력: 전체, 예약, 사용 가능
- 창고 용량: 전체, 예약, 사용 가능
- 시장 공급 재고
- 비축 Stock Lot과 식량 환산량
- 주민·주둔군 수요와 식량안보일수

식량안보일수는 명시된 Fixture 환산 규칙에 따른 게임 지표이며 실제 영양·정책 수치가 아니다.

### 6.2 네 가지 수확 판로

수확 Lot은 조합 출하, 온라인 직판, 수출 대행, 비축 중 하나에 배정할 수 있다. 서버는 비용·노동·기간·예상 수입·시장 공급·비축 후보를 계산하지만 네 판로를 자동 순위화하거나 자동 선택하지 않는다.

| 판로 | 완료 시 대표 효과 |
| --- | --- |
| 조합 출하 | 비용과 Simulation 수입 |
| 온라인 직판 | 비용·수입·시장 공급 |
| 수출 대행 | 비용과 Simulation 수입, 후속 수출 준비 후보 |
| 비축 | 2% Fixture 감모 뒤 비축 Lot·식량 환산량·식량안보일수 |

같은 수확 Lot은 최초 확정 뒤 다른 판로에 다시 배정할 수 없다. 완료 전 예약은 다른 업무가 같은 수량을 쓰지 못하게 한다.

## 7. 물류·화물·창고 규칙

### 7.1 물류 이동

물류 이동은 수확 Lot과 포장 Lot 계보를 보존한 같은 Cargo를 사용한다.

```text
수확 Lot 배정
→ Cargo 이동 미리보기
→ 이동 확정과 원천 수량 예약
→ Reserved
→ InTransit
→ ArrivedAtDestination
→ 목적지 재고 후보
```

목적지 도착은 검수 전 후보이며 곧바로 Hub 재고가 아니다.

### 7.2 화물운송

화물운송은 같은 Cargo에 운송 의뢰·배차 후보·가상 차량 용량과 상태 이력을 연결한다. 물류 이동을 복제하지 않는다.

차량 도착 뒤에도 `하차지도착`에 머물며, 별도 인수 미리보기·확정·작업 완료 Tick에서만 `인수완료`가 된다. 실제 기사, GPS, 운임 정산과 운송사 알림은 만들지 않는다.

### 7.3 창고 적재

검수가 끝난 재고는 `보관 가능`이지만 아직 적재 완료가 아니다. 별도 적재 작업을 만들고 NPC의 이동·작업 단계가 끝나야 `적재 완료`가 된다.

```text
도착 후보
→ 입고 검수
→ 보관 가능
→ 적재 작업
→ NPC 이동
→ NPC 작업
→ 적재 완료
```

### 7.4 공간과 창고 규칙의 상호작용

진부 Hub 입고 검수와 창고 적재는 첫 세계 상호작용 단위로 공간 조건까지 검사한다.

- 입고 검수는 화물 접근, 작업자 접근과 검수 작업 영역 1자리를 요구한다.
- 창고 적재는 보관, 화물 접근, 작업자 접근, 적재 작업 영역과 재고 수량만큼의 보관 용량을 요구한다.
- 미리보기는 공간을 점유하지 않는다.
- 확정은 기존 자원과 공간을 함께 예약한다.
- 완료는 작업 영역을 반환하고, 적재의 보관 예약은 실제 사용 중 용량으로 전환한다.
- 취소는 해당 작업이 만든 예약과 임시 상태만 계보를 따라 반환한다.

현재 첫 구현은 `Scenario` 근거의 검수 공간과 창고를 사용한다. 실제 진부 Hub 경관 그래프 노드 기반 공간 근거로 승격하는 작업은 아직 남아 있다.

### 7.5 감자 생산→Hub 보관 E3 공급선

현재 자동 시험과 시험 HTTP 호스트에서 다음 인과선이 연결돼 있다.

```text
100m² 수확 준비 재배 단위
→ 결정적 수확 300kg
→ 수확 Lot 집하
→ 포장 Lot·Cargo 생성
→ 상차 공간 예약
→ Farm–Hub 회랑 이동 3 Tick
→ Hub 하차 공간 해제
→ 입고 검수
→ StorageEligible
→ 창고 적재
→ PutAwayCompleted
→ 창고 사용 중 용량 300kg
```

상차 공간, 운송 회랑과 하차 공간은 역할별로 따로 판정한다. 출발 시 상차 작업 영역을 반환하고 목적지 도착 시 하차 작업 영역을 반환한다. 이 공급선은 상태 계보·예상 개정·명령 멱등성·공간 예약·저장 재생 해시와 시험 HTTP 왕복을 E3 증거로 가진다.

여기서 300kg과 모든 공간은 결정적 시나리오 시험값이다. 실제 평창 생산량, 실제 도로 통행 가능성, 실제 진부 Hub 보관 면적을 의미하지 않는다. E4는 이 E3 행위를 품는 위치 독립적 WI 공간 모판, E5는 그 모판을 실제 도로·Block·경관 그래프에 배치한 지역 경관, E6는 필요한 공공데이터 계보, E7은 실제 플레이 폐루프로 별도 검증한다.

## 8. 주문·소비·음식배달 규칙

### 8.1 같이주문

- 참여자별 명시적 동의와 의향 수량을 보존한다.
- 같은 참여자의 중복 의향을 막는다.
- 미리보기는 목표 충족 여부만 계산한다.
- 명시적 확정 뒤 완료 Tick에서 목표 충족은 `확정`, 미달은 `모집종료목표미달`로 전이한다.
- 실제 주문·결제·자동 참여 동의를 만들지 않는다.

### 8.2 개별주문과 취소

개별주문 확정은 시장 재고와 노동을 예약하고 포장 작업을 만든다. 작업 완료 Tick에서만 수령준비가 된다. 수령준비 전 취소는 원래 작업과 효과를 취소하고 재고·노동 예약을 반환한다.

주민 수령·소비는 별도 결정이다. 이미 주문 이행에서 시장 재고가 차감됐으므로 소비 완료 때 시장 재고를 다시 줄이지 않는다. 주문·재고 예약·상품·주문자·수량 계보를 검사하고 중복 소비를 막는다.

### 8.3 음식배달

```text
주문대기
→ 조리중
→ 픽업대기
→ 기사배정 후보
→ 픽업완료
→ 전달완료
→ 주문자의 별도 수령확인
```

`전달완료`와 `수령확인`은 다르다. 전달 Task나 NPC·차량 애니메이션만으로 수령확인하지 않는다. 주문자가 별도 미리보기·확정을 하고 완료 Tick을 거쳐야 한다.

## 9. 수출 준비와 선적 규칙

수출 흐름은 하나의 버튼으로 완료되지 않고 독립된 검토·인계 단계로 이어진다.

```text
수출 판로가 적용된 수확 배정
→ 수출 준비·모의 검사
→ Cargo 준비
→ 배송대행지 인계
→ 물류 이동
→ 항만 준비시설 인수
→ 수출 준비성 검토
→ 선적 계획 후보
→ 선적 실행
```

핵심 경계는 다음과 같다.

- 모의 검사 통과는 실제 검사기관 승인이나 수출 완료가 아니다.
- Cargo 준비 완료는 실제 배송대행지 인수·운송 계약·차량 출발이 아니다.
- 배송대행지 인계, 물류 이동, 항만 인수는 각각 별도 미리보기·확정을 요구한다.
- 준비성 검토의 서류·검사 준비 여부는 Simulation 자기 진술이다.
- 선적 계획은 견적·수익 보장이 아니며 정착지 재정과 출고 예약을 즉시 바꾸지 않는다.
- 선적 실행은 세션 seed와 실행 고유 식별자의 결정적 판정으로 성공 또는 손실을 재현한다.
- 실제 수출신고·검역·통관·선적·정산을 만들지 않는다.

## 10. NPC 조직·업무 행동 규칙

NPC는 운영 사용자의 계정이나 실제 조직원이 아니라 Simulation 전용 행위자다.

### 10.1 배정 원칙

1. 조직·시설·필요 역량을 만족하는 활성 NPC만 후보가 된다.
2. 선호 담당자, 현재 작업량, 기술 수준, NPC 고유 식별자 순으로 결정적으로 정렬한다.
3. 적격자가 부족하고 자동 위임이 허용되면 권한을 가진 관리자가 같은 조직·시설의 NPC에게 역량을 위임한다.
4. 자동 위임으로 받은 역량은 다시 위임할 수 없다.
5. 적격자가 없으면 작업을 삭제하지 않고 차단 상태로 남긴다.
6. 정책·역량이 바뀐 다음 Tick에 차단된 작업을 다시 평가한다.

### 10.2 행동 단계

첫 세로 단위는 진부 Hub의 `입고검수 → 적재`다.

| 단계 | Simulation 의미 | Unity 표현 |
| --- | --- | --- |
| 배정 | 담당 NPC와 일정 확정 | 업무 표시 |
| 이동 | WorldTick 기반 이동 단계 | Walk 표현 |
| 작업 | 검수·적재 진행 | 작업 애니메이션 후보 |
| 완료 | 업무 기록과 시설 재고 상태 변경 | 완료 상태 표시 |

사용자는 NPC를 직접 움직여 완료시키기보다 자동 배정, 자동 위임, 선호 담당자와 우선순위 정책을 바꾸는 방식으로 개입한다.

공간 능력은 NPC 역량과 별개다. NPC 역량은 “누가 할 수 있는가”, 공간 능력은 “어디에서 할 수 있는가”를 판정한다. 두 조건이 모두 만족해야 입고 검수나 창고 적재를 확정할 수 있다.

## 11. 농장 생활·생존·계절 방어 규칙

### 11.1 기본 28일 경관 장

새 농장 생존 Session의 기본 규칙은 `farm-survival.scenic-season.r1`이다.

| 날짜 | 플레이 | 서버 상태·규칙 |
| --- | --- | --- |
| 1~23일 | 경관 산책, 지역 발견, 선택 농사 | 평온 탐색, 위협 없음 |
| 24일 | 계절 방어 예고 | 경고, 아직 응답 불가 |
| 25~26일 | 울타리·창고·조명·경계 준비 | 시설 준비도 누적 |
| 27일 | 자동 방어 또는 직접 전투 선택 | 방어 선택 대기 |
| 28일 | 선택 또는 미응답 자동 판정 | 회복 가능한 결과·계절 보고 |

직접 전투를 선택한 경우에만 전투 대기로 전환한다. 선택하지 않으면 28일 자동 방어가 기록되어 진행이 멈추지 않는다. 기본 경관 장에서는 약탈자 사건을 만들지 않는다.

### 11.2 농장 노동

- 플레이어 직접 노동: 개인 체력 소비, 기본 1 Tick, 공동 노동력 예약 없음.
- NPC 위임 노동: 공동 노동력 예약, 기본 2 Tick, 완료 뒤 예약 반환.
- 같은 배우는 농장 작업을 동시에 하나만 수행한다.
- 방어 재료·체력·노동력이 부족하면 미리보기에 차단 이유를 주고 확정을 거부한다.
- 위협 결과는 영구 사망 대신 보급품 손실, 시설 피해, 부상과 수리 필요량으로 남긴다.

### 11.3 기존 봄 준비 전투 규칙

`farm-survival.spring-preparation.r1~r3`은 명시적으로 선택한 기존 전투 시나리오와 저장·재생 호환을 위해 유지한다.

- r1: 방어 준비도로 자동 판정.
- r2: 한 번에 한 공격 박자의 직접 반응.
- r3: 성공한 1인칭 반응을 다음 명령창까지 전술 기회로 연결.

전투 충돌 기준은 전조 시작 뒤 1,000ms다.

| 반응 | 1인칭 일반 구간 | 전술 3인칭 일반 구간 | 완벽 구간 | 결과 |
| --- | ---: | ---: | ---: | --- |
| 방어 | ±320ms | ±220ms | ±70ms | 완벽 피해 0, 일반 피해 3 |
| 카운터 | ±200ms | ±130ms | ±45ms | 성공 피해 0, 경직 |
| 너무 빠름·늦음·미반응 | 해당 없음 | 해당 없음 | 해당 없음 | 피해 10, 점수 0 |

방어 준비도와 반응 점수의 합이 2 이상이면 농장 방어에 성공한다. 판정 등급·피해·점수는 서버가 결정하며 클라이언트 명령에는 넣지 않는다.

## 12. 병렬 경영–전투 규칙

한 팀원이 전투하는 동안 다른 팀원은 같은 Session의 농장·창고·정착지 경영을 계속할 수 있다.

전투 참가 형태는 지휘관, 위임 분대, 관찰자로 나뉜다. 관찰자는 세계 상태를 조작할 수 없다. 경영 측은 보급 상자와 증원 분대를 제한적으로 지원할 수 있지만 같은 자원을 다른 전투나 경영 작업에서 중복 사용하지 못한다.

전투 생성·참가·배치·지원·전투 진행은 모두 명령 식별자와 예상 개정을 검사한다. 진행 중 전투와 자원 예약은 명시적 Session 저장 자료에 포함된다. 현재 활성 전투 잠금은 서버 프로세스의 공유 메모리 저장소가 기준이며 다중 서버 분산 잠금과 자동 시작 복원은 아직 보장하지 않는다.

## 13. 팀 협동·관전·역할 카드·수집 보상

### 13.1 팀 관전

같은 Simulation 팀은 정책이 허용한 시선·따라보기 관전을 별도 건별 요청 없이 사용할 수 있다. 관전 중에는 대상에게 관찰자를 표시한다.

- 관전은 조작 권한을 공유하지 않는다.
- 로컬 이동·시선·재고·세계 시간·개정을 바꾸지 않는다.
- 팀 이탈, 정책 개정, 종료 또는 관찰자의 로컬 위험 시 관전을 종료한다.
- 공개 위치에는 L2 타일, 타일 내부 위치, 표고 참고, 카메라 높이, 시선과 이동 의도만 포함하며 재고·개인 UI·대화는 포함하지 않는다.

### 13.2 팀 공동 역할 카드

역할 카드는 사건 해결용 생존 타로와 다르며 물리 아이템이 아니다.

- 카드 사본 하나는 한 시점에 한 장착 칸에만 있다.
- 팀원이 다른 타일에 있어도 서버 개정을 확인해 원격 장착할 수 있다.
- 활동 시작 동안 카드와 배우가 잠긴다.
- 한 배우는 동시에 하나의 활동만 수행한다.
- 탐험가·농부·물류 담당 표시는 현재 장착 카드와 활동에서 파생된 역할이며 영구 직업이 아니다.

카드 장착·활동 시작·종료는 Session 명령 로그와 저장·재생 해시에 포함된다. 공간 파생 DB에는 규칙 정의만 두고 현재 장착 상태는 복제하지 않는다.

### 13.3 수집 카드

L2·L1 지역 발견과 직접 농사 완료는 개인 수집 카드 기회를 만들 수 있다. 수집 카드는 역할 카드와 생존 타로를 대체하지 않는다. 발견 타일, 미개봉 기회, 실패 보정, 카드 사본, 소유자와 양도 이력은 Session 가변 상태로 저장한다.

## 14. 생존 타로와 일반 타로 규칙

### 14.1 생존 타로

기본 생존 기회는 한 Tick을 하루로 보는 3일 주기와 식량 비축 `2 인일 이하` 위기에서 발생한다. 농장 범위가 지정된 시나리오는 농장 건물·농장 참여자의 자급 식량을 별도로 계산해 외부 탐색 필요 기회를 우선 만든다.

- 미해결 기회는 한 건만 유지한다.
- 같은 seed·Tick·덱 개정·선택 이력은 같은 3장 제안을 만든다.
- 안전 거점에 참여자 전원이 함께 있고 동일 제안에 합의해야 확정할 수 있다.
- 확정 보정선은 즉시 상태를 바꾸지 않고 다음 Tick 한 번만 활성화한다.
- 카드 방향·수치·보정은 서버가 정한다.

### 14.2 일반 타로 계층

일반 타로는 다음 자료를 분리한다.

```text
타로 원형 정의
→ 게임용 해석 정의
→ 시나리오 덱 정의
→ 턴 카드 제안 상태
→ 경영 대응 정의
→ 배치 객체 반응 관점별 조회 결과
```

카드의 상위 의미가 하위 물류·경영 규칙을 보정할 수 있지만 하위 원장을 대신하지 않는다. 클라이언트는 대응 고유 식별자와 예상 개정만 보내며 서버가 원래 업무 미리보기를 계산한 뒤 카드 보정을 적용한다.

## 15. 저장·재생과 결정성

`simulation-save.v1`은 다음을 보존한다.

- Session 생성 요청과 시나리오 seed·자료 개정·규칙 개정
- 저장 시점 상태 사본
- 확정·Tick 등 append-only 명령 로그
- 진행 중 전투와 자원 예약
- 세계 사건·팀 역할·NPC·농장·카드 상태
- 패키지 SHA-256과 재생 결과 SHA-256

복원은 저장된 상태를 aggregate에 직접 주입하는 방식이 아니라 새 Session에 명령을 순서대로 다시 실행하는 방식이다. 패키지 hash와 재생 결과 hash, 세계 Tick과 개정이 모두 맞을 때만 활성 Session으로 등록한다.

공유 공공데이터 DB에는 Session 저장 자료를 넣지 않는다. 별도 Simulation Session DB가 저장 식별자, Session 식별자, schema, Tick, 개정, 명령 수, 재생 hash와 전체 JSON을 보존한다. 활성 aggregate는 기본적으로 프로세스 메모리에 있으며 명시적 저장·복원을 사용한다.

## 16. 공공데이터·AreaSet·경관 그래프 규칙

### 16.1 공공데이터의 역할

공공데이터는 지형·법정동·건물·도로·공개 사업체의 현실 근거다. 위협·재고·NPC·업무 완료를 만들지 않는다.

모든 공간 원본은 출처, 기준일, 좌표계, 수평 해상도, NoData와 SHA-256을 가진다. DEM은 높이 단위와 수직 기준을 추가로 기록한다.

- 물리 표고: 경사·수계·배치 가능 여부의 근거.
- 시각 표고: Renderer 높이 과장과 기준 offset만 담당.
- 원본 자료가 없거나 불충분하면 비슷한 위치·도로·건물을 꾸며내지 않고 미해결로 남긴다.

### 16.2 Tile·Area·AreaSet

| 개념 | 책임 |
| --- | --- |
| Tile | 공간 절단·산출물·캐시 단위. L0 8km, L1 2km, L2 500m |
| Area | 법정동 또는 Farm·Hub·Town 같은 의미 범위 |
| 경관 그래프 | 독립 조립·검증·부분 재생성·스트리밍 단위 |
| AreaSet | 여러 Area·경관 그래프·회랑·시나리오를 묶는 지역 세계 정의서 |

평창 Farm–Hub–Town AreaSet은 대관령 Farm, Farm–Hub 회랑, 진부 Hub, Hub–Town 회랑, 평창 Town의 다섯 경관 그래프를 가진다. 그래프 내부 Node는 다른 그래프 Node를 직접 참조하지 않고 AreaSet의 그래프 관계와 양쪽 외부 연결점 쌍으로만 연결한다.

사람이 작성한 Markdown은 의도·근거·미해결을 설명하고 JSON만 실행 권위를 가진다. Compiler가 양쪽 참조가 일치하는지 검사하고 해시를 분리한다.

### 16.3 경관 그래프 상태와 Unity 스트리밍 상태

서버의 `Declared / Available / PartialUnresolved`는 공간자료와 조립 결과 상태다. Unity의 `Unloaded / Declared / Prepared / Active / Cached`는 플레이어별 메모리·표시 상태다. Unity 스트리밍 상태는 서버의 그래프 준비도를 변경하지 않는다.

첫 대관령 1km 완결 영역은 L2 타일 네 개다. 현재 저장소 기록상 중앙 타일 하나는 DEM·토지피복·배치 마스크가 준비됐고 이웃 세 타일은 공간 산출물 대기 상태다. 따라서 계약·DB·API·조립 코드는 존재하지만 대관령 Farm 전체와 평창 AreaSet 전체가 실자료로 완결됐다고 보지 않는다.

### 16.4 기준 공간 문법과 Synty 제작 조합

기준 경관 문법은 52개 의미군의 A/B/C 변형, 총 156개다.

| 계열 | 의미군 | 변형 포함 수 |
| --- | ---: | ---: |
| 자연 | 12 | 36 |
| 농장 | 8 | 24 |
| 마을 | 6 | 18 |
| 도시·거점 | 6 | 18 |
| 연결망 | 12 | 36 |
| 전환 | 8 | 24 |
| 합계 | 52 | 156 |

이 156개는 서버 경관 그래프가 소비하는 안정된 공간 어휘다. 실제 Synty 팩으로 만들어 둔 제작 조합 재고는 별도 대장으로 관리하고 기준 문법에 후보로 연결한다. 두 대장이 우연히 같은 숫자를 가질 필요는 없다.

현재 조립기는 공간 골격 Node의 계열·의미군·위상을 기준으로 A/B/C 후보를 좁히고 AreaSet·Tile·Node·좌표·문법 hash로 결정적 변형과 회전·반전을 선택한다. 연결구가 있는 문법은 외부 Tile 연결점 계산에도 사용하며 후보가 없으면 `NoCompatibleComposition` 미해결로 남긴다. 경사·수계·토지피복·렌더링 비용은 문법 대장에 보존되어 있지만 현재 Domain 조립기가 전부 강제하는 것은 아니므로 후속 계획·검증 입력과 현재 실행 소비 필드를 구분한다. 상세 목록은 [기준 경관 문법 156개 사용 설명서](../AI/generated/landscape-grammar-156-guide.md)를 따른다.

### 16.5 WI 공간 모판의 현재 위치

`기준 공간 문법 = 단어`, `WI 공간 모판 = 하나 이상의 E3 행위를 품는 재사용 가능한 문장`, `경관 그래프 = 특정 장소에 적용된 글`로 구분한다. WI 공간 모판은 공간 역할·능력·업무 용량·내부 관계·외부 연결구·허용 경관 문법 후보를 가지되 AreaSet·Graph·Tile·절대좌표와 Unity 자산 경로를 갖지 않는다.

첫 구현은 별도 `LandscapePattern`, `PatternTopology`, `OriginMode` 계약을 만들지 않는다. `eng/world-seedbeds/wi-spatial-seedbeds/`의 다섯 실행 정의가 13개 WI를 수용하며, 기존 156개 기준 경관 문법의 `compositionKey`를 허용 후보로만 참조한다. Compiler가 WI의 E3 상태, 능력 충족, 내부 전이, 외부 연결구 쌍, 금지 필드와 결정적 SHA-256을 검증한다. 모판에서 생성한 시험 공간으로 같은 300kg 공급선과 Save/Replay를 다시 통과하지만, 이는 실제 지역 배치나 공공데이터 근거가 아니다.

## 17. 렌더링 의도·Unity·Synty 표현 규칙

Simulation은 “무슨 상태인가”를 확정하고 렌더링 의도는 “무엇을 강조할 것인가”로 번역한다. Unity 구성 대장이 현재 기기 능력에 맞는 실제 표현을 선택한다.

```text
Simulation 상태 사본
→ 렌더링 의도
→ 환경·표면·조명·객체·주의·효과·애니메이션 Channel 합성
→ 공간·Synty 근거와 기기 능력 결합
→ Unity 표현 상태
```

같은 대상과 같은 Channel에서는 높은 우선순위를 선택하고, 같으면 의도 고유 식별자 순으로 결정한다. 억제된 의도와 이유도 남겨 결정성을 보존한다.

예를 들어 `Cargo = InTransit`을 직접 Bloom 수치에 연결하지 않는다.

```text
운송 중
→ 경로 흐름 활성
→ 의미 기반 URP 표현 키
→ Unity가 MaterialPropertyBlock·Particle·Animation으로 표현
```

공간 원본이 흙길을 증명하지 않으면 먼지 효과를 생략한다. 기기가 Particle을 지원하지 않거나 예산이 0이어도 Simulation 상태는 실패하지 않고 단순 표현으로 낮춘다.

## 18. 공간기획자가 규칙을 적용하는 방법

### 18.1 AreaSet에서 시작하는 세계 의도형 기획

1. 지역 세계의 주제와 플레이 경험을 적는다.
2. 독립적으로 조립할 경관 그래프를 나눈다.
3. 그래프마다 농장·거점·마을·회랑 역할과 외부 연결점을 정의한다.
4. 필요한 현실 근거와 자료 한계를 선언한다.
5. 그 공간에서 가능한 Simulation 업무·사건·NPC 활동을 연결한다.
6. 기준 공간 문법과 제작 조합 후보를 선택한다.
7. 서버 준비도와 Unity 표현 상태를 분리해 검토한다.

### 18.2 Synty에서 시작하는 표현 탐색형 기획

1. 팩별로 가능한 공간 재료와 표현 비용을 조사한다.
2. 제작 조합으로 도로·블록·수계·거점 배치를 실험한다.
3. 좋은 배치를 Synty 이름이 아닌 농장 구획·숲 가장자리·십자 농로·수변 회랑 같은 중립 공간 의미로 기록한다.
4. 재사용 가치가 있는 배치를 공간 패턴 보완안으로 승격한다.
5. AreaSet에 적용할 때 지형·경사·수계·도로 근거로 변형·절단하고 경관 그래프로 조립한다.

현재 상향식 설계 지식 저장소는 [Synty 상향식 공간 재고 계획](../Architecture/Synty상향식공간재고계획.md)에 따라 행동 공간 H1 52개와 팩 단독 표현 H1 32개, H2 블록 조립법 24개, H3 경관 청사진 13개, H4 지역 청사진 후보 6개를 관리한다. 이 가운데 기존 승인 H1 다섯 개만 공식 H1 정의다. 팩 표현 H1은 WI·능력·용량을 자동 추론하지 않으며, 연결된 행동 공간과 게임 기획이 없는 9장은 `IdeaInventory`로 격리한다. H4 후보는 실제 AreaSet 권위를 갖지 않는다.

초기 `catalog.v1.json`과 항목별 `catalog.v2.json`은 호환 입력으로 보존한다. 현재 `catalog.v3.json`은 52개 의미군·156개 변형, 검토된 조립법, 문법→H1→H2→H3→H4 계보와 양쪽 파일 SHA-256을 봉인한다. 조회 도구는 WI·공간 능력·팩·문법·위상으로 행동 H1과 표현 H1, H2~H4 후보를 분리해 제안할 뿐 공식 H 정의나 AreaSet·경관 그래프를 자동 생성하지 않는다.

### 18.3 공간과 규칙 연결 질문

- 이 공간에서 누가 어떤 활동을 시작할 수 있는가?
- 활동에 필요한 재정·노동·용량·재료는 무엇인가?
- 미리보기, 확정, 완료는 화면에서 어떻게 구분되는가?
- 작업 중 예약된 공간·시설·자원을 무엇이 다시 쓸 수 없는가?
- 세계 Tick과 전투 Tick 중 어느 시간축을 쓰는가?
- 실패가 영구 파괴인지 회복 가능한 손실인지?
- 공공데이터가 증명한 사실과 시나리오가 만든 의미는 무엇인가?
- Unity가 표현할 수 있지만 확정해서는 안 되는 상태는 무엇인가?

## 19. 현재 증거 수준과 남은 위험

### 19.1 확인된 기반

- 별도 Simulation 서버와 Domain·Application·Infrastructure·Persistence·Server 계층.
- Session, 예상 개정, 명령 멱등성, 세계 Tick, 결정–작업–효과, 저장·재생.
- 수확 판로, 물류·화물·창고, 같이주문·개별주문·소비·음식배달, 수출 준비 흐름.
- NPC 업무, 농장 경관 장·노동·전투, 팀 역할·관전, 세계 사건과 병렬 전투.
- 공간 파생 DB, AreaSet·경관 그래프, L2 스트리밍, 기준 경관 문법, Synty 표현 분리.

### 19.2 아직 완료로 보지 않는 항목

- 실행 중 서버와 전체 규칙의 최신 HTTP 종단 왕복.
- 병렬 전투의 실제 Unity HTTP 저장소·저장 Scene 배선·Play Mode·Game View.
- 대관령 2×2 L2 현실 정합 프로필의 나머지 세 타일 DEM·토지피복·배치 마스크. 이는 선택형 E6 준비도이며 Scenario 세계의 공통 차단 조건이 아니다.
- 평창 다섯 경관 그래프 전체 조립과 양쪽 외부 연결 검증.
- 승인된 WI 공간 모판을 작성 도로 역할·Junction·Block·경관 그래프에 배치하는 E5 계획기와 저장 계보. 실제 도로 정합은 선택한 E6 프로필에서 별도로 수행한다.
- 실제 URP Adapter와 Frame Debugger 성능 검증.
- 자동 저장·서버 재시작 자동 복원·다중 서버 분산 자원 잠금.
- 멀티플레이 위치 전송과 팀 원장의 실제 네트워크 연결.
