# PlayableLoop 문답 정밀화 체계

## 목적

짧은 정차·대기 시간에도 PlayableLoop 기획을 안전하게 정밀화하고, 여러 번의 대화를 저장소 문서로 이어 붙여 승인 가능한 기획서로 만든다. D-398부터 기본은 **한 회차에 핵심 질문 하나**다. 지금·여기·나·너·이렇게와 결과·다음 선택의 상황을 함께 생각하고, 짧은 추천과 대가를 제시한 뒤 답변에 따라 다음 질문을 깊게 이어간다. D-353/D-397의 약 10개 묶음 기본은 대체하며, 묶음은 사용자가 다시 요청할 때만 사용한다.

문답은 공식 기획 절차의 `Draft` 단계다. 대화 기록 자체는 구현 명세나 승인 근거가 아니며, 매 회차의 정리 결과를 판본화된 문답 기록과 주제 기획서에 반영해야 저장소 인계 자료가 된다.

```text
대상 PlayableLoop 선택
  -> 문답 기록 개설
  -> 기존 결정 검색·구현 공백 선정
  -> 지금·여기·나·너의 상황 + 핵심 질문 하나 + 추천·대가
  -> 사용자 답변·수정·보류
  -> 해석·확정 후보·미정·영향 정리
  -> 승인 범위 기획·명세 결속 및 개발 통합 담당 인계
  -> 결과·다음 선택에서 이어지는 후속 질문 하나
  -> 분야별 전문 연구 질문 분기
  -> 전체 모순·누락 검토
  -> 주제 기획서로 합성
  -> 사용자 검토
  -> ReadyForReview
  -> 전문 연구 Accepted·재결속
  -> Approved
```

## 기획 결과의 관계형 저장 — D439

문답에서 WI 재사용/후보와 객체·자산 관계를 판단한 결과는 [기획 문서 → 로컬 관계형 DB 파이프라인](기획판본-서버반입파이프라인.md)에 따라 같은 문서의 표준 블록으로 정리한다. API 전송을 전제로 하지 않고 로컬 검사 뒤 기존 ASP.NET Core 저장 기능을 직접 사용한다. 문서 검토·DB 저장·자산 선택·Unity 적용을 구분하며 미정 답변을 저장 과정에서 자동 승인하지 않는다.

## 안전한 사용 경계

- 이동 중이거나 운전에 주의를 기울여야 할 때 답변을 요구하지 않는다.
- 사용자가 안전하게 정차했거나 대기 중일 때만 문답을 이어간다. 즉시 답변할 필요가 없으며 다음 안전한 시점에 같은 질문부터 재개할 수 있다.
- 핵심 질문 하나에 짧은 추천 답안과 중요한 대가를 붙인다. 즉답할 의무가 없으며 안전한 때 수정·보류로 답할 수 있다. 일곱 관점을 일곱 질문으로 나누거나 한 질문에 여러 결정을 숨기지 않는다.
- 앞 답안을 수정하면 영향을 받는 후속 답안은 자동 확정하지 않고 재검토한다. 같은 상황을 깊게 다루되 이미 답한 내용이나 후반 기능을 억지로 추가하지 않는다.
- 긴 표 작성, 정밀 수치 비교, 화면 확인이 필요한 질문은 묶음에 억지로 넣지 않고 별도 검토 회차로 보낸다.
- 배달 위치, 고객 이름, 연락처, 실제 운행 시각처럼 게임 기획에 필요하지 않은 개인·업무 정보는 기록하지 않는다. 답변에 포함되어도 기획 의미만 일반화한다.

## 한 회차의 계약

기획 스레드는 한 회차마다 다음 순서를 지킨다. 묶음 회차에서도 각 질문은 아래 계약을 독립적으로 만족해야 한다.

1. 현재 대상 PlayableLoop, 주제, 탐구 깊이와 질문 고유 식별자를 밝힌다.
2. 질문이 필요한 이유를 한 문장으로 설명한다.
3. 해당 상황에서 다음 선택을 좌우하는 미정 하나를 골라 질문과 가장 적절한 추천 답안을 작성한다. 회차가 이어지며 소비·실패/회복·공간·표현·귀환을 살피되 기술 구현 방식의 불필요한 사용자 결정을 만들지 않는다.
4. 각 추천의 근거·대가·기존 결정과 차이·의존성을 짧게 남긴다. 자유 수정과 `보류`를 항상 허용한다. 추천 답안을 작성했다는 사실은 사용자 승인이나 실제 E 증거가 아니다.
5. 답변을 받은 뒤 아래 다섯 항목으로 정리한다.
   - 사용자가 말한 의도
   - 확정 후보
   - 남은 미정 또는 충돌
   - 영향을 받는 WI·Logic·Presentation·H·전문 연구
   - 다음 질문
6. 사용자가 의미를 확인하면 문답 기록의 `Confirmed` 항목으로 올린다. `추천 전체 승인`처럼 묶음을 한 번에 승인한 답변은 각 질문의 추천 선택을 개별 결정으로 풀어 기록한다.

짧은 답변을 임의로 완성된 규칙으로 확대하지 않는다. 수치, 보상, 실패 손실, 공간 규모, 애니메이션 시간처럼 플레이 의미를 바꾸는 항목은 해석을 다시 보여주고 확인받는다.

### 네 관점으로 기존 답변과 다음 질문을 연결한다 (D391)

기존 답변을 찾은 뒤 [시간·공간·플레이어·대상 공통 관점](플레이어중심게임개발업무구조.md#시간공간플레이어대상으로-wi를-설명한다-d391)으로 정리한다. 네 관점은 D1~D5 탐구 깊이나 E/H 단계와 별개이며 기존 질문 ID·원문·승인 의미를 유지한다.

- 시간 / 공간 / 플레이어 / 대상의 확정 내용과 미정·해석 제안·해당 없음을 구분하고, 그 사이 WI와 결과→다음 선택을 적는다.
- 하나의 답변이 여러 관점과 여러 H/WI에 연결될 수 있다. 질문 수만큼 H나 WI를 만들지 않으며 기존 관계 색인의 직접 근거·지원 후보·상위 포함·시각 증거 구분을 재사용한다.
- 이미 답한 내용은 원문을 연결하고 다시 묻지 않는다. 누락이 기술 연결인지 새로운 플레이 선택인지 분리한 뒤 후자만 다음 검토 묶음에 넣는다.
- 과거 승인 문서는 우선 대응표로 읽게 한다. 문장 위치·판본·hash가 바뀌는 실제 재편집은 기존 승인 결속을 보존하는 이관 계획 이후 수행한다. 색인 구현·신선도·회귀 검증은 개발에 맡긴다.

### 실제 문답도 지금·여기·나·너·이렇게로 진행한다 (D397)

기존 문서를 분류할 때뿐 아니라 사용자와 새 질문·답변을 주고받을 때도 [공통 안내 말](플레이어중심게임개발업무구조.md#기획의-쉬운-말--지금여기나너이렇게-d394)을 사용한다. D398에 따라 다음 진행 방식을 단일 질문에 적용한다. 새 사고 축이나 질문 대장은 만들지 않는다.

1. **함께 볼 상황:** 기존 원문을 대조해 지금(시간·진행 상태), 여기(공간), 나(상태·의도·가용 수단), 너(상대·사물·환경)를 짧게 제시한다. 확정 내용과 설명용 가정을 구분하며, 이미 답한 칸은 다시 묻지 않는다.
2. **이렇게:** 플레이어가 수행하는 WI·행동·방법과 대가·위험을 설명한다. 하나의 전역 최적해로 강요하지 않고 하지 않기·관찰·보류·위임·후퇴와 다른 유효한 행동을 함께 보존한다. 자동 변화나 읽기 화면을 억지로 새 WI로 등록하지 않는다.
3. **결과와 다음 선택:** 선택의 대가·확인할 변화·남는 상태와 이후 가능한 행동을 연결한다. 다음 선택은 고정 진행 경로가 아니며, 선택한 결과가 다음 문답의 상황이 될 수 있다.
4. **깊이 있는 후속:** 시간 부족, 장소 차이, 플레이어의 준비, 대상 상태처럼 플레이 의미를 바꾸는 조건 하나를 바꾸어 비교한다. 같은 규칙의 재확인을 반복하지 않고 미정인 차이·실패/회복·판독상의 선택만 묻는다. 가정 사례로 규칙·수치·보상을 자동 확정하지 않는다.
5. **검토와 기록(D398):** 한 상황과 핵심 질문 하나·추천·대가를 제시한다. 일곱 칸은 짧은 문장이나 필요한 항목만으로 설명하며 별도 질문 일곱 개로 만들지 않는다. 답변을 정리한 뒤 달라진 상황이나 남은 선택에서 후속 질문 하나를 이어간다. 기존 묶음의 미답변 기록은 보존하되 한꺼번에 다시 제시하지 않는다.

### 수직 심화와 수평 확장의 순환

단일 질문은 한 주제를 끝없이 파고들라는 뜻이 아니다. 같은 장면·노드·세부 대상에서 연속으로 2~3개의 핵심 선택이 확정되면, 다음 질문은 원칙적으로 다른 Area·시스템·플레이 감각의 미정 항목으로 이동한다. 막힌 권위 조건이나 서로 모순되는 선택처럼 바로 닫아야 하는 사항만 같은 주제에서 더 이어간다.

수평 이동은 기존 질문을 폐기하지 않는다. 현재 주제는 `PausedForHorizontalRotation`으로 두고 다음 질문·남은 공백·재개 조건을 기록한 뒤, 아래 축 가운데 현재 전체 기획의 결손이 큰 곳을 고른다.

- 공간: Nature·Farm·Town·Hub·City와 발견·이동·귀환
- 행동: 채집·제작·전투·명상·관계·위임·운영
- 관점: 1인칭 집중·3인칭 활동·광역 운영
- 결과: 개인 회복·NPC 관계·H1 변화·H2 성장·공동체 영향
- 표현: 배치·Synty·Animation·Audio·UI 판독

수평 질문을 한두 번 진행한 뒤 이전 주제의 재개 가치가 높아지면 돌아올 수 있다. 질문 횟수를 기계적으로 균등 배분하지 않고, 전체 게임에서 아직 보이지 않는 플레이 약속을 우선한다. 하나의 개발 인계에 필요한 작은 묶음이 닫혔더라도 사용자가 기획 정밀화를 우선하면 `DevelopmentHandoffDeferred`로 보존하고, 관련 수평 질문이 충분히 모인 뒤 함께 동결한다.

### 전수 현행화와 사용자 문답 우선순위를 분리한다

전수 현행화 순서와 사용자가 답할 질문 순서는 서로 다른 목록이다.

- **전수 현행화 목록**은 누락을 막는 목록이다. 분야 우선순위를 두지 않고 모든 원문·현행 기획·참조·소실·충돌을 반복해서 대조한다.
- **사용자 문답 큐**는 현재 게임 경험을 구체화하는 목록이다. 이미 답한 내용과 기술 공백을 제외하고, 한 번에 질문 하나만 우선순위대로 제시한다.
- 문답 우선순위가 낮다고 기획의 가치가 낮은 것은 아니며, 높은 우선순위가 게임 안의 강제 플레이 순서를 뜻하지도 않는다.

질문 후보는 다음 순서로 비교한다.

1. 게임 상위 목적의 `나의 막힘 → 회복 행동과 대가 → 기여 자원 → 상대의 실제 필요 → 권위 결과 → 환류`를 직접 구체화하는가
2. 플레이어가 초반에 실제로 보고 고를 수 있는 선택이며, 결과와 다음 선택을 닫는가
3. 기존 기획의 핵심 충돌이나 공백을 해소해 Graph Map·배치 맵·작은 개발 인계 범위를 분명하게 만드는가
4. 최근 2~3개 질문이 한 장면에 몰렸다면 다른 Area·행동·관점·결과로 수평 이동하는가
5. 원문·기획 판본이 준비되어 있어 추정 답변이나 기술 조사를 사용자 선택으로 떠넘기지 않는가

질문 큐는 `P0 현재 질문`, `P1 다음 수평 순환`, `P2 핵심 체계 후속`, `P3 수치·균형 후속`, `Hold 근거 대기`, `NotAQuestion 기술·연구·인계`로 구분한다. `P0`는 항상 하나만 둔다. 답변을 받으면 해당 기획 판본에 반영하고 다음 후보를 다시 계산하므로, 오래된 큐의 순서를 기계적으로 소비하지 않는다.

다음 항목은 사용자 문답으로 올리지 않는다.

- 소실 원문 복구, 원작 확보, 라이선스·권리 확인처럼 사실 조사로 해결할 항목
- 정확 Prefab·Clip·Collider·경로·코드 파일·시험처럼 개발 또는 전문 연구가 판정할 항목
- 이미 확정한 선택의 구현 미완료
- 실제 자료 분포를 보기 전의 임계값·시간·거리·확률 숫자

이들은 각 기획의 `Hold`, `전문연구필요`, `구현 가설`, `DevelopmentHandoffDeferred`에 남기고, 실제 플레이 의미가 둘 이상일 때만 선택 차이를 한 질문으로 되돌린다.

답변은 기존 원문·Q/의미 ID와 연결해 확정/미정/제안을 구분한다. 문답 방식에 대한 동의는 예시 상황이나 뒤에 제시할 추천안의 승인이 아니다. 기획은 플레이 의미를 정리하고 개발은 코드·자산·검증 공백을 처리한다. D396의 이미 승인된 준비 작업은 새 문답 전체 완료를 기다리지 않는다.

### 승인과 개발 인계 — D398 단일 질문 기본

### Synty 자산·H 동반 설계 관문

문답에서 건물, 시설, 지형, 도구, 작물, 실내외 소품, 작업 상태처럼 Unity에서 구체적으로 보여야 하는 대상이 발견되면 해당 질문을 답변만으로 닫지 않는다. 다음의 짧은 동반 조사를 수행하고 결과를 같은 문답 기록 또는 연결된 배치 연구에 남긴다.

```text
플레이어가 보아야 할 의미·상태 차이
  -> 필요한 표현 역할
  -> 보유 Synty 실제 Prefab·자산 계열 조사
  -> 직접 사용 / 조합 가능 / 부족 / 보류 판정
  -> H1 기능 공간과 배치 객체 조립안
  -> H2 동선·서비스·생활 관계
  -> H3 반복 폐루프·영역 정체성·성장 관계
  -> VisualKey·fallback·검증 조건
```

- 팩 이름을 Farm·Town·City 같은 게임 영역 권위로 사용하지 않는다. 실제 Prefab 증거와 기능 역할을 먼저 본다.
- `H1`은 플레이어가 직접 사용하거나 판독하는 최소 기능 공간, `H2`는 여러 H1의 동선·서비스 관계, `H3`는 여러 H2가 반복 폐루프와 영역 정체성을 만드는 조합으로 기록한다.
- 하나의 Prefab이 H가 되는 것은 아니다. 여러 자산이 기능·동선·상태 차이를 함께 표현할 때 H 조립 후보가 된다.
- 자산이 충분하면 승인 후보 `assetFamilyId`와 `VisualKey`를 남기고, 부족하면 억지 대체하지 않고 `CompositeRequired`, `DedicatedAssetRequired`, `NeedsReview` 중 하나로 남긴다.
- Synty 원본은 수정하지 않는다. 프로젝트 고유 조합 Prefab과 배치 계획은 원본 GUID·출처·구성 revision을 참조한다.
- 자산 조사는 표현 가능성의 근거일 뿐 H 승인, Scene 배치 또는 E 증거가 아니다. 실제 조립·통행·상태 판독은 별도 연구와 Runtime 증거로 검증한다.
- 같은 질문에서 자산 후보가 명확하면 가벼운 재고 조사로 닫고, 조합 치수·통행·충돌·상태 변화가 플레이를 좌우하면 배치 전문 연구를 `Required`로 분기한다.

### 추천 선택지의 Synty 기반 기획 이미지

공간·건물·Actor·도구·실내외 배치처럼 글만으로 형태와 규모를 상상하기 어려운 질문에서는, 추천 선택지를 설명하는 저해상도 기획 이미지를 함께 제시할 수 있다. 이 이미지는 이후 개발 스레드가 목표 형태와 배치 의도를 이해하는 참고 자료이며 실제 Prefab 조립·Scene 저장·Game View 증거를 대신하지 않는다.

- 이미지 생성 전에 현재 설치된 Synty Prefab과 승인 후보 `assetFamilyId`를 먼저 조사한다. 구매했지만 아직 임포트하지 않은 팩은 공식 구성에 근거한 `PurchasedNotImported` 후보로 분리하고 실제 보유 경로나 GUID를 추정하지 않는다.
- 보유 Synty 자산으로 충분히 조립 가능한 추천안만 이미지화한다. 전용 자산·고급 Shader·새 팩이 없으면 성립하지 않는 형태는 기본 추천안으로 만들지 않는다.
- 프롬프트에는 실제 후보 자산의 기능 역할과 조립 가능한 범위를 적고, 원본 마케팅 이미지를 그대로 복제하거나 존재하지 않는 Prefab을 보유 자산처럼 그리지 않는다.
- 생성 이미지에는 `기획 이미지`, `실제 Scene·Game View 미검증` 경계를 명시한다. 이미지의 건물 크기·통행 폭·Collider·상호작용 위치는 배치 전문 연구와 Runtime 검증 전까지 권위 수치가 아니다.
- 사용자가 선택을 확정해 이후 구현 참고 자료가 되면 `docs/assets/planning/` 아래에 보존하고, 문답 기록에 질문 ID, 선택 번호, 이미지 경로, 참고 화면, Synty 후보 계열, 프롬프트 요약, 알려진 차이를 남긴다.
- 실제 팩 임포트 뒤에는 Prefab Gallery 또는 canonical `SimulationWorldShell`의 저장 Scene 캡처를 참고 자료로 다시 사용한다. 새 기획 이미지가 이전 선택의 의미를 바꾸면 같은 질문의 새 revision으로 재확인한다.
- 이미지가 유용하지 않은 Simulation 수치·권위·Save·API 질문에는 억지로 이미지를 만들지 않는다. 추천안을 시각적으로 판독하는 데 도움이 되는 질문에만 사용한다.

## 질문 식별자와 탐구 깊이

깊이와 Evidence 준비 관계의 기계 단일 원본은 `eng/execution-ledgers/playable-loop-inquiry-depths.json`, 생성 상태판은 [PlayableLoop 문답 깊이와 Evidence 준비 관계](../AI/generated/playable-loop-inquiry-depths.md)다.

### 질문별 깊이 분기와 판본 관리

질문 번호를 계속 늘리는 것만으로 탐구 깊이를 표현하지 않는다. 하나의 핵심 질문은 안정적인 `questionStableId`를 유지하고, 답변·상황 변화·깊이 변화가 생길 때마다 그 질문의 분기 판본을 새로 만든다.

```text
{questionStableId}.r{양의 정수}
```

예를 들어 안정 ID `Q-H1발전-전문운영-01`의 `r1`에서 D2 기본 운영 계약을 물은 뒤 전문 운영 위임을 D3로 더 깊게 묻는다면, 안정 ID는 유지한 채 `Q-H1발전-전문운영-01.r2`가 부모 판본 `Q-H1발전-전문운영-01.r1`을 참조한다. 사람이 보는 표기 `displayQuestionId`는 각각 `Q-H1발전-D2-01`, `Q-H1발전-D3-01`처럼 현재 깊이를 드러낸다. 같은 D3 안에서도 관리자 자율 범위처럼 플레이 의미가 달라지면 `r3`으로 이어갈 수 있다. 전체 Q 번호와 기존 Q 식별자는 추적 호환을 위해 유지한다.

각 질문 판본은 다음 항목을 최소한 기록한다.

| 항목 | 의미 |
| --- | --- |
| `questionStableId` | 질문 계보의 안정 식별자 |
| `displayQuestionId` | 주제·현재 깊이·주제 내 연번을 보여 주는 사람이 읽는 식별자 |
| `branchRevision` | 해당 질문 분기의 판본 |
| `depthCode` | 현재 탐구 깊이 `D1~D5` |
| `parentRevisionRef` | 바로 앞에서 이어진 질문 판본. 첫 판본은 `null` |
| `decisionStatusCode` | `Asked`, `ConfirmedDirection`, `Confirmed`, `Deferred`, `Superseded` |
| `contextDeltaKo` | 이전 판본과 달라진 지금·여기·나·너 |
| `confirmedAnswerKo` | 이번 판본에서 확인된 답. 미확정이면 빈 값 |
| `openQuestionKo` | 다음에 하나만 물을 핵심 공백 |
| `graphImpactAssessment` | 직접 노드·엣지와 인접·파급 영향, 상위 H 파생, 전파 중단 경계 |
| `placementMapImpactAssessment` | 반복 H 인스턴스·상대 배치·배치 제약에 미치는 영향 |
| `supersedesRevisionRefs` | 명시적으로 대체한 과거 판본 목록 |

- 한 판본에는 핵심 질문 하나만 둔다. 여러 선택을 한꺼번에 승인받은 것으로 해석하지 않는다.
- 답변을 받으면 같은 판본을 수정하지 않고 다음 판본을 만든다. 과거 `Asked`는 새 판본의 확인 상태와 대체 참조를 통해 이력으로 남긴다.
- `D1→D2`처럼 깊이가 바뀌면 반드시 새 판본을 만든다. 같은 깊이에서도 전제·대가·실패·회복이 달라지면 새 판본을 만들 수 있다.
- 깊이를 높였다는 사실은 기획의 정밀도가 높아졌다는 뜻일 뿐 Logic·Presentation Evidence나 구현 완료를 자동 승격하지 않는다.
- 대화가 중단되면 `questionStableId / branchRevision / depthCode / openQuestionKo` 네 값을 기준으로 같은 위치에서 재개한다.

#### 질문 판본의 Graph Map 주변 영향

질문이 Graph Map에 영향을 줄 수 있으면 현재 선택의 직접 대상만 적고 끝내지 않는다. 다음 세 영향권을 같은 질문 판본의 `graphImpactAssessment`에서 검토한다.

1. **직접권(0-hop):** 선택·상태·역할이 직접 바뀌는 주 노드와 주 엣지다.
2. **인접권(1-hop):** 주 노드와 기존 명시 엣지로 바로 연결된 노드다. 이름이나 공간적 근접만으로 연결을 추정하지 않는다.
3. **파급권(2-hop):** 공급, 이동, 고용, 관계, 위험, 용량처럼 변화가 한 번 더 전달된다는 인과가 확인된 경우만 본다.

기본 검토 상한은 두 번의 엣지 이동이다. 그보다 먼 변화가 중요하면 현재 질문에서 자동 확정하지 않고 부모 판본과 출발 엣지를 참조하는 자식 질문 revision으로 분리한다. 이 상한은 세계 Simulation의 전파 거리를 제한하는 규칙이 아니라, 한 질문이 무한히 확장되는 것을 막는 기획 검토 경계다.

```text
질문 답변
  → 직접 노드·엣지 변화
  → 명시 엣지를 통한 인접 노드 영향
  → 인과가 확인된 2-hop 파급
  → 전파 중단 경계·미확정 영향 기록
  → 구성 H1 변화로 H2 재산정
  → 필요할 때만 H3·H4 재검토
```

- H2·H3·H4의 성숙도나 상태를 질문 답변으로 직접 올리지 않는다. 하위 H와 엣지의 실제 구성 변화에서 파생해 재산정한다.
- 권위 범위, Area 독립 경계, 닫힌 connector, 용량·시간 부족, 다른 revision, 플레이어가 아직 발견하지 않은 정보 같은 경계를 만나면 전파를 멈추고 `stoppingBoundaryRefs`에 남긴다.
- 현재 Graph Map에 대응 안정 ID가 없거나 엣지 의미가 불명확하면 새 관계를 추정하지 않고 `unknownImpactRefs` 또는 `Blocked`로 반환한다.
- 영향이 없으면 `NoImpact`와 사유를 남긴다. 질문이 많아졌다는 이유만으로 노드나 엣지를 만들지 않는다.

질문이 H의 수량·반복·상대 위치·시야·통행·배경 구성을 바꾸면 Graph Map 영향과 별도로 `placementMapImpactAssessment`를 기록한다. Graph Map에는 플레이 의미와 필수 관계를 남기고, 배치 맵에는 같은 H 정의를 참조하는 여러 배치 인스턴스와 상대 구도를 남긴다. 배치 맵이 없거나 지형·자산·제약 근거가 부족하면 `CreatePlacementMap` 또는 `Blocked`로 인계하며 기획 답변만으로 좌표를 추정하지 않는다.

새 질문은 다음의 사람이 읽는 식별자를 사용한다.

```text
Q-{주제Code}-D{깊이}-{주제내연번} · 전체 Q-{전체연번}
```

예시는 다음과 같다.

```text
Q-병영-D1-01 · 전체 Q-223
Q-병영-D2-03 · 전체 Q-227
Q-Farm농지-D4-02 · 전체 Q-241
```

- `주제Code`는 `병영`, `Farm농지`, `공동체마음`, `회랑방위`처럼 사용자가 즉시 알아볼 수 있는 짧은 한국어 이름을 우선한다.
- `D1~D5`는 문답의 **탐구 깊이**다. Evidence와 동일한 단계는 아니지만 각 깊이는 아래의 `예상 E 준비 범위`를 가진다. 질문 답변은 해당 E의 작업 명세를 준비할 뿐 코드·시험·Runtime 증거 없이 E를 자동 승격하지 않는다.
- `주제내연번`은 같은 주제 안에서 질문 진행량을 보여 주며 두 자리 이상으로 증가시킨다.
- `전체연번`은 프로젝트 전체 문답량과 과거 `Q-001` 참조를 잇는 호환 번호다. 한 번 부여한 전체 번호는 문서 이동이나 주제 재분류 때문에 바꾸지 않는다.
- 기존 `Q-001` 형식의 질문은 그대로 유효하다. 주제별 문서로 이관할 때 새 식별자를 별칭으로 추가할 수 있지만 기존 ID를 삭제하거나 재번호화하지 않는다.
- 확인된 질문의 깊이를 나중에 바꿔야 하면 기존 ID를 조용히 수정하지 않는다. 새 깊이에서 후속 질문을 만들고 `Superseded` 또는 연결 참조를 남긴다.

### 전체 Q 번호와 실제 구현 순서의 분리

`전체 Q-001~`은 질문이 생긴 시간과 결정의 출처를 찾는 **추적 색인**이면서, WI 후보를 빠짐없이 찾는 첫 순회의 순서다. `Q-001 → Q-339`로 한 번 순회해 기존 WI, 새 WI 후보, 직접 WI가 아닌 공통 규칙을 분류한다. 다만 이 번호를 그대로 코드 구현 우선순위로 사용하거나, 질문 하나를 코드 기능 하나로 만들지는 않는다.

실제 구현은 다음 순서로만 선택한다.

```text
Q-001부터 Q-339까지 순차 순회
  -> 기존 WI / 신규 WI 후보 / 직접 WI 없음 추출
  -> 같은 의미의 WI 후보를 StableId로 정규화·통합
  -> 질문을 추출된 WI별 근거 묶음으로 다시 결속
  -> 등록·승인된 현재 PlayableUnit·WI 하나 선택
  -> E7에서 E1까지 영향·누락 검토
  -> 가장 이른 미완료 책임에서 조립 시작
  -> Logic·Presentation을 오가며 코드·시험·Runtime·Evidence 검증
  -> 새 누락이 드러나면 가장 이른 영향 E를 다시 열고 반복
```

따라서 **질문 추출은 번호순**, **구현과 증명은 WI 의존성과 E 피드백 순환**이다. Q 번호가 연속이어도 다른 PlayableLoop·WI에 속하면 같은 구현 묶음이 아니다. 반대로 떨어진 번호라도 같은 승인 기획 revision과 동일 WI의 한 책임을 설명하면 하나의 작은 구현 묶음으로 합성할 수 있다. 최초 조립은 가장 이른 E에서 시작하지만 `E1→E7`을 한 번 직선으로 통과하지 않는다. Logic 또는 Presentation에서 계약·공간·피드백 누락이 드러나면 해당 책임의 가장 이른 E를 다시 열어 왕복한다.

활성 Goal과 무관한 후보 코드·시험은 원장에 `ParkedCandidate` 또는 `ImplementedParked`로 남길 수 있지만 활성 E를 올리거나 다음 번호 구현을 정당화하지 않는다. `Active` 작은 구현 묶음은 [Goal 운영 체계](CodexPlayableLoopGoal운영체계.md)의 담당·기준선·실제 의존성·비중첩 쓰기 범위로 조율하며 전역·스레드별 개수 상한을 두지 않는다. 승인 대기 묶음은 `WaitingForApprovedRevision`으로 남겨 실행 가능한 작업과 구분하고 다른 독립 승인 작업을 막지 않는다. 이는 기존 병렬 운영 기준에 맞춘 잔존 단일 WIP 문구의 정합화이며 새 Goal/WI 자동 활성화 권한이 아니다. `Q 순차 WI 추출`에서 발견된 신규 이름은 `plannedWorldInteractionIds`일 뿐, WI 권위 대장 등록·승인 기획 revision 전에는 구현 순환에 들어가지 않는다.

작은 구현 묶음의 `worldInteractionIds`에는 현재 WI 권위 대장에 등록된 ID만 적는다. 문답에서 책임은 확인됐지만 아직 등록·승인되지 않은 채집·제작·섭취 같은 행위는 `plannedWorldInteractionIds`로 분리한다. 생성 상태판은 이를 `planned:WI-*`로 표시하며, 이는 실제 계약·Runtime·E 증거나 WI WIP가 아니다. 현재 `Active` 또는 `WaitingForApprovedRevision` 묶음에는 planned WI를 넣을 수 없고, 기획 revision과 WI 등록을 마친 뒤에만 활성 묶음으로 전환한다.

탐구 깊이는 다음처럼 판정한다.

| 깊이 | 다루는 질문 | 예상 E 준비 범위 | 질문 뒤에도 별도로 필요한 증거 |
| --- | --- | --- | --- |
| `D1` | 존재 목적, 플레이어 약속, 첫 적용 영역과 역할 | Logic·Presentation `E1` 정의 준비 | 승인 기획 revision·hash와 E1 작업 명세 검증 |
| `D2` | 핵심 폐루프, 조작, 기본 규칙과 첫 임무 | Logic·Presentation `E2` 계약 준비 | 실제 Contract·Application·Unity 투영 코드와 경계 시험 |
| `D3` | 비용, 실패, 부상, 회복, 성장과 손익 | Logic `E3~E4`, Presentation `E3` 검증 준비 | 결정성·거부·회복 시험과 LocalProcess·RemoteHost 동등성 |
| `D4` | 건물, H 공간, 배치, Synty 자산, UI·애니메이션 | Presentation `E4`와 Logic·Presentation `E5` 착수 준비 | 후보 fingerprint, H 결속, 실제 Prefab·World 배치·Renderer·Collider·상태 발현 |
| `D5` | Save/Replay, NPC 연속성, 멀티플레이, 영역 통합과 Runtime 완료 조건 | `E6~E7` 작업 명세와 후속 `E8~E9` 캠페인 준비 | 실제 입력·Play Mode·Game View·Save 재진입·반복 안정성·사람 승인 |

문답 기록은 다음 네 값을 분리해 보여 준다.

```text
현재 문답 깊이: D3
예상 E 준비 범위: Logic E3~E4 / Presentation E3
저장소에서 실제 검증된 E: Logic E2 / Presentation E1 / 통합 E1
다음 차단: 결정성 시험과 실제 Unity 상태 사본 투영
```

- `예상 E 준비 범위`는 질문이 충분히 답변됐을 때 **어느 E 구현을 설계할 수 있는지**를 보여 주는 전망이다.
- `실제 검증된 E`는 `playable-loops.json`, 활성 E1~E7 상호작용 수직 검증 명세와 EvidencePackage만을 읽어 표시한다.
- 전망보다 실제 E가 낮으면 구현·시험 공백이 있다는 뜻이고, 실제 E가 더 높으면 기존 구현을 새 기획 revision으로 재검증해야 하는지 확인한다.
- Logic과 Presentation의 예상 범위 및 실제 E를 따로 기록하고, 통합 E는 기존 원칙대로 두 실제 궤적 중 낮은 값으로만 판정한다.
- D4 질문이 모두 확인돼도 실제 Prefab과 H 결속이 없다면 Presentation E5가 아니다. D5 질문이 모두 확인돼도 Play Mode·Game View·Save 재진입이 없다면 E7·E8이 아니다.

질문 묶음 앞에는 현재 위치를 다음처럼 표시한다.

```text
[병영 기획 — 현재 깊이 D3/5]
확정: D1, D2
진행 중: D3
대기: D4, D5
예상 E 준비: Logic E3~E4 / Presentation E3
실제 검증 E: 미등록 또는 원장 조회값
다음 Evidence 차단: 결정성·거부·회복 시험
답변 형식: 1 3 2 2 1
```

깊이는 반드시 D1부터 한 번만 통과하는 선형 단계가 아니다. D4 자산 조사에서 기본 규칙 누락이 드러나면 같은 주제를 유지한 채 D2 또는 D3 질문으로 돌아간다.

## 질문 순서

질문은 아래 순서를 기본으로 하되 앞 답변에서 더 이른 책임이 다시 열리면 돌아갈 수 있다.

1. 플레이어 상황과 욕구
2. 반복하고 싶은 핵심 선택
3. 시간·자원·위험의 대가
4. 성공·실패·취소·후퇴·회복·귀환
5. WI 단일 책임과 발생원
6. 권위 상태·행위 기록·Save/Replay
7. H 공간 능력과 이동 흐름
8. 건물 유형·상태·성장
9. 실내·실외 배치와 상태 차이
10. 애니메이션·도구 접촉·Task 시간
11. UI·카메라·소리·피드백
12. LocalProcess·RemoteHost·외부 자료 경계
13. 실제 입력·Play Mode·Game View 완료 조건
14. 제외 범위와 다음 폐루프로의 반환

### 질문 균형과 세부 분기 예산

위 순서는 한 방향으로 끝까지 내려가는 체크리스트가 아니라 핵심 폐루프를 여러 관점에서 반복해 살피는 순환 기준이다. 한 답변에서 흥미로운 하위 체계가 열려도 그 체계만 계속 질문해 PlayableLoop 전체를 가리지 않는다.

- 같은 세부 시스템의 연속 질문은 기본적으로 세 개 이내로 제한한다.
- 세 질문 안에 남은 내용은 `확정 후보`, `전문 연구`, `후속 Extension`, `구현 가설`, `제외 범위` 중 하나에 귀속하고 핵심 폐루프 질문으로 돌아간다.
- 사용자가 특정 분야의 심화를 명시적으로 요청한 경우에만 연속 질문 예산을 늘리며, 이때도 원래 PlayableLoop와 별도 연구 분기를 구분한다.
- 질문을 고를 때 최근 질문의 분야 편중을 확인하고, 아직 다루지 않은 가장 이른 핵심 책임을 우선한다.
- 최소한 `상황·욕구`, `선택`, `대가`, `실패·회복·귀환`, `WI`, `H 공간`, `표현`, `저장·실행 경계`에 각각 후보가 생기기 전에는 한 성장축의 세부 수치 조정으로 들어가지 않는다.
- 3~5개 질문마다 만드는 중간 상태 사본에는 `질문 분야 분포`, `과도하게 깊어진 분기`, `다음에 돌아갈 핵심 책임`을 함께 기록한다.

균형 재정렬이 필요하면 새 질문을 바로 던지지 않고 현재 답변을 합성한 뒤 문답 상태를 잠시 `Synthesizing`으로 둔다. 다음 안전한 회차에 다른 책임의 질문 하나로 재개한다.

### Unity 게임 완성 구성요소 대장

질문 균형의 최종 기준은 주제별 질문 횟수가 아니라 **해당 PlayableLoop를 canonical Unity 게임에서 완성하는 데 필요한 구성요소의 공백**이다. 문답 기록은 아래 대장을 유지하고, 다음 질문은 단순 순환 순서가 아니라 플레이어 약속을 실제 게임으로 닫는 데 가장 먼저 필요한 빈 구성요소에서 고른다.

| 구성요소 | 기획에서 채울 내용 | 최종 구현·증거 |
| --- | --- | --- |
| 플레이어 경험·콘텐츠 | 상황·욕구·선택·대가·반복 이유·성공·실패·귀환 | 실제 플레이 흐름과 다음 선택 |
| Simulation 권위·규칙 | 소유 상태·판정식·시간·난수·Revision·Effect | LocalProcess·RemoteHost 동일 결과 |
| WI·Task 실행 | 발생원·Preview·Confirm·Task·취소·결과·행위 기록 | 같은 WI·Command·Revision 파이프라인 |
| 플레이어 조작·카메라 | 이동·선택·상호작용·입력·시점·조작권 반환 | 실제 Input System 조작 |
| H 공간·월드 구성 | AreaSet·H1~H5·동선·범위·Graph·LH 준비 | 승인 배치와 통행 가능한 공간 |
| 건물·배치·자산 | 건물 상태·실내외 배치·Synty 실제 재고·H1→H2→H3 조합·VisualKey·Prefab·충돌·접촉점 | 실제 Synty 자산 조립과 상태 차이 |
| 캐릭터·NPC·애니메이션 | 자세·도구 접촉·전이·피격·중단·NPC 필요 여부 | Animator·Task 시간·행위 판독 |
| UI·음향·시각 효과 | HUD·Preview·경고·접근성·Audio·FX·환경 피드백 | 원인·상태·결과·다음 선택 판독 |
| 성장·경제·균형 | 숙련·보상·자원 비용·난이도·반복 악용 방지 | 판본화된 Profile과 회귀 시험 |
| 자료·출처·외부 경계 | Fixture·공공데이터·승인·결측·Source hash | 외부 실패와 게임 권위 분리 |
| Save·Replay·온라인 | 체크포인트·migration·복원·Solo·Hosted·재접속 | canonical hash와 모드 동등성 |
| Unity 조립·실행 품질 | `SimulationWorldShell` CompositionRoot·수명주기·성능·메모리 | 저장 Scene·Play Mode·Console·Profiler 기준 |
| 시험·Game View·빌드 | 단위·통합·실제 입력·화면·Build Settings·패키징 | EvidencePackage·대표 화면·실행 가능한 빌드 |

각 구성요소 상태는 `미질문`, `후보`, `전문연구필요`, `확정후보`, `기획반영`, `구현증거`, `Runtime증거`, `NotApplicable` 중 하나로 기록한다. `NotApplicable`에는 이유가 필요하다.

- 질문이 이미 충분한 구성요소를 다시 파고드는 것보다 가장 이른 차단 공백을 우선한다.
- 모든 칸을 같은 깊이로 만드는 것이 목적은 아니다. 해당 폐루프에 필요한 칸은 Runtime까지 닫고, 불필요한 칸은 사유 있는 `NotApplicable`로 닫는다.
- E/G/H/WI는 그대로 유지한다. 이 대장은 그것들을 대체하는 새 성숙도 축이 아니라 Unity 게임 완성 누락을 찾는 질문·인계용 관점이다.
- Logic이 높아도 조작·애니메이션·UI·Scene·Game View가 비어 있으면 질문과 완료 판정은 그 공백으로 이동한다.
- 문답이 합성될 때 이 대장의 `확정후보` 이상 항목을 기획서 절과 E1~E7 상호작용 수직 검증 명세에 연결하고, 개발 뒤 `구현증거`와 `Runtime증거`는 별도 EvidencePackage가 갱신한다.

건물·공간·배치·애니메이션 질문이 단순 선택을 넘어 조사와 대안 비교를 요구하면 [전문 심화 연구 분기·재결속 체계](PlayableLoop전문심화연구분기재결속체계.md)의 `Required` 연구로 분기한다. 문답에서 전문 답을 추정해 `Accepted`로 처리하지 않는다.

### 개발 인계 판정

문답을 모두 닫을 때까지 개발을 무조건 미루지는 않는다. 3~5개 질문을 합성했거나 Unity 게임 완성 구성요소 하나가 `확정후보`에 도달하면, 현재 범위가 독립적인 구현 묶음으로 동결 가능한지 확인한다. 실제 승인·인계 조건과 인계 묶음은 [주제 기획 기반 PlayableLoop 개발 체계](주제기획기반PlayableLoop개발체계.md#장기-기획-goal과-실제-개발-스레드-인계)를 따른다.

각 확정 답변은 [기획 문서 독립 관리 체계의 문답 영향 묶음](기획문서독립관리체계.md#문답-영향-묶음의-연속-누적)에 누적한다. `지금·여기·나·너·이렇게`, 오행 관계, 추천·대가가 확정되면 Graph Map 레벨 1 관계와 배치 맵 레벨 2 공간 영향, 레벨 3 조사 대상을 함께 판정한다. 아직 작은 구현 slice로 닫히지 않은 답변은 `AccumulateOnly`로 남기고, 동결 조건을 충족한 묶음만 `ReadyForGraphMap`을 거쳐 `ReadyForDevelopment` 후보가 된다. 기획 스레드는 인계 뒤 중간 진행을 기다리지 않고 다음 질문을 이어간다.

문답 기록의 개발 인계 상태는 다음 중 하나다.

```text
NotReady -> ReadyToDispatch -> Dispatched -> EvidenceReturned
                                 |                  |
                                 +-> FeedbackRequired <-+
```

- `NotReady`: 핵심 미정, 승인 기획서, Accepted 연구, 활성 WI 또는 E1~E7 상호작용 수직 검증 명세 중 하나 이상이 부족하다.
- `ReadyToDispatch`: 구현 범위와 제외 범위가 동결됐고 모든 기획 관문을 통과했다.
- `Dispatched`: 판본화된 인계 묶음을 개발 스레드에 보냈다. 대화 요약만 보낸 상태는 여기에 포함하지 않는다.
- `FeedbackRequired`: 구현 조사에서 플레이어 약속이나 연구 기준선을 다시 열어야 할 발견이 돌아왔다.
- `EvidenceReturned`: 개발 결과와 EvidencePackage를 읽어 인계 범위의 결과가 돌아왔음을 확인했다. 구현 완료나 E 승격 여부는 각 원장과 증거가 별도로 판정한다.

기획 스레드는 `Dispatched` 뒤에도 다른 구성요소나 다음 묶음의 문답을 계속할 수 있다. 다만 개발 중인 같은 WI·기획 revision의 의미를 조용히 바꾸지 않고, 변경 후보는 다음 revision 또는 `FeedbackRequired`로 기록한다.

## 문답 기록 상태

문답 기록은 다음 상태를 사용한다.

```text
Open -> Synthesizing -> Confirmed -> Incorporated -> Closed
```

- `Open`: 다음 질문이 있고 답변을 수집 중이다.
- `Synthesizing`: 답변 사이의 의미와 충돌을 정리 중이다.
- `Confirmed`: 사용자에게 다시 보여준 핵심 해석이 확인됐다.
- `Incorporated`: 확인된 결정이 특정 기획 revision에 반영됐다.
- `Closed`: 남은 미정이 기획서·전문 연구·제외 범위 중 하나에 모두 귀속됐다.

문답 기록은 E 단계가 아니다. `Confirmed`나 `Closed`도 기획서 `Approved`, 코드 구현 또는 Runtime 증거를 뜻하지 않는다.

## 저장과 재개

문답 재개 전 [파일 기반 문답 검색](../../eng/planning-inquiries/README.md)의 `Search`로 질문 ID·주제·키워드를 대조한다. 생성 색인은 현재 원문 hash와 일치해야 하며 오래됐으면 재생성·검증한다. 현재 답변은 주제 원문, 당시 상세 답변은 동결 아카이브, 구현/E는 기존 실행 원장의 책임을 유지한다. 이미 답한 내용을 구현 미완료 때문에 다시 묻지 않는다. `OpenOnly`의 본문 미정 표시는 검토 후보이며 후속 결정에서 해결됐는지 확인한다. 후속 의미 ID를 전역 Q로 임의 재번호화하거나 소실된 질문을 추측해 복구하지 않는다.

각 문답 기록은 다음을 가진다.

- `inquiryStableId`
- 대상 `topicStableId`와 `playableLoopStableId`
- 기록 revision과 상태
- 현재 질문 ID와 전체 호환 번호
- 현재 주제와 탐구 깊이
- 마지막으로 확인된 질문 ID와 전체 호환 번호
- 확정 후보, 확인된 결정, 미정, 충돌
- 전문 연구 분기 후보
- 반영 대상 `designRevision`
- 다음 질문

세부 질문·답변은 원문 전체를 복사하지 않고 게임 기획 의미로 요약한다. 표현 하나가 계약에 중요할 때만 짧은 원문을 보존한다. 대화가 끊기면 주제·깊이·현재 질문 ID·전체 호환 번호와 다음 질문을 기준으로 재개하며 이미 확인한 질문을 처음부터 반복하지 않는다.

3~5개 질문이 끝나거나 하나의 질문 분야가 닫힐 때마다 중간 상태 사본을 만든다.

```text
이번에 확인된 결정
남은 미정
새로 발견된 충돌
필요한 전문 연구
기획서에 반영한 절
다음 질문
```

## 기획서 합성 관문

문답을 주제 기획서로 합성하기 전에 다음을 확인한다.

1. 플레이어 약속과 반복 이유를 한 문장으로 설명할 수 있다.
2. 핵심 선택과 대가가 서로 대응한다.
3. 성공·실패·회복·귀환이 끊기지 않는다.
4. WI 후보가 한 번에 하나의 권위 책임을 가진다.
5. Logic과 Presentation 요구가 구분된다.
6. H와 전문 심화 연구 필요성이 판정됐다.
7. Save/Replay·Local/Remote·외부 효과 경계가 정해졌다.
8. 미정 항목이 승인 차단, 전문 연구, 구현 가설 또는 제외 범위로 분류됐다.
9. 사용자가 핵심 해석을 확인했다.

합성된 문답 기록은 기획서의 `sourcePlanningDocumentRefs`에 연결한다. 기획서는 확인된 결정만 규칙으로 사용하고 미정·가설을 완료된 사실처럼 바꾸지 않는다.

## 질문 작성 원칙

- “어떻게 할까요?”보다 현재 결정해야 할 차이를 드러내는 질문을 쓴다.
- 구현 기술보다 먼저 플레이어가 보고 선택하고 잃고 얻고 돌아오는 경험을 묻는다.
- 답변에 모순이 있으면 맞춰 쓰지 않고 두 해석을 나란히 보여준다.
- 이전 답을 바꾸는 것은 허용한다. 바뀐 결정은 새 기록 revision으로 남기고 영향받는 기획·연구를 다시 연다.
- 답변하지 않은 침묵, 대화 종료 또는 짧은 동의 표현만으로 전체 기획을 승인하지 않는다.
