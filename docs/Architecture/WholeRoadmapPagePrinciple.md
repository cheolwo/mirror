# 전체 로드맵 조화형 페이지 원칙

## 목적

Ssalddel의 페이지 하나는 특정 버전의 고립된 화면이 아니라 `0.0`에서 최종 배포 목표 `3.5`까지 이어지는 업무 흐름의 한 node다. 현재 화면이 제공하는 기능은 현재 완성 단계와 기능 플래그로 제한하지만, 식별자·원장·상태·역할 인계는 후속 버전과 단절되지 않게 설계한다.

현재 완성 단계는 `SsalddelProductRoadmapCatalog.CurrentDeliveryVersion`, 최종 배포 목표는 `SsalddelProductRoadmapCatalog.DeploymentTargetVersion`을 단일 코드 기준으로 사용한다.

## 사용자 관점의 단일 책임

페이지 하나는 **한 사용자가 한 업무 문맥에서 해결하려는 한 가지 질문과 결과**를 소유한다. 새 페이지를 만들거나 기존 페이지의 정보·행동·구조를 의미 있게 바꾸기 전에 이 문서를 읽고 [페이지 책임 카드](../ProjectOverview/page-docs/page-responsibility-template.md)를 작성한다. 기존 상세 README가 있으면 그 문서에 카드를 채우며 별도 정책을 복제하지 않는다.

목적은 `누가 + 어떤 대상을 + 무엇을 판단하거나 완료하는가`로 한 문장에 적는다. 예를 들어 “주문자가 내 주문을 찾아 배달 진행을 확인하고 선택 주문의 수령을 확정한다”다. 파일 하나, 버튼 하나, API 하나 또는 DB 테이블 하나가 단일 책임의 단위는 아니다. 같은 목적을 위한 검색·목록·선택 상세·진행 상태·다음 행동은 함께 구성할 수 있다.

현재 상태에서 가장 필요한 **주 행동 하나를 강조**한다. 상태가 바뀌면 강조 행동도 바뀔 수 있다. 검색·새로고침·뒤로·취소·오류 복구 같은 보조 행동까지 없애거나 모든 상태를 같은 버튼으로 처리하지 않는다. 행동의 가능 여부와 실제 결과는 기존 서버 권한·상태 전이·원장이 결정한다.

### 함께 둘지 분리할지 판단

| 관계 | 구성 기준 | 예 |
| --- | --- | --- |
| 같은 대상·같은 목적의 단계 | 한 페이지의 상태 또는 재사용 컴포넌트로 구성 | 내 주문 목록 → 선택 주문 진행 → 수령 확인 |
| 같은 판단에 필요한 근거·긴 기록 | 요약을 기본 표시하고 상세로 펼침 | 주문 추적의 원장 연결·감사 기록 |
| 다른 완료 결과·권한·입력 문맥·저장 수명 | 독립 업무로 분리하고 명시적 진입/복귀 제공 | 배달 수행과 월 이용료 변경, 주문 추적과 지급 테스트 실행 |
| 여러 업무의 진입 허브 | 현재 상태 요약과 목적별 진입만 조립 | 배달 홈에서 현재 수행·정산 내역·내 정보로 이동 |

분리 판단은 해당 작업을 따로 선택·완료·취소·실패·재시도할 수 있는지 확인한다. 독립 업무를 접힌 카드나 탭 뒤에 넣은 것만으로 책임 분리 완료로 판단하지 않는다. 같은 물리 페이지에 유지해야 한다면 목적별 표시 모드·상태 소유자·입력 수명·진입과 복귀를 분명히 나누고, 현재 구조의 한계와 분리 이유를 기록한다. 섹션으로 스크롤하는 버튼은 별도 페이지나 업무 상태 격리의 증거가 아니다.

줄 수·카드 수·파일 수에 고정 상한을 두지 않는다. 페이지를 무조건 늘리지도 않는다. 판단에 필요한 문맥을 잃지 않으면서 독립 업무를 구분하는 것이 기준이다. 기존 route·별칭·PageKey·저장 키를 이름이나 외형만 보고 삭제·재번호화하지 않는다.

### 인증과 업무의 경계

로그인의 완료 결과는 계정 인증이며 주문·배차·상품 저장과 구별한다. 로그인 자격 입력을 업무 검색·목록·수량/수령 정보·업무 실행 버튼 안에 삽입하지 않는다. 인증 화면의 제목·설명·진입/취소·실패 재시도는 인증 목적만 설명하고, 업무 drawer·업무 단계 탐색·캐시 업무 정보도 동시에 렌더하지 않는다. 필요한 공개 탐색과 원래 업무로 돌아가는 링크는 유지한다.

기존 독립 로그인 route가 있으면 인증 전용 Layout을 사용한다. route를 나누면 작성 수명이 끊기는 기존 흐름은 동일 route의 상호 배타적 인증/업무 표시 모드로 분리할 수 있다. 모드 진입과 복귀는 페이지/조립 VM, 업무 초안은 기존 작성 VM, 자격 입력은 인증 컴포넌트가 소유한다. 숨긴 업무 컴포넌트를 다시 만들기 위해 초안·선택·멱등 요청 ID를 초기화하지 않는다. 비밀번호·토큰을 초안·URL·로그로 옮기지 않는다.

로그인 성공은 원래 업무로 복귀하는 결과이며 주문 제출·수요 저장·배차 수락을 자동 실행하지 않는다. 명시적 로그아웃과 업무 대상 변경의 기존 초안 초기화 조건은 유지한다. 복원 중·익명·인증 실패·정상 업무를 배타적으로 렌더하고, 현재 로그인 세션이 종료됐으면 오래된 업무 snapshot만으로 업무 화면을 유지하지 않는다. 인증/업무 전환의 실제 렌더와 복귀 후 동일 작성 내용·요청 ID를 검증한다.

### 화면에 남길 정보

각 정보가 사용자의 어떤 판단이나 행동을 돕는지 책임 카드에 적고 다음과 같이 배치한다.

| 배치 | 조건 |
| --- | --- |
| 기본 표시 | 대상·현재 상태·핵심 금액/거리·다음 행동과 그 판단에 필요한 근거 |
| 필요할 때 상세 표시 | 긴 이력·동일 업무의 보조 근거·허용된 운영 진단 |
| 다른 업무로 이동 | 개인 설정·정산 이력·정책 편집·지급 실행처럼 주 목적과 독립된 업무 |
| 제품 화면에서 제외 | 이용자의 판단에 쓰이지 않는 구현 설명·정상 heartbeat/FCM 준비·원시 좌표·중복 요약 |

현재 행동을 막는 오류·권한/위치 안내·실패 복구·금액 미확정·추정 경로·테스트/실입금 구분은 관련 위치에서 바로 보이게 한다. 필요한 경고를 진단 정보로 취급해 접거나, 조회 실패를 정상 빈 상태로 바꾸지 않는다. 미확인 값을 0이나 성공으로 대체하지 않는다. 개인정보는 필요·권한에 따라 기존 보호 범위를 유지한다.

### UI·UX 작업 순서

내용과 업무를 보존하는 시각 리팩토링은 [역할 앱 시각 디자인 기준](RoleAppVisualDesignStandard.md)의 공식 자료·토큰·검증 경계를 함께 적용한다. 업무 분리와 시각 표현은 서로 다른 판단이다.

1. 기존 역할별 목록과 상세 README에서 같은 목적의 페이지·컴포넌트를 찾는다.
2. 책임 카드에 주 사용자·대상/진입 문맥·질문·결과·기본/보조 정보·주 행동·독립 업무·실패/복귀를 적는다.
3. 기존 page → code → DB 연결과 대조해 함께 구성할 부분, 컴포넌트로 나눌 부분, 별도 업무로 인계할 부분을 정한다. 도메인 계산·권한·DB 저장을 View로 옮기지 않는다.
4. 기본 화면과 상세/다른 업무로 이동한 항목의 이유를 기록하고 기존 페이지·workflow·navigation을 재사용해 좁게 구현한다.
5. 변경 상태의 loading/empty/error/retry/disabled와 실제 행동·복귀 문맥을 검증한다. 모바일은 텍스트 겹침·잘림·터치·스크롤을, 공유 UI는 소비 앱을 함께 확인한다.
6. 책임 검토·코드/시험·실제 브라우저/앱·APK·운영/입금 증거를 구별해 상세 문서와 변경 기록을 갱신한다.

기존 화면이 있다는 이유로 준수 완료를 자동 부여하지 않는다. 미작성은 `책임 미검토`, 기준과 맞지 않는 부분은 `분리 필요`, 이유 있는 조립은 `같은 목적의 구성`으로 기록한다. 기존 소스/호스트 색인 도구는 화면 존재·ID·링크를 검사하며 단일 책임이나 UX 품질을 자동 판정하지 않는다. 최근 세 화면의 적용 예와 남은 분리는 [책임 점검 r1](../ProjectOverview/page-docs/page-responsibility-review-r1.md)을 참조한다.

## 페이지 구현 기준

새 페이지 또는 의미 있는 페이지 리팩토링은 구현 전에 다음을 정한다.

1. **업무 node**: 페이지가 소유하는 한 가지 업무 질문과 결과
2. **도입 버전**: 이 node가 처음 필요한 제품 버전
3. **선행 근거**: 앞 단계에서 전달받는 stable ID, 동의, 출처와 원장 상태
4. **후속 인계**: `3.5`까지 어떤 역할과 원장이 이 결과를 소비하는지
5. **역할 투영**: 주문자·화주·기사·창고 등 역할별로 같은 상태를 어떻게 다르게 표시하는지
6. **실행 경계**: 읽기, Simulation, platform persistence, 외부 효과를 구분하는 기능 플래그와 권한
7. **실패와 철회**: loading, empty, error, retry, disabled와 철회 가능한 상태
8. **검증 근거**: route, PageViewModel, contract, API/UseCase, 원장 재조회와 소비 역할 테스트

## 코드 구조

```text
Route
  -> Page/Screen
    -> PageViewModel
      -> Feature ViewModel 또는 Workflow Session
        -> Client
          -> Controller API
            -> UseCase/Command
              -> Domain/Infrastructure
                -> Ledger/Event/Outbox
```

- Route는 파라미터와 navigation만 조립한다.
- PageViewModel은 페이지 수명, 표시 상태와 하위 workflow를 조립한다.
- 여러 페이지에서 유지되는 초안은 PageViewModel이 아니라 별도 Workflow Session으로 둔다.
- 실제 상태 변경은 API/UseCase/Command가 권한과 현재 원장을 검증한 뒤 수행한다.
- 성공 뒤 같은 stable ID의 원장을 다시 조회해 다른 역할 앱과 동일한 상태를 표시한다.

## 버전과 배포 경계

- 최종 배포 목표는 `3.5`다.
- 현재 완성 단계가 `0.0`이라는 사실은 최종 목표를 축소하지 않는다.
- 미래 버전의 연결점은 contract와 원장에 보존하되, 해당 기능 플래그가 꺼져 있으면 UI와 API 실행을 열지 않는다.
- 기능 플래그가 켜져 있어도 `SsalddelExecution:Mode=Simulation`이면 결제, 계약, 신고, 자동 배차와 외부 정산을 운영 효과로 실행하지 않는다.
- `3.5` 배포 후보는 `Ssalddel.v3.5.slnx`, 3.5 Compose profile과 전체 릴리즈 게이트를 함께 통과해야 한다.

## 회귀 방지

페이지 capability에는 stable `PageKey`, `IntroducedVersion`, workflow와 feature key, 상호작용 경계, 인증·외부 효과 여부를 기록한다. 여러 프로젝트를 통과하는 기능은 `SsalddelCodeMetadataAttribute`의 `FeatureKey`, `Layer`, `FlowOrder`, `Effects`, `Boundary`로 같은 세로 흐름을 검색할 수 있어야 한다.

화면 단위 테스트만으로 완료를 주장하지 않는다. 최소한 현재 버전의 동작, 후속 인계 contract, 비활성 기능 차단, 동일 원장 재조회와 `3.5` solution 조립 호환성을 함께 확인한다.
