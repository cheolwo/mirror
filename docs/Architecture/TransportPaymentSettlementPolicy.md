# Transport Payment Settlement Policy

이 문서는 홍달의 운송료 결제와 기사 정산 기능을 만들 때 우선 참조하는 기준이다. 목표는 플랫폼 이용료를 무료로 둘 수 있으면서도, 화주 미지급 위험을 줄이고 기사에게는 증빙 완료 후 정산이 보장되는 흐름을 만드는 것이다.

## 기본 원칙

1. 홍달의 플랫폼 이용료 무료 정책과 운송료 결제는 분리한다.
2. 운송료는 화주와 기사 사이의 운송 대가이며, 홍달은 이 돈을 직접 보관하는 지갑 사업자가 되지 않는다.
3. 결제 수납, 예치, 환불, 기사 정산 송금은 등록된 PG, 에스크로, 마켓플레이스 정산 사업자가 맡는다.
4. 홍달 서버는 운송 원장, 증빙, 정산 조건, 정산 지시 이력, 분쟁 상태를 관리한다.
5. 배차는 원칙적으로 운송료가 확보되었거나 후불 승인이 완료된 의뢰만 진입시킨다.
6. 기사에게는 수락 전에 보증 운송인지, 후불 승인 운송인지, 현장 지급 운송인지 명확히 보여준다.
7. 관리자 화면의 강제 정산, 부분 정산, 환불은 홍달 내부 계좌 이체가 아니라 PG/정산사에 대한 정산 지시로 기록한다.

## 권장 운영 모델

1. 화주가 운송 의뢰를 등록하고 운임을 확정한다.
2. 화주는 배차 전에 카드, 계좌이체, 가상계좌, 간편결제 등 PG가 제공하는 수단으로 운송료를 결제하거나 예치한다.
3. PG/정산사는 운송료를 보관하거나 결제 보증 상태로 만든다.
4. 홍달은 `결제확보됨` 상태를 서버 원장에 기록하고 배차대기로 넘긴다.
5. 기사는 `결제보증` 표시가 있는 운송을 수락한다.
6. 상차 완료 증빙이 올라오면 조기 정산 후보가 된다.
7. 하차 완료와 POD가 입증되고 이의제기가 없으면 정산대기로 전환한다.
8. 홍달은 PG/정산사에 기사 정산 지시를 보낸다.
9. PG/정산사 webhook 또는 조회 결과로 정산완료, 실패, 보류를 원장에 반영한다.

## 상태 모델

| 상태 | 의미 | 다음 행동 |
| --- | --- | --- |
| `운임확정` | 화주 의뢰 금액과 결제 조건이 정해짐 | 결제 준비 |
| `결제확보대기` | 결제창, 가상계좌, 계좌이체 등 외부 결제 절차 진행 중 | 결제 완료 webhook 또는 만료 처리 |
| `결제확보됨` | 운송료가 PG/정산사를 통해 확보됨 | 배차대기 생성 |
| `후불승인됨` | 신뢰 화주, 계약 화주, 관리자 승인 등으로 후불 배차 가능 | 배차대기 생성 |
| `상차완료` | 기사 상차 증빙이 서버 원장에 기록됨 | 조기 정산 후보 또는 진행 유지 |
| `하차완료` | 하차 증빙과 POD가 서버 원장에 기록됨 | 정산대기 후보 |
| `정산대기` | 지급 조건은 충족되었고 PG/정산 지시를 보낼 수 있음 | 자동 정산 또는 관리자 확인 |
| `정산보류` | 분쟁, 파손, 미배송, 증빙 부족, 금액 변경 이슈가 있음 | 관리자 검토 |
| `정산완료` | 기사에게 정산이 완료됨 | 원장 종료 |
| `환불대기` | 취소, 배차 실패, 분쟁 결과로 환불이 필요함 | PG 환불 지시 |

## 조기 정산

상차 완료만으로도 기사에게 일부 또는 전액을 조기 정산할 수 있지만, 1.0에서는 자동 지급보다 승인형으로 둔다.

| 조건 | 처리 |
| --- | --- |
| 화주가 상차 증빙을 확인하고 조기 지급을 승인 | PG/정산사에 조기 정산 지시 가능 |
| 플랫폼 운영자가 상차 증빙과 화주 응답을 확인하고 승인 | 조기 정산 지시 가능 |
| 하차 전 파손, 수량 차이, 주소 오류, 운임 변경 가능성이 있음 | 정산보류 |
| 계약 화주 또는 신뢰 등급 화주 | 정책에 따라 상차 완료 후 일부 지급 가능 |

조기 정산이 실행되더라도 홍달 원장에는 승인자, 승인 시각, 지급 비율, 증빙 파일, PG 정산 지시 ID를 남긴다.

## 분쟁과 보류

다음 경우에는 자동 정산하지 않는다.

- 하차 완료 증빙이 없거나 POD가 검수되지 않음
- 수령자가 미수령 또는 파손을 신고함
- 화주가 운임 변경, 취소, 부분 환불을 요청함
- 기사가 상차 또는 하차 조건 변경을 신고함
- PG 결제 상태와 홍달 원장 상태가 불일치함
- webhook 중복, 누락, 순서 역전이 감지됨

보류 상태에서는 관리자만 정산 재개, 부분 정산, 환불, 강제 종료를 실행할 수 있다.

## API 설계 기준

결제 제공자 이름을 핵심 도메인에 직접 박지 않는다. TossPayments, 다른 PG, 에스크로, 정산 대행사를 교체할 수 있도록 서버 내부에서는 제공자 중립 모델을 사용한다.

| 영역 | 권장 필드 |
| --- | --- |
| 결제 준비 | `paymentIntentId`, `requestId`, `amount`, `payerId`, `provider`, `expiresAtUtc` |
| 결제 확보 | `paymentId`, `providerPaymentKey`, `securedAmount`, `securedAtUtc`, `idempotencyKey` |
| 정산 지시 | `settlementInstructionId`, `driverId`, `transportId`, `amount`, `reason`, `approvedBy`, `providerTransferKey` |
| 정산 결과 | `settlementStatus`, `settledAtUtc`, `failedReason`, `providerWebhookId` |
| 감사 | `actorId`, `actorRole`, `source`, `occurredAtUtc`, `rawPayloadHash` |

외부 webhook은 반드시 멱등 처리한다. 결제 완료, 환불 완료, 정산 완료 webhook이 여러 번 오거나 순서가 바뀌어도 서버 원장은 한 번만 상태 전이해야 한다.

## 제공자 선택 메모

2026-07-12 현재 프로젝트 판단은 다음과 같다.

1. TossPayments는 참고 구현과 과거 연동 가이드로 보관한다.
2. Hongdal 1.0의 기본 개발 흐름은 Toss 직접 연동이 아니라 `FakePG`와 제공자 중립 원장을 기준으로 검증한다.
3. 실제 출시 전에는 Toss, Naver Pay, 다른 PG, 에스크로, 마켓플레이스 정산 기능 중 하나를 다시 선택할 수 있어야 한다.
4. 특정 제공자의 API 이름이 남아 있는 코드는 새 기능의 기준으로 삼지 않고, 교체 가능한 어댑터 후보로만 본다.
5. 결제 제공자를 확정하기 전까지 클라이언트 앱은 실제 카드 승인, 계좌이체, 가상계좌 발급, 송금을 발생시키지 않는다.

현재 얻은 정보로 정리한 실무 판단은 다음과 같다.

| 항목 | 정리 |
| --- | --- |
| 플랫폼 수수료 | 0원으로 둘 수 있지만 운송료 수납과 정산 책임은 별도 문제다. |
| 운송료 보증 | 화주 미지급 위험을 줄이려면 결제 확보 또는 후불 승인 상태가 서버 원장에 먼저 남아야 한다. |
| 돈의 보관 | 홍달이 직접 운송료를 받아 보관하고 기사에게 송금하는 구조는 피한다. |
| PG/정산사 역할 | 실제 수납, 환불, 기사 지급, webhook 결과는 등록된 외부 사업자가 맡는 구조가 바람직하다. |
| 개발 단계 | 실제 제공자 계약 전에는 `FakePG`로 상태 전이, 화면 UX, E2E 스모크를 먼저 안정화한다. |
| 법무 검토 | 실제 운영 전에는 PG 등록, 정산자금 보관, 위탁 정산, 운송 주선/중개 책임 범위를 별도로 검토한다. |

## 화면 기준

| 앱 | 화면 책임 |
| --- | --- |
| `HongdalApp` | 결제 보증 여부, 결제 만료, 환불 상태, 조기 정산 승인 여부 표시 |
| `DriverApp` | 보증 운송 여부, 예상 정산일, 조기 정산 후보, 보류 사유 표시 |
| `HongdalAdmin` | 결제/정산 원장, 증빙, 이의제기, 조기 정산 승인, 부분 정산, 환불 지시 |

## 구현 주의

- 홍달이 직접 화주 돈을 받아 보관하고 기사에게 송금하는 구조는 피한다.
- 플랫폼 수수료를 0원으로 둘 수는 있지만 PG 결제 수수료와 송금 수수료는 별도 정책으로 정해야 한다.
- 초기에는 운송료 전액 선결제 후 하차 완료 시 정산을 기본값으로 둔다.
- 현장 지급과 후불 승인은 예외 흐름으로 유지하고, 기사에게 미보증 위험을 명확히 표시한다.
- 결제 실패, 가상계좌 만료, 배차 실패, 기사 취소, 화주 취소, 분쟁 환불은 모두 원장 이벤트로 남긴다.
- 실제 출시 전에는 PG 계약, 전자금융거래법, 정산자금 보관, 위탁 정산 범위에 대한 법무 검토가 필요하다.

## 개발용 Fake Provider

실제 운영 전까지는 `FakePG`와 `FakeSettlement`를 개발용 화면에서만 사용한다. `FakePG` 결제창은 실제 결제가 시작되는 사용 위치에 맞춰 `HongdalApp`의 운송 의뢰 상세 화면에 붙이고, Admin은 원장 확인과 정산 지시 검증 역할에 집중한다. 이 모드는 실제 화주, 기사, 결제, 정산, 운송계약을 만들지 않고 다음 상태 전이를 검증하는 용도다.

1. `결제확보대기`에서 `결제확보됨`으로 전환한다.
2. 결제 확보 이후 `상차완료`와 `하차완료` 증빙 상태를 만든다.
3. 하차 완료 또는 조기 정산 후보 상태에서 `정산완료`를 만든다.
4. 분쟁, 증빙 부족, 검수 필요 상황은 `정산보류`로 전환한다.
5. 모든 Fake 이벤트는 `SIM-` 식별자와 `fake_` 외부키를 사용해 실운영 데이터와 섞이지 않게 한다.

이 모드는 샘플 원장과 E2E 스모크를 안정화하기 위한 장치이며, 실제 PG 키, 실제 계좌, 실제 계약 상대방 정보를 받지 않는다. 화주 앱의 Fake 결제창은 서버의 `POST /api/v1/payments/fake/confirm` 개발용 API를 호출해 `SIM-FPG-` 결제 레코드와 `fake_pg_` 외부키를 생성하고, 운영 Toss 승인 API를 호출하지 않는다. 서버 API는 Development 환경에서만 허용한다.

### 현재 구현 상태

| 영역 | 상태 |
| --- | --- |
| Server | `POST /api/v1/payments/fake/confirm`이 Development 환경에서만 FakePG 결제 승인 레코드를 만든다. |
| Server 원장 | `provider_type=990`, `PG사=FakePG`, `결제Id=SIM-FPG-*`, `PaymentKey=fake_pg_*`로 실운영 결제와 구분한다. |
| HongdalApp | 운송 의뢰 상세의 `Fake 결제창`이 서버 FakePG 승인 API를 호출한다. |
| HongdalAdmin | 결제 목록과 운송 결제/정산 상세에서 FakePG 결제 레코드를 조회할 수 있다. Admin에서 직접 Fake 승인하는 액션은 아직 없다. |
| HongdalAdmin 개발 콘솔 | `FakePaymentSettlementConsole`은 별도 메모리 시뮬레이션이며 서버 FakePG API와 연결되어 있지 않다. |
| Hongdal.WebApp | 일부 결제 화면에 Toss 준비/승인 호출이 남아 있다. 1.0 기본 경로로 쓰지 않을 경우 FakePG 또는 읽기 전용 검증 화면으로 바꿔야 한다. |
| DriverApp | 결제를 실행하지 않고 서버 원장의 결제 상태를 표시/검증하는 쪽이다. FakePG 직접 호출은 없다. |

### 남은 정리 작업

1. `Hongdal.WebApp`의 Toss 결제 실행 화면을 숨기거나 FakePG 개발 흐름으로 바꾼다.
2. Admin에는 실결제 실행 버튼이 아니라 FakePG 레코드 조회, 분쟁, 보류, 정산 지시 검증 중심의 화면을 둔다.
3. `tosspayments-integration-guide.md`는 참고/보관 문서로 표시하고, 새 구현 기준은 이 문서로 둔다.
4. 결제 제공자가 확정되면 FakePG API와 동일한 요청/응답 책임을 가진 provider adapter를 추가한다.
5. 실제 운영 전에는 webhook 멱등성, 환불, 배차 실패 환불, 하차 후 정산, 조기 정산 승인 이력을 테스트로 고정한다.
