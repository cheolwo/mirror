# 전통시장 공공데이터 모듈

## 목적

홍달의 지역 기반 기능을 직장 관리자 중심이 아니라 전통시장과 소상공인 중심으로 확장하기 위한 기준정보 모듈이다. 공공데이터를 홍달의 소유 데이터처럼 직접 수정하지 않고, 원본 기준일과 동기화 이력을 보존한 읽기 모델로 관리한다.

## 공식 데이터 원천

- 제공기관: 소상공인시장진흥공단
- 데이터: [소상공인시장진흥공단_전통시장현황_20250722](https://www.data.go.kr/data/15052837/fileData.do?recommendDataYn=Y)
- 원본 기준일: 2025-07-22
- 갱신 주기: 연간
- 핵심 식별자: 시장코드
- 주요 항목: 시장명, 시장 유형, 지번·도로명 주소, 시도, 시군구, 23개 편의·안전·물류시설 보유 여부

시설 보유 여부는 공공데이터 기준일의 참고 정보다. 현재 운영 여부를 보증하거나 입점 사업자의 권한을 증명하는 자료로 사용하지 않는다.

## 모듈 경계

`TraditionalMarketDbContext`는 기존 주문·운송·커뮤니티용 `HongdalContext`와 분리한다. 물리적으로는 같은 MySQL 연결을 사용하지만 다음 전용 테이블과 마이그레이션 이력을 가진다.

- `public_data_traditional_markets`: 전통시장 기준정보와 시설 현황
- `public_data_traditional_market_sync_runs`: 수집 성공·실패 및 변경 건수
- `__EFMigrationsHistory_TraditionalMarkets`: 모듈 전용 EF Core 마이그레이션 이력

원본에서 사라진 시장은 삭제하지 않고 `IsActive=false`로 전환하여 과거 커뮤니티나 거래 참조가 끊기지 않게 한다.

## API

| 용도 | 메서드와 경로 | 권한 |
|---|---|---|
| 시장 검색 | `GET /api/v1/traditional-markets` | 공개 |
| 시장 상세 | `GET /api/v1/traditional-markets/{marketCode}` | 공개 |
| 공공데이터 전체 동기화 | `POST /api/v1/traditional-markets/sync` | 서버 관리자 |

검색은 키워드, 시도, 시군구, 시장 유형, 공동물류창고 및 전용주차장 보유 여부를 지원한다. 응답의 `CommunityScopeKey`는 `traditional-market:{시장코드}` 형식이며 이후 시장 단위 커뮤니티의 안정적인 범위 키로 사용할 수 있다.

## 설정

기존 `PublicData` 설정을 재사용한다. 인증키는 저장소에 커밋하지 않고 로컬 설정이나 환경 변수로 주입한다.

```json
{
  "PublicData": {
    "DataGoKrServiceKey": "로컬 인증키",
    "TraditionalMarket": {
      "BaseUrl": "https://api.odcloud.kr",
      "ApiPath": "/api/15052837/v1/uddi:1fd54eb7-0565-4755-8ec7-a70931b6dc77",
      "DatasetKey": "semas-traditional-market-status",
      "SourceReferenceDate": "2025-07-22",
      "PageSize": 1000
    }
  }
}
```

`TraditionalMarket:ServiceKey`가 있으면 해당 값을 우선하고, 없으면 `DataGoKrServiceKey`, 마지막으로 기존 `ServiceKey`를 사용한다.

## 사용자별 활용 방향

- 소상공인: 소속 시장 선택, 시장 시설 확인, 시장 단위 커뮤니티 진입
- 방문자·주민: 지역과 시설 조건으로 시장 탐색
- 물류 담당자: 공동물류창고와 전용주차장 정보를 초기 참고 신호로 사용하되 실제 배차 가능 여부는 별도 운영 데이터로 판단
- 플랫폼 운영자: 연간 원본 갱신 시 수동 동기화 실행 및 변경·비활성화 건수 확인

향후 입점 사업자 권한은 공공데이터가 아니라 사업자 인증과 시장 운영주체 승인으로 별도 모델링한다.

## 생활권 공동구매 물류 거점

전통시장 기준정보와 실제 물류 운영 승인은 분리한다. 모든 시장은 주소와 시설 정보를 가진 후보가 될 수 있지만, `traditional_market_logistics_hubs`에 등록되어 시범운영 또는 활성 상태가 된 시장만 공동구매 물류 거점으로 공개한다.

거점 상태는 `Candidate → UnderReview → Pilot → Active` 순서로 진행한다. 운영 중단은 `Paused`, 종료는 `Closed`로 관리한다. 시범운영 또는 활성 전환에는 다음 조건이 필요하다.

- 상인회 또는 운영주체 지정 및 동의
- 현장 확인 완료
- 묶음 입고와 검수·분류 지원
- 주민 수령 또는 근거리 배송 중 하나 이상 지원
- 일일 공동구매 처리 용량과 생활권 서비스 반경 설정

공공데이터의 공동물류창고·전용주차장 표시는 후보 판단의 참고값일 뿐 자동 승인 조건으로 사용하지 않는다. 현재 응답은 `traditional-market-hub:{시장코드}` 형식의 `HubReferenceKey`를 제공한다. 공동구매 원장과의 직접 연결은 이후 이행 배치 기능에서 이 키를 참조해 추가하며, 현재 모듈은 거점 기준정보와 운영 가능 상태를 제공한다.

| 용도 | 메서드와 경로 | 권한 |
|---|---|---|
| 공개 거점 검색 | `GET /api/v1/traditional-market-logistics-hubs` | 공개, Pilot·Active만 |
| 공개 거점 상세 | `GET /api/v1/traditional-market-logistics-hubs/{marketCode}` | 공개, Pilot·Active만 |
| 전체 후보·상태 조회 | `GET /api/v1/admin/traditional-market-logistics-hubs` | 서버 관리자 |
| 후보 등록·운영조건 수정 | `PUT /api/v1/admin/traditional-market-logistics-hubs/{marketCode}` | 서버 관리자 |
| 상태 전환 | `POST /api/v1/admin/traditional-market-logistics-hubs/{marketCode}/status` | 서버 관리자 |

## 아파트-상인회 생활권 협의체

전통시장 물류 거점의 운영 승인과 별도로, 아파트 대표와 전통시장 상인회 대표가 수입·수출 희망 품목을 함께 검토하는 협의체를 둔다. 이 기능은 플랫폼이 거래를 주선하거나 계약을 자동 체결하는 기능이 아니다. 양측 대표가 제안과 의견을 기록하고, 이후 공동주문·수입 물류 워크플로우가 참고할 수 있는 합의 근거를 만드는 기능이다.

협의체는 다음 순서로 진행한다.

1. 아파트 대표 또는 상인회 대표가 상대 대표를 지정해 협의체를 만든다.
2. 요청자는 생성과 동시에 참여 수락 상태가 되고, 상대 대표는 별도 수락을 남긴다.
3. 양측 수락이 완료되면 협의체 상태가 `협의중`으로 바뀐다.
4. 참여 대표는 수입 또는 수출 안건을 만들고 품목, 수량, 국가, 기간, 물류 조건, 예상 금액과 통관 검토 필요 여부를 기록한다.
5. 양측 대표가 각각 `동의`, `보완요청`, `반대` 중 하나를 남긴다. 양측이 모두 동의한 경우에만 안건이 `합의`가 된다.

`traditional-market-council:{협의체Id}`와 `traditional-market-trade-agenda:{안건Id}` 참조 키는 게시글, 원장 또는 공동주문 실행 계획이 협의 결과를 연결할 때 사용한다. 합의는 주문·계약·통관 신고를 자동 생성하지 않는다.

| 용도 | 메서드와 경로 | 권한 |
|---|---|---|
| 내가 참여한 협의체 | `GET /api/v1/traditional-market-councils/mine` | 로그인 사용자 |
| 협의체 상세 | `GET /api/v1/traditional-market-councils/{councilId}` | 양측 대표 |
| 협의체 생성과 상대 대표 초대 | `POST /api/v1/traditional-market-councils` | 로그인 사용자 |
| 초대 수락 | `POST /api/v1/traditional-market-councils/{councilId}/accept` | 지정된 대표 |
| 수입·수출 안건 생성 | `POST /api/v1/traditional-market-councils/{councilId}/agendas` | 참여 수락이 끝난 양측 대표 |
| 안건 결정 | `POST /api/v1/traditional-market-councils/{councilId}/agendas/{agendaId}/decisions` | 양측 대표 |

저장 테이블은 `traditional_market_neighborhood_councils`와 `traditional_market_trade_agendas`이며, 전통시장 모듈의 `TraditionalMarketDbContext`와 전용 마이그레이션 이력을 사용한다. 대표 사용자 ID는 협의체 내부 역할 판정에만 사용하며 전역 회원 역할을 새로 만들지 않는다.

## 수입육 국내 2차 가공과 생활권 배송

호주 등 해외에서 수입하는 육류는 전통시장이 살아 있는 가축을 인수하거나 도축하는 흐름으로
모델링하지 않는다. 해외 승인 작업장에서 도축·1차 가공과 수출 검역을 마친 축산물이 국내에
도착한 뒤, 수입 검역·검사와 통관을 거쳐 공식 반출된 시점부터 국내 이행을 시작한다.

| 순서 | 단계 | 책임 경계 |
| --- | --- | --- |
| 1 | 해외 승인시설 생산 | 도축·1차 가공과 수출국 위생 관리는 해외 생산자와 승인시설 책임 |
| 2 | 수출 검역·냉동 또는 냉장 운송 | 수출 증명, 선적 서류와 국제 콜드체인은 수출자·운송 계약 주체 책임 |
| 3 | 국내 검역·수입검사 | 농림축산검역본부·식품의약품안전처의 공식 결과를 원장 근거로 연결 |
| 4 | 수입신고 수리·통관 반출 | 관세청 반출 근거가 확인되기 전 국내 가공·판매 단계로 넘기지 않음 |
| 5 | 전통시장 영업장까지 냉장·냉동 운송 | 운송 주체의 취급 권한, 온도 조건과 인수 기록을 별도 확인 |
| 6 | 입고·이력 확인 | 품목, 중량, 포장 상태, 소비기한, 수입유통식별번호 등 적용 식별정보 확인 |
| 7 | 국내 2차 가공 | 반입 형태와 신고된 영업 범위 안에서 필요한 발골·정형·절단·소분 수행 |
| 8 | 소비자 단위 포장·표시 | 작업 배치, 중량, 보관 온도, 표시사항과 원제품 추적 연결 유지 |
| 9 | 공동주문별 인계 | 확정 주문과 포장 단위를 연결하고 보관·인계 시점의 온도와 수량 기록 |
| 10 | 생활권 냉장배송 | 판매자가 직접 전달하는 경우와 별도 축산물 운반업자를 쓰는 경우를 구분 |

7단계의 `국내 2차 가공`은 시장 안의 상인이라는 이유만으로 허용되지 않는다. 실제 작업이
식육판매업, 식육포장처리업 또는 식육즉석판매가공업 중 어느 영업에 해당하는지, 해당 사업자가
그 작업을 신고된 시설과 범위 안에서 수행할 수 있는지를 관할 관청과 사업자가 확인해야 한다.
전통시장 공공데이터와 물류 거점 승인은 영업신고·시설 기준·종사자 위생관리·축산물 이력관리
확인을 대신하지 않는다.

플랫폼은 다음 원칙을 지킨다.

- 특정 가공업자나 운송업자를 자동 선정·배정하거나 작업 가능성을 보증하지 않는다.
- 사업자가 역할 참여를 직접 수락하고 영업 종류, 시설 주소가 아닌 시설 참조키, 취급 품목,
  온도대, 일일 처리량과 서비스 범위를 제출한 뒤에도 실제 계약과 인허가는 별도 확인한다.
- 도축과 생축 운송은 전통시장 2차 가공 역할에서 제외한다.
- 검역·검사·통관의 공식 결과가 없으면 시장 입고 이후 단계를 `대기`로 유지한다.
- 소비자 주소는 커뮤니티나 가원장에 공개하지 않고 배송 동의 후 필요한 수행자에게만 전달한다.

### 경제성 계산

전통시장 상인의 작업은 무료 절감액으로 간주하지 않고 지역 내 전문 서비스 보상으로 계산한다.
공동구매 참여자에게는 다음 비용과 산출 기준을 같은 계획 리비전으로 공개한다.

```text
판매 가능 kg당 예상 원가 = (
  국내 반출 완료 수입육 원가
  + 시장까지의 냉장·냉동 운송비
  + 발골·정형·절단·소분 작업비
  + 포장·표시·이력관리비
  + 생활권 냉장배송비
  + 감량·폐기 위험준비금
) / 예상 판매 가능 중량
```

원물 중량과 판매 가능 중량을 분리하여 수율을 표시하고, 상인·운송인·판매자의 보상과 참여자의
예상 편익을 함께 보여준다. 견적 출처와 유효시점이 없거나 처리량·온도·수율 중 하나라도 확인되지
않으면 `확인된 절감액`으로 표현하지 않는다.

### 공식 확인 경로

- [수입식품정보마루 해외작업장 조회](https://impfood.mfds.go.kr/CFCCC01F02): 수출국·해외작업장 승인 상태 확인
- [식품안전나라 업체 검색](https://www.foodsafetykorea.go.kr/portal/mfds_cn_busn_popup.html): 국내 축산물 영업 종류와 업체 정보 확인
- [식육판매업 영업 범위 법령해석](https://www.law.go.kr/LSW/cgmExpcInfoP.do?cgmExpcDatSeq=2292471&mode=2&ofiClsCd=350123): 포장육 절단·재분할 판매의 적용 범위 참고
- [식육즉석판매가공업 규제 정보](https://www.mfds.go.kr/usr/rgltnInvtView.do?seq=202400013): 직접 판매를 전제로 한 가공·재분할 범위 참고
- [축산물 운반업 규제 정보](https://www.mfds.go.kr/usr/rgltnInvtView.do?seq=202400007): 별도 운송 역할과 냉장·냉동 운송 범위 확인
- [축산물이력제 소비자 안내](https://www.mtrace.go.kr/mobile/customerMtraceGuide.jsp): 이력번호와 묶음번호 확인 방식 참고

이 확인 경로는 후보 조사와 화면 안내에 사용한다. 개별 품목·작업·사업자의 적법성을 플랫폼이
판정하는 근거로 자동 사용하지 않는다.

## 국내 농수산물 산지 공동출하와 시장 직입고

국내 농산물과 수산물은 수입품 흐름에 억지로 끼워 넣지 않는다. 상품 출발국가와 배송국가가 모두
`KR`이고 전통시장 생활권을 수령 거점으로 정한 공동구매는 `국내 산지 공동출하` 하위 여정으로
조립한다. 이 여정에는 검역·통관 단계를 만들지 않고, 생산자와 산지 공급 주체가 출하 조건을 직접
수락한 뒤 전통시장 입고 슬롯으로 곧장 연결한다.

| 순서 | 단계 | 책임과 확인 근거 |
| --- | --- | --- |
| 1 | 공동구매 수요·최소 출하량 확정 | 예약 수량과 추가 관심 수량을 분리하고 최소 출하 단위를 확인 |
| 2 | 생산자·산지 공급 주체 직접 수락 | 플랫폼 자동 선정 없이 품목·물량·가격·인계 조건을 당사자가 수락 |
| 3 | 생산지·수확 또는 어획·양식 정보·lot 확정 | 원산지, 품질·규격, 수량, 단가와 반품·감량 기준을 같은 리비전에 기록 |
| 4 | 산지 선별·포장·상차 | 시장 검수와 주문별 배분에 맞는 단위로 포장하고 작업 범위와 상차 기록 유지 |
| 5 | 산지에서 전통시장으로 직송 | 수락된 운송 주체가 확정 lot를 시장 입고 시간에 맞춰 인계 |
| 6 | 시장 입고·수량·품질 검수 | 상인회·시장관리자와 품목 상인이 수량, 품질, 원산지, 포장·온도 상태 확인 |
| 7 | 품목 상인 검수·소분·주문별 배정 | 상인이 직접 수락한 작업 범위 안에서 예약 물량을 참여자별로 먼저 배정 |
| 8 | 예약 수령·동의한 생활권 배송 | 시장 직접 수령 또는 주소 제공에 동의한 주문만 배송 주체에게 인계 |
| 9 | 확정 여유 물량 장날 판매 | 예약 물량과 분리해 공급자·판매 상인이 확정한 재고만 주민에게 공개 |
| 10 | 정산·지역 보상·다음 회차 기록 | 생산자 대금, 운송비, 상인 보상, 수령률과 잔량을 공개 가능한 집계로 기록 |

현재 자동 품목 분기는 국내 거래로 명시된 HS 제03류를 수산물, 제06류부터 제14류를 농산물 후보로
다룬다. 이 분기는 화면에 필요한 취급 프로필을 고르는 보조 분류일 뿐 실제 품목분류나 영업 자격을
확정하지 않는다. 축산물과 가공식품은 품목별 인허가·보관·표시 요건이 다르므로 같은 여정으로
자동 확장하지 않는다.

국내 농수산물 여정은 다음 경계를 지킨다.

- 생산자·생산자단체·산지 공급 주체, 산지 선별·포장 주체, 운송 주체와 시장 입고 주체를 서로
  다른 역할 슬롯으로 둔다. 같은 사업자가 여러 역할을 맡더라도 책임과 근거는 역할별로 남긴다.
- 플랫폼은 생산자, 산지 공급자, 운송인 또는 참여 상인을 자동 선정·배정하지 않는다.
- 농산물은 품목별 적정 온도·통풍·적재 조건을 확인하고, 수산물은 냉장·냉동 조건과 선도·상하차
  기록을 기본 확인 대상으로 둔다.
- 생산지·생산자 또는 어획·양식 정보와 출하 lot를 시장 입고·상인 작업·참여자 배분 기록까지
  연결한다. 공개 화면에는 법정 표시사항을 유지하되 개인 구매내역과 주소를 노출하지 않는다.
- 예약 물량은 참여자의 수령권이므로 시장 입고 뒤에도 현장판매 재고로 자동 전환하지 않는다.
- 가격 비교에는 산지 대금뿐 아니라 선별·포장, 국내 직송, 시장 검수·소분, 판매와 생활권 배송의
  정당한 보상을 함께 넣는다.

원산지 표시의 적용 범위와 방식은 [농수산물의 원산지 표시 등에 관한 법률](https://law.go.kr/LSW/lsInfoP.do?ancYnChk=0&lsId=011154)을
참고하되, 실제 품목·포장·판매 방식별 의무는 판매 주체와 관계 기관이 다시 확인한다.

### 시장 조리 가게 식재료 공급 분기

전통시장 안에는 농수산물을 그대로 판매하는 상점뿐 아니라 반찬, 도시락, 음료, 제과와 식사류를
조리·판매하는 가게가 있을 수 있다. 이 가게가 공동구매 품목을 식재료로 필요로 하면 현장판매
잔량을 임의로 가져가는 방식이 아니라, 공동구매에 별도 수요자로 참여해 공급 조건을 직접 수락한다.

```text
가정 공동구매 예약분 잠금
  -> 시장 조리 가게가 품목·규격·수량·사용 목적·수령·보관 조건 등록
  -> 공급자와 가게가 단가·인수·반품·정산 조건 직접 수락
  -> 가게의 실제 영업신고 범위·조리시설·보관 조건 확인
  -> 시장 입고 검수 뒤 가정 예약/가게 공급/현장판매 lot 분리
  -> 가게 조리장 인계와 산지 lot·수량·보관·사용 배치 연결
  -> 가정 공동구매와 구분한 가게 공급 정산·다음 수요 기록
```

가게 공급은 다음 경계를 지킨다.

- 먼저 확정된 가정 예약분을 가게 공급으로 자동 전환하지 않는다. 가게 물량은 초기 모집 때 별도
  예약하거나 공급자가 추가로 확인한 물량 안에서만 확정한다.
- 플랫폼이나 상인회가 가게를 자동 배정하지 않는다. 가게가 식재료 사용 목적과 필요한 수량을
  제안하고 공급 가격, 인수 시점, 품질·반품과 보관 책임을 직접 수락한다.
- 가정용 꾸러미와 가게용 식재료는 규격, 단가, 세금·증빙, 결제·정산과 반품 조건을 분리한다.
  공동구매 참여자에게는 자기 부담과 전체 물량 구성이 오해되지 않도록 구분된 집계만 보여준다.
- 가게 참조키만 커뮤니티 원장에 공개하고 상호·시설·담당자·연락처의 공개 범위는 가게가 정한다.
  영업 상태와 실제 조리·판매 범위는 공식 업체 정보와 관할 기관 확인을 별도로 거친다.
- 원산지·생산 또는 어획·양식 정보와 산지 lot를 시장 입고, 가게 인수와 조리 사용 배치까지
  연결한다. 가게의 최종 메뉴 표시와 소비자 판매 책임은 식재료 공급 원장이 대신하지 않는다.
- 식재료 인수는 가게 메뉴나 음식 주문을 자동 생성하지 않는다. 실제 메뉴 판매와 배달은 기존
  음식 주문·음식 배달 원장에서 가게가 별도로 수락한다.

음식류를 조리·판매하는 영업의 세부 종류와 범위는
[식품위생법 시행령 제21조](https://law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1021114083)를 참고하고,
후보 가게의 업체 정보는 [식품안전나라 업체 검색](https://www.foodsafetykorea.go.kr/portal/mfds_cn_busn_popup.html)에서
확인할 수 있다. 이 조회는 참여 가게의 개별 식재료 취급과 조리 행위가 적법하다는 플랫폼 보증으로
사용하지 않는다.

## 공동구매 장날

공동구매 물량이 시장으로 들어오는 날을 단순 수령일로 끝내지 않고, 상인회와 참여 상인이 합의한
`공동구매 장날`로 운영할 수 있다. 5일장처럼 주민이 기억할 수 있는 일정에 상품을 입고하고,
공동구매 참여자의 예약 물량을 먼저 보호한 뒤 별도로 확정된 여유 물량만 현장에 진열한다.
공동구매에 참여하지 않은 주민도 시장을 방문해 상품을 살펴보고 현장판매 재고 안에서 구매할 수 있다.

장날은 다음 순서로 준비한다.

1. 커뮤니티 게시글과 가원장에서 예약 수요와 추가 관심 수요를 분리한다.
2. 상인회 또는 실제 시장관리자와 공동사업, 일정, 공용공간, 차량 동선과 시설 사용을 합의한다.
3. 품목을 취급할 상인이 작업 범위, 처리량, 비용과 판매 책임을 직접 수락한다.
4. 입고일, 예약 수령시간, 현장판매시간과 공개 가능한 현장판매 물량을 확정한다.
5. 일정과 확정 물량만 지역 게시판, 시장 현장판과 동의한 구독자 알림에 공개한다.
6. 장날 입고 때 품질, 수량, 원산지·표시와 예약·현장판매 재고 분리를 다시 확인한다.
7. 판매 종료 뒤 예약 수령, 현장 판매량, 잔량, 상인 보상과 주민 반응을 원장에 남긴다.

### 재고와 배정 경계

- 공동구매 예약 물량은 참여자의 수령권이므로 현장판매 재고와 별도 식별·보관한다.
- 추가 관심 수량은 판매 상인과 공급자가 확정하기 전에는 현장판매 가능 물량으로 광고하지 않는다.
- 수령하지 않은 예약 물량을 자동으로 현장판매로 돌리지 않는다. 연락, 환불, 양도, 할인 또는
  기부 조건을 참여 규칙과 판매자의 책임 범위에서 미리 합의한다.
- 플랫폼은 특정 상점에 물량을 자동 배정하지 않는다. 상인회가 참여 범위를 조정하고 각 상인이
  배치 물량과 비용을 직접 수락한 뒤 확정한다.
- 여러 상인이 같은 품목에 참여하면 처리 용량, 취급 범위, 상인별 수락 물량과 실제 이행량을
  공개 가능한 집계로 남긴다. 순환 참여나 상한은 상인회가 합의하되 플랫폼이 가격을 공동 결정하지 않는다.

### 품목별 참여 상점

| 품목 | 기본 참여 역할 | 작업 경계 |
| --- | --- | --- |
| 육류 | 허가·신고된 식육 작업 사업자, 식육 판매 상인 | 국내 반출 후 실제 영업 범위 안의 정형·절단·소분·포장 |
| 채소·과일 | 청과·채소 상인, 선별·소분 담당, 현장 판매 상인 | 검수·선별·등급·단순 다듬기와 세척·절단 등 추가 가공을 구분 |
| 곡물 | 곡물 상인, 필요 시 별도 도정 사업자 | 원물 판매·소분과 도정·가공 책임을 분리 |
| 수산물 | 수산물 판매·처리 사업자 | 보관온도, 손질·가공 범위와 원산지 표시를 별도 확인 |
| 일반 생활상품 | 품목 취급 상인 | 검수·분류·소분·표시 중 직접 맡는 범위를 수락 |

채소·과일은 원물 상태의 선별·단순 소분과 세척·절단·즉석섭취 형태의 추가 가공을 같은 작업으로
간주하지 않는다. 수입 농산물은 식물검역과 통관 반출을 확인한 뒤 장날 이행을 시작하고,
포장·통신판매 화면과 현장에는 적용되는 원산지 표시를 유지한다.

### 지역경제 기록

장날 종료 후에는 최저 판매가격만 성과로 보지 않고 예약 수령률, 현장 방문·판매량, 참여 상점 수,
상인별 작업·판매 보상, 지역 배송 보상, 잔량·폐기량, 지역 안에 지급된 금액과 다음 장날 재참여
의향을 함께 기록한다. 개인의 구매내역이나 주소는 공개하지 않고 동의된 집계만 커뮤니티에 공유한다.

## 시장별 꾸미기 팩과 디자이너 참여

전통시장 꾸미기 팩은 개인이 자기 화면에만 적용하는 읽기 테마와 구분한다. 시장 게시판 표식,
장날 배너, 상품 표식, 예약 수령 안내와 성사 이야기를 하나의 공용 디자인으로 묶되,
`traditional-market:{market-key}` 범위의 한 시장에만 적용한다. 다른 시장이나 개인 게시판으로
자동 확장하지 않는다.

공식 적용은 다음 순서를 따른다.

1. 디자이너가 시장명, 적용 범위, 여섯 개 표식과 보상 제안을 포함한 초안을 제출한다.
2. 플랫폼이 저작권·라이선스, 접근성, 사칭·오인 가능성과 필수 정보 보존 여부를 검토한다.
3. 해당 시장 상인회 또는 실제 시장관리자가 시장명·상징·공용공간에서의 사용을 승인한다.
4. 두 승인이 모두 기록된 리비전만 해당 시장의 공식 팩으로 적용한다.
5. 수정본은 새 리비전으로 다시 검토하며 기존 승인 범위를 자동 승계하지 않는다.

팩으로 꾸밀 수 있는 영역은 시장 머리표, 게시판 표식, 장날 배너, 상품 표식, 수령 표지와
성사 이야기 표지다. 가격, 수량·중량, 원산지, 알레르기, 보관·온도 조건, 수령 장소·시간,
예약 물량과 현장판매 재고 구분은 시스템이 관리하며 색·배경·이미지로 가리거나 의미를 바꾸지 않는다.

디자이너 보상은 상인회·시장관리자와 디자이너가 별도 계약으로 정한다. 현재 꾸미기 상점은
초안 제출, 승인 상태와 제안 내용을 기록하는 시범 경로이며 저작권 양도, 용역 계약 또는 정산을
자동 체결하지 않는다.
