# 음식 배차 알림 복구와 기사 겸 운영자 검증 r54

사용자의 1·2·4번 선택에 따라 평소에는 일반 기사로 일하고 중요한 문제에만 운영자로 개입하는 흐름을 보완했다. [고정 설계](../AI/Planning/공통/PLAN-OPERATIONS-DISPATCH-CORE/notification-recovery.implementation.r54.md)와 [작업 명세](../AI/Planning/공통/PLAN-OPERATIONS-DISPATCH-CORE/notification-recovery.r54.work-order.json)를 따른다. 기존 r53의 코드와 검증 이력은 보존한다.

## 1. 누락·일시 실패 자동 복구

- 발송 worker가 현재 유효한 음식 추천의 누락 알림을 같은 원장·기사·라운드 유일 키로 복구한다. 추천 시작 재호출도 같은 추천의 누락 알림만 보충한다. 요금·추천 라운드·기한·수락은 변경하지 않는다.
- 토큰 미등록·전송 실패는 최대 5회, 5/10/20/30초 이후 재시도한다. 주기 실행 시 실제 간격은 더 길 수 있다. DB 조건부 갱신과 60초 발송 lease를 사용하고 중단된 발송은 새 서비스에서 복구한다. lease와 완료 조건은 읽음 처리의 UpdatedAt과 분리해 마지막 시도 시각·횟수·상태로 묶었다.
- 전송 직전 현재 원장을 재조회한다. 수락·만료·재배정·라운드 변경은 Obsolete로 처리하고 성공한 알림은 재발송하지 않는다. 외부 발송과 DB 완료 사이 중단은 중복 전달 가능성이 있는 at-least-once이며 앱의 정본 재조회·명시 수락 관문을 유지한다.
- 기본 추천 유효기간 60초에서는 5회 소진 전에 만료될 수 있다. 기존 만료/후보 재탐색 흐름으로 돌아가며 알림 복구를 위해 제안 기한을 늘리지 않는다. 5회 소진 긴급 알림은 기한 내 실제 소진한 현재 추천에 해당한다. 모든 짧은 추천의 실패를 즉시 운영 경보로 확대하지 않는다.
- 화물 알림의 기존 계약과 발송 흐름은 유지한다. 새 DB column·migration·공개 API 변경은 없다.

## 2. 조치가 필요한 예외

일시 알림 실패와 회수 가능한 공동 원장 Processing lease는 자동 복구 중으로 표시한다. 현재 유효한 음식 추천의 복구 소진만 긴급 알림 대상으로 올리고 만료·수락·재배정된 과거 알림은 제외한다. lifecycle 주의 단계와 운영자 예외를 구별하여 짧은 지연 경보를 억제한다. 원장 연결 이상·픽업 후 중단 등 기존 중요한 예외는 유지한다.

인증된 알림 상세의 기존 Message에 문제별 다음 행동을 제공한다. 외부 푸시/메일은 개인정보 없는 기존 일반 안내를 유지하고, 알림 확인과 실제 문제 해결을 구별한다. 별도 복구 상세 화면의 오래된 Processing 표시는 이번 변경 밖의 후속 정리 대상이다.

## 4. 본인도 일반 기사로 수행

일반 기사 권한만으로 실제 운행 시작 API와 SQL 근무 저장, 배차 수신 설정, 두 건 순차 추천·앱 배너·명시 수락·도착·조리 대기·픽업·전달·별도 주문자 수령을 연결한 로컬 통합 시험을 추가했다. 본인이 신규 기사일 때 기존 오래 기다린 기사가 먼저 선정되고 타인 추천을 수락할 수 없는 경우도 검사한다. 운영자 API 호출 없이 수행하며 중복·이전·만료 알림은 현재 업무를 바꾸지 않는다.

HTTP host를 재생성한 뒤 새 인증 session/API/PageModel에서 진행 중인 전달 업무를 재조회한다. 같은 SQLite와 시험 memory store를 유지한 host 재생성이다. 전체 서버 프로세스·Redis 재시작 증거가 아니며 GPS·native 알림·FCM·AI 응답은 명시적 시험 경계다. 작업 주기는 시험에서 명시적으로 호출하므로 무인 background timer 실행을 인증하지 않는다.

## 검증과 실행 한계

검증 결과와 원본 로그 위치는 작업 명세에도 기록한다. 최종 집중 Fast `artifacts/local/validation/20261011-223838`은 107개 통과, 실패/건너뜀 0이다. 시험 프로젝트 빌드는 경고 71개·오류 0, 서버 빌드는 경고/오류 0이다. 경고는 기존 using·시험용 연결 소스 형식 충돌·분석기 항목이며 이번 수정 소스의 새 경고는 없다.

다음 최초 실패와 수정 이력은 보존한다.

- Fast `20261011-223036`: 시험용 화물 미사용 port의 DTO namespace 누락으로 build 실패. 실제 DTO 참조를 추가했다.
- Fast `20261011-223241`: 98개 통과·2개 실패. 과거 추천의 무효화와 현재 새 추천 알림의 복구를 함께 검사하도록 기존 시험의 기대값을 정정했다.
- Fast `20261011-223435`: 100개 통과·실패/건너뜀 0. 이후 동일 Pending의 두 worker 경합 시험과 기존 추천 재호출의 복구 기대값을 최종 Fast에 포함했다.
- Task `20261011-223545`: 10,885개 통과·10개 실패·건너뜀 0. 기존 추천 재호출 시험 1개의 알림 호출 기대값을 같은 기사·라운드의 복구 1회로 고쳤다. 나머지 9개는 시험마다 새 InMemory DB 루트를 생성해 전체 실행에서 EF service provider 한도를 넘은 문제였다. 기본 시험 루트만 공유하고 DB 이름은 고유하게 유지해 격리를 보존했다. 경고를 숨기지 않았다. 실패 실행의 임시 Mongo 컨테이너는 정리했다.

최종 Task `artifacts/local/validation/20261011-224039`은 전체 10,895개 통과, 실패/건너뜀 0이다. solution 빌드 경고 6개·오류 0이며, 경고는 기존 회원/관리자 Firebase 미설정 안내다. 기존 `mongo:8.0` 이미지(Mongo 8.0.26)를 `--pull never`로 재사용한 격리 standalone/replica set에서 Mongo 24개를 실제 실행했다. 시험 DB가 기본 DB만 남은 것을 확인하고 이번 실행의 임시 컨테이너 두 개를 정리했다. 기존 DB/볼륨은 변경하지 않았다. 실제 MySQL/Redis 실행·장치 알림 검증은 이 결과에 포함되지 않는다. 원본 근거는 `artifacts/local/food-dispatch-notification-r54/mongo-20261011T134032Z-06703303/summary.json`다.

범위 검사에서 dirty 40개 중 이전 작업 19개를 식별했고, 명세 밖 새 변경 0·관련 없는 이전 파일 해시 보존·설계 해시 불변·HEAD 불변·빈 index·새 문서 링크 12개와 diff 검사를 확인했다.

과거 r49의 결손 관측 문서는 보존하고 해당 시험은 현재 복구 기대값으로 전환했다. 별도 읽기 검토에서도 남은 중대한 결함이나 검증 범위를 넘는 완료 주장은 발견되지 않았다.

코드·로컬 통합 검증과 실제 운영은 별개다. 운영 기능/외부 전송 기본 OFF, 실제 FCM/Gmail·휴대폰·Azure·모델 추론/학습·Unity·commit/push는 수행하지 않는다. 앞선 3번 배차 간격 변경 승인·이력·rollback 기능은 이번 범위가 아니다. UI 화면 변경이 없어 새 화면 캡처는 만들지 않는다.
