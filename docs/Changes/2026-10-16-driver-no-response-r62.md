# 연속 미응답 신규 배차 중지·같은 토글 재개 r62

2026-10-16. [승인 명세](../AI/Planning/공통/PLAN-OPERATIONS-DISPATCH-CORE/driver-no-response.implementation.r62.md)에 따라 음식 기사 앱의 기존 지도 좌측 상단 `신규 배차 받기` 토글과 서버의 추천 만료·활동 원장을 연결했다. 운행·이미 수락한 업무·다른 서버 제한을 보존한다.

현재 상태: `Implemented / LocalValidated / AndroidBuilt / DeviceDeferred / OperationalConfigurationUnchanged`. 최종 시험 결과와 Android 빌드 근거는 아래 표에서 별도로 확인한다.

## 기사 화면과 처리 흐름

```text
신규 배차 받기 ON
├─ 앱에 표시된 유효 추천에 연속 1·2회 미응답 → 계속 수신
├─ 세 번째 연속 미응답 → 신규 수신만 중지
│  ├─ 지도 좌측 상단 기존 토글 OFF · 미응답으로 중지
│  ├─ 운행·이미 수락한 배달은 계속
│  └─ 같은 토글을 기사 본인이 ON → 횟수·미응답 중지 해제
└─ 새로 고침·운행 시작의 자동 ON → 미응답 중지 해제 안 됨
```

중지 안내는 `연속 3회 미응답으로 신규 배차가 꺼졌습니다. 다시 켜면 받을 수 있습니다.`다. 별도 재개 화면·버튼을 추가하지 않는다. 정상 수락·명시적 거절은 연속 횟수를 초기화하지만 이미 중지된 수신을 자동 재개하지 않는다. 시간 경과만으로도 재개하지 않는다.

## 서버 원장과 실패 복구

- 기존 공통 활동 원장을 재사용한다. 앱의 로컬 값이나 오래된 Redis 투영을 정본으로 삼지 않고 원장에서 중지 상태를 재구성한다. 새 DB 테이블·마이그레이션은 없다.
- `PUT api/v1/driver/operational-dispatch/offers/{requestId}/receipt`는 현재 인증 기사·추천 차수·추천 상태·유효시간·수신 가능 여부를 서버에서 검증한다. 앱의 실제 표시 확인과 FCM 발송 성공·사람의 읽음·소리 청취는 다른 근거다.
- 확인 없는 제안·구형 차수 0·확인 전송 실패를 미응답 근거로 만들지 않는다. 같은 제안·차수의 반복 확인과 만료는 멱등 처리한다. 같은 제안의 새 차수는 새 배너·확인 대상으로 구분한다.
- 정상 추천 만료와 미응답 사건을 같은 트랜잭션에 저장한다. 실제 만료 시각을 보존해 재개 전에 표시된 오래된 제안의 지연 처리가 새 연속 횟수를 만들지 않도록 한다.
- 저장·커밋 실패는 이번 사건·대상 원장의 추적만 정리한다. 미저장 대상 변경·동시 수락을 덮어쓰지 않으며, 후속 후보 조회 실패나 커밋 응답 유실 뒤에는 기존 `추천대기` 스캐너가 정본부터 이어 처리한다.
- 본인 토글 ON은 `미응답자동중지해제=true`와 같은 요청 ID를 보존한다. 응답 유실·중복 요청에서도 해제 의사가 바뀌지 않으며, 다른 운영 제한을 해제하지 않는다. 새로운 중지가 발생하면 이전 성공 요청과 구분해 새 재개 요청을 만든다.
- 공통 UI는 표시된 선택 카드의 가시성·계정·수명을 확인하고, 네이티브 UI는 활성 배달 화면의 최신 표시 배너 한 건만 확인한다. 숨은 페이지·단순 데이터 조회를 표시 확인으로 기록하지 않는다. 확인 실패 때문에 수락·기존 수행을 막지는 않는다.

이번 구현은 공통 서버와 음식 기사 네이티브·공통 화면의 수직 범위다. 화물 기사 앱에 같은 토글을 신설하거나 대기 우선순위·요금·AI 모델·운영 기능 플래그를 변경하지 않았다.
