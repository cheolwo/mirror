# 배송료 선결제·화물 주간 지급 준비 r73

2026-10-15. 사용자는 배송료 선결제부터 준비하고, 업무별로 발생한 보수는 한 사람 기준으로 매주 정산하기를 요청했다. 현재 구현 범위는 배송료 준비/수납 확인과 화물 지급 준비 명세이며 음식·피킹까지 합친 실제 주간 송금은 후속이다.

## 구현

- 서버의 저장 운임과 혜택 근거를 결제 준비 시 동결한다. 신규 의뢰 선결제는 `TransportPrepayment:Enabled` 기본 OFF이며 기존 후불 흐름을 보존한다. 화주 직접 운임 제안 API는 `화주직접운임제안=true`일 때 배송료와 기사 제안액을 같게 보관하고 플랫폼 수수료는 0으로 둔다. 기존 UI·CSV 작성에서 이 새 옵션까지 연결한 것은 아니다.
- 토스 승인/인증 조회에서 결제키·주문번호·금액·KRW·상태를 검사한다. `WAITING_FOR_DEPOSIT`는 대기로 남기고 `DONE` 근거가 있어야 승인 후속을 만든다. 승인 시도를 먼저 저장하고 응답 유실 뒤에는 동일 결제를 조회한다. 실제 PG를 호출하지 않은 로컬 모의 시험과 구별한다.
- 비공개 원문 secret 대신 검증 해시를 보관한다. 입금 콜백은 별도 기본 OFF이며 게시된 상태를 신뢰하지 않고 인증 조회로 확인한다. 결제 조회 URL에 포함되는 결제키는 typed HTTP client 로그에서 제외했다.
- 재처리된 승인 후속이 진행·완료·취소 운송을 되돌리지 않는다. 수납 취소/부분취소는 지급 검토를 보류하며 실제 환불이나 운송 취소 완료로 확대하지 않는다.
- `DriverPayoutBatch:Enabled` 기본 OFF. 관리자는 기존 화물 승인 지급요청을 `Weekly` 준비 명세에 묶을 수 있다. 원 운송 완료일의 한국시간 수~화 주간과 목요일 09시 예정일을 기록하며 수요일 설정도 가능하다. 같은 채무의 건별/주간/동시 명세 중복 편입은 DB 고유 제약으로 막는다. 권한·계좌·수납·운임·완료·사건·모드/정책 판본은 다시 확인한다.

## 주간 정산의 남은 연결

음식·화물·피킹을 별도로 송금하는 것이 목표가 아니다. 건별 전문 원장은 유지하면서 한 사람의 지급 가능한 금액을 주간 합산하는 것이 기준이다. [현재 연결 조사](../ProjectOverview/page-docs/weekly-worker-payout-audit-r73.md)와 [정산 기준](../Architecture/TransportPaymentSettlementPolicy.md)을 따른다.

현재 배치는 화물만 포함하며 한 요청 최대 200행이다. 같은 기사·주간의 여러 명세를 한 번의 실제 지급으로 합치는 실행 단위, 누락 자동 수집·늦은 승인 이월, 주 마감·지급일 도래 검사, 은행 휴일·잔액·외부 지급 결과 연결은 아직 없다. `Prepared`는 지급 조건 재검사를 거친 준비 상태이며 주간 확정이나 입금 완료가 아니다. 기존 `기사월정산Service`의 플랫폼 이용료를 기사 수입으로 더하지 않는다. 배송료에 포함된 피킹 참조와 입고비 원가 배부도 중복 보수로 더하지 않는다.

기존 혜택 계산·사용 처리는 재사용한다. 서로 다른 결제가 동일 혜택을 동시에 사용하는 경우의 전역 원자적 예약까지 새로 구현한 것은 아니다. 운영 활성화 전 보완 항목이다.

## 로컬 검증

- 집중 Fast 268개 통과·실패/건너뜀 0개. 최종 Task 11,736개 통과·실패 0개·환경 의존 16개 건너뜀. 전체 소비 앱 빌드 오류 0개·기존 경고 61개. 실제 PG 통신 대신 모의 HTTP 응답을 사용하며 배치 동시 편입은 별도 SQLite 연결로 검사했다.
- Migration 검사 2개에서 신규 열/테이블/참조/고유 제약과 기존 참여 테이블 미재생성을 확인했다. 디자인 전용 비연결 설정의 EF 모델 일치 검사도 통과했다. 실제 DB migration/동시 운영 HTTP/은행 이체 검증은 아니다.
- 고정 소스 42개 변경 없음, 기존 범위 밖 변경 파일 388개와 HEAD 보존을 확인했다. 상세 로그: `artifacts/local/validation/20261015-134319`(Fast), `artifacts/local/validation/20261015-134530`(Task), `artifacts/local/transport-prepayment-settlement-r73`(기준선·동결·모델 대조).
- 발견해 수정한 원인: 시험 암호화 스텁 누락, 주문자와 시험 요청자의 불일치, .NET 10 배열 Contains의 Span 오버로드가 EF 표현식 평가에 유입되는 문제. 실제 주문자 권한을 완화하지 않고 시험 자료/회귀를 보강했으며 DB 조회식은 명시적 Enumerable.Contains로 수정했다. 최초 공유 DTO 빌드 경합도 소스 동결 후 해소했다.

Migration은 결제 근거 두 열과 배치 두 테이블·참조/고유 제약만 추가하도록 검토했다. EF가 함께 제안한 기존 `driver_work_participation` 중복 생성과 unrelated rollback 열 변경은 제거했다. 현재 모델 snapshot에는 기존 r71의 수작업 migration에 있던 참여 모델도 동기화되며 기존 모델은 유지한다. 공용 DB에 적용하지 않았다.

## 실행 경계

실결제·환불·계좌 송금, 운영 ON, 클라우드 배포, 공용 DB 변경, APK 설치·배포/휴대폰 시험, Unity, commit/push는 실행하지 않았다. [기존 화주 검토 화면](http://127.0.0.1:5449/shipper/request/review?case=consented)은 로컬 r69 예시 실행이며 새 r73 결제/주간 명세 화면 완료나 실제 접수 증거가 아니다. 현재 브라우저 제어 표면이 없어 화면 캡처·시각 검수도 미실시다.
