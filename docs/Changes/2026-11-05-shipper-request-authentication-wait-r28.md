# 화주 인증 대기 중 계정이 바뀐 이전 요청 차단

2026-11-05. 화주가 내 의뢰를 조회하거나 접수 결과를 확인할 때, 토큰 갱신을 기다리던 이전 요청이 새 로그인 계정으로 이어지는 경합을 보완했다. 기존 화면·경로·공개 호출·DTO·계산·저장과 서버 권한은 유지한다.

## 발견과 최소 보완

기존 `AuthSession`에는 로그인 의도 취소·판본별 갱신/종료·직렬 저장과 복원 보호가 있다. 관리자 r26의 구현을 복사하지 않았다. 결함은 `AuthApiService`가 갱신 대기 뒤 현재 계정을 처음 읽고, `ServerBackedShipperOperationsService`도 인증/실시간 대기 뒤 현재 bearer를 다시 채택하던 경계다.

실제 두 Client와 기존 화주 Session을 연결한 합성 HTTP에서 원본8사례 중5실패/3통과를 재현했다. 다른 계정·동일 사용자 재로그인 뒤 이전 Ensure가 성공하고, 이전 접수 확인 GET/합성 동의 POST가 새 계정으로 나갔다. 새 계정의 토큰이 만료된 경우에는 이전 요청이 그 갱신/종료까지 실행했다. 정상 갱신·정상 첫 복원 대조 사례는 원본에서도 통과했다.

- 인증 API는 정상 장치 복원 뒤 원 세션 판본·사용자를 잡고 갱신 대기 전후에 확인한다. 대기 중 새 계정을 갱신하거나 지우지 않는다.
- 복원은 같은 인증 Service 안에서 직렬화한다. 중간 수정에서 발견한 첫 호출 취소의 전파도11사례 중1실패로 재현해, 다른 대기 호출이 자기 복원을 다시 시도하도록 보완했다. 여러 Service 인스턴스 전체의 취소 보장은 아니다.
- 업무 Service는 호출마다 같은 판본·사용자·토큰을 보관한다. 인증과 실시간 연결 대기 뒤에도 같은 계정인지 확인하고, 그 토큰으로만 요청을 만든다. 목록 내부 조회와 생성 payload의 화주 ID도 같은 문맥을 사용한다.
- 정상 갱신은 기존 SessionRevision을 유지하므로 계속 허용한다. 실시간 연결 실패의 기존 API 보완 조회, 익명 공개 화물 조회, 안전한 오류 안내·취소와401 비재전송을 보존한다. 결과 미확인 명령을 재송신하지 않는다.

화면에서는 계정이 바뀐 이전 작업을 중단하고 현재 계정에서 명시적으로 다시 조회한다. 페이지·ViewModel의 기존 늦은 응답/이탈 보호는 그대로다. 이번 보완을 최초 장치 복원 도중 계정 교체나 이미 전송한 모든 늦은 응답까지 해결한 것으로 확대하지 않는다.

## 검증과 재개

처음 수정의 관련168통과·중간 취소 회귀11중1실패·좁은 Fast171통과를 각각 보존했다. 첫 필수 Task는 비공개 mapper의 인자 수를 직접 가정한 기존 시험1개가 실패했다. 이를 실제 공개 `AddRequestAsync`와 합성 전송 본문 대조로 보완했으며 기존 화물/부피/취급조건 assertion을 보존하고 화주 ID/bearer 결속도 확인한다.
