# 기사 인증 토큰 저장 완료 뒤 화면 취소 r10

기사의 목록·상세 조회가 로그인 토큰을 갱신하는 동안 화면을 떠나면, 보안 저장은 새 토큰인데 실행 중인 앱은 이전 토큰을 계속 보유할 수 있었다. 다음 조회가 이미 교체된 이전 갱신 토큰을 다시 쓰는 원인이 된다. 화면·경로·서버 인증 계약과 업무 기능은 유지한다.

## 재현과 최소 수정

`DriverApp/Services/AuthSession.cs`는 저장의 정상 반환 직후 호출자 취소를 검사하고 나서 메모리를 갱신했다. 실제 보안 저장 연결의 `ClientAuthTokenJsonStore`는 쓰기 전에 취소를 확인하지만, 진행 중인 기기 쓰기 자체는 취소하지 않는다. 따라서 쓰기가 끝나는 순간 화면 취소가 도착하는 경합이 가능하다.

새 합성 회귀 9사례 중 수정 전 3개가 실패하고 6개가 통과했다. 저장 완료 뒤 취소된 직접 로그인·토큰 갱신과 HTTP 후속 조회에서 저장/메모리 불일치를 확인했다. 저장이 정상 반환한 경우에만 기존 메모리·판본·변경 알림을 먼저 확정하고 취소를 호출자에게 알리도록 검사 한 줄의 위치를 옮겼다. 저장 전 취소·저장 실패의 기존 상태 보존, 판본 비교와 잠금, 로그인/갱신의 서로 다른 세션 판본 규칙은 그대로다. 다른 앱의 인증 구현을 복사하거나 자동 재전송을 추가하지 않았다.

## 검증과 남은 범위

- Fast `20261104-200810`: 신규 9사례를 포함한 인증·경로·내역 회귀 81/81 통과, 실패·생략 0. 소비 기사 앱 빌드 오류 0/기존 경고 65, 시험 의존 빌드 오류 0/기존 경고 229.
- Task `20261104-200924`: 통합 빌드 오류 0/기존 경고 60, 전체 16,928 통과·환경 17생략·실패 0. 실제 TRX 결과를 확인했으며 이전 판본의 숫자를 승계하지 않았다.
- APK139를 새 출력에 1회 포장했다. 선택 입력 3,605개 전후 변경 0, 같은 서명·두 ABI의 내장 앱 DLL·5378 주소를 확인했다. 포장 오류 0·경고행 52이며 고유 경고 수와 구분한다. APK SHA는 `4ca38cbcc64c7348074b7b518f55d2233deb670b396edb5db2f804251eccfca5`, 앱 DLL SHA는 `09c55e8f11d4ce70b478fef9482a51242fe77a8f5bfad9c7cf6bb05ecb83e25a`다. 기존 APK138과 이전 실패/정상 출력은 보존했다. 139는 미설치다.
- 같은 소유 r6 호스트의 현재 PID·부모·시작 시각·명령·두 DLL 해시와 기존 격리 DB를 대조했다. 전후 대상 HTTP는 각각 5/5가 200이며 업무 proof 2개는 불변·금융 행은 0이다. 호스트/DB 재시작이나 실제 인증 갱신·업무 명령은 실행하지 않았다. 이번 정상 조회로 과거 모든 503의 해결을 선언하지 않는다.
- 등록 휴대폰의 설치 APK138 바이트가 이전 서명/설정 검증본과 같음을 읽기로 확인했다. 현재 전면은 배민 내역이고 수집 checkpoint가 미완료이므로 전면·자료를 보존했다. 기존 기사 직접 로그인 질문도 그대로 대기한다. 새 수정의 실제 보안 저장·기기 조회/복귀는 미검증이며 합성 HTTP 시험과 구분한다.

재개 기록은 `artifacts/local/app-stability-r10/e9102efba88641d9acb4c753b3772ea3/completion.json`이다. `reproduction/`의 원래 소스·실패 TRX, 현재 Fast/Task TRX·로그, 소스 결속, 서버 전후 관측과 기기 읽기 근거를 보존한다. 쓰기 결과가 불명확한 저장 예외나 실제 서버의 토큰 회전까지 해결했다는 뜻은 아니다.

다음은 다른 기기 작업과 인증 대기가 해소됐을 때 준비된 139의 데이터 보존 업데이트 후 내역 조회·이탈/복귀를 확인하는 것이다. 설치 전 기기·현재 소스/139·서명/endpoint·같은 서버를 다시 대조한다. 앱 전체 안정화·원격 운영·출시 완료는 아니며, 배달 수집·실제 배차/운행·금융·배포·commit/push는 실행하지 않았다.
