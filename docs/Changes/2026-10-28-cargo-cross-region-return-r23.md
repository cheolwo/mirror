# 서울·경기 이동과 귀가 방향 추천 검증 r23

2026-10-28. [검증 범위](../AI/Planning/공통/PLAN-OPERATIONS-DISPATCH-CORE/cargo-cross-region-return.verification.r23.md)에 따라 현재 소스와 서버 계산을 확인했다. 제품 기능·운영 설정은 바꾸지 않고 기존 r20~r22 변경37개를 보존했다. 새 회귀 파일1개와 검증 문서만 추가했다.

## 먼저 확인된 결론

행정구역 이름으로 서울 밖의 후보를 배제하는 화물 추천 조회 조건은 없으며, 현재 위치/검색 중심과 상차 좌표의 거리를 사용한다. 그러나 이 조회는 이미 해당 기사의 추천 대상으로 배정된 원장만 대상으로 한다. 조회 계산 통과는 새 콜 발행·전용 배정·실시간 전달 성공을 의미하지 않는다.

복귀 우대는 고정한 비공개 기준점까지 **기존 전체 일정 종료 후 복귀 거리**와 **후보를 넣은 전체 일정 종료 후 복귀 거리**를 비교한다. 거리가 줄면 최대20점을 더하며 멀어지면0점이다. 실제 도로 응답 여부·위치 신선도·차량/적재·시간 적격성을 확인하지 못하면 가점을 보류한다. 자동 모드는 귀가 시각이 아닌 기준점과의 거리(기본7km 진입/6km 해제)로 활성화된다.

따라서 현재를 ‘서울→경기에서도 콜을 끊김 없이 받고 정한 귀가 시간까지 집에 돌아오는 흐름 완성’으로 판정할 수 없다.

## 현재 부족한 연결

| 항목 | 현재 소스에서 확인한 내용 |
| --- | --- |
| 개인 귀가 마감 | 화물 기사 운행/복귀 설정에 개인 귀가 희망시각이 없다. 한국시간대별 부담 점수와 개인의 귀가 도착 보장은 다른 조건이다. |
| 전문 기사 앱 설정 | `/driver/work/settings`는 업무·차량·적재·추가배차 입력이며, 복귀 우대 설정 API를 여는 전문 앱 화면 연결이 확인되지 않는다. 음식 기사 앱의 별도 화면과 구분한다. |
| 추천 이유 표시 | 현재 native 추천 상세는 복귀 사유·가점·복귀 거리 개선을 표시하지 않는다. 구형 추천 dialog에 있는 필드를 현행 화면 검증으로 대신할 수 없다. |
| 고정20/50km 활동권역 | [r3 설계](../AI/Planning/공통/PLAN-OPERATIONS-DISPATCH-CORE/cargo-map-first-workloop.design.r3.md)에 남아 있다. 현재 추천목록20/50km는 현재GPS→상차지의 화면 필터이며 집 중심 hard limit가 아니다. |
| A 수행 중 다음 복귀콜 | 현재 복귀 가점 적격성은 미완료 화물 일정이 없는 단독 후보에 한정한다. A 종료 직전의 B에 항상 복귀 방향 가점이 붙는다고 볼 수 없다. |
| 설정 변경과 기존 제안 | 화물 상태 지문/수락 적격성에 복귀 설정Revision·기준점 재대조 연결이 확인되지 않는다. 추천 뒤 귀가 설정 변경 시 기존 제안을 자동 무효화한다는 보장이 없다. |
| 좁은 픽업 접근 한도 | 기본 검색반경 안이면 먼저 허용하는 경로가 있어 기사 설정으로 기본보다 좁히는 강제 한도로 해석할 수 없다. |
| 늦은 픽업 | 대기 중 추천 조회는 늦은 후보를 불가/경고·가점0으로 남길 수 있으며, 수락과 큐의 적격성 검사는 별도다. 추천 화면에 보인다는 사실과 수락 가능을 합치지 않는다. |

순차 왕복은 미리 등록된 추천 후보의 재조회다. 수락·실제 운송 완료·새 콜 발행·인증 세션·설정 저장 API·재시작 영속성을 시험하지 않는다. [추가 시험 소스](../../Ssalddel.Tests/Services/Dispatch/Recommendation/CargoCrossRegionReturnR23Tests.cs)의 모의 도로 제공자는 거리×1.2·분당계산을 사용하는 명시적인 합성 응답이며 실제 도로 통과/교통/ETA 증거가 아니다.

기존 서비스·메모리 DB·합성 좌표/모의 도로 응답의 실행과 실제 인증HTTP·NAVER 도로API·운영DB·휴대폰/GPS·FCM·실운행을 구분한다. 이번 새 휴대폰 화면 검증은 수행하지 않았다. [r22 실제 기기](2026-10-27-cargo-ordered-map-device-r22.md)는 다른 시나리오의 과거 결과다.

## 다음 보완 순서

1. 기존 본인 복귀 설정API를 전문 기사 앱의 저장·재조회와 연결하고, native 제안에 기준점 공개 없이 복귀 거리 개선·가점 적용/보류 이유를 표시한다.
2. 집·지정 거점의 고정 활동반경과 현위치의 픽업 접근 한도를 분리한다. 개인 귀가 도착시각을 입력받는다면 기존 업무·상하차·최종 복귀까지 예상 시간을 같은 서버 적격성 관문에 넣어야 한다.
3. 기존 업무를 마칠 무렵의 다음 제안과 진행 중 복귀 우대의 구간 적재 검증을 연결하고, 설정 판본/기준점이 바뀐 이전 제안을 재검사한다. 같은 시나리오를 새 격리HTTP/DB와 최신 APK에서 검증한 뒤 실운행으로 확인한다.

이는 확인된 결손에 따른 후속 범위이며 이번에 구현·활성화한 기능이 아니다. 적격한 귀가 방향 수요가 없을 때는 없는 상태와 직접 복귀 필요를 표시해야 하며, 항상 복귀콜을 확보한다고 약속하지 않는다.

원시 로그·기준선·시나리오/소스 대조와 `client-audit.md`, `verification-summary.json`은 `artifacts/local/cargo-cross-region-return-r23/`에 보존한다. 사용자 위치·귀가 기준점·실제 고객 주문은 넣지 않았다. commit/push·배포·운영 활성화는 수행하지 않았다.
