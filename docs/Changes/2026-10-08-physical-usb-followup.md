# 실제 휴대폰 USB 후속 검증과 위치 복구

사용자가 USB 연결 후 미완료 검증을 이어가도록 요청했다. Samsung SM-N981N(Android 13/API 33)의 ADB 인증과 USB 5363 연결, 격리 서버 준비 상태를 다시 확인했다. 이 r29 기록 당시 단말은 잠금 화면이었다. 이후 잠금 해제 후 완료 내역·메뉴 저장/원복·앱 복귀·연결 복구를 확인한 [실제 휴대폰 후속 결과](2026-10-08-physical-phone-runtime-r31.md)를 현재 상태로 참조한다. 잠금 설정과 앱 자료는 변경하지 않는다.

기존 [음식 네 역할 페이지 책임](../ProjectOverview/page-docs/food-mobile-four-role-r27.md), [페이지 단일 책임](../Architecture/WholeRoadmapPagePrinciple.md), [역할 앱 시각 기준](../Architecture/RoleAppVisualDesignStandard.md)을 따른다. 기존 네 역할의 수락 이후 휴대폰 시험은 [10월 7일 기록](2026-10-07-physical-phone-naver-maps.md)이며, 이번 신규 주문 작성·복귀·통신 복구 시험 완료로 재사용하지 않는다.

## 이번에 확인한 사실

| 대상 | 이번 결과 |
| --- | --- |
| 단말·서버 | 실제 단말 연결 인증, USB 역방향 연결, 로컬 `/health/ready` 200 확인 |
| 설치 앱 | 시작 시 기사·음식점 `0.1.28/28`, 주문자·운영자 `0.1.27/27` 확인 |
| 기존 완료 주문 | `FOOD-20261007063023875`의 SQL/Mongo 상태·식별자 검사 12개 통과. SQL 수령확인/배달완료, Mongo 음식 주문·운송 완료, Revision 각각 9/9·4/4 |
| 정산 | `AwaitingDeductions`·`NotRequested`, 공제·수령액 null, 지급 검증 0건. 실제 입금이 아님 |
| 새 휴대폰 화면 시험 | 잠금 해제 대기. 새 주문 작성·앱 복귀·통신 복구·완료 내역·메뉴 수정·문제 접수는 아직 실행하지 않음 |

읽기 조회는 여러 쿼리로 수행되어 원자적 DB 스냅샷은 아니다. 기존 시험 서버·DB를 초기화하거나 기존 주문을 다시 생성하지 않았다. 원시 근거는 Git 제외 `artifacts/local/physical-usb-r29-20261008/`에 보관한다.

## 위치 안내와 복구 보완

기사 앱의 공통 ‘위치 권한과 GPS’ 안내가 권한 거부 외에도 위치 미수신·오래된 값에 표시되는 문제를 보완했다. 기존 지도·현재 배달 카드·주 행동·글자 크기와 배차 조건을 유지하면서 원인별 안내만 구분한다.

- 권한 부족, 휴대폰 위치 기능 꺼짐, 확인 중, 수신 지연, 오래된 위치, 센서 실패를 별도 상태로 표시한다.
- 리스너가 실행 중이어도 최근 위치가 없으면 새 위치를 조회한다. 동시 요청은 하나를 공유하며 개별 호출 취소와 전경 수명 종료를 구분한다.
- 조회 실패 뒤 자동 재조회는 60초 제한을 적용한다. 사용자 재확인·앱 재개는 즉시 다시 확인한다. 유효 위치의 서버 heartbeat는 유지한다.
- 기존 30초 신선도와 미래 시각 5초 허용 범위를 유지한다. 중단·계정 변경 이후 늦은 응답과 늦게 시작된 native 리스너는 적용하지 않거나 정리한다. 오래된 위치를 서버로 보내지 않는다.

제품 6개는 `FDriverApp/Services/IFDriverLocationService.cs`, `FDriverLocationService.cs`, `PageModels/MainPageModel.FoodMap.cs`, `MainPageModel.cs`, `MainPageModel.FoodPresentation.cs`, `Pages/MainPage.xaml`이다. 새 `FDriverLocationRecoveryTests` 25개와 기존 대기 문구 기대를 포함한 최종 Fast는 **206/206 통과**, 기사 제품 빌드 오류 0개다. 기존 플랫폼 경고 12개가 남았으며 이번 nullability 경고는 제거했다.

회귀 시험은 연결된 화면 모델과 신선도 정책을 검증한다. Android 센서 자체의 수신 안정성·권한 거절·위치 기능 끄기·실내 무신호·백그라운드/복귀는 실제 휴대폰 확인 대상이다. 현재 이 화면 문구는 소스·바인딩·빌드의 간접 확인이며 새 화면 캡처는 대기 상태다. 테스트 좌표를 실제 단말에 주입하지 않았다.

## 일반 음식 주문 원장 읽기 표시 보완

같은 완료 주문의 Mongo 음식 블록은 `수령확인`이지만 기존 root 요약의 현재 단계는 `픽업대기`였다. 요약 완료 여부만으로 종료를 표시하면 기사배정·픽업대기도 조기에 종료로 보일 수 있으므로, 권한이 확인된 음식 원장의 정확한 음식 블록 상태를 조회 표시 근거로 사용한다.

새 `Ssalddel/Services/Community/FoodOrderLedgerReadPresentation.cs`와 기존 역할별 상세/개별 주문 목록 조회 두 경로에서 표시용 root DTO를 복사한다. `전달완료`는 진행 중으로, `수령확인`만 완료로 표시하고 취소·거절은 닫힘으로 구분한다. 정확한 템플릿·블록 ID·블록 유형·지원 상태가 아니거나 블록이 중복되면 기존 결과를 보존한다. 공동 원장 참가자라는 이유만으로 비공개 음식 상태를 새로 노출하지 않는다.

저장된 Mongo 문서·RDB 업무 상태·권한·ID·Revision·수정 시각·JSON 구조·이력·다이어그램은 변경하지 않는다. 하위원장 변경 명령은 기존 권한 결과와 저장소 재조회로 처리하며 보정된 단계로 업무 허용 조건을 판정하지 않는다. 관련 회귀 **35/35 통과**, 서버·시험 빌드 성공, 독립 검토에서도 현재 범위의 차단 문제 없음이다.

이 보완은 현재 소스의 읽기 경로에 적용했다. **실행 중인 r27 Docker 서버에는 아직 반영하지 않았다.** 따라서 현재 휴대폰이 새 일반 원장 표시를 받는다는 주장은 하지 않는다. 전역 Mongo 요약·상태 이력·다이어그램·세계 집계의 기존 의미도 이번에 수정하지 않았으며 모두 일치한다고 보고하지 않는다.

## APK와 전체 검증

기존 frozen r27 소스는 보존하고 별도 기사 프로젝트 사본에 승인된 위치 제품 6개만 결속했다. 이 APK에는 일반 원장 서버 보완이나 다른 작업트리 변경을 포함하지 않는다. 네이버 Client ID는 저장소 밖 기존 파일에서 빌드 환경으로 전달하며 Client Secret을 넣지 않는다.

신규 기사 `0.1.29/29`를 기존 Debug 서명으로 포장했다. APK SHA-256은 `e62074c9a3e53bd802b5102475f117016a9c574ed8608611f126be4b06f3d202`다. arm64-v8a/x86_64의 실제 내장 어셈블리에서 USB 5363 대상·위치 상태·늦은 리스너 정리·화면 바인딩 속성을 확인했다. source-before/after와 frozen 원본 2,610개 파일을 대조했으며 승인한 제품 6개 외 소스 변화가 없다. 새 저장소 없는 사본에서 기존 publisher의 PlanOnly·공통 빌드/검증 helper를 사용했고 live publisher 전체 실행으로 보고하지 않는다.

최종 Task는 13개 소스/시험 경로를 지정했지만 현행 도구 계약상 전체 `Ssalddel.v3.5.slnx` 빌드와 전체 시험을 수행했다. **8,589개 통과·실패 0·기존 환경 조건 Mongo 2개 건너뜀**, 빌드 오류 0·경고 69개다. 검증 전후 해당 13파일 지문은 일치한다. 근거는 `artifacts/local/validation/20261008-004743/`와 `final-task-result.json`이며, TRX의 건너뜀 counter가 0이어도 실제 결과 항목과 로그의 2개 SKIP을 그대로 보고한다.

실제 휴대폰의 기존 기사 `0.1.28/28`을 `0.1.29/29`로 덮어 설치했다. 설치 성공과 단말 `base.apk` SHA-256·판본이 준비한 APK와 일치함을 확인했다. 앱 삭제·자료 초기화·서명 불일치 자동 제거를 하지 않았다. 첫 설치 사전 확인은 조작 도구의 배열 정규식 판정 오류로 설치 전에 중단했으며 실패 기록을 보존하고 문자열 판정으로 수정했다. 실제 설치 실패나 단말 판본 변경으로 해석하지 않는다.

단말은 마지막 확인에서도 잠금 상태였다. 새 APK의 화면 실행·GPS 수신·복귀·서버 통신은 아직 확인하지 않았고, 기존 APK의 이전 화면 성공을 새 APK 검증으로 재사용하지 않는다. 원시 근거는 `apk/build-result.json`, `driver-r29-install-result.json`, `driver-r29-installed-bytes.json`이다.

## 이어서 할 휴대폰 확인

1. 주문자 새 주문 작성과 반복 제출 방지, 음식점 수락 전 취소. 시험 음식점 101/메뉴 10101을 사용하며 배달 주소는 `모바일 음식 배달 시험 수령지` 한 필드를 직접 입력해야 한다. 기존 APK에 주소 자동 입력 기능은 없다.
2. 완료 배달 목록→상세→복귀, 배달료·거리·문제 접수와 현재 고객 정보 표시. 3일 만료 경계는 기존 최근 주문만으로 완료한 것으로 보지 않는다.
3. 앱 백그라운드·복귀·재시작과 격리 서버 연결 끊김·복구, 중복 업무 명령 방지.
4. 음식점 기존 시험 메뉴의 가격/품절 수정·저장·재조회·정확 원복, 운영자 지원 사건 조회.
5. 위치 보완 APK의 실제 수신·재확인·복귀와 일반 원장 서버 보완 반영 후 목록/상세 표시.

홈의 생활·주문자·음식점·음식기사·화주·화물기사·창고·운영자 8역할은 APK 8개와 같지 않다. 현재 바로 이어갈 자료는 네 음식 역할 앱이다. 생활/화주 옛 통합 APK와 화물기사/창고 포장 시험 APK는 현재 서버·계정·자료를 먼저 결속해야 하므로 USB 연결만으로 완주 가능 상태가 아니다.

Azure·실제 도로 Directions·실운행·실제 결제/입금·commit/push는 이번 범위에 포함하지 않는다.
