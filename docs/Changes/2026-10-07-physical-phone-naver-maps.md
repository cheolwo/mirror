# 네이버 지도 연결과 실제 휴대폰 USB 시험

사용자가 로그인한 네이버 클라우드 콘솔의 기존 `hongdal` 앱에 음식 기사 앱 패키지 `kr.ssalddel.fdriver`를 추가했다. 기존 `kr.hongdal.driver`, 선택된 API, 사용량 한도는 보존했다. 저장 후 다시 연 설정과 실제 Android 휴대폰의 네이버 지도 표시를 각각 확인했다.

이번 범위는 본인 휴대폰과 격리된 로컬 `Simulation` 서버다. 애저 배포·실제 주문·은행 지급·실제 도로 경로까지 완료했다는 의미가 아니다. 같은 작업트리의 다른 변경은 보존하며 commit/push는 수행하지 않았다.

## 지도와 인증 정보

- 기존 Dynamic Map을 이용하며 새 API 활성화나 키 재발급은 하지 않았다. 네이버 콘솔 등록 후 저장된 두 Android 패키지를 다시 확인했다.
- Client ID만 저장소 밖 `C:\Users\user\Documents\지도설정\naver-mobile-client-id.txt`에 보관하고, 기존 음식 기사 빌드 설정에 비공개 환경 변수로 전달했다. Client Secret은 모바일 앱에 복사하거나 저장하지 않았다.
- 음식 기사 Debug APK `0.1.28/28`은 기존 디버그 서명으로 덮어 설치했다. 원래 계정·앱 자료를 지우거나 서명이 다를 때 제거하는 동작은 하지 않았다.
- Samsung SM-N981N, Android 13/API 33에서 실제 네이버 지도 타일과 현재 위치 표시, 배차 대기 화면을 확인했다. 현재 위치가 보였다는 사실을 GPS 정확도나 실운행 경로 검증으로 확대하지 않는다.
- 실제 도로 경로 API 연결은 이번 지도 SDK 인증과 별개다. 기존 시험 서버의 `0.350km`, `IsEstimated=true`, `ActualMapRequest=false`를 보존했다.

공식 기준은 [Maps 앱 등록](https://guide.ncloud-docs.com/docs/maps-app)과 [Android SDK 시작](https://navermaps.github.io/android-map-sdk/guide-ko/1.html)을 대조했다. 앱 인증은 패키지 등록과 SDK의 NCP Key ID 연결로 확인했다.

## 네 역할과 음식점 시험 설정

격리 서버 `mirror-r27-food-mobile-check`의 기존 MySQL/Mongo 자료를 초기화하지 않고 재사용했다. PC의 `127.0.0.1:5363`과 휴대폰의 같은 포트를 USB로 연결했다. 음식 기사·주문자·음식점·운영자 앱의 실제 로그인 상태와 서버 주문 조회를 각각 확인했다. 기존 APK 설치 결과와 새 APK 결과는 구별한다.

음식점 APK는 일반 파일 출력 설정이 Android 패키지 내부 설정으로 자동 들어가지 않아, 로그인은 성공해도 주문 수락에 매장 기본값이 사용되는 문제를 정적으로 확인했다. 기존 서버의 시험 음식점 제한을 느슨하게 바꾸지 않고 아래 세 경로에 기본 비활성 시험 옵션을 추가했다.

| 경로 | 책임 |
| --- | --- |
| `RestaurantDeskApp/RestaurantDeskApp.csproj` | 정확한 합성 자료 판본을 명시한 Android Debug 빌드에만 메타데이터 포함 |
| `RestaurantDeskApp/MauiProgram.cs` | 명시 판본과 HTTP 루프백 5363의 루트 주소가 모두 맞을 때만 시험 음식점 101 설정 연결 |
| `eng/release/publish-mobile-usb-test.ps1` | 기본 OFF인 `UseRestaurantFoodTestFixture`를 음식점 역할에만 전달하고 잘못된 대상 거절 |

Release·미지정·다른 판본·다른 포트·HTTPS·외부 호스트·경로·인증 정보·query/fragment에서는 기존 매장 설정을 유지한다. 운영 매장 등록·실제 계정 권한이나 서버의 업무 상태 관문을 대신하지 않는다. r27 동결 소스는 보존하고 새 선택 프로젝트 소스 사본에서 음식점 후속 APK `0.1.28/28`을 빌드·설치했다. 새 사본 2,539파일과 동결 원본의 지문을 대조했다. 첫 리소스 누락 빌드 실패는 보존하고 프로젝트에 명시된 두 JSON 리소스를 결속한 뒤 재빌드했다.

## 같은 주문의 실제 휴대폰 처리

이전 PC 공통 화면 시험에서 만든 미접수 주문 `FOOD-20261007063023875`를 사용했다. 이번 휴대폰에서 새 주문을 작성했다는 의미는 아니다. 네 역할의 로그인·수락 이후 처리·완료 조회를 같은 격리 서버/DB에서 확인했고, 정산 지급 행동은 실행하지 않았다.

| 휴대폰 행동 | 화면·서버에서 확인한 결과 |
| --- | --- |
| 음식점 주문 확인 | 시험 음식점 101의 이름·주소·좌표가 일치하고 배차 대기로 전환. 기사 배정 전에는 조리 시작 버튼 없음 |
| 기사 배차 수락 | `기사배정`, 같은 주문의 수행 시도 1개. 실제 지도에 주황색 픽업·파란색 전달 핀 표시 |
| 음식점 조리 시작·픽업 준비 완료 | 기사 배정 뒤 조리 버튼 표시. `조리중` → `픽업대기` 이력 기록 |
| 기사 가게 도착·픽업 완료 | 픽업 전 음식점 카드에서 픽업 후 전달지·고객 요청·수령인 카드로 전환 |
| 기사 전달 완료 | `전달완료/배달완료`. 주문자 수령 확인은 아직 없고 정산 원장은 `AwaitingReceipt` |
| 주문자 음식 수령 확인 | `수령확인`, 전달 시각과 별도의 수령 시각 기록. 주문자 화면에 양측 확인 완료 표시 |
| 운영자 같은 주문 상세 조회 | 주문 종료와 단계별 완료 표시. 배달료 2,500원, 공제/수령액 미확정·입금 전 표시 |

최종 SQL 조회는 수행 시도 1개·운송 의뢰 1개·정산 원장 1개를 동일 식별자로 연결했다. 정산은 `AwaitingDeductions`, 지급은 `NotRequested`, 공제와 수령액은 null이며 금융 확인 횟수는 0이다. 실제 금전 지급·은행 입금을 완료한 것으로 표시하지 않는다. 이번 추가 시험의 Mongo 단계별 투영 대조는 수행하지 않았으며 이전 r27의 결과와 구별한다.

초기 주문자 수령 버튼 자동 조작은 스크롤 영역 아래의 접근성 좌표를 사용해 음식 홈으로 이동했고 수령을 처리하지 못했다. 이름이 `orderer-receipt-confirmed-defe7fb9.png`인 첫 캡처는 성공 근거가 아니다. 초기 결과를 보존하고 현재 보이는 영역을 확인한 뒤 다시 실행했다. 최종 근거는 `orderer-receipt-confirmed-verified-79c2e8e9.png`와 같은 주문의 수령 확인 SQL 기록이다. 전용 조작 도구에는 0 크기·스크롤 밖 좌표 거절을 추가했다.

## 현재 검증과 근거

- 지도 SDK 포함·비공개 Client ID 자원 일치·기존 서명 일치·빌드 소스 전후 지문 일치를 확인했다.
- 음식점 시험 설정은 기존 포장 검사 20개·새 opt-in/메타데이터 검사 8개·실제 초기화 블록 guard 검사 40개를 통과했다. 변경 세 경로의 Fast는 소비 앱 빌드와 관련 79개 시험을 통과했다. 현재 검증 도구의 Task 계약은 세 경로를 지정해도 전체 3.5 빌드·전체 시험을 선택하며, 8,540개 통과·실패 0·환경 조건 Mongo 2개 건너뜀을 확인했다.
- 독립적인 세 파일 읽기 검토에서도 출시·원격·다른 역할로 시험 설정이 자동 적용되는 문제는 발견하지 못했다. 루프백 포트 조건 자체는 서버 정체 인증이 아니므로 현재 확인한 격리 서버 연결 범위로 한정한다.
- 지도 연결은 실제 휴대폰의 타일·현재 위치·배차 대기·주황/파랑 핀까지 확인했다. 경로는 `현재 목적지 경로 대기 중`이며 실제 도로를 따르는 선이나 이동 거리까지 검증한 것으로 확대하지 않는다. 활성 지도 캡처에는 전달 핀 일부가 상단에 걸쳐 있어 모든 핀의 화면 맞춤까지 완료한 주장이 아니다.
- 마지막 배차 대기 재확인에서는 정상 대기와 `위치 권한과 GPS를 확인해 주세요`/`위치 다시 확인` 안내가 간헐적으로 바뀌었다. 위치 모드 3·정밀/대략 위치 권한은 켜져 있었고 앞선 캡처의 현재 위치 표시도 확인했지만, 계속 안정적으로 좌표를 받는 상태까지 검증하지 않았다. `driver-naver-map-final-stable-3de3ba01.png`는 파일명과 달리 이 안내가 있어 안정성 성공 근거로 쓰지 않는다.
  - 위치 서비스·화면 모델의 읽기 점검에서 이 문구는 권한 거부뿐 아니라 위치 미수신/예외, 앱 재개 시 초기화, 30초 지난 위치에도 사용하는 공통 안내임을 확인했다. 새 위치 수신 시 다시 대기로 돌아간다. 이번 단말의 구체적인 미수신 원인은 확정하지 않았으며 안내 자체를 네이버 인증 실패나 정확도 문제로 단정하지 않는다.
- 최종 설치 바이트는 기사·음식점 `0.1.28/28`, 주문자·운영자 `0.1.27/27` 네 개 모두 준비한 APK SHA-256과 일치한다. 현재 실행 중 네 프로세스의 로그 버퍼에서 치명 오류 표식 0, 기사 네이버 인증 실패 표식 0을 확인했다. 전체 시간의 모든 오류 부재나 모든 업무 예외의 성공을 보장하는 결과는 아니다.
- 원시 `physical-verification.json`, `installed-packages-final.json`, `final-app-log-check.json`, 단계별 PNG/XML·읽기 전용 SQL 스냅샷을 보존했다. 관리자 최종 화면은 `admin-completed-order-receipt-detail-963d6cc5.png`다.
- 원시 기록은 Git 제외 `artifacts/local/physical-usb-r27-20261007/`, 기사 빌드 기록은 동결 소스 사본의 `artifacts/local/physical-navermap-20261007/`에 보관한다. 화면에는 본인 현재 위치가 있어 저장소의 공개 문서 자산으로 복사하지 않는다.
- UI 구조·디자인 변경 없음. 기존 화면을 실제 휴대폰에서 확인한 간접 변경 기록이며, 브라우저 콘솔 캡처·휴대폰 캡처·APK 해시·서버 상태는 별도 근거로 보관한다.

실제 도로 Directions·Azure HTTPS·실제 판매자 신원·실결제/입금·다른 역할의 지도 SDK 연결은 별도 확인 대상이다.
