# 로컬 서버의 음식 배차에 Ollama 후보 선택 연결 r48

사용자가 사후 사례 검토를 넘어 AI의 후보 선택을 실제 배차 수행 경로에 연결하도록 요청했다. [승인 설계](../AI/Planning/공통/PLAN-OPERATIONS-DISPATCH-CORE/candidate-application.implementation.r48.md)와 [현재 스레드 작업 명세](../AI/Planning/공통/PLAN-OPERATIONS-DISPATCH-CORE/candidate-application.r48.work-order.json)에 따라 기존 음식 추천 서비스에 연결하고 격리 SQLite에서 실제 모델 선택과 추천 저장을 확인했다. 제품 호스트 실행·외부 운영 배포·기사 수락과는 별도다. 화면 변경 없음.

## 변경 범위

- 서버 DI가 새 `IFoodDispatchCandidateAI`와 typed Ollama 서비스를 음식 후보 정책에 연결한다. 기존 관리자 사례 검토의 샘플·설명 저장은 이 실행 입력이나 배차 권한으로 사용하지 않는다.
- 모델은 서버가 허용한 후보 안에서 임시 토큰만 선택한다. 현재 최종 허용 집합·같은 픽업 단계·최신 수요 우선권을 유지하며 실제 기사/주문 ID·상세 주소를 전송하지 않는다. 대기 보정 점수는 실제 대기 분으로 해석하지 않는다.
- 응답 뒤 실제 후보를 다시 평가한다. 후보 선정 서비스의 현재 원장 조회와 추천 저장 직전 원장 재조회가 상태 변경을 보호한다. 원장이 달라지면 새 추천이나 후보 없음 재탐색으로 덮어쓰지 않는다. 직접 기사 지정으로 이 검사를 우회하지 못한다.
- 무효 응답·지연·연결 실패는 현재 엔진 기준 후보로 돌아가고 고정 `FoodDispatchAI.*` 상태만 기존 추천 사유에 남긴다. 호출자 취소와 현재 저장소 재조회 실패는 정상 추천으로 숨기지 않는다. 한 업무 요청의 모델 자동 재시도는 없다.
- 기존 추천·요금 동결·수신 의사·동시성·감사 저장과 기사 제안/수락 흐름을 재사용한다. 새 API·공개 contract·DB schema·화물/생활 배송·UI·Unity는 변경하지 않는다.

## 설정과 실행 경계

`FoodDispatchOllama`의 공유 기본값과 예시 설정은 OFF다. 이번 PC의 Git 제외 `Ssalddel/appsettings.Local.json`에만 `Enabled=true`, timeout 10초를 명시했다. 로컬 파일은 컨테이너·Testing 환경 밖에서 읽으며 환경 변수·명령행이 이후 우선하므로 파일 값만으로 실행 중 호스트의 유효 설정을 인증하지 않는다. 이번에 제품 호스트를 시작하지 않았다.

endpoint는 명시적 포트가 있는 HTTP 루프백 IP만 허용한다. 현재 연결은 기존 Docker의 `127.0.0.1:12681`, 모델은 `qwen3:1.7b`다. proxy·redirect·외부 호스트·다른 모델·도구 호출·외부 프로세스 시작을 허용하지 않는다. timeout 기본 10초/범위 1~90초, 후보 기본 12명/범위 2~30명이다. 제품 DI의 `ValidateOnStart`는 유효하지 않은 호스트 설정을 시작 단계에서 차단한다. 클라이언트를 직접 호출하는 경우의 `InvalidConfiguration`·기존 후보 복귀는 이 호스트 시작 검증과 별도다. 실제 검증의 timeout 90초와 PC 로컬 기본 10초를 구분한다.

새 실행 도구는 기본 실행에서 추론·배차를 하지 않는다. 명시적 실제 검증 요청에만 별도 r48 예산을 먼저 예약하고 격리 DB의 실제 추천 서비스를 호출한다. 실패·중단도 시작 시도에 포함하며 누적 최대 2회다. 외부 알림은 시험 전용 경계에서 억제한다. 기존 r47의 4회·r46의 36회 예산을 다시 열지 않는다.

## 실제 모델 적용 결과

별도 실행의 모델 요청은 1회이고 누적 시작 시도는 1/2다. 두 번째 모델 호출은 하지 않았다. 실제 추천 서비스·격리 SQLite 생성/저장/재조회를 포함한 전체 실행 시간은 8.923376초이며 순수 추론 지연이나 반복 성능 측정으로 표현하지 않는다. 실제 도구의 timeout은 90초였으므로 전체 시간이 10초보다 짧았다는 이유로 제품 호스트의 10초 설정까지 검증했다고 확대하지 않는다.

모델은 기존 엔진과 같은 합성 기사 `application-older`를 선택했다. 기존 엔진에서도 대기 보정 점수 100인 이 기사가 기준 후보였고, 모델 응답이 검증된 뒤 `FoodDispatchAI.Applied` 사유로 추천 저장에 반영됐다. 엔진과 다른 선택, 최적성·정확도·공정성 향상이나 r47의 품질 한계 해소를 입증한 사례는 아니다.

4,000원은 시험용 `ApplicationPricingPort`가 반환한 고정 요금을 기존 추천 저장 함수가 동결한 결과다. 실제 거리 API나 실제 요금 엔진의 계산을 검증한 금액은 아니다. 실행 근거는 `artifacts/local/local-dispatch-ai/candidate-application-r48/runs/20261011T061842Z-6f2e87e0/result.json`과 같은 폴더의 격리 `dispatch.sqlite3`다. 호출 전 예약은 `attempts/attempt-001.json`으로 보존한다. 실행 전후 서버/시험 소스 8개의 해시가 일치하며 설계 SHA-256은 `de7a226c18c62d93c537dab4975014fc38f6b232002c68cbf14bb3e7497fff6c`다. 이는 비공개 로컬 증거이고 저장소 게시 자산이 아니다.

실행 결과 SHA-256은 `e08973a42e5cd216ec8e56e9e564713ad0f43b87ada8755d578722300c4fe83d`, 호출 전 예약 SHA-256은 `cc42f28007d246c264b2de1352062466986cb82476e7c6eaf80a2d1e5cf69031`이다. 원본 실행 근거와 승인 설계는 후속 문구 보완으로 바꾸지 않는다.

## 이력과 남은 확인

r47의 도구·규칙·입력·원응답·최초 1개 통과/3개 복귀·최종 0개 통과/4개 복귀와 r46의 실행 이력을 보존한다. 공유 후보 정책이 r48에서 변경돼 과거 근거의 소스 해시가 현재 검사에서 만료되는 것은 정상이다. 과거 해시나 소진 예산을 새 상태로 덮어쓰지 않는다.

약 4건/h는 사용자 계획 가정이며 현재 기본 3.5건/h를 바꾸지 않았다. 시간대 가점과 마지막 전달지 기반 다음 픽업은 후속 제안으로 유지한다. 현재 수요·여력과 픽업 관문 안에서 장기 대기 기회를 고려하는 기존 정책을 모델이 재정의하지 않는다.

실제 인증 HTTP·운영 MySQL/Redis·휴대폰 알림 수신/기사 수락·운영 부하·Azure/외부 서버·배포·APK·입금·commit/push는 미실행이다. 로컬 설정 활성화와 격리 추천 저장을 외부 서비스 운영 완료로 확대하지 않는다.
