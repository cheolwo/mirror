# 오토바이·다마스 적재 제원 보완 r73

2026-10-19. [승인 계획](../AI/Planning/공통/PLAN-OPERATIONS-DISPATCH-CORE/small-vehicle-loading-specs.implementation.r73.md) · [작업 명세](../AI/Planning/공통/PLAN-OPERATIONS-DISPATCH-CORE/small-vehicle-loading-specs.r73.work-order.json). 기존 [차량 선정 조사](2026-10-19-cargo-vehicle-selection-ai-input-audit.md)의 첫 자료 공백과 검증불가/물리 상한 문제를 보완했다. **CompletedLocalValidation / OperationalDisabled. 실제 운영 DB에는 적용하지 않았다.**

## 바뀐 동작

```text
소형차 초기 자료
├─ 오토바이 / 다마스: 수치 미확인·추천 OFF
├─ 기존 실차 값은 반복 초기화에서도 보존
└─ 기존 관리자 추천 기준 수정 API
   ├─ 길이 / 폭 / 높이 / 최대중량 등록
   ├─ 미확인 상태로 추천 ON → 거절
   ├─ 권장값이 물리 상한 초과 → 저장 전 거절
   └─ 유효한 값 등록 → 기존 상세 추천·기사 적합성에서 재사용

적재 판정
├─ 요구한 중량·부피·팔레트·바닥면적/치수 기준 누락 → 검증불가·추천 제외
├─ 기사 차량제원 없음 → 적합 false
├─ 허용중량 = 실제 최대중량과 운영 권장중량 중 작은 값
└─ 허용부피 = 실제 치수 부피와 양수 권장부피 중 작은 값
```

생략한 모든 화물 축을 새 필수값으로 만들지 않았다. 명시적으로 추천 OFF인 차량은 요구값 유무와 관계없이 엔진·배차 적합성 모두 제외한다. 차량 높이가 없으면 높이·부피 요구를 검증한 것으로 간주하지 않는다. 물리 부피와 바닥면적은 판정 시 반올림하지 않고 표시 매퍼의 반올림은 유지한다. 공개 결과의 기존 경고·불가 사유 배열을 유지하여 새 상태 enum이나 DB 표를 만들지 않았다.

## 등록과 호환

기존 관리자 전용 `PUT /api/v1/admin/vehicle-recommendations/criteria/{vehicleCode}`의 요청에 선택 필드 `적재함길이Mm`, `적재함폭Mm`, `적재함높이Mm`, `최대적재중량Kg`를 추가했다. 앞 세 필드는 mm, 마지막은 kg이며 **생략 시 기존 물리 제원을 보존**한다. 입력은 확인한 내부 적재 공간과 실차·장비 제한을 고려한 화물 한도다.

음수는 거절한다. 명시한 0은 비활성 자료의 미확인값으로 보관할 수 있고 높이 0은 null로 보관한다. 추천 ON에는 양수 길이·폭·최대중량, 오토바이·다마스에는 양수 높이도 필요하다. 기존 권장CBM·운영권장중량·팔레트의 null/0 초기화 의미는 유지한다. 권장부피는 기존 0.001CBM 정밀도에서 양수여야 하며 원값과 반올림값 모두 실제 부피 이하여야 한다. 잘못된 수정은 HTTP 400이고 저장/추적 객체 변경 전에 거절한다.

**등록 단위는 기존 차량코드별 기준표이며 개별 기사·실차별 이력표를 새로 만든 것이 아니다.** 같은 코드의 여러 기사가 하나의 기준을 공유하므로, 해당 차량·장비 모두에 적용 가능한지 확인하기 전 공통 코드를 운영 활성화해서는 안 된다. 개별 모델·장비 식별/배정과 증빙 영속 이력은 후속이다. 직육면체·중량 검사만으로 출입구 통과, 상자 배치, 장착 안전이나 실제 적재를 입증하지 않는다.

## 출처와 미확인값

[공식 출처 대장](../../eng/vehicle-loading/small-vehicle-spec-sources.json)에 공식 자료 5개와 모델·시장·확인일·적용 한계를 기록했다. 혼다/GIVI 장비 한도와 국내 GM 모델 구분은 확인했으나 국내 다마스의 모델별 내부치수·중량 원문과 오토바이 공통 적재함 수치를 확보한 것은 아니다. 원문 파일을 내려받아 해시 검증하지 않아 원문 해시는 null이다.

해외 다마스 450kg, 탑박스 3kg/10kg, 장비 표시 크기, 격리 학습의 오토바이 20kg/0.09CBM을 국내 공통 실차 값으로 넣지 않았다. 템플릿의 필수 정수 0은 미확인 표현이며 조사된 허용값이 아니다.

## 검증

Fast `artifacts/local/validation/20261019-174701`에서 소비 역할 앱을 포함한 `Ssalddel.v3.5.slnx` 빌드와 집중 **89개 통과·실패 0개**를 확인했다. 시험 환경 보완 후 Fast `20261019-180010`에서는 해당 89개와 앞서 실패한 업무 class를 묶어 **115개 통과·실패 0개**를 확인했다. 최종 Task `20261019-180119`는 같은 소비 솔루션 빌드와 전체 **12,929개 통과·실패 0개·환경 의존 16개 생략(총 12,945개)**이다. 생략은 TRX 결과의 `NotExecuted` 16개와 실행 로그를 대조했으며 총괄 Counters의 `notExecuted=0` 필드만 사용하지 않았다. 판정 입력 소스 15개의 해시는 `artifacts/local/small-vehicle-loading-specs/20261019-r73/source-snapshot.json`에 보존하며, 시험 fixture 변경만 포함한 `source-snapshot-r2.json`을 현재 기준으로 고정했다. 최종 Task 뒤에도 소스·승인 계획 해시 일치를 확인했다.

회귀 범위는 미완성 소형차 활성화 거절, 저장 전 검증으로 추적 객체·저장값 보존, 선택 필드 생략 호환, 정상 합성 제원 저장→DB 재조회→추천, 권장 중량·부피 초과, 아주 작은 권장 부피의 0 반올림 거절, 실제 부피·바닥면적 원정밀도, 비활성 제원의 요구값 없는 배차 우회, 제원 미등록 수락 차단과 기존 복귀 가점의 독립 방어, 시드 멱등·기존 실측값 보존이다.

초기 기록도 보존한다. `20261019-173356` 빌드는 대기가 길어 해당 검증의 프로세스만 중단했다(중단에 따른 MSB4166). 변경 프로젝트의 기존 restore assets와 참조 일치를 확인했고 패키지/프로젝트 참조 변경이 없어 이후 `-NoRestore`로 검증했다. `20261019-173858`은 빌드 성공·집중 85통과/4실패였고, 빌드 도중 추가된 엔진 조건보다 앞선 제품 DLL의 3건과 표준 ProblemDetails의 Title 대신 Detail을 검사한 시험 1건을 확인했다. 모든 제품/시험 파일을 동결한 뒤 다시 빌드한 최종 Fast에서 89개가 통과했다.

시험 치수·중량은 합성 자료이며 제조사 제원이 아니다. 실제 DB 초기화/이전·실차·휴대폰/APK 검증·운영 배차·모델 학습·송금·공개 배포·commit/push는 수행하지 않았다. 기존 지도/푸시 설정과 패키지·nullable 경고를 이번 변경으로 해결했다고 표시하지 않는다.

첫 Task `20261019-175042`는 빌드 성공·12,927개 통과·2개 실패·환경 의존 16개 생략이었다. 두 실패는 업무 판정 오류가 아니라 EF의 `ManyServiceProvidersCreatedWarning` 예외였다. 이번에 확대한 Identity 시드 시험 fixture에서 매번 생성하던 `InMemoryDatabaseRoot`를 하나의 정적 객체로 재사용하고, 데이터베이스 이름은 매회 Guid로 달리하여 시험 간 데이터 격리를 유지했다. 다른 업무 시험이나 제품 코드의 경고 설정을 변경하지 않았다. 이름과 root의 관계는 [Microsoft 공식 EF 시험 문서](https://learn.microsoft.com/ef/core/testing/testing-without-the-database#in-memory-database-naming)를 참고했다. 등록·저장 재조회 시험은 EF InMemory 격리 DB와 Controller 직접 호출이며, 새 운영 HTTP·실DB·실차 검증이 아니다.
