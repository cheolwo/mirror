# 역할 앱·업무 OS의 예외 후 업무 지속 검증

2026-10-10 사용자의 요청에 따라, 예외가 생겨도 이미 처리한 결과를 보존하고 같은 업무를 안전하게 이어갈 수 있는지 현재 문서·코드·관련 시험을 대조했다. 제품 코드는 수정하지 않았다.

**주요 부족은 서버의 상태 관문보다 화면 이탈 후 미확정 요청 복원, 완료 후 정본 재조회, 지원 사건에서 원 업무로 돌아가는 연결에 있다.** 동일 화면 안의 재시도는 여러 곳에 구현돼 있지만 앱 재시작·다른 화면 이동·담당자 인계까지 같은 수준으로 이어지지는 않는다.

상태: `SourceAuditGapsFound / RelatedLocalTestsPassed / ProductRuntimeNotVerified`.

## 범위와 판단 기준

- [역할 대장](../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Core/RoleWorkspaceCatalog.cs)의 생활·주문자·음식점·음식기사·화주·화물기사·창고·운영자 8개 진입점을 기준으로 주요 변경·복구 경로를 읽었다. [업무 OS 대장](../../Ssalddel.Contracts/Common/Versioning/OperatingSystemIdentityCatalog.cs)의 10개 OS·62개 책임 단계와 인계 4개도 현행 계약으로 검사했다.
- 업무 OS의 생명주기는 업무 책임 단계다. Android/MAUI의 시작·중지·재개와 구분한다. 책임 단계 순번을 실행 가능한 전이표로 취급하지 않는다. [책임 모델](../Architecture/BusinessWorkflowResponsibilityModel.md)과 [기존 r23 조사](2026-10-06-os-lifecycle-static-audit-r23.md)·[r24 보완](2026-10-06-os-lifecycle-hardening-r24.md)을 재사용하되 현재 소스에서 다시 확인했다.
- 정상 지속은 원장·요청 번호·사용자·판본을 유지하면서 결과를 재조회하거나 허용된 후속 작업만 재시도하는 것이다. 권한·동의·사진·수량 관문을 생략하는 것을 복구로 판단하지 않는다.
- 자동 재조회 가능한 일시 오류, 결과가 불확실한 변경 요청, 재확인이 필요한 동시 변경, 당사자·운영자 판단이 필요한 보류를 구분했다. 배송·수령·지원 사건 종결·지급·알림 확인은 별도 결과다.
- 아래는 주요 예외 경로에 대한 조사다. 모든 페이지와 모든 상태 조합을 전수 실행하거나 r23의 518개 근거 파일 전부를 다시 감사한 결과는 아니다.

기준 작업본: `dev/mirror-integration`, HEAD `d1bab3eec08dc0a49c9a87f882590d394205c9a4`의 기존 변경 포함 작업본. 원시 근거는 Git 제외 `artifacts/local/exception-continuity-audit-20261010/`에 있다.

## 우선 보완할 사항

P1은 중복 원장 생성 가능성을 먼저 닫을 항목, P2는 안전하게 보류되지만 사용자가 이어갈 수 없거나 다른 상태를 보는 항목이다. 실제 운영 사고를 재현·측정한 심각도는 아니다.

### C01 · P1 · 화주 등록의 요청 번호가 재시도마다 변경됨

[작성 모델](../../SsalddelApp/ViewModels/Shipper/ShipperRequestAuthoringPageViewModel.cs) 116행은 제출 때마다 현재 시각으로 `SHP-...`를 만들고, [서버 adapter](../../SsalddelApp/Services/ServerBackedShipperOperationsService.cs) 323행이 이를 `클라이언트요청Id`로 보낸다. [생성 handler](../../Ssalddel/Application/Shipper/Request/Handlers/의뢰생성CommandHandler.cs) 94행의 중복 검사는 같은 사용자·같은 번호에 의존하며 일반 의뢰는 132행에서 새 서버 ID를 만든다.

첫 요청이 저장되고 응답만 유실된 뒤 다음 초에 다시 제출하면 다른 원장이 생길 수 있다. 기존 `ShipperContactWindowAuthoringTests`는 저장 전 실패의 입력 보존과 동시 클릭 차단을 검사하며 커밋 후 유실을 다루지 않는다.

완료 기준: 최초 제출의 번호·본문을 고정하고 재진입에도 같은 사용자로 복원한다. 불확실한 응답 뒤 같은 번호의 결과부터 조회한다. 저장 후 응답 유실→다음 초 재시도·앱 재진입에도 원장 1건인 실패 주입 시험이 필요하다.

**C01a · P2:** 같은 모델 48행은 차량 조회 전에 `_initialized=true`로 바꾸고 실패 후에도 유지한다. 이후 초기화는 즉시 반환해 같은 세션의 등록 비활성이 풀리지 않는다. 입력을 보존한 채 차량·등록 준비만 다시 조회할 경로와 실패→성공 시험이 필요하다.

### C02 · P1 · 생활 배송 작성의 미확정 요청이 화면 종료 때 사라짐

[배송 작성 화면](../../Ssalddel.Ui.Common/Areas/App/Components/Community/Exchange/NeighborhoodDeliveryCreate.razor) 145행의 Dispose는 [작성 VM](../../Ssalddel.Ui.Common/Areas/App/ViewModels/NeighborhoodDeliveryAuthoringViewModel.cs) 435행에서 미확정 요청·원문을 지운다. 재진입은 422행에서 새 번호를 만든다. `NeighborhoodDeliveryViewModelTests`의 동일 번호 재시도는 같은 VM 안에 한정된다.

접수 후 응답 유실→목록 이동→재작성하면 서버가 기존 의뢰를 저장했는지 확인하지 못한 채 새 의뢰가 생길 위험이 있다. 협업에서 복원되는 특정 요청과 일반 배송 작성 경로를 구별해야 한다.

완료 기준: 기존 회원 수행용 보호 저장소 패턴을 검토해 사용자별 최소 미확정 문맥과 결과 조회를 마련한다. 개인정보를 무조건 영구 저장하거나 다른 계정에 넘기지 않는다. 화면 이탈·재로그인·앱 재시작 뒤 원 접수 확인, 취소/명시 폐기와 만료 정리까지 검증한다.

### C03 · P2 · 분산 입고·피킹·사진의 복구가 화면 수명에 제한됨

[분산 화면](../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/DistributedFulfillment/분산이행Screen.razor) 76행의 명시적 복구 링크는 요청 번호를 보존하며, [VM](../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/DistributedFulfillment/분산이행PageViewModel.cs) 426행은 POST 없이 영수증·최신 원장을 조회한다. 이 정상 경로는 `DistributedFulfillmentViewModelTests`가 보호한다.

그러나 일반 이동·종료는 같은 VM 499~504행에서 pending 본문과 [사진 세션](../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/DistributedFulfillment/분산사진업무Session.cs)을 지운다. 사진 업로드 ID·완료 요청 연결도 메모리 전용이다. 이미 저장된 원장·영수증은 남으며, 사라지는 것은 미완료 요청과 업로드의 **클라이언트 재개 문맥**이다.

완료 기준: 사용자·역할·업무·요청 ID·본문 판본·증빙 참조를 최소한으로 복원하고 영수증을 먼저 조회한다. 사진 원본은 보호 저장·기한·폐기 정책을 별도로 정하거나 저장된 업로드 결과를 재조회한다. 원본 부재는 재촬영 필요로 명시하며 성공으로 간주하지 않는다. 종료 시점별 업로드 전/후·커밋 전/후 시험이 필요하다.

### C04 · P2 · 화물 하차 완료 후 이전 카드가 남고 응답 유실을 미저장으로 안내함

[하차 VM](../../DriverApp/ViewModels/Driver/Transport/기사하차PageViewModel.cs) 182~218행은 완료 후 사진 참조·문구만 갱신한다. 정본 재조회나 다음 화면 이동이 없어 64행의 이전 `하차지도착` 기준으로 완료 버튼이 다시 활성화될 수 있다. [사진 완료 service](../../DriverApp/Services/DriverTransportCompletionPhotoService.cs) 110행은 통신 예외를 “완료 처리는 저장되지 않았습니다”로 단정한다.

서버의 같은 완료·사진 중복 보호는 있으므로 중복 재고·정산 발생으로 판정하지 않는다. 확인한 영향은 오래된 완료 카드와 결과 오안내다.

완료 기준: 성공·불명확한 응답 모두 같은 운송을 재조회하고 확인 전에는 결과 확인 상태로 둔다. 확인된 완료 카드는 닫고 완료 내역/다음 업무로 이어간다. 커밋 후 응답 유실·조회만 회복·재조회 실패를 각각 시험한다.

### C05 · P2 · 지원 사건 종결 뒤 회원 배송 복구를 실행할 화면이 연결되지 않음

[복구 controller](../../Ssalddel/Controllers/Admin/NeighborhoodMemberDeliveryRecoveryController.cs)와 [복구 UseCase](../../Ssalddel/Services/Community/NeighborhoodMemberDeliveryUseCase.Recovery.cs) 44~92행은 닫힌 지원 사건·당사자 통지·현재 판본을 검사해 재개/픽업 전 취소를 처리한다. 운영자 Web/App·통합 앱·공통 UI에서 해당 endpoint와 `NeighborhoodMemberRecoveryRequest` 소비는 찾지 못했다. 회원 수행 화면은 운영자 안내를 기다리며 지원 관리 화면은 사건 종결까지만 제공한다.

완료 기준: 종결 사건에서 원 배송을 재조회하고 가능한 복구 행동·담당자·조건을 표시한다. 재개 또는 픽업 전 취소를 별도 확인 후 실행해 기존 수행 슬롯을 정상 정리한다. 사건 종결을 배송 재개·입금 완료로 합치지 않는다. 기존 `NeighborhoodMemberDeliveryRecoveryTests`의 직접 service 시험에 운영자 화면 인계 시험을 추가한다.

### C06 · P2 · 공통 음식 요청 화면에서 POST 응답 유실을 조회로 해결할 수 없음

[FoodRoleActionViewModel](../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Food/FoodRoleActionViewModel.cs) 241~281행은 응답을 받아야 `commandAcknowledged=true`가 된다. 서버가 처리했어도 응답만 유실되면 결과 조회가 거부되고 다음 클릭은 같은 POST를 다시 보낸다. [기존 시험](../../Ssalddel.Tests/Ui/Common/FoodRoleActionViewModelTests.cs) 14~43행도 조회 거부와 동일 POST 두 번을 현재 동작으로 고정한다.

적용 대상은 이 공통 화면의 주문 취소·음식점 수락/거절/조리시간 변경·기사 중단·운영자 검토다. 같은 번호·본문을 보존하므로 중복 효과가 발생한다고 판정하지 않는다. 쓰기만 장애이고 읽기가 회복된 상황에서 조회로 마무리할 수 없는 격차다.

완료 기준: 응답 유실도 미확정 요청으로 다루고 원장/요청 이력을 조회한다. 단순 상태 변화만으로 본 요청 성공을 인증하지 않으며 번호·사용자·대상·본문/판본 근거를 확인한다. 미반영이 확인됐을 때만 원 요청의 명시적 재전송을 허용한다.

### C07 · P2 · 주문자 지도 상세에서 원주문 결속 문제 접수로 인계할 수 없음

[주문자 adapter](../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Food/OrdererRoleWorkspaceAdapter.cs) 57~66행은 수령·수락 전 직접 취소만 구성한다. 공통 지도 메뉴에도 지원 인계가 없다. [기존 주문 상세](../../Ssalddel.Ui.Common/Areas/App/Components/Food/OrdererFoodOrderDetailPanel.razor) 122행에는 원주문이 결속된 지원 링크가 있으나 지도 중심 주 경로에는 연결되지 않았다. 일반 지원 URL은 원주문 정보가 없으면 거래 상세로 돌아가도록 안내한다.

완료 기준: 수락 후 지연·취소 협의·미수령 때 원주문 번호·복귀 경로를 가진 기존 지원 기능으로 인계한다. 상태별 필요한 문제 접수 행동만 제공하고 접수와 실제 취소/환불은 구분한다.

### C08 · P2 · 회원 배송 상세에서 앱 재개 후 지도가 복원되지 않을 수 있음

[MAUI 지도 host](../../SsalddelApp/Services/MauiNeighborhoodMapHost.cs) 218~232행은 중지 때 지도를 숨기고 재개 때 무효화 이벤트를 발행한다. [회원 수행 화면](../../Ssalddel.Ui.Common/Areas/App/Components/Community/Exchange/NeighborhoodMemberWork.razor) 60행은 이를 구독하지 않고 77행의 업무 지문이 같으면 다시 그리지 않는다. 카메라·다른 앱에서 돌아왔을 때 업무 판본이 같으면 지도가 비어 있을 수 있다. 지도 adapter가 계속 예외를 던지면 95~96행의 재렌더 요청도 반복될 수 있다.

완료 기준: 중지/재개에서 지도 표시 수명을 별도로 무효화하고 같은 업무를 복원한다. 지도 실패는 카드·업무를 유지한 채 제한된 재시도로 표시한다. 중지→재개·늦은 렌더·연속 예외 adapter 시험 후 단말에서도 확인한다. 이번에는 단말에서 재현하지 않았다.

### C09 · P2 · 수입 준비 조회의 늦은 응답이 새 원장 화면에 적용될 수 있음

[OrdererGroupImportReadinessLoader](../../OrdererApp/Components/GroupPurchase/OrdererGroupImportReadinessLoader.razor) 121~143행은 이전 조회를 취소하지만 성공·오류 적용 전에 현재 원장 key/요청 세대를 확인하지 않는다. A 원장 조회 중 B로 바꿨을 때 취소 직전 완료된 A 응답이 B의 자료를 덮을 수 있다. `finally`의 현재 CTS 검사만으로 자료 적용을 보호하지 못한다.

공통 Loader의 준비 조회 7개 화면에 해당한다. 읽기 화면의 자료 혼동이며 계약·결제·외부 전송 우회로 판정하지 않는다. 기존 composition 시험은 소스 문구, client 시험은 GET 경로를 확인하며 응답 순서를 뒤집는 화면 시험은 확인하지 못했다.

완료 기준: 성공·오류를 반영하기 전에 원장 key·요청 세대·Dispose 여부를 대조한다. A/B의 성공·오류·취소 응답 순서를 뒤집어 현재 선택만 표시하는 시험을 실행한다.

## 보완 순서

1. **C01·C02:** 신규 의뢰의 미확정 요청 보존·결과 조회. 중복 원장 가능성을 먼저 닫는다. C01a의 준비 재조회도 함께 정리한다.
2. **C04·C06:** 이미 처리된 업무를 조회로 확정하고 완료 카드·버튼을 현재 상태로 전환한다.
3. **C05·C07:** 문제 접수→운영 판단→원 업무 재개/취소를 같은 주문·배송 문맥으로 연결한다.
4. **C03:** 입고·피킹·사진을 화면 종료 뒤에도 원 사용자로 재개한다.
5. **C08·C09:** 앱 재개·원장 전환 때 지도와 읽기 카드의 표시를 보호한다.

공통화는 요청 보관·결과 확인·오래된 응답 폐기 같은 같은 의미의 복구만 대상으로 한다. 음식과 화물의 상태·배차·완료·전문 원장 권한을 하나로 합치는 리팩토링은 권하지 않는다. 각 화면은 현재 단계, 보존한 결과, 기다리는 이유, 다음 행동과 담당자를 보여주면 된다.
