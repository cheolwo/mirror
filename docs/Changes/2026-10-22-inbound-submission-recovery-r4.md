## 업무 흐름

```text
입고 신청
├─ 보호 저장·재조회 실패 → 전송 차단, 다시 확인
└─ 보호 저장된 원요청 ID로 신청
   ├─ 접수 응답 확인 → 같은 입고 내역
   └─ 응답 유실 → 원요청 ID로 결과 조회
      ├─ 본인 정본·요청 ID 일치 → 확인 기록 정리 → 같은 입고 내역
      └─ 아직 없음·조회 실패·다른 ID → 확인 대기 유지
```

구판 단말 전용 관측 ID는 서버 요청 ID로 소급하지 않는다. 새 요청은 TTL 뒤에도 남는 target 표식으로 구분한다. 원요청 GET404는 아직 저장 중인 요청일 수 있으므로 재등록을 허용하는 근거가 아니다.

## 구현과 책임

- 서버는 기존 입고 원장에 선택적 `ClientRequestId`·최초 정규화 입력 SHA를 함께 저장한다. 작성자/요청 ID 유일키로 같은 신청의 중복 행을 막는다. 동일한 최초 내용은 같은 현재 원장으로 확인하고, 다른 내용이면 충돌로 남긴다. 이후 원장 수정·완료는 최초 지문을 바꾸지 않는다.
- 원요청 조회는 기존 운영 인증·기능 플래그·입고 역할과 정본 조회 범위를 유지하면서 작성자 본인만 정확히 대조한다. 창고 소유자는 다른 작성자의 요청 번호를 탐색하지 못한다. DB가 대소문자를 무시해도 인증된 작성자 ID는 정확히 일치해야 한다. 기존 상세 조회처럼 작성자의 창고 회원 상태 변경은 본인 원장 확인 권한을 새로 없애지 않는다.
- 클라이언트는 명령 전 보호 저장한 번호를 실제 POST에 전달한다. 새 화면 진입·결과 확인에서 이 번호의 정본을 조회하고, 요청 번호·입고 ID·현재 계정·세션·서버와 보호 기록을 대조한다. 원기록의 조건부 삭제와 삭제 확인까지 통과해야 확인 대기를 해제한다.
- 아직 결과 없음·조회 장애·다른 번호 응답·저장소 장애에서는 재등록을 막는다. 감사 기록의 후속 실패는 입고 저장 실패와 구분한다. 새 원장이나 목록 내용 매칭, 자동 POST 재전송은 추가하지 않는다.

## 화면 자료

[모바일·PC 화면 모음](../assets/changes/2026-10-22-inbound-submission-recovery-r4/index.html) · [캡처 근거](../assets/changes/2026-10-22-inbound-submission-recovery-r4/evidence.json)

실제 공통 신청 화면 `InboundRequestCreateScreen`에 가상 상태를 입력한 정적 렌더다. 확인 대기·같은 신청 확인·구판 기록 보존의 3사례를 390/1280px로 저장했다. 새 계약의 확인 대기만 기존 버튼을 `접수 결과 확인`으로 표시한다. 확인된 입고는 `등록 내역 확인`으로 이어지고 같은 화면의 재등록은 막는다.

전체 페이지 배치를 확인했지만 버튼 실행·오류창 자동 표시·실제 API 통신·휴대폰 캡처를 의미하지 않는다. 기존 입고 화면의 긴 설명·계약 입력 배치는 이번 요청 결과 복구 범위와 분리했다.

## 검증 결과

- 최종 Fast: 소비 `Ssalddel.v3.5.slnx` 빌드와 집중 **180개 통과**, 실패·미실행 0. 기록 `artifacts/local/validation/20261022-075024/`.
- 최종 Task: 동일 소비 솔루션 빌드와 전체 **14,386개 통과**, 실패 0, 환경 의존 **16개 미실행**. 기록 `artifacts/local/validation/20261022-075140/`.
- SQLite 관계형 DB의 별도 컨텍스트에서 응답 유실 후 조회, 같은 요청 1행 유지, 다른 내용 충돌, 타작성자 차단, 실제 유일 제약, 두 서비스의 저장 경합 복구를 검증했다. 테스트용 동기화 장치로 경합 순서를 고정한 결과이며 운영 부하 시험은 아니다.
- MySQL migration의 오프라인 SQL 생성과 nullable 두 열·작성자/요청 ID 유일키·기존 행 무수정, 현장 임시 입고와 일반 입고의 ID 영역 분리를 확인했다. 실제 기존 DB에 migration을 적용한 결과가 아니다.
- 새 VM에서 같은 보호 기록 복원, 초기404 뒤 늦은 저장 확인, 구판·72시간 뒤 payload 제거·다른 요청 응답·계정/서버 전환·보호 기록 저장/삭제 실패를 검증했다. Web adapter의 인증 JSON 요청은 모의 HTTP handler로 검사했다.
- 실제 공통 신청 화면의 가상3사례·Chrome 390/1280px 총6장, 가로 넘침·브라우저 오류·외부 통신 0. 최종 UI/계약 DLL과 렌더 DLL의 해시를 대조했다.

첫 Fast는 잘못된 ‘작성자 창고 회원 해제 시 본인 조회 차단’ 시험 1건만 실패했다(178개 통과). 기존 권한을 보존하는 기대값으로 바로잡았다. 추가한 대소문자 비교 시험의 생성자 오류로 실패한 두 번째 빌드도 보존하고 명시적 생성자로 수정했다. 제품 변경 없이 렌더 도구에 누락된 Popover provider를 보완한 뒤 화면6장을 생성했다. 실패 로그를 최종 성공 기록으로 대체하지 않는다.

최종 소스23개·시험·화면·빌드 결속·링크 검사는 로컬 `artifacts/local/inbound-submission-recovery/20261022-r1/verification.json`에 연결한다. 기존 dirty snapshot 변경은 보존하고 이번 migration 부분만 추가했다.

## 남은 범위

기존 실행 DB에 새 migration을 적용한 뒤 서버와 클라이언트를 함께 배포해야 새 계약을 사용할 수 있다. 이번에는 기존 DB·서버 배포·운영 플래그를 변경하지 않았다. 실제 휴대폰에서 응답 유실→강제 종료→재실행의 보호 저장·정본 확인은 후속이다.

서버로 보내지 않았던 구판 단말 전용 `create` 번호는 자동 복구하지 않는다. 원요청 결과가 계속 없거나 사전 입력/접근 오류가 미확정으로 남으면 별도 확인이 필요하며 임의 잠금 해제는 제공하지 않는다. 웹 기본 복구 저장소는 메모리 기반이므로 웹 프로세스 재시작 보존을 약속하지 않는다. 다른 OS 적용·실제 외부 통신·운영·지급·새 APK 설치·commit/push는 이번 완료 주장에 포함하지 않는다.
