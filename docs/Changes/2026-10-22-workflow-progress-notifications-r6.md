# 업무 단계별 진행 알림 r6 — 2026-10-22

후속: [r7 실제 휴대폰 샘플 검증](2026-10-22-workflow-progress-device-r7.md)에서 최신 APK203·실제 FCM7건/대표5단계와 클릭/중복/이전단계/프로세스 재시작을 확인했다. 아래 r6 당시의 로컬 검증 결과와 미실행 기록은 보존하며, 새 원장 업무의 단말 전수 E2E로 확대하지 않는다.

- 승인·범위: [계획](../AI/Planning/공통/PLAN-OPERATIONS-DISPATCH-CORE/workflow-progress-notifications.r6.md) · [작업 명세](../AI/Planning/공통/PLAN-OPERATIONS-DISPATCH-CORE/workflow-progress-notifications.r6.work-order.json)
- 현재: `CompletedLocalValidation / ExternalPushAndDevicePending`. 실제 외부 푸시·알림음·단말 조작은 실행하지 않았다.

## 바뀐 흐름

```text
서버가 권한·현재 상태·증빙 확인
└─ 전문 원장 상태 변경 + 기존 Outbox에 알림 예약을 함께 저장
   ├─ 음식: 접수 → 수락 → 기사 배정 → 조리 → 준비 → 기사 도착 → 픽업 → 전달 → 수령
   │  ├─ 수락/조리/배정의 실제 허용 순서는 기존 Guard를 따른다
   │  └─ 주문자는 진행 안내, 현재 확정 기사는 음식 준비 완료 안내
   ├─ 창고: 입고 신청 → 수령 → 검수 → 적재 → 피킹 → 포장 → 출고 준비 → 기사 인계
   │  └─ 요청자·상품 소유자·창고 소유자·실제 지정된 다음 담당자에게 권한별 안내
   └─ 화물: 기존 추천/수락 → 접근 → 상차지 도착 → 상차 → 하차지 도착 → 전달
      └─ 현장 문제는 별도 확인 알림, 전달·인수 확인·정산·실지급은 서로 다른 결과

예약된 알림
├─ 기존 재시도/lease/실패 한도 적용
├─ 통합앱: 계정·설치·단계·발생 시각·내부 경로 확인 → 기기 알림
│  └─ 클릭 → 로그인 필요 시 같은 계정 로그인 → 기존 업무 화면에서 최신 정보 재조회
└─ 기존 전문 앱: 기존 FCM notification 표시 방식 유지, 개별 앱 전경/클릭 통합은 후속
```

위 트리는 업무 이해용이며 모든 단계를 강제로 직렬 실행하는 새 엔진이 아니다. 직접 수령/전달, 기존 예외·취소·피킹/배송 조합과 전문 원장의 허용 행동은 그대로다.

## 구현과 책임

| --- | --- |
| 단계 표현 | 음식 11·창고 9·화물 7개의 사건 코드를 기존 OS·생명주기 단계에 연결한다. 짧은 제목/본문은 공통 계약에서 관리한다. |

| 음식 | 접수/상태 저장과 기사 수행 저장에 결속한다. 조리시간만 변경하거나 같은 상태를 확인하는 요청은 새 알림을 만들지 않는다. 음식점은 기존 인증된 음식점별 SignalR을 유지한다. 음식점 ID로 실제 사용자 ID를 추정하지 않는다. 외부 수행 증거로 조리가 허용된 경우에도 내부 운송 원장을 요구하지 않으며 준비 완료의 기사 알림은 실제 내부 배정에만 추가한다. |
| 창고 | 입고 신청/수령/검수/적재·피킹 시작/완료·포장/준비/기사 인계를 연결한다. 사진 가 입고는 개인 준비 기록이므로 실제 입고 알림을 생성하지 않는다. 본인/다중 역할 중복을 제거하고 다음 포장 담당자의 실제 연결과 창고 접근권을 확인한다. |
| 화물 | 기존 FeatureName과 수락 복구를 유지한다. 단계 알림을 운송/화주 투영과 같은 저장에 넣고, 호환 이벤트 알림은 정본 상태/담당자를 확인할 뿐 원장을 다시 쓰지 않는다. |
| 발송 | 기존 Outbox 발송기의 지원 범위를 확장한다. 통합앱 설치에는 data-only를 보내 앱의 계정/설정 확인 후 표시한다. 구형 설치에는 기존 notification 메시지 방식을 유지한다. 기존 화물의 Push+AlimTalk 채널과 Enabled 설정을 보존하며, 알림톡용 전화/주소는 발송 때 현재 원천과 수신자 권한을 대조한 후 읽는다. |
| 통합앱 | 기존 보호 설치 저장소에 최대 64개·7일의 최소 수신 기록과 클릭 대상을 보존한다. 다른 계정/철회/중복/지연된 이전 알림을 거르고, 알림 수신만으로 화면을 강제 전환하지 않는다. |

## 사용자에게 보이는 정보

예: **피킹 완료** — 다음 작업을 확인해 주세요. / **상차 완료** — 전달지로 이동합니다.

주소·전화·고객명·메모·사진 경로를 신규 푸시 본문에 넣지 않는다. opaque 원천 ID와 기존 내부 경로만 전달하고 상세는 인증 API에서 재조회한다. 진행 안내와 신규 배송 제안 참여는 다른 목적이며, 확인된 소리·진동·야간 설정을 존중한다. 설정이 없거나 배송 제안이 꺼져 있으면 소리·진동을 새로 켜지 않는다. OS에서 업무 진행 채널을 차단하면 표시하지 않는다.

화물의 비공개 Outbox에는 기존 알림톡 템플릿 변수용 opaque 기사 ID 참조도 유지한다. 이 참조는 전화/주소가 아니며 신규 FCM data에는 보내지 않는다. 기존 과거 Outbox를 정리하거나 수정하지 않았다. 새 음식·창고 진행 알림에 알림톡 채널을 추가하지 않았다.

알림 발송 접수와 실제 수신·열람·업무 완료·수령·지급은 별개다. 외부 전송 성공 후 저장 전 중단 등에서 재전송될 수 있어 네트워크의 정확히 한 번 수신을 보장하지 않는다. 단말 중복 기록도 유한 캐시이며 원장의 권위를 대신하지 않는다.

## 남은 확인

- 이번에는 실제 FCM 자격/worker 설정을 켜거나 외부로 알림을 발송하지 않았다. 실제 전경·배경·잠금·알림 클릭·소리·다른 계정 로그인은 USB 기기에서 별도 확인해야 한다.
- 전문 앱 각각의 전경 진행 알림/딥링크 처리는 통합앱과 구분해 후속 검증한다. 브라우저는 기존 실시간 재조회 경로를 유지한다.
- 외부 수행의 동의·배정 증거는 기존 경계를 보존하며 내부 기사 ID로 추정하지 않는다. 업체별 웹훅과 분산 창고 하위 흐름 전체에 신규 진행 알림을 확장한 결과는 아니다. 작업 최초 배정/재배정 알림도 이번 창고 완료 단계 연결과 구분한다.
- 구형 수락의 별도 `배차수락사후처리EventHandler.Transport.cs` 담당자 보정 경로는 기존 코드이며 이번 알림 리팩토링에서 변경하지 않았다. 신규 SQL 수락 복구의 기존 정본 검사와 혼동하지 않는다.
- 새 DB 테이블/스키마, 운영 활성화, 결제·지급, APK 설치, commit/push는 수행하지 않았다. 이전 r5의 실 DB 적용/카메라 과제도 그대로 남는다.

화면 검증 수준: 화면 배치 변경 없음. 기존 알림 클릭의 업무 이동 로직 변경이며 실제 OS 알림 캡처는 미검증이다. 이전 r5 화면 갤러리를 이번 알림 검증으로 사용하지 않는다.
