## 발생 조건과 수정

완료 조건은 **기존 의뢰·묶음·기사 ID와 A를 전송하고, 응답 전에 작성한 B는 성공 뒤에도 남겨 다음 명시 저장에서만 보내는 것**이다. [현재 페이지](../../SsalddelAdmin/Components/Pages/DomesticCargoDispatchAIReview.razor)의 **판정 메모**에 입력 시 즉시 화면의 편집 값을 반영하도록 연결했다. 설치된 MudBlazor 9.5.0 계약에서 기본값은 포커스 이탈 등에 반영하는 지연 방식이므로, 입력 직후 응답이 오는 경우까지 고려한 같은 필드의 설정이다. 입력마다 판단 사례를 저장하는 기능은 추가하지 않았다.

**RAG 판단 사례로 저장**을 누르면 제출 메모의 원문을 지역 값으로 캡처해 기존 요청에 담는다. 성공 시 현재 메모가 제출한 값과 Ordinal로 정확히 같을 때만 비운다. 새 메모가 다르면 앞뒤 공백·개행도 그대로 유지한다. 실패 시 최신 메모를 남기고, 같은 값의 성공 초기화·저장 중 중복 요청 방지·기존 재조회 제한을 보존한다. 같은 원문으로 돌아온 값은 동일한 제출 값으로 취급하며 새 편집 원장이나 세대 번호는 만들지 않았다.

## 같은 업무의 연결과 범위

기존 입력 factory는 배차 큐의 `의뢰Id`로 화주 의뢰를 찾고, 검토 DTO는 같은 `RequestId`를 묶음의 `RequestIds`와 연결한다. 격리 가상 업무에서는 `REQUEST-A`·`REQUEST-B`가 `BUNDLE-MEMO`에 포함되며, `DRIVER-A`와 기존 판정 유형·승인·수동 여부가 A 및 다음 명시 저장의 B와 각각 같은 요청에 들어감을 대조했다. 구성 화물 두 건과 선택은 그대로 유지했다.

이 확인은 기존 조회 → 묶음 구성 → 판단 요청의 경계다. 해당 DTO에 없는 원주문·창고 출고 연결은 미확인으로 두며 문자열·시각으로 추정하지 않았다. 실제 기사 배정·운송 인계·서버 사례 저장을 실행한 것이 아니다. O3 샘플/활성 판단 자료 정책도 보존했다.

Tests 빌드 경고 239개·Admin 소비 빌드 경고 0개, 오류는 모두 0개다. 신규 시험의 renderer 관련 BL0006 2곳과 입력 값 읽기의 MUD0012 1곳이 포함돼 있다. 로그는 `artifacts/local/validation/20261107-181956`이다.

신규 시험은 다른 B·앞뒤 공백 차이·공백 원문, 변경 없는 A의 성공 초기화, 503/401 실패 뒤 최신 B와 명시 재시도, 저장 대기 중 반복 요청 1회, 보존한 B의 다음 저장과 기존 업무 ID를 대조한다. 실제 컴파일된 부모와 하위 MudInput의 `OnInput(string)` C# 핸들러를 `IHandleEvent`로 실행하고 부모 바인딩·실제 textarea 출력·직렬화된 HTTP 본문을 함께 확인했다. 제품의 InteractiveServer 모드를 바꾸지 않았다. HTTP는 `fixture.invalid`의 메모리 handler로 제한했고 외부 요청이나 원장 저장은 없다.
