```text
화주가 운송 조건 입력
├─ 같은 포장 1개의 외포장 치수 × 포장 수량
├─ 포장·팔레트를 포함한 전체 합계 중량
└─ 직접 입력한 전체 부피, 회전·적층, 온도·취급 요청
   ↓ 공통 계산·검사
현재 조건의 서버 차량 추천
├─ 후보 없음·조회 실패 → 입력 유지, 재확인
├─ 조건/계정 변경·이전 응답 → 적용하지 않음

   ↓ 단건·일괄 접수
화주 운송의뢰 원장
├─ 원입력 부피와 판정용 유효 부피를 구분

└─ 물리 제원·중량·비적층 면적·치수·취급 조건 비교
```

## 계산과 보존

- 판정 전 CBM·바닥면적을 소수 3자리로 반올림하지 않는다. 총중량을 포장 수량으로 다시 곱하지 않으며, 전문 원장에 kg를 정수로 올림한 사본보다 의뢰 원장의 decimal 총중량을 우선한다. 정수 범위 밖 전문 투영은 null로 두고 원 총중량을 보존한다.
- 치수×수량 추정값과 직접 입력 CBM을 함께 보존하고 둘 중 큰 값으로 판정한다. 입력이 더 작으면 경고한다. 이는 실제 측정 확인이 아니다. 수량 누락은 원 null과 1개 가정 경고를 남긴다. 회전/적층 미확인도 원 null과 기존 true 가정을 구분한다. 팔레트 0은 ‘없음’이며 음수는 오류다.
- 추천 요청의 회전/적층 JSON 이름은 유지하고 nullable로 넓혀 누락과 명시 true/false를 구분한다. 생략의 유효 가정은 기존 true를 유지하되 경고를 제공한다. 신규 화면은 수량 1과 선택값을 명시한다.
- 구형 저장 CBM을 새 직접 입력값으로 소급하지 않는다. 같은 원입력 또는 기존 GET 유효값의 재전송은 실제 변경과 구분한다. 직접 입력 부피 지우기는 명시적 의도로 처리하며 값과 지우기를 동시에 보내면 거절한다. 승인·결제·배차 뒤 핵심조건 잠금은 새 필드에도 적용한다.
- 실제 화물값 변화가 없으면 적재 근거를 다시 쓰지 않는다. 따라서 구형 기록의 0값을 그대로 둔 연락처 수정은 지원하며, 양수였던 값을 새 0으로 바꾸는 요청은 거절한다. 성공한 일반 수정은 견적 유무와 관계없이 기존 Mongo 동기화에 연결한다.
- 신규 Mongo 근거 표식의 null은 초기화로 재현하고, 표식이 없는 구형 사본은 새 근거를 지우지 않는다. 신규 화물 설명 생략을 주소가 들어간 운송 요약으로 바꾸지 않는다. 조회의 보수 판정값이 과거 저장값과 다르면 경고하며 조회만으로 저장하거나 과거 확인 상태를 올리지 않는다.

## 화면과 일괄 입력

- App/Web 작성 화면은 실제 화물로 서버 추천을 받는다. 별도 중량 OR 부피 간이 추천과 후보가 없을 때의 고정 차량 목록 대체를 제거한다. 서버 응답 자체가 차량을 자동 선택하지 않는다.
- 요청 순번·계정 판본·현재 입력 지문을 대조한다. 초안에 추천 응답/확인 지문을 저장하지 않으며, 서버 추천에서 선택한 차량의 복원 시 재확인 필요 표시는 유지한다. 구형 수동 초안의 차량은 확인된 추천으로 표시하지 않는다.
- 사용자 요청 원문은 초안에 유지하고 적재형태를 포함한 같은 전송 문구를 추천·접수에 사용한다. 추천 차량명·권장값을 화물 설명에 자동 덧붙이지 않는다.
- 일괄 등록은 설명·취급 요청·회전/적층을 같은 추천에 전달한다. 후보가 없거나 선택 차량이 현재 후보에 없으면 기본 차량으로 대신 접수하지 않는다. 추천 근거 판본과 입력 지문도 비교한다.
- CSV 템플릿에 회전/적층과 상·하차 담당자·시간창 열을 추가한다. 상차 시작/종료와 양쪽 담당자 이름·연락처가 없으면 접수 전 보완한다. 하차 창은 선택 사항이지만 입력할 때는 시작/종료를 함께 확인한다. 시간에는 `Z` 또는 `+09:00` 같은 시간대를 요구하고 UTC로 보존한다. ‘현재부터 1시간’이나 ‘확인필요’ 연락처를 자동 생성하지 않는다. 주소·담당자·약속 입력을 생략한 기존 CSV는 미리보기에서 보완할 행으로 남는다.

## 검증 결과

- 첫 소비 솔루션 빌드는 성공했다. 초기 집중 795개 중 7개 실패를 보존하고, 실제 견적 없는 수정 동기화·구판 연락처 수정·화면 오류 중복과 기대문구를 보완했다. 중간 시험 코드의 using 누락으로 빌드 실패한 시도도 보존했다.
- 후속 집중 799개, 접근성 수정 후 800개, 구형 동일값 왕복 보완 후 802개가 통과했다. 첫 전체 Task는 소비 빌드 성공 후 12,992개 통과·24개 실패·환경 의존 16개 생략이었다. 정상 창고 합성 자료가 새 적재 근거를 비워 둔 탓에 명시 확인 대기로 남아 수락·사진/권한 조회·정산 23개가 연쇄 실패했고, 과거 마이그레이션을 최종 모델로 고정한 검사 1개도 실패했다. 실패 기록은 `artifacts/local/validation/20261019-192430/`에 보존한다.
- 정상 창고 자료에는 원입력 CBM·현재 판본·회전/적층을 명시하되, 실제 부분 치수 주의사항의 명시 수락 시험과 정산 당사자 검사는 유지했다. 새 migration의 고정 TargetModel을 준비하고 현재 모델·Snapshot·최신 TargetModel의 일치, 직전 모델 대비 nullable 5열만 추가하는 검사를 보완했다. 과거 TargetModel은 수정하지 않았다.
- 보완 후 창고·정산·조회·스키마를 포함한 집중 1,182개가 모두 통과했다(`artifacts/local/validation/20261019-193559/`). 최종 전체 소비 솔루션 빌드와 Task는 `artifacts/local/validation/20261019-193859/`에서 성공했다. 전체 13,017개 통과·실패 0개·환경 의존 16개 생략이며 TRX의 개별 결과와 로그를 함께 대조했다.
- 로컬 실제 Razor 화면: `artifacts/local/cargo-loading-consistency/20261019-r75/ui-r6/result.json`, 11개 검사·11개 PNG·page error 0·차단된 외부/API 요청 0. 320/390px의 성공·빈후보·실패·변경 후 재확인과 포장 입력, 1280px PC 통합 화면을 검사했다. 머리글·라벨·선택 상태·가로 넘침을 확인했다.
- 화면 응답은 명시적인 합성 메모리 자료다. 신규 서버/영속 집중 시험에는 typed 모의 HTTP, 실제 handler와 JSON 원장 자료의 격리 EF InMemory 투영을 사용하며 기존 창고·정산 회귀는 격리 SQLite 등 자체 시험 환경에서 실행한다. 스키마 비교는 DB 연결을 닫은 채 모델과 migration을 대조한다. 실제 운영 API·운영 MongoDB/MySQL 접속·실차 적재·모델 판단·단말 검증이 아니다.
- 실제 렌더에서 버튼의 `aria-checked`가 빈 속성으로 출력되는 문제를 발견해 `true`/`false` 문자열로 보완하고 선택/미선택 렌더 회귀를 추가했다. 과거 UI 검사 시도는 `ui-r1`~`ui-r5`에 보존한다. MudSelect의 숨은 입력과 중복 label/legend를 구분하도록 검사 선택자도 교정했다.

## 실제 운영과 구분

새 nullable 5열 migration은 준비만 하며 기존 운영/개발 DB에 적용하지 않는다. 실제 DB 사용 전에 스키마 적용 검토가 필요하다. 실제 차량별 제원 대조, 주문 조합·AI 가중치 학습, 운영/worker 활성화, 클라우드·휴대폰/APK 설치·금융·외부 알림·Unity·영상·commit/push는 이번 결과에 포함하지 않는다. 기존의 시뮬레이션/운영 경계와 주문·운송 전문 원장 권위는 유지한다.
