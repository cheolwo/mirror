## 사용 흐름

처음에는 사진만 등록한다. 이름·창고·공급처·계약은 첫 화면의 필수 입력이 아니다. 저장된 사진 신청은 본인 준비 목록에서 다시 열고, 나중에 이름을 붙이거나 입고 정보를 입력한다.

```text
입고 신청
├─ 사진 촬영 / 사진 선택
│  └─ 가 입고 신청
│     ├─ 응답 불명 → 같은 번호로 접수 결과 확인
│     ├─ 확정 거절 → 사진·이름 유지 → 확인 후 다시 신청
│     └─ 접수 확인 → 내 신청에서 이어서 보기
│        ├─ 이름 붙이기
│        └─ 입고 정보 입력
│           └─ 기존 동의·창고·공급처·계약 확인
│              └─ 정식 입고 한 건 연결 → 기존 수령·검수·재고 절차
└─ 직접 입력 → 기존 신청서
```

사진 신청은 실제 반입·보관 책임·재고·운임·보관료·정산을 확정하지 않는다. 기존 현장 임시 입고나 일반 입고 원장의 필수값을 가짜 정보로 채우지 않는다.

## 구현과 책임

- 기존 `/shipper/inbound/requests/new`의 기본 진입을 사진 화면으로 바꿨다. `직접 입력`과 사진 신청의 `입고 정보 입력`은 같은 route의 별도 입력 모드로 기존 신청서를 연다. 선택 사진 신청과 지도 복귀·마커·초안 문맥을 함께 유지한다. Web 지도 경유의 개인정보 동의와 정식 신청 가원장 연결은 보존한다.
- 준비 기록은 소유자·요청 GUID·이름·개정과 비공개 사진의 저장 참조/해시·날짜만 저장한다. 기존 저장소의 비공개 immutable 업로드와 재다운로드 바이트 대조를 재사용한다. 한 장5MB 이하 JPEG/PNG를 실제 디코드해 검사한다. 원본 파일명·클라이언트 제공 객체명이나 공개 URL을 받지 않는다.
- 사진·목록·이름은 기존 운영 인증·입고 역할·기능 플래그 아래 본인에게만 제공한다. DB의 대소문자 무시 정렬과 별도로 작성자 ID를 정확히 대조한다. 사진/접수 응답은 `private, no-store`로 제공한다. 이름 변경은 개정으로 충돌을 검사하고 정식 입고로 연결된 뒤에는 막는다.
- 같은 사진 요청 번호·최초 사진/이름은 같은 결과로 확인하고 내용이 다르면 충돌한다. 사진 선택/촬영 취소는 기존 사진을 유지한다. 입력 오류의 명시적 미적용과 응답 유실을 구분하며, 모호한 결과의 자동 POST는 하지 않는다. 복구 기록에는 사진·이름·Base64를 넣지 않는다. 계정 전환 시 사진·이름·목록을 즉시 지우고 늦은 응답을 버린다.
- 정식 신청의 원요청 번호는 사진 신청 GUID다. 본인 준비 기록의 개정 갱신과 기존 입고의 선택적 단일 FK를 같은 저장에 연결한다. r4 원요청 조회와 유일키를 재사용해 응답 유실·동시 신청도 같은 입고를 확인한다. 사진 없는 기존 요청의 최초 지문은 유지한다.

책임과 인계는 [입고 페이지 카드](../ProjectOverview/page-docs/SsalddelApp/SsalddelApp-P04-1/README.md)에 연결했다.

- 관계형 SQLite의 실제 제약·별도 컨텍스트·저장 경합/개정 충돌을 검사했다. 사진만 접수했을 때 실제 입고·입고상품·재고가 생기지 않고, 정식 전환은 한 입고와 같은 요청 조회로 이어짐을 확인했다. 동시에 먼저 연결된 같은 요청의 replay와 다른 내용의 충돌도 분리했다.
- 사진 유형·크기·실제 디코드, 비공개 immutable 계약과 업로드 후 해시 대조, 본인 조회·타작성자 차단·이름 동시 변경·전환 후 수정 금지를 검사했다. 저장소 시험은 메모리 adapter이며 실제 외부 저장소 접속성 시험이 아니다. Controller의 기존 역할/기능 경계·캐시 금지·짧은 처리 결과와 공통 client의 역할키·multipart 계약을 검증했다. 실제 HTTP 인증 파이프라인 시험과 구분한다.
- 새 ViewModel의 응답 유실·404·다른 번호·보호 저장 장애·삭제 미반영·명시 거절 표식/만료 후 정리 재개·계정 전환과 유휴 사진 제거·늦은 응답을 검증했다. 사진·이름은 보호 marker에 저장하지 않는다.

## 한계와 후속

기존 DB migration과 서버/클라이언트의 함께 배포는 실행하지 않았다. 운영·worker·외부 저장소 계정 설정과 공개 기능은 켜지 않았다. 사진 저장소가 준비되지 않으면 접수 성공으로 표시하지 않는다. 업로드 후 DB 저장 등이 실패하면 미참조 비공개 객체가 남을 수 있으며 자동 삭제 worker는 추가하지 않았다. 목록은 인증 소유자 후보를 정확히 필터링한 뒤 페이지를 구성하므로 매우 많은 개인 기록의 DB 페이지 최적화는 후속이다.

실제 카메라·휴대폰 재시작·실제 외부 HTTP/저장소·운영 보관·재고·지급·새 APK 설치·커밋/푸시는 이번 로컬 완료 범위와 구분한다. Web 기본 복구 저장소의 프로세스 재시작 보존도 별도다.
