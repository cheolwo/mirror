## 달라진 입력 흐름

```text
운송 의뢰 시작
└─ 1. 물품 종류·수량·취급
   └─ 2. 포장 포함 중량·길이·너비·높이
      └─ 3. 출발지·연락 대상
         └─ 4. 도착지·연락 대상
            └─ 5. 상차 시간·선택 하차 시간·요청
               └─ 6. 차량·운송 방식
                  └─ 7. 운임·지급 조건
                     └─ 8. 전체 확인·본인 동의·명시적 접수
                        ├─ 응답 확인 → 같은 의뢰 상세
                        └─ 결과 불명확 → 같은 요청 번호로 결과 조회
```

이전/다음은 같은 초안을 유지하며 현재 단계의 기존 필수값만 확인한다. 연락처 등 권고 항목을 새 필수로 바꾸지 않는다. 일반 초안은 현재 앱 세션의 입력 유지이며 재시작 후 복원을 보장하는 저장이 아니다. 접수 중복 방지·동의와 서버의 최종 검증은 그대로다.

모바일은 현재 질문·짧은 진행 표시와 이전/다음만 제시한다. 선택 정보는 해당 단계의 보조 영역에 둔다. PC의 기존 통합 조립과 상위 4단계의 enum·호환 경로를 보존하고, 실제 입력·API payload를 별도의 새 원장으로 만들지 않는다.

기존 날짜 입력이 브라우저의 정상 `datetime-local` 값을 변환 오류로 처리하는 문제를 실제 조작에서 재현했다. 날짜 문자열을 명시적으로 해석하는 작은 공통 입력으로 교체했으며, 한국 현지 시각·분/초 정밀도·빈 값과 외부 초기화 동작을 보존한다. 최종 확인의 권고 사항도 출발지/도착지/일정/비용 중 실제 수정할 단계로 연결한다. 권고를 새 필수 조건으로 바꾸지 않는다.

## 현장에서 드러난 연결 문제

- 휴대폰은 USB 승인 상태로 확인했다. 기존 통합앱192의 작성 화면을 읽고 상하차·시간이 함께 나온 이전 대표 화면을 새 비공개 자료로 보존했다. 이전 화면은 새 소스 검증으로 사용하지 않는다.
- 최신 자격 모델을 쓰는 격리 서버가 기존 시험 DB의 실차 참조 열 부재로 시작하지 못했다. 기존 표 구조·행 수·소스 해시를 보존하고 **전용 `mirror_ai_device_r114_20261019`에만 r71 신규 Up의 nullable 실차 참조 2열·전문표 1개를 추가**했다. 전체 migration이나 운영/사용자 DB를 갱신하지 않았고, 없는 과거 migration 이력을 만들지 않았다.
- 서버의 `/drivers/me` GET은 배포 기능 분류 누락으로 404였다. 그 읽기 동작만 기존 국내운송 기능에 분류했다. 등록 POST·전역 필터·기능 기본값·다른 관리 API를 열지 않는다. 소스와 시각만으로 반영을 주장하지 않고 재빌드된 실제 DLL의 메타데이터·도구 사본 해시 일치·합성 인증으로 GET 200을 확인했다.
- 실제 화주 차량추천 조회는 200이지만 시험 차량제원이 비어 후보 0개였다. 화면의 기존 일반 선택과 실제 서버 추천 확보를 구분한다. 차량추천 조회는 주문·추천 배차·계약 생성이 아니다.
- 격리 서버 live 200과 ready 503은 다르다. 과거 EnsureCreated 시험 환경의 미적용 migration 문제는 이번 세 항목 추가로 해결됐다고 주장하지 않는다.

### 실기기 198에서 발견한 단계 전환 문제

0.1.198을 기존 192 위에 데이터 삭제 없이 설치하고 설치 APK와 인계 APK의 SHA-256 일치를 확인했다. 합성 계정 로그인·실제 시작 버튼·물품 입력·다음 화면 이동까지 진행했다. 첫 자동화는 URL 변경 직후의 이전 DOM을 너무 일찍 읽어 중단됐으며, 렌더된 현재 단계가 준비될 때까지 기다리도록 별도 수정했다. 이것을 입력 화면 혼합으로 판정하지 않는다.

별도로 실제 `main.shipper-mobile-shell__content`에 이전 스크롤 365.5px가 남아 새 제목이 화면 위 -293.5px에 가려진 것을 확인했다. 모바일 단계가 처음 표시되거나 바뀔 때만 새 제목을 포커스해 중첩 스크롤도 시작 위치로 맞추도록 보완했다. 같은 단계의 입력 렌더·PC 통합 입력에서는 포커스를 옮기지 않는다. 198의 실패 화면과 원본 증거는 비공개로 유지하고 후속 199의 설치/단계 전환 증거와 구분한다.

첫 전체 Task는 소비 솔루션 빌드 성공 후 12,871개 통과·16개 환경 의존 생략·1개 실패였다. `/drivers/me`가 이제 기능 분류를 갖는다는 변경을 반영하지 못한 이전 시험의 기대 오류 코드였으며, 기능 OFF 조회 차단과 여전히 미분류인 등록 POST 차단을 각각 확인하도록 시험을 보완했다. 이 실패는 보존하며 앞선 Fast-r5 결과와 전체 재검증을 구분한다.

### 실기기 199에서 확인한 동일 페이지의 경로 갱신 문제

`artifacts/local/mobile-context-authoring-r72/transition-199-r3.json`에서 URL은 `/shipper/request/dropoff`로 바뀌었지만 진행 표시는 **3단계**, 화면은 이전 **출발지 입력**인 상태를 재현했다. 새 입력 없이 4초 이상 재관측해도 그대로였고, 기록의 스크롤 약 243.2px·제목 위치 약 -171.2px도 유지됐다. 입력을 벗어나거나 다시 렌더된 뒤에야 새 단계가 표시됐다. 이는 198의 단순 중첩 스크롤 보존과 다른 연결 문제다.

모바일과 Web의 `ShipperRequestMobileContextPage`는 포장·출발지·도착지·일정·차량 다섯 경로를 같은 Razor 컴포넌트로 처리한다. 현재 단계를 `Navigation.Uri`에서 읽으면서 경로 변경 구독이 없어, 같은 컴포넌트가 재사용될 때 URL만 바뀌고 화면 갱신이 빠졌다. ### 실제 UI 접수와 후속 API 시험의 구분

실기기에서 **계좌이체**를 선택해 접수한 동일 의뢰는 `cb136458-2631-ce61-c0e9-9adb53e6216b`다. 접수 후 `/shipper/request/{id}`로 이동한 실제 화면(`device-request-receipt-200.png`)과 본인 의뢰 GET·격리 정본을 대조했다. 원 UI 결과는 **생성됨 / 결제대기**, 연결 운송은 **대기·추천 라운드 0·선택/확정 기사 없음**이었다. 이는 실제 결제·입금·배차 또는 배송 완료가 아니다.

먼저 선택한 현금성 정산은 클라이언트 사전 검사에서 막혀 요청 번호 생성·등록 POST까지 가지 않았다. 이후 계좌이체를 선택한 같은 입력 UI에서 정상 접수했다. 이때 오류 안내가 긴 최종 확인 화면의 상단에 있어 화면 밖으로 가려지는 사용성 문제는 **잔여 보완**으로 남긴다. 허용되지 않은 결제 조건을 우회해 접수한 것으로 기록하지 않는다.

UI에서 입력한 요청사항은 GET의 `요금옵션.요청사항`에 `null`로 표시되는 조회 매퍼 차이가 발견됐다. 같은 의뢰·격리 실행·DB에 결속된 정본 검증 경로에서 저장된 법정동 시험 표지를 확인했다. 입력이 저장되지 않았다고 단정하거나 전체 요청사항이 정상 조회됐다고 표시하지 않는다. 표지는 합성 시나리오 레이블이며 실제 GPS·주소의 법정동 판정 근거가 아니다.

원 UI 응답을 별도로 보존한 다음, **정상 API를 이용한 후불 조건 변경·승인은 별도 운영 시나리오 준비**로 수행했다. `api-workflow/.private/`의 원 UI 응답·변경 전후·승인 후 정본과 명령 기록으로 구분한다. 후불 승인 성공을 휴대폰 화면에서 결제하거나 승인한 것으로 합치지 않는다.

같은 의뢰로 AI 추천을 요청했으나 **409 `NoComparableAllowedCandidate`**로 추론 전에 차단됐다(`aiApplied=false`, `fallbackUsed=false`). 원 UI의 중량과 3개 치수는 저장됐지만 `부피Cbm`·수량은 `null`이었고, 시험 기사 두 명의 적재 부피 한도는 각각 **1,000L**였다. 이 상태에서는 부피 비교 자료가 없어 허용 후보를 구성하지 못했으므로 AI의 판단·기사 추천·배너·수락 통과를 주장하지 않는다.

후불 승인 뒤 같은 의뢰에 부피를 추가하려던 정상 수정도 **409 `FreightCoreConditionsLocked`**로 차단됐다. 승인 후 핵심 운송 조건을 잠그는 기존 보호를 해제하거나 DB를 직접 고치지 않았다. 해당 의뢰·원 UI 응답·실패 명령을 보존하고, 필요한 비교 자료를 갖춘 **아래 새 UI 의뢰**로 추천·수행을 따로 확인했다. 새 의뢰의 성공을 이 첫 의뢰의 성공으로 바꾸지 않는다.

### 새 UI 의뢰의 실제 AI 추천·수락·촬영·운송 완료

같은 APK200의 실제 휴대폰 입력에서 **수량 1·부피 0.004㎥**를 명시한 새 의뢰 `c0931d6a-0765-9126-2eba-c921ffc26d25`를 접수했다. 원 UI 조건은 앞선 사례와 같이 **선결제·계좌이체 / 결제대기**이며, 영수증 상세 URL은 `volume-submit-200.command.json`과 `device-volume-request-receipt-200.png`로 남겼다. `phone-flow-200-r4-volume`은 보조 문구가 포함된 결제 버튼을 정확히 `계좌이체`라고만 찾다가 멈췄다. 실제 표시를 포함하는 선택자로 같은 초안을 이어 접수했으며, 실패를 새 중복 주문 생성이나 제품의 결제 오류로 분류하지 않는다.

원 UI 응답을 `api-volume-workflow/.private/ui-submitted-order.original.json`에 보존한 뒤 **별도 정상 API로 후불 조건 변경·승인**을 준비했다. 실제 결제를 수행하거나 휴대폰의 원 접수 조건이 후불이었다고 표시하지 않는다.

```text

└─ 별도 API 후불 시험 준비·승인
```

서버가 허용한 후보 안에서 실제 **`qwen3:1.7b`** 응답을 받아 `cargo-journey-driver-b`를 선택했고, 추천 적용 응답과 정본이 일치했다. 기록은 `applied=true`, `phase=Applied`, `fallbackUsed=false`, **운송 7·추천 라운드 1**이다. 이유 코드는 `LONGER_WAIT_SCORE`·`SERVER_ALLOWED`로 남겼다. 이는 이번 한 시나리오의 실제 모델 추론·추천 적용 확인이며 모델 가중치 학습이나 전체 배차 정확도 검증이 아니다.

실제 휴대폰에서 해당 기사로 로그인하고 추천 조건·보수 **6,200원**을 확인한 뒤 두 확인 항목을 체크해 참여를 수락했다. 이어 지도 업무의 상차지 도착 확인, 상차 화면의 현장 확인·사진 저장, 하차지 도착 확인과 하차 저장을 같은 운송으로 이어갔다. `screens/device-volume-offer-*.png`, `device-volume-pickup-*.png`, `device-volume-dropoff-*.png`에 단계별 화면을 보존했다. 외부 푸시가 먼저 배너를 띄웠거나 알림음이 울렸다는 검증으로 합치지 않는다.

카메라는 첫 사용 시 **앱 사용 중 권한**을 허용해 실제 촬영 앱을 열고 촬영 후 **확인**을 눌러 돌아왔다. 상차·하차는 각각 별도로 촬영했으며, 앱에 `선택한 사진: work-photo.jpg`가 표시된 뒤 현장 확인을 거쳐 **상차 확인 저장 / 하차 확인 저장**을 눌렀다. 상차 인수증에서는 실제 서명문서 확인을 체크하지 않고 생략 동의와 사유 **“합성 현장 사진 촬영 시험이며 실제 서명문서 없음”**을 사용했다. 합성 서명문서나 사진 API 대체 업로드로 실제 촬영을 대신하지 않았다.

하차 저장 뒤 실제 앱은 **인수완료**와 저장된 상태 확인을 표시했다. `api-volume-workflow/.private/api-state.json`의 `cases.r72-ui-volume-order.latestProof`에서 같은 의뢰·운송 7의 **인수완료 / stage 90 / 확정·수행 기사 b / 동결 보수 6,200원**과 사진 두 장의 `bindingVerified`·`completionLinked`·`storageIntegrityVerified`가 모두 `true`임을 대조했다. 상차 사진은 165,513바이트·SHA-256 `73d8bd5aae8717352ce8af8944bcf3bf352ec9a4deb017bf150cf8b55615c718`, 하차 사진은 165,827바이트·SHA-256 `c0d3ab9b5222b45c130a0c619c64475db6819275330859d4305b50f0dde838d7`로 서로 다르다. 정본 endpoint는 촬영 기기 자체를 인증하는 도구가 아니므로 그 안의 `deviceVerified`·`actualCameraCaptureVerifiedByThisEndpoint=false`를 바꾸지 않는다. 실제 카메라 동작은 별도 휴대폰 화면·조작 기록으로 확인했다.

06:47:45 UTC의 첫 완료 직후 proof에서는 운송 정본은 완료됐지만 Mongo 원장이 **진행중 / 하차지도착**이었다. 이 초기 조회 지연을 보존하고 **06:49:02.0783546 UTC에 같은 의뢰를 다시 조회**해 Mongo의 `available`·`exists`·`rdbProjectionExists=true`, **완료 / 인수완료** 수렴을 확인했다. 별도 복구 명령이나 DB 직접 수정 없이 후속 투영이 완료됐으며 즉시 동기 완료로 기록하지 않는다. 정산은 계속 **입금대기**이고 알림 outbox는 **Pending 1개·발송 시도 0회**다. 외부 FCM 수신·배너 자동 표시·알림음·실제 지급은 이번 성공 범위에 포함되지 않는다.

통합 화물 지도의 SDK 키 미설정과 위치 갱신 실패가 있었으며, 대체 목록과 업무 화면으로 수락·상하차를 이어 완료했다. 지도 타일·현위치·실제 이동 경로가 정상이라는 검증은 아니다. 서버의 준비 상태 **503**도 남아 있으며, 로컬 업무 API 통신과 운송 완료를 외부 공개 운영 준비 완료로 확장하지 않는다.

### 통합 화물기사 화면의 사진 촬영 연결

기존 통합 상하차 입력(`/workspace/cargo-driver/transports/{id}/pickup`, `/dropoff`)에는 파일 선택만 있었다. [공통 사진 입력](../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Cargo/CargoTransportActionScreen.razor)이 이미 등록된 `I업무사진촬영Adapter`·[기존 MAUI 촬영 adapter](../../Ssalddel.Client.Infrastructure/Native/Maui업무사진촬영Adapter.cs)를 재사용해 지원 기기에서 **사진 촬영**을 열도록 연결했다. 새 카메라 서비스·사진 원장·완료 API를 만들지 않는다.

- 선택한 파일과 촬영 사진은 [같은 검증·업로드 경로](../../Ssalddel.Ui.Common/Areas/App/RoleWorkspace/Cargo/CargoTransportActionViewModel.cs)를 사용한다. 공통 선택 검사는 기존 **8MB 이하 JPG·PNG·WebP**를 유지하고, 재사용 네이티브 촬영 adapter의 기존 5MB 한도도 유지한다.
- 촬영만으로 상차·하차를 완료하지 않는다. 현장 확인과 사진을 확인하고 **상차 확인 저장 / 하차 확인 저장**을 눌러야 기존 사진 업로드·상태 변경·같은 운송 재조회 절차가 이어진다.
- 재촬영을 시작한 뒤 취소·권한 거부·오류가 나면 이전 사진을 조용히 재사용해 완료하지 못하도록 차단한다. 다시 촬영하거나 현장 사진을 명시적으로 선택해야 완료 조건이 풀린다. 로그인·운송·작업 수명 확인도 유지한다.

코드의 취소·권한 거부·오류 보호는 집중시험으로 확인했다. **APK200의 실제 카메라 열기·상차/하차 별도 촬영·확인·업로드·저장과 운송 정본 완료는 위 새 의뢰에서 확인**했으며, 실제 기기에서 취소·권한 거부·촬영 오류까지 재현한 것으로 확대하지 않는다. 합성 이미지 API 시험이나 별도 기사 앱의 촬영 성공을 이번 증거로 사용하지 않는다.

휴대폰 관찰과 서버 응답을 결합한 최종 로컬 기록은 `artifacts/local/mobile-context-authoring-r72/device-200.completed-local-evidence.json`이다. API 자체의 기기/촬영 미인증 표시는 보존하고 실제 촬영 UI·설치 APK·같은 의뢰·사진 해시를 별도 근거로 연결한다.

후속 보완에서는 선택 부피가 실제 기사 적재 검증에 필요한 경우 접수 전에 알리는 것, 거절된 결제 조건의 오류를 제출 위치에서 보이게 하는 것과 저장된 요청사항의 조회 매퍼 차이를 먼저 다룬다. 파일 선택 UI의 8MB·WebP 안내와 실제 서버 사진의 JPEG/PNG·5MB 한도도 맞춰야 한다. 이번 네이티브 촬영 두 장은 모두 JPEG·5MB 미만이며 이 파일 선택 계약 차이까지 해소한 것은 아니다.
