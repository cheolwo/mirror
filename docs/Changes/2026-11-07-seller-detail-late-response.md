# 판매자 상세에서 늦은 이전 주문 응답 차단

판매 주문 B의 상세를 읽는 도중 주소가 C로 바뀌면, 요청 ID만 C로 바뀐 채 공통 중복 실행 방지가 C 조회를 막았다. 이후 B의 늦은 응답이 C 주소의 상세로 표시될 수 있었다. 선택을 해제해도 이전 조회가 취소를 무시하면 상세가 다시 나타나는 경로도 있었다. 실제 상세 ViewModel의 지연 응답 시험 두 개로 수정 전 두 실패를 재현했다.

## 변경 범위

[작업 상태 기반](../../Ssalddel.Ui.Common/Areas/App/ViewModels/공동구매작업ViewModelBase.cs)에 상세 읽기가 명시적으로 사용하는 최신 조회 실행·초기화 helper를 추가했다. 기존 명령의 `작업실행Async`와 중복 제출 방지 경로는 유지한다. 새 helper는 이전 요청의 성공·오류·완료 처리가 최신 조회의 상태를 덮지 못하게 하고, 현재 요청의 명시 취소는 취소 상태로 정리한다.

[판매 주문 상세 VM](../../Ssalddel.Ui.Common/Areas/App/ViewModels/판매채널주문페이지ViewModels.cs)만 이 경로를 사용한다. 조회 세대·주문 ID·취소와 주입된 기존 계정/세션/서버 문맥을 확인한 뒤 본문을 반영한다. 응답 주문 ID가 다르면 새 상세로 채택하지 않는다. 선택 해제·잘못된 ID는 이전 요청의 게시 권한과 상세를 함께 비운다. 실제 UI 서비스 등록의 기존 `IWorkflowRecoveryContext`를 사용하고, 주입된 문맥 확인 실패를 건너뛰지 않는다. 기존 직접 생성 호출의 호환성은 유지한다.

공용 화면·HTML 구조·CSS·API·상태 전이·목록 검색과 복귀 조건은 바꾸지 않았다. 존재하지 않는 상세는 기존 Client의 404 허용→null→찾을 수 없음 계약을 따른다. 조사에서 별도로 찾은 미조회 필터 복귀(S2), 현재 페이지만 0건인 목록(S3), 운영자 기사/메모(O1·O2)는 이번에 수정하지 않았다.

## 검증

구현·시험 4개 경로를 지정한 Fast에서 관련 시험 **107개 통과·실패 0개**다. Tests 빌드 경고 235개·공용 UI 빌드 경고 0개, 오류는 모두 0개다. 로그는 `artifacts/local/validation/20261107-170149`이다. 신규 VM 경합 20개와 실제 공용 화면 연결 4개를 포함한다.

- VM: 이전 조회 중에도 최신 주문을 실제 조회한다. 늦은 이전 성공·실패·취소, 최신 실패 후 이전 성공, 같은 ID 재조회, 선택 해제·잘못된 ID·직접 취소를 대조했다. 이전 요청이 최신 성공/오류·로딩·완료 시각을 바꾸지 않으며 반환 ID 불일치·null·기존 404 계약을 구별한다. 세션·서버 변경과 주입된 문맥 확인 실패도 검사했다.
- 실제 공용 컴포넌트: 같은 인스턴스에서 A 정상→B 지연→C 전환과 최초 B 초기화 도중 C 주소 적용을 각각 늦은 B 성공·실패로 검사했다. C의 주문 4301·출고 라인 3개·수량 18개가 남고 B 내용과 오류가 표시되지 않는다. 상세 단독 조회에서 목록 조회는 0회다.
- 기존 관련 회귀: 목록/상세 VM, 판매자 접근 재확인·입력 보존, 판매 주문 읽기·경로 계약, 기존 업무 실행 기반과 공동구매 화면을 함께 검사했다.

같은 4개 경로의 마감 Task는 통합 `Ssalddel.v3.5.slnx` 소비 빌드 오류 0개·경고 138개, 전체 시험 **17,355개 통과·환경 의존 17개 생략·실패 0개**다. 로그는 `artifacts/local/validation/20261107-170316`이며 검증 이후 제품·시험 소스를 바꾸지 않았다.

실제 Razor 컴포넌트와 실제 VM에 격리 서비스 응답을 연결한 .NET 렌더·매개변수 시험이다. 브라우저 C# 업무 클릭·실제 라우터 뒤로 가기·키보드 초점, 서버·DB·실기기·운영 사용은 이번에 실행하지 않았다. 외형을 변경하지 않아 루트 README와 [기존 가상 정상 상세 캡처](2026-11-07-seller-order-detail-metrics.md)는 보존했다. 과거 캡처를 이번 지연 응답의 브라우저 재현 근거로 쓰지 않는다.
