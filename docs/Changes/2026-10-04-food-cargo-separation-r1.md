# 음식 배달·화물 자동 배차 분리 r1

음식 후속 재탐색·추천 만료·알림이 화물 실행 조건에 묶여 있던 문제를 분리한다. 음식 업무를 활성화하고 화물을 비활성화한 구성에서도 음식 자신의 후속 작업을 실행할 수 있다. 사용자는 앞서 제안한 우선순위 1번을 진행하면서 두 배달 업무의 분리를 확실하게 해 달라고 요청했다.

화면 없음: 서버 배차 작업과 저장 Port 변경이다. 기존 API·이벤트 payload·DB 식별자와 데이터, 업무 앱 UI는 유지한다. 별도 서버·DB 구축이나 새 APK 적용 결과는 아니다.

## 실행 책임

| 구분 | 음식 배달 | 화물 운송 |
| --- | --- | --- |
| 실행 직전 확인 | Operational + FoodDeliveryWorkflow | Operational + DomesticTransportWorkflow |
| Workload | FoodDeliveryDispatch | DomesticTransportDispatch |
| 배치 설정 | FoodDeliveryDispatchJobs | DispatchQueueJobs |
| 큐/만료/알림 대상 | 음식배달 유형 | 용달운송 유형 |
| 후보 없음 | 음식 재탐색 대기 | 기존 화물 공개배차·시간창 정책 |
| 기사 추천 기록 | 음식 전용 Port + FoodDeliveryDriverApp 확인 | 기존 화물 기사 상태 Port |

두 업무의 Quartz 큐 스캔·추천 만료·추천 알림 JobKey와 trigger를 분리한다. Simulation에서는 두 자동 배차 작업을 등록하지 않으며 직접 호출되어도 실행 정책이 차단한다. 기본 기능 공개 상태나 운영 모드를 자동 활성화하지 않는다.

알림 배치는 큐 ID·요청 ID·업무 유형을 함께 확인한 뒤 자기 업무의 한도를 적용한다. 반대 업무의 대기 Outbox가 먼저 있어도 자기 배치를 소비하지 않는다. 기존 `대기알림발송Async`는 화물 호환 경로이고 음식은 업무유형별 Port를 사용한다. 음식 기사의 추천 기록은 화물 Service에 위임하지 않으며 기존 대기시간/Aging 초기화 의미를 유지한다. 음식의 직접 화물 공개배차 호출도 차단한다.

기기 푸시는 `IDriverPushTokenStore.GetForAppAsync`에 대상 AppKey를 명시한다. 과거 기사 ID 전용 토큰은 화물 앱 토큰으로만 취급하고 음식·미확인 앱으로 대체하지 않는다. 현재 Redis/InMemory 저장소와 공개 토큰 등록은 음식 앱의 별도 기기 토큰을 제공하지 않는다. 이 경우 음식 알림은 외부 전송 없이 실패 상태로 기록하고 화물 알림은 그대로 둔다. 음식 앱 토큰 등록·실제 FCM 수신은 후속 보완이며, 이번의 배치 격리·모의 발송 시험을 실제 앱 알림 완료로 보고하지 않는다.

## 설정

음식 기본값은 큐 스캔 30초, 추천 만료 정리 30초, 알림 15초, 배치 100건, 후보 재탐색 30초다. `FoodDeliveryDispatchJobs`에 각각 `큐스캔주기초`, `추천만료정리주기초`, `알림발송주기초`, `처리배치크기`, `후보재탐색간격초`를 설정한다. 화물의 주기·한도를 음식에 복사하지 않는다. 과거 `DispatchQueue:음식배달후보재탐색간격초`만 새 음식 값이 없을 때 호환하고 새 값이 있으면 우선한다. 시작 시 scheduler 등록과 실행 중 Options는 같은 binding 규칙을 사용한다.

공용 `배차큐정책Options`의 기존 추천 유지시간 등 호환 정책과 실행 인덱스/Outbox/RDB 형태는 남아 있다. 각각의 업무 전용 계산·상태·앱을 같은 정책으로 합치지 않으며, 물리 저장소를 나누는 DB migration은 수행하지 않는다.

## 검증

최종 Fast `20261004-182837`은 서버·시험 프로젝트 빌드와 관련 시험 **96/96**을 통과했다. 음식·화물 기능 플래그 4가지 조합, Simulation/취소 차단, 혼합 DB FIFO·배치 한도, 음식 후보 없음 재탐색·만료 후 다음 후보, 마트 준비 전 차단·포장 완료 인계, 업무별 Outbox와 대상 앱 토큰, 기존 화물 공개배차·추천 기록·음식 요금 의미를 검증한다. 등록 시험은 시작하지 않은 실제 Quartz scheduler에서 두 업무의 JobKey·type·주기를 조회한다.

초기 검증에서 신규 시험의 namespace/fixture 참조를 보정하고 서버 참조 어셈블리를 재빌드했다. Quartz의 프로세스 공용 logging provider가 폐기된 시험 LoggerFactory를 재사용하던 시험 수명 문제는 폐기되지 않는 NullLoggerFactory로 격리했다. 이 과정의 실패 로그는 보존하며 최종 Fast 성공 판본과 구분한다.

초기 전체 시험은 기존 음식 생명주기 factory의 새 음식 추천 Port 누락으로 두 성공 경로가 실패했다. 해당 factory에 음식 전용 시험 Port를 주입하고 화물 상태 Port를 호출하면 실패하도록 보강했다. 실제 음식 요금·가격 동결·수령 확인의 기존 시험 내용은 유지했다.

최종 Task `20261004-182913`은 `Ssalddel.v3.5.slnx` 전체 빌드를 통과했고 전체 시험은 **6,782/6,789**다. 기준 `20261004-165504`의 6,726/6,733과 대조해 신규 **56개 전부 통과**, 새 실패 0·기존 결과 변경 0·삭제 0을 확인했다. 기존 7개 실패는 이름·메시지·전체 스택까지 동일하다. 전체 시험 게이트는 기존 실패로 미통과다. 최종 비교는 `task-result-comparison.json`에 보관한다.

이번 변경은 제품·시험·문서 31경로다. 최종 Fast 이후 제품/시험 26개 파일의 SHA-256 변경 0과 범위 밖 기존 dirty 128개의 변경 0을 확인했다. 문서의 최종 결과 갱신 후 링크와 좁은 diff 공백 검사를 확인한다. 원본·좁은 변경 경로·실행 로그·TRX는 `artifacts/local/food-cargo-separation-r1/`에 보관한다. Operational 배치의 SQLite 회귀는 실제 DB 선택/저장과 격리된 Port를 사용하고 추천 기록 단위시험은 EF InMemory 재조회를 사용한다. 운영 서버의 실제 외부 푸시나 휴대폰 수신 증거로 확대하지 않는다. 새 APK·커밋·푸시는 수행하지 않았다.
