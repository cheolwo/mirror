# 음식점 설정을 닫았다 열 때 미확정 요청 보존

2026-11-05 r21. 현재 수신함의 배송 지원 설정을 저장한 뒤 응답을 잃으면 VM이 원 요청 번호·본문·판본을 보존한다. 그러나 설정 패널을 닫았다 열면 새 VM을 만들어 ‘원 설정 변경 결과 확인’ 문맥이 사라졌다. 송신 중 재열기에서도 다른 VM의 저장을 허용하는 경로를 실제 원본 OrderInbox/Panel/VM으로 재현했다.

## 최소 보완

같은 수신함 페이지가 [음식점배송지원설정Session](../../RestaurantDeskApp/Services/음식점배송지원설정Session.cs)을 소유하고 기존 패널의 ViewModel parameter로 같은 VM을 전달한다. 기존 조건부 패널·버튼·경로·서버 정책을 유지한다. 미확정/송신 중에는 기존 Load/Save 가드가 입력·원 요청과 중복 차단을 보존하며 재열기만으로 PUT를 보내지 않는다. 결과 확인은 사용자의 기존 명시 행동이다.

재사용 범위는 사용자·로그인 세대·인증 토큰의 단일 양수 음식점 claim·현재 endpoint 문맥이다. 클라이언트 설정의 식당 번호를 권한으로 쓰지 않는다. 정상 같은 음식점의 토큰 갱신은 VM을 유지하지만 다른 계정/식당·새 로그인·claim 누락/오류·로그아웃/페이지 종료는 이전 VM 재사용을 막는다. JWT 읽기는 로컬 문맥 격리이며 권한은 서버가 검증한다.

매 요청은 기존 AuthService로 자격을 캡처해 그 토큰만 공급하는 요청별 provider와 실제 Json/ProtectedClient를 사용한다. 전후 문맥과 응답 식당도 대조한다. 전후 검사만으로 공용 API가 새 식당 토큰을 늦게 읽는 경로는 충분하지 않아 이 결속을 보완했다. 이미 보낸 요청의 취소·서버 미적용을 보장하는 것은 아니다.

현재 토큰의 확정401은 기존 AuthService의 원 토큰/사용자/세대 확인을 거쳐 해당 인증만 종료한다. 오래된401은 새 인증을 지우지 않는다. 공용 VM의 `Value=null + pending 유지`로 재확인 버튼과 재조회가 모두 막히는 경로를 피하며 자동 PUT 재전송은 추가하지 않는다.

## 범위와 검증

같은 페이지의 pending·송신 상태를 보존하는 내부 수명 보완이다. 새 설정 route로 옮긴 제안4 전체 구현, 미전송 일반 초안·페이지 이탈·프로세스 재시작의 영속 복구는 아니다. 공통 Panel/VM·금액/지원 정책·서버/DTO/API/DB는 변경하지 않는다.

`artifacts/local/app-stability-r21/a6a5998f594840c58f7a1ff41ce37cfd/`에서 동결 원본·실제 호스트 렌더와 합성 HTTP/원 요청 관측을 보존했다. 이전 단순 API 중간 비교와 토큰 결속 보강 전 소스/출력도 남기고 최종 실제 Json/ProtectedClient 경로와 구분한다. 원본/현재 소스·시험/TRX·소비 빌드와 필수 Task, 서버/기기 확인과 재개는 `completion.json`을 따른다.

등록 기기의 기존 화주146/원앱230·공유 잠금·기기/paused checkpoint는 읽기로 대조했으나 다른 전면 작업을 보존했다. 이 설치본을 음식점 화면 검증으로 쓰지 않는다. 별도 검토 APK 준비/설치·휴대폰 입력·거절된 미리보기/중계 재시도는 없다. 실제 CSS/뷰포트·실휴대폰/운영 검증과 합성 호스트/HTTP 시험은 별도다. 실제 설정 저장·청구/결제/지급·운영 활성화·commit/push는 없다.
