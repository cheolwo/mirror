# 기사 업무 선택과 공통 수락 보호 r71

기사 한 사람이 음식·소형 물품 퀵·화물의 희망 업무를 선택하고, 직접 피킹을 별도 선택하도록 연결했다. [승인 범위](../AI/Planning/공통/PLAN-OPERATIONS-NEIGHBORHOOD-MICRO-HUB/driver-participation.implementation.r71.md)와 [작업 명세](../AI/Planning/공통/PLAN-OPERATIONS-NEIGHBORHOOD-MICRO-HUB/driver-participation.r71.work-order.json)를 따른다. 이번 구현은 직전 제안의 우선 1·2번과 이를 편집할 설정 화면이다. 지도 전체 통합·APK 합병·다른 역할 앱 확대는 후속이다.

## 기사 화면

DriverApp의 기존 `/driver/work/settings`와 음식 기사 앱의 내 정보 → `받을 업무·적재 설정`이 같은 공통 폼을 사용한다. 받을 업무, 차량·적재 조건, 추가 배차의 세 섹션이다. 차량 종류·사용 가능 중량 kg·부피 L·희망 동시 업무 수·음식/물품 분리 가능 여부를 입력하며 모르는 제원은 빈 값으로 보존한다. 희망 선택이 실제 기사 자격이나 차량 제원을 바꾸지 않는다.

저장은 기대 판본으로 한 번 요청하고 동일 계정의 정본을 다시 읽는다. 저장 응답 또는 재조회가 불명확하면 입력·재전송을 잠그고 결과 확인으로 이어진다. 재조회에서 변경 전·동일 저장·다른 최신 설정을 구분한다. 계정/로그인 판본 변경, 페이지 종료와 늦은 응답을 보호한다. 운행 시작/종료, 기존 지도·픽업/전달 카드·운임은 유지한다.

## 서버와 원장

- `GET/PUT api/v1/driver/work-participation`은 인증된 기사 본인만 사용한다. 요청 DTO에 임의의 기사 ID를 받지 않는다. 현재 활동 가능한 음식 또는 화물 프로필을 확인하고, 희망 조건은 실제 수행 자격과 구분해 응답한다.
- `driver_work_participation`의 사용자별 고유 행에 희망 조건과 `Revision`, 별도 `WorkLockRevision`을 둔다. 설정 CAS 갱신과 음식 단건/묶음·화물·마트 수락이 같은 SQL 행 잠금을 사용한다. 사용자 조건 판본을 수락 때 올리지 않는다.
- 미완료 확정 운송과 취소 후 실제 물품을 보유한 분산 주문을 원 운송 ID로 중복 없이 읽는다. 직접 피킹은 기존 분산 주문 연결로 판정하며 새 원장에 업무 상태·정산 상태를 복제하지 않는다.
- 일반회원 배송의 배타 보호, 음식 최대 3건, 기존 화물 차량·시간창·혼적 적합성, 분산 순회의 다른 업무 보호와 사진/바코드 검증은 유지한다. 공통 희망 상한이 기존 전문 한도를 확장하지 않는다.
- 음식·화물·마트 제안 조회와 공개 콜, 실제 후보 선정, 추천 저장·알림 생성 직전에도 희망과 직접 피킹·현재 여력을 검사한다. 요금 계산을 기다리는 동안 의사가 바뀌면 추천을 보류한다. 수락 당시에는 최신 SQL 사실을 다시 검사한다.
- 동일 기사의 기존 수락·완료 영수증 재생은 새 희망 조건으로 막지 않는다. 설정을 끄거나 한도를 줄여도 이미 수락한 업무의 조회·진행·완료는 유지한다.
- 분산 묶음 계획은 전체 운송 ID를 함께 검사한다. 계획 후 희망 한도가 바뀐 경우도 첫 개별 수락 전에 전체를 다시 검사해, 이미 알려진 한도 초과로 일부만 수락되는 일을 막는다. 이 사전 검사는 용량 예약이 아니다. 개별 화물 수락은 기존 별도 트랜잭션을 사용하므로 그 이후의 경합·전문 조건 실패는 기존 `AcceptancePending` 복구로 남으며 묶음 전체의 원자적 수락을 보장하지 않는다.

## 현재 허용 범위

한 기사에게 음식과 물품의 희망을 함께 보관하고 업무가 끝난 뒤 다른 종류로 전환하는 기반을 구현했다. 기존 검증된 유형 내 다건 수행은 전문 규칙과 공통 희망 상한을 모두 만족해야 한다. 같은 화물 실행 흐름의 퀵·화물도 기존 차량/일정 규칙을 통과해야 한다. 확인된 화물 중량·부피와 기사 입력 한도를 비교하며, 한도를 입력했는데 비교할 물품 값이 없으면 근거 부족으로 보류한다.

음식과 화물을 동시에 수행하는 경로는 음식 적재량·전달 기한 등의 공통 근거가 아직 없으므로 추천과 수락을 보류한다. 분리 가능 체크만으로 혼적을 허가하지 않는다. 개별 물품 전달 순서에 따른 정확한 여유 회복과 교차 유형 전체 경로 최적화는 후속이다. 현재 중량/부피의 보수적 합산을 최적 경로 계산이라고 표현하지 않는다.

공통 잠금은 같은 인증 사용자 기준이다. 같은 물리 차량을 여러 다른 계정이 공유하는 경우의 차량 식별·공동 용량 예약을 구현한 것은 아니다. 차량 종류 선택도 물리 차량 ID나 실제 제원 검증을 대신하지 않는다.

전체 Task의 건너뜀 16개는 MySQL 환경값을 지정하지 않은 시험 1개와 MongoDB 환경 의존 시험 15개다. MySQL 한 개는 위의 별도 실제 격리 DB 실행으로 확인했으며 MongoDB 15개를 이번에 실행했다고 표시하지 않는다. 초기 HTTP 헤더 fixture와 API 메타데이터 이름 검사에서 발견한 문제는 수정한 뒤 최종 Task를 다시 통과했다.

공통 Razor 6개 상태의 정적 렌더는 네이티브 터치/화면 배치 검증과 구별한다. 인증 HTTP 시험의 fixture 로그인은 실제 운영 JWT·휴대폰 인증을 대신하지 않는다. MySQL 두 연결 시험도 전체 음식/화물 업무의 여러 서버 HTTP 경합이나 실기기 시험을 대신하지 않는다. 기존 0.1.70 APK·GCS 배포 준비 manifest는 보존했으며 이번 r71 화면/정책을 포함한다고 표시하지 않는다.

`SharedDriverWork:Enabled`는 기본 OFF이며 설정은 준비 목적으로 저장할 수 있다. ON인 환경에서는 설정 없는 기사의 신규 제안과 수락을 보류한다. 기존 Operational 기능 플래그를 켜거나 기존 기본값을 바꾸지 않았다. migration은 준비하며 공용 DB에 적용하지 않는다. 로컬 격리 DB 시험·클라우드 운영·실운행·실입금은 별도다. 이번 변경을 넣은 새 APK 배포·휴대폰 설치·commit/push는 수행하지 않는다.
