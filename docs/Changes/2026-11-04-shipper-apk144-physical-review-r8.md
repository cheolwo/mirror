# 화주 APK144의 작성·최종 검토·입력 복귀 확인 r8

[r7의 늦은 초안 조회 무효화](2026-11-04-shipper-initialization-stale-draft-r7.md)를 포함한 준비된 APK144를 등록 USB 휴대폰에 데이터 삭제 없이 업데이트했다. 정상 메뉴에서 물품 입력부터 8단계 최종 검토까지 진행하고 비용 단계로 돌아와 입력값이 유지됨을 확인했다. 이번에는 제품 소스·APK·서버를 다시 만들지 않았다.

## 실제 확인한 흐름

- 공유 OS 잠금과 등록된 단일 USB·화면 켜짐/잠금 해제·설치 판본을 대조했다. 완료된 배달내역 화면의 장시간 입력 없음과 수집 완료를 읽기로 확인한 뒤, 사용자의 계속 진행 요청 범위에서 설치된 MAIN 진입점을 열었다. 검증 앱의 홈 아래 `업무 시작 → 화물 운송 → 화주 → 업무 도구 → 운송 의뢰 등록 → 시작`으로 이동했다. 임의 주소 이동·Back·강제 종료는 사용하지 않았다.
- 기존143을 같은 서명의144로 `install -r` 1회 업데이트했다. 실제 설치 SHA는 `85100e12e9b42d4c13fa98e2a66f4ea13e9eb94878ccdded226d0e7aaf88f931`이며 포장본과 일치한다. 최초 설치 시각과 별도 원앱230의 메타데이터는 유지됐다. 선택 입력3,273개와 내장 앱 DLL·endpoint의 r7 결속도 마지막 읽기에서 변경0이었다.
- 업데이트 뒤 이전 앱 화면으로 돌아왔을 때 일반 시작 도구는 안전 중단했다. 이후 화면과 입력 이력이 이번 작업의 마지막 조작과 일치함을 다시 대조하고 검증 앱의 MAIN을 한 번 열었다. 로그인 상태와 기존 합성 의뢰 조회가 유지됐다. 새 홈 집계도 정상 응답을 표시했다. 지도 설정 부족 안내는 남아 있어 목록과 주소 직접 입력을 사용했다.
- 소유한 합성 작성 상태만 입력했다. 물품 `R8 synthetic parcel`, 수량1, 총중량2kg, 외포장300×200×100mm, 합성 출발지/도착지, 휴대폰 기본 선택기로 고른 11월5일17:04~18:06 한국시간을 확인했다. 선택 입력인 담당자·연락처·하차 시간 등은 빈값으로 남겼다. 실제 주소·고객 정보를 만들거나 사용하지 않았다.
- `차량 추천 확인`은 실제 로컬 서버의 적재 분석 응답5종을 표시했다. `첫 추천 차량 선택`으로 반환된 `1톤 카고 더블캡`을 선택하고 카드 방식·예정금액50,000원을 입력했다. 이 조회/선택은 의뢰 생성·기사 배차가 아니다.
- 최종 검토에서 물품·크기·출발지·도착지·시간·차량·금액의 요약7항목이 모두 일치했다. 초안 유지 버튼은 활성, 미동의 상태의 `결제 단계로`는 비활성이었다. 두 동의 상자는 화면에서 비선택 상태로 확인했으나 접근성 트리는 checkable 노드0개였으므로 기계 판정의 `allUnchecked=true`를 근거로 쓰지 않는다. 동의 기록·초안 유지·초기화·접수 버튼은 누르지 않았다.
- 실제 화면에 보이는 `이전 · 비용은 어떻게 정하나요?`로7단계에 복귀했다. 새 입력 컨트롤에서도50,000원이 그대로이고 다시 검토로 가는 버튼의 접근성 enabled 상태가 true임을 확인했다. 끝 화면은 이 비용 입력 단계다. 마지막 버튼은 화면 아래에 있었으며 두 번째 검토 진입·터치 가능 여부를 추가 확인한 것은 아니다.
- 입력·단계 이동에서는 기존 `AutoSaveAsync`로 자동 저장을 시도한다. 명시적 초안 유지 버튼을 누르지 않았다는 사실을 미저장으로 해석하지 않으며, 소유 합성 초안을 정리/초기화하지 않았다. 저장소 독립 재조회·앱 재시작 후 복원이나 실제 접수 완료는 이번에 확인하지 않았다.

## 서버·소스와 검증의 범위

같은 r6 검증 호스트의 PID2964·시작 시각·실행 경로와 loopback5378을 다시 확인했다. 실행기 SHA는 `950600a732931cc1159c3992aadff8fdff87e54549f46d9a5c62f109318a5873`, 서버 DLL SHA는 `a6280a94bb3994109f00c849f40196f0542c6f9abcfa2065c3131c46a6888d8e`로 전후 동일하다. 같은 Simulation run/격리 DB이며 외부효과·운영 worker를 비활성으로 둔 기존 환경을 재사용했다.

마지막 live·ready·홈 집계·업무 proof2개는 HTTP5/5가200이었다. 두 업무 proof SHA는 전후 동일하고 결제·지급 요청·지급 outbox는0이다. 준비된 APK의 정상 UI에서 실제 차량 분석과 기존 조회가 수행됐다는 근거이며 원격 운영·모든 과거503의 해결이나 실기기 경합 재현으로 확대하지 않는다. 마지막 서버 검사 도구는 JSON 시각이 DateTime으로 읽힌 뒤 소수점 문자열 비교에서 한 번 중단했고, 동일 DLL과 UTC ticks를 대조해 표기 차이임을 확인했다. 서버 재시작은 하지 않았다.

r7의 실제 Fast24/24·Task16,904통과/환경17생략/실패0과 앱/통합 빌드는 그 판본의 근거로 보존한다. 이번은 제품 소스 변경 없이 해당 APK의 물리 사용 흐름을 추가 확인한 회차다. 문서 경로·diff 검사는 별도이며 새 자동 회귀/전체 시험 통과 수로 재사용하지 않는다.

## 근거와 다음 한 가지

재개 근거는 `artifacts/local/app-stability-r8/56229f16612d4ba5ad43476fff34f5f6/completion-r2.json`이다. 같은 폴더의 `device-install-revised144.json`, `review144-launch-after-update.json`, `input144-*.json`, `time144-*.json`, `vehicle144-*.json`, `nav144-cost-to-review.json`, `review144-summary-checks.json`, `nav144-review-to-cost.json`, `final-phone-readback.json`, `runtime-before.json`/`runtime-after.json`/`runtime-final-identity.json`이 입력·기기·서버를 구분한다. 원시 UI와 스크린샷은 메모리에서만 관찰했다. r7의 미설치 포장 근거와 이전 정상/실패는 그대로 보존했다.

다음은 이 화주 흐름을 반복 빌드하지 않고, 아직 확인하지 못한 화물기사의 좁은 조회·오류 후 복귀 흐름을 같은 소유 환경에서 조사하는 것이다. 계정/기기 점유를 먼저 대조하고 실제 배차 수락·운행·금융은 수행하지 않는다. 저장소 오류·인증 만료·화면 이탈 경합의 물리 재현과 다른 역할 전체·앱 전체 안정화·원격 Operational은 미완료다. 배민 수집 checkpoint·영상·MYBOX·commit/push·배포는 변경하지 않았다.
