# 화물 적재 차량 선정과 AI 조합 입력 연결 조사

> 후속 구현: [소형차 제원·검증불가·물리 상한 보완 r73](2026-10-19-small-vehicle-loading-specs-r73.md). 아래는 구현 전 조사 시점 기록이며 새 코드와 검증 결과는 후속 기록을 따른다.

2026-10-19. 사용자는 화물 조건에 따라 오토바이·다마스·트럭 등을 선정하는 기존 코드를 먼저 조사하고, 접수 주문과 현재 기사 상황을 AI가 인지해 조합하는 방향을 구체화하도록 요청했다. **현재 작업 트리의 정적 코드·초기 자료·기존 시험 소스 조사**다. 제품 코드·설정·DB·모델·APK·운영 상태는 변경하지 않았고 시험을 새로 실행하지 않았다.

## 결론

화물의 크기·중량을 차량 제원과 비교하는 엔진은 이미 있다. 서버 화주 추천과 기사별 적합성 판정은 같은 순수 적재 엔진을 사용한다. 다만 모바일의 간이 추천, 서버 추천, 접수 원장, 실제 배차, AI 검토 자료 사이의 입력이 다르다. **새 학습 자료를 늘리기 전에 이 연결을 일치시키는 것이 우선**이다.

차량 수단을 AI가 임의로 발명하거나 소형 퀵의 5,000원·10분 가정을 전국 화물에 확대하는 방식으로 보완하지 않는다. 다음은 조사에서 도출한 후속 제안이며 구현·학습·운영 적용 완료가 아니다.

```text
화물 조건 입력·확인
└─ 기존 적재 엔진: 가능한 차량 후보·불가/미확인 이유
   └─ 접수 원장: 화물 조건·계산 근거·판본 보존
      └─ 실제 기사/실차·현재 적재·수행 일정 확인
         └─ 가능한 주문 묶음·픽업/전달 순서 계산
            └─ AI 비교 → 사용자 검토 자료
               └─ 서버 최신 조건 재확인 → 기사 추천·수락
```

| 부피 추정 | 양수 CBM이 없고 세 치수가 있으면 m 단위 길이×폭×높이×수량으로 추정해 소수 셋째 자리로 반올림·경고 반환 | 같은 파일 130–151행. 추정은 원장 저장과 별개 |

회전은 바닥의 길이·폭을 교환하는 범위다. 여러 상자의 실제 3차원 배치·무게중심·현재 차량 적재 잔량을 이 엔진이 모두 계산하는 것은 아니다. 포장 한 개의 치수 적합과 총량 검사만으로 전체 실물 배치가 입증되지는 않는다.

## 차량 자료와 별도 도구의 범위

- [일반 초기 차량 자료](../../Ssalddel.Infrastructure/Persistence/IdentityDataSeeder.cs) 319–868행에는 **22개 코드·1톤~5톤급 카고/탑차/윙바디/냉동탑 등**이 있다. 오토바이·다마스·라보는 297–316행의 운임표에는 있지만 이 일반 차량제원 시드에는 없다. 운임표와 적재 제원은 다른 자료다.
- [격리 훈련 시드](../../eng/Ssalddel.DispatchTraining/DispatchTrainingSeed.cs) 56–74행의 오토바이 20kg·0.09CBM은 합성 시험값이다. 실차 자료나 일반 실행 DB의 제원으로 승격하지 않는다.
- 초기 자료의 1톤 카고 높이 355mm·5톤 카고 높이 400mm는 엔진에서 포장 높이 제한과 부피 계산에 쓰인다. 이 값이 옆판 높이인지 실제 허용 적재 높이인지 **자료 의미 재검증이 필요**하다. 이번에 실차 측정·제조사 제원·현재 DB를 조회한 것은 아니다.
- [혼적 순서 계획기](../../Ssalddel.Contracts/Common/VehicleLoading/혼적상하차순서계획.cs)는 **이미 주어진 하차 순번**을 이용해 나중에 내릴 물건을 안쪽에 먼저 싣도록 안내한다. 최적 배송 순서나 도로 경로를 새로 찾는 알고리즘이 아니다.
- [관리자 차량 화면](../../SsalddelAdmin/Components/Pages/VehicleManagement.razor)은 현재 안내 카드다. [추천 기준 조회·수정·시뮬레이션 API](../../Ssalddel/Controllers/Admin/06_관리/차량추천관리Controller.cs)는 있으나 실제 기준표와 시험 입력/결과를 PC 화면에서 다루는 연결은 확인되지 않았다.

## AI 학습 전에 일치시켜야 할 연결

### 1. 모바일 간이 추천과 서버 상세 추천

[작성 ViewModel](../../Ssalddel.Ui.Common/Areas/App/ViewModels/운송의뢰작성ViewModel.cs) 319–358행은 적재 형태·온도·중량/부피 임계값으로 별도 목록을 만든다. [앱 서비스](../../SsalddelApp/Services/ServerBackedShipperOperationsService.cs) 140–157행의 차량 목록 호출도 현재 작성 화물의 제원을 전부 보내지 않고 일반화물·수량 1로 이름 목록을 얻는다. 화면 추천을 상세 적재 엔진의 동일 결과라고 해석하면 안 된다.

### 2. 추천에서 계산한 값과 접수에 저장한 값

서버 추천은 CBM을 추정하지만 [생성 핸들러](../../Ssalddel/Application/Shipper/Request/Handlers/의뢰생성CommandHandler.cs) 159–171행은 입력 CBM을 그대로 저장한다. [일괄 지원](../../Ssalddel/Application/Shipper/Request/화주운송의뢰일괄등록지원.cs)도 추정값을 응답에 보여 주면서 생성에는 원본 행의 CBM을 넘긴다. [공통 참여 검사](../../Ssalddel/Services/Dispatch/Participation/SharedDriverWorkAdmissionService.cs) 139–149행과 [순수 참여 정책](../../Ssalddel.Domain/기사/SharedDriverWorkAdmissionPolicy.cs) 69–74행은 저장 CBM으로 부피 한도를 확인한다. 따라서 치수가 있어도 저장 CBM이 없으면 근거 부족으로 제외될 수 있다.

[추천 DTO](../../Ssalddel.Contracts/Shipper/Request/화주운송의뢰Dtos.cs) 94–108행에는 바닥회전/적층 플래그가 있지만 생성 화물 DTO 167–180행에는 없다. 배차 적합성 입력은 회전·적층을 `true`로 만들고 비적층 바닥면적을 전달하지 않는다. 추천 때 본 취급 제약과 배차 때 본 제약이 같다는 보장이 부족하다.

단건은 선택한 차량 문자열을 저장하며, 일괄 확정은 사용자가 지정한 차량을 우선한다. 추천 허용 집합·조건/계산 판본을 접수와 결속하는 별도 검사가 이 경로에서 확인되지 않았다. 이후 기사 적합성·참여·자격 검사는 존재하므로 안전검사 전체가 없다는 결론으로 확대하지 않는다.

### 3. 적합·부적합·검증불가 구분

차량화물적합성Service 29–34행은 차량제원이 없을 때 `true + 검증하지 못했다는 경고`를 반환한다. 적재 엔진도 어떤 용량 기준이 없으면 경고와 함께 해당 축 검사를 진행하지 못한다. 공통 참여 등 별도 관문은 있지만, 이 결과 자체를 AI 자료에서 안전 적합으로 표시하면 안 된다.

또한 운영 권장 중량은 최대 중량보다 먼저 쓰이고, 관리 API 수정은 양수 여부를 확인하지만 최대 중량 상한과 비교하는 보호는 확인되지 않았다. CBM의 물리/권장 최솟값과 달리 중량에는 같은 상한 결합이 없다. 실차 기준과 운영 권장값의 관계를 먼저 명시해야 한다.

### 4. 실제 조합 계획과 현재 AI 입력

[조율 입력 Factory](../../Ssalddel/Services/Dispatch/Coordination/국내화물배차조율입력Factory.Evaluation.cs)는 공통 참여·적합성, 기사 위치·경로/시간, 기존 일정 삽입·복귀·비용/점수를 다룬다. 이 기반을 재사용할 수 있다.

하지만 [r113 검토기](../../eng/CargoRegionalTrainingReview/CargoTrainingCases.cs)는 교육용 별도 적격성 사례이고, [r114 로컬 AI 선택](../../eng/CargoAiDeviceVerificationR114/CargoAiSelector.cs) 및 [시험 호스트](../../eng/CargoAiDeviceVerificationR114/CargoJourneyControlStartupFilter.cs)는 서버 허용 기사 후보의 점수·거리·가용/픽업 ETA를 받아 선택한다. 여러 주문의 포장 배치·구간별 잔여 적재·픽업/전달 순서 계획을 현재 모델이 직접 구성한다고 표현하면 안 된다.

## 후속 순서 제안

1. **자료·의미:** 오토바이·다마스 등 제원 출처, 개별 포장/총화물 치수 의미, 카고 높이, 실제 최대값/운영 권장값을 검토한다. 근거 없는 합성 수치를 실차 제원으로 넣지 않는다.
2. **한 입력을 끝까지 보존:** 화면·상세 추천·단건/일괄 접수·원장·기사 적합성·학습 자료가 같은 중량/부피/회전/적층/취급 조건과 판본을 읽도록 한다. 추정값과 사용자 확인값은 구분한다.
3. **허용 후보를 엄격히 표현:** 적합/부적합/검증불가와 이유·한도를 남기고, 실제 차량·기존 적재·계획의 각 구간을 확인한다. 기존 가드나 권한을 학습 준비 때문에 해제하지 않는다.
4. **계획을 비교하는 AI:** 가능한 차량/기사와 주문 묶음·수행 순서 후보를 계산한 뒤 AI가 그 안에서 비교하도록 하고, 사용자는 지도·시간표·적재 변화·보수와 이유를 보며 승인/정정/보류한다. 실제 학습·운영 적용은 별도 단계다.

기존 5분 추가 우회 질문이나 단건 B 선택을 이번 차량 코드 조사 요청으로 승인 처리하지 않았다. 다음 문답의 초점은 화물 입력과 차량 적재 기준의 의미부터 확인하는 것이다.

## 조사 증거와 한계

원장과 플래그를 유지하는 읽기 전용 조사다. 근거 파일 14개의 SHA-256과 현재 HEAD는 `artifacts/local/cargo-vehicle-selection-audit/20261019-r1/source-index.json`에 기록했다. 기존 적재 엔진·혼적 순서·화주 추천 시험 소스도 읽었으나 **이번에 시험/빌드·DB/API 조회·모델 추론·기기 검증을 새로 실행하지 않았다.** 자료 변경이나 실제 환경 상태에 관한 결론은 후속 검증이 필요하다. 문서 검사는 별도다.
