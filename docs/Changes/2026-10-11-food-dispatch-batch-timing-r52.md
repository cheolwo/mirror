# 음식 배차의 짧은 주문 수집과 시점 판단 r52

사용자는 주문이 들어올 때마다 바로 배차하면 더 좋은 조합을 놓칠 수 있으므로, 주문을 잠시 모으고 기사 상황과 조합 가능성을 고려해 기다릴지 진행할지 판단하도록 요청했다. [수락 설계](../AI/Planning/공통/PLAN-OPERATIONS-DISPATCH-CORE/batch-timing.implementation.r52.md)와 [작업 명세](../AI/Planning/공통/PLAN-OPERATIONS-DISPATCH-CORE/batch-timing.r52.work-order.json)를 기준으로 구현했다. 실제 운영 활성화와 모델 학습은 별도다.

## 동작

- 음식 주문의 **첫 추천 전** 서버 정책이 수집 또는 기존 즉시 배차를 결정한다. 자동 후보 선정과 직접 기사 지정이 같은 관문을 사용한다. 기존 제안·수락·거절 뒤 재추천, 화물·생활 배송·마트 업무에는 새 대기를 적용하지 않는다.
- 초기 시험값은 수집 30초, 절대 상한 60초, 호환 후보 2건, 마감 여유 15초, 자료 신선도 15초다. 최초 큐 `CreatedAt`을 기준으로 하며 새 주문·재조회·`UpdatedAt` 변경으로 연장하지 않는다. 스캐너가 기한 이후 다음 주기에 재평가할 수 있으므로 정확히 60초 안에 제안이 도착한다는 SLA는 아니다.
- 가까운 픽업·전달 조합이 보이면 일찍 진행한다. 조리 예정 완료 시각이 확인됐으면 배차를 더 늦추지 않는 보수적 상한으로 사용한다. 실제 픽업·도착 시각을 마감으로 바꾸거나 미확인 조리 시각을 만들지 않는다.
- 기사 여력·수요 자료가 미확인/오래됨, 조회 한도 초과, 조회 실패, 기사 부재, 신규 주문 유입 근거 부족 또는 지연 위험이면 추가로 기다리지 않는다. 기존 후보·요금·수락 관문을 그대로 거친다.
- 수집 중 새 추천·요금 동결·알림을 만들지 않는다. 기존 수요 참여 서비스가 수행하는 판정 투영 복구 쓰기는 가능하며 이를 메타데이터에 표시했다. 판단 뒤 큐를 재조회하고 판본·최초 시각이 바뀌었으면 낡은 판단을 적용하지 않는다.

## AI와 서버의 경계

`FoodDispatchTiming`과 `FoodDispatchTimingOllama`는 공유 기본값과 예시에서 모두 OFF다. 켜진 로컬 모델은 서버가 허용한 `Collect` / `DispatchNow`만 선택한다. 주소·좌표·실제 주문/기사 ID·메뉴·개인 이름은 보내지 않고 상대 시간과 집계 수치만 전달한다. 모델 응답의 중복 키·허용 밖 행동·추가 필드·도구 호출·크기 초과를 거부하며, 기본 2초와 남은 수집 시간 중 짧은 시간으로 제한한다. 실패하면 추가 대기 없이 기존 흐름으로 복귀한다. 모델 대기 뒤 현재 시각과 자료 신선도를 다시 계산한다.

기하적으로 가까운 주문은 조합 검토 기회다. 실도로·적재·모든 약속 시간 통과, 실제 다건 공동 예약·원자적 수락, 전역 최적화 완료를 의미하지 않는다. 수집 종료 뒤 현재 한 건씩의 배차 흐름으로 진행한다. 기사별 평균 단가 4,000원 수렴 점수는 이번 변경에 포함되지 않았다.

## 학습 후보

별도 [실행 도구](../../eng/local-dispatch-ai/DispatchTimingScenarioRunner/README.md)가 기존 r50의 504건·339지점을 익명 출처와 분리 근거로 재사용한다. 대기 시간·주문 유입·기사 상황은 합성이다. 현재 순수 정책을 직접 호출한 수집/조합 발견/시간 만료/긴급/희박 수요/자료 미확인/기사 부재/재추천 8유형을 각 504개, 총 4,032개 준비했다. 지점별 학습 2,784·검증 856·평가 392로 분리했고 지점 교차·후보 입력 중복·격리는 0이다. 준비 답안은 0행, 대표 한국어 검토표는 24개다.

이는 `CurrentPolicyDraft / Pending`인 정책 검토 초안이다. 런타임 AI 프롬프트와 바로 호환되는 학습 포맷 또는 최적해가 아니며, 실제 학습용 변환과 사람 검토는 후속이다. r50·r51 자료와 도구는 보존한다. 모델 호출·가중치 학습·사람 승인·운영 변경은 수행하지 않는다.
