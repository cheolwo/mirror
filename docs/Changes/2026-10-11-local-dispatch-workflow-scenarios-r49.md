# 주문·Ollama 배차·기사 앱 로컬 통합 시나리오 r49

주문 생성 → 음식점 수락 → 배달권의 기사 후보·Ollama 선택 → 추천·요금 저장 → 기사 앱 배차 안내 → 수락·도착·픽업·전달 → 주문자 수령 확인을 반복 실행하는 로컬 검증 도구와 시험을 추가했다. 실제 주문·기사 Controller의 루프백 HTTP와 기존 서버 서비스, 격리 SQLite, FDriver API client·알림 수신기·PageModel을 함께 실행했다. 제품 소스·설정은 이번 판본에서 변경하지 않았다.

사용자는 USB 검증을 **지금은 로컬 통합 시험까지**로 제한했다. 실제 휴대폰·Android 알림 배너·소리·FCM 전달·Azure·운영 활성화·commit/push는 실행하지 않았다. 앞선 r44~r48의 변경과 실행·실패·예산 이력은 보존했다.

## 승인 범위와 구현

- [승인 설계](../AI/Planning/공통/PLAN-OPERATIONS-DISPATCH-CORE/workflow-scenarios.implementation.r49.md) · [작업 명세](../AI/Planning/공통/PLAN-OPERATIONS-DISPATCH-CORE/workflow-scenarios.r49.work-order.json). 설계 SHA-256은 `d9da9dafa4a4ee1c80be91856d6a9e096ba6041a714e0bbbde60d065fd775423`으로 유지했다.
- 서버 fixture는 실제 주문 접수·음식점 수락·배차 요청 Outbox·후보 정책·추천 저장·기사 수행·수령 확인 서비스를 연결한다. 새 DbContext의 `AsNoTracking` 재조회로 저장된 상태를 단계마다 대조한다. 식당 조리 시작·준비 완료는 기사 수락 뒤 실제 HTTP로 실행한다.
- 모바일 시험은 제품의 `FoodDeliveryDriverApiService`, `FDriverFoodPushReceiver`, `MainPageModel`을 사용한다. 실제 서버 알림 payload를 수신기에 주입하고 서버 정본을 다시 조회한다. 알림 자체는 자동 수락하지 않으며 명시적인 수락·도착·픽업·전달 명령으로 진행한다.
- [반복 실행 도구](../../eng/local-dispatch-ai/DispatchWorkflowRunner/README.md)는 기본 실행에서 업무·추론을 시작하지 않는다. `--mock` 성공 뒤 선택한 24개 소스 파일 해시가 일치해야 `--actual`을 허용한다. 이는 전체 의존 소스 그래프의 동일성 인증은 아니다. 모델은 기존 Docker의 루프백 `127.0.0.1:12681`, `qwen3:1.7b`만 사용했다.
- r49 누적 시작 예산 4회 중 실제 호출은 2회다. 호출 전 예약 파일을 독점 생성하며 실패·중단 시도도 보존한다. 이전 판본의 예산은 재사용하지 않았고 남은 슬롯을 채우기 위한 호출은 하지 않았다.

## 실제 모델과 업무 흐름 결과

같은 선택 소스의 모의 실행 `20261011T065624Z-mock-58e575ac`에서 세 흐름을 먼저 통과했다. 이어 실제 실행 `20261011T065859Z-actual-077d3d06`도 세 흐름을 통과했고 실행 전후 선택 소스 해시가 같았다.

| 사례 | 최종 모델 허용 후보 | 실제 모델 호출 | 선택 결과 | 앱·서버 수행 |
|---|---:|---:|---|---|
| 같은 배달권 | 2명 | 1회 | `FoodDispatchAI.Applied`, 기존 기준과 같은 `scenario-older` | 수령 확인까지 통과 |
| 인접 배달권 | 2명 | 1회 | `FoodDispatchAI.Applied`, 기존 기준과 같은 `scenario-older` | 수령 확인까지 통과 |
| 현재 수요·처리 여력 | 1명 | 0회 | `FoodDispatchAI.SingleCandidate`, 장기 대기 우선권 유지 | 수령 확인까지 통과 |

현재 수요 Policy는 기사별 우선순위를 부여한다. 그 우선권을 적용한 마지막 사례에서는 모델 허용 후보가 한 명만 남으므로 모델을 호출하지 않았다. AI를 실행하기 위해 순위를 같게 만들거나 관문을 완화하지 않았다. 이 사례의 결과 객체는 `Fallback=true`와 `InferenceSkipped=true`를 함께 기록하지만 모델 오류가 아니라 단일 후보의 계획된 생략이다.

두 실제 모델 응답은 모두 `{"candidateToken":"C1"}`이며 HTTP 200·허용 선택 검사를 통과했다. 기존 엔진과 같은 기사를 선택했으므로 판단 품질 개선·다른 후보 선택·최적 배차를 입증한 것은 아니다. 모델 제한 시간은 시험 전용 90초였으며 제품 호스트의 10초 설정·성능·부하 검증으로 확대하지 않는다.

세 사례에서 기사 앱 HTTP 요청은 각각 20개다. 제안은 수락 가능 상태, 수락 후에는 `PickupTravel`의 픽업 카드, 도착 후에는 `PickupWaiting`, 픽업 후에는 `Delivery`의 전달 카드로 전환됐다. 전달 완료 뒤 현재 수행 카드는 사라지고 주문자의 수령 확인은 별도 HTTP로 처리됐다. Simulation의 실제 요금 정책에 합성 경로·기상을 넣어 계산한 2,500원을 추천 시 동결하고 끝까지 보존했다. 운영 경로·기상·실제 지급액 검증은 아니다.

시험 호스트를 닫은 뒤 독립적인 읽기 전용 SQLite 조회에서도 주문 `수령확인`, 운송 상태 `인수완료`·단계 99, 수행 시도 1개·`Completed`, 도착·픽업·전달 시각, 확정 기사·동결 요금, 알림 Outbox `Succeeded`를 대조했다. 여기서 `Succeeded`는 기록용 FCM 포트의 성공 응답이다. 실제 FCM 전달이 아니다. 주문 동기화 Outbox는 각각 `Succeeded, Pending`이며, 완료 뒤 생긴 후속 동기화 1개는 이 시험에서 처리하지 않았다. 모든 후속 원장 동기화가 완료됐다고 주장하지 않는다.

## 오류·복구·권한 시험

신규 통합 시험 22개가 통과했다. 이 중 알림 공백 3개는 **현재 결함을 재현하는 시험**이며 수정 완료를 뜻하지 않는다.

| 범위 | 확인한 사례 |
|---|---|
| 정상 수행 3개 | 같은 권역·인접권·현재 수요, 단계별 카드·버튼과 저장 상태, 별도 수령 확인 |
| 모델 대안 2개 | 허용되지 않은 선택·HTTP 503에서 기존 후보로 복귀하고 수행 완료 |
| 알림 검증 5개 | 다른 앱·사용자·유형, 빈 제안 ID, 만료 payload 거부 |
| 중복·조회·응답 복구 5개 | 중복 알림/Outbox 조회, 장치 알림 게시 거절 후 앱 내부 안내, 정본 조회 실패 동안 수락 차단, 수락 응답 유실 뒤 재조회·추가 POST 없음, 조기 픽업·전달 차단 |
| 기사·HTTP 권한 4개 | 다른 기사 수락 거부, 미인증 401·주문자 403·알 수 없는 토큰 401, 수행 시도 미저장 |
| 알림 공백 3개 | 추천 저장 뒤 Outbox 생성 실패, 토큰 없음으로 Failed 후 토큰 복구, 일시 전송 실패로 Failed 후 전송 복구 |

알림 공백에서는 추천·요금·라운드가 저장된 뒤 같은 추천을 재시도해도 누락된 Outbox가 다시 생성되지 않는다. 이미 `Failed`인 항목도 Pending 처리나 같은 라운드 예약으로 재발송되지 않는다. 앱의 정본 조회로 배차 안내를 복구할 수 있는 경우와 백그라운드 알림의 재발송 보장을 구분해야 한다. 다음 제품 보완 우선순위는 추천과 알림의 영속 연결, 현재 유효한 추천의 누락 복구, 만료·수락·중복을 확인하는 제한 재시도다. 이번 판본은 시험·도구 범위여서 제품 코드는 수정하지 않았다.

## 확인하지 않은 경계

- 실제 APK 화면 렌더·휴대폰 설치·Android 배너/소리/진동/탭·FCM 네트워크 수신은 확인하지 않았다. 이번 배너 근거는 제품 PageModel의 앱 내부 상태와 기록용 알림 게시 요청이다.
- 인증은 fixture Bearer를 사용했다. 실제 운영 JWT 발급·만료·갱신 및 보호 저장소는 검증하지 않았다. 역할과 범위에 따른 실제 Controller HTTP 권한 관문은 시험했다.
- GPS·지도 수명은 비활성화하고 서버 위치를 합성했다. 경로·기상·영역 자료, 재고·가격 재검사, 암호화 저장, Mongo/음식 전문 원장 동기화, 정산 외부 포트는 대체했다.
- 도메인 이벤트는 기록용 발행기를 사용했고 Outbox는 시험이 명시적으로 처리했다. 제품 호스트의 자동 이벤트 처리·주기 작업, MySQL/Mongo/Redis 분산 동시성·재시작 회복·부하를 확인한 것은 아니다.
- 식당 UI·주문자 UI는 렌더하지 않았다. 해당 상태 변경은 실제 서버 HTTP로 실행했다. 실제 고객 자료·외부 알림·금전 이체·운영 설정 변경은 0건이다.
