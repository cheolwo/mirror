## 0. r3 현행 방향 — 디오라마 우선과 배달권 관계

City·Town·Hub·Farm은 더 이상 Unity가 차례로 완성해야 하는 네 개의 선행 게임 월드로 취급하지 않는다. 현실 지역 자료로 만든 디오라마가 어떤 공간적 성격을 갖는지 설명하고, 자료·배치·반복 자산·랜드마크·카메라 표현을 선택하는 **디오라마 환경 유형**으로 재사용한다.

| 유형 | 디오라마에서 뜻하는 공간 성격 | 예시 |
| --- | --- | --- |
| `City` | 고밀 주거·상업·교통·공공 서비스가 섞인 도시 생활권 | 서울의 행정동·역세권, 사가정·면목 생활권 |
| `Town` | 저·중밀 주거와 작은 상권·시장·생활 시설이 모인 읍·면·소도시 생활권 | 시골 읍내, 지역 전통시장 중심 생활권 |
| `Hub` | 반입·보관·분류·출고·환적 흐름이 공간의 중심인 물류·산업 결절 | 물류센터, 물류단지, 항만·철도 화물 거점 |
| `Farm` | 경작·축산·수확·저장 같은 생산 흔적이 공간의 중심인 농업권 | 농장, 시설재배 단지, 농촌 생산 구역 |

이 분류는 행정동·법정동·역세권·주소·좌표 같은 현실 지역 식별자를 대신하지 않는다. 같은 실제 지역 안에도 여러 유형의 성격이 섞일 수 있다. 예를 들어 사가정역 생활권 전체는 `City`에 가깝지만, 그 안의 마트 물류거점이나 배송센터는 `Hub` 성격을 가질 수 있다. 농촌 읍내는 `Town`을 중심으로 주변 `Farm` 성격이 이어질 수 있다.

혼합 지역은 **주 유형 하나 + 보조 유형 여러 개**로 기록한다.

```text
RegionStableId                 실제 지역 정체성
PrimaryDioramaKind             City | Town | Hub | Farm 중 주 유형 하나
SecondaryDioramaKinds          필요한 보조 유형 0개 이상
EnvironmentOverlays            Nature·하천·산지·해안 등 환경 보조 유형
ClassificationEvidenceRefs     분류 근거 자료
ClassificationRevision         분류 판본
GameplayAreaStableId           후속 게임 영역 결속 시에만 선택적으로 사용
```

현재 Unity 공간 개발의 최우선은 행정동·역세권 디오라마다. City·Town·Hub·Farm 분류는 이 디오라마의 표현 성격을 설명하는 데 사용하며, 유형별 게임플레이를 먼저 구현하기 위한 대체 우선순위로 사용하지 않는다.

배달권과의 관계는 다음처럼 고정한다.

```text
공식 행정동 안정 ID와 공간 자료
    → 행정동 디오라마 자료·배치·관찰 준비
    → 서버 배달운영권역 원장이 여러 행정동 안정 ID를 묶음
    → 후속 승인 뒤 주문·배차·정산의 운영 권역으로 사용
```

디오라마는 각 행정동의 공간을 관찰 가능하게 준비하고, 배달운영권역은 여러 행정동을 하나의 운영 단위로 묶는 서버 원장이다. Unity에서 가까워 보인다는 이유만으로 행정동을 권역에 포함하지 않는다. 역세권 1km 디오라마는 여러 행정동을 가로지를 수 있는 관찰 화면이므로 배달권 경계로 사용하지 않는다. 세부 운영 기준은 [행정동 기반 배달운영권역 r2](Planning/운영/PLAN-OPERATIONS-ADMIN-DONG-DELIVERY-TERRITORY/README.md)가 소유한다.

유형이 바꾸는 것은 기본 건물 밀도, 반복 자산 후보, 대표 랜드마크, 도로·공터의 비율, 카메라 관찰 기준점, LOD 구성 같은 표현 기본값이다. 유형만으로 주문·재고·배차·경작·수확·이동 가능성이나 플레이 완료를 확정하지 않는다.

Unity에서는 유형마다 Scene을 만들지 않는다. canonical `SimulationWorldShell` 안에서 선택한 지역 패키지를 불러오고 같은 조립 파이프라인에 유형별 표현 규칙을 적용한다. 기존 City·Town·Hub·Farm 게임플레이·스토리·독립 폐루프는 삭제하지 않지만 디오라마 기반선 뒤의 후순위로 유지한다.

아래 r1의 연속 월드·자연 경계·자산 후보 내용은 호환 참고로 보존한다. 현행 Unity 실행 순서는 아래 7절이 아니라 디오라마 자료·배치·관찰 우선순위를 따른다.

## 1. 추천 결론

**하나의 연속된 지형 위에 Farm·Town·Hub·City의 성격을 다르게 배치하고, 그 사이를 Nature의 능선·숲·하천·완만한 경사로 연결한다.** 네모난 구역마다 건물을 전시하기보다, 걸어가면서 지형과 건물의 윤곽·밀도·길의 형태가 달라져 장소를 알아보게 하는 방향이다.

먼저 큰 지형과 실제 보행을 확보하는 [D406 실행 계획](월드맵우선-초기표시정리와보행검증-2026-08-31.md)은 유지한다. 네 영역의 완성을 기다려야 첫 장소를 사용할 수 있는 구조로 만들지 않는다. Nature는 네 업무영역 밖에 따로 격리한 전시장도, Farm부터 City까지 순서대로 통과시키는 강제 경로도 아니다.

## 3. 네 영역의 성격과 추천 경관

아래 지형은 기존 위치에 적용 가능성을 조사할 **구도 후보**다. 새로운 산·하천·도로 위치나 생산 면적을 확정한 것은 아니다.

| 영역 | 플레이어가 알아볼 성격 | 추천 지형·공간 구성 | 보유 자산에서 우선 찾을 것 | 이어질 플레이의 방향 |
| --- | --- | --- | --- | --- |
| Farm · 농장 | 넓은 여백, 낮은 건물, 길게 이어지는 경작 흔적 | Nature 가장자리의 완만한 생산 대지. 숲 가장자리·수로·농로가 밭과 야생의 차이를 드러냄 | Farm의 밭·농장 건물·창고, Nature의 수목·바위·지면 후보 | 재배·수확·집하와 관리. 보이는 밭과 실제 작물 상태는 따로 연결 |
| Town · 타운 | 가까운 생활, 골목과 작은 광장, 저층 지붕 | 완만하고 아늑한 생활 지형. 정원·나무·빈터에서 골목·광장으로 밀도가 점차 높아짐 | Town의 저층 주거·상점·골목·광장 소품, Nature의 생활권 가장자리 식생 | 주민·상점·생활 서비스와 교류. City의 고밀 상업권과 구분 |
| Hub · 허브 | 넓고 낮은 창고, 정돈된 마당, 물류 동선 | 기존 교통 결절의 사용 가능한 평탄지. 숲·경사면을 지나 적재 마당과 창고 윤곽이 보이게 구성 | 기능 대장의 창고·물류·도로·마당 계열. City/Construction 등 팩 이름이 아니라 실제 용도로 선정 | 반입·보관·분류·출고 준비. 보행 접근과 차량 동선 의도를 구분 |
| City · 시티 | 더 높은 건물 밀도, 뚜렷한 중심부와 서비스 거점 | 기존 예약 위치를 유지하며 저밀 외곽에서 중심부로 밀도를 변화시키는 구도 검토 | City의 건물·상업 시설·도로·광장 계열. 판타지 분위기와 맞는 윤곽·재질부터 선별 | 수요·주문·거래·소비. 현재는 구도 제안이며 진입·업무 활성화는 별도 |

Town은 단순히 ‘작은 City’, Hub는 ‘창고가 있는 City’로 처리하지 않는다. 영역마다 먼저 할 수 있는 독립적인 행동이 다르고, 그 차이가 풍경에서도 읽혀야 한다. City의 원경 윤곽을 검토하더라도 실제로 들어갈 수 있는 완성 영역처럼 안내하지 않는다.

## 4. 경계를 벽 대신 풍경으로 읽게 하는 방법

| 장치 | 적용 제안 | 주의할 점 |
| --- | --- | --- |
| 능선·완만한 언덕 | 지형을 돌아 나오면 다른 영역의 대표 건물 윤곽이 나타나도록 시야를 구성 | 모든 영역을 같은 산벽으로 막지 않음. 산 Prefab의 보이는 외형과 걸을 수 있는 지형은 별도 확인 |
| 하천·물가·식생대 | 물과 주변 식생이 장소의 구분과 방향 찾기를 도움 | 하천을 새로 만들거나 다리를 추가하는 것은 별도 지형 선택. 하나의 다리만 강제하는 경로로 자동 확정하지 않음 |
| 숲 가장자리·빈터 | 빽빽한 숲→성긴 나무→열린 생산/생활 공간으로 밀도를 변화 | 무작위 흩뿌리기보다 군집·여백·작업 접근을 보존. 나무가 WI 대상을 가리지 않게 함 |
| 길·건물 밀도 | 농로, 생활 골목, 물류 마당, 도시 가로의 차이로 영역을 판독 | 길 모양만으로 운송 계약이나 통행 권한을 만들지 않음. 기존 연결점과 실제 접근 가능성을 대조 |
| 공통 바탕·다른 특징 | 지면·바위·식생의 공통 재질감을 유지하고 지역별 대표 윤곽을 다르게 함 | 서로 다른 팩의 색·크기·시대감이 충돌하는 후보는 연결 보완 또는 보류. 원본 재질을 일괄 수정하지 않음 |

**풍경의 경계, H/AreaSet의 의미 경계, 실제 통행·업무 가능 범위는 같다고 가정하지 않는다.** 플레이어가 느끼는 전이 구간을 마련하되, 실제 영역 판정은 기존 공간 계약을 따른다. 가능한 우회·다른 접근은 기존 지형과 승인된 연결 근거에서 찾고, 보이지 않는 벽이나 순간 이동으로 연속성을 꾸미지 않는다.

[절기 경관 방향](../Architecture/PlayableLoops/PlanningSessions/시간절기/seasonal-time-context.inquiry.r1.md)도 함께 반영한다. 단풍·적설·안개로 색감이 달라져도 농장의 여백, Town의 골목, Hub의 창고 윤곽, City의 밀도로 위치를 알아볼 수 있게 한다. 영역 구분을 색 하나에만 의존하지 않는다. 기존 네 계절 표현 단서가 곧 24절기 실제 적용 완료인 것은 아니다.

## 5. Prefab 조사는 무엇부터, 어디까지 할 것인가

전체 자산을 매번 다시 조사하지 않고 **역할별 소수 후보 → 기존 근거 재사용 → 부족한 실측만 보완**한다. 후보 수를 채우려고 맞지 않는 자산을 억지로 넣지 않는다.

| 조사 묶음 | 먼저 볼 자산 분류 | 조사에서 답할 질문 |
| --- | --- | --- |
| 큰 지형 | Nature, Alpine Mountain 계열의 지형·산·절벽·바위 | 원경 장식인가, 가까이 접근 가능한 지형인가? 지면과 연결되는가? 반복 배치 이음매가 드러나는가? |
| 숲과 전이대 | Nature의 수종·관목·풀, 기존 색 변형과 계절 표현 | 가까운 잎·줄기와 먼 LOD가 일관적인가? 군집 크기·가림·계절 제어가 역할에 맞는가? |
| 네 영역의 대표 윤곽 | Farm 농장 건물, Town 저층 건물, 기능별 창고·물류 시설, City 상업/고밀 건물 | 실측 크기와 출입구가 Player에 맞는가? 네 영역을 구분하면서 같은 세계의 미감에 어울리는가? |
| 가까운 생활·업무 단서 | 밭·상점·집하·적재·표지·울타리 등 기존 기능 분류 | 현재 WI와 실제 상태 공급이 있는가? 장식뿐이면 그것을 분명히 구분했는가? |

재사용 단서로 [LS01 연구](../Architecture/PlayableLoops/Farm경관-LS01-공간배치연구.md)의 Farm `SM_Bld_Barn_01/02` 크기 조사와 Nature `SM_Tree_Birch_01`의 재질·LOD 기록 등이 있다. 이는 이번 네 영역에 최종 채택됐다는 뜻이 아니다. 나머지는 팩별 대표 이름을 추측하지 않고 실제 목록에서 정확한 Prefab을 찾는다. Construction은 공통 시공/지원 자산이며 독립 영역으로 만들지 않는다.

개발·공간 담당의 후보 반환에는 다음을 한 행으로 연결한다. 기존 E4 자산 조사 필드·명세·보고를 재사용하고 새 운영 DB나 중복 전수 대장은 만들지 않는다.

- 영역/경관 역할·연결 WI/H·플레이어가 알아볼 순간.
- 자산 계열, 정확 파일 경로/GUID·판본/hash, 주후보·대체 또는 보류 사유.
- 크기·축척·pivot·Renderer/LOD·재질, Collider/지지면·출입/작업 접근과 주변 간섭.
- 기존 조사 근거와 이번 새 확인의 구분, `재사용 가능 / 연결 보완 / 가공 필요 후보 / 미검사`.
- 산/숲/건물 외형 자료, H 조립, 실제 Game View의 증거 종류 구분.

자산이 어울리지 않을 때는 먼저 기존 대체 후보나 소유 복사본의 허용된 연결을 검토한다. 새로운 Blender 가공·구매·공유 원본 수정은 이 제안서의 자동 실행 항목이 아니다.

## 6. H와 WI에 연결하는 기획 단위

기존 H 기준을 대체하지 않고, AreaSet의 영역 의도에서 H3 경관 역할·H2 기능 묶음·H1 행동 장소까지 내려가며 연결한다. 실제 필수/선택 관계와 고유 식별자는 기존 정의를 따른다. Prefab 하나가 자동으로 H1이 되거나, 창고 외형이 보인다고 보관 업무가 성립하지 않는다.

| 관점 | 첫 검토 예: 숲 가장자리에서 Farm을 알아보고 접근하기 |
| --- | --- |
| 지금 | 절기·시간대·날씨가 달라도 길과 대상이 읽히는가? 정확 절기/조건은 비교 회차에서 고정 |
| 여기 | 기존 Farm 기준점·H 경관·접근 연결 안에서 어디를 보여줄 것인가? |
| 나 | 기존 Player의 시점·크기·실제 이동 가능 상태는 무엇인가? |
| 너 | 지형·숲·농장 건물·현재 작업 대상 중 무엇을 판독해야 하는가? |
| 이렇게 | 기존 이동으로 접근·관찰하고, 준비된 WI가 있을 때만 그 입력으로 이어감 |
| 결과 | 경계 통과·대상 식별·통행 결과를 확인. 화면만으로 수확/보관 성공을 만들지 않음 |
| 다음 선택 | 머무르기·기존 작업·돌아가기·가능한 다른 접근을 고를 수 있는가? |

이는 검토 예시이지 Farm을 모든 플레이의 필수 출발지로 정하는 새 규칙이 아니다.

## 7. 실행 순서와 담당 — 작은 장소부터 연결한다

| 순서 | 산출물 | 담당·승인 경계 |
| --- | --- | --- |
| 1. 기존 D406 기반 확보 | 초기 표시 분류·정리 전후, 기존 월드맵 구도와 실제 Player 보행/귀환 근거 | 개발 조율·공간 실제 확인. 본 제안의 미승인 배치를 끼워 넣지 않음 |
| 2. 네 영역 의도와 후보 정리 | 이 제안서의 영역 특징표 + 기존 자산/구성 패턴 대응과 결손 | 기획 의미 검토, 개발·공간의 파일 기반 보완. City 예약 상태 보존 |
| 3. 대표 전이 구간 하나 선정 | 기존 기준점을 유지한 구도 후보, 필요한 Prefab·지지/통로 조건과 예상 비용 | 사용자 검토 뒤 필요한 전문 연구·명세에 결속. 숲 가장자리↔Farm을 첫 후보로 추천하되 강제 경로는 아님 |
| 4. 작은 실제 조립·보행 | 한 구간의 실제 배치·입력·표시 해제/재적용·Game View | 개발 구현/통합, 공간 단독 Editor·캡처. 자산 추가 제작이 필요한 부분만 별도 배분 |
| 5. 다른 영역으로 확장 | 같은 기준을 Town·Hub·City의 특성에 맞게 재사용 | 각 영역 독립 준비와 연구를 확인. City 예약 해제·새 영역 연결을 자동 승인하지 않음 |

세 공간 엔진의 역할은 [기존 파이프라인](../Architecture/지도구성과세계자산배치분리.md)을 따른다. 월드맵은 지형·기준점, 배치는 기능/경관 계획, LH는 셀 준비·수명, Unity 표현은 실제 조립·재질·LOD를 맡는다. Simulation 상태와 Sky 빛·기상까지 새 지도 엔진에 합치지 않는다.

검토에서는 같은 후보/카메라/시간·날씨의 비교와 실제 이동 중의 연속성을 나누어 본다. 경계에서 지면·색·수목이 사각형으로 끊기거나 갑자기 나타나는지, 건물과 지형이 겹치는지, 길을 알아보고 왕복할 수 있는지, 재진입에 중복/누락이 있는지 확인한다. 거리·성능 수치는 현재 측정 후 정하며, 보기 좋은 정지 그림만으로 보행·성능 통과를 선언하지 않는다.

## 8. 이번 작성 결과와 다음 검토

이번 결과는 **기존 자료를 연결한 기획 제안서**다. 상세 지형 배치·최종 자산·색 팔레트·새 도로/교량·City 활성화·E 승격은 확정하지 않았다. 처음 받을 시각 결과는 거대한 네 영역 완성도가 아니라, 기존 월드맵 기반과 한 전이 구간에서 역할·보행·화면이 함께 성립하는 작은 근거를 권한다.

개발에는 이 문서와 결정의 링크·현행 기준·자산 목록 참조 확인 및 전문 파일 조사상의 결손 반환을 인계한다. 코드·시험·색인/현재 상태 통합은 개발에서 수행하며 기획은 공유 코드를 수정하지 않는다. 이번 제안만으로 Editor 작업을 확대하지 않는다.

D406의 현재 별도 차단도 구분한다. 담당 보고상 Unity Editor/Game View가 없고 Hub·Bug Reporter만 관측되어 첫 live 확인이 중단됐다. 원인과 미저장 상태가 미확정인 동안 자동 재시작·복구 선택을 하지 않는다. 이 상태는 네 영역의 기획안 자체가 막힌 것이 아니며 파일 기반 검토는 계속 가능하다.
