# 보완하며 제작 규칙을 축적하는 절차

- 상태: ConfirmedWorkflow / EvidenceBoundCandidates. 2026-09-27 사용자 요청: 기능 증가보다 기존 결손 보완을 계속하고, 그 경험으로 앱 제작 절차를 표준화한다.
- 선행: [r10 문답](app-production-guided-intake.r10.md). [r9 입력 형식](app-production-intake.r9.md)과 기존 코드/실행 증거 구분은 유지한다.
- 이번 범위: 음식점 메뉴 보완에서 확인한 내용을 재사용 가능한 조건부 규칙으로 남긴다. 새 자동 생성기·규칙 엔진·점수·전용 DB·강제 전수시험을 추가하지 않는다.

## 기본 작업 순서

1. 기존 기획/코드/실행 기록으로 **결손 하나**와 영향을 받는 사람·정보·업무 종료 조건을 고른다. 기술 사실은 AI가 조사하고 실제 정책 결손만 질문한다.
2. 수정 전 실패를 재현할 시험과 허용 파일/제외/검증 상한을 기록한다. 재현 불가라면 확인된 코드 근거와 미재현 상태를 분리한다.
3. 기존 계약을 유지하는 작은 보완을 하고 실패 시험이 통과하는지 본다. 정상·거절·결과 미확인·회복·재조회 중 영향을 받은 경로를 함께 확인한다.
4. 실제 수행한 범위의 결과를 같은 PLAN 결과 문서에 남긴다. 자동시험과 DB/HTTP/화면/기기/출시는 서로 대체하지 않는다.
5. 결과에 **적용 조건 / 관측 문제 / 보완 방법 / 검증 근거 / 반례·미확인**을 한 줄로 남기고, 입력과 현황표의 현재성을 점검한다. 다시 결손 하나를 고른다.

각 회차는 검증된 작은 결과 또는 명시적인 차단에서 마무리한다. 반복 요청이 없는 백그라운드 실행·무기한 개발을 설정하지 않는다. 승인되지 않은 기능이나 금전/권한 정책을 후보 규칙으로 우회해 추가하지 않는다.

## 현재 추출한 규칙과 한계

| 구분 | 조건과 재사용할 방법 | 근거·범위 |
| --- | --- | --- |
| 기존 원칙 | 화면이 아니라 업무 하나의 입력→행동→서버 판정→재조회→종료를 단위로 한다 | [r10](app-production-guided-intake.r10.md), 새로운 제품 기획이 아님 |
| 관측에서 추출한 후보 | 화면과 서버가 같은 의미의 값을 받으면 길이·정규화 규칙을 공유하고 저장 전에 재검사한다 | [메뉴 r6 결과](../PLAN-SYSTEM-REGIONAL-OPERATIONS-E2E-SCAFFOLD/restaurant-menu-validation.r6.result.md). 의미가 다른 역할의 제한까지 하나로 합치지는 않음 |
| 관측에서 추출한 후보 | 업무 거절은 메시지만 아니라 저장 값과 revision이 그대로인지 독립 재조회로 검사한다 | r6 InMemory와 [메뉴 충돌 r7 결과](../PLAN-SYSTEM-REGIONAL-OPERATIONS-E2E-SCAFFOLD/restaurant-menu-conflict.r7.result.md)의 SQLite·독립 Context 검증. 실제 MySQL 동시성·인증 HTTP는 미검증 |
| 기존 구현에서 추출한 후보 | 확정 거절·응답 미확인·저장 성공 후 목록 실패는 서로 다른 복구 행동을 제공한다 | [메뉴 r2](../PLAN-SYSTEM-REGIONAL-OPERATIONS-E2E-SCAFFOLD/restaurant-menu-mobile.r2.md). 요청 ID 영속 멱등성·앱 종료 복구를 보장하지 않음 |
| 관측에서 추출한 후보 | 업무상 예상한 충돌만 특정 오류로 분류하고 내부 오류를 같은 거절로 숨기지 않는다 | [r7 결과](../PLAN-SYSTEM-REGIONAL-OPERATIONS-E2E-SCAFFOLD/restaurant-menu-conflict.r7.result.md)의 충돌 관련10/10에 포함. Controller 직접 시험과 실제 HTTP 오류 미들웨어 검증은 별개 |
| 확인된 경계 | 사전 revision/중복 확인과 DB 저장 순간의 동시성 보장은 다르다 | r6 미검증 경계와 r7 제외. 사전 검사 성공만으로 동시 두 요청 안전을 주장하지 않음 |
| 기존 원칙 | 코드/시험 소스/실행/장치/배포를 분리하고 입력 변경 시 근거를 다시 확인한다 | [도구 증거 의미](../../../../../eng/planning-inquiries/app-production/README.md), 과거 통과를 현재 판본에 소급하지 않음 |

후보는 다음 실제 업무에서 다시 대조한다. 다른 앱에서 성립하지 않는 조건이 나타나면 후보를 제한하거나 폐기하고 이유를 남긴다. 한 업무 성공이나 이 문서 승인만으로 모든 앱의 공통 규칙/공통 코드로 자동 승격하지 않는다.

## 입력 자료 관리

r9 메뉴 초안의 예전 제한·hash는 역사적 자료다. r6/r7 이후 재검토 경고를 지우기 위해 과거 승인이나 시험 기준을 덮어쓰지 않는다. 새 입력 판본을 연결할 때 해결된 충돌, 아직 남은 DB/API·기기 환경, 사람 검토 상태를 구분한다. 이번 요청은 보완 작업의 승인이지 전체 앱 입력의 일괄 확인이 아니다.

확정: 기능 확장보다 결손 보완과 근거 있는 절차 축적을 우선한다. 미정: 후보 규칙의 다른 앱 적용 범위. 다음 질문 하나: 없음. 현재 결손은 기술 검증으로 조사 가능하다.
