# 앱 공통 제작 절차

통합 앱과 화주·기사·음식점·주문자·창고·운영자 앱의 개발은 **사용자가 업무 한 건을 끝까지 처리하고 중단 뒤에도 이어갈 수 있는 단위**로 진행한다. 같은 의뢰·주문·운송을 관련 역할에서 다시 조회하고 다음 담당에게 인계할 수 있어야 한다. 제품 목표는 [통합 앱 1.0](../../../../Versions/unified-1.0/README.md)이며 현재 완성 근거는 [업무별 마감표](../../../../Versions/unified-1.0/checklist.md)가 소유한다.

이 안내가 앱 작업의 공통 진입점과 처리 절차를 소유한다. 제품 업무 규칙은 각 PLAN·서버 원장에, 계획과 코드·시험·결과의 관계는 기존 `role-app-links.json`에 유지한다. 자료 형식은 [r9](app-production-intake.r9.md), 필요한 질문은 [r10](app-production-guided-intake.r10.md), 실패 보완은 [r11](app-production-repair-cycle.r11.md), 이번 적용 범위는 [r13](app-common-workflow.r13.md)을 따른다. 입력 자료는 기존 PLAN과 코드에서 필요한 내용을 모은 제작용 요약이다.

## 업무 한 건을 정하는 기준

AI가 기존 기획·화면·API·원장·시험을 먼저 확인해 다음 내용을 채운다. 사용자가 이미 정한 내용을 다시 묻지 않으며, 실제 제품 선택이 남은 질문만 모아 확인한다.

| 작업 카드에 남길 내용 | 기존 입력 위치 |
| --- | --- |
| 누가 무엇을 완료하는지, 이번 포함·제외 범위와 시작/종료 상태 | `purpose` |
| 권한, 원장 소유자, 같은 요청·주문·운송 ID와 읽고 쓰는 정보 | `information` |
| 역할별 행동, 서버의 확정 결과, 재조회와 다음 담당의 인계 | `workflow` |
| 요약/상세, 주 행동, 로딩·빈 상태·오류·처리 중·성공·복귀 | `uiStates` |
| 중복·취소·응답 유실·종료 후 복구, 결과 확인 수단과 재개 조건 | `recovery` |
| 이번 소스·서버·APK 기준선, 결과물별 검증과 남은 일 | `deliverables`와 별도 검토 기록 |

여러 앱에 걸친 한 업무는 관계 대장으로 묶되 프로필·입력은 대상 앱별로 둔다. 작업 카드가 승인된 제품 PLAN이나 원장을 대신하지 않는다. 같은 파일·공유 계약의 담당과 수정 범위를 정하고, 독립 작업은 병렬로 진행할 수 있다.

## 여섯 단계의 처리와 통과 조건

| 단계 | 입력과 처리 | 다음 단계의 완료를 주장할 근거 | 실패했을 때 돌아갈 곳 |
| --- | --- | --- | --- |
| 준비 | 기존 기획·코드에서 프로필/작업 입력을 채우고 권한·인계·오류/복구·수정 범위를 확인한다. 입력 확인, 기존 실행 승인, 환경 준비를 나누어 점검한다. | 실제로 확인한 입력과 승인된 범위, 현재 소스 기준선 및 수행할 검증 목록. 새로운 입력의 사람 검토를 소급 생성하지 않는다. | 미정 제품 선택은 질문으로, 기술 결손은 조사로, 환경 결손은 해당 결과물의 보류로 돌린다. |
| 구현 | 기존 contract·API·UseCase·원장·공통 UI를 연결하고 해당 역할 앱에 행동과 결과 재조회를 붙인다. | 변경 코드와 직접 관련 시험, 영향 소비 앱의 빌드 결과. 컴파일 성공과 업무 완료는 구별한다. | 업무 의미/권한 문제는 준비, 코드/조립 문제는 구현으로 돌아간다. |
| 서버 완주 | 격리 환경에서 인증된 실제 제품 API와 DB를 거쳐 같은 업무를 끝까지 처리하고 관련 역할에서 다시 조회한다. | 같은 실행·원장 ID의 저장/판본·Event/Outbox·인계 결과, 재처리의 중복 없음과 요청 미확정 확인. 모의 제공자/합성 자료 범위를 함께 기록한다. | 원장/API/동기화 책임으로 돌아간다. 확인 계약이 없으면 미확정으로 두고 자동 재전송하지 않는다. |
| 휴대폰 확인 | 현재 소스의 대상 APK로 업무를 수행하고 종료·재실행·통신 단절·계정 전환·응답 유실·데이터 보존 업데이트를 확인한다. | 기기 종류, 설치/실행 APK와 서버 판본·접속 대상, 실제 조작·재조회·복구 결과. 에뮬레이터와 실휴대폰, 포장과 설치/실행은 별개다. | 앱 표시/입력/수명 문제는 구현으로, 서버 결과 불일치는 서버 단계로 돌아간다. |
| 제한 사용 | 명시한 대상·역할·기능 범위에서 사용하고 불편·실패를 재현해 보완한다. | 사용 범위·수행 결과·보완/회귀 확인과 남은 제한. 전체 역할이나 운영 효과로 확대하지 않는다. | 영향받은 가장 이른 단계와 같은 작업 기록으로 돌아간다. |
| 공개 준비 | 현재 배포 후보의 접근 권한·서버 접속·알림/지도·백업 복원·운영 요건을 [공개 관문](../../../../Versions/release-gates.md)과 대조한다. | 같은 후보의 필요한 기술·운영 관문. 실제 배포와 외부 효과는 승인된 별도 실행 결과로 기록한다. | 해당 제품·운영 책임으로 돌리고 공개 범위를 유지한다. |

이 단계는 완료를 판정하는 기준이며 화면 시안·문서·기술 조사의 병행을 막지 않는다. 서버나 기기가 준비되지 않아도 승인 범위의 독립 준비는 계속한다. 다만 뒤 단계 자료가 있다는 이유로 앞 단계 검증을 통과로 채우지 않는다. 운영·Simulation·Unity의 결과는 각 책임에서 검증하고 필요한 계약만 연결한다.

## 현재 판본을 함께 확인하는 법

실행 전에 소스 commit과 이번 변경 경로/해시, 정확한 기획/입력 판본, 선택한 서버와 DB·시험 자료의 소유권을 남긴다. 서버 검증은 실제 endpoint·실행 빌드·모드·원장 ID, 모바일 검증은 대상 앱·APK 해시/버전·설정된 endpoint·기기 종류를 같은 회차에 결속한다. 비밀값이나 실제 고객 정보를 입력표에 복사하지 않는다.

과거 r121 HTTP와 r124/125 에뮬레이터 결과처럼 서로 다른 소스·서버·APK 기록은 각각의 과거 근거로 보존한다. 최신 역할 앱의 동일 업무 완주로 합산하지 않는다. 입력이나 공유 contract가 바뀌면 영향을 받은 결과를 재검증 대상으로 표시한다.

`Fast`는 직접 영향 검사, `Task`는 해당 작업의 소비 경계 검사, `Release`는 공개 후보의 통합 검사로 실제 선택 목록·실패·생략을 남긴다. `eng/`의 도구 변경은 현재 Fast의 문서/지침 분류와 별도로 `eng/tests/app-production.ps1` 같은 전용 시험을 지정한다. 관리 도구의 안전한 evidence bridge는 `LiveHttpDb`, 실제 기기, 배포, 운영 효과를 대신 증명하지 않는다. 이 결과는 해당 종류의 실제 실행 기록으로 별도 연결한다.

## 첫 적용과 결과 반환

첫 적용은 [화물 한 건의 역할별 마감 계획](../../공통/PLAN-OPERATIONS-DISPATCH-CORE/cargo-lifecycle-pilot.evidence.r1.md)이다. 화주 접수부터 기사 판단·상하차·화주 인수·운영자 재조회까지 같은 건으로 대조한다. 앱별 입력·환경과 이전 검증의 한계를 먼저 연결하고 실제 실행 상태는 수행한 범위만 갱신한다.

매 작업의 결과는 **업무명 / 이번 변경 / 자동시험·서버·실제 휴대폰 확인 / 미확정과 차단 / 다음 작업**으로 반환한다. 도구 생성·코드 존재·시험·브라우저·APK·실휴대폰·운영을 서로 다른 사실로 표시한다. 실패는 같은 업무에 재현 → 작은 수정 → 관련 회귀 → 조건과 한계 기록으로 환류하며 공통 규칙 확대는 별도 판단한다.

## 입력 작성 순서

1. AI가 기존 PLAN·API·화면·시험을 대조해 앱 공통 프로필과 작업 입력을 먼저 채운다.
2. 입력 점검으로 출처·hash·누락·충돌을 확인한다. 코드로 확인할 수 있는 것은 사용자가 다시 설명하지 않는다.
3. **정보가 부족할 때만** AI가 질문 하나씩 제시하고 답변을 입력에 누적한다. 기존 확정 사항은 다시 묻지 않고 기술 사실은 AI가 조사한다. 사용자는 실제 제품 선택만 답하며, 빈 양식 전체를 작성하지 않는다. 질문 우선순위·답변 반영·종료 기준은 [r10](app-production-guided-intake.r10.md)을 따른다.
4. 입력 판본을 확인한 뒤에도 기존 `Approved` 기획·작업지시서·허용 경로 수용 절차를 별도로 거친다.
5. 작업 범위의 구현·시험·화면·APK를 수행하고 같은 입력 기준의 결과를 반환한다. 장치 설치·배포는 추가 단계다.
6. [보완 순환 r11](app-production-repair-cycle.r11.md)에 따라 실패 재현→작은 보완→검증의 결과에서 적용 조건과 한계를 갖는 규칙 후보를 남긴다. 후보만으로 새 기능이나 전체 앱 공통화를 승인하지 않는다.

## 공통 프로필과 작업 입력

| 자료 | 입력할 내용 | 재사용 |
| --- | --- | --- |
| 앱 공통 프로필 | 앱 ID, project, 플랫폼, 탐색, 표현, 인증, 서버, 시험 환경 | 앱마다 한 번 작성하고 변경 시 재검토 |
| 목적·범위 | 이번 업무, 대상 앱, 영향 역할, 포함/제외 | 선택 업무만 |
| 정보·권한·표본 | 읽고 쓰는 정보, 서버 소유자, 개인정보 경계, 비식별 예 | 기존 정보대장 연결 |
| 업무 순서 | 시작→사용자 행동→서버 처리→정본 재조회→종료 | 기존 API/UseCase 연결 |
| 화면 상태 | 정상·로딩·빈 목록·실패·저장 중·성공 | 기존 UI 우선 |
| 실패·회복 | 중복, 응답 유실, 충돌, 취소, 재시도, 실패 후 복귀 | 현재 보장과 새 요구 분리 |
| 결과물 | 업무 시험, 화면 환경·입력 절차, APK 대상 및 제외 | 결과물별 환경 준비 |
| 검토 기록 | 확인한 프로필/입력 hash, 사람 확인, 기존 승인 참조, 환경 준비 | 입력 변경 시 재검토 |

복사할 양식: [프로필](../../../../../eng/planning-inquiries/app-production/templates/app.profile.json), [작업 입력](../../../../../eng/planning-inquiries/app-production/templates/task.intake.json), [검토](../../../../../eng/planning-inquiries/app-production/templates/task.review.json). 각 사실은 `status/value/critical/sources`를 가지며 출처는 저장소 상대 `path/sha256`와 선택 `revision/anchor`로 연결한다. `#anchor`는 path에 합치지 않는다. `NotApplicable`에는 이유가 필요하다.

`ExistingConfirmed`는 기존 근거로 확인한 내용, `Proposed`는 제안, `Unresolved`는 미정이다. 코드가 있다는 사실이 실행 성공이라는 뜻은 아니다. 가게·기사·주문자의 실제 계정·주소·연락처·키·토큰·서명 비밀번호를 넣지 않는다. 비밀 설정은 저장소 밖에 두고 입력표에는 준비 상태만 기록한다. 도구의 명백한 비밀 패턴 검사는 모든 민감정보를 탐지하는 보증이 아니므로 내보내기 전 사람이 내용을 검토한다.

## 상태를 읽는 법

- 제작 입력: `NotReviewed` 미연결, `NeedsInformation` 입력/검토 보완, `Confirmed` 입력 확인, `Changed` 기준 변경.
- `inputState`는 입력 완비 여부, `reviewState`는 사람 확인 여부다. 확인은 정확한 입력 hash에 결속한다.
- `approval`은 기존 실행 승인 선언을 별도로 점검한 결과다. `Declared`도 이 조회 도구가 실행 권한을 새로 주는 상태가 아니다.
- `environment`는 결과물별 준비 여부다. APK 서명이 미확인이어도 자료 준비까지 중단할 이유는 없다. 반대로 환경 준비만으로 앱 개발을 승인하지 않는다.
- 코드 존재, 시험 소스 존재, 실행 결과, 현재성은 r8의 독립 축을 유지한다. 과거 업무는 접수표 미연결을 이유로 미구현으로 바꾸지 않는다.

입력 준비와 환경 준비는 분리한다. 확인된 입력도 환경 차단이 남을 수 있다. 주요 미정·기준 불일치·차단 충돌은 작업 인계 준비가 되었다고 표시하지 않는다.

## 점검과 결과 반환

```powershell
./eng/planning-inquiries/manage-app-production.ps1 -Mode IntakeCheck -WorkItemId APP-RESTAURANT-MENU
./eng/planning-inquiries/manage-app-production.ps1 -Mode Write
./eng/planning-inquiries/manage-app-production.ps1 -Mode Validate
./eng/release/publish-mobile-field-test.ps1 -ServerBaseAddress https://example.invalid -AppNames restaurant -PlanOnly
```

`IntakeCheck`의 종료 코드 3은 보완/검토 필요이지 제품 시험 실패가 아니다. `Write/Validate`는 기획 자료 정합성 검사이며 완료 승인 관문이 아니다. `PlanOnly` 주소는 형식 점검 예시이며 실제 접속·포장하지 않는다. 현재 `-AppNames`를 생략하면 주문자·음식점·음식 기사·운영자·화주·화물 기사·창고의 7앱 전체 대상이므로 필요한 앱을 명시한다. 설명용 역할과 실제 패키지 대상 이름을 혼동하지 않는다.

화면 증거에는 정적 시안 / 공용 Razor 합성 / API 연결 / Android 실행을 구별한다. APK 파일 생성, 장치 설치, 배포도 별개다. 이 입력 도구나 Node 시험을 통과한 것으로 음식 업무·실제 서버·앱 출시를 통과했다고 보고하지 않는다.

r9의 기존 입력 예제: [음식점 메뉴 검토 초안](restaurant-menu-input-review.md). 현재 공통 절차의 첫 화물 적용은 위의 역할별 마감 계획을 따른다.
