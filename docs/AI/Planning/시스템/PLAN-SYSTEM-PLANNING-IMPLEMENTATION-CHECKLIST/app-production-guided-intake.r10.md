# 부족한 정보만 문답으로 채우는 앱 제작 절차

- 기획 ID: `PLAN-SYSTEM-PLANNING-IMPLEMENTATION-CHECKLIST`
- 판본: `app-production-guided-intake.r10`
- 상태: `ConfirmedWorkflow / DocumentationOnly`
- 승인 근거: 2026-09-27 사용자 “정보가 부족한 경우 … 문답을 … 계속 하면서 … 채워지는 방식”, 후속 “그래 그렇게 설정이 됐으면 좋겠어”.
- 선행: [입력 표준 r9](app-production-intake.r9.md), [r9 구현 결과](app-production-intake.r9.result.md).
- 적용: 기존 앱의 업무 보완과 새 역할 앱의 제작 입력 준비. 제품 구현·배포의 포괄 승인은 아니다.

## 확정

사용자는 빈 양식을 전부 채우지 않는다. AI가 기존 기획·코드·자료로 먼저 입력을 구성하고, 이번 업무에 꼭 필요한 정보가 부족할 때만 대화를 이어 채운다. **문답은 필수 의식이 아니라 실제 결손을 보완하는 절차**다. 충분한 정보가 있으면 새 질문을 억지로 만들지 않는다.

### 1. 앱 전체가 아니라 이번 업무부터 고른다

현재 요청에 대상 앱·역할·업무가 드러나 있으면 그대로 사용하고 다시 묻지 않는다. 대상 자체가 불명확해서 범위를 정할 수 없을 때만 첫 질문으로 좁힌다. 음식점·기사·주문자·운영자의 모든 기획을 매번 한꺼번에 입력하거나 확정하지 않는다.

### 2. 다루는 정보를 먼저 찾아 연결한다

다음 항목을 r9의 `information`과 `workflow` 입력에 요약하고 기존 정보대장·계약·원장·API를 출처로 연결한다. 새로운 독립 원장이나 문답 전용 DB를 만들지 않는다.

| 확인할 것 | 음식점 메뉴 업무의 예 |
| --- | --- |
| 누구에게 어떤 목적으로 필요한 정보인가 | 음식점은 메뉴를 관리하고 주문자는 공개 메뉴를 조회 |
| 정보가 어디서 생기는가 | 음식점 입력·기존 메뉴 DB·공공자료·계산 결과 중 구분 |
| 누가 읽고 누가 바꾸는가 | 가게 소유 범위에서 변경, 공개 여부에 따른 조회 |
| 언제 생성·변경·확인되는가 | 등록/수정 후 서버 저장, 같은 목록 재조회 |
| 다른 역할과 공유할 부분은 무엇인가 | 이름·가격·품절과 내부 관리 정보 구분 |
| 실패·민감정보·금전과 어떤 관계인가 | 미확인 저장·중복·권한 거부, 실개인정보 없는 시험 표본 |

주소·코드 경로·기존 API처럼 검색/코드 확인으로 채울 수 있는 것은 AI가 조사한다. 업무 정책·공개 의도·허용 행동처럼 사람이 정해야 하는 것과 구분한다. 기획과 코드가 다르면 차이를 남기고 어느 쪽이 정본인지 임의로 결정하지 않는다.

### 3. 결손을 나누고 필요한 질문 하나만 한다

- **기존 확정:** 근거·판본과 함께 재사용한다. 모순이나 변경 요청이 없으면 재질문하지 않는다.
- **조사할 사실/기술 결손:** AI가 조사·대조한다. 사용자가 API·DB·hash를 설명하게 하지 않는다. 접근이 막히면 필요한 환경 조치만 별도로 알린다.
- **사용자 선택:** 지금 만들 업무에 영향을 주는 미정 정책만 질문한다. 정확성·권한·개인정보·금전·업무 시작/종료를 막는 결정부터 다룬다.
- **후속/제외:** 이번 업무에 필요하지 않으면 사유와 함께 남긴다. 모든 미래 경우를 결정할 때까지 문답을 늘리지 않는다.

질문은 짧은 실제 상황, 선택할 내용, 추천과 대가를 제시한 뒤 **한 번에 하나**만 묻는다. 자유로운 말로 답할 수 있어야 하며 번호 선택이나 JSON 작성을 강요하지 않는다. 양식의 기본 질문은 빈칸 안내이지 반드시 사용자에게 읽어야 하는 질문 목록이 아니다.

예시 형식(아직 실제 정책을 묻거나 승인한 것이 아님):

> 조리 중인 주문에 취소 요청이 들어왔습니다. 음식점이 상황을 확인한 뒤 응답하도록 할까요? 추천은 확인 후 응답이며, 바로 취소되는 방식보다 처리가 늦어질 수 있습니다.

### 4. 답변을 누적하고 필요한 경우에만 다음 질문으로 간다

답변은 해당 업무의 canonical PLAN에 질문/의미 식별자, 사용자 의도, 결정/미정, 영향받는 입력 항목으로 기록한다. 기존 ID를 보존하고 전체 질문 번호를 새로 만들지 않는다. 간단한 답변의 의미가 분명하면 그대로 반영하고, 중요한 해석이 갈릴 때만 해당 지점을 되묻는다.

앱 공통 사항은 프로필을 재사용하고 업무별 내용은 여섯 입력 묶음에 연결한다. 해결된 질문은 활성 `questions`에서 제외하되 답변 근거는 기획 문서에 보존한다. 남은 질문·충돌은 지우거나 승인으로 바꾸지 않는다. 입력/출처 변경에 따른 hash와 검토의 현재성은 r9 도구로 재점검한다.

### 5. 충분해지면 문답을 끝내고 확인 요약을 돌려준다

이번 범위의 사용자 선택이 채워지고, 미정은 제외 사유 또는 차단으로 구분됐을 때 다음을 짧게 보여준다.

- 이번 앱/업무가 다룰 정보와 사용자 행동
- 재사용할 기존 기능과 새로 보완할 범위
- 남은 기술·환경 차단 및 이번에 하지 않을 것
- 검증·화면·시험 APK 등 요구 결과물

확인된 답변을 전체 입력표의 사람 확인이나 개발 승인으로 확대하지 않는다. 자료가 충분하면 기존 기획·작업지시서·허용 경로·명시적 실행 승인 절차로 연결하며, 이미 유효한 승인이 있으면 그 범위에서 진행한다. 정보가 충분한 것, 환경이 준비된 것, 코드가 있는 것, 실제 시험한 것은 각각 다르다.

## 현재 반영과 미정

이번에는 **저장소의 기획·입력 안내에 대화형 작업 절차를 확정**했다. 자동 질문 생성 엔진, 신규 입력 웹 화면, 백그라운드 문답 자동화는 추가하지 않았다. r9 도구의 `questions/conflicts`, 입력 검토·환경 상태를 재사용한다.

[음식점 메뉴 초안](restaurant-menu-input-review.md)의 기존 탐색·새 메뉴 비공개 등을 다시 질문하지 않는다. 길이 제한·서버 URL 검사 차이는 먼저 AI가 조사할 기술 항목이고, 이 문답 방식 승인으로 제품 수정이나 예제 전체 입력 확인을 승인하지 않는다.

다음 질문 하나: 없음. 지금은 제작 절차를 설정하는 요청이며 새 제품 선택이 필요하지 않다. 다음 앱 업무의 자료를 대조한 뒤 실제 부족한 사용자 선택이 있을 때만 시작한다.
