# 앱 공통 제작 절차 적용

- 상태: `Approved / ImplementationInProgress / OperationalDisabled`
- 승인 근거: 2026-10-26 사용자가 공통 앱 개발 절차 제안 뒤 “한번 작업을 작업을 진행해 줘봐.”라고 요청했다.
- 제품 목표: 기존 모든 업무를 포함하는 [통합 앱 1.0](../../../../Versions/unified-1.0/README.md).
- 공통 절차 정본: [앱 제작 입력 안내](app-production-input-guide.md). 기존 r8 추적·r9 입력·r10 문답·r11 보완·r12 대표 실행과 원 기록을 재사용한다.

## 이번 작업의 결과

앱 개발 요청을 기존 제작 입력과 관계 대장에 연결하고, 준비·구현·서버 완주·휴대폰 확인·제한 사용·공개 준비의 입력과 통과 조건을 같은 업무 기록에서 찾을 수 있게 한다. AI가 기존 기획·코드·시험으로 입력을 먼저 채우며 제품 선택이 남은 부분만 사용자에게 확인한다.

단계는 개발 검증의 기준이다. 제품의 주문·배차·입출고 상태를 새 관리 DB에 복제하지 않는다. 도구의 입력 확인·자료 현재성·시험 통과는 실제 서버나 휴대폰의 업무 완료를 자동 승격하지 않는다.

## 포함 범위

1. 기존 입력 안내를 공통 제작 절차로 보강하고 AGENTS, 제작 도구 사용법, 통합 1.0 마감표에서 연결한다.
2. 같은 업무의 원장·역할 인계·오류와 복구·현재 소스/서버/APK·결과 근거를 한 작업으로 결속하는 기준을 정한다.
3. 기존 app-production 도구에 화주·창고의 설명용 역할과 한글 필터를 추가한다. 권한·앱 패키징 대상과는 별개다.
4. 기존 시험 fixture의 변경된 검증/포장 도구 의존과 현재 7앱 계약을 반영하고 전용 도구 시험을 실행한다.
5. 첫 적용 대상으로 화물 한 건의 화주·전문 기사·운영자 입력을 앱별로 등록한다. 제품 책임은 기존 `PLAN-OPERATIONS-DISPATCH-CORE`가 소유한다.
6. 화물 파일럿은 동일 실행/의뢰/운송 ID, 현재 서버·APK, 역할별 재조회와 중단 후 결과 확인의 검증 계획까지 준비한다. 신규 입력을 사용자가 직접 검토했다고 소급 기록하지 않는다.
7. 생성 상태판과 현재 작업·결과 기록을 갱신하고 기준 문서의 옛 제품 목표 문구를 통합 1.0과 호환 분류로 구분한다.

## 역할별 분담

| 담당 | 변경 범위 |

| 공통 절차 | 입력 안내, AGENTS, 제품 마감 링크, 기획/변경/현재 작업 기록, 최종 통합과 생성물 |

같은 파일은 한 담당자만 수정한다. 공통 파일의 기존 변경은 보존하고 반영 직전에 다시 읽는다. 독립 작업의 병렬 진행을 허용하며 다른 업무의 활성 개수만으로 차단하지 않는다.

## 검증과 마감

- 도구 변경은 `eng/tests/app-production.ps1`로 검사한다. 문서/eng-only Fast 결과를 전용 도구 시험 통과로 해석하지 않는다.
- 기존 생성기의 Write/Validate와 새 화물 입력별 IntakeCheck를 실행한다. 사람 확인/환경 미확인에 따른 종료 3은 예상 보류로 보고하고 통과로 바꾸지 않는다.
- 현재 변경 경로만 지정해 문서/형식 검사를 수행하고 상대 링크·JSON·diff를 확인한다.
- 가능하면 생성 상태판에서 화주/기사/운영자 항목을 실제 브라우저로 확인한다. 순수 DOM 시험과 브라우저 확인은 구별한다.
- 결과는 `app-common-workflow.r13.result.md`에서 문서·도구 시험·상태판·화물 실행 준비를 나누어 기록한다.

## 실행 범위

이번 승인은 공통 절차·도구·파일럿 등록과 로컬 도구 검증이다. 화물 API/DB schema/실제 권한·운영 모드·가격/금융/배차 정책을 변경하지 않는다. 실행 중 서버/컨테이너/기기 점유, DB 초기화, 실제 API 업무 실행, APK 빌드/설치, 공개 배포, commit/push는 이번 회차에서 수행하지 않는다. 화물 실제 검증은 정확한 환경과 새 입력을 수용한 다음 회차의 실행 결과로 별도 남긴다.
