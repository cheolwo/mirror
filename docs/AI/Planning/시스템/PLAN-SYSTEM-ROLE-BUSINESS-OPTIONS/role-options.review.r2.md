- 요청: 구현 전에 음식·화물의 역할별 선택 항목과 화면 처리 옵션을 다시 조사하고 보완 후보를 제시한다.

## 1. 결론과 조사 범위

선택 항목은 이미 상당 부분 존재하지만, **개인 화면 설정, 자신의 업무 조건, 상대와 합의할 조건, 플랫폼 정책**이 서로 다른 화면·DTO·원장에 흩어져 있다. 옵션을 모두 새로 만드는 것보다 기존 항목의 주체·적용 범위·변경 시점·저장 위치를 먼저 정리하는 편이 적절하다.

음식의 주문자·음식점·기사·운영자와 화물의 화주·기사·창고를 대조하고, 기존 여덟 역할 중 생활 참여자도 인접 범위로 확인했다. 기획 목차, 역할 작업공간 r22, 음식 비용 분담 r26, 각 역할의 화면·DTO·UseCase·설정 코드를 읽었다. 이번 대장은 해당 범위의 정적 조사이며 모든 API·앱·단말의 전수 실행 검증은 아니다.

표의 ‘현재 근거’는 코드·기획에서 확인한 항목이다. ‘보완 후보’는 미승인 제안이다. DTO 값이 존재하는 것, 저장 경로가 존재하는 것, 모든 소비 앱의 화면·실제 수신·지급이 연결되는 것은 별개의 사실이다. 완성도 점수나 출시 가능 판정은 하지 않는다.

## 2. 옵션을 네 종류로 구분

| 종류 | 예시 | 결정 주체·적용 범위 | 저장·변경 경계 |
| --- | --- | --- | --- |
| 개인 표시 | 지도/목록, 카드 자세히, 금액 내역 접기, 조회 필터 | 보는 사람·기기/계정/조회 | 업무 원장·상대 조건·권한을 바꾸지 않음 |
| 자신의 운영 의사·기본값 | 신규 제안 받기, 알림, 기본 조리 추천, 복귀 콜 선호 | 본인 또는 해당 가게·조직의 권한자 | 다른 사람이 의존하는 조건은 서버 저장·재조회가 필요 |
| 건별 조건·상대 합의 | 시간창, 작업 범위, 요금표, 비용 분담, 인계 방법 | 제안자와 영향을 받는 당사자 | 초안→제안→상대 확인→확정 시 판본 동결. 변경 가능한 단계만 허용 |
| 플랫폼 운영 정책 | 기본 요율, 허용 범위, 한시 할증, 승인 권한 | 권한 있는 운영자 | 정책 판본·유효 시각·감사 근거 보존. 기존 확정 건에 소급하지 않음 |

수락·조리 시작·픽업·전달·인수·출고는 **상태를 바꾸는 업무 행동**이지 평소 설정의 ON/OFF가 아니다. 인증·현재 상태·revision·멱등·정본 재조회와 확정 금액 보존도 해제 가능한 옵션으로 만들지 않는다. `Required / Conditional / OptionalTool`은 표시 위치 분류이며 합의·업무 권한이 아니다.

## 3. 음식 역할별 대장

### 주문자

| 영역 | 현재 근거 | 보완 후보·추천 | 확인 시점 |
| --- | --- | --- | --- |
| 음식점 탐색 | 행정동·반경·이름·종류·주문 가능 여부 필터 | 지도/목록 기본 보기, 자주 쓰는 검색 조건 | 조회 때. 검색 반경과 가게의 주문 허용 범위를 구별 |
| 주문 입력 | 메뉴·수량, 본인/다른 수령인, 전달 요청, 취소 사유 | 직접 받기/문 앞 등 전달 방식과 연락 선호를 필요한 만큼 구조화 | 주문 확인 때. 현재 전달 요청 자유 문구를 대체하지 않고 병행 |
| 비용 | 본인 잔여 부담 상한, 음식점 분담 조건 r26 | 적용 요금표와 본인 부담을 최종 확인에 함께 표시 | 주문 전. 금액 미확인을 0원으로 보이지 않음 |
| 수행 방법 | 자동 수행 조건의 비용·기한·업체 범위·정보 제공 동의 입력 | 자주 쓰는 조건 저장 후 ‘이번 건만 변경’, 허용 단계에서 철회·변경 | 기존 r25/r26의 확정·취소 관문을 유지 |
| 알림·공개 | 일부 정보 동의·연락 입력 기반 | 주문 단계 알림 채널, 연락 가능 방식·공개 범위 | 알림 설정이 필수 업무 사실이나 서버 기록을 없애지 않음 |

지도상의 주변 기사에게 주문자가 직접 업무를 확정하는 기능, 특정 실적 기준의 기사 자격, 자동 연락처 공개를 이번 옵션으로 추가하지 않는다. 상대 선택과 기사 수락은 별도이며 기존 승인·동의 정책을 다시 대조해야 한다.

### 음식점

| 영역 | 현재 근거 | 보완 후보·추천 | 확인 시점 |

현재 `PreparationTimeSettings`는 **이 기기에서 사용할 추천값**임을 화면에서 밝힌다. 이를 가게 전체 동기화나 서버에 확정된 조리시간으로 설명하면 안 된다. ‘20분 초과 안내’ 등 기존 조리 알림 기획도 실제 통지 연결을 별도로 확인한다.

## 6. 화면 처리 추천

1. **현재 업무 화면**: 현재 단계, 이번 건의 확정 조건, 지금 가능한 행동을 기본 표시한다. 수락 전에는 대가·작업 범위·시간·비용 부담을 함께 확인한다.
2. **내 업무조건**: 자주 쓰는 본인 설정·가게 설정을 독립 페이지에서 관리한다. 개인 표시, 알림, 업무 기본값을 묶음별로 구분하고 원 업무로 돌아가는 경로를 둔다.
3. **이번 건 조건**: 기본값을 가져와 요약하고 ‘이번 건만 변경’을 제공한다. 어떤 조건이 본인 선택이고 상대 확인 대기인지 보인다. 새 기본값 저장과 이번 건 변경은 별개 행동이다.
4. **요금표·계약 관리**: 당사자·적용 범위·판본·기간·제안/수락/철회 상태를 독립 관리한다. 단순 화면 설정과 같은 저장 버튼으로 계약을 확정하지 않는다.
5. **고급 정보**: 과거 이력·계산 상세·보조 도구는 접을 수 있다. 미확정·한도 초과·상대 미동의·필수 적합성·취소/철회·문제 연락은 접힌 설정 뒤에 숨기지 않는다.

알림 OFF, 신규 제안 OFF, 운행 종료, 공개 OFF는 네 가지 서로 다른 의사다. 설정 저장 실패·지원되지 않는 항목·미합의 상태는 그대로 표시하며 저장된 것처럼 낙관적으로 확정하지 않는다. 여러 기기에서 바뀌거나 견적 중 판본이 바뀌면 서버의 현재 조건을 다시 읽고 필요한 동의를 받는다.

## 8. 보완 우선순위와 발견한 연결 공백

1. **기존 항목 분류와 적용 범위 표시**: 조리 기기 추천값↔가게 서버 조건↔주문 확정값, 알림↔신규 제안↔운행↔공개, 기준 견적↔합의 운임↔기사 대가를 먼저 구별한다.
2. **이미 승인한 요금표·비용 분담 연결**: r1/r26·음식/화물 계산을 재사용한다. 요금표 선택·상대 수락·판본 동결과 최종 확인을 먼저 닫는다. 새 단가·수수료를 여기서 정하지 않는다.
3. **기존 설정의 소비 공백 보완**: 음식 기사 앱의 공통 알림 설정, 통합 역할 카드의 표시 설정, 가게 공통 조리 기본값의 실제 저장/조회와 연결을 확인한다. 코드 존재만으로 연결됐다고 보고하지 않는다.
4. **화물의 자유 문구를 필요한 만큼 구조화**: 상하차 노동·장비·무료 대기·추가 정차를 견적과 기사 제안에서 같은 의미로 읽게 한다. 기존 수락 이후 잠금을 보존한다.
5. **창고 계약과 권한 분리**: 검토용 요율표의 실제 합의 경로와 관리자/현장 권한을 확인한다. 공급·예약·묶음·자동 수락 등 신규 영역은 승인 후 별도 범위로 진행한다.

후속 구현 검증에는 본인/상대/운영자 권한 차이, 기기 간 동기화, 오래된 판본·미동의·만료·철회 차단, 확정 건 비소급, 비용 분담 합계, 재요청·응답 유실 뒤 정본 재조회, 접어도 필수 조건·회복 행동이 보이는지를 포함한다. 모의 계산·API/DB·UI·APK/단말·실금전 증거는 분리한다.
