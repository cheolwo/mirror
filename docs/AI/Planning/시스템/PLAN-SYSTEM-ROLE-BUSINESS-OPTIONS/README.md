# 역할별 업무조건과 사전 합의 요금표 r1

- 기획 ID: `PLAN-SYSTEM-ROLE-BUSINESS-OPTIONS`
- 판본: `r1`, 기준일: 2026-10-07.
- 기획 상태: `Approved`. 직전 제안에 대한 사용자의 `Implement the proposed plan.` 요청을 승인 근거로 기록한다.
- 개발 인계 상태: `NotReady`. [개발 작업지시서](development-work-order.r1.md)의 기준선·소유권 관문을 먼저 닫는다. 제품 구현 완료가 아니다.
- 주 책임: `operations`. Unity·게임 Simulation의 상태나 화면을 변경하지 않는다.

## 목적과 확정 범위

‘방편’은 정식 업무 절차 안에서 당사자가 선택·합의할 수 있는 처리 조건이다. 플랫폼이 모든 금액과 수행 방법을 일방적으로 정하는 구조 대신, 플랫폼 기본안과 당사자 사이의 사전 합의안을 선택할 수 있게 한다.

사용자가 선택한 기본은 **사전 요금표 중심**, 첫 범위는 **요금표와 비용 분담 연결**이다. 건별 흥정과 플랫폼 이용료에 배송비를 포함하는 상품은 후속 후보다. 구체적인 단가·수수료율, 실제 청구·지급 활성화는 이번 승인에 포함하지 않는다.

## 네 가지 결정을 분리

| 결정 | 선택 내용 | 결정 주체와 경계 |
| --- | --- | --- |
| 수행 요금 | 운송수단, 픽업비, 전달비, 거리 단가와 산정 기준 | 플랫폼 기본안 또는 업무 당사자 간 사전 합의안 |
| 비용 분담 | 주문자 부담, 음식점 정액 지원·비율 분담·전액 부담 | 음식점 조건 제시와 주문자 본인 부담 상한 확인 |
| 수행 수락 | 해당 조건으로 실제 업무를 맡을지 | 기사·운송업체의 기존 건별 수락 절차 |
| 플랫폼 이용료 | 별도 부과 또는 배송 포함 상품 | 기존 정책 유지. 새로운 포함 상품은 후속 |

음식점과 주문자의 비용 분담만으로 기사 대가를 변경하지 않는다. 요금표 수락은 모든 배차의 자동 수락이 아니다. 고객에게 받은 금액, 음식점 부담, 기사 지급 예정액, 플랫폼 이용료와 지급 완료도 각각 구분한다.

## 사전 합의 요금표

1. 기존 음식 배달의 픽업·전달·거리 계산과 화물의 차량별 운임 계산을 재사용한다. 음식·화물 계산기와 원장은 합치지 않는다.
2. 플랫폼 기본안 외에 음식점·화주와 기사·운송업체가 관계별 요금표를 제안하고 상대방이 수락·거절할 수 있게 한다. 철회는 이후 적용을 막되 이미 동결된 업무의 근거를 지우지 않는다.
3. 제안·수락은 본인 또는 권한 있는 조직에 한한다. 화면에서 역할을 선택한 사실이나 상대방 식별자를 입력한 사실을 권한으로 해석하지 않는다.
4. 적용 당사자, 업무 종류, 운송수단, 단가, 거리 기준·단위·반올림, 유효 기간, 판본과 합의 근거를 연결한다. 자유로운 계산식 실행 대신 기존 계산 항목을 사용한다.
5. 견적에 적용한 요금표와 계산 근거를 표시한다. 명시적으로 선택한 합의안이 미합의·만료·철회 상태이면 재선택을 요구하며 다른 요금표로 조용히 대체하지 않는다.
6. 서버가 권한·합의·업무의 현재 상태를 검증한 뒤 기존 Command·원장·Event/Outbox 경로로 저장한다. 성공 뒤 모든 당사자가 같은 원장을 다시 조회한다.
7. 이미 확정된 제안·업무 금액은 요금표 변경으로 소급 계산하지 않는다. 재요청과 응답 유실에서 같은 멱등 키로 원 결과를 확인한다.
8. 음식 비용 분담은 [생활권 물류 r26](../../공통/PLAN-OPERATIONS-NEIGHBORHOOD-MICRO-HUB/delivery-cost-sharing.implementation.r26.md)을 재사용한다. 별도 분담 계산기를 만들거나 그 작업의 진행 상태를 완료로 간주하지 않는다.

## 역할별 선택 항목 대장

다른 영역은 후보를 정리하는 범위이며 새 요율·계약을 활성화하지 않는다. 정책상 불허와 코드 미연결은 다른 상태로 표시한다.

| 역할 | 선택 항목 | 동의할 상대 | 적용 단계와 이번 범위 |
| --- | --- | --- | --- |
| 생활 참여자 | 직접 수령·직접 전달·기사 배송과 비용 조건 | 거래 상대, 필요하면 수행자 | 기존 생활 배송을 보존하고 조건 대장만 연결 |
| 주문자 | 본인 배송비 상한, 음식점의 분담 조건 확인 | 음식점이 제시한 조건을 확인 | 주문 동의. r26 재사용 |
| 음식점 | 배송비 분담, 관계별 수행 요금표 제안·수락 | 주문자, 기사·운송업체를 각각 구별 | 주문 전 설정과 수행 전 합의 |
| 음식 기사 | 운송수단에 맞는 요금표 제안·수락·거절 | 음식점 또는 권한 있는 계약 상대 | 사전 합의와 건별 배차 수락을 분리 |
| 화주 | 차량별 운임, 거리 기준, 픽업·전달 등 기존 항목 | 기사·운송업체 | 의뢰 전 합의와 확정 의뢰의 금액 보존 |
| 화물 기사 | 적용 차량·운임 조건과 건별 수락 | 화주 또는 권한 있는 계약 상대 | 음식 정산과 합치지 않음 |
| 창고 담당 | 보관 기간·공간 단위·입출고 작업비 | 이용자·화주 | 후보 대장만 작성. 수치·계약 활성화 후속 |
| 운영자 | 플랫폼 기본안, 선택 가능 범위, 합의 결과 조회 | 당사자의 합의를 대신하지 않음 | 기본 정책 관리와 예외 확인 |

공급자의 납품 주기·수량·배송비 포함 여부도 후속 후보로 둔다. 이 대장으로 조직 담당자의 실제 계약 권한이 확인된 것은 아니다.

## 구현 순서와 검증

1. 승인 PLAN·내용 해시·정확한 기준선·수정 경로와 기존 변경 소유권을 결속한다.
2. 사전 요금표의 제안·상대 수락/거절·철회·재조회와 멱등 저장을 먼저 완성한다.
3. 음식·화물별 계산기에 각각 연결하고 적용 판본과 금액을 해당 업무에 동결한다.
4. r26 분담 조건과 견적 표시를 연결하고 당사자 화면에서 같은 결과를 확인한다.
5. 다른 역할은 기존 선택 항목·코드 연결·미연결을 대장으로 구분한다.

완료 검증은 다음을 포함한다.

- 플랫폼 기본안과 합의안이 기존 계산기로 정확히 계산되는지.
- 타인 요금표 수정, 미합의·만료 조건 적용, 중복 수락, 오래된 revision을 차단하는지.
- 음식점·주문자 부담 합계와 총 배송비가 일치하며 기사 대가·플랫폼 이용료와 혼동되지 않는지.
- 요금표 변경·철회 뒤에도 확정 업무의 금액과 근거가 보존되는지.
- 응답 유실·재시작·Outbox 재처리가 중복 합의·업무·지급을 만들지 않는지.
- 당사자 화면에서 동일 조건·판본·결과를 서버로부터 재조회하는지.
- 모의 계산, 서버 시험, 실제 DB/API, 화면, 실지급 증거를 별도로 보고하는지.

## 미정과 제외

구체적 요율·최대액·새 수수료·배송 포함 상품·건별 흥정·실제 청구와 지급 활성화는 미정 또는 제외다. 기존 기상·시간대 할증과 과거 동결 금액을 이 작업으로 임의 변경하지 않는다. 조직별 기존 권한을 대조하지 못한 경로는 허용으로 추정하지 않고 개발 관문에 남긴다.

2026-10-08 사용자가 우선순위 3·4번의 직접 구현을 승인했다. 현재 로컬 작업트리에서 진행하는 [수용 범위 r4](agreements-alerts.implementation.r4.md)와 [화면 책임](../../../../ProjectOverview/page-docs/agreed-rates-notification-settings-r1.md)을 따른다. 과거의 작업실 교대 질문은 이번 승인 범위에 적용하지 않는다. 구현·로컬 시험·APK와 실제 기기·공용 DB 적용·실지급은 별도다.
