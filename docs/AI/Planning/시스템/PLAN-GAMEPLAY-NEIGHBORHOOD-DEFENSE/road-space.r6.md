### 원본 결손과 변환 누락을 구별

1. **원본에 있는 폭도 전달하지 않음:** way `1055786332`는 `highway=footway`, `footway=sidewalk`, `width=3`을 가진다. 화면에 6개 선분으로 들어오지만 변환 JSON은 `id/kind/양끝 좌표`만 남긴다. Unity `사가정지리MeshBuilder.cs`는 이를 다른 footway와 똑같이 표시 폭 1.5로 그린다. `3`은 원문 태그값이며 이번에 실제 현장 폭을 측정한 것은 아니다.
2. **대부분의 폭·차로 수는 원본부터 없음:** 원본에서 차로 수가 있는 두 way `153148439`, `1112327042`는 용마터널 관련 사가정로이며 각각 `lanes=2`, `oneway=yes`, `tunnel=yes`다. 현재 변환은 터널을 제외한다. 두 값을 지상 사가정로 전체의 차로 수나 폭으로 일반화하지 않는다. 터널이 현재 지도에 보이지 않는 것을 실제 부재로 해석하지 않는다.
3. **표현 폭은 하드코딩:** primary/secondary=10, footway/steps=1.5, 나머지=4의 기호 폭이다. secondary_link와 주거도로도 현재 같은 4로 표현된다. 원본의 도로 등급 차이가 충분히 반영된 폭 산정이 아니다.
4. **행정동 투영에서도 속성 손실:** `행정동실자료완결.ReadRoads`와 `행정동디오라마RoadInput`은 식별자·양끝 좌표·근거 종류만 전달한다. 현재 Unity JSON에 있는 도로 종류조차 이 입력에는 없다. 따라서 Unity 렌더러만 바꿔서는 행정동 자료 흐름 전체를 해결하지 못한다.

기존 공간 수집 영수증 `artifacts/local/neighborhood-source-acquisition/receipt.json`의 `roadAndEntranceAcquired=false`와 과거 공식 자료 보고서의 도로구간 자료 미확보 상태를 확인했다. 이것은 해당 수집 묶음의 기록이다. 현재 모든 DB·전 저장소에 공식 도로 자료가 없다는 결론은 아니다. 이번에는 실제 DB 재조회나 새로운 공식 도로 파일 확보를 하지 않았다.

## 보완 순서 제안 — 구현 승인 아님

1. 원본의 도로 종류·이름·보도/횡단 구분·폭 원문·일방통행·입체 구분을 정규화 단계에서 보존한다. 미상 폭은 미상으로 유지한다. 기존 way/선분 ID로 계보를 연결한다.
2. 사가정로·면목로·용마산로·면목천로부터 공식 도로 자료의 차로 수/폭/대상 구간·이용조건을 확인한다. 같은 이름이나 근접 좌표만으로 자동 결합하지 않는다. 이번 점검은 그 자료를 확보했다는 뜻이 아니다.
3. 원본 폭·추정 폭·게임 표현 폭을 나눈 중간 변환 결과를 만들고, 도로 종류별 상대 크기와 골목 두 명 교행 기준을 함께 검토한다. 실제 폭 자료가 거의 없으므로 현재 자료만으로 현실 기반 수치 비율을 확정하지 않는다.
4. 보도 중복 계산, 면형 보행 구역, 교차로·건물 겹침과 입체 교차를 검사한 뒤 Unity가 읽도록 한다. 도로 폭 변경으로 영향받는 기존 옥상 배치도 재검사한다. OSM 배경 자료 또는 넓어진 렌더링 자체에 게임 이동/전투 권위를 부여하지 않는다.
