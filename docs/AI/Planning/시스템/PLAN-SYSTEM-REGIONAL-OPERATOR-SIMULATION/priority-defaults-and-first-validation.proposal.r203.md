### 준비·대기·포장을 읽는 예

추천안에서 커피 한 잔은 총5분 안에 마감/포장을 포함한다. 마감/포장에 **마지막1분을 배정하는 예시**를 검토할 수 있지만, 에스프레소 추출 자체를 길게 바꾸거나 세부 단계마다5분을 더하지 않는다. 실제 레시피 조건과 게임의 작업 예산/연출 시간을 구분한다.

앞 작업이2분 남았고 내 커피 작업이5분이면 **대기 약2분 + 준비5분 = 픽업 준비까지 약7분**으로 읽는다. 여기에는 기사 도착·픽업/배송은 포함하지 않는다. 시작한 작업의 경과는 집중/이완·창/층/회차 전환에도 유지하며 공통 시계를 쓴다. 실제로 화면에서 기다리는 시간/배속·연출 압축은 r174/r202의 별도 미정이다.

작업은 **접수/대기→자원 확보→제조/조리 진행→마감/포장→픽업 가능→인수**로 읽는 안이다. 상태 이름/새 API를 이 문서에서 확정하지 않는다. 각 단계의 권위 결과와 기존 ID/원장/명령을 명세에서 결속한다.

## 3. 현재 라떼 자료에서 비용·단위를 정하는 방법

현재 값은 모두 `hongdal-business-first-chain.json`의 **기존 가상 검토팩** 값이다. 시장가격이나 사용자에게 새로 확정받은 경제 수치가 아니다. 첫 비교에서는 유지하고 시간/상태 변화의 영향을 분리하는 안을 권한다.

| 의미 | 현 팩/첫 해석 |
| --- | --- |
| 주문·입고 단위 | 우유1팩=1000mL |
| 제조 기준 | 라떼1잔에 우유170mL |
| 점포 가상 매입가 | 우유1팩2400원 |
| 가상 판매가 | 라떼1잔4500원 |
| 계산 가능한 부분 원가 | 우유 사용분만 `2400÷1000×170=408원` |

**408원은 라떼 전체 원가가 아니다.** 현 제조 프로필은 우유만 소모한다. 원두·컵·뚜껑·필요 포장재/수율·근무비가 미연결이다. 첫 완전 원가 프로필은 이들을 별도 SKU/수량/단가/판본에 연결해야 한다. 모르는 비용을0원으로 채워 `4500−408`을 순이익으로 표시하지 않는다. 잔량은 mL로 이월하며 한 잔마다 우유 한 팩을 소모하지 않는다.

매출/비용의 대상 경제 주체도 명시한다. 현재 점포 `sales`, 공급 `supply-payable`, 동 수요 자금은 같은 통합 현금 계정이 아니다. 첫 창에는 **매출 / 확인된 재료사용원가 / 공급 미지급 / 범위가 명확한 가용자금**을 구분하고, 통합 계정 연결 전 서로 더하지 않는다. 미지급은 실제 지급이 아니다.

새 시간 프로필의 판매 인식은 **유효 판매 주문의 인수 결과에 연결**하는 안을 후속 검토할 것을 권한다. 현 `produce`의 제조 완료 가상 매출·기존 저장/이력은 이번 제안으로 소급 수정하지 않는다. 카페 현장 고객 인수는 가능해야 하며 배달 Core 통합을 매출/카페 독립 시작의 필수 전제로 걸지 않는다. 수금/지급은 해당 별도 기록을 따른다.

## 4. 공간·인구는 이 범위부터 정한다

### 공간의 첫 기준

기존 모듈은 면목제3·8동과7동을 시작 지역으로 둔다. 첫 비교의 초점만 한 동에 두며 기존 다른 동의 진행을 없애지 않는다. 매장 A/B·카페/창고의 실제 결속 위치를 재사용한다.

가상 출입구·표현 길은 **가상 인계점/가상 경로**로 표시하고 선택한 지점들의 연결/통과를 확인한다. 실제 Core 배달 경로와 순찰 표현이 같은 업무를 수행한다고 표시하지 않는다. `traversalReady=false`/`gameplayReady=false` 등 현재 준비 상태와 역사 경계 제한도 보존한다. 실제 출입구/공식 도로를 받을 때는 별도 판본/접근 검증 뒤 전환한다.

### 인구와 주문의 첫 기준

한 동의 실제 유동지표·기준분기·단위/코드 대응을 먼저 조회 가능하게 하는 것을 권한다. 미결속이면 근거와 이유를 표시하고 면적을 사람 수로 바꾸지 않는다. 검토가 끝난 프로필만 기존 수요 입력 후보로 준비한다.

원문 인구/동 집계의 수요, 실제 Core 주문, 군중/순찰 표현은 별도로 유지한다. 첫 시간/처리량 검토에는 아래의 명시한 **가상 주문 일정**을 사용할 수 있다. 표시한 동이나 군중 수를 늘려 주문을 늘리지 않으며, 팩의 비교 분모/seed·자료/규칙 판본을 고정한다. 개별 주문 핀은 기존 주문 ID/`order_received`를 읽는 경로를 재사용한다.

## 5. 첫 검토용 시나리오와 기록 제안

첫 개발/검토 후보로는 **기존 카페의 라떼1잔을 시작→5분 진행→준비 완료 한 번**으로 만드는 작업을 권한다. 현재 검수/단위/가용·격리 재고를 보존하고 배달 Core 외부 주문 수용은 별도 후속 범위로 둔다. 배달·광고·전자상거래·무역의 플레이어 시작을 카페 완료 뒤로 제한하는 제안이 아니다.

시간/자원 명세가 준비된 뒤 사용할 **가상 카페 비교 시나리오**는 다음과 같다. 아직 실행한 시험/측정값이 아니다.

| 시나리오 | 제안 조건 | 확인할 선택 |
| --- | --- | --- |
| 한산함 | 가상 시간1시간·커피6건·작업자1/제조슬롯1 | 대기/유휴와 비용이 어떻게 읽히는가 |
| 바쁨 | 같은 조건·커피10건 | 작업자/슬롯 점유가 대기로 이어지는가 |
| 과부하 | 같은 조건·커피14건 | 받아내지 못하는 양/대기와 인력·설비 선택이 드러나는가 |

이 숫자는 비교를 위한 합성 부하다. 현 팩의 `waitingCups=1`과 구별해 별도의 합성 주문 도착 시험자료로 제공하며, 이미 현재 큐에6/10/14건이 생긴다는 뜻이 아니다. 동일한 주문 도착 일정/seed·초기 재고/규칙을 사용한다. 5분 작업 한 슬롯의 단순 계산을 현재 `partnerOrdersPerHour`에 덮어쓰거나 현실 처리능력으로 표시하지 않는다. 식사·휴식/고장·이송/동선·작업 병렬을 포함한 실제 처리량은 별도다.

과부하 비교는 **직원만 증원**한 경우와 **직원/제조슬롯을 함께 늘린** 경우를 나눌 수 있다. 슬롯이 병목이면 사람만 늘려도 처리량이 늘지 않을 수 있다. 효과를 미리 지급하지 말고 동일 조건의 대기/실제 완료·비용 변화로 확인한다. 이후 연구/엔진 개선은 대기·헛이동·재작업의 변화부터 비교하는 안을 권한다.

기록은 기존 회차/업무·행위 결과를 재사용해 **대상 주문/작업 ID·규칙/자료 판본·수량/단위·대기/시작/완료/인수 시각·예약/소모·비용/결과·막힌 이유·회복/귀환**을 묶는다. 보고를 연 횟수·순찰 애니메이션·결정 순회 버튼을 실제 작업 완료로 세지 않는다. 회차 마감/다음 준비는 기존처럼 새 시간·날짜·돈·주문을 만들지 않는다.

## 6. 순서와 반환 범위

추천 준비 순서는 **① 한 작업의 단위/시간·포장 범위 → ② 자원/재고의 예약·소모·완료 → ③ 원가/자금의 단위·범위 → ④ 같은 조건의 결과 비교**다. 공간/인구 결속은 필요한 업무 범위에서 병행하되 미해결 자료를 통계 기반으로 꾸미지 않는다. 실제 카페→배달 연결, 여러 잔 배치·직무 병렬화와 전체 경제 통합은 해당 작은 작업이 준비된 다음 별도 인계로 둔다.

현재 커널의 즉시 제조를 시간 작업으로 바꾸는 데 필요한 상태/저장·명령/인계·직원/설비 점유·실패/회복·표현/입력은 E1~E7 명세와 현 파일 소유/승인 판본에 결속해야 한다. 이 문서는 구현 지시서나 코드 쓰기 승인, 기존 Goal 활성화가 아니다. 전체 Core 재통합·새 OS/Scene·DB·수집/예약·그림 제작으로 범위를 넓히지 않는다.
