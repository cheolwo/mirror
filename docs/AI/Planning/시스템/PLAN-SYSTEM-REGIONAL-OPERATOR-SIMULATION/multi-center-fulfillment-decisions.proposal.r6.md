## 이번에 확장하는 방향

사용자는 위치 바코드로 적재대를 안내하는 구조를 **주문 접수→출고 물류센터 결정→그 센터의 적재 위치 결정→현장 출고 작업**으로 확장하도록 요청했다. r5의 현장 절차를 하위에 유지하고 여러 거점을 운영하는 상위 판단을 구체화한다. 큰 물류센터와 작은 도심 거점 모두 같은 판단 계층을 적용할 수 있지만 각 공간의 기능·조건·용량을 같다고 보지는 않는다.

운영자에게는 센터를 먼저 정하고 내부로 들어가는 단계로 보여 준다. 다만 센터를 고를 때 이미 그 안의 적격 재고·보관 위치·인력·출고 가능 시간을 확인해야 한다. 재고 총량만 보고 센터를 확정한 뒤 꺼낼 수 없는 물건이나 수행 불가능한 작업을 발견하게 만들지 않는다.

## 각 단계가 결정하는 것

| 계층 | 확인할 내용 | 다음 단계에 넘길 결과 |
| --- | --- | --- |
| 주문·출고 조건 | 품목·수량·단위·소유/판매 조건·수령지·시간 약속·분할 허용 조건 | 같은 주문과 라인의 수요·제약·판본 |
| 센터 선택 | 적격 가용 재고, 배송 가능 권역, 취급/운영 조건, 내부 출고 준비와 운송 가능성 | 단일 센터 또는 여러 센터의 품목별 출고 수량·선택/제외 이유 |
| 센터 안 재고·위치 선택 | 해당 센터의 입고 재고·로트·보관 위치·유효 조건·기존 예약 | 어느 선반/칸의 어떤 재고를 얼마나 사용할지와 주문 예약 근거 |
| 직원 작업 배정 | 담당 자격·근무 가능 시간·현재 부하·피킹/포장 방식·인계 지점 | 담당자별 위치·물품·수량·작업 순서와 확인 절차 |
| 포장·인계·운송 | 피킹 결과·포장/용기·출고 대기장·기사와 차량 조건 | 실제 인수·배송·수령의 개별 결과 |

센터 안 재고 후보는 센터 평가 때도 요약해서 사용하며, 최종 선택과 예약은 그 요약에 사용한 재고 참조를 이어받는다. 단계마다 독립적으로 재고를 새로 찾아 중복 배정하지 않는다. 위치·로트·소유자·수량은 결합된 재고 조건이므로 로트와 위치를 서로 맞지 않게 고를 수 없다.

```text
고객 주문과 출고 조건
  → 적격 재고·내부 처리 가능성을 가진 센터 후보
  → 센터별 준비 시간 + 운송 + 분할 부담 비교
  → 선택 센터의 위치·재고·작업 가능성 상세 확인
  → 최신 판본 재검증·센터 계획 확정·해당 재고 예약
  → 직원별 위치 안내·피킹 → 포장 → 기사 인수 → 배송·수령

내부 위치/재고/담당이 불가
  → 같은 센터의 적격 대안 검토
  → 해결되지 않으면 다른 센터·분할·일정 조정·보류로 상위 재판단
```

단계는 책임을 나눈 것이며 되돌아가지 않는 일방향 확정 절차가 아니다. 이미 완료한 실물 작업은 계획 재계산만으로 되돌리지 않는다.

## 센터를 고르는 기준

출고 권한·품목/소유 관계·판매/출고 가능 재고·취급 조건과 필수 시간/운송 조건부터 확인한다. 필수 조건을 통과한 후보끼리 준비 예상 시간·이동/운송 비용·작업 부하·분할 배송 부담을 비교한다. 어떤 배송권·시간 조건을 필수 제한으로 볼지, 선호로 볼지는 시나리오 정책에 명시하며 점수로 금지 조건을 덮지 않는다. 가중치와 수치는 이번에 정하지 않는다.

센터가 가깝다는 이유로 무조건 선택하지 않는다. 고객에게 도착 가능한 시점은 재고 확보, 앞선 작업 대기, 피킹·포장, 운송 확보와 이동의 제약을 함께 받아야 한다. 일부 작업은 병행될 수 있으므로 모든 시간을 단순 합산하거나 거리를 실제 배송 시간으로 바꾸지 않는다. 실측·추정·자료 부족도 구분한다.

설명용 사례는 다음과 같다. 실제 센터나 처리 시간을 등록하는 값이 아니다.

| 후보 | 현재 상황 | 비교 결과의 예 |
| --- | --- | --- |
| A센터 | 가장 가깝지만 해당 시간에 피킹 담당이 없음 | 다음 가능 시간과 지연을 비교. 약속을 지킬 수 없다면 제외/보류 |
| B센터 | 조금 멀지만 적격 재고·근무·포장 준비가 가능 | 주문 약속을 충족하면 선택 후보 |
| C센터 | 일부 품목만 출고 가능 | 단일 출고가 어려울 때 허용된 분할 대안으로 비교 |

센터 선정은 전체 네트워크의 최적 해답을 항상 보장한다고 표현하지 않는다. 자료가 있는 후보와 현재 규칙 안에서 비교한 결과와 근거를 보여 준다.

## 한 센터와 여러 센터, 한 선반과 여러 선반

한 센터가 여러 선반에서 물건을 꺼내 한 출고로 묶을 수 있고, 한 주문을 여러 센터에서 나눠 출고할 수도 있다. 센터 수·선반 수·포장 수·기사 운송 건수를 서로 같은 숫자로 취급하지 않는다.

복수 품목 주문은 가능한 단일 센터 계획과 허용된 여러 센터 조합을 비교한다. 분할 시 늘어나는 배송 단위·비용·도착 약속과 일부만 도착할 가능성을 주문 조건에 반영한다. 허용되지 않은 분할이나 추가 비용을 숨겨 확정하지 않는다. 센터 간 재고 이동은 별도 이송 작업이며 센터 선택만으로 물건을 다른 센터에 생성하지 않는다.

상위 주문 아래 센터별 출고 계획, 그 아래 라인별 재고 배분·예약과 피킹/포장 작업을 연결한다. 주문 라인별 배분 합계는 요청 수량을 넘지 않고 같은 재고는 여러 라인·동시 주문에서 중복 사용하지 않아야 한다. 일부 센터의 준비 완료를 전체 주문 출고나 고객 수령 완료로 올리지 않는다.

## 확정과 재계획의 경계

후보 조회·점수 비교·계획 생성은 읽기 판단이고, 재고 예약·직원 작업 생성·실제 피킹은 별도 사건이다. 계획에 주문/계획 판본·센터·재고/위치 참조·수량과 판단 이유를 묶고, 확정 직전에 해당 재고·현재 예약·위치·수행 가능성을 다시 확인한다. 센터만 확정하고 재고는 잡히지 않은 상태는 별도로 표시한다.

여러 센터의 예약은 **일부 성공을 전체 성공으로 표시하지 않는 것**이 원칙이다. 같은 저장소에서 일괄 확정할 수 있는 범위와 다른 시스템의 보상/재시도가 필요한 범위를 후속 명세에서 구분한다. 실패한 계획을 무조건 새로 발행하지 않고 성공한 예약을 조회해 유효 유지·해제·다른 센터 재계획을 결정한다. 요청 재시도로 예약과 작업이 중복 생성되지 않게 한다.

이미 피킹·포장·기사 인수가 진행됐다면 단순 예약 해제와 물품 반납/재배정·운송 변경은 별개다. 이전 담당에게 발행한 작업도 판본·취소/변경 상태를 확인한 뒤 새 지시와 충돌하지 않게 한다. r5의 위치·물품·수량 확인과 부족/불일치 예외를 그대로 적용한다.

## 게임에서 어떻게 보일지

- 권역 지도에서는 센터 후보마다 주문 충족 여부·출고 준비 예상·배송 약속·비용·현재 병목을 비교한다. 선택 이유와 제외/자료 부족을 함께 본다.
- 선택한 센터를 열면 해당 주문의 재고 위치와 직원 작업이 디오라마의 선반·포장대·출고 대기장에 연결된다. r5의 위치 바코드 확인은 이 하위 단계에 둔다.
- 직원 작업이 막히면 운영자는 내부 대안, 담당/일정 조정, 다른 센터·분할 계획을 비교한다. 후보 선택과 실제 결과·대가를 같은 회차에 남긴다.
- 기본은 직원 NPC가 작업하고 플레이어가 운영 판단을 하는 방식이다. 정확한 자동 결정/개입 UI와 직접 체험 범위는 아직 미정이다.

상위 목적에 대한 기여는 주문 약속과 수행 가능한 현장 자원을 연결하는 것이다. 직원의 시간·보수·부담, 고객의 수령 품질과 플랫폼 수익을 함께 비교하며 한 센터로 물량을 몰아 처리량만 높이는 선택을 자동 정답으로 두지 않는다. 오행/괘는 기존 상위 기획의 보조 해석을 유지하고 이번에 새 배속을 정하지 않는다.

경험 기록에는 당시 센터별 적격 재고·처리 가능성·거리/비용 자료의 판본, 비교 후보·제외 이유·선택, 예약/작업 변경, 위치별 실제 가상 수행과 주문별 결과를 연결한다. 선택하지 않은 센터의 결과는 관측 사실로 만들지 않는다. 별도 시뮬레이션 비교와 [r1의 학습 적격·평가·현실 추천](gameplay-experience-learning.proposal.r1.md)은 계속 구분한다.

## 현재 기반과 후속 설계

2026-10-25 현재 소스 읽기 기준이며 이번에 엔진·서버·Unity를 실행하지 않았다.

- [출고 배치 기준서](../../../../Architecture/OutboundBatchEngine.md)는 창고 선택과 하위 피킹 배치를 이미 분리한다. 이번 제안은 새 상위 엔진을 중복 신설하기보다 이 책임을 게임의 센터→내부 작업 판단으로 구체화한다.
- [OutboundBatchEngine](../../../../../Ssalddel/Services/LogisticsProcessing/Warehouse/OutboundBatchEngine.cs)과 [계약 DTO](../../../../../Ssalddel.Contracts/Common/Warehouse/OutboundBatchDtos.cs)는 창고·입고 재고별 배분, 배송권·거리/비용 정보, 분할 여부와 부족 라인을 반환한다. 계획 함수 자체가 예약·실물 출고를 실행하는 것은 아니다.
- 현재 필수 후보조건은 활성 창고·판매자/SKU·가용 수량·판매 가능 계약이며 배송권은 점수 선호다. [배분 정책](../../../../../Ssalddel.WorkflowRules/UnityPackage/Runtime/창고출고배분Policy.cs)은 단일 센터로 각 라인을 충족하는 안을 먼저 찾고 없으면 후보순으로 분할한다. 단일/분할안의 총비용을 모두 비교하는 전역 최적화는 아니다. 모든 품목 보관/기한·현장 인력·시간 약속·실시간 교통·최단 경로의 검증이 완성됐다고 표시하지 않는다.
- [판매채널 예약 경로](../../../../../Ssalddel/Services/LogisticsProcessing/SalesOrders/SalesChannelOrderSyncService.cs)는 같은 SQL 트랜잭션에서 전체 재고의 조건부 예약을 처리하고 실패하면 롤백한다. 이 경로의 일괄 예약과 여러 시스템에 걸친 예약/보상은 구분한다. [피킹 작업 생성](../../../../../Ssalddel/Services/LogisticsProcessing/Warehouse/출고피킹작업생성Service.cs)은 내부 배정 불가 시 보류하며 다른 센터를 자동 재선정하는 흐름은 이번 조사에서 확인하지 못했다.
- r5의 일반 창고/분산 물류 차이는 유지한다. 센터의 세부 위치·로트·작업 가능성을 일관된 판본으로 요약하고 확정·예약·작업·실제 수행에 연결하는 게임용 Simulation 설계가 추가로 필요하다. 기존 한 경로의 SQL 예약을 모든 다중 센터/시스템의 실행·복구 완료로 확대하지 않는다.

## 확정·미정·인계
