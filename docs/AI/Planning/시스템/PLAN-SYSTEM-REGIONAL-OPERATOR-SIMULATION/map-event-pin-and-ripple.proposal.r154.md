## 1. 플레이어가 보는 한 번의 흐름

후속 [효과 선택 r157](optional-map-visual-effects.design.r157.md)은 낙하·파동·흐르는 빛을 선택형으로 제공하는 사용자 방향이다. 아래 움직임은 효과 사용 시의 제안이며, 끈 상태에도 정적 표식·현재 건수·문구·상세/업무 선택과 중요 알림을 유지한다.

**주문 접수 확인 → 핀이 내려와 착지 → 얇은 파동이 퍼짐 → 대기 중인 주문 표식이 남음 → 선택해서 상세 확인**을 기본 표현으로 제안한다. 주문은 이미 Core에 접수된 사실이며 연출 종료를 기다려 접수되는 것이 아니다.

| 순간 | 표현 | 남는 정보 |
| --- | --- | --- |
| 새 주문 확인 | 해당 매장의 화면상 위쪽에서 핀이 짧게 내려온다 | 위치와 새 주문의 존재 |
| 착지 | 작게 한 번 안착하고 바닥에서 얇은 원 두 겹이 퍼진다 | `새 주문` 아이콘/짧은 문구 |
| 연출 종료 | 파동은 사라지고 미처리 주문 표식·현재 대기 건수만 유지한다 | 대기·진행·완료 등 현재 상태 |
| 선택 | 해당 주문/묶음의 기존 상세·추천 후보를 읽는다 | 현재 가능한 업무 행동 |

낙하 약0.35~0.45초, 파동 약1초는 검토 시작값이다. 카메라가 보는 위에서 내려오되 도착점은 기존 지리 좌표/매장 앵커에 고정한다. 이동·확대 중에는 도착점을 다시 투영한다. 파동 크기는 판독 가능한 화면 범위로 제한하며 실제 수요권·배송 가능 반경·음파 전파·매출 증가를 뜻하지 않는다. 큰 반동·계속 반복되는 파동은 기본으로 두지 않는다.

첫 주문 핀 위치는 **픽업 매장**을 추천한다. 플레이어의 첫 질문이 어느 매장의 주문에 어떤 기사를 연결할지이기 때문이다. 배송지는 해당 주문을 고른 뒤 기존 경로/상세와 함께 보여 주는 안이다. 이 위치 선택은 아직 미정이다. 좌표가 없거나 공개 범위상 사용할 수 없으면 지역 중심이나 주변 건물을 대신 찍지 않고 위치 미확인 주문 목록으로 안내한다.

## 2. 화면 효과와 현재 주문 표식을 따로 관리한다

공통 처리에는 두 입력 경로가 필요하다.

```text
Core의 현재 상태 사본 ───────────────────→ 현재 주문/작업 표식·대기 건수
Core에서 새로 확인한 사건 → 중복·시점 확인 → 위치·관점 해석 → 제한된 연출 큐
                                                          ↓
                                            낙하·착지·파동의 일회 표현
```

핀·파동이 끝나거나 생략돼도 주문/작업이 사라지지 않는다. 연출 큐는 하단의 업무 대기열과 별개다. 대기 건수는 현재 권위 상태에서 읽고, 짧게 보이는 `이번 새 주문 +N`만 해당 사건 묶음에서 센다. 큐 길이나 대표 핀 수로 실제 주문 수를 계산하지 않는다.

공통 표현 책임은 아래처럼 작게 나눈다. 이름은 제안이며 새로운 공용 EventBus나 실제 DTO를 이미 만든 것으로 보지 않는다.

| 표현 책임 | 하는 일 | 하지 않는 일 |
| --- | --- | --- |
| 기존 상태/사건을 읽는 Adapter | 현재 소비판의 상태·사건을 읽고 최초 로딩/복원과 정상 진행을 구별 | 주문 생성·원장 수정 |
| 사건 표현 Policy | 회차 범위·사건 종류별 중복, 발생 시각·우선순위·묶음·연출 만료 판정 | 업무 수락·배차·시간 진행 |
| 지도별 위치/집계 | 매장/업무 ID와 허용 좌표를 현재 축척에 투영하고 같은 장소를 집계 | 좌표 추정·행정동/법정동 동일시 |
| 공통 표현 Player | 낙하·원 확산·투명도와 장식 객체 수를 제한 | 권위 상태·연출을 완료 조건으로 판정 |
| 표식·상세 View | 현재 상태를 읽어 표식을 유지하고 기존 상세/목록으로 진입 | 연출 선택을 주문 수락·직접 조작 시작으로 해석 |

일반 건물의 회색과 관리 매장/시설의 운영색은 그대로다. 새 주문은 주문 아이콘·짧은 문구·일시적 강조로 구별하고 건물 전체를 운영색으로 바꾸지 않는다. 파동은 기사·주요 경로·선택 표식보다 낮은 층, 업무 패널보다 아래에 두며 클릭을 가로채지 않는다. 이동 중인 장식 핀에도 업무 Hit 영역을 붙이지 않는다. 기존 안정 표식과 목록은 정상 선택을 유지한다.

## 3. 한 규칙, 사건별로 다른 표현

| 사건 | 공통 처리 | 표현 프로필 제안 |
| --- | --- | --- |
| 주문 접수 | 새 사건 한 번·장소·현재 대기 상태 연결 | 핀 낙하+착지 파동 |
| 픽업/작업 준비 완료 | 같은 업무의 새 상태 변화 | 기존 표식에 준비 아이콘·짧은 강조. 매번 새 주문 핀을 만들지 않음 |
| 배송/검수 완료 | 확정 결과를 읽고 대기 표식을 갱신 | 한 번의 완료 표시 뒤 현재 상태로 정리. 보상은 정식 정산을 읽음 |
| 새 지사/시설 등장 | 기존 Territory 의미와 운영색 유지 | 기존 구 지도 낙하/파동 재사용 후보 |
| 지연·실패·중요 결정 | 지속 알림과 복구 진입 연결 | 별도 아이콘·문구·우선순위. 파동이 끝나도 미해결 의미 유지 |

형태·문구로 뜻을 구별해 색이나 소리에만 의존하지 않는다. 소리는 향후 선택 항목이며 이번 제안의 필수 요소로 추가하지 않는다. 첫 구현 후보는 음식의 `order_received` 한 종류와 동네 지도 소비다. 다른 사건·축척의 일반화는 같은 기준이 확인된 뒤 잇는다.

## 4. 겹침·축척·입력·시간 규칙

- **밀집:** 짧은 묶음 시간 동안 같은 매장/대표 위치에 몰리면 대표 낙하 한 번과 `이번 +N`으로 표현한다. 현재 대기 건수와 개별 주문 ID·상세 목록은 보존한다. 이미 있는 집계에 새 주문이 추가돼도 새 도착 피드백은 남기되 집계 전체를 재낙하하지 않는다. 묶음 시간·동시 연출 수 상한은 실측 뒤 정한다.
- **축척:** 건물/동네에서는 개별 장소, 구에서는 동/지사에 맞춘 요약, 광역에서는 센터/회차 등 현재 경영 질문으로 집계한다. 지리적 위치가 없는 업무를 시설로 임의 배정하지 않는다. 축척 전환은 같은 사건의 재발생이 아니다.
- **화면 밖/가림:** 일반 사건은 현재 관점의 새 주문 수·목록에 남기고 카메라를 자동 이동하지 않는다. 나중에 화면에 들어왔다고 오래된 낙하를 몰아서 재생하지 않는다. 사용자가 목록에서 위치 보기를 선택한 경우에만 기존 지도 이동을 요청한다.
- **집중·이완:** 어느 쪽에서도 같은 사건을 읽는다. 운전·커피·포장 중 새 주문이 입력·카메라·직무를 빼앗지 않는다. 상세를 읽는 것과 작업을 시작하는 것은 별개이며 r151의 `다음 작업`과 현재 가용/담당 확인을 유지한다.
- **시간:** 일반 알림 연출은 배속과 분리한 짧은 표현 시간을 사용하고, 가상 시계 정지 직전에 시작한 낙하도 안착까지 끝내는 안을 추천한다. 이 동안 주문·기사·정산 시간은 진행시키지 않는다. 화면 비활성/최소화 후 오래된 연출은 생략하고 현재 표식과 목록으로 복귀한다. 기존 생활 보행의 가상 시간 규칙과 구별한다.
- **움직임 감소:** 낙하·확산 대신 즉시 나타나는 정적 아이콘·테두리·문구를 제공한다. 정보·선택·대기 건수는 동일하다. 강한 번쩍임과 지속 반복은 사용하지 않는다.
- **중요 알림:** 연출 수 제한·직무 필터·화면 밖 처리로 지연/실패/복구 진입을 지우지 않는다. 일반 주문 애니메이션과 구분한 지속 알림 책임을 유지한다.

## 5. 재조회·복원·중복의 경계

처음 로딩하거나 저장을 복원하면 그 상태를 기준선으로 등록하고 기존 주문은 안정 표식으로 보인다. 정상 진행에서 새로 확인한 사건만 일회 연출 후보가 된다. 재조회·뒤로 가기·확대/축소·카메라 이동·같은 사건 재전송으로 다시 떨어뜨리지 않는다.

중복은 주문 ID만이 아니라 **회차 범위와 사건의 발생 단위**로 구별해야 한다. 새 회차에서 같은 주문 ID를 써도 이전 회차의 감지 기록으로 막지 않는다. 같은 주문의 접수·준비·지연을 같은 사건으로 합치지 않는다. 사건을 큐에 넣거나 화면 밖으로 생략했을 때 표현 소비를 기록하고, 다른 축척에서 다시 새 사건처럼 만들지 않는다. 이 기록은 연출 관찰 기록이며 주문을 처리했다는 업무 기록이 아니다.

현재 `DispatchEvent`에는 `orderId/at/code/text`가 있으며 전역 사건 ID·확정 sequence·Revision이 있다고 가정하면 안 된다. 첫 `order_received`는 회차별 주문당 한 번이라는 Core 보장이 실제 확인된 경우에 한해 기존 정보로 범위를 좁힐 수 있다. 반복 가능한 일반 사건은 기존 확정 식별 계약을 조사하고, 안정적으로 구별할 수 없으면 현재 상태 표시로 제한한다. 같은 시각·문구의 해시만으로 확정 사건 고유성을 만들어내지 않는다.

상태 사본 두 개만으로 관찰 사이에 일어난 모든 사건을 복원할 수는 없다. 사건 이력이 잘렸거나 확인 기준이 불명확하면 여러 낙하를 지어내지 않고 현재 대기·진행 상태와 확인 가능한 새 사건만 보여 준다. 연출은 생략될 수 있는 피드백이며 누락 없는 업무 알림·정확한 원장 처리는 기존 계약이 맡는다.

## 7. 검토·검증과 현재 산출물

대화용 동작 개념은 실제 지리와 무관한 단일 기준점에서 주문 1건과 같은 장소의 여러 건을 연출한다. 버튼은 가상 사건을 재생할 뿐 실제 주문·위치·수요·Unity 입력을 사용하지 않는다. 일반/움직임 감소의 정보 일치를 보는 용도이며 게임 구현·성능·최종 시각 승인 근거가 아니다.

후속 실제 검증은 신규1건·동일 사건 재수신·복원·새 회차의 동일 ID·여러 건·기존 집계에 추가·지도 밖/가림·낙하 중 이동/줌·집중 작업 중 접수·시계 정지/배속·움직임 끄기·지연 취소/해결을 확인한다. 준비/취소/완료가 낙하 중 도착하면 최신 상태 표식을 우선하고 오래된 접수 연출은 종료/생략한다. 모든 경우 주문·재고·금액·정산·명령 수가 장식 재생으로 바뀌지 않아야 한다.

- **확정된 사용자 방향:** 새 주문을 핀 낙하와 착지 파동으로 알아차리게 하는 시각 피드백, 지도 사건의 공통 처리 구조 제안.
- **제안·미정:** 픽업 매장 기준, 세부 타이밍·모양·색·반경·동시 수·묶음 시간·정지 중 안착, 공통 타입과 사건 식별 계약. 제품 코드는 미구현이다.
- **다음 질문 하나:** 첫 새 주문 핀은 **픽업 매장**에 꽂고 배송지는 주문을 고른 뒤 보여 줄까? 기사 연결의 첫 판단과 맞아 이 구성을 추천한다.
