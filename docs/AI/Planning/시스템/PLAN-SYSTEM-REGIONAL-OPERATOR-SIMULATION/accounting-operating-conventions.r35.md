## 1. 조사 결론

프로젝트에는 하나의 `회계 날짜`만 두지 않고 다음 세 시간축을 분리한다.

1. `업무 발생축`: 주문·조리·배달·취소·환급·정산 의무가 발생한 시각
2. `현금 이동축`: PG 입금, 음식점·기사 지급, 고객 환급, 세금 납부가 실제로 일어난 시각
3. `회계 보고축`: 일·주·월·분기·반기·연말 마감과 적용 회계기간

13주 전망은 매주 앞으로 13주를 보는 내부 자금관리 도구이고, 분기는 고정 회계기간의 실적 보고다. 같은 거래 원본을 사용하되 한쪽을 다른 쪽으로 대신하지 않는다.

## 2. 공식 체계에서 가져올 관습

### 적용 회계기준과 계정체계의 판본화

[외부감사법 제5조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1031407025)는 회계처리기준을 한국채택국제회계기준과 그 밖의 법정 기준으로 구분한다. 따라서 회사 설립형태·규모·외부감사·상장 여부가 정해지기 전에는 K-IFRS 계정체계를 운영 정본으로 고정하지 않는다.

[OpenDART 재무정보 개발가이드](https://opendart.fss.or.kr/guide/main.do?apiGrpCd=DS003)는 IFRS 적용 회사의 정기보고서 주요·전체 계정과 XBRL 재무제표, 공시용 표준계정과목체계를 제공한다. 프로젝트의 내부 Stable ID는 유지하고, 외부 공시가 필요해질 때 승인된 관리계정만 적용 기준의 XBRL taxonomy 계정에 매핑한다. OpenDART 계정을 내부 업무 원장의 식별자로 직접 사용하지 않는다.

### 수익·현금·의무의 분리

[한국회계기준원 시행 중 기준 목록](https://www.kasb.or.kr/front/board/ingAccountingList.do)은 수익, 현금흐름표, 금융상품, 충당부채 등 서로 다른 기준을 별도로 둔다. 프로젝트도 고객 결제, 플랫폼 수익 후보, PG미수, 음식점·기사 지급의무, 조건부 준비금과 실제 현금을 각각 분리한다.

### 세무 달력의 별도 관리

[국세청 부가가치세 안내](https://nts.go.kr/nts/cm/cntnts/cntntsView.do?cntntsId=7693&mi=2401)는 부가가치세 과세기간을 6개월로 두고 각 과세기간을 3개월 예정신고 구간으로 나누며 사업자 유형에 따라 신고 대상과 방식이 달라짐을 안내한다. 따라서 `1~4분기 경영 보고`와 `부가가치세 예정·확정 신고`를 동일 상태로 합치지 않는다. 법인·개인·간이과세 여부와 적용 기한은 `ComplianceCalendarRevision`에서 판본화한다.

## 3. 회계 순환의 프로젝트 표준

```text
업무 Event 수락
  → 증빙 봉투 결속
  → 재무 사건 생성
  → 관리계정 분개 후보
  → 보조원장 전기
  → 은행·PG·업무 원장 대사
  → 시산표·미대사 목록
  → 월·분기 마감 검토
  → 조정 또는 역분개
  → 승인 판본 보고
```

- 전표 후보는 삭제하지 않고 취소·역분개·조정으로 이력을 남긴다.
- 원 업무 Event의 식별자·revision·증빙 hash를 잃은 금액은 `미대사`로 남긴다.
- 마감 뒤 과거 기간을 바꿀 때는 `ReopenedWithReason`과 재승인 기록을 요구한다.
- 동일한 멱등 key의 Event 재처리가 같은 재무 사건이나 전표 후보를 중복 생성하지 않는다.
- 실제 전표 확정은 `ApprovedForOperationalPosting` 권한이 생길 때까지 열지 않는다.

## 4. 관습적 운영 주기

| 주기 | 자동 기본 작업 | 회계사 검토 | 운영자에게 보여줄 결과 |
| --- | --- | --- | --- |
| 실시간 | 주문·정산·지급·환급 재무 사건과 증빙 결속 | 미매핑·금액 불일치만 예외 확인 | 현재 가용현금·확정 의무·즉시 경보 |
| 일마감 | 은행·PG·주문·기사·음식점 보조원장 대사, 미대사 이월 | 큰 차이·증빙 누락·중복 후보 | 오늘 순현금 변화와 해결할 예외 |
| 주마감 | 13주 전망을 한 주 앞으로 이동, 지급 일정·정책 민감도 재계산 | 현금 최저점·미지급 위험·가정 변화 | 다음 13주 현금 방어선과 조언 카드 |
| 월마감 | 기간 cutoff, 미수·미지급·선수·선급·감가·세금 후보, 시산표 | 조정분개 후보, 계정 대사, 가계정 잔액 | 월 손익·재무상태·현금흐름과 미확정 항목 |
| 분기마감 | 3개월 실적, 전분기·예산 비교, 공시 taxonomy 후보 | 중요 판단·본인/대리인·수익 인식 검토 | 1~4분기 경영 보고와 위험 설명 |
| 반기·연말 | 적용 기준 재무제표·세무 달력·감사 자료 후보 | 외부 회계사·세무사 확인 | 승인 보고서와 미승인 차이 |

자동 기본 작업은 운영자가 매번 버튼을 누르지 않아도 수행한다. 다만 미대사, 미승인 계정 매핑, 현금 부족, 중요 추정 변경, 마감 후 수정은 회계사 카드와 운영자 판단 대상으로 남긴다.

## 5. 13주 전망과 분기 결산의 결합

- 13주는 `ForecastAsOfDate`부터 91일을 일별 원장으로 계산하고 주별로 묶는다.
- 회계 분기는 `FiscalYearCalendarRevision`에 따라 시작·종료일을 고정한다. 기본 후보는 1~3월, 4~6월, 7~9월, 10~12월이지만 회사 결산월 승인 전 운영 정본은 아니다.
- 한 주가 두 분기에 걸치면 주간 전망은 그대로 두고, 회계 보고는 각 거래 발생일·현금일로 해당 분기에 나눠 집계한다.
- 같은 거래가 13주 전망과 분기 보고 양쪽에 보이더라도 재무 사건 ID는 하나다.
- 분기 종료는 13주 전망을 정지시키지 않는다. 분기 실적이 확정되면 이후 전망의 실제값으로 치환하고 차이를 예측오차로 기록한다.

## 6. 필수 보조원장과 대사

| 보조원장 | 기준 원본 | 주요 대사 |
| --- | --- | --- |
| 고객 결제·환급 | 주문, PG 승인·매입·취소·입금 | 주문 청구액 = PG 처리액 + 미처리 차이 |
| 음식점 정산 | 상품대금·취소 보호·공제 근거 | 주문별 의무 = 지급 + 미지급 + 승인된 조정 |
| 기사 수행대금 | 정상·취소 수행 시도와 지급 상태 | 수행대금 의무 = 지급 + 미지급, 정상·취소 별도 분석 |
| 지사 운영보상 | 지사 계약·시간대·업무 귀속 | 산정 대상 = 지급 + 미지급 + 검토 차이 |
| 플랫폼 수익 후보 | 수수료·배달료·광고·기타 계약 | 본인·대리인·수행의무 판본과 금액 대조 |
| 현금·은행 | 은행·PG 입출금 원문 | 장부 현금 = 은행 잔액 + 조정 중 항목 |
| 세금 후보 | 세금계산서·카드·현금영수증·계산 근거 | 신고 대상·기간·공급가액·세액 후보 대조 |

대사식은 회사 정책으로 숨기지 않고 회계사 상세 화면에서 양쪽 원본, 차이, 경과일, 담당자와 해결 상태를 보여 준다.

## 7. 마감 상태와 역할 분리

`Open → SoftClosed → AccountantReview → Closed → ReopenedWithReason`

- `Open`: 업무·재무 사건 수락
- `SoftClosed`: 자동 대사·시산표가 생성됐지만 조정 가능
- `AccountantReview`: 중요 예외와 회계 매핑 검토 중
- `Closed`: 승인 판본으로 보고 잠금
- `ReopenedWithReason`: 사유·승인자·영향 보고와 함께 제한 재개

작은 조직에서 한 사람이 여러 역할을 맡더라도 시스템에는 `PreparedBy`, `ReviewedBy`, `ApprovedBy`를 분리해 남긴다. 동일인이 겸임하면 숨기지 않고 `RoleCombined`로 표시해 후속 내부통제 보완 대상으로 삼는다.

## 8. 운영자 통합 UX에 스며드는 방식

별도 회계사 앱·화면·상위 메뉴를 만들지 않는다. 같은 운영자 통합 화면에서 권한에 따라 다음 카드와 상세 영역을 제공하며, 분개장을 첫 화면에 던지지 않는다.

1. `오늘`: 대사 완료율, 미대사 금액, 오늘·내일 지급, 가용현금
2. `13주`: 현금 최저점, 부족 예상주, 지급의무, 정책별 차이
3. `월마감`: 시산표, 계정 대사, 조정분개 후보, 마감 차단
4. `분기`: 1~4분기 실적·전망·예산 차이와 중요 판단
5. `상세`: 업무 Event, 증빙, 보조원장, 관리계정, 차변·대변 후보, 승인 판본

정상 거래는 자동 대사·기본 매핑으로 조용히 흐르고, 회계사는 예외와 중요한 판단에 집중한다. 운영자는 `왜 현금이 부족한가`, `어떤 의무가 언제 지급되는가`, `정책을 바꾸면 어느 계정과 현금이 변하는가`를 자연어 조언으로 먼저 본다.

## 9. 개발 반영 순서

1. `AccountingCalendarRevision`: 회계연도, 월·분기·반기·연말, 영업일·마감 상태
2. `EvidenceEnvelope`: 주문·PG·은행·세금·계약 증빙 식별자와 hash
3. 보조원장별 `FinancialEvent` 투영과 멱등
4. 관리계정 전표 후보·전기·시산표·역분개
5. 주문/PG, 음식점, 기사, 지사, 현금, 세금 후보 대사
6. 일·주·월·분기 마감과 reopen 이력
7. 13주 전망 actual/forecast 결합과 예측오차
8. 운영자 통합 예외 카드·회계 조언·승인 판본
9. 실제 회계사 검토 뒤 외부 회계·세무 Adapter를 별도 Goal로 검토

## 10. 검증

- 일·주·월·분기 집계가 동일 재무 사건에서 파생되고 합계가 일치한다.
- 차변·대변 후보, 보조원장 잔액과 총계정 후보가 통화별로 일치한다.
- PG·은행·주문·기사·음식점 대사 차이를 0으로 숨기지 않는다.
- 마감 뒤 수정은 역분개·조정·재개 이력 없이 과거 값을 덮어쓰지 못한다.
- 같은 seed·업무 revision·회계 달력·계정 매핑 revision으로 13주와 분기 결과가 재현된다.
- 13주 전망이 분기 경계에서 초기화되거나 중복 집계되지 않는다.
- 사업자 유형이 달라지면 신고 달력 후보가 새 revision으로 바뀌고 과거 판본은 보존된다.
- 자동 마감 실패는 운영을 성공으로 표시하지 않고 `ReviewRequired`로 남긴다.

## 11. r36에서 폐쇄된 질문

오늘의 대사·지급 예외와 13주 전망은 별도 회계사 화면이 아니라 운영자 통합 화면의 같은 재무 관점에서 연결한다. 상단 상시 요약과 운영자 표시 용어는 `operator-integrated-accounting-summary.r37.md`가 소유한다.
