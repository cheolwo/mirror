## 1. 플레이어가 반복해서 확인하는 질문

지금은 사가정역 주변의 가상 매장에 주문이 적은 오늘 오전이다. 나는 점주 또는 고객 매장을 맡은 광고 운영자다. 한 검색어에서 경쟁 매장보다 덜 보이는 이유를 확인하고, 제한된 돈을 광고·정보 정리·메뉴/처리 여력 중 어디에 쓸지 고른다. 광고업으로 출발한 사람에게 자기 음식점 소유를 요구하지 않는다.

**검색어 선택 → 내 매장의 페이지 확인 → 한 가지 개선/홍보 선택 → 실행·관찰 → 비용·정상 주문 결과 비교 → 다음 회차 조정**을 짧은 반복으로 제안한다. 페이지 상승 자체와 돈을 버는 결과는 따로 읽는다. 손실이 나면 예산을 줄이거나 중단하고, 매장 준비를 보완한 뒤 같은 지도·매장으로 돌아온다.

서비스 가칭은 r176의 **동네찾기**를 유지한다. 플레이어가 직접 열어 보는 독립적인 게임 내 장소검색 창이며 지도와 왕복한다. 이름·사진·메뉴는 가상 매장 정보를 사용한다. 실제 업체를 관찰하는 화면에는 가상 중개 의뢰나 부정행위 평가를 붙이지 않는다.

## 2. 검색 목록과 매장 상세 화면

| 영역 | 보여 줄 내용/행동 |
| --- | --- |
| 검색 조건 | `게임 내 가상 검색`, 검색어, 가상 고객의 기준 위치/범위, 시간대, 정렬, 집계 시각. 역을 보는 카메라 위치와 검색 기준 위치를 따로 유지 |
| 검색어 탭 | `사가정역 치킨`, `사가정역 피자`, `사가정역 맛집` 등 즐겨찾기. 탭별 내 매장 노출을 비교 |
| 광고 영역 | `[광고]` 표식, 대상 매장·영업/주문 가능 상태·광고 위치. 일반 검색 번호에 포함하지 않음 |
| 일반 목록 | 매장 이름·메뉴/업종·거리·예상 대기·게임 내 이용 경험. 내 관리 매장은 민트/관리 배지로 식별 |
| 내 매장 요약 | `일반 검색 14위 · 2페이지 4번째`, `[내 매장 위치 보기]`. 지금 페이지에 없더라도 상태 확인 가능 |
| 페이지 이동 | 제안값은 일반 결과 페이지당 10곳. 1~10위=1페이지, 11~20위=2페이지. 광고 칸은 별도 |
| 매장 상세 | 메뉴/가격·사진·영업시간·대기·주문 가능 여부·게임 내 이용 이력. `[지도에서 보기]`로 해당 건물 강조 |
| 운영자 도구 | `[광고 설정]`, `[매장 정보 개선]`, 소개 후 `[중개업자 연락]`, `[유입 결과]` |

페이지 크기·상세 배치는 제안이다. 후보가 10곳 이하라면 두 번째 페이지를 억지로 만들지 않는다. 미노출·조건 불일치·자료 미준비는 `11위` 같은 숫자로 바꾸지 않는다. 페이지 이동으로 목록을 다시 추첨하지 않고 같은 조회 판본을 유지한다.

매장 상세에서 지도에 갔다 돌아와도 검색어·선택 매장·페이지를 복원한다. 플레이어의 검색/새로고침/페이지 이동은 판독 행동이며 노출수·클릭수·광고비·주문을 발생시키지 않는다. 지표를 만드는 것은 고객 시뮬레이션의 별도 행동이다.

## 3. 같은 화면에서 세 가지 경영 선택

| 선택 | 플레이어 설정/얻는 것 | 결과 화면 |
| --- | --- | --- |
| 정식 광고 | 대상 매장·관심 주제·지역/시간대·예산 한도. 광고 칸의 발견 기회를 얻음 | 광고 위치·노출·유효 열람·정상 주문 기여·집행 비용 |
| 매장 개선 | 정보/메뉴를 정리하거나 품질·재고·바리스타/기사 여력을 보완 | 검색 의도 부합·이탈/대기·실제 이용 경험의 변화 |
| 중개업자 의뢰 | 소개받은 NPC에게 대상 검색 의도·규모·기간·비용 조건을 맡김 | NPC 납품 주장, 잠정 일반 순위 변화, 정상 주문, 검증/회복 상태 |

정식 광고가 광고 칸의 상단에 나왔다고 일반 검색 1위로 표시하지 않는다. 관심과 정상 이용 경험이 이후 일반 검색에 영향을 줄 수 있지만, 광고비가 곧 일반 순위 점수는 아니다.

중개업자 경로는 r177처럼 **일반 순위가 실제로 잠정 상승할 수 있는 가상 경로**로 둔다. 순위 상승을 전부 무효로 만들거나 매번 강제 적발하지 않는다. 계약 비용·효과의 불확실성·신호 제외/노출 제한·중단/회복이 경영의 대가다. 합성 열람 자체는 정상 고객·주문·매출을 만들지 않는다. 정상 고객이 올라간 목록을 보고 선택하고, 기존 업무 흐름에서 이행해야 성과가 생긴다.

보유 IP/계정은 NPC의 가상 자원량으로만 표현한다. 실제 접속 신원·체류 초·클릭 순서·우회 설정을 조절하는 화면은 만들지 않는다. 게임의 신호 반영과 검증은 자체 규칙이며 실제 서비스의 판정표가 아니다.

## 4. 처음부터 전문 경영까지

첫 체험은 한 행정동·한 역 검색 문맥·한 매장을 대상으로 한다. 강남역은 요청한 데이터 후보 예시이며 게임 첫 지역을 강남으로 바꾸는 결정이 아니다. 여러 역·업종은 목록에 준비하되 모두 동시에 운영하게 하지 않는다.

1. 안내를 받아 검색어 하나를 고르고 내 매장의 페이지와 정보 부족을 확인한다.
2. 제한된 정식 캠페인 하나를 설정해 실행·관찰하고 결과를 확인한다.
3. 정식 광고를 경험한 뒤 NPC 소개를 받는다. 소개받음은 계약·지급·효과 발생과 다르다.
4. 광고 유지·매장 개선·중개 의뢰 중 다음 선택을 한다. 거절/보류 후 기존 경영으로 돌아올 수 있다.
5. 연구를 통해 검색어 비교·소재 개선·처리 여력 예측·여러 매장 예산 배분으로 확장한다. 전국 광고망은 전국 경영과 심화 준비의 후속이다.

r183에 따라 광고 입문은 처음부터 선택할 수 있다. ‘전국 지도를 열어야 기초 광고를 시작할 수 있음’으로 되돌리지 않는다. 광고업 시작은 준비된 가상 고객사 매장으로 체험하는 안이다. r178의 점주 예시는 이 역할에도 적용할 수 있지만, 고객사 캠페인의 경험을 소개 조건으로 인정할지는 아래 질문의 미정 사항이다.

## 5. 순위 비교·회차·일일 결산

순위의 키는 `검색어/의도 + 고객 기준 위치/범위 + 정렬 + 집계 판본`이다. 같은 매장도 `사가정역 치킨`과 `사가정역 맛집`에서 다르게 나온다. 수치 예시는 홍달 설계 예시이며 실제 네이버 자료가 아니다.

| 비교 예시 | 광고 칸 | 일반 검색 | 해석 |
| --- | --- | --- | --- |
| 시작 | 없음 | 14위/2페이지 | 이 검색 문맥에서 아직 덜 보임 |
| 정식 광고 실행 후 | 2번째 | 14위/2페이지 | 광고 발견 기회가 늘었음. 일반 순위 상승은 아직 없음 |
| 별도 중개 의뢰 후 | 유지/중단 선택 | 잠정 7위/1페이지 가능 | 계약 효과 예시. 정상 주문·비용·검증은 따로 확인 |

일반 순서는 이전 확정 집계와 제한된 잠정 신호로 계산하고, 현재 고객 세션에서는 고정한다. 현재 클릭을 즉시 다시 순위에 넣는 순환은 두지 않는다. 정확 반영 시점·가중치·동률/난수·감쇠·검증 시점은 미정이다. 같은 문맥/규칙일 때 순위 증감을 표시하고, 검색 범위나 후보집합이 달라진 비교에는 조건 변경을 표시한다.

회차 결과는 `내 일반 페이지/위치 · 광고 위치 · 정상 고객 열람/주문 · 비용 · 실제 이행 결과`를 읽고 다음 선택으로 돌아온다. r174의 KST 일일 집계와 r187의 같은 날 여러 회차를 유지한다. 회차 마감이 다음 현실 날짜를 만들지 않는다. 주문 생성·이행·정산·현금 이동의 시각도 구별한다.

NPC 납품 보고와 게임 계산 결과는 별도 열이다. 검색 신호가 나중에 제외돼도 이미 정상 이행된 주문을 되감지 않는다. 결과 재열람·재접속으로 비용을 중복 차감하지 않는다. 앱 종료·부재중에 광고비·트래픽·주문·벌금을 임의 생성하지 않는 기존 경계는 유지한다. 진행 중 캠페인의 종료·재개, 미집행 예산의 승계와 자정 경계의 상세 처리만 미정으로 둔다.

## 6. 역×음식 키워드 준비와 API의 역할

로컬 후보는 **역3개 × 업종/의도12개 = 기본36개**다. `맛집`을 제외한 11태그에 `배달/포장`을 붙인 후속66개까지 총102개를 저장했다. 강남역 피자·맛집·치킨·파스타와 사가정역/면목역 조합이 포함된다. 실제 검색량·순위·추세는 수집되지 않아 `null / NotCollected`다.

`맛집`은 검색 의도, 피자/족발/파스타 등은 검색용 태그다. 인허가 업태나 대표메뉴의 문자열 근거를 별도로 보존한다. 메뉴 문자열이 발견됐다고 전체 메뉴·전문점·역 반경 식당 집합을 확정하지 않는다. 강남은 현재4구 음식점 자료 밖이며 역명 seed만 준비했다. 사가정·면목도 역세권별 식당 조인은 미검증이다.

공식 API는 게임 바깥의 참고 자료 역할로 한정한다. [SearchAd 명세](https://naver.github.io/searchad-apidoc/assets/json/ncc-keywordstool.json)는 검색량 등 관련 지표를 제공하지만 플레이스 일반 순위를 반환하지 않는다. [지역 검색 API](https://api.ncloud-docs.com/docs/naver-api-hub-search-local)는 `display` 최대5·`start`1이라 2·3페이지 순위 수집기로 사용할 수 없다. 관측 통계와 게임 고객수/순위는 별도 저장한다.

[실제 플레이스 순위 안내](https://help.naver.com/service/30026/contents/23472?lang=ko&osType=COMMONOS)는 관련도·인기도·거리·정보 등의 복합 판단을 설명한다. [실제 광고 안내](https://ads.naver.com/help/faq/763)는 입찰/품질에 따른 광고 노출을 설명하며, 플레이스검색광고는 키워드 단위 입찰 상품이 아니라고 한다. 홍달의 키워드 중심 예산 UI는 자체 게임 설계다.

## 7. Claude가 첫 구현을 준비할 때 확인할 것

첫 후보 범위는 **합성 검색 문맥 하나 + 충분한 가상 매장 후보 + 검색 목록/상세/지도 왕복 + 정식 광고 한 건 결과 비교**다. 2페이지를 확인하려면 적격한 고유 가상 매장이 최소11곳 필요하다. 이를 위해 실제 업체를 임의로 복제하거나 화면 클릭을 고객 행동으로 세지 않는다. 중개 의뢰는 소개/계약/검증까지 별도 후속 slice로 준비한다. 이 순서는 개발 착수 승인이 아니다.

승인 후 기획 revision/hash·한 WI·정확 쓰기 경로·E1~E7 명세를 결속해야 한다. 확인 후보는 검색 문맥별 순위 차이, 광고와 일반 순위 분리, 페이지/지도 왕복, 플레이어 조회의 무과금/무집계, 고객·주문 중복 방지, 계약/비용 멱등성, 이행/일일 보고 연결이다. 새 Scene·Core·DB·Graph Map·자동 수집/예약을 이 제안으로 만들지 않는다.
