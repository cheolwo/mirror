- 상위 기획: `README.md` r34

## 1. 목적

운영 절차에서 돈이 움직일 때마다 단순히 잔액만 더하고 빼지 않고, 어떤 업무 사건 때문에 누구에게 얼마의 권리·의무가 생겼는지와 어떤 회계 분류 후보인지 연결한다. 가상 권역의 `회계사 역할`은 이 자료를 읽고 운영자에게 현금 부족, 미지급 의무, 수익 인식 불확실성, 조정이 필요한 거래와 정책의 재무 영향을 조언한다.

```text
업무 사건
  → 경제적 원인·당사자·금액·기한을 가진 재무 사건
  → 기준중립 관리계정 원장
  → 차변·대변 회계 매핑 후보
  → 회계사 검토·승인 판본
  → Simulation 결산·조언
```

업무 원장은 주문·조리·배차·전달·취소 사실의 정본이고 회계 원장은 그 사실을 다시 해석한다. 회계 분류가 바뀌어도 과거 업무 사건을 고쳐 쓰지 않는다.

## 2. 공식 기준을 반영한 경계

- [외부감사법 제5조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1031407025)는 회사에 적용되는 회계처리기준을 한국채택국제회계기준과 그 밖의 법정 회계기준으로 구분한다. 회사 유형·규모·상장 여부를 확정하지 않은 상태에서 하나의 외부 보고 계정체계를 운영 정본으로 고정하지 않는다.
- [한국회계기준원 시행 중 기준 목록](https://www.kasb.or.kr/front/board/ingAccountingList.do)에는 K-IFRS 제1115호 수익, 제1007호 현금흐름표, 제1037호 충당부채·우발부채·우발자산 등이 포함된다. Simulation의 현금, 수익, 지급의무, 준비금은 서로 다른 의미로 관리한다.
- [K-IFRS 제1115호 본인·대리인 질의회신](https://kasb.or.kr/front/board/View016005.do?seq=35578)은 다른 당사자가 재화·용역 제공에 관여할 때 플랫폼이 정해진 재화·용역을 이전 전에 통제하는지와 주된 책임, 재고위험, 가격 결정 재량 등 구체적 사실을 종합해 본인·대리인을 판단하도록 설명한다. 따라서 고객 총 결제액을 플랫폼 매출로 자동 기록하지 않는다.
- [K-IFRS 제1115호 수익 인식 질의회신](https://kasb.or.kr/front/board/View016005.do?seq=40409)은 세금계산서 발행일 자체가 아니라 수행의무 이행과 통제 이전을 기준으로 수익 인식 시점을 판단한다고 설명한다. PG 수납, 주문 완료, 정산 지급과 수익 인식은 서로 다른 사건으로 둔다.

이 문서의 계정 이름은 개발과 Simulation을 위한 `후보`다. 실제 계정과목, 총액·순액 표시, 부가가치세, 손금·익금과 충당부채 해당 여부는 적용 회계기준·계약·세무 사실을 확인한 회계사 승인을 받아야 한다.

## 3. 네 층의 원장

| 층 | 책임 | 예시 | 변경 권한 |
| --- | --- | --- | --- |
| 업무 사실 | 주문·조리·배차·전달·취소·환급의 canonical 사건 | `OrderAccepted`, `CourierArrived`, `CancellationConfirmed` | 각 OS UseCase |
| 재무 사건 | 누구의 권리·의무가 언제 얼마 생겼는지 | 고객 청구, 음식점 지급의무, 기사 수행대금 의무 | 재무 UseCase |
| 관리계정 | 13주 현금과 운영 의사결정용 기준중립 분류 | 가용현금, 제한자금, 미지급 의무, 준비금, 운영수익·비용 후보 | Simulation 원장 |
| 회계 매핑 | 적용 기준에 따른 차변·대변 후보와 승인 판본 | 현금/PG미수금, 정산예수·미지급금, 수수료수익 후보 | 회계사 검토·승인 |

관리계정은 외부 재무제표 계정과목과 동일하다고 주장하지 않는다. 하나의 관리계정이 회사의 역할·계약에 따라 서로 다른 회계 계정으로 매핑될 수 있고, 승인 판본이 바뀌어도 당시 판본으로 만든 과거 Simulation 결과를 재현할 수 있어야 한다.

## 5. 회계 매핑 판본

`AccountingMappingRevision` 후보는 다음을 가진다.

- 적용 법인·사업모델·회계기준 Code와 유효기간
- 관리계정 Stable ID
- 발생 조건과 기준 업무 Event·Revision
- 차변 계정 후보·대변 계정 후보
- 금액 산식·통화·부가세 처리 후보
- 본인·대리인 가정과 근거 계약
- 수익·비용·자산·부채·내부 준비금 분류
- 증빙 종류와 source hash
- `Draft / AccountantReviewed / ApprovedForSimulation / ApprovedForOperationalPosting / Retired`
- 검토 회계사 식별자, 검토시각, 의견, 승인 범위

`ApprovedForSimulation`은 13주 가상 결산에서 사용할 수 있다는 뜻이고 실제 회계시스템 전표 승인이 아니다. `ApprovedForOperationalPosting`은 별도 권한·연동·내부통제·회계사 확인이 갖춰진 뒤에만 열며 이번 기획에서는 비활성이다.

## 6. 가상 회계사 역할

회계사 역할은 주문이나 배차를 수행하지 않고 재무 사건과 매핑을 검토하는 조언자다.

### 입력

- 주문·취소·환급·기사·음식점·지사 지급의무
- PG 승인·매입·입금·수수료와 실제 현금 이동
- 관리계정 잔액과 13주 지급 예정표
- 정책 revision과 기준·피크·스트레스·회복 scenario
- 미매핑·불일치·기한 초과 거래

### 조언 출력

- 13주 중 현금 최저점과 부족 예상일
- 확정 의무를 지킨 뒤 쓸 수 있는 가용현금
- 주문당 플랫폼 기여금과 정책별 증감
- 취소·환급·기사 보호 정책의 계정별 영향
- PG 입금 지연·환급 급증·기사 공급 정책의 민감도
- 본인·대리인 판단이 바뀔 때 총액·순액 수익 표시 차이
- 증빙 누락, 대사 불일치, 미승인 계정 매핑과 마감 차단 사유
- 운영자에게 제안하는 현금 방어선·정책 중단·회계사 검토 요청

조언은 이유 Code, 사용한 원장 revision, 정책·계정 매핑 판본, 가정과 불확실성을 포함한다. 회계사 NPC의 말이나 카드만으로 실제 전표·지급·환급·세무 신고를 확정하지 않는다.

## 7. 운영자 통합 화면의 회계 관점

회계사는 별도 앱이나 전용 화면을 소유하지 않는다. 아래 항목은 모두 같은 운영자 통합 화면의 카드·상세 영역이며, 권한이 있는 사용자가 필요할 때 회계 상세를 펼친다.

| 통합 영역 | 기본 운영 요약 | 필요 시 회계 상세 |
| --- | --- | --- |
| 오늘의 자금 | 가용현금, 오늘 지급, 위험 경보 | 현금·제한자금·미지급 의무의 대사 |
| 주문 경제성 | 주문당 수입·지출·기여금 | 계정 매핑, 본인·대리인 가정, 인식 시점 |
| 13주 전망 | 주별 최저 현금, 정책 전후 비교 | 계정별 발생·현금·잔액, 민감도와 마감 상태 |
| 예외 사건 | 취소·환급·분쟁의 운영 영향 | 기사·음식점·고객·플랫폼 금액의 분리와 증빙 |
| 마감 준비 | 처리되지 않은 위험 수 | 미매핑, 가계정, 미대사, 미승인 판본 목록 |

기본 운영자 화면은 회계 전문용어만 나열하지 않고 `왜 돈이 묶였는지`, `언제 지급해야 하는지`, `정책을 바꾸면 최저 현금이 어떻게 달라지는지`를 먼저 설명한다. 상세보기에서 계정과목 후보·차변·대변·근거를 연다.

## 8. 첫 Simulation 분개 예시

아래는 실제 회계 확정이 아니라 구조 검증용 후보다.

### 고객 결제 후 PG 입금 전

- 재무 사건: 고객 결제 승인·매입
- 관리 원장: `PG미수 증가`, `음식점 지급의무 후보`, `플랫폼 수익 후보`, `세금 후보`
- 회계 후보: 차변 `PG미수금 후보`; 대변은 음식점 정산의무와 플랫폼 용역대가 후보로 분리
- 차단: 플랫폼의 본인·대리인 판단과 계약상 수행의무가 미승인이면 외부 수익 전표를 확정하지 않음

### 정상 배달 완료

- 재무 사건: 기사 정상 수행대금 확정
- 관리 원장: `기사 정상 수행대금 미지급 증가`
- 회계 후보: 차변 `배달용역원가 후보`; 대변 `기사수행대금미지급금 후보`

### 픽업 전 주문자 취소

- 재무 사건: 취소 단계·기사 비귀책·정책 revision으로 취소수행대금 확정
- 관리 원장: `기사 취소수행대금 미지급 증가`, 고객 환급·음식점 보호·플랫폼 부담은 별도 발생
- 회계 후보: 차변 `배달용역원가 후보`; 대변 `취소수행대금미지급금 후보`
- 차단: Fixture 비율은 Simulation에서만 사용하고 실제 원화 지급 전표에 사용하지 않음

### 주문자 이의 제기 중 조건부 환급 준비

- 재무 사건: 책임 비율 미확정, 환급 가능액 격리
- 관리 원장: `조건부 환급 준비금 증가`, `가용현금 감소`
- 회계 후보: 없음 또는 회계사 검토 대기
- 차단: 내부 현금 방어 금액을 자동으로 충당부채·비용으로 전표화하지 않음

## 9. 개발 순서

1. 기존 돈 관련 원장·계약·정산 Event를 조사해 동일 금액을 중복 소유하는 지점을 찾는다.
2. 기준중립 `FinancialEvent`와 관리계정 Stable ID, 당사자·금액·기한·원인 revision 계약을 만든다.
3. 취소수행대금 Fixture를 포함한 음식배달 정상·취소 사건을 관리계정에 투영한다.
4. `AccountingMappingRevision`과 회계사 검토 상태를 만들되 운영 전표 쓰기는 비활성화한다.
5. 13주 Simulation에서 현금·발생·잔액을 계정별로 재현하고 복식 보존식을 검사한다.
6. 기존 운영자 읽기 모델에 회계 요약·조언 카드와 미대사·미매핑 마감 차단을 연결한다. 별도 회계사 앱·화면은 만들지 않는다.
7. 실제 회계사가 회사 적용 기준·계약·세무 처리·계정과목을 검토한 판본만 후속 운영 Adapter 후보로 넘긴다.

## 10. 검증

- 모든 재무 사건의 차변·대변 후보 합계가 통화별로 일치한다.
- 업무 Event 재처리가 관리 원장·분개 후보를 중복 생성하지 않는다.
- 발생시점, 지급기일, 실제 현금일과 수익 인식 후보 시점을 분리한다.
- 음식점·기사·지사·고객·플랫폼 의무를 상계 없이 독립 재조회한다.
- 같은 입력·계정 매핑 revision·seed로 같은 13주 결과와 hash를 만든다.
- 본인·대리인 가정을 바꾼 비교 scenario가 현금 자체를 바꾸지 않고 표시 수익과 계정 분류 차이를 드러낸다.
- 미승인 매핑·미대사 거래·가계정 잔액이 있으면 Simulation 마감 상태를 `ReviewRequired`로 표시한다.
- Unity는 계정별 요약·조언 카드만 읽고 실제 전표나 지급을 확정하지 않는다.

## 11. r36에서 폐쇄된 질문

회계사 전용 화면은 만들지 않고 기존 운영자 통합 화면에 현금·지급의무·대사 예외를 결합한다. 계정과목·차변·대변·증빙 계보는 필요할 때만 상세 영역에서 연다. 상단 상시 요약과 운영자 표시 용어는 `operator-integrated-accounting-summary.r37.md`가 소유한다.
