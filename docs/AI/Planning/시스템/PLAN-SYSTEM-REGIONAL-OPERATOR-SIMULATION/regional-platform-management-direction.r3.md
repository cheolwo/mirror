# [기획 · 동북권 플랫폼 경영 게임 · PLAN-SYSTEM-REGIONAL-OPERATOR-SIMULATION · 방향 r3]

2026-10-25. `PlatformOperatorManagementPrimaryConfirmed / FiveRegionScopeConfirmed / VideoDioramaContextConfirmed / BalancedObjectivesConfirmed / ProposedDesign / ImplementationDeferredByUser`.

## 확정한 중심

사용자는 **중랑구·동대문구·광진구·구리시·노원구**를 중심으로 음식점·배달기사·화물 운송을 운영하는 플랫폼의 입장에서 경영하는 게임을 원한다. 주행 영상과 디오라마는 그 게임 안에서 현장을 이해하고 운영 판단을 내리는 자료·표현으로 연결한다. 플레이할수록 당시 상황·판단·결과가 경영 경험으로 쌓이는 방향이다.

플레이어의 기본 역할은 가상 플랫폼 운영자다. 운영 상황 파악→가능한 조정 선택→시간 경과와 업무 진행 관찰→수익·배송 품질·참여자 보수 결산→다음 선택의 반복을 중심으로 삼는다. 영상/선분 검토나 3D 산책을 게임의 기본 목적이나 필수 노동으로 두지 않는다. 필요하면 현장 시점이나 주행 근거를 열고 다시 경영 화면으로 돌아온다.

이 방향은 기존 [지역 운영자 기획](README.md)의 운영자 정체를 구체화한다. [영상·디오라마 연결 r2](video-diorama-play-experience.proposal.r2.md)의 관계·출처 보존과 [학습 환류 r1](gameplay-experience-learning.proposal.r1.md)의 균형 평가를 유지하되, 기본 진입점은 경영 상황이다. 직전의 ‘먼저 연결 방안을 제안’ 요청은 유지하며 이번에 게임 코드·Scene·자료 연결·학습·배포를 시작하지 않는다.

## 경영하는 업무와 선택

| 업무 | 플레이에서 살펴볼 상황 | 선택의 예시 |
| --- | --- | --- |
| 음식 배달 | 권역별 주문 집중, 조리 대기, 기사 여력, 픽업·전달 지연 | 현재 가능한 기사/묶음/추천 순서와 대기를 비교하고 지원할 권역을 판단 |
| 화물 운송 | 접수 조건, 차량·적재 여력, 상하차 일정, 독차/혼적 가능성 | 현재 조건에 맞는 차량·수행 순서·가능한 조합을 비교 |
| 플랫폼 공통 운영 | 보유 현금·비용·대기 업무·기사/작업자 보수·예외 | 제한된 자원으로 어느 문제를 먼저 해결할지 선택하고 결과 비교 |

위는 제안 동작이다. 현재 음식 Simulation의 자동 배정을 복수 기사 직접 선택 기능이 이미 있는 것처럼 표시하지 않는다. 음식과 화물을 한 화면에서 조망하되 각 업무의 차량·자격·적재·수락·완료·정산 조건은 그대로 구분한다. 같은 지도에 있다는 이유로 음식기사를 화물차 기사로 취급하지 않는다. 기사와 작업자의 수락·거절 등 기존 역할 조건을 운영자 선택으로 덮지 않는다.

창고·마트·공간·작업자 협업은 장기적으로 같은 플랫폼 경영에 연결할 수 있다. 각 영역의 독립 업무와 플레이·상호 인계 조건을 확인한 뒤 확장하며 Farm→Hub→City를 첫 필수 루프로 삼지 않는다. 기존 13주/계절 캠페인·이야기·시작 자원 기획은 이번 지역 방향으로 삭제하거나 새 수치로 덮지 않는다.

## 영상·디오라마가 경영 안에서 작동하는 방식

- **주행 영상:** 선택한 업무의 도로·매장 접근 상황을 확인하는 실제 참고 기록이다. 같은 장소·확인된 구간·방향·촬영 조건으로 찾아볼 수 있게 한다. 실제 PTS와 검토 범위를 유지하고, 영상 길이만으로 화물차 ETA나 통행 가능성을 확정하지 않는다.
- **디오라마:** 권역 안의 매장·기사·차량·주문·도로를 조망하고, 선택한 업무가 어느 공간에서 진행되는지 이해하는 장면이다. 가상 이동과 현재 업무 단계는 Simulation 결과를 표현한다. 모형 위 도착·Animation 종료가 업무 완료의 권위는 아니다.
- **경영 경험:** 어떤 권역의 어떤 조건에서 어느 선택을 했고 수익·품질·보수가 어떻게 달라졌는지를 쌓는다. 사용한 공간·규칙·시나리오 판본을 함께 남겨 다른 선택이나 이후 회차와 비교한다.

예를 들어 중랑구에 음식 주문이 몰리고 광진구에서 화물 상차가 예정된 상황을 보며, 업무별 적격 후보와 자원 상황 안에서 대응을 선택한다. 필요한 도로/매장을 누르면 관련 디오라마와 검토된 주행 컷을 열고 경영 화면으로 돌아온다. 이 예시가 새 혼합 배차 정책·실제 운송·운영 권한의 승인은 아니다.

공통 연결은 r2의 `원본 SHA·실제 PTS ↔ 지도 선분/판본 ↔ 3D 공간 ↔ 게임 회차/판단/결과` 관계를 재사용한다. 새로운 복제 원장보다 기존 자료 사이의 판본화된 참조를 우선한다.

## 화면 구성 제안

1. 상단: 운영 기간·현금/손익·배송 지연·참여자 보수 등 현재 판단에 필요한 요약.
2. 중앙: 다섯 지역을 조망하는 지도/디오라마. 권역별 주문·기사·차량·진행 업무를 구분해 선택한다.
3. 업무 목록·선택 패널: 현재 처리할 일과 문제가 생긴 일, 가능한 선택·예상 영향·미확인 조건을 확인한다.
4. 선택한 현장: 매장/도로 상세, 해당 3D 장면과 관련 주행 영상을 필요할 때 열고 현재 업무로 복귀한다.
5. 회차 결산: 수익·배송 품질·참여자 보수의 변화와 원인이 된 선택을 함께 보고 다음 운영을 결정한다.

첫 경영 조망과 현장 상세·결산의 정확한 UI와 조작 방식은 후속 설계 대상이다. 기존 공식 `SimulationWorldShell`을 유지하며 지역마다 별도 공식 Scene을 만들지 않는다.

## 경험 축적과 현실 활용

판단 직전 상태·허용 후보·선택·가상 결과를 먼저 연결한다. 결과 평가는 사용자가 선택한 수익·배송 품질·참여자 보수의 균형을 유지한다. 구체 비율·최소 기준·새 금전/인사 정책은 미정이다.

게임 경험은 검토된 학습 후보이며 자동 정답이 아니다. 기존 경험 보관·검토 도구를 잇는 adapter, 미사용 평가·현실 조건 비교·운영과 나란히 비교하는 단계를 r1대로 분리한다. 실제 모델 학습·운영 모델 변경·실제 주문/기사/금융 변경·Steam 배포는 이번 작업에서 하지 않는다.
