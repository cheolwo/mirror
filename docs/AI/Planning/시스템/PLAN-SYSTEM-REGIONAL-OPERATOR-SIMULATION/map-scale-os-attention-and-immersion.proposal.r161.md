## 1. 중심 제안 — 높이마다 맡는 책임과 대표 질문을 바꾼다

같은 세계를 **가까이서는 한 건을 책임지는 사람, 멀리서는 여러 업무를 연결하는 사람**의 입장에서 본다. 지도에 들어왔을 때 ‘나는 누구를 돕고, 지금 무엇을 고르며, 무엇이 달라지는가’를 먼저 읽게 한다.

OS를 높이에 배타적으로 배정하지 않는다. 같은 음식배달도 동네에서는 한 주문의 조리·픽업·전달, 구에서는 동네별 기사 여력, 서울에서는 여러 구의 서비스 범위와 거점 연계로 초점이 달라진다. 자료의 실제 공간/시간 해상도와 게임의 현재 권한·준비 상태는 각각 유지한다.

첫 화면은 **대표 질문 하나 → 그 판단에 필요한 근거 → 선택과 대가 → 직접 결과 → 다음 선택**으로 구성하는 안이다. 정보량·지표 수·화면 배치는 제안이며 이번에 새 UI로 확정하지 않는다. 해야 할 일이 없는 때에는 정상 운영/관찰 상태를 보여주며 임의 사건을 만들어 채우지 않는다.

서울·도시권은 r144의 구/광역 사이 경영 초점을 정밀화하는 제안이다. 서울 관찰 높이의 존재를 이 경영 기능의 구현 완료로 해석하지 않는다. 전국은 r155의 대한민국 우선 범위를 유지한다. 지구본 관찰 기반과 **WindowsGame의 지구본 조달 업무 초점 미연결**을 구별하며, 지구본 전체가 없다고 보고하지 않는다.

동네는 표시상의 경영 범위다. 법정동·행정동·상권·서비스 구역은 서로 다른 ID와 관계를 유지한다. 이 표를 [기존 의미 확대](../PLAN-SYSTEM-GEOSPATIAL-TILE-SEMANTIC-ZOOM/README.md)의 Z/H 단계·자료 타일 주소와 일대일 대응시키거나 새로운 번호로 바꾸지 않는다.

현재 [정본 카탈로그](../../../../../Ssalddel.Contracts/Common/Versioning/OperatingSystemIdentityCatalog.cs)는10개다. 음식점은 `FoodDeliveryOS`의 역할/단계이며 독립 `RestaurantOS`를 만들지 않는다. 가맹·생산·공장 경영은 기존 게임 기획의 확장 역할과 준비된 모듈로 다루며, 현재 카탈로그에 별도 `FranchiseOS / ProductionOS / FactoryOS`가 구현돼 있다고 보고하지 않는다. 커뮤니티·운영·교육 같은 나머지 업무는 필요한 맥락에서 보조 진입하고 매 지도의 기본 업무 목록으로 전부 펼치지 않는다.

OS 단계의 표시 순서는 필수 실행 순서표가 아니다. 예를 들어 조리와 배차의 조건을 새로 직렬화하지 않는다. 화면은 기존 계약이 확인한 현재 단계·대기 이유·허용 행동을 읽는다. [업무 실행 책임 기준](../../../../Architecture/BusinessWorkflowResponsibilityModel.md)에 따라 엔진은 후보·이유·예상을 제공하고 확정은 준비된 주체의 기존 Command/권한 경계에서 이뤄진다.

## 4. 정보의 초점을 정하는 순서

첫 화면에는 다음 순서를 추천한다.

1. **내 입장과 지금의 질문:** ‘중랑구 배달 운영 — 다음 기사를 어느 동네에 둘까?’처럼 범위·역할·목적을 말한다. 기술 OS ID를 화면 제목으로 나열하지 않는다.
2. **판단의 직접 근거:** 현재 작업의 막힘·사용 가능한 자원·약속 여유를 먼저 본다. 구 전체의 모든 메뉴·개별 위치·연간 무역을 동시에 기본 표시하지 않는다.
3. **선택의 대가:** 후보별로 좋아질 점과 생길 부담을 같이 본다. 이윤뿐 아니라 납기·품질·안전·재작업·참여자의 이동/대기와 복귀 여건을 읽는다.
4. **직접 결과:** 계획/담당이 확정됐는지, 보류/실패했는지를 즉시 구별한다. 실제 이동·전달·검수·정산 완료는 해당 업무가 수행된 뒤 따로 확인한다.
5. **다음 선택과 귀환:** 같은 직무를 계속하거나 경영으로 돌아간다. r151의 ‘다음 작업’ 버튼으로 준비된 한 건을 시작하며 자동 연속 시작으로 바꾸지 않는다.

전체 현황·다른 지표·상세 원장은 사용자가 펼칠 수 있게 남긴다. 높은 지도에서는 요약을 읽고 선택한 대상을 자세히 보는 방식이 정보 탐색 연구의 개요·확대/필터·요청 시 상세 원칙과 맞는다. [Shneiderman, 1996](https://www.cs.umd.edu/users/ben/papers/Shneiderman1996eyes.pdf).

명확한 목표·피드백·통제감은 게임 즐거움 평가 모델에서도 다루는 요소다. 이 문서에서는 각 높이에 적용할 설계 가설로 사용하며 홍달에서 몰입 향상이 검증됐다고 주장하지 않는다. [Sweetser & Wyeth, GameFlow, 2005](https://doi.org/10.1145/1077246.1077253).

## 5. 몰입을 이어 주는 전환과 표현

- **일반 높이 전환:** r144처럼 새 높이의 대표 경영 요약으로 초점을 바꾸되, 맡고 있던 업무 요약·선택·입력과 상세 복귀를 남긴다. 같은 높이에서 지도만 옮기면 선택 OS를 유지한다.
- **같은 일 따라보기:** 사용자가 현재 주문/운송을 따라 상위·하위 관점을 고르면 같은 ID·Revision의 요약/상세로 읽는다. 상위 화면에서 ‘이 주문이 어느 지역 부담에 포함되는지’가 확인되는 관계를 제공한다.
- **다른 업무로 이어 보기:** 보충발주·센터 출고·화물·배달은 서로 다른 업무일 수 있다. 실제 인계/관계 ID가 있을 때만 연결한다. 모든 배달에 지구본 공급 사슬이 있는 것처럼 만들어내지 않는다.
- **긴급 상황:** 급한 일·실패 이유·복구 진입은 어느 높이에서도 찾을 수 있게 한다. 알림이 카메라나 현재 직접 조작을 자동 탈취하지 않는다. 처리 후 원래 OS·선택·카메라로 돌아온다.
- **표현과 결과:** 회색 기본 건물·관리 매장 민트색은 유지한다. 선택한 사람/장소/연결을 우선 강조하며 새 사건은 높이에 맞게 묶는다. 핀·파동·운송선의 장식 효과를 꺼도 현재 일과 결과는 남는다.
- **공통 시간:** 넓은 지도는 더 긴 계획 기간을 보여줄 수 있지만 높이 전환만으로 가상 시간을 빨리 돌리거나 되감지 않는다. 정지/진행은 기존 공통 시계를 따른다.
- **집중·이완:** 지도 높이와 참여 방식은 별도다. 구 지도를 보거나 창고 안으로 들어갔다고 직접 조작을 시작하지 않는다. 직접 조작 중 업무는 안전하게 인계하고 이완으로 돌아가는 기존 규칙을 따른다.

넓은 지도에서 좁은 현장으로 내려오는 과정이 의무 코스가 되지 않도록 한다. 구 운영에 관심이 있으면 거기 머물 수 있고 현장 미니게임을 반복할 수도 있다. 모든 지도를 열어야 한 업무를 끝낼 수 있게 만들지 않는다.

## 6. 두 가지 플레이 예시

### 예시 A — 동네의 한 주문과 구의 기사 배분

가상 동네에서 음식이 준비됐는데 이어받을 기사가 부족하다. 동네 화면에서는 ‘준비된 주문을 누가 이어받을까?’가 중심이다. 사용자는 현재 가능한 기사·다른 약속·픽업/전달 여유를 보고 연결 후보를 선택하거나 기다린다.

구 화면으로 올라가면 같은 주문은 해당 동네의 대기/지연 위험 요약에 포함된다. 구 운영자의 다음 선택은 ‘다음 가용 기사를 이 동네로 지원할지, 다른 동네의 여유로 남길지’다. 이동 부담·기존 약속·추정치의 불확실성을 함께 보여준다. 지도를 누르는 순간 기사가 순간 이동하거나 이미 맡은 운송을 취소하지 않는다.

결정을 확정하면 먼저 배치 계획/담당의 결과를 확인한다. 이후 실제 이동·픽업·전달의 진행과 지연/안전/대기 부담을 읽는다. 동네로 돌아오면 같은 주문과 선택을 이어 보고, 실패하면 이유와 재연결/기다림 같은 준비된 회복을 고른다. 사용자가 ‘내 선택이 어느 동네의 어떤 일에 영향을 주었는지’ 읽는 것을 목표로 한다.

### 예시 B — 도시의 보충 회차와 전국의 차량 연결

가상 도시의 한 거점에서 여러 구의 보충 요청이 모였다. 서울·도시권에서는 ‘부족이 급한 구에 일부를 먼저 보내거나, 준비를 기다려 묶어 보낼지’를 비교한다. 선택은 적재/처리 여력·시간창·추가 이동 부담을 바꿀 수 있으며 즉시 점포 입고 완료가 되지는 않는다.

전국에서는 실제 인계가 연결된 운송의 차량·다음 납기·복귀를 본다. ‘하차 후 가능한 복귀 화물을 기다릴지, 공차로 다음 약속에 복귀할지’가 대표 판단이다. 결과를 보려면 운송·하차·검수가 각자의 업무 상태로 이어져야 한다. 관련 없는 국내 배달이나 생산/창고 영역을 필수 선행으로 요구하지 않는다.

두 예시는 새로운 동작·경제 수치·업무 확정 권한의 승인이나 우유5팩/Core 구현 인계가 아니다. 실제 사용 가능한 행동은 현재 구현/승인 명세로 다시 좁힌다. 세계 조달 예시는 별도 상세 기획 전에는 가상 후보 비교·자료 근거 검토/보류의 제안으로 남긴다.

## 7. 수집 자료는 판단의 근거로 배치한다

| 관점 | 공공자료가 돕는 질문 | 현재 게임 상태와 구별할 것 |
| --- | --- | --- |
| 동네·구 | 분기별 인구/상권 맥락은 어디가 다른가? | 실제 접수 주문·가용 기사·개별 고객/매장 수요는 해당 게임/업무 상태 |
| 서울·전국 | 국가/항만/항공 물량·가격·지역 조건은 어떤 배경인가? | 현재 센터 재고·출고 준비·차량·납기와 실제 O/D는 별도 상태 |
| 지구본 | 품목별 상대국·무역 규모·기준 가격을 어떻게 비교할까? | 연간 무역 단가가 현재 공급자의 견적·재고·수입 계약은 아님 |

r160의 공공자료 DB 점검을 기준으로 한다. 서울 추정인구45,631행은 분기/공급자 영역 자료이며 서울8자리 통계 코드와 경계 대응은 별도다. 공개 사업장/건물 연결 테이블은0행이고 KCS항만2,431행은 추가 정규화 전 원문행이다. NOAA63행은2026-09-01~07의 일부0.05도 격자 분석 수온이며 현재 날씨/운송 위험을 자동 결정하지 않는다. 수치·코드·연구 후보의 준비 상태와 이용 조건을 팩별로 유지한다.

미확인 관계를 임의 지도 배치·추정 매출·실시간 보행·현재 운송으로 채우지 않는다. 자료 보기에서는 표/그래프·비교·연결 확인 중의 이유를 읽고 게임을 진행하지 않는다. 게임에서는 별도 승인된 가정/변환과 동결 판본을 쓴다. 데이터팩을 설치하거나 통계 기간을 선택하는 행동이 업무 사건을 만들지 않는다.

## 8. 첫 검토 범위와 재미 검증

먼저 **구 지도 한 화면의 ‘기사 여력 배분’**을 대표 상황으로 정밀화하는 안을 추천한다. 사용자의 기존 구 지도 우선 방향과 연결하되 실제 구현은 승인된 작은 WI/검증 명세로 따로 준비한다. 동네로 내려가 같은 주문의 진행을 보고 돌아오는 경로까지만 첫 후보로 삼고 서울·전국·지구본 전체 구현을 시작하지 않는다.

시각 검토에서는 한 상황의 진입→선택→계획/담당 결과→현장 진행→회복→구 복귀를 보여준다. 그 뒤 제한된 실제 입력 시범에서 다음을 확인한다.

| 확인 질문 | 관찰할 근거 |
| --- | --- |
| 지금 누구 입장에서 무엇을 결정할지 말할 수 있는가? | 첫 화면의 역할·대표 질문 이해, 첫 의미 있는 선택까지의 망설임/도움 요청 |
| 후보별 좋아질 점과 부담을 구별하는가? | 가장 가까운 기사만 누르지 않고 약속·이동·대기·여유를 읽는지 |
| 자신의 선택이 무엇을 바꿨다고 이해하는가? | 계획 확정과 실제 픽업/전달을 구별하고 결과의 이유를 설명하는지 |
| 정보가 많아도 선택한 일을 잃지 않는가? | 구↔동네·긴급 복구 뒤 선택/입력/카메라를 이어가는지 |
| 이완과 자료 보기에서도 부담 없이 머물 수 있는가? | 즉시 개입을 강제받는 느낌·불필요한 경보·반복 클릭의 피로가 있는지 |

지도에 머문 시간이나 클릭 수만으로 재미를 판정하지 않는다. 목표 이해·선택의 이유·결과의 인과·통제감·다시 해볼 의향을 함께 확인한다. 구체 시간 목표·지표 상한·대상자 수·보상 수치는 아직 미정이다. 이 문서는 몰입 검증 완료나 실제 게임 품질 승격 근거가 아니다.
