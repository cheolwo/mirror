## 1. 현재 구현과 이번 차이

최신 Claude 종합 계획은 r210을19:45에 읽고19:48경 문서에 음악 항목을 추가했으나 구현은 하지 않았다고 기록한다. 현재 WindowsGame의 AudioSource는0.42초 합성 알림음이고 BGM/외부 PCM 입력 경로는 없다. 읽은 최신 빌드는19:28:50 KST 성공·오류0/경고0이며 밀집 빛1·2 판이다.

`Roam.cs:154–155`의 `lightBeat`와 셰이더 `_ActivityBeat`는 **이미 같은 시계**다. 중심/개별 후광에는 대상별 Phase, 땅에는 공간별 sway를 더하므로 **시계를 음악으로 바꾸는 것만으로 중심과 땅의 박자가 같아지지는 않는다**. Claude 음악 메모의 이 부분은 시계 공유와 대상 위상 공유를 나눠 보완해야 한다. 기존 문서는 수정하지 않고 여기서 차이를 명시한다.

입력 지문·공식 출처/제한은 `artifacts/local/external-music-analysis-r211-20261114/source-readback.json`에 둔다. OS 이름/버전/빌드만 읽어 이 PC가 Windows11 Home·빌드26200임을 확인했다. **출력 장치·프로세스 취득·멜론/유튜브 음악의 실제 신호는 시험하지 않았다.**

## 2. 추천 구조 — 곡을 재생하는 앱과 반응하는 게임을 분리

사용자가 같은 Windows PC에서 음악을 재생하고, 게임은 사용자가 고른 소리 입력의 분석 결과를 받아 빛을 움직이는 경로를 제안한다. 내장 BGM 곡이 먼저 정해져야만 외부 반응 설계를 시작할 수 있는 것은 아니다.

**사용자 음악 앱 → 선택한 출력/앱의 오디오 샘플 → 저음/온셋·템포/박 추정 → 신뢰도와 시각 반응 → 개별 빛**의 흐름이다. 멜론/유튜브 계정·곡 목록을 조회하거나 음악을 게임에 배포하는 서비스 연동과 구분한다. 이 제안이 특정 서비스 전체의 호환이나 이용 허락/제휴를 확인했다는 뜻은 아니다.

음악은 원래 앱에서 계속 재생한다. 게임은 분석용 입력을 다시 스피커로 내보내지 않는 구조를 권한다. 외부 PCM을 Unity AudioSource로 다시 재생해야만 분석할 수 있다고 설계하지 않는다.

이 PC의 빌드는 위 샘플 최소 버전보다 높지만 실제 취득 성공의 근거는 아니다. 보호된 재생 스트림은 루프백으로 얻지 못할 수 있다. 입력 없음/미지원은 그대로 표시하고 보호나 접근 제한을 우회하는 경로를 만들지 않는다. 각 앱/브라우저·출력 장치의 실제 호환은 후속 검증 대상이다.

**제안 우선순위:** 지원 여부를 확인한 앱별 입력을 고를 수 있게 하고, 장치 전체 입력은 사용자가 범위를 알고 명시적으로 선택하는 대안으로 둔다. 브라우저 프로세스에는 다른 탭 소리가 섞일 수 있다. 입력 실패 시 마이크·다른 앱·시스템 전체로 자동 확대하지 않는다. 다른 기기에서만 나는 음악은 이 PC의 출력 입력으로 자동 들어오는 것이 아니다.

## 4. 자동 분석은 두 단계로 나눈다

### 4.1. 먼저 저음/세기에 반응

입력 샘플이 오면 음량 포락선과 저/중/고역 에너지를 계산하고, 완만한 상승/감쇠·강도 상한으로 빛을 움직이는 안이다. **주파수 성분 분석과 BPM 추정은 다른 작업**이다. 이 단계는 박이 확실하지 않아도 음악의 강약에 반응할 수 있지만 곡의 정확한 박을 알아냈다고 표시하지 않는다.

### 4.2. 박 추정이 안정되면 리듬에 맞춤

[Ellis의 비트 추적 연구](https://www.ee.columbia.edu/~dpwe/pubs/Ellis07-beattrack.pdf)와 [librosa 공식 beat_track 설명](https://librosa.org/doc/main/api/generated/librosa.beat.beat_track.html)은 소리 시작의 강도인 온셋·템포의 주기성·그에 맞는 박 위치를 함께 다룬다. 이를 참고해 최근 입력 구간에서 **온셋 변화 → 템포 후보 → 박 위상/신뢰도**를 갱신하는 실시간 설계를 검토한다. 연구/배치 분석 함수를 그대로 호출하면 모든 곡의 실시간 박자가 해결된다는 뜻은 아니다.

처음에는 ‘리듬 찾는 중’ 상태로 강약에 부드럽게 반응하고, 템포/위상이 안정되면 박에 맞춘 움직임을 점차 강화하는 안이다. 박이 불분명하거나 후보가 자주 바뀌면 에너지 반응 또는 기존의 잔잔한 호흡으로 돌아간다. **임의의 모든 곡·첫 박·박자표·정확한 BPM·저지연을 보장하지 않는다.**

느린/빠른 해석이 반/두 배로 갈리는 경우를 고려해 화면 반응을 느리게/보통/빠르게 보정하는 후보를 둔다. 이는 곡 재생 속도나 게임 시간을 바꾸는 설정이 아니다. 반응 속도·추정 구간·신뢰도 문턱·전환 시간은 미정이다.

## 5. 입력 상태/시계·어댑터의 경계

- 분석 결과에는 입력의 시각/유효 상태·강도/대역 에너지·온셋·추정 BPM/박 위상/신뢰도를 포함하는 안이다. 실제 필드/고유 식별자·저장 규격은 아직 확정하지 않는다. Unity 표현은 최신 결과만 읽고 프레임마다 취득/분석을 중복 실행하지 않는다.
- 외부 앱의 곡 시작 시각은 Unity `AudioSettings.dspTime`으로 직접 알 수 없다. [캡처 패킷의 장치/QPC 위치·시각과 무음/중단 플래그](https://learn.microsoft.com/en-us/windows/win32/api/audioclient/nf-audioclient-iaudiocaptureclient-getbuffer)를 참고해 입력 시간축과 추정 박을 결속하고, 표현 시계에 대응시켜야 한다. 정확한 매핑/분석·출력 지연 보정은 후속 시험이 필요하다.
- 입력 없음·무음·끊김·오래된 결과를 구분한다. 곡 변경/광고/일시정지를 오디오만으로 정확히 알아낸다고 단정하지 않는다. 신호 변화 때 신뢰도를 낮추고 다시 안정화하는 안이다. 곡 제목/가수·서비스명을 소리만으로 식별하는 기능은 포함하지 않는다.
- 장치 변경·블루투스 재연결·샘플률/채널 변화·앱 종료에서 입력을 정리하고 명시한 선택 범위 안에서 재연결하는 정책이 필요하다. 입력이 안 온다고 이전 BPM을 무기한 확정값처럼 유지하지 않는다.
- 취득/분석과 Unity 주 화면을 분리하는 Windows 어댑터를 권한다. 후보는 네이티브 WASAPI 연결 또는 호환성을 확인한 관리형/별도 보조 프로세스다. [NAudio의 현재 공식 WASAPI README](https://github.com/naudio/NAudio/blob/main/src/NAudio.Wasapi/README.md)는 net9.0을 대상으로 하므로 최신 패키지를 Unity에 바로 넣을 수 있다고 전제하지 않는다. 후보 버전·배포/프로세스 수명·Unity/Windows 호환은 선택 전 점검한다.

## 6. 입력 선택·로컬 처리의 사용자 경험 — 제안

‘외부 음악 반응 켜기 → 앱 또는 출력 장치 선택 → 입력/분석 상태 확인 → 빛 반응’의 짧은 흐름을 권한다. 켜는 동작과 입력 범위를 사용자가 알 수 있게 하고 언제든 끌 수 있게 한다. 앱 선택을 운영체제의 마이크 권한과 같은 것으로 표현하지 않는다. 자동 시작/기본값·재실행 시 취향 복원은 미정이다.

**원음은 저장/업로드하지 않고 필요한 짧은 분석 버퍼와 특징만 메모리에서 처리**하는 안을 추천한다. 진단 로그에도 원음/음악 파일을 남기지 않는 방향이다. 이는 제안이며 실제 완료된 보호 기능이 아니다. 지금 조사에서는 소리 취득 자체를 하지 않았다.

장치 전체 입력의 알림/다른 앱 소리를 음악으로 오인할 수 있음을 선택 화면에서 짧게 알려 주고, 가능한 경우 대상 앱 입력을 권한다. 현재 게임 알림음도 전체 입력에 섞일 수 있으므로 외부 분석과 알림을 분리할 방법을 검토한다. 입출력 선택이 어려운 사용자에게는 내장 호흡/효과 끄기를 계속 제공한다.

## 7. 빛·명덕·공통 시간의 관계

명덕은 빛의 기준 크기, 음악 특징은 일시적인 퍼짐/명암만 조절한다. 외부 음량·BPM·재생 시간으로 명덕/경 상태·정신 차림·제조/배달·보상을 올리거나 공유 세계 상태를 바꾸지 않는다. 같은 세계를 보는 사람도 각자 듣는 음악에 맞춘 로컬 표현을 선택할 수 있는 후보이다.

안정된 추정 박 격자에 개체별 허용 박/분할 박을 배정해 밀집 구분을 유지한다. 같은 대상의 중심/주변 빛·땅이 어느 위상을 공유할지는 별도 결정이다. **공통 시계로 바꾸는 것과 위상을 맞추는 것은 다르다.** 첫 검토는 식별점은 유지하고 주변 개별 빛만 반응·땅은 잔잔하게 두는 r210 후보를 이어갈 수 있다.

음소거·게임 정지/배속·집중/이완과 외부 앱 재생은 서로 독립일 수 있다. 소리가 계속 들어와도 정지한 게임의 업무/명덕 시간이 흐르는 것은 아니다. 효과/움직임 감소에서는 같은 식별·선택·업무 정보를 유지한다. 각 전환에서 리듬을 계속 보일지 멈출지는 후속 선택이다.

## 8. 준비/검토 순서 — 제안

1. **Windows 입력 가능성:** 지원 OS/앱/장치에서 선택한 신호가 오는지·끊을 수 있는지·범위를 넓히지 않는지 확인한다. 실제 캡처는 해당 구현/실행 범위를 수용한 뒤 수행한다.
2. **강약 반응:** 원음 파일 저장 없이 저음/음량 특징을 읽어 준비된 개별 빛 하나에 반영한다. 실제 명덕/업무 값은 유지한다.
3. **자동 리듬:** 박자가 분명한 곡·불분명한 곡·전환/무음에서 추정과 신뢰도/대체 표현을 비교한다. 모든 곡 성공을 전제하지 않는다.
4. **밀집/입력 전환:** 개체별 박 배정·선택/알림 판독과 장치/앱 변경·정지/배속·효과 끄기를 대조한다. 실제 배포 대상 Windows에서 호환성을 따로 기록한다.

이는 개발 순서 제안이며 새 DLL/패키지/프로세스·녹음/실행을 시작한 것이 아니다. 멜론/유튜브 음악의 실제 호환 표·지연/정확도·CPU/메모리 기준은 아직 없다.

## 9. 확정 / 미정 / 다음 질문 하나

**사용자 요청:** 사용자가 듣는 외부 음악의 특성을 자동으로 알아차려 빛을 조정하는 방식을 제안한다. 내부 곡/BPM을 먼저 고정하는 경로에만 한정하지 않는다.

**추천:** Windows에서 선택한 외부 출력/앱의 소리를 로컬로 분석하고, 강약 반응부터 시작해 추정이 안정되면 박자 반응을 강화한다. 입력 상실/낮은 신뢰에서는 잔잔한 표현으로 돌아간다.

**미정:** 입력/플랫폼·서비스 호환·앱/장치 선택/기본값, 캡처 어댑터/배포·특징/추정 알고리즘/시간/신뢰도·지연/반응 강도, 로그/버퍼·사용자 제어/모드·실제 명세/검증과 구현 수용.

**다음 질문 하나:** 첫 구현을 검토할 때 **음악을 트는 앱을 고르는 방식부터 할지, 선택한 출력 장치 전체를 받는 방식부터 할지**를 지원 환경/검증 결과와 함께 정한다. 이번에는 어느 취득 범위도 실제로 켜지 않았다.
