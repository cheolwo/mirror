## 1. 플레이어가 키우는 것은 배차실의 판단 능력이다

배달·카페·창고를 운영하면 언제 준비됐고 얼마나 기다렸는지, 어떤 추천과 선택이 어떤 결과로 이어졌는지 알게 된다. 이 기록으로 개선 과제를 발견하고, 다음 판단 기능을 검토·채택하는 경험을 제안한다.

**운영 → 기록 검토 → 개선 과제 → 새 기능 시험 → 방침 선택 → 달라진 운영 확인**을 반복한다. 게임 돈은 설비·연구 여건을 마련하는 후보이고, 단순히 돈이나 반복 건수만 내면 모든 판단이 좋아지는 규칙은 제안하지 않는다. 비용·소요 시간·승급 수치는 미정이다.

음식·화물·피킹·출고는 같은 성장 틀을 공유하되 분야별로 다른 역량을 가진다. 음식 배차를 오래 했다는 이유로 화물의 차량 적합성·혼적 판단을 자동 숙달하지 않는다. 한 분야만 계속하는 사용자도 그 분야 안에서 높은 단계까지 발전할 수 있게 한다.

## 2. 다섯 단계의 공통 사다리 제안

| 단계 | 플레이어에게 열리는 판단 | 음식 배차의 예 | 화물 배차의 예 |
| --- | --- | --- | --- |
| 1 수기 운영 | 적격 후보·상태를 보고 직접 선택. 이완에서는 사전에 정한 단순 방침으로 수행 | 가능한 기사 중 픽업·전달 순서를 판단 | 적합 차량 후보 중 운영자가 선택 |
| 2 추천 보조 | 후보 순위와 짧은 이유를 비교 | 가까운 기사·도착 경로·현재 대기 비교 | 접근 거리·차종·가능 일정 비교 |
| 3 시간 관리 | 준비·도착·기한의 예상과 실제 오차를 보고 배차 시점을 판단 | 조리 완료와 기사 도착을 맞추고 즉시 배차/짧은 대기의 대가 비교 | 상하차 시간창·현재 약속을 고려한 계획 비교 |
| 4 묶음 조율 | 여러 업무가 기존 약속과 자원에 미치는 영향을 비교 | 후속 픽업·여러 주문의 잔여 일정 비교 | 합짐·구간별 적재·여러 정차의 가능한 대안 비교 |
| 5 권역 계획 | 한 지역의 부족·지연·돌발 상황에 대응할 대안을 미리 준비 | 점심 수요·기사 부족·구 단위 지사 지원 비교 | 권역 복귀·차량 부족·센터 회차/경로 단절 대응 |

이 단계는 게임에서 소개하고 접근할 판단의 성장안이다. 실제 코드의 개발 버전 순서나 현재 서버 기능의 부재를 뜻하지 않는다. 현재 규칙에 있는 상위 판단을 일부러 없애거나 물리·안전 규칙을 낮춰 초급 엔진을 만들지 않는다. 가장 높은 단계가 모든 상황에서 유리하거나 전역 최적해를 보장하지도 않는다.

**필수 제약은 1단계부터 동일하다.** 차량·기사 적격, 유효 경로, 현재 가용, 적재/취급 조건, 시간창·선행 상태·재고·수락/권한 등은 해당 기존 업무 계약대로 검사한다. ‘성장하면 안전 검사가 열린다’는 방식으로 만들지 않는다. 엔진은 후보·점수·이유를 내고, 선택과 확정은 기존 플레이어/사전 방침·Core 명령 경계를 따른다.

## 3. 승급은 작은 개선 과제를 해결하면서 한다

첫 표본은 **음식 배차의 픽업 대기 줄이기**를 권한다.

1. 가까운 기사를 바로 보냈는데 매장 대기가 잦다는 운영 결과를 본다.
2. 기존 지사/운영 방침 화면에서 `픽업 대기 원인 보기` 과제를 고른다.
3. 조리 준비·기사 도착·다른 주문의 약속을 나란히 확인한다.
4. `거리 중심`과 `준비 시각 고려` 후보를 별도 가상 검토 회차에서 비교한다. 기본 주문·도로·기사 조건과 외부 사건은 같은 입력 판본으로 맞춘다.
5. 음식 지연·기사의 총 작업/대기·보수·이동/운영 비용·수익을 함께 보고 플레이어가 방침을 고른다.
6. 선택한 판단 기능을 이후 운영에 사용하고, 다음 문제를 관찰한다.

레스토랑 앞에서 기다린 시간만 줄고 다른 곳의 유휴 시간이나 이동이 늘었다면 전체 개선이라고 판정하지 않는다. 기존 약속 지연이나 참여자 보수가 나빠진 점도 드러낸다. 모든 개선 과제를 별도 시험처럼 강제하지 않고 일상 운영의 짧은 검토 선택으로 둔다.

직접 배달·바리스타·포장과 이완 자동 수행 모두 권위 결과에 결속된 기록을 남길 수 있다. 엔진 성장 기회를 집중 모드에만 주거나 다른 직무 수행을 의무로 만들지 않는다. 직접 수행 추가 보너스는 r146/r147의 별도 자격·정산 규칙을 유지한다. 선택/클릭·같은 회차 복제·단순 신호 해제 횟수는 독립 개선 사례로 중복 집계하지 않는다.

## 4. 한 방향 성장과 운영 방침의 선택을 함께 둔다

배차실이 성장하면 더 많은 판단을 검토할 수 있고, 실제 운영에서는 `약속 시간 중심`, `짧은 대기 중심`, `가능한 묶음 중심` 같은 기존 정책의 조합을 선택한다. 타로 운영 방침 카드는 이 차이를 사람이 이해하는 표현 후보다. 한 카드가 모든 목적에서 최고가 되는 설계는 피한다.

단계가 높아져도 물량이 적으면 단순 방침을 계속 쓸 수 있다. 새 기능은 정보·설비/연구 비용과 관리 부담을 요구할 수 있으며, 정확한 비용은 후속 기획이다. 커피·포장 전용 플레이도 해당 분야의 준비/불량·품절·작업 배치 개선으로 연결할 수 있지만 첫 구현을 여러 분야 동시 성장으로 넓히지 않는다.

기존 지도의 경영 책임에도 연결한다. **건물**에서는 그 매장·창고의 준비·피킹·출고를, **동네**에서는 개별 배달과 가까운 업무를, **구**에서는 여러 매장·지사의 수요와 기사 부족을, **광역**에서는 센터 회차·차량·권역 복귀를 판단한다. 엔진 성장으로 해당 지도의 비교 도구가 깊어지게 하되, 엔진 하나의 단계만으로 새 사업·지도·운영권이 자동으로 열리지는 않는다.

장기적으로는 음식 배차의 `준비 시각 맞추기`, 화물 배차의 `일정·적재·복귀`, 피킹의 `동선·마감 순서`, 출고의 `회차·처리 능력`, 집단화의 `시간·장소·참여 조건`처럼 분야별 개선 과제를 둔다. 분야 간 연결은 각 분야의 독립 운영이 준비된 뒤 선택하는 확장이다.

## 5. 게임 성장·규칙 버전·실제 AI 학습을 구별한다

| 구분 | 무엇을 뜻하는가 | 이번 제안의 한계 |
| --- | --- | --- |
| 게임 성장 단계 | 플레이어가 검토·사용할 수 있는 판단 기능 | 위 다섯 단계와 해금 조건은 제안 |
| 엔진/정책 판본 | 실제 후보 계산 규칙과 비교 평가의 버전 | 기존 정책을 재사용하고 검증한 판본만 선택. 진행 회차를 몰래 교체하지 않음 |
| AI 모델 학습 | 적격 자료로 별도 모델을 학습·평가 | r1의 후속 절차. 플레이 횟수나 경험 수가 곧 가중치 학습·운영 적용은 아님 |

새 성장 기록에는 시나리오·seed·입력/정책 판본·판단 당시 볼 수 있던 정보·적격/배제 후보·추천/실제 선택·직접/자동 수행 주체·권위 결과·실패/회복·평가 범위를 결속한다. 미래 주문과 숨겨진 정보가 일반 추천 입력으로 새지 않게 한다. 가상 사건 처리와 실제 음식/화물 이행 결과도 다른 종류로 기록한다.

새 후보는 미리 보지 않은 시나리오와 피크·저물량·자료 부족·지연/회복 등 서로 다른 조건에서 비교한다. 같은 회차를 양쪽 정책이 동시에 수정하지 않고 분리한 Simulation에서 같은 외부 조건을 사용한다. 이런 통제 비교를 현실에서의 인과 효과나 실사용 성능 보장으로 확대하지 않는다.

적용은 플레이어가 고르고 판본을 보존한다. 새 판본이 불리하면 이후 추천에 이전 방침을 사용할 수 있게 하되 이미 확정된 주문·정산·성과를 되감지 않는다. 현실 서버 배포·실제 배차·모델 등록은 별도 승인/검증 경계다.

## 6. 기존 구현에서 출발할 곳

[엔진 카탈로그](../../../../Architecture/EngineOverview.md)의 배차·집단화·출고·피킹·적재 판단과 기존 정책을 재사용한다. 첫 표본은 [음식배달후보선정Policy](../../../../../Ssalddel.WorkflowRules/UnityPackage/Runtime/음식배달후보선정Policy.cs)와 [게임 세션](../../../../../Ssalddel.Sagajeong.Core/UnityPackage/Runtime/FoodManagementSession.cs)의 Preview→Assign 경계가 적합하다. 추천·도착/준비 평가가 이미 있는 부분과 새 성장/승급·비교 화면을 구별한다.

서버에도 선택적인 AI 후보 선택 경로가 있으므로 과거 학습 준비 문서의 ‘어댑터 없음’을 현행 전체 사실로 재사용하지 않는다. 코드 존재·설정 활성·게임 연결·모델 학습·운영 적용은 각각 확인해야 한다.

- **확정:** 사용자가 단계적 엔진 진화를 게임에 넣는 방안의 제안을 요청했다. 기존의 수익·배송 품질·참여자 보수 균형과 추천/확정 경계를 유지한다.
- **제안·미정:** 다섯 단계, 개선 과제, 해금/비용/평가 기준·기록/저장 계약은 검토 전이며 새 엔진 성장은 아직 구현하지 않는다.
- **다음 질문 하나:** 첫 성장 대상을 음식 배차의 `가까운 기사 추천 → 준비 시각까지 고려`로 잡을까? 기존 음식 게임과 순수 정책을 재사용할 수 있어 이를 권한다.
