## 문답 r107 — 긍정 맥락을 살린 선제 예외 안내

[긍정 맥락을 살린 선제 안내 r107](positive-context-proactive-exception-communication.r107.md)은 예외를 부정적 경고로만 보여 주지 않고, 서버에서 확인된 밝은 맥락과 실제 영향·현재 조치·다음 안내를 함께 전달하도록 확정한다.

- 주문 집중으로 조리가 늦어질 때는 `주문이 많이 들어와 순서대로 조리 중`이라는 확인된 사실을 사용할 수 있다.
- `맛있어서`, `인기가 있어서`처럼 자료가 직접 증명하지 않은 평가는 자동 생성하지 않는다.
- 밝은 표현으로 지연을 축소하지 않고 예상시각 변화와 다음 안내·선택을 함께 보여 준다.
- 다음 문답은 기사 부족으로 인한 배차 지연에서도 밝은 맥락과 기사 자율성을 어떻게 함께 설명할지다.

## 문답 r108 — 후기와 함께 보는 지연 선택

[후기와 함께 보는 지연 선택 r108](review-supported-delay-choice.r108.md)은 조리 지연 때 공개 후기를 참고해 기다릴지 판단할 수 있게 하되, 후기를 취소 억제 수단으로 사용하지 않는 경계를 확정한다.

- 현재 상황·예상 지연·환불 조건을 후기보다 먼저 명확히 보여 준다.
- 기다리기와 취소 요청을 같은 수준에서 식별할 수 있게 유지한다.
- 현재 메뉴에 직접 연결되고 공개 정책을 통과한 후기만 사용하며 좋은 후기만 임의로 선별하지 않는다.
- 다음 질문은 후기 카드를 기본 접힘으로 둘지 한 건을 먼저 보여 줄지다.

## 목표

현실 자료를 읽기 전용 기준선으로 사용하면서, 플레이어가 가상 배달운영권역의 운영자가 되어 정책을 선택하고 시간 경과 뒤 결과를 비교·원복하는 게임 폐루프를 만든다. 실제 주문·배차·정산·담당자 배정은 변경하지 않는다.

## 문답 r1 — 운영자 정체

### 지금·여기·나·너·이렇게

- 지금: 행정동 디오라마, Draft 배달운영권역, 음식·화물·창고·마트 OS의 단계별 관찰 자료가 준비돼 있지만 실제 운영 활성과 Unity의 운영 Command는 열려 있지 않다.
- 여기: 사가정역 1km × 1km 관찰 창을 보존하고 면목제3·8동을 첫 운영·집계 권위로 사용한다. 면목제7동 등 겹치는 행정동은 자기 귀속을 유지한 인접 맥락으로 표현한다.
- 나: 실제 플랫폼 관리자가 아니라 `가상 권역 운영자`다.
- 너: 행정동별 현실 자료 기준선 위에서 움직이는 가상 음식점·기사·주문자·차량·창고·마트와 운영 사건이다.
- 이렇게: 운영자는 전체 조망과 선택 추적으로 현재 상태를 보고, 정책 후보의 예상 효과·부작용을 비교해 Simulation에만 적용한다. 선택하지 않으면 판본화된 기본값으로 진행하며 적용 기간 종료·조건 악화·명시적 원복 때 이전 정책으로 돌아간다.

### 권위 경계

1. 공공자료·검증된 운영 관측은 현실 기준선이며 카드나 Simulation이 원문을 바꾸지 않는다.
2. 정책 선택은 `SimulationPolicyDraft → Previewed → ActiveInSimulation → Expired/RolledBack`의 가상 원장만 변경한다.
3. 실제 운영 원장은 읽지 않거나 승인된 비식별·읽기 전용 사본만 사용한다.
4. Unity는 정책 선택 UI와 결과 표현을 제공할 수 있지만 GameObject·Animation·NPC 도착만으로 결과를 확정하지 않는다.
5. 실제 운영 후보로 전환하려면 별도 권한·Preview·명시적 확인·서버 Command·canonical 재조회가 필요하며 이번 기획에는 포함하지 않는다.

### 운영자가 보는 다섯 묶음

| 묶음 | 첫 의미 | 기본 동작 |
| --- | --- | --- |
| 권역 현황 | 행정동 구성, 자료 준비도, 공간·생활 결손 | 결손을 정상값으로 숨기지 않음 |
| 생활 관찰 | 주문·조리·픽업·이동·전달·귀환과 다른 OS 상태 | 전체는 계속 흐르고 선택 대상만 추적 |
| 정책 조정 | 시간대 공급, 조리 예상, 주문 허용 범위, 거점 운영 | 무입력 시 안전한 기본값 유지 |
| 예외 개입 | 적체·부족·지연·중단·불일치 | 자동 처리와 운영자 판단 대상을 분리 |
| 결산 | 처리량·완료율·지연·대기·가상 비용·회복 | 정책 전후와 출처·한계를 같이 표시 |

### 첫 폐루프 후보

`현황 관찰 → 이상 징후 또는 운영 기회 발견 → 정책 후보 비교 → 기본값 유지 또는 한 정책 선택 → 시간 경과 → 결과·부작용 결산 → 유지·수정·원복 → 다음 운영 구간`

운영자가 계속 클릭하지 않아도 세계가 진행되는 것이 기본이다. 정책은 발효 시각·종료 시각·대상 권역·입력 자료 revision·효과 범위·부작용·원복 조건을 가진다.

### 절기·아르카나·주역 카드 경계

- 절기·제철 자료는 출처와 기준 시각을 가진 현실 관측층이다.
- 아르카나·주역 카드는 운영 사실이 아니라 가상 정책의 이야기·위험·기회 표현이다.
- 카드는 가상 수요·NPC 선호·사건 발생 가능성·회복 비용처럼 명시된 Simulation 변수만 바꾼다.
- 주문 완료·배차·정산·공공자료 값을 직접 성공시키거나 덮어쓰지 않는다.
- 첫 일반 운영 폐루프가 안정되기 전에는 카드가 필수 선행조건이 아니다.

### 오행·괘상 관계

- 운영자의 관계 후보는 경계와 멈춤을 다루는 `간(艮)`과 흐름·위험을 읽는 `감(坎)`이다.
- 이는 정책 카드의 서사·표현 후보일 뿐 배차 점수, Evidence, 실제 권위 결과가 아니다.
- 첫 일반 운영 상황이 확정되기 전까지 효과 수치와 활성 카드는 미정이다.

## 문답 r2 — 점심 피크와 가상 기사 가용 의향 알림

### 지금·여기·나·너·이렇게

- 지금: 점심 피크 주문 후보가 늘고, 현재 수행 중인 기사와 새 주문을 맡을 수 있는 기사 수를 비교했을 때 가까운 시간 안에 미배정 적체가 예상된다.
- 여기: 첫 소규모 가상 배달운영권역과 그 안의 음식점·대기점·주요 이동 경로다. 정확한 행정동 구성은 아직 미정이다.
- 나: 권역 전체의 수요·공급과 기사 부담을 함께 보는 가상 권역 운영자다.
- 너: 현재 운행 중인 가상 기사, 운행 의향이 꺼진 가상 기사, 휴식·다른 업무·거리·피로 상태 때문에 응답하지 않을 수 있는 기사 후보군이다.
- 이렇게: 운영자는 단순 기사 수가 아니라 예상 주문, 미배정 대기, 수행 중인 건, 예상 복귀 시각과 기사 가용 용량을 보고 부족 경보를 받는다. 정책이 허용하면 가상 기사에게 운행 가능 여부를 묻는 모집 알림을 보내고 응답 뒤에만 배차 후보 풀에 포함한다.

### 알림과 배차의 분리

`기사 부족 감지 → 알림 정책 판정 → 가상 모집 알림 → 기사별 수신·열람·수락·거절·만료 → 가용 후보 등록 → 별도 배차 후보 계산`

- 알림 수락은 특정 주문 수락이나 배차 확정이 아니다.
- 알림을 거절하거나 무응답이어도 불이익을 주지 않는다.
- 가상 기사의 휴식·피로·현재 위치·다른 수행 업무·알림 차단 설정을 무시하지 않는다.
- 같은 권역·부족 구간·정책 revision에 중복 알림을 보내지 않으며 재알림에는 cooldown을 둔다.
- 고객 상세 주소·실제 기사 위치·연락처는 알림에 포함하지 않는다.
- A안의 첫 판본에서는 실제 FCM·문자·실제 기사 앱을 호출하지 않는다. Unity와 Simulation 안의 가상 알림함·NPC 반응만 검증한다.

| 현재 가용 기사 | 새 업무를 받을 수 있는 가상 기사 | 온라인 표시만으로 가용하다고 판정하지 않음 |
| 수행 중 기사 | 현재 업무와 예상 복귀 시각 | 완료 Animation으로 복귀를 확정하지 않음 |
| 기사별 용량·피로 | 동시 수행 상한과 휴식 필요 | 알림으로 안전 상한을 우회하지 않음 |
| 이동·조리 예상 | 픽업 준비와 실제 이동 후보 시간 | 이동망 결손을 0분으로 처리하지 않음 |

정확한 임계값은 아직 확정하지 않는다. 첫 구현 후보는 `다음 관측 구간의 예상 필요 기사 수 > 안전하게 새 업무를 받을 수 있는 기사 수`가 일정 시간 계속될 때 `DriverSupplyShortageForecast`를 만드는 방식이다.

### 가상 알림의 최소 상태

`Prepared → SentInSimulation → Delivered/Unavailable → Viewed → Accepted/Declined/Expired`

알림 수락 뒤에도 기사 상태가 바뀌면 배차 후보 계산에서 다시 검증한다. 알림 전달 실패나 만료는 기사 책임 거절로 집계하지 않는다.

### 운영자 화면 결과

- 경보 카드: 예상 부족 시간, 예상 주문·가용 기사 범위, 근거 자료 revision, 불확실성.
- 정책 Preview: 알림 대상 규모, 예상 응답 범위, 재알림 제한, 가상 인센티브 비용과 기사 피로 위험.
- 디오라마 표현: 알림을 받은 가상 기사 후보의 일반화 표식, 수락 뒤 대기점 또는 권역 유입, 실제 배차 뒤 별도 이동.
- 결산: 발송·도달·수락·거절·만료, 가용 후보 증가, 미배정 대기 변화, 완료율·지연·가상 비용, 과도한 알림 횟수.

### 실패·회복 후보

- 응답 부족: 적체를 숨기지 않고 다음 정책 선택을 연다.
- 전달 실패: 재알림 cooldown 뒤 다시 시도하거나 인접 가상 후보군 검토로 이동한다.
- 수락 후 상태 변경: 배차에서 제외하고 기사 책임 실패로 만들지 않는다.
- 과잉 모집: 새 주문을 강제로 만들지 않고 기사 유휴·가상 비용을 결과에 남긴다.
- 알림 피로: 기사별·권역별 빈도 상한을 넘으면 자동 중단하고 기본 정책으로 돌아간다.

### 오행·괘상 관계

- `감(坎)`은 점심 피크의 흐름과 부족 위험을 읽는 표현 후보다.
- `손(巽)`은 알림이 퍼지고 기사 후보가 권역에 유입되는 표현 후보다.
- 이는 이야기·UI 메타데이터이며 실제 기사 행동, 배차 우선순위나 성공률을 자동 결정하지 않는다.

## 문답 r3 — 혼합형 자동화와 현금 안정성 뼈대

### 지금·여기·나·너·이렇게

- 지금: 점심 피크 부족 경보가 발생했으며, 운영자는 매번 알림을 승인하지 않아도 되지만 잘못된 예측이 과잉 모집과 가상 비용을 만들지 않게 해야 한다.
- 여기: 한 소규모 가상 배달운영권역의 점심 피크 운영과 그 권역에 귀속된 가상 현금·미지급 의무 원장이다.
- 나: 서비스 수준뿐 아니라 기사·음식점·지사에 지급할 의무와 가용현금 방어선을 함께 지키는 가상 권역 운영자다.
- 너: 주문 수요, 기사 후보, 음식점, 지사, PG 지연, 환불, 고정비와 각 지급 시점을 가진 가상 재무 상태다.
- 이렇게: 주의 단계에서는 자동으로 Preview만 만들고, 심각 단계에서는 사전에 승인한 시간대·대상·빈도 상한 안에서만 가상 모집 알림을 자동 발송한다. 각 정책의 인센티브·처리량·지연·현금 영향을 같은 revision으로 계산하고, 지급 의무를 지키지 못하는 정책은 적용 전에 차단한다.

### 혼합형 알림 자동화

| 단계 | 자동 동작 | 운영자 개입 |
| --- | --- | --- |
| 정상 | 기본값으로 계속 관찰 | 없음 |
| 주의 | 부족 근거와 정책 Preview 카드 생성 | 유지·수정·즉시 발송 가능 |
| 심각 | 사전 승인된 시간대·대상·cooldown·빈도·예산 안에서만 가상 알림 자동 발송 | 범위 밖이면 확인 필요 |
| 보호 중단 | 예산·빈도·피로·자료 품질 관문 실패 시 자동 발송 중단 | 원인 확인 뒤 정책 재승인 |

자동 발송은 언제든 원복할 수 있고, 같은 부족 사건·정책 revision의 재처리는 중복 알림과 비용을 만들지 않는다.

### 재무 원장의 분리

가상 잔액 하나만 보여 주지 않고 다음을 분리한다.

1. `가용 운영현금`: 정책·고정비·보상에 실제로 사용할 수 있는 Simulation 자금.
2. `제한·통과 자금`: 음식점 상품대금, 원천징수·보험·법정 납부 후보처럼 플랫폼 운영비로 사용할 수 없는 가상 자금.
3. `확정 미지급 의무`: 기사 수행대금, 지사 지급, 음식점 정산, 환불·차지백, 세금·보험 후보.
4. `조건부 준비금`: 사고·대량 환불·PG 지연·수요 급락·정책 실패에 대비한 방어선.
5. `성장 예산`: 안정성 방어선을 충족한 뒤에만 사용할 수 있는 별도 가상 예산.

기사 수행대금, 지사 운영보상·시간대 인센티브, 음식점 상품대금, 환불과 법정 공제 후보는 서로 다른 원장과 지급 상태를 가진다. 지사에 돈을 보냈다는 사실과 기사가 실제 지급받았다는 사실도 합치지 않는다.

### 현금 안정성 판정

첫 계산의 목표는 회계상 이익이 아니라 `모든 시점에서 지급 의무와 안전 준비금을 지킬 수 있는 최소 비제한 시작 현금`을 찾는 것이다.

```text
시점별 방어 필요액
  = 안전 기간 안에 만기인 지급 의무
  + 조건부 준비금
  + 확정 운영비
  - 그 시점까지 실제 사용할 수 있는 확정 유입

최소 시작 운영현금
  = 모든 검증 시점의 방어 필요액 가운데 최댓값
```

PG 승인액이나 아직 정산되지 않은 고객 결제는 실제 가용 시점 전에는 유입으로 세지 않는다. 음식점·기사·지사에 지급할 돈을 플랫폼 여유자금으로 세지 않으며, 미지급 의무가 남은 채 현금잔액만 양수인 상태를 안정으로 판정하지 않는다.

### 첫 입력 묶음

| 입력 | 기준 |
| --- | --- |
| 주문량 | 평상·점심 피크·저수요 범위와 취소·환불률 |
| 플랫폼 유입 | 음식점 월 구독료, 고객 배달료, 승인된 기타 가상 수익 |
| 기사 비용 | 기본 수행대금, 거리·시간대·가상 모집 인센티브, 직접/지사 기사 비율 |
| 지사 비용 | 기사 수행대금 재원과 분리된 운영보상·사업주 비용 후보 |
| 음식점 지급 | 상품대금과 실제 가용하지 않은 통과 자금, 지급 시점 후보 |
| 결제 지연 | PG 유입 지연, 실패·환불·차지백 시차 |
| 고정비 | 서버·지원·관리·거점과 기타 판본화된 Simulation 비용 |
| 충격 | 기사 응답 부족, 조리 지연, 주문 급증·급락, PG 지연, 환불 증가 |

기존 기획에서 사용했던 `20억원`은 외부 확정 자본이 아니라 비교할 수 있는 내부 시작자금 scenario 하나로만 둔다. 모델은 금액을 먼저 정당화하지 않고, 필요한 최소 현금을 계산한 뒤 20억원 scenario의 잔여 여력·소진 기간·과잉 자본 여부를 비교한다.

### 검증 시나리오와 출력

- `기준`: 예상 주문·응답·환불·PG 지연이 기준 범위 안에 있음.
- `점심 피크`: 모집 알림과 인센티브가 늘고 기사 공급이 지연됨.
- `스트레스`: 주문 급증과 PG 지연·환불 증가가 겹침.
- `회복`: 자동 알림을 중단·원복하고 적체와 지급 의무를 정상화함.

출력은 주별·일별 가용현금 최저점, 미지급 의무, 지급 지연 0건 여부, 최소 시작 운영현금, 손익분기 주문량, 현금 소진 기간, 정책별 추가비용과 완료율·지연 변화다. 평균값만 보지 않고 기준·스트레스 범위를 함께 보존한다.

### 시간 해상도 후보

- 점심 피크의 주문·기사 흐름은 짧은 Simulation Tick으로 관찰한다.
- 현금 유입·지급 의무는 일별로 합산한다.
- 기사·지사 정산은 기존 후보인 한국시간 수요일~화요일 주기를 보존한다.
- 음식점 상품대금 지급일과 법정 공제·보험 적용은 아직 확정하지 않으며 실제 출시 전 별도 검토가 필요하다.

### 실패·회복

- 지급 방어선 미달: 정책 적용을 차단하고 인센티브 축소·대상 축소·운영자 확인을 연다.
- PG 지연: 미확정 유입을 가용현금으로 세지 않고 준비금을 사용한 결과를 별도 표시한다.
- 과잉 모집: 기사 유휴와 추가 비용을 숨기지 않고 정책 원복 후보를 만든다.
- 적자 지속: 미지급을 허용해 성공으로 꾸미지 않고 현금 소진 예상일과 축소·중단 선택을 보여 준다.
- 자료 결손: 낙관값으로 대체하지 않고 범위 확대·정책 자동화 중단으로 회복한다.

### 오행·괘상 관계

- `곤(坤)`은 지급 의무와 운영 기반을 받치는 재정 토대의 표현 후보다.
- `절(節)`은 알림·인센티브·예산의 상한과 절제를 보여 주는 정책 카드 후보다.
- 이 메타데이터는 자금 생성, 지급 면제, 실제 회계·법률 판정을 만들지 않는다.

## 문답 r4 — 13주 운영 직렬화와 예외 처리

### 지금·여기·나·너·이렇게

- 지금: 점심 피크의 분 단위 주문·기사 흐름과 일·주 단위 정산·현금 흐름을 13주 동안 이어서 관찰해야 한다.
- 여기: 한 소규모 가상 배달운영권역, 그 권역의 음식배달 업무 원장과 가상 재무 원장이다.
- 나: 화면상의 NPC를 직접 움직이는 사람이 아니라 업무·지급 의무·예외를 보고 정책을 승인하거나 원복하는 가상 권역 운영자다.
- 너: 각자 안정 ID·revision·허용 행동을 가진 주문, 음식점, 기사, 배달 업무, 알림, 지급 의무, PG 유입과 예외 사건이다.
- 이렇게: 모든 업무를 하나의 거대한 상태 문자열로 합치지 않고 OS별 업무 instance와 단계 기록, OS 간 인계, 돈의 발생·만기·지급 기록을 시간순으로 결속한다. 실패한 단계는 전체 실행을 처음부터 되감지 않고 가장 이른 책임 단계에서 보류·재시도·대체·원복한다.

### 여기서 말하는 직렬화

직렬화는 단순 JSON 변환이 아니라, 중단·재시작·재조회 뒤에도 같은 업무를 같은 순서와 의미로 복원할 수 있는 실행 계보를 뜻한다.

```text
SimulationRun
└─ OperatingPeriod                          # 13주 전망의 주·일·점심 피크 구간
   ├─ WorkInstance                         # OS별 실제 업무 단위
   │  ├─ LifecycleStepRecord               # 단계·revision·직접 결과
   │  ├─ ActionRecord                      # Preview·Confirm·자동 정책 결정
   │  ├─ ExceptionCase                     # 차단·재시도·회복·원복
   │  └─ HandoffRecord                     # 다른 OS 또는 재무 원장 인계
   ├─ FinancialObligation                  # 기사·지사·음식점·환불 지급 의무
   ├─ CashMovement                         # 실제 가상 유입·유출 시점
   └─ PeriodClose                          # 일·주 마감과 13주 전망 갱신
```

각 기록은 최소한 `RunStableId`, `WorkStableId`, `OperatingSystemId`, 정의 판본, 단계 ID, revision, 발생 시각·가상 시각, 원인 Command/정책, 이전·다음 상태, 금액 영향 참조, 관련 주체와 위치, 상태 hash를 가진다.

### 세 가지 시간축

| 시간축 | 담당 | 주요 결과 |
| --- | --- | --- |
| 짧은 Tick | 주문·조리·기사 알림·배차·이동 | 점심 피크 적체와 가용 기사 변화 |
| 일 마감 | PG 확정 유입, 환불, 운영비, 일별 예외 | 가용현금·미지급 의무·자료 품질 |
| 주 마감 | 수요일~화요일 기사·지사 정산 후보와 전망 갱신 | 지급 가능 여부, 현금 최저점, 다음 주 정책 |

13주 전망은 이 세 축을 한 숫자로 뭉개지 않는다. 짧은 업무 결과가 어떤 일·주 원장에 반영됐는지 안정 참조로 연결한다.

### OS와 운영 조정의 분리

- `FoodDeliveryOS`는 주문 응답·조리·기사 가용·배차·픽업·전달·수령·귀환과 실패·회복 의미를 소유한다.
- 가상 권역 운영 정책은 OS 단계를 임의 변경하지 않고 `AvailableActions`, 정책 Preview와 환경 요구사항을 통해 허용된 Command만 요청한다.
- 현금 전망과 지급 의무는 음식배달 단계의 직접 결과를 참조하지만 음식배달 OS 안에 회계 상태를 끼워 넣지 않는다.
- 다른 OS와 연결할 때는 같은 `WorkStableId`로 합치지 않고 `HandoffStableId`로 부모·자식 또는 선행·후속 관계만 기록한다.
- `PlatformOperationsOS`는 아직 공통 lifecycle이 없으므로 새 단계를 임의 생성하지 않는다. 첫 판본의 운영자 행동은 판본화된 정책·예외 결정 원장으로 관리하고, 별도 OS 승격은 후속 기획으로 남긴다.

### API 후보 묶음

경로 이름은 구현 전 기존 route와 충돌을 다시 확인하는 후보이며, 첫 계약은 다음 책임을 분리한다.

| 책임 | 후보 API 의미 | 상태 변경 여부 |
| --- | --- | --- |
| 현황 조회 | 13주 run, 현재 피크, OS 단계, 가용현금·의무 요약 | 읽기 전용 |
| 정책 Preview | 기사 부족 알림·인센티브·대상 확대의 예상 효과·비용 | 무변경 |
| 정책 Confirm | 예상 revision과 멱등키로 Simulation 정책 적용 | 가상 정책만 변경 |
| 허용 행동 조회 | 현재 상태에서 운영자가 선택할 수 있는 작은 `AvailableActions` | 읽기 전용 |
| 예외 목록·상세 | 차단 원인, 영향 업무·금액·재개 지점·추천 행동 | 읽기 전용 |
| 예외 결정 | 재시도·보류·대체·원복·중단 중 허용된 행동 요청 | 해당 가상 원장 변경 |
| 원장·전망 재조회 | canonical 업무·재무 상태와 새 13주 전망 | 읽기 전용 |

모든 변경 API 후보는 `ClientRequestId`, `ExpectedRevision`, 정책 판본, 가상 시각과 행위자 역할을 요구한다. 성공 응답만 믿지 않고 같은 원장을 다시 조회한다.

### 예외 사건 구조

```text
Detected
  → Quarantined
  → AwaitingPolicy | RetryScheduled | AlternativeProposed
  → Resolved | RolledBack | Escalated | ClosedUnresolved
```

예외는 업무 실패와 사람의 잘못을 같은 뜻으로 사용하지 않는다. 최소 범주는 다음과 같다.

- `DriverSupplyShortage`: 가용 기사 부족 또는 응답 지연.
- `NotificationDeliveryFailure`: 가상 알림 전달 실패·만료.
- `InvalidLifecycleTransition`: OS Core가 허용하지 않는 순서.
- `StaleOrConflictingRevision`: 낮은 revision 또는 같은 revision의 다른 내용.
- `PgSettlementDelay`: 예상 시점에 가용현금이 되지 않은 결제 유입.
- `PayoutLiquidityShortfall`: 만기 지급 의무와 준비금 방어선 미달.
- `RefundOrChargebackSpike`: 환불·차지백이 기준 범위를 초과.
- `DataQualityBlocked`: 수요·위치·금액 자료 결손 또는 오래됨.
- `CrossOsHandoffFailure`: 선행 OS 결과와 후속 OS 입력 불일치.

각 예외는 원인, 영향받은 업무·주체·금액, 최초 발견 시각, 현재 책임 단계, 자동 재시도 가능 여부, 운영자 선택 후보, 가장 이른 재개 단계와 원복 대상을 가진다.

### 운영자 역지사지 화면

운영자는 기술 로그 대신 다음 질문에 답할 수 있어야 한다.

1. 지금 무엇이 멈췄는가?
2. 누구의 업무와 지급에 영향을 주는가?
3. 자동 회복을 기다려도 되는가?
4. 지금 선택할 수 있는 행동과 예상 비용은 무엇인가?
5. 아무것도 하지 않으면 언제 현금·완료율·지연이 위험해지는가?
6. 결정 뒤 어느 원장을 다시 확인해야 하는가?

기사에게는 강제 참여나 불이익으로 보이지 않아야 하고, 음식점에는 조리·정산 상태가, 지사에는 플랫폼 송금과 기사 지급 책임이, 재무 운영자에게는 제한자금·의무·가용현금이 분리되어 보여야 한다.

### 결정성·복구 검증 후보

- 같은 seed·초기 현금·정책·업무 입력은 13주 최종 hash와 주별 마감이 같아야 한다.
- 중간 저장 뒤 재시작해도 알림·배차·지급이 중복되지 않아야 한다.
- Outbox 또는 외부 Stub 실패 뒤 재처리해도 같은 직접 결과는 한 번만 생겨야 한다.
- PG 지연·기사 부족·환불 급증을 주입해도 미지급을 숨기거나 다른 OS를 임의 완료하지 않아야 한다.
- LocalProcess와 RemoteHost는 같은 Core 입력에 같은 업무·재무 결과를 내야 한다.
- Unity는 상태 사본을 표현할 뿐 예외 해결이나 지급 성공을 자체 확정하지 않아야 한다.

### 오행·괘상 관계

- `수뢰둔(水雷屯)`은 운영 초기의 얽힌 업무·현금·예외를 한 번에 해결하지 않고 순서를 세우는 이야기 후보다.
- `풍수환(風水渙)`은 분산된 알림·업무 상태를 다시 한 원장 계보로 모으는 회복 표현 후보다.
- 괘상은 예외 우선순위·금액·성공을 자동 판정하지 않는다.

## 문답 r5 — 음식배달 우선과 기존 OS 생명주기 사람 관점 감사

### 선택 확정

첫 직렬화 범위는 `FoodDeliveryOS + 기사 가용 의향 알림 + 관련 재무 의무`로 확정한다. 다른 OS를 무시하지는 않지만, 처음부터 네 OS의 상태와 예외를 하나로 합치지 않는다. 음식배달 한 절편에서 반복되는 판정 책임이 실제로 드러난 뒤에만 공통 Policy·Engine 후보를 추출한다.

### 현행 OS 생명주기 대조 결과

현행 코드에는 안정 OS 식별자 10개가 등록돼 있다. 그중 순서 있는 생명주기 대장이 있는 것은 다음 5개다.

| OS | 대장 단계 | 사람 관점에서 먼저 볼 결손 |
| --- | ---: | --- |
| 화주 운송관리 | 8 | 의뢰자와 위임 담당자의 동의·변경·인수 책임 |
| 국내 화물운송 | 8 | 상하차 대기, 안전 중단, 증빙 분쟁과 기사 부담 |
| 음식배달 | 8 | 조리 지연·현장 대기·수령 실패·취소 시점별 보상 |
| 창고·커머스 이행 | 9 | 스캔 작업자의 실수 회복, 인력 교대, 부분 수량 처리 |
| 살뜰마트 도심물류 | 8 | 품절 대체 동의, 피킹 부담, 라스트마일 인계 책임 |

공동구매 수요, 공동구매 수입, 커뮤니티 신뢰, 플랫폼 운영, 교육·현장체험 OS는 안정 식별자는 있지만 같은 수준의 생명주기 대장이 없다. 이 다섯 OS에는 현재 기획에서 단계를 추측해 추가하지 않는다.

일부 기존 기획 문서는 생명주기 정의가 4개라고 적지만 현행 코드와 시험은 창고를 포함한 5개를 검사한다. 이 차이는 이번 음식배달 기획에서 다른 문서를 조용히 고치지 않고 `문서 기준선 드리프트`로 기록한다.

### 음식배달에서 실제로 갈라져 있는 상태

음식배달은 현재 한 개의 상태 기계가 아니라 여러 원장이 협력하는 구조다.

| 층 | 현행 자료 | 의미 |
| --- | --- | --- |
| 개념 생명주기 | 주문·음식점 응답·조리·배차·픽업·전달·취소/보상·중단/회복 8단계 | 사람이 이해하는 OS 책임 범위 |
| 주문 원장 | 정상 7상태와 거절·취소를 포함한 9상태 | 주문자·음식점이 보는 정본 진행 |
| 기사 수행 시도 | 수락·가게 도착·픽업 완료·중단·전달 완료 5상태 | 기사 한 명의 실제 수행과 현장 대기 |
| 역할별 조작 | 주문자 2개, 음식점 4개, 기사 5개 `AvailableActions` | 현재 revision에서 누를 수 있는 버튼 |
| 중단 검토 | 보호·기사·음식점·플랫폼 책임 판정 | 사람 운영자가 중단 책임을 검토하는 별도 절차 |
| 정산 자료 | 배달료·기사 수행대금·플랫폼 차액의 일·주 조회 후보 | 완료 결과의 금액 표현, 13주 현금 원장과는 아직 미결속 |

따라서 첫 과제는 상태를 하나로 합치는 일이 아니다. 같은 `WorkStableId` 아래 각 원장의 revision과 직접 결과, 사람의 판단, 재무 의무가 왜 생겼는지를 연결하는 `생명주기 결속표`를 만드는 일이다.

### 사람 관점에서 드러난 첫 결손 목록

| 관점 | 이미 있는 것 | 보완할 질문 |
| --- | --- | --- |
| 주문자 | 주문 취소, 전달 뒤 수령 확인 | 음식점 수락 뒤 취소, 주소·요청 변경, 수령자 부재, 오배송·누락 이의 제기는 누가 언제 처리하는가 |
| 음식점 | 수락·거절, 조리시간 변경, 픽업 준비 완료 | 품절·대체 메뉴·주문 폭주·임시 중지, 기사에게 실제로 음식을 넘긴 사람과 시각을 어떻게 확인하는가 |
| 기사 | 제안 수락·거절, 가게 도착, 픽업, 전달, 일부 중단 사유 | 휴식·피로·위험 회피, 장시간 대기 중 선택권, 수령자 연락 불가와 안전한 귀환을 어떻게 보호하는가 |
| 권역 운영자 | 중단 책임 판정 | 사건 대기열의 담당자·기한·우선순위·상향·인계와 해결 가능한 조작을 어떻게 제한하는가 |
| 지사·재무 | 일부 수행대금·배달료 자료 | PG 미수, 음식점 지급, 기사 수행대금, 지사 운영보상, 환불·보상 의무를 어느 사건에서 언제 발생시키는가 |
| 시스템 | 예상 revision, 멱등 요청, Outbox 일부 | 알림 실패·중복·만료, OS 간 인계 실패, 재처리 뒤 동일 결과를 어떻게 증명하는가 |

특히 `기사 가용 의향 알림`은 아직 음식배달 정상 원장에 포함된 업무가 아니다. 알림 수락은 배차 수락이 아니며, 기사에게 응답하지 않았다는 이유로 불이익을 주지 않는 동의·빈도·휴식 보호가 먼저 필요하다.

### 공통 Engine으로 추출하는 기준

절차가 자세해졌다는 이유만으로 모두 Engine으로 만들지 않는다.

- `Process Manager/Coordinator`: 한 주문의 여러 원장과 다음 책임자를 이어준다.
- `Policy`: 현재 상태·역할·revision에서 허용 또는 차단 이유를 순수하게 판정한다.
- `Engine`: 둘 이상의 업무 사례에서 반복되고, 같은 입력에 같은 후보·점수·이유를 반환하며, 저장·확정 권한을 갖지 않는 계산만 맡는다.
- `UseCase/Command`: 사람의 확인, 권한, 현재 DB와 예상 revision을 검증해 실제 상태를 바꾼다.
- `Adapter`: 실제 푸시, PG, 지도, 모바일, Simulation, Unity처럼 환경별 실행 수단을 맡는다.

첫 Engine 후보는 기사 가용성 판단, 부족 경보, 알림 대상 후보, 배차 후보, 조리 지연 위험, 지급 의무 전망이다. 알림 발송 확정, 배차 확정, 책임 판정과 실제 지급은 Engine에 넣지 않는다.

### 첫 사람 중심 절편 추천

`기사 가게 도착 후 음식 조리 지연`을 첫 예외 절편으로 추천한다. 현행 코드에 가게 도착 시각, 현장 대기초, 조리 지연 중단, 재조리·재배차와 사람 책임 검토의 일부가 이미 있어 새 의미를 추측할 필요가 적다. 동시에 다음 사람들의 이해관계가 한 번에 드러난다.

```text
기사 가게 도착
→ 준비 완료 여부와 새 예상시각 확인
→ 유급/무급 대기 경계와 기사 선택
→ 계속 대기 또는 안전한 중단·재배차
→ 음식점·주문자 알림
→ 기사 대기보전·음식점/플랫폼 책임 후보
→ 재조리·환불·새 배차 의무
→ 운영자 예외 종료
```

이 절편이 닫히면 다른 OS의 상하차 대기, 창고 검수 보류, 마트 품절 대체처럼 `현장 사실 확인 → 시간 초과 → 사람 선택 → 책임·비용 → 회복` 구조를 공통 절차 후보로 비교할 수 있다.

## 문답 r6 — 기사 가게 도착 후 조리 지연 절편

### 선택 확정

첫 사람 중심 예외 절편은 `기사 가게 도착 후 조리 지연`으로 확정한다. 이 절편은 단순 타이머가 아니라 기사에게는 시간과 안전, 음식점에는 조리 사실과 인계 책임, 주문자에게는 예상 도착과 취소·환불 가능성, 운영자에게는 재배차와 비용 방어, 재무에는 대기보전·추가 수행대금·환불 의무가 걸린 작은 운영 사건이다.

### 현행 기반과 보완할 부분

현행에는 다음 사실이 이미 있다.

- 기사 가게 도착 시각과 음식배달 시도 revision
- 실제 현장 대기초
- 표시된 준비 예정 시각을 10분 초과한 뒤의 조리 지연 중단
- 픽업 전 재배차, 픽업 후 재조리·재배차 구분
- 보호·기사·음식점·플랫폼 책임의 사람 검토

그러나 현재 자료만으로는 `10분이 지났으니 중단한다`와 `누가 어떤 정보를 보고 기다리거나 떠나기로 선택했는가`가 충분히 연결되지 않는다. 다음을 보완한다.

1. 기사 도착 뒤 음식점이 `준비 완료 / 새 예상시각 / 예상 불가` 가운데 하나를 갱신한다.
2. 시스템은 원래 준비 예정, 새 예상시각, 기사 도착과 현재 시각으로 지연 구간을 계산한다.
3. 기사는 자신의 현장 화면에서 계속 대기, 불이익 없는 이탈 요청, 사실 불일치 신고 가운데 현재 가능한 조작만 본다.
4. 음식점은 기사 선택과 무관하게 실제 준비 완료 시각과 인계 여부를 기록한다.
5. 주문자는 내부 책임 코드가 아니라 변경된 예상 도착, 지연 사유의 일반화 표현, 취소·환불 가능 여부만 본다.
6. 운영자는 모든 지연을 직접 승인하지 않고 충돌·반복·고액·재배차 실패·사람 신고가 있는 사건만 검토한다.
7. 재무 원장은 대기보전 후보, 재배차 추가비용, 환불·음식점 보상 후보를 실제 지급과 분리해 의무 발생 근거로 기록한다.

### 제안 상태 흐름

```text
기사 도착 기록
→ 음식점 준비 사실 확인
→ 정상 대기
→ 지연 경고
→ 기사 선택 대기
   ├─ 계속 대기 → 대기보전 후보 누적 → 픽업
   ├─ 보호 이탈 → 기존 시도 종료 → 재배차
   └─ 사실 불일치 신고 → 사건 격리 → 운영자 검토
→ 픽업 또는 취소·재배차·재조리
→ 비용 의무 확정 후보
→ 사건 종료와 13주 결산 반영
```

`지연 경고`, `기사 선택 대기`, `운영자 검토`는 음식 주문의 새 최종 상태를 뜻하지 않는다. 주문 원장의 단계와 기사 수행 시도·예외 사건을 같은 업무 계보로 연결하는 보조 상태다.

### 사람 보호 원칙

- 기사에게 계속 대기를 강제하지 않는다.
- 보호 이탈은 배차 거절이나 악용으로 자동 집계하지 않는다.
- 음식점의 새 예상시각 입력만으로 음식점 책임을 자동 확정하지 않는다.
- 기사와 음식점의 시각 차이는 원본 기록을 보존하고 운영자 검토 전 한쪽을 거짓으로 판정하지 않는다.
- 주문자에게 기사·음식점의 상세 내부 사유나 개인 식별 자료를 노출하지 않는다.
- 대기보전과 추가비용은 정책 revision이 계산한 후보이며 실제 지급은 별도 확정 관문을 지난다.

### 첫 공통화 후보

이 절편에서 공통화할 수 있는 것은 `현장 지연 대응 Policy`다.

```text
입력
  원래 예정시각, 갱신 예정시각, 도착시각, 현재시각
  준비 완료 여부, 이전 경고·선택, 정책 revision

출력
  지연 구간
  역할별 AvailableActions 후보
  대기보전·재배차·운영자 검토 필요 코드
  다음 확인 시각
```

Policy는 누구의 잘못인지, 실제 지급액, 재배차 기사와 실제 주문 상태를 확정하지 않는다. 이 패턴이 화물 상하차 대기나 창고 검수 보류에서도 반복된다는 증거가 생기면 그때 `현장 지연 대응 Engine`으로 승격할 수 있다.

## 문답 r7 — 조리 지연 시 기사 자유 배차 해제

### 선택 확정

조리 지연 대응은 `기사 선택권 보장형`으로 확정한다. 음식점이 주문 수락 때 정한 조리 예정시각을 넘겼고 기사의 가게 도착이 기록돼 있다면, 기사는 운영자 승인 없이 `조리 지연 배차 해제`를 선택할 수 있다.

여기서 배차 해제는 주문 취소가 아니다.

```text
기사의 현재 수행 시도만 보호 종료
→ 기사는 새 업무를 받을 수 있는 상태로 복귀
→ 음식 주문과 조리는 유지
→ 주문은 재배차 대기로 복귀
→ 새 기사 후보 계산
→ 주문자에게 예상 도착 변경 알림
→ 비용·책임 후보는 별도 원장과 사람 검토로 이동
```

### 판단 기준시각

- 기준은 음식점이 주문을 수락하며 처음 확정한 `조리 준비 예정시각`이다.
- 음식점은 실제 상황에 따라 새 예상시각을 알릴 수 있지만 변경 전·후 시각과 변경 사유를 판본으로 보존한다.
- 뒤늦게 예정시각을 연장해 이미 열린 기사 선택권을 다시 잠글 수 없다.
- 기사가 기준시각보다 일찍 도착했다면 기준시각까지는 정상 대기다.
- 기준시각을 넘기면 별도의 운영자 승인이나 추가 유예시간 없이 배차 해제 조작이 열린다.
- 사고·위험기상·고장·개인 긴급 중단은 조리 지연과 별도 사유로 계속 다룬다.

### 역할별 결과

| 역할 | 배차 해제 직후 결과 |
| --- | --- |
| 기사 | 현재 시도는 `ProtectedRelease`로 종료되고 거절·악용·귀책으로 자동 집계되지 않는다 |
| 음식점 | 조리와 준비 완료 기록을 계속할 수 있으며 새 기사에게 인계할 준비 상태를 갱신한다 |
| 주문자 | 주문은 유지되고 새 예상 도착과 재배차 진행만 안내받는다 |
| 운영자 | 일반 지연은 자동 회복시키고 반복 지연·사실 충돌·재배차 실패만 검토한다 |
| 재무 | 기사 이동·대기 보전, 재배차 추가비용과 환불 위험을 각각 후보 의무로 기록한다 |

### 상태와 조작 경계

- 새 역할 조작 후보: `FoodDelivery.ReleaseAssignmentForPreparationDelay`.
- 입력에는 `ClientRequestId`, 기사 수행 시도 `ExpectedRevision`, 음식 주문 revision, 기준 조리 예정시각을 포함한다.
- 서버 또는 Simulation 권위는 기사·수행 시도·주문·도착 기록과 기준시각을 다시 검증한다.
- 같은 요청을 반복하면 같은 보호 해제 결과를 반환하고 두 번 재배차하거나 두 번 보전하지 않는다.
- 늦은 픽업 완료 요청이 동시에 도착하면 먼저 확정된 revision 뒤 정본을 재조회해 한 결과만 유지한다.
- Unity에서는 기사가 가게에서 이탈하고 주문이 재배차 대기로 돌아가는 모습을 표현할 수 있지만 GameObject 이동이 보호 해제 성공을 확정하지 않는다.

### 운영상 의미

이 선택은 기사에게 `기다리거나 불이익을 받는` 강제 구조를 만들지 않는다. 반대로 배차 해제만 반복해도 아무 기록이 남지 않는 구조도 아니다. 반복 패턴은 운영자 검토 후보가 될 수 있지만 사람 검토 없이 기사 책임이나 제재로 자동 변환하지 않는다.

## 문답 r8 — 조리 지연 두 시계와 재배차 우선순위

### 조리 지연 성립 조건

조리 지연 배차 해제는 다음 두 조건이 모두 성립해야 열린다.

1. 기사가 가게에 실제 도착하고 `가게 도착` 조작을 완료해 `DriverArrivedAt`과 수행 시도 revision이 기록돼 있다.
2. 음식점이 주문 수락 때 선택한 조리 요청시간으로 계산한 최초 `CommittedReadyAt`을 현재시각이 넘겼지만 아직 픽업 준비 완료가 아니다.

즉, 기사 도착 기록이 없거나 최초 준비 예정시각 전이면 조리 지연 배차 해제를 사용할 수 없다. 음식점이 이후 새 예상시각을 입력해도 `CommittedReadyAt`은 감사 기준으로 보존한다.

### 두 지연 시계

음식점의 조리 지연과 기사가 현장에서 실제로 겪은 지연을 같은 숫자로 사용하지 않는다.

```text
RestaurantPreparationDelay
  = CurrentTime - CommittedReadyAt

DriverOnSiteDelay
  = CurrentTime - max(DriverArrivedAt, CommittedReadyAt)
```

- `RestaurantPreparationDelay`는 음식이 최초 약속보다 얼마나 늦었는지 나타낸다.
- `DriverOnSiteDelay`는 기사 도착과 준비 예정시각이 모두 지난 뒤 실제 현장에서 겹친 지연만 나타낸다.
- 기사가 준비 예정시각보다 늦게 도착했다면 도착 전 시간은 기사 대기시간으로 계산하지 않는다.
- 기사가 일찍 도착했다면 준비 예정시각 이전 시간은 정상 조기 도착 대기이며 조리 지연 대기로 계산하지 않는다.
- 배차 해제 사건에는 두 시간, 최초·변경 준비 예정시각, 도착시각과 각 revision을 함께 남긴다.

기사 조작 가능 여부는 두 조건으로 판정하고, 음식점 지연 분석은 첫 번째 시계, 기사 보전 후보는 두 번째 시계를 기본 근거로 사용한다. 도착까지 이동한 비용의 별도 보전 여부는 아직 확정하지 않는다.

### 조리 지연 재배차 우선순위

조리 지연 보호 해제로 다시 대기열에 들어간 주문에는 `PreparationDelayRedispatch` 사유와 우선순위 상향 후보를 부여한다.

- 우선순위는 주문 상태가 아니라 배차 대기 원장의 재배차 사유·라운드·판본으로 기록한다.
- 이전 기사는 기본 재추천 대상에서 제외한다. 본인이 새 제안을 다시 명시적으로 허용하는 후속 정책 없이는 같은 지연 건을 곧바로 되돌려 보내지 않는다.
- 새 기사에게는 준비 완료 여부와 현재 예상 대기정보를 숨기지 않는다.
- 우선순위가 높아도 기사에게 수락을 강제하지 않는다.
- 주문 취소·새 기사 확정·배달 불가 종료 뒤에는 우선순위 상향을 제거한다.
- 재배차 우선순위 때문에 안전·거리·권역·기사 가용성 같은 기본 자격 검사를 건너뛰지 않는다.

현행 음식배달 배차 엔진은 한 배차 대기 건 안에서 다음 기사 후보를 고르는 책임이 중심이다. 여러 주문 중 어떤 건을 먼저 추천할지는 별도의 `배차 대기열 우선순위 Policy` 책임으로 둔다. 조리 지연 보너스를 기사 후보 점수에 섞어 기사 자체의 적합도가 높아진 것처럼 표현하지 않는다.

### 13주 운영 관측

13주 Simulation에서는 다음을 따로 본다.

- 조리 지연 보호 해제 주문 수와 전체 주문 대비 비율
- 음식점별 최초 준비 예정 대비 지연 분포와 반복 횟수
- 기사별 실제 현장 지연시간과 보호 해제 뒤 새 업무 획득시간
- 우선 재배차 성공시간, 추가 이동거리·추가 수행대금·고객 지연
- 우선순위 상향이 일반 대기 주문의 지연을 얼마나 늘렸는지
- 같은 주문의 반복 해제·재배차 횟수와 운영자 검토 전환 여부

이 관측은 음식점이나 기사의 제재 점수를 자동 생성하지 않는다. 운영자가 정책을 비교하고 우선순위가 다른 사람에게 과도한 대가를 전가하는지 확인하는 자료다.

## 문답 r9 — 음식배달 OS 보호 재배차 우선순위 큐

### 선택 확정

조리 지연으로 보호 해제된 주문은 음식배달 OS가 소유하는 배차 대기열의 `보호된 상위 우선순위 큐`에 등록한다. 일반 주문보다 먼저 배차 시도를 시작하지만, 우선순위가 기사에게 강제 수행 권한을 만들지는 않는다.

```text
조리 지연 보호 해제
→ 음식배달 배차 대기 원장에 재등록
→ PriorityClass = PreparationDelayProtected
→ 상위 우선순위 큐에서 주문 선택
→ 적격 기사 필터
→ 기사 후보 순위 계산
→ 제안·수락
→ 배차 확정
```

우선순위 큐는 `어떤 주문의 배차를 먼저 시도할지`를 결정한다. 음식배달 배차 엔진은 선택된 주문에 대해 `어떤 기사에게 제안할지`를 결정한다. 두 책임을 섞지 않는다.

### 최소 적격 기사 검사의 의미

안전·거리·권역·가용성 검사는 상위 주문을 일반 주문 뒤로 보내는 감점이 아니다. 우선 주문을 먼저 꺼낸 뒤 제안 가능한 기사 집합을 만드는 최소 조건이다.

| 검사 | 의미 | 하지 않는 일 |
| --- | --- | --- |
| 안전 | 사고·위험기상·고장·보호 중단 등 현재 수행을 권하지 않아야 할 상태인지 확인 | 우선 주문이라는 이유로 위험 상태 기사에게 강제 제안하지 않음 |
| 거리 | 음식점까지 도달 가능한 거리·시간 상한 안인지 확인 | 가장 가까운 기사만 무조건 확정하지 않음 |
| 권역 | 해당 배달운영권역 또는 승인된 협력권역의 수행 대상인지 확인 | 행정동이나 거주지를 기사 차별 점수로 사용하지 않음 |
| 가용성 | 운행 의향이 있고 휴식·오프라인·다른 수행 중이 아닌지 확인 | 알림 미응답자를 자동 가용 기사로 만들거나 수락을 강제하지 않음 |

적격 기사 집합이 만들어진 뒤에야 픽업 예상시간, 현재 업무와 경로 부담 같은 배차 후보 기준을 적용한다.

```text
주문 우선순위 선택
→ 기사 최소 적격 검사
→ 적격 기사 안의 후보 순위 계산
→ 제안
→ 기사 수락 뒤 확정
```

### 큐 항목의 최소 기록

- 주문·배차대기·재배차 사건 안정 식별자
- `PriorityClass = PreparationDelayProtected`
- 최초 배차 요청시각과 보호 재배차 등록시각
- 최초 조리 준비 예정시각과 현재 준비 상태
- 음식점 조리 지연·기사 현장 지연
- 이전 수행 기사 제외 근거
- 추천 라운드와 현재 revision
- 우선순위 적용·해제 사유와 정책 revision

상위 우선순위는 새 기사 확정, 주문 취소, 배달 불가 종료 때 해제한다. 재배차가 반복돼도 최초 주문시각과 이전 시도 계보를 잃지 않는다.

### 남은 운영 문제

상위 주문에 현재 적격 기사가 한 명도 없을 수 있다. 이 주문이 큐 맨 앞을 계속 막으면 다른 배달도 전부 멈추는 `선두 막힘`이 생긴다. 반대로 바로 일반 큐로 내리면 보호 우선순위의 의미가 사라진다. 따라서 적격 기사 없음 상태에서도 우선권을 보존하면서 다른 주문 처리를 막지 않는 재시도 규칙이 필요하다.

## 문답 r10 — 비차단 우선권과 병렬 배차

### 선택 확정

상위 주문에 현재 적격 기사가 없을 때는 `비차단 우선권 유지`를 사용한다. 조리 지연 주문은 `PreparationDelayProtected` 등급을 잃지 않고 다음 후보 탐색 시각에 다시 평가되며, 그동안 다른 처리 가능한 주문의 배차는 계속 진행한다.

사용자 경험상 이런 상황은 드물 수 있으므로 첫 Simulation에서는 주 흐름이 아니라 복구 안전장치로 검증한다. 발생 빈도를 부풀려 게임 난이도나 기사 부족을 인위적으로 만들지 않는다.

### 병렬 처리 의미

우선순위 큐는 하나의 전역 작업자가 주문 하나씩 끝낼 때까지 기다리는 물리적 단일 줄이 아니다. 여러 주문을 병렬로 처리하되 각 주문에는 한 시점에 하나의 유효한 배차 시도만 존재해야 한다.

```text
배차 Scheduler
├─ 보호 재배차 주문 A lease → 기사 후보 탐색
├─ 일반 주문 B lease        → 기사 후보 탐색
└─ 일반 주문 C lease        → 기사 후보 탐색

주문 A에 적격 기사 없음
→ A 우선등급 유지 + 다음 탐색 예약
→ B·C 배차는 계속 진행
```

- 같은 주문은 queue revision과 짧은 lease로 중복 작업자를 막는다.
- 다른 주문은 독립 lease를 얻어 병렬로 진행할 수 있다.
- lease 만료·작업자 실패 뒤에는 같은 revision을 확인하고 재진입한다.
- 기사 수락이 먼저 확정되면 다른 늦은 제안·수락은 정본 revision 불일치로 거절한다.
- 보호 주문에 적격 기사가 다시 생기면 다음 due cycle에서 일반 주문보다 먼저 후보 탐색 기회를 얻는다.

### 가까운 기사 우선과의 관계

현행에는 기사 위치와 음식점까지의 거리 계산·범위 검증 경로가 있다. 이를 보호 재배차에도 재사용한다.

```text
1. 주문 Scheduler가 보호 주문을 먼저 선택
2. 적격 기사 집합 구성
3. 적격 기사 안에서 음식점까지 거리·예상 도착·현재 업무 부담 평가
4. 가까운 적합 기사부터 제안
5. 기사 수락 뒤 배차 확정
```

주문의 `PreparationDelayProtected` 등급을 기사 거리 점수에 더하지 않는다. 주문 우선순위와 기사 후보 순위는 서로 다른 축이다. 가까운 기사라는 이유만으로 휴식·다른 수행·권역·안전 조건을 무시하지도 않는다.

### 비차단 재탐색 기록

- 후보 없음 판정시각과 이유 코드
- 당시 검사한 적격 기사 수
- 다음 후보 탐색 시각과 재탐색 횟수
- 우선등급 유지·변경 revision
- 병렬 처리 중인 다른 주문 수
- 새 기사 확정까지 걸린 시간

정확한 재탐색 간격과 backoff 상한은 첫 구현 전 부하 시험에서 정한다. 이 값은 주문의 우선등급과 분리된 운영 설정이며, 변경할 때 정책 revision을 남긴다.

## 문답 r11 — 조리 지연 회복 혜택을 재배차 우선순위로 제한

### 선택 확정

조리 지연 배차 해제에 별도 도착 보전·대기시간 보전·추가 인센티브를 만들지 않는다. 이번 절편의 회복 혜택은 해당 주문이 새 배차 건으로 만들어질 때 `PreparationDelayProtected` 상위 우선순위 큐에 들어가는 것으로 제한한다.

```text
조리 지연 배차 해제
├─ 기존 기사: 불이익 없는 수행 시도 종료 + 가용 상태 복귀
├─ 음식 주문: 유지
├─ 새 배차 건: 보호 상위 우선순위 적용
└─ 추가 금전 의무: 생성하지 않음
```

기사가 가게까지 이동하고 현장에서 기다린 사실은 삭제하지 않는다. 다만 이번 기획에서는 이를 지급 의무가 아니라 운영 품질 관측치로 사용한다.

### 금전·정산 경계

- `DriverArrivalCompensationObligation`을 새로 만들지 않는다.
- `DriverOnSiteDelayCompensationObligation`을 새로 만들지 않는다.
- 기존 기사 수행대금·완료 정산 규칙을 조리 지연 보호 해제 때문에 조용히 변경하지 않는다.
- 조리 지연 재배차의 추가 거리·소요시간·성공률은 13주 운영비 분석에 남기지만 지급 예정액으로 계산하지 않는다.
- 향후 법률·계약·운영 정책이 별도 보전을 요구하면 새 revision과 별도 승인으로 다시 연다.

### 기사 보호와 주문 우선권의 구분

기사에게 제공되는 것은 추가 금전 혜택이 아니라 다음 보호다.

- 조리 지연 배차 해제를 거절·악용·기사 귀책으로 자동 집계하지 않음
- 현재 수행 시도 종료 뒤 다른 주문 후보가 될 수 있음
- 해제한 동일 주문을 곧바로 다시 강제 제안하지 않음

주문에 제공되는 것은 다음 회복 우선권이다.

- 새 배차 건을 `PreparationDelayProtected`로 등록
- 일반 주문보다 먼저 후보 탐색 기회 부여
- 적격 기사가 없으면 우선등급을 유지하며 비차단 재탐색

따라서 기사 보호와 주문 우선권을 하나의 금전 보상 개념으로 합치지 않는다.

### 조리 지연 절편 기획 폐쇄 조건

다음 사항을 기획 기준선으로 닫는다.

1. 기사 도착과 최초 준비 예정시각 경과의 두 조건
2. 음식점 조리 지연과 기사 현장 지연의 두 시계
3. 운영자 승인 없는 기사 보호 배차 해제
4. 주문 유지와 새 배차 건 생성
5. 보호 상위 우선순위 큐와 비차단 병렬 재탐색
6. 적격 기사 안에서 가까운 기사 우선 후보 선정
7. 별도 도착·대기 금전 보전 없음

이 폐쇄는 구현·E 단계·실제 지급·Unity 실행 승인이 아니다. 다음 구현 인계 전에는 기존 API·원장·배차 queue와 정확한 쓰기 경로를 다시 대조해야 한다.

## 문답 r12 — 픽업 후 수령자 부재와 조건부 문 앞 전달 증거

### 선택 확정

기사가 음식을 픽업한 뒤 전달지에 도착했지만 수령자를 만나지 못한 경우, 수령자에게 최대 3회 연락을 시도한다. 세 번 모두 연결되지 않으면 무조건 전달 완료로 만들지 않고 `비대면 전달 허용 여부`와 `안전하게 둘 수 있는 장소`를 먼저 판정한다. 두 조건이 충족될 때만 문 앞 또는 주문자가 지정한 안전 장소에 두고 배달 사진을 남긴다.

```text
전달지 도착
→ 연락 시도 1·2·3회 기록
→ 모두 실패
→ 비대면 전달 허용 + 안전 장소 존재?
   ├─ 예: 현장 사진 전송 → 서버 증거 수락 → 수령자 부재 전달 완료 후보
   └─ 아니오: 전달 완료 금지 → 미정인 안전 예외 처리로 이동
```

전화 통화 화면 캡처는 보조 첨부가 될 수 있지만 정본 기록으로 삼지 않는다. 앱·서버가 각 시도의 순번, 시작·종료시각, 결과 코드(`NoAnswer`, `Rejected`, `Connected`), 행위자 역할, 주문·기사 수행 revision을 직접 남긴다. 기본값으로 통화 음성을 녹음하지 않으며, 외부 전화 앱 화면을 첨부할 때는 전화번호 등 불필요한 개인정보를 가린 보조 자료로만 받는다.

### 문 앞 전달 허용 조건

다음 조건을 모두 충족해야 한다.

1. 주문자의 사전 요청 또는 판본화된 플랫폼 정책이 비대면 전달을 허용한다.
2. 음식·주문 특성상 직접 인계가 필수가 아니다.
3. 공동현관 밖 노출, 우천, 통행 방해, 동물 접근, 도난 위험 등 명백한 위험이 없는 장소다.
4. 사진을 서버가 정상 수락해 증거 식별자와 hash를 반환했다.

사진 전송 실패·서버 수락 실패 상태에서는 전달 완료로 확정하지 않는다. 네트워크가 끊기면 암호화된 로컬 임시 보관과 재시도를 허용할 수 있지만, 업로드 성공 전 상태는 `EvidenceUploadPending` 후보로 남긴다. 비대면 전달이 금지됐거나 안전 장소가 없으면 기사가 임의 장소에 두고 완료할 수 없다.

### 증거 묶음

정본 증거 묶음은 단순 스크린샷 한 장이 아니라 다음 항목을 같은 주문·수행 시도 revision으로 연결한다.

- 도착 기록과 위치 품질 코드
- 최대 3회의 연락 시도 기록과 결과
- 비대면 전달 허용 근거의 정책·주문 revision
- 앱에서 촬영한 원본 사진의 object key·SHA-256·촬영시각·업로더 역할
- 서버 수락시각, 전달 위치의 일반화된 표시, 수령자 알림 결과
- 이후 열람·내보내기·삭제·법적 보존 조치의 감사 기록

사진은 문 앞 음식과 필요한 주변 맥락만 담고 얼굴, 전화번호, 공동현관 비밀번호, 이웃 세대 내부와 같은 불필요한 정보를 피하도록 촬영 안내를 제공한다. Unity와 공개 API에는 원본 사진·전화번호·상세 주소를 보내지 않는다. 운영 화면에는 권한이 있는 담당자만 최소한의 미리보기를 보고, 필요하면 별도의 가림 처리본을 사용한다.

### 보존·분쟁 경계

- 증거는 분쟁 대응을 위한 `배달 증거 후보`이지 민사소송의 승패나 증거능력을 자동 보장하지 않는다.
- 원본, hash, 생성·수락 시각, 주문 revision, 접근 기록을 보존해 임의 편집본보다 계보를 설명할 수 있게 한다.
- 분쟁 제출은 권한 있는 내보내기 절차가 manifest와 hash를 묶어 생성하며, 기사가 개인 메신저로 원본을 전달하는 방식은 사용하지 않는다.
- 수집 목적과 기본 보존기간을 정책 revision에 명시하고 목적 달성·기간 만료 뒤에는 파기한다. 분쟁 또는 법적 보존 조치가 열릴 때만 해당 자료를 별도 격리하고 접근을 감사한다.
- 개인정보의 수집·이용은 목적에 필요한 최소 범위와 적법한 근거를 가져야 하며, 목적 달성 또는 보유기간 경과 뒤 지체 없이 파기하되 다른 법령상 보존 의무가 있으면 분리 보관한다.

관련 법적 기준선은 [개인정보 보호법 제15조](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029335387), [개인정보 보호법 제21조](https://law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0021&lsiSeq=283839&urlMode=lsScJoRltInfoR), [전자문서 및 전자거래 기본법](https://www.law.go.kr/lsInfoP.do?lsId=002000)을 따른다. 실제 운영 전에는 보존기간·동의 또는 다른 처리 근거·분쟁 제출 양식을 법률·개인정보 담당자가 별도로 승인해야 한다.

### 현행 자산 재사용 경계

화물·기사 앱에 있는 `수령자 부재` 사유와 사진·인수증 계열 증거 구조는 참고·재사용 후보일 뿐 음식배달 지원 완료 증거가 아니다. 음식배달 주문, 기사 수행 시도, 연락 시도와 증거 수락을 명시적으로 결속하는 별도 수직 절편이 필요하다. 이번 문답은 구현·DB 저장·API·Unity 표현·법률 승인을 수행하지 않는다.

## 문답 r13 — 문 앞 전달 우선과 고객센터 판단형 보호 종료

### 선택 확정

수령자 부재의 기본 회복 순서는 `안전한 문 앞 전달 → 고객센터 채팅 판단 → 지시 이행 → 기사 보호 종료`로 정한다. 안전하고 허용된 문 앞 전달이 가능하면 사진과 서버 수락을 완료한 즉시 기사는 다음 배차를 수행할 수 있다. 문 앞 전달이 불가능할 때만 고객센터 예외 사건을 열고, 기사가 음식을 임의로 보유·소비·양도하는 상태는 기본 선택지로 두지 않는다.

```text
3회 연락 실패
├─ 문 앞 전달 허용·안전
│  └─ 사진·서버 수락 → 수령자 알림 → 기사 보호 종료 → 다음 배차 가능
└─ 문 앞 전달 불가
   └─ 고객센터 채팅 사건
      ├─ 대체 안전 장소 지시
      ├─ 음식점 반환 지시
      ├─ 현장 폐기 지시
      └─ 추가 대기 지시
         → 지시 이행 증거 → 기사 보호 종료 → 다음 배차 가능
```

고객센터 담당자는 주문·연락 시도·현장 사진·음식 특성·경과시간을 보고 판본화된 선택지 중 하나를 결정한다. 자유 문장 채팅은 상황 설명에 사용하되, 실제 상태를 바꾸는 결정은 구조화된 `DispositionCode`, 사유, 담당자 역할, 결정시각, 예상 주문·수행 revision과 함께 별도 명령으로 확정한다.

`DisposeOnSite`는 담당자가 명시적으로 승인한 현장 폐기이며 기사 개인의 임의 처분이 아니다. 폐기 지시와 필요한 이행 확인이 끝나면 기사에게 음식 보관 책임을 계속 지우지 않는다. 반환·폐기 비용과 기사 수행대금 영향은 별도 재무 의무 후보로 남기며 이번 문답에서 금액을 정하지 않는다.

### 통화 버튼과 서버 기록의 결합

기사 앱의 `수령자에게 전화` 버튼과 서버 연락 시도 API를 하나의 사용자 조작으로 묶되, 다음 사실을 분리한다.

1. 서버가 `ContactAttemptId`와 짧은 유효기간의 가상번호·통화 token을 발급한다.
2. 앱이 승인된 통화 중계 Adapter를 호출한다.
3. 중계 사업자의 callback이 `Initiated → Ringing → Answered/NoAnswer/Failed → Ended`를 서버에 전달한다.
4. 서버는 provider event ID, 발생시각, 수신시각, 순번, 주문·수행 revision과 멱등 key를 검증해 정본 사건으로 추가한다.
5. 앱은 서버 정본을 재조회해 남은 연락 횟수와 다음 가능한 조작을 표시한다.

버튼 클릭은 `연락 시도 의사`만 증명한다. 실제 발신·호출·연결·통화 종료는 중계 callback이 있을 때만 각각 확정한다. 외부 전화 앱으로 빠져나간 경우에는 확인 가능한 범위가 줄어들므로 `UnverifiedExternalDial`로 표시하고 기사 입력만으로 `Answered`를 확정하지 않는다. 통화 내용은 기본 녹음하지 않는다.

Simulation에서는 같은 계약의 가짜 통화 Adapter가 결정적 callback을 생성한다. 실제 통신사·통화 중계 업체, 요금, 약관, 가상번호 방식은 운영 구현 전에 별도 선정·승인한다.

### 고객센터 채팅 사건

문 앞 전달이 불가능하면 `RecipientUnavailableSupportCase`를 열고 다음 항목을 유지한다.

- 주문·기사 수행·3회 연락 시도와 현장 증거 참조
- 사건 개설시각, 응답 기한, 담당 queue와 현재 담당자
- 기사·담당자 메시지의 작성자·시각·message ID
- 허용되는 처분 코드와 각 코드에 필요한 추가 증거
- 담당자의 결정, 사유, 결정시각과 예상 revision
- 기사 이행 확인, 보호 종료시각과 다음 배차 가용시각

채팅 메시지 자체가 반환·폐기·전달 완료를 확정하지 않는다. 권한 있는 담당자가 구조화된 결정을 확정하고, 기사가 그 결정을 이행한 뒤 서버 정본을 재조회해야 한다. 기사에게는 현재 담당 상태와 응답 기한을 보여 주며 중복 사건 개설은 멱등 처리한다.

### 증거·분쟁 경계 보강

전자 기록은 작성자·수신자와 송수신 시각이 보존되고 원래 형태로 열람·재현될 수 있도록 관리한다. [전자문서 및 전자거래 기본법 제4조의2·제5조](https://www.law.go.kr/lsInfoP.do?lsId=002000)는 전자문서의 열람 가능성과 작성자·수신자·송수신 시각 보존을 다루지만, 앱 로그 하나가 특정 소송 결과를 자동 보장한다는 뜻은 아니다.

통화 callback·고객센터 채팅·사진·처분 명령은 같은 manifest로 내보낼 수 있게 계보를 유지한다. 개인정보 처리는 주문 계약 이행과 분쟁 대응에 필요한 범위와 목적 안에서 설계하고, 실제 운영 전에는 [개인정보 보호법 제15조](https://www.law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1029335389)에 따른 처리 근거·고지·보존기간을 법률·개인정보 담당자가 확인한다.

## 문답 r14 — 고객센터 미응답 시 정책표 안의 기사 선택

### 선택 확정

고객센터 담당자가 응답기한 안에 처분 명령을 내리지 못하면 `판본화된 안전 기본표`를 적용한다. 서버는 음식 특성·픽업 후 경과시간·현장 안전·문 앞 전달 허용·음식점 반환 가능 여부와 현재 정책 revision을 평가해 기사에게 지금 실행 가능한 조작만 제공한다. 기사는 그 `AvailableActions` 안에서 하나를 선택하고, 필요한 이행 증거를 제출하면 보호 종료 후 다음 배차를 수행할 수 있다.

```text
고객센터 응답기한 만료
→ 서버가 정책표·주문·현장 revision 재검증
→ 허용 조작 계산
   ├─ DoorDropAtVerifiedSafePlace
   ├─ ReturnToMerchant
   └─ DisposeOnSite
→ 기사가 열린 조작 중 하나 선택
→ 이행 증거 수락
→ RecipientUnavailableResolved
→ 기사 보호 종료·다음 배차 가용
```

`ContinueWaiting`은 담당자 미응답 뒤 기사를 무기한 붙잡는 기본 조작으로 두지 않는다. 다만 기사가 자발적으로 짧은 추가 대기를 선택할 수 있게 할지는 후속 정책 후보로 남긴다.

### 제한된 선택권

- 서버가 제공하지 않은 처분은 앱에서 선택할 수 없다.
- 문 앞 전달은 주문자 허용과 안전 장소가 다시 확인될 때만 열린다.
- 음식점 반환은 음식점 수령 가능 상태와 반환 거리·시간 상한을 충족할 때만 열린다.
- 현장 폐기는 문 앞 전달과 반환이 모두 부적합하고 정책표가 허용할 때만 열린다.
- 음식의 개인 보유·소비·재판매·제3자 양도는 어떤 정책표에서도 열지 않는다.
- 같은 사건에 하나의 유효한 해결 명령만 허용하며 예상 revision과 멱등 key로 중복 선택을 차단한다.

기사의 선택 기록에는 정책 revision, 당시 제공된 전체 `AvailableActions`, 선택한 조작, 선택시각, 이행 증거와 서버 수락시각을 남긴다. 이 구조는 기사에게 현장 종료 수단을 주면서도 사후에 플랫폼 규칙과 기사 선택을 구분할 수 있게 한다.

### 다음 배차 복귀

이행 증거가 서버에서 수락되면 현재 수행 시도를 `RecipientUnavailableResolved` 사유로 보호 종료하고 기사를 다시 가용 후보로 돌린다. 고객센터 채팅 사건은 `ResolvedByPolicyFallback`으로 닫고, 늦게 도착한 담당자 명령은 이미 닫힌 revision을 변경하지 못한다. 음식 배달 완료·환불·음식점 대금·기사 수행대금의 재무 결과는 선택한 처분 코드에 따라 별도 원장에서 계산하며, 기사 가용 복귀를 그 계산 완료까지 막지 않는다.

Simulation에서는 같은 seed·정책 revision·주문·현장 입력으로 동일한 `AvailableActions`가 나오는지, 기사 선택 뒤 중복 종료가 발생하지 않는지, 고객센터의 늦은 응답이 결과를 뒤집지 않는지를 검증한다.

## 문답 r15 — 고객센터 응답 제한시간 3분

### 선택 확정

기사의 현장 대기 부담을 우선해 고객센터 응답 제한시간은 `3분`으로 정한다. 3분은 세 번째 연락 실패와 고객센터 사건 개설이 모두 기록된 시점 중 더 늦은 시점부터 계산한다.

```text
FallbackEligibleAt = max(ThirdContactFailedAt, SupportCaseOpenedAt) + 3분
```

3분 안에 담당자의 유효한 처분 명령이 도착하면 그 명령을 따른다. 3분이 지나면 서버가 사건과 정책 revision을 다시 읽고 안전 기본표의 `AvailableActions`를 연다. 기사가 한 조작을 확정한 뒤 들어온 담당자 응답은 사건 메모로 보존할 수 있지만 이미 확정한 처분을 변경하지 못한다.

### 시간 판정 경계

- 앱의 로컬 시계가 아니라 서버 수락시각으로 3분을 계산한다.
- 세 번째 통화가 실제로 진행 중이거나 연결된 경우에는 `NoAnswer`로 닫히기 전까지 제한시간을 시작하지 않는다.
- 고객센터 사건 개설 API 재시도는 같은 멱등 key를 사용하며 제한시간을 다시 시작하지 않는다.
- 앱이 오프라인이어도 서버의 제한시간은 진행한다. 재연결 후 정본 상태와 현재 `AvailableActions`를 다시 조회한다.
- 3분 경과는 자동 폐기 명령이 아니라 기사가 정책표 안의 조작을 선택할 수 있게 되는 조건이다.

이 3분은 첫 Simulation·운영 정책 기본값이다. 실제 점심 피크 관측에서 상담 응답률·기사 추가 대기·음식 품질 악화가 확인되면 정책 revision으로 조정하되, 과거 사건의 제한시간을 소급 변경하지 않는다.

## 문답 r16 — 현장 폐기 최소 증거

### 선택 확정

정책표가 `DisposeOnSite`를 허용하고 기사가 이를 선택한 경우, 최소 이행 증거는 `처분 후 사진 1장 + 정책·위치·시각 자동 기록`으로 정한다. 처분 전 사진을 의무화하지 않아 현장 체류와 불필요한 촬영을 줄이되, 어떤 정책이 어느 주문에서 폐기를 허용했고 실제 이행 자료가 언제 수락됐는지는 서버 계보로 보존한다.

### 증거 수락 조건

- 사진은 기사 앱의 사건 화면에서 직접 촬영하며 기본적으로 사진첩 파일 대체를 허용하지 않는다.
- 서버는 주문·기사 수행·고객센터 사건·처분 명령 revision과 사진 object key·SHA-256·촬영시각·수락시각을 연결한다.
- 앱이 수집한 위치에는 품질 코드를 붙인다. 정확 위치는 권한이 제한된 보호 원장에 두고 Unity·공개 API·일반 운영 카드에는 일반화 위치만 제공한다.
- 사진에는 처분 결과만 필요한 범위로 담고 얼굴·주거 내부·상호·차량번호·공동현관 비밀번호 등 불필요한 정보를 피하도록 촬영 안내를 제공한다.
- 서버가 사진과 metadata를 수락하기 전에는 `DisposeOnSiteCompleted`를 확정하거나 기사를 다음 배차 후보로 복귀시키지 않는다.
- 네트워크 장애 때는 암호화된 임시 보관과 재전송을 허용할 수 있지만, 사진을 개인 사진첩·메신저에 보관하거나 제출하는 방식을 정본으로 사용하지 않는다.

사진 한 장만 따로 떼어 증거라고 하지 않는다. 3회 연락, 고객센터 미응답 3분, 당시 열린 `AvailableActions`, 기사 선택, 정책 revision과 처분 후 사진을 하나의 manifest로 묶는다. 이 증거 묶음은 플랫폼의 정책 허용과 기사 이행을 설명하기 위한 자료이며 실제 분쟁 결론을 자동 확정하지 않는다.

## 문답 r17 — 정상 기사 수행대금과 현장 폐기 우선

### 선택 확정

수령자 부재가 기사 귀책 없이 문 앞 전달 또는 승인된 현장 폐기로 끝나면, 배차 수락 때 확정된 기사 수행대금을 정상 지급한다. 수령자 부재를 이유로 감액·미지급·기사 벌점을 만들지 않는다. 기본 처분은 음식점 반환보다 `DisposeOnSite`를 우선한다. 이미 전달지까지 이동한 음식을 음식점으로 돌려보내도 다시 판매하기 어렵고 음식점에서 폐기할 가능성이 높기 때문이다.

```text
기존 배차
├─ 배차 수락 때 수행대금 확정
├─ 픽업·이동·3회 연락·정책 절차 이행
├─ 문 앞 전달 또는 승인된 현장 폐기
└─ 기존 수행대금 정상 지급

반환이 반드시 필요한 예외
└─ 기존 배차 연장 아님 → 별도 반환 배차 후보 → 별도 대금 확정
```

### 수행대금 경계

- 기존 배차 수행대금은 처분 방식이 아니라 배차 수락 revision에 결속한다.
- 정책 절차를 정상 이행한 기사에게 수령자 부재 책임을 전가하지 않는다.
- 현장 폐기는 추가 대금 의무를 자동 생성하지 않는다.
- 음식점 반환도 기존 배차에 임의의 귀환 가산금을 붙이지 않는다.
- 플랫폼이 반환을 꼭 요구하는 예외라면 `ReturnToMerchantDispatch`라는 별도 업무·배차로 생성하고, 기사가 새 금액과 조건을 보고 별도로 수락하게 한다.
- 별도 반환 배차를 거절했다고 기존 배차 대금이나 기사 지표를 감액하지 않는다.

기사 수행대금 지급 원인은 `RecipientUnavailableResolved`와 이행 증거 수락으로 남긴다. 음식값 환불, 음식점 상품대금, 플랫폼 부담과 고객 청구는 별도 재무 원장에서 결정하며 기사 수행대금과 상계하지 않는다.

### 현장 폐기 우선 경계

안전 기본표는 문 앞 전달이 불가능할 때 일반 조리 음식에 대해 현장 폐기를 우선 후보로 열 수 있다. 다만 폐기 금지 품목·회수 의무가 있는 물품·음식이 아닌 상품은 이 기본값에 포함하지 않는다. `ReturnToMerchant`는 법적·계약상 회수 의무 또는 음식점의 명시적 회수 승인이 있는 예외에만 열고, 필요한 경우 별도 반환 배차로 전환한다.

## 문답 r18 — 확인된 주문자 부재의 주문 청구 유지

### 선택 확정

플랫폼·음식점·기사의 귀책 없이 주문자가 전달지에 없고, 연락·대기·문 앞 전달 검토·증거 절차를 모두 정상 이행했다면 주문은 재무상 `수령 완료 상당`으로 처리한다. 주문자 청구를 유지하고 음식점 상품대금과 기사 수행대금을 정상 지급한다. 주문자가 실제 음식을 손에 받지 못했더라도, 주문자 부재 때문에 이행할 수 없었던 비용을 기사나 음식점에 이전하지 않는다.

이 판정은 단순히 `수령자 없음` 버튼 하나로 열리지 않는다. 다음 사실이 같은 주문 revision에서 확인돼야 한다.

1. 기사의 전달지 도착과 위치 품질
2. 최대 3회 연락 시도와 통화 callback 결과
3. 고객센터 사건과 3분 응답 제한시간
4. 안전한 문 앞 전달이 불가능했던 이유
5. 정책표가 허용한 처분과 기사 선택
6. 문 앞 전달 또는 현장 폐기 증거의 서버 수락

조건이 충족되면 `RecipientAbsenceCustomerAttributable` 원인 코드를 남기되, 이는 공개 낙인·신뢰점수·검색순위·향후 주문 자동 거절에 사용하지 않는다. 반복 여부를 곧바로 사기나 고의로 해석하지 않으며 분쟁 사건 안에서만 필요한 범위로 사용한다.

### 플랫폼 잘못이 함께 있는 경우

주소 전달 오류, 가상번호·통화 중계 장애, 고객센터 사건 생성 실패, 앱의 문 앞 요청 누락처럼 플랫폼 원인이 확인되면 전액을 주문자에게 돌리지 않는다. 원인별 부담을 다음처럼 별도 원장에 나눈다.

- `CustomerResponsibilityShare`
- `PlatformResponsibilityShare`
- 필요할 때만 `MerchantResponsibilityShare`, `CourierResponsibilityShare`, `ExternalResponsibilityShare`

모든 비율의 합은 100%여야 하며, 플랫폼 부담분은 주문자 환급 또는 고객지원 보상 의무와 플랫폼 비용으로 연결한다. 기사 수행대금과 음식점 상품대금은 이 비율과 상계하지 않고 먼저 정상 의무로 보존한다. 정확한 비율은 근거 없는 AI 점수로 자동 확정하지 않는다.

전자상거래법은 소비자 책임으로 재화가 멸실·훼손되거나 시간이 지나 재판매가 곤란할 정도로 가치가 감소한 경우 등의 청약철회 제한과 사업자의 사전 표시 의무를 규정하지만, 이것만으로 개별 배달 수령자 부재 사건의 청구를 자동 확정할 수는 없다. [전자상거래 등에서의 소비자보호에 관한 법률 제17조](https://www.law.go.kr/lsInfoP.do?lsId=009318) 실제 운영 약관·사전 고지·환급 비율은 법률 검토를 거친다.

## 문답 r19 — 원인 규칙표 후보와 이의·복합 사건 사람 확정

### 선택 확정

부담 비율은 `원인 규칙표가 근거 있는 후보를 생성하고, 이의·복합 사건만 담당자가 확정`하는 방식으로 정한다. 명백한 단일 원인은 현재 정책 revision과 완전한 증거 묶음이 일치할 때만 자동 확정할 수 있다. 플랫폼 장애가 하나라도 포함되거나 여러 원인이 경합하거나 주문자가 이의를 제기하면 자동 확정을 중단하고 사람 검토 사건으로 전환한다.

### 규칙표 입력과 출력

규칙표는 다음 입력만 사용한다.

- 도착·연락·고객센터·문 앞 전달·처분 증거의 완전성
- 주소·통화 중계·앱·고객센터 API의 장애 코드와 영향 시간
- 주문자 요청·주소 변경·비대면 전달 선택의 revision
- 음식점·기사의 실제 행위 기록과 서버 수락시각
- 적용 약관·운영 정책 revision

출력은 `책임 주체별 후보 비율`, 근거 코드, 소비한 증거 ID, 적용 규칙 ID·revision, 사람 검토 필요 여부다. 기계학습 추정, 고객 평판, 과거 주문 횟수, 경제력·지역·개인 특성을 비율 근거로 사용하지 않는다.

### 자동 확정과 사람 검토의 경계

```text
완전한 증거 + 단일 원인 + 이의 없음
→ 규칙표 후보 → 정책 허용 범위 검사 → 자동 확정 가능

플랫폼 장애 또는 복합 원인 또는 주문자 이의 또는 증거 충돌
→ 후보만 보존 → ResponsibilityReviewCase → 담당자 확정
```

담당자는 후보 비율을 그대로 승인하거나 수정할 수 있지만, 수정 사유와 사용한 증거를 남겨야 한다. 확정에는 예상 revision과 멱등 key를 요구하고, 이후 새 증거가 들어오면 기존 결정을 덮어쓰지 않고 새 검토 revision을 연다. 기사·음식점 대금은 이 검토 때문에 보류하거나 상계하지 않는다.

소비자분쟁해결기준은 일반 기준과 품목별 기준으로 구분되므로 내부 규칙표가 법정 기준이나 외부 분쟁조정 결과를 대신하지 않는다. [소비자기본법 시행령 제8조](https://www.law.go.kr/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=900638601) 당사자 합의가 되지 않는 분쟁에는 별도 피해구제·분쟁조정 경로가 있음을 주문자 안내에 포함한다.

## 문답 r20 — 이의 검토 중 주문 청구 유지와 조건부 환급 준비금

### 선택 확정

주문자가 수령자 부재 책임 판정에 이의를 제기해도 원 주문 청구는 우선 유지한다. 동시에 규칙표가 산출한 플랫폼 부담 후보액 또는 담당자가 정한 검토 대상 금액을 `ConditionalCustomerRefundReserve`로 격리해 13주 가용현금에서 차감한다. 검토 결과 플랫폼 부담이 확정되면 해당 금액을 환급 의무로 전환하고, 주문자 책임으로 확정되면 사용하지 않은 준비금을 해제한다.

```text
이의 접수
→ 원 주문 청구 유지
→ ResponsibilityReviewCase 개설
→ ConditionalCustomerRefundReserve 설정
→ 가용 운영현금에서 제외
→ 검토 확정
   ├─ 플랫폼 부담: CustomerRefundObligation으로 전환
   └─ 주문자 부담: 준비금 해제
```

### 원장 분리

- 원 주문 청구·PG 수납 상태는 기존 결제 원장에 유지한다.
- 기사 수행대금과 음식점 상품대금은 정상 지급 의무로 유지한다.
- 조건부 환급 준비금은 내부 Simulation·현금 방어 원장에 별도 기록한다.
- 실제 환급 의무는 담당자 확정 또는 별도 자동 확정 조건이 충족된 뒤 생성한다.
- 준비금 설정·증액·감액·해제·환급 전환은 모두 원인 사건·책임 판정 revision과 연결한다.
- 같은 이의 사건의 재요청은 멱등 처리해 준비금을 중복 적립하지 않는다.

`ConditionalCustomerRefundReserve`는 현금 안정성 Simulation을 위한 내부 용어다. 외부 재무제표의 회계상 충당부채인지, 계약부채·미지급금·기타 분류인지 이번 기획에서 확정하지 않는다. 실제 회계 분류와 세무 처리는 회계·세무 담당자의 정책 승인을 별도로 받아야 한다.

### 주문자 안내

주문자에게는 이의 접수 여부, 현재 검토 중인 사실, 기사·음식점 대금 세부 정보가 아닌 본인 주문의 증거 요약, 다음 상태와 예상 답변 기한을 보여 준다. 내부 책임 후보 비율은 확정 전 그대로 노출하지 않고, 확정 뒤 최종 책임 사유와 환급 금액·방법을 설명한다. 법정 피해구제·분쟁조정 권리를 제한하는 문구를 사용하지 않는다.

## 조사·결정 r21 — 공식 소비자분쟁 절차를 참고한 내부 답변 기한

### 공식 기준 조사

- [소비자기본법 제58조](https://www.law.go.kr/LSW/lsSideInfoP.do?docCls=jo&joBrNo=00&joNo=0058&lsiSeq=277233&urlMode=lsScJoRltInfoR)는 한국소비자원장이 피해구제 신청을 받은 날부터 30일 안에 합의가 이뤄지지 않으면 소비자분쟁조정위원회에 지체 없이 조정을 신청하도록 하고, 원인 규명에 상당한 시일이 필요한 사건은 정해진 범위에서 연장할 수 있게 한다.
- [한국소비자원 피해구제 절차 안내](https://www.kca.go.kr/odr/link/pg/pr/osPgStpSobiGuidW.do)는 접수된 피해구제를 30일 안에 처리하고 사안에 따라 연장할 수 있다고 안내한다. 이는 플랫폼 내부 고객센터 사건과 별개의 외부 피해구제 절차다.
- [한국소비자원 소비자분쟁조정 안내](https://www.kca.go.kr/odr/bj/ma/bjInfo.do)는 조정위원회가 신청일부터 30일 안에 조정을 마치는 것을 원칙으로 하되 정당한 사유가 있으면 연장할 수 있다고 안내한다.
- [소비자분쟁해결기준](https://www.law.go.kr/LSW/admRulInfoP.do?admRulSeq=2100000217293&chrClsCd=010201)은 분쟁 해결을 위한 합의·권고 기준이다. 이번 조사에서는 음식배달 수령자 부재에 대해 플랫폼 내부 첫 응답을 정확히 몇 시간 안에 하라는 별도 항목을 확인하지 못했다.

외부 피해구제·분쟁조정의 30일 기준을 플랫폼 내부 서비스 목표로 그대로 사용하지 않는다. 배달 음식은 시간 경과에 민감하고 증거 대부분이 서버에 있으므로 내부 판단은 외부 절차보다 훨씬 빠르게 제공한다.

### 내부 서비스 수준 확정

```text
이의 접수 즉시: 사건번호·접수 상태 자동 통지
24시간 이내: 담당자의 첫 응답
3영업일 이내: 통상 사건 최종 판단
7영업일 이내: 외부 통화·PG·장애 로그가 필요한 예외 사건 최종 판단
```

- 7영업일 연장은 한 번만 허용하고 3영업일 기한 전에 연장 사유·필요 자료·새 기한을 주문자에게 알린다.
- 단순 담당자 적체는 자동 연장 사유가 아니다.
- 플랫폼이 이미 보유한 로그 제출을 주문자에게 다시 요구하지 않는다.
- 기한 계산은 서버 달력과 정책 revision을 사용하며 휴일 정의를 판본화한다.
- 기한 초과 사건은 운영자 상향 queue에 들어가고 환급 준비금은 유지한다.
- 외부 한국소비자원 피해구제·분쟁조정·소송 절차의 기한과 권리는 이 내부 기한으로 축소하지 않는다.

### 수령자 부재 절편 기획 기준선 폐쇄

다음 기준을 하나의 기획 절편으로 닫는다.

1. 전달지 도착 뒤 최대 3회 연락과 통화 callback 증거
2. 안전하고 허용된 문 앞 전달 우선
3. 문 앞 전달 불가 시 고객센터 3분 응답 대기
4. 미응답 시 정책표 안의 기사 선택과 현장 폐기 우선
5. 처분 후 사진 1장·정책·보호 위치·서버 시각 증거
6. 기존 기사 수행대금 정상 지급과 예외 반환의 별도 배차
7. 확인된 주문자 부재의 주문 청구 유지
8. 플랫폼 복합 원인의 후보 규칙표와 사람 검토
9. 이의 중 조건부 환급 준비금과 내부 답변 기한

이 폐쇄는 구현 인계 준비 완료나 법률·PG·회계 승인 완료가 아니다. 실제 API·DB·앱·통화 중계 Adapter·권한·보존기간·약관·외부 제공자 계약을 대조한 수직 구현 명세가 별도로 필요하다.

## 문답·조사 r22 — 음식점 수락 후 주문자 취소의 단계별 비용 결속

### 새 절편 범위

다음 음식배달 사람 중심 결손은 `음식점 수락 후 주문자 취소`다. 음식점 수락은 조리 시작과 동일한 사건으로 간주하지 않는다. 주문자가 취소를 요청한 순간 다음 상태를 서버에서 원자적으로 동결한 뒤 허용 조작과 비용 원인을 계산한다.

| 축 | 동결 상태 후보 | 의미 |
| --- | --- | --- |
| 음식점 | `AcceptedPreparationNotStarted`, `PreparationStarted`, `PreparationCompleted` | 실제 조리·재료 투입 여부 |
| 기사 | `NoAcceptedAssignment`, `AcceptedEnRouteToMerchant`, `ArrivedAtMerchant`, `PickedUp` | 기사에게 이미 발생한 수행 의무와 이동 |
| 결제 | `Authorized`, `Captured`, `SettlementPending`, `RefundPending` | 환급·정산 쓰기 경로 |
| 취소 | `Requested`, `Quoted`, `Confirmed`, `Rejected`, `Expired` | 취소 요청과 금액 Preview·확정을 분리 |

취소 요청은 즉시 주문을 취소하지 않는다. 서버가 동결 사본과 정책 revision으로 `취소 가능 여부`, 주문자 예상 환급액, 음식점 보호금액, 기사 보호금액, 플랫폼 고객지원 부담 후보를 Preview하고 주문자가 금액을 확인한 뒤 확정한다. 예상 revision이 달라지면 오래된 Preview를 거절하고 다시 계산한다.

### 공식 기준 조사와 적용 경계

[전자상거래 등에서의 소비자보호에 관한 법률 제17조](https://law.go.kr/LSW/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1022341869)는 시간이 지나 다시 판매하기 곤란할 정도로 가치가 감소한 재화 등에 청약철회 제한 가능성을 두지만, 제한 사실을 소비자가 쉽게 알 수 있게 명확히 표시하도록 요구한다. 계약·공급 사실·시점이나 소비자 책임을 다투면 통신판매업자가 이를 증명해야 하며, 표시·광고 또는 계약과 다르게 이행된 경우의 권리는 별도로 보존된다.

따라서 내부 정책은 다음 경계를 따른다.

- 음식점의 `수락`만으로 조리 시작이나 환불 불가를 자동 확정하지 않는다.
- 조리 시작은 음식점 행위 기록·시각·주문 revision으로 증명한다.
- 주문 화면과 취소 Preview에 단계별 환불 제한과 근거를 사전 고지한다.
- 플랫폼·음식점 귀책, 표시·계약 불일치는 주문자 변심 취소와 분리한다.
- 일률적인 원가율이나 80% 공제를 근거 자료 없이 만들지 않는다.
- 법이 허용하는 손해배상·비용 범위와 실제 약관은 운영 전 법률 검토를 거친다.

### 조리 시작 뒤 기본 방향

조리가 시작된 뒤 주문자가 단순 변심·실수로 취소하면 주문자 책임을 기본 후보로 둔다. 음식점 상품대금은 실제 조리 단계와 승인 정책에 따라 보호하고, 기사에게 발생한 비용은 기사 상태별 별도 의무로 계산한다. 주문자에게 법적 근거 없이 임의의 원가율을 표시하지 않으며, 취소 불가 또는 제한 환급 후보와 근거를 Preview한다.

플랫폼이 실수 취소를 구제하려면 `CustomerCancellationSupportReserve`를 사용한다. 이는 음식점·기사 보호금액을 깎는 것이 아니라 플랫폼이 주문자에게 제공하는 별도 선의성 환급·쿠폰 비용이다. 13주 전망에는 다음을 포함한다.

- 기간별 준비금 상한과 사용액
- 주문당 지원 상한과 승인 역할
- 조리 단계·기사 단계별 평균 지원액
- 반복 신청 검토 건수와 사람 승인 비율
- 준비금 적용 전후 가용현금 최저점

반복 취소를 곧바로 사기로 확정하거나 개인 특성·지역·경제력을 지원 제외 근거로 사용하지 않는다. 정책 상한을 넘는 사건은 사람 검토 후보로 전환한다.

### 기사 단계 분리

- `NoAcceptedAssignment`: 기사 지급 의무가 아직 생성되지 않은 후보
- `AcceptedEnRouteToMerchant`: 이동이 시작된 기사 보호금액을 정해야 하는 현재 미정 분기
- `ArrivedAtMerchant`: 도착 사실과 현장 대기·취소 원인을 결속
- `PickedUp`: 수령자 부재 절편 또는 취소 후 처분 절편과 연결

기사 단계와 음식점 조리 단계는 서로 독립 축이다. 조리는 시작됐지만 기사 미배정일 수 있고, 기사는 이동 중인데 조리 미시작일 수도 있으므로 하나의 주문 상태 문자열로 합치지 않는다.

## 문답·조사 r23 — 조리 미시작 전액 환불과 타 플랫폼 비교

### 확정된 조리 미시작 분기

음식점이 주문을 수락했더라도 취소 요청의 서버 동결 사본이 `AcceptedPreparationNotStarted + NoAcceptedAssignment`라면 주문자에게 전액 환불한다. 음식점 보호금액과 기사 수행대금은 만들지 않으며, 승인만 된 결제는 승인 취소하고 이미 매입된 결제는 전액 환급 의무로 전환한다. 근거가 없는 결제·플랫폼 실비를 주문자에게 별도로 공제하지 않는다.

취소 요청과 조리 시작이 경합하면 서버가 먼저 수락한 사건과 예상 revision으로 판정한다. 취소 요청이 먼저 수락된 뒤 음식점이 조리 시작을 소급 입력해 전액 환불을 막을 수 없다. 반대로 조리 시작 사건이 먼저 수락됐다면 아래의 조리 시작 뒤 분기로 진입한다. 플랫폼 장애로 취소 요청 전달이 늦어져 음식점이 조리를 시작한 경우에는 주문자 단순 변심이 아니라 플랫폼 귀책 후보로 분리한다.

### 조리 시작 뒤 설계 방향

- `PreparationStarted` 뒤 주문자 단순 변심은 자동 전액 환불 대상에서 제외하되, 곧바로 일률적인 환불 불가로 확정하지 않는다.
- 음식점 보호금액은 주문 금액, 실제 조리 시작 사건, 메뉴의 재판매 가능성, 사전 고지와 정책 revision을 근거로 Preview한다. 임의 원가율은 사용하지 않는다.
- 음식점 또는 플랫폼 귀책, 품절, 표시·계약 불일치, 잘못된 조리 시작 기록은 주문자 단순 변심과 분리하고 주문자 보호를 우선한다.
- 조리 시작 사건은 행위자·서버 수락시각·주문 revision·근거를 남기며 뒤늦은 소급 입력을 허용하지 않는다.
- 음식점 보호가 필요한데 플랫폼이 주문자를 선의성으로 구제하면 음식점 보호금액을 감액하지 않고 `CustomerCancellationSupportReserve`가 별도 부담한다.
- 실제 대외 약관과 환급·정산 산식은 법률·PG·회계 검토 전까지 Simulation 정책 후보로만 둔다.

## 문답 r24 — 가게 도착 전 취소수행대금 보장

기사가 유효한 배차 제안을 수락한 뒤 음식점으로 이동 중인데 기사 귀책 없이 주문자가 취소하면, 가게 도착 전이라도 `취소수행대금`을 지급한다. 이는 완료 수행대금의 일부를 사후 임의로 떼어 주는 것이 아니라 배차 제안 시점에 기사에게 별도로 고지하고 수락과 함께 동결하는 보호 의무다.

- 지급 조건은 `유효한 배차 수락 + 취소 확정 시점에 수행 활성 + 기사 귀책 없음`이다.
- 취소 요청만 접수되고 최종 취소되지 않았다면 지급 의무를 확정하지 않는다.
- 같은 배차 시도와 취소 사건에는 취소수행대금을 한 번만 생성하고 멱등 식별자로 중복 지급을 막는다.
- 취소수행대금은 음식값 환불, 음식점 보호금액, 정상 완료 수행대금과 별도 원장에 기록한다.
- 주문자 변심, 플랫폼 장애, 음식점 취소 등 원인에 따라 최종 부담 주체는 달라질 수 있지만 기사 지급 자체를 책임 검토 종료까지 보류하지 않는다.
- 기사 앱과 운영자 Preview에는 금액·지급 사유·부담 주체 검토 상태·정산 예정 상태를 구분해 표시한다.
- Unity에는 보호 지급 결과의 일반화된 상태 사본만 제공하며 실제 지급 권위는 서버 재무 원장에 둔다.

## 문답 r25 — 완료 수행대금 우선 표시와 취소 건 상세

배차 제안·수락 화면의 주 금액은 `배달 완료 시 받을 수행대금` 하나만 표시한다. 취소수행대금을 완료 수행대금과 나란히 전면 표시해 기사 선택을 복잡하게 만들지 않는다. r24의 `배차 제안 시 취소수행대금을 별도 고지한다`는 화면 표현은 이 판본으로 대체한다.

취소가 실제 확정된 배차 건에만 수행내역의 `취소 건 상세보기`를 연다. 상세보기에는 다음을 표시한다.

- 원래 배차 수락시각과 완료 예정 수행대금
- 취소 요청·확정시각과 취소 원인 코드
- 취소 시점의 기사 단계: 수락 직후·음식점 이동 중·음식점 도착·픽업 뒤
- 적용된 취소수행대금 정책 이름·판본
- 산정 요소와 최종 취소수행대금
- 지급 확정·정산 예정·지급 완료 상태
- 주문자·플랫폼·음식점 중 최종 부담 주체의 확정 또는 검토 중 상태
- 문의 또는 이의제기 조작

취소 전에는 개별 주문의 가상 취소금액을 보여주지 않지만, 기사 앱의 일반 정책 화면에서는 취소수행대금이 지급되는 조건과 산정 원칙을 언제든 확인할 수 있게 한다. 실제 취소 뒤에는 당시 정책 revision과 입력값을 동결해 이후 정책 변경으로 과거 상세가 달라지지 않게 한다. 기사 위치의 원시 궤적이나 주문자의 개인정보는 상세 산정 설명에 노출하지 않는다.

## 문답 r26 — 취소수행대금 단계별 정액

취소수행대금은 실시간 이동거리·GPS 궤적·초 단위 경과시간을 사후 계산하지 않고, 취소 확정 순간 서버가 확인한 수행 단계별 정액으로 산정한다.

| 수행 단계 | 판정 근거 | 취소수행대금 후보 |
| --- | --- | --- |
| `AssignmentAcceptedBeforeDeparture` | 배차 수락은 확정됐지만 출발·이동 근거 없음 | 수락·기회비용을 보호하는 첫 정액 |
| `EnRouteToMerchant` | 음식점 방향 이동 시작 사건이 서버에 수락됨 | 이동 부담을 반영한 두 번째 정액 |
| `ArrivedAtMerchant` | 음식점 도착 사건과 허용 위치 범위가 확인됨 | 현장 도착 부담을 반영한 세 번째 정액 |
| `PickedUp` | 음식 수령이 확정됨 | 이 표의 가게 도착 전 취소가 아니라 픽업 후 별도 처리 절편 |

- 단계는 기사 앱 버튼 하나만 믿지 않고 배차 상태·서버 시각·허용 위치 범위·주문 revision을 함께 검증한다.
- GPS 원시 궤적은 단계 사실 확인에 필요한 보호 자료일 수 있지만 금액을 미터 단위로 증감하는 산식에는 사용하지 않는다.
- 취소 요청 시점이 아니라 취소가 서버에서 확정된 시점의 유효 수행 단계를 사용한다. 다만 플랫폼 처리 지연으로 단계가 올라간 경우에는 지연 귀책을 별도로 검토한다.
- 같은 단계는 같은 정책 판본에서 같은 금액을 산출하며 운영자나 고객센터가 사건별로 임의 금액을 바꾸지 못한다.
- 정책 변경은 새 배차부터 적용하고 이미 수락된 배차와 확정된 취소 건은 당시 정책 revision을 유지한다.
- 정확한 원화 정액은 기사 계약·시장 자료·회계 검토 전까지 확정하지 않고 Simulation 범위값으로 13주 현금 영향을 비교한다.

## 문답 r27 — 수행 진척에 따른 단계별 금액 상승

픽업 전 취소수행대금은 `배차 수락 직후 < 음식점 이동 중 < 음식점 도착` 관계로 높아진다. 배차 수락으로 다른 주문 기회를 포기한 단계부터 최소 정액을 보장하고, 이동과 현장 도착이라는 확인된 수행이 추가될 때만 다음 정액을 적용한다.

- 각 단계의 정확한 원화 금액과 차액은 정책 판본이 소유한다.
- 단계 간 금액은 같거나 역전되지 않으며 `AcceptedAmount < EnRouteAmount < ArrivedAmount` 불변식을 검증한다.
- `ArrivedAmount`는 픽업과 전달을 완료했을 때의 정상 수행대금을 넘지 않는다.
- 운영자·고객센터가 개별 사건에서 더 낮은 단계로 소급하거나 금액을 임의 감액할 수 없다.
- 잘못 기록된 단계는 원본 사건을 덮어쓰지 않고 정정 사건과 승인 근거를 남긴다.
- Simulation은 낮음·기준·높음 정책 범위로 13주 총 취소수행대금, 가용현금 최저점, 단계별 기사 보호 비중을 비교한다.

## 문답 r28 — 픽업 후 취소의 정상 수행대금 보장

음식 픽업이 서버에서 확정된 뒤 기사 귀책 없이 주문자가 취소하면, 기사에게 배차 수락 때 확정된 정상 수행대금 전액을 지급한다. 이 단계부터는 픽업 전 `취소수행대금` 표를 적용하지 않는다.

- 지급 조건은 유효한 픽업 확정 사건, 취소 확정, 기사 비귀책이다.
- 주문자 환급 여부, 음식점 보호금액, 음식의 최종 처분이 미정이어도 기사 지급 의무를 먼저 확정한다.
- 배달이 중단돼 실제 전달 완료 사건은 만들지 않더라도 재무 원장에는 `PostPickupCancellationProtectedPay` 원인을 남긴다.
- 정상 완료 건과 같은 금액을 지급하되 운영 지표에서는 정상 전달 완료와 취소 보호 지급을 구분한다.
- 이 지급을 정상 배달 완료율이나 기사 완료 건수로 부풀리지 않는다.
- 취소 귀책에 따른 최종 부담은 주문자·플랫폼·음식점 책임 원장에서 후속 판정하며 기사 대금과 상계하지 않는다.
- 픽업 후 음식 반환·안전한 현장 폐기·전달 중단은 기사 대금과 분리된 처분 사건으로 관리한다.

## 문답 r29 — 픽업 후 현장 폐기와 Food·Cargo OS 회수 경계

픽업 후 주문자 취소가 확정된 일반 조리 음식은 전달을 중단하고 `FoodDeliveryOS`의 판본화된 안전 정책표에 따라 현장 폐기를 기본으로 한다. 처분 사진 1장과 정책·일반화 위치·서버 시각을 수락한 뒤 기사 수행을 보호 종료하고 다음 배차 후보로 복귀시킨다.

법적·계약상 회수 의무는 두 OS에서 같은 강도로 취급하지 않는다.

| 구분 | `FoodDeliveryOS` | `CargoDeliveryOS` |
| --- | --- | --- |
| 주 대상 | 즉시 소비하는 조리 음식 | 회수·반환·인계 가치가 지속되는 화물 |
| 픽업 후 취소 기본 | 전달 중단 뒤 안전한 현장 폐기 | 계약·품목 지시에 따른 회수·반환·지정 인계 |
| 반환의 위치 | 명시된 회수 예외만 별도 반환 배차 | 계약 이행의 주요 정상·예외 분기 |
| 기사 조작 | 정책표가 연 `DisposeOnSite` 또는 명시적 `ReturnToMerchantDispatch` | 운송계약이 연 `Return`, `Recover`, `AlternateHandover` 후보 |
| 증거 | 처분 사진·정책 revision·서버 수락 | 인수·반환·보관 상태·서명 또는 사진·계약 revision |
| 재무 | 정상 수행대금 보호, 예외 반환은 새 배차 | 원 운송·회수·반환 의무와 계약별 대금 |

- 음식배달 주문을 취소 뒤 화물배달 건으로 몰래 재분류하지 않는다.
- 공통화는 처분 사건 식별자·revision·증거 hash·감사 기록 같은 기술 봉투까지만 허용한다.
- 회수 여부, 허용 조작, 기사 대금과 완료 의미는 각 OS의 정책과 계약이 소유한다.
- `FoodDeliveryOS`의 반환 예외는 주문 생성 또는 픽업 전에 명시된 근거가 있어야 하며 고객센터의 사후 자유 문장만으로 새 회수 의무를 만들지 않는다.
- `CargoDeliveryOS`의 강한 회수 의무를 음식배달의 일반 조리 음식에 자동 상속하지 않는다.
- 두 OS 모두 기사 개인 보유·소비·재판매·제3자 양도를 기본 조작으로 열지 않는다.

## 문답·조사 r30 — 역할 집중형 정상 흐름과 내부 예외 내규

### 정상 흐름 우선 원칙

제품의 기본 경험은 예외 정책 운용이 아니라 각 역할의 본업에 집중한다.

- 주문자는 주문하고 음식점 수락·조리·배차·픽업·배달·완료 진행을 관찰한다.
- 음식점은 주문 확인·수락·조리·포장·기사 인계에 집중한다.
- 기사는 배차 확인·음식점 이동·픽업·전달·완료에 집중한다.
- 운영자는 정상 흐름을 상시 감시하되, 취소·수령자 부재·회수·폐기·분쟁 같은 예외가 발생했을 때만 관련 정책 카드와 허용 조작을 연다.

반환·회수·폐기 규칙은 `선의 내규`를 포함한 내부 운영 정책으로 판본화할 수 있지만 정상 화면의 주 흐름으로 노출하지 않는다. 다만 주문자에게 불리한 취소·환불 제한이나 비용은 단순히 내부 규정이라는 이유로 숨기지 않고 주문·취소 확인처럼 결정에 필요한 시점에 이해 가능한 문장으로 고지한다.

### 소비자분쟁해결기준 대조

[현행 소비자분쟁해결기준](https://law.go.kr/admRulLsInfoP.do?admRulSeq=2100000270136)은 2025년 12월 18일 시행된 공정거래위원회고시 제2025-14호다. 이 기준은 분쟁당사자 사이의 원활한 해결을 위한 구체적인 합의 또는 권고 기준이며, 플랫폼 내부 규칙을 자동 승인하거나 개별 사건의 법적 결론을 확정하는 인증표가 아니다.

2025년 개정의 외식업 관련 주요 내용은 음식점 예약 취소·예약부도와 사전 고지 기준 정비다. 이를 배달 주문 취소의 고정 환급률로 그대로 옮기지 않는다. [일반적 소비자분쟁해결기준](https://www.law.go.kr/LSW/flDownload.do?flNm=%5B%EB%B3%84%ED%91%9C+1%5D+%EC%9D%BC%EB%B0%98%EC%A0%81%EC%86%8C%EB%B9%84%EC%9E%90%EB%B6%84%EC%9F%81%ED%95%B4%EA%B2%B0%EA%B8%B0%EC%A4%80%5B%EC%A0%9C8%EC%A1%B0%EC%A0%9C2%ED%95%AD%EA%B4%80%EB%A0%A8%5D%0A&flSeq=36143637)은 사업자 귀책 피해의 수리·교환·환급·배상과 계약 이행, 거래가격 증명, 사업자 귀책 처리비용 부담 등의 공통 원칙을 둔다.

따라서 예외 내규는 다음 준법 대조표를 가진다.

| 항목 | 필수 기록 |
| --- | --- |
| 기준 판본 | 소비자분쟁해결기준 시행일·고시 번호, 전자상거래법과 적용 약관 판본 |
| 적용 범위 | 음식배달 주문 취소·품질·오배달·지연·미수령 중 어떤 사건인지 |
| 귀책 구분 | 주문자·음식점·기사·플랫폼·외부 원인과 근거 |
| 소비자 효과 | 환급·재조리·재배달·배상·비용과 사전 고지 위치 |
| 역할 보호 | 음식점 보호금액·기사 대금과 소비자 환급의 분리 여부 |
| 이의 절차 | 담당자, 답변 기한, 증거 열람, 1372·한국소비자원 등 외부 절차 안내 |
| 검토 상태 | 내부 후보·법률 검토 완료·운영 승인·폐기 및 대체 판본 |

- 현행 기준이나 법령과 충돌 가능성이 있으면 내규 자동 적용을 중단하고 사람 검토로 보낸다.
- 소비자에게 더 불리한 내부 내규를 `선의`라는 이름만으로 정당화하지 않는다.
- 분쟁 기준이 직접 규정하지 않은 배달 취소 세부 단계는 전자상거래법·약관·실제 손실·귀책·사전 고지를 함께 검토한다.
- 기준 개정 시 새 사건부터 새 판본을 적용하고 과거 사건의 당시 근거와 결과는 보존한다.
- 정상 주문 진행 화면에는 준법 대조표 전체를 노출하지 않고 예외 발생 시 관련 근거·금액·이의 조작만 역할별로 제공한다.

## 문답 r31 — 주문자 핵심 7단계와 예외 카드

주문자의 정상 주문 화면은 다음 핵심 7단계 타임라인을 사용한다.

`주문 접수 → 음식점 수락 → 조리 중 → 기사 배정 → 픽업 → 배달 중 → 완료`

- 각 단계는 서버가 수락한 권위 사건에서 파생하며 앱의 임의 로컬 전환으로 확정하지 않는다.
- 현재 단계, 완료된 단계, 다음 예상 단계만 먼저 보여주고 내부 원장·정책·재무 상태를 정상 타임라인에 섞지 않는다.
- 예상 조리·픽업·도착 시각은 범위로 표시하고 확정 약속처럼 표현하지 않는다.
- 동일 단계 안의 세부 사건은 접근성 설명이나 상세보기에서만 제공한다.
- 지연·취소·재조리·재배차·환급처럼 주문자의 이해나 선택이 필요한 문제가 실제로 발생했을 때만 예외 카드를 연다.
- 예외 카드는 원인, 현재 영향, 예상 변경 시간, 주문자가 지금 할 수 있는 조작, 환급·비용 Preview와 문의 경로를 제공한다.
- 해결된 예외 카드는 정상 타임라인을 막지 않고 이력으로 접되, 분쟁·증거 보존 대상은 서버 원장에 유지한다.
- Unity 디오라마는 같은 상태 사본으로 음식점 조리·기사 이동·전달을 관찰 표현할 수 있지만 주문 상태를 변경하지 않는다.

## 개발 인계 r32 — 서버 우선 수직 절편 계획

[현행 개발계획 r33](development-handoff.r33.md)에서 다른 GPT 계정이 구현을 이어갈 수 있도록 현재 코드 기준선, 재사용 경로, 미정 정책의 중단 관문, 8개 단계와 검증 조건을 고정했다. 최초 계획은 r32에서 만들었고 r33에서 실시간 기사 위치 결정을 반영했다.

- 첫 절편은 기존 수명주기 조회와 주문자 공통 UI를 재사용하는 `주문자 7단계 타임라인 읽기 모델`이다. 기사 위치 공개와 정확 금액 없이 시작할 수 있다.
- 후속 절편은 `수락 후 취소 Preview·확정 → 조리 지연 보호 해제·재배차 → 수령자 부재 보호 종료 → 역할 앱 예외 카드 → 13주 운영·현금 Simulation → Unity 읽기 전용 관찰 → 정책·카드 확장` 순서다.
- 서버 업무 사실, Simulation 결과, Unity 표현은 서로 다른 완료 증거로 보고한다. Unity는 공식 `SimulationWorldShell` 하나를 유지하고 업무 Command 권위를 갖지 않는다.
- 취소수행대금 원화 금액, 음식점 보호금액, GPS 세부 품질 기준, 실제 통화 제공자, 증거 보존기간과 운영 행정동 범위는 구현자가 정하지 않는다. 필요한 기능은 정책 revision과 비활성 기본값 또는 Simulation Fixture까지만 준비한다.
- 이 인계는 작은 절편의 개발 준비를 의미하며 실제 운영 활성, 법률·PG·회계 승인, 전체 묶음 일괄 구현이나 E 자동 승격을 의미하지 않는다.

## 문답 r33 — 주문자 실시간 기사 위치

주문자에게 현재 주문을 수행 중인 기사의 위치를 실시간으로 보여주는 방향을 확정한다. 기사 앱 또는 운행 단말이 GPS 관측을 서버에 전송하고, 서버가 유효한 배차·주문 소유권·위치 최신성을 확인한 뒤 주문자 조회와 실시간 채널로 전달한다. 기사 단말이 주문자 단말에 직접 위치를 보내지 않는다.

- 공개 구간은 기사가 유효한 배차를 수락한 시점부터 픽업 이동·배달 이동을 거쳐 전달 완료, 주문 취소, 배차 보호 해제 또는 다른 기사로 교체되기 전까지다.
- 주문자는 본인 주문의 현재 수행 기사 위치만 볼 수 있다. 운영자·음식점·다른 주문자에게 같은 공개 권한이 자동으로 생기지 않는다.
- 주문자 화면은 서버가 마지막으로 수락한 현재 위치, 마지막 갱신시각, 최신성 상태와 예상 도착 범위를 표시한다. 새 GPS가 끊기면 추측 위치를 실제 위치처럼 이동시키지 않고 `위치 갱신 지연`과 마지막 갱신시각을 표시한다.
- 주문자 API와 실시간 채널은 현재 표시용 위치만 제공한다. 주문 완료·취소·배차 종료 뒤 구독을 즉시 닫고 과거 원시 GPS 궤적 전체를 주문자에게 제공하지 않는다.
- 서버 보호 원장은 운영상 필요한 원시 관측을 별도 권한·보존정책·접근 감사 아래 둘 수 있다. 주문자 화면 공개와 내부 보호 보존은 같은 권한이나 보존기간으로 간주하지 않는다.
- 기사 앱은 백그라운드·권한 거부·오프라인·정확도 저하를 구분해 전송하고, 서버는 오래되거나 정확도가 기준 이하인 관측을 현재 위치로 승격하지 않는다.
- Unity 관찰 세계에는 실제 기사 개인의 원시 GPS를 직접 흘리지 않는다. 운영 주문 관찰 프로필이 필요하면 서버가 승인한 현재 위치 사본을 해당 주문의 표현 좌표로 투영하며, 가상 NPC 위치와 실제 기사 위치를 같은 권위로 혼합하지 않는다.
- 정확한 전송 주기, 위치 정확도 하한, stale 판정 시간, 지도 스냅 방식과 보호 원장 보존기간은 성능·배터리·법률 검토를 거쳐 설정 판본으로 확정한다. 이는 실시간 위치 공개 방향 자체를 다시 여는 질문은 아니다.

## 문답·조사 r34 — 회계사 역할과 기준중립 관리계정

[회계사 역할·원장 r34](accountant-role-and-ledger.r34.md)에 음식배달 업무의 돈 흐름을 계정별로 설명하고 13주 운영을 조언하는 가상 회계사 역할을 추가했다.

- 돈의 흐름은 `업무 사건 → 재무 사건 → 기준중립 관리계정 → 회계 매핑 후보 → 회계사 승인 판본`으로 연결한다.
- 관리계정은 가용현금, 제한자금, PG미수, 음식점·기사·지사 지급의무, 고객 환급의무, 조건부 환급 준비금, 플랫폼 수익 후보와 비용 후보를 분리한다.
- 기사 정상 수행대금과 취소수행대금은 분석용 하위계정을 나누되 같은 기사 지급의무 계보를 사용한다. 음식점 정산·고객 환급과 자동 상계하지 않는다.
- 고객 총 결제액을 플랫폼 매출로 자동 기록하지 않는다. 플랫폼이 각 재화·용역의 본인인지 대리인인지와 수행의무 이행 시점을 계약 사실과 적용 회계기준으로 검토한다.
- `ConditionalCustomerRefundReserve`는 내부 현금 방어 관리계정이며 회계사 승인 없이 외부 회계상 충당부채나 비용으로 전표화하지 않는다.
- 회계사 역할은 13주 현금 최저점, 지급 예정, 주문당 기여금, 취소·환급 정책 영향, PG 지연 민감도, 미대사·미매핑 거래를 보고 운영자에게 조언한다.
- 회계사 조언은 원장 revision·계정 매핑 판본·가정·불확실성을 포함한다. 조언 카드나 NPC 말이 실제 전표·지급·환급·세무신고를 확정하지 않는다.
- 회사에 적용할 회계기준, 실제 계정과목, 총액·순액 수익 표시, 부가가치세와 세무 처리는 실제 회계사가 검토한 승인 판본에서만 확정한다.

## 조사·기획 r35 — 회계 운영관습과 13주 전망 결합

[회계 운영관습 r35](accounting-operating-conventions.r35.md)는 공식 회계기준·OpenDART 공시 계정체계·국세청 신고주기를 조사하고, 프로젝트 내부 운영에 다음 관습을 반영한다.

- 업무 발생, 실제 현금 이동, 회계 보고 기간을 서로 다른 시간축으로 기록한다.
- 회계 순환은 `업무 Event → 증빙 → 재무 사건 → 분개 후보 → 보조원장 → 대사 → 시산표 → 마감 검토 → 조정·역분개 → 승인 보고` 순서를 따른다.
- 정상 거래는 자동 대사·기본 매핑으로 조용히 처리하고, 미대사·증빙 누락·중복·미승인 계정·현금 부족·중요 추정 변경만 회계사 판단 카드로 올린다.
- 일마감은 은행·PG·주문·기사·음식점 원장을 대사하고, 주마감은 13주 전망을 한 주 앞으로 이동한다.
- 월마감은 cutoff·미수·미지급·조정분개·시산표를 검토하고, 분기마감은 3개월 실적·예산·전분기 비교와 중요 회계판단을 정리한다.
- 부가가치세의 6개월 과세기간·3개월 예정 구간은 1~4분기 경영보고와 별도 `ComplianceCalendarRevision`으로 관리한다. 사업자 유형에 따른 신고 방식은 실제 세무 검토 전 확정하지 않는다.
- 13주 전망은 91일 이동 전망으로 유지한다. 분기 경계를 지나도 초기화하지 않고 실제 실적을 전망의 actual로 치환해 예측오차를 남긴다.
- 관리계정 Stable ID를 DART/XBRL 계정으로 직접 대체하지 않는다. 적용 회계기준과 공시 의무가 확정된 뒤 승인 매핑으로 연결한다.
- 마감 상태는 `Open → SoftClosed → AccountantReview → Closed → ReopenedWithReason`이며 과거 값을 조용히 덮어쓰지 않는다.
- 작은 조직에서 한 사람이 작성·검토·승인을 겸하더라도 역할을 기록하고 `RoleCombined`로 드러낸다.

## 문답 r36 — 운영자 통합 회계

[운영자 통합 회계 r36](operator-integrated-accounting.r36.md)은 회계사 전용 앱·화면·상위 메뉴를 만들지 않고 회계를 운영자 통합 화면의 한 관점으로 결합한다.

- `회계사 역할`은 별도 업무 화면이 아니라 재무 사건 분류, 대사, 중요 판단과 승인 판본을 남기는 내부 역할·권한·검토 계보다.
- 운영자는 주문·기사·권역 상황과 함께 가용현금, 지급의무, 13주 최저점, 미대사·마감 위험을 같은 화면에서 본다.
- 정책 Preview는 처리량·지연뿐 아니라 현금·지급의무·관리계정 영향을 같은 revision으로 반환한다.
- 정상 거래는 자동 대사·기본 매핑으로 조용히 처리한다. 미대사·현금 부족·미승인 매핑·마감 후 수정 같은 예외만 운영자 확인이나 회계사 검토로 올린다.
- 계정과목·차변·대변·증빙 hash·본인/대리인 판단은 기본 화면이 아니라 필요할 때 여는 상세 영역에서 제공한다.
- 외부 회계사 검토는 별도 앱을 만들지 않고 기간·source revision·hash·미정 항목을 가진 검토 묶음과 의견 회신으로 연결한다.

## 문답 r37 — 상단 회계 요약과 운영자 용어

[운영자 회계 요약 r37](operator-integrated-accounting-summary.r37.md)은 통합 화면의 상단 고정 지표와 표시 용어를 확정한다.

- 상단에는 `가용현금`, `향후 7일 지급의무`, `13주 현금 최저점`, `정산 확인 필요` 네 지표를 항상 표시한다.
- 운영자 화면에서는 `미대사 위험 건수`라는 표현을 사용하지 않는다.
- `정산 확인 필요`는 오류 확정이 아니라 주문·PG·은행·기사·음식점·환급 기록을 서로 맞춰 보아야 하는 미해결 사건 수다.
- 내부 계약·코드는 호환 가능한 `ReconciliationException` 분류를 유지하고, 회계 감사 자료에서는 `미대사`·`대사 차이`라는 전문 용어를 사용할 수 있다.
- 선택하면 같은 운영자 화면의 상세 영역에서 원인별 건수·영향 금액·경과시간·담당자·가능한 조작을 보여준다.

## 문답 r38 — 정상 자동화와 예외 우선 확인 주기

[예외 우선 재무 확인 r38](exception-first-financial-review.r38.md)은 정상 경로를 자동화하고 운영자가 예외와 정기 결산에 집중하는 구조를 확정한다.

- 정상 주문·정산·지급은 자동 집계·대사하며 운영자에게 건별 승인을 요구하지 않는다.
- `정산 확인 필요` 사건은 관련 주문·지급·환급만 격리하고 나머지 정상 업무는 계속한다.
- 운영자는 예외를 수시 확인하고 정상 경로는 `매주 정산`, `매월 운영 결산`, `13주 종합 점검`에서 요약으로 검토한다.
- 13주 이동 전망은 매주 갱신한다. 13주마다 하는 종합 점검은 누적 actual, 예측오차, 서비스 수준과 다음 13주 정책·현금 방어선을 깊게 재검토하는 별도 절차다.
- 시스템의 자동 일마감은 유지하지만 기준 안의 정상 일마감을 운영자가 매일 승인할 필요는 없다.
- 주간·월간·13주 조회는 같은 운영자 통합 화면의 기간별 보기이며 별도 회계 앱이 아니다.

## 문답 r39 — 주간 정산 요약 단순화

[주간 정산 요약 r39](weekly-settlement-summary.r39.md)은 주간 마감 결과에서 `정산 완료율`을 제거한다.

- 기본 항목은 `이번 주 정산 총액`, `정산 후 가용현금`, `정산 확인 필요` 세 가지다.
- 정상 건별 목록은 기본적으로 숨기고 감사·문의·표본 확인 때만 상세 조회한다.
- 정산 처리 중에는 완료율 대신 현재 상태, 시작시각, 예상 다음 확인시각과 중단 사유를 표시한다.
- 정산 총액은 기사·음식점·지사·고객 환급 하위 합계로 추적할 수 있지만 플랫폼 수익과 통과 자금을 섞어 매출처럼 표현하지 않는다.

## 문답 r40 — 월간 전월 실적 비교와 서원

[월간 실적·서원 r40](monthly-performance-and-vow.r40.md)은 객관적인 결산 비교와 운영자의 게임적 방향을 분리한다.

- 월간 수치 비교는 `이번 달 실적 ↔ 전월 실적`만 사용한다.
- `월초 계획`이나 계획 달성률은 기본 회계 비교에 넣지 않는다.
- 운영자는 월초에 “이번 달에는 이 방향을 지켜 보겠다”는 비구속 `서원`을 선택할 수 있다.
- 서원은 예산·외부 계약·성과평가·배차 우선순위·자동 보상·불이익 근거가 아니다.
- 월말에는 전월 실적 비교와 서원 회고를 분리해 보여주며, 서원은 `지킴 / 일부 지킴 / 이어서 살핌`으로 돌아본다.
- 서원 자체는 돈이나 업무 상태를 바꾸지 않는다. 실제 정책 효과는 별도 Preview·확정과 Simulation revision으로 추적한다.

## 문답 r41 — 안정 운영 서원과 기본정책 묶음

[안정 운영 서원·정책 r41](stable-operations-vow-policy.r41.md)은 기본 서원에 실제 운영 안전선이 존재해야 한다는 기준을 확정한다.

- 운영자가 별도 서원을 고르지 않으면 `안정 운영 유지`를 기본 서원으로 둔다.
- 기본 서원은 지급의무 보호·가용현금 방어선·정상 경로 자동화·예외 격리·서비스 안전선·알림/인센티브 상한·미승인 실험정책 금지를 묶은 승인 정책 판본을 참조한다.
- 서원 선택 자체가 정책을 활성화하지 않는다. 정책은 별도 권한·Preview·승인·활성화 절차를 거쳐야 한다.
- 정확한 현금 하한·서비스 임계값·알림 빈도·인센티브 금액이 미정이면 운영값을 발명하지 않고 Simulation 범위값 또는 비활성 상태를 유지한다.
- 유효한 정책 판본이 없으면 `안정 운영 유지`를 성공 상태처럼 표시하지 않고 `정책 기준 미확정`으로 드러낸다.
- 아르카나·주역 카드도 기본 안전선을 우회할 수 없다.

## 문답 r42 — 사가정역·면목제3·8동 생활상 기준

[사가정·면목3·8 생활상 기준 r42](sagajeong-myeonmok38-living-pilot.r42.md)은 발전한 사가정역 디오라마를 보존하면서 행정동 권위와 생활상 보완 순서를 결속한다.

- `station:kr:kric:s1107:0722`의 기존 1km × 1km 디오라마를 첫 생활상 관찰 창과 시각 회귀 기준으로 유지한다.
- `region:kr:hjd:1126057500` 면목제3·8동을 첫 운영·집계 권위로 확정한다.
- 면목제7동 등 관찰 창과 겹치는 행정동은 계속 보이게 하되 자기 행정동 귀속을 유지하고 면목제3·8동 집계에 복제하지 않는다.
- 현행 화면 보존, 공식 경계 결속, 주소·필지·출입구, 이동 표면·신호 관계, 사업장·건물 역할, 생활 업무, 운영·재무, 실제 Game View 순으로 결손을 닫는다.
- 첫 생활 업무는 같은 `WorkStableId`와 revision으로 이어지는 합성 음식배달 정상 7단계를 추천한다. 실제 사람·주문·결제·배차 권위는 열지 않는다.
- Graph Map에는 기존 노드를 재사용하는 관계 후보만 넘기며 검토 전 통합됐다고 보고하지 않는다.
- 기존 안정 운영정책 안전선의 자동 차단·경고 구분 질문은 폐기하지 않고 정책 관문으로 계속 보존한다.

## 문답 r43 — 사가정 점심 정상 배달 1건

[사가정 점심 정상 배달 r43](sagajeong-lunch-normal-delivery.r43.md)은 첫 실제 Game View 판독 장면을 예외가 없는 정상 음식배달 1건으로 확정한다.

- 면목제3·8동 귀속이 확인된 음식점 역할 건물 하나, 합성 기사 한 명, 전달지 역할 건물 하나를 사용한다.
- 주문 접수부터 전달 완료까지 정상 7단계를 같은 `WorkStableId`·revision으로 표현한다.
- 실제 상호명·개인·주문·결제·GPS는 사용하지 않고 기존 사가정 화면을 보존한다.
- 검증된 이동 graph가 없는 구간을 실제 도로 주행처럼 표시하지 않는다.
- 정상 절편을 먼저 닫은 뒤 조리 지연·보호 재배차·수령자 부재를 별도 후속 절편으로 연다.

## 문답 r44 — 면목제3·8동 건물 우선과 이동 결손 표현

[면목3·8 건물 우선 이동 r44](myeonmok38-building-first-movement.r44.md)는 생활상 이동 전에 현행 면목제3·8동 대상 건물을 가능한 한 모두 실자료 기반으로 준비하는 원칙을 확정한다.

- 현행 경계 안 모든 대상 건물을 실자료 기반 표현 또는 명시적인 `MissingCoverage`로 판정한다.
- 데이터 기반 건물은 검증된 윤곽·행정동 귀속·높이 근거를 기본으로 하고 주소·PNU·출입 기준점의 상태를 따로 보존한다.
- 검증된 출발·도착 건물과 연결 구간에서만 Actor 경로 이동을 허용한다.
- 자료가 없거나 이동망이 끊긴 구간은 임의 보간하지 않고 `이동 중` 상태와 마지막 확인시각으로 표현한다.
- 새 건물 판본이 완전한 판정 집합과 회귀 검증을 갖추기 전 기존 사가정 화면을 일괄 교체하지 않는다.

## 문답 r45 — 공공자료 매스와 중요 건물 Blender 상세화

[면목3·8 공공자료 매스·Blender 상세화 r45](myeonmok38-public-mass-blender-detail.r45.md)는 사가정역과 같은 공공데이터 기반 매스를 면목제3·8동 전수 건물의 첫 표현으로 확정한다.

- 실제 외관 모델을 기다리지 않고 검증된 윤곽·높이 근거·안정 식별자를 가진 절차적 매스를 먼저 만든다.
- 높이 자료가 없는 건물은 일반화 높이임을 명시하고 실제 높이처럼 설명하지 않는다.
- 역·시장·아파트·공공시설 등 중요한 건물만 외관 근거와 이용조건 확인 뒤 Blender로 점진 상세화한다.
- Blender 교체는 같은 건물의 `VisualRoot`만 바꾸며 주소·PNU·행정동·역할·출입 기준점·업무 revision을 유지한다.
- 다른 지역 외관을 대체 자료로 사용하거나 상세 모델을 업무 권위로 해석하지 않는다.

## 문답 r46 — 사가정역 우선과 기존 Blender 기획 통합

[사가정역 Blender 기획 결속 r46](sagajeong-station-blender-binding.r46.md)은 첫 상세화 묶음을 사가정역 출구 주변으로 확정하고, [역세권 기획 r30](../PLAN-SYSTEM-STATION-AREA-DIORAMA-MODULES/sagajeong-station-blender-integration.r30.md)에 기존 기획을 통합했다.

- r8의 안전 교체·fallback, r9의 사진/파생 모델 권리 분리, r11의 사진 원장, r26의 출구 1~4 위치·번호 기준점을 재사용한다.
- 운영자 Simulation은 승인된 `VisualKey`와 안정 식별자만 소비하며 별도 사진·Blender·Prefab 대장을 만들지 않는다.
- 출구 1·2의 사진은 CC BY-SA와 내용·현행성 검토가 남아 Blender 작업을 아직 열지 않는다.
- 출구 3·4는 정확 외관 근거가 없어 기존 일반화 표식을 유지한다.
- 사가정시장 입구·대표 골목은 다음 묶음 후보로 보존한다.

## 문답 r47 — 출구 1~4 순서 확정과 운영자 관점 복귀

[운영자 관점 복귀 r47](operator-perspective-return.r47.md)은 사가정역 출구 상세화 순서를 `1번 → 2번 → 3번 → 4번`으로 닫고 Blender 기획 문답을 일단 멈춘다.

- 출구마다 독립 근거·권리·모델·안전 교체 관문을 통과한다.
- 자료가 없는 출구는 앞 출구 외관을 복제하지 않고 일반화 표식을 유지한다.
- 운영 기획은 평일 11시 30분 점심 피크 직전의 면목제3·8동 운영자로 관점을 돌린다.
- 정상 주문은 자동 진행시키고 미배차·지연·기사 부족·사람 판단 필요 사건과 재무 안전을 우선순위로 읽는다.
- 첫 다음 결정은 운영자가 가장 먼저 대응할 위험이다.

## 문답 r48 — 첫 위험과 원인 카드

[첫 위험·원인 카드 r48](first-risk-and-cause-cards.r48.md)은 점심 피크 직전 운영자가 `미배차·지연 임박 주문`을 먼저 보도록 확정한다.

- 같은 위험 목록에서 `기사 부족`, `조리 지연`, `위치 갱신 중단` 원인을 분리하되 사건 자체를 복제하지 않는다.
- 원인 카드는 서버 상태 사본을 해석하는 관점별 조회 결과이며 주문·배차·위치 원장을 직접 변경하지 않는다.
- 복합 원인은 여러 표지를 함께 보이고, 대표 원인은 현재 회복을 막는 가장 이른 병목으로 두되 불확실하면 `원인 확인 중`으로 남긴다.
- 다음 결정은 기사 부족 카드에서 운영자가 처음 실행할 조작이다.

## 문답 r49 — 가용 의향 알림과 피크 부족 할증

[기사 부족 알림·피크 할증 r49](shortage-alert-and-peak-surcharge.r49.md)는 기사 부족 카드의 첫 조작을 `가용 의향 알림 Preview`로 확정한다.

- 실제 부족이 계속되면 `피크 부족 할증` 후보를 열고 기사 총 예상 지급액에 별도 구성요소로 표시한다.
- 할증은 안전·거리·권역 필터를 우회하거나 기사에게 주문 수락을 강제하지 않는다.
- 주문자 확정 금액과 기사 수락 시 확정 지급액을 소급 변경하지 않는다.
- 다음 결정은 신규 주문과 이미 진행 중인 위험 주문의 할증 비용을 누구에게 귀속할지다.

## 문답 r50 — 플랫폼 부담 피크 할증

[플랫폼 부담 피크 할증 r50](platform-funded-peak-surcharge.r50.md)은 기사 부족 회복을 위한 피크 할증을 전액 플랫폼 부담으로 확정한다.

- 주문자 배송료는 주문 확정 시 고정하며, 이후 기사 부족을 이유로 추가 청구하지 않는다.
- 피크 할증은 주문자 배송료와 분리된 기사 추가 지급이고, 기사 수락 시 플랫폼의 지급의무로 확정한다.
- 기본 수행대금·기존 할증·피크 부족 할증을 기사 제안 화면과 재무 계보에서 구분한다.
- 다음 결정은 피크 할증 금액 산정 방식이다.

## 문답 r51 — 부족 단계별 건당 정액

[단계별 정액 피크 할증 r51](tiered-fixed-peak-surcharge.r51.md)은 기사 피크 할증을 부족 단계별 건당 정액으로 확정한다.

- 같은 정책 판본·권역·시간창·부족 단계·주문 조건에는 같은 정액을 적용한다.
- 기사 수락 시 단계와 정액을 동결하고 이후 단계 변화로 소급 증감하지 않는다.
- 운영자 건별 임의 입력과 실시간 입찰식 연속 변동은 기본 조작에서 제외한다.
- 다음 결정은 유상 피크 할증 단계 수다.

## 문답 r52 — 관리자 설정과 자동 피크 할증

[관리자 설정·자동 피크 할증 r52](admin-configured-automatic-peak-surcharge.r52.md)는 관리자가 단계·금액·피크시간·부족 기준·예산·현금 방어선을 판본화하고 시스템이 그 범위 안에서 자동 적용하도록 확정한다.

- 시스템은 피크시간, 실제 기사 부족, 예산과 현금 방어선을 확인해 적용 가능한 단계를 고른다.
- 정책 범위 밖 금액·대상·시간은 자동 생성하지 않고 운영자 확인을 요청한다.
- 정책 변경은 신규 제안부터 적용하며 이미 수락된 기사 지급액은 보존한다.
- 다음 결정은 가용현금을 건당 금액에 반영할지 활성 범위에만 반영할지다.

## 문답 r53 — 공공자료 동기화 관찰 Simulation 게임

[공공자료 동기화 게임 기준선 r53](public-data-observation-game-baseline.r53.md)은 첫 제품을 Unity에서 실행하는 현실 공공자료 기반 지역 관찰 Simulation 게임으로 다시 정렬한다.

- 서버가 공공자료를 수집·검증·판본화·게시하고 Unity는 접속 시 최신 승인 manifest와 필요한 지역 타일만 내려받는다.
- 현실 기준선, 가상 생활 상태, 운영 정책과 Unity 표현의 권위를 분리한다.
- 첫 폐루프는 사가정역·면목제3·8동 자료 동기화부터 정상 음식배달 관찰, 운영 정책 Preview, 시간 경과 결과와 저장·재진입까지다.
- 피크 할증의 현금 연동·금액 세부 문답은 이 상위 게임 기준선 뒤로 보류한다.
- 다음 결정은 활성 Simulation 세션의 공공자료 판본 전환 시점이다.

## 문답 r54 — 세션 자료 판본 고정

[세션 자료 판본 고정 r54](session-pinned-public-data-revision.r54.md)는 접속 시 최신 승인 자료를 확인하되 시작한 Simulation 세션을 선택한 지역 자료 판본과 hash에 고정한다.

- 새 판본은 플레이 중 내려받을 수 있지만 활성 세션으로 즉시 교체하지 않는다.
- 저장·재생은 같은 지역 자료 판본, Simulation seed와 정책 revision을 사용한다.
- 새 자료 전환은 다음 접속·명시적 재시작 또는 Migration Preview 뒤에만 수행한다.
- 다음 결정은 새 자료 다운로드와 게임 진입의 관계다.

## 문답 r55 — 기존 판본 즉시 시작·백그라운드 갱신

[백그라운드 지역 자료 갱신 r55](background-regional-data-update.r55.md)은 검증된 기존 판본으로 즉시 시작하고 새 호환 판본은 백그라운드에서 받도록 확정한다.

- 새 자료는 임시 영역에서 hash·크기·계약·전체 투영 hash를 검증한 뒤 다음 세션 후보가 된다.
- 다운로드 실패는 현재 세션과 기존 검증 캐시를 손상하지 않는다.
- 정상 갱신은 작은 상태 표시로 두고 사용자 조치가 필요한 실패만 상세 카드로 연다.
- 다음 결정은 첫 설치에 현실 지역 자료 기준선을 동봉할지다.

## 문답 r56 — 사가정·면목제3·8동 초기 기준선 동봉

[사가정 초기 기준선 동봉 r56](bundled-sagajeong-baseline.r56.md)은 첫 설치에 검증된 사가정역 1km·면목제3·8동 최소 지역 자료를 동봉하도록 확정한다.

- 동봉 자료도 서버와 같은 manifest·tile 계약과 투영 hash를 사용한다.
- 공식 출처·권리·품질·배포 승인·개인정보 제거·단계별 증거 관문을 통과한 자료만 포함한다.
- 현행 후보가 이 관문을 모두 통과했다고 아직 간주하지 않는다.
- 다음 결정은 첫 관찰용 합성 생활 Fixture의 동봉 여부다.

## 문답 r57 — 정상 음식배달 합성 Fixture 동봉

[정상 음식배달 Fixture 동봉 r57](bundled-normal-delivery-fixture.r57.md)은 초기 기준선에 같은 seed로 재현 가능한 사가정 정상 음식배달 1건을 포함하도록 확정한다.

- 실제 주문·개인·결제·GPS 없이 합성 음식점 역할·기사·전달지·주문을 현실 공간 기준선 위에 결속한다.
- 주문 접수부터 전달 완료·기사 복귀까지 정상 7단계를 같은 업무 식별자와 revision으로 표현한다.
- 검증된 이동 graph만 경로로 보이고 결손 구간은 추정하지 않는다.
- 다음 결정은 첫 정상 배달 관찰 중 사용자가 개입할 범위다.

## 문답 r58 — 첫 실행부터 배달 플랫폼 운영자

[시작부터 플랫폼 운영자 r58](platform-operator-from-start.r58.md)은 사용자를 첫 실행부터 가상 배달 플랫폼의 사가정·면목제3·8동 권역 운영자로 둔다.

- 정책을 정상 배달 완료 뒤까지 잠그지 않고 첫 회차부터 Preview와 Simulation 적용을 허용한다.
- 플레이어는 Actor를 직접 조종하지 않고 공급·배차·알림·할증·예산·예외 정책을 결정한다.
- 정상 업무는 자동 진행하고 운영자는 위험·정책·사람 판단 사건에 집중한다.
- 다음 결정은 첫 플레이 가능한 운영 회차의 시간 범위다.

## 문답 r59 — 기존 절기 캠페인의 배달 운영 재사용

[절기 운영 캠페인 재사용 r59](seasonal-delivery-operation-campaign.r59.md)은 기존 24절기·제철과 절기 전략 턴·타로 카드 기획에서 시간층·분기·카드 권위 구조를 배달 플랫폼 운영에 재사용하는 제안이다.

- 실시간 운영, 일 단위 마감, 절기 캠페인 마감의 세 시간층을 유지한다.
- 절기 초·중·후반과 두 전략 분기를 기사 공급·피크·현금·예외 정책 검토 지점으로 번역한다.
- 아르카나 카드는 하위 업무를 직접 확정하지 않고 기존 규칙의 허용된 보정 후보만 제공한다.
- Farm 방어·공세와 개인 학습 내용은 자동 이식하지 않는다.
- 다음 결정은 피크 회차부터 13주 운영 장까지의 캠페인 중첩 규모다.

## 문답 r60 — 긴박한 첫 피크와 잔잔한 절기 시작

[긴박한 프롤로그·잔잔한 절기 시작 r60](urgent-prologue-calm-seasonal-campaign.r60.md)은 게임을 해결 가능한 피크 운영 위기에서 시작하고 안정 복귀 뒤 일반 절기 캠페인으로 넘어가는 리듬을 확정한다.

- 첫 프롤로그는 미배차·기사 부족·조리 병목처럼 운영 정책으로 회복 가능한 사건을 사용한다.
- 일반 절기 캠페인은 변화된 일상·제철·기상·자료 품질을 읽는 잔잔한 시작에서 초중후반 긴장을 쌓는다.
- 공식 제철 자료는 합성 메뉴·시장·마트·주문 구성 후보로 연결하되 수요·가격을 직접 확정하지 않는다.
- 다음 결정은 첫 피크 프롤로그의 핵심 사건이다.

## 문답 r62 — 첫 피크 중심 사건

[첫 피크 중심 사건 r62](urgent-lunch-demand-driver-shortage.r62.md)는 첫 긴박한 프롤로그의 중심 사건을 `예상보다 빠른 점심 주문 증가 + 가용 기사 부족`으로 확정한다.

- 결과 위험은 `미배차·지연 임박 주문`, 원인은 `주문 증가`와 `가용 기사 부족`으로 나누어 보여 준다.
- 첫 대응은 기사 가용 의향 알림 Preview이고, 부족이 지속될 때 플랫폼 부담 피크 할증 후보를 연다.
- 기사 안전·확정 지급의무·현금 방어선을 지키며 안정 상태로 돌아오는 것을 성공으로 본다.
- 합성 주문·기사 수, 부족 임계값, 시간 배율과 정확 성공 수치는 아직 확정하지 않는다.

## 문답 r63 — 절기 캠페인 Simulation Core 우선

[절기 캠페인 Core 우선 계획 r63](seasonal-campaign-core-first-plan.r63.md)은 후속 구현을 `Simulation Core → Unity 표현과 콘텐츠` 순서로 진행하도록 확정한다.

- 기존 역경 전용 `SimulationHexagramCampaign`의 이야기 상태를 공통 캠페인으로 오용하지 않는다.
- 공통 계약, phase 상태 전이, revision·멱등성, Preview/Confirm, 안전 기본값과 Save/Replay를 먼저 계획한다.
- 첫 Fixture는 r62의 점심 주문 조기 증가와 가용 기사 부족을 사용한다.
- 정확 규모·시간 배율·카드 수치·제철 효과와 Unity 화면은 이번 계획에서 확정하거나 구현하지 않는다.
- 통합 개발계획 r61의 기존 번호는 보존하고 정상 배달 상태 사본과 Unity 프롤로그 사이에 Core 개발 단위를 둔다.

## 문답 r64 — Unity 절기 캠페인 관찰 Coordinator

[절기 캠페인 관찰 Coordinator r64](unity-seasonal-campaign-observation-coordinator.r64.md)는 `SeasonalCampaignObservationCoordinator`가 기존 행정동 디오라마·운영 상태·카드·NPC 읽기 결과를 하나의 운영자 화면 모델로 조합하도록 확정한다.

- Unity는 Simulation Domain·Application을 직접 참조하지 않고 공유 계약의 상태 사본만 소비한다.
- 기존 Client·Interpreter·Reconciler·마지막 정상값·선택 저장·카드 Workspace·NPC Presenter를 복제하지 않고 재사용한다.
- Campaign 전용 신규 범위는 얇은 읽기 Adapter, Interpreter, Coordinator, ScreenModel과 Presenter 후보다.
- 새 공식 Scene을 만들지 않고 기존 `SimulationWorldShell`의 View Socket으로 후속 결속한다.
- 이번 판본은 계획뿐이며 코드·Unity 배치·Game View 증거를 만들지 않았다.

## 문답 r65 — 원천별 마지막 정상 상태 유지

[원천별 마지막 정상 상태 유지 r65](unity-source-failure-retention-policy.r65.md)는 Campaign 구성 원천 하나의 갱신이 실패해도 다른 원천과 전체 디오라마를 지우지 않도록 확정한다.

- 실패한 원천은 마지막 정상 상태·시각·revision을 유지하고 `갱신 지연`을 표시한다.
- 지연 상태를 실제 객체 삭제·업무 종료·캠페인 전환으로 해석하지 않는다.
- 최신 상태가 필요한 조작은 안전하게 제한하되 무관한 관찰·선택·카메라 이동은 유지한다.
- 지역 전환 때 이전 지역의 stale 상태를 새 지역으로 가져가지 않는다.
- 원천별 revision 묶음은 `CompositionRevisionSet`으로 설명하고 가짜 단일 revision으로 합치지 않는다.

## 개발계획 r66 — 절기 운영 Campaign 단계적 리팩토링

[절기 운영 Campaign 리팩토링 계획 r66](seasonal-campaign-refactoring-plan.r66.md)은 r63~r65를 실제 코드로 옮길 때의 단계·예상 경로·검증·중단·커밋 경계를 정리한다.

- 기존 Workflow Runtime·Simulation Runtime·Hexagram Campaign과 Unity 디오라마 수신 경로를 우선 재사용한다.
- 공유 계약 → Domain → Local Runtime → Save/Replay → RemoteHost → Unity 수신부 → Coordinator → Presenter·기존 World 결속 순서다.
- 범용 만능 Campaign base class, 기존 Hexagram 계약 이주, 새 공식 Scene과 Unity의 권위 판정은 금지한다.
- 첫 수직 절편은 사가정역·면목제3·8동의 합성 점심 피크 한 건으로 제한한다.
- 이번 판본은 계획만 작성했으며 구현과 Goal/WI 활성화는 하지 않았다.

## 문답 r67 — 운영자 예외 우선 복귀

[운영자 예외 우선 복귀 r67](operator-exception-first-return.r67.md)은 관리자가 정상 주문을 계속 감시하지 않고 자동 처리 뒤에도 판단이 필요한 예외를 우선해서 보도록 확정한다.

- 복귀 카드에는 현재 위험, 원인, 이미 수행된 자동 조치, 비용·현금 영향과 다음 결정을 묶는다.
- 정상 흐름과 전체 시간순 기록은 상세 조회로 내리고, 예외가 없으면 불필요한 결정을 만들지 않는다.
- Unity는 상태 사본의 예외와 허용 조작을 표시할 뿐 자체 판정하지 않는다.
- 다음 결정은 카드에 바로 노출할 조작의 깊이다.

## 개발 인계 r61 — r33 이후 신규 기획 통합

[통합 개발계획 r61](development-handoff.r61.md)은 기존 음식배달 정상·예외·13주 재무·Unity 관찰 계획을 보존하면서 공공자료 판본 동기화, 검증 캐시, 사가정 동봉 기준선, 운영자 첫 피크, 플랫폼 부담 할증, 절기·아르카나·제철 캠페인을 하나의 단계별 인계로 정리한다.

- 첫 신규 절편은 기존 행정동 디오라마 API와 Unity Decoder·Client·Interpreter를 재사용하는 지역 자료 세션·검증 캐시 기반이다.
- 현행 자료의 `distributionApproved=false`를 유지하며 개발 Fixture와 실제 배포 기준선을 분리한다.
- 후속은 합성 정상 배달 → Unity 프롤로그 → 기사 알림·할증 → 시간층 → 절기 카드·제철 → 기존 예외 심화 → 배포 순서다.
- 다른 GPT 계정이 바로 사용할 첫 작업 지시문과 중단·검증·커밋 경계를 포함한다.

## 확정

- 첫 방향은 `A. 가상 권역 운영자 우선`이다.
- 현실 자료는 읽기 전용 기준선, 정책 결과는 Simulation 결과로 분리한다.
- 실제 플랫폼 운영 명령은 후속 별도 관문으로 미룬다.
- 무입력 기본값, 정책 Preview, 기간 종료와 원복을 처음부터 포함한다.
- Unity는 하나의 `SimulationWorldShell` 안에서 관찰·선택·결산을 표현한다.
- 첫 운영 상황은 `점심 피크 음식배달 균형 운영`이다.
- 기사 부족 시 가상 기사에게 운행 가용 의향 알림을 보낼 수 있다.
- 알림 수락과 실제 주문 배차는 별도 상태·판정으로 유지한다.
- 실제 푸시·문자·기사 앱 호출은 첫 Simulation 범위에서 제외한다.
- 기사 부족 알림은 `혼합형`으로 운영한다. 주의 단계는 Preview만 자동 생성하고 심각 단계는 사전 승인 범위 안에서만 자동 발송한다.
- 정책 적용 전에 처리량뿐 아니라 가용현금·미지급 의무·준비금 방어선을 함께 검증한다.
- 필요한 현금은 임의 시작자금이 아니라 기준·스트레스 scenario 전 기간의 최대 방어 필요액으로 계산한다.
- 기존 20억원 가정은 내부 비교 scenario이며 외부 가격·자본 확정이 아니다.
- 첫 현금 안정성 검증 기간은 `13주 이동 전망`이다.
- 13주 실행은 하나의 거대한 상태 값이 아니라 `SimulationRun → OperatingPeriod → OS별 WorkInstance → 단계·행위·예외·인계 기록`과 별도의 재무 의무·현금 이동·기간 마감 원장으로 직렬화한다.
- 모든 상태 변경은 안정 식별자, 예상 revision, 멱등 요청 식별자, 정책 revision, 가상 시각과 행위자 역할을 남기며, 조회·Preview·확정·예외 처리·정본 재조회 API 책임을 분리한다.
- 예외는 관련 행위자를 자동으로 실패 처리하지 않고 격리한 뒤 가장 이른 책임 단계에서 재시도·대안·원복·상향 판단으로 회복한다.
- 아직 공통 생명주기가 정해지지 않은 `PlatformOperationsOS`의 단계를 이번 기획에서 새로 만들지 않는다.
- 첫 직렬화 범위는 `FoodDeliveryOS + 기사 가용 의향 알림 + 관련 재무 의무`다.
- 기존 OS의 생명주기를 먼저 대조하고, 사람의 선택·보호·책임·보상 결손을 밝힌 뒤 공통 Engine 후보를 추출한다.
- OS 전체 생명주기, 환경 Adapter와 실제 상태 권위는 하나의 공통 Engine에 합치지 않는다.
- 첫 사람 중심 예외 절편은 `기사 가게 도착 후 조리 지연`이다.

- 회계 운영은 실시간 재무 사건, 일마감 대사, 주별 13주 전망, 월 가결산, 분기 경영보고, 반기·연말 외부 검토 후보의 다중 주기를 사용한다.
- 13주 이동 전망과 달력 분기 결산은 같은 재무 사건에서 파생하되 서로 대체하지 않는다.
- 회계 마감 뒤 수정은 조정·역분개·사유 있는 재개로 남기며 과거 값을 조용히 덮어쓰지 않는다.
- 별도 회계사 앱·화면·Unity Scene은 만들지 않고 기존 운영자 통합 화면에 회계 요약·예외·상세 조회를 결합한다.
- 운영 화면의 회계 카드는 읽기 결과이며 주문·배차·전표·지급을 직접 확정하지 않는다.
- 운영자 통합 화면에는 네 회계 요약 지표를 항상 표시하고, 화면 명칭은 `정산 확인 필요`로 통일한다.
- 정상 재무 경로는 자동 처리하고 운영자는 예외를 수시 확인하며 정상 결과는 주간·월간·13주 주기로 요약 검토한다.
- 정산 예외는 관련 사건만 격리하고 다른 정상 주문·지급·환급을 일괄 중단하지 않는다.
- 주간 마감 결과에는 정산 완료율을 표시하지 않고 정산 총액·정산 후 가용현금·정산 확인 필요만 기본 표시한다.
- 월간 결산은 전월 실적만 기본 비교하고, 월초 서원은 회계 계획과 분리된 비구속 회고 항목으로 둔다.
- `안정 운영 유지` 기본 서원은 판본화된 기본 운영정책을 참조하며 서원 자체는 정책 활성화 권위를 갖지 않는다.
- 사가정역 1km × 1km 디오라마를 면목제3·8동 생활상의 첫 관찰 창이자 시각 회귀 기준으로 유지한다.
- 면목제3·8동을 첫 운영·집계 권위로 사용하고 면목제7동 등 교차 행정동은 자기 귀속을 유지한 인접 맥락으로 표현한다.
- 건물은 한 행정동 또는 `Unresolved`에만 귀속하고 경계 교차 도로는 계보를 유지한 채 선분을 나눈다.
- 미진한 공간·생활 자료는 현행 화면을 해치지 않는 단계별 관문으로 보완한다.
- 첫 생활상 판독 장면은 사가정 점심 시간의 합성 음식배달 정상 1건이다.
- 정상 7단계는 서버 또는 합성 Simulation의 상태 사본이 확정하고 Unity는 같은 `WorkStableId`·revision을 읽기 전용으로 표현한다.
- 면목제3·8동 이동 표현 전 현행 경계 안 모든 대상 건물을 실자료 기반 건물 또는 `MissingCoverage`로 전수 판정한다.
- 검증된 건물·기준점·연결 구간만 경로 이동에 사용하고 결손 구간은 `이동 중` 상태로 표현한다.
- 면목제3·8동 전수 건물은 공공데이터 기반 절차적 매스를 첫 표현으로 사용하고 중요 건물만 후속 Blender 상세 모델로 교체한다.
- 상세 모델 교체 전후에 건물 안정 식별자와 공간·업무 결속을 유지한다.
- 첫 Blender 상세화 묶음은 사가정역 출구 주변이며 기존 역세권 디오라마의 사진·권리·출구·안전 교체 기획을 정본으로 재사용한다.
- 권리·현행성·모델 브리프·기술 검증이 닫히기 전 Blender·Unity 교체는 차단한다.
- 사가정역 출구 Blender 상세화 순서는 1번, 2번, 3번, 4번이며 Blender 관련 기획 문답은 일단 닫는다.
- 운영자 역지사지 기획은 점심 피크 직전의 첫 위험 판단에서 재개한다.

- 실제 통화 중계 Adapter·가상번호·callback 제공자의 계약과 비용

- 직접계약 기사·지사 기사 비율과 지사 운영보상 범위
- 적용 회계기준, 플랫폼 본인·대리인 판단, 실제 계정과목과 부가가치세·세무 처리

## 예상 검증 경계

- Logic 후보: 같은 seed·자료 revision·정책 revision의 결정성, 무입력 기본값, 정책 Preview 무변경, 적용·만료·원복, Save/Replay와 Local/Remote 동등성.
- Presentation 후보: 전체 조망·대상 선택·정책 비교·시간 경과·결산 카드의 원인과 결과 판독, Unity가 운영 권위를 갖지 않는지 확인.
- 위치 후보: 유효 배차·주문 소유권, 최신 위치 revision, stale 전환, 기사 교체, 완료·취소·보호 해제 때 구독 종료, 과거 궤적 비노출을 검증한다.
- 회계 후보: 보조원장·총계정 후보·시산표의 합계, PG·은행·주문 대사, 마감·재개 이력, 13주와 분기 집계의 동일 재무 사건 결속을 검증한다.
- 실제 구현·E 단계·Scene·Game View·DB·API·commit·push는 아직 승인하지 않는다.
