- 상태: `PrototypeImplementationAuthorized / PickupRidingDirectionConfirmed / UnityPreviewMovieVerified / LocalThreeWayPrototypeVerified / ProductIntegrationPending`.
- 선행: [장소·영상·플레이 연결 r2](video-diorama-play-experience.proposal.r2.md), [Unity 체험→앱 개선 r120](unity-first-app-feedback-cycle.proposal.r120.md), [공통 디오라마 뼈대 r121](longform-game-shared-diorama.framework.r121.md).
- 판본 관계: r121의 공통 공간 방향을 유지하고, 이번 첫 시제품의 중심을 설명 카드에서 **연속되는 픽업·주행 장면**으로 좁힌다. 앞서 제안했던 조리 지연 사건은 확정하지 않는다.

## 1. 제안하는 제품 흐름

사용자의 실제 배달 경험을 같은 동네의 가상 여정으로 체험하고, 그 여정에서 롱폼에 넣을 장면을 뽑고, 체험 중 불편한 정보를 앱 설계에 돌려준다. 핵심 연결 단위는 **같은 공간 판본·여정·행동/상태 기록**이다.

```text
실제 픽업·주행 영상 / 확인된 배달·공간 근거
                  ↓ 장소·기록 대응 검토
        사가정 공통 디오라마 + 여정 기록
          ├─ 체험: 픽업 → 라이딩 → 픽업 → 라이딩
          ├─ 영상: 같은 기록의 카메라·구간을 선택해 출력
          └─ 앱: 체험에서 부족했던 정보·조작을 보완 후보로 기록
                       ↓
            보완된 앱/표시로 같은 여정 재체험
```

게임의 이동과 영상의 이동을 따로 작성하지 않는다. 장소·도로·정차/출발/이동·시각과 사용 판본을 하나의 여정 기록에 두고 게임·카메라·장면표가 읽는다. 운영 서버의 실제 배달 원장, Simulation의 가상 상태, Unity 표현 책임은 [기존 기준](../../../../Architecture/OperationsSimulationUnity작업흐름분리.md)을 유지한다. 실제 배송 API/DB나 사용자의 영상 원본을 이번 시연이 변경하지 않는다.

## 2. 같은 여정을 쓰는 세 가지 결과물

| 관점 | 사용자가 하는 일 | 다른 관점으로 넘기는 것 |
| --- | --- | --- |
| 동네 체험 | 매장 앞 정차·픽업과 다음 매장으로의 주행을 재생/정지하고 구간 이동 | 현재 여정·시각·장면·발견한 불편 |
| 롱폼 장면 | 같은 여정을 픽업 컷/라이딩 컷으로 보고 MP4·장면표를 받음 | 원본 여정과 공간 판본이 연결된 편집 소재 |
| 앱 보완 | 다음 매장·이동 구간 표시 같은 부족 정보를 기록하고 시안에서 보완 | 같은 조건으로 재체험할 표시 변화와 개선 명세 |

롱폼에서는 실제 주행과 디오라마 주행을 연결해 매장 주변·도로·이동 흐름을 보여준다. 위치 대응이 확인된 장면부터 실제 컷→같은 동네의 3D 픽업/라이딩→실제 컷으로 이어갈 수 있다. 자연스러운 소개는 익숙한 공간과 직접 체험 가능한 업무를 함께 보여주는 데서 시작한다. 실제 촬영·개략 재현·가상 시연은 시청자가 구분할 수 있도록 표시한다.

## 3. 이번 가벼운 구현의 명세

첫 범위는 사가정 기존 디오라마에서 **가상 픽업 A/B와 한 도로 선분**을 사용하는 12초 연속 시연이다. 실제 매장 간 배달 경로나 실제 속도·소요시간의 재현이 아니다. 정식 첫 게임 사건·선택·대가를 확정하는 작업과 분리한다.

| 구간 | 프레임 범위 (24fps) | 표현 |
| --- | --- | --- |
| 0~2초 | 0~47 | 픽업 A 정차 |
| 2~6초 | 48~143 | A→B 라이딩 |
| 6~8초 | 144~191 | 픽업 B 정차 |
| 8~12초 | 192~287 | B→A 라이딩 |

구현은 두 부분이다.

1. **실제 Unity 3D 출력:** 기존 사가정 상세 건물·주변 도로가 살아 있는 비공개 PreviewScene에서 간단한 기사/오토바이 모형과 추적 카메라의 Transform을 프레임마다 갱신하고 Camera.Render로 PNG를 출력한다. 이 PNG열을 MP4로 인코딩한다. 정지 PNG를 확대·이동해 만든 영상과 구분한다.
2. **로컬 연결 시제품:** 브라우저에서 같은 12초 영상의 재생·정지·구간 이동, 4컷 장면표/MP4 받기, 현재 시각의 불편 기록→앱 시안의 다음 픽업 표시→같은 여정 다시 보기를 제공한다. 실제 Unity 실시간 조작 게임이나 실제 역할 앱 반영을 의미하지 않는다.

UI는 여정의 공통 고유 식별자·판본·시각을 유지한다. 앱 시안에서 다음 매장 표시를 보완해도 영상·도로·주행 시간은 바뀌지 않는다. 과거 기록과 가상 결과를 홍보 성과나 실제 배송 성과로 바꾸지 않는다.

## 4. 현재 자산과 수정 경계

- 공간 기반: [사가정 제작 방식 추출 r50](../PLAN-SYSTEM-ADMIN-DONG-DIORAMA/sagajeong-construction-recipe.extract.r50.md) 및 [상세 표현 r114](../../../../Changes/2026-10-26-detailed-building-representation-r114.md)의 기존 비공개 연구 장면. 주변 Overture 건물과 상세 전면 연구를 재사용한다.
- 실제 Unity 렌더 입력: 별도 영상 작업공간의 `edit-kit/private/detailed-building-study/20261026-r1/input.private.json`. 이번에 새 출력으로 실행하고 기존 원문·이전 출력은 덮어쓰지 않는다.
- Unity 허용 수정: 새 Editor 전용 `사가정픽업라이딩PreviewCapture.cs`와 `.meta`, 기존 `사가정상세건물PreviewCapture.cs`의 opt-in 호출. 실행 중 드러난 기존 null-envelope 보고서 예외도 같은 파일의 null-safe 검사 한 줄로 보완했다. 환경변수가 없으면 새 기능을 실행하지 않는다. 새 공식 Scene·Prefab·runtime 게임 규칙·운영 DB·Goal/WI를 만들지 않는다.
- 시제품 경로: `artifacts/local/sagajeong-threeway-r122/`. `dist/`는 로컬 화면, `unity-journey/`는 프레임과 출력 근거, 별도 압축본은 사용자용 묶음이다.
- 전환 전 ‘준비시간 확인’ 모델 두 파일은 선행 실험으로 보존하되 이번 픽업·라이딩 화면에서 로드하거나 사용자용 묶음에 넣지 않는다.

이 작업은 사용자 요청으로 허용된 로컬 동작 시제품이다. 정식 제품의 새 플레이 규칙·주체·운영 연결을 구현하는 승인이나 E 단계 증거를 대신하지 않는다. Game View·실제 입력·실시간 FPS·설치형 빌드와 공개 배포는 별도다.

## 5. 권역을 정밀하게 넓히는 방식

대상 권역은 **중랑구·동대문구·광진구·노원구 공릉/태릉 일대**다. 시작은 사가정과 그 주변의 연결 가능한 작은 도로 구간이다. 그 뒤의 정확한 우선순위는 실제 배달 기록에서 자주 방문하는 매장·연속 주행 구간과 확보된 공간 근거로 정한다. 구 이름만으로 바로 전역을 상세 제작하지 않는다.

| 층위 | 모든 작업 구역에서 함께 맞출 기준 | 주행 영상에서 확인할 내용 |
| --- | --- | --- |
| 공간 뼈대 | 도로 연결·교차로·건물 외곽·매장/건물 대응 | 건물을 통과하지 않고 픽업 지점과 도로가 이어지는가 |
| 공통 표현 | 도로 폭/높이·재질·조명·카메라 거리에서의 밀도 | 구역 전환 때 상세 수준이 급격히 달라지지 않는가 |
| 주요 관측 지점 | 확인된 매장 외관·출입 방향·간판·주행 랜드마크 | 픽업 근접 장면과 코너·교차로에서 위치를 이해하는가 |
| 이동과 출력 | 정차/출발·회전·다음 매장·동일 여정 재현/카메라 규약 | 게임과 영상이 같은 경로·상태·판본을 읽는가 |

[r48의 전체 구역 품질 층별 누적](../PLAN-SYSTEM-ADMIN-DONG-DIORAMA/area-wide-layered-quality.decision.r48.md)을 유지한다. 한 매장만 과도하게 정밀하게 만든 뒤 주변을 방치하는 방식으로 확장하지 않는다. 실제 영상에 드러나는 구간을 연결하되, 가상 주행 성공으로 실제 도로 방향·통행 가능·매장 출입을 확정하지 않는다.

## 6. 완료 판단과 다음 단계

이번 시제품의 완료 판단은 실제 3D 프레임·12초 MP4, 네 구간과 카메라/모형 이동, 로컬 세 관점의 같은 시각/상태 연결, 앱 시안의 표시 보완과 재체험, 장면표/JSON 받기다. 프레임/영상 해시·입력 보존·정리/복구와 기능 검증 결과를 아래에 남긴다.

- 확정: 사가정 디오라마를 활용하는 연속 픽업·라이딩과 영상 추출 목적, 롱폼·게임·앱 개선의 순환, 후속 정밀화 대상 권역.
- 미정: 실제 첫 배달 날짜/매장/연속 도로·이동 방향, 정식 게임 선택·대가, 실제 주문 DB 읽기 연결, 실촬영 편집 구간, 설치형 제품·공개 배포.
- 다음 질문 하나: 이 동작 시안 다음에는 **어느 실제 배달 하루 또는 연속 매장 두 곳을 첫 재현 구간으로 삼을까?** 기존 기록·영상에서 대응 근거를 먼저 확인하고 구체 시안으로 제시한다.

## 검증 결과

- Unity CLI graphics 최종 attempt2 exit0. 1920×1080·24fps·288 PNG·12초이며 288개 SHA/치수/시간·네 단계 경계를 확인했다. source-before/after가 기존 r114 조감과 exact SHA 일치하며 임시 객체 제거·PreviewScene 종료·기존 활성 Scene과 설정/패키지6파일 보존을 확인했다. Pipeline 연결 Editor가 없어 CLI를 사용했다.
- 첫 attempt1은 낮은 카메라 가림과 기존 null-envelope 보고서 예외로 exit1이었다. 실패 출력을 보존하고 높은 추적 조망 및 null-safe 한 줄 보완 뒤 attempt2로 완주했다. 새 C#/shader 오류·예외0이며 기존 URP shadowResolution 경고4회는 남는다.
- MP4 전체 디코딩288프레임·12초·1080p 통과. 양쪽 라이딩 구간은 각각96개 고유 디코드 프레임이다. 영상 SHA-256은 `2e21b1beb30d7f17ed5dc559d2d804afa6101c21f5646fef20eb24cf1ec6fcf1`이다.
- JavaScript 상태 시험8개 통과. 실제 브라우저에서 재생·정지·6초 컷 이동·관점 전환·불편 기록·보완 적용·같은 여정 재체험·초기화를 확인했다. 1366px와 기본 좁은 화면을 확인하고 viewport는 복원했다. 현재 브라우저 오류 로그0이다.
- UI에서 MP4·장면표JSON·순환기록JSON을 실제로 받았다. 받은 MP4 해시가 원본 출력과 일치하고 두 JSON의 case/revision·6초 시각·네 구간·captureEvidence가 연결되며, 보완 상태만 applied이고 actualAppChanged/actualLedgerChanged는 false다.
- 화면·실패/보완·변경 파일과 미검증 범위의 상세 기준은 [변경 기록](../../../../Changes/2026-10-29-sagajeong-pickup-riding-r122.md)이다. 실제 배달 기록/실촬영 연결·정식 게임 직접 조작·Play Mode/Game View·실시간 FPS·설치형 빌드·다른 권역 정밀화·운영/공개·commit/push는 수행하지 않았다.

새 공간 관측·정본 적용은 없고 기존 공간 규칙의 지지/반례/무효화 판정을 바꾸지 않는다. 이번 동작 시제품만으로 공통 공간 규칙을 승격하지 않는다. **새 디오라마 규칙 후보 없음.**
