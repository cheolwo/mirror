## 2. 권하는 순서 — 같은 일을 끝내고 다음 선택을 바꾸는 경험

우선순위는 개발 승인이나 현재 Claude 작업의 재배치가 아니다. P0 검토에서 발견한 가장 이른 문제를 먼저 고치고, 아래 후보 중 하나를 선택해 좁게 잇는 방식이다. 모든 후보를 첫 검토의 선행 조건으로 붙이지 않는다.

| 후보 | 부족한 부분 | 플레이어에게 필요한 결과 | 가장 작은 다음 범위 / 대가 |

| **P0 · 기존 배달 두 회차의 실제 입력 검토** | 촬영·규칙과 별개로 일반 실행에서 선택→진행→결과→다음 대상이 읽히는지 검토 대기 | 안내를 따라 한 건을 끝내고, 같은 세션에서 다른 한 건을 스스로 고름 | 기존 실제 주문/기사 두 건. 상태/입력 문제를 먼저 찾음. 신규 사업이나 명덕 구현은 늘지 않음 |

P1 두 후보는 계약·쓰기 경로가 분리되는 범위에서 병렬 준비할 수 있다. 기존 주문의 정산 연결이 전체 명부 완성을 기다릴 필요도 없다. 동 고용수만큼 기존 Core 기사를 복제/임의 배정하지 않으며 실제 주체·집계용 표현·미결속을 구분한다. 카페·명덕·자료의 P2 후보도 전체 선후행 사슬로 고정하지 않는다. 사용자가 어떤 경영의 재미를 먼저 보려는지에 따라 한 후보를 골라 진행한다. 첫 입력 검토에 전체 명부·시간 제조·명덕을 필수로 붙이지 않는다.

## 3. 첫 완료 목표 후보 — 한 동에 집중한 배달 두 건

**같은 현실 날짜·같은 검토용 세션에서, 실제 주문 두 건을 서로 다른 회차 대상으로 수행하고 결과를 읽어 다음 준비로 돌아오는 것**을 먼저 권한다. 현재 소속/집중 동은 하나로 두고 기존 다른 동 전달은 업무가 이어짐을 유지한다. 경계 밖 안내의 미연결은 발견 사항으로 남기며 모든 동 지도 완성을 선행하지 않는다.

1. 현재 코드/빌드·검토용 저장 범위를 특정한다. 사용자 본 저장을 새 게임으로 덮어쓰지 않는다. 이번 기획 작성에서는 실행하지 않았다.
2. 기존 안내로 운영 시작→실제 주문 하나와 기사 선택→배정→픽업/전달 진행을 수행·관찰한다. 직접 조작과 위임/관찰의 구체 범위는 현재 구현에 맞춘다.
3. 해당 주문ID·상태가 회차 결과와 맞는지 본다. ‘전달됨’과 정산/지급을 구분하고, 금액이 연결 전이면 그 한계를 그대로 읽을 수 있어야 한다.
4. 회차 마감은 현실 날짜/일일 결산을 강제로 넘기지 않는다. 같은 세션에서 다른 주문을 골라 두 번째 회차를 진행한다. 중복 마감·이전 대상 잔류를 확인한다.
5. 실패/보류 표본이 기존 계약으로 가능한 범위에서 다시 선택/계속하기/이유 표시를 확인한다. 현재 없는 취소·실패 전이를 검토를 위해 제품에 만들어 넣지 않는다. 없는 표본은 ‘미검증’으로 남긴다.

첫 검토의 결과물은 잘 되는 장면과 막히는 장면, 해당 입력/주문·판본, 다음 수정 하나다. 검토할 Windows 빌드의 실행 준비는 이 목표에 포함하며, 외부 공개 준비까지 기다리지 않는다. 배달은 기존 검토 표본이며 모든 플레이어의 필수 시작 분야로 고정하지 않는다. 저장 기반은 확인하되 **진행 중 회차의 저장/재개는 r187 첫 검토판의 비저장 범위와 분리**한다. 이후 선택할 저장·재진입 과제에서 중복 정산/재귀속 없이 복원되는지 확인해야 한다.

이 목표를 통과해도 카페 시간 제조·새 명덕·정신 차림·전체 지역 성장·전체 게임 출시까지 완성된 것은 아니다.

## 4. 경영을 만드는 자료와 수치의 빈칸

### 기존 자료를 한 작업의 단위로 묶기

원본 보유·DB 저장·팩 준비·현재 게임 소비·배포 가능은 각각 확인한다. 이번에는 DB를 재조회하지 않았다. 기존 수집 문서의 행 수를 오늘 다시 센 결과로 제시하지 않는다.

- **인구:** 현 `Resources/hongdal-dong-demand.json`은 인구 대신 주거 연면적㎡와 임시 시간대/요일 모양을 사용한다. 보유한 실제 통계와 연결하려면 출처의 행정동 코드·기간·관측 종류와 지도 경계 판본 대응이 필요하다. 유동인구·거주인구·화면 군중·주문 기회를 서로 같은 수로 읽지 않는다([r200](dong-population-map-and-order-demand.design.r200.md)).
- **길:** `Runtime/길찾기Policy.cs:8–12`의 큰길/골목·가상 출입구는 건물 배치에서 계산한 표현값이다. 실제 오토바이 통행 가능망·차로·시간을 검증한 근거가 아니다. 기존 Core 배달 경로와 순찰 표현 길도 구분한다. 보행망을 오토바이망으로 바로 소비하지 않는다([r201](gameplay-data-gaps-and-collection-priorities.research.r201.md)).
- **카페:** 현재 라떼의 우유170mL와1L당2,400원은 우유 사용 원가408원의 근거다. 원두·컵·뚜껑·포장·노동·임대까지 포함한 총원가나 순이익이 아니다. 누락 비용을0원으로 채우지 않는다([r203](priority-defaults-and-first-validation.proposal.r203.md)).
- **시간:** 커피 약5분·음식10~15분은 사용자 확정이다([r202](coffee-food-preparation-time-defaults.confirmed.r202.md)). 1잔/1인분·포장 포함·작업자1/자리1·재료 점유/소모 시점·표시 배속 등은 r203의 미승인 추천이다. 이번에도 기본값으로 확정하지 않는다.

다음 자료 준비 후보는 기존 한 점포/메뉴ID에 재료·단위·작업시간·작업자/설비·비용의 출처/결측을 붙이는 작은 표다. 전국 메뉴/원가 수집 완료나 카페–배달 외부 주문 통합을 그 표의 전제로 두지 않는다.

### 명덕과 기존 성장 규칙의 정합

[r206](awake-activities-and-mindfulness-skill.design.r206.md)의 사용자 방향은 **성공/매출 여부와 관계없이 깨어서 한 모든 활동**이다. 반복 가능한 정신 차림의 대상·지속/회복·재사용 간격·부담·관찰 위임과 활동 측정 단위는 아직 선택할 부분이다. 기존 하루 한 번의 기사 경 점검을 새 스킬이 이미 구현된 것으로 읽지 않는다.

같은 행위 기록에서 개인의 누적과 활동한 동/받은 동의 지역 누적을 연결한다([r207](cross-dong-delivery-and-recipient-mingde.design.r207.md)·[r208](pickup-preparation-and-local-mingde.design.r208.md)). 같은 사건을 같은 동/같은 사유로 중복 더하지 않는다. 픽업 동은 여러 사람의 준비/제조/포장/인계가 있어 더 쌓일 수 있다는 방향이며 고정 배율·항상 더 큼·자동 균등 배분을 확정하지 않는다. 즉시 제조에서 실제 없던 작업자/시간 활동을 소급 생성하지 않는다.

기존 동의 운영 단계와 새로운 명덕 레벨업·연구/해금의 관계도 정해야 한다. 별도 규칙이 같은 동을 이중 승급시키거나, 한 번의 금액 증가가 자동으로 모든 성장을 여는 방식은 아직 승인된 것이 아니다. 빛의 성장·음악의 순간 맥동·명덕 수치를 구분한다.

## 5. 화면·확장·배포에서 후속으로 볼 것

첫 입력 검토에서는 **선택한 기사/주문·현재 장소·목적지·상태·다음 행동**을 찾을 수 있는지를 본다. [r212](soft-road-following-delivery-lines.design.r212.md)의 기사 빛/선 기준색 일치와 부드러운 연결은 그 판독을 돕는 후보이며, 경로 그림이 도착/업무 완료를 대신하지 않는다. 동 고르기·창 열기·목록/건물 선택의 실제 조작과 귀환은 시안/방향 촬영과 별도로 확인한다. 사업 진입의 r198 제안과 현 동 관리 창의 차이는 향후 해당 기획에서 조정한다.

넓은 지도·여러 직무/센터 내부·외부 음악 분석·추가 광효과는 후속 확장 후보로 둔다. 이미 진행 중인 Claude 작업을 이 제안으로 중단하거나 회수하지 않는다. 특히 새 음악 파일 분석 소스의 존재와 내장 BGM·외부 앱 소리 취득의 실제 성공은 다른 사실이다. 새로운 장치/곡·외부 서비스 호환/실시간 반응은 이번에 실행하지 않았다.

다른 Windows PC에 배포하는 준비는 별도 과제다. 현재 실행 파일이 존재하는 것에 더해 패키지 전체·데이터/자산 이용 조건·비개발 PC 최초 실행·설정/저장/재시작·화면 크기/성능을 확인해야 한다. 현재 자료의 ‘역사 경계 후보·내부 검토용’은 유지한다. 이 항목은 이번 플레이 검토나 문서 검증의 완료 조건으로 붙이지 않으며 전체 출시 가능 판정을 하지 않는다.

## 6. 확정 / 미정 / 다음 질문 하나

**확정·재사용할 방향:** Unity Windows 중심, 한 행정동에 집중, 작은 한 건에서 안내를 받고 같은 날 회차를 반복한다. 기존 실제 게임 주문/기사/매장ID·정산·재고·저장 기반을 재사용한다. 확인한 구현 사실은 현황이며 신규 기능 승인이 아니다.

**미정:** 이 문서의 우선순위 채택, 실제 입력 검토의 담당/실행 범위, 정산 보고 결속, 집계와 개인화의 전환/회계 계약, 카페 작업 단위/슬롯/비용, 정신 차림 대상/측정·동 성장, 선택할 실제 자료와 판본, 성장 보상/확장 조건. 이번 요청으로 이 값을 묶어 승인하지 않는다.

**다음 질문 하나:** 첫 완료 목표를 **‘기존 배달 두 회차를 실제로 조작하고, 각 주문의 결과와 다음 선택을 읽는 것’**으로 잡을까? 추천 이유는 이미 있는 흐름으로 막히는 위치를 빨리 찾을 수 있기 때문이다. 대가는 새 카페/명덕/확장 기능의 구현 범위가 이 검토에서 늘지 않는다는 점이다.

## 7. 변경·검증 범위

기획 정본·맥락 색인/대장·PLANNING·현재 작업·해당 Windows 현황만 갱신한다. 기존193개 기획 원문·입력 JSON3개·README 초기 보존 본문을 유지한다. 문서 지문/링크/색인·변경 공백과 문서용 빠른 검증을 확인하고 결과를 로컬 조사 폴더에 둔다. 제품 시험·Unity 빌드/실행·실제 입력·DB/예약 변경·새 시안·전역 결정·commit/push는 수행하지 않는다. 검증 도중 바뀐 외부 소스는 새 빌드의 증거로 합치지 않는다.
