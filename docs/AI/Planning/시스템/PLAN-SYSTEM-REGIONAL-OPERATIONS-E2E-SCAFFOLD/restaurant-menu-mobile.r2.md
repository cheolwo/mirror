# 기존 메뉴 API와 음식점 메뉴 화면 연결

2026-09-27 사용자 “화면을 볼 수 있게 … 메뉴 등록 화면도 … 진행” 요청으로 [r1](restaurant-mobile-workflow.r1.md)을 이어간다. 실제 메뉴 화면과 별도 로컬 합성 미리보기를 만들되 실영업·외부 공개·배포는 하지 않는다.

## 구현

- `/menus`를 음식점 홈·서랍·Release 허용 route에 추가했다. 기존 `RestaurantRouteView` 인증과 음식점 서버 권한을 유지한다.
- 메뉴명·소개·가격·대표 사진 HTTPS URL·공개·품절을 입력한다. 새 메뉴는 비공개 기본값이다. 이미지 업로드·옵션 그룹은 구현하지 않았으며 URL을 임의 다운로드하지 않는다.
- 기존 `Ssalddel음식주문Client`의 인증·401 갱신·HTTP 오류 경로를 메뉴 GET/POST/PUT에도 재사용한다. 별도 서버나 로컬 상품 원장을 만들지 않는다.
- 등록 요청과 입력을 응답 미확인 상태에서 보존하고 같은 요청을 재시도한다. 서버는 현재 요청 ID 존재 검사와 음식점·메뉴명·동일 내용 비교로 중복 등록을 방지하므로, 요청 ID가 영속 멱등 원장에 저장된다고 주장하지 않는다.
- 수정은 조회한 `Revision`을 `예상Revision`으로 전달한다. 충돌/실패 안내 후 재조회·재선택을 요구하며 자동 덮어쓰지 않는다. 400/403/404/409 명시적 거절은 입력 잠금을 해제한다.
- 저장 성공 뒤 목록 재조회 실패는 저장 실패와 별도로 알린다. 조회 실패를 샘플 메뉴로 대체하지 않는다.

## 화면 보기와 증거 경계

`eng/RestaurantMenuPreview`가 제품의 동일 Razor 파일을 링크하고 메모리 전용 합성 메뉴를 제공한다. `http://127.0.0.1:5387/`에서 사용자가 확인할 수 있다. 430px 이하 콘텐츠 폭과 기존 음식점 색상·카드 스타일을 사용한다. 운영 DB·실제 인증·실결제·알림 호출은 없다. 메뉴 외 링크의 화면은 이 미리보기에서 제공하지 않는다.

페이지 HTTP200·메뉴 HTML과 MudBlazor CSS/JS·앱 CSS의 HTTP200을 확인했다. Codex 우측 브라우저 열기는 `queued`로 반환되었다. 브라우저 제어 도구는 목록이 비어 있고 Windows Computer Use는 Whale 창 소유자 불일치로 재시도에도 실패했다. 따라서 **직접 시각 검수·스크린샷·브라우저 버튼 클릭 완료를 주장하지 않는다**. 모바일 네이티브 렌더와도 구분한다. 사용자가 볼 수 있는 링크를 제공하고 미리보기 서버는 요청 범위 내 로컬에서 실행해 둔다.

## 검증

- 메뉴 Razor 처리 메서드 인메모리 검사 7개 통과: 초기 조회, 잘못된 입력, 응답 유실, 같은 요청 재시도, 명시적 거절 후 수정 가능, 저장/목록 실패 분리. UI 클릭·운영 DB 증거가 아니다.
- Android build 경고0·오류0. 화면 구성/서버 메뉴 UseCase 집중시험26/26 통과·실패/건너뜀0. 기록은 `artifacts/restaurant-menu-build-final.log`, `artifacts/local/validation/restaurant-menu/restaurant-menu.trx`. 새 메뉴 그림·음식 사진은 생성하지 않았다.
- r1 전체 Task의 범위 밖 실패7건을 해결한 작업이 아니다. commit·push·배포 없음.
