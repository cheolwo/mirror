## 구현한 정상 흐름

`주문대기 → 주문확인 → 기사배정 → 조리중 → 픽업대기 → 픽업완료 → 전달완료 → 수령확인`

기존 `restaurant-acceptance`는 매장의 주문 확인·준비 가능 확인과 배차 Outbox 예약을 담당한다. 수락만으로 조리중이 되거나 조리 완료 예정 시각이 시작되지 않는다. 예상 조리 분은 기존 `적용조리분`에 보존한다.

조리 시작은 기존 `restaurant-progress`의 새 `조리시작` 작업과 `FoodOrder.StartCooking` 행동을 사용한다. 요청 ID와 현재 주문 revision을 확인하고 주문의 현재 운송 원장, 확정 기사, 최신 배달 시도의 연결·활성 상태를 서버에서 검증한다. 후보 추천, 미확정 배차, 해제된 기사, 다른 제안에 속한 시도, 중단·픽업·완료된 시도는 조리 시작을 허용하지 않는다. 기존 음식점 운영자 권한과 매장 소유권 검사를 재사용한다.

실제 조리 시작 시각은 서버의 상태 이력에 저장하고 응답에 별도로 제공한다. 완료 예정 시각은 이때부터 계산하며 같은 트랜잭션에서 현재 배달 시도의 표시 준비 예정 시각과 revision도 갱신한다. 새로운 DB 열이나 migration은 필요하지 않는다. 조리 시작의 멱등 재시도는 상태 이력과 후속 Event를 중복 생성하지 않는다.

## 화면·배차·조회 연결

- 음식점 앱의 수락 버튼은 `주문 확인·배차 요청`으로 표시한다. 기사 배정 확정 뒤 서버가 제공한 행동에 따라 별도의 `조리 시작` 버튼을 표시한다. 선택한 조리 분은 서버 재조회 뒤에도 복원한다.
- 주방 전표도 실제 주문 상태와 `조리대기 / 조리중 / 픽업준비`를 구분한다. 주문 확인 전표에 즉시 조리 지시를 남기지 않고 앱에서 배차 확인 후 조리를 시작하도록 안내한다.
- 배차 확정과 조리·픽업 준비 상태를 분리한다. 재배차가 성립해도 이미 시작된 조리나 준비 완료 상태를 기사배정으로 덮어쓰지 않는다.
- 기사 이탈은 조리 전이면 주문확인·배차 대기로 돌아가고, 조리 후이면 조리 시작 이력을 유지하며 재배차한다. 조리 시작은 배차 해제 뒤 오래된 화면에서도 차단한다.
- 픽업은 실제 준비 완료 근거를 확인한다. 주문자 안내와 운영 조회에 주문확인·기사 확보 대기를 반영하고, 완료 상태 사본은 새 정상 순서를 검증한다.
- 조리시간 통계는 새 주문의 실제 조리 시작부터 준비 완료까지 측정한다. 배차 대기를 조리 시간에 포함하지 않는다. 과거 수락 즉시 조리 주문의 관측은 호환한다.

## 호환 및 적용 경계

기존 즉시 픽업 요청은 **이미 준비된 음식**으로 따로 기록한다. 새로운 조리를 시작했다는 근거로 쓰지 않으며 기사 배정 전에는 기사 픽업을 진행할 수 없다. 과거 Simulation·저장 재생의 수락→조리 전이는 공통 규칙에서 호환용으로 보존하지만 운영 저장소는 새 확인·배차 검증 경로만 사용한다. InMemory 샘플 저장소는 실제 배차 원장이 없으므로 조리 시작을 허용하지 않는다.

수락 전 거절·주문자 취소와 기존 픽업 후 재조리·중단 정책은 유지했다. 주문 확인 이후 새 거절/취소/환불 정책, 자동 배차 대기 제한과 비용 보상은 아직 미정이며 이번에 새로 만들지 않았다. 실제 결제·배차·정산 기능의 기본 활성화와 금액 정책도 변경하지 않았다.
