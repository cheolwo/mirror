- 선행: [공급·가공 관계 r31](ingredient-supply-graph.plan.r31.md), [국내·수입 조달 경로 r32](domestic-and-import-supply-paths.plan.r32.md)

## 확정한 진행 방향

품목 하나를 골라 끝까지 깊게 만드는 질문을 반복하는 대신, 여러 품목에 공통으로 적용되는 기반을 얇게 한 층씩 쌓는다. 사용자의 3D 프린팅 비유처럼 한 층에서 정한 범위를 고르게 다루고, 그 위에 관계·근거·업무·표현을 추가한다.

r31의 원두 한 경로 우선·r32의 양파 두 경로 우선 제안과 품목 선택 질문은 **현재 개발 순서로 사용하지 않는다**. 두 예시는 후속 시험 사례로 보존한다. 국내/수입, 원산지/매입 경로, 추론 후보/확인 사실의 구분은 유지한다.

여기서 층은 작업 묶음의 비유다. H 공간 계층이나 E/G 증거 단계, 기존 기술 Layer·API 판본을 새로 정의하지 않는다. 공급 관계 범위의 순서를 바꾸는 것이며 다른 게임 WI의 승인·검증 체계를 일괄 대체하지 않는다.

## 수평 범위

첫 묶음은 기존 조사 목록의 쌀·밀가루·소고기·돼지고기·닭고기·우유·감자·양파·마늘·당근·토마토·커피 **12개 재료**를 제안한다. 이는 이미 있는 자료를 재사용하기 위한 작업 범위이며 전체 메뉴 재료를 대표하거나 조사 완료했다는 뜻은 아니다.

- 품목별로 같은 항목을 점검하되, 자료량을 억지로 같게 만들지 않는다.
- 공급처·원산지·가격 근거가 없으면 미확인과 이유를 남긴다. 자료 결손이 다른 품목 전체를 막지 않도록 한다.
- 품목·관측·분류가 기존에 있으면 참조를 연결한다. 층을 맞춘다는 이유로 다시 수집하거나 새 DB/원장으로 복제하지 않는다.
- 새 품목군은 현재 묶음의 공통 계약과 조회가 안정된 뒤 별도 묶음으로 추가한다. 수평 확장을 무제한 전수 수집으로 해석하지 않는다.

## 층별 산출물과 완료 기준

아래 번호는 다음 개발 우선순위다. 이미 있는 기능을 먼저 확인하며 각 층을 처음부터 다시 만들지 않는다. 가격 자료처럼 앞서 확보된 부분은 해당 층에서 재사용한다.

| 순서 | 12개 재료에 공통으로 쌓을 내용 | 확인 가능한 결과 |
| --- | --- | --- |
| 1. 식별·분류 기반 | 재료 ID, 이름/별칭, 규격 차이, 레시피/메뉴 참조, 원산지 근거 상태, 자료원별 코드 참조 | 모든 대상이 기존 ID 또는 명시적인 연결 결손으로 조회됨. 생두/볶은 원두, 냉장/냉동 등 차이가 보존됨 |
| 2. 공급 관계 기반 | 생산자·중도매인·식자재 업체·제조시설·가맹본부·음식점의 역할과 가능한 연결 | 재료별 적용 후보·미확인·해당 없음이 조회됨. 특정 업체의 실제 납품 사실과 역할 경로 가설이 섞이지 않음 |
| 3. 가격·통계 근거 | 기존 국내 가격, HS 무역 관측, 기준일·단위·통화·출처·규격 조건 | 같은 조회 형식으로 관측값 또는 결손 이유를 반환. 서로 비교할 수 없는 가격은 자동 합산/환산하지 않음 |
| 4. 업무 흐름 연결 | 기존 입고·검수·가공·출고·운송·인수 의미와 물품 묶음 참조 | 실제 원장 참조와 설명용 시나리오를 구별해 조회. 제조가 필요 없는 경로도 통과하며 수량·상태의 미확인을 숨기지 않음 |
| 5. 관계 탐색 | 재료·메뉴·시설 관점의 공통 노드/관계 조회와 상세 근거 | 여러 재료를 같은 방식으로 탐색하고 확인/추론/미확인 및 출처를 판독 가능. 표시를 위해 원장 상태를 바꾸지 않음 |
| 6. 공간 표현 | 검증된 읽기 결과와 기존 Unity 표현의 결속 | 후속 승인 범위에서 기존 Scene에 연결. 자료 관계 준비와 실제 Play/Game View 증거는 별도 확인 |

각 층에서 모든 품목에 같은 공급 경로를 복사하거나 없는 사실을 채우지 않는다. 공통으로 갖추는 것은 **표현·조회할 수 있는 규칙**이지 모든 재료가 같은 과정을 거친다는 결론이 아니다.

## 한 층을 닫는 방법

층마다 작은 범위의 계약 → 저장/기존 자료 연결 → 독립 재조회 → 관련 시험까지 확인 가능한 단위로 묶는다. DB 설계만 모두 끝내고 나중에 API를 붙이거나, 모든 화면을 마지막에 한꺼번에 연결하는 순서가 아니다. 이번 순서의 수평성은 품목 범위에 적용하고, 실행 검증은 작은 단위로 유지한다.

- 대상 목록·입력 판본·기존 ID를 고정하고 기존 데이터/계약을 보존한다.
- 대상별 `연결됨 / 후보 / 미확인 / 해당 없음`을 이유와 함께 보고한다. 이 표시는 조회 의미 제안이며 새 enum을 지금 확정하지 않는다.
- 저장이 필요한 층은 같은 입력 재처리의 중복 방지와 독립 재조회를 확인한다. 조회 전용 층은 원본 쓰기 없음과 동일 입력 결과를 확인한다.
- 단일 품목의 자료 결손은 기록한 뒤 다른 품목을 진행한다. 잘못된 식별자 병합, 단위 혼합, 실제 사실과 가설 혼합 같은 공통 계약 결함은 다음 층으로 넘기지 않는다.
- 미확인 수가 0이어야 다음 층으로 가는 것은 아니다. 모든 대상의 결과/결손 이유가 드러나고 공통 계약·시험이 통과했는지가 기준이다.
- 보고는 대상 수, 연결/결손 수, 코드 존재, 저장·재조회·시험의 실제 실행 여부로 한다. 근거 없는 완성도 백분율이나 모든 업무 완성 판정을 붙이지 않는다.

운영 업무를 실행해야 하는 시험에는 별도의 승인된 격리 범위가 필요하다. 설명용 공급 그래프가 실제 입고·납품·결제·정산 명령을 발생시키지 않으며, 층별 완료는 Unity나 운영 출시 완료를 뜻하지 않는다.

## 바로 다음 개발 단위

**기존 12개 재료 전체의 식별·분류·출처 연결을 같은 형식으로 조회하는 첫 층**을 준비한다. 기존 메뉴–레시피 관계와 가격 조사 목록을 대조해 공통 식별자를 연결하고, 규격/원산지/분류/관계의 확인 여부와 결손 이유를 함께 반환하는 것이 목표다.

다시 양파·커피 중 하나를 선택하도록 묻지 않는다. 필요한 경우 두 품목은 공통 규칙의 차이를 검사하는 회귀 사례로 사용한다. 실제 구현 착수 시 기존 계약·소유 파일·저장 경로·승인 범위를 확인하며 이번 문답만으로 새 게임 Goal이나 대량 수집을 활성화하지 않는다.

## 미정·질문 운영

미정은 실제 식별자 대조에서 발견될 연결 충돌, 기존 저장 구조로 표현되지 않는 결손과 구현 파일 범위다. 먼저 저장소에서 확인할 사항이며 품목 선택 질문으로 돌리지 않는다.

**다음 질문: 없음.** 사용자가 정한 수평 적층 방향을 반영한다. 근거 없는 원산지/거래 확정, 외부 공개·유료 수집 또는 기존 계약을 깨는 선택처럼 사용자 판단이 실제로 필요한 경우에만 핵심 질문 하나를 한다.

이번 변경은 r33·목차·현재 작업 문서다. 신규 수집·DB 조회/쓰기·제품 코드·Graph Map 원본·Unity·commit·push 변경 없음. 새 디오라마 규칙 후보 없음.
