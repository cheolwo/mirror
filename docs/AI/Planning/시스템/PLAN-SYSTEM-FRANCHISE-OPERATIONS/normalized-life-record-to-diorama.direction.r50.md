# 정규화한 생활 기록을 입력하면 공간 조회부터 디오라마 표현까지 이어진다

- 기준일: 2026-09-26.
- 상태: `NormalizedInputToDioramaDirectionConfirmed / InputAndPreparationContractProposed / ProductImplementationDeferred`.
- 사용자 방향: 영상 편집 전에 필요한 정보를 입력하듯이, 디오라마도 입력 정보를 정규화하고 그 정보에 따라 공간·음식점 자료를 불러와 생활상을 표현한다. 매 기록마다 Scene을 수동으로 배치하는 방식에서 반복 가능한 입력 중심 흐름으로 발전시킨다.
- 선행·상위 목적: [방문 순서·동간 연결 r49](visit-sequence-cross-dong-refactoring.proposal.r49.md)의 후속 입력 기준. [서로의 생활상을 알아보는 r47](living-world-mutual-understanding.direction.r47.md)을 유지하며, 당면 표본은 자신의 과거 음식점 방문이다.
- 연계: [입력은 영상이 아닌 방문 데이터 r48](visit-data-diorama-animation.proposal.r48.md), [표현 수명 r46](living-world-semantic-streaming.implementation.r46.md), [서버 상태→Unity 설계](../../../../Architecture/UnityServerStateToWorldProjectionDesign.md). r49의 공간 조립·동별 검증을 대체하지 않는다.
- 권위·관련 결정: 기존 비공개·읽기 전용 경계 유지. 일반 기획 답변이므로 새 전역 결정은 만들지 않는다.
- WI·PlayableLoop/인계: 신규 등록 없음, `ReadyToDispatch=false`. 입력 계약·표현 규칙은 제안이며 이번에 코드·DB·Scene을 변경하지 않는다.
- Graph Map 영향: 기록→방문→가게→확인된 공간→표현 규칙의 관계 후보. 기존 고유 식별자 대조와 승인 인계는 후속이며 Graph Map 원본·생성물을 직접 수정하지 않는다.

## 1. 목표와 관찰 경험

**충분한 입력과 준비된 자료가 있으면 지도·가게·캐릭터·순서 재생을 자동 조립하고, 부족한 부분만 구체적으로 알려준다.**

```text
기록 입력/가져오기
  → 공통 형식으로 정돈
  → 기존 가게·공간 자료 조회
  → 연결 검사와 준비 결과
  → 배치·행동 표현 계획
  → 기존 디오라마에 반영·재생
```

- 지금·여기: 관찰자가 자신의 방문 기록을 선택하고 해당 지역의 디오라마를 열려는 상황.
- 나·상대: 기록 당사자를 나타내는 대체 기사 캐릭터와 방문한 가게의 표현. 실제 사용자의 현재 위치나 실제 음식점의 현재 작업 상태가 아니다.
- 행동·결과: 목록을 입력하거나 가져온 뒤 준비 결과를 확인한다. 준비된 구간에서는 가게 표시·메뉴 카드·순차 이동이 함께 나오고, 같은 형식의 다음 기록도 Scene 수작업 없이 불러본다.
- 실패·회복: 어느 방문의 지점·위치·지도 자료가 부족한지 알 수 있고, 해당 정보만 보완하여 준비 검사를 다시 한다. 중간 방문을 숨기거나 임의 지점으로 대체하지 않는다.
- 오행 관계: 기존 역할 해석을 표현 메타데이터로 재사용할 수 있으나 이번 입력 정규화로 괘상·역할·업무 권한을 새로 확정하지 않는다. 운영·성장 규칙이 아닌 생활 관찰의 보조 표현이다.

여기서 정규화는 모든 데이터를 하나의 DB에 옮긴다는 뜻이 아니다. **가게 기준정보, 매번 발생하는 방문 사실, 지도 자료, 표현 설정을 구분하고 고유 식별자로 연결한다**는 뜻이다. 과거 기록 가져오기와 서버의 실제 운영 상태 조회는 서로 다른 입력 Adapter로 두며, 현재 표본 때문에 새로운 운영 서버나 공통 업무 원장을 만들지 않는다.

## 2. 사람이 넣는 것과 시스템이 채우는 것

아래는 입력 화면/가져오기가 따라야 할 제안이다. 사람이 좌표·행정동 코드·타일 번호·Prefab 이름을 매번 작성할 필요는 없다.

| 구분 | 입력/관리할 내용 | 책임과 부족할 때의 처리 |
| --- | --- | --- |
| 기록 묶음 | 기록 이름 또는 기존 기록 선택. 날짜는 아는 경우만 | 내부 `RecordId`, 원본 참조·판본/hash는 시스템이 관리한다. 편집일을 방문 시각으로 바꾸지 않는다. |
| 방문 순서 | 1→2→3 등 확인된 순서. 기존 목록이면 그대로 가져오기 | 명시 순서의 중복·누락을 검사한다. 원본에 순서가 없으면 입력 목록의 순서가 실제 방문 순서인지 확인받기 전 재생 기준으로 확정하지 않는다. |
| 가게 | 등록된 지점 선택, 또는 상호·지점명과 공개 주소/지역 단서 | 기존 `StoreId`와 연결하고 주소·좌표·행정동·건물 자료를 조회한다. 같은 이름의 여러 지점이면 후보를 보여주고 미확정으로 남긴다. |
| 메뉴 | 그 방문에서 기록한 메뉴. 모르면 미확인 | 메뉴 미확인은 가게 방문 표현을 막지 않는다. 자동 조회된 현재 메뉴/레시피를 그날 주문한 메뉴로 채우지 않는다. |
| 일시·기타 사실 | 실제로 확인된 경우에만 방문 일시·근거 참조 | 정확한 시간이 없으면 순서 기반 연출 시간을 쓴다. 실제 운행 시간·거리로 보고하지 않는다. |
| 공간 연결 | 원칙적으로 자동 조회·검사 결과 | 검증된 지점 좌표, 행정동 경계 판본·소속, 건물 연결, 공통 좌표·필요 타일·출처를 결속한다. 주소의 동 이름을 행정동 코드로 그대로 치환하지 않는다. |
| 표현 설정 | 판본이 있는 기본값 + 필요할 때 선택 | 대체 기사 자산, 표지, 연결선, 정차 연출, 배속·카메라. 방문 사실이나 운영 상태와 별도로 관리한다. |

가게·메뉴 등을 직접 입력하는 화면을 새로 만드는 것이 첫 선행 조건은 아니다. 기존 편집 입력을 공통 형식으로 가져오는 작은 Adapter부터 시작할 수 있다. 표·폼·파일은 입력 수단이며, Unity가 받는 검증된 의미는 같아야 한다. 매체 파일·고객 주소·정밀 개인 GPS·연락처는 이 표본의 입력에 요구하지 않는다.

## 3. 기존 계약을 보존한 연결 구조

[RegionalPickupRecordBinding](../../../../../Ssalddel.Unity/Runtime/WorldProjection/RegionalPickupRecordBinding.cs)의 현재 계약을 이번에 다시 확인했다. `RecordId`, `VisitId`, `StoreId`, `Sequence`, 메뉴/주소/좌표/지역 확인 필드가 있지만 준비 자동화 전체가 구현된 것은 아니다. [r49 감사](visit-sequence-cross-dong-refactoring.proposal.r49.md)의 순서 재생·입력 연결·다중 동 조립 결손은 계속 남아 있다. 이전 JSON 집계를 이번에 재수행하지 않았다.

### 원본 → 입력 초안 → 검증된 방문 사본

- 원본 편집 자료는 보존한다. 상호 문자열만 들어온 미해결 초안을 바로 기존 `RegionalPickupRecord`의 검증된 방문으로 취급하지 않는다.
- 원본 항목 ID와 연결해 `VisitId`를 안정적으로 부여한다. 재입력해도 중복 방문을 만들지 않고, 정정은 같은 방문의 새 판본으로 구분한다. 배열 인덱스·순서만으로 ID를 매번 새로 만들지 않는다.
- 가게 결속 전에는 임의의 실제 `StoreId`를 발급하지 않는다. 기존 편집용 ID와 서버 가게 ID가 서로 다르면 출처별 대응 관계를 먼저 확인한다. 값의 이름이나 형태가 비슷하다는 이유로 같다고 간주하지 않는다.
- 가게 객체는 `StoreId`로 재사용하고 재방문은 서로 다른 `VisitId`로 남긴다. 메뉴 관찰도 각 방문에 속한다.
- `delivery-visit-record.v2`, `RecordedVisit`, `LocalReviewOnly=true`, `IsOperationalState=false` 및 픽업 완료 확정 거절을 유지한다. 현재 계약에 임의로 새 업무 사건을 섞지 않는다.
- 운영 서버의 주문·조리·배송 확정 상태는 나중에 기존 운영 관찰 계약과 권한 검사를 통해 별도로 들어온다. 방문 입력만으로 그런 사실을 보충하지 않는다.

### 자동 조회는 기존 자료의 재사용부터

확인된 지점 ID → 공개 가게 위치 → 판본이 있는 행정동 소속 → 필요한 동/타일 → 배치 후보 순으로 연결한다. 지점·주소·좌표·원본 판본이 유지될 때 확인 결과를 재사용하며 변경·상충이 있으면 관련 결속만 다시 검사한다. 같은 가게를 방문할 때마다 사람에게 주소를 다시 쓰게 하지 않는 것이 목표다.

조회는 보유 자료와 허용된 기존 읽기 경로를 우선한다. 자료가 없다는 이유로 Unity 실행 중 임의 크롤링·새 유료 API 호출·DB 직접 접근·전체 지역 수집을 시작하지 않는다. 수집이나 위치 확인이 필요한 항목은 별도 보완 목록으로 반환한다. 과거 방문과 현재 가게/지도 자료의 기준 시각을 함께 보존하며 현재 자료가 과거 상황을 소급 증명하지 않도록 한다.

## 4. 준비 결과를 거친 뒤 표현을 조립한다

사용자가 입력을 끝냈다는 사실과 공간이 준비됐다는 사실을 구분한다. 입력 한 묶음의 검사 결과에는 다음을 남기는 안을 제안한다.

- 채택한 기록 ID·원본 판본/hash와 방문 목록.
- 가게·공간·지도·표현 규칙의 참조와 판본/hash.
- 방문별로 바로 표현 가능 / 대체 표현 가능 / 필수 자료 보류 및 구체적인 부족 항목.
- 필요한 동·물리 타일·동별 도형 조각과 현재/다음 구간 로드 범위.
- 가게·기사 표지의 고유 식별자, 위치 근거, 선택할 표현 규칙과 재생 순서.

이 결과는 업무 원장이 아닌 **다시 계산할 수 있는 표현 준비 결과**다. 원본을 바꾸지 않으며 초기에는 비공개 메모리 결과로 충분하다. 동일 입력·자료 판본·표현 규칙이면 동일한 배치/재생 계획이 나와야 한다. 실행 시각 같은 진단값과 결정적 결과를 분리한다.

| 부족한 것 | 제안하는 처리 |
| --- | --- |
| 정확한 가게 모델/외관 자산 | 검증된 위치에 기존 저폴리 대체 건물 또는 중립 표지. 실제 외관 복원으로 표시하지 않는다. |
| 건물·출입구 결속 | 검증된 가게 좌표에 중립 표지. 임의 출입구를 만들지 않는다. |
| 메뉴 | 방문 재생은 허용, 메뉴 카드만 미확인. AI 음식 이미지를 채워 넣지 않는다. |
| 실제 방문 시각·주행선 | 확인된 순서와 연출 시간·표현용 연결선을 사용. 실제 경로나 소요 시간으로 표시하지 않는다. |
| 지점 식별·좌표·지역의 필수 근거 | 해당 방문과 연결 구간을 보류한다. 2번을 생략하고 1→3을 실제 연속 구간처럼 자동 연결하지 않는다. |
| 필수 지도 조회/판본 검증 실패 | 해당 구간 진입을 멈추고 재시도/부족 목록을 표시한다. 조회 실패를 가짜 지역 샘플로 숨기지 않는다. |

준비 결과가 허용한 대상만 기존 `SimulationWorldShell`에서 생성·갱신·제거한다. 한 번 확인한 가게는 재사용하고, 방문 목록이 달라져도 전체 장면을 매번 재생성하지 않는다. 메뉴 정정은 메뉴 표현에, 위치 정정은 공간 결속·해당 구간에 영향을 주도록 의존 관계를 분리한다. 해제·반복 로드·요청 취소와 동간 공통 원점·지면 중복 방지는 r49를 따른다.

## 5. 생활상 표현 규칙의 첫 범위

첫 표현 규칙은 **음식점 방문 순서** 하나로 제한한다.

`기록 선택 → 관련 지역/가게 준비 → 기사 기호 등장 → 방문 번호 순으로 이동 → 가게 강조 → 선택 시 메뉴/근거 보기 → 재생 종료`

기사가 화면상 가게에 도착한 것은 기록 재생의 한 장면이지 픽업 인수 완료가 아니다. 방문만 있는 기록에서 조리·적재·배송 완료를 자동 생성하지 않는다. 가상의 연출을 추가하려면 기록 사실과 별도 표시·기획이 필요하다.

후속으로 창고 입고·프랜차이즈 납품 등의 생활상을 표현할 때도 **입력·검사·자료 결속·표현 준비의 공통 뼈대**를 재사용하되, 각 업무의 상태 의미와 권위는 해당 OS 계약이 소유한다. 모든 업무를 하나의 범용 Event나 거대한 규칙 엔진으로 합치는 것은 이번 제안이 아니다.

## 6. 다음 개발 단위와 인수 기준

r49의 첫 단계인 입력 준비를 이 방향으로 구체화한다. 구현 후보 순서는 다음과 같다.

1. 기존 편집 입력을 최소 방문 초안으로 읽고 입력 검사·부족 목록을 돌려주는 경로.
2. 기존 가게·좌표·지역 자료와 결속하고 표현 준비 결과를 만드는 경로.
3. 같은 결과를 r49의 순서 재생과 동간 공간 조립에 연결하는 경로.
4. 입력만 바꾼 두 번째 기록으로 같은 기능을 반복 검증하는 경로.

인수 기준은 첫 기록의 화면이 한 번 나오는 것에 그치지 않는다.

- 준비된 범위에서 다른 기록을 넣어도 Scene·Prefab·코드를 수동 수정하지 않고 해당 방문·가게·순서가 바뀐다.
- 같은 입력을 두 번 넣어도 가게·방문·캐릭터가 중복 생성되지 않고 재방문은 보존된다.
- 모호한 지점·미확인 위치·누락 메뉴를 각각 보류/대체 표현 기준에 맞게 처리한다.
- 입력 정정·자료 판본 변경 시 영향을 받은 결속과 표현만 무효화하고 다시 준비한다.
- 권한·공개 범위를 넘는 조회나 원본 업무 상태 변경이 없고 운영 완료를 만들어내지 않는다.
- 입력/준비 결과 자동 시험, 실제 자료 조회, Play Mode, Game View는 별도로 검증한다. 이번 문서 작성은 그 구현 증거가 아니다.

## 확정 / 미정 / 다음 질문

- 확정: 정규화한 정보 입력에서 관련 자료 조회·공간 조립·생활상 표현까지 이어지는 반복 가능한 구조를 지향한다. 기존 편집 자료를 재사용하고 매번 수동 배치하는 부담을 줄인다.
- 제안: 사람 입력·자동 조회·표현 설정을 분리하고, 표현 준비 결과를 거쳐 첫 방문 순서 규칙으로 연결한다. 입력만으로 모든 미지의 사실을 자동 완성한다는 뜻은 아니다.
- 미정: 구체 입력 UI, 가져오기 형식별 Adapter, 첫 표본, 조회 경로의 실제 연결, 표현 규칙 판본·자원 예산과 개발 인계. 이 세부안 전체를 승인된 구현 명세로 간주하지 않는다.
- 다음 질문: 지금 없음. 다음 구체화는 기존 방문 자료의 필수/선택 필드와 준비 결과를 작은 표본 하나에 적용하는 것이다.
