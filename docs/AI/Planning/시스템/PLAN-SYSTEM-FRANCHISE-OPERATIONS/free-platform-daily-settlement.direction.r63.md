## 확정한 방향

사용자는 배달 활동으로 생활 수입을 마련하면서 앱과 영상을 만들고 있다. 초기 플랫폼은 수익화보다 무료로 이용할 수 있는 업무 흐름의 완성을 우선한다. 외부 API의 무료 제공 범위를 최대한 활용하고, 비용과 이용 규모가 늘면 추후 과금을 검토한다. 배달·촬영 활동은 앱 개선의 자료이며 새로운 촬영을 앱 완성의 선행 조건으로 만들지 않는다.

무료 방향의 대상은 플랫폼 이용이다. 음식 주문대금, 기사 노동의 배달대금, 결제·송금 비용과 서버 운영비는 각각 별도로 기록한다. 모든 비용이 없어진다거나 사용자가 무제한으로 운영비를 부담한다는 약속으로 확대하지 않는다. 참여 역할별 무료 범위와 실비 부담 주체는 아직 구체화하지 않았다.

기사 배달대금의 당일 정산·지급을 우선 목표로 해석한다. 당일 금액 집계에 그치지 않고 실제 당일 입금까지 이어지는 흐름을 목표로 삼되, 지급 수단·시간창·재원을 확인하기 전에는 상시 당일 입금을 보장한다고 표시하지 않는다. 음식점 매출과 지사 대금에도 같은 지급 주기를 적용할지는 미정이다.

## 기존 정책과의 관계

[r60](delivery-app-parallel-completion.direction.r60.md)의 영업이익 4% 목표는 과거 방향으로 보존한다. 초기 과금을 시작할 근거로 사용하지 않으며, 영구 폐기나 새로운 건당 수수료율로 해석하지 않는다. 향후 과금 범위·요금·공지·동의·적용일을 결정할 때 재검토한다.

[기존 이용량·구독 기획](../PLAN-SYSTEM-USAGE-COST-SUBSCRIPTION-METERING/README.md)의 사용량 기록은 운영비를 파악하는 데 재사용할 수 있다. 기록이 쌓이는 것만으로 청구를 발생시키지 않는다. 현재 금액 설정·구독·수수료를 이번 문답에서 0으로 변경하지 않았으며, 무료 정책의 제품 적용은 별도 명세로 연결한다.

[기사 지급 상세](../../공통/PLAN-OPERATIONS-FOOD-DRIVER-PAYOUT-DETAIL/README.md)의 동결 배차 금액, 총액·공제·수령액 구분, 월 보험 확정 경계는 유지한다. 기존 주간 정산 이력을 일간 정산으로 재작성하지 않는다. 기사 월정산 페이지의 플랫폼 이용료 결제를 기사 배달대금 지급으로 재명명하지 않는다.

## 당일 정산·지급 흐름 제안

| 단계 | 기존 흐름에 이어 붙일 내용 | 완료 근거 |
| --- | --- | --- |
| 배달 완료 | 서버가 완료·최종 기사·책임 지사·수락 시 동결 금액을 확인 | 기존 배달 원장과 완료 상태 대조 |
| 일별 정산 | 한국 시각의 완료일·마감 정책으로 대상 확정, 공제 근거와 미확정 항목 분리 | 같은 배달을 중복 포함하지 않는 정산 내역 |
| 지급 준비 | 실제 지급 가능 잔액과 미지급 채무 확인, 보류 이유와 지급 예정 시점 안내 | 확보된 재원·지급 대상·지급액의 대조 |
| 지급 요청 | 선택한 지급 수단의 허용 시간 내 요청, 재시도에도 중복 지급 방지 | 동일 지급 식별자의 요청·조회 결과 |
| 지급 확인 | 최종 성공 응답·지급 증빙을 확인한 뒤 지급 완료 표시 | 요청 성공과 실제 지급 성공의 분리 |
| 후속 조정 | 취소·환불·보험 월 확정 차액을 별도 조정 내역으로 연결 | 과거 정산과 지급 내역 보존 |

마감 시각은 아직 정하지 않았다. 일별 공제 가계산과 월 확정 금액을 구별하며, 미확인 공제를 0으로 채우거나 영상의 개인 정산 비율을 플랫폼 전체의 실제 공제로 적용하지 않는다. 기존 계산 검토 API는 지급 완료의 근거가 아니다.

PG 매출 발생액과 현재 지급 가능한 현금도 구별한다. PG 정산 전에 기사에게 지급하려면 그 사이의 지급액을 충당할 재원이 필요하다. 금액·한도는 주문량과 정산 지연을 확인한 뒤 정하며, 현재 사용자 배달 수입을 플랫폼 지급 재원으로 편입하지 않는다.

## 무료 API 활용과 확인한 공식 자료

조회 기준일은 2026-10-02다. 제공사 전체 비용이 무료라고 판단하지 않으며 계정 자격, API별 월 한도, 상업 이용·보관 조건, 초과 과금과 장애 시 동작을 확인한다. 기존 SDK와 서버를 재사용하고 실제 호출량·저장량·운영비를 먼저 측정한다. 한도 도달 시 새 외부 호출의 제한과 진행 중 주문의 완료·정산 방법을 따로 설계한다.

- [네이버 Maps 무료 이용량 FAQ](https://www.ncloud.com/support/faq/all/2828): 무료 이용량은 대표 계정에 제공되고 여러 Application의 사용량을 합산한다. 콘솔의 한도·알림 설정을 활용하되 전체 Application의 한도 합계를 함께 관리한다. 현재 프로젝트 계정의 무료 자격·키·콘솔 설정은 확인하거나 변경하지 않았다.
- [토스페이먼츠 지급대행 공식 안내](https://docs.tosspayments.com/guides/v2/payouts): 지급 가능 잔액과 미정산 잔액을 구별한다. 예시 서비스의 바로지급은 영업일 08:00~15:00 요청으로 제한되며 라이브 요청에 비용이 발생한다. 야간·휴일을 포함한 기사 당일 지급에 그대로 적용할 수 있다고 단정하지 않는다. 해당 안내는 셀러 지급대행의 사례이며 기사 지급 적합성·계약·제공사 선택은 미정이다.

위 자료는 비용·시간창·재원을 검토할 근거다. 특정 업체를 계약하거나 외부 송금을 실행한 결과가 아니다.

## 우선순위와 남은 결정

1. 기존 주문→주문 확인→기사 배차→조리→전달 흐름과 본인 거래 조회를 완성한다. 별도 앱을 새로 만드는 의존성을 추가하지 않는다.
2. 기사 일별 정산 내역과 서버 원장의 연결을 명세화한다. 완료일·마감·공제 확정·보류·조정·중복 방지의 대표 사례를 기존 화면에서 검증하는 작은 구현 범위를 먼저 정한다.
3. 지급 재원·기사 지급이 가능한 수단·시간창·비용을 확인한 뒤 실제 당일 지급 연결을 검증한다. 그 이후 이용량에 따른 과금 여부를 검토한다.

미정은 무료 범위·운영비 예산, 정산 대상 역할, 마감 시각, 지급 재원과 한도, 지급 수단, 월 확정 차액 처리다. 지금 방향 기록에 필요한 다음 질문은 없다. 이 문서는 제품 코드·DB·실지급·운영 활성화를 바꾸는 구현 명세나 실행 결과가 아니다.
