## 확정한 검토 가정과 계산

고객 배달비3,000원과 음식점 배달비3,000원을 합쳐 **주문1건당6,000원**을 배달 재원으로 확보한다고 가정한다. 음식 주문대금과 별개이며 매출에 비례한 플랫폼 수수료는0이다. 기사에게는 기존 기록의 세전 배달료를 지급하고, 예비금 사정으로 지급액을 감액하지 않는다. 이 금액은 초기 모델 검토 입력이며 실제 요금 공지·결제·지급의 활성화가 아니다.

```text
주문별 배달 재원 = 고객 배달비 + 음식점 배달비
주문별 차액 = 배달 재원 − 기사 세전 지급액
차액 > 0: 예비금 적립
차액 < 0: 예비금에서 부족액 충당
예비금 잔액 = 시작 자금 + 실제 확보한 배달 재원 − 기사 지급액 − 별도 비용/보상
```

적립액/인출액은 동일 차액의 설명이다. 기사 배달료와 적립/인출을 중복 차감하지 않는다. 기사 원천세·보험을 원천 공제하더라도 납부 채무가 남으므로 기사 수령액만으로 플랫폼 비용을 계산하지 않는다. 고용주 보험·지사 보수·결제·환불·세금 등 확인되지 않은 별도 비용은 비용 제외 또는 명시적인 가정으로 표시한다. 실제 비용0으로 확정하지 않는다.

## 기존 실적을 사용한 실제 재현 결과

09.23~10.01 최신 구술 접수9개 파일, 배달273건을 SHA와 함께 읽고 건별 ID·날짜·입력 순서·건수/배달료 합계를 검산했다. `history/`·영상 방문·메뉴 펼친 행을 중복 합산하지 않는다. B마트17건은 따로 구분하여 음식점256건을 기본 표본으로 사용한다. 개인 실적 원문과 결과는 Git 제외 로컬 산출물로 보존한다. 6,000원과 같은 배달료는0건이며 적립/부족액이0원이다.

| 음식점256건, 별도 비용 제외 | 금액 |
|---|---:|
| 확보 재원256×6,000원 | 1,536,000원 |
| 기사 세전 배달료 | 1,005,020원 |
| 저렴한 배달251건에서 적립한 차액 | 534,230원 |
| 비싼 배달5건의 부족액 충당 | 3,250원 |
| 최종 잔액 | **530,980원** |

구술 입력 순서·같은 주문 지급 전 배달비 확보 가정에서는 시작 자금0원으로 음수 잔액이 발생하지 않았다. 실제 완료/결제 시각이 없고 운영비도 제외되어 있으므로 무자본 운영 가능이나 지급 안정성 보장으로 해석하지 않는다.

| 비교 가정 | 최종 잔액 | 재현 경로를0원 이상으로 유지할 추가 시작 자금 |
|---|---:|---:|
| 음식점 · 즉시 확보 · 비용 제외 | 530,980원 | 0원 |
| 음식점 · 건당 비용250원 가정 | 466,980원 | 0원 |
| 음식점 · 건당 비용500원 가정 | 402,980원 | 0원 |
| 음식점 · 건당 비용1,000원 가정 | 274,980원 | 0원 |
| 음식점 · 양쪽 배달비1일 뒤 확보 | 530,980원 | 148,580원 |
| 음식점 · 고객 즉시/점주1일 뒤 | 530,980원 | 34,580원 |
| 이전 비교 · 고객/음식점 각2,500원 | 274,980원 | 0원 |
| B마트 포함 · 비용 제외 | 563,480원 | 0원 |
| 09.23~29 전체 · 기존 별도 보상 지급 | 90,860원 | 0원 |

250/500/1,000원은 실제 PG 수수료가 아닌 비용 부담 범위를 보는 가정이다. 지연은 달력 날짜 기준이며 그날의 배달 전에 입금된다고 가정한다. 실제 PG 영업일·입금 순서와 다르다. 표의 최종 잔액은 지연 대금까지 모두 들어온 이후 금액이며, 마지막 배달일의 실제 사용 가능 현금과 구분한다. 양쪽1일 지연 사례의10.01 종료 현금은332,980원이고 미수금198,000원이 다음 날 들어온 뒤530,980원이 된다.

기존 별도 보상 비교는 같은 전체204건에 미션182,000원+건수 보상104,000원+달성 보너스30,000원을 한 번씩 반영한다. 건별 배달료에 이미 포함된 피크/거리/B마트 할증은 다시 더하지 않는다. 보상을 음식점197건에 임의 배분하거나 자체 플랫폼의 보상 정책으로 채택하지 않는다. 부가세·보험 고용주 부담·기타 운영비는 여전히 별도다.

## 구현한 도구와 검증 경계

`simulate_reserve.py`의 `simulate()`는 정수 원 단위의 시작 자금·보호 하한·건당/일별 비용·고객/음식점 입금 지연·별도 비용을 입력받는다. 주문별 적립/인출·현금 잔액·발생 잔액·미수금·자금 결손과 일별/전체 합계를 반환한다. 마지막 주문 뒤의 지연 입금도 별도 날짜로 처리하며 차액의 자금 보존을 검산한다. 음수 잔액은 필요한 추가 재원이지 실행된 마이너스 계좌나 성공 송금이 아니다.

영상용 전체 접수 확인과 금액 분석 범위는 다르다. 09.23·10.01 원문의 전체 접수 미확인 상태를 그대로 source snapshot에 남겼다. 날짜·배달료·건수 검산을 위치/메뉴/원본 연결의 확인 완료로 확대하지 않으며 편집 preflight나 영상은 변경하지 않았다.

독립 금액 사례12개를 통과했다. 비싼 배달 우선의 순서 위험, 마지막 잔액 양수지만 중간 음수, PG 미수금/현금 분리, 시작 자금/보호 하한, 기사 세전 비용과 추가 비용의 중복 방지, 중복 ID/순서·미확인 금액 차단, 기간 비용 범위, 접수 상태 보존을 검사했다. 실제9원문+기존 보상 근거는 실행 전후 SHA가 동일하다.9비교 시나리오를 실제로 실행했고 앱·서버 HTTP·DB·은행 지급의 새 실행 증거는 아니다.

검토 결과는 `artifacts/local/food-delivery-reserve/20261002-r2/scenarios.json`, `공동배달비-예비금-검토.html`이다. 재현 결과·개별 기록/경로·원문은 공개·GitHub push 대상이 아니다. 도구와 일반 정책 설명만 저장소 변경 대상이다.
