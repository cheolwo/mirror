## 확정

사용자는 당일 정산·당일 입금이 이루어진다는 가정 아래 **주문 한 건을 업무의 기준 단위**로 삼고 싶다고 밝혔다. 주문번호로 접수·배차·조리·전달·정산·지급 결과를 연결한다. 먼저 대표 주문 한 건이 끝까지 이어지는 좁은 흐름을 완성하고 같은 구조로 여러 주문을 처리한다.

당일 입금은 설계·시험의 정상 경로 가정이다. 운영 재원과 지급 수단이 마련됐다는 실제 증거나 실송금 승인으로 해석하지 않는다. r63의 무료 이용 방향과 미정 지급 대상 역할·재원·마감 조건은 유지한다.

## 주문 한 건의 업무 흐름

`주문 등록 → 결제 확인 → 음식점 주문 인지 → 기사 배차 확정 → 조리 시작 → 픽업 → 전달·수령 확인 → 주문별 정산 → 당일 지급 요청 → 입금 결과 확인`

결제 확인은 해당 주문의 결제수단·정책에 따른 단계이며 첫 시험에서는 모의 결제만 사용한다. 기사 배차 확정 이후 조리 시작이라는 r62의 순서는 유지한다. 전달과 주문자 수령 확인도 기존 업무 의미와 서버 검증을 보존한다. 자동 수령 확정 시간이나 고객 확인 지연 시 지급 조건을 새로 정하지 않는다.

위 흐름은 사람이 보는 업무 순서다. 기존 주문 완료 상태를 지급 완료 상태로 바꾸거나 공개 API의 상태 문자열을 재정의하지 않는다. 배달 진행과 정산·지급 진행은 각각 기록하고 주문 상세에서 함께 조회한다. 이미 배달된 주문의 지급이 실패하면 배달 완료 사실은 유지하고 지급 문제를 표시한다.

## 주문번호로 묶을 정보

| 정보 | 주문에 연결할 기록 | 기준 |
| --- | --- | --- |
| 주문·상품 | 주문자·음식점·상품·수량·주문대금 | 기존 주문과 상품 기록 재사용 |
| 결제 | 승인·취소·환불·현재 잔액의 참조 | 과거 승인 사실과 현재 지급 가능 자금 구별 |
| 배차·배달 | 제안·배달 시도·최종 유효 기사·책임 지사·픽업/전달 시각 | 재배차 이력 보존, 지급 대상 중복 방지 |
| 기사 대금 | 수락 때 동결한 배달료와 구성 근거 | 주문대금·고객 배달비와 구별, 완료 시 새 요율로 재계산하지 않음 |
| 정산 | 주문별 지급 대상액·공제/배분 근거·수령액·보류 사유 | 미확정 금액의 상태를 보존 |
| 입금 | 지급 식별자·대상·주문별 배분·요청/성공/실패·증빙 | 요청 완료와 실제 지급 완료 구별 |
| 조정 | 취소·환불·월 확정 차액·이의 처리 | 원래 정산과 지급 내역을 보존한 별도 조정 |

DB 내부의 기존 숫자 Id와 외부 주문번호는 각각 유지한다. 배달 시도·정산·지급 기록의 고유 식별자는 독립적으로 보존하고 검증된 관계로 주문번호까지 추적한다. 한 주문에 여러 재배차 시도가 있어도 정상 완료 대금은 최종 유효 수행과 연결한다. 별도 중단 보상은 확정 정책이 있을 때 독립 항목으로 기록한다.

일별 목록은 주문별 정산을 날짜로 모아 보는 집계다. 기간 단위 미션·프로모션·보험 확정은 기간 원장에 남기고, 주문별로 배분할 때 그 근거를 연결한다. 각 주문에 기간 보상을 통째로 복제하거나 월 보험을 건마다 독립 확정하지 않는다.

송금은 기사·음식점별로 당일 여러 주문을 합칠 수 있다. 이 경우 지급 기록에 주문별 배분을 남겨 각 주문의 지급 여부를 확인한다. 주문 한 건을 기준으로 삼는다는 선택이 건마다 은행 송금 한 번을 의무화하는 뜻은 아니다. 실제 묶음 지급 여부와 음식점/지사 지급 범위는 후속 결정이다.

## 기존 코드와의 대조

- [음식주문](../../../../../Ssalddel.Domain/음식/음식주문.cs)은 `Id`, `주문번호`, 주문대금·상태·배차 참조와 과거 결제승인 사실을 이미 가진다. 현재 환불 잔액·정산·지급 완료로 승인 필드를 해석하지 않는다.
- [음식배달시도](../../../../../Ssalddel.Domain/음식/음식배달시도.cs)는 주문번호·제안Id·기사Id·시도StableId·수락/픽업/전달 시각을 가진다. 새 주문 중심 흐름의 배달 이력 연결로 재사용한다.
- [주문자 수령 확인 Handler](../../../../../Ssalddel/Application/Food/Handlers/주문자음식주문수령확인CommandHandler.cs)는 요청 식별자·본인·현재 상태를 검증하고 새 변경에만 이벤트를 발행한다. 이 Handler 확인만으로 정산 원장이나 송금이 연결됐다고 판단하지 않는다.
- [기사 운송대금 지급 요청](../../../../../Ssalddel.Domain/기사/기사운송대금지급요청.cs)과 [지급 승인 UseCase](../../../../../Ssalddel/Application/Admin/Settlement/기사지급승인UseCase.cs)는 운송/의뢰·기사·금액·멱등키·승인·Outbox의 기존 패턴이다. 음식 주문별 공제·최종 지급 대상·정산 배분까지 연결됐는지 별도 확인해야 하며 현재 그대로 음식 당일 정산 구현이라고 보고하지 않는다.
- [기존 모바일 검증 r1](../../../../ProjectOverview/page-docs/mobile-polish-r1.md)은 한 합성 주문의 역할 앱·서버 업무 연결을 확인했다. 실제 음식 주문의 당일 정산·입금 검증은 포함하지 않았다.

서버가 주문·배달·금액·지급 상태를 확정한다. 역할 앱은 기존 화면과 권한으로 본인 업무를 수행하고 결과를 읽는다. 외부 지급 요청과 응답은 기존 Outbox·재시도 방식의 재사용 가능성을 검토하며, 응답 유실 시 같은 지급 식별자의 결과를 먼저 조회한다.

## 첫 구현·검증 단위 제안

1. 주문번호로 주문·현재 배달 시도·동결 배달료·정산·지급을 함께 조회하는 기존 화면/API 경로와 결손을 대조한다. 우선 범위는 주문자·음식점·기사 각 1명, 주문 1건, 배달 1회다.
2. 격리 `Simulation`에서 같은 주문의 등록부터 수령 확인까지 실행한 뒤 주문별 정산 기록과 모의 지급 결과를 결속한다. 지급 재원 확보·유효 지급 대상·확인된 공제 기준·한국 시각 같은 날 안의 성공을 정상 시험 입력으로 명시한다.
3. 반복 완료 알림·지급 재시도·재배차·모의 지급 실패·날짜 경계에서 중복 정산과 중복 입금이 없는지 확인한다. 실패를 지급 완료로 표시하지 않으며, 날짜 경계를 넘긴 지급은 원래 정산일과 실제 지급일을 따로 남긴다.
4. DB 재조회와 기존 역할 앱에서 동일 주문번호·금액·배달 상태·정산 상태·지급 결과를 대조한다. 모의 지급은 화면과 기록에서 표시하고 실제 은행 입금 완료로 승격하지 않는다.

완료 기준은 주문 1건의 업무 이력·금액 근거·정산·모의 지급 증빙이 끊김 없이 이어지고 앱에서 같은 결과를 확인하는 것이다. 상세 DB migration·API 계약·UI writePaths와 자동 공제/지급 승인 정책은 이 방향만으로 확정하지 않는다.

## 미정·이번 변경 범위

수령 확인 지연 시 지급 조건, 마감 시각, 세금/보험 월 확정과 당일 지급 차액 처리, 음식점/지사 당일 지급 범위, 운영 재원·지급 수단은 미정이다. 방향을 기록하기 위한 다음 질문은 없다. 실제 지급 범위를 넓히기 전에 해당 작은 구현 명세에서 필요한 결정만 다룬다.

이번에는 이 방향 문서와 PLAN 목차·기획 목차·현재 작업만 갱신했다. 기존 제품 코드·DB·요율·지급 설정·영상과 다른 미커밋 작업은 보존한다. 당일 정산 API·정산 원장·실송금의 새 구현은 아직 수행하지 않았다.

검증: 문서4경로 Fast(`20261002-133624`)·`git diff --check` 통과. 본문의 로컬 링크10개 존재와 새 문서의 끝 공백 없음을 확인했다. 문서 전용 검사이며 제품 build·업무 시험·모의 지급 실행은 하지 않았다.
