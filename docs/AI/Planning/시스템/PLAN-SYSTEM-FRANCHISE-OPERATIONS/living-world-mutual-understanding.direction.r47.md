## 확정한 목적

**업무 데이터가 보여 주는 사람들의 행동과 연결을 통해, 서로의 삶을 알아봐 주는 관찰 경험을 지향한다.**

처리량·진행률만 나열하는 것으로 목적을 달성했다고 보지 않는다. 관찰자가 누가 어떤 일을 하고, 그 일이 누구의 다음 행동을 가능하게 하는지 이해하도록 설계한다. 다만 이해·친밀감이 실제로 생겼다는 효과를 코드 존재나 자동 시험으로 증명하지 않는다. 사람의 추후 화면 검토가 필요하다.

## 서버와 Unity의 역할

`서버가 확정한 업무 사실 → 공개 권한·비식별 상태 사본 → 역할·행동·인계의 해석 → Unity 생활상 → 선택 시 근거`

- 서버는 주문·조리·픽업·인계 등의 사실, 시각, revision과 공개 범위를 소유한다.
- 해석은 같은 사실에서 현재 행동과 연결된 역할을 읽는다. 자료 결손·대기·갱신 실패를 구별하며 개인의 마음이나 성실성을 판정하지 않는다.
- Unity는 허용된 현재 단계 안에서 행동·이동·기다림·인계를 표현한다. 상대의 다음 일을 가능하게 하는 연결이 보이도록 하되, 애니메이션이 업무를 완료하거나 새 실제 사실을 만들지 않는다.
- 클릭 시에만 현재 하는 일·다음 인계·근거와 마지막 확인 시각을 간단히 확인하는 구성을 제안한다. 기본 화면은 행동 중심, 자세한 글은 선택 뒤라는 r45 방향을 유지한다.

새로운 감정 추론 엔진·사람 평가 점수·상호작용 서버를 만들자는 뜻이 아니다. 기존 상태 사본·OS 분배·선택·표현 경로를 먼저 재사용한다.

역할 간 연결도 같은 업무 연결키·시각·revision과 확인된 인계 관계가 뒷받침해야 한다. 비슷한 시각에 일어났다는 이유만으로 다른 사람을 지연의 원인으로 지목하지 않는다. 원인이 기록되지 않았으면 모르는 상태로 남긴다.

## 첫 음식 배달 장면의 해석 예시 — 제안

| 관측된 사실이 있을 때 | 보여 줄 생활상 후보 | 단정하지 않을 것 |
| --- | --- | --- |
| 음식점이 조리를 시작함 | 음식을 준비하는 역할과 이후 픽업 인계 | 인기·맛·조리사의 감정 |
| 기사가 픽업 대기 단계임 | 준비를 기다리고 받아 갈 역할 | 태만·귀책·장소의 정확한 현재 GPS |
| 픽업 인수가 확정됨 | 음식점의 준비가 기사의 전달로 이어짐 | 수령 완료·검증되지 않은 실제 주행 경로 |
| 주문자의 수령 확인이 확정됨 | 여러 역할의 일이 한 식사 전달로 이어짐 | 만족·감사·친구 관계의 자동 성립 |

지연도 확인된 사유까지만 설명한다. '주문이 많아서'는 실제 업무량·등록 사유가 뒷받침할 때만 쓰고, '맛집이라 늦었다'처럼 좋은 의도로라도 사실을 꾸미지 않는다. 휴식·대화도 생활상 후보지만 데이터가 없으면 실제 사람의 행동으로 만들지 않는다. 가상 장면은 가상이라고 구별한다.

## 공개와 관계의 경계

상호 이해라는 목적이 개인 공개 동의를 대신하지 않는다. 특정인의 실시간 위치·근무시간·사적 생활을 기본 노출하지 않는다. 재식별 위험이 있으면 집계·익명 역할 또는 비표시를 사용하며, 관련 권한·동의가 없는 현재 표본을 실제 사람과 연결하지 않는다.

업무 사실·관찰 공개·이야기 발행·메시지·친구 요청·연락처 공유는 기존 기준처럼 분리한다. 이번 방향 확인으로 감사 알림·채팅·친구 요청·공개 게시·근무 평가 기능을 자동 추가하지 않는다. 오행·괘상 역시 서로의 역할을 이해하는 선택적 설명이지 실행·평가 권한이 아니다.

## 현재 구현과의 간격

r46은 사가정 음식 표본의 상세 표시·해제·최신 복귀와 TTL을 확인한 **표현 수명 기반**이다. 사람의 생활을 충분히 알아볼 수 있는 행동 연출·이해 카드·실제 업무 데이터 연결까지 완료한 것은 아니다. 현재 검증용 큰 상태 패널은 최종 경험으로 확정하지 않는다.

구체적 개발 후보는 기존 음식 표본에서 한 역할의 행동과 인계 이유를 먼저 읽히게 하는 작은 보완이다. 기존 정상·회복 상태 사본을 재사용하며 새 공급망 통합·전국 공간 확장·서버 실행을 선행 조건으로 추가하지 않는다. 아직 실행하지 않는다.
