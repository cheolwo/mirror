# 기록을 보관하고 원할 때 Unity로 보내 디오라마에서 본다

- 기준일: 2026-09-26.
- 상태: `OptInUnitySendDirectionConfirmed / RecordStorageAndDeliveryFlowProposed / ProductImplementationDeferred`.
- 사용자 방향: 입력한 자료를 정리·보관하고, 원하는 경우 보내기를 선택하면 Unity와 연결되어 표현되도록 한다. 기존 자료 가져오기 외에 직접 입력도 가능해야 한다.
- 해석 범위: 이번 문서에서는 자료 보관을 DB화하는 방향으로 이해했다. 구체 DB 종류·테이블·저장 위치는 아직 선택하지 않았다.
- 선행·상위 목적: [정규화 입력→표현 r50](normalized-life-record-to-diorama.direction.r50.md), [순서 재생·동간 공간 연결 r49](visit-sequence-cross-dong-refactoring.proposal.r49.md), 서로의 생활상을 알아보는 관찰 목적.
- 관련 결정·권위: 기존 비공개 기록·읽기 전용 표현 경계를 유지하며 새 전역 결정은 만들지 않는다. 관련 WI·PlayableLoop 신규 등록 없음, `ReadyToDispatch=false`.
- Graph Map 영향: 기존 기록·판본→사용자가 선택한 전달 대상→표현 준비 결과 관계 후보. 원본/생성물은 수정하지 않는다.
- 이번 범위: 방향과 권장 흐름의 문서화만. 실제 저장·전달 API·DB·Unity를 구현하거나 실행하지 않는다.

## 1. 사용자에게 보이는 흐름

```text
직접 입력 / 기존 자료 가져오기
          ↓
내 기록으로 저장 → 목록에서 다시 열고 수정
          ↓ 사용자가 원할 때
[Unity로 보내기]
          ↓
자료 준비·연결 검사 → Unity에서 불러오기 → 디오라마 표현
```

관찰자는 자신의 기록 목록에서 한 묶음이나 명시적인 방문 구간을 선택한다. 기본 전송 대상은 본인 권한의 Unity 관찰 세션으로 제안한다. 저장과 보내기는 별도 동작이며, 수정하거나 저장할 때마다 장면을 자동으로 바꾸지 않는다. 다른 사람에게 공개·공유하는 기능도 별도다.

준비된 기록을 보내면 Unity가 관련 지도·음식점 정보를 읽고 방문 표시와 순서 재생을 조립한다. 필수 자료가 부족하면 해당 방문의 보완 항목을 보여주고 저장된 기록으로 돌아가 수정할 수 있다. 기존 기록을 읽어오는 경우에도 같은 준비 검사를 거친다.

오행 역할·운영 권한·성장 규칙은 이 전달 동작으로 바뀌지 않는다. 표현된 도착은 방문 재생의 결과이지 실제 픽업·배송 완료가 아니다.

## 2. 저장과 전달은 서로 다른 책임이다

| 동작 | 권장 의미 | 자동으로 하지 않는 것 |
| --- | --- | --- |
| 내 기록 저장 | 입력/가져오기 출처·방문 ID·판본을 보관하고 다시 조회한다. 부족한 내용은 초안으로 남긴다. | 위치 검증 완료, 운영 원장 확정, Unity 반영 |
| Unity로 보내기 | 선택한 기록 판본·방문 범위의 표현 준비를 요청하고, 허용된 최소 사본을 Unity에서 읽을 수 있게 한다. | 원본 DB 전체 복사, 타인 공개, 새 주문·배차 생성 |
| Unity에서 불러오기 | 요청한 판본과 준비 결과를 검사하고 필요한 공간·가게 표현을 조립한다. | 최신 판본으로 몰래 교체, 임의 위치/주행선/완료 사실 생성 |
| 수정 후 다시 보내기 | 같은 기록의 새 판본을 명시적으로 선택해 반영한다. | 수정 중인 초안의 즉시 실시간 반영 |

기존 편집 작업공간의 보관 DB·원본을 삭제하거나 새 저장소로 일괄 이관하지 않는다. 기존 저장·조회 경로와 식별자 대응을 먼저 조사해 재사용한다. 서버 측 영속 기록이 필요하면 기존 API/UseCase 경계에서 권한·판본·중복을 검사하며 별도 서버를 늘리지 않는다.

Unity는 DB에 직접 접속하지 않는다. 사용자에게는 ‘보내기’지만 내부 구현은 **선택한 기록을 서버의 허용된 읽기 경로로 제공하고 Unity가 조회하는 방식**을 우선 제안한다. 원문 파일·DB 비밀번호·토큰을 전달 링크나 로그에 넣지 않는다. 구체 route와 알림/조회 방식은 기존 기능 조사 후 정한다.

## 3. 보내기 전에 고정할 정보

- 기록 ID, 선택한 판본·원본 hash, 방문 범위와 순서.
- 요청자·수신 범위에 대한 접근 권한. 기본값은 본인용 비공개 검토로 제안한다.
- 가게·좌표·행정동·지도·표현 규칙의 참조 판본과 r50의 준비 검사 결과.
- 재시도해도 같은 요청으로 인식할 멱등 식별자. 동일 기록이라도 새 판본/선택 범위는 구분한다.

전달 사본에는 방문 순서·표현에 필요한 가게/메뉴·허용된 공개 가게 위치·근거만 포함한다. 고객 주소·연락처·원본 영상·타인의 정밀 GPS는 포함하지 않는다. 공개 상점 위치까지 제거하여 배치가 불가능하게 만드는 것이 아니라 용도와 권한에 맞는 최소 자료로 한정한다.

현재 `RecordedVisit`·`LocalReviewOnly=true`·`IsOperationalState=false` 계약을 유지한다. 운영 완료 사건을 넣거나 모든 개인정보를 공개할 수 있는 새 통로로 해석하지 않는다. 데이터 이용조건상 Unity 검토가 허용되는 범위도 준비 검사에서 확인한다.

## 4. 실패와 재전송

저장, 준비, 전달, 실제 표시는 별도 상태로 관리하는 안을 제안한다. 적어도 화면에는 **저장됨 / 자료 보완 필요 / 전달 대기 / Unity 수신 / 표현 완료 또는 표현 실패**를 구분한다. 준비 과정의 구체 상태 코드는 구현 전 기존 계약과 대조한다.

- 저장은 성공했지만 준비에 실패할 수 있다. 이때 기록은 보존하고 부족한 항목만 보여준다.
- Unity가 꺼져 있으면 전달 대기로 남긴다. 다음 실행에서 해당 요청을 선택해 읽는 방식으로 제안하며 강제로 실행하지 않는다. 만료·보관 기간은 후속 정책으로 정하고 무기한 보관을 전제하지 않는다.
- 수신 성공은 화면 표현 성공이 아니다. Unity가 해당 판본의 대상 조립 결과를 확인한 경우에만 표현 완료로 표시한다. 이 확인은 표시 진단이지 운영 업무 완료 Event가 아니다.
- 연결/표현 실패 시 같은 판본으로 재시도한다. 중복 요청으로 가게·방문·캐릭터가 늘어나지 않아야 한다.
- 원본이 수정돼도 대기 중인 요청을 새 판본으로 몰래 바꾸지 않는다. 새로 보내기를 통해 교체하며 이전 입력 판본과 요청의 관계는 추적 가능하게 한다.
- 준비된 새 표시로 바꾸기 전 기존 표시를 지워 빈 화면만 남기지 않는다. 단, 권한 철회·삭제·만료를 확인하면 기존 표시도 즉시 차단/정리한다. 연결이 끊긴 동안 철회를 즉시 알 수 있다고 가정하지 않으며 조회 권한의 유효기간·오프라인 표시 허용 범위는 후속 정책으로 정한다. 복구를 이유로 허용 기한이 지난 사본을 유지하지 않는다.
- 보내기 취소와 원본 삭제를 구분한다. 취소는 해당 전달/표시를 철회하는 것이며 보관 원본을 자동 삭제하지 않는다. 원본 삭제의 보존 정책은 별도로 결정한다.

## 5. 후속 구현의 작은 완료선

**기록 한 묶음을 저장→다시 조회→보내기→Unity에서 같은 판본으로 표현**하는 흐름 하나를 먼저 닫는다. 기존 자료 가져오기부터 연결하되 직접 입력도 같은 저장·준비 경로를 사용할 수 있게 한다. 입력 화면을 별도 대형 앱으로 만드는 것이 선행 조건은 아니다.

이후 같은 판본 재전송, 정정 판본 전송, Unity 미실행 후 재개, 필수 자료 부족, 권한 철회를 검증한다. r49의 순서 재생·동간 조립과 r50의 입력/조회 규칙은 그대로 재사용하며 장면 수작업이 다시 필요하지 않은지를 확인한다.

저장·조회/API 시험, 실제 DB, Unity 수신, Play Mode·Game View는 각각 다른 증거로 기록한다. 현재 문서만으로 이 연결이 구현됐다고 보고하지 않는다.
