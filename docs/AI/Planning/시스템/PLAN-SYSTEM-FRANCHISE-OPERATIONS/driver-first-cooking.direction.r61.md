- 범위: 사용자가 제시한 주문 인지·기사 배차 선행·조리 시작 분리 방향과 현행 코드 차이를 기록한다. 이번에는 기획 문서만 변경하며 제품 상태 전이·DB·과금·실결제·실배차를 변경하지 않는다.

## 확정 방향

주문자가 주문하면 음식점은 먼저 주문을 인지하고 메뉴·재고·영업·조리 가능 여부를 확인할 수 있다. 이 확인은 조리 시작을 뜻하지 않는다. 기사가 제안을 수락하고 서버가 현재 유효한 배차를 확정한 뒤에 음식점이 조리 시작을 선택할 수 있도록 한다.

사용자 목적은 기사 확보 전에 음식을 조리하여 전달할 수 없게 되는 위험을 줄이는 것이다. 기사 후보가 있거나 알림을 보냈다는 사실만으로 조리 시작을 열지 않는다. 기사 확정 이후에도 사고·이탈·취소가 가능하므로 전달을 보장한 상태로 표시하지 않는다.

조리·기사 배정이 하나의 주문 상태를 덮어쓰는 방식으로 구현돼 있다. 신규 구현은 조리 상태와 배차 상태가 동시에 정확하게 표현되는지 공통 상태 전이 규칙·DTO·EF/InMemory 저장소·역할 앱·운영 Projection까지 점검한다. 이 문서의 화면 용어는 새 stable ID나 API 계약을 이미 확정한 것이 아니다.

## 제안 흐름과 조리 시작 조건

| 단계 | 음식점 | 기사/플랫폼 | 주문자 |
| --- | --- | --- | --- |
| 주문 접수·인지 | 주문을 보고 준비 가능 여부·예상 조리시간 확인. 조리 시작은 대기 | 유효한 결제/주문과 매장 준비 가능 상태를 근거로 배차 준비 | 주문 접수 및 확인 상태 표시 |
| 배차 대기 | 배차 상태 조회·메뉴 불가 등 거절 가능 | 후보 추천·기사 수락을 기다림. 후보와 확정을 구분 | 기사 확보 중이라는 실제 상태 표시 |
| 유효한 기사 확정 | 조리 시작 행동 활성화 | 서버가 기사·원장·현재 시도·판본을 검증해 배차 확정 | 기사 배정 및 조리 시작 대기를 구분 |
| 조리 시작 | 명시적으로 조리 시작. 서버 성공 뒤 갱신 | 확정한 기사와 예정 준비시각을 연결 | 실제 조리 시작 상태 표시 |
| 준비·픽업·전달 | 준비 완료와 기사 인계 | 기존 수행 단계로 연결 | 기존 추적·수령 흐름 유지 |

조리 시작 Command는 버튼 활성화만으로 허용하지 않는다. 인증된 매장 소유자, 현재 유효한 주문·결제 조건, 유효한 기사 배차와 현재 배달 시도, 취소/중단 없음, 요청 revision과 멱등 ID를 서버가 검증해야 한다. 조리 시작과 배차 해제가 동시에 요청되면 트랜잭션 또는 경쟁 제어로 순서를 결정하고 최신 결과를 재조회한다.

매장이 수행 불가능한 주문에 기사부터 불필요하게 배정하지 않도록, 주문 인지와 준비 가능 확인은 조리 시작과 구분해 설계한다. 예상 조리시간은 배차 전에 수집할 수 있지만 실제 조리 시작 시각과 약속된 준비시각의 산정·동결 시점은 별도 구현 명세에서 정한다.

## 예외 처리의 구분

- **배차 미확정:** 조리는 대기한다. 주문자·매장에게 배차 대기 상태를 표시한다. 최대 대기시간과 취소/결제 승인 해제·환불 조건은 미정이다.
- **기사 확정 후, 조리 전 이탈:** 유효한 배차가 없어지면 조리 시작을 차단하고 재배차 대기로 돌아가는 방향으로 설계한다. 오래된 버튼이나 Event로 조리를 시작할 수 없어야 한다.
- **조리 시작 후 기사 이탈:** 이미 시작된 조리 사실·비용을 보존하고 기존 중단·재배차 절편에 연결한다. 미조리 상태로 되돌려 이력을 지우지 않는다.
- **매장 거절 또는 주문자 취소:** 배차 해제·기사 통지·결제 후속을 연결한다. 보상·위약금·취소 가능 시간은 여기서 새로 정하지 않는다.
- **이미 준비된 음식:** 주문 때문에 새로 조리한 경우와 구분한다. 기존 즉시 픽업 가능 기능과의 호환 조건은 구현 검토에 남기며 자동 예외 허용으로 확정하지 않는다.

## 우선 적용 및 검증 계획

1. 주문 인지/준비 가능 확인, 배차 대기, 배차 확정, 조리 시작의 상태·행동 계약을 정리하고 공통 Guard·조회 Projection과 대조한다.
2. 수락 시 즉시 조리와 배차 생성이 함께 실행되는 기존 경로를 분리하고, 배차 Outbox와 기사 확정 뒤 조리 시작 Command를 메인 서버에 연결한다. 실제 결제 승인 연결의 기존 기본 비활성과 환경 준비 조건을 재사용한다.
3. 주문자·음식점·기사 앱에서 동일 원장을 조회한다. 음식점은 ‘주문 확인’과 ‘조리 시작’을 구분하고, 배차 전 조리 시작 버튼과 API 요청 모두 차단한다.
4. 배차 없는 주문, 기사 후보만 있는 주문, 정상 확정 후 조리, 동시 조리/배차 해제, 중복 요청·Event 재시도, 매장 거절, 조리 전·후 기사 이탈을 확인한다. 정상 1건은 역할 앱→서버/DB→Event→역할 앱 재조회까지 실행 근거를 남긴다.

## 미정 및 실행 상태

배차 대기 제한, 매장 확인 제한, 취소·환불·보상 기준, 실제 시간대 경계는 아직 정하지 않았다. 이번 사용자 방향을 다시 묻지 않고, 구체 구현에 필요한 항목만 기존 기획과 대조해 후속으로 정한다.

제품 코드·DB migration·HTTP/UI 실행·APK·Unity·commit·push는 이번 문서 작성에서 수행하지 않았다. 기존 다른 스레드의 미커밋 변경을 보존한다.
