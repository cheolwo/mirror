# [기획 · 공동 참여·정산 투명성 · PLAN-SYSTEM-FRANCHISE-OPERATIONS · r57]

> 후속 [r58 플랫폼 수수료 표시 확정](participant-platform-fee-visibility.decision.r58.md): `participant-settlement-platform-fee-visibility`는 사용자 동의로 `Confirmed`가 됐다. 아래 `Asked`와 질문은 당시 문답 이력이며 재질문하지 않는다. 전체 재무 공개나 제품 구현 승인은 아니다.

## 상태와 선행

- 기준일: 2026-09-28.
- 상태: `ConfirmedDirection / SettlementTransparencyFirst / SettlementVisibilityAsked`. 공동 참여와 정산 투명성의 우선순위만 확정한다. 제품 구현·공개·실제 정산 실행 승인이 아니다.
- 선행: [가게 정보 확인·정정 r56](local-merchant-information-review.direction.r56.md), [생활과 수고를 이해하는 목적 r47](living-world-mutual-understanding.direction.r47.md), [자료 순환 r38](delivery-content-data-cycle.plan.r38.md).
- 재무 계산·운영 정책의 기준은 [기존 운영·재무 기획](../PLAN-SYSTEM-REGIONAL-OPERATOR-SIMULATION/README.md)이 소유한다. 이번 문서는 참여자 관점의 우선순위와 조회 요구를 연결하며 수수료·공제·지급 주기를 새로 결정하지 않는다.

## 사용자 확정 방향

초기에는 사용자가 주로 준비하되, 음식점 사장님과 배달기사님도 자기 가게 정보·배달 경험·기록을 보태며 함께 만드는 시스템을 지향한다. 참여를 가게 정보 정정만으로 좁히지 않는다. 역할별 참여 범위와 공개 동의는 별도로 정해야 한다.

그 기반으로 **정산 구조의 투명성을 먼저 마련한다.** 누구나 모든 개인정보를 열람한다는 뜻이나 참여 기록에 자동 보상을 부여한다는 뜻은 아니다. 출자·지분·수익 배분·공동 의결권도 이번 발언으로 확정하지 않는다.

r56의 `local-merchant-correction-review-policy` 질문은 `DeferredByPriorityChange`다. 사용자는 운영자 사전 검토 방식을 승인한 것이 아니라 공동 참여와 정산 우선순위로 논의를 옮겼다. 기존 확인·정정 준비 방향은 유지하고 쇼츠 제작 개선은 계속 제외한다.

## 먼저 설명 가능해야 할 정산 정보 — 제안

| 관점 | 본인 업무와 연결해 확인할 정보 후보 |
| --- | --- |
| 음식점 | 판매대금 기준, 취소·환불 조정, 본인 부담 수수료·배달비, 정산 대상액, 보류액, 지급 상태 |
| 기사 | 인정된 수행 건, 기본 대가·거리/기상 등 할증, 적용 공제와 근거, 지급 대상액, 보류액, 지급 상태 |
| 운영자 | 같은 거래의 수취·지급 의무·통과자금·플랫폼 수수료 구분, 실제 입출금 근거, 금액 불일치와 미처리 건 |

각 금액은 대상 거래·계산 근거·적용 정책 판본·확정 시점과 연결한다. 예상액/확정액/보류액/실제 지급액을 구분하고, 지급 예정일이 확인되지 않았으면 임의로 약속하지 않는다. `지급 승인`이나 화면의 완료 효과를 실제 입금으로 표시하지 않는다. 플랫폼 수수료는 비용 차감 후 이익과 구별한다.

기존 기사 화면의 간단한 `보류` 표현 방향은 유지한다. 본인이 확인 가능한 보류 금액·상태와 상세/문의 경로를 두는 후보이며, 복잡한 내부 예외 코드·제3자 개인정보를 화면에 그대로 노출하지 않는다. 화면 구성은 이번 문답으로 확정하지 않는다.

## 함께 만드는 기록과 정산 권위의 구분

- 가게·기사가 낸 기록·정정·이의는 원본 근거를 보존해 검토 가능한 입력으로 받는 방향을 검토한다. 타 플랫폼에서 수행한 배달이나 개인 방문 기록을 우리 플랫폼의 지급 의무로 자동 변환하지 않는다.
- 참여자가 자기 금액에 질문·이의를 남길 수 있어야 한다는 제안과, 누구나 금액을 직접 바꿀 수 있다는 권한은 구분한다. 확정 원장 변경은 기존 서버 권한·상태·판본 검증 경계를 유지한다.
- 수정 전후 금액·사유·처리 주체·시각을 추적하고 과거 확정 내역을 조용히 덮어쓰지 않는다. 조정의 반영 시점은 기존 정산 정책과 연결해 후속 검토한다.
- 한 건의 이견을 이유로 무관한 정상 건을 자동 보류하지 않는다. 실제 처리 조건은 기존 예외 정책과 대조한다.
- 본인 내역, 거래 상대방에게 허용된 정보, 플랫폼 집계 공개는 서로 다른 조회 범위다. 연락처·계좌·세무 증빙·다른 사람의 전체 수입을 투명성 명목으로 공개하지 않는다.

## 기존 기반과 남은 확인

- [재무 사건 구현 r2](../PLAN-SYSTEM-REGIONAL-OPERATOR-SIMULATION/financial-impact-ledger.implementation.r2.md)는 결제 승인 Outbox의 멱등 투영·계산 판본·충돌 기록·관리자 조회를 제공하는 기반이다. 음식점과 기사의 실제 지급 완료 증거는 아니다.
- [주간 정산 요약 r39](../PLAN-SYSTEM-REGIONAL-OPERATOR-SIMULATION/weekly-settlement-summary.r39.md)는 종류별 지급 의무·플랫폼 수익/통과자금 구분과 예외 상세를 기획한다. 본인 앱에서 그 흐름이 완성됐다고 해석하지 않는다.
- [음식 결제 승인 반영 r5 결과](../PLAN-SYSTEM-REGIONAL-OPERATIONS-E2E-SCAFFOLD/restaurant-payment-approval.r5.result.md)는 승인 결과를 같은 음식 주문에 연결했지만 환불·정산·지급·실제 역할 화면까지 검증한 결과가 아니다.
- 현행 [기사 배달 업무 DTO](../../../../../Ssalddel.Contracts/Driver/Food/FoodDeliveryDriverWorkspaceDtos.cs)는 `DriverPayout`·날씨 할증·`PricingPolicyRevision` 등 건별 계산 근거를 제공한다. 이 DTO에 공제·보류·실제 입금·정정 이력까지 있는 것은 아니다.
- 현행 [음식 주문 DTO](../../../../../Ssalddel.Contracts/Food/음식주문Dtos.cs)는 주문·승인 금액과 업무 이력을, [운영 재무 DTO](../../../../../Ssalddel.Contracts/Admin/Finance/운영재무Dtos.cs)는 원본 판본·금액·증빙·매핑·대사 예외를 제공한다. 관리자 재무 조회를 그대로 사장님·기사님에게 공개할 권한은 아니며 원본 업무 이력을 정산 수정 이력으로 간주하지 않는다.
- [기사 월정산 DTO](../../../../../Ssalddel.Contracts/Driver/Food/배달기사월정산Dtos.cs)의 배차 건수·이용료·결제 완료는 기사 이용료 청구 관점이다. 기사에게 지급할 수행대금 원장으로 사용하지 않는다. 위 소스는 읽기만 했으며 실행 검증은 하지 않았다.
- 다음 구현 후보는 합성 거래 하나에서 역할별 금액·계산식·정책 판본·보류·수정 이력·지급 증거를 함께 대조하는 것이다. 별도 작업 명세와 실행 승인 전에는 제품·DB·송금 경로를 변경하지 않는다. 거래 금액과 세율·공제율을 임의로 만들지 않는다.
