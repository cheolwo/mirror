## 목표

앱 사용자가 서버의 어떤 기능을 얼마나 사용했고 그 사용이 플랫폼에 어떤 원가를 만들었는지 재현 가능하게 측정한다. 측정 결과는 구독 상품을 설계하고 운영경제성을 검토하는 근거로 사용한다.

이 단계는 사용량을 관찰하는 단계다. 측정값만으로 사용자를 자동 청구하거나 기능을 차단하지 않는다.

주문자 구독과 150건 활동 기사 지정 제안의 세부 경제성은 [주문자 구독·150건 활동 기사 지정 경제성 r9](orderer-subscription-preferred-driver-economics.r9.md)가 소유한다. 기존 음식점 조직 월 구독을 첫 외부 출시 후보로 둔 결정은 유지하며, 주문자 구독은 지정 제안 기능의 별도 상품 후보로 추가한다.

## 현재 기준선

현재 코드에는 다음 기반이 존재한다.

- `SsalddelCodeFeatureKeys`와 `SsalddelCodeMetadataAttribute`: 기능·단계·효과와 `MayIncurExternalCost`를 설명할 수 있다.
- `사용자행위로그Middleware`: API 요청, 사용자, 앱, route, 결과와 trace를 기록한다.
- `기사월정산`: 기사별 배차 건수와 월 이용료를 집계한다.
- `재무사건`·`관리계정전기`: 확정 업무 Event를 기준 중립 재무 의미로 투영한다.
- `플랫폼운영경제성Calculator`: 반복수익·변동비·고정비와 손익분기 주문 수를 계산한다.

그러나 사용자 행위 로그는 감사 목적이고 원가 원장이 아니다. 기사 월정산은 한 역할의 기존 이용료 정책이고 공통 구독 계량기가 아니다. 재무 사건은 금액이 확정된 업무 결과이며 HTTP 호출량이나 외부 API 원가를 대신하지 않는다. 따라서 세 자료를 합치지 않고 그 사이에 공통 사용량 계층을 추가해야 한다.

## 네 층의 분리

```text

  → 사용량 사실 원장
  → 직접 원가·추정 원가 귀속
  → 판본화된 구독 정책 평가
  → 청구 후보·운영경제성 Preview
```

| 층 | 소유 사실 | 하지 않는 일 |
| --- | --- | --- |
| 사용량 사실 | 누가 어떤 기능 단위를 언제 얼마나 성공·실패·재시도했는가 | 금액 확정 |
| 원가 귀속 | 외부 공급자 청구액, 저장량, 공유 인프라 배부 추정 | 사용자 판매가격 결정 |
| 구독 정책 | 월 기본료, 포함량, 초과량, 유예·상한, 적용 판본 | 과거 기간 소급 변경 |
| 청구·재무 | 확정된 청구 후보와 결제·미수·현금 흐름 | 원시 API 로그를 회계 전표로 승격 |

## 측정 단위

모든 메서드 호출을 과금 단위로 만들지 않는다. 너무 낮은 단위는 구현 변경에 따라 청구가 흔들리고 내부 재시도까지 사용자에게 전가할 위험이 있다.

두 종류의 단위를 함께 둔다.

### 기술 사용량

- `http.request`: 인증된 API 요청 1건
- `external.provider.call`: 외부 API 실제 송신 1건
- `notification.send`: 외부 알림 공급자 전송 1건
- `object-storage.byte-day`: 저장 바이트·일
- `response.egress.byte`: 응답 전송 바이트
- `background.job.execution`: 사용자·조직에 귀속 가능한 작업 실행 1건

기술 사용량은 원가 분석용이다. 기본 구독 청구 단위로 곧바로 사용하지 않는다.

### 업무 사용량

- 주문 생성·완료
- 배차 제안·수락·완료
- 운송 의뢰·완료
- 입고·피킹·포장 완료
- 공개자료 새로고침
- 이미지·문서 같은 비용 발생 산출물 생성

업무 사용량은 사용자에게 설명 가능한 구독 포함량 후보다. 내부 조회·재시도·Projection은 원 업무의 중복 사용량으로 계산하지 않는다.

## 사용량 사실 계약

첫 계약은 다음 의미를 가진다.

| 필드 | 의미 |
| --- | --- |
| `UsageEventStableId` | 재처리에도 바뀌지 않는 사용량 사건 식별자 |
| `MetricKey` | 측정 단위의 안정 키 |
| `FeatureKey`·`OperationKey` | 기능과 실제 동작 |
| `ActorUserStableId` | 실제로 요청한 사용자 |
| `BillingSubjectStableId` | 원가와 구독을 귀속할 개인·조직 계정 |
| `AppKey` | 관리자·기사·화주·주문자 등 사용 앱 |
| `Quantity`·`UnitCode` | 수량과 단위 |
| `OccurredAtUtc` | 사용 시각 |
| `OutcomeCode` | 성공·거절·실패·취소 |
| `RequestId`·`CommandId`·`IdempotencyKey` | 중복 방지와 추적 연결 |
| `ExecutionMode` | `Simulation` 또는 `Operational` |
| `CostBasisCode` | `DirectObserved`, `TariffEstimated`, `AllocatedEstimate`, `Unknown` |
| `RateRevision` | 원가 단가 또는 배부 규칙 판본 |

요청 body, query 전문, 주소, 전화번호, 정밀 GPS, 토큰, 오류 원문은 저장하지 않는다. 사용자별 조회 권한, 보존 기간과 삭제·익명화 정책을 별도 관문으로 둔다.

## 서버 결속 위치

```text
HTTP Middleware
  → 요청 봉투·응답 결과·bytes·시간 측정

Command / Query / UseCase
  → 설명 가능한 업무 사용량 확정

Typed 외부 Adapter
  → 공급자 호출·과금 수량·단가 판본 측정

Event / Outbox
  → 같은 업무 transaction에서 사용량 사실을 멱등 발행

사용량 Projector
  → 사용자·조직·기능·일/월별 읽기 사본
```

기존 `사용자행위로그Middleware`는 감사 로그로 유지한다. 여기에 금액 계산을 넣지 않는다. 공통 요청 계량기는 별도 middleware·collector로 두고, 과금 후보가 되는 업무 단위는 명시적 metadata와 Event/Outbox에서만 확정한다.

## 중복과 실패 규칙

- 같은 `CommandId`·`IdempotencyKey`로 성공한 업무 단위는 한 번만 센다.
- HTTP 재시도와 실패 호출은 기술 원가에는 남길 수 있지만 업무 구독 사용량에는 중복 포함하지 않는다.
- 서버 내부 Projection·Outbox 재처리·캐시 재구성은 사용자 업무 사용량이 아니다.
- 공급자 호출이 실패해도 실제 비용이 발생할 수 있으므로 `OutcomeCode`와 원가 관측을 분리한다.
- 사용량 기록 실패가 원 업무를 조용히 성공시켜도 되는지 기능별로 구분한다. 청구 후보 업무는 동일 transaction Outbox를 우선한다.
- 구독 정책 변경은 `EffectiveFromUtc` 이후 새 사용량에만 적용하고 과거 기간을 소급 변경하지 않는다.

## 사용자와 비용 귀속 주체

`ActorUserStableId`와 `BillingSubjectStableId`를 분리한다. 직원 한 명이 음식점·마트·운영조직을 대신해 기능을 사용했다고 해서 그 개인에게 비용을 청구해서는 안 된다.

권장 기본값은 다음과 같다.

- 개인 독립 사용: 사용자 계정이 비용 귀속 주체다.
- 음식점·마트·지사·회사 업무: 조직의 구독 계정이 비용 귀속 주체고 사용자는 행위자다.
- 플랫폼 내부 관리자: 플랫폼 내부 원가로 귀속하며 외부 고객 청구 후보에서 제외한다.
- `Simulation`: 측정은 하되 실제 청구 후보에서 제외한다.

### 확정된 귀속 해석 순서

1. 서버는 인증 사용자와 현재 역할 결속에서 `ActorUserStableId`를 확인한다.
2. 요청이 선택한 업무 조직과 사용자의 유효한 담당자·구성원 권한을 서버에서 다시 검증한다.
3. 유효한 조직 결속이 있으면 `BillingSubjectStableId`를 그 조직의 구독 계정으로 고정한다.
4. 개인 전용 기능만 명시적으로 개인 구독 계정에 귀속한다.
5. 플랫폼 내부 운영 기능은 플랫폼 내부 원가 계정에 귀속하고 외부 청구 후보에서 제외한다.
6. 조직 결속이 없거나 둘 이상으로 모호하면 개인에게 추정 귀속하지 않는다. `AttributionPending`으로 보존하고 구독 포함량·초과량·청구 후보에서 제외한다.

클라이언트가 보낸 조직 ID만 신뢰하지 않는다. 조직 구성원·담당자 권한과 적용 시점 revision을 서버 원장에서 확인하며, 한 사용자가 여러 조직을 담당할 때는 현재 업무 문맥에서 선택·검증된 조직만 비용 귀속 주체가 된다.

## 구독 정책 초안

첫 운영은 `ShadowMetering`으로 둔다.

- 월 기본료와 포함 기능은 기획상 계산하되 실제 청구하지 않는다.
- 초과 사용은 표시만 하고 차단·자동 결제하지 않는다.
- 30일 이상 내부 사용으로 사용자·조직별 원가 분포와 이상치를 확인한다.
- 직접 원가와 공유 인프라 배부 추정을 구분해 보여 준다.
- 기존 기사 월 이용료는 공통 구독 원장으로 즉시 합치지 않고 별도 정책으로 유지한다.
- 첫 외부 구독 상품은 음식점 조직의 월 구독으로 확정한다. 주문 접수·상태 조회·조리시간 관리 같은 기본 기능을 먼저 계량한다.
- 주문자 개인 구독은 `150건+` 활동 기사 지정 제안 이용권의 별도 상품 후보로 둔다. 일반 주문·일반 배차는 구독 없이 유지한다.
- 주문자 구독의 가격·포함량·기사 지정 보너스는 주문 1건, 구독자 1개월, 플랫폼 기간 전체의 세 단계 경제성을 함께 본 뒤 확정한다.
- 주문 비율 수수료를 기본 수익모델로 삼지 않는다. 월 가격과 포함량·초과 정책은 30일 `ShadowMetering`과 지급 안정성을 본 뒤 확정한다.

## 영업이익 4% 목표와 자금 순환

플랫폼은 과도한 이익 극대화보다 지속 가능한 운영과 참여자·서비스 생태계의 순환을 지향한다. 영업이익 목표는 **플랫폼 보유 매출 대비 약 4%**로 둔다.

여기서 플랫폼 보유 매출은 구독료와 계약상 플랫폼에 귀속되는 용역 대가다. 음식점 상품대금, 기사 수행대금, 고객 환급금, 세금·보험 등 플랫폼이 대신 보관하거나 지급해야 하는 통과자금은 분모에 넣지 않는다. 총 주문 결제액이나 총거래액을 플랫폼 매출로 간주하지 않는다.

```text
플랫폼 보유 매출
  - 운영비용
  = 영업이익 후보

목표 영업이익률
  = 영업이익 후보 / 플랫폼 보유 매출
  ≈ 4%
```

4%는 주문마다 떼는 고정 수수료가 아니며, 개별 사용자 청구 공식도 아니다. 기간별 운영 결과를 판단하고 구독 가격·원가 절감·환원 규모를 조정하는 경영 목표다.

### 현금과 이익을 분리한다

장부상 영업이익이 발생해도 바로 분배 가능한 현금이 생겼다고 보지 않는다. 자금 순서는 다음과 같다.

1. 음식점·기사·화주·창고 등 다른 주체에게 지급할 금액을 보호한다.
2. 고객 환불·분쟁·세금·보험·PG 정산 등 확정 또는 합리적으로 예상되는 의무를 보호한다.
3. 서버·인력·고객지원 등 현재 운영비를 지급한다.
4. 정해진 운영 안전 유보금 하한까지 적립한다.
5. 위 항목을 충족한 뒤 남는 금액만 `순환가능잉여현금` 후보로 계산한다.
6. 판본화된 순환 정책이 환원·재투자·추가 유보의 배분안을 만든다.

`순환가능잉여현금`은 회계상 이익·배당가능이익과 동일하다고 주장하지 않는다. 실제 배당·성과보상·쿠폰·요금 인하·투자는 각각 세무·계약·회사법·노무 검토와 별도 승인 뒤 실행한다.

### 순환 정책 계약

`SurplusCirculationPolicyRevision`은 다음을 가진다.

- 적용 기간·법인·통화
- 목표 영업이익률 `4%`
- 운영 안전 유보금 하한과 산정 근거
- 보호해야 할 제한자금·미지급 의무·환불·세금 후보
- 환원·서비스 재투자·추가 유보의 비율 후보
- Preview 결과와 승인 상태
- 소급 적용 금지와 적용 시작 시각

초기 상태는 `PreviewOnly`다. 서버는 실제 송금 대신 배분 제안만 만들고, 총괄 운영자가 근거와 현금 흐름을 확인한다. 자동 지급은 별도 승인 Goal 전까지 비활성이다.

순환가능잉여현금의 배분 대상은 다음 네 바구니로 확정한다.

| 바구니 | 목적 | 경계 |
| --- | --- | --- |
| 서비스 품질 재투자 | 서버·보안·도구·고객지원·업무 품질 개선 | 일반 운영비와 신규 투자 제안을 구분 |
| 이용 조직 환원 | 음식점·마트·화주 등 구독 조직의 요금 경감·공동 혜택 후보 | 개별 사용량에 따른 자동 차등 보상 금지 |
| 현장 참여자 지원 | 기사·피킹·포장 등 실제 현장 참여자의 안전·교육·지원 후보 | 수행대금·법정 지급·보험 의무와 합치지 않음 |
| 추가 유보 | 변동성·장애·환불·확장에 대비한 추가 안전자금 | 기본 운영 안전 유보금 하한을 먼저 충족 |

각 비율은 `SurplusCirculationPolicyRevision`이 소유한다. 비율 변경은 적용 시작 이후에만 효력이 있고 이미 마감한 기간에 소급하지 않는다. 한 바구니의 잔액을 다른 바구니로 옮기는 경우에도 사유·승인·revision을 남긴다.

## Unity 우선 운영 정책 실험장

실제 배달 플랫폼의 영업·채용·외부 지급을 먼저 열지 않는다. Unity의 가상 세계에서 운영 규칙을 충분히 만들고 관찰한 뒤, 검증된 정책 계약과 순수 계산 코어만 실제 운영 서버가 채택할 수 있도록 준비한다.

```text
판본화된 운영 정책 계약
  ↓
운영정책 Simulation Core
  ↓
LocalSimulationRuntime / Save / Replay / WorldTick
  ↓
SimulationWorldShell 정책 카드
  ↓
NPC 주문·조리·배차·피킹·운송·자금 흐름 변화 관찰
  ↓
검증된 정책 후보와 근거
  ↓ 별도 승인
실제 운영 서버 Adapter
```

Unity의 역할은 두 가지로 분리한다.

- 가상 Simulation에서는 정책 카드를 통해 가상 인력·구독·자금·서비스 수준을 변경할 수 있다.
- 실제 운영 자료를 볼 때는 계속 읽기 전용이며 주문·지급·채용·배차·정산 원장을 변경할 수 없다.

같은 코어를 사용한다는 것은 운영 DB와 Simulation 저장을 합친다는 뜻이 아니다. 공유 대상은 결정적인 계산 규칙, 값 객체, 정책 계약과 결과 해석이다. 실제 사용자·계약·결제 권한은 Operations가, 가상 시간·NPC·Save/Replay는 Simulation이, 카드와 3D 표현은 Unity가 각각 소유한다.

### 재사용할 현행 기반

- `LocalSimulationRuntime`: LocalProcess에서 공통 Simulation Core 명령과 상태 사본을 사용한다.
- NPC 정책 변경·revision 충돌·재조회·Save/Replay 경계가 존재한다.
- 창고 입고·출고 정책 카드 Presenter가 초안→명시적 적용→권위 상태 재조회 흐름을 검증했다.
- canonical Scene은 새로 만들지 않고 `SimulationWorldShell` 하나를 유지한다.

창고 정책 카드의 기존 경로는 재사용 기반이지만 실제 `SimulationWorldShell` 카드 UI·Game View 결속은 아직 완료 증거가 없다. 이를 전체 운영 정책이 이미 Unity에서 작동한다고 해석하지 않는다.

### 첫 정책 카드 묶음 후보

| 카드 | 가상으로 바꾸는 값 | 관찰 결과 |
| --- | --- | --- |
| 운영 인력·역할 용량 | 역할별 NPC 수, 시간대 가용성, 동시 처리량, 휴식·복구 | 대기열, 지연, 유휴, 과부하 |
| 음식점 월 구독 | 포함 기능·포함량·가상 월 가격 | 반복수익, 조직별 사용량, 초과 후보 |
| 서비스 수준 | 주문 목표 시간, 조리시간 선택, 배차·회복 우선순위 | 완료율, 평균 대기, 예외 건수 |
| 자금 안전 | 4% 목표, 유보금 하한, 네 순환 바구니 비율 | 가용현금, 지급 가능성, 순환 Preview |

인력 카드는 실제 고용 Command가 아니다. `가상 운영 역할 슬롯`을 조정하며 개인 이름·실제 임금·근로계약을 만들지 않는다. 비용은 가상 인원·시간대·역할별 단가 revision으로만 계산하고 실제 채용 판단은 별도 운영·법률·노무 검토로 남긴다.

## 면목제3·8동 디오라마 하단 역할 카드 슬롯

첫 화면 대상은 기존 면목제3·8동 행정동 디오라마다. 디오라마의 지역 바닥·건물·NPC를 선택하면 Game View 하단에서 카드 슬롯이 위로 열리고, 현재 선택 문맥에 속한 생활·업무 주체를 가로 카드 열로 보여 준다.

```text
면목제3·8동 디오라마
  ├─ 지역 바닥 선택 ───────────────┐
  ├─ 음식점 건물 선택 ────────────┤
  └─ 주민·기사 NPC 선택 ──────────┤
                                      ↓
┌────────────────────────────────────────────┐
│ 면목제3·8동 · 생활 주체 12                 │
│ [전체] [주민] [음식점] [배달 기사] [업무] │
│                                            │
│ [주민 카드] [음식점 카드] [기사 카드] ... │
└────────────────────────────────────────────┘
```

하단 슬롯은 Hearthstone의 손패처럼 카드를 알아보기 쉽게 펼치고 Total War의 부대 카드처럼 현재 지역의 주체를 빠르게 선택하는 표현을 참고한다. 그러나 무작위 뽑기·카드 소모·희귀도·덱 과금은 만들지 않는다. 카드는 이미 존재하는 가상 주체와 업무 상태를 선택·관찰하는 인터페이스다.

### 카드 종류

| 카드 | 대표 대상 | 앞면에 보일 정보 | 선택 결과 |
| --- | --- | --- | --- |
| 주민 카드 | 합성 주문자·생활 NPC | 표시명, 현재 생활 상태, 주문 유무, 대표 위치 | 해당 NPC를 카메라로 추적 |
| 음식점 카드 | 합성 음식점 역할이 결속된 건물 | 음식점명 후보, 영업·조리 상태, 대기 주문 수, 담당 용량 | 건물 확대와 주문·조리 요약 |
| 배달 기사 카드 | 합성 음식 배달 NPC | 대기·이동·픽업·전달 상태, 현재 담당 업무 | 기사 추적과 경로·업무 요약 |
| 업무 카드 | 주문·조리·배달 같은 진행 업무 | 현재 단계, 경과 시간, 주의 상태 | 관련 주민·음식점·기사 관계 강조 |

첫 판은 `주민 / 음식점 / 배달 기사` 세 주체 카드를 필수로 하고 업무 카드는 관계를 설명하는 보조 탭으로 둔다. 창고·마트·화물은 같은 계약을 재사용하되 면목제3·8동 첫 판이 닫힌 뒤 추가한다.

### 선택 규칙

- 지역 바닥을 선택하면 그 지역의 현재 활성 카드 전체를 연다.
- 건물을 선택하면 해당 건물에 명시적으로 결속된 음식점·주거·업무 카드만 앞으로 정렬한다.
- NPC를 선택하면 해당 NPC 카드와 현재 업무 관계 카드를 앞으로 정렬한다.
- 카드를 한 번 선택하면 디오라마의 대상이 강조되고 카메라가 부드럽게 초점을 맞춘다.
- 같은 카드를 다시 누르거나 상세 버튼을 누르면 상태·관계·비용 Preview를 펼친다.
- 카드 슬롯을 접어도 선택 대상과 Simulation은 유지된다. 슬롯을 닫는 행위가 NPC 업무를 중단하지 않는다.
- 실제 운영 관찰 모드에서는 모든 카드가 읽기 전용이다. Simulation 모드에서도 주체 카드는 선택용이며 정책 변경은 별도 정책 카드 슬롯에서 명시적으로 적용한다.

### H1·H2·H3에 따른 카드 열림

하단 슬롯 상단에는 현재 공간 문맥을 다음 순서로 표시한다.

```text
면목제3·8동 디오라마
  > H3 생활·서비스 회랑
    > H2 주문·조리 업무 블록
      > H1 주문 포장 작업점
```

행정동은 자료 귀속과 디오라마 선택 범위이고 H3와 같은 개념이 아니다. 행정동 안에 명시적으로 결속된 H3·H2·H1만 카드 탐색 대상으로 사용한다.

| 선택 공간 | 하단 슬롯의 기본 카드 | 카드 선택 결과 |
| --- | --- | --- |
| 행정동 디오라마 | 결속된 H3 요약 카드와 `H 미결속` 진단 | 생활·서비스 회랑 선택 |
| H3 | 구성 H2 요약 카드, 활성 주민·음식점·기사 집계 | 독립 업무 블록으로 확대 |
| H2 | 구성 H1 카드와 현재 업무·시설·주체 카드 | 구체 과업 공간으로 확대 |
| H1 | 직접 관련 주민·음식점·기사·업무 카드 | GameObject·Anchor 초점과 상태 상세 |

- H1은 주문 포장점·주거 수령점처럼 플레이어가 식별하고 접근할 수 있는 구체 과업 공간·상호작용 지점이다.
- H2는 둘 이상의 H1을 시작·선택·결과·회복 또는 귀환으로 연결한 독립 업무 블록이다.
- H3는 여러 H2와 그 사이의 접근·정보·업무 관계를 묶는 생활·서비스 회랑이다.
- H3 카드에는 모든 개인 카드를 펼치지 않고 주체 수·대기·주의 상태를 집계한다.
- H2 카드에서는 해당 업무 블록에 참여하는 시설·주체·업무를 보여 준다.
- H1에 들어갔을 때만 직접 상호작용 대상 카드를 앞에 펼쳐 정밀 선택한다.
- 상위로 돌아가면 마지막 선택·필터·스크롤 위치를 복원한다.
- H2·H3가 없어도 승인된 H1이 있으면 `행정동 > H1` 직접 경로를 허용한다. 빈 H2·H3를 임의 생성하지 않는다.
- 행정동 첫 진입은 H3 요약 카드를 기본으로 한다. `전체 주체` 필터를 누르면 현재 행정동의 합성 주민·음식점·기사 카드를 바로 볼 수 있다.

기존 사가정 결속에서는 다음 경로를 첫 후보로 재사용한다.

- 음식점: `h1-stock:town-order-packing` → `h2-candidate:town-order-fulfillment` → `h3-candidate:town-market-fulfillment`
- 주민 전달: `h1-stock:town-resident-pickup` → `h2-candidate:lowrise-residential` → `h3-candidate:town-resident-service-loop`

`candidate`는 카드에 후보 상태를 표시해야 하며 확정 H처럼 보이지 않는다. H 계층이 끊겼거나 판본이 맞지 않으면 상위 카드로 추정 연결하지 않고 `WaitingForHBinding`을 표시한다.

### 카드 대장 계약

새 카드 원장을 Unity가 소유하지 않는다. Simulation 상태 사본에서 다음 읽기 모델을 만든다.

- `AdministrativeAreaStableId`
- `RosterRevision`
- `SubjectStableId`
- `SubjectKindCode=Resident|Restaurant|FoodCourier|Work`
- `DisplayName`
- `CurrentStateCode`
- `SemanticPlaceStableId`
- `RelatedSubjectStableIds`
- `AttentionStateCode`
- `SourceKindCode=SyntheticSimulation|OperationalProjection`
- `ReadOnly`
- `HLevelCode`
- `HStableId`
- `ParentHStableId`
- `HBindingRevision`
- `HBindingStateCode=Confirmed|Candidate|WaitingForHBinding`

기존 사가정 건물 역할 카드의 `Restaurant`, `ResidentialDelivery`, `Warehouse`, `GeneralUnbound` 결속은 시설 카드의 기반으로 재사용한다. 기존 `SimulationTeamRoleCard`는 일행의 역할 장착·전투 의미를 가지므로 디오라마 생활 주체 카드와 상태·API를 합치지 않는다. 공통 시각 컴포넌트가 필요하면 카드 틀·선택 강조·가로 스크롤만 재사용한다.

## 플레이어 사이 카드 교환

카드 교환은 허용하되 카드의 의미에 따라 권한을 분리한다.

| 카드 종류 | 교환 | 이유 |
| --- | --- | --- |
| 디오라마 주민·음식점·기사 주체 카드 | 불가 | 실제·가상 주체를 소유물로 취급하지 않는 관찰 참조 카드 |
| 진행 업무 카드 | 불가 | 주문·조리·배달 상태의 읽기 사본이며 업무 권한이 아님 |
| 지역 관찰·경험 수집 카드 | 가능 후보 | 디오라마에서 확인한 공개·합성 공간 특징과 경험을 표현하는 소유 가능한 사본 |
| 플레이어 멘토 카드 | 취득·공유, 직접 소유권 교환과 분리 | 발행 동의·친구 공개 범위·판본을 가진 학습 사본 |
| 전투·일행 역할 카드 | 기존 장착 원장 유지 | 운영·관찰 카드와 효과·소유권을 합치지 않음 |

지역 관찰·경험 카드는 예를 들어 `면목제3·8동 골목 생활`, `점심 주문 집중`, `주거 수령 흐름`, `비 오는 날 배달 관찰`처럼 공개 또는 합성 근거를 요약한다. 실제 주민 이름·상호·주소·기사 위치·주문 내역은 카드에 넣지 않는다.

### 기존 기반과 확장 경계

현행 `CollectibleCardTransfer`는 같은 Simulation 팀 구성원 사이에서 수집 카드 사본의 소유권을 한 방향으로 이전하고, 카드 사본·소유자·양도 이력을 Session과 Save/Replay에 보존한다. 첫 교환 기능은 이 규칙을 폐기하지 않고 다음 계약을 추가하는 방향이다.

```text
내 보유 수집 카드 선택
  → 교환 상대 선택
  → 내가 제안할 카드 + 상대에게 요청할 카드
  → 상대 검토·수락 또는 거절
  → 양쪽 소유권·판본 재검증
  → 원자적 교환
  → 두 플레이어 상태 사본 재조회
```

상태 후보는 `Draft → Offered → AcceptedByCounterparty → ConfirmedByOfferer → Completed`이며 어느 단계에서든 `Cancelled`, 만료 시 `Expired`, 소유권·판본 불일치 시 `Stale`로 닫는다. 한쪽 카드만 먼저 이전하지 않는다.

### 교환 UI

- 하단 카드 슬롯에는 `관찰`과 `내 카드` 탭을 분리한다.
- `관찰` 탭의 주민·음식점·기사 카드는 선택·추적·상세 보기만 제공한다.
- `내 카드` 탭의 교환 가능 수집 카드만 `교환 제안` 버튼을 가진다.
- 교환 상대가 제안 내용을 수락한 뒤 최초 제안자가 최종 확인해야 완료한다.
- 완료 뒤 양쪽 모두 서버·Simulation 권위 상태를 다시 읽고 카드 슬롯을 갱신한다.
- 교환 알림이 디오라마 관찰과 NPC WorldTick을 중단하지 않는다.

### 안전 경계

- 첫 판은 현금·유료 재화·경매·공개 시장·희귀도 가격을 만들지 않는다.
- 동일 카드 사본 복제, 자기 계정 간 반복 이전, 만료 제안 재사용을 멱등 키와 소유권 revision으로 막는다.
- 차단·신고·친구 해제 이후 새 교환 제안을 열지 않는다.
- 카드 교환이 배차 점수·기사 우선순위·음식점 노출·구독 가격에 영향을 주지 않는다.
- 실제 운영 계정의 업무 권한·정산·연락처·위치·원장 접근권을 카드와 함께 이전하지 않는다.

### 규모와 개인정보 경계

- 첫 면목제3·8동 Fixture는 화면에서 식별 가능한 소수 합성 NPC·시설만 카드화한다.
- 실제 주민·기사 이름, 연락처, 주소, 정밀 GPS를 카드에 넣지 않는다.
- 이후 대상이 많아지면 카드 가상화·필터·검색을 사용하며 모든 주민을 한 번에 GameObject로 만들지 않는다.
- 운영 자료 카드에는 비식별 역할·현재 업무 단계만 표시하고 실제 사람 카드를 수집형 자산처럼 다루지 않는다.

### 상향식 구현 순서

1. 가상 역할 한 종류와 업무 대기열 한 개를 고른다.
2. 인원 0명·1명·복수 명에서 처리량·대기·회복을 결정적으로 계산한다.
3. 정책 변경 Preview와 Confirm, revision 충돌, Save/Replay를 닫는다.
4. 기존 카드 Presenter 규칙으로 읽기 쉬운 카드 한 장을 만든다.
5. `SimulationWorldShell`에서 정책 적용 전후 NPC와 대기열 변화를 관찰한다.
6. 같은 입력의 결과 hash와 4%·유보금·순환 Preview를 연결한다.
7. 이후 음식점 구독·서비스 수준·자금 안전 카드를 독립 카드로 추가한다.
8. 실제 운영 적용은 검증된 정책 판본을 서버 Adapter가 명시적으로 수용할 때만 별도 진행한다.

하단 역할 카드 구현은 4~5 사이에 둔다. 먼저 면목제3·8동의 합성 주민·음식점·기사 상태 사본을 안정 ID로 만들고, 선택→카드 정렬→카메라 초점→상세→전체 보기의 읽기 폐루프를 닫은 뒤 정책 카드와 연결한다.

H 탐색은 역할 카드보다 먼저 해석한다. 현재 행정동·H3·H2·H1 문맥을 결정한 다음 그 공간에 명시적으로 결속된 주체·시설·업무 카드만 조회한다.

## 관리자 화면

첫 화면은 청구서가 아니라 읽기 전용 사용량·원가 관찰 화면이다.

```text
기간 / 앱 / 조직 / 사용자 / 기능 필터
  ├─ 총 요청·업무 사용량
  ├─ 직접 관측 원가
  ├─ 단가 기반 추정 원가
  ├─ 공유 인프라 배부 추정
  ├─ 원가 미확정 사용량
  ├─ 구독 정책을 적용했을 때의 Preview
  ├─ 플랫폼 보유 매출 대비 영업이익률
  └─ 보호자금·유보금 충족 뒤 순환가능잉여현금 Preview
```

사용자 상세에는 비용 총액만 보여 주지 않고 어떤 기능·단위·단가 판본에서 나온 값인지 드릴다운할 수 있어야 한다. 운영 화면에서 사용량을 수정하거나 소급 청구하지 않는다.

## 구현 우선순위

1. `MetricKey` Catalog와 기능·동작 결속 대장을 만든다.
2. append-only `사용량사건`과 일·월 집계 Projection, privacy allowlist를 만든다.
3. `SsalddelAdminApp 0.1.0`의 다섯 route를 기술 사용량 첫 절편으로 계측하되 내부 운영 원가로만 귀속한다.
4. 비용이 실제 발생하는 외부 Adapter부터 직접 원가·단가 판본을 연결한다.
5. 주문·배차·운송·입고의 업무 사용량을 기존 Event/Outbox와 멱등 결속한다.
6. 관리자 읽기 API와 사용량·원가 화면을 추가한다.
7. 30일 `ShadowMetering` 결과로 월 구독 포함량·상한·초과 정책을 Simulation한다.
8. 플랫폼 보유 매출·운영비·유보금 하한과 4% 목표를 이용한 순환 정책 Preview를 연결한다.
9. 사람 승인, 약관·환불·세금·결제 검토 뒤에만 실제 청구·배분 Command를 별도 Goal로 연다.

현행 우선순위에서는 1~8을 Unity 운영 정책 실험장 안에서 먼저 수행한다. 실제 음식점 청구·기사 지급·채용·자동 배분은 후순위다.

## 검증

- 같은 멱등 키 재처리가 업무 사용량을 늘리지 않는다.
- 사용자와 비용 귀속 조직이 다를 때 개인에게 잘못 청구되지 않는다.
- 실패·재시도·Outbox 재처리·백그라운드 작업의 집계 규칙이 각각 유지된다.
- `Simulation` 사용량이 운영 청구 후보에 섞이지 않는다.
- 원가 단가 판본을 바꿔도 과거 사건의 계산 근거를 재현할 수 있다.
- 사용자·조직·기능별 합계가 원시 사용량 사건 합계와 일치한다.
- 개인정보 금지 필드가 직렬화·로그·관리자 응답에 포함되지 않는다.
- 계량 장애가 핵심 주문·운송 업무의 latency와 가용성을 부당하게 악화시키지 않는다.
- 재무 사건·현금 흐름·기사 월정산과 사용량 원장이 서로 덮어쓰지 않는다.
- 총거래액·상품대금·기사 수행대금 같은 통과자금이 플랫폼 보유 매출에 섞이지 않는다.
- 영업이익 4%와 실제 가용현금·유보금·순환가능잉여현금이 서로 다른 값으로 표시된다.
- 유보금 하한이나 순환 정책 판본을 바꿔도 과거 Preview를 당시 판본으로 재현한다.
- 같은 seed·정책·가상 입력은 같은 인력 처리·대기열·자금 결과 hash를 만든다.
- 카드 적용 전에는 권위 Simulation 상태가 바뀌지 않고 적용 후 같은 revision 상태를 재조회한다.
- Save/Replay와 Local/Remote가 같은 정책 계약과 계산 결과를 사용한다.
- 실제 운영 관찰 모드에서 Unity 카드가 운영 주문·배차·채용·지급 상태를 변경하지 않는다.
- 지역·건물·NPC에서 연 카드가 같은 `SubjectStableId`를 선택하고 전체 Scene을 재생성하지 않는다.
- 카드 슬롯 열기·정렬·접기·카메라 초점이 WorldTick과 NPC 업무를 중단하지 않는다.
- 운영 자료에서는 개인정보 금지 필드가 카드·상세·로그·Save/Replay에 남지 않는다.
- 기존 전투·일행 역할 카드 상태와 디오라마 생활 주체 카드 상태가 서로 변경되지 않는다.
- H3→H2→H1 이동과 상위 복귀가 같은 H 결속 revision에서 결정적으로 재현된다.
- `Candidate`와 `WaitingForHBinding`이 확정 H 또는 실제 업무 장소로 승격되어 표시되지 않는다.
- H2·H3 미결속 상태에서도 승인된 H1 직접 선택은 유지되며 빈 계층을 자동 생성하지 않는다.
- 같은 교환 제안을 재처리해도 카드 소유권이 한 번만 바뀐다.
- 교환 완료는 양쪽 카드가 같은 transaction에서 함께 이전되며 한쪽만 이전되지 않는다.
- 주체·업무·멘토·역할 카드는 교환 가능 수집 카드로 잘못 분류되지 않는다.
- 교환 취소·만료·소유권 충돌 뒤 양쪽 카드 슬롯이 최신 상태를 재조회한다.

## 제외

- 실제 구독 결제와 자동 갱신
- 미납 차단과 서비스 정지
- 사용자별 가격 차별
- 확정 세금계산서·회계 전표·수익 인식
- 공유 인프라 비용을 실제값처럼 표시
- 기존 기사 월 이용료·음식점 정산·배달 수행대금의 일괄 통합
- 자동 배당·성과보상·쿠폰 지급·요금 인하·재투자 송금
- 4% 목표를 보장 수익률이나 개별 거래 수수료로 적용
- Unity 정책 카드에서 실제 채용·계약·청구·지급 실행
- Simulation NPC 인원과 실제 직원·기사의 동일시
- 무작위 카드 뽑기·희귀도·카드 소모·덱 과금
- 실제 사람을 수집 카드처럼 등급화하거나 배차 점수로 사용
- 행정동을 H3로 자동 변환하거나 주소·건물 유형만으로 H1·H2·H3 생성
- 주민·음식점·기사·업무 카드를 소유물로 양도하거나 판매
- 카드 공개 경매·현금 거래·유료 뽑기·희귀도 가격 책정

## 확정

- 원자적 측정은 설명 가능한 안정 단위로 하며 내부 메서드 호출을 과금 단위로 삼지 않는다.
- 사용량 사실, 원가, 구독 정책, 청구·재무를 분리한다.
- 첫 적용은 실제 과금 없는 `ShadowMetering`이다.
- 서버가 사용량 사실의 권위를 가지며 앱은 조회만 한다.
- 음식점·마트·지사처럼 여러 사람이 함께 쓰는 업무 기능은 조직 구독 계정에 비용을 귀속한다.
- 개인 사용자는 행위자로 추적하되 조직 업무 비용을 개인에게 자동 청구하지 않는다.
- 조직 귀속을 검증하지 못한 사용량은 `AttributionPending`으로 닫힌 채 실패하며 청구 후보에서 제외한다.
- 첫 외부 구독 상품은 음식점 조직 월 구독이다.
- 주문자 개인 구독은 150건 활동 기사 지정 제안의 별도 상품 후보이며 일반 주문·일반 배차를 유료화하지 않는다.
- 주문자 구독의 단위경제성은 지정 주문 1건·구독자 월·플랫폼 기간 전체를 분리해 계산한다.
- 플랫폼 보유 매출 대비 영업이익률 약 4%를 운영 목표로 둔다.
- 의무 지급과 운영 안전 유보금 충족 뒤 남는 현금만 순환 후보로 본다.
- 순환가능잉여현금은 서비스 품질 재투자·이용 조직 환원·현장 참여자 지원·추가 유보의 네 바구니로 관리한다.
- 네 바구니의 비율은 판본화하며 이미 마감한 기간에 소급하지 않는다.
- 실제 영업보다 Unity 운영 정책 실험장을 먼저 완성한다.
- 공유 코어는 계산 규칙과 정책 계약에 한정하고 운영 원장과 Simulation 저장은 분리한다.
- 면목제3·8동 디오라마 선택 시 주민·음식점·배달 기사 카드를 하단 슬롯에 펼치는 방향을 사용한다.
- 디오라마 생활 주체 카드는 기존 전투·일행 역할 카드와 의미·상태·API를 분리한다.
- 하단 슬롯은 행정동→H3→H2→H1 문맥을 먼저 정한 뒤 해당 공간의 주체 카드를 연다.
- H2·H3가 미정이어도 승인된 H1을 직접 선택할 수 있고 빈 계층은 자동 생성하지 않는다.
- 행정동 첫 진입은 H3 요약 카드를 우선하고 `전체 주체` 필터를 별도로 제공한다.
- 플레이어 카드 교환 방향을 허용하되 디오라마 주체·업무 카드는 양도 불가로 둔다.
- 교환 가능한 첫 범위는 별도 소유권을 가진 지역 관찰·경험 수집 카드다.

## 미정

- 첫 외부 비용 Adapter와 최초 구독 상품의 포함량·가격은 사용량 자료를 본 뒤 정한다.
- 주문자 구독료, 월 지정 제안 포함량, 정상 완료 건당 기사 지정 보너스는 `ShadowMetering` 뒤 정한다.
- 운영 안전 유보금의 정확한 하한과 4% 목표 허용 범위는 운영 자료를 본 뒤 정한다.
- 네 바구니의 최초 비율은 실제 사용량·현금 흐름을 본 뒤 정한다.
- 첫 인력 카드가 대표할 운영 역할과 업무 대기열을 정해야 한다.
- 지역·건물·NPC 선택이 하단 카드 전체 보기와 필터 보기를 어떻게 전환할지 첫 기본 상태를 정해야 한다.
- 행정동을 처음 선택했을 때 H3 요약 카드부터 보일지 전체 주체 카드부터 보일지 정해야 한다.
- 첫 교환 상대 범위를 같은 Simulation 팀과 명시적 친구 관계 중 어디까지 열지 정해야 한다.
