## 4. Claude에게 우선 전달할 두 수정

아래는 `reviewed-source-fingerprints.json`에 기록한 소스 판본의 결손이다. Claude가 같은 파일을 계속 고치는 중이므로 적용 직전 최신 코드를 다시 확인한다.

### A. 건물 색인을 메시와 같은 판본에 결속

현재 `buildingIndexSha256`는 목록에 있지만 `LoadBuildingIndex()`는 JSON을 바로 읽는다. 먼저 원본 TextAsset 바이트의 SHA256을 목록과 대조하고, 그다음 schema·원점·미터 환산값·동 귀속·ID 중복·동별 수량을 검사해야 한다. 통과하기 전에는 클릭 가능한 건물 외곽이나 역할 대응을 만들지 않는다. 색인 실패는 건물 선택 불가와 이유로 표시하고 기존 OSM 색인을 대신 얹지 않는다.

**회귀 조건:** 정상 자원, 색인 한 바이트 변조, 색인 누락, 원점/환산값 불일치, 중복 ID, 목록 밖 동, 동별 수량 불일치를 각각 확인한다. 독립 감사기는 이러한 입력을 분류하지만 **게임의 실패 처리 연결은 아직 구현·검증하지 않았다**.

### B. 목록 없음과 목록 손상을 구별

현재 `EnsureDongManifest()`는 목록 부재와 잘못된 schema/내용을 모두 null로 반환하며 `DongModulesActive`가 false가 되면 예전 OSM을 읽을 수 있다. 다음 세 경우를 구분한다.

| 조건 | 기대 결과 |
| --- | --- |
| 목록 파일을 의도적으로 제거 | 기존 OSM 복귀 유지 |
| 기존 `--sagajeong-*` 검증 촬영 | 기존 OSM 검증 경로 유지 |
| 목록은 있으나 파싱/schema/필수 항목 실패 | 목록 오류를 표시하고 모듈 처리를 중단. OSM 메시·색인을 정상 대체 자료로 읽지 않음 |

단순히 `DongModulesActive`를 true로 바꾸면 null 목록을 쓰는 코드가 생길 수 있다. **자원 존재/요청 여부·유효 목록·로드 성공**을 구분하고 메시와 색인 양쪽의 분기를 함께 확인한다. 이 구분 때문에 화면의 업무 결과·돈·재고·시계가 바뀌면 안 된다.

## 5. 다음 시각·자료 보완 순서

1. **현재 여섯 동의 도로 판독:** 큰길 표현과 OSM 배달 경로가 어긋나거나 빈 땅을 달리는 구간을 먼저 표시한다. 기존 도로 그래프는 1,388노드/1,458간선이며 동쪽 한계가 약 127.09345도다. 면목3·8동 모듈은 약 127.11015도까지라 이 표본만으로 여섯 동 전체 골목을 채울 수 없다. 골목 추가는 출처·자료 세대·범위와 동별 누락률을 확인한 뒤 별도 연결한다. 배달 경로를 바꾸지 않고 GUI 선을 덮는 것만으로 실제 도로 보완 완료라 하지 않는다.
2. **4구 목록·준비도:** 구별로 기존 scope 포함 여부·현행 자료 여부·소비 자원 존재·읽기 성공·권리 제한을 별도 표시한다. 노원은 **r2 scope에 0개**이며 서울 원자료가 없다는 뜻은 아니다. 수집됨/그릴 수 있음/통행 가능을 한 개의 준비 상태로 합치지 않는다.
3. **주소와 높이:** 주소 없는 건물은 미확인으로 유지한다. 가장 가까운 주소를 자동으로 실제 주소라 붙이지 않는다. 원본 높이·층수 환산·상징 높이와 14m 위의 표현 압축을 구별한다.
4. **읽기 수명/카메라:** 동별 카메라 복귀와 필요할 때 로드/해제를 별도 후속 기능으로 다룬다. 먼저 현재 붙여 보기·띄워 보기·이 동만 보기의 클릭/역할/배달 표식 좌표와 업무 불변을 실제 실행판에서 확인한다.

추가 동을 구울 때도 특정 동만 높은 품질로 만들지 않고 r48의 전체 범위 공통 품질 원칙을 따른다. 새 지역이나 현행 자료 취득을 이번 감사 통과만으로 자동 승인하지 않는다.
