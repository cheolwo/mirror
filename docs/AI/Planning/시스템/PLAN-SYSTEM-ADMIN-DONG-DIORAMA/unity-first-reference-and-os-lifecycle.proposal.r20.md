## 결론과 승인 범위

면목제3·8동을 **행정동 디오라마의 참조 대상**, 기존 사가정역 1km×1km 창을 **생활 모습을 자세히 관찰하는 참조 창**으로 삼는다. Unity에서 한 업무가 보이도록 연결하고, 그 모습을 통해 OS 간 상태·인계·예외의 빈틈을 찾아 공통 규칙과 원장을 보완한 뒤 다른 동으로 넓힌다.

- 확정 방향: 2026-09-22 사용자 요청에 따라 Unity 중심의 점진적 개발, 면목제3·8동 기준 비교, 기능을 만들면서 OS 생명주기 적합성을 재검증하는 방향을 기록한다.
- 제안 상태: 아래 작업 순서·개별 구현 범위는 `Proposed`다. 실행 승인·기획 hash·작업지시서·정확한 쓰기 경로를 결속하기 전 제품 코드를 변경하지 않는다.
- 대체 관계: [r19](README.md#r19-면목제38동-아이소메트릭-디오라마-우선순위)의 공간·권리·출처 관문은 유지한다. 다만 사진·고급 외관 제작을 모두 끝내야 생활 표현에 착수하는 순서 대신, **공간 정밀화와 격리 합성 업무 검증을 분리하여 작은 단위로 함께 진행**하는 순서를 제안한다. 합성 실험의 성공은 현재 행정 경계 게시나 실제 운행 허가를 만들지 않는다.
- 이번 작업: 문서·현재 소스 조사만 수행했다. Unity 실행·DB 재조회·새 자료 수집·운영 workflow 실행·commit·push는 하지 않았다.

## 2. 참조 모듈에서 복제할 것과 복제하지 않을 것

다른 동에 복제할 것은 사가정 건물·숫자·좌표가 아니라 **자료를 읽고, 공간을 조립하고, 업무를 알아볼 수 있게 보여주는 계약**이다.

| 구성 | 재사용할 것 | 동마다 별도로 가져올 것 |
| --- | --- | --- |
| 공간 자료 | 기존 manifest/tile/overlay, 공통 사가정 원점 ENU·500m 격자 | 행정동 ID, 경계 판본·hash, 건물·도로, 결손·사용 가능 상태 |
| 공간 포함 관계 | 기존 H 의미 계층과 Graph Map의 관계 | 어떤 지역·블록·시설이 연결되는지에 대한 검증된 결속. 행정동을 무조건 H3로 지정하지 않음 |
| 역세권 상세 창 | 기존 역세권 Host·8계층 Adapter | 역 ID, 관찰 범위, 해당 동과의 겹침 관계. 역 중심 1km 사각 전체가 한 동 안에 있다는 가정 금지 |

## 3. Unity 중심 개발의 의미와 상태 권위

Unity 중심이라는 말은 **사용자가 보고 확인할 수 있는 결과를 개발의 기준으로 삼는다**는 뜻이다. 주문 수락·재고 증감·인수 완료를 MonoBehaviour에서 새로 확정한다는 뜻은 아니다.

```text
공공 공간 자료 → 행정동 구성 대장·타일 → 배경 표현
                                            ↓ 의미 위치 연결
합성 업무 입력 → 기존 업무 Runtime/Command → 확정 상태 사본 → Unity 관찰
                         ↑                                  ↓
                   규칙·계약 보완 ← 화면과 원장을 대조한 결손 기록
```

- 자율 NPC 실험: 기존 Simulation Core의 `LocalProcess` 또는 같은 Core를 실행하는 `RemoteHost`를 쓴다. 로컬 실험 결과를 실제 운영 원장으로 전환하지 않는다.
- 실제 운영 논리 검증: 격리 `Development + Simulation` 호스트에서 기존 업무 Controller→UseCase/Command→원장→Event/Outbox→조회 경로를 통과시킨다. 테스트 데이터·외부 효과 차단을 유지한다.
- 표본 재생은 화면 검사용으로 계속 유용하지만, 미리 써놓은 단계 문자열을 재생한 결과는 업무 규칙 실행 증거가 아니다.
- 관찰 화면은 GET과 메모리 사본만 사용한다. 실험 시작·초기화는 기존 검증 도구가 맡고, 관찰 카메라와 지역 전환이 주문을 생성하거나 Simulation을 재시작하지 않는다.
- 각 OS 원장을 하나의 가변 원장으로 합치지 않는다. 주문/업무 연관 식별자·인계 Event·각 원장의 revision을 결속하여 한 건의 시간순 사건과 현재 상태를 함께 조회한다. 서로 다른 OS의 revision 숫자가 같아야 한다고 가정하지 않는다.
- 실패 시 동결 사본·오류·만료를 드러낸다. 서버 연결 실패를 합성 성공 화면으로 대체하지 않는다.

## 4. 우선순위와 완료를 확인할 장면

### P0 — 면목제3·8동을 재사용 가능한 기준판으로 정리

1. 현재 후보 경계·기존 사가정 상세 창·업무 의미 위치의 ID와 판본을 한 참조 구성에 결속한다. 현행 경계 부재는 계속 표시한다.
2. 공간 선택 단계와 실제 로드 성공을 분리한다. 클릭한 이름이 아니라 받은 구성 대장의 ID·hash로 현재 지역을 표시한다.
3. 행정동 전체→사가정 상세 창→업무 장소 선택→되돌아가기까지 같은 Scene에서 확인한다. 카메라 복귀·선택 해제·모듈 해제 때 이전 지역 객체가 남지 않아야 한다.
4. 공간 자료 교체와 업무 사본 갱신을 분리한다. 업무 단계가 바뀔 때 건물·도로 전체를 재생성하지 않는다.

산출물: 참조 구성의 연결표, 미결속·누락 목록, 전체/근접/복귀 Game View와 입력 재현 기록. 현행 경계·출입구 수집은 별도 자료 관문으로 유지하고 비공개 합성 실험과 혼동하지 않는다.

### P1 — 음식 주문 한 건으로 OS 간 연결 검증

처음부터 모든 OS를 다시 만들지 않고 아래 한 건의 흐름을 검증 묶음으로 삼는다. 실제 구현은 준비된 주체 사이의 WI 하나씩 분해한다.

| 주체·OS | 확인할 직접 결과 | 다음 책임과 인계 조건 |
| --- | --- | --- |
| 주문자·주문 | 주문 생성과 접수 상태 | 음식점이 같은 주문을 조회하고 수락·거절 가능 |
| 음식점·판매 | 수락·조리 시작·준비 완료 | 수락 후 배차 후보 탐색과 조리는 병행 가능. 픽업 가능과 단순 배차 대기를 구분 |
| 배차·배달 | 제안·기사 수락·도착·픽업 | 기사 거절 가능, 음식 준비 완료와 인계 확인 없이 픽업 완료 금지 |
| 배달·주문 | 전달·수령 확인 | 전달과 주문자 수령 확인의 소유·완료 기준을 기존 계약과 대조 |

추천 첫 WI는 **음식점이 주문을 수락하여 조리 상태와 배차 대기 정보가 함께 이어지는 구간**이다. 기존 WI/승인 명세를 먼저 찾아 재사용한다. 이후 픽업→전달→수령 확인을 별도 작은 작업으로 닫는다.

Unity에서는 주문자·음식점·기사 표식과 선택 카드에 현재 단계·대기 이유·갱신 시각을 보여준다. 이동 애니메이션은 이미 확정된 단계 안에서만 보간하고 다음 업무 성공을 예측하지 않는다. 도로 권위가 없으면 합성 이동 기준점임을 표시한다.

### P2 — 예외와 회복을 같은 기준판에서 검증

- 조리 지연과 배송 지연을 먼저 다룬다. 기사 재배차 대기는 정상 배차 상태일 수 있으므로 그 자체를 예외 사건으로 새로 중복 등록하지 않는다.
- 조리 지연의 예상 시각 변경·알림 정책, 픽업 전 배차 해제·재배차, 픽업 후 사고의 보호 보류·후속 인계를 각각 기존 계약과 비교한다.
- 주문 취소·환불·금전 귀속·기사 귀책을 표현 계층이나 시나리오 Runner가 자동 확정하지 않는다. 정책 미정은 미정으로 표시한다.
- 중복 Command·낮은 revision·늦게 도착한 옛 지역 응답·통신 실패/복구·TTL 제거를 시험한다. 실패한 한 건 때문에 다른 건 전체를 되감지 않는다.

산출물: 정상과 회복의 전후 원장·상태 사본 대조, 대기/회복/복귀 화면. 새로 필요한 정책만 사용자 문답으로 돌려보낸다.

### P3 — 다른 행정동 한 곳에 같은 구성을 적용

면목제3·8동 기준판이 P1의 정상 흐름과 P2의 대표 회복 하나를 통과하면, 기존 30개 후보 중 인접 동 한 곳을 고른다. 대상은 자료 결손·권리·좌표 결속을 확인한 뒤 정하며 이번 문서에서 임의 확정하지 않는다.

동별 분기 코드를 복사하지 않고 공간 자료·의미 위치·표현 프로필만 교체한다. A→B→A 전환에서 이전 응답 혼입·객체 중복·권위 상태 초기화가 없음을 검증한다. 두 동의 건물 수나 생김새를 같게 맞추지 않으며, 30개 전체 확장은 이 검증 이후 배치 작업으로 진행한다.

### P4 — 창고·마트·화물의 독립 생명주기를 순차 확장

| 순서 | 기존 모듈을 재사용할 검증 묶음 | 첫 대표 회복 |
| --- | --- | --- |
| 창고 | 입고 계획→입고→검수→적치→재고 반영 | 12개 중 정상 10개 적치·불량 2개 격리. 폐기·환불 자동 확정 금지 |
| 마트 | 주문→재고 확보→피킹→포장→인계 | 품절/수량 불일치 또는 인계 대기. 포장 완료와 기사 픽업 완료를 분리 |
| 화물 | 의뢰→수락→상차→운송→하차→인수 | 정상 8개 인수·파손 2개 보호 보류. 보험·배상·귀책 자동 확정 금지 |

위 순서는 개발 우선순위이지 창고가 있어야 화물을 실행할 수 있다는 의존 관계가 아니다. 각 영역은 독립 Fixture와 원장으로 실행한다. Farm 생산이나 영역 간 운송을 필수 선행 조건으로 삼지 않는다. 정밀 외관·Blender 랜드마크·광고는 이 흐름을 읽기 어렵게 하거나 검증을 막는 부분부터 보완한다.

## 5. 이후 구현 작업마다 남길 검증

1. 기획 항목별 `코드 존재 O/X`와 정확한 소스 경로를 적는다. 미조사 항목은 X가 아니라 미조사로 둔다.
2. 별도로 자동 시험, 실제 Runtime/서버 실행, Unity 화면을 구분한다. 이 구분은 완성도 점수가 아니다.
3. 각 WI는 기존 Goal·승인 기획 revision/hash·허용 경로와 E1~E7 명세를 결속한다. Graph Map은 주체·기능·인계 관계, 배치맵은 위치·표현 제약을 맡는다.
4. 첫 화면·업무 진행·예외·회복/복귀를 같은 실행 ID로 캡처한다. PNG만으로 움직임이나 서버 업무 성공을 증명하지 않고 단계·revision·필요 시 Transform 기록을 함께 대조한다.
5. 작은 변경의 기본 관찰은 약 5분으로 제한하고, 기존 600초 시나리오처럼 끝까지 보아야 하는 항목은 별도 장기 검증으로 명시한다. 실행하지 않은 10분·빌드 검증을 완료로 표시하지 않는다.
6. 지역 전환 전후 NPC Tick·원장·객체 수·Console을 확인한다. 기존 오류와 신규 오류를 구별하고 실제 화면을 사용자에게 보여준 뒤 다음 작업을 정한다.

## 6. 개발 인계 후보와 이번 종료 판정

- 첫 개발 대상: P0의 기존 공간 선택→구성 대장→표현→복귀 연결. 쓰기 후보는 Hongdal `Ssalddel.Unity/Runtime/WorldProjection/`와 Unity의 기존 `WorldMap` 선택·`World` 조립/시험이다. 정확 파일·작업 소유와 승인 hash는 개발 수용 시 동결하며 이 목록으로 전체 폴더 수정을 승인하지 않는다.
- P1 인계 전: 실제 주문·음식점·배차 Controller/UseCase와 Simulation Adapter를 대조하여 재사용/누락을 구분한다. 이번 조사는 그 모든 실제 업무 경로를 검증한 결과가 아니다.
- 미정: 두 번째 행정동, 단계별 UI 상세, 기존 계약으로 해소되지 않은 회복 정책. 현행 경계 수집·배포 승인은 별도 관문을 유지한다.
- 다음 질문 하나: 첫 생활 검증을 음식점의 주문 수락→조리 시작·배차 대기 연결부터 시작할까요? 추천은 이 구간이다. 세 역할의 상태 연결을 작게 확인할 수 있으며, 픽업·인수 완료까지 한 번에 구현하는 부담을 피할 수 있다.
- 출처와 반례 점검: 기존 코드·판본화된 기록만 사용했다. 활성 사가정 프로필 한 개와 30개 후보 자료의 차이는 전체 동의 생활 기능 동등성을 주장할 수 없다는 근거다. 기존 출처·비공개·권위 분리 규칙을 유지한다. 새로운 현장 관찰이나 반복 실험이 없으므로 **새 디오라마 규칙 후보 없음**. 기계 대장과 E 상태를 승격하지 않는다.
