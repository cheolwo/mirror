# [기획 · 월드·공간·배치 · PLAN-SYSTEM-ADMIN-DONG-DIORAMA · 구현 r5]

## 승인 근거

2026-09-14 사용자는 동북서울 30개 행정동 디오라마를 사가정역 디오라마에서 검토한 깊이에 맞춰 계속 발전시키고, 현재 캡처 가능한 수준이면 행정동별 화면을 남기며, 부족하면 도로명주소·도로·골목·신호·생활 자료를 더 수집해 배달 기사와 주민의 생활상을 표현할 수 있게 해 달라고 요청했다.

이 요청은 30개 동이 이미 사가정역과 동등하다고 간주하는 승인이 아니다. 사가정역 자체도 여러 독립 검증 조각의 합이며, 실제 저장 Scene에서 완결된 단일 생활 디오라마는 아니다. 따라서 공통 깊이 기준과 자료 결손을 먼저 고정하고, 현재 자료로 가능한 기초 공간 화면과 생활상 화면을 구분한다.

## 이번 구현 범위

1. `northeast-seoul-rider.r2`의 정확한 30개 행정동에 공통 깊이 관문을 적용한다.
2. 역사 경계·건물 외곽·NodeLink 중심선만 담은 r2 후보를 서버의 `current` 포인터를 건드리지 않는 로컬 Unity 검토 묶음으로 내보낸다.
3. Unity는 후보 봉투와 기존 manifest·tile·overlay 계약을 검증한 뒤 한 번에 행정동 하나만 조립한다.
4. 새 Scene을 만들거나 저장하지 않고 canonical `SimulationWorldShell`에서 런타임 임시 객체로만 기초 공간을 표시한다.
5. 30개 동 전체 조망 PNG와 면목제3·8동 전체·근접 PNG를 실제 Play Mode Game View에서 남긴다.
6. 화면에는 `역사 경계 후보`, `주소·통행·차선·신호·보도 미검증`, `읽기 전용`, `공개 불가`를 명시한다.

이번 범위는 주소·필지·출입구·보도·골목·차로·신호·사업체·생활인구·NPC·운영 생명주기를 새로 수집하거나 게임에 적용하지 않는다. 해당 자료가 없는 상태를 화면 완성으로 숨기지 않는 것이 이번 구현의 핵심이다.

## 사가정 기준선의 해석

- 건물·주소·도로·차로·신호·보도·골목·사업체·생활인구·NPC·운영 OS·H·날씨는 서로 다른 자료와 실행 판본이다.
- 사가정의 주소는 후보·충돌·미해결 상태를 전수 기록했지만 공식 건물 주소로 승격된 것은 아니다.
- 신호 125건은 좌표계 결속이 차단되어 있고, 화면의 정지·재출발은 합성 저밀도 검증이다.
- 기사 1명과 차량 3대, 음식점 12곳, 4개 OS는 합성·검증 전용이며 실운영 사실이 아니다.
- 그러므로 30개 동의 목표는 위 조각을 복사하는 것이 아니라 같은 자료 계약·결손 표시·권위 경계를 재사용하는 것이다.

## 로컬 Unity 검토 묶음

서버 도구가 다음 봉투를 `artifacts/local`에만 쓴다.

- 후보 batch ID·scope hash·투영기 판본과 hash
- `publishBlocked=true`, `currentPointerUsed=false`, `distributionApproved=false`
- 행정동별 manifest·tile·빈 overlay
- 파일 SHA-256과 행정동별 건물·도로·tile 수
- `baseGeometryCaptureReady=true`, `lifeDioramaCaptureReady=false`
- 주소·필지·출입구·보도·골목·차로·신호·업체·생활·NPC·운영 결속의 결손 코드

Unity는 MongoDB를 직접 읽지 않으며 일반 API의 `current`를 우회해 게시된 것처럼 보이지 않는다. 로컬 봉투가 후보임을 검증하고, 기존 `AdministrativeDongDioramaInterpreter`를 통과한 자료만 표현한다.

## Unity 조립·성능 경계

- 활성 행정동은 한 개만 유지하고 전환 시 Mesh·Material·선택 상태를 모두 해제한다.
- 건물별 GameObject·Collider를 만들지 않고 결합 Mesh와 공유 vertex-color Material을 사용한다.
- 행정동 경계에서 동적 화면 범위를 계산하며 1km 정사각형이나 역 마커를 강제하지 않는다.
- NodeLink는 폭·차로가 없는 중심선이므로 일정한 기호 폭으로만 표시한다.
- 건물 높이는 원본 높이 또는 명시된 4m 기호값을 사용하고 주소·상호·역할을 추측하지 않는다.
- 기존 사가정 View와 Scene·Prefab은 수정하지 않는다.

## 자료 수집 순서

1. 최신 JUSO `TL_SCCO_GEMD`와 도로명주소 전자지도 또는 위치정보요약DB
2. 일별 연속지적도와 PNU coverage
3. 실폭도로·도로구간·출입구, 서울 차선·교차로·횡단보도·신호
4. 소상공인 상가정보·공개 시설과 건물/출입구 명시 결속
5. 250m 생활인구·교통 관측의 시간대별 익명 집계
6. 면목제3·8동 하나에서 차량·오토바이·보행·신호·OS 상태 사본 검증
7. 같은 계약을 나머지 29개 동에 확대

각 단계는 공식 링크·기준일·수집일·원본 hash·CRS·이용조건을 보존하고, 로컬 DB에 `PendingHumanReview` 또는 동등한 검토 상태로 저장한 뒤 독립 재조회와 멱등성을 확인한다. 승인이나 원본이 필요한 단계는 자료를 추측해 채우지 않는다.

## 검증 계획

- 서버: 동일 입력의 검토 묶음 byte 결정성, 30개 exact set, manifest/tile hash, 개인정보 없음, `current` 포인터 불변
- Unity EditMode: 후보 봉투 변조 거절, 중복 건물·tile 거절, 동적 범위, 결합 Mesh 예산, 행정동 전환 해제
- Unity Play Mode: canonical Scene, 활성 행정동 하나, 30개 순차 조립, 실제 Game View PNG, Console 오류, Scene hash·dirty 불변
- 증거 상한: 기초 공간 표현 증거이며 주소·차선·신호·보행·통행·운영 또는 생활상 완결 증거가 아님

## 완료 조건

- 30개 행정동 각각의 기초 공간 PNG와 파일·투영 hash가 서로 연결된다.
- 면목제3·8동의 전체·근접 화면이 실제 Play Mode Game View로 남는다.
- 어떤 캡처도 `current`, 공개 배포, 통행 가능, 게임플레이 준비 또는 사가정 생활상 동등성을 주장하지 않는다.
- 다음 수집에서 각 동의 결손 상태를 같은 관문으로 갱신할 수 있다.
