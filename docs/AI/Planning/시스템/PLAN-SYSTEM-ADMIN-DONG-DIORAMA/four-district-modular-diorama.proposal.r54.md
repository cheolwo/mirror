## 3. 모듈 단위 — 관리 단위는 동, 공간 조각은 기존 타일

```text
4구 대상/준비도 목록
  → 행정동별 manifest·자료/품질 모듈
    → 공통 좌표의 기존500m 타일 참조
      → 지면·건물·도로·확인된 오버레이의 공통 조립
        → 현재 동의 경영 안건·건물 역할을 읽는 게임 화면
```

**한 행정동 모듈은 그 동의 자료와 준비도를 묶는 단위**다. 행정동 하나를 타일 하나나 별도 Scene 하나로 만들지 않는다. 공통 격자 위치와 원본 자료를 재사용하되, 행정동별 타일 사본의 지역 ID·projection/hash와 선택 manifest의 결속은 보존한다. 한 동의 타일 payload를 다른 동에 그대로 넣지 않는다. 역세권 상세는 기존처럼 여러 타일을 보는 창이고 새 행정동 소유 영역이 아니다. 이 관찰 창의 참조와 행정동 간 타일 payload 공유를 같은 것으로 취급하지 않는다.

| 모듈에 읽을 내용 | 역할 |
| --- | --- |
| 행정동 고유 ID·명칭·상위 구·경계 판본 | 어떤 관리 지역인지 식별. 현행 목록/법정동 대응은 출처·효력 기준과 함께 대조 |
| manifest/타일·원점/범위·판본/hash | 그 동의 실제 공간을 선택하고 같은 입력으로 재현 |
| 건물/도로/지형/오버레이 참조 | 같은 조립 방식에 동별 실제 형상/자료를 넣음. 없는 층은 결손/미검증으로 표시 |
| 자료·표현·통행·게임 준비 상태 | 모듈 존재·보기·주행/배달 가능·업무 완료를 구별 |
| 건물/업무 역할 참조·관찰 위치 | 기존 게임의 건물 역할/선택과 카메라 복귀를 지역별로 연결. 실제 업무/점포를 새로 추정하지 않음 |

모듈화할 것은 **제작/읽기 계약과 조립 방식**이다. 면목동 메시·도로·건물 배치를 복사해 동 이름만 바꾸지 않는다. 실제 높이와 추정 높이, 원본 외곽과 합성 채움도 기존 근거 구분을 유지한다.

## 4. 동 사이 공간과 상태를 보존한다

- 기존 사가정 원점 ENU·500m 격자·단위/변환을 재사용한다. 동별 임의 원점이나 지면 오프셋으로 경계를 어긋나게 하지 않는다.
- 건물은 기존 원본 `PointOnSurface`의 단일 경계 포함 규칙을 따른다. 무효/경계 밖/복수 판정은 미해결로 남긴다. 이 도형 귀속 규칙을 건물의 법적 소유/주소/행정 관할 확정으로 확대하지 않는다.
- 도로는 기존 경계 절단·원본 ID 계보를 유지한다. 인접 동의 공유 지점·연결/표현 접합은 별도 검증하고 보기용 도로가 있다는 이유로 통행 가능을 선언하지 않는다.
- 법정동·행정동·서비스 권역·역세권 창은 별도 ID/판본이다. 법정동 면목동 하나를 가리키는 여러 행정동 이름을 같은 경계로 취급하지 않는다.
- 동 전환은 표현 자원의 로드/해제와 관찰 상태 전환이다. Core/Kernel의 시계·기사·진행 주문·자금/재고·정산·개인 성장·작성 입력을 초기화하거나 업무를 복제하지 않는다.
- 새 동이 준비되지 않았거나 로드 실패면 대상/이유와 현재 보고 있는 지역을 구별한다. 다른 동의 지형을 새 동 이름으로 표시하지 않는다. 마지막 정상 화면·기존 업무는 보존한다.

회색 기본 건물·내 관리 매장 민트·선택 강조의 기존 스타일은 공통으로 사용한다. 관리 관계는 기존 역할 원장을 읽고, 동 전체를 내 매장 색으로 칠하지 않는다. 자료/권리가 확인되지 않은 실제 가맹점·빈 점포·주민을 만들어 채우지 않는다.

## 5. 자료 관문과 네 구 확장

[r16 수집 관문](current-boundary-building-entrance-collection-gate.decision.r16.md)은 정확30개 scope의 **현행 경계 → 같은 배포 세대 건물/건물군 → 출입구** 순서와 사용 상한을 소유한다. 현재 저장된 관문은 `NotCollected / ApplicationBlocked`이며 이번에 취득/적용 완료로 바꾸지 않았다.

사용자가 요청한 네 구 전체는 기존 r2의 단순 활성화가 아니라 **대상 범위 확장**이다. 다음을 별도 후보 판본으로 준비해야 한다.

1. 네 구의 현행 행정동 목록/코드·효력 기준을 공식 관할 자료와 대조한다.
2. 기존30개와의 유지/분할·병합/신규·누락을 표시한다. 노원과 기존 scope 밖 동을 포함한다.
3. 검증된 집합을 새 scope 후보 revision에 결속하고 기존 r2/r16 원본을 보존한다.
4. 기존 관문 패턴과 자료 판본/권리·결손 검사를 새 범위에 명시적으로 연결한다. 도로 경계·연결 실패는 별도로 해소/재검증한다.

기존 Mongo 후보 collection·공용 manifest/타일/overlay 읽기 계약과 검증기를 재사용한다. 원본 수집·DB 저장·비공개 관찰·현재 게시·배포·Windows 보기·통행/배달은 각각 확인한다. 이 기획은 수집 예약 변경이나 machine scope/current pointer의 쓰기를 수행하지 않는다.

## 6. 추천하는 작은 준비 순서

| 단계 | 준비할 결과 | 검증할 핵심 |
| --- | --- | --- |
| 1 네 구 목록/준비도 | 전체 대상 후보를 같은 목록에서 읽고 기존/누락/보류를 표시 | 현재 행정동 집합·자료/판본과 scope 관계 |
| 2 기존 두 정거장 비교 | 면목본동·면목2동을 첫 연결 검토 후보로 하여 각자의 공간을 같은 UI/축척 원칙에서 비교 | 카드뿐 아니라 실제 경계·도로·건물이 달라짐, 지역 ID·공통 좌표 일치 |

| 4 네 구 공통 품질 확장 | 준비된 동부터 공통 건물/도로 판독층을 넓히고 상세를 층별 누적 | 지역별 준비도·프레임/메모리·인접 접합·보존/복귀 |

첫 두 정거장은 현재 관찰한 문제를 확인하기 위한 **제안 후보**이며 구현 승인/자료 준비 완료가 아니다. 모든 동을 최고 정밀도로 한 번에 만들거나 다른 동 준비를 첫 결과의 필수 조건으로 삼지 않는다. 공간 보기를 먼저 확인하고 해당 동의 실제 게임 주문/주행·역할 작업은 각 업무의 독립 명세로 연결한다.

현재 Windows는 고정 `hongdal-diorama`와 `hongdal-buildings` 묶음을 읽는 경로가 확인된다. 다음 개발 수용에서는 **정거장 지역 ID → 기존 동 manifest/타일 → 현재 소비 메시/건물 색인**의 Adapter 범위를 좁게 정해야 한다. HDIO/색인을 바꿔 읽는 것과 안전한 주행/픽업/전달 완주는 다른 검증이다.

## 7. 시안·개발 검토와 완료 조건

[Claude 입력서](../../../Handoffs/2026-11-13-Codex-Claude-4구다중동디오라마-준비-r54.md)에 실제 서로 다른 동의 비교·구별 준비도·전환 실패를 다음 시안의 검토 장면으로 남겼다. 이번에는 새 이미지/모델을 생성하지 않았다.

- 동 ID/manifest/판본과 실제 표시 경계·건물·도로가 일치한다.
- 두 동 전환/복귀에서 건물 ID·게임 업무·카메라/선택·작성 입력이 보존되고 중복/고아 객체가 생기지 않는다.
- 공통 좌표·인접 격자의 접합·행정동별 타일 결속·경계 도로의 표시/연결을 같은 판본에서 검증한다. 자료 미준비·로드 실패·낮은/늦은 판본·삭제/재등장을 드러낸다.
- 실제 게임 조작과 직접 주행은 준비된 지역/명세에서만 시험하며 다른 소비판의 PreviewScene·옛 캡처를 현재 Windows Runtime 근거로 승계하지 않는다.

**확정:** 요청한 네 구를 우선 범위로 기획하고 최신 캡처3장·시안1장을 직접 확인했다. 기존30개 모듈의 실제 파일/보존 audit와 현행 미준비·현재 고정 자료 소비의 차이를 확인했다.

**제안·미정:** 네 구의 현행 전체 목록/코드·새 scope/수집 관문 결속, 각 구 첫 대표 동, 자료/권리·품질 충족, 정확한 소비 Adapter·시안 승인·개발 명세/쓰기 경로와 Runtime 결과. 새 범위를 기존30개 수집/적용 승인에 자동 포함하지 않는다.

**다음 검토 하나:** 현재 두 정거장인 면목본동·면목2동을 각각 다른 공간 모듈로 읽는 비교부터 준비할까? 기존 순회의 이름만 바뀌는 문제를 가장 작게 검증할 수 있어 추천한다.
