# 공공데이터포털 분야 분류·MySQL 수집 계획 r5

- 상위 기획: `PLAN-SYSTEM-KOREAN-PENINSULA-PUBLIC-DATA-WORLD`
- 문서 성격: 로그인 계정의 현재 활용 목록을 바탕으로 한 수집 준비안
- 확인일: 2026-09-21
- 상태: `Proposed / PortalInventoryObserved / CollectionNotStarted`
- 첫 상세 권역: `region:kr:hjd:1126057500` 면목제3·8동과 사가정역 1km 상세 관찰 창
- 권위 경계: 공공자료 원본·정규화·품질 판정은 서버와 자료 저장 계층이 소유하고 Unity는 승인된 읽기 전용 투영만 사용한다.

## 확인한 현재 범위

로그인된 공공데이터포털의 `Open API 활용신청`과 `파일데이터 활용` 목록을 읽기 전용으로 확인했다.

- 사용 중 Open API: 37건
- 파일데이터 활용: 7건
- 현재 저장소의 `공공데이터포털활용ApiModuleCatalog`: 33개 API를 10개 업무 모듈로 분류
- 차이: 포털 현재 목록에는 식품영양성분, 건축HUB 건축물대장, HACCP·생약 관련 7건이 기존 33개 catalog에 없고, 기존 catalog의 공동주택 관리비 관련 3건은 현재 사용 중 목록에서 확인되지 않았다.

이 차이는 API 이름으로 덮어맞추지 않는다. 다음 구현에서 공공데이터포털의 공개 `dataId/UDDI`, 제공기관, 공개 명칭을 기준으로 `현재 사용 가능 / 만료·중단 / catalog only / adapter ready`를 각각 대조한다. 활용신청 record ID, 인증키, 사용자 개인정보는 기획 문서·DB 원장·로그·Unity에 저장하지 않는다.

## 우선순위

### P0 — 출처 대장 동결

44건을 모두 `SourceId + DatasetId`로 대조하고 다음 항목을 채운다.

- 제공기관, 공개 명칭, 공식 URL, 접근 방식, 자료 형식
- 공개 data ID/UDDI, 사용 가능 상태, 이용 조건, 출처 표기
- 공간 단위, 시간 단위, 기준 시각, 갱신 주기
- 호출 한도, 페이지 방식, 증분 키, 전체 재수집 필요 여부
- 개인정보·사업자 식별자·주소의 공개/보호 범위
- adapter·normalizer 준비 상태와 첫 허용 지역

### P1 — 사가정·면목제3·8동 공간 기반

1. 행정표준코드 법정동 API와 법정동코드 파일을 상호 대조해 지역 코드 판본을 고정한다.
2. 건축HUB 건축물대장은 법정동·지번 기준으로 면목동 범위를 먼저 수집한다. 행정동 귀속은 검증된 행정동 경계와 건물 위치를 사용하며 문자열로 추측하지 않는다.
3. 공동주택 단지 목록·기본 정보를 건축물·도로명주소 안정 식별자와 결속한다.
4. 상가(상권)정보와 전통시장 2종을 사업장·시장 후보로 적재하되 현재 영업·실제 입점·광고 승인을 자동 확정하지 않는다.
5. 물류창고업등록정보를 지역 물류 거점 후보로 적재하되 가용 용량·운영 계약·출입 가능을 별도 검증한다.

### P2 — 지역 생활 관찰층

- KOSIS 지역 통계·지표
- 식품영양·HACCP·수입식품 공개 근거
- 지하철 공기질, 공동주택 에너지
- 한국관광공사 지역문화·관광 시설

P2는 P1의 지역 안정 식별자와 단위·시점 정규화가 닫힌 뒤 연결한다.

### P3 — 전국 공급망·경제 시계열

- 수협 조합·위판장·창고·재고·입출고·위탁판매
- 학교급식 계약
- 온라인 가격, 관세청 수출입 실적

전국 시계열은 사가정 디오라마를 채우기 위한 배경 관측이지 특정 점포의 실제 재고·가격·계약을 확정하는 자료가 아니다.

### P4 — 제한·후순위

- 국세청 사업자 상태는 업무상 필요하고 권한이 있는 단건 검증에서만 호출한다.
- 제주 국제학교와 생약 공정서 등 첫 권역에 직접 결속되지 않는 자료는 catalog에는 보존하되 자동 수집을 켜지 않는다.
- 공동주택 입찰·계약·유지관리 자료는 목적·보관기간·공개 범위를 별도 승인하기 전 대량 적재하지 않는다.

## MySQL 적재 구조

기존 수집 기반을 재사용하고 API별 임의 테이블을 먼저 늘리지 않는다.

```text
ExternalDataSourceCatalog
  └─ ExternalDataIngestionRuntime
       ├─ private raw object/file storage
       │    └─ 원본 본문, 원본 hash
       └─ MySQL PublicDataIngestionDbContext
            ├─ public_data_ingestion_runs
            ├─ public_data_raw_snapshots
            ├─ public_data_normalized_records
            ├─ public_data_region_mappings
            └─ 검증된 분야별 읽기 원장
                 ├─ 건축물대장·행정구역 귀속·용도 집계
                 ├─ 공개 인허가 사업장·건물 결속
                 └─ 후속 자료군별 필요한 최소 투영
```

- `public_data_ingestion_runs`: 실행 시각, 성공/실패, 건수, 재시도, 오류 코드를 기록한다.
- `public_data_raw_snapshots`: 원본의 위치·길이·hash·출처 판본·관측 시점을 기록한다.
- `public_data_normalized_records`: `RecordKey` 기반 멱등 정규화 관측을 보관한다.
- `public_data_region_mappings`: 제공기관 지역코드를 `RegionStableId`에 판본화해 결속한다.
- 건축물·사업장처럼 조회·결속 규칙이 이미 확립된 자료는 기존 특화 원장을 사용한다.
- 원본 본문은 MySQL BLOB으로 무차별 복제하지 않는다. 비공개 원본 저장소에 두고 MySQL에는 위치·hash·계보와 정규화 결과를 적재한다.
- 새 특화 테이블은 범용 정규화 행만으로 업무 조회·무결성·개인정보 분리를 충족할 수 없을 때 별도 migration과 독립 재조회 시험을 갖추어 추가한다.

| 형태 | 예 | 권장 방식 |
| --- | --- | --- |

| 시계열 | 가격, 통계, 공기질, 에너지, 재고·입출고 | 관측시각·단위별 append-only, 정정 판본 별도 기록 |

실제 갱신 주기는 각 API 문서와 응답 기준일을 P0에서 다시 확인한 뒤 확정한다. 임의의 일·주·월 주기를 사실처럼 고정하지 않는다.

## 실행 순서

1. `목록 대조`: 포털 37 API·7 파일과 코드 catalog 33 API를 공개 data ID로 비교한다.
2. `출처 등록`: `ExternalDataSourceDefinition`에 분야, 접근 방식, 권리, 갱신, credential reference를 등록한다.
3. `비밀 분리`: 인증키는 .NET User Secrets 또는 배포 환경 secret store에서만 제공한다.
4. `수집`: local `Staging + Simulation`에서 P1 한 자료씩 제한 범위로 호출한다.
5. `원본 고정`: 원본 저장 위치·SHA-256·출처 판본·관측/수집 시각을 기록한다.
6. `정규화`: 지역 코드, 주소, 좌표계, 단위, 시점을 표준화하고 결손·거절 사유를 보존한다.
7. `MySQL 저장`: 실행 원장·원본 사본 메타데이터·정규화 행·지역 매핑을 한 수집 단위로 결속한다.
8. `독립 재조회`: 저장 프로세스와 다른 조회에서 건수·hash·지역 범위·누락을 확인한다.
9. `멱등 재실행`: 동일 입력을 다시 실행해 중복 행이 생기지 않고 기존 hash가 재사용되는지 확인한다.
10. `검토 투영`: 품질·권리·개인정보 관문을 통과한 최소 자료만 관리자 조회와 후속 Unity 상태 사본 후보로 연다.

## 첫 구현 묶음과 완료 조건

첫 구현은 `P1-1 행정코드 + P1-2 건축HUB` 두 자료로 제한한다.

- 면목동 법정동 코드와 면목제3·8동 안정 식별자의 관계가 판본화되어 있다.
- 건축HUB 원본 hash와 수집 실행이 MySQL 원장에 남는다.
- 건축물은 원본 법정동·지번·도로명주소 근거를 잃지 않는다.
- 행정동 귀속이 불가능한 건물은 `Unresolved`이며 임의 귀속되지 않는다.
- 같은 입력을 두 번 실행해 원본 snapshot과 정규화 record가 중복되지 않는다.
- 잘못된 인증, 호출 한도, schema 변경, 기준일 불일치, 지역 매핑 실패가 성공으로 숨겨지지 않는다.
- 독립 MySQL 재조회로 실행 건수, 원본 hash, 정규화 건수, 거절 건수, 지역 범위를 확인한다.
- 상세 주소·사업자번호·인증키는 Unity 계약과 공개 관찰 자료에 포함되지 않는다.
- 이 단계의 결과는 DB 수집 증거이며 Unity Scene·Game View·현재 영업·배달 가능 증거가 아니다.

## 제외

- 이번 r5 문서 작성 중 실제 API 호출, 파일 다운로드, MySQL migration·적재·재조회
- 로그인 계정의 인증키·개인정보·활용신청 내부 record ID 기록
- 44건 동시 수집과 무제한 전국 수집
- 공공자료를 근거로 한 현재 영업·가격·재고·통행·배달 가능 자동 확정
- 검토되지 않은 상세 주소·사업자 상태·계약 자료의 Unity 또는 공개 API 배포
- 자료가 없는 도로·차로·보도·신호·필지·행정 경계를 다른 자료로 추정 생성
