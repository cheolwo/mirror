# 배달비 구성과 기간 공제의 계산 검토 기반 r6

- 기획 ID: `PLAN-OPERATIONS-FOOD-DRIVER-PAYOUT-DETAIL`

- 사용자 요청: 직접 정리한 배달비 구성과 정산 경험을 미러의 산정·정산 보완에 활용한다.
- 상태: `ReviewCalculatorImplemented / AdminApiImplemented / TargetedValidationPassed / FullValidationHasBaselineFailures / OperationalLedgerDeferred`

## 이번 구현

기존 관리자 요금 정책 API 아래에 두 검토 행동을 추가했다. `서버관리자전용`, 기존 3.0 버전·음식 배달 기능·업무 분류를 유지한다.

| API | 입력과 결과 |
| --- | --- |
| `POST /api/v1/admin/food-delivery-pricing-policy/payout-preview` | 유효기간·판본·픽업비·전달비·거리 단위·절사/올림 정책과 건별 거리·시간대 할증·매장 프로모션·지역 할증 → 항목별 구성과 합계 |
| `POST /api/v1/admin/food-delivery-pricing-policy/settlement-preview` | 대상 기간의 배달료·미션비·별도 기간 프로모션·달성 보너스, 적용 판정·비율·필요경비·절사·근거 → 공제 항목과 수령액 검토 |

계산은 `음식배달지급검토UseCase → 음식배달지급검토Policy`에서 수행한다. 기존 DB 정책·배차 제안·지급 요청·송금 상태를 변경하지 않는다. 응답은 계산 정책 사본을 포함한다. 검토용 입력을 공식 판정이나 운영 요율 승인으로 간주하지 않는다.

[합성 검토 입력 예시](calculation-review.examples.json)에 두 API의 입력과 기대 금액을 남겼다. 배달 구성은 4,720/1,700/2,180원 사례, 기간 정산은 합성 총액을 사용한다. 개인의 실제 주간 합계·매장·주소를 포함하지 않는다.

## 건별 지급 규칙

```text
거리 지급액 = 절사 또는 올림(max(0, 거리(km) × 1000 - 포함거리(m)) / 단위(m)) × 단위 지급액
구성 합계 = 픽업비 + 전달비 + 거리 지급액 + 시간대 할증 + 매장 프로모션 + 지역 할증
기사 공제 전 지급액 = 구성 합계 + max(0, 최소 지급액 - 구성 합계)
```

- 동시 픽업 묶음을 명시한 경우에만 요청 목록의 첫 건에 픽업비를 한 번 적용한다. 같은 매장 이름·인접 번호·0km만으로 묶음을 추정하지 않는다. 다른 날의 묶음 재사용은 거부한다. 목록 순서가 픽업비 귀속 순서이며 정책 사본과 결과 행을 함께 보존해야 한다.
- 앱 표시 거리·경로 추정·확정 경로를 구별한다. 미확인은 계산 오류이며 확인된 0km는 유효하다. 거리 단위는 m, 입력 거리는 km, 금액은 정수 원이다.
- 금액과 거리 등 필수 JSON 항목의 누락은 400 오류다. 미션·할증·보상이 없으면 확인된 0을 명시한다. 보험 적용 상태를 생략하면 `Unknown`으로 보존한다.
- 배달료에 이미 포함된 시간대 할증·매장 프로모션을 기간 미션비나 건수 보상으로 다시 더하지 않는다.
- 사용자의 관찰에서는 픽업/전달 각 700원, 100m당 80원 절사와 네 시간대 할증 비교가 가능했다. 이는 관찰 사례이며 외부 플랫폼 공식 전체 요금표로 확정하지 않는다. 실제 시간대 경계도 자동 추정하지 않는다.
- 기존 미러의 포함거리·기본거리 합산·기상/한시 수요 할증은 그대로 유지한다. 이 검토 정책을 기존 제안 생성 경로에 자동 적용하지 않는다.

## 기간 공제 규칙

```text
B = 이미 할증을 포함한 배달료 합계 + 세전 미션비
R = 별도 기간 프로모션 + 세전 달성 보너스
총 지급액 = B + R
보험 기준 = B 또는 B + R (명시한 처리 판본·근거에 따름)
각 보험 = 절사(보험 기준 × (1 - 필요경비율) × 기사 부담률)
기본 소득세·지방소득세 = 각각 절사(B × 해당 비율)
보상 원천세 = 별도 절사(R × (적용 소득세율 + 적용 지방소득세율))
수령액 검토 = 총 지급액 - 기본 세금 - 기사 부담 보험 - 보상 원천세
```

- `Unknown`, `Applicable`, `NotApplicable`을 구별한다. 적용 여부·보상 보험 처리 근거가 미확인이면 `NeedsReview`, 공제 금액·수령액은 `null`로 둔다. 모르는 값을 0으로 표시하지 않는다.
- 모든 적용/미적용 판정에는 근거가 필요하다. 비율은 소수(3%는 `0.03`)로 입력한다. 기본값은 적용 미확인이며 법정 비율·최저보험료를 하드코딩하지 않는다.
- 최저보험료는 명시한 정책에만 해당 기간 합계에 한 번 적용한다. 보수가 0인 기간에 최소 보험료를 생성하지 않는다. 기간 정산 검토를 일별로 여러 번 호출해서 합한 값을 주간·월간 확정액으로 간주하지 않는다.
- 보험 기준에서 별도 보상을 제외하는 개인 정산 검토는 지원한다. 일반적인 법적 제외로 확정하지 않는다. 기본 세금의 10원 절사와 별도 보상 세금의 1원 절사를 각각 정책으로 지정할 수 있다.
- 공제가 총액을 넘으면 음수 수령액을 지급 결과로 확정하지 않고 검토 필요로 반환한다.
- 플랫폼 수수료·사업주 부담 보험·상품대금은 기사 공제로 넣지 않는다. 플랫폼 매출·수익·자금 흐름은 별도 원장에서 다룬다.
- 건수 프로모션 달성 판정은 이번 API가 수행하지 않는다. 지급 대상 기간·완료 건수·정책 판본으로 먼저 확인한 세전 보상만 입력해야 한다. 121건째/250건 달성 등 기존 관찰 규칙을 미러 전체의 기본값으로 바꾸지 않는다.

## 출처와 한계

2026-10-02 공식 자료를 다시 확인했다. [국세청 사업소득 원천징수 방법](https://www.nts.go.kr/nts/cm/cntnts/cntntsView.do?cntntsId=7902&mi=6622)은 원천징수 대상 사업소득에 대한 3%를 안내한다. [근로복지공단 노무제공자 산재보험 안내](https://webzine.comwel.or.kr/vol152/sub02.html)는 월 보수 신고, 실보수 부과와 노무제공자·사업주 분담을 설명한다. 이는 계약·자격 판정과 공식 월 보험료 결과를 건별 숫자에서 추측하지 않는 근거이며, 개인 자료의 모든 비율·최저액·보상 제외를 확인하는 자료는 아니다.

실제 공제계산서·신고/부과 결과·노무/세무 검토가 운영 정책의 선행 조건이다. 검토 API에는 이를 승인하거나 송금하는 기능이 없다. 촬영 원본·사진·주소·주문자/기사 신원·계좌·전사 원문은 복사하지 않았다. 시험은 합성 식별자와 금액 사례를 사용한다.

## 후속 순서

2026-10-02 [r7 배차 총액 기준](dispatch-total-only.direction.r7.md)을 먼저 따른다. 배차 제안에는 공제 전 총 배달료 한 개만 표시하고, 세부 구성은 원장·완료 정산 상세에서 확인한다. 기존 총액 기록이 있으므로 새 원장을 처음부터 만드는 것보다 기존 제안 계산 Service와 운송/지급 원장을 연결·보완한다.

1. 기존 제안 계산 Service에 승인된 항목별 계산 정책을 연결한다. 이미 있는 총액·판본·기상/수요 기록을 활용하며 거리 근거·세부 지급 구성의 결손을 보완하고 과거 결손을 구별한다. 기사 제안의 기존 `DriverPayout` 총액 표시를 사용한다. 현재 `기사기본거리지급액` 합산 필드는 그대로다.
2. 기사 수행대금과 기간별 공제 원장을 추가한다. 공단의 월 확정 결과·공제 증빙·정정 다음 기간 반영·멱등 처리를 연결한다. 기존 `기사월정산`은 플랫폼 이용료라서 재사용하지 않는다.
3. 기사 본인의 완료 내역·지급 구성·기간 공제 조회를 연결한다. 승인·송금 처리·실지급 확인은 각각 별도 상태로 유지한다.
4. 플랫폼 구독/수수료 수입·사업주 부담·기사 지급·지사 보상·PG 지연을 분리해 수익성과 지급 가능 현금을 검증한다.
