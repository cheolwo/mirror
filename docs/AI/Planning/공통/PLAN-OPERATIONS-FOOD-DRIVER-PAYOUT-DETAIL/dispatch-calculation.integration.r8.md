# 실제 배차 제안의 세부 계산 연결 r8

- 기획: `PLAN-OPERATIONS-FOOD-DRIVER-PAYOUT-DETAIL`
- 판본: `dispatch-calculation.integration.r8` (2026-10-02)
- 승인 근거: 사용자의 “실제 배차에 연결하는 그걸 진행해 줘.”
- 범위: 기존 서버 배차 제안 계산·동결·기사 총액 조회. 운영 요율을 바꾸거나 외부 운영/지급을 활성화하지 않는다.

## 연결한 동작

`음식배달기사제안요금Service → 음식배달기사제안요금Policy → 음식배달지급검토Policy.구성계산`으로 배차 계산을 연결했다. 관리자 r6 검토와 실제 배차는 같은 구성 계산을 사용한다. 기존 포함거리·100m 단위 올림·기본 지급액·최소 지급액과 기상/한시 수요 할증은 유지한다. 검토 API의 정수 입력 제한과 기존 운영 정책의 소수 지급액은 구분한다.

기본 지급액의 픽업 몫은 기존 음식 요금 정책 관리자 API의 nullable `DriverPickupPayout`으로 지정한다. 전달 몫은 총 기본액에서 그 몫을 뺀 값이다. null이면 `LegacyUnsplit`으로 남기며 기존 기본액을 실제 전달비로 확정하지 않는다. 계산 계약의 DropoffFeeKrw 칸에 기본액 전체가 들어 있어도 이 구분 코드가 우선한다. 별도 배분을 지정했을 때만 `PickupDropoffSplit`이다. 기본 합계는 바뀌지 않는다.

기본/거리/최소 보정 합계에 검증된 기상 할증과 기존 유효시간의 한시 수요 할증을 더한다. 한시 수요 할증의 Simulation 제한은 유지한다. 다른 플랫폼에서 기록한 700원·80원 등의 금액이나 시간대 구간을 현재 정책으로 자동 채택하지 않는다. 매장 프로모션·지역 할증·동시 픽업 중복 면제에는 현재 확정된 배차 입력이 없으므로 적용하지 않는다. 같은 매장이라는 이유만으로 픽업비를 제거하지 않는다. 미션·기간 보상·원천세·보험은 배차 총액에 섞지 않는다.

제안 전 기존 운송 실행 투영의 합계 필드와 `기사제안요금계산근거Json`을 같은 SaveChanges에 저장한다. JSON은 기본액 배분 상태, 구성별 금액, 경로 추정 거리, 해당 의뢰 키, 계산 정책 사본, 기상 근거, 할증, 정책 판본과 서버 시각을 보존한다. 구성 계약의 유효일은 이 계산의 UTC 날짜로 한정한 재현용 사본이며 새 운영 요율의 실제 시행/종료일을 추론한 값이 아니다. 거리 근거 `RouteEstimate`는 기존 좌표 거리 계산이며 앱 거리·실제 주행/도로 경로 실측으로 승격하지 않는다.

재추천은 기존 판본을 유지한다. 기사 조회는 기존 `DriverPayout`으로 저장 총액 한 개를 반환하며 제안 카드의 표시를 늘리지 않는다. 수락·전달 완료 뒤에도 계산 근거와 지급액은 보존된다. 과거 동결 기록은 재계산/JSON 역채움하지 않는다. 판본 없는 과거 기록에 대한 기존 조회 fallback과 선택적 서비스 생성자의 호환 경로는 유지한다. 제품 DI는 기존 실제 계산 Service를 주입한다.

새 계산에서 거리가 null/음수/범위 밖이거나 정책 단위·구성이 유효하지 않으면 제안 전 `배차구성오류`로 차단한다. 0km는 실제 입력이 0인 경우에만 유효하다. 추천 상태 변경·알림 생성 전에 차단하며 수정 후 재시도할 수 있다. 수락 후 현재 정책으로 금액을 재산정하지 않는다.
