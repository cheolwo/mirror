# [기획 · 운영체제·화주 물류 · PLAN-OPERATIONS-SHIPPER-TRANSPORT-MANAGEMENT · r5]

- 기획 판본: `shipper-transport-management-os.r5`
- 상태: `Approved / RequestHandoffImplemented / CompletionReturnReceiptAcceptanceImplemented / PartialDamageReviewImplemented / OperationalActivationDeferred`
- 상위·관련 기획: `PLAN-OPERATIONS-LOGISTICS-OS`, `PLAN-OPERATIONS-DISPATCH-CORE`, `PLAN-OPERATIONS-SSALDDEL-MART-SUPPLY-NETWORK`
- 관련 WI·PlayableLoop: 없음. 운영 서버의 화주 업무 생명주기이며 Unity 실행 기획이 아님
- Graph Map 영향: `NoImpact` — 운영 업무 책임과 원장 관계를 정리하며 Unity 공간 관계를 만들지 않음
- 개발 인계 상태: `AcceptedInCurrentThread / FourOperationalSlicesImplemented / FrontendUnchanged`

## 목적

기존 화주 운송의뢰·기준운임·일괄등록·인수증·정산·재위탁 기능을 새로 복제하지 않고 `화주 운송관리 OS`의 한 생명주기로 재정렬한다. 화주가 운송 조건을 확정하는 책임과 기사 배차·상차·운송을 실행하는 책임을 분리하고, 두 업무는 판본화된 운영체제 업무 인계 원장으로 연결한다.

화주는 고정 직업이나 단일 앱 사용자가 아니다. 판매자·마트·창고·공동행동 운영자처럼 이번 계약에서 물건을 맡기는 당사자가 화주 역할을 가질 수 있다.

## 확정

안정 운영체제 식별자는 `ShipperTransportManagementOS`다. 다음 여덟 단계를 순서 있는 생명주기로 관리한다.

1. 화주 당사자 확정
2. 화물 정의
3. 운송 조건·운임 검토
4. 운송의뢰 확정
5. 화물운송 인계
6. 진행·조건 변경
7. 인수·검수
8. 정산·비정상 운송 처리·업무 회복

화주 운송관리 OS는 화물·상하차·운임·정산 조건과 화주의 최종 확인을 소유한다. `DomesticCargoTransportOS`는 인계를 수락한 뒤 기사 후보·배차·상차·운송·하차 실행을 소유한다. 화주 OS는 기사 후보를 직접 선택하거나 기사 상태와 배차 상태를 변경하지 않는다.

음식점·마트·일반 판매자는 개념적으로 같은 판매 업무군에 속할 수 있지만 코드 상속으로 하나의 거대 판매 OS에 묶지 않는다. 조리, 재고 할당, 피킹·포장처럼 서로 다른 이행 생명주기는 독립 책임으로 유지하고 운송이 필요한 결과만 화주 또는 배송 OS에 명시적으로 인계한다.

## 수직 조각 1 — 의뢰 확정과 화물운송 인계

현재 `POST api/v1/shipper/requests`는 다음 순서의 확정 경계다.

```text
화주 입력 초안
  → 서버 기준운임 계산·요금 정책 검토
  → 화주 운송의뢰와 화물 요구조건 저장
  → ShipperTransportManagementOS 인계 요청
  → 기존 화물 운송의뢰 존재 확인
  → DomesticCargoTransportOS 인계 수락
  → 같은 화주 의뢰 재조회에서 인계 상태 표시
```

인계는 `ShipperTransportRequestToDomesticCargo` 계약의 `shipper-transport-request-cargo-handoff.v1` 판본을 사용한다. 결정적 요청 ID를 사용해 같은 의뢰 재처리는 같은 인계 원장과 두 개의 요청·수락 Outbox를 재사용한다.

최소 상태 사본에는 화물 종류·수량·중량·부피·팔레트·온도·차량 조건·시간창·운임·정산 시점과 생명주기 단계만 포함한다. 화주 사용자 식별자, 실제 주소, 상세 주소, 전화번호와 GPS 좌표는 인계 사본과 Outbox에 복제하지 않는다. 같은 서버의 화물운송 실행은 권한이 있는 기존 화주 의뢰 원본을 별도로 조회한다.

인계 수락은 배차 시작이 아니다. 선결제 완료·후불 승인·현장지급 같은 기존 조건이 충족되어야 기존 배차 전이가 시작된다.

## 수직 조각 2 — 운송 완료와 화주 인수·검수 반환

기존 기사 업무의 `운송인수완료Command`는 하차 사진을 필수로 확인하고 운송 원장의 상태와 도착 시각을 저장한 뒤 `운송인수완료됨Event`를 발행한다. 이 권위 경계를 재사용해 다음 순서로 결과를 반환한다.

```text
기사 하차 증빙 제출
  → 운송 원장 인수완료·도착 시각 저장
  → DomesticCargoTransportOS 완료 결과 인계 요청
  → ShipperTransportManagementOS 인수·검수 대기
  → 화주의 기존 인수증 등록
  → 완료 결과 인계 수락
  → 기존 후불 정산 상태는 인수증등록완료로 진행
```

역방향 인계는 `DomesticCargoCompletionToShipperAcceptance` 계약의 `domestic-cargo-completion-shipper-acceptance.v1` 판본을 사용한다. 최소 상태 사본에는 운송 실행 고유 식별자, 완료 상태·시각, 하차 증빙 존재 여부와 양쪽 생명주기 단계만 넣는다. 사진 객체명·URL, 기사·화주 식별자, 주소·연락처와 GPS는 복제하지 않는다.

`인수완료` 이벤트만으로 화주 인수·검수를 자동 수락하지 않는다. 도착 OS인 화주 운송관리 OS의 기존 인수증 등록이 있어야 역방향 인계를 수락한다. 이때도 정산 완료, 지급, 파손 판정, 반품과 재위탁은 자동 확정하지 않는다. 기존 자료처럼 역방향 인계가 없는 의뢰는 기존 인수증 등록 호환 경로를 유지한다.

## 용어

이 기획에서 과거의 추상적인 `회복 경로`는 `비정상 운송 처리·업무 회복`으로 표현한다. 이는 실패 상태를 지우거나 운송을 자동 재시작한다는 뜻이 아니다. 수량 부족·파손·인수 보류·증빙 불충분 같은 사건을 보존하고, 정산을 안전하게 멈춘 뒤 당사자 검토와 명시적 결정으로 정상 정산, 보충 배송, 반품, 재배송 또는 종료 중 하나에 도달하는 업무 절차다.

## 수직 조각 3 — 비정상 운송 사건과 정산 보류

첫 적용 범위는 기존 기사 현장 예외 코드 `수량불일치`, `화물훼손`, `하차지부재`다. `운송문제신고Command`가 운송 원장의 기존 메모·첨부를 저장하는 같은 DB 저장 단위에서 결정적 사건 고유 식별자의 `비정상운송사건` 원장을 생성하거나 revision을 전진시킨다.

사건 원장에는 운송·의뢰 참조, 안정 유형 코드, 단계, 검토 상태, 현재 담당, 정산 보류 전 상태, 증빙 존재 여부와 신고 시각만 둔다. 신고 사유 원문, 기사 메모, 사진 객체명·URL, 주소·좌표는 복제하지 않는다. 같은 운송과 같은 유형의 재신고는 새 사건을 만들지 않는다.

열린 사건은 화주 의뢰의 정산 상태를 `비정상운송검토보류`로 바꾸고 다음 경로를 모두 막는다.

- 운송 완료 뒤 입금 요청 생성
- 기사 지급 준비 조회와 관리자 지급 승인
- 검토 중 화주의 정산 조건·현장 지급·후불 승인 변경
- 결제 승인 완료 이벤트가 도착했을 때 보류 상태 덮어쓰기

보류는 기사 과실, 환불, 보상, 반품, 재배송 또는 재위탁 확정이 아니다. 배차·운송 상태와 기사 평가·추천 점수도 변경하지 않는다. 화주 조회는 비식별 사건 요약과 보류 여부만 반환한다.

## 수직 조각 4 — 정상분 인수·영향분 보류와 운영자 결정

문제 신고는 선택적인 정상 확인 수량·영향 수량과 현장 진행 불가 여부를 받는다. 화주 의뢰의 전체 화물 수량과 수량 합을 검증하고 사건 원장에 업무 통제 상태와 보류 범위를 따로 기록한다. 신고 직후 운임 정산은 검토를 위해 잠시 보류하지만 정상 운송 상태를 중단으로 덮어쓰지 않는다.

플랫폼 운영자는 사건 목록을 조회하고 예상 revision·멱등 요청 ID·검토 근거로 `정상분 인수·영향분 보류`, `전체 운송 보류`, `운송 재개`, `사건 종료`를 결정한다. 정상 8개·파손 2개 부분 인수 결정은 운임 정산 잠금을 해제하며 파손분은 적재물 보험 적용 가능성 검토 상태로 남긴다. 보험금·귀책·배상액·재배송은 자동 확정하지 않는다.

이 구현은 기존 공개 route를 유지한다. 운영체제 인계 원장은 재사용하고, 비정상 운송 사건에는 별도 RDB 원장과 migration을 추가한다. 같은 migration은 이미 코드에 있으나 이전 migration 스냅샷에 빠져 있던 기사 기상 할증 열도 함께 동기화한다.

## 검증

- 운영체제 안정 식별자·별칭·여덟 단계 순서 검증
- 저장된 의뢰만 인계할 수 있고, 미저장 의뢰는 원장·Outbox를 만들지 않는 검증
- 동일 의뢰 인계 재시도의 결정성·멱등성 검증
- 최소 상태 사본에서 주소·전화번호·화주 사용자 식별자를 제외하는 검증
- 아직 운송 원장이 없어도 같은 화주 의뢰 재조회에서 수락된 OS 인계를 읽는 검증
- 인계만으로 배차상태가 `미시작`에서 변경되지 않는 검증
- 하차 증빙과 완료 시각이 없으면 역방향 인계가 생성되지 않는 검증
- 완료 결과 사본에서 사진 경로·주소·기사 식별자를 제외하는 검증
- 화주 인수증 등록이 역방향 인계를 수락하되 정산 완료를 자동 확정하지 않는 검증
- 완료 뒤 같은 화주 의뢰 재조회에서 역방향 인계 상태를 읽는 검증
- 세 우선 유형별 사건 생성·정산 보류와 기타 예외 비대상 검증
- 같은 운송·유형 재신고의 고유 식별자 재사용과 revision 전진 검증
- 열린 사건의 입금 요청·기사 지급 준비·관리자 지급 승인 차단 검증
- 화주 조회 DTO에 원문 메모·증빙 URL·상세 주소가 없는지 검증
- 정상 8개·파손 2개의 전체 수량 정합성, 영향분 보류와 보험 적용 가능성 검토 상태 검증
- 운영자 결정의 예상 revision 충돌과 같은 요청 ID 멱등 재시도 검증
- 부분 인수 결정 뒤 기사 운임 지급 준비가 열리고, 기존 검토대기 자료는 계속 차단되는 호환 검증

## 다음 우선순위

1. **수령인 부재 처리**: 재연락·현장 대기 기록 뒤 수령 불가 사건을 열고 운영자가 새 시간창·안전 보관·반송을 결정한다.
2. **역방향 인계 결과 결속**: 비정상 운송 사건이 열리면 완료 결과 인계를 즉시 수락하지 않고 보류 상태와 사건 고유 식별자를 연결한다. 해결 결과가 확정된 뒤 화주 OS 수락 또는 별도 종료를 기록한다.
3. **Web·모바일과 Unity 분리**: Web·모바일은 당사자의 신고·검토·결정 화면을 제공한다. Unity는 승인된 비식별 상태 사본으로 `검토 중`, `영향분 보류`, `처리 완료`를 관찰만 하며 운영 Command를 보내지 않는다.

`비정상 운송 사건 원장 → 정산 보류 판정 → 운영자 예상 revision 결정 → 영향분 보류·정산 재개 → 화주 재조회`는 구현됐다. 다음 구현 대상은 수령인 부재의 대기·재연락·운영자 선택이다. 실제 환불·보상·재배송·재위탁 실행은 계속 포함하지 않는다.

## 제외와 후속

- 실제 결제·배차·기사 제안·운송 실행 자동 활성화
- 기존 운영 자료의 일괄 소급 인계
- 핵심 조건 변경 뒤 새 revision과 기사 재동의
