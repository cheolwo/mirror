# 배차 알림 복구와 기사 겸 운영자 로컬 검증 r54

상태: Approved / ReadyToImplement. 현재 사용자 요청 `1번, 2번, 4번 보완 진행`을 구현 승인으로 사용한다. 기준 commit은 `08931c2371f29de615f4a4f133b535e5df76bf7f`이며 기존 r53 변경 19개를 보존한다.

## 목적과 책임

평소에는 본인도 일반 기사 권한과 같은 선정 기준으로 일하고, 자동 복구가 소진되거나 중요한 문제가 발생했을 때만 운영자가 개입한다. 서버가 원장과 수락을 확정하고 AI는 기존 후보·시간 판단의 보조로 유지한다. 본인 우선 배차나 자동 수락 권한을 추가하지 않는다.

## 승인 범위

1. 음식 배차 발송 주기에서 현재 유효한 추천의 누락 Outbox를 재생성한다. 같은 대기 원장·기사·라운드의 기존 유일 키를 재사용하고 추천 라운드·기한·요금을 변경하지 않는다. 같은 유효 추천 시작 재호출도 누락 알림을 복구한다. 원장 저장과 Outbox 사이 중단은 다음 worker가 복구하며 한 transaction으로 성공했다고 주장하지 않는다.
2. 일시 실패/토큰 미등록은 최대 5회, 5/10/20/30초 간격으로 같은 Outbox에서 재시도한다. 기존 15초 job 주기에 따라 실제 시도 간격은 길어질 수 있다. 발송 직전 현재 원장·기사·라운드·미수락·만료를 재확인한다. 오래된 알림은 Obsolete로 종료한다. Sending 상태와 60초 lease, DB 조건부 갱신으로 동시 발송을 제한하고 중단된 발송은 lease 뒤 복구한다. 외부 전달과 DB 저장 사이 응답 유실 때문에 정확히 한 번 전달은 보장하지 않으며 기존 앱의 재조회/중복 방어를 유지한다.
3. 일시 실패/복구 중 상태는 사람의 경보 대상에서 제외한다. 현재 유효한 추천의 복구 소진과 원장 연결 이상·픽업 후 중단은 운영 확인 대상이다. 기존 lifecycle의 주의와 운영자 예외를 구별하고 인증된 알림 상세에 문제별 다음 행동을 제공한다. 외부 메시지는 기존 개인정보 없는 일반 안내를 유지한다. 확인 버튼은 문제 해결로 취급하지 않는다.
4. 별도 모바일 화면 신설 없이 일반 기사 계정의 순차 두 건 수행, 배너/명시 수락, 전달과 수령 분리, 이전 알림 방어, HTTP host 재생성 후 정본 재조회를 로컬 통합 시험한다. 운행 시작을 기존 경로로 검증 가능한지 확인하고 불가능한 구간은 한계로 기록한다. 같은 SQLite/시험 store를 유지한 host 재생성과 전체 프로세스/Redis/단말 재시작은 구분한다.

## 불변 경계

화물 발송 계약/기존 동작, 역할 권한, 요금, 배차 점수와 수집 정책은 유지한다. 새 DB column·migration·API contract·UI 화면은 추가하지 않는다. 기존 운영/외부 전송 OFF를 켜지 않는다. 실제 FCM·Gmail·휴대폰·Azure·Unity·모델 추론·학습·commit/push는 포함하지 않는다. 정책 간격 조정 승인/이력/rollback(앞선 3번)은 별도 후속이다.

## 검증

SQLite 저장 후 새 service scope에서 누락 복구, 일시 실패와 토큰 복구, 지연/최대 횟수, 만료/수락/재배정/성공 무재발송, Sending lease와 병행 worker를 검증한다. 기존 알림 결손 재현 시험은 현재 회귀 기대값으로 바꾸되 r49의 과거 실패 관측 문서는 보존한다. 운영 알림은 복구 중 억제·소진 활성·중대 예외·해결 재조회·다음 행동을 검증한다. 역할 앱 PageModel/실제 HTTP API/SQLite 통합을 실행하고 Fast 후 Task 결과 및 실행 한계를 별도 변경 기록에 남긴다.
