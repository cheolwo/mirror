# 화주 모바일 맥락별 운송 의뢰 작성 r72

- 기획 ID: `PLAN-OPERATIONS-DISPATCH-CORE`, 판본 `mobile-context-authoring.r72`, 2026-10-19.
- 상태: `ApprovedInCurrentThread / CompletedLocalValidation / OperationalDisabled`.
- 승인: 사용자는 USB 디버깅을 허용했고, 모바일 입력을 맥락별 페이지로 나누고 이전에 보류된 실기기 검증을 진행하도록 요청했다. 같은 스레드에서 아래 좁은 범위의 구현·시험 APK 갱신·설치·합성 자료 검증을 승인한 것으로 기록한다.

## 페이지 책임

같은 화주와 같은 의뢰 초안을 유지하면서 현재 질문에 필요한 정보만 입력한다. 최종 확인 이전 단계 이동은 서버 의뢰 등록·기사 추천·계약·결제의 완료가 아니다. 기존 원장·권한·자격 및 등록 준비 관문은 바꾸지 않는다.

| 순서 | 모바일 질문 | 입력 문맥 | 경로 |
|---|---|---|---|
| 1 | 무엇을 보내나요? | 품목·수량·적재/온도·설명 | `/shipper/request/cargo` |
| 2 | 얼마나 크고 무거운가요? | 포장 포함 중량·길이/너비/높이·선택 부피/팔레트 | `/shipper/request/package` |
| 3 | 어디서 받나요? | 상차 도로명/상세주소·연락 대상 | `/shipper/request/pickup` |
| 4 | 어디로 보내나요? | 하차 도로명/상세주소·연락 대상 | `/shipper/request/dropoff` |
| 5 | 언제 운송하나요? | 상차 필수 시간창·하차 선택 시간창·요청 | `/shipper/request/schedule` |
| 6 | 어떤 차량을 이용하나요? | 기존 차량 선택·운송방식·서비스 수준 | `/shipper/request/vehicle` |
| 7 | 비용은 어떻게 정하나요? | 기존 운임·지급 조건, 부가 절차는 선택 정보 | `/shipper/request/procedure` |
| 8 | 이 내용으로 접수할까요? | 전체 검토·동의·명시적 등록·미확정 결과 조회 | `/shipper/request/review` |

기존 상위 4단계 enum 값·URL·PC 통합 입력·의뢰 payload·동의·중복 보호를 유지한다. 모바일 전용 명시적 순서와 부분 화면 표시만 추가한다. 기존 `/transport`는 종합 입력 호환 경로다. 주소·연락처는 URL이나 공개 예시 자료에 추가하지 않는다.

## 입력 수명과 실패

- 이전/다음은 같은 작성 State를 공유한다. 단계의 기존 필수항목만 확인하며 새 전화·가격·자격 요건을 임의 추가하지 않는다.
- 이전 단계 이동을 막지 않고 입력을 유지한다. 최종 접수의 현재 서버 검증과 결과 불명확 시 동일 원문·요청 ID 조회 우선을 유지한다.
- 일반 초안은 현재 앱 세션 안에서 유지된다. 재시작 후 복원이나 자동 저장 완료라고 표시하지 않는다.
- 좁은 폭은 현재 단계·짧은 진행 표시·이전/다음·보완 이유를 표시하고 PC는 기존 큰 화면 조립을 유지한다.
- 모바일 단계가 처음 표시되거나 바뀔 때 제목을 포커스해 이전 화면의 중첩 스크롤이 다음 질문을 가리지 않게 한다. 같은 단계 입력 렌더와 PC 통합 입력에는 이 전환 포커스를 적용하지 않는다.

## 실기기에서 확인한 후속 보완

- 여러 입력 경로가 같은 페이지 인스턴스를 재사용할 때 URL만 바뀌고 이전 질문이 남는 현상을 199에서 확인했다. 모바일/Web 호스트는 현재 지원 입력 경로의 변경을 구독해 다시 표시하고, 페이지를 떠나면 구독을 해제한다. 공통 화면의 제목 포커스와 초안은 유지한다.
- 사용자가 확인한 빈 벽·책상 촬영 범위에서 상차·하차 사진까지 검증한다. 통합앱 화물 화면은 기존 사진 선택을 보존하고 이미 등록된 모바일 촬영 어댑터를 재사용한다. 촬영만으로 업로드·상태 완료를 실행하지 않으며 취소·권한/형식/크기 오류·계정/업무 변경 후의 늦은 사진은 완료로 처리하지 않는다.
- 198·199와 실패 증거를 보존한 별도 200 APK를 제작한다. 최종 실기기 증거는 같은 합성 의뢰의 입력·접수·추천·수락·사진·서버 완료 확인을 연결하며, 후불 운영 시험에 필요한 별도 API 설정은 화면 접수와 구분한다.

## 현재 검증 단계

- 최종 Fast-r8 **330개 통과·실패/생략 0개**, Task-r3 소비 솔루션 빌드와 **12,884개 통과·실패 0개·환경 의존 16개 생략**을 확인했다. 공통 브라우저의 일반 검사 **6/6**·중첩 스크롤 **9/9**·**42회 전환·50PNG·대표 11장**과 실제 APK200 휴대폰의 8단계·초안 유지·17캡처를 구분해 보존했다.
- APK **0.1.200/code200** 제작·데이터 삭제 없는 교체 설치·설치 바이트 대조를 완료했다. 첫 의뢰의 부피 누락에 따른 후보 차단과 승인 후 수정 차단을 보존했다. 필요한 부피를 실제 입력한 새 의뢰에서는 접수→별도 API 후불 시험 준비→실제 로컬 AI 추천→휴대폰 수락→상차/하차 별도 촬영·저장→운송 정본 인수완료·사진 무결성·Mongo 완료 수렴을 확인했다. 후불 준비는 전부 화면에서 처리한 것으로 합치지 않는다.
- 198/199의 실패와 이전 시험은 그대로 보존한다. 지도·GPS·외부 FCM/소리·실제 수납/송금과 ready 503 문제는 별도이며, 실제 기기의 촬영 취소·권한 거부는 재현하지 않았다. 현금성 정산 오류 위치·선택 부피와 적재 검증 간 사전 안내·요청사항 조회 매퍼 차이도 후속 보완으로 기록한다.
- 상세 결과·대표 화면·입력/검사 해시의 정본은 [r72 변경 기록](../../../../Changes/2026-10-19-mobile-context-authoring-r72.md)이며 운영은 비활성이다. 이 검증 갱신으로 승인 범위나 작업 명세를 확대하지 않는다.

## 작업 소유와 검증

- core 담당: 새 모바일 단계 계약/route/기존 Context overload와 VM의 순수 단계 검증·해당 시험.
- UI 담당: 공통 Cargo/Transport/Procedure/Review Screen의 선택 표시와 Frame/모바일 navigation, 기존 통합 화면의 작은 화면 진입·해당 render 시험.
- root: 호스트 페이지 조립·책임 문서·승인 상태/결과, 전체 소비 빌드·현재 validation router·시험 APK·USB 설치/실행·대표 화면.
- 조사 담당: 기존 단말·포장·격리 서버 준비 읽기 전용 확인. 자격 검토의 실제 자료·운영 활성화를 변경하지 않는다.
- 격리 Simulation 자료만 사용한다. 사용자 개발/운영 DB 마이그레이션, 실제 주문·신고·수납/송금·FCM·공개 배포·Unity·영상·commit/push는 실행하지 않는다. 기기 시험은 내 앱에 한정하고 다른 앱의 거래/알림을 조작하지 않는다.
