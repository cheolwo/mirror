# 주문부터 기사 수행까지의 로컬 배차 통합 시나리오 r49

- 기획: `PLAN-OPERATIONS-DISPATCH-CORE`, 판본 `dispatch-core.r49`.
- 상태: `Approved / ReadyToDispatch / AcceptedInCurrentThread / IsolatedIntegrationAuthorized / ExternalEffectsExcluded`.
- 사용자 요청: 주문 발생부터 Ollama의 배달권·기사 선택, 모바일 배차 배너 알림, 기사 수락과 수행까지 여러 상황에서 이어서 검증한다.
- 승인 범위: 현재 사용자 요청에 따라 개발 통합 담당이 아래의 테스트·도구·문서 경로와 격리 검증, 별도 실제 추론 예산을 현재 스레드에서 수용했다. 제품 앱·서버 소스와 설정은 기본 변경 0개이며 외부 운영·알림 발송은 포함하지 않는다.
- 기준: [r48 승인 설계](candidate-application.implementation.r48.md), [r48 구현·실행 결과](../../../../Changes/2026-10-11-local-dispatch-candidate-application-r48.md), [작업 명세](workflow-scenarios.r49.work-order.json).

## r48에서 확인한 것과 이번에 잇는 것

r48은 실제 음식 후보 정책과 Ollama 선택을 기존 추천 저장에 연결하고, 합성 기사·주문의 격리 SQLite에서 모델 1회와 추천·감사·활동 사건의 저장/재조회를 확인했다. 모델은 기존 기준 후보와 같은 기사를 선택했다. 실제 주문 접수, 앱 배너, 기사 수락·수행이나 실제 FCM 수신을 이 결과에 포함하지 않았다. 4,000원은 시험 고정 요금의 동결 결과였고 실제 경로·요금 엔진 계산의 검증이 아니었다.

이번 최소 목표는 **한 시나리오의 같은 주문과 배차 식별값**으로 접수→음식점 확인→배차 후보→추천 원장→알림 힌트→모바일 정본 재조회→기사 수락→음식점 준비→기사 픽업·전달을 연결하는 것이다. 상태를 시험 DB에 직접 덮어써 업무 절차를 통과한 것으로 만들지 않는다. 초기 합성 음식점·메뉴·기사·운행 자료의 준비와 업무 상태 전이는 구분한다.

음식점 확인과 새 조리 시작은 다르다. 현재 주문 저장소는 음식점 수락 뒤 배차대기를 연결하고, 새 조리는 유효한 기사 배정 뒤 시작한다. 기사의 전달 완료와 주문자의 수령 확인도 별개다. 이미 준비된 음식의 예외는 기존 정책으로만 처리한다. 이번 시험을 위해 순서를 바꾸거나 새로운 주문·수락 원장을 만들지 않는다.

## 최소 검증 구성과 증거 수준

기존 실제 UseCase·후보 정책·추천/수행 서비스를 재사용하는 격리 통합 fixture를 우선 구성한다. 외부 Mongo/Redis/경로/요금/푸시 경계는 필요 시 시험용 포트로 분리하고 각 사례에 무엇을 대체했는지 남긴다. 실제 업무 원장까지 통과했는지 확인할 수 없는 포트는 완료로 보고하지 않는다. 새로운 실행 모드를 만들지 않고 기존 Simulation/Operational 의미와 시험 데이터 격리를 보존한다.

| 증거 | 목표 또는 확인 방법 | 구분할 한계 |
| --- | --- | --- |
| 실제 주문·원장 | 실제 접수·상태 변경 서비스와 격리 SQLite 저장/재조회 | 초기 자료 직접 준비와 실제 업무 전이 구분, 운영 MySQL/Mongo 미검증 |
| API action | 기존 Controller action의 요청·응답·업무 서비스 연결 | 직접 action 호출은 실제 HTTP route·middleware 인증 검증이 아님 |
| 로컬 HTTP | 격리 loopback HTTP에서 실제 모바일 API client와 기존 음식 Controller 연결 | 시험 인증과 제품 JWT/미들웨어 인증은 구분, API action만 호출한 구간을 HTTP로 인증하지 않음 |
| Ollama | 기존 루프백·고정 모델·제한 토큰의 실제 요청/응답 | 모델 적용·기존 엔진 복귀·엔진과 같은 선택을 별도 기록 |
| 알림 Outbox·수신 코드 | 실제 Outbox 생성과 시험용 발송 포트, 그 payload를 실제 수신 코드에 입력 | 시험 포트 성공·수신 코드 입력은 실제 FCM 전송/기기 수신이 아님 |
| 모바일 PageModel | 실제 모델·API adapter·서버 정본으로 배너 상태와 수락/수행 명령 검증 | ViewModel 상태는 화면 픽셀·Android/MAUI 실행 증거가 아님 |
| 화면 렌더 | 필요하면 승인 범위 안의 기존 컴포넌트 렌더로 별도 확인 | 렌더·캡처가 없으면 화면 미검증, 새 UI 제작을 기본 범위로 추가하지 않음 |
| 실제 휴대폰·FCM | 별도 장치/인증·설정·발송 승인에서 확인 | 이번 초안의 자동 실행·완료 기준에 포함하지 않음 |

서버의 실제 요청과 모바일 API adapter는 신규 시험 fixture의 Kestrel loopback HTTP와 임시 포트로 연결한다. fixture 전용 Bearer token으로 인증하고 기존 음식 주문·기사 업무·수신 상태·알림 설정 Controller를 노출한다. 이 시험 인증은 실제 로그인·제품 JWT 인증의 증거가 아니다. 단순히 시험용 API가 미리 만든 성공 DTO를 반환하는 구성만으로 주문→알림→수행 통합을 인증하지 않는다. 실제 UI의 가시성 조건과 PageModel 상태 연결을 정적으로 대조하며, 실제 렌더를 수행했을 때만 시각 검증을 추가한다. OS 알림·GPS·지도·FCM은 시험 포트이며 실제 장치 기능으로 보고하지 않는다.

기존 추천 저장과 알림 Outbox의 분리, `Failed` 알림의 자동 복구 공백은 이번에 제품 코드를 수정하지 않는다. 실제 현행 결과를 반례로 기록하고 추천 저장·알림 준비/실패·모바일 정본 조회가 서로 다른 상태임을 보여 준다. 반례를 통과로 바꾸기 위해 도구가 누락된 자동 복구를 대신 실행하지 않는다.

## 시나리오 우선순위

첫 정상 사례를 끝까지 연결한 뒤 같은 fixture에서 예외를 추가한다. 수십 개의 결정적인 모의 사례로 오류·동시성·복구를 넓히고 실제 모델 호출은 작은 주요 사례에만 사용한다. 아래는 사례군 제안이며 구현 전 통과 개수로 기록하지 않는다.

| 사례군 | 주요 입력/상황 | 확인할 업무 결과 |
| --- | --- | --- |
| 정상·공간 탐색 | 같은 권역·인접권·제한 확장, 유효 후보 없음 | 실제 탐색 단계·허용 집합, 선정 또는 대기 결과 보존 |
| 기사 적격·참여 | 수신 OFF·GPS 만료·수행 상한·거절, 동급 장기 대기 | 부적격 제외, 기존 수요·여력·픽업 관문 안의 기회 고려 |
| 수요 자료 | 현재/만료·여력 충분/부족·피크 전환 가정 | 관측 품질·현재 정책·시험 가정 구분, 시간대만으로 우선권 창작 금지 |
| 모델 예외 | 시간 초과·연결 실패·무효 JSON·모르는 토큰·허용 범위 밖 선택 | 현재 엔진 복귀, 자유 문장 저장/추가 재시도 없음 |
| 응답 중 변경 | 후보 수신 OFF·큐 상태 변경·기존 수락·유효기간 종료 | 최신 후보/원장 재검사, 중복 추천·오래된 선택 저장 금지 |
| 알림·계정 | 중복 알림·다른 계정·화물 앱 payload·만료·푸시 미구성 | 개인정보 없는 힌트, 잘못된 배너/자동 실행 없음, 정본 조회 유지 |
| 수락·수행 | 만료/타인 제안, 배정 전 조리·준비 전 픽업·전달 선후관계 | 서버 가능 행동과 단계별 필요한 카드, 권한 밖 상태 전이 차단 |
| 업무 지속·중복 | 접수/수락 응답 유실·같은 요청 재확인·중복 전달·앱 계정 전환 | 정본 조회와 멱등 처리, 사건/원장 중복 없음, 이전 계정 자료 제거 |

최소 정상 완주에는 기사 수락→가게 도착→음식점 조리·준비→픽업→전달과 주문자 수령 확인의 분리를 포함한다. 사건의 최종 상태뿐 아니라 각 단계에서 가능한 다음 행동, 담당자, 배너 제거/유지와 정본 재조회 결과를 확인한다. 실제 돈 지급과 사진·위치 장치 기능은 시험 포트와 별도 결과로 기록한다.

## 별도 실제 모델 호출 예산

실제 모델 주요 사례는 `same-region`, `adjacent-region`, `demand-capacity` 3개다. 같은 권역의 동급 후보·장기 대기, 같은 권역 후보 부재에서 인접권 후보 비교, 현재 수요·가용 여력/수행 제약 안의 복수 후보 비교를 각각 다룬다. 각 fixture에는 적격 후보 2명과 제외 후보를 두며 호출 전에 같은 fixture의 모의 실행과 실제 적격 후보를 확인한다. 후보가 한 명뿐인 경우 모델을 호출한 사례로 집계하지 않는다. 구현에서 주요 사례가 달라지면 실행 전에 작업 명세에 정확한 대상과 변경 이유를 기록한다.

실패·중단을 포함한 r49 누적 시작 시도 상한은 **4회**다. 호출 전에 별도 비공개 예산을 예약하고 요청/응답·입력·소스 해시를 연결한다. 재실행·실패 복구로 예산을 초기화하지 않는다. 실제 모델을 부적절한 응답으로 유도하기 위한 반복 호출 대신 그런 예외는 HTTP 모의 응답으로 검증한다. 남는 예산을 채우기 위한 호출도 하지 않는다.

기존 r48 누적 1/2와 출력·r47 4회·r46 36회 이력은 불변 보존한다. r48의 남은 슬롯을 r49에 재사용하거나 이전 실패를 삭제하지 않는다. 모델 다운로드·가중치 학습·GPU 변경·외부 대체 모델·새 프로세스 자동 시작은 포함하지 않는다.

서버 fixture의 `CreateAsync(scenarioId, HttpClient, databasePath)`와 `BaseAddress/DriverId/OfferId/AccessToken`, `RecommendAsync/DispatchPendingNotificationsAsync/MarkPreparationReadyAsync/SetDriverLocationAsync/ConfirmReceiptAsync/ReadSnapshotAsync/PushMessages`를 통합 접점으로 둔다. namespace는 `Ssalddel.Tests.Services.Dispatch.AI`다. 실제 주문 등록→음식점 수락→요청 Outbox→배차 큐→Ollama 정책→추천 저장→알림 Outbox→기사 수행→주문자 수령을 같은 식별값으로 연결한다. 마지막 `IFcmPushService`만 발송 기록용 포트로 대체하며 외부 전송은 없다.

필수 모바일 조회는 현재 운행 상태·현재 업무·수신 의사·알림 설정이며 수행은 기존 음식 수락/도착/픽업/전달 Controller로 연결한다. `Tests.csproj`의 기존 FDriver 링크를 재사용하고 제품 앱 소스를 수정하지 않는다. 외부 지리정보·Mongo·실제 Firebase 호출은 없고 지도/GPS 수명은 모바일 시험에서 비활성화한다.

위 범위를 승인 설계·정확한 해시·명세로 동결한다. 새 제품 결손 수정을 발견하면 이번 기본 경계에서 제외하고 개발 통합 담당에게 반환한다. 최종 검증에는 집중 시험·관련 소비 앱 빌드·범위 Fast/Task·시나리오별 단계 근거를 반환하며, 실제 DB/HTTP/모바일 PageModel/렌더/기기 수신을 각각 보고한다. 설계 동결은 실제 모델 성공·모든 시나리오 통과·외부 운영의 인증이 아니다.

## 제외 범위

제품 앱/서버 소스·공유/로컬 설정 변경, 실제 고객·외부 운영 DB·FCM/이메일/Slack 실발송·Azure·배포·APK 설치·기기 조작·지도/요금 유료 API·화물·Unity·입금·정책 수치 변경·모델 학습·commit/push는 범위에서 제외한다. 발견한 결손은 원인을 먼저 기록하고, 관련 없는 기능 추가나 기존 기획 일괄 수정으로 확대하지 않는다.
