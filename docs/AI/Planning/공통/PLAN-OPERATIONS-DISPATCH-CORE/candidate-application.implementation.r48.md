# 로컬 서버의 음식 배차에 Ollama 후보 선택 연결 r48

- 기획: `PLAN-OPERATIONS-DISPATCH-CORE`, 판본 `dispatch-core.r48`.
- 승인 근거: 사용자가 사후 검토를 넘어 AI를 실제 배차 수행 경로에 연결하도록 요청했다. 현재 스레드에서는 아래 서버 연결과 격리된 로컬 검증 범위를 수용한다. Azure 배포나 외부 운영 자료 변경·알림 발송을 승인한 것으로 확대하지 않는다.
- 설계 상태: `Approved / AcceptedInCurrentThread / LocalApplicationAuthorized / ExternalOperationalEffectsExcluded`.
- 앞선 근거: [배달권 후보 검토 r47](candidate-advisory.implementation.r47.md), [r47 품질 한계와 원응답 재검증](../../../../Changes/2026-10-11-local-dispatch-candidate-advisory-r47.md), [사용자 문답 방향](배차-사례-문답검토절차.md).
- 현재 스레드 인계: [작업 명세](candidate-application.r48.work-order.json). 실제 구현·시험 결과는 별도 r48 변경 기록으로 반환한다.

## 연결할 업무 경로

기존 서버 DI에서 음식 후보 정책에 `IFoodDispatchCandidateAI`를 주입한다. 인터페이스는 활성 여부와 `SelectAsync(trace, cancellationToken)`을 제공하고 결과 `FoodDispatchAISelection`은 기사 ID와 고정 상태 코드를 반환한다. AI가 영속 상태를 직접 확정하지 않는다.

음식 후보 정책이 현재 관문을 통과한 후보를 계산한 뒤 새 typed Ollama 서비스가 제한된 후보를 비교한다. 응답 후 실제 후보와 현재 배차대기 원장을 다시 확인하고, 유효하면 기존 후보 선정 결과를 통해 추천·요금 동결·수신 의사·기사 수락 원장 경로로 진행한다. 새로운 배차 API·원장·수락 경로를 만들지 않는다. 추천 대상 선정과 기사 수락은 서로 다른 상태다.

```text
기존 서버 후보 선정
  → 현재 허용 후보·기준 후보 산출
  → 선택 기능이 켜져 있을 때 Ollama 제한 호출
  → 응답 뒤 후보·배차대기 현재 상태 재확인
  → 기존 추천 서비스의 요금·수신·상태 검사와 저장
  → 기존 기사 제안·수락 흐름
```

기존 `FoodDeliveryDispatchAIReviewService`의 관리자 사례 저장·샘플 자료는 이번 실행 입력이나 확정 권한으로 재사용하지 않는다. 음식 배달 전용 연결이며 화물·생활 배송과 원장을 합치지 않는다.

## 모델에 허용하는 선택

모델 입력은 현재 검토 결과의 `CandidateAllowed`이면서 최종 허용 ID 집합에 포함된 후보로 제한한다. 기준 후보와 같은 픽업 단계만 허용하고, 수요 자료가 최신이면 수요 우선순위가 기준 후보보다 낮아지는 선택을 허용하지 않는다. 후보 제한 수를 적용하더라도 기준 후보는 비교에 남겨 둔다. 현재 적격·수신 의사·GPS·동시 수행·접근 반경·거절·픽업 관문을 AI가 우회하지 못한다.

실제 기사 ID·주문 ID·상세 주소는 모델에 보내지 않는다. 호출별로 `C1` 같은 짧은 임시 토큰을 부여하고 거리·픽업 단계·대기·참여 우선순위 등 선택에 필요한 최소 근거만 보낸다. 토큰과 실제 기사 ID의 대응은 서버 내부에서만 사용하며 모델이 새로운 ID·후보·수치·자격을 만들도록 하지 않는다. 주소·정확한 고객 위치·연락처·주문 원문은 입력과 진단 출력에 넣지 않는다.

응답 JSON의 허용 필드·토큰·현재 후보 연결을 검증한다. 선택 결과는 고정 `StatusCode`를 기존 추천 사유에 연결해 현재 감사 경로에 남긴다. 모델의 자유 문장을 감사 근거나 사용자 안내로 직접 저장하지 않는다.

## 지연·오류·변경 시 업무 지속

새 Options의 기본값은 OFF다. 기존 기능이 꺼져 있으면 모델 호출 없이 현행 후보 정책을 유지한다. 활성 예시도 기본 OFF로 보존하며 이번 PC의 Git 제외 `appsettings.Local.json`에서만 명시적으로 ON을 준비할 수 있다. 공유 운영 설정이나 Azure 설정을 켜지 않는다.

- endpoint는 명시적 포트를 가진 `http` 루프백 주소만 허용한다. 외부 호스트·proxy·redirect·클라우드 대체·도구 호출·외부 프로세스 자동 시작을 허용하지 않는다.
- 기본 timeout은 10초, 허용 범위는 1~90초다. 후보 수 기본값은 12명, 허용 범위는 2~30명이다. 값은 시작 시 검증하고 호출별 취소를 전달한다.
- 잘못된 JSON·알 수 없는 토큰·부적격·timeout·연결 실패에는 현재 엔진 기준 후보를 사용한다. 모델 실패를 업무 저장 성공이나 샘플 결과로 숨기지 않고 고정 상태 코드로 구분한다.
- 모델 응답 후 후보가 바뀌었거나 현재 큐가 더 이상 추천 가능하지 않으면 오래된 선택을 적용하지 않는다. 최신 후보·원장을 다시 검사하고 새 기준 후보 또는 기존 준비 안 됨 결과로 돌아간다. 이미 수락한 업무를 빼앗거나 제안을 중복 저장하지 않는다.
- 모델 호출의 자동 재시도·새 프로세스 실행으로 지연을 늘리지 않는다. 호출 이후 검사에서 변경이 발견돼도 같은 업무 요청에서 모델을 반복 호출하지 않는다.

기존 서버가 요금 계산·현재 상태·동시성 검증과 영속 저장의 권위다. 실제 알림의 종류·수신자·발송 경로를 늘리지 않는다. 모델 실패로 기존 경로가 계속되는 것과 모델이 실제로 후보를 선택해 적용된 것은 별도로 기록한다.

## 로컬 검증과 추론 예산

격리 SQLite DB와 합성 기사·주문, 외부 알림을 억제하는 시험용 경계에서 실제 추천 서비스를 호출한다. 모델이 선택한 허용 후보가 기존 추천 저장에 반영되는 정상 경로와, 오류·지연·후보/큐 변경 때 현행 엔진으로 복귀하는 경로를 각각 검증한다. 실제 고객·운영 DB·외부 알림·입금은 변경하지 않는다. 로컬 통합 시험을 실운영 기사의 수락이나 휴대폰 수신으로 표현하지 않는다.

실제 Docker 모델 검증은 우선 1회다. 추가 확인이 필요한 경우 실패·중단을 포함해 r48 누적 추론 요청 시작 최대 2회까지 허용한다. 호출 전에 별도 비공개 예산을 예약하고 재실행도 같은 상한을 따른다. r47의 소진된 4회 예산이나 r46의 36회 기록을 재사용·초기화하지 않는다. 모델·GPU·가중치·다운로드는 변경하지 않는다.

r47의 도구·규칙·근거·원응답·최종 0개 통과/4개 복귀 기록은 보존한다. 공유 음식 정책 소스가 r48에서 변경되면 r47의 과거 근거가 현재 검사에서 만료되는 것이 정상이다. 과거 해시를 새 소스로 덮어써 소급 통과시키지 않는다. r47 품질 한계가 해소됐다거나 모델을 학습시켰다고 보고하지 않는다.

집중 시험·서버 빌드·Fast·Task, 격리 추천 저장, 실제 모델 호출과 유효 선택/복귀를 각각 기록한다. 실제 모델이 timeout 또는 무효 응답으로 복귀하면 그 사실을 그대로 반환하며 AI 적용 성공으로 바꾸지 않는다. 구현 완료와 로컬 설정 활성화·호스트 실행·운영 배포는 서로 다른 결과다.

## 제외 범위

새 API·공개 contract·DB schema·UI·APK·Unity·화물/생활 배송·외부 운영 DB·알림 수신자 확대·Azure·배포·commit/push는 이번 범위에 포함하지 않는다. 모델 가중치 학습·새 모델 다운로드·GPU 변경·컨테이너 자동 시작도 수행하지 않는다. 전체 배차의 최적성·공정성·수입·운영 안정성은 이 연결의 자동 인증 대상이 아니다.
