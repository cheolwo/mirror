## 목표와 책임

상하차 완료, 일반 입고 신청·완료에서 앱을 다시 열어도 이전 요청 결과부터 확인한다. 기존 전문 원장과 GET이 정본이며 단말의 복구 기록은 미확정 요청의 관측만 소유한다. 로컬 GUID를 서버 멱등 키로 표시하지 않는다.

1. 명령 전 계정·서버·업무 종류·대상 ID·로컬 관측 ID를 보호 저장하고 다시 읽어 확인한다. 실패하면 POST를 보내지 않는다.
2. 새 ViewModel에서 동일 계정·서버의 관측을 복원하고 GET을 먼저 수행한다. 다른 계정·세션·대상의 늦은 결과를 반영하지 않는다.
3. 정본 완료 확인 또는 명시적인 같은 OS·단계의 `NotApplied`가 있을 때만 조건부로 기록을 지운다. 삭제 후 재조회로 삭제 성공을 확인한다. GET 미완료·조회 실패·시간 경과·메모 손상은 미적용의 증거가 아니다.
4. 일반 입고 신청의 응답 ID를 잃으면 목록 수동 확인까지 제공한다. 기존 서버에 접수 결과 조회 계약이 없으므로 후보 자동 확정·재등록·강제 초기화를 제공하지 않는다.

## 화면 책임 카드

- 기사 상차·하차: 현재 운송의 완료 여부 확인과 해당 단계의 다음 행동만 제공한다. 복구 확인 전에는 완료 버튼을 잠그고 기존 사진·확인 항목을 보존한다. 사진 캐시 만료는 미확정 요청 해제를 뜻하지 않는다.
- 입고 신청: 접수된 번호가 있으면 같은 신청을 조회한다. 접수번호를 받지 못했다면 “신청 결과 확인 필요”와 목록 확인을 제공하고 새로운 신청으로 우회하지 못하게 한다.
- 입고 완료: 같은 입고 ID의 완료 상태를 재조회한다. 완료 응답 후 조회 실패는 저장 성공과 조회 실패를 구분한다. 다른 입고 선택은 이전 미확정 관측을 지우지 않는다.

## 저장·호환 경계

`IWorkflowRecoveryStore`와 기존 단말 보호 저장소를 재사용한다. 새 범위만 정규화된 API 주소의 해시로 구분하며 기존 복구 키·기록은 이동하거나 초기화하지 않는다. 토큰·주소·상품명·사진·서명·전체 초안은 일반 복구 자료에 저장하지 않는다. 기존 72시간 뒤 payload 제거 정책 이후에도 ID·target을 보존해 미확정 차단을 유지한다. 계정 변경·보호키 손상·읽기/쓰기/삭제 실패를 빈 기록으로 바꾸지 않는다.

MAUI 보호 저장소의 재실행 보존과 웹의 메모리 저장소를 구별한다. 웹 프로세스 재시작 영속성을 이번 범위에서 약속하지 않는다. 서버 상태 전이·사진 영수증·권한·원장·worker OFF·API route와 기능 기본값은 유지한다. 자동 POST 재전송·새 멱등 엔진·운영 활성화·commit/push는 하지 않는다.

## 완료와 후속

[구현·업무 트리·검증·화면](../../../../Changes/2026-10-21-durable-workflow-recovery-r3.md)을 따른다. 최종 Fast212·전체14,328개 통과/환경16개 미실행, 실제 공통 컴포넌트 가상5사례·10렌더를 확인했다. 파일 IO를 위임한 실제 공통 저장소의 독립 프로세스3회 왕복도 통과했다. 단말 SecureStorage의 강제 종료 후 복원·새 APK 설치·외부 서버·운영 검증을 대신하지 않는다. 일반 입고 접수번호 전 유실의 요청별 조회 계약, 구판 실패 사유 정형화와 다른 OS 적용은 후속이다.

## 검증·인계

새 VM 및 새 보호 저장소 인스턴스에서 동일 데이터 복원, 쓰기 전 차단, 미확정 GET 반복 시 POST 0, 완료 확인 후 해제, 계정·서버·운송 단계 격리, 만료·손상·삭제 실패를 시험한다. 동일 코드의 동시 제출·늦은 응답도 검토한다. 영향 client 빌드와 scoped Fast/Task를 실행한다. 문서에 로컬 시험·실제 단말 재실행·APK 설치·외부 서버 검증을 분리해 기록한다.
