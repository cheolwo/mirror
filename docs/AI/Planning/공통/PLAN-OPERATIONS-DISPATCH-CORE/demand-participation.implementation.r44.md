## 판단과 업무 효과

`음식배달수요참여Policy`는 15분의 최근 신규 주문과 현재 미배정 주문을 읽어 다음 60분의 참여 여력을 계산한다. 기본 처리량은 기사당 시간당 3.5건이며 측정된 생산성이나 보장 소득이 아닌 조정 가능한 초기 가정이다. 기존 기사가 남은 업무를 마친 뒤 처리할 수 있는 여력을 먼저 반영한다. 관측률과 선택적인 미래 수요 참고값은 더하지 않고 큰 값을 사용한다.

수락한 업무·최근 수락 이력·유효 보유 제안이 있는 기존 활동 기사는 목표 인원을 넘었다는 이유로 제외하지 않는다. 신규 기사는 현재 근무 시작과 실제 수락·완료 시각으로 계산한 대기 순서를 사용한다. GPS 갱신이나 추천 표시만으로 대기 시작을 초기화하지 않는다. 최근 배차 수가 적고 실제 대기가 긴 기사를 먼저 비교한다.

장기 대기 기본 30분에는 한 명의 추가 기회를 허용하며, 주문이 기본 10분 이상 지연되면 추가 한 명을 허용한다. 이는 영구적인 운행 승격이나 배타 예약이 아니라 매 추천 시점의 권고다. 이미 수락한 업무와 유효 제안을 취소하거나 기사 수신 의사를 OFF로 바꾸지 않는다.

`음식배달배차업무정책`에 연결하여 조회 수 제한 **전에** 참여 우선순위를 적용한다. 음식 앱·현재 음식 근무·수신 ON·GPS 신선도·동시 수행 여력·접근 반경·거절 이력·픽업 시간 조건을 유지한다. 평가한 후보 중 가장 적절한 픽업 단계 안에서 참여 우선권을 적용하며, 그 단계에 참여 허용 기사가 없으면 같은 단계의 기존 적격 후보를 재탐색하고 추천 사유에 적시성 예외를 남긴다. 명시적인 적격 미충족 기사는 이 예외로 살리지 않는다. 픽업 지연 단계는 참여 우선권보다 먼저 비교한다.

특정 기사로 직접 추천을 시작하는 경로도 기능 활성 시 같은 후보 선정 결과를 확인한다. 자동 경로의 이미 계산된 후보와 유효한 기존 제안은 다시 취소·재선정하지 않는다. 실제 수락 시점의 권한·동시 수행 상한·원장 동시성 검사는 기존 UseCase가 소유한다.

## 원장과 관측 경계

서비스는 SQL `운송원장`, 현재 `기사근무`, `음식배달시도`를 조회하고 기존 음식 권역 인덱스와 기사 위치·수신 투영을 연결한다. 공간 인덱스의 갱신 시각을 수요 관측 시각으로 사용하지 않는다. 근무 ID와 기사·음식 실행 유형을 일치시키며, 같은 주문의 최신 시도와 플랫폼 책임 중단을 대조한다. 수신 조회가 기존 정본에서 캐시를 복구할 수 있지만 업무·의사 원장을 변경하지 않는다.

미확인 지역·현재 큐 누락·DB 실패·기사/주문/시도 조회 상한 초과는 `Unknown`, 관측 만료는 `Stale`이다. 이를 주문 0건으로 대체하지 않으며 기존 후보 선정 규칙으로 복귀한다. SQL 조회 기본 상한은 5,000건, 기사 500명이다. 큰 운영 규모의 지역 필터·집계 최적화는 후속이며 불완전한 조회를 완전한 수요로 사용하지 않는다.

권역과 인접 권역이 겹칠 수 있으며 여러 서버가 동시에 신규 기사를 추천할 수 있다. **권역 전체의 원자적 정원 통제·영속 대기열·수입 보장은 구현하지 않았다.** 기존 단일 운송 행의 RowVersion과 수락 관문을 권역 정원 잠금으로 설명하지 않는다.

## 설정과 복귀

`FoodDemandParticipation:Enabled` 기본값은 `false`다. 활성 여부는 서버 구성에서만 바꾸며 이번 작업에서 운영 설정은 켜지 않았다. 옵션은 시작 시 검증한다.

```json
{
  "FoodDemandParticipation": {
    "Enabled": false,
    "관측시간창분": 15,
    "수행관측시간창분": 60,
    "최대조회건수": 5000,
    "최대권역기사수": 500,
    "주문지연주의분": 10,
    "정책": {
      "시간당목표처리건수": 3.5,
      "계획시간창분": 60,
      "최대수요관측경과분": 5,
      "최대기사관측경과분": 5,
      "장기대기기회분": 30,
      "장기대기추가인원": 1,
      "주문지연추가인원": 1
    }
  }
}
```

비활성화하면 새 참여 필터·순서를 사용하지 않는다. 진행 중 업무·제안을 초기화할 필요는 없다. 추가 UI/수신 상태/새 DB를 만들지 않아 기존 코드의 업무 소유권을 유지한다.

## 로컬 AI

[독립 로컬 시험 도구](../../../../../eng/local-dispatch-ai/README.md)를 제공한다. 공식 Ollama portable와 `qwen3:1.7b` 모델은 사용자 폴더에 준비하고 해시를 확인했다. 합성 집계 세 가지와 JSON 검증만 사용하며 실제 주소·기사·고객·원장을 읽지 않는다. 자동 시작·외부 서버 통신·실배차 쓰기 권한을 추가하지 않는다.

모델 실행은 자동 승인 검토의 프로세스 시작 거절로 미검증이다. 도구 시험 통과와 실제 모델 추론을 구분한다. 일반 LLM은 배차 전문 최적화 엔진이 아니며, 서버 규칙은 최종 결정, OR-Tools 같은 도구는 제약 조합 계산, LLM은 참고 설명 역할로 분리한다. 이번에는 최적화 도구 설치나 운영 모델 학습을 하지 않았다.

## 검증 반환

새 정책·실제 후보 선정·SQLite 정본 관측·직접 추천 보호를 포함한 Fast 89건과 전체 Task 10,386건이 통과했다. 환경 의존 Mongo 시험 15건은 건너뛰었으며 [변경 기록](../../../../Changes/2026-10-11-food-demand-participation-r44.md)에 실제 실행·이전 실패·수정 근거를 남겼다. 로컬 AI 방어 시험 14건도 통과했다. 로컬 시험을 실운영·단말·소득 효과·LLM 정확도로 승격하지 않는다.
