## 목적과 책임

일반 입고 신청의 응답 ID를 받지 못해도 서버에 실제 전달한 원요청 ID로 신청 결과를 확인한다. 기존 입고 원장의 요청자·선택적 원요청 ID·최초 정규화 입력 SHA를 같은 저장에 묶고 요청자/ID 유일키로 중복 원장을 차단한다. 새 원장·자동 POST 재전송·후보 내용 매칭·임의 잠금 해제는 만들지 않는다.

서버는 동일 ID·동일 최초 입력이면 현재 같은 원장을 반환하고, 동일 ID·다른 입력은 충돌로 거절한다. 저장 후 원장 수정·완료로 최초 지문을 바꾸지 않는다. 충돌은 원 요청의 미적용 증거가 아니므로 `Unknown`으로 안내한다. GET은 기존 입고 조회 권한 안에서 현재 인증된 작성자 본인만 정확히 대조한다. 기존 조회가 작성자에게 허용하듯 창고 회원 상태가 바뀌어도 본인 원장 확인은 유지하며, 창고 소유자·회원이라는 이유로 다른 작성자의 원요청을 조회하지 못한다. 없는 결과의404는 `NotApplicable`이다. 아직 저장 중일 수 있으므로404로 재제출을 허용하지 않는다. 신규 조회 응답은 캐시하지 않는다.

## 계약과 호환

일반 저장 요청과 항목 응답에 선택적 `Guid? ClientRequestId`를 더한다. 항목 응답의 `멱등재시도여부`는 중복 감사 생성을 피하는 서버 결과이며 입력 권한을 주지 않는다. null인 기존 client·현장 임시 입고·주문 자동 입고는 기존 경로를 유지한다. `Guid.Empty`는 유효한 요청 ID로 받지 않는다.

새 client는 보호 저장·재조회한 Guid를 POST의 ClientRequestId로 보낸다. TTL 뒤에도 남는 target `create-request` / `create-request:{입고ID}`로 서버 전달형을 구분한다. r3의 `create`는 서버에 전달하지 않은 단말 관측 ID이므로 새 계약에 소급 연결하지 않는다. `create:{ID}`와 `complete:{ID}`도 보존한다. 새 표식만 원요청 GET을 사용하며 정본 응답의 정확한 요청 ID·대상 ID와 조건부 삭제/삭제 확인을 통과해야 해제한다. 원요청 조회가 현재 정본 전체를 반환하면 추가 ID GET은 요구하지 않는다.

## 화면 책임

신청 화면은 신청 내용을 입력하거나 이번 신청의 결과를 확인한다. 원요청 확인은 기존 새로고침/결과 확인을 재사용하고 긴 기술 설명이나 새 업무 메뉴를 늘리지 않는다. 목록의 비슷한 행을 정답으로 고르지 않는다. 조회 실패·아직 미확인·다른 ID 응답·저장소 장애에서는 기존 입력과 잠금을 유지한다. 계정·세션·서버·관측 ID가 바뀐 뒤의 늦은 응답은 다른 업무를 덮지 않는다.

## 검증과 실행 경계

별도 SQLite 컨텍스트에서 요청자/ID 유일키와 재조회, 같은 내용 재접수1행·다른 내용 거절·다른 작성자 접근 거절·현장 ID 분리·수정 후 최초 지문 보존을 검증한다. client는 응답 유실→새 VM→원요청 GET→같은 원장 확인, 초기404→늦은 저장, 구판/TTL/저장소 실패/계정 전환을 검증한다. 저장 후 감사 실패도 미적용으로 오인하지 않는다.

스키마 변경은 migration과 snapshot·로컬 격리 검증까지만 준비한다. 기존 실행 DB에 자동 적용하거나 운영·worker·권한·사진/동의 조건을 켜지 않는다. scoped Fast/Task 및 소비 client 빌드를 수행하고 화면 정적 렌더·로컬 HTTP/DB·실제 단말을 구분해 기록한다. 커밋·푸시·APK 설치는 이번 범위에 포함하지 않는다.
