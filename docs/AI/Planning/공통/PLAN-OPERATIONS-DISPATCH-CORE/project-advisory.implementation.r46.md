# 프로젝트 근거를 참고하는 로컬 배차·운영 AI r46

- 기획: `PLAN-OPERATIONS-DISPATCH-CORE`, 판본 `dispatch-core.r46`.
- 승인 근거: 사용자가 배차·운영 판단 보조를 선택한 뒤 프로젝트 규칙·사례 참고, 기존 시나리오 비교, 검토 기록 분리 계획에 `Implement the proposed plan.`으로 구현을 요청했다.
- 작업 상태: `Approved / AcceptedInCurrentThread / Implemented / LocalValidationCompleteWithQualityLimits / HumanReviewPending / OperationalDisabled`.
- 기준: [수요 참여 r44](demand-participation.implementation.r44.md), [오프라인 시나리오 r45](offline-scenarios.implementation.r45.md), [실제 Docker 연결](../../../../../eng/local-dispatch-ai/docker/README.md). 앞선 실행 차단과 후속 Docker 성공은 각 당시 기록으로 보존한다.

## 목적과 권위

프로젝트에서 이미 계산한 수요 참여 결과를 로컬 언어 모델에 설명하게 하고, 위험·비교 가능한 대안·출처를 운영자가 검토한다. 모델의 가중치를 바꾸는 추가 학습이 아니다. 제품 서버 API·DB·설정·실제 배차·요금·알림·지급은 변경하지 않으며 최종 상태 권한은 기존 서버 UseCase에 남는다. 음식 배달의 합성 사례만 다루고 화물·생활 배송을 합치지 않는다.

Ollama의 시스템 지시와 예시는 실행 입력을 맞춤화하는 수단이다. 별도로 학습한 가중치를 가져오는 작업과 구분한다. 이번에는 추가 모델·학습 도구·GPU·임베딩 모델을 다운로드하거나 활성화하지 않는다. [공식 Modelfile 안내](https://docs.ollama.com/modelfile), [모델 가져오기 안내](https://docs.ollama.com/import).

## 입력과 근거 연결

기존 .NET 시나리오 도구가 실제 `음식배달수요참여Policy`의 관측 기준·계획 처리량 3.5건/h 결과에서 설명용 입력을 내보낸다. 12개 합성 상황별 주요 시점 최대 3개, 총 최대 36개다. 시점별 주문량·기사 여력·대기·자료 상태와 규칙 결과를 연결하며 원시 고객·실제 기사·실제 주문 자료는 읽지 않는다. 기존 288개 비교의 결과·결정 해시는 별도로 보존한다.

허용 목록의 문서·코드만 읽고 출처 경로·앵커·판본·SHA-256을 실행에 결속한다. 저장소 전체를 검색해 임의 파일이나 비공개 기록을 모델에 보내지 않는다. 다음 세 종류를 구분한다.

| 종류 | 의미 | 해석 |
| --- | --- | --- |
| `implemented` | 현재 구현된 규칙과 실행 경계 | 현재 동작의 근거이며 운영 활성화 증거는 아님 |
| `simulation_assumption` | 합성 도착·수행표와 처리량 등 시험 가정 | 실제 수요·경로·처리량·SLA로 표현하지 않음 |
| `proposed` | 후속 검토·승인 방향 | 이미 구현되거나 적용된 규칙으로 표현하지 않음 |

앵커·해시가 현재 내용과 다르거나 필요한 입력·근거가 무효하면 모델 호출을 진행하지 않는다. 새 입력은 새 근거 해시로 구분한다. 데이터 누락·만료를 수요 0건으로 채우지 않으며 모델이 모르는 숫자·출처를 만들어 채우도록 하지 않는다.

## 설명과 대안 비교

기존 Python 로컬 클라이언트와 실행 중인 Docker `qwen3:1.7b`를 재사용한다. 기본 동작은 HTTP 없는 dry-run이고 명시적 `--execute`에서만 순차 호출한다. 루프백 IP·명시적 HTTP 포트만 허용하고 proxy·redirect·도구 호출·클라우드 대체는 허용하지 않는다. 한 실행의 기본 상한은 36개, 개별 대기 기본값은 90초다. 이번 구현 검증의 모델 추론 요청 시도도 중단된 진행 요청을 포함해 최대 36회 이내로 제한한다. 실행 도구는 컨테이너를 자동 시작하거나 종료하지 않는다.

입력에는 현재 규칙 결과와 기존 비교 4개를 넣는다. 관측 기준(`observed`), 정책 OFF 가정(`policy_off`), 과대 예측 가정(`over`), 미래 도착표를 아는 비교 상한(`oracle`)을 구분한다. 대안의 지표는 이미 계산한 동일 시나리오 전체 기간의 사후 결과다. 수치의 동일/증가/감소 관계도 도구가 계산해 제공하고 모델이 새로 만들어내지 않도록 한다. 해당 시점에서 미래를 예측한 값이나 지금 정책을 바꾸면 얻을 효과로 표현하지 않는다. `oracle`은 실제 AI 예측이나 적용 가능한 실운영 성능이 아니다. 모델은 해당 사례의 한국어 설명·위험·대안 의견·참조 근거를 반환하고 다른 제안은 미검증 의견으로 남긴다.

모델 응답이 규칙 결과나 대안 지표를 변경하지 못하도록 응답 구조·출처·숫자·읽기 전용 표시를 검사한다. `baseline`은 수요·보호/추가/대기 인원·자료/사유·예외 여부를 원문 계산과 정확히 대조한다. 자유 설명에는 숫자를 넣지 못하게 하고 짧은 한국어를 요청한다. 생성 요청의 일반 문장 상한은 120자, 응답 검사 상한은 180자다. 숫자는 검증한 사실·비교 지표로 별도 표시한다. 사례와 관련된 규칙만 실행 입력에 제공하고 `AUTHORITY` 근거를 반드시 인용한다. 미구현 제안을 현재 기준선의 근거로 쓰지 않는다. 대안 의견은 계산된 `policy_off`·`over`·`oracle` 중 최대 2개를 요청하며 응답 검사 상한은 3개다. 새 의견은 `unverifiedProposal`에 분리하고 없으면 null이다.

`unverifiedProposal`의 정확한 문자열 `none`·`null`·`없음`·`제안 없음`만 빈 제안의 어휘 표현으로 보고 null로 정규화한다. 원문과 정규화 이력을 보존하며 다른 문장·필드·숫자·출처·실제 제안 내용을 고쳐 통과시키지 않는다. 중복 JSON 키 등 나머지 무효 응답은 복구해서 채택하지 않는다.

잘못된 JSON·출처·숫자·미완료·시간 초과·연결 실패는 해당 응답을 실패로 기록하고 규칙 결과를 유지한다. 응답이 통과해도 사람이 모든 설명의 정확성·운영 적합성을 검토한 것으로 인증하지 않는다. 실제 구조 통과 응답에서 비교 지표를 잘못 옮기거나 모순된 설명이 확인됐으므로 현재 소형 모델의 자유 설명은 자동 운영 판단에 채택하지 않는다. 확인된 사실·비교 지표와 설명을 나눠 사용자 검토 참고용으로만 보존한다. 현재 CPU 시험에서 설명 한 건이 수십 초 걸려 실시간 배차 요청의 동기 처리에 넣기에는 느리므로 기존 배차와 분리된 사후 검토 범위를 유지한다.

## 실행 기록과 사람 검토

명령과 기본 경로는 [개발 도구 사용법](../../../../../eng/local-dispatch-ai/README.md#프로젝트-근거를-참고하는-설명-r46)을 따른다. 입력·근거·모델·요청·응답·검사·소요시간·실패 이유는 `artifacts/local/`의 실행별 폴더로 분리한다. 원시 응답을 해석 전에 비공개로 보관하고 파싱된 응답은 거절된 내용도 `responses/`와 해시로 보존한다. 원문·제한적 어휘 정규화·채택된 `advice`·사람 승인을 구분한다. 이전 실행이나 사람의 정정은 덮어쓰지 않는다. 실제 모델 호출 수와 dry-run 사례 수를 구분한다.

최종 실행 뒤 별도 `project_review_report.py`가 현재 정본 입력·실행·결과 해시와 사례/기준값을 대조해 `verified-comparison.md` 수치표를 만든다. C# 입력의 정책 결과·대안 4종을 직접 표시하고 null은 미확인으로 남긴다. AI 초안은 별도 `report.md`로 분리해 승인된 판단처럼 수치표에 섞지 않는다. 보고서·입력·실행·결과·생성기 해시는 `verified-comparison.meta.json`에 연결하고 동일 내용만 재사용한다. 추가 추론이나 새 UI가 아니며 수치표 생성도 사람 승인·의미 정확도 측정이 아니다.

검토자는 실행 ID·사례 ID를 선택해 검토자 이름, `approved` 또는 `needs_correction`, 메모를 append-only로 남긴다. 이 명령은 실제 사람의 검토 의견을 기록하기 위한 것이며 도구 실행 성공을 자동 승인하지 않는다. 검토자 이름 입력을 독립적인 신원 확인으로 표현하지 않는다. 존재하는 검증 통과 응답만 검토할 수 있고 요청·실행·응답 해시를 함께 보존한다. 같은 사례의 최신 의견이 `approved`인 것만 향후 학습 후보 파일로 분리하며 이후 정정 필요 의견은 파생 후보에서 제외한다. 이력과 원응답은 삭제하지 않는다.

학습 후보는 검토 이력·후보 파일·연결된 실행의 해시를 다시 대조한다. 파일 교체가 실패하면 후보·검사 메타데이터를 무효화하고 기존 검토 이력은 보존한다. 학습 후보 생성은 실제 추가 학습·학습 품질·운영 승격과 별개다. 정정된 응답이나 AI 자기 응답을 자동 정답으로 삼지 않는다.

## 검증과 인계

- .NET 근거 내보내기: 12개 상황·최대 36개 사례, 정확한 관측 시점·정책 결과·기존 대안 연결, 누락/만료 보존과 기존 결과 불변.
- Python 방어: 기본 HTTP 0회, 루프백 제한·proxy/redirect 금지, 잘못된 입력/출처/숫자/JSON·timeout·tool call 복귀, 해시 결속·기존 기록 보존.
- 검토 원장: 존재하는 실행·사례 연결, 승인/정정 구분, append-only, 승인만 학습 후보 분리. 자동 승인 없음.
- 실제 모델: 기존 12개 상황에서 최대 36회 순차 호출하며 성공·실패·응답 시간·출처 검사를 모두 보존한다. 성공률은 설명 구조 검사 결과이며 실제 배차·예측 정확도 지표가 아니다.

이번 실행 수치와 검사 결과는 [변경 기록](../../../../Changes/2026-10-11-local-dispatch-project-advisory-r46.md)에 남겼다. 12개 상황·30개 시점을 실제 호출해 구조 검사 18개 통과·12개 규칙 결과 복귀를 확인했다. 구조 통과는 설명 정확도가 아니며 모두 사람 검토 대기다. Python 시험 44개와 C# 도구 내부 검사 174개가 통과했고 기존 288개 비교의 결과 해시는 유지됐다. CPU 응답 중앙값 37.227초·p95 43.672초이며 읽기 전용 사후 검토 범위를 유지한다. 최종 실행과 수치 대조 보고서가 생성됐지만 가중치 학습·사람 승인·제품 화면·APK·단말·Azure·실운영·commit/push는 수행하지 않았다.
