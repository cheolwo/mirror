# 화물 3역할·음식 4역할 독립 관리 r9

- 상태: CompletedLocalAndDeviceGroupingValidation / MapFindingsRemain (2026-10-22)
- 승인: 사용자의 제안 계획 구현 요청. 같은 앱·서버·DB와 홈 한 화면의 두 업무 그룹을 선택했다.
- 기존 업무 패키지 `freight-delivery`, `food-delivery`, `order-warehouse`와 전문 원장·권한을 재사용한다.

## 확정된 화면과 책임

홈의 화물 운송에는 화주·화물기사·화물 관리자, 음식 배달에는 주문자·음식점·음식기사·음식 관리자를 표시한다. 생활·창고의 기존 진입은 아래 별도 영역에 유지한다. 관리자 두 진입은 같은 기존 `operator` 자격을 사용하되 조회·카드·메뉴·복귀·선택 상태는 업무별로 나눈다. 음식 운영에 섞인 화물 사건은 화물 관리자 문맥으로 옮기며 창고 업무는 별도 진입을 유지한다.

`/workspace/operator?business=freight-delivery`와 `food-delivery`를 명시적 진입으로 사용한다. 기존 `/workspace/operator`는 음식으로 호환한다. 고유 역할의 기존 URL은 보존한다. 업무를 바꿀 때 이전 조회·지도·오류·선택이 다른 업무에 나타나지 않게 하고 미확정 요청 ID를 업무별로 보존한다. 인증·지도 호스트·알림 기술·공통 화면은 복제하지 않는다.

## 구현 순서

1. 업무 문맥·홈 그룹과 관리자별 Adapter/조회/복귀를 분리한다.
2. 화주 접수 → 추천 → 기사 수락 → 상차·운송·하차 → 화주 인수와 관리자 예외 검토를 기존 계약으로 검증한다.
3. 음식 주문 → 음식점 수락 → 기사 배정 → 조리/이동 → 픽업 → 전달 → 수령 확인과 관리자 복구를 기존 계약으로 검증한다.
4. 두 업무의 독립 정상/예외와 공통 기술 회귀를 통과한 뒤 추후 통합을 검토한다.

관리자 운송 조회에 선택적 `business` 필터를 추가한다. 새 화물 진입은 서버에서 현재 운송 유형을 필터링하며 잘못된 구분은 전체 조회로 처리하지 않는다. 기존 필터 없는 API·구판 URL은 호환한다. DB schema·권한·완료 조건·운임·배차 알고리즘·정산·실지급은 변경하지 않는다.

## 완료 기준과 경계

- 홈 3/4역할과 기존 생활·창고 접근, 관리자 로그인/복귀/알림 진입 호환.
- 화물/음식이 동시에 있어도 조회·지도·명령·요청 ID가 섞이지 않음. 늦은 응답과 로그아웃 보호.
- 정상 한 건과 기존 통신 끊김·중복 수락·사진 실패·결과 미확정 복구를 묶음별로 확인.
- 집중 Fast·Task 및 소비 build·APK 제작·실제 렌더/허용된 기기 확인을 구분해 기록.
