# 업무 단계별 진행 알림 r6

- 상태: CompletedLocalValidation / ExternalPushAndDevicePending (2026-10-22)
- 승인: 사용자가 입고·음식 주문/피킹/배달·화물 요청의 절차 진행에 맞춰 기존 알림을 리팩토링하도록 요청했다.
- 기준: 각 전문 원장의 서버 확정 상태가 권위다. OS catalog의 순서를 실행 가능한 상태 전이로 추정하지 않는다.

## 구현 범위

1. 기존 `Command알림Outbox`에 단계 코드·짧은 문구·인증된 관계자·기존 업무 화면을 담는다. 새 알림 DB나 상태 엔진을 만들지 않는다.
2. 음식 접수/수락/조리/준비/기사 배정/도착/픽업/전달/수령, 창고 입고/검수/적재/피킹/포장/출고/인계의 실제 변경과 알림 예약을 같은 저장 경계에 둔다. 사진 가 입고는 개인 준비이며 실제 입고 알림으로 승격하지 않는다.
3. 화물은 기존 수락·상하차·문제 알림과 재시도를 재사용한다. 알림 처리기가 상태를 다시 쓰지 않으며 과거 단계/다른 담당자의 이벤트를 거부한다.
4. 수신자별 같은 원천·단계·발생 식별자를 재사용한다. 조회/동일 상태/중복 요청에서는 새 알림을 만들지 않는다. 새 단계가 아닌 조리시간 변경은 기존 재조회 신호만 유지한다.
5. 주소·전화·고객명·사진 경로·원문 메모를 푸시 본문에 넣지 않는다. 알림을 누르면 인증된 기존 업무 화면에서 최신 정보를 다시 조회한다.
6. 통합앱의 기존 수신 설정을 존중하며 진행 알림 수신과 안전한 기존 경로 연결을 보완한다. 기사 추천 배너/수락 알림과 일반 진행 안내는 합치지 않는다.

## 보존 경계

- 단계 완료, 전송 접수, 사용자 열람, 수령 확인, 정산, 실지급은 서로 다른 결과다.
- 잘못된 수신자 ID를 추정하지 않는다. 음식점은 기존 인증된 음식점 SignalR 그룹을 유지한다. 창고는 소유자/실제 지정 담당자/기존 접근 가능한 요청자만 대상으로 한다.
- DB Outbox의 재전송과 외부 FCM은 최소 한 번 전달 경계다. 네트워크의 정확히 한 번 수신을 보장한다고 표현하지 않는다.
- 기존 운영/worker/외부 푸시 설정은 바꾸지 않는다. 실제 알림음·단말/외부 전송·운영 배포는 별도 검증한다.
- 관련 없는 dirty 파일과 기존 r3/r4/r5 자료를 보존한다. commit/push/APK 설치/실 DB migration을 실행하지 않는다.

## 검증

집중 시험으로 수신자·단계·내용 최소화·기존 경로·중복 요청·실패 저장/재시도·오래된 이벤트 상태 역행 방지를 확인한다. `Fast` 후 `Task`와 공유 계약 소비 빌드를 수행한다. 로컬 시험 결과와 실제 FCM·단말 관측을 구분해 변경 기록에 남긴다.

완료: Fast536, Task14,588통과/환경16미실행, Android·Windows·웹·서버 소비 솔루션 빌드 통과. [단계별 수신·변경·최종 검증](../../../../Changes/2026-10-22-workflow-progress-notifications-r6.md)을 정본으로 따른다. 신규 DB/스키마·운영 설정·실제 외부 발송·단말·commit/push는 실행하지 않았다.
