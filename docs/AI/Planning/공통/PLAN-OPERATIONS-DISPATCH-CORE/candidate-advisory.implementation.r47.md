# 배달권·기사 후보 근거를 연결하는 로컬 배차 AI r47

- 기획: `PLAN-OPERATIONS-DISPATCH-CORE`, 판본 `dispatch-core.r47`.
- 승인 근거: 사용자가 기존 배달권 안의 주문·기사와 인접 배달권을 고려한 기획을 Ollama가 참고하도록 현재 프로젝트의 리팩토링을 요청했다. 현재 스레드에서 아래 좁은 구현 범위를 수용한다.
- 설계 상태: `Approved / AcceptedInCurrentThread / OperationalDisabled`.
- 앞선 범위: [수요 참여 r44](demand-participation.implementation.r44.md), [오프라인 시나리오 r45](offline-scenarios.implementation.r45.md), [프로젝트 근거 설명 r46](project-advisory.implementation.r46.md), [사용자 문답 방향](배차-사례-문답검토절차.md).
- 개발 반환과 실제 검증 결과: [r47 변경 기록](../../../../Changes/2026-10-11-local-dispatch-candidate-advisory-r47.md).

## 해결할 차이

r46은 실제 수요 참여 Policy의 주문량·기사 여력과 참여 인원 결과를 설명하는 범위였다. 같은 배달권·인접 배달권의 실제 기사 후보, 픽업 가능 단계, 후보 제외와 최종 선정 근거가 모델 입력에 없었다. 이 작업은 기존 음식 배달 후보 선정의 읽기 전용 검토 결과를 별도로 내보내 이 차이를 줄인다. 저장소 전체나 실제 고객 자료를 모델에 넣지 않으며 가중치 학습도 하지 않는다.

## 책임과 현재 정책

기존 `음식배달배차업무정책`의 후보 조회·적격 평가·정렬을 재사용한다. `후보검토Async`는 같은 계산에서 배달권 탐색과 후보 판정 근거를 반환하고 기존 `다음후보선정Async`는 그 결과의 선정 후보를 반환한다. 이 분리로 운영 알고리즘·공개 API·수신 의사·수락·DB·요금·알림을 바꾸지 않는다. 모델 결과를 이 운영 경로가 읽거나 실행하지 않는다.

| 현재 근거 | 모델에 전달할 의미 |
| --- | --- |
| 같은 음식배달권 | 현재 주문 픽업지가 속한 권역과 해당 공간의 기사 후보 |
| 인접 음식배달권 | 기존 후보 수·참여 정책·복귀 평가 조건에 따라 조회·비교에 포함하는 주변 권역 |
| 제한 공간 확장 | 기존 권역 후보를 확보하지 못했을 때 기존 검색 반경 안에서만 적용하는 후속 탐색 |
| 적격·픽업 단계 | 거절/제외 기사, 수신 의사, GPS·경로·수행 여력과 음식 준비 시각을 현재 정책대로 평가한 결과 |
| 참여·기회 순서 | 실제 수요·가용 여력의 참여 권고와 대기·기존 활동·최근 배차를 비교하는 현재 코드 결과 |
| 권역 복귀 | 기존 복귀 조건과 일정 검토에서 확인된 가점. 다음 픽업 출발점을 마지막 전달지로 바꾸는 것과 구별 |

같은 권역에 충분한 기사가 있을 때 인접권을 무조건 추가하거나, 자료가 불명확한데 참여 정책이 유효한 것으로 해석하지 않는다. 읽기 전용 결과는 실제 평가 경로를 기록하며 후보 부재·조회 미실행·누락값을 각각 보존한다. 조회되지 않은 권역을 주문·기사 0건으로 채우지 않는다. 계산의 빈 결과를 오류 없는 최적 배차로 표현하지 않는다.

## 합성 사례와 문맥의 구분

별도 `CandidateScenarioRunner`에서 실제 후보 정책을 합성 기사·주문·권역 저장소와 합성 경로 응답으로 실행한다. 현재 코드의 후보·제약·선정 결과, 입력 자료의 현재성·출처, 소스·규칙·입력 SHA-256을 내보낸다. 실제 DB·기기·위치·고객·업무 API를 읽지 않는다. 경로 시간·조리 준비·기사 위치·배달권 주문량은 시험 가정이며 네이버 경로·실제 수요·실운영 관측이라고 표시하지 않는다.

입력의 근거는 다음 상태로 나눈다. 모든 사용자 방향을 이미 운영 코드에 반영된 사실로 합치지 않는다.

| 상태 | 적용 범위 |
| --- | --- |
| `implemented` | 실제 코드가 현재 계산한 후보 관문·검색·정렬·최종 권위 |
| `user_preference` | 시간표보다 실제 수요와 가용 여력 우선, 수행 조건이 비슷하면 장기 대기자에게 다음 제안 기회 우선이라는 사용자 확인 방향 |
| `simulation_assumption` | 합성 위치·경로·준비 시간·수요, 계획 처리량 등 |
| `proposed` | 시간대 전환 가점, 수행 중 기사의 확정 마지막 전달지와 잔여시간을 다음 픽업 출발점으로 사용하는 후속안 |

사용자의 약 4건/h는 계획 경험값이다. 현재 contract 기본 3.5건/h와 r45·r46 비교는 보존한다. 가정의 30분을 장기 대기 임계값으로 확정하지 않는다. 대기시간이 길지만 픽업이 늦어지는 구체적 절충안은 사용자 미답변이며 승인된 정책으로 기록하지 않는다. 현재 코드의 픽업 단계 우선과 사용자 정책 방향의 세부 조합은 구별한다.

## Ollama의 제한된 검토

기존 루프백 전송 클라이언트와 실행 중인 Docker `qwen3:1.7b`를 재사용한다. 기본 진입은 HTTP 없는 준비 검사다. 명시적 실행만 모델을 호출하며 이번 r47의 실제 추론 요청 시작은 중단·실패를 포함해 누적 최대 4회다. 호출 전에 비공개 예산 기록을 예약하고 재실행도 같은 누적 한도를 따른다. 이전 r46의 36회 예산·실행·응답을 재사용해 추가 호출하거나 소급 수정하지 않는다.

모델은 제공된 허용 후보 ID 또는 후보 없음과 제한된 판단 근거 코드만 반환한다. 후보·점수·거리·시간·수요 수치를 새로 생성하지 않는다. 자유 설명 대신 검증된 사실표와 고정 근거 코드의 한국어 문구를 표시한다. 허용된 후보 중에서도 현재 관문·픽업 단계 등 입력의 제한을 벗어나는 선택은 거절한다. 모델이 어떤 선택을 했는지와 현재 정책의 기준 선택은 별도로 보존한다.

입력·규칙·소스의 해시와 판본을 다시 대조하며 다른 경로·임의 모델·외부 주소·proxy·redirect·도구 호출·클라우드 대체는 허용하지 않는다. 잘못된 JSON·중복 키·후보 발명·부적격 선택·근거 오류·자료 변경·timeout·연결 실패에는 현재 정책 결과를 유지하고 이유를 남긴다. 의미 정확도나 운영 적합성을 구조 검사로 인증하지 않는다.

## 검증·이력·완료 경계

동일권 후보 충분/부족, 인접권 추가, 제한 확장, 적격 제외, 현재성 미확인, 픽업 제약, 참여·장기 대기 조건을 합성 사례와 집중 시험으로 대조한다. 기존 후보 선정 반환과 읽기 전용 검토 결과의 선택이 같은지도 검사한다. Python은 입력/근거 결속·응답 제약·fallback·누적 예산·기록 보존을 검증한다. 실제 실행한 사례·검사·모델 호출 수는 변경 기록에만 확정한다.

실행별 입력·요청·원응답·검사·시간·선정 비교는 Git 제외 `artifacts/local/local-dispatch-ai/`에 보관한다. 도구 성공, 구조 검사, 사람 검토, 승인, 학습 후보와 실제 학습은 다른 상태다. 이번 결과를 자동 승인하거나 학습 후보로 만들지 않는다.

기존 정책 파일이 변경되므로 r46 입력의 해당 소스 해시는 현재 소스와 달라질 수 있다. r46의 실행 당시 기록·응답·보고서는 보존하고, 현재 소스 재검사에서 `stale`로 거절하는 것이 정상이다. 과거 실행을 현재 기준으로 다시 통과시키거나 기존 해시를 덮어쓰지 않는다.

서버의 최종 권한·수락·동시성·영속 상태 권위와 기존 기능 기본 OFF를 유지한다. 화물·생활 배송·새 UI·APK·Unity·Azure·외부 알림·배포·commit/push는 이번 범위에 포함하지 않는다. 로컬 합성 후보 검토는 실제 배차 연결·경로 최적화·전체 플랫폼 안정성이나 소득 보장의 증거가 아니다.
