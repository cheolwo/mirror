# 퀵 기사 이동 중 후속 콜·연속 수행 검증 r63

- 기획 ID·판본: `PLAN-OPERATIONS-DISPATCH-CORE / dispatch-core.r63`, 2026-10-16.
- 상태: `Reviewed / LocalTestsValidated / GapsIdentified / ImplementationNotAuthorized / DeviceDeferred`.
- 사용자 요청: 퀵 기사가 현재 콜을 수행하거나 다음 지역으로 이동하는 동안 다음 콜을 받아 업무를 이어갈 수 있도록 배려됐는지 검증한다.
- 기준: `dev/mirror-integration`, HEAD `b02f541aa00156376e6e33525753cd8a983d6671`와 현재 작업 트리. [기존 구성 검토 r57](driver-dispatch-structure.review.r57.md), [수행 가능성·대기 방향 r56](quick-dispatch-feasibility-waiting.design.r56.md), [미응답 중지 구현 r62](driver-no-response.implementation.r62.md)를 현재 소스와 다시 대조했다.
- 이번 범위: 제품 코드·정책·설정 변경 없이 소스, 기존 집중 시험과 실제 서버 필터를 검증했다. 외부 운영·실제 주행·휴대폰·FCM/알림음 검증은 포함하지 않는다.

## 판단

**수행 중 추가 콜을 표시·수락하는 기반은 있으나, 퀵 기사에게 다음 목적지 기준으로 콜을 제안하고 기존 업무에서 다음 업무까지 자연스럽게 이어주는 흐름은 미완성이다.** 추가 수락이 가능한 것, 최적의 후속 후보를 찾는 것, 현재 업무 카드를 보존하는 것, 실제 알림을 받는 것은 각각 다른 검증 결과다.

생활 퀵은 `생활배송배차방식`이 있는 기존 화주 의뢰를 사용하고 공통 업무 선택에서는 `QuickDelivery`로 구분된다. 실제 추천·수락·운송 경로는 화물 기사 `DriverApp`과 서버의 화물 전문 정책이다. 음식 `FDriverApp`의 `WorkKind`·퀵 표시 지원이나 음식의 후속 앵커를 생활 퀵 통합 완료로 확대하지 않는다.

근거: `Ssalddel/Services/Community/NeighborhoodDeliveryUseCase.cs:134`, `Ssalddel/Services/Dispatch/Participation/SharedDriverWorkAdmissionService.cs:152`, `FDriverApp/Services/FoodDeliveryDriverApiService.cs:77,174,204`.

### 1. 자동 후보와 마지막 목적지

`용달운송배차업무정책.cs:85`는 픽업지 주변의 **현재 위치**를 조회하고 `:173`에서 현재 GPS→픽업 직선거리를 평가한다. 차량·운행·위치 유효성은 검사하지만 모든 기존 업무의 마지막 종료지/시각을 이 입력에 전달하지 않는다. 별도 `배차추천경로Service.Location.cs:54`도 현재 GPS가 있으면 우선 반환한다.

따라서 ‘지금 위치는 다음 픽업에서 멀지만 현재 업무를 마치면 바로 옆으로 가는 기사’를 초기 후보에서 놓칠 수 있다. 이는 소스에서 도출한 사례이며 실제 주문·주행 측정 결과가 아니다. 음식의 `음식권역복귀일정평가Service.cs:70`에는 기존 전체 업무의 마지막 전달지/예상 종료를 반환하는 옵션 경로가 있으나 퀵 자동 후보에는 같은 연결이 없다.

### 2. 수신·추가 업무 보호의 차이

- `SharedDriverWorkAdmissionPolicy.cs:40,44`는 옵션 활성 시 추가 수신 의사와 개인/운영 동시 상한을 검사한다. 기본 개인 상한은 1, 운영 상한은 4이며 서로 비교한다. 미확인 적재량을 0으로 만들어 통과시키지 않고 반납 책임도 보존한다.
- `화물배차수락적격성Service.cs:79,127,157,168,185`는 현재 운송을 포함한 일정·시간창·적재를 재검사한다. `배차수락CommandHandler.cs:174,213`의 수락 관문과 연결돼 있다.
- 이 공통 업무 선택/여력 검사는 운영 배차의 신규 수신 ON/OFF·미응답 자동중지를 대신하지 않는다. `용달운송배차업무정책.cs:113` 이후 후보 경로와 일반 수락에는 공통 수신 허용 호출이 없고, `화물연속배차UseCase.cs:162`는 raw 수신 의사/실효 상태만 비교한다.
- 연속 예약 ID가 없는 일반 수락은 `화물연속배차UseCase.cs:287`에서 예약 검사만 생략한다. 이것을 일반 수락 전체의 무조건 허용이라고 해석하지 않는다. 추천 차수·현재 대상·전문 적격성·공통 여력 등 다른 수락 관문은 별도로 존재한다.

### 3. 네이티브 기사 화면

`DriverApp/NativeDriverHomePage.xaml.cs:597,623`은 추천 알림 사건을 받아 배너를 갱신한다. `DriverHomeRoutePlanningService.cs:26,89,121`의 연계 경로는 현재 업무의 다음 상/하차지를 거쳐 새 픽업·하차지로 이어지는 **표현**이며 모든 업무의 마지막 목적지 기준 후보 선정 증거가 아니다.

`DriverRecommendationDecisionService.cs:43,151`은 서버 수락과 강제 원장 재조회를 수행한다. 하지만 `NativeDriverHomePage.xaml.cs:390,514,528`은 그 뒤 `_currentTransport`를 다시 읽지 않고 추천 수락 경로를 표시하며 `TransportFooterBar.IsVisible=false`로 기존 카드를 숨긴다. 수락 재조회가 실패해도 별도 주의 문구와 수락 결과는 보존되므로, 이때 화면이 임의로 새 업무로 확정 이동하지 않게 할 필요도 있다.

`DriverNativeHomeWorkspaceState.cs:44`와 `NativeDriverHomePage.xaml.cs:55`은 재진입 정본 갱신을 제공한다. 추천 목록·진행 운송 Razor 페이지의 30초 보완 조회와 네이티브 홈의 추천 카운트다운은 별도다. `DriverRecommendationPushRecovery.cs:57,82,116`의 복귀 처리는 저장된 알림 대상과 정본을 확인하며 지속적인 전체 업무 조회를 보장하지 않는다.

음식 앱은 기존 선택 업무가 남아 있으면 유지하고 없으면 다음 활성 업무를 선택하는 근거가 있다(`MainPageModel.cs:249,257,750,847`). 이 시험을 퀵 네이티브 화면의 A 수행→B 수락→A 완료→B 전환 검증으로 대신하지 않는다.

### 4. 다음 콜 예약의 현재 실행 경계

`화물연속배차Options.cs:7`의 기본값은 `Enabled=false`, `ShadowMode=true`, 운임 정책 비활성이다. `화물연속배차BackgroundService.cs:29,51,61`은 이 조건과 활성 기사 목록을 통과해야 탐색한다. 작업공간 GET은 상태·시간약속·위험만 읽고 예약을 새로 만들지 않는다.

기사별 다음 한 건 보유는 있지만 의뢰 전체를 독점하는 예약 키는 없다(`화물연속배차원장Configuration.cs:50`). 일반 후보·만료 정책도 이 예약 원장을 조회하지 않는다. 기존 추천 대상·TTL·수락 경합 보호와 이 예약을 혼동하지 않는다.

또한 실제 `화물연속배차Controller.조회`의 metadata와 제품 `SsalddelApiFeatureBoundaryFilter`를 직접 실행했다. Feature 서비스는 모두 true인 검증용 구현을 사용했으며 운영 설정은 바꾸지 않았다. 결과는 `404 FeatureBoundaryUnclassified`, action 미진입이었다. 비교 대상인 기존 `기사운영배차공통Controller.수신상태조회`는 같은 필터를 통과했다. 연속배차 Controller의 실행 Feature 분류가 빠져 있어 옵션을 켜는 것만으로 API 연결이 완성되지 않는다. 이것은 필터 직접 호출 검증이며 실제 인증 HTTP·기기 요청은 아니다.

## 보완 우선순위 제안

1. **서버의 퀵 신규 수신 조건 통일:** 후보 선정·추천 저장·일반 수락·연속 예약에서 공통 ON/OFF·미응답 중지·추가 수신·여력을 일관되게 검사한다. 이미 수락한 업무 복구·완료는 신규 조건으로 막지 않는다.
2. **후속 후보의 출발 기준 통일:** 수행 중이면 모든 기존 업무의 마지막 목적지·완료 예상시각에서 새 픽업·전달을 평가한다. 유휴 이동 중에는 현재 GPS를 사용한다. 기존 일정에 지장 없는 후보를 먼저 추리고 r56의 대기 우선 방향과 미확인 근거를 유지한다.
3. **네이티브 화면의 A→B 마감:** B 수락 후에도 서버의 현재 행동 A를 유지하고, A가 끝나면 같은 카드·지도에서 B로 전환한다. 앱을 나갔다 돌아오지 않아도 보완 조회가 이어지고, 조회 실패 때 마지막 확인 업무와 확인 중 상태를 보존하도록 검증한다.
4. **별도 다음 콜 예약 마감:** 실행 Feature 분류·앱 설정/수락 계약·예약 경쟁을 먼저 정리한 뒤 실제 활성화 여부를 별도로 결정한다. 기본 OFF를 임의 해제하지 않는다.

가장 필요한 새 통합 검증은 **퀵 A 수행 중 B 제안 → B 수락 → A 카드·약속 유지 → A 완료 → B 자동 전환**, 그리고 같은 조건에서 수신 OFF·자동중지·조회 실패·만료·용량 부족을 바꿔 비교하는 것이다. 이번 요청은 검증이므로 이 제안을 구현하거나 새 정책으로 확정하지 않았다.
