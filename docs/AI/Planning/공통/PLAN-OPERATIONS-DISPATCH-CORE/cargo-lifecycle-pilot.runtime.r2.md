# 화물 서버·실제 휴대폰 검증 r2

- 사용자 요청: 공통 절차 다음 단계로 서버와 휴대폰 검증 진행.
- 준비 기준: [파일럿 입력 r1](cargo-lifecycle-pilot.evidence.r1.md). r1의 준비 전용 승인을 소급 확대하지 않고 이번 요청의 실행 범위를 따로 기록한다.
- 범위: 현재 제품의 격리 Development/Simulation 서버, 신규 합성 GUID DB, 화주·전문 기사·운영자의 같은 의뢰/운송 조회와 재실행 확인. 실제 운송·외부 Push·실결제·송금·운영 공개는 제외한다.
- 방법: 기존 IntegratedWorkflowR108 하네스·제품 HTTP 여정을 재사용한다. 현행 클라이언트 입력 해시와 일치하는 검토 APK는 재사용하고, 일치하지 않는 관리자만 별도 출력으로 빌드한다. 기존 앱·데이터와 다른 서버·컨테이너·볼륨은 보존한다.

## 실행과 증거 경계

1. 소스/서버 DLL/APK/endpoint·USB reverse·기기와 신규 DB의 소유를 기록한다.
2. 신규 화주 접수·승인 후불·추천·수락을 제품 API로 처리하고 같은 의뢰/운송을 휴대폰에서 관측한다. 이 하네스는 선결제를 비활성화하므로 후불 성공을 기본 선결제 성공으로 표시하지 않는다. 제어 추천·합성 경로·위치·사진은 실제 AI/GPS/카메라와 구분한다.
3. 앱 강제 종료 후 재실행과 본인 원장 재조회를 확인한다. HTTP 처리와 휴대폰 버튼 조작의 범위를 각각 남긴다. 결과가 불명확한 변경 요청은 재전송하지 않는다.
4. 소유한 서버만 중지/같은 DB로 재시작하고 완료·중복·원장 보존을 조회한다. 운영자 제품 API와 native 목록도 별도로 대조한다.
5. 금융/외부 전송 0건과 시험 기사 종료·이번 reverse 정리를 확인한다. 실제 확인하지 못한 화면·기능·기기 상태는 실패/보류로 남긴다.

추적 제품 코드 변경은 이번 검증의 전제가 아니다. 결함을 찾으면 재현·원인·영향을 먼저 남긴다. 기존 사람 검토 Pending을 시험자가 완료로 바꾸지 않으며, 사용자의 실행 요청과 입력 문서의 항목별 확인은 구분한다. 로컬 원캡처·계정·토큰은 비공개 artifacts에 두고 결과 문서에는 합성 사례와 검증 상한만 쓴다.

결과 자료는 `artifacts/local/cargo-lifecycle-runtime-r14/`와 그 안에서 연결한 신규 하네스 출력에 보존한다. 결과는 별도 변경 기록에서 정리하며 이 실행 계획을 성공 증거로 사용하지 않는다. commit/push·배포·공유 환경 초기화는 수행하지 않는다.
