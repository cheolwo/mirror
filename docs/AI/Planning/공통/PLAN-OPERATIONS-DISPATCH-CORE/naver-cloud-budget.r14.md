# 월50만원 네이버 클라우드 단일 서버 운영안 r14

상태: ResearchCompleted / EstimatePrepared / ResourcesNotCreated. 조사일: 2026-10-22. [배포 방향 r13](naver-cloud-role-hosting.r13.md)의 비용 구체화다.

사용자 요청은 관리형 DB를 별도 대여하지 않고 앱·DB를 서버에 묶어 배포할 때 월50만원으로 가능한 구성을 조사하는 것이다. **부가세 포함50만원**, 한국 VPC g3·Linux·24시간 운영을 가정한다. 아래는 공식 공개 요금과 명시된 사용량을 조합한 예상안이며, 실제 계정 콘솔 견적·크레딧·운영 처리량을 확인한 결과가 아니다.

## 한 서버·하나의 배포 묶음

```text
NCP Linux VM 1대 · Docker Compose 1묶음
├─ API 서버
├─ MySQL 8.4
├─ MongoDB 8
├─ Caddy · HTTPS
└─ Ollama · 연결·부하 검증 후 선택

DB 데이터 → 별도 영속 볼륨
복구 사본 → VM 밖의 비공개 저장소
메뉴 사진·휴대폰 푸시 → 기존 GCS·FCM 연결 우선 유지
```

한 VM에서 각각의 컨테이너를 실행하면 관리형 DB 별도 요금 없이 기존 [Compose](../../../../../deploy/azure-vm/compose.yaml)를 발전시킬 수 있다. 앱·DB를 한 컨테이너 안의 복수 프로세스로 합치는 것보다 서비스별 재시작·업데이트·자원 한도를 분리하기 쉽다. 기존 코드도 여러 컨테이너 구성이다. 이 안은 서버 한 대를 임대해 DB를 직접 관리하는 방식이므로 백업·복원·패치 책임이 남는다.

## 추천 후보와 계산

AI 추론을 API·DB와 함께 시험할 후보는 **High CPU-g3 8vCPU·16GB**다. 가벼운 시작은 Standard-g3 4vCPU·16GB이며 부하 확인 후 확대한다. CPU 추론을 검증하지 않았으므로 특정 동시 사용자/주문 처리량이나 AI 응답 시간을 보장하지 않는다.

공식 한국 요금표의 서버 월 표시액은 VAT 별도다. 4vCPU·16GB Standard는170,240원, 8vCPU·16GB High CPU는282,240원, 4vCPU·32GB High Memory는234,240원, 8vCPU·32GB Standard는346,240원이다. 아래 서버 금액은 해당 월 표시액에 VAT10%를 더했다. 스토리지·IP는730시간으로 계산했으며 서버 시간요금×730과 월 표시액을 혼동하지 않는다. [공식 요금표](https://www.ncloud.com/charge/region/ko)

백업·지도·GCS·도메인/로그 행은 실사용 견적이 아닌 **예산 배정액**이다. 기존 다른 프로젝트의 Azure/GCS 비용, 인건비, PG 수수료, 유료 SMS/알림톡, GPU·유료 AI API, Kubernetes·로드밸런서·관리형 DB는 포함하지 않았다. 기본 알림은 기존 FCM 경로를 우선하며 실제 인증·수신 검증은 별도다.

## 무엇을 운영할 수 있고 무엇을 먼저 측정해야 하나

- API·원장 저장·인증·운송 접수/추천/수락/완료·기본 실시간 연결·사진 참조를 한 서버에서 시험할 구조다. 서버 사양만으로 안정적인 주문/기사 수를 정하지 않는다. 주문 접수율·GPS 갱신 주기·DB 쿼리·SignalR 연결·AI 호출/지연·사진 크기를 함께 측정한다.
- [기존 Ollama Docker](../../../../../eng/local-dispatch-ai/docker/compose.yaml)는 CPU4·메모리6GiB 제한과 동시 추론1개를 사용한다. [현재 화물 옵션](../../../../../Ssalddel/Services/Dispatch/AI/CargoDispatchOllamaOptions.cs)은 qwen3:1.7b·기본2초 제한·숫자 loopback 주소를 검사한다. 컨테이너 배치 검증 없이 일반 서비스 DNS나 원격 IP로 바꾸지 않는다. 실패/지연 시 기존 규칙 결과로 복귀하며, GPU 학습·큰 모델의 상시 고속 추론을 이 예산으로 보장하지 않는다.
- 서버 인터넷 전송이200GB에서1,000GB로 커지면 같은 계산은 약551,305원이 된다. 큰 주행 원본/영상은 앱 서버의 디스크·전송 예산에 섞지 않고 기존 영상 배포 경로를 사용한다. 사진 축소·불필요한 반복 조회 억제·로그 회전과 필요한 데이터만 전달하는 정책을 마련한다.
- Maps는 현재 계정의 대표 계정 여부·상품별 무료량을 콘솔에서 확인한다. 무료를 무조건 가정하지 않는다. API별 일/월 한도·알림과 **한도 초과 사용** 설정을 함께 점검한다. 비용 알림을 전체 서버 요금의 자동 차단으로 오인하지 않는다. [현행 VPC Maps 한도·초과 사용 관리](https://guide.ncloud-docs.com/docs/application-maps-app-vpc)

## 복구와 다음 준비

1. 앱·DB 영속 볼륨을 분리하고 DB 포트를 외부에 공개하지 않는다. 단일 VM 장애 시 앱·DB가 함께 중단될 수 있다는 운영 조건을 기록한다.
2. VM 밖에 암호화 DB 덤프·키링·필수 인증서/암호화키의 복구 사본을 둔다. [기존 백업](../../../../../deploy/azure-vm/operations-alerts/backup.sh)은 Azure 업로드에 연결돼 있으므로 NCP/GCS 대상 변경과 격리 복원을 검증해야 한다. 볼륨만 있거나 백업 파일만 생성됐다고 복구 완료로 표시하지 않는다.
3. 실제 자료의 크기를 보고 일/주 보관량을 정한다. MySQL·Mongo의 서로 다른 덤프를 전역 원자 스냅샷으로 주장하지 않고, 복구 후 같은 주문/운송의 연결을 대조한다.
4. NCP용 배포 설정을 로컬에서 검증한 뒤 시험 서버로 접수→배차→수락→사진→완료→재시작/오류 복구·FCM 수신을 확인한다. 기존 Operational/Simulation·기능 옵션은 검증 없이 켜지 않는다.
5. 실사용 계측 후 서버·스토리지·트래픽·지도 한도를 확정한다. 예상40만원/45만원 등 비용 알림은 설계 후보이며 이번에 설정하지 않았다.

이번에는 공식 자료와 기존 코드 조사·계산·문서만 진행했다. 네이버 계정/콘솔 견적 조회, 유료 자원 생성, 앱/DB 코드 변경·배포·APK·실운영·commit/push는 하지 않았다.
