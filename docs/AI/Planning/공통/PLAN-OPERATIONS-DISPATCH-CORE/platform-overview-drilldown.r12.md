# 플랫폼 운영 요약에서 세부 업무로 이어지는 조정안 r12

상태: Wave1CompletedLocalValidation / RemainingR12WorkPending. 기준일: 2026-10-22.

## 승인된 첫 구현 범위

사용자가 조정안 적용을 요청했다. [첫 구현 작업 명세](platform-overview-drilldown.r12.work-order.json)에 따라 공개 화물 참여 요약→월별 비식별 집계·기준의 세부 화면, 관리자 운송·지원 목록의 분야/조건 복귀, 모바일 커뮤니티 내부 복귀 전달을 먼저 구현한다. 기존 상세·명령·권한은 유지한다. 공개 세부 조회는 개인별 운송/계정 식별자를 반환하지 않는다.

[첫 구현 결과·실제 화면](../../../../Changes/2026-10-22-overview-drilldown-r12.md): 최종 Task14,807통과·실패0·환경16미실행, 신규104사례와 최종37소스 동결·실제 읽기 API/공유 Razor 화면을 대조했다. APK·물리 기기·외부 운영은 이번에 시험하지 않았다.

이번 첫 구현은 전체 r12의 일괄 완료가 아니다. 음식/창고의 전체 페이지 탐색, 본인 정산·재무 목록 투영 분리, 후원 수납/실입금·공개 기여자/교육의 준비는 후속 단계로 보존한다. r11의 미정 순위식이나 실제 자금 수납·새 권한을 활성화하지 않는다.

사용자는 플랫폼 전반의 운영 요약을 먼저 보고, 선택한 요약에서 구체적인 세부 내역으로 내려갈 수 있도록 프로젝트 전반의 조정안을 요청했다. 아래 조사 결과는 구현 전 기준선이다. [누적 홈 r10](home-participation.r10.md), 후속 [운영후원·기여자 기획 r11](operating-support-contributors.r11.md)을 연결하며 첫 구현의 변경·검증은 별도 결과 문서로 기록한다.

## 1. 조사 결론과 범위

현재 통합앱·웹 홈은 `RoleSelectionHome`을 소비한다. r10의 누적 금액/화물 완료 참여 표시에는 세부 근거로 이동하는 링크가 없다. 역할 진입은 화물3·음식4·생활/창고2의9개이며, 관리자가 두 업무 문맥에 공통으로 등장해 실제 역할 종류는8개다.

공통 `RoleMapWorkspace`는 지도와 선택된 한 건의 요약·접힌 상세·업무 목록을 조립한 **현재 업무 화면**이다. 역할 전체의 운영 현황 화면은 아니다. 기존 수행·상세 화면을 버리고 새 화면으로 대체하기보다 앞의 읽기 전용 요약과 필터 목록 연결을 보완하는 것이 적절하다.

조사는 공통 홈, 8역할 카탈로그/Adapter와 통합앱·웹 route, 관리자 재무·정산·지원·교육의 주요 API/UseCase를 대상으로 했다. 모든 소스 파일·상태·기기를 전수 검증한 결과가 아니며 새 실행·빌드·APK·운영 시험도 하지 않았다. Unity·영상 편집은 범위 밖이다.

## 2. 목표 정보 구조

```text
플랫폼 홈 · 운영 요약
├─ 참여·활동 → 분야별 집계와 기준 → 동의한 활동자 소개
├─ 후원·운영비 → 후원 입금 / 반환 / 비용 충당 내역
├─ 업무 현황 → 화물 / 음식 / 창고·생활별 현황
├─ 성과·분배 → 공개 가능한 확정 집계와 근거
├─ 도움·교육 → 질문·도움 / 검토된 교육 과정
└─ 내 업무 시작
   ├─ 화물: 화주 / 기사 / 관리자
   ├─ 음식: 주문자 / 음식점 / 기사 / 관리자
   └─ 생활 / 창고

권한이 필요한 내역
└─ 로그인·기존 역할 확인 → 내/담당 목록 → 선택한 한 건 → 기존 상태별 업무
```

일반적인 이동은 **운영 요약 → 선택 분야의 내역 → 한 건 상세 → 필요한 업무 처리**다. 같은 질문의 목록과 상세는 기존 화면의 선택 상태로 구성할 수도 있어 물리 페이지4개를 모든 역할에 강제하지 않는다. 관계 다이어그램은 원장 연결을 이해하는 데 도움이 되는 곳에서 기존 진입을 재사용한다.

공개 홈은 [기존 3단계 내비게이션](../../../../Architecture/ThreeStageClientNavigation.md) 바깥의 공통 셸 문맥이다. 운행 중 기사·진행 중 작업·알림의 기존 직접 진입은 해당 업무로 이어진다. 매번 홈이나 현황을 거치게 해 필요한 행동을 늦추지 않는다. 역할의 지도 중심 수행 화면은 유지한다.

### 요약이 소유할 정보

| 분야 | 홈의 짧은 요약 | 선택 후의 세부 내역 | 현재 준비 상태 |
| --- | --- | --- | --- |
| 참여·활동 | 확인된 완료 기록·역할별 참여 계정 | 집계 기간·업무 범위·포함/제외 기준. 개인 소개는 별도 공개 동의가 있는 항목만 | r10 화물 누적 집계만 연결됨. 개인 순위/품질 집계는 r11 설계 |
| 후원·운영비 | 확인된 후원 입금·후원 충당 지출·집계 잔액 | 비식별 입금/반환/서버·DB 등 비용 충당 내역 | r11 설계. 수납·실입금·충당 공개 정본 미연결 |
| 업무 현황 | 공개가 정해진 분야별 운영 집계 | 공개 집계 기준 또는 로그인 후 내/담당 상태별 목록 | 역할별 작업 목록은 있으나 플랫폼 공개 집계와 동일하지 않음 |
| 성과·분배 | 확정 이익·실제 공동분배 지급액 | 공개 가능한 확인 근거. 개인별 보수·입금/지급은 본인/관리자 내역 | r10 금액null. 기존 정산·재무 전문 API는 권한·Simulation 경계가 있음 |
| 도움·교육 | 공개 가능한 활동 안내·과정 정보 | 기존 질문·도움, 동의한 참여자 소개, 검토된 과정 | 질문 게시판과 교육 API는 있음. 전용 물류 교육 화면·강사 검토는 별도 준비 |

홈에 모든 원장·순위표·입력 양식·전체 주문을 나열하지 않는다. 홈의 수치/요약은 명확한 분야 제목과 `자세히` 진입을 가지며, 이용 불가한 기능을 작동하는 링크처럼 표시하지 않는다. 실제 공개된 정보가 없는 분야는 미집계/준비 상태를 설명하고 기존 업무 진입은 유지한다.

## 3. 공개·본인·관리자의 깊이를 구분

| 범위 | 볼 수 있는 세부 정보 | 연결 원칙 |
| --- | --- | --- |
| 공개 | 공개 집계의 기간·기준·비식별 근거, r11에서 정한 공개 이력·동의한 소개 | 공개 전용 최소 응답 사용. 관리자 DTO나 전체 개별 거래를 전달하지 않음 |
| 본인/현재 당사자 | 내 의뢰·주문·수행·보수·문제 내역 | 로그인 뒤 서버가 현재 당사자를 다시 확인하고 기존 전문 화면으로 인계 |
| 기존 관리자/담당자 | 담당 업무의 진행·정체·사건·재무·지급 기록 | 화물/음식 업무 격리와 기존 역할/기능 경계 유지. 새 관리자 권한을 만들지 않음 |

공개 ‘전체4건’에서 본인 목록의 ‘내1건’으로 들어갔으면 범위가 바뀌었음을 표시한다. 공개 전체 숫자가 개인 전체 거래를 열람할 권리를 뜻하지 않는다. 개인의 연락처·고객 주소·위치·결제키·계좌·증빙 원문을 공개 요약이나 URL에 넣지 않는다. 상담/교육 소개는 r11의 별도 동의·검토를 따른다.

## 5. 수치와 내역을 일치시키는 기준

1. **같은 정의:** 요약과 목록은 같은 업무·단계·기간·권한·제외 기준을 소비한다. r10의 하차 완료 기록, 화주 수령 확인, 정산 승인, 입금 진술, 실송금은 각각 구분한다. 기사 월정산의 이용료 납부를 기사 수입으로 표시하지 않는다.
2. **집계 기간:** 완료·후원 등의 전체 누적과 ‘지금 대기/진행 중’의 현재 상태를 구분한다. 현재 업무 카드는 별도 기준 시각을 표시한다. 주간·월간 자료를 누적 합계로 재명명하지 않는다.
3. **부분 목록:** 최근50건·200건·공정별 첫 페이지는 전체 건수가 아니다. 서버의 정확한 TotalCount/별도 집계를 재사용하거나, 현재 페이지임을 표시한다. 정보 미확보는0이 아니다. 200건 상한이나 HasMore를 확인하지 않고 누적 완료/없음을 결론내리지 않는다.
4. **시각과 변경:** 조회 시각은 과거 고정 snapshot의 보증이 아니다. 상세 진입 시 원장 revision이 달라졌으면 최신 상태임을 알린다. 카드별 집계 시각이 다르면 가장 최근 시각 하나로 모두 새 자료인 것처럼 표시하지 않는다.
5. **출처와 원장:** 기존 주문 원장은 업무 이유와 하위 원장 참조를 보유하고, 각 전문 원장이 상태·금액을 결정한다. 요약용 새 원장/DB를 복제하지 않고 권한에 맞는 최소 읽기 투영을 둔다. 연결 근거 없는 ID나 하위 완료 상태를 추정하지 않는다.

제안하는 공통 메타데이터는 지표 키, 업무 범위, 기간 종류/범위, 공개 범위, 집계 시각·출처 판본, 집계 상태와 숫자의 단위다. 명칭과 저장 방식은 구현 전에 기존 계약을 재검토한다. 이는 신규 DTO 구현 완료를 뜻하지 않는다. 화면에는 이해에 필요한 기간·기준·상태만 표시한다.

## 6. 조회와 내비게이션의 실제 책임 분리

표시를 접었다는 이유만으로 요약 조회가 된 것은 아니다. 다음 두 곳은 조회 내용 자체를 분리할 대상이다.

- `NeighborhoodSettlementUseCase.Read.cs`의 `MySummaryAsync`는 약정·판본 전체를 읽은 뒤 각 `GetAsync`로 상세까지 조립한다. 본인 목록의 최소 투영과 페이지 조회를 먼저 제공하고 선택된 약정만 기존 상세로 읽는 조정이 필요하다. 기존 당사자 필터·기능 옵션·Simulation 경계를 유지한다.
- 운영 재무 사건 목록은 관리계정 전기목록을 함께 적재한다. 목록은 사건 요약과 페이지/TotalCount, 선택한 사건은 상세 원장으로 구분할 수 있다. **현재 사건 단건 GET은 확인되지 않았으므로 새 상세 API는 후속 구현 대상**이다.

지원 사건의 증거 GET은 열람 감사기록을 남긴다. 요약을 펼치는 것만으로 이를 자동 미리 읽지 않고 사용자가 명시적으로 증거를 여는 행동을 유지한다. 상세 진입이 승인·지급·사건 종결을 자동 실행해서도 안 된다.

### 이동·복귀 문맥

`역할 + 업무 + 공개/본인/관리 범위 + 기간 + 상태 필터 + 페이지/cursor + 선택 대상 + 허용된 복귀 경로`를 유지한다. 현재 selected·관리자 business·일부 기사 내역 날짜 복귀는 재사용한다. 음식 행동 페이지의 고정 지도 복귀와 창고/화물 작업의 지도 기본 복귀에는 새 목록의 기간·상태·페이지 문맥을 보완한다.

이미 있는 `PageNavigationContext`의 from/focus·내부 경로 검사, `ShipperRequestDetailNavigationContext`의 의뢰 상세 책임별 왕복, `CommunityBoardNavigationContext`의 게시판·검색·페이지·필터·지역을 우선 재사용한다. 분야별 조립기로 연결하고 같은 역할의 전역 문맥 클래스를 중복 신설하지 않는다. `RoleWorkspaceNavigation`/`RoleWorkspaceState`에 아직 없는 기간·목록 조건만 좁게 확장한다.

복귀 URL은 기존 내부 허용 경로와 navigation 조립기를 확장하며 임의 외부 경로를 받지 않는다. 로그인 성공은 원래 화면 복귀이며 자동 업무 실행이 아니다. 역할/업무 전환은 이전 요청 결과가 새 화면을 덮지 않게 기존 격리와 취소 처리를 유지한다.

URL의 business·mode·return은 탐색 문맥일 뿐 서버의 실제 역할·실행 모드·외부 효과를 변경하는 권한이 아니다.

## 7. 페이지 책임 카드와 실패·복구

| 화면 | 소유하는 한 가지 결과 | 기본 정보/주 행동 | 다른 책임으로 인계 |
| --- | --- | --- | --- |
| 플랫폼 홈 | 전체 운영의 현재 공개 현황을 이해하고 분야를 선택 | 짧은 요약·기준 시각·상세 진입 | 긴 원장·개별 처리·내/관리자 업무 |
| 분야 내역 | 선택한 수치의 범위와 근거를 확인 | 기간·업무·집계 근거와 허용된 목록, 한 건 선택 | 권한이 필요한 원문·업무 명령 |
| 역할별 목록 | 내/담당 업무를 찾아 선택 | 상태·기한·필요 금액 등 핵심 필드와 필터/페이지 | 독립 입력·정산·증거·문제 처리 |
| 선택 상세/수행 | 한 건의 현재 단계와 다음 행동을 처리 | 상태별 필요한 정보·허용된 주 행동·복귀 | 실제 정산·송금·다른 전문 원장의 상태 확정 |

미집계·실제0·조회 실패를 구분하며 한 분야 조회 실패가 홈·기존 업무 진입 전체를 막지 않게 한다. 상세 실패는 짧은 업무 맥락 안내와 재조회/목록 복귀를 제공한다. 권한 없음·기능 비활성·보존 기간 종료를 빈 목록이나0으로 바꾸지 않는다. 불명확한 처리 결과는 기존 요청 ID·입력을 보존해 정본을 재조회한다.

모바일은 요약 카드→목록→선택 정보에 집중하고, 화주·관리자의 데스크톱은 같은 목적의 표·필터·선택 상세를 넓게 배치할 수 있다. 독립 업무를 같은 페이지에 숨겨두는 방식은 [기존 페이지 책임 기준](../../../../Architecture/WholeRoadmapPagePrinciple.md)으로 다시 검토한다.

## 9. 구현 시 검증할 사례

- 요약4건이 같은 기준의 공개 근거4건/집계로 연결되는지, 내 목록으로 바뀌면 범위를 명시하는지.
- 51/201건 및 창고 공정별 다음 페이지가 빠지지 않고 현재 페이지 수와 전체 집계를 구분하는지.
- 로그인 취소/성공, 업무 전환, 목록→상세→작업→복귀에서 기간·필터·페이지·선택이 유지되는지.
- 직접 주소 입력·타인 식별자·관리자 URL을 통해 비공개 원문에 접근할 수 없는지.
- 요약은 정상이지만 상세 조회 시 상태가 바뀐 경우와 데이터 삭제·보존 종료·권한 철회가 구분되는지.
- 미집계·성공한0·부분 조회·오류·오래된 집계와 재시도가 실제 화면에서 구별되는지.
- 요약/목록을 여는 것만으로 증거 감사 조회·승인·지급·고객 알림 등 의도하지 않은 동작이 생기지 않는지.
- 공통 UI·서버 시험, 실제 브라우저/앱 렌더, APK·물리 기기·실제 운영 결과를 각각 기록하는지.
