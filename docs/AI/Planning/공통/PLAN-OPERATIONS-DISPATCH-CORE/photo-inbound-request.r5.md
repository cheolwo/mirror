## 한 가지 결과와 인계

처음 신청 화면은 사진 촬영·선택과 `가 입고 신청`만으로 본인 전용 준비 기록을 만든다. 이름은 선택이며 창고·공급처·계약·수량은 이때 요구하지 않는다. 사진과 이름을 상품·공급처나 실제 반입의 확인으로 추정하지 않는다. 기존 긴 신청서는 `직접 입력` 또는 가 신청의 `입고 정보 입력`으로 유지한다. 지도 경유의 기존 개인정보 동의와 가원장 연결은 보존한다.

```text
사진 촬영·선택 → 가 입고 신청
├─ 접수 확인 대기 → 같은 요청 번호로 결과 확인
└─ 본인 사진 신청 확인
   ├─ 이름 붙이기·나중에 이어서 입력
   └─ 입고 정보 입력 → 기존 동의·창고 권한·필수 조건 검사
      → 정식 입고 신청 한 건 연결 → 기존 수령·검수·재고 처리
```

## 원장과 소유권

새 준비 모델은 작성자·요청 GUID·선택 이름·개정·비공개 사진의 저장 참조/해시와 날짜만 소유한다. 재고·계약·운송·정산 상태를 복제하지 않는다. 기존 현장 임시 입고를 완화하거나 일반 입고에 미정 창고/가짜 공급처를 넣지 않는다. 사진은 기존 `IObjectStorageService`의 비공개 저장과 재다운로드 대조를 재사용하며 클라이언트에 버킷/객체 경로·공개 URL을 받거나 노출하지 않는다. 사진 응답은 인증된 소유자에게만 제공하며 원본 파일명은 보관하지 않는다.

일반 입고에 선택적 사진 신청 ID를 연결하고 DB의 한 대 일 유일키로 한 사진 신청이 여러 입고로 전환되지 않게 한다. 연결 시 작성자·미연결 상태를 검사하고 사진 신청 개정 갱신과 실제 입고 생성을 같은 저장에서 처리한다. 전환의 `ClientRequestId`는 사진 신청 GUID를 사용해 r4의 중복 방지·응답 유실 조회를 재사용한다. 기존 사진 없는 요청의 지문은 바꾸지 않는다. 실제 입고/재고·보관료는 기존 별도 조건과 완료 단계가 소유한다.

사진 접수는 같은 ID·같은 사진/최초 이름이면 같은 결과를 확인하고 다르면 충돌한다. 수정 이름은 revision 비교로 보호한다. 업로드 실패·저장 실패를 접수 성공으로 표시하지 않으며, 응답 유실 시 자동 POST 없이 같은 ID를 조회한다. 사진 원본/Base64는 일반 복구 기록에 넣지 않는다. 계정·세션·서버 전환과 늦은 응답은 현재 화면을 덮지 않는다. 사진은 JPEG/PNG 한 장, 최대5MB이며 촬영/선택 취소는 기존 선택을 유지한다.

같은 OS·단계의 명시적 미적용 거절만 별도 target 표식으로 보호 저장·재조회한 뒤 정리한다. 삭제 장애 뒤 재진입은 이 거절 표식의 조건부 삭제/부재 확인을 재개한다. 일반 결과 없음404나 거절 표식 저장 실패를 미적용으로 추정하지 않는다. marker에는 사진·이름·원문 오류를 넣지 않는다.

## 검증과 한계

사진만으로 저장/재조회·다른 작성자 차단·파일 유형/크기·저장 대조 실패·응답 유실·이름 동시 수정·동일 신청 1건 연결과 재고/정산 미생성을 격리 시험한다. 공통 UI의 빈 화면·사진 선택·확인 대기·저장 후 이름/보완·연결 완료를 모바일/PC로 렌더하고 소비 솔루션 빌드·scoped Fast/Task를 수행한다. 기존 공개 기능 플래그·역할·운영 활성화·실 DB migration·APK 설치·커밋/푸시는 바꾸지 않는다. 실제 카메라·휴대폰 재시작·운영은 별도 증거다.
