# 음식 주문의 짧은 수집과 배차 시점 판단 r52

상태: `Approved / ImplementationInProgress / LocalOnly`. 사용자가 2026-10-11 현재 스레드에서 주문을 잠시 모아 기사 상황과 조합 가능성을 고려하고, 바로 배차할지 기다릴지 판단하도록 구현을 요청했다. 기존 r50 조합 검토와 r51 학습 후보를 보존한다.

## 범위와 책임

- 서버 순수 정책이 `Collect`, `DispatchNow`, `ExistingFlow`와 고정 대기 기한을 계산한다. AI는 서버가 허용한 행동만 선택하며, 서버가 현재 시각과 원장을 다시 확인한다.
- 음식 배차의 첫 추천 전에만 적용한다. 이미 제안·수락한 업무, 거절 뒤 재추천, 화물·생활 배송·마트 선행 작업은 새 수집 대기를 적용하지 않는다.
- `FoodDispatchTiming:Enabled`와 별도의 `FoodDispatchTimingOllama:Enabled`는 기본 OFF다. 로컬 시험에서 명시적으로 켜서 검증하며 운영 설정·실제 고객·외부 알림·모델 가중치·APK·Unity·Azure는 바꾸지 않는다.
- 실제 다건 원자적 수락·여러 주문의 공동 예약·전역 최적화는 이번 범위가 아니다. 현재 단건/2건 조합의 기하 검토는 유망 후보라는 뜻이며 적재·모든 약속 시간의 검증으로 승격하지 않는다. 기한이 끝나면 기존 한 건씩의 후보 선정·요금 동결·추천 흐름으로 진행한다.

## 결정 순서

1. 비대상·기존 제안·재추천은 기존 흐름을 유지한다.
2. 잘못되거나 오래된 수요·기사 여력·위치/권역·주문 조회, 조회 한도 초과 또는 읽기 실패가 있으면 기다리지 않고 기존 배차 관문으로 진행한다. 모르는 값은 0으로 인증하지 않는다.
3. 최대 대기 기한 또는 확인된 조기 마감이 임박하거나 지연 위험이 있으면 즉시 기존 배차를 진행한다.
4. 같은 권역/인접권에서 유망 조합이 보이거나 호환 후보 수가 기준에 도달하면 일찍 진행한다. 호환은 근접 픽업/전달의 기하 후보이며 실도로·시간/적재 약속은 후속 기존 관문이 소유한다.
5. 신규 주문이 더 들어올 근거가 없거나 제안 허용 기사가 없으면 수집 대기를 하지 않는다.
6. 나머지 경우만 짧게 수집한다. 최초 큐의 `CreatedAt`을 기준으로 하며 새 주문 유입·반복 평가·`UpdatedAt` 변경은 이 기한을 연장하지 못한다.

초기 시험 설정은 수집 30초·절대 최대 60초·호환 후보 2건·마감 여유 15초·자료 최대 경과 15초다. 운영 최적값 또는 합의된 서비스 SLA가 아니라 관리 가능한 시험 기본값이다. 수집 시간은 최대 대기보다 길 수 없고 AI가 임의 시간을 반환하지 않는다. 스캐너의 실행 간격 때문에 실제 재평가는 기한 이후 다음 스캔일 수 있으며 기한 도달 이후 새 수집 연장은 허용하지 않는다. CPU 모델 지연은 남은 판단 시간 안에서 제한하고 실패/지연에는 즉시 기존 흐름으로 복귀한다.

확인된 픽업/조리 마감이 없으면 이를 생성하지 않는다. 최초 큐 시각에 따른 짧은 상한만 적용하며 실제 도착·모든 약속 시간의 검증을 주장하지 않는다. 기사 배정 후 조리를 시작하는 기존 원칙 때문에 수집은 조리 시작을 늦출 수 있다. 시험에서 기다린 시간과 사유를 함께 확인한다.

## 입력과 연결

- `FoodDispatchTimingInput`: 현재/최초 큐/관측 시각, 선택적인 확인된 배차 마감, 대상/기존 제안/재추천, 수요·여력 확인 여부, 지연 위험, 유망 조합 여부, 대기/호환 주문 수, 제안 허용 기사 수, 관측 기반 신규 주문 추정.
- 수요·기사 상태는 기존 수요 참여 서비스를 재사용한다. 신선도와 제안 허용을 보존한다. 주문 풀은 음식·미배정·동일/인접 권역·최대 조회 한도 안에서만 읽는다.
- 큐 전환 서비스의 첫 후보 선정과 직접 추천 시작에도 같은 수집 판단을 적용한다. 판단 뒤 원장 판본을 재확인하고 기존 제안·취소가 발생했으면 오래된 판단을 적용하지 않는다. `Collect`는 새 제안·요금 동결·알림을 만들지 않는다.
- 구조화한 사유·정책 판본·대기 기한을 기존 결과/안전한 로그로 반환한다. 원문 주소·기사 이름·개인정보를 모델이나 새 로그에 넣지 않는다.

## 학습 후보와 한계

기존 r50의 504건·339지점은 익명 출처 연결에만 재사용한다. 주문 도착·기사 상황·대기 시간은 합성이다. 현재 순수 정책을 호출해 수집/조합 발견/시간 만료/긴급/희박 수요/자료 미확인/기사 없음/재추천 사례를 만든다. 모델 입력은 상대 시간·수치·고정 코드만 포함한다. 지점별 train/validation/test를 분리하고 동일 입력은 전부 격리한다. 모든 답안은 `Pending / CurrentPolicyDraft`, ready는 빈 상태로 두며 사람 승인·실제 학습·운영 효과로 표현하지 않는다.

기사별 평균 단가 4,000원·종합 가점은 선행 대화의 방향이며 아직 이 정책의 최적화 목적이나 학습 성공으로 구현하지 않는다. 이번에는 **배차 시점**의 판단을 연결한다. 실제 도로 이동·예상 지급액·평균 단가·시간당 수입을 함께 최적화하는 후속 설계와 구분한다.

## 로컬 검증

- 정책 경계: 기본 OFF, 30/60초, 마감 여유, 새로운 주문이 기한을 연장하지 않음, 0명/희박/미확인/만료 자료, 유망 조합 조기 진행, 기존 제안·재추천 제외.
- 서비스/AI: 익명 입력·허용 행동·중복 JSON/허위 행동·시간 초과/잘못된 응답·취소·판단 중 기한 도달·조회 실패/한도 초과·현재 원장 변경.
- 격리 SQLite 전환: 수집 중 추천/요금/알림 0, 기한 또는 조합 조건 충족 뒤 기존 추천, 재호출 중복 없음, 직접 추천에서 우회 불가. 화물/마트는 기존 흐름 유지.
- 학습 후보: 출처/도구/정책 해시·엄격 필드·지점 분리·동일 입력 격리·준비 답안 0·개인정보 없음·결정적 재생성.
- `validate-changes.ps1 -Paths`의 Fast와 Task로 이번 범위만 검증한다. 모델 실제 호출·외부 FCM·휴대폰·운영 DB/배포·수입 개선 검증은 수행하지 않는다.
