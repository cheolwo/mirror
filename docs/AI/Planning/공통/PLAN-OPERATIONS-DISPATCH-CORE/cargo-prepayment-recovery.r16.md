# 화물 선결제 접수·동일 업무 복구 r16

상태: `Approved / CompletedLocalValidation / ActualPGCheckoutPending / NativeRecoveryPending / OperationalDisabled`. 승인: 2026-10-22 사용자 후속 요청(우선순위 1·2).

## 확정 범위

- 신규 기본 의뢰는 결제 전에는 접수 준비로 표시한다. 서버가 결제를 확인한 뒤 정식 접수·배차 대기로 이어진다.
- 결제와 기사 수락이 서로 기다리는 r15 F1 경로를 기존 선결제 옵션·결제 준비/승인/Outbox에 연결한다. 상차 뒤 결제를 신규 기본으로 사용하지 않는다.
- 수납과 하차/인수·지급 준비·주간 정산·실지급은 구분한다. 하차만으로 송금하지 않으며 기존 지급 자격·신고 보류·운영 기본 OFF를 유지한다.
- F2 통합 기사 입력 시간초과와 F3 Web 의뢰/계정 전환을 보완한다. 결과 미확정이면 같은 업무 결과부터 조회한다. 자동 POST, 미조회 결과의 성공 처리, 다른 계정/서버의 복구 기록 재사용은 하지 않는다.
- 로컬 Simulation/FakePG와 실제 PG를 구분한다. 실제 결제·자원 생성·배포·휴대폰 설치·commit/push는 이번 승인에 자동 포함하지 않는다.

## 페이지 책임

기존 화주 접수 확인은 화주가 확정한 운송 조건으로 접수 준비 기록을 생성하고 기존 결제 route로 인계한다. 기존 결제 화면은 동일 의뢰의 금액·결제 상태 확인과 사용자 결제 선택만 소유한다. 기존 기사 수락/상하차 입력 화면은 현재 업무 처리와 결과 확인을 소유한다. 기존 Web 상세 화면은 선택 의뢰와 현재 계정의 최신 조회만 표시한다. 새 주문/정산 원장이나 별도 앱은 만들지 않는다.

## 분담과 수정 경계

- root: 기존 선결제 정책/handler·계약·화주 결제/작성 route와 서비스·공통 표시, 직접 회귀 및 승인/변경/현재 작업 기록.
- F2 담당: `CargoInputLifetime.cs`, `CargoOfferActionViewModel.cs`, `CargoTransportActionViewModel.cs`, 신규 `CargoInputRecovery.cs`, 해당 두 입력 Screen, `MauiWorkflowRecoveryStore.cs`, `CargoInputTimeoutRecoveryR16Tests.cs`.
- F3 담당: Web `ShipperRequestDetailPageViewModel.cs`, `WebShipperDetailLifetimeR16Tests.cs`. root는 완료 인계 후에만 같은 VM을 변경한다.
- 접수 투영/기존 큐의 추천 금지와 신규 생성 입력의 결제 결과 주장 차단을 서버 F1 담당이 소유한다. root는 본인 전용 선결제 상태 조회와 기존 FakePG POST의 명시적인 국내운송 기능 분류를 연결한다. 다른 미분류 결제 명령을 일괄 개방하지 않는다.
- 기존 dirty 변경·원장/계약 ID·역할·기능 경계는 보존한다. 담당 외 파일 변경이 필요하면 정확한 경로를 먼저 조율한다.

## 완료 기준

1. 새 선결제 의뢰가 결제 전 추천/수락되지 않으며 결제 준비·확인 후 같은 의뢰만 배차 대기에 진입한다. 취소·금액 변경·중복/지연 승인도 기존 guard로 검사한다.
2. 모바일/Web 결제 전 안내가 접수 완료나 배차 진행으로 과장되지 않고, 실패/취소/미확정에서 같은 의뢰로 복귀한다.
3. 수락·상하차 시간초과 후 중복 제출을 차단하고 재실행 후 같은 운송의 결과를 재조회한다. 실제 화면 이탈 취소는 오류로 오인하지 않는다.
4. 느린 A 응답이 B 선택·계정 변경 뒤 화면을 덮지 않는다. 이전 finally가 최신 busy 상태를 해제하지 않는다.
5. 변경별 회귀, 소비 client/server 빌드, Fast/Task와 가능한 공통 화면 렌더를 확인하고 실제 기기·실금융·외부 운영 미검증은 따로 남긴다.

선행: [r15 검토](cargo-three-role-readiness.review.r15.md). [구현 결과·시험·화면](../../../../Changes/2026-10-22-cargo-prepayment-recovery-r16.md): Fast362·Task14,893통과/환경16미실행과 공통 화면 검증. 실제 PG/송금·제품 HTTP 종단간·단말 재실행 검증은 미완료다.

## 실증 범위

로컬에서는 명시적으로 허용한 Simulation 선결제로 접수 준비→수납 확인→배차 인계를 검증한다. 실제 토스 결제창과 앱 복귀·상용 수납/자금 보관·실지급은 아직 연결/실증하지 않았다. 기존 준비/승인 API와 PG 정책이 있다는 사실을 실제 결제 서비스 완료로 표시하지 않는다. 이는 현재 구현 결과의 한계이며 사용자의 최종 운영 목표를 축소하거나 완성으로 간주하는 결정이 아니다.
