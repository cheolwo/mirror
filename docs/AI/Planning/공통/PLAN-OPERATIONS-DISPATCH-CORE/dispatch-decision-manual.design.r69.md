# 퀵·화물 AI 배차 판단 매뉴얼 문답 r69

- 기획 ID: `PLAN-OPERATIONS-DISPATCH-CORE`, 판본 `dispatch-core.r69`, 2026-10-19.
- 상태: `CurrentFlowReviewed / UrgentDeadlineBypassAccepted / PromiseFirstOptimizationAccepted / DriverSupportRequestDirectionAccepted / OperationsCloseoutPrioritized / FeatureExpansionDeferred / PolicyQuestionsDeferred / ImplementationNotRequested`.
- 최신 사용자 요청: 기능과 세부 정책을 계속 늘리기보다 주문 한 건이 들어와 마무리되는 과정을 갖추고, 실제 운영에서 얻는 경험으로 보완한다. 이전 단계별 문답은 아래 이력에 보존한다.
- 이번 범위는 현재 소스·기획 대조와 마감 범위 정리다. 새 정책 구현·시험 데이터 승인·모델 호출/학습·서버/DB·기기 조작·설정 변경은 수행하지 않는다.

## 현 우선순위 — 주문 한 건의 마감과 운영 경험

2026-10-19 사용자는 다른 논의를 잠시 두고, 필요한 주문 처리 과정을 마무리하여 실제로 써 보면서 쌓아 가는 방향을 요청했다. **새 기능·새 역할·세부 배차 정책의 추가를 보류하고, 기존 퀵·화물 한 건의 시작과 끝을 닫는 데 집중한다.** 이는 기존 기능의 일괄 비활성화·코드 삭제나 운영 설정 변경을 뜻하지 않는다. 음식·창고 등 기존 업무는 보존하며 현재 대표 검증 한 건을 좁힌다.

마감할 업무 흐름은 다음과 같다.

```text
주문 접수·접수 결과 확인
└─ 배차 대기 → 조건에 맞는 기사에게 추천
   └─ 기사에게 알림 → 조건·기사 보수 확인 → 수락
      └─ 픽업 도착 → 필요한 증빙 → 픽업 완료
         └─ 전달 도착 → 필요한 증빙 → 전달 완료
            ├─ 주문자·기사의 같은 완료 결과 재조회
            └─ 보수 내역·정산 대상 확인
```

전달 완료·주문자 수령·정산 대상·실제 입금은 기존대로 별개다. 결제나 송금을 이번 마감 때문에 완료된 것으로 표시하지 않는다. 접수 응답이 끊김·추천 만료/중복 수락·증빙 업로드 실패처럼 이 한 건을 막을 수 있는 예외는 기존 복구 경로로 재개되는지 확인한다. 예외마다 새 기능을 늘리기보다 현재 상태·실패 이유·다음 행동이 분명한지를 본다.

현재 확인된 마감 순서는 다음과 같다.

1. **수락 화면의 실제 차단부터 해결 대상으로 삼는다.** r114의 시간대 없는 UTC 의미 응답을 한국 시간대에서 9시간 일찍 만료로 해석하는 문제를 확인했다. 추천 유지시간을 늘리거나 만료 검사를 생략하는 방법으로 숨기지 않는다.
2. **기사 보수의 정본을 화면과 맞춘다.** 일반 화물에서는 소형 배송 전용 `Pricing`이 없을 수 있다. 고객 청구액을 기사 보수로 대체하지 않고, 수락 전 약정 기사액과 수락 후 동결 기사액을 구분해 같은 업무에서 일관되게 확인한다. 보수 미표시와 수락 차단은 별개 결함이다.
3. **그다음 같은 한 건을 실제 공통 앱의 수락부터 완료 조회까지 다시 검증한다.** 직접 API 수락 성공을 화면 수락 성공으로 바꾸지 않는다. r114의 이전 실패·모델 거절 기록은 보존하고 새 검증 판본으로 비교한다.
4. **외부 운영 준비와 실제 휴대폰 검증은 별도 완료 관문으로 둔다.** 현재는 로컬 검증 범위를 유지한다. r114의 readiness 503·미적용 migration, 실제 푸시 수신/알림음·기기 사진·통신은 아직 남은 항목이며 문서 정리로 통과 처리하지 않는다.

이 마감 방향은 수용했지만, 이번 문답에서 제품 수정·실제 배포·금전 처리·운영 기능 활성화를 실행한 것은 아니다. 운영 경험을 쌓는 단계에서는 한 건마다 막힌 상태·복구 행동·결과만 남겨 다음 보완의 근거로 사용하며, 사례를 자동 학습 정답이나 승인된 정책으로 바꾸지 않는다.

추가 정책 질문은 지금 이어가지 않는다. 아래의 대기 기록 질문, 지원 요청 수신 범위, 세부 가중치·학습 전략은 **미답변 그대로 보류**하고, 실제 업무를 마무리하는 데 필요해진 때 다시 다룬다.

## 문답 방법

한 단계 설명 → 작은 가상 사례 → 사용자 결정 → 매뉴얼의 확정/미정 기록 순서로 이어간다. 모든 단계를 한꺼번에 답하도록 요구하지 않는다. 일반적인 방향 동의를 임계값·요금·학습 정답·운영 활성화 승인으로 확대하지 않는다.

각 판단은 **필요한 정보 / 반드시 지킬 조건 / 비교 기준 / 선택 또는 보류 / 판단 근거 / 다시 확인할 시점**으로 정리한다. 입력 관측과 판본·선택 결과·근거 코드로 설명하며, 모델의 사적인 내부 사고 과정은 기록 대상으로 삼지 않는다.

## 유지하는 기존 결정과 구현 차이

- [기사 관점 검토 r57](driver-dispatch-structure.review.r57.md): 현재 대기 가점은 실제 대기분 순서와 다르며 추천 기록만으로 대기 보정 기준이 초기화되는 공백이 있다. 대기 시작점과 추천만 받은 경우의 보존 여부는 아직 미정이다.
- [후속 콜 r64](quick-driver-continuity.implementation.r64.md): 수행 중 기사에게는 기존 전체 업무 끝점·종료 예상과 현재 근거를 확인해야 한다. 기능 존재·옵션 활성·실제 도로/단말 검증은 구분한다.
- [실제 모델·API 검증 r68](cargo-ai-device-verification.implementation.r68.md): 3회 중 2회는 이유 불일치로 추천하지 않았고 1회는 적용·API 인수완료까지 확인했다. 모델 성능·공정성 개선의 입증이나 실제 휴대폰 검증은 아니다. 일반 화물 보수 표시와 추천 만료 시간대 문제도 그대로 남아 있다.
- 평균 4,000원 지향, 플랫폼 비용·손익, 권역 복귀, 신규 기사 유입 등은 기존 기획과 연결해 후속 문답으로 다룬다. 이번 매뉴얼 시작 요청만으로 강제 단가·상한·비율·가중치를 새로 확정하지 않는다.

## 첫 문답 — 약속시간을 위한 수집 대기 예외

`quick-dispatch-manual-urgent-bypass-collection / Answered / UrgentDeadlineBypassAccepted`.

기존 질문은 시간 여유 주문을 잠깐 모아 조합하되 확인된 약속시간 때문에 지금 추천해야 하면 수집 대기를 건너뛸지였다. 사용자는 2026-10-19 **“약속 시간 지키려면 바로 배차해 줘야지.”**라고 답했다.

따라서 **확인된 약속시간을 지키는 데 지금 추천이 필요하고 현재 적합 후보가 있으면, 더 좋은 조합을 기다리는 대기보다 즉시 추천을 우선한다.** 기사 수행 가능성·기존 업무 약속·차량/적재·현재 원장 재검사는 유지한다. 기사에게 제안을 보내는 것과 기사 수락 후 배정 확정은 구분한다.

이 답변은 시간 여유 계산의 ETA·상하차 체류·오차 여유 수치, ‘긴급’ 표시 주체, 일반 주문 수집 상한·재평가 시점, 적합 후보 없음 대응, 모델 호출 지연/장애 시 대체 경로를 함께 확정하지 않는다. 실제 배차 정책 구현·운영 활성화·시간 약속 자동 연장·요금 변경도 수행하지 않았다.

## 두 번째 문답 — 기사 부족 시 지원 요청과 약속 안에서의 조합

`quick-dispatch-manual-no-feasible-driver-notice-consent / RespondedWithSupportRequestDirection / TimeChangeConsentUnresolved`.

사용자는 기사가 없으면 등록 기사에게 해당 업무를 처리해 달라는 알림을 보낼 수도 있다고 답했다. 또한 조합을 우선하면 플랫폼 이익만 강조할 수 있으므로 **약속시간은 지키되 그 안에서 조합을 잘 만들도록 AI를 학습**시키는 방향을 분명히 했다. 이는 앞선 시간 변경 동의 질문의 전체 수용이 아니라, 기사 부족 대응에 지원 요청이라는 방안을 추가한 답변이다.

기획 방향은 다음과 같다.

1. 확인된 시간 약속을 지킬 수 있는 기사·계획을 먼저 검사한다. 이미 맡은 업무의 약속도 함께 보호한다.
2. 현재 적합 후보가 없으면 등록 기사에게 지원을 요청하는 방안도 사용할 수 있다. 등록 기사 전원에게 무조건 발송하거나 신규 배차 OFF를 우회하는 권한까지 확정한 것은 아니다.
3. 지원 요청 발송·도착·열람·참여 의사·수신 ON·현재 적격성·추천·수락·배정 확정은 별개다. 알림을 보냈다고 기사 확보나 약속 이행이 확정된 것으로 표시하지 않는다.
4. 지원자가 응답하면 현재 일정·위치·차량·적재·수신 조건과 시간 약속을 다시 검사해 기존 추천/수락 절차에 연결하는 방향이다. 휴식·직접 수신 중지·미응답 자동 중지를 알림 발송/열람으로 해제하지 않는다.
5. 그 안에서 기존 장기 대기 우선 방향을 유지하며 조합의 효율을 개선한다. 시간 약속 위반으로 판단된 안을 높은 플랫폼 수익이나 더 많은 묶음이라는 이유로 선택하지 않는다. 공정성·동선·비용 사이의 세부 비교 수치와 순서는 아직 정하지 않았다.

학습·평가용 사례를 만들 때도 이 순서를 반영하는 방향이다. 예를 들어 ‘수익/묶음은 좋아지지만 약속 위반’은 허용안으로 승격하지 않고, ‘약속을 지키는 여러 조합’의 비교나 ‘가능 후보가 없어 지원 요청이 필요한 경우’를 별도 상황으로 다룬다. 미확인 ETA를 약속 준수로 채우거나 알림 성공을 배차 성공으로 라벨링하지 않는다. 이번 답변으로 학습자료 생성/승인·모델 가중치 학습·지원 요청 기능 구현·실제 알림 발송을 수행하지 않았다. 현재 r114 선택기의 행동은 후보 선택/보류이며 지원 요청 행동이 구현됐다고 보고하지 않는다.

## 이전 문답 위치 — 미답변 보존

- **확정:** 약속 준수 우선·그 범위 안의 조합 개선, 필요한 즉시 추천, 기사 부족 시 등록 기사에게 지원을 요청할 수 있다는 방향. r56 장기 대기 우선과 현재 역할/원장 책임은 유지한다.
- **미정:** 지원 요청 수신 범위·별도 동의·횟수/시간대·탐색 범위, 끝내 기사 확보가 안 된 경우의 주문자 안내·시간 변경 동의, 시간 여유 계산·수집 상한·실제 대기 시계·보조 목표의 세부 기준과 운영 적용.
- **지원 알림의 기존 질문:** `quick-dispatch-manual-support-off-duty-opt-in / Asked / Unanswered / DeferredForAlgorithmReview`.

> 신규 배차를 꺼 둔 기사님에게도, 별도로 ‘지원 요청 알림 받기’에 동의한 경우에는 도움 요청을 보내도 될까요?

이 질문은 일반 배차 수신과 지원 요청 수신의 의사를 분리할지 다룬다. 답변 전에는 신규 배차 OFF 기사에게 지원 요청을 발송해도 된다고 간주하지 않는다. 지원 요청에 응답했다는 이유로 운행/수신을 자동으로 켜거나 시간을 임의 변경하지 않는다. 다른 관련 당사자의 시간 변경 동의·취소/환불·추가 요금은 후속 문답이며, 무응답을 동의로 취급하지 않는다.

## 이전 문답 재개 — 기사 선택 알고리즘의 대기 기록

사용자는 신뢰 인정의 관계별 주간 상한까지만 우선 정하고 AI 배차 알고리즘 논의를 먼저 이어가도록 요청했다. 따라서 거래 신뢰의 상세 질문과 지원 알림 수신 범위는 미답변 상태로 보존하고, 후보 선택의 핵심인 실제 대기 기록부터 재개한다.

기존 **약속시간·전체 업무 수행 가능성 확인 → 가능한 후보 사이 장기 대기 우선 → 약속 안에서 조합 개선** 방향은 다시 묻지 않는다. 현행 대기 보정점수와 실제 대기분은 다르고, 추천 생성 시 대기 보정 기준을 갱신하는 현재 코드가 이 기획을 보장한다고 보지 않는다.

당시 질문은 r57의 기존 `quick-driver-waiting-preserve-on-offer / Asked / Unanswered`를 재사용했다. 최신 마감 우선 요청에 따라 `DeferredForOperationsCloseout`으로 보류하며 답변된 것으로 해석하지 않는다.

> 기사님이 30분을 기다린 뒤 추천 알림을 받았지만 아직 수락하지 않은 상태라면, 알림이 왔다는 이유만으로 기다린30분을0으로 만들지 않고 기존 대기 기록을 유지하도록 할까요?

이는 **추천이 생성/표시된 시점의 대기 기록 초기화 여부**만 묻는다. 수락·업무 완료 중 언제 초기화할지, 제안 대기 중 시간이 계속 쌓일지, 거절·만료의 책임/불이익과 초기화는 별도 문답이다. 이전 r56의 대기 시작점 질문과 신규 수신 중지/재개 기준을 함께 확정하지 않는다. 실제 모델 학습·배차 코드 변경·서버/기기 실행은 수행하지 않았다.
