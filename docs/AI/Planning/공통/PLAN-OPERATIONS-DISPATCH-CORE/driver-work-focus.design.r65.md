# 기사 업무 집중 기간 기획 r65

- 기획 ID·판본: `PLAN-OPERATIONS-DISPATCH-CORE / dispatch-core.r65`, 2026-10-16.
- 상태: `DirectionAccepted / SwitchingRuleAccepted / PeriodBoundaryAsked / ImplementationPendingPolicy`.
- 사용자 방향: 하루 퀵을 하기로 했으면 퀵에, 음식 배달을 한 주간 하기로 했으면 음식 배달에 집중하도록 시스템이 도와야 한다. 빈번한 업무 전환 때문에 기사 집중과 운영 관리가 어려워지는 것을 줄인다.
- 선행 구현: [퀵 후속 콜 r64](quick-driver-continuity.implementation.r64.md). 현재 업무 유지·후속 콜·수신 중지/재개·응답 유실 복구는 보존한다.
- 이번 범위: 현재 코드 조사와 운영 기준 기획. 제품 코드·DB·기능 플래그·APK·실제 배차·모델·commit/push는 변경하지 않았다. 기간 중 변경은 사용자가 **맡은 업무를 모두 마친 뒤 본인이 변경 가능**을 선택했고, 하루/주간 시간 기준을 다음 질문으로 남겼다.

## 확인된 현재 구조

| 책임 | 현재 코드 | 현재 의미와 공백 |
| --- | --- | --- |

소스 경로: 설정 계약은 `Ssalddel.Contracts/Driver/Settings/`, 프로필·순수 정책은 `Ssalddel.Domain/기사/`, 저장은 `Ssalddel/Application/Driver/Participation/`, 공통 관문은 `Ssalddel/Services/Dispatch/Participation/`이다. 앱 선택과 실제 업무 종류를 같은 것으로 해석하지 않는다.

## 반영할 운영 원칙

1. **가능한 업무와 지금 집중할 업무를 구분한다.** 기사님이 음식·퀵·화물 모두를 할 수 있어도, 선택한 기간에는 그중 한 종류의 신규 배차에 집중한다. 기존 자격·차량·적재 여력을 바꾸거나 특정 업무의 수행 자격을 박탈하는 뜻이 아니다.
2. **AI는 선택된 업무 범위 안에서 조합한다.** 다른 종류의 주문이 많거나 예상 수입이 높아도 AI가 집중 업무를 자동으로 바꾸지 않는다. 같은 종류 안의 후속 콜·묶음·대기 우선·복귀 방향·단가 검토는 기존 엔진을 사용한다.
3. **새 배차와 이미 맡은 업무를 분리한다.** 기간 만료·수신 OFF·선택 변경은 기존 업무를 취소하거나 카드·완료·정산·지급 근거를 숨기지 않는다. 수행 중 A와 이미 수락한 B는 r64의 정본 순서로 계속 처리한다.
4. **서버에서 같은 선택을 확인한다.** 화면 체크만으로 제한하지 않고 후보 탐색·추천 저장/알림·조회·공개 콜 수락·자동 추천 수락에서 같은 집중 업무와 판본을 대조한다. 전문 일정·차량·적재 검사를 생략하지 않는다.
5. **앱 재실행이나 수신 토글은 업무 전환이 아니다.** 같은 계정의 집중 선택은 서버에서 재조회한다. 미응답 중지 뒤 토글 ON은 수신 재개이며, 집중 종류·기간을 임의 초기화하거나 연장하는 행동으로 사용하지 않는다.
6. **기간 중 변경은 맡은 일을 모두 마친 뒤 기사 본인이 한다.** 현재 수행·수락한 후속 업무·보유 물품의 반납 책임이 남았으면 전환을 보류한다. 완료된 과거 업무나 정산/지급만 남은 기록을 현재 수행 업무로 간주해 전환을 막지 않는다. 변경할 수 있다는 이유로 AI나 운영자가 자동 전환하는 권한을 얻는 것은 아니다.

## 최소 설계안 — 구현 전 제안

- 기존 업무 프로필 아래에 `현재 집중 업무 / 적용 시작·종료 / 선택 판본`을 구분한다. 현재 선택 한 건부터 다루고, 장기 달력·근무 예약·관리자의 강제 편성으로 확장하지 않는다. 필드·감사 기록·migration 방식은 구현 명세에서 기존 구조와 다시 대조한다.
- 업무 종류는 기존 `FoodDelivery / QuickDelivery / CargoTransport` 분류를 사용한다. 직접 피킹은 작업 방식이며 새로운 집중 업무 종류로 늘리지 않는다. 포장 마트와 일반 화물의 실행 원장 차이는 기존 분류 정책을 보존한다.
- 집중 선택을 실제 적용할 때는 선택 상태와 적용 중 여부를 표시한다. 기본 OFF인 혼합 수행 옵션에만 검사를 넣고 집중 제한이 작동한다고 설명하는 구현은 피한다. 기존 실행 Feature 경계와 초기 사용자 호환을 검토한 뒤 적용하며, 이번 기획에서 플래그를 켜지 않는다.
- 업무 시작 화면에는 `오늘 퀵 / 한 주간 음식 배달`처럼 종류와 기간을 선택하는 간단한 절차를 둔다. 지도에는 현재 종류·기간의 짧은 상태만 표시하고 변경 상세는 기존 업무 설정이 소유한다. 관리자에게도 같은 현재 선택을 보여 준다. 이 화면안은 아직 구현하지 않았다.
- 승인된 변경 규칙을 적용할 때는 수락 중/보유 업무/사진·인수 미완료/미반납 책임을 전문 원장에서 확인하고, 같은 프로필 판본과 SQL 변경 경계에서 처리한다. 오래된 다른 종류의 미수락 제안·푸시는 무효화하고 새 설정으로 재평가하며 기사 미응답으로 벌점을 주지 않는 방향을 검토한다. 주문 원장·이력 자체를 삭제하지 않는다.
- 기간 종료만으로 다른 종류를 자동 수신시키거나 자동 운행 종료를 하지 않는 안을 권장한다. 같은 업무 재선택·연장 여부와 수신 안내는 기간 기준을 정한 후 명세화한다. 집중 기간과 주간 정산 기간은 서로 다른 책임이다.

```text
가능한 업무·수행 자격
└─ 기사 본인의 집중 업무 선택 + 적용 기간
   ├─ 신규 후보 → 선택한 종류만 일정·적재·위치 검토 → 추천·수락
   ├─ 이미 맡은 업무 → 기존 상태와 완료·정산 절차 유지
   ├─ 신규 수신 OFF/미응답 중지 → 현재 집중 선택 유지
   └─ 업무 전환 요청 → 기간 중 변경 규칙 확인 → 정본 재조회
```

## 답변과 다음 질문

- 질문 ID: `driver-work-focus-switch-before-expiry`.
- 상태: `Answered / Accepted`. 사용자 답변: **맡은 업무를 모두 마친 뒤 본인이 변경 가능 (권장)**. 기간이 끝날 때까지 강제 잠금하거나 수행 중 안내만 하고 변경을 허용하는 대안은 채택하지 않았다.
- 다음 질문 ID: `driver-work-focus-period-boundary`, 상태 `Asked / Unanswered`.
- 질문: 하루와 주간 기간의 기준을 어떻게 할지. 권장안은 `하루는 운행 종료까지 / 주간은 선택일부터 7일`이다. 대안은 `하루는 자정까지 / 주간은 월요일~일요일`, `기간 없이 본인이 변경할 때까지`이며 아직 어느 안도 선택됐다고 기록하지 않는다.
- 권장안의 이유: 자정을 넘겨 진행하는 한 번의 운행을 중간에 끊지 않고, 주간 선택은 앱 재실행·다음 날 운행에도 유지할 수 있다. 정확한 시작·종료 시각은 화면에 표시하고, 승인된 기간 중 변경 규칙은 어느 기간안에서도 보존한다.
- 다른 종류의 일감이 늘었을 때 전환을 권유할지, 기간 만료 후 재선택/연장을 어떻게 안내할지도 후속 기획이다. 아직 자동 전환·운영자 강제 변경·소득 보장으로 확대하지 않는다.

## 구현 시 확인할 사례

오늘 퀵 선택 중 음식 후보·공개 콜을 차단하는지, 한 주간 음식 선택이 앱 재실행·운행 종료 뒤에도 남는지, 같은 종류의 B는 A 수행 중에도 기존 적격성 기준으로 받을 수 있는지, 만료/변경 중의 A·B 완료와 미반납 책임을 보존하는지, 설정 변경과 수락의 동시 요청·오래된 알림·계정 변경·시간 경계를 판본으로 보호하는지 확인한다. AI 설명과 학습 사례에도 집중 업무·기간·배제 이유를 남기되 실제 모델 학습이나 운영 적용 완료와 구분한다.
