# 주거 공간의 상품 등록·구매 신청·퀵 배송 설계 r4

- 기준일: 2026-10-05
- 기획 ID: `PLAN-OPERATIONS-NEIGHBORHOOD-MICRO-HUB`
- 상태: `DirectionConfirmed / DetailedDesignProposed / ImplementationPending`
- 범위: 사용자가 동의한 집과 일상 공간의 상품·보관·픽업 기능, 기존 주문·재고·화물 배차와의 연결
- 이번 작업: 현재 코드 대조와 설계 문서. 제품 코드·DB·앱·실제 운영을 변경하지 않았다. 법적 요건 조사·판정은 이번 범위에서 제외한다.

## 1. 방향과 첫 이용 예

사용자가 본인 집의 사용 가능한 부분을 등록하고 동의하면 그 공간을 물류 거점으로 표현할 수 있게 한다. 주거·비주거 여부는 공간을 설명하는 값이며 주거라는 이유만으로 등록을 차단하지 않는다. 물류센터 신축, 전용 창고, 사물함 보유를 참여 조건으로 두지 않는다.

예를 들어 사용자가 집에 있는 상품 10개와 가격·픽업 가능 시간을 등록한다. 이웃이 2개 구매를 신청하면 해당 수량을 임시 예약하고 판매자가 가능한지 확인한다. 구매자가 상품·배송 요금을 확인한 뒤 근처의 적합한 기사가 배차 제안을 수락하면 판매자에게 픽업 준비를 요청한다. 기사가 2개를 인계받아 전달하고 구매자가 수령을 확인한다. 이 과정에서 나머지 8개, 예약된 2개, 실제 인계된 2개를 구별한다.

한 공간은 다음 기능을 선택적으로 제공한다. 상품 판매가 없는 보관·운송도 계속 지원한다.

| 기능 | 사용자가 등록하는 것 | 연결할 업무 |
| --- | --- | --- |
| 보유 상품 판매 | 상품·수량·단위·가격·상태·픽업 시간 | 구매 신청 → 주문별 재고 예약 → 출고 → 배송 |
| 보내는 물건 픽업 | 품목·포장·중량·수령지·가능 시간 | 기존 화주 운송 의뢰 → 화물·퀵 배차 |
| 타인의 물건 단기 보관 | 사용 구획·시간·용량·인수 방법 | 보관 예약 → 실제 입고 → 인계·출고 |

같은 집에서 여러 기능을 제공해도 공간과 용량을 중복 생성하지 않는다. 음식 주문·조리·음식 기사 배차는 기존 음식 업무를 유지하며, 일반 보유 상품을 음식 주문으로 가장해 연결하지 않는다.

현재 거점 서비스는 `IndependentNonResidentialSpace`를 고정하고 첫 비주거 Pilot 정책으로 준비 상태를 판단한다. 운영 모드 활성화와 실제 지급도 비활성이다. 이를 r4 구현 완료로 보지 않는다. 기존 r1 데이터·시험은 `LegacyPilot` 호환 프로필로 보존하고, 새 주거 등록은 별도 공간 기능 프로필로 판정하도록 설계한다. r1의 비주거 제한을 새 일반 공간 모델의 공통 제약으로 확대하지 않는다.

기존 개별원함·마트 구매 요청은 재고 예약·실주문·배송을 자동 확정하는 계약이 아니다. 또한 마트 포장 완료의 마지막 배송 인계는 음식 업무로 연결된다. 일반 집 상품은 기존 판매·출고와 화물 운송 경계를 연결하는 전용 어댑터가 필요하다. 용량 예약 완료나 모의 보상 기록을 상품 판매·배송 완료로 사용하지 않는다.

## 3. 정보 관계와 저장 책임

다음은 논리 모델이며 새 테이블·migration이 적용됐다는 뜻이 아니다. 기존 ID·공개 계약을 보존하고 필요한 연결만 추가한다.

```text
사용자 ── 공간 참여·동의 ── 공간 1 ── 구획 N ── 제공 기능 N
                              │          │
                              │          └─ 공간 용량 예약 ── 업무 StableId
                              └─ 기존 창고 연결 ── 상품 재고·수량 예약

등록 상품 ── 판매 게시 ── 구매 신청/주문 ── 주문 품목·재고 예약
                                          └─ 출고 인계 ── 운송 의뢰
                                                           └─ 화물 배차·픽업·전달
```

| 논리 정보 | 관계·최소 필드 | 책임 |
| --- | --- | --- |
| 공간 등록 | 등록 사용자, `SpaceStableId`, 공간 유형, 대략 위치, 보호된 픽업 위치 참조, 상태·revision | 공간 제공 범위의 정본. 위치와 구획을 임의 생성하지 않음 |
| 공간 구획 | 공간 1 : 구획 N, 구획 이름, 공유 용량 자원 ID | 집 전체·현관·선반 등 사용자가 지정한 부분. 정밀한 실내 도면은 필수 아님 |
| 기능·담당 연결 | 구획, 판매/픽업/보관, 담당 사용자, 시간, 허용 품목 조건, 가동 상태 | 기능마다 필요한 입력만 요구. 픽업만 제공하는 공간에 보관 용량을 강제하지 않음 |
| 공간 참여·동의 | 사용자, 공간/구획/기능 범위, 판본, 동의·철회 시각 | 본인=관리담당자이면 한 입력 흐름에서 필요한 동의를 받음. 다른 담당자면 각자 동의 |
| 상품·판매 게시 | 소유 사용자, 기존 상품 ID, 출처 기록, 가격·단위·상태, 기능 연결 | 상품의 정체성과 어느 곳에서 어떤 조건으로 판매하는지를 분리 |
| 재고·수량 예약 | 상품·창고, 보유/예약/가용 수량, 주문 품목 ID, 만료·상태 | 기존 재고 정본 재사용. `가용=판매 가능한 보유-유효 예약`, 불량·출고분 제외와 음수·과판매 차단 |
| 공간 용량 예약 | 공유 자원, 업무 StableId, 시작·종료 시각, 건수·중량·필요 시 부피, 상태 | 상품 수량과 별개. 같은 자원을 여러 기능에서 중복 예약하지 않음 |
| 구매 신청·품목 | 구매자·판매자, 상품/수량/가격 판본, 픽업·전달 가능 시간, 요금 확인 상태 | 요청을 받은 것과 판매·배송이 확정된 것을 구별 |
| 출고·운송 연결 | 주문 품목·예약 ID, 출고 인계 ID, 기존 운송 의뢰 ID, 업무 종류, revision | 한 주문의 반복 인계 요청에서 운송 의뢰·배차를 중복 생성하지 않음 |

자가 보유품은 사용자가 신고한 실물과 수량이다. 서버의 물리적 실사 완료로 표시하지 않는다. 등록 어댑터에서 출처를 `UserDeclared`로 보존하고 기존 입고·재고 정본의 필수 필드를 충족시킨 뒤 판매상품과 연결한다. 집 상품을 넣기 위해 전체 판매상품의 필수 외래키를 없애거나 수입·구매 이력을 꾸미지 않는다. 기존 입고 계약이 이 출처를 받지 못하면 해당 경계에 출처 유형을 추가하는 작은 설계·구현이 선행한다.

이미 집에 보관 중인 본인 상품은 재고로 기록한다. 주문이 들어올 때마다 같은 보관 공간을 새로 점유한 것으로 계산하지 않는다. 포장·픽업 대기 자원 예약이 필요한 경우에만 추가 용량을 예약한다. 타인의 물건을 받는 기능은 실제 인수·보관·출고 이력을 따로 남긴다.

주문에서 예약한 수량을 기존 출고·운송으로 인계할 때 같은 예약을 이어받는다. 기존 [창고 작업 서비스](../../../../../Ssalddel/Services/LogisticsProcessing/Warehouse/WarehouseOperationService.cs)는 운송 생성 시 가용 수량 차감·예약 수량 증가를 수행하므로 그대로 추가 호출하여 이중 예약하지 않는다. 픽업 확정에서는 실물 보유 수량 차감과 해당 주문 예약의 소진을 같은 트랜잭션에서 반영하고, 픽업 전 취소는 해당 예약만 해제한다.

## 4. 구매에서 배송까지의 상태

화면은 아래 이용 흐름을 보여주되 구매·재고·운송의 상태를 하나의 새 원장에 중복 저장하지 않는다. 연결 UseCase가 각 정본을 읽어 현재 단계와 가능한 행동을 제공한다.

| 이용 단계 | 서버에서 확정할 것 | 사용자에게 필요한 행동 |
| --- | --- | --- |
| 상품 공개 | 동의·기능 가동·판매 게시 판본과 가용 수량 | 구매자는 상품·가격·대략 위치·가능 시간 확인 |
| 구매 신청 | 요청·품목과 만료 있는 수량 예약 | 판매자는 가능 여부 확인 또는 거절 |
| 요금 확인 | 상품대금·배송 부담액·기사 운임과 요금 유효기간을 별도 기록 | 구매자는 전체 조건 확인. 거절·기한 만료 시 예약 해제 |
| 배차 대기 | 기존 화물 운송 의뢰·큐 연결, 적합한 기사 후보 조회 | 기사는 픽업/전달 대략 위치·물건·시간·총 운임을 보고 수락 |
| 기사 배정 | 수락한 기사와 현재 배차의 유일성, 위치 조회 권한 | 판매자는 픽업 준비, 기사는 현재 픽업 업무 확인 |
| 픽업 준비 완료 | 실제 준비 선언과 인계 가능한 주문별 수량 | 기사는 도착·수량 대조·픽업 완료 |
| 픽업 완료 | 예약한 수량의 실제 출고와 인수 책임 이전 | 기사는 전달지로 이동. 판매 재고는 해당 수량만 차감 |
| 전달·수령 | 기사 전달 기록과 구매자 수령 확인을 구별 | 구매자는 수령 확인 또는 문제 접수 |

판매자의 가능 확인은 재고·시간 확인이다. 기사 배정 전에 포장 시작을 강제하지 않으며, 배정 후 준비를 안내한다. 이미 준비된 상품은 실제 준비 상태를 명시적으로 선언할 수 있다. 준비 완료·기사 도착·수량 확인 전에는 픽업 완료를 확정하지 않는다.

배차 대기는 기사가 반드시 온다는 뜻이 아니다. 후보가 없으면 대기 상태와 재탐색·취소 가능한 시점을 표시한다. 무기한 수량을 묶지 않도록 만료를 두고, 만료 후에는 자동 확정 대신 구매자에게 재신청·새 요금 확인을 제공한다. 기존 업무의 수락·거절·만료·취소 정책을 어댑터에 연결한다.

## 5. 가까운 기사와 요금

일반 집 상품에는 `OperatingSystemIds.DomesticCargoTransport`(`DomesticCargoTransportOS`)와 기존 화물 배차 엔진을 사용한다. 음식의 `OperatingSystemIds.FoodDelivery`(`FoodDeliveryOS`), 조리 상태, 음식 배차 큐·기사 정산과 독립시킨다. 식별자의 기준은 [운영체제 카탈로그](../../../../../Ssalddel.Contracts/Common/Versioning/OperatingSystemIdentityCatalog.cs)다. 퀵은 새 앱을 만들기보다 기존 화물의 서비스 유형·운송 수단·품목 적합성·시간창 프로필로 연결하는 후보이며, 기존 계약에서 지원하지 않는 유형은 추가 계약이 필요하다.

서버는 기사 현재 위치·가동 여부·차량·수용량·약속 시간과 실제 경로를 기준으로 후보를 찾는다. 가까운 직선거리만으로 확정하지 않는다. 후보 기사에게 총 운임을 먼저 보여주고 수락을 받아야 한다. 같은 배차를 여러 기사가 수락해도 한 명만 유효하며, 먼저 수락한 기사라는 조건만으로 해당 상품의 픽업 완료를 생성하지 않는다.

기존 [화물 운임 계산기](../../../../../Ssalddel/Application/Shipper/Request/화주운송기준운임계산기.cs)의 오토바이·오토바이 퀵 기본운임·km 단가·최소운임과 운영자 설정을 우선 대조한다. 음식용 픽업비·전달비·100m 단가를 자동 적용하지 않는다. 상품대금, 구매자 배송 부담, 판매자 부담, 기사 운임은 별도이며 플랫폼 수수료·예비금·실제 결제/지급 정책을 이 설계만으로 확정하지 않는다. 경로 미확인·조회 실패는 운임 미확정으로 나타내고 거리 0·무료로 바꾸지 않는다. 요금이나 배송 조건이 바뀌면 새 판본을 구매자에게 확인받는다.

## 6. 중단·철회·개인정보의 업무 처리

- **픽업 전 취소·거절·만료:** 주문 수량 예약과 필요한 공간 예약을 해제하고 연결된 운송 의뢰를 취소한다. 취소와 기사 수락·픽업이 동시에 오면 revision과 실제 인수 여부를 대조해 한 결과만 확정한다.
- **픽업 후 문제:** 재고를 자동 복원하지 않는다. 물건의 현재 인수자·위치·반환 또는 재전달 업무를 기록하고 실제 반납 후 재고를 되돌린다. 배송 실패를 배송 완료로 처리하지 않는다.
- **기능 중지·공간 동의 철회:** 해당 범위의 신규 공개·구매·예약·배차를 막고 기존 건을 대기/취소/반환으로 분류한다. 이미 픽업한 건은 진행 기록을 보존한다. 철회한 집의 주소는 새 조회에서 차단하며 반환이 필요하면 제공자가 새 인계 장소를 동의하거나 운영자가 별도 해결 업무를 진행한다.
- **집 주소:** 공개 상품·거점 조회는 대략 위치만 제공한다. 서버는 보호 위치로 경로를 계산하고, 배정된 기사에게 해당 활성 업무의 픽업 정보만 필요한 기간에 제공한다. 구매자·다른 기사에게 집의 상세 주소·출입 정보가 노출되는 일반 API를 만들지 않는다.
- **업무 종료:** 상세 위치·연락처 조회 권한을 종료하고 앱의 업무 사본을 정리한다. 거래·재고·운임 이력은 별도로 유지한다. 음식 기사 상세의 기존 3일 정책을 모든 집 상품·화물 데이터 삭제 기간으로 복사하지 않는다.
- **중복·동시 요청:** 수량 예약과 픽업 확정은 DB 트랜잭션·revision·유일 키로 보호한다. 같은 멱등성 키와 같은 내용은 기존 결과를 반환하고 다른 내용이면 충돌 처리한다. Outbox 재전송은 운송 의뢰·출고·정산을 중복 생성하지 않는다. 통신 실패 시 상태 조회로 확인하고 새 쓰기를 자동 반복하지 않는다.

## 7. 화면 → 처리 코드 → DB의 분리

[한 페이지의 역할 기준](../../../../Architecture/WholeRoadmapPagePrinciple.md)과 [업무 책임 모델](../../../../Architecture/BusinessWorkflowResponsibilityModel.md)에 맞춰 기존 앱의 페이지를 확장한다. 사람 한 명이 판매자·공간 담당자·구매자를 맡을 수 있으며 역할마다 새 앱 가입을 강제하지 않는다.

| 페이지의 한 목적 | 주로 보여줄 정보·행동 | 처리 책임과 정본 |
| --- | --- | --- |
| 내 공간 등록·관리 | 사용할 구획·기능·시간·동의·중지 | 공간 UseCase → 등록·구획·기능·동의 |
| 내 상품 등록·관리 | 상품·수량·가격·판매 여부 | 보유품 등록/판매 UseCase → 기존 상품·입고·재고·게시 |
| 주변 상품 탐색·상세 | 상품·가격·대략 위치·가능 시간, 구매 신청 | 공개 조회/구매 요청 → 판매 게시·가용 수량·요청 |
| 판매 요청 상세 | 이번 요청의 품목·수량·시간, 가능 확인 → 픽업 준비 → 인계 | 판매자 작업 UseCase → 주문 품목·출고 |
| 구매 진행 상세 | 이번 주문의 요금 확인·현재 단계·취소·수령 | 구매자 작업 UseCase → 구매·운송 조회 |
| 기사 현재 업무 | 수락 전 총 운임, 배정 후 픽업 → 전달에 필요한 카드 | 기존 화물 기사 UseCase → 배차·운송·인수 기록 |
| 운영자 문제 처리 | 미배차·미수거·반환 등 선택한 예외의 현재 책임자·행동 | 기존 운영자 업무 → 각 정본의 해결 명령 |

화면의 정보는 상태에 따라 바뀐다. 등록 화면에 진행 주문·정산을 한꺼번에 넣지 않으며, 기사 업무 카드에는 지금 픽업하거나 전달할 한 건을 우선 표시한다. 주소·품목·요청 사항은 구분된 섹션으로 보여준다.

## 8. API 계약 후보

아래는 미구현 API 제안이다. 기존 `/api/v1/common/neighborhood-logistics-hubs`의 보호 계약을 유지하고, 실제 구현 시 호환 DTO 판본 또는 별도 r4 등록 경로를 선택한다. 일반 사용자를 기존 관리자·운영사용자 권한 전체에 추가하지 않고 본인 등록·거래 참여·배정 관계를 각각 검사한다.

| 경로 후보 | 사용자·권한 | 결과 |
| --- | --- | --- |
| `POST /api/v1/common/neighborhood-logistics-hubs/self-registrations` | 인증 사용자, 본인 등록 | 공간·구획·기능·동의와 revision |
| `PUT /api/v1/common/neighborhood-logistics-hubs/{id}/capabilities/{capabilityId}` | 해당 공간·기능 담당자 | 기능 시간·상태 수정, 신규 업무 가능 여부 |
| `POST /api/v1/common/home-goods` | 해당 판매 기능 담당자 | 출처 있는 보유품·입고/재고 연결 |
| `POST /api/v1/common/home-goods/{id}/listings` | 상품 소유자·지정 판매 담당자 | 가격·수량·픽업 조건의 판매 게시 |
| `GET /api/v1/common/neighborhood-goods` | 공개 조회 | 집 상세 주소 없는 상품 목록 |
| `POST /api/v1/common/neighborhood-purchase-requests` | 인증 구매자 | 품목·수량 예약·만료·요금 확인 상태 |
| `POST /api/v1/common/neighborhood-purchase-requests/{id}/seller-confirmation` | 해당 판매자 | 가능/거절과 조건 판본 |
| `POST /api/v1/common/neighborhood-purchase-requests/{id}/confirmation` | 해당 구매자 | 요금·조건 확인 후 출고/운송 연결 |
| `POST /api/v1/common/neighborhood-purchase-requests/{id}/cancellation` | 해당 거래 당사자, 단계별 정책 | 해제 완료 또는 진행 중 문제 처리 상태 |
| `GET /api/v1/common/transport-requests/{id}/pickup-access` | 해당 활성 배차의 기사 | 범위·만료 있는 픽업 정보 |

기사 수락·도착·픽업·전달과 판매자의 준비 완료는 기존 화물·출고 API를 대조해 연결한다. 확인 없이 새 동명 endpoint를 복제하지 않는다. 공개 응답과 업무 전용 응답을 분리하며, 보호 정보 응답에는 캐시 금지와 업무 만료를 적용한다. 구매 요청·픽업·취소는 command ID와 revision을 받고 UI가 최신 정본을 다시 읽는다.

## 9. 구현 우선순위와 완료 조건

첫 구현은 **집 한 곳·판매자 한 명·상품 한 종류·주문 한 건·기사 한 명**으로 제한한다. 다거점 묶음 배차·사물함 장비·자동 결제·Unity 시각화는 이 흐름 검증 뒤에 확장한다.

1. **주거 공간과 상품 연결:** 주거 유형 등록·본인 동의·픽업 기능, 자가 보유품의 출처와 기존 재고 연결, 대략 위치의 상품 공개. 집 상품을 실제 조회할 수 있어야 완료다.
2. **구매와 수량 예약:** 2개 신청·판매자 가능 확인·전체 요금 확인·만료/취소 해제. 같은 2개를 두 사람이 동시에 신청해도 가용 수량을 넘기지 않고, 재시도에서 주문을 중복 생성하지 않아야 완료다.
3. **화물 기사와 한 건 완주:** 기존 화물 운송 큐 연결·운임 제안·수락·준비·2개 부분 인계·전달·수령. 상품 10개 중 2개만 출고되고 음식 기능 OFF와 독립적으로 동작해야 완료다.
4. **공간 기능 확장과 복구:** 시간창·공유 용량, 제3자 보관·반환, 기사 미도착·픽업 후 실패·동의 철회. 신규 업무 차단과 기존 물건 인수 책임이 일치해야 완료다. 기본 취소·수량 해제·주소 보호는 1~3단계부터 적용한다.

단계마다 페이지 → UseCase/API → DB를 함께 기록하고 실제 서버·앱에서 같은 주문·출고·운송 ID를 대조한다. 필수 반례는 마지막 수량 동시 신청, 다른 내용의 같은 멱등 키, 기사 동시 수락, 취소와 픽업 경합, 동의 철회, 다른 사용자의 집 주소 조회, 응답 유실 뒤 재조회, 픽업한 물건의 실제 반납 전 재고 복원 차단이다.

이 문서는 구현에 들어갈 설계 기준이다. 현재 앱에서 주거 상품의 거래·자동 배차·실결제·실제 입금이 가능한 것으로 보고하지 않는다. r1 코드의 기존 동작·운영 비활성은 유지하며 r4 구현에서 좁은 경계부터 변경한다.
