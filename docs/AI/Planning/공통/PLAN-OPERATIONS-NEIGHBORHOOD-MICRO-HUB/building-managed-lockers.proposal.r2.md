# 건물 관리업체·전자 사물함 거점 확장 제안 r2

- 기준일: 2026-09-24
- 상태: 사용자 구상 기록 / 세부 정책 제안 / 구현·실운영 승인 아님
- 선행: [기존 생활권 소형 물류거점 r1](README.md#r1-기존-승인-범위)

## 사용자 의도와 확정 범위

건물 관리업체가 설치·관리하는 소규모 전자 사물함을 보관·픽업 거점으로 연결한다. 기사가 그곳에서 물건을 픽업하여 수령인에게 전달하는 서비스를 통해 동네의 소득 활동 기회를 만들고자 한다. 플랫폼이 사물함을 공급하는 방식과 관리업체가 설치한 장비를 연결하는 방식은 모두 검토 후보이며 어느 사업 모델도 확정하지 않았다.

기존 r1의 소유자·관리담당자·플랫폼 승인, 비주거 공간·상온 밀봉품·Simulation 한정과 실제 지급 비활성은 유지한다. 관리업체의 참여만으로 공간 사용권이나 설치·운영 적합성이 확인된 것으로 처리하지 않는다. 실제 운영 요건은 별도 검토가 필요하며 이번에는 법률 조사·적법성 판정을 하지 않았다.

## 역할 분리 제안 — 아직 승인되지 않은 상세

- 공간 권리자: 공간 사용에 대한 동의·철회.
- 건물 관리업체: 사물함 관리담당자. 접근 가능 시간·설비 상태·현장 문의 관리. 물건 소유자나 판매자로 자동 간주하지 않는다.
- 판매자/물건을 맡기는 사람: 물건 등록·보관 의뢰·투입. 첫 대상은 다음 질문으로 결정한다.
- 기사: 제시된 조건을 보고 배송을 수락하고, 허가받은 칸에서 픽업·인계. 가입만으로 출입·전체 사물함 권한을 부여하지 않는다.
- 수령인: 물건 수령 확인. 플랫폼: 권한·예약·업무 기록·관계자 연락 조율.

## 최소 흐름 제안

보관 의뢰 → 크기·중량·시간에 맞는 칸 예약 → 투입 확인 → 배송 요청·기사 수락 → 제한된 픽업 권한 → 물건 인수 확인 → 전달·수령 확인.

문 열림/닫힘은 설비 사건일 뿐 실제 물건 투입·인출·인수 완료와 동일하지 않다. 전자 잠금장치의 결과와 업무 원장의 인계 확인을 구별한다. 통신 두절·문 잠김·빈 칸/물건 불일치·미수거는 보류와 담당자 확인으로 연결하며 자동 완료·귀책·지급을 확정하지 않는다.

기존 거점의 총용량 예약 아래에 장비/칸 식별자·예약·물건 연결·접근 권한·설비 사건을 추가하는 방향을 검토한다. 기존 창고 위치/재고 계약을 먼저 대조하며 별도 재고 원장을 중복 생성하지 않는다. Unity에는 준비된 비식별 보관·픽업 상태만 표시하고 개방 코드·정확한 사적 위치·출입 권한은 내보내지 않는다.

## 미정과 다음 질문 하나

미정: 누가 처음 물건을 넣는지, 공급/구매/임대 주체, 장비 연동, 비용·보상 부담, 고장 대응, 분실·파손 절차, 설치 공간·품목의 실제 운영 요건. 공간 분산만으로 대형 센터를 대체하거나 수익·일자리 창출이 보장된다고 판단하지 않는다. 장비·유지관리·투입/픽업 노동·체류 시간·배송 밀도를 함께 검토한다.

다음 질문: 첫 사례는 **동네 상점이 판매한 상온 밀봉 상품을 사물함에 넣고, 기사가 픽업해 주문자에게 전달하는 방식**으로 잡을까? 추천 이유는 기존 주문·창고·배송 흐름을 활용할 수 있어서다. 개인 간 택배와 공동 재고까지 동시에 시작하지 않는 대신 첫 사례의 범위가 좁아진다. 답변 전에는 확정하지 않는다.

이번 변경은 기획 문서뿐이다. 코드·DB·Unity·장비 연동·수집·시험·commit·push 없음. 새 디오라마 규칙 후보 없음.
