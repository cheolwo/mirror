# 사전 참여·약속 영향·성과 환류 제안 r114

기준일: 2026-10-24. 상태: `AdvanceParticipationAndImpactDirectionAccepted / ProposedDesign / CancellationPolicyDetailsPending / ImplementationNotStarted`.

사용자는 생산자와 주문자가 사전 참여하고 서로의 예약을 근거로 일을 준비하며, 약속 변경/취소의 상대방 영향과 이행에 따른 이익을 알림·화면으로 확인하는 통합 매칭·예약 구조를 원했다. [모바일 예약·상호 수락 r113](mobile-work-appointments.design.r113.md)을 구체화한다. 이번에는 설계만 보강하고 새 예약·취소·금전 부담·성과금 정책·알림 발송을 실행하지 않는다. [r112 변화 조회](shared-outcomes.implementation.r112.md)의 코드·시험·모바일 미검증 상태는 보존한다.

## 1. 중심 구조와 사전 참여

사용자에게 보일 이름은 **함께할 일과 약속**을 제안한다. 내부적으로는 기존 공동운영 회차 아래 생산/공급·구매/수령·공간·현장 작업·기사 인계의 개별 약속을 연결하는 통합 협업 예약 관리다. 누구나 의향에서 시작할 수 있으며 모든 참여자가 동시에 모여야 관심 표시를 할 수 있는 구조로 만들지 않는다.

| 참여자 | 시작 전에 올릴 정보 | 확정과 분리할 것 |
|---|---|---|
| 주문자 | 필요한 품목·수량·희망 수령 시간·수용 가능한 조건 | 관심 수요, 조건부 예약, 실제 주문·결제·수령 |
| 생산자/공급자 | 공급 가능 품목·수량·기한·최소 인수 조건·품질/포장·생산/픽업 책임 | 공급 의향, 확정 공급 약속, 생산 완료·실재고·실제 입고 |
| 공간 제공자 | 수용 범위·용량·사용 시간·보관/반환 조건 | 공간 제안, 별도 사용 동의, 실제 수용 가능 상태 |
| 현장 참여자 | 가능한 역할·시간과 확인한 업무 안내 | 관심, 개별 작업 예약, 실제 근무·완료 |
| 기사 | 기존 근무/추천·배차 수락과 인계 가능 조건 | 현장 예약, 기사 배정, 실제 픽업·전달 |

조건부 예약에는 “필요 수요/공급·공간·인력이 이 시각까지 확보되면 다음 단계 확인”을 명시한다. 기준 충족은 확정 후보이며 자동 발주·생산 시작·대금 수취가 아니다. 관계자가 같은 조건 판본을 확인한 뒤 전문 주문·입고/근무·운송 원장으로 인계한다. 필요한 선행은 업무별로 다르며 재고 확보용 입고에 주문자를 일괄 필수로 두지 않는다.

기대와 책임을 묵시적으로 추정하지 않고 수량·시간·담당·보수/가격 조건·변경 가능한 시점·취소/인계 방법을 예약 전에 보인다. 화면 열람만으로 이 조건 동의가 된 것으로 저장하지 않는다.

## 2. 현재 재사용할 근거와 미연결

- [개별 원함 원장](../../../../../Ssalddel/Services/Orderer/공동구매개별원함원장Service.cs)은 본인의 비구속 수요와 철회를, [생산자 연결](../../../../../Ssalddel/Services/Orderer/DomesticGroupPurchaseProducerConnectionService.cs)은 공급 가능/최소 물량·기한·품질 등 초안을 다룬다. 현재 생산자 directory의 기본 미연결을 실제 매칭 성공으로 보고하지 않는다.
- [공동구매 경제성](../../../../../Ssalddel/Services/CollectiveProcurement/CollectiveProcurementEconomicsEngine.cs)은 잠재/확약 수량·최소량·추정 비용/편익을 계산한다. 수요 충족·계산 편익을 실제 발주·매출·절감·수령액으로 표시하지 않는다.
- [입고 협의](../../../../../Ssalddel/Application/Warehouse/DistributedFulfillmentUseCase.InboundCollaboration.cs)는 같은 판본의 양측 동의와 여유 용량을 검사한다. 단순 취소는 수령 전 범위이고, [실물 취소](../../../../../Ssalddel/Application/Warehouse/DistributedFulfillmentUseCase.Custody.cs)는 이미 픽업한 물품의 반환 책임을 유지한다.
- [음식 주문 취소 합의](../../../../../Ssalddel/Application/Food/음식주문취소합의UseCase.cs)는 명시한 비용 근거·조건 동의·별도 실행과 판본/멱등 처리가 있다. 조리/기사 수행 전 등 한정된 업무이므로 범용 생산/근무 예약 취소에 그대로 적용하지 않는다.
- [정산 이의·정정](../../../../../Ssalddel/Application/Settlement/NeighborhoodSettlementUseCase.Entries.cs)은 원 금액을 덮지 않는 별도 정정과 당사자 확인을, [성과금](../../../../../Ssalddel/Application/Settlement/NeighborhoodSettlementUseCase.ActivityRewards.cs)은 기여·수령 근거와 모의 재무 입력의 구분을 유지한다.

각 전문 원장을 가로지르는 사전 약속의 의존관계, 취소 전 영향 조회, 그 결과에 결속된 변경 확인과 공동운영 알림은 아직 추가 설계/구현 대상이다.

## 3. 약속의 연결과 취소 영향

기존 `LedgerId/CycleId`와 전문 원천 ID·현재 판본을 참조하는 약속 및 의존관계를 둔다. 예를 들어 공급 약속과 입고 일정, 그 입고를 기다리는 피킹, 해당 주문의 수령 시간 관계를 명시한다. 같은 동네·비슷한 시각이나 참여자라는 이유만으로 의존·책임을 추정하지 않는다. 영향받은 한 약속을 취소했다고 전체 회차나 관계없는 약속을 자동 취소하지 않는다.

취소 전에 **이 약속을 바꾸면 어떤 영향이 있나요?**를 읽기 전용으로 제공한다.

| 표시 항목 | 뜻과 근거 |
|---|---|
| 조정이 필요한 약속 | 직접 연결된 공급·입고·근무·주문/수령·인계 일정. 확인/가능성/미확인을 구분 |
| 이미 진행한 일 | 실제 생산/입고/작업·픽업·보관·반환 근거. 앞으로 할 일과 구분 |
| 이미 발생한 비용·보수 | 실제 수행/자재/운송 등 확인된 원천과 상태. 발생·정산확정·실지급을 분리 |
| 기대 이익의 변화 | 아직 확정되지 않은 매출·성과금·대기/재배정 비용의 예상 변화와 가정. 청구 금액이 아님 |
| 합의한 취소 조건 | 적용 판본·당사자 확인과 근거. 미합의 금액을 0원이나 확정 위약금으로 만들지 않음 |
| 가능한 대안 | 시간/수량 조정, 다른 담당 제안, 인계, 유지, 취소. 대체자를 자동 확정하지 않음 |

영향이 크더라도 취소 사유만으로 귀책·손해 책임·벌점·감봉을 확정하지 않는다. 취소 금액 검토와 본인의 유효한 철회/변경 결정, 이미 맡은 물품의 인계 의무는 별개다. 수행한 보수와 다툼 없는 금액을 취소 버튼으로 지우지 않고 정정/이의 경로를 제공한다. 새로운 자동 공제·위약금·신뢰 감점 기준은 이번에 정하지 않는다.

변경은 `영향 조회 → 본인 결정 → 현재 원천/조건 판본 재검사 → 변경 저장 → 당사자 안내 → 필요한 대체안 재합의`로 처리한다. 미리보기 뒤 상태가 바뀌면 영향을 다시 보여준다. 미리보기·단순 조회 자체는 취소·동의·알림을 만들지 않는다. 요청 ID/내용 지문과 판본 검사를 재사용하고, 불명확한 통신 결과는 같은 요청 결과를 조회한다.

## 4. 약속 이행의 편익과 비용

예약 단계는 약정 단가/수량·시간·추정 비용과 가정을 이용한 기대 편익을, 완료 뒤에는 실제 수행/비용·수령·정산 근거로 확인 가능한 성과를 보여준다. `기대 → 수행 근거 확인 → 정산 확정 → 지급/수령 확인`을 분리하고 예상값을 실현값으로 덮지 않아 최초 기대와 현재 결과를 비교할 수 있게 한다.

개인 화면은 본인 보수·확인 비용·조건부 판매 성과·지급 상태를, 작업공간은 권한/동의 범위의 공동 처리량·대기/재작업·총비용 변화를 보여준다. 더 오래 일한 효과와 같은 시간의 효율 개선을 구분한다. 공급 약속을 지켰다는 사실만으로 매출·영업이익·실수령을 확정하지 않고 모의 경제성은 모의로 표시한다.

정상 이행과 조기 변경/인계로 해결한 사실은 기록할 수 있지만 신고가 없거나 취소를 참았다는 이유로 자동 보상하지 않는다. 기대 이익 감소는 취소자가 지급해야 할 채무로 변환하지 않는다. 밀집·참여·예약 수 증가가 개인 소득 증가를 보장하는 것으로 표현하지 않는다.

## 5. 통합 앱 모바일과 알림

`참여할 일 / 받은 제안 / 내 약속 / 함께 확인한 결과` 진입을 활용한다. 예약 상세에는 필요한 당사자의 수락·조건·시간 약속과 현재 시작 준비를 표시한다. 취소 화면은 영향받는 단계·일정과 비용/기대의 구분을 먼저 보여주고 `시간 조정`, `대체 담당 제안`, `취소`를 선택하게 한다. 별도의 과도한 경고나 공개 비난을 기본으로 두지 않는다.

실제 자료가 아닌 설명 예: “이 공급 약속을 취소하면 연결된 입고와 수령 일정의 재확인이 필요합니다. 대체 공급이 합의되면 일부 일정을 유지할 수 있습니다. 추가 비용은 확인 중입니다.” 개인별 금액·민감 사유를 다른 참여자에게 그대로 보여주지 않는다.

변경 알림은 저장된 상태 변화만 원천 사건/Outbox에 결속하고 직접 영향받는 당사자에게 보낸다. 전문 원장별 저장 경계가 다르므로 Mongo와 SQL 전체를 한 트랜잭션이라고 가정하지 않는다. 알림 의도의 중복을 막고 재시도하되 네트워크 도착을 정확히 한 번이라고 약속하지 않는다. 현재 음식/창고/화물 중심 단계·경로 허용목록에 새 공동운영 변경을 명시적으로 추가·검증해야 한다.

휴대폰 알림에는 “예약 조건이 변경됐어요. 앱에서 확인해 주세요.” 정도를 보여주고, 본인 권한을 재확인한 앱 상세에서 일정·영향·대안을 확인한다. 알림 발송·도착·열람·변경 동의·실제 재예약은 별개 상태다. 실제 통합 앱 APK에서 계정별 제안/예약·취소 전/후·알림 진입·판본 충돌·재실행/통신 복구를 검증한다.

## 6. 구현 권고와 미정

첫 범위는 생산자 한 곳·공간 한 곳·입고 담당·주문자 소수의 한 회차다. 사전 의향 → 조건부/확정 약속 → 의존관계 → 취소 전 영향 조회와 대안 → 명시 변경과 관련자 알림 → 실제 결과의 기대 대비 확인 순으로 구현한다. 전문가별 실제 재고·고용/근무·배차·정산 권위는 유지한다.

추가할 공통 책임은 사전 참여/약속 연결, 약속 의존관계, 취소 영향 조회·변경 확인, 성과 비교 조회다. 알림은 기존 전달 체계에 연결한다. 공급 최소량·예약 마감·변경 유예·취소 조건·비용/책임 검토 주체·금액 산식·공개 범위는 미정이다. 알림이나 화면을 만드는 승인이 금전 제재·자동 책임 판단·실제 운영 중개/청구의 승인은 아니다.
