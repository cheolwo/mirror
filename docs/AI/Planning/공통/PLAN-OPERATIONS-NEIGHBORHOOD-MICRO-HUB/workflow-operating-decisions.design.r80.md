- 기준 구현: [r76](workflow-exception-closeout.implementation.r76.md). 기존 제품 코드·권한·운영·지급은 변경하지 않는다.

## 확정한 답변

- 질문 의미 ID: `reported-delivery-issue-release-authority`
- 이전 상태: r79의 `Asked / Unanswered`
- 현재 상태: `Answered / SupportTriageAccepted / FinancialAuthorityOpen`
- 사용자 답변 원문: **“신고하는 경우에는 그 운영자가 일단은 한번 검토를 해봐야지. 운영자가 검토를 간단하게 그 고객센터 상담원이 일단은 그 문제 상황을 좀 인지를 하고 어떻게 할지 처리를 하는 식으로 만드는 게 좋겠다라는 생각이 있어.”**

고객이 신고하면 고객센터 상담원이 먼저 문제 상황을 파악하고 간단히 검토한 뒤 처리 방향을 정리하고 필요한 조치를 이어가는 방향을 수용했다. 신고 접수 후 해당 주문의 미지급 정산 보류는 r79에 따라 유지한다.

운영 검토를 별도의 추상적인 대기 상태로만 두지 않고, 상담 담당자가 현재 문제·필요한 확인·다음 조치를 인지하고 맡는 업무로 기획한다. 여기서 고객센터 상담원은 업무 책임의 표현이며, 기존 계정에 새 역할이나 금융 권한을 자동 부여하는 승인이 아니다.

## 접수에서 처리까지의 흐름

```text
고객 문제 신고
├─ 해당 주문의 미지급 정산 보류 [r79]
└─ 고객센터 상담원의 1차 검토 [r80]
   ├─ 신고 내용·현재 주문/배송 상태 확인
   ├─ 허용된 전달 증빙·고객과 수행자의 설명 확인
   ├─ 부족한 사실 확인·처리 방향 정리
   └─ 가능한 조치 안내 또는 해당 업무 담당자에게 인계
      └─ 후속 처리 상태·결과 안내를 별도로 기록
```

상담의 질문은 ‘지금 어떤 문제가 있고, 무엇을 확인해서 어떤 조치로 이어갈까?’다. 초기에는 신고 내용·현재 상태·전달 근거·당사자 설명·다음 조치가 중심이 되며 모든 원장과 기술 진단을 나열하는 화면을 가정하지 않는다. 실제 상담 화면·버튼·권한은 아직 구현하지 않는다.

상담 배정·자료 확인·처리안 안내·업무 인계와 실제 재배송·환불·정산 보류 해제·송금은 각각 별도 결과다. 상담을 완료했다고 주문이나 금융 결과까지 완료한 것으로 처리하지 않는다. 기존 [역할별 업무 트리](../../../../ProjectOverview/page-docs/role-workflow-tree-r76.md)의 전문 원장·지원 사건·금융 분리와 일치시킨다.

## 이번 답변으로 정하지 않은 범위

- 상담원이 정산 보류 해제·환불·추가 비용·책임 부담을 직접 확정할 수 있는 권한과 상한.
- 운영자와 상담원이 같은 사람인지, 여러 담당자로 나눌지 및 구체적인 계정 권한.
- 증빙 충분성·책임 판정·검토 기한·재심/이의·연락 두절 시 최종 처리 기준.
- 새 비용·기지급 회수·실제 송금·타 업무의 권한을 일괄 변경하는 정책.

r78의 무응답 정산 방향, r79의 실제 신고 시 보류와 일부 선지급 미확정 상태는 유지한다. 상담원이 신고를 검토한다는 답변을 모든 금융 결정권의 승인으로 확대하지 않는다. 반대로 상담원이 어떤 처리를 할지 논의할 가능성도 닫지 않으며 다음 문답에서 범위를 정한다.
