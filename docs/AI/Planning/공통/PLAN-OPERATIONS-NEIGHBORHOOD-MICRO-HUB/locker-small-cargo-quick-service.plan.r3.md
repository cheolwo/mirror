# 전자 사물함 픽업 기반 소형 화물·퀵서비스 r3

- 기준일: 2026-09-24
- 상태: 서비스 방향 확인 / 상세 미정 / 기획만
- 선행: [전자 사물함 제안 r2](building-managed-lockers.proposal.r2.md)

## 확정한 의도

건물 관리업체가 전자 사물함의 위치를 거점으로 등록하고, 기사가 그곳에서 물건을 픽업해 지정 수령지로 전달하는 소규모 화물·퀵서비스를 지향한다. 음식 배달처럼 픽업·전달 경험은 간단하게 하되 음식 주문이나 조리 단계에 종속시키지 않는다. r2에서 제안한 동네 상점의 상품 판매를 필수 출발점으로 확정하지 않는다.

관리업체는 우선 사물함 거점 등록·관리 주체다. 위치 등록만으로 운송 주문·배차·기사 출입 권한이 자동 생성되는 것은 아니다. 보내는 사람의 운송 의뢰와 기사의 수락을 별도 흐름으로 둔다. 기존 화주/화물 의뢰·인계 기능을 재사용할 후보로 삼되 코드 적합성은 후속 대조한다. 새 OS나 앱을 지금 생성하지 않는다.

## 간단한 서비스 흐름

관리업체의 사물함 거점 등록 → 보내는 사람의 해당 거점 출발 운송 의뢰 → 기사 수락 → 허가된 칸에서 픽업·인수 확인 → 지정 수령지 전달·수령 확인.

사물함에서 수령인에게 보내는 방향을 먼저 다룬다. 사물함 간 운송, 반품, 상시 재고 판매는 이번 발언만으로 추가 확정하지 않는다. 물건이 실제 준비되었는지 확인하는 방법과 운송 의뢰 시점은 상세 설계에서 정한다.

## 미정과 보호 경계

등록 화면은 위치 중심으로 간단하게 시작하되 실제 픽업에는 담당자·접근 가능 시간·사물함/칸 식별·장비 연동 여부 등 필요한 최소 정보가 별도로 확인되어야 한다. 정확 위치의 공개 범위와 일회성 개방 권한은 구분한다. 문 열림은 물건 인수 완료가 아니다.

허용 크기·중량·품목, 이용 차량, 거리·요금, 비용 부담, 물건을 넣는 사람과 시점, 미수거·고장·분실 대응은 미정이다. 기존 r1의 비주거/Simulation 한정과 실운영·실제 지급 비활성은 바꾸지 않는다. 실제 설치·운송 관련 운영 요건은 별도 검토하며 이번에 적법성이나 수익성을 판단하지 않는다.

다음 질문 하나: 첫 이용자는 개인과 사업자 모두 운송을 의뢰할 수 있게 열어 둘까? 제안은 의뢰자 유형을 고정하지 않고 첫 검증 대상만 한 유형으로 좁히는 것이다. 사용자 답변 전에는 확정하지 않는다.

이번에는 기획 문서만 변경했다. 코드·DB·Unity·장비 연동·외부 조사·실행 시험·commit·push 없음. 새 디오라마 규칙 후보 없음.
