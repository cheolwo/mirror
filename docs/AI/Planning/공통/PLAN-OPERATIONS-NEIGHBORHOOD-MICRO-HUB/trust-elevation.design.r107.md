## 사용자 방향과 확정 범위

당사자가 서로 신뢰할 수 있으면 플랫폼이 대금을 보관하지 않고 직접 계좌이체로 거래할 수 있는 흐름을 지향한다. 거래에서 쌓인 신뢰는 간괘의 산 이미지에서 영감을 얻어 **신뢰의 높이**로 표현한다. 사용자를 특정 산에 고정하지 않고 현재 높이를 국내외 실제 산의 높이와 비교한다. 이는 실제 GPS 고도나 금융기관의 신용점수가 아니다. 괘의 상징을 업무 권위·자동 판단·게임 기능 승인으로 해석하지 않는다.

사용자는 다음 질문에 **“상호 완료·대금 수령 확인 후 상승”**으로 답했다.

- 유상 거래: 양측 거래 완료 확인과 대금 수령 확인이 모두 갖춰진 뒤 상승 대상으로 인정한다.
- 나눔·교환: 지급할 대금이 없으므로 양측의 약속 이행 확인을 사용한다.
- 송금했다고 한쪽이 신고한 것, 배송 기사의 전달 완료, 주문 제출, 게시글 작성만으로 높이를 올리지 않는다.
- 상대방 미응답은 확인 대기이며 자동 부정 평가로 바꾸지 않는다. 기존 지원·정정 절차와 연결할 후속 규칙은 미정이다.

후속 질문 **“거래 금액이 달라도, 약속 한 건을 지킨 가치는 같은 기준으로 평가하는 방향이 좋을까요?”**에 사용자는 **“그래 뭐 그런 것도 나쁘지 않지.”**라고 답했다. 거래 금액에 가중치를 두지 않고, 확인된 약속 이행을 같은 기본 기준으로 평가하는 방향을 수용했다. 이는 건당 상승량이나 모든 역할/업무의 동일 가산량까지 확정한 답변은 아니다.

이전 2026-10-17에는 상품 종류나 수량이 다르면 같은 상대와도 계속 신뢰를 쌓고 같은 조건 반복은 일주일 세 번 정도 인정하는 방향이었다. 이 예외는 아래 **2026-10-19 동일 두 사람의 주간 총3회 방향**으로 대체한다. 과거 답변과 예시는 이력으로 보존하며 현행 예외로 재사용하지 않는다.

상승 자격·금액 중립·일주일 기간과 최신 동일 두 사람의 주간 총3회 정도 인정 방향을 확정했다. 거래당 상승량·최초 표시 조건·반복 집계 경계·확인된 약속 위반의 조정·이의제기·유효 기간·역할별 표시 범위는 미정이다. 실제 계좌 검증이나 지급 보증을 새로 제공하는 결정도 아니다.

기존 r105의 **상품·음식 대금 직접 거래 / 서비스비 플랫폼 수납 준비**를 모든 역할의 직접 지급 기본값으로 일괄 변경하지 않는다. 이번 방향은 당사자가 선택하는 직접 거래와 그 신뢰 표현을 구체화한다. 기존 금융·자동 지급·운영 플래그를 변경하지 않는다.

## 2026-10-19 보충 — 서로의 거래와 약속을 알아봐 주는 미러

사용자는 미러 안에서 거래를 시작하거나 대금을 결제·수납·정산하지 않아도 거래 증빙과 당사자의 거래 사실을 확인해 신뢰에 반영할 수 있기를 원했다. 산·빛·거울의 이미지를 통해 **사람들이 서로 지킨 약속과 실제 교류를 알아볼 수 있도록 비춰 주는 공간**이라는 미러의 방향을 보충했다.

따라서 직접 이체 등으로 미러 밖에서 시작·완료한 거래도 사후에 등록하고 확인 이력의 원천으로 다루는 방향을 수용한다. 미러가 돈을 받거나 정산했다는 사실은 이 경로의 신뢰 인정 필수 조건이 아니다. 기존 상품대금·배송 보수·서비스비·주간 정산 원장을 없애거나 모든 역할의 지급 방식을 바꾸는 결정으로 확대하지 않는다.

사용자에게 보이는 설명은 `미러`, `교류 공간`, `서로 확인한 거래`, `지켜진 약속`, `신뢰의 근거`를 중심으로 다듬는 방향이다. 이번 발언을 프로젝트 이름·코드 식별자·전역 용어의 일괄 교체 지시로 보지는 않는다. 간괘·산·빛·거울은 관계를 표현하는 영감이며 거래 검증 권한·실제 은행 확인·금융 신용평가·지급 보증을 대신하지 않는다.

기본 흐름은 다음과 같이 제안한다. 기존 상호 확인 원칙은 유지하고 외부 거래의 등록·증빙 형식은 후속 설계로 남긴다.

```text
미러에서 시작한 거래 또는 사후 등록한 외부 거래
→ 어떤 약속과 거래였는지 기록
→ 같은 거래에 필요한 증빙·당사자 확인 연결
→ 양측 거래 완료 확인
→ 유상 거래라면 받는 쪽의 대금 수령 확인
→ 같은 원거래의 중복·변경 이력 대조
→ 신뢰 반영 자격 판정
→ 별도로 정할 계산 정책에 따라 신뢰의 높이·확인된 이력 표시
```

- 증빙 제출·상대 확인·신뢰 반영·공개 표시는 서로 다른 상태다. 자료를 올렸다는 사실만으로 거래가 확인됐거나 점수가 올랐다고 표시하지 않는다.
- 현재 승인된 기본은 유상 거래의 상호 완료·받는 쪽 대금 수령 확인, 나눔/교환의 상호 약속 이행 확인이다. 한쪽 송금 신고나 사진 한 장을 이 확인 대신 사용하도록 이번에 승인한 것은 아니다.
- 이체 내역·사진·영수증·거래 대화 등 어떤 형식의 자료를 허용하고 무엇을 필수로 요구할지는 아직 미정이다. 받는 쪽 수령 확인과 실제 은행 검증도 구분한다.
- 하나의 거래에 연결된 주문·배송·입금·증빙 추가·정정은 같은 원거래를 가리키게 한다. 사진/파일 수나 기록 경로 수를 거래 수로 늘려 신뢰를 중복 가산하지 않는다. 사후 외부 거래의 식별·상대 연결·중복 판정 세부 규칙은 후속이다.
- 거래의 공개에는 기존 당사자 동의와 최소 공개 기준을 유지한다. 증빙 원본·계좌·주소·사적인 대화·상대 이름/관계망을 신뢰 표시 때문에 자동 공개하지 않는다. `당사자들이 확인한 거래`를 미러의 전수 사실 검증이나 지급 보증으로 표현하지 않는다.
- 신뢰에 반영할 개인 이력과 AI 배차 판단을 분리한다. 이번 방향만으로 점수가 높은 사람에게 자동 배차 우선권을 주거나 점수가 낮다는 이유로 업무를 막는 정책은 만들지 않는다.

이번 보충은 기획 기록이다. 외부 거래 접수·증빙 업로드·새 신뢰 원장/점수·화면·계좌 조회·결제/정산·모델 학습을 구현하거나 실행하지 않았다. 배차 매뉴얼 r69의 지원 요청 수신 동의 질문에도 답변한 것으로 해석하지 않는다.

## 2026-10-19 보충 — 동일 두 사람의 주간 총3회 인정 후 배차 논의로 복귀

사용자는 악용을 줄이기 위해 같은 두 사람이 거래했다는 기록은 **일주일 단위로 총3회 정도만 신뢰에 인정**하는 것으로 우선 정하고, 나머지는 여기서 멈춘 뒤 AI 배차 알고리즘부터 논의하도록 요청했다.

- 상한의 단위는 같은 두 사람 사이의 관계다. 이전의 상품 종류/수량이 다르면 계속 가산한다는 예외보다 이 주간 총량 방향을 우선한다. 상품명·수량·업무 역할을 바꿔 같은 관계의 신뢰 인정 한도를 새로 여는 규칙을 유지하지 않는다.
- 이는 **신뢰 반영 횟수**의 제한이며 실제 거래 횟수를 막거나 초과 거래의 정상 완료 기록을 지우는 결정은 아니다. 쌍방 확인 등 기존 자격을 갖춘 거래에 적용하는 상한 방향이다.
- 하루 한 번~두 번이라는 발언은 범위로 보존하며, 고정 일1회 또는 일2회 제한을 임의로 선택하지 않는다. 달력 주/최근7일, 날짜 경계와 실제 집계·정정 세부 기준도 미정이다. `총3회 정도`를 기획 방향으로 기록했으며 구현/운영 수치를 활성화하지 않았다.
- 증빙 파일 첨부 필수 여부·점수 상승량·상대 확인 방식 등의 질문은 미정 보류한다. 이 발언을 앞선 증빙 첨부 질문의 찬성 답변으로 바꾸지 않는다.
- 다음 주제는 [AI 배차 판단 매뉴얼 r69](../PLAN-OPERATIONS-DISPATCH-CORE/dispatch-decision-manual.design.r69.md)이다. 거래 신뢰의 이 주간 상한을 배차 우선권이나 기사 자격에 자동 연결하지 않는다.

## 기존 원장과 실제 공백

| 책임 | 기존 근거와 재사용 범위 |
| --- | --- |
| 약속과 거래 완료 | `생활협업UseCase.cs`의 완료 제안→반대 당사자 완료 확인, 조건 판본·CAS·멱등 요청을 재사용 |
| 직접 지급 사실 | `NeighborhoodSettlementUseCase.Payments.cs`의 송금 신고→받는 쪽 부분/전액 수령 확인을 재사용. `IsActualBankVerified=false`와 실제 은행 확인을 구분 |
| 배송·보관 완료 | 전문 원장의 완료 권위를 조회하며 거래 완료와 중복 집계하지 않음 |
| 공개 이력 | 완료 상태+모든 당사자의 공개 동의 경계를 보존. 점수나 합계가 새로운 공개 정보가 되는 범위도 별도로 결정 |
| 지원 사건 | 신고·검토·결과 안내·종결·이의제기를 유지. 사건 종결/기각 수를 귀책 확정이나 자동 감점으로 사용하지 않음 |
| 커뮤니티 상징 | 기존 `CommunityActivityBoardBundleDefinition.MountainSymbol/MountainName`의 간·산 상징이 있음. 공개 주간 활동 집계는 개인 신뢰 원장이 아니므로 점수 원천으로 재사용하지 않음 |

실제 연결 공백은 다음과 같다.

1. `NeighborhoodSettlementSourceResolver`는 분산입고/분산주문·운송·음식·마트를 지원한다. 일반 생활협업 자체의 상품대금 확인에는 기존 원천을 연결하는 어댑터가 필요하다. 협업 완료를 대금 수령 확인으로 대신하지 않는다.
2. 일반 MAUI의 `/community/me` 본문은 로그인 상태와 무관하게 방문자로 고정돼 있다. Web의 인증된 개인 화면과 같은 신원·정본 조회를 맞춘 뒤 신뢰를 붙여야 한다. r106의 상단 사람 아이콘 수정은 본문 인증 연결 완료가 아니다.
3. 개인 신뢰 집계와 산 표시 카탈로그는 아직 구현돼 있지 않다. 공개 게시글·친구 수·비식별 주간 집계를 개인 신뢰 점수로 변환하지 않는다.

## 최소 책임 분리 제안

```text
기존 주문/생활협업 원장
├─ 약속 조건과 양측 거래 완료
├─ 배송·보관 전문 원장의 근거
└─ 직접 지급 약정 → 송금 신고 → 수령 확인
          ↓ 같은 원천 ID·조건 판본·완료 결과를 대조
신뢰 근거 조회/투영
├─ 중복 없는 완료 사실과 정정 이력
├─ 실제 은행 확인 여부와 당사자 확인 구분
└─ 공개 가능 범위와 확인 대기
          ↓ 버전이 있는 미정 계산 정책
신뢰의 높이
          ↓ 실제 산 사실 카탈로그와 비교
프로필/거래 전 상대 정보의 표시 전용 카드
```

산 카탈로그에는 사용자의 거래·계좌·신뢰를 저장하지 않는다. 전문 원장의 사실을 프로필이 직접 수정하지 않으며, 주문·배송·정산으로 연결된 한 거래를 여러 번 가산하지 않는다. 산 높이 자료의 정정도 사용자 신뢰 자체를 변경하지 않는다. 표시된 높이만으로 직접 지급을 강제하거나 배차·이용 권한을 자동 제한하지 않는다.

## 계산 정책에서 다룰 항목 — 제안, 미확정

- **확정 방향:** 양측 확인된 약속 이행을 거래 금액과 무관한 같은 기본 기준으로 평가한다. 재산·지역·친구 수 등 별도 가중치도 승인한 것이 아니다.
- **현행 반복 인정 방향:** 동일 두 사람 사이에서는 상품/수량 차이와 관계없이 일주일에 총3회 정도만 신뢰 반영 대상으로 인정한다. 처음 거래를 포함한 주간 총량 방향이며 실제 거래 제한은 아니다. 하루1~2회 언급의 정확한 상한·달력 주/최근7일·집계/정정 세부 기준은 미정이고 운영 수치를 활성화하지 않는다.
- 새 회원은 낮은 신뢰로 단정하지 않고 **아직 확인된 거래 기록이 없어요**로 표현한다.
- 신고 접수만으로 높이를 깎지 않는다. 귀책을 확정할 근거·정정/이의제기·적용 시점이 마련되기 전 자동 감점은 구현하지 않는다.
- 거래 금액·대금 지급·수령·지원 사건의 민감한 상세는 공개하지 않는다. 상대방 이름이나 관계 그래프를 점수 설명 때문에 새로 공개하지 않는다.
- 표시 높이와 별도로 확인 거래 수·집계 기간·정책 판본 등 이해 가능한 근거를 제공한다. 전수 기계 검증이나 지급 보증처럼 표현하지 않는다.

### 반복 거래의 구분 예시 — 2026-10-17 이력, 현행은 주간 관계별 총량 우선

**아래 표의 상품/수량별 계속 인정은 이전 방향의 이력이다. 현행에서는 서로 다른 상품/수량의 독립 거래도 동일 두 사람 사이 주간 총3회 정도의 공통 상한 안에서만 신뢰 반영 대상으로 삼는다.** 원거래 재전송·정정을 새 거래로 만들지 않는 원칙은 유지한다.

모든 예시는 기존의 상호 완료 확인과 유상 거래의 대금 수령 확인을 충족한 **독립된 실제 거래**를 전제로 한다. 같은 주문/거래의 재전송·판본 변경은 새 거래가 아니다.

| 같은 상대와의 상황 | 수용된 방향과 남은 경계 |
| --- | --- |
| 사과 거래 뒤 배 거래 | 상품이 다른 별도 거래이므로 계속 상승 대상으로 인정 |
| 사과1kg 거래 뒤 사과2kg 거래 | 실제 수량이 다른 별도 거래이므로 계속 상승 대상으로 인정. 양이 두 배라고 상승량을 두 배로 확정한 것은 아님 |
| 사과1kg의 같은 조건을 반복 | 일주일에 총3회 인정하는 방향. 달력 주/최근7일의 집계 경계·초기 포함 해석은 구현 전에 확인 |
| 같은 거래의 완료 요청을 재전송 | 기존 거래 ID/결과 판본으로 한 번만 집계 |

| 한 주문 안의 여러 상품 행 | 상품 행 수를 거래 수로 늘리지 않음. 분할 거래의 실질 판정 규칙은 후속 |

수량은 같은 단위로 비교해야 하므로1kg과1000g을 다른 수량으로 취급하지 않는다. 동일 상품의 범위를 상품 ID·메뉴·규격·옵션·카테고리 중 무엇으로 판단할지, 같은 기간 안에서 어떤 조건별 묶음에3회를 적용할지는 후속 기획이다. 단순 명칭 유사도나 AI 추정만으로 거래를 묶어 신뢰를 제한하지 않는다.

## 구현 순서 제안과 다음 질문

1. 현재 인증된 사용자에 맞춰 모바일/Web 개인 화면의 조회 책임을 통일한다.
2. 일반 생활협업의 대금 약정·수령 확인을 기존 지급 원장에 연결하고 상호 완료와 함께 읽는다.
3. 사용자와 상승량·반복 거래·문제 정정 규칙을 정한 뒤 신뢰 근거 투영과 정책을 구현한다.
4. 공식 산 카탈로그를 검토 저장·재조회하는 수집 어댑터와 표시 전용 카드를 붙이고, 처음 이용/미응답/부분 지급/취소·환불/신고·정정/중복 요청/공개 동의 철회를 검증한다.

반복 거래의 기간 질문은 **“일주일”**로 `Answered / PeriodAccepted`다. 이전 질문 **일주일은 거래 시점의 최근7일로 볼까요, 매주 월요일~일요일로 끊을까요?**는 `Asked / Unanswered`로 유지한다. 당시 최근7일을 제안했지만 이번 외부 거래 방향 발언은 집계 경계의 답변이 아니다. 집계 경계와 중복3회의 정확 묶음은 아직 확정하지 않았다.

증빙 질문 `trust-external-evidence-attachments-required / Asked / Unanswered / DeferredForDispatch`는 보류한다. 사용자가 이 주제는 관계별 주간 총3회 방향까지만 정하고 AI 배차로 복귀하도록 요청했다.

> 외부 거래도 양쪽의 거래 완료 확인과 유상일 때 받는 쪽의 대금 수령 확인을 기본 증빙으로 삼고, 영수증·이체 내역·사진 첨부는 필요할 때 보충하는 방식으로 할까요?

이는 이전의 상호 확인 자격을 다시 정하는 질문이 아니라, **사후 외부 거래에서 파일 첨부를 필수로 요구할지**를 정하는 질문이다. 첨부 없이 상호 확인한 기록의 인정과 실제 은행/외부 기관 검증은 다르다. 상대가 미러를 이용하지 않을 때의 확인 방식·확인이 충돌하는 경우·최소 기록 항목·중복 탐지는 후속이다. 확정 상승량·운영/결제 기본값·원장/개인정보 공개 범위·자동 배차·Unity·commit/push 승인을 이 문서가 대신하지 않는다.
