- 사용자 답변 원문: **“근데 그냥 회사 내에서도 그냥 건물주분들한테 그냥 입고를 하는 거지 뭐. 나랑 그냥 서포트용만 좀 제공을 하는 거고. 그래서 내가 뭐 이렇게 크게 자본이 필요 없게끔 만드는 게 중요할 것 같네.”**

## 수용한 방향

- 질문 의미 ID: `presale-receiving-storage-funding-owner`
- 이전 상태: r86의 `Asked / Unanswered`
- 현재 상태: `Answered / LowCapitalSupportAccepted / SpecificCostPayerOpen`

물품을 맡기는 업체와 공간 제공자가 직접 입고·보관 조건을 협의하고, 플랫폼은 그 업무를 지원하는 방향으로 해석하여 수용한다. 플랫폼이 물품을 매입하거나 창고를 직접 확보하거나 입고·보관비를 선지급해야만 이용할 수 있는 구조를 필수로 두지 않는다. 큰 재고·시설 자본을 플랫폼이 먼저 투입하는 것을 기본 모델로 삼지 않는 것이 이번 답변의 핵심이다.

구체적인 유상 비용 부담자와 지급 시점까지 이번 답변으로 확정하지는 않는다. 업체가 항상 물품 소유자라고 가정하지 않으며, 건물주·공간 제공자와 실제 입고·피킹·포장 작업자도 구분한다. 한 사람이 여러 역할을 맡을 수 있어도 제공 공간·실제 수행 업무·보수 근거를 합치지 않는다.

| 주체 | 기본 역할의 제안 |
| --- | --- |
| 물품을 맡기는 쪽 | 권한 있는 물품 등록, 입고·보관·회수 조건 제안, 합의한 비용 부담 |
| 공간 제공자 | 수용 가능 품목·공간·시간 제시, 입고·보관 조건 동의 |
| 실제 작업자·기사 | 합의한 입고·피킹·포장·배송 수행과 수량·사진 등 근거 기록 |
| 플랫폼 | 조건 협의·재고 기록·업무 제안/인계·배송 연결·보수/정산 내역을 돕는 소프트웨어 제공 |

이 역할표는 후속 설계 방향이다. 새로운 계정·금융 권한이나 실제 계약 책임을 자동 부여하지 않는다. 지원 중심이라는 사업 방향만으로 플랫폼의 모든 운영 책임이 없어지는 것으로 설명하지 않는다.

## 기존 원장·재원 기획과의 연결

[r63](supplier-space-inbound.implementation.r63.md)은 이미 물품 소유자와 공간 소유자가 같은 조건 판본에 동의하고 입고 예약을 확정하는 구조다. 업체·공간 제공자의 직접 협의를 이 구조에 연결하며, 예약만으로 재고나 작업 보수가 생긴 것으로 처리하지 않는다. 실제 사진·수량 근거와 완료 업무가 입고·보관 보수로 연결되는 경계를 유지한다.

[r60](receiving-outbound.implementation.r60.md)의 입고·보관과 출고·배송 분리, [r61](settlement-economics.implementation.r61.md)의 원가 귀속·기본 보수·성과금 분리는 보존한다. 지원 중심으로 방향을 정했다고 기존 계약의 지급 의무나 완료된 작업 보수를 지우지 않는다.

r86의 ‘플랫폼이 지급하는 신규 일감은 재원을 확보한 뒤 제안’ 원칙은 **그 지급 방식이 선택된 일감에만** 유지한다. 업체가 직접 지급하기로 한 업무까지 플랫폼 중앙 수납·선입금·지급 보증을 필수화하지 않는다. 주문자 결제금을 해당 주문의 재원으로 연결하는 선택 경로도 그대로 두되, 이 입고 모델에 무조건 적용하지 않는다. 실제 수금·지급 주체와 확인된 지급 내역은 별도로 기록할 대상이다.
