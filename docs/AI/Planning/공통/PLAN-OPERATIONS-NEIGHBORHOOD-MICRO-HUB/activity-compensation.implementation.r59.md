`PLAN-OPERATIONS-NEIGHBORHOOD-MICRO-HUB / r59 / Implemented / LocalValidated / OperationalDeferred`

2026-10-12 사용자가 기존 원장 구조를 활용해 앞서 제안한 1~5번을 리팩토링하고 필요한 기능을 추가하도록 직접 요청했다. 이 문서는 같은 작업실의 현재 요청을 수용한 구현 범위다. 다른 작업실의 미승인 인계를 수용하거나 운영을 활성화하는 문서가 아니다. [작업 명세](activity-compensation.r59.work-order.json)와 [검증 반환](../../../../Changes/2026-10-12-activity-compensation-r59.md)을 따른다.

## 원칙과 현재 범위

| 원칙 | 기존 구조 재사용과 보완 |
| --- | --- |
| 상품·수량별 업무 의존성 | 기존 입고·예약·피킹·전달·고객 수령 관문을 유지한다. 새 상태 머신을 중복 생성하지 않는다. |
| 실제 수행자와 기여 기록 | 기존 완료 영수증에 주문·예약·Lot·실제 재고 이력·처리자·수량·사진·원주문 참조의 보호된 행별 근거를 더한다. 묶음 피킹의 실제 행을 주문별로 읽는다. |
| 기본 보수와 추가 성과금 분리 | 기존 작업비 약정·발생·확인·지급 신고·수령 확인을 유지하고 별도 `ActivityReward` 발생 항목을 추가한다. 기본 보수는 판매 성과금이나 고객 수령에 새로 종속시키지 않는다. |
| 합의한 잉여와 배분 정책 | 지급자·참여자·정책 판본·활동별 가중치·배분 비율·수익/기본 작업비/기타 비용/예비금 근거를 같은 약정 판본에 동의한다. 모르는 값은 null이고 임의 비율은 제공하지 않는다. |
| 본인 활동·정산 확인 | WebApp와 일반 살뜰 앱의 목록/상세 경로에서 본인 항목과 다음 행동을 확인한다. 타인의 개별 금액·사진 근거는 서버에서도 제한한다. |

활동별 보수는 기존 `Free / Fixed / PerUnit / StoragePeriod` 등 합의 기준을 따른다. 특정 고용 형태나 시급을 소프트웨어가 일률적으로 대체·판정하지 않는다. 실제 농장 업무, 일반 작업자 위임·모집은 이번 완료 범위에 포함하지 않는다.

## 공동 성과금 계산

`잉여 = max(0, 합의 수익 - 기본 작업비 - 기타 비용 - 예비금)`

`성과금 풀 = floor(잉여 × 합의 배분율 / 100)`

`개인 점수 = Σ(원주문에 귀속된 완료 수량 × 사전 합의 활동 가중치)`

풀을 개인 점수 비율로 나누고 정수 원 미만의 잔여는 큰 소수 잔여 순서, 동률이면 안정된 사용자 식별 순서로 배분한다. 동일인이 여러 역할을 수행하면 합산하며 풀과 배분 합계는 정확히 일치한다. 풀 자체의 1원 미만 잔여도 별도로 보존한다.

첫 연결은 `DistributedOrder / StoredGoods`와 `SimulationPartyStatement` 경제 진술에 한정한다. 수익·비용 근거는 당사자 합의 입력이며 실재원·은행 대사·확정 영업이익을 인증하지 않는다. 같은 지급자의 알려진 기본 작업비 약정 합계를 줄여 잉여를 부풀리는 입력은 보류한다.

## 발생과 보호

최신 약정 판본에 필요한 당사자 모두 동의하고, 현재 원천 판본·정책·최종 고객 수령·주문별 수행자/수량/시각/사진 근거가 있어야 계산한다. 입고·피킹 활동의 합계가 최종 수령 수량과 다르면 보류한다. 기본 작업비는 기존 완료 근거로 독립 발생한다.

미리보기의 계산 지문과 약정 Revision을 명령에 결속한다. 원천·기여가 바뀌면 다시 조회해야 한다. 같은 요청은 같은 영수증을 반환하고 동일 원주문의 성과금은 다른 약정·판본에서도 다시 발생시키지 않는다. 계산 결과와 근거는 영수증에 동결하며 이후 정책 변경으로 과거 금액을 조용히 재계산하지 않는다. 조정은 기존 별도 조정 항목을 사용한다.

입고·보관은 새 영수증에도 실제 사실을 보존하지만, 최종 주문별 귀속이 없는 Lot 전체 실적을 여러 주문에 반복 배분하지 않는다. 구형 묶음 영수증도 주문별 수량을 추정하지 않는다. 해당 활동을 성과금 대상으로 설정했는데 정확한 연결이 없으면 `WaitingForEvidence`다. 보관 수량×일의 주문별 배분은 후속이며 현재는 보류한다.

## 화면·서버·저장 책임

[페이지·코드·DB 책임](../../../../ProjectOverview/page-docs/activity-settlements-r59.md)에 실제 경로와 역할을 정리한다. 새 정산 테이블을 늘리지 않고 기존 약정·판본·항목·지급·명령 영수증을 재사용한다. `distributed_receipts.CompletionLinesJson`만 nullable 보호 컬럼으로 추가하며 완료 뒤 수정하지 않는다. 공용 DB에 migration을 적용하지 않는다.

운영 기능은 기존 `NeighborhoodSettlement.Enabled=false`, 정확한 `neighborhood-settlement-r38` profile·Simulation·관계형 DB 관문을 유지한다. Unity·실제 알림·송금·기기 설치·Azure·운영 활성화·commit/push는 이번 범위가 아니다. 로컬 구현, 시험, 실제 화면 사용, 단말·실운영은 별도 증거다.
