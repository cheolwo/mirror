## 1. 대조 결과

직접 수령·직접 전달은 양측 합의와 완료 확인을 기존 협업 흐름으로 처리한다. 일반 회원 배송은 의뢰·제안·원자적 수락·사진 검증·응답 복구가 각각 구현돼 있다. 그러나 거래와 회원 배송을 한 흐름으로 이어서 끝내는 데 세 가지 막힘이 있다.

1. 사진 증빙이 있어야 서버가 `CanPickup` 또는 `CanDeliver`를 주는데, 화면은 이 값이 있어야 첫 사진 촬영을 연다. 같은 단계 조건에 묶인 픽업/전달 주소·연락처 카드도 첫 증빙 전에는 표시되지 않는다.
2. 회원 배송 입력은 `DispatchMode`를 금지하고, 협업 연결 입력은 같은 값을 필수로 요구한다. 협업 거래와 회원 배송을 함께 접수할 수 없다.
3. 회원의 전달 완료는 원의뢰의 `하차완료`까지만 기록한다. 협업은 `인수완료`를 요구하며 회원 배송의 수령 확인 명령은 확인되지 않았다. 2번을 고쳐도 이 연결은 별도로 보완해야 한다.

따라서 개별 구현과 기존 시험 통과를 일반 회원 거래의 전체 완료 증거로 사용하지 않는다. 현재 기능·Operational 기본 OFF를 유지한다.

## 2. 처음 운영할 때의 역할과 경계

준비된 환경에서 초대한 성인 3~5명, 생활 물품 하루 1~3건을 기존 최소 운영 단위로 사용한다. 이는 이번에 실제 참여자를 모집하거나 운영을 시작한다는 뜻이 아니다.

| 주체 | 맡는 일 | 구분해야 할 권한 |
|---|---|---|
| 제공자 A | 물품·수량·가능 시간·조건을 제시하고 실제 인계를 확인 | 글 등록만으로 배송 의뢰나 지급을 만들지 않음 |
| 구매·수령 당사자 B | 조건·수령 방법을 합의하고 실제 수령과 비용을 확인 | 의뢰 작성자와 수령자가 같은 계정인지 먼저 확인 |
| 본인 O | 운영자로 문제를 확인하고, 배송 참여자로 받은 유효 제안을 선택 | 운영자 권한과 건별 수행 권한을 분리 |
| 다른 배송 참여자 H | 본인에게 제안된 건을 수락하고 사진·픽업·전달 기록 | 다른 회원의 의뢰·상세정보를 임의 열람하지 않음 |

제안은 원의뢰 작성자에게 보내지 않는다. 본인이 배송할 첫 사례는 다른 회원이 작성한 의뢰에서 본인에게 온 유효한 제안을 수락하는 방식이어야 한다. 본인 의뢰를 운영자 권한으로 자신에게 강제 배정하는 명령은 현재 확인되지 않았다.

플랫폼·배차 수수료 0원과 배송 보수는 별개다. 거래대금, 확정 배송비, 비용 분담, 지급 신고, 상대방 확인, 실제 계좌 입금도 각각 구분한다. 배송 완료만으로 지급 완료를 만들지 않는다. 음식 주문·조리, 전문 화물 기사, 분산 창고 업무를 일반 회원 배송과 하나의 원장으로 합치지 않는다.

## 3. 정상 거래를 따라가는 세 가지 사례

### S01. 구매자가 직접 받기

1. **당사자 행동:** A와 B가 수량·시간·인계 장소·직접 수령·금액을 같은 조건 판본으로 합의한다.
2. **화면:** 협업 작성/상세에서 수령 방법과 합의 상태를 확인하고, 필요한 인계 정보 공유에 동의한다.
3. **서버·원장:** 양측 동의 → 시작 → 제공자의 완료 제안 → 상대방 확인으로 협업을 완료한다. 운송 의뢰와 배차 큐는 만들지 않는다.
4. **운영자:** 다툼이 있을 때 당사자의 실제 인계 여부와 합의 판본을 확인한다. 대신 수령이나 입금을 인증하지 않는다.
5. **결과:** 직접 거래 완료와 지급 확인은 별개다. 기존 코드와 직접 전달 시험으로 처리 가능함을 확인했으며 실제 현장 거래는 미검증이다.

### S02. 제공자가 직접 가져다주기

S01과 같은 양측 합의·완료 확인을 사용하되 인계 방법은 제공자 직접 전달이다. 제공자가 수령 장소를 확인할 수 있는 정보 공유 동의가 필요하다. 전문 기사·일반 회원 배송 의뢰를 자동 생성하지 않는다. 기존 시험은 제공 글/필요 글과 두 직접 인계 방법의 역할 조합을 포함한다.

### S03. 합의한 거래를 일반 회원이 배송하기

| 단계 | 당사자가 기대하는 화면·행동 | 현재 서버·원장 결과 | 판정 |
|---|---|---|---|
| 거래 조건 합의 | 협업에서 배송 방법·분담 비용을 확인 | 기존 협업 합의는 있음 | 개별 처리 가능 |
| 회원 배송 신청 | 합의 판본과 원의뢰를 연결해 한 번 접수 | 협업 연결의 필수 `DispatchMode`와 회원 배송의 금지 조건이 충돌 | 연결 보완 필요 |
| 제안·수락 | 본인 제안에서 보수·물품·기한 확인 후 수락 | 독립 회원 의뢰의 제안과 한 명 수락 보호는 있음 | 개별 처리 가능 |
| 첫 픽업 사진 | 촬영 → 전송 → 픽업 완료 | 증빙 없는 `Assigned` 응답에서 촬영 단계가 비어 있음 | 화면/서버 계약 보완 필요 |
| 첫 전달 사진 | 촬영 → 전송 → 전달 완료 | 증빙 없는 `PickedUp` 응답도 같은 조건 충돌 | 화면/서버 계약 보완 필요 |
| 실제 수령 | 수령 당사자가 배송 결과 확인 | 회원 `Delivered`는 `하차완료`; 협업 완료는 `인수완료` 요구 | 수령 확인 연결 필요 |
| 비용 확인 | 약정·수행·지급 신고·수령 확인을 구분 | 기존 정산 원천은 전문 `확정기사Id`를 사용하며 일반 회원 수행자 연결이 없음 | 정산 연결 필요 |

현재 S03을 실제 앱에서 완주했다고 보고하지 않는다. 운영자는 이 빈틈을 수동 완료·허위 사진·지급 완료 처리로 우회하지 않는다.

## 4. 문제 상황과 운영자 개입

### E01. 주변 참여자가 없거나 제안이 만료됨

- **화면/행동:** 참여자는 빈 제안 목록에서 설정·내 업무·새로고침을 볼 수 있다. 개별 만료 제안은 만료 상태를 표시한다. 의뢰자는 일반 대기 안내를 본다.
- **서버/원장:** 후보가 없으면 회원 의뢰는 `Pending`으로 남는다. 제안은 최대 5분 또는 더 짧은 원의뢰 시간 조건에 따라 만료하며, 제안 만료가 거래·의뢰 취소를 뜻하지 않는다.
- **제한:** 같은 의뢰에서 이미 제안한 회원에게 다시 제안하는 경로는 없다. 새로 자격을 갖춘 다른 회원은 fanout 실행 시 제안받을 수 있다. 회원 분기의 의뢰 상세는 기존 전문 배차의 조건/협업 복귀 영역도 표시하지 않는다.
- **운영자:** 대기 원인과 당사자 가능 시간을 확인하고 직접 인계나 시간 변경을 제안할 수 있다. 회원 전용 재모집·재예약 전환 명령이 구현됐다고 안내하지 않는다.
- **보완:** 후보 없음/전체 만료를 구분하고, 다음 선택과 필요한 재동의를 의뢰 화면에 연결한다.

### E02. 두 사람이 동시에 수락함

- **서버/원장:** 직렬화 트랜잭션, 활성 수행 슬롯, 조건부 큐 갱신으로 한 명만 확정한다. 다른 제안은 `AssignedElsewhere`로 읽힌다.
- **화면:** 충돌 시 최신 결과를 확인하고, 수락 응답 유실 시 같은 요청 ID와 GPS 자료로 재시도한다.
- **운영자:** 실제 확정 수행자를 조회한다. 늦게 도착한 화면이나 중복 알림을 이유로 두 번째 배정을 만들지 않는다.
- **판정:** 별도 SQL 컨텍스트 동시 수락 시험과 UI 응답 복구 시험이 있다. 실제 두 휴대폰 동시 시험은 하지 않았다.

### E03. 알림·통신·사진 전송이 실패함

- **알림:** 앱 제안 목록·조회 경로가 있다. 실제 Firebase 구성과 휴대폰 수신은 r43에서 보류했으므로 실제 푸시 성공을 전제하지 않는다.
- **통신:** 요청 ID와 영수증을 보존해 원요청 결과를 먼저 조회한다. 앱 재시작 후 서버 상태로 복구하고 중복 완료를 피하는 기존 시험이 있다.
- **사진:** 업로드 시작과 업로드 완료를 구분한다. 비공개 정규화 사진의 SHA-256·건·단계·판본을 검증하고 완료 시 다시 확인한다. 복구 저장소에는 원본 사진을 넣지 않으며 원본 없는 미완결 전송은 재촬영을 안내한다.
- **제한:** 이 보호는 E03의 개별 API/복구 경로에 대한 증거다. S03의 최초 촬영 진입 충돌을 해결해 주지 않는다.
- **운영자:** 성공 여부가 불명확하면 원의뢰와 원요청 결과를 확인한다. 사진 수신 실패를 픽업/전달 완료로 바꾸지 않는다.

### E04. 픽업 전 취소 또는 픽업 후 수행 중단

- **픽업 전:** 의뢰 작성자는 최신 판본으로 `Pending`/`Assigned`를 취소할 수 있다. 원의뢰·큐·회원 슬롯을 함께 갱신하며 취소 응답 유실 복구가 있다. 수행 회원의 임의 취소와는 다르다.
- **픽업 후:** 수행 회원은 문제를 접수하고 `Issue / AfterPickupRecoveryRequired` 및 지원 사건을 남긴다. 물품 책임과 활성 슬롯을 유지한다.
- **운영자 명령:** 관리자 API는 `Resume` 또는 `CancelBeforePickup`을 받는다. 같은 지원 사건의 종결과 당사자 통지 근거가 필요하다. 픽업 후 재개는 같은 회원의 `PickedUp`으로 돌아가 새 전달 사진을 요구한다. 수락 후 72시간이 지난 재개는 차단된다.
- **미구현:** 픽업 후 반품 완료, 다른 회원으로의 재배정, 물품 책임 이전을 끝내는 회원 배송 명령은 확인되지 않았다. 지원 사건 종결만으로 물품 처리가 끝나지 않는다.
- **보완:** 반환 장소·수령자·증빙·책임 이전·재배송 동의와 최종 상태를 정한 뒤 기존 원의뢰/사건/슬롯에 연결해야 한다.

### E05. 전달했다고 하지만 받지 못했거나 보수를 받지 못함

- **현재 안내:** 회원 수행 화면은 `전달 완료 · 수령 확인 대기`와 비용 확인의 분리를 표시한다. 그러나 완료 후 문제 버튼은 열리지 않고 의뢰자 상태 카드의 지원 안내도 직접 행동으로 이어지지 않는다.
- **기존 지원 경로:** 원의뢰 상세의 거래보호 안내와 공통 분쟁 접수·추가 정보·이의 제기·사건 조회는 있다. `POST api/v1/common/transaction-disputes`는 원의뢰 작성자와 배정 회원 등의 당사자 권한을 확인한다. 배송 완료 상태만으로 접수를 금지하지 않는다.
- **연결의 한계:** 공통 분쟁 접수는 회원 배송의 `Issue`/`SupportCaseId`를 자동 갱신하지 않는다. 전달 완료 회원 화면에 공통 지원으로 이어지는 링크가 없다.
- **수령자 권한:** 연락처에 적힌 수령자 이름·전화번호가 그 사람의 계정 권한을 만들지는 않는다. 원의뢰 작성자와 같은 계정인지, 협업 당사자 권한으로 접수해야 하는지 먼저 확인한다.
- **지급:** 회원 전달 완료 후 원의뢰의 결제·정산 상태는 `결제대기`로 남는다. 기존 정산의 Cargo 원천은 전문 기사 식별자를 참조하므로 회원 수행자에게 즉시 적용된다고 볼 수 없다. 정산 앱 화면도 이전 사용자 선택으로 보류한 범위다.
- **운영자:** 수령 사실, 배송비 약정, 지급 신고, 상대방 확인을 각각 대조한다. 연락·합의·사건 종결을 은행 입금이나 자동 환불 완료로 기록하지 않는다.
- **보완:** 수령 확인 권한/명령, 완료 후 지원 진입, 회원 수행자 정산 원천과 비용 확인을 각각 연결한다.

### E06. 상세정보 열람 기한이 지나거나 해결되지 않은 업무가 남음

- **실제 코드:** 상세정보는 기능 활성·유효 원의뢰·동의와 `Assigned`/`PickedUp`/`Issue` 상태, **수락 시점부터 72시간 이내** 조건에 따라 제공한다. 완료 후 72시간 공개가 아니다.
- **완료/취소:** `Delivered`/`Cancelled`는 즉시 주소·연락처·요청 메모를 숨기며 보수 등 업무 요약은 남긴다. `Assigned` 응답에는 픽업지와 전달지가 함께 포함될 수 있고 `PickedUp`에서는 픽업지를 숨긴다.
- **사진 보존:** 상세정보 열람 제한과 사진 보존/삭제는 별도다. 미완료 업무·지원 사건·보존 판단이 불명확하면 사진 삭제를 보류하는 기존 처리가 있다. 활성 저장소 삭제를 모든 백업 삭제로 설명하지 않는다.
- **보완:** 72시간이 지나도 물품을 가진 미완료 업무를 어떻게 확인·회수·마감할지 운영 절차와 제한된 복구 명령이 필요하다. 제한을 없애거나 연락처를 계속 보관하는 것으로 대신하지 않는다.
