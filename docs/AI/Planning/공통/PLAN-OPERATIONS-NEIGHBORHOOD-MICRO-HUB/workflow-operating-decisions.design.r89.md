원문의 ‘입구/출구’는 업무 문맥상 입고/출고로 정리하되 원문은 보존한다. 중간 분류·통합 업체 가능성도 언급됐지만 마지막에 제시한 직접 순회 입고·공간 제공자 일정 관리를 우선 방향으로 해석한다.

## 수용한 답변과 방향

- 질문 의미 ID: `space-capacity-and-service-classification`
- 이전 상태: r88의 `Asked / Unanswered`
- 현재 상태: `Answered / UsableSpaceClassificationAccepted / OptionalWorkScopeAccepted`

규모는 실제 제공할 보관 공간으로 나누고 피킹·포장·기사 인계는 제공자가 선택하는 방향을 수용했다. 소형·중형·대형의 수치 경계나 구체적인 요금·서비스 한도까지 확정한 것은 아니다.

추가로 입고 예정일에 맞춰 공급업체가 상품을 준비하고 여러 공간을 순회 납품하며, 공간 제공자가 입고 일정을 확인하고 해당 공간의 수령·보관을 관리하는 방향을 수용한다. 여러 업체의 상품을 한 공간에서 관리할 수 있게 지원하되, 플랫폼이 상품을 매입하거나 별도 물류센터·중간 분류업체를 확보하는 것을 필수로 두지 않는다.

## 일정에서 실제 입고·출고까지

```text
공급업체별 상품·물량·입고 예정일 준비
└─ 각 공간의 수용 조건·기간·도착 시간 범위 협의
   └─ 양측 동의한 입고 예약 확정
      ├─ 공급업체: 상품 준비·순회 납품 일정 관리
      └─ 공간 제공자: 예정 입고 확인·수령 준비
         └─ 도착 → 실제 품목·수량·사진·적재 위치 확인
            └─ 입고 재고 반영 → 주문별 피킹·포장·출고·배송
```

공급업체의 순회 일정은 여러 공간의 개별 예약을 연결하는 계획이다. 한 번의 순회 계획만으로 모든 공간의 입고 동의가 성립하지 않으며 실제 납품 완료도 아니다. 상품 준비·출발·도착 예정과 실제 수령을 각각 구분하는 설계를 제안한다. 순회 경로 최적화·새 차량 운영·AI 자동 일정 확정은 이번 요청으로 구현하거나 승인한 것으로 보지 않는다.

## 공간 제공자가 확인할 정보의 제안

| 기본 정보 | 업무 목적 |
| --- | --- |
| 입고 예정일·합의한 도착 시간 범위 | 언제 받아야 하는지 확인 |
| 공급업체·해당 예약의 담당자 | 누가 가져오고 누구와 조율할지 확인 |
| 품목·예정 수량·필요 보관 조건 | 상품과 수용 여력·적재 위치 준비 |
| 준비/도착 예정·일정 변경·미입고 상태 | 지금 필요한 확인과 다음 조치 판단 |
| 실제 수령 수량·차이·사진 근거 | 보관 재고와 수행 업무 확정 |

오늘·다가오는 입고를 공간 단위 일정으로 묶어 보여주는 안이다. 여러 공급자의 예약이 있어도 다른 업체의 계약 금액·물품 소유자별 상세 재고·타 공간의 정밀 위치를 일괄 공개하지 않는다. 건물주가 직접 받는 경우와 합의된 현장 담당자가 받는 경우의 책임·권한도 구분한다. 새로운 전용 앱이나 전체 물류센터 기능을 추가하는 구현 요청은 아니다.

## 기존 기준과 미정 범위

r63의 도착 시간창·보관 기간·조건 판본 동의·공간 전체 용량 검사를 재사용한다. 미수령 확정 예약은 수용 여력 계산에 반영하되 실재고나 완료 보수로 만들지 않는다. 일정이 지났다는 이유로 자동 입고·자동 예약 해제·자동 공간 확보를 처리하지 않는다. 부분 수령은 실제 받은 수량만 반영하고 예정 대비 차이를 남긴다.

공급·보관 협의, 입고 예약, 실입고 재고와 주문별 출고는 각각 기존 전문 원장에 연결한다. 입고와 출고 보수·원가 귀속을 분리하는 r60/r61 기준을 유지한다. 비용 부담 질문 `receiving-storage-consignor-cost-default`는 계속 `Unanswered / Preserved`다.

미정은 입고 전 알림 시점·채널, 일정 변경·미도착 처리, 실제 준비 상태의 확인 근거, 반복 납품 일정, 순회 계획의 작성 담당·차량/경로 지원 범위다. 분류·통합을 별도 업체에 맡기는 방식은 선택 후보로 보존하며 현재 기본 모델에 의무적으로 추가하지 않는다.
