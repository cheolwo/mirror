# 생활 거래의 투명한 정산 · 승인 구현 r32

상태: `Implemented / LocalValidated / ServerAndLedgerOnly / AppAndOperationalDeferred`. 2026-10-08 사용자의 `Implement the proposed plan.` 승인을 수용해 서버·원장 구현과 로컬 검증을 완료했다. 집중 48개·전체 8,986개 시험이 통과했고 환경 의존 MongoDB 시험 2개는 건너뛰었다. 앱 화면·APK·Unity·배달 영상·외부 송금·Azure·공용 DB 적용은 이번 범위에서 제외한다. [이전 보관 합의·사진 완료 r31](storage-agreement-photo-proof.implementation.r31.md)의 업무 원장은 그대로 소비한다.

## 1. 음식·보관 상품·운송을 구별한다

- `PreparedFood`: 조리한 음식을 바로 전달하는 음식 주문. 기존 음식 원장·배차·기사 정산이 권위다.
- `StoredGoods`: 공간에 보관된 상품. 포장 식품도 포함할 수 있으며 상온·냉장·냉동과 유통기한은 선언된 취급 조건으로 기록한다. 조건 기록을 실제 시설·온도 검증으로 표현하지 않는다.
- `TransportOnly`: 상품 판매 없이 운송만 하는 화물 의뢰. 기존 화물 운임·지급 준비가 권위다.

같은 사람이 상품 소유자·판매자·공간 제공자·작업자·기사 역할을 겸할 수 있다. 역할 명칭이나 요청에 적힌 사용자 ID만으로 접근 권한을 부여하지 않고 원본 업무의 실제 당사자를 조회한다. 고객 주소·전화·계좌번호는 새 정산 원장에 복제하지 않는다.

## 2. 누가 누구에게 지급하는지 약정한다

상품대금·판매 대행비·보관료·입고비·피킹비·배송료를 각각 지급자, 수령자, 계산 기준, 금액과 근거로 구분한다. 모르는 금액은 `null`, 명시적인 무료만 0이다. 플랫폼 수수료·세금·보험을 임의로 추가하지 않는다. 배송료에 이미 포함된 피킹은 별도 유료 항목으로 중복 청구하지 않는다.

보관료는 약정별 `Free / PerUnit / StoragePeriod`를 선택한다. 판매되지 않은 재고에도 합의한 기간 보관료가 발생할 수 있으므로 특정 판매 주문에 강제로 종속시키지 않는다. 기간은 명시한 시작·끝과 이미 경과한 시간만 사용하고 현재 재고로 과거 점유량을 역산하지 않는다.

상품대금 경로는 약정별 `OwnerDirect / SellerCollect`를 선택한다. 소유자 직접 수금은 구매자→소유자, 판매자 수금은 구매자→판매자와 판매자→소유자 전달 의무를 함께 기록한다. 첫 구현은 총액 전달과 별도 대행비를 사용하며 자동 상계는 하지 않는다. 전달액은 새로운 매출이 아니며 같은 사람 사이의 내부 배분도 외부 수입·지출을 늘리지 않는다.

현재 상품 판매가로 과거 주문금액을 만들지 않는다. 분산 주문에 동결 판매대금이 없으면 금액을 미확정으로 보존한다. 기존 음식·화물 기사 지급 원장은 참조만 하며 새 지급 의무나 송금을 중복 생성하지 않는다.

## 3. 약정·작업·지급 확인을 나눈다

`약정 제안 → 해당 판본에 당사자 동의 → 원본의 실제 완료 근거에 따른 비용 발생 → 비용 당사자 확인 → 지급자 지급 신고 → 수령자 수령 확인`을 별도로 기록한다. 사진 업로드·피킹 완료·배송 완료·주문 수령은 지급 완료가 아니다. 수령 확인도 당사자 확인 기록이며 은행 거래를 검증했다는 의미가 아니다.

약정 변경 시 새 판본과 재동의를 요구하고 기존 발생 금액은 보존한다. 취소·반품·분쟁은 원본 항목을 수정하는 대신 조정 항목을 추가한다. 상품 반환만으로 이미 수행한 배송·보관을 자동 취소하지 않는다. 부분 지급·중복 요청·동시 변경·지급 신고 중복 배분을 검증한다.

## 4. 구현 범위와 순서

1. 계약 DTO와 보호된 약정·판본·발생 항목·지급 신고·명령 영수증을 추가한다. 개인정보와 금액 payload는 기존 저장 보호 경계를 따른다.
2. 분산 재고/주문·음식 주문·화물 의뢰에서 실제 당사자와 동결 금액·완료 근거를 읽는 서버 연결을 구현한다. 기존 업무 상태·지급 원장은 수정하지 않는다.
3. 인증된 서버 API에서 판본 동의·발생·당사자 확인·분쟁·조정·부분 지급 신고·수령 확인과 본인 요약을 제공한다. 기능은 기본 OFF, 정확한 `neighborhood-settlement-r38` profile·Simulation·관계형 DB에만 허용한다.
4. 격리된 로컬 DB/API·권한·보호 저장·중복 방지·회귀 시험으로 검증한다. 실제 운영·은행·공용 DB 적용은 별도다.
5. 이후 앱은 역할과 업무 상태에 필요한 정산 정보만 카드·목록·상세에 연결한다. 이번에는 앱 화면을 추가하거나 APK를 다시 만들지 않는다.

## 5. 수용 기준

- 다거점·여러 소유자, 일부 입고/피킹/판매, 미판매 보관, 기간 중 약정 변경을 구별한다.
- 소유자 직접 수금과 판매자 수금의 잔액을 보존하고 대행 전달을 매출로 중복 집계하지 않는다.
- 배송비 공동 부담과 피킹비 포함 여부, 동일인 역할을 확인한다.
- 원본 금액·당사자 변경 시 미래 발생은 재동의를 요구하고 과거 발생은 불변이다.
- 원본 주문과 화물 의뢰가 같은 배송을 가리키면 기존 기사 지급을 중복 생성하지 않는다.
- 비용 미확정·분쟁·부분 지급·중복 요청·잘못된 수령자 확인·범위 밖 조회를 차단한다.
- 실제 사진·완료량 근거가 없는 요청 수량만으로 비용을 발생시키지 않는다.
