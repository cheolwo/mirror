- 기준 구현: [r76](workflow-exception-closeout.implementation.r76.md). 기존 원장을 이용하는 기획이며 제품 코드는 변경하지 않는다.

## 확정한 답변

- 질문 의미 ID: `platform-funded-work-start-gate`
- 이전 상태: r85의 `Asked / Unanswered`
- 현재 상태: `Answered / FundingBeforeOfferAccepted / OrderPaymentFundingAccepted`
- 사용자 답변 원문: **“그렇지 뭐 재원을 확보를 해두는 게 좋지. 그리고 이제 주문자가 이제 결제를 하면은 그거를 이제 매출로 잡아가지고 되고 재원으로서 이용하면은 괜찮을 것 같아. 회계적으로 계산을 한다고 하면은.”**

플랫폼이 보수를 지급하는 신규 일감은 작업자에게 제안하기 전에 재원을 확보하고, 부족하면 신규 제안을 보류하는 방향을 수용했다. 주문자 결제금을 해당 주문의 작업 보수 지급 재원에 연결한다. 재원 부족을 이유로 이미 합의한 기본 단가나 기존 수행 보수 기록을 임의로 줄이지 않는다.

사용자의 ‘매출’ 표현은 결제금으로 재원을 마련하려는 의도로 보존한다. 결제금 전액을 결제 즉시 플랫폼 매출로 인식한다는 회계 결론으로 확정하지 않는다. 거래총액·공급자에게 지급할 금액·작업 보수·플랫폼 몫을 각각 추적하는 설계를 제안한다.

## 결제금·매출·지급 재원의 구분

| 항목 | 기획에서 구분할 의미 |
| --- | --- |
| 주문 거래총액·수납액 | 주문자가 무엇에 대해 얼마를 결제했는지. 이를 플랫폼 매출이나 자유롭게 쓸 잔액과 같은 필드로 두지 않는다. |
| 공급자·작업자 지급 의무 | 계약에 따라 상품 제공자·입고/보관/피킹/포장/배송 수행자에게 지급할 금액. 해당 업무·당사자·약정 판본과 연결한다. |
| 재원 확보·배정 | 결제 확인, 정산 대기, 지급 가능 잔액, 해당 주문에 배정한 금액을 구분한다. 같은 잔액을 여러 일감의 재원으로 중복 집계하지 않는다. |
| 플랫폼 매출 | 플랫폼이 계약상 본인으로 공급하는지 대리인으로 주선하는지와 수행 의무 충족 시점에 따라 판정할 대상이다. 잔여금·배분액을 곧바로 회계 매출이나 영업이익으로 표시하지 않는다. |

IFRS 15의 수익 인식은 약속한 재화·용역의 이전에 따른 수행 의무 충족을 기준으로 한다. 결제 시점만으로 인식 시점이 정해지는 것은 아니다. [IFRS Foundation 공식 개요](https://www.ifrs.org/issued-standards/list-of-standards/ifrs-15-revenue-from-contracts-with-customers/). 대리인 거래는 주선 대가인 수수료 등을 수익으로 인식하는 순액 구분이 있으며, 본인·대리인 판정은 공급 전 통제와 계약 내용을 살핀다. [IFRS Foundation 공식 교육 자료, Module 23](https://www.ifrs.org/content/dam/ifrs/supporting-implementation/smes/2025-modules/module-23.pdf), [IFRS 해석위원회 본인·대리인 검토](https://www.ifrs.org/news-and-events/updates/ifric/2022/ifric-update-april-2022/).

이는 설계에 필요한 구분을 확인한 것이며 이 사업에 적용할 회계 기준·실제 계약·세무 분개를 확정한 것은 아니다. 상품 판매와 배송·보관 등 서비스의 본인·대리인 지위도 일괄로 같다고 가정하지 않는다.

토스 지급대행은 `pendingAmount`와 `availableAmount`를 나누고, 계약된 정산 주기에 따라 지급 가능한 잔액으로 전환한다. 따라서 결제 확인만으로 즉시 송금할 수 있다고 기록하지 않는다. [토스 공식 지급대행 가이드, 정산 잔액 확인](https://docs.tosspayments.com/guides/v2/payouts#2-정산-잔액-확인하기). 위 공식 자료는 2026-10-15 조회했으며 실제 계정의 계약·잔액·입금을 조회하거나 확인한 것은 아니다.

## 기존 구조에 연결할 범위

```text
주문자 결제
└─ 결제 정본 확인·해당 주문 재원 연결
   ├─ 공급자 등에게 지급할 몫과 기본 작업비 구분
   ├─ 실제 확보·배정 재원 확인 → 신규 작업 제안
   │  └─ 부족 → 신규 제안 보류
   └─ 작업 수행·증빙·금액 확인
      └─ 지급 조건 확인 → 기존 주간 명세 → 실제 지급 결과 확인
```

재원이 확보됐다는 것은 지급 조건 충족이나 송금 완료와 별개다. 고객 신고가 있으면 기존 해당 주문 미지급 정산 보류 기준을 유지한다. 기지급·진행 중 업무를 신규 제안 보류와 함께 취소하는 것으로 확장하지 않는다.

[r73](transport-prepayment-settlement.implementation.r73.md)의 현재 첫 결제 연동 범위는 **배송료 선결제**다. 이번 재원 방향 수용만으로 상품대금 수납·판매자 분할 지급이 구현되거나 범위가 확대됐다고 표시하지 않는다. 실제 수납·지급은 기존 [운송 결제·정산 기준](../../../../Architecture/TransportPaymentSettlementPolicy.md)의 PG/정산사 경계를 유지한다. 당사자 직접 정산 거래까지 플랫폼 선결제를 필수화하거나 다른 주문의 자금을 임의로 전용하는 승인도 아니다.

[r60](receiving-outbound.implementation.r60.md)의 입고·보관 보수는 판매·출고를 기다리지 않는 별도 흐름이다. 판매 전에 발생한 입고비를 미래 주문 결제금만으로 이미 확보했다고 표시하지 않는다. [r61](settlement-economics.implementation.r61.md)의 입고·보관 원가 배부는 주문 손익에 비용을 연결하는 회계 귀속이며, 입고 작업자에게 새 지급 채무·현금을 만드는 기능이 아니다. 기존 기본 비용·성과금·플랫폼 잔여금 분배 구조와 중복 지급 방지를 보존한다.
