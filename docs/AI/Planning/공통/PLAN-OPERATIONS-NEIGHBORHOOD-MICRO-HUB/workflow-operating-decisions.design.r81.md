- 기준 구현: [r76](workflow-exception-closeout.implementation.r76.md). 이번에는 기획만 갱신하며 제품 권한·외부 알림·실제 금융 처리는 변경하지 않는다.

## 확정한 답변

- 질문 의미 ID: `support-agent-financial-action-authority`
- 이전 상태: r80의 `Asked / Unanswered`
- 현재 상태: `Answered / CenterManagerAuthorityAccepted / OperatorNoticeRequired`
- 사용자 답변 원문: **“뭐 꼭 운영자 승인을 받을 필요까지는 없고 그냥 운영자한테는 알림만 일단 가고 그게 센터의 그런 이제 관리자도 관리자도 좀 처리할 수 있는 권한을 주는 게 좋겠다라는 생각이 있어.”**

고객센터 관리자가 맡은 사건을 권한 범위 안에서 직접 처리하고, 운영자는 알림을 받는 방향을 수용한다. 정산 보류 해제·환불·추가 비용 등 사건 처리 결정을 모두 운영자 사전 승인에 묶지 않는다. 운영자 알림의 발송·읽음 확인이나 응답을 센터 관리자 처리의 선행 조건으로 두지 않는다.

r80의 상담원 1차 확인은 유지하되 일반 상담원과 고객센터 관리자는 구분한다. 센터 관리자가 사건 처리 권한을 갖는 방향은 확정했고, 세부 권한 범위·대상 사건·비용 부담 기준은 후속 기획에서 정한다. 모든 상담원에게 동일한 금융 권한을 주거나 다른 센터의 모든 사건에 접근할 수 있다는 뜻은 아니다. 별도 금액 한도나 운영자 승인 대상 예외를 이번 답변에 임의로 추가하지 않는다.

## 접수에서 처리까지의 흐름

```text
고객 문제 신고
├─ 해당 주문의 미지급 정산 보류 [r79]
├─ 운영자에게 알림 [r81: 사전 승인·읽음 대기 없음]
└─ 고객센터 상담원의 1차 확인 [r80]
   ├─ 신고·주문 상태·허용된 증빙·당사자 설명 확인
   └─ 고객센터 관리자의 사건 처리 결정 [r81]
      ├─ 판단 근거·담당자·대상 주문·조치 범위 기록
      ├─ 필요한 전문 업무에 결정 전달 및 실행 상태 확인
      └─ 처리 결과를 당사자에게 안내하고 운영자에게 알림
```

신고 접수 알림과 처리 결과 알림은 운영자에게 상황을 알리는 기능으로 기획한다. 알림이 아직 전달되지 않았거나 읽히지 않은 상태를 처리 승인 대기로 바꾸지 않는다. 실제 발송 경로·재시도·실패 안내는 미정이며 이번 문서 변경으로 외부 메시지를 발송하거나 알림 연결을 완료한 것은 아니다.

관리자의 결정, 후속 재배송·환불 실행, 정산 보류 해제, 실제 입금 확인, 사건 종결은 각각 별도 결과로 남긴다. 보류 해제가 곧 송금 완료는 아니며 기존 주간 정산 원칙도 유지한다. 사건 처리 권한을 정한 것만으로 원장 금액이나 지급 재원을 임의로 바꾸지는 않는다.

## 이번 답변으로 정하지 않은 범위

- 증빙이 엇갈리거나 부족할 때 추가 확인·책임 판정·비용 부담·이의 제기 기준.
- 첫 안내·추가 안내·최종 해결 기한과 담당자 부재 시 인계 방식.
- 실제 환불·송금 실행 수단, 지급 실패 복구와 이미 지급한 사건의 처리 기준.

[r78](workflow-operating-decisions.design.r78.md)의 전달 증빙·지급 재원이 있는 무응답 정산 방향과 [r79](workflow-operating-decisions.design.r79.md)의 실제 신고 시 보류는 유지한다. 이 기획에서 운영자 사전 승인을 공통 조건으로 되살리지 않는다. 추가 확인을 이유로 무기한 보류하거나 자동 귀책·자동 환불하는 기준도 확정하지 않았다.
