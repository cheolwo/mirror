# 살뜰마트 포장 전표·기사 픽업 확인 제안 r54

- 기획 ID: `PLAN-OPERATIONS-NEIGHBORHOOD-MICRO-HUB`

- 상태: `SourceReviewed / ProposedDesign / ImplementationApprovalPending / OperationalDeferred`
- 관계: [피킹·포장 표본 r52](ssalddel-mart-picking-sample.implementation.r52.md), [선반 카메라 입력 r53](ssalddel-mart-camera-scan.implementation.r53.md)의 후속 제안. 기존 승인·구현·시험 결과를 대체하거나 승격하지 않는다.

## 사용자 요청과 목적

포장 담당자가 주문 전표를 미리 출력하여 상품 포장에 붙이고, 배정된 기사님이 QR을 스캔하거나 전표의 네 자리 번호를 입력하여 실제 픽업을 확인하도록 한다. 출력은 포장 완료 전에도 가능하게 하되, 인계 가능한지는 서버의 현재 업무 상태로 판단한다.

창고 직원의 **피킹**은 적재대에서 상품을 모으는 일이고, 기사의 **픽업**은 준비된 포장 상품을 인수하는 일이다. 선반 QR과 상품 포장 QR을 같은 코드나 완료 행동으로 취급하지 않는다. 이번 문서는 제안이며 제품 코드·DB·앱·실제 프린터·기사 업무를 변경하지 않는다.

## 제안하는 업무 절차

1. **전표 준비·출력:** 담당자가 선택 주문의 전표를 발급하고 출력 창을 연다. 주문 표시번호, 상품·수량, 포장 번호, QR, 큰 네 자리 확인번호를 담는다. 포장 완료 전에도 가능하며 `전표 출력은 픽업 준비 완료가 아닙니다. 앱에서 현재 상태를 확인하세요.`를 표시한다.
2. **피킹·포장 완료:** 기존 피킹·포장 절차에서 상품·수량과 전표 부착을 확인한다. 서버는 현재 포장 내용과 유효 전표 판본을 결속한다. 종이의 인쇄 시점 상태가 아니라 서버 상태가 기준이다.
3. **기사 전표 확인:** 기사 앱의 현재 배정 건에서 `QR 스캔` 또는 `번호 4자리 입력`으로 같은 전표를 확인한다. 매장·주문 표시번호·봉투 수와 인계 가능 여부를 보여준다. 촬영 화면·원문 인식값은 저장하거나 로그로 남기지 않는다.
4. **실물 픽업 확인:** 물건을 받은 기사님이 `상품을 받았어요 · 픽업 완료`를 누른다. 서버가 담당 기사·배정 시도·주문 취소 여부·포장 완료·전표 유효성을 다시 검사한 뒤 한 번만 인수를 기록한다.
5. **같은 결과 재조회:** 창고와 기사 앱이 같은 인계 원장을 다시 조회한다. 창고에는 `기사 인계 완료`, 기사에는 `픽업 완료 · 전달하러 가기`로 표현한다. 픽업은 전달·수령·정산·지급 완료를 뜻하지 않는다.

스캔 즉시 완료하지 않고 요약 뒤 한 번 확인하는 방식을 추천한다. 다른 봉투를 읽거나 화면을 비춘 경우의 오픽업을 줄이기 위한 제안이며 아직 승인되지 않았다. 담당자의 포장 전표 발급·기록과 기사의 인수 Command는 권한을 분리한다. 새로운 병렬 업무 원장 대신 기존 주문·포장·운송 인계 참조에 묶는다.

## 전표·번호·실패 처리 제안

- **네 자리 번호:** 주문번호 끝자리와 별도로 서버가 발급한 `전표 확인번호`를 추천한다. 기사님이 이미 선택한 현재 배정 주문 안에서만 대조하고, 네 자리만으로 전체 주문을 검색하거나 픽업 권한을 주지 않는다. 시도 횟수 제한과 일반화된 실패 안내를 두며 전화번호·계좌 끝자리는 쓰지 않는다. 기존 공개 주문번호는 바꾸지 않는다.
- **QR:** 개인정보나 외부 이동 URL 없이 유효 포장 전표의 불투명 참조·판본을 식별한다. 카메라는 식별 입력만 제공하며 인증과 최종 상태 검증은 서버가 한다. r53의 선반 코드 허용 목록은 그대로 두고 포장 전표용 해석 경계를 별도로 결속한다.
- **미리 출력:** 같은 내용·판본의 단순 재출력은 같은 전표를 쓴다. 출력 실패로 주문·포장·픽업을 다시 만들지 않는다. 출력 창을 열었다는 사실을 `인쇄 완료`로 기록하지 않는다.
- **내용 변경·분실:** 상품·수량·포장 구성이 바뀌면 이전 전표를 무효화하고 새 판본을 발급한다. 분실 등으로 코드 자체를 교체할 때도 구 전표는 사용할 수 없게 한다. 단순 재출력과 코드 폐기·재발급은 다른 행동이다.
- **미준비·취소·재배정:** 포장 미완료는 대기 사유를 보여주고 픽업을 막는다. 취소 주문·무효 전표·현재 담당자가 아닌 기사는 거절한다. 담당 기사 변경은 같은 상품 전표를 확인하더라도 최신 배정 시도를 다시 검사한다.
- **여러 봉투:** 포장마다 `1/2`, `2/2`와 고유 참조를 두고 모든 필수 포장 인수를 확인해야 주문 전체 픽업으로 전환한다. 일부만 받은 경우 나머지를 자동 완료하지 않는다. 초기 표본은 주문당 한 포장으로 좁히되, 다중 포장을 지원하지 않는 단계에서는 해당 주문의 픽업을 막고 제한을 표시한다.
- **통신 불확실:** 오프라인 성공으로 표시하지 않는다. 같은 요청 ID·예상 revision·인계 판본을 보존하여 결과를 먼저 재조회하고, 불확실한 POST를 새 ID로 자동 반복하지 않는다. 동시 스캔·재요청도 인수·재고 감소·Event/Outbox를 중복 생성하지 않도록 한다.
- **개인정보:** 기본 전표에는 상품·수량·매장·표시번호·포장 수와 확인 수단만 둔다. 수령인 연락처·상세주소는 기사 앱의 필요·권한 조회로 제공하고 QR에 넣지 않는다. 표본 전표는 합성 자료로 만들며 r52의 비공개 출처를 출력물·캡처로 옮기지 않는다.

전표 발급은 포장 참조·전표 판본·활성/무효 상태·발급자를 보유하고, 출력 요청은 별도 이력으로 남기는 안이다. 인수 기록에는 현재 배정 참조·기사·서버 시각·요청 ID·적용 revision을 결속한다. 조회와 Command가 서로 다른 시점에 실행돼도 최종 Command가 최신 상태를 다시 검사한다. QR 조회만으로 실물 수령을 증명했다고 보지 않는다.

## 구현 순서와 인수 조건 제안

1. **격리 표본 한 건:** r52/r53을 보존하고 주문당 한 포장의 전표 미리보기·QR·네 자리·출력 창 요청을 연결한다. 모의 기사 조회와 명시적 픽업 확인도 여전히 `Simulation / 모의`로 표시한다. 실제 마트 인계 차단 정책을 해제하지 않는다.
2. **서버 수직 연결:** 승인된 범위에서 마트 원천·포장 단위·배정 시도·담당 기사와 Command를 연결한다. 인증 HTTP·격리 DB·원장·Event/Outbox·양측 재조회까지 동일 요청/revision으로 대조한 뒤 실제 앱 연결 여부를 판정한다. 일반 화물 인계나 음식 주문을 임시로 생성하여 통과시키지 않는다.
3. **장치 검증:** 창고 앱의 인쇄 Adapter와 기사 앱 카메라·직접 입력을 결속하고 실제 프린터·Android를 별도 검증한다. 기존 음식점 PrintManager나 브라우저 `BarcodeDetector`가 있다는 이유로 단말 완료로 간주하지 않는다.

필수 검증은 조기 출력 후 픽업 차단, 정상 포장 뒤 동일 전표 사용, 틀린 번호·타 주문/타 기사 QR, 취소·재배정·구 판본, 동시/반복 요청·응답 유실·재시작, 출력 취소/재출력, 다중 포장 부분 인수다. 전표 생성 시험과 58/80mm 실제 크기의 디코딩, 물리 인쇄·휴대폰 촬영은 별도 증거로 기록한다. r53 선반 표찰 디코딩 결과를 포장 전표의 결과로 승계하지 않는다.

## 확정 / 미정 / 다음 질문 하나

- 사용자 요청 방향: 살뜰마트 직원이 전표를 출력·부착하고 기사님이 QR 또는 네 자리 입력으로 픽업을 확인한다. 포장 전 출력도 가능하게 한다.
