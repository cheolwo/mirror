## 현재 근거와 첫 구현 범위

실제 포장 UseCase → 포장 Event → 마트 배차대기 Service → OS 인계 → 공통 운송 큐 경로는 존재한다. 그러나 실제 음식기사 소비자는 음식주문·음식배달시도를 요구하므로 제품 readiness는 `MartLastMileConsumerBindingUnavailable`로 보류한다. r56의 합성 QR·고정 기사·격리 인수 기록을 운영 권한이나 전표로 승격하지 않는다.

이번 첫 소프트웨어 조각은 실제 마트 원천 검증 Adapter, 실패 후 명시적 포장 재요청의 배차 재확인, 다른 원천 운송번호 충돌 보호, 기존 OS 인계/운송 큐의 연결 시험으로 닫는다. 이것은 기사 수락·픽업·전달까지 운영 연결이 완료됐다는 뜻이 아니다. 같은 번호의 가짜 음식 주문 생성, 제품 readiness 해제, 실제 배차·외부 알림은 하지 않는다.

## 구현 계약

1. 마트 주문·출고 관계의 읽기 전용 원천 Adapter를 만든다. 주문 참조·동일 판매자/주문자·유효 출고/상품 관계와 준비 근거를 조회하며 저장·배차·원장 권위는 갖지 않는다. 내부 결과에 개인정보·주소·정밀 위치를 넣지 않는다. 기존 준비 판정과 인증은 우회하지 않는다.
2. 제품 readiness는 기능 관문을 먼저 검사하고 Adapter의 원천 결속을 재사용하되 기사 소비자 미지원 보류를 유지한다. DI에 기존 서버 범위로 등록한다.
3. 포장 저장 후 Event 실패 등으로 후속 인계가 누락되었을 때, 현재 인증된 사용자·같은 창고 접근권한·동일 포장 수량/유형이 확인된 명시적 완료 재요청은 별도 배차 재확인 Event로 기존 인계 Service를 다시 호출한다. 최초 포장자와 다른 담당자도 현재 같은 창고 접근권한이 있으면 재확인할 수 있다. 포장 사실·재고이동·문서/알림 Event는 새로 만들지 않는다. 자동 POST 재전송이나 스케줄러·durable Outbox 자동 복구를 새로 약속하지 않는다.
4. 공통 큐에서 마트 포장 원천과 관계된 기존 의뢰는 원본 유형·ID·화주·배차 업무가 일치할 때만 재사용한다. 충돌 시 상태/주소/화주를 덮거나 인덱스를 갱신하지 않는다. 마트 Service의 확정 기사 조기 반환에서도 같은 원천 결속을 확인한다. 과거 다른 업무의 정상 호환은 보존한다. 기존 피킹 완료 시험은 원래 완료 Event 1건과 새 재확인 Event 1건을 구분하도록 최소 수정한다.
5. 격리 SQLite 또는 기존 독립 Fixture에서 실제 마트 배차 Service·OS 인계 Coordinator·공통 큐의 연결을 검증한다. 소비자 준비 `true`는 명시적인 시험 Fixture에만 주입한다. 실제 Mongo·Redis·외부 API 대신 기록용 경계 Adapter를 사용하면 그 사실을 기록한다.

## 검증과 반환

원천 부재/중복/관계 불일치·준비/취소·낮은 근거, 포장 재요청의 인증/충돌/후속 실패, 동일 Event·번호 재처리·원천 충돌 불변, 기능 OFF·기사 미지원 보류, 음식·일반 창고 회귀와 관련 소비 앱 build를 확인한다. 직접 영향 시험, Fast, Task, 문서 링크와 diff를 각각 기록한다.

UI·카메라·프린터·실제 기사·공용 DB schema 적용·실제 Outbox/Redis·운영 활성화는 제외한다. 변경 기록과 `CURRENT_WORK.md`는 이 상한을 그대로 유지한다. 다음 소프트웨어 단계는 마트 전용 기사 시도·운영 전표·요청 결과 영속과 FDriver 수락/픽업/전달 소비 결속이다.
