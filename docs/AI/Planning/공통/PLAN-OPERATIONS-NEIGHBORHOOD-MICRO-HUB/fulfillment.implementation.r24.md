# 생활 배송 수행 방식 선택 r24

2026-10-07. 사용자는 생활 물품·퀵 배송을 우리 앱에서 접수하고, 자체 배차와 외부 플랫폼 위탁 후보를 같은 업무 목록·지도에서 비교하는 계획의 구현을 승인했다. 현재 상태는 `Implemented / LocalSimulationValidated / RealProviderPending`다. 실제 외부 플랫폼 API가 공개되었다고 전제하거나 주장하지 않는다.

## 승인한 결과

화물·수량·무게·인계 장소·시간 조건을 입력하면, 조건을 충족하는 수행 후보의 총비용·완료 예정 시각·견적 만료를 보여준다. 시간 조건을 충족한 후보 중 낮은 비용, 동률이면 빠른 완료를 추천하고 사용자가 견적과 정보 제공에 동의한 뒤 확정한다. 비용이나 완료 시각이 미확인인 후보는 확정하지 않는다.

앱이 접수한 한 건에는 하나의 수행만 활성화한다. 자체 배차를 선택하면 기존 자동 추천·공개 콜·병행의 의미와 기사 수락 경계를 유지한다. 외부 위탁을 선택하면 자체 배차 큐를 함께 생성하지 않는다. 기존 접수 건을 자동으로 외부에 재등록하지 않는다.

v1의 외부 후보는 `모의 퀵 배송`과 `모의 생활 배송` 두 개다. `NeighborhoodFulfillment:Enabled`가 켜진 Simulation에서만 제공하며 기본값은 꺼짐이다. 모의 완료·합의 비용은 실제 운행·수금·지급·정산 완료의 증거가 아니다. 실제 플랫폼·결제 API 호출과 Unity 변경은 이번 범위에서 제외한다.

## 서버와 복구 책임

`IFulfillmentProvider`는 역량 확인, 견적, 접수, 상태 조회, 취소를 제공한다. 서버는 견적·현재 선택·실행 시도와 이력을 별도 영속 기록으로 소유한다. 기존 로컬 의뢰 식별자에 공급자 식별자와 외부의 불투명한 접수 식별자를 연결한다. 사용자·소유권·동의·기존 거래 보호는 모든 조회와 변경에 적용한다.

견적 확정은 서버의 현재 견적·비용·만료·화물/시간 조건과 대조한다. 실행 시도는 같은 요청 식별자로 재조회하며 응답 유실을 실패로 간주해 다른 공급자에게 자동 접수하지 않는다. 취소 응답이 불명확하면 결과를 확인할 때까지 변경을 차단한다. 취소 확인 또는 확정 실패 이후 새 견적과 사용자 확인을 거쳐 수행 방식을 바꾼다. 동시에 확정·취소·재시도한 요청은 DB 판본 비교와 중복 키로 보호한다.

견적에는 정확한 주소·담당자 연락처를 공급자에게 보내지 않는다. 이번 모의 접수도 실행 식별자·상태·예정 시각만 사용하며 개인정보 payload를 새로 저장하거나 외부로 전송하지 않는다. 기존 의뢰의 개인정보 암호화 경계를 보존한다. 실제 공급자 연결 시에는 필요한 최소 개인정보와 별도 동의를 계약에 결속한다. 공개 지도는 기존 동네 대표점만 사용하고 사유 인계 장소·외부 추적 정보를 공개 레이어에 추가하지 않는다.

## 기존 계약과 화면

기존 `DispatchMode`와 API 경로를 보존한다. 배송 요청에 선택과 완료 희망 시각을 nullable로 추가하고, 견적에 후보 목록, 배송 상세/사유 지도에 수행 상태를 추가한다. 선택하지 않는 구형 클라이언트는 기존 자체 배차 흐름으로 처리한다. 새 nullable 필드는 구형 접수 fingerprint를 바꾸지 않도록 직렬화한다.

기존 작성·상세 화면에서 후보 선택과 현재 수행을 표시한다. 별도 외부 플랫폼 앱이나 새로운 지도 홈을 만들지 않는다. 페이지별 기본 정보·주 행동·오류 복귀는 [책임 카드](../../../../ProjectOverview/page-docs/neighborhood-fulfillment-r24.md)에 결속한다.

## 완료 조건과 검증

- 자체 배차 회귀, 외부 선택 시 자체 큐·기사 제안·현장 지급 미생성, 기본 비활성화와 Operational 차단.
- 관계형 DB에서 동시 확정, 동일 요청 재시도, 응답 유실 후 재조회, 재시작, 취소 확인 전 변경 차단.
- 다른 사용자 접근 차단, 견적 시 개인정보 최소화, 만료/알 수 없는 금액·시간 차단, 모의 정산 제외.
- 실제 공통 Razor를 320/390px에서 렌더하여 후보 비교·모의 표시·확정·대기/오류/결과 불명확·취소 복구와 가로 넘침을 확인.
- 관련 집중 시험 후 `eng/validate-changes.ps1` Fast·Task, 공통 UI를 소비하는 호스트 빌드.

최종 Fast 536개·Task 8,162개 시험 통과(환경 조건 Mongo 2개 건너뜀), 전체 3.5 제품/소비 앱 빌드 오류 0, 실제 공통 UI의 22개 모바일 흐름을 [변경 기록](../../../../Changes/2026-10-07-neighborhood-fulfillment-r24.md)에 결속했다. 격리 시험·UI 예시 렌더를 실제 외부 사업자 접수, 개인 단말, Azure 배포나 지급으로 확대하지 않는다. 커밋·푸시·배포는 이번 요청에 포함되지 않는다.

## 로컬 사용과 후속 공급자 연결

개발 서버 프로세스에 `SsalddelExecution__Mode=Simulation`, `NeighborhoodFulfillment__Enabled=true`를 지정하면 기존 생활 배송 견적에 세 후보가 나타난다. 운영 설정 파일이나 공용 서버의 기본값은 바꾸지 않는다. 새 서버 버전을 DB에 연결하기 전에 `20261007140000_AddNeighborhoodFulfillment` migration을 적용해야 한다. 기본 기능 플래그가 꺼져 있어도 기존 의뢰 모델에 추가한 두 열을 사용하므로 스키마 갱신이 필요하다. 이번 작업은 실제 MySQL DB의 migration을 실행하지 않았다. 견적의 비용·시간은 실제 사업자 요금·차량 위치를 조회한 값이 아니라 명시된 모의 조건이다.

실제 업체를 추가할 때는 그 업체가 허용한 공식 접수·조회·취소 계약, 고객 동의와 개인정보 제공 범위, 외부 요청 멱등 키와 응답 유실 후 확인 방법, 배차·완료·취소 상태 의미, 요금·결제·정산 책임을 먼저 확정한다. 기존 모의 공급자 이름을 실사업자 이름으로 바꾸는 방식으로 활성화하지 않는다. 역량과 견적·접수 adapter를 해당 계약에 맞춰 추가하고 같은 복구 시험을 거친다.
