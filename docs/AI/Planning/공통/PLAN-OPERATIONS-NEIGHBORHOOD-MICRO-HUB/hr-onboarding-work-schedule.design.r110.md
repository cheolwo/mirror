## 1. 현재 코드의 기반과 추가할 부분

- [HR 참여 운영](../../../../../Ssalddel/Application/HumanResources/HR참여운영UseCase.cs)과 [계약/급여 일정 DTO](../../../../../Ssalddel.Contracts/Common/Hr/HrEmploymentContractDtos.cs)에 계약 초안·서명과 급여 예정 구조가 있다. [계약 서비스](../../../../../Ssalddel/Services/HumanResources/HrEmploymentContractService.cs)는 시급 외 계약의 환산 검토가 필요하면 서명을 막고, 실제 근무기록을 통한 금액 계산은 별도 후속으로 남긴다. DTO의 PerTask를 완성된 건당 급여로 설명하지 않는다.
- [입고 협의](../../../../../Ssalddel.Contracts/Common/Warehouse/DistributedInboundCollaborationDtos.cs)에는 실제 입고 시작/종료 시간창이 있다. 여기에 근무자 신청·수락·다른 일정과의 충돌 검사를 연결해야 한다.
- [기본 작업 보수](../../../../../Ssalddel/Application/Settlement/NeighborhoodSettlementUseCase.Entries.cs)는 완료 근거·확인 처리량·동의 단가의 PerUnit 계산을, [추가 성과금](../../../../../Ssalddel/Application/Settlement/NeighborhoodSettlementUseCase.ActivityRewards.cs)은 주문별 기여·고객 수령·당사자 동의를 확인한다. 기존 지정 profile·Enabled·Simulation 관문을 유지한다. 운영 급여·실제 판매/은행 확인까지 연결됐다고 보고하지 않는다.
- 교육·행사 참여 혜택은 [별도 InMemory 서비스](../../../../../Ssalddel/Services/HumanResources/HrParticipationBenefitRecordService.cs)다. 이를 물류 숙지 이수·근무 보수 원장으로 재사용하지 않는다.

## 2. HR 인력과 배송기사의 역할 분리

입고·검수·적치·피킹·포장·출고 준비 인력은 기존 HR 역할과 조직/거점 범위에 연결한다. 운영 담당자, 실제 고용/계약 주체, 보수 지급 주체를 구분하며 공간 제공자라는 이유만으로 고용주로 정하지 않는다. 배송기사는 기존 근무·추천·배차·수락·인계 절차를 유지한다. 기사가 창고 업무도 희망하면 해당 업무의 안내·지원·권한을 별도로 확인하고 수락 일정의 중복을 함께 검사한다.

고정 인력은 계약과 반복 근무표를 재사용하고, 추가/단기 작업은 개별 일정에 신청하는 방식으로 제안한다. 같은 사람을 매 주문마다 신규 채용하지 않는다. 지원·근무 확정·전문 작업 권한은 별개 상태다.

## 3. 등록 → 업무 숙지 → 업무 신청

1. **본인 참여 등록**: 희망 작업·가능 시간·고정/일시 참여 의향을 등록한다. 실제 계약 정보는 필요한 후속 단계에서 별도로 받는다.
2. **전체 업무 흐름 안내**: 공급→입고검수→적치→주문→피킹·포장→기사 인계→배송·수령을 짧게 보여주고 본인 역할의 전후 담당자를 알려준다.
3. **내 업무 절차 숙지**: 실제 작업 화면 예시와 확인할 수량/바코드·이상 발생 시 보류/연락 방법·다음 담당자 인계 기준을 안내한다. 공통 안내 뒤 역할별 핵심 절차를 제시하고 간단한 상황 질문으로 이해를 확인한다. 열람만으로 현장 숙련이나 자격을 증명하지 않는다.
4. **숙지 기록과 일정 열람**: 어느 절차 판본을 언제 확인했는지 보존한다. 매번 전체 안내를 반복하지 않고 변경된 부분과 해당 작업의 주의 사항을 확인한다. 일정 목록은 먼저 둘러볼 수 있으나 신청은 본인 등록과 필요한 안내 확인 뒤 가능하도록 한다.
5. **업무 신청**: 실제 입고 계획에 연결된 날짜·시작/종료 예정·거점·작업 범위·필요 인원·보수 조건을 보고 신청한다. HR 검토/계약·활성 역할의 현재 조건을 확인한 뒤 업무 일정을 확정한다. 기존 계약자는 유효한 계약/역할을 재사용한다.
6. **근무·작업과 보수**: 확정된 일정에서 해당 전문 작업으로 진입하고 출근/종료 기록과 검수 수량·피킹/포장·인계를 구분해 남긴다. 실제 수행량과 완료 근거로 보수 발생을 확인하며 지급 예정·실제 지급과 분리한다.

첫 작업은 현장 담당자와 실제 절차를 확인하도록 제안한다. 안내 판본 변경·일정 지연·작업 조건 변경 시 변경 항목을 다시 확인하고, 이미 진행한 작업/물품 책임을 안내 갱신으로 삭제하지 않는다.

## 4. 일정과 신청 화면 예

아래는 실제 모집이 아닌 화면 설계용 예다.

| 항목 | 표시 예 |
|---|---|
| 작업 | 입고·검수 |
| 일정 | 10월 28일 10:00~12:00 예정 |
| 장소/인원 | 해당 거점 · 1명 모집 |
| 할 일 | 수량 대조, 상태 확인, 검수 결과 입력, 적치 담당에게 인계 |
| 준비 상태 | 업무 안내 확인 완료 · 현재 역할/시간 확인 필요 |
| 보수 조건 | 확인된 처리량에 따른 작업 보수와 별도 판매 성과 조건 |
| 행동 | 업무 조건 확인 후 신청 |

수락 시 최신 근무표와 다른 확정 업무·이동 시간을 다시 확인한다. 역할 등록을 가능한 근무 시간으로 간주하지 않는다. 신청·검토 중·확정·변경 확인 필요·진행·작업 확인·취소/대체 모집을 구분한다. 일정 변경 알림은 사용자가 허용한 범위로 보내며 이번에 실제 발송하지 않는다.

## 5. 입고 처리량과 판매에 따른 보수 표시

정확한 고용 형태·계약 단가·성과금 산식은 미정이다. 기존 HR 계약/급여와 작업별 정산의 권위를 구분하고 별도 검토 전 관문을 풀지 않는다.

- **작업 완료로 발생하는 보수**: 적용 계약/약정에 따라 확인된 근무시간 또는 검수 완료 처리량 등 실제 근거로 산정한다. 개당 조건이라면 `확인 처리량 × 동의한 작업 단가`를 표시한다. 신청 시의 예상 수량·예상 금액과 완료 후의 확정 처리량·발생액은 구분한다.
- **판매에 따른 추가 보수**: 해당 사람이 기여한 물품/주문이 약정한 판매·수령 조건을 충족했을 때 별도 계산한다. 우선 기존 고객 수령·주문별 기여 근거를 재사용하는 방향이며 실제 산식과 확정 시점은 추가 합의가 필요하다. 입고 수량 전체를 판매 수량으로 추정하지 않는다.
- **보수의 구분**: `작업 보수 발생액 / 판매 성과 확인 대기 / 추가 보수 발생액 / 지급 예정 / 실제 지급 확인`을 각각 보여준다. 아직 팔리지 않은 물품의 조건부 금액을 확정 수입으로 합산하지 않는다.
- **사전 조건**: 대상 물품·판매 인정 시점·단가/비율·여러 작업자에게 나누는 기준·미판매/취소/반품 처리·지급 주체와 주기를 작업 신청 전에 확인한다. 반품을 근거로 이미 완료한 작업 보수를 자동 삭제하지 않으며 정정 사유와 별도 검토를 남긴다.

기본/시간/건당 보수와 판매 성과 보상의 조합을 설정할 수 있다는 제안이며, 판매 성과금만으로 고용계약의 보수를 대체하는 정책을 이번에 확정하지 않는다. 근무자가 신청 당시 확인한 조건 판본과 지급 근거를 유지한다.

## 6. 첫 구현 권고와 미정

**권고 순서**는 기존 HR 지원 화면에 물류 업무 안내·판본별 이해 확인을 연결 → 한 거점의 입고 일정에 신청/검토/근무 확정을 연결 → 실제 작업량·근무기록과 보수 조건을 표시 → 별도 판매 성과 보상을 연결하는 것이다. 교육 이수·근무 신청·계약·작업 권한·실제 지급을 한 버튼의 완료 상태로 합치지 않는다.

**확정한 방향**은 HR 중심의 현장 인력 관리, 신청 전 업무 절차 숙지, 날짜/시간이 있는 일정, 사전에 이해할 수 있는 작업/판매 보수 조건이며 배송기사는 기존 배차를 유지한다.

**미정**은 고정/단기 계약 유형, 신청 전 필요한 안내 범위와 현장 확인, 첫 대상 업무, 근무표 확정 방식, 작업 단가와 판매 성과 산식·확정 시점·지급 주기다. **다음 검토 하나**는 첫 화면을 `HR 본인 등록 → 입고검수 안내 → 입고 일정 신청`으로 잡을지다. 이번에는 구현을 시작하지 않는다.
