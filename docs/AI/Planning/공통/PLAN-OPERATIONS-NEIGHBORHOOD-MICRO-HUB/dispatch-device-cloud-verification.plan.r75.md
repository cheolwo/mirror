# 주문 접수부터 기사 수행까지 검증 계획 r75

2026-10-15. 상태 `Proposed / VerificationPlanPrepared / ExecutionPending`.

사용자 요청은 데이터가 있다는 가정에서 주문 접수 → 배차 대기 → 적정 기사 추천 → 휴대폰 알림·소리 → 명시적 수락 → 배달료와 수행 단계별 화면을 검증할 계획이다. 먼저 화물 한 건을 끝까지 따라가고 음식 한 건에 같은 검증 틀을 적용한다. 이번 판본은 코드·r74 결과·Azure 읽기 조회·공식 자료를 대조한 계획이며 새 업무 시험, APK 변경, 배포를 완료한 기록이 아니다.

- 이번 Azure 읽기 조회에서 관리 API 인증 성공, 활성 구독 3개, 기본 구독의 Korea Central App Service와 `F1 / Free` 플랜 1개를 확인했다. 다른 구독 리소스 전수 조사, 현재 앱의 배포 내용·사용량·상태, 무료 잔량은 미확인이다. 기존 서비스를 덮어쓰거나 요금제를 바꾸지 않았다.

## 시험 데이터와 실행 환경

1. 격리된 r75 데이터베이스·계정과 `E2eRunStableId`를 사용한다. 기존 r74 데이터와 근무 상태는 보존한다. 화주/주문자·음식점·기사·관리자·공간/창고 담당을 분리하고 시험 계정만 대상으로 제한한다.
2. 매장 3곳·메뉴 9개, 소형 화물 1건, 적격 기사 2명 이상을 최소 구성으로 한다. 가까운 장기 대기 기사, 가까운 신규 기사, 수행 중인 기사, 부적격 기사, 인접 권역 기사를 상황별로 추가한다. 정확한 시험 금액은 기존 요금 정책으로 산출·동결하고 임의로 배차 성공 금액을 주입하지 않는다.
3. 실제 고객 주소·전화·주문은 사용하지 않는다. 공개 매장 자료와 합성 전달 지점을 분리하고 모든 합성 위치·경로·유가·시간은 Provider 이름·판본·입력·해시로 기록한다. 합성 GPS를 실제 휴대폰 위치로 인증하지 않는다.
4. 휴대폰 한 대에서는 해당 기사 앱을 시험하고 나머지 역할은 PC의 실제 역할 화면/API로 조작한다. 화면 시험 없는 API 행위를 역할 화면 확인 완료로 표시하지 않는다. 동일 계정의 여러 로그인으로 세션이 교체되는 시험 간섭도 방지한다.
5. 외부 API 비용 0원 모드는 실제 SQL/Mongo·인증·주문·배차 정책·수락을 사용하고 외부 자료 포트만 고정한다. 실제 경로 API·Ollama 추론·실제 FCM은 각각 별도 실행 항목이다. 규칙 엔진만 실행한 결과를 Ollama 판단 검증으로 기록하지 않는다.

`eng/Ssalddel.CargoJourneyVerification/CargoJourneyFactory.cs`의 r74 호스트는 모든 `IHostedService`와 외부 HTTP를 차단한다. 해당 호스트에서 주문을 넣는 것만으로 자동 배차·푸시가 동작한다고 가정하지 않는다. r75에서는 기존 전환 코어와 필요한 Outbox 처리만 허용한 격리 실행 프로필/한 차례 실행을 준비한다. 기존 개발 환경 Guard를 완화하거나 r74 시험 호스트를 그대로 외부에 공개하지 않는다.

음식 시험 작업자 `Ssalddel/Services/Development/MobileFieldTest/모바일음식배차시험작업자.cs`는 특정 매장·기사·좌표의 기존 fixture에 한정돼 있다. 이를 그대로 다중 기사 시험으로 부르지 않고, 시험 대상 허용 목록을 갖춘 별도 프로필에서 실제 엔진의 전체 후보를 평가한다. 지정 기사를 넣는 r74 `offer` 제어 API는 화면 시험용이며 적정 기사 선정의 증거에서 제외한다.

음식은 음식점 주문 인지/수락 뒤 기사 확정 전 조리 시작을 차단하는 기존 원칙을 확인한다. 주문 제출만으로 음식점 수락·조리·기사 수락·고객 수령을 자동 처리하지 않는다. 사진 조건이 있는 전문 업무만 사진을 요구하며 모든 음식 픽업에 새 사진 의무를 추가하지 않는다.

수행 중 기사 후보는 현재 GPS만 보지 않고 마지막 확정 목적지·도착 예상 시각·기존 약속·구간별 적재량을 확인한다. 4,000원 평균 보수 방향은 기존 정책의 보조 평가 대상으로 두며 자격·기한·확정 보수·비용 한도를 우회하지 않는다. 혼합 색 배너는 혼합 동시 수행 허가가 아니다. r71에서 근거 부족으로 보류하는 음식+화물 조합은 보류가 정상 결과다.

## 알림과 “살뜰배달~!”

음식 앱은 polling → `FDriverFoodNotificationState.Reconcile` → `FDriverFoodNotificationService.Publish`와 `FDriverFoodPushReceiver`의 두 알림 진입이 있다. 같은 서비스에서 계정·설정·중복·권한을 검사해 OS 알림과 WAV 재생을 요청한다. 기존 WAV는 짧은 기계음이며 “살뜰배달~!” 음성은 없다. 코드 호출 가능성과 실제 기기의 청취 성공은 다르다.

화물 서버에는 `notification.title/body + data` FCM 경로가 있으므로 OS 배경 알림 가능성을 배제하지 않는다. 앱 수신 식별자·알림 클릭의 의뢰 인계·맞춤 음원은 별도 검증·보완 대상이다. SignalR 운송 변경 재조회가 백그라운드 배차 푸시를 대신한다고 가정하지 않는다.

우선 두 앱에서 기존 소리로 정상 경로를 확인하고, 짧은 “살뜰배달~!” 음성 파일을 패키지에 넣는 좁은 변경을 준비한다. 억양은 파일 시안으로 확인하며 네트워크 음성 생성이나 새 LLM을 알림 재생의 필수 조건으로 만들지 않는다. Android 기존 채널의 소리 설정·사용자 변경을 존중하고 변경 음원 적용 방법을 시험한다. 중복 메시지·polling 경합에도 같은 제안은 반복 발성하지 않아야 한다.

| --- | --- |
| 앱을 보고 있을 때 | 유효 제안의 배너와 선택한 소리/진동. 탭하면 해당 의뢰 정본을 조회 |
| 홈으로 나간 상태 | 실제 FCM → OS 알림 → 탭 → 동일 의뢰. 정본 조회 실패 시 캐시로 수락하지 않음 |
| 잠금 화면 | 고객 주소·전화 없이 일반 새 요청 문구. 사용자가 잠금을 풀면 해당 업무로 복귀 |
| OS의 프로세스 종료 후 | 재수신/알림 클릭에서 세션·정본 복원. 실제 관찰 결과를 남김 |
| 사용자가 설정에서 강제 종료 | 위 경우와 별도 기록. 자동 수신을 합격 조건으로 강제하지 않고 수동 재실행 후 복원 확인 |
| 권한 거부·채널 차단·무음·야간 무음 | 사용자 선택을 우회하지 않음. 앱 안의 정본 조회·권한 안내는 유지 |
| 중복·만료·계정 변경·오프라인 | 중복 소리 억제, 만료 수락 금지, 이전 계정 정보 폐기, 재연결 후 정본 복원 |

FCM 접수 ID는 기기 수신 증거가 아니며 OS 알림 게시 로그도 실제 청취 증거가 아니다. 알림 발행·수신·표시 로그와 사용자 청취/허용된 시험 녹음 결과를 따로 기록한다. 기존 화면 유지 임시 설정은 작업 중에만 쓰고 잠금·보안 설정을 제거하지 않는다.

## Azure 무료 범위와 통신 시험

### A. 확인된 F1을 활용한 통신 시험

기존 F1 플랜에서 별도 시험 앱을 둘 수 있는지 현재 앱 수·CPU/저장 사용량·지원 런타임부터 확인한다. 가능하면 기존 서비스를 보존한 채 최소 인증 API를 HTTPS로 띄워 휴대폰 LTE/Wi-Fi에서 로그인·API 요청·오프라인 복구를 확인한다. F1은 일일 CPU 60분 등의 제한과 Always On 미지원이 있으므로 24시간 배차 작업자 실행을 보장하는 환경으로 쓰지 않는다. 무요청 상태에서 앱이 내려가는 동작과 재시작도 결과에 적는다. [공식 F1 가격·한도](https://azure.microsoft.com/en-us/pricing/details/app-service/windows/), [서비스 한도](https://learn.microsoft.com/en-us/azure/azure-resource-manager/management/azure-subscription-service-limits), [Always On과 유휴 종료](https://learn.microsoft.com/en-us/azure/app-service/configure-common).

최소 연결 API가 통과해도 전체 주문/DB/배차를 클라우드에서 통과한 것으로 표시하지 않는다. 전체 앱이 F1의 메모리/런타임/CPU 제약과 격리 DB 연결을 충족할 때만 같은 업무 시나리오를 확장한다. PC DB 포트를 인터넷에 열어 연결하는 방법은 사용하지 않는다.

### B. 전체 배차를 짧게 검증할 후보: Container Apps Consumption

F1에서 전체 서버·작업자·DB 시험이 맞지 않으면 Container Apps Consumption을 검토한다. 공식 월 무료 제공량은 구독별 vCPU 180,000초·메모리 360,000 GiB초·HTTP 200만 요청이다. 해당 구독의 남은 제공량과 DB·이미지 저장소·로그·전송 비용은 확인 후 판단하며 전체 구성이 0원이라고 보장하지 않는다. [공식 과금 기준](https://learn.microsoft.com/en-us/azure/container-apps/billing).

짧은 시험 동안 API·필요 배차/Outbox 작업자와 격리 SQL/Mongo를 준비한다. DB 무료 후보가 없으면 합성 데이터 전용 단일 복제본의 임시 다중 컨테이너 구성을 기술 후보로 평가할 수 있다. 리소스 적합성·probe·준비 순서·접근 경계 확인 전 구현 방식을 확정하지 않는다. 임시 DB는 복제본 종료 시 소실될 수 있으므로 재시드·내보내기를 마련하고 영속성/재해 복구 시험과 구별한다. [다중 컨테이너](https://learn.microsoft.com/en-us/azure/container-apps/containers), [임시 저장소](https://learn.microsoft.com/en-us/azure/container-apps/storage-mounts).

시험 중에만 필요한 복제본을 유지하고 종료 후 0/중지와 임시 리소스 정리를 확인한다. 배차 대기 원장은 DB 안에 있으므로 HTTP 기반 scale-to-zero만 설정하면 주문 대기 중 작업자가 실행되지 않을 수 있다. 시험 시간의 최소 복제본 또는 검증된 이벤트 기동을 명시한다. [확장 규칙](https://learn.microsoft.com/en-us/azure/container-apps/scale-app).

### 실제 클라우드 통신의 합격 기준

- APK의 서버 주소가 Azure HTTPS이며 USB reverse·localhost 우회 없이 동작한다. 시험 전에 reverse 상태를 기록하고 로컬 시험 연결을 제거/비활성한 상태에서 확인한다. 인증서 오류 무시나 cleartext 허용으로 통과시키지 않는다.
- 서버 인증·권한·DB migration/readiness·전문 원장 판독·배차 작업자·Outbox가 같은 판본에 연결된다. 필요한 시험 API만 인증된 시험 계정에 제한하고 기존 개발 fixture 제어 API는 외부에 노출하지 않는다.
- 앱 첫 실행의 알림 권한·채널과 Firebase 앱 등록·기기 설치 토큰·서버 발송 자격을 실제로 연결한다. FCM 자체는 무료 제품이나 다른 Firebase/GCP 자원을 무료로 가정하지 않는다. [공식 Firebase 요금 구분](https://firebase.google.com/docs/projects/billing/firebase-pricing-plans).
- foreground/background의 payload 처리·알림 클릭 경로가 다르므로 둘 다 확인한다. [Android FCM 수신 공식 문서](https://firebase.google.com/docs/cloud-messaging/android/receive-messages). 앱 polling/로컬 주입 알림은 실제 인터넷 FCM 수신과 별도 결과로 둔다.
- 클라우드 장애·휴대폰 네트워크 전환·앱 재실행 뒤 같은 주문/제안/확정 업무를 복원한다. 실제 PG·실지급·광범위 운영 활성화는 이 시험과 구별한다.
