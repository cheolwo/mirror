# 고객 신고 응답 6시간·처리 24시간 기준 기획 r83

- 기준 구현: [r76](workflow-exception-closeout.implementation.r76.md). 이번에는 기획만 갱신한다.

## 확정한 답변

- 질문 의미 ID: `reported-delivery-issue-first-response-window`
- 이전 상태: r82의 `PartiallyAnswered / BusinessHoursDirectionAccepted / DurationClarificationPending`
- 현재 상태: `Answered / ResponseSixHoursAccepted / HandlingTwentyFourHoursAccepted`
- 사용자 답변 원문: **“그래서 응답은 될 수 있으면 6시간 이내 하는데 처리는 24시간 내에 그렇게 하는 걸로 좀 기준을 잡았으면 좋겠네요.”**

| 구분 | 기획 기준 | 의미 |
| --- | --- | --- |
| 첫 응답 | 가능한 한 6시간 이내 | 상담 담당자가 상황을 확인하고 고객에게 답한다. 접수 자동 알림만으로 사람의 첫 응답 완료를 대신하지 않는다. |
| 사건 처리 | 24시간 이내 목표 | 센터 관리자가 증빙·당사자 설명을 검토하여 사건의 처리 결과가 나오도록 진행한다. 단순 경과 안내만으로 처리 완료를 대신하지 않는다. |

두 기준은 앞선 사용자의 근무시간·영업일 발언을 이어 **근무시간을 고려한 기준으로 해석**한다. 이번 답변에서 6시간과 24시간의 적용 대상은 명확해졌다. 실제 영업 시간표·휴일과 기한 기산 시점은 아직 정하지 않았다. 근무시간 24시간을 실제 경과 24시간 또는 1영업일로 임의 환산하지 않는다.

r82에서 확인용 후보로 제시했던 ‘24시간 내 처리 경과·다음 일정 안내’는 최신 답변의 확정 기준이 아니다. 24시간은 **처리 목표**이며, 최종 결과 없이 경과 안내만 했다는 이유로 충족한 것으로 기록하지 않는다.

## 업무 흐름과 보존 기준

```text
고객 신고 접수
├─ 해당 주문의 미지급 정산 보류
├─ 운영자·담당 고객센터 관리자에게 알림
└─ 상담원 상황 확인
   ├─ 가능한 한 6시간 이내 응답
   └─ 센터 관리자 검토·처리 → 24시간 이내 처리 목표
      └─ 처리 결정·후속 실행·실제 지급 결과는 각각 기록
```

[r81](workflow-operating-decisions.design.r81.md)의 센터 관리자 처리 권한과 운영자 사전 승인·읽음 대기 불필요 방향, r82의 양쪽 알림 원칙을 유지한다. 상담·결정과 실제 재배송·환불·정산 보류 해제·송금 완료·사건 종결은 같은 상태로 합치지 않는다. 예를 들어 환불을 결정했어도 실제 환불 완료는 별도로 확인한다. 알림의 구체 발송 시점·전달 실패 복구는 후속 설계 대상이다.

6시간 또는 24시간이 지났다는 사실만으로 자동 보류 해제·환불·귀책 판정·처리 완료를 확정하지 않는다. 목표 초과는 미해결 상태로 드러내고, 후속 안내·담당 유지 방식은 아래 질문에서 별도로 정한다.

## 미정과 다음 질문 하나

- 미정: 실제 근무 시간표·휴일·시간대·기한 기산 시점, 24시간 내 해결이 어려운 사건의 안내·추가 처리 기준, 책임·비용 부담 기준.
- 다음 질문 의미 ID: `reported-delivery-issue-unresolved-deadline`
- 상태: `Asked / Unanswered`
- 질문: **24시간 안에 해결되지 않으면, 사유와 다음 처리 예정 시각을 당사자에게 안내하고 담당 센터 관리자가 계속 맡도록 할까요?**
- 제안: 담당자 없이 방치하거나 완료로 표시하지 않고, 미해결 사유와 후속 일정을 남긴다. 운영자·담당 센터 관리자 알림도 제안하되, 이를 운영자 사전 승인 절차로 바꾸지는 않는다. 구체적인 연장 횟수·자동 연장·무기한 보류를 승인한 것은 아니다.
