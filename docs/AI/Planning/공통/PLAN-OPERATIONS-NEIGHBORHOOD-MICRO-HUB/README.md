# [기획 · 운영체제·생활권 물류 · PLAN-OPERATIONS-NEIGHBORHOOD-MICRO-HUB · r1]

- 상태: `Approved / FirstSimulationSliceImplemented / OperationalActivationDeferred`
- 상위·관련 기획: `PLAN-OPERATIONS-ORDER-CENTERED-WORK-NETWORK`, `PLAN-OPERATIONS-SSALDDEL-MART-SUPPLY-NETWORK`, `PLAN-OPERATIONS-LOGISTICS-OS`, `PLAN-ARCH-OPERATIONS-UNITY-TRANSFER-001`
- 첫 적용 범위: 독립적으로 관리되는 비주거 유휴 공간의 상온 밀봉품 단기 보관·기사 인계·주문자 수령

## 목적

주택가 가까이 있는 독립 비주거 유휴 공간을 곧바로 영업 시설로 간주하지 않고, 소유자와 관리담당자가 자발적으로 신청하여 생활권 단위 소형 물류거점 후보로 검토할 수 있게 한다. 첫 구현은 실제 보관 영업이나 유상 지급을 열지 않고 `Simulation`에서 신청·동의·검토·용량 예약·인계 완료를 검증하는 준비 체계다.

## 확정한 업무 경계

1. MongoDB의 기존 지도 신청 가원장이 신청 의도와 참여 관계의 원본이다. 생활권 물류거점 신청은 실제 `warehouse-inbound` 원장을 조회해 신청자가 생성자 또는 참여자인지 확인한다.
2. MySQL의 `생활권물류거점`은 동의·현장 확인·플랫폼 승인·가동 상태·용량·보상 시뮬레이션을 위한 안정 투영이다.
3. 소유자, 지정 관리담당자, 플랫폼 담당자의 세 관문이 모두 충족되어야 Pilot 후보가 된다. 어느 한 동의가 철회되면 가동 중인 거점은 즉시 `Paused`로 전환한다.
4. 첫 Pilot은 상온 밀봉품, 짧은 보관시간, 건수·총중량 한도만 다룬다. 냉장·냉동, 위험물, 주거 내부 공간, 임의 주소·출입구 생성은 제외한다.
5. 완료 건당 고정 보상은 Simulation 원장에만 기록하며 `실제지급대상=false`다. 결제·정산·세금·보험·시설 허가 관문이 별도로 열리기 전에는 지급하지 않는다.
6. 정확 위치는 보호된 참조로만 저장한다. 공개 API와 Unity 상태 사본은 생활권 키와 대략 위치만 포함한다.

## 생명주기

`Candidate → UnderReview → Pilot → Active → Paused/Closed`

- `Candidate`: Mongo 신청 원장과 공간 고유 식별자를 결속한 후보
- `UnderReview`: 소유자·관리담당자 동의와 현장 조건을 검토하는 상태
- `Pilot`: `Simulation`에서 용량 예약과 인계를 시험할 수 있는 상태
- `Active`: 장래 운영 관문을 위한 상태이며 현재도 실제 운영은 비활성
- `Paused`: 동의 철회, 용량·안전 문제 또는 운영 판단으로 신규 배정을 중단
- `Closed`: 후보를 닫은 상태

## 기존 업무와의 결속

Pilot 진입 시 기존 `창고`에 `임시보관소`로 한 번만 연결한다. 따라서 재고가 별도로 입고되고 배송권·거리 조건을 충족하는 경우 기존 `OutboundBatchEngine`의 창고 후보 체계를 재사용할 수 있다. 그러나 생활권 거점이라는 이유만으로 재고나 주문 목적지, 배차 권위를 자동 생성하지 않는다.

예약은 `업무StableId`를 통해 주문·출고·운송 인계와 연결할 수 있고 멱등성 키로 중복 예약을 막는다. 인계 완료도 별도 멱등성 키를 사용하며 모의 보상 기록은 한 번만 생성한다.

## Unity 관찰 경계

운영 서버의 `운영지역장면조회UseCase`는 `Pilot`·`Active` 거점을 읽기 전용 `WarehouseActor / NeighborhoodMicroHub` 항목으로 투영한다. 이 항목은 대략 위치, 수용량, 인계 가능 기능만 표현한다. Unity는 후보 승인, 예약, 인계 완료, 보상 지급을 확정하지 않는다.
