## 현재 구현: 작은 생활 협업·보관 r9

사용자가 승인한 네 항목을 [생활 협업 구현 r9](life-collaboration.implementation.r9.md)에 결속한다. 공개 제공·필요 글 또는 보관 능력에서 신청하고, 같은 계정이 신청자·제공자·참여자로 활동한다. 조건의 양측 합의 → 수행 → 상대방 완료 확인을 별도 보호된 원장에 기록하며 플랫폼 결제·자동 지급을 전제하지 않는다. 작은 보관 능력의 시간·수량 예약과 인수·반환은 별도로 확인한다. 동네 대표 위치만 공개하고 정확 인계 주소·연락처는 현재 안내에 양측이 동의했을 때 공유한다.

## 현재 구현: 생활 교류 최소판 r6와 생활 배송 r7

사용자 후속 요청에 따른 [서버 배차 연결 r7](server-dispatch.r7.md)은 공개 글과 별도 배송 의뢰를 서버 견적·기존 화물 원장/대기열로 연결했다. 접수와 기사 수락을 구별하고 선정 기사에게 상세 정보를 제공하는 별도 동의/철회를 추가했다. 실제 자동 제안·기사 수행·Azure 공개 운영과 다중 서버 접수는 별도 검증이 남는다.

사용자의 최신 지향은 사람들이 자유롭게 제공할 것과 필요한 것을 올리고 서로 교류하는 장이다. [생활 교류 최소 구현 r6](exchange-mvp.r6.md)가 공개 게시/문의의 책임·코드·저장·검증 범위를 소유한다. 고정 판매/창고/기사 역할, 플랫폼 결제, 상세 주소 등록을 첫 이용의 조건으로 두지 않는다. 제공/필요 글과 공개 문의는 기존 0.0 게시글 API/DB를 사용하며 실제 배송 의뢰의 주소·연락처는 본인 계정과 동의로 별도 관리한다. r6에서 후속이던 상호 완료 확인과 동의 공개 이력은 현재 r9에서 보호된 협업 원장에 구현했다. 입금·거래대금 인증은 추가하지 않았다.

r5의 재고·예약·업무 참여 스캐폴드는 중단 시점에 미검증이었다. 이번에 원본을 로컬 비공유 작업 자료에 보관하고 제품 실행·DI·EF 모델에서 그 스캐폴드만 분리했다. 새 테이블이 없는 최소판과 r4의 후속 업무 설계를 구별한다. 기존 다른 업무 변경은 유지했다.

## 이전 확장 설계: r4 주거 공간의 상품 등록·구매 신청·퀵 배송

[주거 상품·퀵 배송 설계 r4](residential-goods-quick-delivery.design.r4.md)는 후속 업무 확장의 상세 제안이다. 사용자가 동의한 집을 공간·구획·판매/픽업/보관 기능으로 등록하고, 보유 상품 공개 → 구매 신청 → 수량 예약 → 기존 화물 기사 배차 → 인계·전달을 연결한다. 주거 여부는 설명값이며 새 설계의 등록 제한으로 사용하지 않는다. 법적 요건 검토는 이번 범위에서 제외한다.

상태는 `DirectionConfirmed / DetailedDesignProposed / ImplementationPending`이다. 기존 r1의 비주거 Pilot은 현재 구현의 범위로 보존하며 r4 전체의 참여 조건으로 확대하지 않는다. 음식·화물 업무 분리, 현재 코드의 실운영·실지급 비활성은 유지한다. 본인과 관리담당자가 같은 경우는 한 등록 흐름에서 필요한 동의를 받는 간편 설계를 기준으로 한다.

## 목적

주택가 가까이 있는 독립 비주거 유휴 공간을 곧바로 영업 시설로 간주하지 않고, 소유자와 관리담당자가 자발적으로 신청하여 생활권 단위 소형 물류거점 후보로 검토할 수 있게 한다. 첫 구현은 실제 보관 영업이나 유상 지급을 열지 않고 `Simulation`에서 신청·동의·검토·용량 예약·인계 완료를 검증하는 준비 체계다.

## 확정한 업무 경계

1. MongoDB의 기존 지도 신청 가원장이 신청 의도와 참여 관계의 원본이다. 생활권 물류거점 신청은 실제 `warehouse-inbound` 원장을 조회해 신청자가 생성자 또는 참여자인지 확인한다.
2. MySQL의 `생활권물류거점`은 동의·현장 확인·플랫폼 승인·가동 상태·용량·보상 시뮬레이션을 위한 안정 투영이다.
3. 소유자, 지정 관리담당자, 플랫폼 담당자의 세 관문이 모두 충족되어야 Pilot 후보가 된다. 어느 한 동의가 철회되면 가동 중인 거점은 즉시 `Paused`로 전환한다.
4. 첫 Pilot은 상온 밀봉품, 짧은 보관시간, 건수·총중량 한도만 다룬다. 냉장·냉동, 위험물, 주거 내부 공간, 임의 주소·출입구 생성은 제외한다.
5. 완료 건당 고정 보상은 Simulation 원장에만 기록하며 `실제지급대상=false`다. 결제·정산·세금·보험·시설 허가 관문이 별도로 열리기 전에는 지급하지 않는다.
6. 정확 위치는 보호된 참조로만 저장한다. 공개 API와 Unity 상태 사본은 생활권 키와 대략 위치만 포함한다.

## 생명주기

`Candidate → UnderReview → Pilot → Active → Paused/Closed`

- `Candidate`: Mongo 신청 원장과 공간 고유 식별자를 결속한 후보
- `UnderReview`: 소유자·관리담당자 동의와 현장 조건을 검토하는 상태
- `Pilot`: `Simulation`에서 용량 예약과 인계를 시험할 수 있는 상태
- `Active`: 장래 운영 관문을 위한 상태이며 현재도 실제 운영은 비활성
- `Paused`: 동의 철회, 용량·안전 문제 또는 운영 판단으로 신규 배정을 중단
- `Closed`: 후보를 닫은 상태

## 기존 업무와의 결속

Pilot 진입 시 기존 `창고`에 `임시보관소`로 한 번만 연결한다. 따라서 재고가 별도로 입고되고 배송권·거리 조건을 충족하는 경우 기존 `OutboundBatchEngine`의 창고 후보 체계를 재사용할 수 있다. 그러나 생활권 거점이라는 이유만으로 재고나 주문 목적지, 배차 권위를 자동 생성하지 않는다.

예약은 `업무StableId`를 통해 주문·출고·운송 인계와 연결할 수 있고 멱등성 키로 중복 예약을 막는다. 인계 완료도 별도 멱등성 키를 사용하며 모의 보상 기록은 한 번만 생성한다.

## Unity 관찰 경계

운영 서버의 `운영지역장면조회UseCase`는 `Pilot`·`Active` 거점을 읽기 전용 `WarehouseActor / NeighborhoodMicroHub` 항목으로 투영한다. 이 항목은 대략 위치, 수용량, 인계 가능 기능만 표현한다. Unity는 후보 승인, 예약, 인계 완료, 보상 지급을 확정하지 않는다.

## r1 당시 남은 질문

첫 운영 화면을 만들 때 소유자와 관리담당자가 같은 사람인 소규모 거점을 별도 간편 절차로 허용할지 미정이었다. r4는 간편 등록을 설계 기준으로 정리했다. 현재 구현은 같은 사용자도 두 역할을 맡을 수 있지만 두 동의 기록은 각각 요구한다.
