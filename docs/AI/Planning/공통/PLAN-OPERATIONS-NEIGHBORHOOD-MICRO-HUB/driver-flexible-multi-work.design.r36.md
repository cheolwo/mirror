# 기사 자율 다건 수행과 음식·생활 화물 공동 여력 r36

- 날짜: 2026-10-08.
- 상태: `AcceptedDirection / ProposedDesign / ImplementationPending`.
- 후속: [기사 업무 선택과 공통 수락 보호 r71](driver-participation.implementation.r71.md)에서 우선 1·2번과 설정 화면을 구현한다. 근거가 없는 음식·화물 동시 수행과 전체 경로 통합은 계속 후속이다.
- 사용자 방향: 기사 본인이 오토바이 배달통에 실을 수 있는 물품과 수행 여력에 맞춰 음식·화물을 여러 건 선택하고, 픽업·전달을 조합해 시간당 배달 수입을 높일 기회를 갖도록 한다. 3·4건은 사용자가 든 예이며 모두에게 강제하는 고정 목표나 수입 보장이 아니다.
- 이번 범위: 현재 코드의 읽기 조사와 후속 설계 기록. 제품 코드·배차 상한·DB·기능 활성화·APK·실행 환경은 변경하지 않는다.
- 관계: [분산 순회 r30](distributed-warehouse.implementation.r30.md)의 피킹/전달 혼합과 구간별 적재량을 재사용한다. [원주문·동시 변경 보호 r35](root-order-selection-concurrency.implementation.r35.md)는 완료된 별도 범위이며 교차 유형의 배차 여력 보호를 대신하지 않는다.

## 현재 구현과 부족한 연결

| 현재 코드에서 확인한 것 | 확인 범위와 차이 |
| --- | --- |
| [음식 활성 업무 정책](../../../../../Ssalddel/Services/Dispatch/Recommendation/음식배달기사활성업무Policy.cs)은 최대 3건 고정 | 기사 개인의 희망 건수나 배달통 용량으로 정하는 상한은 아니다. |

음식 [작업공간 UseCase](../../../../../Ssalddel/Application/Driver/Food/FoodDeliveryDriverWorkspaceUseCase.cs)의 묶음 제안은 두 건 조합이다. 현재 음식 묶음 검사는 새 요청 사이의 조리 시각·픽업/전달 근접 조건이며 조리 시각이 없는 항목을 포함한 전체 품질·시간 보장으로 해석하지 않는다. 추가 수락 ON/OFF는 이미 운행 시작과 독립적이므로 새 중복 스위치 대신 기존 수신 의사를 재사용한다.

위 내용은 현재 소스의 정적 조사다. 기존 시험 통과 수를 이번 교차 수행의 실행 증거로 재사용하지 않는다. 현재 두 유형을 동시에 실제 수락할 수 있다고 인증하지 않는다.

## 기사 선택과 서버 판정

기사의 선택은 기존 본인 등록·업무 권한 안에서 적용한다. 유형 선택이나 화면 진입만으로 새로운 역할 권한을 부여하지 않는다. 같은 사람의 음식/화물 기사 식별자가 다르면 인증 주체와 실제 차량의 연결을 확인한 뒤 공동 여력을 계산한다.

| 기사 본인이 정할 조건 | 서버가 현재 업무와 함께 확인할 사실 |
| --- | --- |
| 음식만·생활 물품만·둘 다 중 받고 싶은 제안 | 해당 유형의 현재 수행 권한과 차량/배달통 적합성 |
| 동시 수행 희망 건수, 추가 제안 받기/일시 중단 | 이미 수락한 미완료 건수와 운영상 허용 상한 |
| 실제 배달통 사용 가능 부피·안전 중량·필요한 분리 구획 | 각 물품의 크기/중량, 매 구간의 최대 적재량, 혼적 가능 조건 |
| 감수할 추가 이동·시간의 한도 | 기존 업무의 전달 기한·조리 준비/대기·픽업/피킹/사진·전달 소요 시간 |

기사 희망 상한을 낮추거나 추가 제안을 끄면 신규 제안·수락에 적용하고 이미 수락한 물품 책임은 유지한다. 별도 미성년 정책·계약 준비·운영 활성화 상태는 이번 방향으로 변경하지 않는다.

건수와 적재량은 별개다. 네 건이라도 공간이 부족하면 추가 수락을 막고, 전달 후 공간이 비면 새 건을 받을 수 있다. 수락한 건은 향후 픽업을 포함한 약속이며, 현재 실은 물품만 세어 초과 수락하지 않는다. 부피 단위는 정규화하고 팔레트가 적용되지 않는 오토바이 생활 물품은 해당 없음이라는 확인과 단위 매핑을 사용한다. 크기·중량 미확인을 0이나 적재 가능으로 바꾸지 않는다.

음식과 화물의 업무·원장·완료·운임·정산은 계속 분리한다. 같은 차량에 실제로 함께 싣는 것은 품목·포장·온도·분리 구획의 호환 근거가 있는 조합에 한한다. 유형을 둘 다 선택했다는 이유로 모든 조합의 혼적을 허용하지 않는다.

## 기존 원장을 이용한 공동 여력

기존 운송·음식 수행·분산 예약/피킹의 식별자를 참조해 기사 한 사람의 미완료 약속과 실제 인수 수량을 읽기 모델로 모은다. 새로운 통합 원장에 원 업무 상태나 지급 상태를 복제하지 않는다. 취소·반납 대기처럼 책임이 남은 물품도 적재량·일정에 포함한다.

조회용 공동 계획만으로 수락을 허용하지 않는다. 음식 단건/묶음 수락, 화물 수락, 분산 순회 수락의 각 기존 명령 경계에서 같은 기사·차량의 최신 수락 현황과 정책 판본을 재검사한다. 앱 두 개·서버 두 개·동시 요청도 한 적재 여유를 중복 점유하지 못하도록 영속 동시성 제어를 설계한다. 프로세스 내부 잠금만으로 이 요건을 완료 처리하지 않는다. SQL 업무 저장·기존 Mongo 원장 투영/Outbox의 완료 범위와 복구는 구별한다.

예상 계획은 기존에 픽업/전달한 사실과 현재 적재량을 시작점으로 삼는다. 같은 장소의 준비된 여러 물품은 한 방문 후보로 묶되 건별 인수 확인·금액·사진 요건은 유지한다. 주문별 픽업 선행을 지키면서 `픽업 A → 픽업 B → 전달 A → 픽업 C → 전달 B`처럼 추가 삽입을 비교할 수 있다. 이미 든 음식의 기한을 깨는 경로는 후보에서 제외한다. 제한된 탐색 결과를 전역 최적 경로라고 표현하지 않는다.

## 화면 책임과 수입 판단

기본은 기존 전체 지도와 현재 정차의 접는 카드다. 현재 건의 주 행동이 픽업인지 전달인지 상태에 맞춰 제공하며 다른 배달 목록을 현재 카드 안에 계속 펼치지 않는다. `추가 배차 보기`로 들어갔을 때만 현재 기사에게 허용된 추가 후보를 비교·선택하고 수락 뒤 현재 업무로 돌아온다. 공개 콜까지 확장할 경우 기존 공개/추천 방식과 명시 수락을 재사용하되 음식 주문 전체를 자동 공개하지 않으며, 다른 기사와 같은 콜의 중복 수락도 보호한다. 고객 상세 주소·연락처는 기존 배정·보존 권한 안에서만 제공한다. 픽업 주황·전달 파랑·비활성 회색의 기존 표현을 유지한다.

추가 후보에는 건별 지급 예정액, 이번 추가로 늘어나는 금액·거리·시간, 변경될 방문 순서를 우선 제공한다. 조리 대기·피킹·사진/스캔·전달 시간이 포함된 유효한 경로 근거가 있을 때만 전체 계획의 시간당 세전 배달 수입 참고값을 계산한다. 참고값은 `계획의 건별 지급 예정액 합계 ÷ 예상 소요 시간`이며 실제 지급·공제 후 순수입이나 수입 보장이 아니다. 모르는 거리·시간은 숫자를 만들어 채우지 않는다. 묶는다는 이유로 이미 수락한 운임·픽업비를 자동 감액하지 않는다.

기사가 제안을 거절하거나 단건을 선택해도 현재 수행과 운임은 유지한다. 이탈/변경은 기존 중단·재배차·반납 절차를 사용하고 새 제안 선택이 임의 취소 명령이 되지 않게 한다. 사용자가 방문 순서를 바꾸려면 최신 조건을 만족하는 재계획을 확인·확정한다.

## 보완 순서와 완료 조건

1. 기존 음식 고정 상한과 화물 여력 검사의 적용 지점을 정리하고 기사 개인 희망 조건·배달통 제원을 저장/조회하는 작은 계약을 설계한다. 모든 정규화·API·화면을 하나의 서버 정책 결과로 연결하고 숨은 고정 `3`/`Take(4)`를 함께 확인한다. 기본값과 운영 최대 상한은 아직 확정하지 않는다.
2. 같은 기사의 기존 업무와 후보 한 건으로 공동 일정·적재 미리보기와 수락 직전 검증을 연결한다. 음식/화물 양쪽과 분산 수락이 같은 영속 자원을 사용해 동시 초과 수락을 막는 것을 우선한다.
3. 기존 지도에 추가 후보 비교·명시 수락·픽업/전달 혼합 순서와 상태별 현재 카드를 연결한다. 큰 설정 메뉴·별도 새 앱을 먼저 늘리지 않는다.
4. 격리 환경에서 네 건 사례와 거부/복구를 검증한 뒤 개인 APK·단말 검증으로 이어간다. 실운영 활성화는 자동 포함하지 않는다.

최소 검증 사례는 기사 희망 1·3·4건과 정책 판본 변경, 작은 음식/생활 물품 네 건의 유효 순회, 네 번째 큰 물품의 적재 초과, 기존 음식 기한 위반, 전달 후 여유 회복, 두 앱·두 서버의 동시 마지막 여유 수락, 동일 요청 재처리·응답 유실, OFF 후 기존 업무 유지, 취소/반납 책임·수령/지급 분리다. 네 건을 처리할 수 있다는 실행 증거와 시간당 수입이 실제 늘었다는 관찰은 별도다.

현재는 방향과 제안 문서만 정리했다. 음식 최대 3건 및 화물/분산의 기존 거부 조건은 그대로이며 제품 구현·실기기·운영 HTTP/DB·실제 혼적/배송·배달 수입 변화·APK·Azure·Unity·영상·commit/push를 수행하지 않았다.
