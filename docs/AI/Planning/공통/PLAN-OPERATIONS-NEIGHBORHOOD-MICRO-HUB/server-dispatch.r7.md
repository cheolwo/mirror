# 생활 교류의 서버 배차 연결 · r7

## 사용자 후속 방향

일반인이 배송 의뢰를 등록하면 서버가 적합한 기사에게 배차를 제안한다. 음식 배달과 생활 화물의 서버 처리는 분리하되 사람의 일상 활동을 고정 사업 역할로 제한하지 않는다. 플랫폼 결제 중개를 배차의 필수 조건으로 만들지 않는다. 제공/필요 글만으로 픽업지·전달지·물건·시간·요금 동의를 추론하지 않는다. 사용자의 계속 진행 요청에 따라 공개 글과 분리된 배송 의뢰 등록을 최초 진입으로 삼는다.

기본 흐름은 `배송 의뢰 등록 → 서버 배차 대기 → 적합한 기사에게 제안 → 기사 수락 → 픽업 → 전달 → 완료`다. 기사 부재·거절·제안 만료는 대기/재제안 상태로 남기며 실제 배차 확정으로 표시하지 않는다.

## 이번 구현 단위와 페이지 책임

생활 화물을 기존 화주 의뢰·서버 운임·현장지급 합의·화물 배차 대기열에 연결한다. 일반 인증 사용자의 본인 의뢰이며 화면에서 화주나 사업자 역할을 선택하는 절차를 추가하지 않는다. 음식 주문은 기존 음식 전용 흐름을 유지한다. 일반인이 만든 음식의 주문·조리·보관 조건을 기존 음식점 주문으로 가장하는 새 연결은 이번 범위에 포함하지 않는다.

| 페이지 | 사용자 질문과 결과 | 기본 정보와 주 행동 | 실패·복귀 |
| --- | --- | --- | --- |
| `/community/exchange/deliveries` | 내가 요청한 배송은 어디까지 진행됐나 | 본인 의뢰·배송비·대기/제안/기사 수락 상태, 의뢰 상세 선택 | 로그인·조회 실패·빈 목록·재조회; 교류 목록 복귀 |
| `/community/exchange/deliveries/new` | 이 물건을 어디서 어디로 배송할까 | 비공개 픽업/전달 정보·시간·물건·수량·중량·차량, 동의 → 서버 견적 → 배송비 확인과 직접 지급 합의 → 명시적 접수 | 견적 실패·금액 변경·미확정 등록은 입력/요청 ID 보존, 중복 클릭 차단; 본인 목록에서 확인 |
| `/community/exchange/deliveries/{requestId}` | 이 의뢰의 현재 상태와 조건은 무엇인가 | 본인 의뢰의 장소/시간·물건·서버 배송비·수금 예정·배차 단계, 최신 상태 조회 | 다른 사람의 의뢰·없는 의뢰·서버 오류, 본인 목록 복귀 |
| MAUI `/community/login` | 배송 의뢰를 내 계정으로 처리할 수 있나 | 기존 계정 인증, 허용된 생활 교류 경로로 복귀 | 실패 안내·재입력·진행 중 잠금, 외부 returnUrl 거부 |

공개 문의에는 상세 주소·전화·배송 조건을 복사하지 않는다. 동의의 수집 목적·출처·문안·소유자·철회 검증을 유지하며, 이번 신청 동의는 선택 기사에게 개인정보를 제공하는 다음 단계의 별도 근거를 대신하지 않는다. 직접 지급 합의는 `현장수금예정`이며 입금/수금 완료가 아니다. 무료 배송·분할 부담·무상 교환의 배송비 정책은 별도 확장이다. 현재 자동 배차 기능·운영 실행 관문은 유지하고, 비활성일 때는 활성 대기 상태를 표시한다.

## 구현한 작은 연결

1. **배송 의뢰 입력과 소유권**: 인증 사용자가 생활 화물의 픽업·전달 조건, 시간, 물건·수량·중량/차량 조건과 배송료 합의를 명시한다. 상세 주소·전화번호는 공개 교류 글/댓글에 저장하지 않는다. 공개 글 ID는 선택 출처이며 상대방의 배송 동의를 대신하지 않는다. 기존 인증과 신청 개인정보 동의를 재사용한다.
2. **서버 등록 → 배차 대기**: `생활배송의뢰UseCase`가 주소를 서버에서 확인하고 기존 운임을 재계산한다. 확인 금액이 달라지면 접수를 거절하고 새 견적을 요구한다. 기존 화주 생성·현장지급 Command와 화물 큐를 재사용한다. `neighborhood-delivery:` 요청 ID와 입력 fingerprint로 같은 요청의 응답 유실·원장 저장 후 큐 실패를 재개하며, 다른 내용으로 재송신하면 거절한다. 한 서버의 동시 요청만 잠금으로 보호하므로 다중 서버의 동시 접수는 DB 유일 키 보강이 필요하다.
3. **후보 제안 → 기사 수락**: 기존 화물 배차 엔진의 기사 적격성·시간·차량·중량·운행 상태 및 원자적 수락을 유지한다. `Operational`과 자동 배차 기능이 활성일 때 기존 서버 작업이 제안한다. 접수·추천·수락·종결은 별도 상태이며 이 코드 연결을 실제 기사 추천/푸시/수락 실행 증거로 표현하지 않는다.
4. **본인 진행 조회와 선정 기사 정보 제공**: 본인은 목록/상세에서 같은 의뢰 ID의 상태를 재조회한다. 확정 기사·추천 차수·제공 목적/항목/기한을 보여 주고 별도 동의와 철회를 기존 운송 사건에 저장한다. 원 신청 동의가 유효하고 현재 기사·회차가 같으며 배송 미종결·72시간 이내인 경우에만 해당 기사 조회에 상세 정보를 제공한다. 추천/공개 배차/전국콜에서는 상세 주소·좌표를 가린다. 배송 완료는 금전 이체/은행 확인이나 거래 신뢰 인증을 뜻하지 않는다.

화면 → 공용 client/VM → `api/v1/common/neighborhood-deliveries` → 생활 배송 adapter/기존 화주 UseCase → 기존 `화주운송의뢰`·`운송원장`·`운송이벤트` 저장 관계다. 새 테이블·마이그레이션은 없으며 등록과 별도 동의의 소유권 검사를 서버에서 수행한다. Web 세 화면과 MAUI 세 화면은 같은 컴포넌트를 사용하고, MAUI 계정 인증은 `/community/login`에서 별도 처리한다.

## 검증과 미완료 경계

[r6 최소판](exchange-mvp.r6.md)의 글/문의는 실제 공유 UI·HTTP·생산용 UseCase·SQLite로 검증한다. 생활 배송은 격리 DB 시험에서 실제 기존 의뢰 생성·조회·현장지급·배차 큐 저장을 사용하고, 주소·운임·동의·Mongo 투영·외부 실행 경계는 대역으로 구별한다. 루프백 배송 화면은 같은 제품 컴포넌트/VM이지만 전용 화면 검토용 client를 사용하므로 실제 운영 배차 증거가 아니다. 상세 실행 결과는 [서버 배차 변경 기록](../../../../Changes/2026-10-05-neighborhood-server-dispatch-r1.md)에 기록한다.

다중 서버 DB 멱등성, 실제 운영 설정의 거리 API/자동 추천·알림·기사 수락/픽업/전달 완주, Azure 공개 운영·실지급·개인 휴대폰 설치는 별도 검증이 남는다. 음식은 기존 전용 흐름을 유지하고 일반인 음식 제조·판매 연결, 분할/무료 배송, 동의 기반 공개 거래 이력은 이번에 추가하지 않는다.
