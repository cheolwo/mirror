## 1. 수령의 전문 근거

기존 마트 기사의 `Delivered`는 전달 사실이다. 숫자 `마트주문.Id`의 실제 주문자만 현재 배송시도·픽업 전표·정확한 주문상품/출고행·픽업 당시 출고 이력을 대조한 뒤 전량 수령을 확인한다. 비구속 Guid 마트주문요청 및 일반 상품 입고 확인을 실제 마트 배송 수령으로 재사용하지 않는다. 판매자·기사·관리자가 역할만으로 대신 확인할 수 없다.

기존 `마트배송시도`에 nullable 보호 `고객수령근거Json` 한 열을 추가한다. 수령 근거에는 주문 ID/참조·주문자·시도 ID·전달 당시 판본과 시각·수령 확정 판본과 시각·전표/픽업 시각·정확한 상품/출고/수량 및 지문·요청 ID/입력 지문만 보존한다. 주소·연락처·QR·사진 원문을 새로 수집하지 않는다. 상태 `Delivered`와 주문·최상위 원장은 수령 상태로 덮어쓰지 않는다.

확정 근거는 불변으로 보존하고, 실제 주문자가 명시한 부분 수령·누락·파손 신고는 별도의 보류 근거로 같은 보호 자료에 기록한다. 수령 전후 모두 보류를 기록할 수 있으며 기존 수령·보수·지급 사실은 삭제하지 않는다. 보류가 있으면 새 양수 지급의 관문을 닫는다. 자동 보류 해제·대리 확인·분쟁 종결·환불 완료는 만들지 않는다. 예외 해제 정책과 화면은 후속이다.

## 2. 판본·재시도와 원천 검증

현재 시도의 `Revision` CAS와 relational Serializable transaction을 재사용한다. 기대 판본이 다르거나 실제 전달·사용된 전표·상품별 출고 연결이 불완전하면 확정하지 않는다. UTC 시각의 순서·미래 시각·주문/출고 취소·잘못된 당사자·SKU·수량·출고 이력 변경도 검사한다. 픽업 후 출고된 재고에 픽업 준비 상태를 다시 요구하지 않고 당시 `마트기사픽업` 출고 이력과 시도·전표를 확인한다.

멱등 요청은 해당 주문/배송시도와 인증 주체에 한정한다. 같은 요청 ID와 같은 입력은 기록을 재사용하고 다른 의미는 충돌이다. 응답이 불명확하면 요청 결과를 조회하며, 새 요청 ID로 우회하지 않는다. 다른 새 요청으로 이미 확정된 수령을 다시 쓰지 않는다. 늦은 기사·창고 Outbox도 보호 수령 근거를 덮거나 되돌리지 않는다.

수령 판단과 정산이 같은 `마트수령근거Reader`로 현재 전문 원본을 검증한다. 배송 시도 판본과 수령 근거의 판본을 구분한다. 기존 실제 픽업의 전량 재고 제약을 확대하지 않는다.

코드 검토에서 창고 작업의 SQL `datetime(6)`와 JSON의 100ns 시각 정밀도 차이를 확인했다. 신규 피킹 시작/완료·포장 완료는 저장 전에 공통 UTC 마이크로초 단위로 정규화해 SQL과 JSON에 같은 값을 쓴다. 기존 엄격한 근거 일치 검사를 완화하지 않으며 과거 근거를 일괄 변경·승격하지 않는다. DB 정밀도 절삭 모사는 로컬 회귀로 확인하고 실제 MySQL 왕복은 별도다.

## 3. 기존 정산의 지급 조건

검증된 수령 근거가 있는 마트 원천만 기존 고객 수령 기반 지급 관문을 충족하도록 한다. 고객 수령 근거 DTO를 작업 보수 및 성과금용 `RewardOutcome`과 분리하고, 수령 수량은 주문상품/출고행을 한 번씩 합산한다. 피킹과 포장 작업량을 더한 값을 수령량으로 쓰지 않는다.

수령·보류의 진전은 사전 합의용 `SourceVersion/SourceDigest`·당사자·단가를 바꾸지 않는다. 본인 보수 양측 확인, 명시적 지급 신고, 수령 진술과 실제 은행 이체는 기존대로 분리한다. 수령 확인만으로 보수 발생·확정·지급 신고·실제 송금·상품 대금·기사 보수·추가 성과금을 만들지 않는다. 음수 조정의 기존 환급 경로와 발생한 보수를 보존한다. 기본 OFF·Simulation 경계는 유지한다.

## 4. 완료 기준

- 실제 마트 전달만으로 지급은 차단되고 주문자 전량 수령 뒤 기존 확정 작업 보수만 명시적으로 지급 신고할 수 있다.
- 전달 전·타인·다른 주문/시도/전표·판본 충돌·취소·수량/출고 이력 불일치·부분/누락/파손 보류에서 수령 확정 또는 신규 지급을 허용하지 않는다.
- 같은 요청 재조회·낡은 판본/DB 수정의 충돌·수령 후 문제 신고·별도 두 주문의 격리와 기존 보수 보존을 검증한다. 늦은 투영은 기존 후속 처리 코드의 근거 미변경 경계를 대조하며 실제 동시 HTTP/MySQL 및 수령과 Outbox의 운영 결합 실행은 별도다.
- 집중 Fast와 전체 Task, 소비 앱 빌드, 보호 저장 및 격리 SQLite migration, 문서 링크·기존 변경 해시를 확인한다. HTTP/단말·공유 DB·외부 지급·운영 완료로 확대하지 않는다.
