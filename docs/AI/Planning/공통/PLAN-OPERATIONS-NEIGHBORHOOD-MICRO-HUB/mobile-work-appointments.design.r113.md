# 통합 앱의 모바일 업무 예약·상호 수락 제안 r113

기준일: 2026-10-24. 상태: `MobileValidationPriorityAccepted / ProposedDesign / AppointmentDetailsPending / NewFeatureImplementationNotStarted`.

사용자는 통합 앱의 모바일 화면에서 매칭된 일을 수락·거절하고 특정 날짜/시간의 약속을 갖춘 뒤 업무가 진행되기를 요청했다. 기사 실시간 배차는 기존 방식을 유지하고 주문자도 참여·수령 약속의 당사자가 될 수 있게 한다. 이번 요청은 코드 구조·리팩토링·추가 기능에 대한 제안이다. [r112 변화 조회](shared-outcomes.implementation.r112.md)는 보존하며 새 예약·매칭·근무/지급·DB 변경을 시작하지 않는다.

## 1. 현재 구현과 공백

| 기존 기능 | 현재 의미 | 추가할 부분 |
|---|---|---|
| [HR 본인 지원](../../../../../Ssalddel/Application/HumanResources/HR역할지원CommandUseCase.cs) | 관심 지원·철회, 제출 요청 ID 중복 방지 | 업무 안내 이해 확인·특정일 신청·쌍방 약속 |
| [HR 역할 배정](../../../../../Ssalddel/Services/HumanResources/EfCoreHrRoleAssignmentStore.cs) | 관리자 역할 배정·거점/조직 범위, 반복 요일/시간 접근 허용 | 개별 시간 예약 확정·다른 약속과 충돌 검사 |
| [기사 예약](../../../../../Ssalddel/Application/Driver/Reservation/Handlers/예약생성CommandHandler.cs) | 미래 근무 시작 저장과 기존 추천 연결 | 현장 약속용 종료시각·양측 수락·요청 ID/CAS 구조가 아님 |
| [공동운영](../../../../../Ssalddel/Services/Community/공간공동운영UseCase.cs) | 역할 수락·조건 동의·거점/보관/입고/주문 확인 | 일정별 인원 충원·숙지·시간 약속·작업 권한 연결 |
| [공동운영 주문](../../../../../Ssalddel/Application/Mart/공간공동운영주문UseCase.cs) | 주문자/판매자 조건 확인과 명시적 전문 인계 | 주문자 수령 약속과 현장 작업 일정 연결 |

통합 앱은 기존 `/community/space-cooperations`와 공용 Workspace를 소비한다. 새 화면은 이 진입을 재사용하고 독립적인 일정의 수락·취소·상세는 별도 업무/상태로 분리한다. 기존 `AcceptRole`을 특정 업무 수락 명령으로 바꾸지 않는다.

## 2. 목표 흐름

`역할 관심/등록 → 필요한 업무 안내 → 개별 업무 신청 또는 제안 → 상대 확인 → 당사자 수락 → 시간 약속 확정 → 시작 전 준비 점검 → 전문 업무 수행 → 인계/결과/정산 확인`.

신청·추천은 예약이 아니고 예약은 실제 작업 시작이나 고용/보수 확정 자체가 아니다. 등록한 사람 전원이 매 작업마다 수락하는 것이 아니라 해당 업무에 필요한 당사자·역할·인원만 확인한다. 유효한 고정 근무표와 계약은 다시 가입시키지 않고 근거로 연결한다. 지금 일하고 싶은 참여자에게도 가까운 시작 시각의 일을 제시하고 그 시간 약속을 확정할 수 있다.

기사에게는 기존 실시간 추천·배차·수락을 유지한다. 출고 인계 예정은 배차 요청/현재 기사 상태를 참조하며 현장 참여 수락으로 기사 배정을 대신하지 않는다. 주문자는 구매·수령 조건의 당사자다. 본인이 별도 현장 역할을 선택한 경우에만 그 역할의 등록·숙지·신청을 거친다.

## 3. 추가할 세 가지 의미

1. **업무 모집**: 회차·전문 원장·작업 단계, 장소 범위, 시작/종료 시간창, 필요 역할·인원, 선행 업무, 조건/안내 판본과 보수 약정 참조를 가진다. 희망 역할과 특정 시간대의 빈자리를 구분한다.
2. **업무 제안·신청**: 사람과 모집 업무를 연결하고 `제안/신청 → 상대 확인 → 양측 수락 → 예약 확정`을 분리한다. 거절·철회·만료·변경 확인 대기도 보존한다. 일방의 클릭으로 상대 의사를 대신하지 않는다.
3. **확정 약속**: 사람·업무·시간창·장소·조건 판본·양측 수락 근거를 보존한다. 정원과 같은 사람의 중복 시간 수락은 서버 트랜잭션/예약 경합 제어로 막는다. 단순 조회 후 저장만으로 충돌 방지를 주장하지 않는다.

공유 DTO는 기존 Common/Community, 영속 명령은 Community UseCase와 HR/전문 원장 연결, UI는 공용 ViewModel/Client와 통합 앱 조립으로 나눈다. 추천 엔진을 먼저 크게 만들거나 기사 예약을 확장하기보다 이 세 의미를 먼저 완성한다. 실제 고용/급여·상품 예약·기사 배정은 해당 전문 정본이 계속 소유한다.

명령은 요청 ID와 내용 지문으로 멱등 처리하고 `ExpectedRevision`으로 경합을 검증한다. 수락 직전 현재 확정 일정·HR 범위/시간·이동 여유·정원을 서버에서 재검사한다. 시간·장소·보수·업무/숙지 기준의 중요한 변경은 새 판본의 재동의를 받는다. 알림은 기존 알림 시스템에 인계하되 수신만으로 약속을 확정하지 않는다.

## 4. 준비 완료와 실제 시작

회차 준비 조회에는 필요한 담당/인원·시간 약속·조건·숙지의 부족 이유를 더한다. 실제 시작 가능 여부는 해당 전문 서버 명령이 현재 권한·공간/재고·시간창·선행 업무를 다시 확인해 판정한다. 화면 표시나 과거 예약 성공만으로 시작하지 않는다.

단계마다 필요한 선행이 다르다. 주문 기반 피킹은 확정 주문·예약 재고·앞선 적치 등이 필요하지만 재고 확보용 입고에 아직 없는 주문자를 무조건 요구하지 않는다. 배송/수령 완료까지 기다려야 입고를 시작하는 순환 조건도 만들지 않는다. 기존 입고에는 협의/수용 정책 없는 옛 자료의 호환 분기가 있다. 새 매칭 업무의 명시적 일정 근거가 없으면 미확인으로 두며 옛 기록을 예약 완료로 승격하지 않는다.

거절은 해당 제안의 상태이며 신뢰 감점·보수 차감·다음 기회 배제의 근거가 아니다. 미시작 약속의 취소·철회·조건 변경은 준비를 보류하고 대체 담당을 찾는다. 이미 작업했거나 물품이 움직이면 전문 원장에서 중지·반환·인계를 처리하고 기존 수행·재고·보수 근거를 지우지 않는다.

## 5. 모바일 화면과 검증

기존 `생산에 참여해 보세요.`에서 `참여할 일`, `받은 제안`, `내 약속`으로 이어진다. 목록은 업무·장소 범위·월일/시간·할 일·보수 조건·다음 행동을 간결히 보여주고 긴 조건은 상세에서 확인한다. 받은 제안의 **거절은 왼쪽, 수락은 오른쪽**으로 둔다. 수락 뒤 상대 확인 대기와 예약 확정을 구분한다.

예약 상세에는 담당별 수락·조건·안내 확인과 시작을 막는 이유를 보여준다. 실제 작업으로 진입하고 완료 뒤 다음 담당자 인계 확인으로 연결한다. 주문자에게는 본인 주문/수령 약속, 현장 담당자에게는 필요한 작업 범위만 표시하며 다른 사람의 개인 보수·연락처를 노출하지 않는다.

검증은 **실제 통합 앱 APK의 휴대폰 화면과 동작**을 우선하고 좁은 폭 브라우저/컴포넌트 렌더를 보조 근거로 구분한다. 제안→상세→수락/거절→복귀, 양측 확인, 중복 수락 경쟁, 만료·조건 변경·철회, 앱 재실행/통신 실패 뒤 동일 요청 결과 조회, 계정 전환·권한 만료, 글자 확대·좁은 폭·키보드/하단 탐색 가림을 실제 예약 서버/영속 저장 재조회와 함께 검증한다.

## 6. 구현 순서와 미정

한 거점의 입고검수 일정 한 건부터 ① 업무 안내/신청 전 확인 ② 제안·상호 수락·예약 확정 ③ 충돌·변경·만료/취소 ④ 시작 전 준비·전문 업무 진입을 모바일에서 완성한 뒤 피킹·포장·주문자 수령 약속으로 넓힌다.

업무별 필수 당사자·확정 주체·마감/이동 여유·반복 근무표 연계·보수/계약 조건·알림 채널은 미정이다. 이 제안은 새 자동 배정·고용·급여·지급·제재 정책 확정이나 신규 기능 구현 완료를 뜻하지 않는다.
