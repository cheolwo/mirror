# 생활 앱의 외부 배송 가정 연결 r28

2026-10-07. 상태는 `Approved`다. 사용자는 배민·쿠팡이츠에도 배송 접수 API가 있다고 가정하여 공통 업무 구조를 준비하는 제안 뒤 `Implement the proposed plan.`으로 구현을 승인했다. 이는 해당 업체의 API 존재·제휴·실제 요금·운영 승인을 확인했다는 뜻이 아니다.

## 승인한 결과

생활 물품 한 건의 입력 → 견적 → 접수 → 기사 배정 → 픽업 → 전달 → 당사자 완료 확인을 기존 생활 앱·원장·r25 수행처 연결로 닫는다. 직접 수령·직접 전달과 기존 자체 배송·음식 배송을 보존한다.

기존 의뢰번호·물품·수량·무게·픽업/전달 위치와 연락처·시간창·요청사항·비용 상한·동의를 재사용하고 포장 크기는 선택 입력으로 추가한다. 값이 없으면 만들어 넣지 않는다. 카카오 T의 [공식 접수 문서](https://logistics-developers.kakaomobility.com/document/post-orders)는 위치·연락처·물품 크기의 참고 근거다. 우리 공통 입력을 다른 업체의 실제 요청 형식으로 주장하지 않는다.

기존 `I자동수행Provider`·접수 시도·동의·모의 사건 기록을 재사용한다. 카카오 문서 기반 및 배민·쿠팡이츠 API 가정 후보는 이름과 견적에 모의 표시를 붙인다. 업체의 실제 endpoint·인증·응답·요금은 추측하여 구현하지 않는다. 기능과 가정 후보 opt-in은 기본 꺼짐이며 Simulation에서만 사용한다. 기존 provider ID는 유지한다.

추가 후보는 서버가 반환한 활성 후보 목록에만 노출한다. 후보 수·소진 판정은 등록 및 동의한 목록 기준으로 제한하고 같은 동의 판본에서 각 후보를 한 번만 시도한다. 불명확한 접수·취소나 비용 미확인은 다른 업체 접수를 막는다.

외부 모의 전달 증거는 현재 실행·원 의뢰·동의 판본에 결속해 읽는다. 내부 기사나 큐를 생성하거나 원 화물의 내부 기사 완료 상태를 꾸며내지 않는다. 생활 약속의 완료 제안과 상대 확인·지급은 독립 상태로 유지한다. 가정 배송 증거는 Simulation 밖의 실제 완료 근거가 아니다.

## 구현과 검증 상한

공통 입력·서버 후보·모의 수행·생활 약속 연결과 공통 UI만 수정한다. 격리 SQLite 및 필요 시 기존 로컬 검증 DB, 인증 대역 HTTP·공통 UI 렌더로 중복/재시작/불명확 결과/취소/늦은 사건/타인 접근과 내부 큐 0건을 확인한다. 집중 시험·영향 소비 호스트 build·Fast/Task를 구분한다. 모바일 예시는 확정 시안이나 휴대폰 증거가 아니다.

실제 업체 호출·개인정보 외부 전송·실결제·실지급·공용 DB migration 적용·APK 설치·Unity·운영 활성화·commit·push·배포는 제외한다. 인계의 정확 소유 파일과 승인 hash는 [작업지시서](development-work-order.r28.md)가 결속하고 실제 결과는 별도 변경 기록으로 반환한다.
