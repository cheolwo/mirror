## 고객지원은 지금 정한 범위에서 정리

[r78](workflow-operating-decisions.design.r78.md)부터 r84까지의 수용 방향을 보존한다. 전달 증빙·지급 재원이 있는 단순 무응답과 실제 신고를 구분하며, 신고 시 해당 주문의 미지급 정산을 보류한다. 상담원 1차 확인·센터 관리자 처리·양쪽 관리자 알림과 가능한 한 6시간 응답 → 24시간 처리 목표 → 미해결 시 72시간 처리 목표 → 운영자 직접 처리 인계의 방향은 그대로다.

- 보류할 질문: `reported-delivery-issue-operator-absence-owner`
- 이전 상태: r84의 `Asked / Unanswered`
- 현재 상태: `Deferred / NotDecided / TopicChangeRequested`

대체 담당자 지정은 승인 또는 거절된 것이 아니라 이번 논의에서 뒤로 둔다. 시간표·기산 시점 등 세부 미정도 이력에 남기며, 고객지원 전체 설계나 실제 운영 준비가 완료됐다고 표시하지 않는다. 이번 분야 전환을 이유로 고객지원 세부 질문을 계속 늘리지 않는다.

## 다음 분야의 제안 순서

| 분야 | 이미 있는 구조 | 다음에 정할 부분 |
| --- | --- | --- |
| 기본 작업 보수의 재원 | 입고·보관과 출고·배송의 보수 발생·지급 분리, 비용 귀속, 잔여금 분배 | 누가 기본 보수를 지급하며, 언제 어떤 재원을 확보하고 부족하면 새 일감을 어떻게 할지 |
| 작업 수락과 인계 | 사진·수량 근거와 단계별 완료 기록 | 맡은 일을 중단하거나 일부만 끝냈을 때 다음 담당자가 이어받을 업무와 보수 |
| 공간·재고 운영 약속 | 보관 계약·반출 합의·사진 인계·잔량 검사 | 물품 소유자 무응답·공간 종료 때 실제 회수 담당·기한·추가 비용 |

이 순서는 제안이다. 사용자가 세 분야의 세부 정책이나 구현을 일괄 승인한 것은 아니다. 우선 기본 작업 보수의 지급 재원을 논의하여 주문·입고 계약과 실제 수행자가 함께 확인할 수 있는 기준을 정하는 것을 추천한다.

## 기존 원장 구조를 이용하는 범위

[r60](receiving-outbound.implementation.r60.md)은 입고·보관 보수와 출고·배송 보수를 별도 흐름으로 둔다. 입고 작업비를 판매 주문마다 다시 지급할 채무로 만들지 않는다. [r61](settlement-economics.implementation.r61.md)은 비용·예비금을 반영한 잔여금에서 참여자 성과금과 플랫폼 몫을 나누는 구조다. 기본 작업비를 차감한 뒤 나누는 이 계산을 새로 정할 질문처럼 반복하지 않는다.

아직 함께 정할 것은 합의 수익과 실제 지급 재원의 차이, 지급 책임자, 재원 부족 시 새 작업 제안을 어떻게 조절할지다. [r73](transport-prepayment-settlement.implementation.r73.md)의 화물 배송료 선결제 준비가 있다고 해서 입고·피킹·포장 등의 모든 기본 작업비가 확보됐다고 간주하지 않는다. 같은 재원을 여러 작업의 지급 보장으로 중복 계산하지 않으며 서버 운영 예산을 작업 보상 재원으로 합치지 않는다.

아래 질문은 **플랫폼이 보수를 지급하는 일감**으로 한정한다. 당사자가 직접 정산하기로 한 거래까지 플랫폼 결제·선입금·자금 보관을 필수화하는 제안이 아니다. 실제 은행 이체·결제 계약을 새로 실행하지 않는다.

## 다음 질문 하나

- 질문 의미 ID: `platform-funded-work-start-gate`
- 상태: `Asked / Unanswered`
- 질문: **플랫폼이 보수를 지급하는 일감은, 작업자에게 제안하기 전에 지급 재원을 확보하고 부족하면 신규 제안을 잠시 보류하도록 할까요?**
- 제안: 입고·피킹·포장·배송의 지급 책임과 확보 재원을 각 업무 근거에 연결한다. 확보되지 않은 예상 매출만으로 지급을 보장하지 않으며, 재원 부족을 이유로 이미 합의한 작업자의 기본 단가를 조용히 줄이지 않는다.
- 미정: 재원 확인 수단·소유자·확보 시점, 보류 후 재개 조건, 이미 시작한 업무의 부족분 처리. 선결제·예비금 출연·플랫폼 전액 보상·실송금·새 코드 구현은 아직 승인하지 않았다.
