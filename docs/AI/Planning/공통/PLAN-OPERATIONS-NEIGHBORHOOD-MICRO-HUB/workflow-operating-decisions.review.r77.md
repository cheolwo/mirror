## 확정된 방향과 현재 보호

주문을 기준으로 전문 업무 원장을 연결하고, 입고·보관과 출고·배송을 분리한다. 실제 수행자·수량·사진·합의 단가로 기본 작업 보수를 기록하며 공동 성과금은 별도로 둔다. 업무별 발생액과 본인 주간 명세, 지급 신고와 실제 입금은 구분한다. 한 사람이 여러 역할을 수행할 수 있지만 단계별 완료·인계와 보수 근거는 보존한다.

이는 [r59](activity-compensation.implementation.r59.md), [r60](receiving-outbound.implementation.r60.md), [r61](settlement-economics.implementation.r61.md), [r73](transport-prepayment-settlement.implementation.r73.md), [r76 결과](../../../../Changes/2026-10-15-workflow-exception-closeout-r76.md)에 따른다. 기본 보수의 발생과 고객 수령 뒤 정상 지급이라는 서로 다른 시점을 기획 모순이나 보수 삭제로 설명하지 않는다.

1번의 근거는 [r60의 역사와 예외 보호](receiving-outbound.implementation.r60.md#역사와-예외-보호), 2번은 [r61 계산과 근거](settlement-economics.implementation.r61.md#계산과-근거), 3·4번은 [r76 후속](../../../../Changes/2026-10-15-workflow-exception-closeout-r76.md#아직-별도로-필요한-일)과 [r63 계약·회수](supplier-space-inbound.implementation.r63.md), 5번은 [r45 운영자 알림](operator-alerts.implementation.r45.md)이다.

회수 조건·예비금·알림 기능 자체가 없다는 뜻은 아니다. 기능을 이용해 실제 책임·최종 처리 기한·자금 부족·무응답을 어떻게 끝낼지의 공통 정책이 미정이다. `max(0, 수익−비용)` 계산으로 배분 가능한 잔여금이 0이 되는 것과 실제 손실이 없어지는 것은 다르다. 합의 수익·지급 신고도 확보된 현금과 동일하지 않다.

## 문답 진행 방법

생활 물품 주문 한 건을 골라 정상 수행, 고객 무응답, 일부 누락, 담당자 중단, 공간 회수 거절을 각각 따라간다. 각 상황에서 `현재 담당 → 필요한 확인 → 기다리는 기한 → 다음 담당 → 비용·보수 → 종결 근거`를 정한다. 정책을 합의한 다음에만 해당 기획 판본과 필요한 구현 범위를 별도로 승인한다. 새로운 전역 질문 번호·새 D 항목·ReadyToDispatch 작업 명세는 만들지 않는다.

## 이번 검토의 한계

기존 문서·직전 구현 기록을 읽어 미정 정책을 추렸다. 새 테스트·앱 실행·법률 조사·실제 계약·입금 검증은 수행하지 않았다. 실제 책임·계약 효력·의무 적용을 이번 기획 검토로 확정하지 않는다. r76 로컬 시험 결과를 운영 완료로 승격하지 않는다.
