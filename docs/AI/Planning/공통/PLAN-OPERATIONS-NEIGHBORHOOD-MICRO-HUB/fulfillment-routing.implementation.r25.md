# 생활 배송·음식 배달 자동 수행처 선정 r25

- 기준일: 2026-10-07.
- 상태: `Implemented / LocalSimulationValidated / SimulationOnly / RealProviderPending`.
- 선행: [생활 배송 수행 방식 선택 r24](fulfillment.implementation.r24.md), [기사 배차 뒤 조리 시작 r62](../../시스템/PLAN-SYSTEM-FRANCHISE-OPERATIONS/driver-first-cooking.implementation.r62.md).
- 승인: 사용자가 생활·음식 모두 플랫폼 선정, 사전 조건 안 자동 접수, 시간 충족 후 낮은 총비용, 같은 조건 안 자동 재선정, 음식점 정액 지원과 주문자 잔여 부담을 선택한 뒤 계획 구현을 요청했다.

## 승인 결과

생활 배송과 음식 배달의 자체 배차·모의 위탁 후보를 플랫폼이 선정한다. 희망 완료 시각을 충족하는 후보 중 낮은 총비용을 우선하고 동률이면 빠른 완료 시각, 이후 고정 공급자 ID 순서로 결정한다. 사용자의 비용 상한·시간·허용 공급자·개인정보 제공 및 자동 접수 동의 범위 안에서만 실행한다. 비용·시간·가용성이 불명확하거나 후보가 없으면 이유를 표시하고 보류한다.

새 기능은 `FulfillmentRouting:Enabled` 기본값 꺼짐과 `SsalddelExecution:Mode=Simulation` 경계를 사용한다. 실제 업체 API, PG, 청구·지급·운영 공개·Unity·DOT 상시 운영·커밋/푸시는 이번 구현의 완료 주장에 포함하지 않는다. 기존 접수·구형 클라이언트는 자동으로 전환하지 않는다.

## 공통 선정·실행·복구

공통 Coordinator가 견적·선정 근거·사전 동의·현재 수행·실행 시도를 소유하고 생활/음식 원천 adapter가 권한·현재 상태·배차를 검증한다. engine은 후보와 평가를 반환하며 실제 상태 확정은 서버 Command/Coordinator의 트랜잭션을 통한다.

원천 종류는 `NeighborhoodDelivery`, `FoodOrder`다. 원 요청당 현재 수행은 하나이며 현재 키는 `(SourceKind, SourceId)`다. 수행/조리 차수는 시도·견적 근거에 저장하고 활성 또는 Unknown 수행을 우회하는 새 접수 키로 사용하지 않는다. 기존 r24 세 테이블 이름과 실행 ID를 유지하고 discriminator·동의/분담 근거와 인덱스를 확장한다. 기존 생활 데이터는 명시적으로 기본 discriminator를 채운다.

자동 실행 직전에 원 요청·동의·견적 판본, 현재 상태, 만료·회수, 허용 공급자와 비용·시간 조건을 다시 확인한다. 현재 실행 시도를 영속 저장한 뒤 같은 멱등 키로 호출한다. 응답 유실·재시작은 같은 시도를 확인하며 일시적인 조회 실패/404를 확정 실패로 취급하지 않는다. Outbox claim·결과 저장, 자체 큐 생성, 옛 기사 제안 수락, 원장 재투영도 동일 수행 판본으로 보호한다.

확정 실패 또는 취소 완료 뒤 같은 동의 조건 안에서 재견적·자동 재선정한다. Unknown/CancelPending, 취소 비용 또는 발생 비용 미확인은 재접수하지 않는다. 이미 발생한 확정 비용까지 누적 상한에 포함한다. 동일 원 요청+동의 판본에서 공급자별 접수는 한 번이며 후보 소진 뒤에는 재확인을 요구한다. 자체 기사 한 명의 거절은 공급자 실패가 아니며 같은 내부 수행에서 기존 기사 추천을 이어간다. 동의 철회나 기한 경과는 새 접수를 멈추고 현재 수행을 임의로 완료/취소하지 않는다.

## 음식 배달과 비용 분담

음식점이 주문당 정액 지원액 `S`와 설정 판본에 명시적으로 동의한다. 주문자는 지원액과 본인 잔여 부담 상한 `A`를 확인한다. `S`와 설정 판본을 해당 주문에 동결하며 지원 설정 변경·동의 갱신·leg 변경·재견적마다 초기화하지 않는다. 생활 배송은 `S=0`이다.

발생한 확정 비용+새 수행 견적의 주문 전체 누적 총비용을 `C`라 하면 음식점 부담은 `min(S,C)`, 주문자 부담은 `C-min(S,C)`이며 주문자 부담이 `A`를 넘으면 접수를 보류한다. 메뉴 합계·고객 배달비·음식점 지원액·공급자 수행비·자체 기사 지급액은 별도다. 지원/비용 기록은 실제 청구·입금·환불·기사 지급 완료가 아니다.

음식 정상 순서는 `주문 확인 → 플랫폼 선정·접수 → 유효 기사 배정 → 음식점 명시 조리 시작 → 픽업 → 전달 → 수령 확인`이다. 식당 확인과 같은 트랜잭션에는 공통 수행 요청을 예약하고 자체 음식 큐를 동시에 생성하지 않는다. 내부 선정 이후 기존 음식 배차 엔진·기사 수락 경로를 사용한다. 견적 ETA는 기사 확보 대기·조리·픽업·전달을 포함하며 음식 전용 가격/경로 근거를 사용한다.

외부 Accepted는 유효 기사 배정이 아니다. 현재 공급자·실행·수행/조리 차수·배정/해제 판본에 결속된 별도 배정 증거 adapter를 통해 조리 시작을 검증한다. 가짜 내부 기사 계정이나 화물 의뢰/큐를 생성하지 않는다. 외부 기사 해제와 공급자 접수 취소는 다르며 오래된 배정 응답은 조리 가능 상태를 복원하지 못한다. 모의 업체도 영속 접수와 배정·픽업·전달을 개별 단계로 기록하고 시간 경과만으로 주문을 완료하지 않는다.

조리 시작 이후 처리처 자동 변경은 보류한다. 기사 변경으로 이미 시작한 조리·준비 완료 이력을 초기화하지 않는다. 기존 주문 취소·재조리 경계를 보존하고 새 취소/환불/대기 보상 정책을 만들지 않는다. 모의 외부 완료를 내부 기사 정산 recorder에 입력하지 않는다.

## API·화면·호환

공통 계약에 자동 수행 동의, 선정 결과/근거, 비용 분담, 배정 증거를 추가한다. 새 등록 필드는 nullable이고 null 직렬화 제외로 기존 접수 fingerprint를 보존한다. 기존 생활 API와 음식 주문번호·상태·가능 행동을 유지한다. 기존 음식 주문 API 아래 자동 조건 저장·수행 상태/재확인과 식당 지원 설정을 추가하고 주문 취소와 공급자 취소를 별도 행동으로 유지한다.

신규 UI는 후보 수동 선택보다 비용·시간·위탁 조건과 자동 동의를 받는다. 주문자 상세는 선정 이유·비용 분담·모의 구분·최신 확인·진행/확인 필요 상태를 보여준다. 식당은 주문 확인→배정 확인→조리 시작의 기존 행동을 유지한다. 내부 기사 제안/수락은 보존하고 모의 외부 업무를 실제 제안·지급 준비에 섞지 않는다. 기존 기능 꺼짐/구형 요청/기존 manual 수행은 호환하지만 새 자동 current와 경합하는 경로에도 같은 판본 검사를 적용한다.

## 검증과 완료

- 관계형 영속·동시 선정·중복 요청·호출 전 종료·응답 유실/재시작·취소 경합·늦은 응답·동의 철회/갱신·상한/만료·공급자 소진과 자동 재선정.
- 외부 선정 뒤 옛 음식 Outbox/원장/기사 제안이 자체 큐를 부활시키지 않음. 접수만으로 조리 시작 불가, 최신 배정/해제 증거와 조리 상태 보존, 준비 완료 뒤 픽업·전달·수령 확인.
- 정액 지원의 주문 전체 1회 적용, 발생 비용 미확인 차단, 메뉴 합계/기사 요율 보존, 모의 결제/정산 혼입 차단, 다른 주문자/식당 접근 차단.
- 실제 공유 Razor의 320/390px 상태·오류·복귀와 가로 넘침, 기존 r24 회귀, 집중 시험 후 Fast·Task·소비 앱 빌드. synthetic 렌더·HTTP/DB 완주·외부 업체·실제 단말·운영은 독립 결과로 기록.
- 스키마 migration과 기존 discriminator 채움 검증, 기존/무관 dirty 보존·문서 링크·diff 검사. 실제 공용 DB 적용·커밋/푸시·배포는 별도다.

구현과 로컬 검증을 마쳤다. 집중 138개·Fast 344개·Task 8,234개 통과(환경 조건 Mongo 2개 건너뜀), 전체 3.5 제품/소비 앱 빌드와 실제 공통 Razor의 26개 모바일 장면을 확인했다. 음식 서비스/HTTP의 대역 범위, SQLite migration 적용과 MySQL SQL 생성, 미실행 공용 DB/업체/PG/단말 경계는 [변경·검증 기록](../../../../Changes/2026-10-07-fulfillment-routing-r25.md)에 결속한다. 아래 상태는 실제 업체 운영 완료가 아니다.

## 로컬 실행 준비

기본 플래그는 꺼짐이다. DB 연결 전에 r24 `20261007140000_AddNeighborhoodFulfillment`과 r25 `20261007160000_AddAutomaticFulfillmentRouting` 스키마가 필요하다. Simulation 설정에서 `FulfillmentRouting:Enabled=true`로 켜면 조건 확인 뒤 공통 Outbox 작업이 수행을 접수한다. 모의 업체 단계는 인증된 관리자 증거 API로 명시적으로 전이하며 자동 시간 완료를 사용하지 않는다. r25 migration Down은 원천별 데이터 손실을 막도록 차단했으며 별도 검토된 되돌림 migration이 필요하다.

기능을 끄면 기존 자동 요청은 조회 전용 정지로 표시하고 비용·상한을 미확인으로 유지한다. 현재 업체 접수의 취소를 뜻하지 않는다. 실제 공급자 연결과 공용 DB 적용·운영 단말·지급은 별도다.
