# 생활 공간 입고·보관과 출고·배송 분리 r60

`PLAN-OPERATIONS-NEIGHBORHOOD-MICRO-HUB / r60 / Implemented / LocalValidated / OperationalDeferred`

2026-10-12 사용자가 입고 과정과 출고 후 배송 과정을 각각 관리하도록 제안을 수용하고 리팩토링을 직접 요청했다. [r59 활동 보수·성과금](activity-compensation.implementation.r59.md)을 보존하며 이번 요청은 같은 작업실의 후속 구현이다. [작업 명세](receiving-outbound.r60.work-order.json)와 [검증 반환](../../../../Changes/2026-10-12-receiving-outbound-r60.md)을 따른다.

## 두 업무의 경계

| 흐름 | 기존 정본 | 새 약정에 허용하는 보수 | 지급 시점 |
| --- | --- | --- | --- |
| 입고·보관 | `DistributedLot`, 입고 사진·실제 재고 변화·보관 구간 | 입고비·보관료 | 개별 완료 작업과 금액의 양측 확인 후 지급 신고. 전량 입고·판매·배송을 기다리지 않음 |
| 출고·배송 | `DistributedOrder`, 예약·피킹 이력·전달·고객 수령 | 피킹비·배송비·판매대금·판매대행·소유자 전달금 | 정상 지급 신고는 최종 배송과 고객 수령 근거 확인 후. 기본 보수 발생은 수행 시 기록 |

새 약정은 서버가 `WorkflowKind`와 `PaymentReleaseCondition`을 원천 종류에서 동결한다. 다른 흐름의 항목 추가와 출고 지급 관문 완화는 차단한다. 완료 작업의 기록·보수 발생·금액 확인·지급 신고·수령 확인·은행 확인은 계속 별개다. 원배송 원장의 운임 참고를 신규 지급 채무로 만들지 않는다.

입고·출고는 실제 Lot/예약/주문 ID로 연결한다. 입고 한 번이 여러 출고 주문에 나뉘어도 입고 작업비를 주문마다 복제하지 않는다. 전체 재고의 피킹·반환 이력은 보관 기간 계산에만 사용하고 별도 `StorageEvidenceReferences`로 보존한다. 새 수량별 보관 약정은 입고 완료 수량으로 계산하며 고객 판매를 근거로 대신 사용하지 않는다.

입고는 Planned/PartiallyReceived/Received를 실제 수량과 사진 근거로 읽는다. 부분 입고도 완료된 수량만 청구할 수 있다. 분산 입고의 파손·반려 전용 상태/명령은 이번에 추가하지 않으며 일반 창고 검수 API로 우회 완료하지 않는다.

출고 정산 참여자는 해당 주문의 실제 피킹 담당자, 현재 기사와 기존 소유자·판매자·공간 제공자·고객이다. 같은 Lot의 다른 주문 피킹 담당자나 별도 입고 담당자에게 현재 주문 정산 접근권을 부여하지 않는다. 후속 출고 작업자가 추가되어 입고 약정의 동의 판본이 바뀌지 않도록 분리한다.

## 역사와 예외 보호

기존 `WorkflowKind=null` 판본은 `LegacyMixed`로 표시하고 과거 발생액·지급 기록·동의·요청 영수증은 소급 변경하지 않는다. 명시적으로 조건을 수정할 때는 새 흐름을 동결하고 다시 동의한다. 구형 혼합 약정의 잘못된 항목으로 추가 청구하는 것은 차단한다.

지급 관문은 각 항목의 당시 약정 판본을 따른다. 증액 조정도 원본 항목 판본을 따르며 최신 약정으로 우회하지 않는다. 음수 조정의 환불은 고객 수령 관문에서 제외하지만 기존 실수령·환불 상한·양측 확인 검사는 유지한다. 이미 확정한 입고비와 구형 채권은 불필요한 원천 재조회 장애로 지급 신고를 막지 않는다.

출고 고객 수령 근거가 없거나 원천 조회가 실패하면 정상 지급 신고는 대기한다. 이미 수행한 보수를 0으로 삭제하지 않는다. 실패 배송·장기 미수령의 별도 합의 종결/예외 지급 정책은 후속이며, 이번에 무조건 지급 또는 자동 미지급으로 확정하지 않는다. 공동 성과금은 기존 고객 수령·동의·현재 기여·잉여 검사를 유지한다. 입고 비용의 주문별 원가 배분을 추정해 추가하지 않는다.

## 화면·코드·저장 책임

기존 `/activity-settlements`와 상세 route를 유지한다. 목록은 입고·보관/출고·배송/기타·기존 약정으로 구분하며 상세는 현재 단계·현재 약정 지급 기준·당시 약정에 따른 항목별 대기 사유를 보여 준다. 지급 대기 중에도 발생액·이의·지급 진술·수령 기록은 남긴다. 원시 재고 ID와 사진 주소는 화면에 노출하지 않는다. [페이지 책임](../../../../ProjectOverview/page-docs/activity-settlements-r60.md)을 따른다.

`NeighborhoodSettlementUseCase.Workflow`가 약정 경계·판본별 지급 관문을, `SourceResolver`가 현재 전문 원장의 작업·수량·근거와 연결 재고를 소유한다. 순서표나 클라이언트 플래그로 업무를 완료하지 않는다. 기존 약정/판본/항목 JSON을 재사용하며 새 테이블·새 migration은 추가하지 않는다. r59의 기존 migration을 공용 DB에 적용하지 않는다.

기존 기본 OFF·Simulation·정확한 profile·당사자 권한·revision·멱등 경계를 유지한다. 실제 지급·은행·단말·Azure·운영 활성화·Unity·commit/push는 이번 범위가 아니다.
