## 목적

음식 주문, 마트 주문, 공동구매, 개별 수입·수출, 화물 운송 의뢰처럼 서로 다른 업무를 **주문 또는 주문이 되기 전의 의도**에서 시작해 추적한다. 주문이 확정된 뒤 발생한 판매 이행, 조리, 창고 입출고, 피킹·포장, 배차, 배송·운송, 인수·검수, 정산과 비정상 업무 처리가 어떤 운영체제(OS)로 넘어가고 다시 어떤 결과로 돌아오는지 하나의 업무망으로 설명한다.

주문은 모든 상태를 직접 소유하는 거대 OS가 아니라 전체 업무가 시작된 이유와 최종 결과를 잇는 **인과축**이다. 각 OS는 자기 원장과 상태 전이의 권위를 유지하고, 다른 OS에는 판본화된 Command·Event·업무 인계 계약으로만 영향을 준다.

보조 담당자의 기본 권한은 승인한 대로 `진행 조회·현장 증빙 등록·연락 기록`으로 제한한다. 주소·시간·연락처, 운임·정산, 배차 조건, 인수 확정과 비정상 운송 처리는 화주가 해당 담당자에게 명시적으로 추가한 현재 revision에서만 허용한다.

업무망 조회는 주소·연락처·좌표·사용자/기사 식별자를 반환하지 않으며 원본 주문·운송·인계 원장을 변경하지 않는다. `CorrelationStableId`는 루트 운송 서비스 주문의 비식별 안정 키이고, 각 OS 원장의 고유 식별자와 revision은 별도로 보존한다.

## 현재 저장소에서 확인한 기반

- `OperatingSystemIds`에는 화주 운송관리, 화물운송, 창고 이행, 공동구매 수요, 공동구매 수입, 음식배달, 살뜰마트 도심물류, 커뮤니티 신뢰, 플랫폼 운영, 교육·현장체험 OS가 등록돼 있다.
- `OperatingSystemLifecycleCatalog`에는 현재 화주 운송관리, 화물운송, 음식배달, 살뜰마트 도심물류 네 OS의 순서 있는 내부 생명주기만 정의돼 있다. 나머지 OS 식별자는 존재하지만 같은 수준의 생명주기 대장이 아직 없다.
- 커뮤니티 원장 대장에는 `주문 통합 원장`이 주문을 루트로 판매·창고 입출고·배송·운송 원장을 한 맥락으로 묶도록 정의돼 있다. 개별 주문을 모은 공동 주문은 원천 개별 주문을 대체하지 않는 집계 원장이다.
- 실제 코드에는 다음 OS 간 인계가 이미 존재한다.

```text
ShipperTransportManagementOS
  ── ShipperTransportRequestToDomesticCargo ──> DomesticCargoTransportOS
  <─ DomesticCargoCompletionToShipperAcceptance ──

WarehouseCommerceFulfillmentOS
  ── WarehouseOutboundToCargoTransport ──> DomesticCargoTransportOS

SsalddelMartUrbanLogisticsOS
  ── SsalddelMartLastMileToFoodDelivery ──> FoodDeliveryOS
```

- 현행 `운영체제업무인계` 원장은 실제 요청·수락·결과 인계를 기록하지만, 모든 OS의 가능한 선후행 관계를 설명하는 정적 설계 대장은 아니다.

## 확정

### 1. 주문을 중심에 두되 주문 이전을 지우지 않는다

주문이 성립하는 길은 하나가 아니다.

```text
판매자 제안 선행
  상품·서비스 제안 → 구매자 선택 → 조건·동의 확정 ┐
                                                   │
구매자 수요 선행                                  ├→ 확정 주문
  개인 의향 → 공급자 탐색·매칭 → 조건·동의 확정 ─┤
                                                   │
공동 수요 선행                                    │
  비구속 의향 → 모집·집계 → 공급자 매칭            │
  → 각 참여자의 명시적 주문 확정 → 공동 주문 집계 ┘
```

상품 게시, 개인 의향, 공동구매 모집은 주문의 근거가 될 수 있지만 그 자체가 확정 주문은 아니다. 당사자·대상·수량·가격 또는 운임·이행 조건·동의 판본이 확정되는 관문을 지나야 주문 업무망의 루트가 열린다.

### 2. 화물 운송 의뢰도 서비스 주문으로 본다

화물 운송 의뢰는 물건을 사는 상품 주문은 아니지만, 화주가 운송 서비스를 요청하고 조건·운임을 확정한다는 점에서 서비스 주문이다. 다만 기존 `화주 운송관리 OS` 원장을 없애고 범용 주문 원장에 물리적으로 합치지는 않는다. 공통 주문 관점에서 같은 인과축으로 조회할 수 있게 연결하고, 화물 정의·운임·인수·검수의 권위는 화주 운송관리 OS에 남긴다.

### 3. 화주 기본값과 실제 업무 담당자를 분리한다

이 기획에서 `화주`는 운송 건의 조건을 결정하고 결과를 확인하는 대표 역할이고, `운송 담당자`는 화주에게 권한을 받아 화면에서 실제 업무를 처리할 수 있는 사람이다. 두 역할은 같은 사람일 수도 있고 다를 수도 있다.

기본값은 다음처럼 단순하게 둔다.

```text
개별 주문
  주문한 개인 = 기본 화주
  └─ 선택: 대행자·담당자에게 운송 업무 권한 위임

공동 주문
  공동주문 대표 = 기본 화주
  └─ 선택: 실무 담당자에게 운송 업무 권한 위임
```

예를 들어 개인 주문자 민수가 직접 운송을 신청하면 `민수=화주=실제 요청 행위자`다. 민수가 물류 대행자에게 맡기면 `민수=화주`, `대행자=권한 있는 운송 담당자`다. 공동주문 대표 영희가 직접 신청하면 `영희=화주=실제 요청 행위자`이고, 영희가 실무 담당자 철수에게 맡기면 `영희=화주`, `철수=권한 있는 운송 담당자`가 된다.

담당자가 운송 의뢰를 작성·제출하거나 진행을 관리해도 화주가 담당자로 바뀌지는 않는다. 감사 기록에는 항상 `이 운송의 화주가 누구인지`와 `이번 Command를 실제로 수행한 사용자가 누구인지`를 함께 남긴다.

공동 운영 주체가 있더라도 사용자 화면과 운영 생명주기의 기본 화주는 그 공동주문의 대표로 둔다. 공동 운영 주체는 공동주문 묶음, 비용 분담, 계약·정산의 귀속 범위를 나타내는 별도 참조로 유지한다. 따라서 대표가 교체되거나 담당자가 바뀌어도 원천 개별 주문과 공동주문 묶음은 사라지지 않는다.

다음 역할을 서로 다른 값으로 보존한다.

- `원천주문범위`: 운송이 발생한 개인 주문 또는 공동주문 묶음
- `화주역할자`: 개인 주문자 또는 공동주문 대표
- `실제행위자`: 이번 운송 의뢰·수정·조회 Command를 실행한 사용자
- `위임근거`: 화주가 담당자에게 허용한 업무 범위와 판본
- `비용귀속범위`: 개인 주문 또는 공동주문 비용 원장
- `수하인`: 실제 도착지에서 물건을 인수하는 개인·거점·운영 주체

위임에는 대상 주문 또는 공동주문 묶음, 금액·시간·지역 상한, 유효기간, revision과 철회 상태를 둔다. 대표나 담당자가 바뀌어도 이미 확정된 운송의 당시 역할·권한 판본은 감사 기록으로 보존한다.

담당자는 단순 입력 보조자가 아니라 `운송전권담당자`를 기본으로 한다. 유효한 위임과 승인된 주문·비용 범위 안에서는 다음 운영 업무를 대부분 수행할 수 있다.

- 운송 의뢰 초안 작성·제출·수정·취소 요청
- 운임 견적 확인과 승인된 상한 안의 조건 확정
- 배차 진행 확인, 기사 제안·수락 결과 확인과 연락 조정
- 상하차 시간·연락처·현장 요청사항의 일상적인 조정
- 상차·하차·인수 증빙 확인
- 최종 인수·검수와 승인된 범위 안의 정산 확인
- 수량 불일치·파손·하차지 부재 같은 비정상 운송 신고·검토·회복안 선택
- 재배송·반품 검토와 후속 업무 요청

담당자에게 주지 않는 것은 운영 권한이 아니라 **업무 주인 자체를 바꾸는 권한**이다.

- 화주역할자를 다른 사람으로 변경
- 원천 개인 주문이나 공동주문 묶음의 참가자·수량·동의를 변경
- 공동주문 대표를 교체하거나 공동 운영 주체를 변경
- 승인된 비용 상한을 넘어 새 부담을 확정
- 자기 권한을 다른 담당자에게 재위임
- 원장·증빙·감사 기록을 삭제하거나 과거 revision을 덮어쓰기

이 경계를 넘는 변경이 필요하면 담당자가 변경안을 만들 수는 있지만, 화주 또는 해당 주문 권위자의 새 승인을 받아야 한다. 화주는 언제든 미래 Command에 대한 담당자 권한을 철회할 수 있지만, 이미 적법하게 실행된 업무와 감사 기록은 소급 삭제하지 않는다.

담당자 구성은 운송 건마다 다음처럼 둔다.

```text
화주
  └─ 주 담당자 1명
       ├─ 보조 담당자 0명
       ├─ 보조 담당자 1명
       └─ 보조 담당자 여러 명
```

- `주 담당자`는 유효한 위임 범위 안에서 앞서 정한 운송 운영 권한 대부분을 행사하며 기사·화주·현장 사이의 기본 연락 창구가 된다.
- `보조 담당자`는 화주가 각자에게 부여한 조회·현장 처리·증빙·연락 같은 범위만 수행한다. 주 담당자의 계정을 공유하지 않는다.
- 한 운송 건에는 활성 주 담당자를 정확히 한 명만 둔다. 화주 본인이 직접 관리하면 화주가 주 담당자를 겸한다.
- 주 담당자 교체는 기존 담당자 고유 식별자를 덮어쓰지 않고 `종료 revision → 새 담당자 지정·수락 revision`으로 기록한다.
- 보조 담당자는 주 담당자 부재만으로 자동 승격되지 않는다. 화주가 새 주 담당자를 명시적으로 지정하거나 직접 업무를 다시 맡는다.
- 주 담당자와 보조 담당자는 다른 사람에게 권한을 재위임할 수 없다. 담당자 지정·범위 변경·철회는 화주가 소유한다.
- 교체와 철회는 이후 Command부터 적용하며, 이전 담당자가 유효한 권한으로 수행한 업무·증빙·감사 기록은 유지한다.

플랫폼 위임은 별도 운영·법률 관문을 통과한 경우에만 가능한 유형으로 남기며, 공동주문이라는 이유로 플랫폼을 기본 화주나 비용 부담자로 만들지 않는다.

### 4. OS 사이에는 전역 순번이 아니라 부분 순서를 둔다

모든 OS에 `1, 2, 3`의 단일 전역 순번을 부여하지 않는다. 공급계약·재고 보충은 고객 주문보다 먼저 일어날 수 있고, 한 주문의 창고 작업과 배송 준비는 일부 병렬로 진행될 수 있으며, 분할 배송은 하나의 주문에서 여러 자식 업무로 갈라진다. 비정상 업무 처리는 앞 상태를 지우지 않고 원래 업무를 보류한 채 검토·재처리·종료 중 하나로 되돌린다.

따라서 OS 내부에는 기존처럼 순서 있는 `LifecycleStage`를 두고, OS 사이에는 `출발 단계 → 인계 계약 → 도착 단계 → 반환 조건`의 방향성 있는 엣지를 둔다.

### 5. 공통 업무 구간

| 구간 | 의미 | 대표 책임 |
| --- | --- | --- |
| 0. 발견·관계 | 상품·서비스·수요를 발견하고 대화한다 | 커뮤니티·공공자료 조회. 주문 자동 생성 금지 |
| 1. 제안·의향 형성 | 판매 제안, 개인 의향, 공동 수요를 구체화한다 | 판매 주체, `GroupPurchaseDemandOS`, 커뮤니티 원장 |
| 2. 주문 확정 | 당사자·대상·수량·가격/운임·조건·동의를 판본화한다 | 주문 종류별 권위 UseCase와 원장 |
| 3. 이행 준비·수행 | 조리, 재고 할당, 입출고, 피킹·포장, 수입 이행을 수행한다 | 음식점·마트·창고·수입 OS |
| 4. 배송·운송 | 후보·제안·수락, 픽업/상차, 이동, 전달/하차를 수행한다 | `FoodDeliveryOS`, `DomesticCargoTransportOS` |
| 5. 인수·정산 | 결과를 주문에 반영하고 인수·검수·정산한다 | 주문/화주 원장과 정산 권위 |
| 6. 비정상 업무 처리·회복 | 사건을 보존하고 보류·검토·재처리·종료를 명시한다 | 원래 업무 OS와 권한 있는 당사자 |

`CommunityTrustOS`, `PlatformOperationsOS`, `EducationFieldExperienceOS`처럼 여러 구간을 지원하거나 관찰하는 OS는 실행 순서 한 칸에 억지로 넣지 않고 교차 책임으로 표시한다.

### 6. 주문 루트가 소유할 최소 의미

공통 주문 관점은 다음만 소유하거나 참조한다.

- 주문 종류와 안정 고유 식별자
- 주문을 확정한 당사자·역할·동의 판본
- 상품 또는 서비스 항목, 수량, 가격·운임과 통화
- 약속한 결과와 시간창
- 원천 제안·개인 의향·공동 수요의 참조
- 원천 개별 주문 또는 공동주문 묶음과 운송 필요의 참조
- 화주역할자·실제행위자·비용귀속범위의 역할 결속과 위임 근거 revision
- 발생한 자식 업무의 OS·업무 고유 식별자·현재 결과 참조
- 전체 결과를 계산한 기준 revision과 미완료·보류 사유

주문 루트는 음식 조리 상태, 창고 적재 위치, 기사 위치, 배차 후보, 운송 증빙이나 지급 상태를 직접 변경하지 않는다. 각 자식 OS의 권위 결과를 읽어 전체 주문 관점을 계산한다.

## OS 간 인계 계약에 필요한 항목

후속 정적 대장은 최소한 다음을 표현해야 한다.

- 인계 엣지 안정 ID와 계약 판본
- 출발 OS·출발 생명주기 단계
- 출발 업무 고유 식별자·revision과 발생 Command/Event
- 도착 OS·진입 생명주기 단계
- 인계 방식: `ChildWork`, `ResponsibilityTransfer`, `Observation`, `ReturnForAcceptance`
- 관계 수: `1:1`, `1:N`, `N:1`
- 권한·동의·기능 관문
- 도착 OS의 완료 조건과 출발 OS로 돌려줄 최소 결과
- 실패·만료·거절·비정상 업무 처리 엣지
- 주문 전체 상태를 전진시킬 수 있는 결과인지 여부

Engine은 후보·점수·전략을 반환할 뿐 이 엣지를 수락하거나 주문 상태를 확정하지 않는다. 확정은 권한을 검증한 UseCase/Command와 각 OS 원장이 수행한다.

## 대표 업무망

### 살뜰마트 주문

```text
판매 가능 상품·재고 준비
  → 고객 주문 확정
  → 재고 할당
  → 피킹·포장
  → 음식배달 OS 자식 업무 인계
  → 배차·픽업·전달
  → 배송 결과를 마트 주문에 반영
  → 인수·정산 또는 비정상 업무 처리
```

### 화물 운송 서비스 주문

```text
화주의 운송 의향
  → 화물·조건·운임 검토
  → 화주 운송의뢰 확정
  → 화물운송 OS 실행 책임 인계
  → 배차·상차·운송·하차
  → 화주 OS로 완료 결과 반환
  → 인수·검수
  → 정산 또는 비정상 운송 처리·업무 회복
```

### 공동 수요 주문

```text
각 개인의 비구속 의향
  → 모집·수요 집계
  → 판매자·공급 조건 매칭
  → 각 개인의 명시적 주문 확정
  → 공동 주문 집계
  → 수입/판매/창고/배송 자식 업무
  → 각 개인 주문으로 결과 환류
```

공동 주문은 개인의 동의·비용·철회 가능 상태를 덮어쓰지 않는다. 수요 집계나 지리적 가까움만으로 주문·배차·계약을 자동 확정하지 않는다.

## 구현 우선순위

1. **현행 대조표**: 모든 `OperatingSystemIds`에 대해 내부 생명주기 정의 여부, 주문 전/확정/이행/결과 구간, 실제 원장·UseCase·인계 계약과 미구현을 한 표로 만든다.
2. **화주 역할·담당자 위임 계약**: 기존 공개 `화주Id`를 바로 재해석하지 않고, 원천 주문·공동주문 묶음·화주역할자·실제행위자·담당자 위임·비용 귀속을 연결하는 내부 권위 원장과 검증 경계를 먼저 정의한다.
3. **정적 OS 상호작용 대장**: 새 실행 권위를 만들지 않는 `OperatingSystemInteractionCatalog`를 두고, 이미 구현된 네 계약만 먼저 등록해 출발·도착 단계와 반환 조건을 검증한다.
4. **공통 주문 관점 계약**: 서로 다른 실제 원장을 합치지 않고 상품 주문·서비스 주문·공동 주문을 같은 방식으로 추적할 읽기 전용 `OrderWorkNetworkProjection`을 정의한다.
5. **첫 왕복 검증**: 이미 정방향과 역방향 인계가 모두 있는 `화주 운송관리 → 화물운송 → 화주 인수`를 첫 표본으로 삼아 주문 확정부터 결과 반환까지 같은 상관 ID와 revision이 이어지는지 검증한다.
6. **개인·공동주문 위임 표본**: 개인 주문자 또는 공동주문 대표가 기본 화주가 되고, 권한 있는 담당자가 대신 의뢰·관리하더라도 화주와 원천 주문·비용 귀속이 바뀌지 않는 경로를 검증한다.
7. **마트·음식 확장**: `살뜰마트 주문 → 피킹·포장 → 음식배달 → 마트 주문 결과`를 두 번째 업무 유형 표본으로 연결한다. 하나의 주문에서 여러 배송 업무가 갈라지고 다시 합쳐지는 조건을 포함한다.
8. **누락 생명주기 보완**: 창고, 공동구매 수요·수입 등 실제 코드와 원장이 확인된 OS부터 생명주기 대장을 추가한다. 안정 식별자만 있다는 이유로 단계를 추측해 만들지 않는다.
9. **관찰 표현**: 서버의 읽기 전용 주문 업무망 상태 사본이 안정된 뒤에만 Web·모바일의 당사자 업무 화면과 Unity의 비식별 관찰 표현을 각각 연결한다.

## 현재 발견한 보완점

- OS 안정 식별자 10개와 생명주기 정의 4개의 범위가 일치하지 않는다.
- 정적 상호작용 대장은 현재 실제 구현된 네 계약만 담는다. 가능한 관계를 추측해 채우지 않았으므로 새 OS 인계는 계약·원장·시험과 함께 추가해야 한다.
- 음식배달 OS는 주문·음식점 응답·조리·배차·전달을 한 생명주기에 함께 담고, 살뜰마트 OS는 주문 전 공급 준비와 고객 주문 이행을 함께 담는다. 당장 OS를 분리하기보다 먼저 공통 업무 구간과 책임을 메타데이터로 구분해야 한다.
- 화주 운송 표본에는 OS별 실제 인계 상태·revision을 조합하는 정식 읽기 관점이 생겼다. `주문 통합 원장` 전체나 다른 주문 종류의 상태를 합치지는 않았다.
- 공동구매 수요 관련 안정 OS와 일부 커뮤니티 원장 모듈의 운영체제 표기가 같은 의미인지 호환 경계인지 대조가 필요하다. 확인 없이 기존 저장 값을 일괄 변경하지 않는다.
- 현재 `화주운송의뢰`는 `주문자UserId`와 `화주Id`를 구분하지만, 일반 사용자의 생성 경로에서는 두 값이 사실상 현재 사용자로 결속된다. 요청자와 다른 화주를 지정할 수 있는 것은 서버 관리자뿐이다.
- 운송 의뢰가 생성된 뒤에는 화주가 주·보조 담당자를 지정해 실제 조회·수정·인수·정산 확인 권한을 줄 수 있다. 그러나 운송 생성 전 위임, 금액·기간·지역 상한과 원천 주문 범위를 결속하는 상위 권위 원장은 아직 없다.
- `주문자집단운영주체`에는 운영 주체 유형과 `대표UserId`가 있으나 특정 공동주문 묶음·각 개인 주문·비용 분담 원장과 화주 운송의뢰를 잇는 권위 계약은 확인되지 않았다. 이 연결 없이 대표를 자동 화주로 복제하지 않는다.

## 제외

- 범용 주문 OS가 다른 OS의 상태를 직접 변경하는 구조
- 모든 OS에 단일 전역 순번을 부여하는 구조
- 기존 공개 route·저장 안정 식별자·원장을 한 번에 통합하거나 이름을 바꾸는 작업
- 의향·모집·집계를 명시적 동의 없이 주문으로 승격하는 작업
- 배차·결제·정산·계약의 운영 자동 활성화
- Unity 공간 Graph Map이나 Scene 변경

## 미정

- 화물 운송 서비스 주문을 물리적인 `주문 통합 원장` 자식으로 저장할지, 화주 운송의뢰 원장을 유지한 채 공통 주문 관점에서만 연결할지
- 공동 운영 주체의 계약·비용 원장과 대표 화주의 관계를 운영 활성화 전에 확인할 법률·회계 관문
- 음식 주문 안의 음식점 이행과 음식배달 실행을 장기적으로 별도 OS로 나눌지
- 판매 제안의 공통 안정 식별자와 판매 OS 생명주기를 새로 둘지
- 주문 전체 완료 계산에서 부분 완료·분할 배송·부분 취소를 어떤 상태 집합으로 표현할지
- 개인·공동 주문을 운송 의뢰에 연결할 원천 주문 범위·비용 귀속 계약과 생성 전 위임 경계
