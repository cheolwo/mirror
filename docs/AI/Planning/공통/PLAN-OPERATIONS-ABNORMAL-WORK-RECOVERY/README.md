## 목적

정상 업무의 단계별 반대 상태를 기계적으로 늘리는 대신, 사건이 생겼을 때 사람과 물건을 먼저 보호하고 사실·책임·비용을 성급하게 확정하지 않으면서 업무를 안전하게 멈추고 다시 이어 가거나 종료하는 공통 절차를 정한다.

비정상 업무는 정상 흐름을 지우는 별도 세계가 아니다. 원래 주문과 각 OS 원장을 유지한 채 다음 순서로 다룬다.

```text
감지·신고
  → 즉시 보호 조치
  → 영향 범위 분리
  → 증거·상태 보존
  → 당사자 통지와 임시 담당 지정
  → 검토·결정
  → 재처리·대체·부분 완료·종료
  → 정산·보상·이의 제기
  → 원래 주문 업무망으로 결과 반환
```

## 현재 코드 기준선

- 화물운송은 `수량불일치`, `화물훼손`, `하차지부재` 신고를 비정상 운송 사건으로 보존하고 정산을 보류한다.
- 이 보류는 기사 과실, 환불, 보상, 반품, 재배송 또는 재위탁 확정이 아니다.
- 화주 또는 권한 있는 담당자가 예상 revision과 근거를 제출해 사건을 검토·결정하는 Command는 아직 없다.
- 음식배달·마트·창고의 지연·품절·부분 처리·작업 중단도 같은 공통 원칙으로 비교해야 하지만, 각 OS의 실제 상태와 책임은 합치지 않는다.

## 문답 원칙

- 한 번에 결정 하나만 묻는다.
- 먼저 사람의 안전과 추가 손실 방지를 정하고, 귀책과 금액은 그 뒤에 정한다.
- 신고만으로 당사자 평가나 책임을 확정하지 않는다.
- 문제가 없는 수량·작업까지 멈출지는 사건별로 명시한다.
- 자동 재배송·자동 환불·자동 기사 교체처럼 외부 효과가 큰 조치는 별도 승인 없이 확정하지 않는다.
- 각 답변은 주문자·화주/담당자·판매자·창고 작업자·기사·운영자 관점에서 다시 대조한다.

## AWR-Q1 확정 — 일부 파손의 기본 처리와 계약 우선

화물 10개 중 2개가 파손되고 8개가 정상인 경우의 기본값은 다음과 같다.

```text
정상 8개
  → 상태·수량 확인
  → 일부 인수
  → 원래 주문의 정상 처리 결과로 반환

파손 2개
  → 영향 수량 격리
  → 사고·증빙 보존
  → 해당 수량과 관련 정산 보류
  → 계약·보험 검토
```

다만 이 기본값은 운송 거래 계약의 명시적인 배상·인수 조건보다 우선하지 않는다. `하나라도 파손되면 전체 인수·배상 검토`, `파손 수량만 분리`, `세트 상품이라 일부 사용 불가` 같은 특약이 있으면 사건 접수 시점의 계약 판본에 따라 영향 범위와 보류 범위를 다시 계산한다. 안전·오염·품질 전파 위험이 있으면 계약의 부분 인수 허용 여부와 별개로 전체를 임시 격리할 수 있다.

따라서 비정상 사건은 원문 계약을 복제하거나 나중 조건으로 덮어쓰지 않고 최소한 다음 참조를 가져야 한다.

- 원래 주문·운송 업무 고유 식별자와 사건 발생 시점의 계약 판본
- 총수량·정상 확인 수량·영향 수량·격리 수량
- 부분 인수 허용 여부와 전체 배상·세트 불가분 특약 적용 여부
- 임시 보호 범위와 그 근거
- 보류된 정산 범위
- 후속 보험 사고 접수·검토 상태의 별도 참조

### 플랫폼 적재물 보험 방향

플랫폼은 운송 중 적재물 파손 위험을 기사나 화주 한쪽에 즉시 전가하지 않고, 적용 가능한 적재물 관련 보험 체계를 보험사와 마련해 사고 접수·심사·지급 결과를 비정상 업무 생명주기에 연결하는 방향을 기본으로 한다.

보험은 다음 경계를 지킨다.

- 사고 신고만으로 보험 적용, 귀책, 배상액 또는 지급을 확정하지 않는다.
- 서버는 사고 시점의 계약·보험 정책 판본과 접수 고유 식별자를 보존한다.
- 보험사 심사 결과와 플랫폼의 임시 지원·최종 정산은 서로 다른 상태로 기록한다.
- 정상 수량의 일부 인수와 파손 수량의 보험 검토를 동시에 진행할 수 있다.
- 실제 보험 상품, 가입 주체, 피보험자·수익자, 자기부담금, 보장 한도, 면책과 청구 절차는 법률·보험사·운영 검토 전까지 미정이다.

Unity에는 계약 원문·보험 증권·사진·당사자 식별자를 보내지 않는다. `부분 인수`, `영향분 보호 보류`, `보험 검토 중`, `회복 작업 중`, `종료`처럼 서버가 확정한 비식별 관찰 상태만 후속 상태 사본으로 제공한다.

## AWR-Q2 확정 — 원장 중심 문제 신고와 관계자 통지

비정상 업무의 기본 진입점은 특수한 긴급 위험 판정 화면이 아니라 기존 운송 원장에 결속된 `문제 사건 원장`이다. 기사·화주 또는 권한 있는 담당자는 현재 운송 건에서 관찰한 문제 종류를 선택하고 필요한 설명·증빙을 더해 플랫폼 운영 담당자와 관련자에게 알린다.

첫 문제 종류는 다음처럼 좁게 시작한다.

- 배송·운송 지연
- 운송 상품 파손
- 교통사고
- 수량 불일치
- 상차·하차 또는 수령 불가
- 기타 문제

문제 신고는 다음 정보를 가진다.

- 문제 사건 고유 식별자와 원래 운송 의뢰·운송 실행 원장 참조
- 신고 종류, 관찰 시각, 현재 업무 단계와 신고자 역할
- 사람이 입력한 설명과 별도 접근 통제를 받는 사진·증빙 참조
- 사건 상태, 담당 운영자, 최근 변경 revision
- 관계자 통지 결과와 확인 여부
- 업무 통제 상태, 보류 범위와 검토 기한
- 계약 판본과 보험 사고 접수의 선택적 참조

신고자는 관찰한 사실을 남기며 귀책·배상액·환불·보험 지급을 확정하지 않는다. 보험사 통지는 보험 적용 가능성 검토와 사고 접수가 시작된 뒤 별도 상태로 기록한다.

### 세 상태의 분리

문제 발생으로 원래 운송 상태를 `오류` 하나로 덮어쓰지 않는다.

```text
운송 생명주기 상태
  예: 배차확정 / 상차완료 / 운송중 / 인수완료

문제 사건 상태
  예: 접수됨 / 담당자확인 / 검토중 / 조치결정 / 종료

업무 통제 상태
  예: 계속진행 / 주의진행 / 일부보류 / 전체보류 / 재개
```

이 세 상태를 함께 조회해야 `운송중이지만 지연 검토 중`, `상차완료 상태에서 파손분 일부 보류`, `교통사고 신고 뒤 전체 보류`처럼 실제 상황을 잃지 않고 표현할 수 있다. Unity는 이 중 비식별 요약만 받아 NPC·차량·화물의 대기·점검·재개 상태를 관찰하게 된다.

관계자 알림은 사건 종류와 업무 관계를 기준으로 플랫폼 운영 담당자, 화주 또는 권한 있는 담당자, 배정 기사, 수령 측 가운데 필요한 사람에게만 보낸다. 모든 관계자에게 상세 주소·전화번호·보험 자료를 일괄 공개하지 않는다.

## AWR-Q3 확정 — 정상 진행 유지와 영향 범위만 보류

일반적인 문제 신고는 사건 접수·관계자 알림·담당자 검토 필요 상태를 만들되 운송 전체를 자동 보류하지 않는다. 현장에서 정상적으로 처리할 수 있는 수량과 단계는 계속 진행한다.

예를 들어 화물 10개 중 8개가 정상이고 2개가 파손됐다면 다음처럼 처리한다.

```text
정상 8개
  → 수량·상태 확인
  → 인수 가능
  → 정상 처리 결과 보존

파손 2개
  → 영향 수량 분리·증빙
  → 해당 수량과 관련 정산만 보류
  → 계약·적재물 보험 검토
```

신고자가 `현장 진행 불가`를 선택하거나 안전·오염·품질 전파 위험 때문에 분리가 불가능한 때에만 영향 범위를 임시 보류한다. 전체 운송 보류는 계약상 불가분 조건, 전체 안전 위험 또는 운영 담당자의 명시적 결정이 있을 때 적용한다.

## 통제를 잃지 않는 단계형 구현 제안

제가 비정상 경로 전체를 한 번에 추측해 구현하지 않는다. 정상 생명주기의 각 단계에서 발생 가능한 `누락·지연·불일치·파손·거절·중단·중복`을 후보로 조사하되, 실제 변경은 아래 관문을 통과한 작은 수직 조각 하나씩 진행한다.

```text
기준선 조사
  → 사례 하나와 완료 조건 고정
  → 원장·상태·권한·알림·정산 시험부터 작성
  → 내부 상태 전이 구현
  → 집중 시험과 회귀 검증
  → 사용자에게 결과·미구현·새 질문 반환
  → 다음 사례 승인 또는 수정
```

각 조각에서 자동 귀책, 자동 환불, 자동 재배송, 자동 보험 지급과 실제 외부 통지는 기본 제외한다. 예상 revision, 멱등성, 이력 보존과 권한 검사를 먼저 닫고, 정책이 미정인 외부 효과는 `검토 필요`에서 멈춘다.

### 구현 우선순위 후보

1. **부분 파손 수직 조각**: 정상 수량·영향 수량·보류 범위를 사건 원장에 기록하고, 정상분 인수와 영향분 정산 보류를 분리한다. 운영 담당자는 예상 revision으로 `일부보류·전체보류·재개·종료`를 결정한다.
2. **지연·수령 불가 조각**: 운송은 유지하면서 새 시간창·재연락·대기·복귀 가운데 명시적으로 선택하고, 무응답 확대 절차를 붙인다.
3. **교통사고 조각**: 사람 안전과 추가 손실 방지를 우선하고 운송 진행 가능 범위를 판단한다. 계약·보험 사고 접수는 별도 참조로 연결한다.
4. **정산·보상 조각**: 사건 해결 결과를 정상분 정산, 영향분 보류·보험 검토와 결속한다. 지급·배상 확정은 승인된 계약 정책 뒤에 둔다.
5. **다른 OS 확장**: 화물에서 검증한 사건 원장 골격만 음식배달·마트·창고에 재사용하고, 각 OS의 업무 상태와 회복 선택은 따로 정의한다.

현재 코드는 `수량불일치·화물훼손·하차지부재 신고 → 사건 원장 → 화주 알림 → 운송 건 전체 정산 보류`까지 구현돼 있다. 따라서 첫 구현은 새 체계를 만드는 작업보다 현재의 전체 보류를 수량·계약·위험 범위에 맞는 부분 보류로 정밀화하고, 아직 없는 운영 담당자의 검토·결정 Command를 추가하는 작업이 된다.

## AWR-Q4 확정과 첫 구현 결과

첫 구현을 `화물 10개 중 정상 8개 인수·파손 2개 보류` 사례로 제한했다. 기사 문제 신고 계약에는 선택적인 정상 확인 수량·영향 수량·현장 진행 불가를 추가하고, 서버는 화주 운송의뢰의 전체 화물 수량과 합이 일치하는지 검증한다.

신고 직후에는 기존 안전 경계대로 운임 정산을 임시 보류하지만 운송 상태를 오류나 중단으로 바꾸지 않는다. 사건 원장은 `주의진행·일부보류·전체보류`, `영향수량·전체운송`을 별도 상태로 기록한다.

플랫폼 운영자는 관리자 API에서 사건 목록을 조회하고 사건 revision을 확인한 뒤 다음 결정을 명시적으로 제출한다.

- 정상분 인수·영향분 보류
- 전체 운송 보류
- 운송 재개
- 사건 종료

첫 결정인 정상분 인수·영향분 보류에서는 정상 수량과 영향 수량을 다시 검증하고, 운임 정산의 임시 잠금을 해제한다. 파손 수량은 `적용 가능성 검토 대기` 보험 상태로 남으며 보험 적용·귀책·배상액·지급은 확정하지 않는다. 같은 클라이언트 요청 ID는 같은 결과를 재사용하고, 다른 내용 재사용과 오래된 예상 revision은 거부한다.

기존 `운영검토대기` 자료는 새 보류 bool 값이 없어도 계속 정산을 차단한다. 새 운영자 결정 뒤에는 명시적인 정산 보류 여부를 따르므로 부분 인수 결정이 기사 운임 지급 준비를 막지 않는다.

## 확정

- 비정상 업무 경로를 사용자와 한 질문씩 문답하며 정밀화한다.
- 첫 사례는 현재 서버 기반이 있는 화물 하차 시 수량 불일치로 시작한다.
- 일부 파손의 기본 계약 요건은 정상 수량을 확인 후 일부 인수하고 영향 수량과 그 정산만 보류하는 것이다.
- 사건 시점의 명시적 운송 거래 계약·특약이 기본값을 대체하며, 안전·품질 전파 위험은 전체 임시 격리 근거가 될 수 있다.
- 플랫폼은 적용 가능한 적재물 관련 보험 체계를 마련하고 사고 접수·심사·지급 결과를 비정상 업무 생명주기에 연결하는 방향을 기본으로 한다.
- 보험 접수는 귀책·배상액·보험금 지급을 자동 확정하지 않는다.
- 비정상 업무의 기본 진입점은 원래 운송 원장에 결속된 문제 사건 원장이다.
- 문제 종류를 선택하고 설명·증빙을 남기면 플랫폼 운영 담당자와 필요한 관계자에게 알린다.
- 원래 운송 생명주기 상태, 문제 사건 상태와 업무 통제 상태를 분리해 함께 관리한다.
- 긴급 안전 위험은 일반 문제 신고의 특수한 종류이지 별도 원장 체계가 아니다.
- 일반 문제 신고는 운송 전체를 자동 보류하지 않고 정상 처리 가능한 범위를 계속 진행한다.
- 파손·불일치 수량만 분리할 수 있으면 정상분은 인수하고 영향분과 관련 정산만 보류한다.
- `현장 진행 불가`, 불가분 계약 또는 전체 안전 위험이 확인된 범위만 임시 보류한다.
- 첫 구현은 정상 8개·파손 2개 사례의 수량 원장, 부분 보류, 운영자 revision 결정과 보험 적용 가능성 검토 상태까지 완료했다.
- 구현은 승인된 결정과 권위·상태·회복 조건이 충분히 닫힌 뒤 별도 인계한다.
