# 실시간 위치 대신 픽업·전달 단계를 표현한다

- 판본·기준일: r5 / 2026-09-26
- 상태: `StageBasedObservationConfirmed / LiveGpsNotRequired / ProductImplementationDeferred`.
- 이전 판본: [역할별 자기 업무 조회 제안 r4](role-scoped-work-observation.proposal.r4.md), [관계 표시 r3 기준선](README.md#r3-기준선--확정-사항과-미답변-보존).
- 사용자 답변: 실시간이나 GPS까지 필요하지 않으며, 픽업하고 도착지까지 가는 모습을 표현하면 된다.
- 질문 의미 ID: `restaurant-related-rider-current-observation-scope` / `Answered`. r4의 미정 GPS 관찰 범위를 이번 관찰 기능에는 요구하지 않는 것으로 정한다.
- 작업 범위: 기획 기록만. 새 WI·Goal·PlayableLoop 등록 없음. `ReadyToDispatch=false`.

## 1. 확정한 경험

음식점은 **자기 주문을 맡은 기사들이 음식을 픽업하고 전달하는 모습**을 보고, 기사는 **본인이 수행한 배달과 관련 음식점**을 돌아본다. 실제 위치를 추적하는 화면이 아니라 업무 흐름을 알아보는 표현이다.

`서버가 확인한 업무 단계 → 허용된 상태 사본 → 디오라마의 픽업·이동·인계 표현`

이번 기능은 정밀 GPS 수집·실시간 위치 전송·실제 운행 경로 재현을 전제로 하지 않는다. 기존 기사 업무 앱의 길찾기·위치 기능을 삭제하거나 다른 관점의 GPS 정책을 변경한다는 뜻은 아니다.

## 2. 단계 표현의 경계

| 서버에서 확인한 사실 | 표현할 수 있는 모습 | 표현만으로 확정하지 않는 사실 |
| --- | --- | --- |
| 픽업 전 | 음식점에서 픽업을 기다리는 모습 | 이미 음식이 기사에게 인계되었다는 판단 |
| 픽업 확인·전달 중 | 음식점 기준점에서 목적지 방향으로 가는 합성 이동 | 실제 현재 위치·실제 동선·도착 예상 시각·도착 완료 |
| 전달 완료 | 서버의 완료 단계에 맞는 전달 마무리 | 별도 수령 확인이나 정산 완료까지 자동 확정 |
| 지연·중단·보류 | 확인된 상태를 유지하고 필요한 경우 움직임을 멈추는 표현 | 기사 귀책·사고 원인·복구 완료의 추측 |

애니메이션이 목적지에 도달해도 서버의 업무 상태를 바꾸지 않는다. 서버의 다음 상태를 아직 받지 않았다면 완료 연출로 넘어가지 않는다. 종점 직전 대기 등 구체적인 처리 방식은 구현 전 정하며, 경로·속도·반복 방식은 이번 답변으로 확정하지 않는다.

비실시간 조회에서 중간 단계를 놓쳤다면 최신 확인 상태로 맞춘다. 확인하지 않은 픽업·이동 이력을 실제로 관찰한 것처럼 만들어 재생하지 않는다. 완료 이력의 연출을 제공하게 되면 현재 운행과 구분한다.

## 3. 위치·권한·갱신

- 이동 경로와 목적지는 합성·일반화된 의미 기준점으로 표현하는 제안이다. 이를 위해 정밀 GPS나 수령인의 상세 주소를 Unity에 새로 보내지 않는다. 실제 위치가 아닌 업무 단계 기반 연출임을 화면 범례나 선택 상세에서 알 수 있게 한다.
- r4의 서버측 자기 업무 필터를 그대로 적용한다. 같은 기사가 수행하는 다른 음식점의 주문·하루 전체 동선까지 보여 주지 않는다. 과거 공동 완료 관계가 현재 활동의 관찰 권한이 되지 않는다.
- r3의 완료 횟수·양측 공개 설정·원장 보존 기준을 유지한다. 관계 배지 공개와 본인 업무 조회는 별개다.
- 갱신은 기존 인증 조회를 재사용하는 방향으로 두되 주기는 미정이다. 기존 화면 진입·수동 갱신·주기 조회 중 적합한 방식을 좁혀 정한다. 이번 기능 때문에 새 실시간 위치 API나 SignalR 구독을 필수로 만들지 않는다. r4의 갱신 알림 재사용은 선택적 수단으로 남는다.
- 오래된 사본은 마지막 확인 시각과 갱신 상태를 구분하고 서버 상태보다 앞서 표현하지 않는다. 기존 TTL·권한 회수·로그아웃 제거 경계를 유지한다.
- 합성 표본과 실제 운영 자료는 구분한다. 업무 단계 기반 애니메이션은 실제 운행·도착·완료를 입증하는 자료가 아니다.

## 4. 다음 구현 때 확인할 최소 조건

1. 허용된 자기 업무만 조회되고 다른 주문·기사 이력이 섞이지 않는다.
2. 서버 픽업 확인 전 출발·전달 표현으로 앞서가지 않는다.
3. 이동 애니메이션의 종점 도달이 완료 Command나 원장 변경을 발생시키지 않는다.
4. 비실시간 갱신·실패·중단·낮은 revision에도 마지막 확인 단계와 최신 유효 상태로 수렴한다.
5. 정밀 GPS 없이도 기존 의미 기준점과 상태 사본으로 픽업·전달 흐름을 표현할 수 있다.

위 항목은 향후 검증 기준이며 이번에 실행한 시험 결과가 아니다. Graph Map 영향은 기존 주문·기사·음식점·인계 관계와 표현 제약을 재사용하는 범위로 인계하며, 이번에 원본·생성물을 수정하지 않는다.

## 확정 / 미정 / 다음 질문

- 확정: 이번 자기 업무 관찰에는 실시간·GPS가 필요하지 않다. 서버가 확인한 픽업·전달 단계를 이동 모습으로 표현한다. 표현이 실제 업무의 권위를 갖지 않는다.
- 미정: 경로·속도·대기/반복 방식·조회 주기·표시명과 카드 세부 항목. r4 조회 구현과 권한 보완은 여전히 제안 단계다.
- 기존 미답변: r3 최근 완료 내역 기본 10건, 생활상 이해 r47의 첫 카드 문구는 이번 답변으로 승인하지 않는다.
- 다음 질문: 없음. 이번 관찰 범위는 정리되었으며 제품 구현은 별도 요청·기획 관문 점검 후 진행한다.

변경은 기획 문서·목차·현재 작업 기록에 한정한다. 제품 코드·서버·DB·Unity 실행·commit·push 없음. 새 디오라마 규칙 후보 없음.
