## 1. 목적

음식점과 배달 기사가 반복해서 만나도 매번 낯선 주체처럼만 보이지 않게 한다. 두 역할이 같은 완료 업무 근거를 보며 `이 음식점과 몇 번째 배달인지`, `이 기사님과 몇 번 함께했는지`를 알아볼 수 있게 한다.

사용자가 말한 `카르마`는 공개 평점이나 배차 점수가 아니라, 두 주체가 실제로 함께 마친 업무에서 생긴 인과의 기록으로 해석한다.

```text
음식 주문·배차
  → 기사 수락
  → 음식점 픽업 인계
  → 고객 전달·수령 확인
  → 완료 Event
  → 음식점-기사 업무 관계 Projection 갱신
  → 다음 만남에서 양쪽 역할 화면에 같은 횟수 표시
```

## 2. 같은 사실을 두 관점으로 표현한다

관계의 정본은 `RestaurantStableId + DriverStableId` 쌍과 완료 Event revision이다. 앱마다 횟수를 따로 계산하지 않는다.

| 시점 | 기사 화면 | 음식점 화면 |
| --- | --- | --- |
| 기사 배차 제안 | `온기식당과 함께 완료한 배달 6회 · 이번이 7번째 후보` | 아직 특정 기사가 확정되지 않았으면 표시하지 않음 |
| 기사 배정 완료 | `이 음식점에서 7번째 픽업 예정` | `이 기사님과 함께 완료한 배달 6회 · 이번이 7번째 예정` |
| 픽업 인계 | `이 음식점과 다시 만났어요` | `이 기사님과 다시 만났어요` |
| 수령 확인 완료 | 양쪽의 `함께 완료한 배달`을 같은 revision으로 `7회` 갱신 | 양쪽의 `함께 완료한 배달`을 같은 revision으로 `7회` 갱신 |

- 현재 진행 건은 완료 횟수에 미리 포함하지 않고 `예정`으로 구분한다.
- 첫 버전의 관계 배지는 `함께 완료한 배달 N회` 하나만 표시한다. 픽업 인계 횟수는 별도 숫자로 보여 주지 않는다.
- 기사에게는 음식점 상호와 관계 횟수를, 음식점에는 배정된 기사 표시명과 관계 횟수를 보여 준다.
- 음식점 직원 개인과 기사의 관계로 자동 해석하지 않는다. 첫 범위는 음식점 사업체·영업점과 기사 사이의 업무 관계다.
- 주문자와 다른 기사에게 이 쌍의 관계 횟수를 공개하지 않는다.

## 3. 화면 배치

### 기사 배차 제안·상세

음식점 이름 아래에 작은 관계 배지를 둔다.

```text
온기식당
[함께 완료한 배달 6회]  이번이 7번째 후보
픽업 1.2km · 전달 2.6km · 예상 지급 6,500원
```

관계 배지는 거리·지급·예상시간보다 강한 색으로 강조하지 않는다. 기사는 관계와 무관하게 제안을 수락하거나 거절할 수 있다.

### 음식점 주문 상세·배달 인계

기사 배정 전에는 관계 수치를 보여 주지 않는다. 기사 배정 뒤 `배달 인계` 카드에 표시한다.

```text
배달 기사 배정 완료
[함께 완료한 배달 6회]  이번이 7번째 예정
도착 예상 · 픽업 준비 상태
```

음식점은 관계 횟수를 보고 특정 기사를 유지·교체하거나 배차 순위를 바꿀 수 없다. 배차 권위는 기존 배차 엔진과 기사 선택에 남는다.

## 4. 정본과 집계 규칙

- 첫 안전 기준은 수령 확인까지 닫힌 정상 완료 배달만 `함께 완료한 배달`에 더하는 것이다.
- 취소·배차 제안 만료·기사 거절·미픽업·재배차 전 원기사는 완료 횟수에 포함하지 않는다.
- 재배차 뒤 실제 픽업·전달을 완료한 기사만 해당 완료 관계에 포함한다.
- Event 재처리는 `DeliveryStableId + CompletionRevision + RelationshipProjectionKind` 멱등 키로 중복 증가를 막는다.
- 관계 Projection이 지연되거나 실패하면 이전 정상 횟수와 `갱신 지연`을 표시하며 앱이 추측해서 올리지 않는다.
- 픽업 인계 사실은 업무 원장과 감사·복구에 필요하면 보존할 수 있지만 관계 배지의 숫자로 합산하거나 완료 횟수와 병기하지 않는다.
- 관계 수치는 배달 원장을 대신하지 않으며 원본 Event에서 다시 구성할 수 있는 읽기 모델이다.

## 5. 친밀감과 공정성 경계

- 반복 횟수를 별점·신뢰 점수·기사 등급·음식점 등급으로 바꾸지 않는다.
- 반복 횟수를 배차 점수, 거리 판정, 지급액, 할증, 제안 우선순위나 거절 불이익에 사용하지 않는다.
- 반복 만남이 신규 기사 진입을 막는 단골 기사 잠금으로 이어지지 않게 한다.
- 함께한 횟수가 많아도 친구 관계나 연락처 공개로 자동 전환하지 않는다.
- 완료 업무 뒤 두 당사자는 기존 `WorkRelationshipSnapshot`에서 상대를 다시 확인하고 원할 때만 친구 요청을 보낼 수 있다.
- 친구 요청의 거절·무응답·차단은 향후 배차와 노출에 영향을 주지 않는다.
- 신고·차단·안전 사건이 있으면 관계 배지와 후속 친구 요청 제안을 숨기되, 감사용 업무 사실은 권한 있는 운영 원장에 보존한다.

## 5.1 관계 배지 클릭과 공개 설정

- 관계 배지를 누르면 두 주체가 함께 완료한 배달 목록으로 이동한다.
- 상세에는 완료 시각, 양쪽이 이미 아는 음식점, 완료 상태와 관계 순번만 표시한다. 주문자의 이름·연락처·상세 주소·정밀 위치·원시 GPS 경로는 포함하지 않는다.
- 기사 설정에는 `음식점에 함께한 배달 횟수 표시`를 둔다. 음식점 설정에는 `기사에게 함께한 배달 횟수 표시`를 둔다.
- 신규 기사·음식점의 기본값은 `표시 ON`이다. 첫 안내에서 무엇이 상대에게 보이는지 설명하고 언제든 끌 수 있게 한다.
- 기사가 OFF로 바꾸면 음식점 화면에서 해당 기사와의 관계 배지·클릭 상세를 숨긴다. 음식점이 OFF로 바꾸면 기사 화면에서 해당 음식점과의 관계 배지·클릭 상세를 숨긴다.
- 한쪽의 일반 배달 내역과 완료 원장은 본인의 업무 기록이므로 유지한다. 상대 공개를 끈다고 원장·정산·감사 기록을 삭제하지 않는다.
- OFF는 이후 상대 화면 노출에 즉시 적용하며 과거 완료 업무를 취소하거나 배차·지급에 영향을 주지 않는다.
- 상대 화면에서는 OFF를 `0회`로 바꾸거나 비공개 선택 사실을 강조하지 않고 관계 배지 자체를 표시하지 않는다.
- 설정 조회가 실패하거나 판본을 확인할 수 없으면 기본 ON으로 추측하지 않고 관계 배지와 상세 진입을 숨긴다.
- 공개 설정은 역할별 앱 로컬 값이 아니라 서버에 저장된 본인 소유 설정과 revision을 정본으로 한다.

| 음식점 주문의 기사 배정·픽업·전달 상태 | 음식 주문·배달 원장, `RestaurantDeskApp`, `FDriverApp` | `O` |

`O`는 기반 코드가 존재한다는 뜻이며 음식점-기사 관계 화면이 구현되거나 실제 장치에서 검증됐다는 뜻이 아니다.

## 확정

- 음식점과 배달 기사 양쪽이 같은 완료 업무 횟수를 각자의 화면에서 확인한다.
- 첫 버전은 `함께 완료한 배달 N회` 하나만 표시하고 픽업 인계 횟수를 분리 표시하지 않는다.
- 관계 배지는 클릭해 함께 완료한 배달 목록으로 이동한다.
- 기사와 음식점은 각각 상대 화면에 관계 횟수를 보여 줄지 정할 수 있고 신규 기본값은 표시 ON이다.
- 한쪽이 표시를 끄면 상대 화면의 배지와 상세 진입을 숨기되 완료 업무 원장은 삭제하지 않는다.
- 관계는 음식점 영업점과 기사 사이의 쌍으로 시작한다.
- 진행 중인 현재 배달은 `N번째 예정`, 완료 뒤에만 `N회 완료`로 바뀐다.
- 관계 횟수는 배차·지급·평점·자격에 영향을 주지 않는다.
- 친구 관계와 연락처 공개는 기존 명시적 요청·수락·별도 동의 절차를 따른다.

## 미정

- 기사 표시명을 어느 시점부터 어떤 익명 수준으로 음식점에 보여 줄지
- 관계 상세에서 최근 함께한 완료 내역을 기본 몇 건까지 보여 줄지
- 관계 Projection 보존 기간과 탈퇴·차단 뒤 표시 정책
- 업무 관계에서 친구 요청을 제안하는 최소 완료 횟수와 제안 빈도

## 다음 질문 하나

관계 상세에 최근 함께 완료한 배달을 기본 몇 건까지 보여 줄까?

추천은 최근 10건이다. 더 오래된 내역은 명시적인 `더 보기`로 불러오고, 관계 상세에서 주문자 개인정보나 전체 이동 경로를 다시 노출하지 않는다.
