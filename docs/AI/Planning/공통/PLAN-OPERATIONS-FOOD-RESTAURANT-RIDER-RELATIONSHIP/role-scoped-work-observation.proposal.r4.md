## 1. 같은 원장을 각자의 관점으로 읽는다

**한 번 관련된 사람의 모든 활동이 아니라, 나와 연결된 업무와 함께한 기록을 보여 준다.** 음식점 관점의 주체는 직원 개인이 아닌 권한을 가진 영업점이며, 기사는 로그인한 본인이다. 프랜차이즈 본부·다른 지점의 권한을 자동 상속하지 않는다.

| 관점 | 지금 함께하는 업무 | 완료된 내역 | 선택적 관계 표시 |
| --- | --- | --- | --- |
| 음식점 | 우리 주문을 수락한 기사별 픽업 대기·전달 단계, 관련 주문 묶음 | 우리 음식점 주문의 완료 기록 | 이 기사와 함께 완료한 배달 횟수·최근 공동 완료 내역 |
| 기사 | 본인이 수락한 현재 배달·음식점·인계 단계 | 본인이 실제 수행한 음식 배달 목록, 허용된 건별 상세·지급 정보 | 음식점별 함께 완료한 배달 횟수·최근 공동 완료 내역 |

현재 업무, 본인 업무 이력, 상대에게 보이는 관계 배지는 별개다. 같은 기사가 여러 주문을 처리하면 사람 카드는 하나로 묶고 허용된 주문만 그 아래 표시한다. 다른 가게 주문·전체 하루 동선·다른 기사 수익은 따라오지 않는다. 과거에 함께 일했다는 사실은 현재 활동을 계속 관찰할 권한이 아니다.

## 3. 서버 쪽 구현 제안

### A. 원장과 조회 권한부터 연결

1. 로그인 주체와 현재 영업점/기사 권한을 서버가 확정한다. 화면이 전달한 `restaurantId`, `driverId`, 사람 카드 ID를 그대로 신뢰하지 않는다.
2. 현재 업무는 기존 주문·배차·운송·배달 시도에서 실제 관련자를 확인하여 읽는다. 기사 수락 전 후보를 '현재 우리 주문을 운행하는 기사'로 표시하지 않는다.
3. 완료 이력은 실제 수행 기사와 완료 기준을 기준으로 읽는다. 영업점 stable ID로 묶으며 음식점 이름이 같다는 이유로 합치지 않는다.
4. 권한 필터 후 페이지·인원 수·주문 수를 계산한다. 전체 지역 자료를 Unity에 보낸 뒤 client에서 숨기거나, 전역 상위 500건을 먼저 자른 뒤 본인 자료를 찾지 않는다.
5. 일자·상태·음식점 필터와 페이지 조회를 붙인다. 첫 화면에 보여 줄 기간과 건수는 미정이며 최근 10건은 r3의 미답변 제안으로 남는다.

기존 음식점 inbox/기사 workspace/상세 조회를 우선 재사용하고, 반복 조합이 필요한 기사별 묶음·완료 집계에만 작은 읽기 모델을 보완하는 안이다. 기존 route의 결과 범위를 조용히 바꾸지 않고 호환 계약을 점검한 후 연결한다.

### B. 함께 완료한 관계는 별도 읽기 모델

`영업점 stable ID + 기사 stable ID` 쌍과 완료 Event revision을 기준으로 r3 규칙을 재사용한다. 완료 원장·정산을 복제하는 새로운 정본이 아니다.

- 수령 확인까지 닫힌 정상 완료만 집계한다. 취소·거절·배차 제안·재배차 전 원기사의 시도를 완료 횟수로 더하지 않는다.
- Event/Outbox 재처리는 기존 r3 멱등 키로 중복 증가를 막는다. 지연·실패는 갱신 상태로 표시하고 client가 횟수를 올리지 않는다.
- 기사/음식점 각각 상대에게 관계 배지·관계 상세를 보여 줄지 정하는 기존 기본 ON·개별 OFF 정책을 보존한다. 설정 조회 실패는 숨김이며 0회로 표시하지 않는다.
- 관계 공개 OFF와 본인의 배달 내역·업무 원장 보존을 구분한다. 한쪽의 OFF가 상대의 이미 정당하게 보유한 자기 주문 이력을 지우지는 않는다.
- 관계가 많다는 이유로 배차·지급·평점·자격을 바꾸지 않는다. 친구·연락처·알림 공개는 별도 선택이다.

### C. 변화 알림은 재조회 계기로 사용

기존 인증 SignalR 경로는 '변경됨'을 알리는 데 재사용하고, 실제 표시 내용은 서버에서 현재 권한으로 다시 조회한다. 배차 취소·기사 교체·영업점 권한 회수·공개 철회가 생기면 이전 개인 사본과 구독을 제거한다. 알림 유실·중복·역순에도 재조회로 수렴해야 한다. 이러한 회수 경로가 이미 검증되었다고 주장하지 않는다.

## 4. Unity와 모바일의 화면 제안

같은 업무 원장을 사용하되 전송 DTO를 무조건 공유하지 않는다. 현재 음식점·기사 업무 DTO와 일반 관계 기록에는 수령인 정보·주소·좌표·메모·내부 참조가 포함될 수 있어 Unity에 통째로 전달하지 않는다.

- 음식점 선택: 하단 `현재 연결된 기사` 카드 묶음. 기사 카드 선택 시 **우리 주문의** 현재 단계·다음 인계·마지막 확인 시각만 펼친다.
- 기사 본인 선택: 하단 `진행 중 / 배달 내역 / 함께한 음식점`을 분리한다. 완료 이력 선택은 현재 위치 추적이나 실제 이동 경로 재생으로 바뀌지 않는다.
- 같은 업무는 앱과 Unity에서 같은 업무 revision·시각으로 연결한다. Unity에는 화면 범위의 비식별 객체/업무 연결키·허용 표시명·단계·근거·TTL만 내려 주는 전용 최소 상태 사본을 제안한다.
- 현재 지역 장면 API의 비식별 지역 관찰과 '내 업무 관계 관찰'의 권한 범위를 구별한다. `내 관련 업무만`이라는 표시를 client 필터만으로 구현하지 않는다. 구체적인 route/query 판본은 개발 전 호환 검토 대상이다.
- 지도상의 애니메이션은 업무 단계에 따른 합성 표현임을 구별한다. 실제 위치·실도로 경로가 승인·검증되지 않았으면 정확한 현재 운행으로 표현하지 않는다.
- 로그아웃·권한 회수 때 관찰 사본을 즉시 지우고 일반 Save/Replay·로컬 기록에 남기지 않는다. 본인 배달 이력은 서버 원장 조회이며 Unity의 영구 보관으로 대체하지 않는다.

## 5. 추천 구현 순서와 검증

1. **내 관련 업무 범위:** 한 음식점·복수 기사, 한 기사·복수 음식점의 권한 행렬과 기존 주문/시도/완료 연결을 닫는다.
2. **조회 완성:** 음식점 관련 기사 목록과 기사 본인 음식배달 이력을 서버에서 제공한다. 취소·재배차·오래된 권한·이름 중복·다중 주문 묶음을 시험한다.
3. **관계 배지:** 기존 r3 완료 집계와 양측 설정을 구현한다. 업무 이력 접근 권한과 공개 설정을 섞지 않는다.
4. **Unity 연결:** 조회에 성공한 동일 업무를 기존 상태 사본·선택·r46 표현 수명 구조에 연결한다. 실제 화면과 API 권한 시험은 별도로 남긴다.

최소 반례는 타 음식점 ID 대입·타 기사 이력 요청 거부, 같은 기사 묶음 속 다른 음식점 주문 제외, 재배차 전 기사의 현재 관찰 제거, 상대 공개 OFF 후 관계 배지 숨김/자기 업무 이력 유지, 완료 Event 중복·역순, stale 표시·로그아웃 제거다. r46의 짧은 표본 화면을 이 기능의 실제 업무 연결 증거로 대신하지 않는다.
