# 로그인한 음식점의 주변 지도와 자기 업무를 함께 불러온다

- 판본·기준일: r6 / 2026-09-26
- 상태: `StoreCenteredRegionalObservationConfirmed / LoadingDesignProposed / ProductImplementationDeferred`.
- 사용자 방향: Unity 로그인 후 자기 음식점 위치와 반경을 기준으로 지역 자료를 불러와 맵을 구성하고, 자기 업무에 연결된 주문자·기사를 그 위에 표현한다. 사가정역 고정 장면에 한정하지 않는다.
- 기준선: [r4 자기 업무 조회](role-scoped-work-observation.proposal.r4.md), [r5 GPS 없는 단계 표현](stage-based-delivery-observation.decision.r5.md), [r45 확대별 자료 수명](../../시스템/PLAN-SYSTEM-FRANCHISE-OPERATIONS/living-world-semantic-streaming.proposal.r45.md).
- 범위: 기획 기록 및 기존 코드의 좁은 정적 조사. 제품 코드·새 Scene·서버 실행·공공자료 수집·DB 변경 없음. 새 Goal·WI 등록 없음, `ReadyToDispatch=false`.

## 1. 세 범위를 구분한다

**가게를 중심으로 지도를 구성하되, 지도 안에 있다는 이유만으로 그 사람을 조회하지 않는다.**

| 범위 | 정하는 내용 | 정하지 않는 내용 |
| --- | --- | --- |
| 지도 관찰 범위 | 가게 주변 어느 지역의 배경 자료를 요청할지 | 주문 허용·기사 배차·개인정보 열람 권한 |
| 주문·배달 운영 범위 | 서버 정책상 실제 주문·배달이 가능한 조건 | Unity에 지역 자료가 있다는 이유로 영업 가능 판정 |
| 자기 업무 조회 범위 | 현재 로그인 주체·영업점에 허용된 주문·기사·주문자 역할 | 반경 안 모든 주민·잠재 주문자·기사의 개인 활동 |

7km·10km는 사용자 예시이자 기존 탐색 정책과 연결해 검토할 값이다. 이번 발언으로 모든 가게의 운영 반경을 7km 또는 10km로 변경하지 않는다.

### 기존 정책에서 확인한 차이

- [음식점 탐색 정책](../../../../Architecture/OrdererRestaurantSearchPolicy.md)에는 주문자 탐색 기본 7km·허용 1~10km·빠른 선택 3/5/7/10km가 기록되어 있다.
- [음식점 탐색 조회 코드](../../../../../Ssalddel/Application/Food/음식점탐색조회UseCase.cs)는 서버 정책 허용 범위를 검사하고, 선택한 공개 행정권역 기준점에서 음식점까지의 직선거리로 걸러낸다. 음식점 중심의 실제 배달 허용 반경을 조회하는 것과 다르다.
- [주문자 기획](../PLAN-OPERATIONS-ORDERER-ACTIVE-ORDER-HOME/README.md)은 10km 탐색이 주문·배차 성사를 보장하지 않으며, 역세권 디오라마 범위·기사 후보 반경·주문자 탐색 반경을 구별한다.

따라서 기존 탐색 정책 값을 가게별 배달권으로 이름만 바꿔 쓰지 않는다. 향후 가게별 관찰 범위가 어떤 운영 정책을 참조할지, 중심점·거리 기준·유효 기간·판본을 서버에서 명시하는 작은 조회 연결이 필요하다. 직선 반경과 도로 주행거리를 혼용하지 않는다.

## 2. 로그인부터 표현까지 — 연결 제안

1. **관점 확인:** 서버가 로그인 주체의 역할과 접근 가능한 영업점을 확인한다. 여러 가게 권한이 있으면 선택하도록 하고, 등록 위치가 없으면 위치 확인 대기로 남긴다. 장치 GPS를 필수로 수집하지 않는다.
2. **관찰 범위 조회:** 선택 가게의 검증된 등록 위치와 관찰에 사용할 정책 범위를 받는다. 가게 ID를 client가 보내더라도 권한은 서버가 검증한다.
3. **지역 자료 목록 조회:** 범위와 교차하는 행정구역·공간 타일·자료 레이어의 준비 상태와 판본을 확인한다. 가게가 동·구 경계에 있어도 인접 지역 자료를 찾는다. 행정동 중심점만 비교해 필요한 경계 타일을 누락하지 않는다.
4. **지도 조립:** 사용 가능한 경계·도로·건물 자료를 공통 좌표 기준으로 기존 `SimulationWorldShell`에 구성한다. 행정동이나 음식점마다 별도 공식 Scene을 만들지 않는다.
5. **자기 업무 조회:** 권한 필터를 먼저 적용한 주문·확정 기사·주문자 역할의 최소 상태 사본을 받는다. 반경 내 전체 사람 자료를 받아 client에서 숨기는 구조는 사용하지 않는다.
6. **생활상 표현:** 음식점에서 준비·픽업하고 목적지 방향으로 전달하는 모습을 r5처럼 서버 확정 단계 안에서 표현한다. 대상을 선택할 때 관련 업무 카드와 마지막 확인 시각을 연다.

음식점 등록 위치와 지도 좌표를 사용한다는 것은 기사의 실시간 GPS를 추적한다는 뜻이 아니다. 주문자도 상시 위치를 가진 주민으로 추적하지 않고 **해당 주문의 수령 역할·일반화된 목적지 기준점**으로 표현한다. 실명·전화번호·동호수·정밀 배달 주소를 Unity에 새로 포함하지 않는다. 실제 건물 결속이 확인되지 않으면 임의 주택을 주문자의 집으로 지정하지 않는다.

## 3. 넓은 범위는 요약, 선택한 곳은 상세 — 제안

- **처음:** 반경 전체의 가벼운 지도와 내 가게·관련 업무 흐름을 보여 주는 안을 추천한다. 7~10km 전체를 상세 GameObject로 한꺼번에 만들지 않는다.
- **확대:** 현재 화면과 선택 대상 주변의 준비된 건물·도로·행동 표현만 단계적으로 불러온다. 행정구역은 분류·집계, 타일은 로드 단위이며 같은 개념이 아니다. H 의미 계층과 기술 LOD도 새로 합치지 않는다.
- **축소·이동:** 상세 객체를 정리하고 요약으로 돌아간다. 화면 밖 배달 자체를 취소하거나 서버 업무를 멈추지 않는다. 카메라 이동에 따라 관찰 반경·배달 요금을 자동 변경하지 않는다.
- **자료 부족:** 준비된 상위 지도와 결손 상태를 유지한다. 다른 동이나 사가정 자료로 몰래 대체하지 않고, 범위를 넓힌다고 새 수집·유료 API·공개 승인을 자동 실행하지 않는다.
- **반경 밖 자기 업무:** 진행 중 주문은 지도 범위나 정책이 바뀌었다고 원장에서 사라지지 않는다. 허용된 목록·경계 안내로 남기며 상세 공간을 추가 로드할지는 별도 선택으로 정한다.

여러 동에 걸친 도로·건물·같은 기사는 기존 고유 식별자로 중복 없이 연결한다. 자료별 좌표계·원점·단위·판본/hash·허용 이용 범위를 확인하고, 호환되지 않는 자료를 한 지도처럼 덧붙이지 않는다.

## 4. 배경 자료와 내 업무 자료의 수명

공개·이용 허용된 지역 자료는 판본과 용량 한도 내에서 재사용한다. 개인 업무 사본은 로그인 관점·영업점·권한 범위별 메모리로 분리하고 Save/Replay·일반 지역 캐시에 넣지 않는다.

로그아웃·영업점 전환·권한 회수 때 이전 업무 사본을 비우고, 늦게 도착한 이전 요청을 새 화면에 적용하지 않는다. 공개 지도 캐시 재사용이 다른 계정의 사람·주문 자료 재사용으로 이어져서는 안 된다. 기존 TTL·revision·부분 실패 정책을 재사용하며 구체 조회 주기·자원 예산은 아직 정하지 않는다.

## 5. 현재 기반과 다음 작은 구현 후보

기존 [r46 표본 구현](../../시스템/PLAN-SYSTEM-FRANCHISE-OPERATIONS/living-world-semantic-streaming.implementation.r46.md)과 [생활관찰표현Session](../../../../../Ssalddel.Unity/Runtime/WorldProjection/생활관찰표현Session.cs)은 한 지역 음식 사본의 상세/요약·해제·복귀 기반이다. [타일 스트림 서비스](../../../../../Ssalddel.Simulation.Application/SimulationWorldStreamingService.cs)는 대관령 Farm 기준이며, 음식점 중심 여러 지역 로그인 관찰이 이미 연결되었다는 증거는 아니다.

기존 [행정동 정밀화 r39](../../시스템/PLAN-SYSTEM-ADMIN-DONG-DIORAMA/focused-area-refinement.decision.r39.md)의 소수 구간 집중 방침은 유지한다. 이번 일반화 방향으로 보류된 30개 동 일괄 정밀화나 전국 수집을 재개하지 않는다. 보유한 역사 경계·비공개 검토 자료를 현행·공개 가능한 자료로 자동 승격하지 않는다.

다음 구현 후보는 **등록 음식점 한 곳 → 허용된 관찰 범위 → 준비된 지역 타일 목록 → 관련 배달 한 건 표현**이다. 이후 두 번째 가게·행정동 경계 사례로 중심점 하드코딩 여부를 확인한다. 실행 전 기존 인증·API·좌표·타일 구성 대장을 점검하고 작업 명세·허용 경로·검증 상한을 좁힌다.

필수 반례: 다른 가게 ID 요청, 반경 안 무관한 사람 제외, 동 경계 타일 누락·중복, 위치 미등록·자료 부족, 범위 변경 후 기존 주문 보존, 계정/가게 전환 뒤 늦은 응답, 로그아웃 삭제, 애니메이션 종점과 실제 완료 불일치. 이는 향후 검증 기준이지 이번 시험 결과가 아니다.

Graph Map 영향은 기존 영업점·주문·수령 역할·기사·공간 연결과 범위 제약의 추가 인계 후보다. 이번에 원본·생성물·E 증거·공간 권위를 바꾸지 않는다. 새 디오라마 규칙 후보 없음.
