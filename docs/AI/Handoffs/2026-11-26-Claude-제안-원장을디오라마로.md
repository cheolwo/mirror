## 사용자의 말

> 이번에 뭐 앱 같은 거 만든다고 했을 때 주문 원장이란 게 있고 주문자 집단 원장이란 게 있고 그런 원장 같은 게 존재를 하긴 했었거든. … 그것에 대해서 한번 조사를 해본 다음에 지금 디오라마 관련한 거기서 어떻게 적용할지에 대해서 한번 좀 제안을 한번 해줘 봐봐. (14:22)

## 1. 조사 — 이미 있는 것

출처: `docs/Architecture/OrderRootLedger.md` · `GroupPurchaseDemandProcessManager.md` · `ApartmentGroupPurchaseSurplusRevenueFlow.md` · `FoodFocusedGroupPurchase.md` · `UrbanMarketResidentialOrdererGroupIntegrationDesign.md`, `docs/AI/DECISIONS.md` D-028 · D-029 · D-030 · D-043 · D-054, 코드 `OrdererApp/Components/GroupPurchase/*` · `Ssalddel.Simulation.Domain/.../Simulation같이주문.cs`.

### 원장 계층(개별성 우선)

```text
개별 원함 원장   ← 원본. 비구속. 본인만 바꾸고 철회. 상품 · 수량 · 수령 권역 · B2B/B2C
     ↓ ID 참조(복제 아님)
자동집단 수요    ← 투영. 「상품 · 배송권 · 보관 온도 · 물류 방식 · 거래유형」이 같은 원함을 묶은 모집 진행
     ↓ 따로 명시적 동의 · 예약결제
개별 주문 원장   ← 계약 · 수령권의 원본(주문 원장 루트: order · food-order · ssalddel-mart)
     ↓ 합산
주문집계 원장(group-order) ← 같이 주문 모집 원장(group-purchase) 밑
     ↓ 각 개별 주문 밑에 이행 원장
판매 · 창고입고 · 창고출고 · 배송 · 운송 원장
```

### 모집 상태(Process Manager)

| 상태 | 뜻 |
| --- | --- |
| `CollectingDemand` 모으는 중 | 원함이 늘고 줄 때마다 진행도를 다시 셈 |
| `ReadyToConfirm` 확정 대기 | 목표를 채움. **자동 확정하지 않고** 사람 검토로 |
| `RecruitmentClosedTargetNotReached` 목표 미달 | 이유 + 대안(더 넓은 모집권 · 다른 시간창 · 다른 수령 방식) |
| `Confirmed` / `HandoffReady` | 주문 확정이 아니라 **모집 결과 인계 승인** |

- 정체된 모집은 Aging으로 「더 넓은 모집권」 대안을 받는다.
- 국적 · 성별 · 경제력 같은 속성은 집단 자격 · 순위 · 가격에 쓰지 않는다.

### 이미 정한 원칙

1. **표현은 권위가 아니다.** NPC 도착 · 차량 애니메이션 · 상자 Renderer 수는 완료와 수량의 근거가 아니다(D-030 · D-043). 원장 상태가 화면을 움직이고, 화면이 원장을 바꾸지 않는다.
2. **공개는 권역 합계만.** 개별 원함 · 주소 · 연락처는 본인과 권한자만 본다. 남에게는 상품 · 배송권 · 참여자 수 · 총 희망수량만 보인다.
3. **공동주택은 새 원장이 아니다.** 기존 자동집단의 배송권 · 생활권 · 공동수령 문맥이다(D-029). 대표는 남의 주문을 대신 확정하지 못한다.
4. **잔여재고는 네 종류로 나눈다.** 예약분 · 운영 여유분 · 취소 · 미수령분 · 그 밖. 예약분은 자동 판매 금지.
5. **생산자 쪽 입구가 이미 있다.** 주문자 앱 여정에 「긴급 수확 제안 → 긴급 수확 검토」 화면이 있다. 출하 기한이 짧은 공급 물량을 같이 주문과 잇는 검토다. 긴급하다는 이유로 배차 · 계약 · 가격을 자동 확정하지 않는다.
6. **Simulation 같이주문이 이미 있다(D-054).** Preview → Confirm → 완료 WorldTick에서 `확정` 또는 `모집종료목표미달`. 실제 주문 · 결제가 아니다.

→ 오늘 제안한 「남는다 → 모인다 → 받는 곳 → 닫힌다」는 **이 원장 계층을 그대로 따라가면 된다.** 새 개념을 만들 필요가 없다.

## 2. 디오라마에 얹기 — 원장마다 모양 하나

| 원장 · 상태 | 디오라마 표현 | 지도 단위 |
| --- | --- | --- |
| 긴급 수확 제안(생산자) | 농촌 판 밭에 「내보낼 수 있음」 깃발 + 출하 기한 시계 | 농촌 판 필지 → 시군 |
| 개별 원함 | **본인 화면에만** 자기 집 자리에 작은 빈 고리 | 본인: 건물 / 남: 안 보임 |
| 자동집단 수요(모으는 중) | 세부칸 위로 빛 알갱이가 모여 「한 트럭까지 n상자」 막대 | 세부칸 → 동(배송권) |
| 확정 대기 | 고리가 닫히고 금빛으로 멈춤 — 「사람 확인 대기」 칩 | 동 |
| 목표 미달 | 알갱이가 흩어지지 않고 둘레 이웃 칸으로 점선이 번짐(「더 넓히면 차요」) | 세부칸 → 이웃 칸 |
| 개별 주문(확정) | 빈 고리 → 찬 점(본인 화면) | 건물 |
| 주문집계(group-order) | 트럭 한 대 | 산지 → 거점 길 |
| 운송 원장 | 전국 지도의 길 위 트럭 빛 | 전국 · 구 |
| 창고입고 · 출고 | 받는 곳(거점) 건물에 상자 쌓임 · 줄어듦 | 동 디오라마 거점 |
| 배송 / 공동수령 | 거점 → 집 빛줄 또는 「찾으러 오세요」 칩 | 동 |
| 잔여재고 | 거점 상자 중 회색 상자 = 아직 주인 확인 전(자동 판매 안 함) | 거점 |
| 닫힘(이행 끝) | 생산지와 동네가 함께 밝아짐(명덕) | 두 디오라마 + 길 |

- **배송권 = 세부칸 → 타일 → 동** 계층을 쓴다. 오늘 정한 동 시선의 「무대」 묶음 규칙(이어진 칸 1~3개)이 그대로 「모집권」이 된다.
- 무대가 차면 → 모임이 생기기 좋은 곳이라는 뜻이 된다.

## 3. 입장마다 같은 원장이 다르게

| 입장 | 보이는 원장 | 못 보는 것 |
| --- | --- | --- |
| 주문자 | 내 원함 · 내 주문 · 우리 동 모집 진행 · 거점까지 몇 분 | 남의 원함 · 주소 |
| 농가(생산자) | 내 긴급 수확 제안 · 어느 동이 모이고 있나(합계) · 트럭 출발 | 개인 주문자 |
| 거점(가게 · 지사 · 창고) | 입고 · 출고 · 잔여재고 네 종류 · 찾으러 올 수(합계) | 결제 정보 |
| 화물 기사 | 운송 원장: 산지 → 거점 · 상차 · 하차 시각 | 주문 내용 |
| 홍달 경영자 | 동마다 모집 상태 · 정체 · 거점 빈 동 | 개인값 |

입장 카드의 「필수 · 부가」 기준(하루 한 번 이상 마주치면 필수)을 원장에도 쓴다. 예: 주문자에게 「우리 동 모집 진행」은 필수, 「운송 원장」은 부가.

## 4. 순서(가안)

| 차례 | 담당 | 일 |
| --- | --- | --- |
| L0 | Codex | 원장 계층 · 상태 코드 · 공개 범위를 **표 한 장**으로(게임이 읽을 계약). Simulation같이주문 · 긴급수확 화면의 실제 필드 대조 |
| L1 | Claude | 시안: 「배추 한 트럭」을 원장 상태 순서대로(모으는 중 → 확정 대기 → 트럭 → 거점 → 닫힘) 사가정 동 디오라마 위에 |
| L2 | Claude | 게임: 모의(Simulation) 같이주문 원장 하나를 읽어 동 디오라마에 표현만. 상태를 바꾸는 버튼 없음 |
| L3 | 둘 다 | Firebase 로그인 뒤: 본인 원함만 본인 화면에. 남에게는 권역 합계만(bands와 같은 원칙) |

## 지킬 것

- 화면이 원장을 바꾸지 않는다. 애니메이션이 끝나도 상태는 원장이 정한다.
- 자동 확정 · 자동 배차 · 자동 가격 없음. 확정 대기는 사람 확인을 기다린다.
- 개별 원함 · 주소는 본인 화면에만. 공개 화면은 동 · 세부칸 합계.
- 실제 결제 · 계약은 홍달 밖에서(오늘 제안의 D단계와 같음).
