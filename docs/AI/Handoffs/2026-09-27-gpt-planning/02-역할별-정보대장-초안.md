# 음식 주문 역할별 정보대장 — 기획 문답용 초안

기준일: 2026-09-27 / 관련 인계: `01-프로젝트-기획인계.md`

최신 사용자 요청은 화면을 늘리기 전에 각자가 다루는 정보를 정리하는 것이다. 아래는 **기존 코드 확인 결과와 권한 설계 후보를 나눠 적은 초안**이다. 전체 권한 정책이 이미 승인/구현/검증됐다는 뜻이 아니다. ‘배달의민족’이라는 음성 표현은 앞 대화에서 ‘배달기사’로 이해했으며 외부 플랫폼 연동을 이번 범위로 넣지 않았다.

## 1. 각자가 보고 싶은 핵심 질문

| 역할 | 핵심 질문 | 직접 하는 일 | 해서는 안 되는 해석 |
| --- | --- | --- | --- |
| 주문자 | 무엇을 주문했고 언제 받을 수 있나? 취소/환불은 어떻게 됐나? | 메뉴 선택·주문·요청사항·허용 단계 취소·수령 확인 | 자기 주문 밖 기사/다른 손님의 상세 업무 조회 |
| 음식점 | 무엇을 얼마나 준비해야 하나? 언제 픽업되나? 얼마를 받나? | 메뉴·품절 관리, 주문 수락/거절, 조리시간·준비 완료 | 기사 대신 픽업/전달을 확정하거나 결제 완료를 임의 입력 |
| 배달기사 | 어떤 제안이며 어디서 픽업하고 전달하나? 대가는 얼마인가? | 제안 수락/거절, 픽업·전달·문제 기록 | 운영자가 기사에게 강제로 수락시킨다고 가정 |
| 운영자 | 어느 업무가 멈췄나? 사실과 돈 흐름이 맞나? | 권한 내 조회·상담·검토·승인·정책 관리 | 모든 정보 무제한 열람, 신고만으로 귀책/차감 확정 |
| 서버 | 누가 언제 무엇을 정당하게 변경했나? | 권한/현재 상태/revision 검증·정본 저장·사건 발행 | 화면 애니메이션이나 클릭 효과를 완료 사실로 간주 |

## 2. 정보별 최소 대장

코드 상태는 ‘존재 / 미확인 / 없음(확인 범위)’이며 완성도 등급이 아니다. 조회·변경 역할은 문답으로 구체화할 후보이고 기존 권한 검증을 약화할 근거가 아니다.

| ID | 정보 | 최초 입력/확정 후보 | 각 역할에 필요한 조회 | 현재 근거 / 결손 |
| --- | --- | --- | --- | --- |
| INFO-01 | 음식점 식별·가게 정보 | 등록 권한자 → 서버 | 공개 정보는 주문자, 자기 가게는 음식점, 픽업 필요 정보는 기사 | 음식점 DTO/접근범위 코드 존재. 필드별 공개 대조 후속 |
| INFO-02 | 메뉴·소개·가격 | 음식점 → 서버 | 주문자는 공개 메뉴, 음식점은 자기 메뉴, 주문 시점 내역은 주문 관계자 | 메뉴 관리 DTO/API/UI 존재. 사진 업로드 없음 |
| INFO-03 | 공개·품절·영업 여부 | 음식점 권한 → 서버 | 주문 가능 여부와 해당 주문 영향 | 공개/품절 UI 존재. 영업 상태 앱 연결 없음 |
| INFO-04 | 주문번호·항목·수량·주문 시점 금액 | 주문자 요청 → 서버 검증 | 같은 주문에 관계된 역할의 필요한 항목 | 음식주문 계약/등록/조회 코드 존재. 서로 다른 앱의 별도 사실 생성 금지 |
| INFO-05 | 수령지·연락처·전달 요청 | 권한 있는 주문자 → 서버 | 필요한 수행 역할에 필요한 시점만 | 필드 코드 존재. 정확한 공개 시점·마스킹·보존 대조 미확인 |
| INFO-06 | 결제 시도·승인·실패 | 결제 처리 계층/검증된 결과 | 주문자는 자기 결과, 음식점은 처리 가능 여부, 운영자는 수납 대조 | 공통 결제/Outbox 존재. 음식 주문 최종 적용 연결 미확인 |
| INFO-07 | 음식점 수락·거절·사유 | 해당 음식점 → 서버 | 주문자·수행 기사·담당 운영자 | 상세 화면/Handler 존재. 거절→환불까지 종단 미확인 |
| INFO-08 | 기본 조리시간·이번 주문 예상시간 | 음식점 → 서버/기기 설정의 소유 구분 필요 | 주문자 안내, 기사 픽업 판단, 운영 지연 확인 | 기본값/5·10·15·20분/주문 진행 변경 코드 존재. 기기 기본값과 원장 상태 혼동 금지 |
| INFO-09 | 조리 완료·픽업 준비 | 음식점 → 서버 | 주문자·배정 기사·운영자 | 픽업 준비 Command/화면 존재. 기사 픽업과 다른 사건 |
| INFO-10 | 배차 제안·수락·거절·배정 상태 | 배차 계산/기사 선택 → 서버 | 기사 판단 정보, 음식점·주문자의 배정 결과 | 배차 엔진·기사 업무 코드 존재. 재배차 대기 자체를 무조건 예외 사건으로 분류하지 않음 |
| INFO-11 | 픽업·전달·수령 확인 | 기사 수행/주문자 확인 → 각각 서버 | 같은 주문의 진행 상태 | 정상 생명주기 시험 존재. GPS가 있어야만 상태 표현 가능한 것은 아님 |
| INFO-12 | 취소 요청·취소 확정·환불 상태 | 역할별 요청/허용 정책 → 서버 | 당사자 요청/결과, 음식점 준비 중단, 운영자 환불 대조 | 취소 Handler 존재. 음식 주문 환불 종단 미확인 |
| INFO-13 | 지연·문제 신고·보호 보류 | 관련자 신고 → 검토 권한자의 처리 | 관련 범위의 진행/연락·검토 정보 | 예외/운영 조회 코드·기획 존재. 신고와 귀책/차감 확정 분리 |
| INFO-14 | 음식점 매출·수수료·차감·지급대상·보류·지급완료 | 확정 업무/금전 사건에서 서버 계산·승인 | 음식점 자기 내역, 권한 있는 운영자 대조 | 음식점 앱 전용 정산 화면/client 없음(최근 점검 범위). 신규 연결 필요 |
| INFO-15 | 기사 배달료·할증·공제·지급 내역 | 적용 정책 사본/업무 사건 → 서버 | 해당 기사·권한 있는 지급 담당 | 월 이용료/화물 지급/음식 배달 대금을 구별해야 함. 음식점 정산과 합치지 않음 |
| INFO-16 | 플랫폼 기간 현금 흐름·의무 | 재무사건/전기 → 조회 투영 | 담당 운영자·총괄의 권한 내 | 관리자 finance 화면/API 기록 존재. 가용 잔액·확정 이익으로 자동 해석 금지 |
| INFO-17 | 시간순 사건·처리 주체·revision·요청 ID | 서버 각 변경 단계 | 당사자용 이력과 감사용 원문을 분리 | 상태이력/Event/Outbox 코드 존재. 모든 역할이 모든 원문을 보는 것은 아님 |
| INFO-18 | 상담·관련자 연락·처리 결과 | 담당자/당사자 입력 → 서버 | 사건 관계자별 대화·초대 범위 | 고객지원 기획과 일부 기반. 전체 지원 UI/권한 구현 미확인 |
| INFO-19 | 완료 배달 관계 횟수·공개 설정 | 완료 사실 집계 + 당사자 공개 선택 | 기사·음식점 관계 확인 | 기획 이력 존재. 본인의 비공개 선택을 무시한 공유 금지, 현재 연결 재점검 필요 |
| INFO-20 | Unity 관찰용 상태 사본 | 서버 정본에서 비식별 조회 | 로그인 관점/승인 범위의 단계·관계·공간 표현 | 관찰 계약·코어·일부 화면 존재. 실명·연락처·상세주소·실운영 ID를 배포 자원에 넣지 않음 |

## 3. ‘공통’이라는 말의 의미

주문번호·상태·메뉴 내역 등은 여러 역할이 같은 사실을 참조할 수 있다. 그렇다고 동일 JSON을 모두에게 주거나 수정 권한을 공유하자는 뜻은 아니다.

- 음식점 조리 완료와 기사 픽업은 이어지는 **다른 사실**이다.
- 기사 전달 완료와 주문자 수령 확인은 **다른 사실**이다.
- 취소 요청과 취소 확정, 환불 요청과 환불 완료는 **다른 사실**이다.
- 주문 합계와 음식점에 지급할 금액, 기사 대가, 플랫폼 수익은 **다른 계산/채무**다.
- 서버가 확정한 값과 화면의 ‘예상’·‘마지막 확인’은 구분한다.
- 갱신 실패는 마지막 정상 자료와 함께 표시할 수 있지만 완료/0원/빈 정상 목록으로 바꾸지 않는다.

## 4. 정상 업무와 사건 기록을 함께 읽기

주문 등록 → 음식점 수락 → 조리 진행/기사 배정 → 픽업 준비·기사 픽업 → 전달 → 수령 확인이라는 정상 경로를 기준으로 각 사건의 담당자와 시각을 연결한다. 조리와 배차는 병행될 수 있으므로 모든 사건에 단일 강제 직렬 순서를 붙이지 않는다.

금전 경로는 이 업무 경로 옆에서 별도로 연결한다. 결제 승인 시점, 수락 전 결제 여부, 취소 단계별 환불 조건, 정산 대상이 되는 시점은 최신 정책/계약과 코드 대조가 필요한 항목이다. 이 초안이 새 결제 정책을 확정하지 않는다.

사건마다 최소 `업무 ID / 사건 ID / 발생 시각 / 서버 기록 시각 / 요청자 역할 / 이전·다음 상태 / revision / 요청 ID / 관련 원장 ID`를 조사 후보로 삼는다. 저장소의 기존 이름을 먼저 찾고 같은 뜻의 새 필드를 중복 생성하지 않는다.

## 5. 개인정보·권한 질문

- 주문자는 자기 주문만 보는가? 대표·대리 주문은 별도 위임이 필요한가?
- 음식점은 조리에 필요하지 않은 수령인 개인정보까지 볼 이유가 있는가?
- 기사는 제안 때 필요한 정보와 수락 후 필요한 상세가 다른가?
- 운영자 통계→문제 사건→개인 상세로 들어갈 때 권한/감사 기록은 어떻게 구분하는가?
- 완료 뒤 연락처·정밀 위치가 계속 필요한가? 필요한 기록과 보존 기간은 누가 정하는가?
- 자기 업무 이력, 공동 원장, 커뮤니티 공개 경험, 친구 관계는 각각 별도 동의/공개 상태인가?

이 질문들은 아직 결론이 아니다. 각 항목에 기존 정책이 있으면 먼저 찾고 재질문을 줄인다.

## 6. 문답 순서 제안

1. 같은 주문 한 건에서 역할별 첫 화면에 필요한 최소 정보 확정.
2. 주문 상세에 공통으로 연결할 사건 기록과 역할별 비공개 정보 구분.
3. 음식점의 ‘받을 돈’에 필요한 원장·결제·환불·정산 항목 구분.
4. 지연·거절·취소·응답 유실 때 누가 무엇을 보고 행동할지 결정.
5. 정해진 한 항목만 Codex에 코드 존재 조사/구현/시험으로 넘김.

한 번에 한 질문을 권장한다. 첫 질문 후보: **‘음식점이 주문 한 건을 열었을 때, 조리·인계 정보와 별도로 결제 상태를 어디까지 알아야 하는가?’** 기존 결제 완료 보장 수준을 확인하지 않은 상태에서 조리를 자동 허용하거나 막는 정책을 만들지는 않는다.
