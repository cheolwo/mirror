# Mirror(거울) 프로젝트 — GPT 채팅 기획 인계

기준일: 2026-09-27 KST / 인계 판본: 1

이 파일 하나만 첨부해도 기획 대화를 시작할 수 있다. 역할별 정보 논의에는 함께 만든 `02-역할별-정보대장-초안.md`를 추가한다. 화면 검토가 필요하면 `menu-list.png`, `menu-editor.png`도 첨부한다.

**이 문서는 현재 작업의 요약 사본이지 개발 승인서나 출시 완료 증명서가 아니다.** 저장소에 접근하지 못하는 GPT도 이해할 수 있도록 주요 사실과 제한을 본문에 넣었다. 파일 경로는 후속 Codex가 찾을 단서이며, GPT가 첨부하지 않은 코드·다른 대화·로컬 파일에 접근할 수 있다는 뜻은 아니다.

## 1. 가장 먼저 알아야 할 현재 상황

1. 사용자는 음식점·주문자·배달기사·운영자가 서로의 일과 생활을 이해하고 협업할 수 있는 플랫폼을 만들고 있다.
2. 서버·모바일·웹·Unity·공공데이터 수집 코드는 이미 상당히 있다. 새 시스템을 먼저 만들지 말고 기존 원장·API·업무 절차를 재사용해야 한다.
3. 현재 이 대화의 구체적인 개발 대상은 **음식점 앱 RestaurantDeskApp**이다. 메뉴 등록과 주문 처리부터 작게 완성하려고 한다.
4. 최신 UI는 주문 첫 화면과 `주문 / 메뉴 / 가게` 하단 탐색, 메뉴 목록→입력→저장→목록 복귀까지 반영됐다.
5. **음식 주문 결제·환불·음식점 정산을 한 건으로 끝까지 검증한 상태는 아니다.** 주문 정상 경로 시험 성공과 실결제·실지급 성공을 혼동하면 안 된다.
6. 가장 최근 사용자는 화면을 더 늘리기 전에 **각 역할이 다루는 공통 정보와 고유 정보부터 정리**하려고 한다. 지금은 GPT 채팅에서 그 기획을 이어갈 자료를 요청한 상태다.

## 2. 프로젝트가 지향하는 것

- 프로젝트 표시명은 Mirror(거울). Ssalddel/살뜰과 Hongdal은 기존 코드·저장소 폴더의 이름이다. 명칭이 다르다고 별개 사업/서버로 분리하지 않는다.
- 정보 공개형 커뮤니티에서 출처 있는 자료를 보고, 대화·참여·명시적 동의를 통해 주문·공동행동·실제 업무로 연결한다.
- 음식점과 기사는 수행 횟수만으로 평가하거나 통제하는 대상이 아니다. 서로의 수고와 관계를 알아볼 수 있는 환경을 지향한다.
- 앱은 실제 업무 도구이고, Unity는 그 생활상을 공간과 움직임으로 관찰·체험하는 표현 수단이다. 사용자가 반드시 게임을 해야 업무 앱을 쓸 수 있는 구조는 아니다.
- 사용자 혼자 먼저 사용해 보고 필요한 사람과 함께 확장하는 방향이다. 지금은 디자인 외주보다 업무 흐름이 끊기지 않는 최소 UI를 우선한다.
- UI 이미지는 탐색용 샘플이다. 캡처·파일화·Git 커밋 자체는 확정 디자인 승인이 아니다.

| 책임 | 주 구성 | 소유하는 정보/상태 |
| --- | --- | --- |

운영 변경의 기본 경로는 `화면 → Controller API → UseCase/Command → Domain/Infrastructure → DB/Event/Outbox → 같은 원장 재조회`다.

엔진은 후보·점수·분류를 계산한다. 권한·현재 상태를 검증하는 서버 업무 실행 계층이 확정한다. MongoDB 원장과 RDB는 역할이 다르지만 각 앱이 별개 사실을 만들어서는 안 된다. Event/Outbox 동기화는 멱등 재처리·순환 방지가 필요하다.

실행 효과는 `SsalddelExecution:Mode`의 `Simulation`/`Operational` 경계로 통제한다. 기본 운영 방향은 단일 Ssalddel 서버이며 기존 이름의 프로젝트가 있다고 별도 운영 서버 증설을 승인한 것으로 해석하지 않는다.

## 5. 제품 로드맵과 현재 우선순위를 구별하기

공용 제품 로드맵: `0.0 커뮤니티·공공데이터 → 0.5 개별 주문 → 1.0 같이 주문 → 1.5 공급·가격·무역 준비 → 2.0 화물 → 2.5 창고·판매 → 3.0 음식 배달 → 3.5 마트·도심 물류`.

기본 공개 기준은 0.0이며, 후속 코드는 준비된 capability와 운영 요건에 맞춰 별도 공개한다. 현재 음식점 앱을 작업한다고 전체 3.0 서비스의 실운영을 활성화한 것은 아니다. 앱 `0.1.0` 버전, 제품 로드맵 `3.0`, 기획 `r4`는 서로 다른 번호다.

과거에는 운영자 앱 출시, Unity 관찰·디오라마 정밀화가 각각 먼저였던 시기가 있다. **현재 이 대화에서는 음식점 앱을 우선하고, 다음 기획은 역할별 정보 정리다.** 예전 우선순위를 자동 복원하지 않는다.

## 6. 음식점 앱 — 가장 최근의 구체적 결과

### 구현된 UI 흐름

- 첫 진입 `/`와 `/orders`는 주문 수신함이다. 로그인 후에도 주문 화면으로 간다.
- 하단 `주문 / 메뉴 / 가게`, 기존 서랍은 보존했다.
- `/menus`: 메뉴 목록과 등록/수정 폼을 **서로 다른 화면 상태**로 보여준다. 별도 편집 URL은 아니다.
- 메뉴명·소개·가격·선택적 HTTPS 사진 주소·공개 여부·품절을 다룬다. 사진 업로드는 아직 없다.
- 새 메뉴는 비공개 기본값. 저장 성공 후 서버 목록을 다시 읽고 목록으로 복귀한다.
- 입력 중 다른 화면으로 이동하려 하면 저장 또는 명시적 입력 취소를 안내한다. 등록 응답을 확인하지 못했을 때는 요청을 보존한다.
- 수정은 조회한 revision을 전송한다. 서버 오류를 샘플 성공으로 바꾸지 않는다.
- `/store`: 기존 홈을 가게 관리 진입점으로 옮겼다. 메뉴·기본 조리시간 설정을 재사용한다.
- 영업 상태 변경과 음식점 정산 내역은 아직 미연결임을 표시한다. 없는 정산을 0원·지급 완료로 표시하지 않는다.

### 기존 주문 업무

- 주문 수신함 조회와 실패/빈 목록/갱신 상태 구분.
- 정확한 주문번호 상세 조회, 수락·거절, 조리 예상시간 변경, 픽업 준비 완료.
- 기본 조리시간 5/10/15/20분 선택. 상품별 기본시간과 실제 판매 메뉴 등록은 별개다.
- SignalR 인증 연결·재연결·서버 재조회 요청 코드가 있다.
- 수락 후 전표 준비·출력 경로가 있다. 출력 실패와 주문 상태 전이 실패를 구분한다.
- 기사 수락·픽업·전달은 기사 역할과 서버의 상태 전이가 담당한다. 음식점 화면이 임의로 배송 완료를 찍지 않는다.

## 7. 결제·환불·정산 — 특히 잘못 전달하면 안 되는 부분

사용자는 주문 한 건이 처리된 뒤 얼마가 남고 누구에게 얼마를 지급해야 하는지 확인하는 것을 중요하게 여긴다. 하지만 현재 다음 경계를 지켜야 한다.

1. `음식배달정상수직생명주기Tests`는 주문→수령확인→관찰 사본을 검증한다. 추천 운송을 직접 넣고 **NoOpSettlement**를 사용한다. 정산 완료 증거가 아니다.
2. `음식주문결제승인완료EventHandler`는 `FoodOrderPaymentApproved` 의도를 Outbox에 적재한다. 후속 음식 주문 결제 반영 소비자는 최근 검색에서 확인되지 않았다. 전체 결제 기능이 없다는 단정과도 구분한다.
3. 주문 취소 Handler의 취소·활동·Event는 존재한다. 같은 음식 주문 환불까지 연결되는 경로는 최근 점검에서 확인되지 않았다. 주문 취소와 환불 완료를 같은 상태로 다루면 안 된다.
4. `기사월정산Service`는 배차 건수와 **기사 이용료** 계산이다. 음식점 판매대금이나 기사 배달대금 지급 원장이 아니다.
5. 화물의 `기사지급준비UseCase`가 있다고 음식 배달/음식점 정산이 완성됐다고 볼 수 없다.
6. `RestaurantDeskApp`의 음식점 정산 화면/조회 연결은 아직 없다.
7. 관리자 현금 흐름 조회는 기존 재무사건·관리계정전기에서 기간 유입/유출·미수/지급/환불 의무 변동을 보여주는 코드가 있다. 기초 잔액이 없으면 가용 현금 총액이나 확정 이익으로 추정하지 않는다.

다음 구현 후보는 **샘플 주문 한 건의 결제 승인→주문 처리→취소 시 환불 또는 정산 대상 생성→음식점 조회**다. 실지급 없이 동일 주문·금액·revision·중복 처리·실패 재시도를 검증해야 한다. 회계 정책·정산일·차감·소급 적용·실결제를 구현자가 임의 확정하지 않는다.

과거 대화에는 배달료·거리 할증·구독·영업이익률 4% 같은 여러 경제성 가설이 있었다. **플랫폼 수수료율과 영업이익률은 다르며, 이 요약으로 가격 정책을 새로 확정하지 않는다.** 최신 정책 코드·원가·기간·세금/PG 비용을 별도 대조해야 한다. 과거 자금 가정을 실제 보유 자금으로 해석하지 않는다.

## 9. Unity·지구본·디오라마와 게임

### 유지할 기본 골격

- canonical Scene은 `SimulationWorldShell`. 새 기능마다 공식 Scene을 늘리지 않는다.
- 현실 운영 사실, 게임 가상 상태, Unity 표현을 분리한다. 애니메이션 도착은 업무 완료 증거가 아니다.
- 데이터→해석→공간/객체/움직임→클릭 시 상세 근거를 지향한다. 글자를 먼저 가득 띄우는 방식은 피한다.
- 지구본→국가/한반도→시도→시군구→행정동/역세권→세부 디오라마로 내려가며 필요한 데이터만 적재/해제하려고 한다. 전체 연속 전환 완료를 의미하지 않는다.
- Graph Map은 식별자·관계·기획/코드 결속, 배치맵은 위치·경계·형상·높이 근거·배치 제약을 다룬다. 기존 데이터와 도형 맵을 점진 확장한다.
- 공공 지도는 배경 근거다. 실제 영업점·진입로·배송 가능 위치·현행 건물 용도를 지도만 보고 확정하지 않는다.

### 최근 기록상 상태

- 지구본·행정 경계·계층 확대·행정동 진입·디오라마 검토 자료와 일부 실제 Game View가 있다.
- r55 문서 기준 일반 지도에서 준비된 동 진입은 역사 코드 `11260570`의 사가정 역세권 일부 보기다. r54의 면목제3·8동 정밀 검토 지도는 별도 Editor 진입이며 두 경로 통합은 미완료다. r55의 단계별 상위 복귀 작업은 실행 결과가 아직 비어 있어 완료로 표시하지 않는다.
- 30개 역사 행정동 자료의 경계·도로·건물·등고선 등 검토가 진행됐다. 현재는 전 지역 일괄 고도화 대신 **면목제3·8동 사가정역 주변 한 구간**을 우선하는 r39 방향이다.
- ‘38동’은 문맥에 따라 **면목제3·8동**을 음성으로 표현한 것일 수 있다. 디오라마 38개가 완성됐다고 해석하지 않는다. 행정동·법정동·역세권·타일은 서로 다른 단위다.
- 방문 순서 재생 r54: 동결 타일과 합성 A→B→A 재생 화면 확인 기록이 있지만 실제 방문 기록은 위치 근거 검토 대기다. `SimulationReplayHashMismatch`와 Console 오류가 남아 전체 완료가 아니다.
- 운영 음식 진행 사본은 revision·TTL·낮은 revision 삭제 보호 등의 코어/서버 시험이 있다. 600개 입력 순회는 실제 10분 Play 관찰이 아니다.
- 무역 DB 사본의 선박·항공기 모형은 통계 기반 참고 표현이다. 고정 대표 모형 수이지 실제 대수·실제 항로·실시간 운항이 아니다.
- 수온·물고기 이동, 남북 교류·철도/물류, 제조시설·새벽 공급은 자료 조사/가상 표현/계획의 범위를 구분한다. 법률·제재·현실 노선 운행 허가를 보장하지 않는다.

Farm·Hub·City는 독립 영역이며, 기본 구현을 항상 Farm→Hub→City 운송으로 강제하지 않는다. 기존 스토리·게임 기획은 보존하되 현재 모바일 음식점 작업에 새 전투·스토리 기능을 끼워 넣지 않는다.

H는 공간 의미 계층, WI는 상호작용/행위 단위, E는 검증 증거 단계, G는 관리 체계다. 이 번호들은 제품 버전이나 완료율이 아니다. 오행·괘상은 맥락별 역할 해석의 렌즈이며 금전 실행 권한이 아니다. 프랜차이즈 관점 최종 r37은 생산자 목·제조 화·운영자 토·플랫폼 금(태괘)·가맹 음식점 수(감괘), 자금은 관계 사이의 기운으로 정리됐고 이를 전 도메인의 고정 분류로 확대하지 않는다.

## 10. 공공데이터·메뉴·재료·배달 영상 자료

- 공식 레시피 원본과 음식점 실제 메뉴를 분리하고 메뉴ID↔레시피ID 참고 연결을 만든다. 공공 레시피를 해당 가게의 실제 배합·원산지로 단정하지 않는다.
- 2026-09-24 기록: 관찰 메뉴 60개 대조, 메뉴 21개에 참고 레시피 13종/연결 22건. 나머지는 구성 확인 필요 또는 적절한 후보 없음으로 남겼다.
- 12개 공통 재료 기반 조회, HS 후보·KAMIS 가격 근거·결손·출처를 묶은 읽기 경로가 있다. HS 통계 단위가액은 실제 거래 매입가가 아니다.
- 생산→가공→공급→판매는 물품 흐름과 관리/조율 관계를 구분한다. 국내산과 수입산을 함께 표현하되 추정 공급자를 실제 거래처로 등록하지 않는다.
- 배달 영상의 방문·메뉴·구간 기록은 별도 로컬 SQLite/자료 작업과 연결돼 있다. 일부 조회·멱등 저장·영향 구간 조회 기록이 있으나 서버 운영 주문이나 Unity의 실제 재생과 동일하지 않다.
- 영상·사진·주소·원본 기록과 이용 조건은 각각 관리한다. 개인정보나 비공개 매장/배달 주소를 Unity 배포 자원·인계 첨부물에 자동 포함하지 않는다.

이 인계에는 실제 계정·연락처·정밀 배송 주소·DB 덤프·API 키·비밀번호·개인 영상 원본을 넣지 않았다. 과거 채팅 전체를 원문으로 내보낸 문서도 아니다.

## 11. 이제 GPT와 먼저 논의할 주제

**현재 요청: 역할별로 무엇을 다루는지 정리한 뒤, 그 정보로 UI와 업무 절차를 설계한다.**

권장 출발점은 음식 주문 한 건이다. 공통 정보와 고유 정보를 나누고 각 정보마다 아래 항목을 적는다.

`정보명 / 업무상 의미 / 정본 원장·고유 ID / 최초 입력자 / 변경 가능한 역할·단계 / 조회 역할·범위 / 변경 사건·revision / 개인정보·보존 / 실패·미확인 표현 / 코드 근거`

표시 규칙:

- `존재`: 해당 코드/계약 위치를 확인했다는 뜻. UI·DB·실운영 완료는 별도.
- `미확인`: 이번 범위에서 추적하지 못했다. 없다고 단정하지 않는다.
- `없음(확인 범위)`: 예를 들어 특정 앱의 정산 화면/클라이언트 검색 범위에서 없었다.
- `기획 초안`: 사람이 판단해야 할 책임·공개·화면 제안. 자동 승인 아님.

완성도 점수나 임의 퍼센트 대신 위 사실과 증거를 분리한다. 중복 정보를 앱마다 복제하지 말고 같은 사실의 관점별 조회를 설계한다. 정산은 ‘주문 금액·결제 금액·환불 금액·정산 대상·차감·보류·지급 완료’를 한 숫자로 합치지 않는 데서 시작하면 좋다.

```text
승인 근거 / 개발 인계 상태 / 결과 반환 위치:
```

이 초안에 없는 번호·hash·지급 정책을 GPT가 만들어 채우면 안 된다. 다른 계정/장치에서 이어갈 때는 승인 문서를 저장소에 반영하고 정확한 커밋을 공유해야 한다. **이번 미커밋 작업을 전달하는 일과 새 기획을 승인하는 일은 별개**다. commit·push·배포·실제 결제 활성화는 별도 요청이 필요하다.
