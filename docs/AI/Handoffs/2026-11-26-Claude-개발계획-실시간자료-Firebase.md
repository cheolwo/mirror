# 실시간 자료 구조 — 주기대로 받아 Firebase에 싣고, 앱은 바뀐 것만 내려받는다

2026-11-26 · Claude 개발 계획 + 시안 1장 · 내부 검토용 · 배포 아님

## 사용자의 말

> 데이터들을 관찰을 하는 거니까 좀 실시간성이 좀 중요하다고 생각이 들거든. … 오픈 API 같은 것들을 좀 주기적으로 이렇게 활용을 해서 수집을 해가지고 … 파이어베이스에다가 뭐 자동적으로 그런 데이터들을 실으면은 … 유니티의 모바일 앱에서 사용자가 뭐 로그인을 하면은 데이터들이 뭐 실시간으로 이렇게 파이어베이스에서 다운로드 받아져가지고 … 구조적으로 좀 개편을 할 필요가 있겠다 (12:39)

## 결론

1. **지금 구조:** 자료를 구워 앱 안(`Resources/hongdal-data-*.json` 14개, 1.8 MB)에 넣는다. 자료가 바뀌면 앱을 다시 빌드해야 한다.
2. **바꿀 구조:** 수집기 → 등급 거르기 → Firebase → 앱. 앱에 든 자료는 「씨앗」(처음 켤 때 · 끊겼을 때)으로만 남긴다.
3. **「실시간」은 자료마다 다르다.** 5~10분 자료, 하루 자료, 달 · 분기 자료, 한 해 자료를 나눠 싣고, 화면에는 층마다 「언제 것인지」 칩을 붙인다.
4. **오전에 정한 층 묶음 설계가 그대로 바탕이 된다.** `hongdal-tile-<층>.json`(release · asOf · sha256 · 공개 등급)과 `hongdal-tile-layers.json`(판 목록)이 곧 Firebase에 싣는 판 목록이다.

## 구조

| 자리 | 하는 일 | 지킬 것 |
| --- | --- | --- |
| ① 원천 | 공공 API · 파일. 주기가 저마다 다르다 | 공식 API · 파일만 |
| ② 수집기 | 주기표대로 받는다. 원본은 PC SQLite 원장에 둔다 | 인증키는 수집기에만. 실패하면 앞 판을 지우지 않는다 |
| ③ 등급 거르기 | `public`은 그대로, `bands-only`는 띠(0~5)로, `internal`은 올리지 않는다. 판 목록을 만든다 | 보안각서 자료 · 재배포 금지 원값은 PC 밖으로 안 나간다 |
| ④ Firebase | 판 목록 + 층 파일 / 실시간 값 / 계정 | 쓰기는 수집기 계정만. 앱은 읽기만(계정 문서는 본인 것만) |
| ⑤ 앱 | 로그인 → 판 목록 → 바뀐 층만 받아 저장 → 보는 구의 실시간만 5분마다 | 끊기면 저장한 판, 없으면 씨앗. 층마다 기준 시각 칩 |

### Firebase 안에서 나눠 싣기

| 무엇 | 어디 | 까닭 |
| --- | --- | --- |
| 판 목록 + 층 파일(하루 · 달 · 해) | Hosting(무료) 또는 Storage(Blaze) | 파일 단위로 바뀐 것만 받으면 된다 |
| 실시간 값(5~10분) | Firestore 문서(구마다 하나, 덮어쓰기) | 작고 자주 바뀐다. Hosting은 배포 단위라 5분 갱신에 맞지 않는다 |
| 계정(명덕 · 역할별 레벨) | Auth + Firestore `users/{uid}` | 명덕은 한 계정에서 역할이 함께 쓴다(11-25 결정) |

### 확인한 Firebase 조건(2026-11-26 조회)

- **Cloud Storage:** 2026-02-03부터 무료 요금제(Spark)에서는 쓸 수 없다. Blaze(카드 등록)가 필요하다. Blaze에도 무료 한도가 있다(새 버킷은 미국 3개 리전에서만 무료 한도).
- **Cloud Functions(예약 함수):** Spark에서 쓸 수 없다.
- **Spark로 되는 것:** Hosting(저장 10 GB · 전송 하루 360 MB), Firestore(읽기 하루 5만 · 쓰기 2만 · 저장 1 GiB), Auth.
- **Unity SDK:** Android · iOS용이다. Windows 등 데스크탑은 베타이고 공식 지원은 에디터 안 개발용뿐이다.
  - 그래서 앱은 SDK 없이 HTTPS 요청(UnityWebRequest)으로 읽는다. 폰과 데스크탑이 같은 코드를 쓴다.
  - 잃는 것: 실시간 리스너 · SDK 오프라인 캐시. 5분 폴링과 자체 캐시로 대신한다(원천 주기가 5분이라 손해가 작다).

### 무료 한도 어림

- 실시간 문서: 한 사람이 구 하나를 5분마다 읽으면 하루 288번. 읽기 5만이면 하루 약 170명분이다(구 하나만 볼 때).
- 층 파일: 지금 팩 전체가 1.8 MB다. Hosting 전송 360 MB면 전체를 하루 200번 받을 수 있다. 바뀐 층만 받으면 훨씬 여유가 있다.
- 동 디오라마 파일(사가정 한 판 약 10 MB)은 Hosting 무료 전송으로는 하루 36번뿐이다. 이것을 올릴 때 Blaze + Storage가 필요하다.

## 주기 등급과 화면 표시

| 칩 | 주기 | 자료 | 비고 |
| --- | --- | --- | --- |
| 지금 hh:mm | 5~10분 | 서울 실시간 도시데이터(주요 121장소: 인구 5분 · 상권 10분 · 도로 · 날씨), 따릉이, 기상 실황 | 121장소만. 한 번에 한 곳씩 부른다. 공공누리 1유형(출처 표시) |
| 어제 · 날짜 | 하루 | 승하차, 경락값, 생활인구 | 생활인구는 원래 며칠 늦게 나온다 |
| 평소 · 달 요일 시간대 | 달 평균 | 생활인구 · 체류 띠, 길 속도 월평균 | 121장소 밖은 이것이 바탕 |
| 연도 | 한 해 | 공시지가, 사고다발, 건물 | |
| 끊김 · n분 전 | — | 실시간이 15분 넘게 안 옴 | 세기를 「평소」로 되돌리고 칩만 빨갛게 |

- 실시간이 없는 곳을 실시간처럼 꾸미지 않는다. 「평소」 위에 「지금」이 있는 곳만 덧입힌다.
- **확인 필요:** 사가정역이 121장소에 드는지 모른다(목록 파일 확인은 R1). 안 들면 사가정의 「지금」은 날씨 · 길 속도 · 따릉이까지이고, 사람 수는 「평소」다.
- 동 시선 시안과 잇기: 무대 **자리**는 「평소」가 정하고, 무대 **세기**는 「지금」 값이 있으면 그것으로 숨 쉰다.

## 정한 것(12:50)

- **요금제: 무료(Spark).** Storage · 예약 함수를 쓰지 않는다.
  - 층 파일 → Hosting, 실시간 값 → Firestore, 계정 → Auth + Firestore.
  - 그래서 수집기는 **집 PC 예약 작업**으로 정해진다.
  - 동 디오라마 큰 파일 배포는 Blaze를 쓸 때 다시 정한다.
- R1을 Codex 대기열에 올렸다: [인계](2026-11-26-Claude-인계-실시간주기표-Codex.md).

## 정할 것(처음 물은 것 — 위에서 정해짐)

1. **요금제.** 가안: 무료(Spark)로 R4까지 가고, 동 디오라마 큰 파일을 올릴 때 Blaze로 올린다.
2. **수집기 자리.** 가안: 집 PC 예약. 키와 수집 도구가 이미 있다. PC가 꺼지면 앱에 「끊김」으로 보인다. 늘 켜진 실시간이 필요해지면 클라우드 예약 함수(Blaze)로 옮긴다.

## 지킬 것

- 인증키는 수집기에만 둔다. 앱 · Firebase · git에 넣지 않는다.
- 보안각서 자료(도로명주소 · 내비게이션용DB · 지하철 층)는 Firebase에 올리지 않는다. 앱에 구워 넣는 판의 범위는 따로 정한다.
- 생활인구 · 체류는 띠만 올린다.
- 층마다 출처 · 기준 시각을 화면에서 볼 수 있게 한다.
