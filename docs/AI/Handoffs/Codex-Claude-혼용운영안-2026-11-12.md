# Codex·Claude 혼용 운영 기준 (2026-11-12, 게임 범위 적용)

2026-11-12 사용자는 Unity 기반 Windows 실행판 개발에 집중하고 Codex에서 기획과 구현/미구현을 정리해 Claude가 이어받기 쉽게 만들도록 요청했다. 이 문서는 그 **게임 범위의 기본 역할과 교대 기준**이다. 방향은 [r140](../Planning/시스템/PLAN-SYSTEM-REGIONAL-OPERATOR-SIMULATION/unity-windows-development-direction.r140.md), 기능별 상태는 [Unity Windows 구현 현황](Unity-Windows-구현현황.md)이 소유한다. 앞선 제안의 “Codex 전체 담당, Claude 미지정”은 게임 역할에 한해 이 기준으로 대체하며 수집·영상·앱/서버의 기존 배정과 예약은 유지한다.

새 체계를 만들지 않는다. 기존의 `기획 작업실`·`개발 작업실` 교대 규칙에 두 도구를 배치하는 방법만 정한다.

## 사용자가 말한 방향

- Codex는 사용량이 넉넉하다. 여러 생각과 계획을 넓게 펼치는 기획과, 오래 걸리는 이어 작업에 쓴다.
- Claude는 Codex에서 나온 기획·설계·아이디어를 모아 구현 계획을 쓰고 실제 구현에 들어간다.
- Claude가 계획과 뼈대를 세운 뒤 Codex에게 이어 작업을 넘길 수도 있어야 한다.

## 기본 역할

| 구분 | Codex | Claude |
| --- | --- | --- |
| 주로 하는 일 | 문답, 기획 판본, 시안, 구현/미구현 대조, 완료 조건과 반환 검토 | 기존 구현 조사, 구현 계획, 승인 범위의 코드·시험·실제 Windows 확인 |
| 고치는 곳 | 기획·현황·인계 문서. 방식 B/C로 별도 수용한 경우 해당 코드 | 인계에 적힌 코드 경로, 관련 시험·구현 증거·반환 문서 |
| 남기는 것 | 기획 판본, 구현 현황, 작업지시서와 다음 한 건 | 재사용/변경 계획, 구현 결과·남은 부분·검증별 근거 |

계정이나 도구 이름이 권한이 아니라는 기존 원칙은 그대로다. 작업마다 이번에 어느 작업실 역할인지 인계 문서에 적는다.

## 세 가지 운영 방식

### A. Codex 기획 → Claude 구현

가장 기본이다.

1. Codex가 기획을 정리하고 승인 판본과 작업지시서를 만든다.
2. Claude가 인계를 현재 코드와 대조하고, 이미 있는 구현을 재사용하는 계획을 남긴다. 승인된 범위의 통상 구현 선택마다 새 승인을 요구하지 않는다.
3. Claude가 구현하고 검증한 뒤 반환 문서를 남긴다.
4. Codex가 반환을 읽고 다음 기획으로 이어 간다.

### B. Claude 계획·뼈대 → Codex 이어받기

구현량이 많을 때 쓴다.

1. Claude가 기획을 모아 구현 계획을 쓰고 핵심 뼈대를 만든다. 뼈대는 화면 하나, 흐름 하나가 실제로 도는 범위까지다.
2. Claude가 **이어받기 묶음**(아래 양식)을 남긴다. 무엇이 됐고, 무엇이 비었고, 어떤 순서로 채울지 적는다.
3. Codex가 묶음을 읽고 현재 코드와 대조한 뒤, 수용한 범위만 이어서 채운다.
4. 막히거나 기획 판단이 필요하면 Codex가 `FeedbackRequired`로 돌려보낸다.

뼈대의 코드 존재·빌드·실제 화면과 승인/통합 상태는 별개다. Codex는 이어받기 전에 기준 판본·허용 경로·검증 명령을 다시 확인한다. 최신 사용자 요청은 기획·현황 정리이며 오늘 시제품 전체의 코드 통합을 자동 승인하지 않는다.

### C. 한 도구 단독

작은 수정, 버그 하나, 조사 하나는 한 도구가 처음부터 끝까지 한다. 끝나면 짧은 반환 문서만 남긴다.

## 교대 규칙

- **공용 기억은 저장소다.** 두 도구는 서로의 대화를 볼 수 없다. 넘길 내용은 저장소 문서로 남긴다.
- **기획을 바꿔야 하면 구현 쪽이 고치지 않는다.** 질문으로 돌려보내고 새 판본을 기다린다.
- **같은 파일을 동시에 고치지 않는다.** 동시에 일하면 작업본을 나누고, 같은 checkout이면 교대로 일한다. `CURRENT_WORK.md`는 의미 있는 설계·구현·검증과 교대 때 최신 snapshot으로 갱신한다.
- **`artifacts/local`은 탐색용이다.** 정식 채택은 대상 프로젝트·경로·보존 범위를 명시한 인계에서 결정한다. 현황 정리만으로 파일을 옮기지 않는다.
- **증거 수준을 나눠 적는다.** 정적 검사, 빌드, 시험, 실행 화면, 커밋 여부를 따로 적는다.
- **기획 상태와 소비판 상태를 분리한다.** 다른 소비판에 이미 구현된 것을 전체 미구현으로 적지 않는다. 시안·임시 계산·기능 통합·검증 대기를 [현황표](Unity-Windows-구현현황.md)에 구분한다.

### 같은 PC와 다른 PC의 교대

같은 PC의 미커밋 작업본은 저장소 절대 경로·branch·HEAD, 기존 dirty 목록/소유 경계, 넘기는 파일 목록과 SHA-256, 허용 경로와 완료 조건으로 고정한다. 받는 쪽은 편집 전에 다시 읽고 지문 차이를 확인한다. 작업본 경로 하나만으로 동일 판본이라 판단하지 않는다. 실행 중인 창·빌드·세이브의 소유도 별도로 확인한다.

다른 PC·클라우드 또는 같은 작업본에 직접 접근할 수 없는 별도 계정은 [GitHub 교대 운영 체계](../../Architecture/GitHub기반기획개발교대운영체계.md)의 push된 정확한 commit과 전달 완료 기준을 따른다. 로컬 묶음·경로는 자동 공유되지 않는다. 교대 편의를 이유로 commit·push를 자동 수행하지 않는다.

## 인계 묶음 양식

### Codex → Claude (구현 인계)

```
- 작업실 역할: 개발 작업실 (Claude)
- 대상 기획: PLAN ID, 판본, 상태
- 만들 범위 / 제외 범위
- 완료 조건 (화면·시험·실행 확인 중 무엇까지)
- 허용 경로 (writePaths)
- 기준 branch·commit
- 같은 PC 미커밋이면: 저장소/프로젝트 경로, 기존 dirty 경계, 입력·변경 파일 목록/SHA-256
- 현재 편집·빌드·실행 소유와 필요한 자원
- 재사용할 구현 / 이번 소비판에서 연결할 차이
- 검증 명령
- 돌려받을 위치
```

### Claude → Codex (이어받기 묶음)

```
- 작업실 역할: 개발 작업실 이어받기 (Codex)
- 근거 기획과 Claude 구현 계획 위치
- 된 것: 파일, 동작, 확인한 증거 수준
- 빈 것: 남은 단계를 순서대로, 단계마다 완료 조건
- 건드리지 말 것: 결정된 구조, 다른 작업 영역
- 기준 branch·commit, 같은 PC 미커밋이면 작업본 경로·dirty 경계·파일 목록/SHA-256
- 이번 범위의 허용 경로, 실행 소유와 반환 조건
- 빌드·실행 방법
- 기획에 돌려보낼 질문
```

### 공통 반환 (작업 종료)

```
- 한 일 / 바꾼 파일
- 현황표에서 갱신할 행 / 기획만·다른 소비판 구현·시제품·통합·검증 대기 구분
- 실행한 검증과 결과 (정적·빌드·시험·실행 화면 구분)
- 남은 문제와 다시 시작할 곳
- 커밋·push 여부
```

## Claude 실행 환경에 따른 차이

Claude는 실행 환경에 따라 할 수 있는 일이 다르다. 인계할 때 어느 환경인지 적는다.

| 환경 | 할 수 있는 것 | 못 하는 것 |
| --- | --- | --- |
| Claude Code (PC에서 직접 실행) | 셸, git, `eng/validate-changes.ps1`, 빌드·시험 | 사용자가 허용하지 않은 commit·push |
| Claude 데스크톱 원격 세션 (2026-11-12 작업) | 연결 폴더 파일 읽기·쓰기, 화면 클릭으로 빌드 스크립트 실행, 실행 화면 확인 | PC 셸과 git 명령, 저장소 검증 스크립트 실행 |

위 원격 세션의 제약은 2026-11-12 해당 작업의 관측이며 모든 Claude 환경의 고정 제약이 아니다. 실행 시 사용 가능한 도구를 확인한다. 미커밋 결과는 위 같은 PC 대조 절차로 읽을 수 있으며, commit·push는 별도 요청 범위다.
