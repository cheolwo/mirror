# Codex·Claude 혼용 운영 기준 (게임 범위 적용)

2026-11-20 사용자 결정으로 게임의 기획·개발 협업은 **작업별 양방향 배정**을 따른다. 2026-11-12의 역할 배정은 초기 운영 이력이다. Unity Windows 우선순위는 [r140](../Planning/시스템/PLAN-SYSTEM-REGIONAL-OPERATOR-SIMULATION/unity-windows-development-direction.r140.md), 기능별 상태는 [Unity Windows 구현 현황](Unity-Windows-구현현황.md), 자료 작업은 [데이터 협업 기준](../DataCollection/Collaboration.md)에서 확인한다.

## 작업별 역할

| 역할 | 할 일 |
| --- | --- |
| 기획·개발계획 담당 | 현재 구현을 확인하고 기획 판본을 정리한다. 구현 순서, 재사용할 코드, 완료 조건을 개발계획에 적는다. |
| 구현 담당 | 인계와 실제 작업본을 맞춘 뒤 승인된 변경을 구현한다. 코드·시험·실행 결과와 다음 작업을 반환한다. |
| 반환 검토 담당 | 기획과 완료 조건으로 결과를 확인한다. 별도 지정이 없으면 해당 건을 넘긴 기획·개발계획 담당이 검토한다. |

각 역할은 Codex와 Claude 모두 맡을 수 있다. 사용자 요청과 기존 배정을 기준으로 [공용 작업 대기열](CODEX-대기열.md) 또는 개별 인계에 담당을 적는다. 기획과 개발계획 담당이 다른 경우 각각을 표시한다. 인계를 받은 구현 담당은 현재 작업본에서 필요한 구현 순서나 시험 방법을 구체화할 수 있다.

## 기획 전 현재 구현 대조

2026-11-14 사용자 요청으로 기존 ‘반환을 읽고 다음 기획으로 잇기’를 기획 작성 전의 기본 절차로 명시한다. **현재 구현을 먼저 확인하고, 사용자 질문/답변이 바꾸는 부분을 결합해 기획서를 작성한다.** 기존 역할·승인·실행권을 바꾸는 규칙은 아니다.

1. `CURRENT_WORK.md`·[구현 현황](Unity-Windows-구현현황.md)에서 질문 대상의 작업본/담당과 현행 기획을 찾고, 관련된 최신 구현 반환·빌드/화면 기록으로 이어 간다. 반환이 지목한 소스·빌드·판본을 대조해 최신 여부를 확인한다.
2. 실제 작업본의 관련 소스·팩/자료·계약을 읽어 이미 있는 동작과 미연결/진행 중인 부분을 확인한다. 코드 존재·시험·빌드·수행자의 화면 확인·이번에 직접 한 실행을 나눠 적고, 실행판 근거는 해당 빌드에만 귀속한다. 다른 소비판/예전 시제품을 현재 Windows 실행판과 섞지 않는다.
3. 확인한 현황과 사용자 답변을 결합해 **그대로 재사용 / 기존 구현 보완·연결 / 신규 필요 / 미확인**으로 나눈다. 사용자 확인은 해당 선택에만 적용하며 기획 추천·미정·코드의 임시값을 묶어 승인된 것으로 올리지 않는다.
4. 기획서 앞부분 또는 관련 절에 아래의 짧은 ‘현재 구현과 이번 차이’를 남긴다. 이후 현재 기획 판본·목차·필요한 현황만 갱신한다. 원본 구현 사실은 반환/소스가 소유하고 기획은 근거와 이번 차이를 참조한다.
5. 작성 중 관련 파일이 달라지면 바뀐 부분만 다시 확인한다. 확인할 수 없는 코드/실행판은 **미확인**으로 남기고 근거가 있는 부분의 기획을 계속한다. 새 의미 있는 변경에서는 관련 범위를 다시 확인하되, 같은 입력 지문/근거를 방금 확인했다면 그 범위와 시점을 명시해 재사용할 수 있다. 매 질문마다 프로젝트 전체 감사·새 빌드·실행을 요구하지 않는다.

```text
현재 구현과 이번 차이
- 확인 시점/대상: 프로젝트 경로·branch/commit 또는 소스/반환 판본
- 현재 되는 것: 이번 질문과 관계된 동작, 근거 링크와 확인 수준
- 진행 중/빈 것/미확인: 담당·미연결·검증 한계
- 사용자 답변으로 달라지는 것: 이번에 확정한 의미와 유지할 미정
- 기획 범위: 재사용 / 보완·연결 / 신규 필요와 제외 범위
```

이 기록이 새 승인 관문·Goal 활성화나 자동 구현을 뜻하지 않는다. 현황표가 뒤처졌으면 확인한 관련 행/시점과 차이를 갱신하고, 반환의 빌드/화면 기록을 이번에 직접 조작한 근거로 보고하지 않는다. 문서 체계만 바꾸는 경우에는 작업 절차와 검증 범위를 기록하며 새 게임 판본을 만들 필요는 없다.

## 세 가지 운영 방식

### A. 기획과 개발계획을 넘겨 구현

**Codex 기획·개발계획 → Claude 구현 → Codex 검토** 또는 **Claude 기획·개발계획 → Codex 구현 → Claude 검토**로 이어 간다. 두 방향에서 같은 절차를 쓴다.

1. 기획·개발계획 담당이 현행 구현을 대조하고, 기획 판본과 단계별 작업지시서를 남긴다.
2. 구현 담당이 기준 판본, 허용 경로, 구현 승인과 검증 조건을 확인하고 수용한 단계를 진행한다.
3. 구현 담당이 결과와 검증 근거를 반환하고, 검토 담당이 완료 조건을 확인한다.

### B. 진행 중인 구현을 이어받기

Codex와 Claude 어느 쪽도 진행 중인 구현을 상대에게 넘길 수 있다. 작업 지점·기준 커밋·수정 파일·실제로 확인한 증거·남은 단계와 완료 조건을 적는다. 이어받은 쪽은 현재 작업본과 대조하고 수용한 범위를 진행한다. 기획 판단이 필요한 발견은 `FeedbackRequired`로 돌려보낸다.

### C. 한 도구 단독

작은 수정, 버그 하나, 조사 하나는 같은 도구가 맡은 범위 안에서 끝까지 진행할 수 있다. 기획에서 구현 역할로 넘어갈 때는 현재 승인과 허용 경로를 확인한다.

## 교대 규칙

- **공용 기억은 저장소다.** 두 도구는 서로의 대화를 볼 수 없다. 넘길 내용은 저장소 문서로 남긴다.
- **기획을 바꿔야 하면 구현 쪽이 고치지 않는다.** 질문으로 돌려보내고 새 판본을 기다린다.
- **같은 파일을 동시에 고치지 않는다.** 동시에 일하면 작업본을 나누고, 같은 checkout이면 교대로 일한다. `CURRENT_WORK.md`는 의미 있는 설계·구현·검증과 교대 때 최신 snapshot으로 갱신한다.
- **`artifacts/local`은 탐색용이다.** 정식 채택은 대상 프로젝트·경로·보존 범위를 명시한 인계에서 결정한다. 현황 정리만으로 파일을 옮기지 않는다.
- **증거 수준을 나눠 적는다.** 정적 검사, 빌드, 시험, 실행 화면, 커밋 여부를 따로 적는다.
- **기획 상태와 소비판 상태를 분리한다.** 다른 소비판에 이미 구현된 것을 전체 미구현으로 적지 않는다. 시안·임시 계산·기능 통합·검증 대기를 [현황표](Unity-Windows-구현현황.md)에 구분한다.

### 같은 PC와 다른 PC의 교대

같은 PC의 미커밋 작업본은 저장소 절대 경로·branch·HEAD, 기존 dirty 목록/소유 경계, 넘기는 파일 목록과 SHA-256, 허용 경로와 완료 조건으로 고정한다. 받는 쪽은 편집 전에 다시 읽고 지문 차이를 확인한다. 작업본 경로 하나만으로 동일 판본이라 판단하지 않는다. 실행 중인 창·빌드·세이브의 소유도 별도로 확인한다.

다른 PC·클라우드 또는 같은 작업본에 직접 접근할 수 없는 별도 계정은 [GitHub 교대 운영 체계](../../Architecture/GitHub기반기획개발교대운영체계.md)의 push된 정확한 commit과 전달 완료 기준을 따른다. 로컬 묶음·경로는 자동 공유되지 않는다. 교대 편의를 이유로 commit·push를 자동 수행하지 않는다.

## 인계 묶음 양식

### 공통 구현 인계

```
- 담당: 기획·개발계획 / 구현 / 반환 검토
- 개발계획·작업지시서 위치와 이번에 시작할 단계
- 대상 기획: PLAN ID, 판본, 상태
- 만들 범위 / 제외 범위
- 완료 조건 (화면·시험·실행 확인 중 무엇까지)
- 허용 경로 (writePaths)
- 기준 branch·commit
- 같은 PC 미커밋이면: 저장소/프로젝트 경로, 기존 dirty 경계, 입력·변경 파일 목록/SHA-256
- 현재 편집·빌드·실행 소유와 필요한 자원
- 재사용할 구현 / 이번 소비판에서 연결할 차이
- 검증 명령
- 돌려받을 위치
```

### 진행 중인 구현을 넘길 때 추가할 정보

```
- 된 것: 파일, 동작, 확인한 증거 수준
- 빈 것: 남은 단계를 순서대로, 단계마다 완료 조건
- 이어받기 전 확인할 구조와 실행 중인 작업
- 기획에 돌려보낼 질문
```

### 공통 반환 (작업 종료)

```
- 한 일 / 바꾼 파일
- 현황표에서 갱신할 행 / 기획만·다른 소비판 구현·시제품·통합·검증 대기 구분
- 실행한 검증과 결과 (정적·빌드·시험·실행 화면 구분)
- 남은 문제와 다시 시작할 곳
- 커밋·push 여부
```

## Claude 실행 환경에 따른 차이

Claude는 실행 환경에 따라 할 수 있는 일이 다르다. 인계할 때 어느 환경인지 적는다.

| 환경 | 할 수 있는 것 | 못 하는 것 |
| --- | --- | --- |
| Claude Code (PC에서 직접 실행) | 셸, git, `eng/validate-changes.ps1`, 빌드·시험 | 사용자가 허용하지 않은 commit·push |
| Claude 데스크톱 원격 세션 (2026-11-12 작업) | 연결 폴더 파일 읽기·쓰기, 화면 클릭으로 빌드 스크립트 실행, 실행 화면 확인 | PC 셸과 git 명령, 저장소 검증 스크립트 실행 |

위 원격 세션의 제약은 2026-11-12 해당 작업의 관측이며 모든 Claude 환경의 고정 제약이 아니다. 실행 시 사용 가능한 도구를 확인한다. 미커밋 결과는 위 같은 PC 대조 절차로 읽을 수 있으며, commit·push는 별도 요청 범위다.
