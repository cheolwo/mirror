# 2026-11-12 Claude 제안 — 흩어진 자료·엔진·업무 OS를 홍달 디오라마 경영 시뮬레이션에 녹이는 구조

[혼용 운영 기준](Codex-Claude-혼용운영안-2026-11-12.md)의 Claude 제안이다. 사용자 요청(2026-11-12)에 따라 프로젝트에 흩어진 자료와 엔진·업무 OS를 조사하고, 홍달 경영 시뮬레이션 하나로 모으는 구조와 뼈대, 단계 계획을 제안한다. 코드와 PLAN 판본은 바꾸지 않았다. 기획으로 받아들일 부분은 Codex가 판본에 반영한다.

## 0. 한눈에

### 후속 기획·진행 보고 (2026-11-12)

지도별 경영 책임·자동 초점·창고 내부 모델 진입/귀환은 [r144](../Planning/시스템/PLAN-SYSTEM-REGIONAL-OPERATOR-SIMULATION/scale-os-management-focus.design.r144.md)에 문서화했다. **Core 통합과 우유 5팩 흐름은 사용자 전달 기준 Claude 구현 중**이며 이 제안서 작성 당시의 미정·착수 질문과 현재 진행 보고를 구별한다. 실제 코드·통합·검증 결과는 별도 반환에서 확인하며 이번 기록이 작업을 중단하거나 새 범위의 실행권을 부여하지 않는다. 아래 내용은 제안 작성 당시의 조사·선택지 이력으로 보존한다.

- 자료는 이미 많이 모여 있고, Codex가 2026-11-11에 전수 색인과 여섯 묶음으로 정리해 두었다. 부족한 것은 수집이 아니라 **게임까지 가는 길**이다.
- 규칙도 이미 많다. 음식 배달·화물·창고·마트의 업무 OS와 엔진, 서버와 게임이 함께 쓰는 규칙 패키지가 있다. 다만 **규칙을 돌리는 Core가 둘**이고 홍달 게임은 그중 작은 쪽만 쓴다.
- 제안은 새 체계를 만드는 것이 아니다. 이미 있는 다섯 가지(생산·소비 두 축 r134, 업무 OS 생명주기, 법정동 패키지, 세션 자료 판본 고정 r54, 점진 공개 r141)를 **한 줄기**로 잇는다.
- 한 줄기는 이렇다: 자료를 **팩**으로 굽고 → 업무 OS를 **모듈**로 꽂고 → 모든 것을 **건물(장소)**에 묶어 → **축척**에 따라 다른 사업을 보여 준다.

## 2. 제안하는 구조

### 2.1 원칙

1. **건물이 중심이다.** 매장·창고·센터·공장은 모두 지도의 건물이다. 사람·차량·주문·재고는 건물에 묶인다.
2. **자료는 팩으로만 들어온다.** 게임은 원본을 직접 읽지 않는다. 회차는 시작할 때의 팩 판본에 고정한다.
3. **업무는 모듈이다.** 음식 배달도 여러 모듈 중 하나다. 모듈은 같은 시계·원장·저장을 쓴다.
4. **엔진은 추천만 한다.** 확정은 플레이어가 한다. 서버의 원칙과 같다.
5. **축척이 곧 사업 범위다.** 축소할수록 더 큰 사업이 보인다.

### 2.2 네 층 — 자료·규칙·투영·표현

```text
   (게임 밖 · 굽는 시간)                          (게임 안 · 실행 시간)

 ① 자료                                     ② 규칙   게임 커널 + 업무 모듈      Unity 없음
 원본 ──▶ 정리 ──▶ 팩 ══════════════▶          │ 상태 사본
 수집      법정동·     공간·생활·                 ▼
           업종 기준   업종·표현          ③ 투영   장면 모델 (무엇을 얼마나 보일지)
                                                │
                                                ▼
                                       ④ 표현   2.5D 디오라마 + HUD      WindowsGame
                                                │ 명령 (후보 보기 → 확정)
                                                └──────────▶ ②
```

아래로는 상태만, 위로는 명령만 흐른다. 2026-11-12 구조 개편안의 규칙·실행·투영·표현에서 규칙과 실행을 한 층으로 보고, 앞에 자료 층을 더했다.

### 2.3 자료 → 팩

| 팩 | 담는 것 | 재료 | 단위 |
| --- | --- | --- | --- |
| 공간 팩 | 경계, 도로, 건물·주소, 횡단보도·차선, 지형 | 법정구역 경계, OSM, 노드링크, 서울시 도로 자료 | 법정동 |
| 생활 팩 | 시간대별 수요 곡선, 붐비는 곳, 시설·상권 후보 | 유동인구, 상권, 시설 목록, 날씨 | 법정동·분기 |
| 업종 팩 | 메뉴·레시피·재료·원가, 품목·단위·가격, 화물·창고 표본, 가맹 운영 조건 | 배달 통합 DB의 **집계값**, 가격 자료, 프랜차이즈 조사 | 업종 |
| 표현 팩 | 타로, 학습 카드, 건물·차량 외형 | 타로 78장, 카드 후보, Synty | 게임 전체 |

팩마다 목록 파일에 다음을 적는다: 식별자, 판본, 입력 SHA-256, 출처, 기준일, 이용 조건, **배포 가능 여부**(내부 검토만 / 배포 가능 / 미확인), 개인정보 등급.

- 목록은 기존 `neighborhood-package-registry.v2`와 지역 Experience Package를 상위로 쓴다. 새 등록부를 만들지 않는다.
- 생활 팩은 원본 수치를 그대로 싣지 않는다. "점심에 이 동네 주문이 많다" 같은 **게임용 곡선**으로 바꿔 싣고, 변환 방법을 적는다. 인구가 주문으로 바뀌는 비율은 자료가 아니라 게임 규칙이다.
- 개인 배달 자료는 원본·고객·주소를 팩에 넣지 않는다. 업종별 메뉴 구성, 준비 시간 분포, 시간대 주문 비율 같은 집계만 쓴다.

### 2.4 게임 커널과 업무 모듈

**커널이 맡는 것** (지금 작은 Core가 단순한 형태로 이미 한다)

- 가상 시계, 회차, 난수 씨앗
- 명령: 후보 보기 → 확정, 판본 번호와 명령 ID로 중복·엇갈림 방지
- 사건 기록, 저장과 재생
- 공통 원장: 돈, 시간(경 유지), 재고의 이동
- 공통 개체: **장소**(건물), **주체**(기사·점주·작업자), **자원**(차량·재고 묶음), **일**(주문·발주·운송 의뢰), **인계**

**모듈이 맡는 것**

```csharp
interface IBusinessModule
{
    string OsId { get; }                    // 기존 카탈로그 ID 그대로. 예: FoodDeliveryOS
    void Start(ModuleContext context);      // 팩에서 읽은 자료와 씨앗
    void Tick(long elapsedMs);              // 가상 시각 진행
    Candidates Preview(Command command);    // 후보와 추천만 돌려준다
    Result Confirm(Command command);        // 검증한 뒤 상태를 바꾼다
    object Snapshot();                      // 화면용 상태 사본
}
```

- 단계 이름과 허용 전이는 기존 생명주기 카탈로그를 따른다. 게임만의 단계를 만들지 않는다.
- 후보 계산은 `Ssalddel.WorkflowRules`의 정책을 먼저 쓴다.
- 모듈끼리는 직접 부르지 않는다. **인계**를 커널에 내면 받는 모듈이 가져간다. 인계에는 보내는 쪽, 받는 쪽, 대상, 확정 수량·단위, 시각, 근거를 담는다(r71의 인계 기록과 같다).

### 2.5 엔진과 업무 OS를 게임으로 옮기는 대응

| 운영 플랫폼의 것 | 게임에서의 모습 |
| --- | --- |
| 업무 OS | 플레이어가 여는 **사업 라인**. 단계가 디오라마에서 사람·차량·화물의 움직임으로 보인다 |
| 판단 도구(엔진) | **추천**. 후보와 이유를 보여 주고 플레이어가 고른다. 지금의 "추천 기사 B"가 첫 사례다 |
| 스케줄링 정책 | **운영 방침 카드**. 마감 우선(EDF), 가까운 순(Geo Nearest), 묶음 배송(Batching), 오래 기다린 순(Aging), 차량 적합 우선(Fit First). 지금의 전차·절제·여제 카드가 방침을 바꾸는 첫 사례다 |
| 실패와 회복 사례 | **사건**. 픽업 지연, 품절, 수량 불일치, 수령자 부재. 회복 절차가 곧 플레이어의 대응이다 |
| 역할 앱의 화면(기사·음식점·창고·화주) | 건물이나 사람을 눌렀을 때의 **입장 카드**. 같은 일을 서로 다르게 본다 |
| 미리보기 → 확정 | 후보 보기 → 배정. 이미 같은 모양이다 |
| Simulation / Operational 경계 | 게임은 항상 Simulation이다. 운영 자료는 읽기 전용 파생만 들어온다 |

엔진마다 게임 장면으로 옮기면 이렇다.

| 엔진 | 게임 장면 |
| --- | --- |
| 운송 의뢰 배차 | 주문이나 화물을 누르면 기사·차량 후보와 이유가 뜬다 |
| 출고 배치 | 발주가 들어오면 "어느 창고의 어느 재고로 낼지" 후보가 뜬다 |
| 피킹 배치 | 창고 건물에서 작업자에게 피킹·포장을 나눈다 |
| 차량 적재·혼적 | 트럭에 화물을 싣는 순서와 적재율을 본다 |
| 집단화 | 같은 단지·같은 품목의 수요가 묶여 공동 주문 후보가 된다 |

같은 단계 정의를 실제 앱과 게임이 함께 쓰면, 게임은 실제 운영 체계의 **연습판**이 된다. 작은 Core에는 이미 내부 검토용 내보내기(`game-business-preparation.v1`)가 있다. 게임 결과를 운영에 쓰는 길은 지금처럼 닫아 둔다.

### 2.6 디오라마에 올리는 방법

**건물에 역할을 붙인다.** 2A-2에서 만든 건물 색인이 출발점이다. 건물마다 역할(매장·창고·센터·공장·주거)과 소속(내 운영·제휴·미관여)을 붙인다. 건물을 누르면 주소 다음에 "이 건물에서 하는 일"이 나온다(r142 입지 시험, r143 운영 매장 강조와 같은 자리).

**사업마다 표현 층을 둔다.** 음식 배달은 오토바이, 화물은 트럭과 상·하차, 창고는 건물 상태와 드나드는 차량, 인구는 회색 보행자다. 층은 켜고 끌 수 있고, 아직 열지 않은 사업의 층은 보이지 않는다(r141).

**축척마다 다른 사업을 보여 준다.**

| 축척 | 범위 | 여기서 하는 경영 | 주로 쓰는 팩 |
| --- | --- | --- | --- |
| 건물 | 건물 하나 | 매장·창고의 준비 상태, 재고, 사람 | 업종 팩 |
| 동네 (2.5D) | 법정동 하나 | 음식 배달, 매장 운영, 입지 시험 | 공간·생활 팩 |
| 구 | 여러 법정동 | 가맹점 망, 배달권, 도심 창고·마트, 기사 모집 | 공간 팩(경계), 생활 팩 |
| 광역 | 서울·수도권 | 물류센터 출고 회차, 간선 화물 | 노드링크, 업종 팩 |
| 나라·세계 | 생산지·항만·공항 | 생산자 연결, 수입 | 가격·무역 자료, 세계 목록 |

2A-1의 "더 축소하면 구 지도로"가 이 사다리의 첫 칸이다.

날짜 없이 관문으로 진행한다. 지금 진행 중인 2B(법정동 팩)·2C(공공 건물 자료)는 1단계에 들어간다.

| 단계 | 할 일 | 관문 |
| --- | --- | --- |
| **0. 뼈대** | S1~S5 | 같은 두 주문에서 정산 9,600 / 7,200 / 3,600원과 저장·이어하기가 그대로다. 음식 배달이 모듈 1호로 돈다 |
| **1. 팩 두 개** | 면목동 공간 팩(경계·횡단보도 포함), 생활 팩 1판(유동인구 → 시간대 수요 곡선, 표시만) | 같은 입력이면 같은 팩. 한계 배율이 법정동 경계에 맞는다. 실제 관측과 게임 해석이 화면에서 구분된다 |

## 6. 주의

- **개인정보.** 개인 배달 관측의 원본·고객·주소·정산 원문은 팩에 넣지 않는다. 집계만 쓴다.
- **권리.** 메뉴 이미지 3,194개, 강의 대본, 카페 글, OCR 카드는 이용 조건이 확인되지 않았다. 배포 가능 여부가 "미확인"인 팩은 내부 검토판에만 넣는다. 타로 78장은 CC0다.
- **실제 상호.** 실제 매장 이름과 가상 메뉴를 한 화면에 붙이려면 기존 방식(샘플 표시, 제휴 없음 표시)을 따른다.
- **운영 경계.** 게임 상태가 실제 주문·배차·결제를 바꾸지 않는다. 운영 자료는 읽기 전용 파생만 쓴다.
- **수치의 뜻.** 유동인구는 주문 수가 아니고, 도로 형상은 교통량이 아니다. 변환은 게임 규칙으로 따로 적는다.

## 7. 결정이 필요한 것

1. **Core를 어떻게 합칠까.**
   - 가. 작은 Core에 모듈을 키운다. 빠르지만 화물·창고·가맹 규칙이 두 벌이 될 수 있다.
   - 나. 홍달을 큰 Simulation 세션으로 옮긴다. 규칙은 한 벌이지만 옮기는 일이 크다.
   - 다. 게임 쪽 계약(명령과 상태 사본)을 고정하고, 뒤에서는 순수 정책은 `WorkflowRules`를 쓰고 이미 큰 Simulation에 있는 것(공급망 등)은 어댑터로 감싼다.
   - 제안은 "다"다. 다만 큰 Simulation의 코드는 이번에 문서로만 확인했다. 실제로 감쌀 수 있는지는 0단계에서 공급망 모듈 하나로 확인한다.
2. **개인 배달 자료를 어디까지 쓸까.** 집계 분포만 / 가상 매장에 분포를 입힘 / 내부판에 한해 실제 상호. 제안은 "가상 매장에 분포를 입힘"이다.
3. **첫 인계 사슬을 r71의 우유 5팩으로 할까.**
4. **0단계를 바로 시작할까.**

## 8. 하지 않는 것

- 새 수집, 새 API 키, 유료 생성은 이 제안에 없다.
- 기존 기획 체계(E·G·H·WI, 괘·오행 분류)는 바꾸지 않는다. 이 구조는 그 위의 구현 배치다.
- 다른 Unity 세계(Farm·Hub·City)와 역할 앱은 건드리지 않는다.
