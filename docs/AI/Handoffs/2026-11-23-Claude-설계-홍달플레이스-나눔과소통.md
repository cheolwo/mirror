## 1. 한 줄로

**홍달 플레이스 = 「카드」를 내놓는 곳.** 상품도, 실내 배치도, 소식 · 질문도 모두 같은 껍데기의 카드다. 카드는 한 저장소(정본)에 쌓이고, 지도 위 자리(역 · 타일 · 동)에 꽂히며, 다른 사람이 **보고 · 가져가 고치고 · 묻고 · 답한다.** 누가 무엇을 가져가 고쳤는지는 끊기지 않는 줄(계보)로 남는다.

```
           ┌──────────── 홍달 플레이스 ────────────┐
 내놓기 →  │  카드 저장소(정본)                      │ → 보기 창(손님 · 점주 · 운영 · 근거)
           │   ├ 상품 카드   ├ 공간 카드   ├ 이야기 카드 │
 가져가기 ← │   └ 줄(계보 · 답 · 참고)                 │ ← 지도(역 · 타일 · 동)에 꽂힘
           └───────────────────────────────────────┘
```

## 2. 왜 「카드 하나의 껍데기」인가

- 상품 · 공간 · 이야기를 따로 만들면 검색 · 공유 · 신고 · 계보를 세 번 만든다. 껍데기를 하나로 두면 **새 갈래(예: 레시피, 배차 방침, 역 꾸밈)가 늘어도 「내용」 칸만 더한다** — 타일 그릇을 「열린 꼴」로 둔 것과 같은 생각이다.
- 지금 플레이스의 매장 페이지(r195)도 카드의 한 갈래(「장소 카드」)로 다시 읽힌다. 이미 만든 것을 버리지 않는다.

## 3. 카드의 꼴 (스키마 v1 가안)

### 3.1 공통 껍데기

| 칸 | 뜻 |
| --- | --- |
| `id` | `card:<갈래>:<만든 곳>:<번호>` — 만든 곳은 `game`(게임 속 인물) · `local`(내 PC의 플레이어) · `net`(뒤에 온라인) |
| `kind` | `product` · `space` · `story` · `place`(매장 페이지) — 늘어날 수 있다 |
| `title` · `summary` | 이름과 한 줄 |
| `author` | 만든 이: 역할(점주 · 기사 · 공급자 · 손님 · 지사 · 플레이어)과 게임 속 이름. 실명 없음 |
| `where` | 지도 자리(선택): 역 이름 · 타일 `(q, r)` · 행정동 코드. 지도에서 「이 역 둘레에서 나온 카드」를 모아 볼 수 있다 |
| `revision` · `createdAt` | 판본과 만든 때(게임 시각 + 실제 시각) |
| `from` | 원본 카드 `id`와 판본 — **가져가 고친 것이면 반드시 남긴다**(계보) |
| `visibility` | `private`(나만) · `game`(게임 속 사람들) · `export`(파일로 내보낼 수 있음) · `public`(뒤에 온라인) |
| `rights` | 출처와 조건: `game-made`(게임이 만든 것) · `player-made` · 공공데이터면 출처와 이용 조건. **내부 검토 자료(주소 원문 등)에서 나온 카드는 `export` 이상이 될 수 없다** |
| `tags` | 업종 · 재료 · 분위기 등 검색 낱말 |
| `body` | 갈래별 내용(아래) |

### 3.2 상품 카드 (`product`)
- 이름 · 갈래(음료 · 식사 · 상품) · 크기/용량 · 가격대(게임 가격) · **재료 목록**(재료 낱말은 이미 모은 `menu-ingredient-foundation`의 이름표에 맞춘다) · 원가 추정(재료값 자료 `menu-ingredient-prices`) · 만드는 단계(카페 작업 맵 r167의 작업대 이름) · 사진(게임 렌더 그림).
- 「이 상품을 파는 매장」은 상품 카드가 아니라 **장소 카드 → 상품 카드를 가리키는 줄**로 둔다. 같은 상품을 여러 매장이 가져다 쓸 수 있다.

### 3.3 공간 카드 (`space`) — 실내 배치
- **방:** 바닥 모양(0.5 m 격자의 다각형) · 층 · 문 · 창 · 벽.
- **부품:** 게임 부품 목록의 `partId`(카운터 · 에스프레소 바 · 좌석 · 픽업대 · 냉장고 · 선반 …), 자리(x, y), 돌림, 쓰임 이름표(주문 · 제조 · 픽업 · 대기).
- **흐름:** 손님 동선 · 직원 동선(선), 주문 → 제조 → 픽업 차례(r167의 「한 층 흐름」).
- **셈(자동):** 넓이 · 좌석 수 · 작업대 길이 · 동선 길이 · 「주문에서 픽업까지 걸음 수」. 이 셈이 게임 규칙(제조 시간 · 대기)에 쓰일 수 있다 — 공유된 배치를 가져다 쓰면 **숫자로 차이가 난다.**
- **그림:** 위에서 본 평면 썸네일, 2.0에서는 동 디오라마 안 그 건물 속 3D.
- 「점포 유형은 같은 작업 모듈의 배치 차이」(r167)를 그대로 카드로 만든 것이다. 실제 프랜차이즈의 도면 · 이름 · 로고는 넣지 않는다.

### 3.4 이야기 카드 (`story`)
- 소식(새 메뉴 · 휴무) · 질문 · 답 · 후기 · 함께 하자는 제안(예: 「이 상품의 재료를 같이 사자」, 「이 역 둘레 배달을 나눠 맡자」).
- 질문과 답은 `from`이 아니라 `replyTo`로 잇는다. 다른 카드(상품 · 공간)를 가리킬 수 있다 — **「이 배치에서 픽업대를 왜 문 옆에 뒀어요?」**

### 3.5 줄 (카드 사이의 관계)
| 줄 | 예 |
| --- | --- |
| `derivedFrom` | 공간 카드 B는 A를 가져와 좌석을 줄인 판 |
| `uses` | 장소 카드(카페 1호점) → 상품 카드(라떼) · 공간 카드(1호점 배치) |
| `replyTo` | 질문 → 답 |
| `refers` | 이야기가 상품을 가리킴 |
| `endorsed` | 「참고했어요」 — 좋아요 대신, **실제로 가져다 쓴 일**을 센다 |

## 4. 소통의 흐름 — 네 동사

| 동사 | 하는 일 | 남는 것 |
| --- | --- | --- |
| **내놓기** | 내 매장의 상품 · 배치를 카드로 만든다. 게임 속 매장이 생기면 자동으로 초안이 생긴다(r195의 자동 등록과 같은 길) | 카드 + 공개 범위 |
| **보기** | 플레이스의 「나눔」 탭 · 지도의 역/타일 창 · 매장 페이지에서 본다. 역할마다 보이는 칸이 다르다(정본 하나 · 창 여럿) | 열람 기록(집계만) |
| **가져가 고치기** | 남의 상품 · 배치를 내 매장에 들여와 바꾼다. 원본은 그대로, 내 것은 새 판본 | `derivedFrom` 줄 · 원작자에게 「누가 참고했어요」 알림 |
| **묻고 답하기** | 카드에 질문을 달고 답한다. 게임 속 인물도 묻고 답한다(아래) | `replyTo` 줄 |

- **역지사지(r269)와 묶기:** 카드를 볼 때 「이 배치를 손님 자리에서 · 직원 자리에서 · 배달 기사 자리에서」 바꿔 본다(같은 공간 카드의 동선을 역할마다 다른 색으로). 공유가 곧 남의 입장을 보는 연습이 된다.
- **관찰과 개입(r328):** 플레이어가 아무것도 안 해도 게임 속 인물들이 서로 카드를 내놓고 가져다 쓴다 — 지켜보면 동네의 유행이 퍼지는 게 보인다. 플레이어는 원할 때 끼어든다.

## 5. 누구와 나누나 — 세 겹(넓혀 가는 순서)

| 겹 | 상대 | 저장 | 언제 |
| --- | --- | --- | --- |
| **① 게임 안** | 게임 속 인물들(점주 · 공급자 · 기사 · 손님)과 플레이어 | 세이브 안의 카드 저장소(JSON/SQLite) | 첫 걸음. 지금 구조로 된다 |
| **② 파일로** | 다른 플레이어 — 카드를 `.hongdal-card`(묶음은 `.hongdal-pack`) 파일로 내보내고 가져오기 | 파일 + 서명(지문 SHA256) · 계보 | 1.0 안에 넣을 수 있다. 서버가 필요 없다 |
| **③ 온라인** | 모든 플레이어 — 스팀 창작마당(Workshop) 또는 홍달 서버 | 원격 | 1.0 뒤. 운영(신고 · 관리) 체계가 먼저다 |

- 세 겹 모두 **같은 카드 꼴**을 쓴다. ①에서 만든 카드가 그대로 ② · ③으로 나간다 — 처음부터 꼴을 하나로 정하는 까닭이다.
- 게임 속 인물이 만드는 카드(①)는 규칙이 만든다: 매장의 업종 · 동네 성격(타일 성격)에 맞춰 배치 몇 벌 · 상품 몇 벌을 고르고 조금씩 바꿔 내놓는다. 「번화가 타일의 카페는 좌석을 줄이고 픽업대를 앞으로」 같은 유행이 생긴다.

## 6. 지도와 묶기

- 카드의 `where`로 지도에 꽂는다. **구 지도:** 역 창에 「이 역 둘레에서 나온 카드 n장」. **타일 지도:** 타일 그릇 창에 「나눔」 줄(그 칸의 상품 · 공간 카드 수와 많이 쓰인 것). **동 디오라마(2.0):** 그 건물을 누르면 그 매장의 공간 카드가 3D로 열린다.
- 계보는 지도 위 빛의 줄로 보일 수 있다 — A 역의 배치를 B 역 매장이 가져다 쓰면 두 역 사이에 가는 빛이 한 번 흐른다(명덕 빛과 같은 말씨, 가안).

## 7. 게임 규칙과의 이음 (가안 · 정할 것)

- **나눔은 손해가 아니다:** 내 카드를 누가 가져다 쓰면 내 매장의 「알려짐」이 오른다(플레이스 자연 순위 r238의 한 점수 칸). 광고(r326 · r327)는 돈으로 위에 서는 것, 나눔은 쓰여서 알려지는 것 — 두 길을 나란히 둔다.
- **공간 카드의 숫자가 경영에 닿는다:** 픽업까지 걸음 수 → 제조 · 대기 시간, 좌석 수 → 매장 안 손님 수. 그래서 좋은 배치를 찾아 가져다 쓰는 일이 실제로 이득이 된다.
- **명덕과의 관계:** 남에게 쓰인 카드 한 장을 「닫힌 생명주기 한 건」처럼 셀지 — 지금 정한 「주문 한 건마다 빛」과 섞이지 않게 따로 둘지는 뒤에 정한다.

## 8. 지킬 선

1. **실제 상호 · 로고 · 사람 이름 · 실제 주소는 카드에 못 들어간다.** 내놓기 전에 이름 거르개(실제 상호 목록 · 브랜드 낱말 · 전화 · 주소 꼴)를 지난다. 걸리면 「게임 이름으로 바꿔 주세요」.
2. **자료 권리:** 카드는 게임이 만든 값과 출처 표시가 되는 공개 자료만 담는다. 주소기반 원문 · 건물 원천 · 개인 배달 기록에서 나온 값은 `visibility`가 `game`을 넘지 못한다(파일 · 온라인으로 못 나감).
3. **가져가 고친 것은 계보를 지운 채 내놓을 수 없다.** 원작자 이름(게임 이름)은 따라간다.
4. **③ 온라인은 신고 · 숨김 · 관리자 검토가 먼저다.** 그 체계 없이 공개 공유를 열지 않는다.
5. 공유는 **안 해도 된다.** 플레이를 강요하지 않는다(r328).

## 9. 만드는 길

| 걸음 | 무엇 | 크기 | 메모 |
| --- | --- | --- | --- |
| **N0** 카드 꼴 v1 ✅ 11-23 | 3절을 JSON 스키마로 굳힌다(`hongdal-card.v1`) + 검사(이름 거르개 · 권리 · 계보) — 순수 규칙 · Kernel 검사 | 소 | 다른 걸음이 다 기대는 바탕 |
| **N1** 게임 안 저장소 | 세이브 안의 카드 저장소 · 지금 매장(카페 1호점)과 메뉴 팩에서 상품 카드 · 장소 카드를 자동 생성 | 소 ~ 중 | 플레이스 시험 자료를 카드로 옮겨 읽는다 |
| **N2** 「나눔」 탭 | 플레이스 앱 판에 탭 하나: 카드 목록 · 카드 보기 · 계보 줄 · 질문/답(읽기 먼저) | 중 | 주문자 뷰의 짜임을 그대로 쓴다 |
| **N3** 공간 카드 | 실내 배치 꼴 + 평면 썸네일 + 자동 셈(넓이 · 좌석 · 걸음 수) · 카페 1호점 한 벌과 변형 두 벌 | 중 | 편집기는 처음엔 「부품 몇 개 옮기기」만 |
| **N4** 게임 속 인물의 나눔 | 규칙이 카드를 내놓고 가져다 쓴다(타일 성격 · 업종) → 동네 유행 | 중 | 관찰 모드에서 보이는 재미 |
| **N5** 파일로 나누기 | `.hongdal-card` 내보내기 · 가져오기 · 지문 · 계보 확인 | 소 ~ 중 | 1.0에 넣을 수 있는 공유 |
| **N6** 지도에 꽂기 | 역 창 · 타일 그릇 창에 「나눔」 줄, 계보 빛 | 소 | 타일 지도와 바로 이어짐 |
| **N7** 온라인 조사 | 스팀 창작마당 조건 · 운영 체계 · 신고 흐름 조사 → 사용자 판단 | 소(조사) | 구현은 그 뒤 |

- 차례: N0 → N1 → N2 → N3 → N6 → N5 → N4 → N7. N0 ~ N2는 지금 플레이스 코드 위에서 바로 된다.

## 12. Codex 정렬 · N0 구현 (2026-11-23 10:07)

사용자: 「현재 Codex도 그러한 방향으로 가고 있으니까 그것에 맞춰서 계속 작업이 진행이 됐으면 좋겠네.」

Codex는 같은 날 `hongdal-diorama-product-catalog-20261123/share-r1/scene-share.js`로 **`hongdal-card.v1`을 먼저 좁게 굳혀 두었다**(상품 · 공간 두 갈래, 로컬 파일 나눔만). 3절의 넓은 껍데기는 가안으로 두고, **게임은 Codex가 정한 좁은 판을 그대로 따른다.** 넓히는 일은 두 쪽을 함께 바꿀 때만 한다.

### 12.1 지금 판(v1 · local-slot-review)의 꼴 — Codex 그대로

| 칸 | 지금 판에서 받는 값 | 3절 가안과의 차이 |
| --- | --- | --- |

| `revision` | 1 이상 정수 | 같음 |

- `color`: 상의(`body`)만 `#RRGGBB`, 소문자로 맞춤.

### 12.3 Codex 조립 엔진과의 이음 (다음 걸음의 뼈대)

- **공간 카드 = 칸 고르기의 묶음.** 지금 `body.items`는 Codex 카탈로그(`catalogPack`)의 칸(slot)별 선택이다. `docs/Architecture/상품관측기반실내공간조립엔진.md`의 Zone/Fixture/Surface/Slot이 커지면, 공간 카드의 다음 `profile`은 `InteriorPlanHandle`(판본 고정) 하나를 가리키게 한다 — 카드가 배치를 통째로 싣지 않고 **판본이 고정된 계획을 가리킨다.**
- **상품 카드 = 카탈로그 한 줄의 가리킴.** 원가 · 재료(3.2절)는 카드에 싣지 않고 받는 쪽이 자기 `catalogPack`에서 다시 읽는다. 받는 쪽 목록에 없으면 「자료 미확인」으로 칸 이름만 보인다(share-r1 `readShare`의 fallback과 같음).
- **N1(게임 안 저장소)** 은 Codex 카탈로그 · 꾸미기 저장과 겹치므로 **Codex의 세이브 꼴이 정해진 뒤** 그 위에 카드 목록만 얹는다. 그 전에는 게임이 `.hongdal-card` 파일을 읽어 보이는 N5(파일 나누기)를 먼저 하는 편이 겹침이 적다 — 차례를 N0 → N5(읽기) → N2 → N1로 바꾸는 것을 제안한다(정할 것).

### 12.4 정할 것 하나
- 차례: Codex 세이브 꼴을 기다리는 동안 **게임이 `.hongdal-card` 파일을 읽어 보여 주는 것(N5 읽기)** 을 먼저 할지.
