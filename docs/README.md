## 게임 개발 업무 순서

게임 개발과 리팩토링이 공통으로 보존할 기준은 [프로젝트 불변 개발 골격](Architecture/프로젝트불변개발골격.md)에 둔다. 파일·모듈·표현은 바꿀 수 있지만 권위·공통 Core·명령·시간·E/G/H·공간 성장·단일 공식 Scene·호환 경계를 바꾸려면 새 확정 결정과 호환 근거가 필요하다.

Simulation·Unity 게임 작업은 [플레이어 중심 게임 개발 업무 구조](Architecture/플레이어중심게임개발업무구조.md)에 따라 플레이어가 보는 상황·욕구·선택·재료·조립·결과·다음 선택을 먼저 닫고, [플레이 폐루프와 증거 묶음 개발 체계](Architecture/플레이폐루프와증거묶음개발체계.md)로 여러 WI의 귀환 폐루프와 실제 증거 범위·무효화·협업 인계를 기록한다. 각 폐루프는 [논리·표현·결과 순환 개발 방법론](Architecture/플레이폐루프논리시각이중순환체계.md)에 따라 논리와 표현을 각각 하향 검토·상향 검증하고 결과·귀환 관문에서 통합하며, [엔진 상호작용 검증 체계](Architecture/플레이폐루프엔진상호작용검증체계.md)로 WI 권위 실행과 LH·Sky·실내외 표현이 같은 명령·Revision을 설명하는지 확인한다. 이 왕복은 E8 개별 안정성과 E9 영역 조화·사람 승인에서도 유지되고 E10만 불변 후보의 제한 운영 통합 관문이다. 표현 궤적의 공통·조건 검사는 [표현 검증 모듈 상태판](AI/generated/playable-loop-presentation-validation.md)에서 확인한다. 현재 영역별 Core·Extension과 실제 완결 순서는 [플레이 폐루프 완결 로드맵](Architecture/플레이폐루프완결로드맵.md)에서 확인한다. 새 작업은 [게임 개발 작업 단위 템플릿](ProjectOverview/templates/게임개발작업단위템플릿.md)에 PlayableLoop, 논리·표현 현재 E, 결과·귀환 조건, WI·H, 권위 소유자, 협업·인계와 검증 범위를 기록한다.

## 문서 유형

### 기준 문서

현재 판단의 단일 기준이다. 동일한 정책이나 로드맵을 설명하는 새 문서를 만들기 전에 기존 기준 문서에 절을 추가한다.

### 제안서와 구현 계획

아직 확정되지 않은 선택지, 단계별 구현안과 검증 계획을 기록한다. 문서 첫부분에 어떤 기준 문서를 따르는지와 무엇을 결정하지 않는지를 적는다.

### 변경 기록과 페이지 증빙

특정 시점에 무엇이 바뀌었고 무엇을 검증했는지 남기는 기록이다. 현재 코드와 달라질 수 있으므로 삭제하거나 기준 문서에 합치지 않는다. 현재 상태를 판단할 때는 실제 route, contract, test와 기준 문서를 함께 확인한다.

## 새 문서 작성 기준

1. 먼저 이 문서와 대상 폴더의 `README.md`에서 같은 책임의 기준 문서를 찾는다.
2. 기존 기준을 보완할 수 있으면 새 문서를 만들지 않고 해당 절을 갱신한다.
3. 별도 제안서가 필요하면 기준 문서와의 책임 차이, 확정되지 않은 범위와 종료 조건을 명시한다.
4. 파일을 대체할 때는 기존 경로를 바로 삭제하지 않고 짧은 호환 안내를 남긴다.
5. 변경 기록과 페이지별 캡처 증빙은 중복처럼 보여도 이력 추적을 위해 보존한다.
6. 문서 링크와 `git diff --check`를 검증하고, 코드 상태를 문서만으로 완료했다고 표현하지 않는다.
