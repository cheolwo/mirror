# Azure·모바일 연결 보완과 검증 현황

2026-10-04. 이 문서는 [연결 준비 조사](AzureMobileReadinessAudit-20261004.md)에서 확인한 공백을 현재 소스로 보완한 내용과 실행 증거의 경계를 연결한다. 기존 조사 문서는 당시 읽기 전용 기준선으로 보존한다. 이번 구현은 그 조사 이후의 미커밋 변경을 포함하므로 HEAD만 배포한 판본과 같다고 볼 수 없다.

**최신 전수 시험 6,975건과 같은 주문의 네 역할 실제 Debug APK 업무 완주를 확인했다. 내부 시험 Release 7개도 패키지·다운로드·에뮬레이터 설치/시작을 확인했다. 공개 Azure 서버와 개인 휴대폰 통신은 아직 확인하지 않았다.** 관찰 재탐색·추천 만료 회귀 4건·Debug 7개 검사·실제 음식점 응답 유실 복구와 DB 복원을 확인했다. 기사 도착 응답 유실·재시작 후 정본 복구도 실제 proxy/UI/DB 15조건으로 확인했다. 이후 기사 완료 상세·통신 복구 보완은 새 서버·기사 APK에서 실제 화면 및 DB 근거를 대조했다. 최신 기사 APK의 추가 주문은 수령까지 UI에서 진행했고 DB 19조건과 Admin 5단계 완료도 확인했다. Release는 기존 성공 2개 재사용과 후속 5개 새 빌드이며 시험 서명·접속 불가 주소를 사용한다. 업무 완료는 공제 확정·지급 요청·실입금 완료와 구별한다.

사용자의 최신 범위는 휴대폰이 없더라도 가능한 소스·HTTP 계약·DB 왕복·도구 보호 조건·APK 구조·에뮬레이터 화면을 최대한 확인하는 것이다. 실제 개인 휴대폰 설치·절전·잠금·Wi-Fi/모바일 데이터와 공개 HTTPS가 필요한 확인을 로컬 표본 성공으로 대체하지 않는다. 지도·Unity·실결제·실입금은 이번 검증의 필수 범위를 확대하지 않는다.

## 복구·인증·알림 보완의 의미

음식점과 기사 미확정 요청은 저장 완료 후 전송하며, 앱 재시작 후 같은 계정의 정본을 먼저 읽는다. 응답 유실 뒤 사용자가 같은 작업을 명시 재시도할 때만 원래 ID·payload·revision을 보낸다. 저장/복원/삭제 실패는 성공이나 빈 초기 상태로 숨기지 않는다. 전체 주문 객체·고객 주소·연락처를 pending 저장소에 넣지 않는다. 음식점은 아래 실제 APK 응답 유실·재시작·GET 복구 표본까지 확인했다. 이는 UI·프록시 요청 수·서버 DB 정본을 결합한 증거이며 장치 내부 SecureStorage/request ID를 직접 열람한 결과는 아니다. 기사의 응답 유실·재시작 복구도 아래 별도 표본으로 확인했으며, 개인 휴대폰 검증은 남아 있다.

공통 인증은 시간 경과와 세션 mutation 순서를 확인한다. 이전 계정의 늦은 갱신 거절을 역할 wrapper가 다시 무조건 Clear하던 경계를 제거하고, GET 401 재조회에도 원 owner를 결속한다. 보호 본문 생성이 지연되는 경우에는 실제 전송 직전에도 owner를 재확인한다. 오류로 새 계정의 세션을 지우거나 이전 쓰기를 새 토큰으로 자동 반복하지 않아야 한다. 관련 소스 검토는 `artifacts/local/azure-mobile-hardening-r1/root-review.md`에 보존한다. 기존 계약·인증 필터 117건과 통합 Fast 495건을 확인했고, 음식점 최종 401의 화면 자체 취소 후 세션 정리·종료 이벤트 중 계정 변경을 추가한 필터 87건과 최신 전수 6,975건도 통과했다. 모든 역할의 실제 장치 복귀는 별도 경계로 남긴다.

음식 기사 Push의 선택적 Android 구성은 외부 음식 앱용 Firebase 설정 경로가 있을 때만 켜진다. 화물 앱 파일을 자동 재사용하지 않는다. 설정 부재는 전경 조회·앱 복귀로 안내한다. 서버 Push payload는 음식 AppKey/기사/의뢰/만료의 최소 식별자만 보내며 고객·주소·메뉴·메모를 넣지 않는다. **Firebase 설정과 서비스 계정이 현재 제공되지 않아 실제 FCM 발송·잠금 수신은 미검증**이다. 현재 단일 토큰 Port의 최근 활성 설치 선택은 여러 기기 fanout 보장을 뜻하지 않는다.

독립 검토의 F1/F2는 현재 소스에 반영했다. [Firebase 수신 콜백](../../FDriverApp/Platforms/Android/FDriverFirebaseMessagingService.cs)은 로컬 owner·만료 확인과 일반 알림 게시를 최대 3초 안에 기다리고, 시간 초과 시 취소한다. 새 토큰 콜백은 로컬 보존만 수행하며 서버 등록은 전경 경로에서 진행한다. Android 알림 권한·앱 전체 알림·음식 알림 채널이 꺼진 상태를 서버 설치 등록 성공과 구별해 안내한다. Fast에서 음식 Push 순수 시험 21건을 확인했다. 외부 설정을 만들지 않는 최종 독립 컴파일은 Android C# 조건 분기 활성화·실제 GoogleServicesJson 항목 0·오류 0·종료 코드 0을 확인했다. 이전 helper의 MSBuild 검사식 오류와 동시 APK 변경 검사 실패 기록은 보존한다. 컴파일 전후 제품 소스·원 APK·복사한 지도 binding 해시는 같고 APK를 생성하거나 실행하지 않았다. 이 결과는 Firebase 설정을 포함한 운영 APK나 실제 Push 수신 증거가 아니다. 근거는 `food-push/implementation-notes.md`, `conditional-compile.md`와 아래 실행 표다.

최초 Task의 실패는 `FoodDeliveryV30PageCompositionTests.음식점진행변경은_같은멱등요청을한번재시도하고_판본충돌시정본을재조회한다`, `RestaurantAuthRecoveryTests.ForcedRefreshWithUnusableCachedSessionRequiresLoginWithoutRedirectLoop(kind: missing-user, clearFails: false)`, `RestaurantMenuSessionRecoveryTests.RealClientFinal401SharesSessionEndWithMenuAndPreservesRequest`였다. 진행 요청 시험은 자동 POST 재시도를 기대하던 이전 계약을 원 요청 영속 보존·정본 확인·사용자 명시 재시도로 갱신했고, 사용자 ID 없는 캐시는 Anonymous 정책으로 확인한다. 최종 401은 화면의 SessionEnding 구독자가 요청 수명을 취소한 뒤에도 확인된 세션을 revision 조건으로 정리하도록 고쳤다. 이때 새 계정이 생기면 삭제하지 않으며, 거절 확인 전 요청 취소는 세션을 보존한다. 원본과 최초 실패 로그를 보존했고 신규 인증 회귀 3건을 포함한 87건 필터와 최신 전수 6,975건은 모두 통과했다.

Admin 신규 시험은 State 17, List 13, Client 8, 구성 신규 1이며 기존 검토 상태를 공용으로 옮긴 시험도 함께 확인했다. 실제 discovery에 신규 39건이 있고 지정 필터의 기존 시험을 포함한 84건 모두 통과했다. 사용 DLL SHA-256은 `3B4483F26E0A650FC82C0CD6A24F67DCC31EC1FC5D1A296E69DAD3B0A954E6D3`다. `artifacts/local/azure-mobile-hardening-r1/admin/ui-validation-plan.md`와 `prepare-admin-ui.cjs`는 합성 주문의 읽기 전용 화면 확인 준비 도구이고 APK 조작 완료 기록은 아니다.

정상 E2E의 정산 표본은 세전 2,500원·모의 공제 100원·모의 지급 2,400원이며 `SimulationFixture`다. 재조리 E2E도 실제 송금이 아니다. 경로 가격은 0.250km의 `FoodObserverSimulationRouteFixture`로 실제 지도 API 요청이 없다. 실제 네 APK UI 주문 `FOOD-20261004115530941`의 DB 대조 시각은 2026-10-04 12:49:17 UTC다. 현재 주문은 수령확인, 배차 큐는 종료, 기사 완료 시도와 동결 정산 원장은 각각 1개다. 과거 30분 조리시간 변경은 같은 요청 ID로 이력 1개가 보존되어 있고, 이후 조리·준비 완료 상태에서 현재 적용 조리분은 0이다. 초기 선택 20분·과거 변경 30분·준비 완료의 현재 값 0을 같은 의미로 덮어쓰지 않는다. 정산은 세전 2,500원만 동결되었으며 `AwaitingDeductions`/`NotRequested`, 공제·수령액 NULL·실제 공제 근거 없음·지급 요청/outbox 0이다. 호스트는 Development/Simulation이지만 이 정산 원장의 저장 실행모드는 아직 빈 값이므로 저장된 Simulation 지급 기록으로 만들지 않는다. 추천 알림은 시도 0의 Pending, 수령 후 세계 projection도 시도 0의 Pending이다. 이는 실제 FCM·Unity 게시·실제 현금 결제·은행 입금 또는 외부 네트워크 전수 검증이 아니다.
